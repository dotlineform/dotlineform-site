# Docs Viewer Development

Docs Viewer owns the shared document reader, local authoring and package review services, builders, and checked configuration. This directory contains code; the configured external Docs workspace contains canonical document input, replaceable Working output, media, and one read-only Preview snapshot. Durable development documentation lives in [documentation/studio](../documentation/studio/).

## Repository structure

| Path | Responsibility |
| --- | --- |
| `bin/docs-viewer` | Launcher for the local Docs Viewer service. |
| `build/` | Document and Search entrypoints, the controlled Preview builder, Catalogue document-design maintenance, and focused `docs_builder/` modules. |
| `config/` | Workspace registration and destinations, route/report registries, service defaults, generated browser defaults, document-package profiles, and shared semantic-token definitions. |
| `runtime/` | Shared reader and route-specific JavaScript, local management/Review/import/package modules, and vendor dependencies. |
| `services/` | Loopback HTTP service, exact Working reads/writes, imports and packages, media handling, Preview preparation, and publication/distribution. |
| `shell/` | Local Manage and Docs Review HTML shells. |
| `static/` | Canonical shared/public and local-only stylesheets and icons. |
| `templates/` | Public-route shell template. |
| `tests/` | Existing checks and fixtures, subject to the maintained test policy. |

Shared/public runtime assets are canonical here and have a tracked public subset under `site/docs-viewer/`. [site-tools/config/site-code-update.json](../site-tools/config/site-code-update.json) is the sole inventory for that projection. Management and other local-only files stay outside it. Repository lint tooling lives in `tooling/lint/` and is invoked through `bin/lint`, `bin/lint-python`, or `bin/lint-js`.

The configuration owners are explained in [Configuration And Extension Points](../documentation/studio/Configuration_And_Extension_Points.md). Browser defaults are generated by `build/docs_builder/browser_config.py`; edit workspace configuration rather than those projections. `config/defaults/docs-viewer-service.json` contains only capability defaults. `config/semantic-tokens/registry.json` shares family, target and identity definitions between Python and the Source editor; executable token and UI behavior stays in code.

## Workspace and local surfaces

[config/workspace/docs-workspace.json](config/workspace/docs-workspace.json), using `docs_workspace_v5`, is the storage authority. Set `DOTLINEFORM_DOCS_BASE_DIR` in `.env.local` to the existing Docs workspace root directly. `DOTLINEFORM_PROJECTS_BASE_DIR` independently selects project/media and document-package storage; neither setting is an alias or fallback for the other.

The principal layout is:

```text
$DOTLINEFORM_DOCS_BASE_DIR/
├── working/
│   ├── source/
│   │   ├── documents/
│   │   ├── media/build-source/mermaid/
│   │   └── collections/<collection>/
│   │       ├── documents/
│   │       └── media/build-source/mermaid/
│   ├── generated/
│   │   ├── documents/
│   │   ├── search/index.json
│   │   ├── collections/<collection>/documents/
│   │   ├── catalogue/
│   │   └── reports/
│   ├── assets/works/
│   ├── catalogue-updates-pending.json
│   └── catalogue-publish-pending.json
├── preview/
│   ├── documents/
│   ├── search/index.json
│   ├── collections/<collection>/documents/
│   ├── catalogue/
│   ├── assets/works/
│   └── preview-manifest.json
└── assets/media/
    ├── workspace/
    └── collections/<collection>/
```

Working owns authoring and generated local reads. Ordinary hierarchy and sibling order come from `working/source/documents/index-order.json`; named collections have flat document ownership and exact configured report hosts. Shared document assets contain the configured media types; registered producer inputs remain with their Working source owner. Working and Preview retain separate Work assets. Preview has no persistent source/generated tree or browser route. [Source Organisation](../documentation/studio/Source_Organisation.md) owns the exact document, collection and media boundaries.

Unavailable external storage fails visibly without creating a replacement root. Empty standard directories may be retained. To relocate the workspace, stop the local services, move the complete workspace including shared assets, update the environment setting, verify the configured locations, and restart. Do not use generated or Preview output as canonical source.

Run project commands from the repository root:

```bash
docs-viewer/bin/docs-viewer
```

The loopback service reads `.env.local` and serves Manage at `/docs/` and enabled package review at `/docs-review/`. Docs Review reads validated package content; applying returned content belongs to an explicit Import operation. Local API targets contain an exact `doc_id` and, for a named owner, `collection`; the service resolves Working without caller-selected stages. Public `/analysis/` uses static repository output and no local write services. Use `bin/local-studio` for Studio and `bin/site-preview` for the public artifact.

## Authoring and builds

Application Source Save awaits validated source persistence, exact document/Links generation, and fresh display before completing. The filesystem watcher and browser refresh timer are retired. Ordinary saves and exact-document Rebuild do not regenerate Search or registered media. Links maintenance belongs directly to Working document builds.

For a deliberate external Markdown edit, edit the canonical Working file and explicitly rebuild its exact document IDs. Supply the intended `last_updated` timestamp for a body, Title or Summary change; Rebuild does not infer it from filesystem edit time. Add `--collection` for a configured named owner:

```bash
python3 docs-viewer/build/build_docs.py --stage working --only-doc-ids <comma-separated-doc-ids> --skip-media-builds --write
python3 docs-viewer/build/build_docs.py --stage working --collection <collection-id> --only-doc-ids <comma-separated-doc-ids> --skip-media-builds --write
```

Targeted builds merge saved metadata and preserve unselected payloads. Full document builds are for intentional reconciliation, missing targeted prerequisites, or a global builder/configuration change. Use `--skip-media-builds` for docs-only reconciliation; registered media production belongs to an explicitly selected full build or publication preparation. Commands default to dry-run without `--write`; Document Build's `--diagnostics` adds machine-readable output.

Search has one explicit whole-index rebuild:

```bash
python3 docs-viewer/build/build_search.py --stage working --write
```

Run it only when Search is the task or a Search rebuild is explicitly requested. The Manage **Rebuild docs and Search** action handles infrequent persistent-media source changes. Recents refreshes during a full Working Build or Publish; ordinary targeted edits preserve its saved output.

Build commands accept independent `--docs-base-dir` and `--projects-base-dir` overrides after loading `.env.local`. Controlled Preview builds require explicit isolated temporary inputs and are normally owned by Publish. [Builder](../documentation/studio/Builder.md) owns orchestration; [Runtime](../documentation/studio/Docs_Viewer_Runtime.md#source-editing-and-save) owns awaited Save and display behavior.

## Catalogue and publication

Catalogue authoring uses its own Save → Refresh → Regenerate → Publish owners. Refresh produces selected Catalogue consumer JSON and private report inputs; Regenerate updates queued Work documents. Missing or malformed private queues stop the operation. [Catalogue Save And Refresh](../documentation/studio/Catalogue_Save_And_Refresh.md) and [Catalogue Deployment](../documentation/studio/Catalogue_Deployment.md) own the incremental contract.

Manage exposes one awaited Publish action, backed by an empty-object `/docs/publish` request. It completes queued Catalogue Work publication, captures eligible Working input, builds ordinary and other collection documents in temporary storage while retaining completed Catalogue documents, validates/replaces Preview, and distributes that same completed snapshot to configured repository/R2 destinations. There is no stage selector, separate preparation/distribution action, or intermediate confirmation.

Ordinary and other collection documents require explicit boolean `draft`; Catalogue documents reject that field and have fixed eligibility. Draft and ordinary `working/source/documents/unpublishable.json` exclusions include descendants; excluding a collection host excludes its collection. All downstream document consumers receive the same prepared set.

Publish copies the existing valid Working Search index byte-for-byte without rebuilding it or requiring freshness after an ordinary edit. Preparation failure prevents shared distribution; completed earlier Catalogue Work effects remain. Failure before Preview replacement preserves the previous snapshot; replacement failure leaves no valid receipt. Distribution failure retains completed Preview and reports incomplete publication. Fix the reported cause and rerun Publish; do not add automatic retries, backup trees, or separate distribution recovery actions.

Review repository output through `bin/site-preview`. Git commit and push are explicit separate actions. Deploy Public is the manually triggered GitHub Pages workflow over the committed `site/` artifact, with no deploy-time build or external-workspace access. The inactive historical publication-lineage workflows are retired.

## Development checks

Use [Development Checklist](../documentation/studio/Development_Checklist.md) for implementation guardrails and [Testing](../documentation/studio/Testing.md) for selecting proportionate evidence. Test creation or changes require a separately agreed specification. Historical scope-bearing tests remain unreviewed for the current workspace; a profile name or old pass result does not establish current coverage.

When a changed canonical public asset is represented in the projection inventory, run:

```bash
bin/site-code-update
bin/site-code-update --check
bin/site-validate
```

Inspect the exact tracked `site/` delta before committing. Repository development-document edits are maintained directly in `documentation/studio/` and do not require Docs or Search generation. Recover source and code through their maintained owners and Git history, then rerun the owning Build or Publish operation.
