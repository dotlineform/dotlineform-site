# Docs Viewer Development

Docs Viewer owns the shared document reader, local authoring and package review services, builders, and checked configuration. This directory contains code; the configured external Docs workspace contains canonical document input, replaceable Working output, media, and one read-only Preview snapshot. Current system documentation lives in [Reference](../documentation/reference/Source_Tree_Ownership.md); live implementation/review guidance lives in [Development](../documentation/development/README.md).

## Repository structure

| Path | Responsibility |
| --- | --- |
| `bin/docs-viewer` | Launcher for the local Docs Viewer service. |
| `build/` | Document and Search entrypoints, the controlled Preview builder, Catalogue document-design maintenance, and focused `docs_builder/` modules. |
| `config/` | Workspace registration and destinations, route/report registries, service defaults, generated browser defaults, document-package profiles, and shared semantic-token definitions. |
| `runtime/` | Shared reader and route-specific JavaScript, local management/Review/import/package modules, and vendor dependencies. |
| `services/` | Loopback HTTP service, exact Working reads/writes, imports and packages, media handling, Preview preparation, and publication/distribution. |
| `shell/` | Local Manage and Docs Review HTML shells. |
| `static/` | Canonical shared/public and local-only stylesheets and icons. |
| `templates/` | Public-route shell template. |
| `tests/` | Existing checks and fixtures, subject to the maintained test policy. |

Shared/public runtime assets are canonical here and have a tracked public subset under `site/docs-viewer/`. [site-tools/config/site-code-update.json](../site-tools/config/site-code-update.json) is the sole inventory for that projection. Management and other local-only files stay outside it. Repository lint tooling lives in `tooling/lint/` and is invoked through `bin/lint`, `bin/lint-python`, or `bin/lint-js`.

The configuration owners are explained in [Configuration And Extension Points](../documentation/reference/Configuration_And_Extension_Points.md). Browser defaults are generated by `build/docs_builder/browser_config.py`; edit workspace configuration rather than those projections. `config/defaults/docs-viewer-service.json` contains only capability defaults. `config/semantic-tokens/registry.json` shares family, target and identity definitions between Python and the Source editor; executable token and UI behavior stays in code.

## Workspace and local surfaces

[config/workspace/docs-workspace.json](config/workspace/docs-workspace.json), using `docs_workspace_v10`, is the storage authority. Set `DOTLINEFORM_DOCS_BASE_DIR` in `.env.local` to the existing Docs workspace root directly. `DOTLINEFORM_PROJECTS_BASE_DIR` independently selects project/media and document-package storage; neither setting is an alias or fallback for the other.

The principal layout is:

```text
$DOTLINEFORM_DOCS_BASE_DIR/
├── working/
│   ├── source/
│   │   ├── index-order.json
│   │   ├── recent-exclusions.json
│   │   ├── selected.json
│   │   ├── unpublishable.json
│   │   ├── documents/
│   │   └── collections/<collection>/documents/
│   ├── generated/
│   │   ├── documents/
│   │   ├── search/index.json
│   │   ├── collections/<collection>/documents/
│   │   ├── catalogue/
│   │   └── reports/
│   ├── assets/
│   │   ├── media/{workspace,collections/<collection>}/
│   │   └── works/
│   ├── docs-publish-pending.json
│   ├── catalogue-updates-pending.json
│   └── catalogue-publish-pending.json
└── preview/
    ├── documents/
    ├── search/index.json
    ├── collections/<collection>/documents/
    ├── catalogue/
    └── assets/
        ├── media/{workspace,collections/<collection>}/
        └── works/
```

Working owns authoring and generated local reads. Ordinary hierarchy and sibling order come from `working/source/index-order.json`; its leaf records omit `children`, and branches carry nonempty child arrays. Named collections have flat document ownership and exact configured report hosts. Working and Preview retain separate document-media and Work assets. Registered producer inputs remain with their Working source owner. Preview has no persistent source/generated tree or browser route. [Source Organisation](../documentation/reference/Source_Organisation.md) owns the exact document, collection and media boundaries.

Unavailable external storage fails visibly without creating a replacement root. Empty standard directories may be retained. To relocate the workspace, stop the local services, move the complete workspace including shared assets, update the environment setting, verify the configured locations, and restart. Do not use generated or Preview output as canonical source.

Run project commands from the repository root:

```bash
set -a
. ./.env.local
set +a
docs-viewer/bin/docs-viewer
```

Exporting the file supplies workspace roots to the process. The service reads its binding and capability settings and serves Manage at `/docs/` and enabled package review at `/docs-review/`. Docs Review reads validated package content, and applying returned content belongs to an explicit Import operation. Local API targets contain an exact `doc_id` and, for a named owner, `collection`. The service resolves Working. Public `/` uses static repository output. Use `bin/local-studio` for Studio and `bin/site-preview` for the public artifact. [Environment and local recovery](../documentation/reference/Local_Setup.md)

## Authoring and builds

Application Source Save awaits validated source persistence, exact document/Links generation, and fresh display before completing. The filesystem watcher and browser refresh timer are retired. Ordinary saves and exact-document Rebuild do not regenerate Search or registered media. Links maintenance belongs directly to Working document builds.

For a deliberate external Markdown edit, edit the canonical Working file and explicitly rebuild its exact document IDs. Supply the intended `last_updated` timestamp for a body, Title or Summary change; Rebuild does not infer it from filesystem edit time. Add `--collection` for a configured named owner:

```bash
python3 docs-viewer/build/build_docs.py --stage working --only-doc-ids <comma-separated-doc-ids> --skip-media-builds --write
python3 docs-viewer/build/build_docs.py --stage working --collection <collection-id> --only-doc-ids <comma-separated-doc-ids> --skip-media-builds --write
```

Targeted builds merge saved metadata and preserve unselected payloads. Full document builds are for intentional reconciliation, missing targeted prerequisites, or a global builder/configuration change. Use `--skip-media-builds` for docs-only reconciliation; registered media production belongs to an explicitly selected full build or publication preparation. Commands default to dry-run without `--write`; Document Build's `--diagnostics` adds machine-readable output.

Search has one explicit whole-index rebuild:

```bash
python3 docs-viewer/build/build_search.py --stage working --write
```

Run it only when Search is the task or a Search rebuild is explicitly requested. Manage **Refresh Search and Recent** updates both discovery files without document rendering or media production. Only changed files join the Publish queue; ordinary targeted edits preserve saved discovery output.

Full Working Rebuild is explicit maintenance for broad renderer/configuration/policy changes, persistent-media edits or reconciliation:

```bash
python3 docs-viewer/build/rebuild_working.py --write
```

This command requires `--write` and has no dry-run mode. It regenerates ordinary/non-Catalogue documents and referenced media, exact dependencies, Selected, Search and Recent. It queues changed output and media-only changes, preserving existing pending selections. Catalogue Regenerate retains its own generation and Work publication owner. Reload the reader after maintenance to display its results.

Build commands accept independent `--docs-base-dir` and `--projects-base-dir` overrides after loading `.env.local`. Preview receives selected finished artifacts through Publish and has no document builder. [Builder](../documentation/reference/Builder.md) owns orchestration; [Runtime](../documentation/reference/Docs_Viewer_Runtime.md#source-editing-and-save) owns awaited Save and display behavior.

## Catalogue and publication

Catalogue authoring uses its own Save → Refresh → Regenerate → Publish owners. Refresh produces selected Catalogue consumer JSON and private report inputs; Regenerate updates queued Work documents. Missing or malformed private queues stop the operation. [Catalogue Save And Refresh](../documentation/reference/Catalogue_Save_And_Refresh.md) and [Catalogue publication](../documentation/reference/Catalogue_Save_And_Refresh.md#per-work-publish) own the incremental contract.

Manage exposes one awaited Publish action, backed by an empty-object `/docs/publish` request. Working operations prepare the finished files and removal selections upstream. Publish consumes those exact Docs and Catalogue queue units, transfers them through Preview to configured destinations, verifies selected transfers and removes successful units. [Generation and publication owners](../documentation/reference/Builder.md#publish-preparation)

Ordinary and other collection documents require explicit boolean `draft`; Catalogue documents reject that field and have fixed eligibility. Draft and ordinary `working/source/documents/unpublishable.json` exclusions include descendants; excluding a collection host excludes its collection. All downstream document consumers receive the same prepared set.

Publish copies the existing valid Working Search index byte-for-byte without rebuilding it or requiring freshness after an ordinary edit. Preparation failure prevents shared distribution; completed earlier Catalogue Work effects remain. Failure before Preview replacement preserves the previous snapshot; replacement failure leaves no valid receipt. Distribution failure retains completed Preview and reports incomplete publication. Fix the reported cause and rerun Publish; do not add automatic retries, backup trees, or separate distribution recovery actions.

Review repository output through `bin/site-preview`. Git commit and push are explicit separate actions. Deploy Public is the manually triggered GitHub Pages workflow over the committed `site/` artifact, with no deploy-time build or external-workspace access. The inactive historical publication-lineage workflows are retired.

## Development checks

Use [Development Checklist](../documentation/development/Development_Checklist.md) for implementation guardrails and [Verification](../documentation/development/Verification.md) for selecting proportionate evidence. Automated test scripts/profiles remain suspended pending the [test/check review](../documentation/_working/Review_Test_Policy_And_Checks.md); test changes require separately agreed scope. Historical scope-bearing tests remain unreviewed for the current workspace; a profile name or old pass result does not establish current coverage.

When a changed canonical public asset is represented in the projection inventory, run:

```bash
bin/site-code-update
bin/site-code-update --check
bin/site-validate
```

Inspect the exact tracked `site/` delta before committing. Repository documentation is maintained directly under `documentation/` and requires no Docs or Search generation. Recover source and code through their maintained owners and Git history, then rerun the owning Build or Publish operation.
