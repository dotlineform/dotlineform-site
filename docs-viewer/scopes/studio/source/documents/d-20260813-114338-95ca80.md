# SDM-2 — Documents Linking Here Report

## Complete Result

An ordinary document can host one local report block that lists every other document in the same scope whose rendered link resolves to the exact current `doc_id`. The list is generated from current documents, so it does not require a manually maintained related-documents section.

This delivery begins only after SDM-1 is accepted and closed.

## Report Contract

- register one focused report id, provisionally `docs_backlinks`
- use the loaded report-host document's exact `{scope, doc_id}` as the target
- list one deduplicated row per source document as links, e.g. [Studio Documentation Maintenance](/docs/?scope=studio&doc=d-20260813-114338-c6b682)
- retain deterministic document order and a clear empty state
- ignore same-document fragment links and links inside literal code
- update the generated relationship data during full and targeted Docs builds
- keep the first adopter and executable report local-only

“Static” describes the generated data source. The report still uses the existing one-block, one-inert-host, allowlisted-loader runtime contract; it does not introduce build-time executable Markdown or a second report mechanism.

## Data Boundary

Produce one compact scope-level backlink index from exact rendered document anchors. A targeted build updates the changed document's outgoing-link contribution and regenerates the reverse mapping, so removing or retargeting a link cannot leave a stale incoming row.

Reuse the existing Docs link-resolution rules rather than interpreting Markdown URLs independently. The producer and report must not infer identity from titles, filenames, link labels, selected rows, or browser route state.

## Boundaries

This delivery does not:

- aggregate links from other scopes
- publish the report or its data to a public route
- include external links, media references, parent relationships, or unlinked semantic similarity
- add a graph database, relationship service, API endpoint, generic query layer, or background crawler
- change the one-report-per-document source contract
- add backlinks automatically to every document

Cross-scope or public adoption requires a separate privacy, publication, rebuild, and composition decision.

## Likely Owners

## SDM-2.0 — Review Result

The existing parent-scope Docs build is sufficient. Sub-scope builds use their own pipeline and remain unchanged.

### Exact payload

Write `docs-viewer/scopes/<scope>/published/documents/backlinks.json` with this minimal shape:

```json
{
  "schema": "docs_backlinks_v1",
  "scope": "studio",
  "generated_at": "2026-08-13T14:00:00Z",
  "by_target": {
    "d-target": [
      {
        "doc_id": "d-source",
        "title": "Source document",
        "viewer_url": "/docs/?scope=studio&doc=d-source"
      }
    ]
  }
}
```

Targets with no incoming links are omitted. The report treats an absent key as an empty result. Target keys are serialized deterministically; rows sort by case-insensitive title and then exact `doc_id`.

### Full and targeted builds

The full build derives the reverse mapping from the newly rendered payload for every current document. A targeted build overlays the newly rendered selected payloads on the existing unselected `by-id/<doc_id>.json` payloads, drops documents no longer present in current source, and regenerates the complete reverse mapping. The existing by-id payloads are therefore the unchanged documents' outgoing-link contributions; no second contribution cache is added.

The scope index is part of the normal generated write plan, including stable `generated_at` reuse when its comparable content is unchanged. A targeted link removal or retarget replaces the selected source's old contribution before the reverse mapping is written.

### Shared link resolution

Extract the HTML anchor collector, URL resolution, Docs target parsing, text normalization, and same-document-fragment predicate from `docs_broken_links.py` into one pure `docs_rendered_links.py` service module. Broken Links continues to call that module with the configured viewer routes and known scopes. The backlink producer calls the same parser, accepts only exact viewer targets in the current scope and current document set, excludes the source document itself, and deduplicates `{source_doc_id, target_doc_id}` pairs. Code and `pre` anchors remain excluded by the shared collector.

### Exact report target and local URL

The report selects the exact target only from `context.viewerScope` and `context.payload.doc_id`. It does not read `context.doc`, the route query, a selected row, the title, the filename, or link text. The local browser scope record supplies an explicit `backlinks_url`; public browser records and external-local scope records omit it in this delivery. The focused loader fetches that static URL directly and adds no management-service route.

The first adopter is [Studio Documentation Maintenance](/docs/?scope=studio&doc=d-20260813-114338-c6b682), which already has incoming ordinary-document links. [Report Block Tokens](/docs/?scope=studio&doc=d-20260810-211748-1f8b6f) replaces its stale hand-maintained registry table with the existing registry-backed `reports_list` block rather than adding missing rows manually.
