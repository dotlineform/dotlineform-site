# SDM-2 — Documents Linking Here Report

## Complete Result

An ordinary document can host one local report block that lists every other document in the same scope whose rendered link resolves to the exact current `doc_id`. The list is generated from current documents, so it does not require a manually maintained related-documents section.

This delivery begins only after SDM-1 is accepted and closed.

## Report Contract

- register one focused report id, provisionally `docs_backlinks`
- use the loaded report-host document's exact `{scope, doc_id}` as the target
- list one deduplicated row per source document with its exact title and viewer URL
- retain deterministic document order and a clear empty state
- ignore same-document fragment links and links inside literal code
- update the generated relationship data during full and targeted Docs builds
- keep the first adopter and executable report local-only

“Static” describes the generated data source. The report still uses the existing one-block, one-inert-host, allowlisted-loader runtime contract; it does not introduce build-time executable Markdown or a second report mechanism.

## Data Boundary

Produce one compact scope-level backlink index from exact rendered document anchors. A targeted build updates the changed document's outgoing-link contribution and regenerates the reverse mapping, so removing or retargeting a link cannot leave a stale incoming row.

Reuse the existing Docs link-resolution rules rather than interpreting Markdown URLs independently. The producer and report must not infer identity from titles, filenames, link labels, selected rows, or browser route state.

## Boundaries

This delivery does not:

- aggregate links from other scopes
- publish the report or its data to a public route
- include external links, media references, parent relationships, or unlinked semantic similarity
- add a graph database, relationship service, API endpoint, generic query layer, or background crawler
- change the one-report-per-document source contract
- add backlinks automatically to every document

Cross-scope or public adoption requires a separate privacy, publication, rebuild, and composition decision.

## Likely Owners

- the Docs builder and its generated write plan for the scope-level static index
- the existing pure rendered-anchor and Docs-target parsing seam used by Broken Links
- `docs-viewer/config/reports/reports.json` for local report metadata
- the local report loader allowlist and one focused report module
- focused Python producer/targeted-build tests and narrow JavaScript report tests
- [Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) and [Report Block Tokens](/docs/?scope=studio&doc=d-20260810-211748-1f8b6f) for durable current-state documentation

## SDM-2.0 — Sanity Gate

Before implementation, confirm:

- the exact generated payload path and minimal schema
- how full and targeted builds merge outgoing-link contributions
- the pure link-resolution owner reused by the producer and Broken Links
- the report-host context used to select the current exact target
- the first source document that will adopt the report
- the exact production/test files and rough diff size

Stop for review if the shape requires a general relationship framework, cross-scope coordination, a new service route, or broad report-runtime changes.

## Completion Evidence

- exact same-scope links produce deterministic deduplicated incoming rows
- link removal and retargeting remove stale rows after a targeted build
- titles, filenames, labels, and current UI selection cannot redirect the report target
- code examples, self-fragments, external URLs, and cross-scope links remain outside the first result
- the registered local report renders populated and empty states through the existing host
- focused builder/report tests, relevant lint, Studio docs generation, and `git diff --check` pass
