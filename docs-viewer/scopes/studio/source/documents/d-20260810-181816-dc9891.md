# Catalogue Works Report Migration

## Purpose

Replace the permanent read-only `/studio/studio-works/` route with one local Docs Viewer **Catalogue Works** report. The report remains the complete inspection surface for published canonical Works, but it displays rows only after a search and leaves permanent Studio routes to focused editing and workflow responsibilities.

This feature distinguishes Catalogue Works from the existing local Docs Viewer [Works Report](/docs/?scope=studio&doc=d-20260810-115737-901d0f), whose rows are published Series and whose purpose is Project-document coverage. The new report id is `catalogue_works`; it does not reuse or broaden `works`.

## Current Starting Point

[Catalogue Works](/docs/?scope=studio&doc=d-20260401-000000-ebf14a) owns the current `/studio/studio-works/` route. The route is not server-rendered: its Studio JavaScript loads canonical Works and Series through the Local Studio Catalogue read API, augments storage context, filters to published records, constructs rows, sorts them, and preserves optional Series route state in the browser.

The current page has no ordinary search or filter controls. It renders the complete published list by default, shows only the first value from plural `series_ids`, and its **Copy series** action copies an alphabetical list of published Series titles rather than the current Work table.

[Catalogue Drafts](/docs/?scope=studio&doc=d-20260418-000000-16bf7e) remains a deliberate Studio route. It is a recovery and maintenance workflow for locating draft Works and Series and opening their exact editors. Draft records are not part of Catalogue Works reporting, and this feature does not move or reproduce Catalogue Drafts.

No implementation or delivery is authorised by this feature document.

## Sequence

[Report Blocks](/docs/?scope=studio&doc=d-20260810-180114-003d2a) precedes this feature and supplies the single block-level report-host contract. Catalogue Works then becomes the motivating wide tabular report for [Expanded Report View](/docs/?scope=studio&doc=d-20260810-165949-ee4d35).

The migration must work as an ordinary embedded report before Expanded Report View begins. This feature may declare the report's semantic presentation kind, stable columns, and expanded eligibility, but the expanded presentation and manual column-width behavior remain owned by Expanded Report View.

## Report Contract

- One ordinary document in the `studio` scope hosts the local-only `catalogue_works` report through one Report Block.
- The report population is every exact canonical Work with `status: published`. Draft, malformed, or unknown records do not enter the population and require no status column, cue, or filter.
- The report loads its complete current input but renders no rows for an empty search. There is no initial all-Works table and no implicit **Show all** mode.
- A non-empty search matches normalized Work id, title, and exact Series id or title. Search never infers identity from a partial title match when composing a target.
- Search results contain the current columns **Work**, **Year**, **Title**, **Series**, and **Storage**. Every exact `series_ids` membership is retained and presented; the report does not collapse a Work to its first Series.
- Column headings own accessible sorting for the current search result. Search and sort remain report-owned browser state and use report-prefixed URL parameters if persisted in the route.
- Work and Series links retain exact existing activation targets. The report does not edit catalogue data or reproduce Work or Series editor forms.
- Clearing the search removes the rows and returns to the contained search prompt rather than rendering the complete population.
- Empty matches, unavailable input, and invalid input use contained report states. A failed current read never falls back to public Catalogue JSON or an older result.

## Semantic HTML Presentation

Catalogue Works is a stable rectangular dataset and uses a semantic HTML table with `thead`, `tbody`, column headers, rows, and cells. Sorting controls may live inside header cells, and Work or Series links remain ordinary interactive cell content.

The report owns stable column ids and one ordered header/row correspondence. CSS owns the responsive embedded presentation but does not replace table semantics with a parallel Grid renderer. The ordinary report fits or reflows inside the document measure; horizontal scrolling and temporary manual widths arrive only through Expanded Report View.

The initial report explicitly exposes **Copy table** after a current search has results. It copies the complete current matching table, including its headers and current row order, as tab-separated plain text suitable for spreadsheet paste. It does not copy the complete loaded population, hidden non-matches, an alphabetical Series list, action labels, or arbitrary interactive DOM outside the semantic table.

## Frontend And Server Boundary

The Local Studio Catalogue service remains the authority for canonical Work and Series reads, validation, and exact record identity. The Docs Viewer report module owns search, filtering, sorting, table rendering, result count, clipboard projection, links, and contained browser states.

The migration should reuse the existing browser-safe Local Studio Catalogue reads. It does not add a server-rendered page, report-specific endpoint, versioned report response, persisted result, or generated report Markdown merely to relocate the presentation. If a later filter needs data absent from the accepted browser read model, that filter must first receive an explicit Studio-owned projection rather than reading a repository path or public Catalogue payload directly.

`catalogue_works` is local-only because it depends on local Studio Catalogue authority and curator context. Its module and CSS belong to the local report graph and local report stylesheet; public report metadata, loaders, data, and CSS remain unchanged.

## Route Retirement

The completed migration removes `/studio/studio-works/` rather than preserving a redirect, route alias, empty shell, or duplicate reader. The retirement includes its Studio route registration, template, JavaScript entry module, route-only text and CSS, runtime/config assertions, route smoke, Admin Checks entry, and current-route documentation. A bounded reference scan must update any exact inbound navigation to the new Docs Viewer report host before removal.

Studio retains the Work and Series editor routes because their primary purpose is canonical mutation. Catalogue Drafts also remains in Studio as the explicit exception for recovery and maintenance: it finds unfinished canonical records and hands them to those focused editors rather than acting as a general read-only catalogue report.

## Later Filter Adoption

Search and current-column sorting are part of the migration. Additional filters follow only after the migrated report and its accepted data inputs can be inspected in practice.

Candidate filters include:

- **Medium** — exact `medium_type` values are already canonical, but a binary digital/physical filter requires a separately approved classification rule. Values such as `digital print` demonstrate that the classification cannot be inferred safely from one word or from storage presence.
- **Storage** — yes/no can derive from the presence of the canonical storage value once the migration confirms the accepted field and read-model ownership.
- **Tags** — become eligible only after Works have an exact tag-assignment authority and an explicit local browser projection. This feature adds no inert tag control, placeholder field, speculative join, or preloaded CSS.

Each adopted filter is code-owned, deterministic, and backed by an existing or deliberately added data contract. Filters narrow a non-empty search; they do not independently reveal the complete population or become parameters in the Report Block.

## Boundaries

This feature does not:

- include draft Works or duplicate Catalogue Drafts;
- turn Catalogue Status into a Docs Viewer report or remove its Studio workflow;
- merge `catalogue_works` with the Series-grained documentation-coverage `works` report;
- add catalogue mutation, inline editing, bulk selection, publication, or repair actions to the report;
- introduce a generic Catalogue report engine, server-side search product, arbitrary query language, saved report, or report-parameter mechanism;
- read public Catalogue aggregates or exact public payloads as canonical input;
- add medium classification or Work tags before their exact authority is approved;
- implement Expanded Report View, horizontal scrolling, or manual column widths; or
- retain the retired Studio route as a compatibility surface.

## Potential Delivery Shape

1. **Migration sanity check** — confirm the exact report host, Local Studio read contract, current published population, plural Series presentation, search fields, semantic columns, clipboard projection, inbound links, route/CSS owners, and bounded retirement diff. Stop if the result requires a new report server, generic search framework, Report Block parameters, or route compatibility layer.
2. **Catalogue Works report and route cutover** — add the local report metadata and module, Report Block host, search-required semantic table, sorting, exact links, Copy table, contained states, local CSS, and focused report evidence; then remove the Studio Works route and its exact owners in the same complete cutover.
3. **Data-backed filters** — after migration acceptance, inspect the available read model and add only independently approved medium, storage, or later tag filters with their exact data and classification contracts.
4. **Closeout** — update Reports with the shipped report inventory, rewrite Catalogue Works and Local Studio Routes to current ownership, verify Catalogue Drafts and editors remain intact, and then make Catalogue Works available as the representative Expanded Report View adoption.

These are candidate outcomes, not active deliveries or permission to implement them. The migration is independently complete without later filters or expanded presentation.

## Success Meaning

The feature succeeds when every published canonical Work can be found through one search-driven local Docs Viewer report, every result preserves exact Work and plural Series identity in a semantic HTML table, and Copy table represents the current sorted search result. `/studio/studio-works/` and its dedicated presentation owners are absent, while Catalogue Drafts and focused catalogue editors remain Studio-owned. No public report capability, draft-report duplication, server report product, Report Block parameter, or Expanded Report implementation is introduced.
