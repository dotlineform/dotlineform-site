# TDL-0 — Tag Document Metadata Authoring Refactor Delivery

## Status And Purpose

Active at the completed TDL-0.1 review gate as the standalone UI prerequisite to [TDL-1](/docs/?scope=studio&doc=d-20260804-160201-47af2d), consuming the completed [SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf). Implementation is parked before TDL-0.2. This delivery moves Analysis Tags document `group` editing out of the app-level **Edit metadata** modal so that the shared modal can contain only document-common front matter.

The current generic modal has a dedicated `group` field populated from sub-scope configuration. The field is useful, but its ownership is wrong: `group` belongs to the registered Tag-document customisation, not to every document. SSC-1 shipped the accepted customisation and aspect vocabulary; TDL-0 adds the `tag_fields` `DocsSubScopeAssignableFieldGroup` and relocates the field before TDL-1 extends its server-owned fields with `tag_id`.

## Complete Outcome

On the local Manage route, Info remains read-only and displays all metadata projected by the exact active document's resolved scope/sub-scope configuration. For the current Analysis Tags registration, that includes the document's configured `group` state beneath the common document summary. Public Info receives no Manage customisation data or controls.

A resolved `sub_scope_customisation` that declares `DocsSubScopeAssignableFieldGroup(group_id="tag_fields", ...)` may expose a focused Tag-document fields action and modal. `analysis/tags` is the current configuration registrant intended to gain that declaration. The server resolves it with `sub_scope_customisation_assignable_field_groups()` and the browser checks its projected ID with `hasDocsViewerAssignableFieldGroup()`; the current ordered group choices remain in validated customisation settings.

The modal initially edits only document `group`, using the current configured choice order and exact source value. It owns confirmation, cancellation, exact `{scope, sub_scope, doc_id}` target, source revision, mutation feedback, and clear/unassigned behavior. TDL-1 later extends the same registered field group and modal with optional canonical `tag_id` selection while Info remains read-only.

After the migration, **Edit metadata** no longer contains, hydrates, renders, validates, or submits `group`. Together with SSP-0's Projects extraction, this restores the target boundary: **Edit metadata** owns common document fields, while configured sub-scope workflows own their fields.

Document `group` and canonical Tag Registry `group` remain independent fields. Existing create-time seeding stays create-only. Editing a Tag document's group through this modal never updates, compares, repairs, or triggers a build from the Registry group, and editing the Registry never rewrites document front matter.

## Awareness And Registration Boundary

- **Edit metadata** remains document-agnostic and knows only common front matter.
- **Info** resolves the active collection's registered metadata display contribution and renders its values read-only.
- The focused Tag-document modal resolves the active collection's declared assignable Tag-document fields and their choices.
- Current availability in `analysis/tags` is a configuration fact, not a hard-coded route or collection-name condition.
- `analysis/tags` public presentation as Concepts does not change its technical collection identity or expose Manage authoring capability publicly.

## Delivery Discipline

TDL-0 consumes SSC-1's `DocsSubScopeAssignableFieldGroup`, exact-target, metadata, browser-composition, and access-safe capability projection, then reuses the current Analysis Tags group choices, management modal shell, revision receipts, atomic source mutation, and targeted sub-scope rebuild. The exact definition and projected `tag_fields` group own availability and accepted fields. It does not introduce a generic field-schema editor, editable Info panel, Tag Registry synchronization, generic cross-collection mutation service, public management contribution, or Tag association behavior.

TDL-0.0 is a short scope-and-spec sanity gate. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

#### TDL-0.0 Sanity Note — 11 August 2026

The current implementation fits the delivery without a new framework. `analysis_tags` has the correct exact collection identity, document-group choices, private manifest, and browser, but no metadata aspect or assignable field group. SSC-1's `plan_assign_field_group()` service and the shipped Projects modal/Info contribution provide the accepted capability-selected, exact-target, revision-safe pattern; TDL-0 should add `tag_fields` through that seam and keep the generic metadata modal as the temporary old owner until TDL-0.2 removes it.

The broad owners are the Analysis Tags customisation definition and validation, hosted Manage context and Info composition, the generic metadata modal, the focused assign-field-group mutation/modal workflow, targeted sub-scope rebuild, and their existing service, module, route, and public-isolation contracts. Report Blocks and intentional child-document exclusion do not expand this surface. The repaired Analysis-only public location seam is a completed prerequisite regression fix, not a TDL-0 implementation dependency.

The bounded result remains read-only configured group display, a capability-selected Tag-document modal, exact revision-safe group mutation, retirement of generic `group` editing, and a clean TDL-1 extension point for `tag_id`. Primary risks are duplicate field ownership during cutover, hard-coded collection checks, leaking private metadata or controls publicly, and accidentally coupling Registry group to document group. Those conditions remain stop signals. That gate stopped before implementation; TDL-0.1 was subsequently approved and completed below.
