# Sub-Scope Publishing

## Purpose

Sub-Scope Publishing coordinates the path from private working documents to reviewed public documents and exact public Catalogue document-link metadata. Working documents may remain together in `dotlineform/projects` and optionally declare `folder_path`, `work_id`, `series_id`, or no subject. Focused projections support Manage subject cues, Project State, one explicit subject-link authoring action, editorial copy, publication-lineage status, curator coverage reporting, and public Work/Series metadata without making subject presence a save, copy, publishability, or publication gate.

## Complete Feature Outcome

A working document may declare zero or one normalized Folder, Work, or Series subject. The declaration means what the document is about. It is never inferred from title, filename, body content, route state, destination, selected UI state, or semantic-token usage. Malformed or conflicting declarations remain non-blocking authoring evidence and enter no exact subject association.

Project State scans immediate project directories, joins canonical Works by exact first-level `project_folder`, groups their current `series_ids`, and places Project documents through exact Folder, Work, or Series subjects. It remains an independently useful live, in-memory report. Resolver Tokens were retired before implementation, and SSP-2.6 removed the unused persisted resolver lookup; Project State now has neither a persisted relationship product nor a document-build consumer.

SSP-6 owns two shipped local file-reconciliation reports. Uncataloged Files starts from exact existing Work source directories and reveals ordinary files that are not used as Work primary sources. Missing Source Files starts from canonical Works and reports complete expected source paths that do not resolve. Separate parent/report-host documents preserve their opposite row grains; neither report mutates Project State, Works, or files. SSP-6.3 removed the superseded Studio route, APIs, generator, activity surface, and static Markdown output without changing these reports or Docs Viewer Project State.

The Source editor offers one **Insert subject link** action. A Work or Series subject inserts the existing semantic-token syntax for that exact catalogue identity. A Folder subject inserts the existing `dlf-local:` Markdown link for that exact relative path. This is an ordinary Source-owned typing convenience: it does not add a concurrency protocol, expand related items, change front matter, or follow later subject reassignment. Manage may activate the local link; the existing publication boundary leaves local targets inert and exposes no local path or capability publicly.

Collection-aware copy takes a `dotlineform/projects` document into the exact `analysis/works` collection as an independent Editorial copy. New uses the public-capable target's included-by-omission `publishable` default; exact Replace preserves the selected Editorial document's current gate. Copy retains canonical optional subject bytes without interpreting them. Later Working changes do not retarget an Editorial child, and ordinary publication remains subject-agnostic. A reviewed child becomes public only through the existing Analysis Publish workflow and its ordinary public report host.

Document lineage begins only with the exact configured Copy and is owned by the current Working `doc_id`. A Working document may have zero-to-many current Editorial children, but the private table stores a record only while at least one child exists; each child carries exact Copy evidence and an optional current published URL. New adds a child, Replace updates one exact child, deleting Working ends the complete lineage record, and deleting Editorial immediately removes its public projection through DPD-1 before removing that child. Set Publishable changes only the next-Publish gate. Scope-wide Publish remains the positive promotion action and reconciles published URLs for surviving Editorial children. Projects needs no Working icon, shows the highest Editorial or Published state across current children, and remains the complete presentation surface for this Working-owned purpose. Project State document cues continue to show subject-placement provenance.

Public Work and Series by-ID payloads contain links only to published documents whose final canonical source explicitly declares that exact Work or Series subject. This is an aboutness projection owned by SSP-5. Semantic tokens record content mentions and relationships for analysis; a token occurrence alone never adds a document to Work/Series `doc_url[]` metadata. Public display of those links requires a later Catalogue presentation delivery outside this feature.

## Boundary

Sub-Scope Publishing owns the SSP sequence, the shared typed-subject contract, and the handoffs between working, derived, editorial, and public projections. Individual deliveries own their schemas, builders, UI, reports, tests, and review gates.

The feature does not infer subject or lineage identity, impose one-to-one document cardinality, make subject metadata a lifecycle rule, synchronize working and editorial documents, synchronize documents with folders or catalogue records, compare or merge content during Copy, expand a subject into related targets, add a resolver parser or relationship lookup, use semantic mentions as public aboutness, roll Work associations up to Series or Series associations out to member Works, publish local Folder identities, display `doc_url[]` on public Catalogue routes, or combine Copy and publication into one mutation.

[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61) remains the identity, link, and mention-usage owner. The existing Analysis Publish workflow remains the only positive public promotion authority; confirmed document Delete owns immediate removal of the exact public projection through DPD-1.

## Delivery Discipline

Each SSP delivery begins with a short scope-and-spec sanity gate and ends each implementation stage with focused evidence plus an independent code/diff review. A gate confirms current owners, blast radius, deliverables, risks, and a concrete stop condition without freezing an exhaustive file inventory or implementation. No delivery begins merely because the feature-level model is accepted.
