# Sub-Scope Publishing

## Purpose

Sub-Scope Publishing coordinates the path from private working documents to maintained contextual references and reviewed public documents. All normal working documents may remain together in `dotlineform/projects` and optionally declare `folder_path`, `work_id`, `series_id`, or no subject. Focused projections then support Manage authoring cues, Project State, catalogue-document coverage reporting, current-reference rendering, editorial copy, and public catalogue metadata without making subject presence a lifecycle gate.

The feature keeps one sequence because subject declaration, reverse association, Project State, Resolver Tokens, collection-aware copy, and Work/Series-page document links share one authoring-to-publication foundation. Project State remains folder-specific, while Work/Series reverse association is optional document metadata that may participate from any public collection.

[SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf) is the shared configuration prerequisite. It establishes one registered `sub_scope_customisation` seam for report projections, read-only metadata, focused actions, validation, import, and transfer aspects before SSP adds a Projects assignable-subject group. SSP does not create a parallel declared-fields workflow.

[SSP-0 — Projects Subject Assignment Foundation Delivery](/docs/?scope=studio&doc=d-20260804-164519-c7ad4e) is the completed standalone prerequisite to subject implementation. It keeps Info read-only, moves Projects folder assignment from **Edit metadata** into a modal selected by the sub-scope's declared assignment capability, and establishes the exact-target mutation and interaction seams that SSP-1 extends with Work/Series search. Projects is the current configuration registrant, not a hard-coded browser condition.

[SSP-1 — Document Subject And Association Delivery](/docs/?scope=studio&doc=d-20260802-194426-087cfe) is complete. [SSP-2 — Docs Viewer Project State Delivery](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) is reopened for SSP-2.5 after live use exposed its Folder-subject-only document join; the accepted SSP-2.0–2.4 scan, report, interaction, and freshness-transfer checkpoints remain intact. SSP-2.5 traces Folder-, Work-, and Series-subject documents into real-folder rows and versions the changed report/lookup semantics. [SSP-3 — Resolver Tokens Delivery](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4) remains proposed and waits for that reclosed product before implementation.

[Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee) owns the complete cross-delivery model. All retained concept, architecture, and delivery documents are direct children of this feature. Delivery titles use SSP numbering, so the index tree expresses a possible implementation order without a separately maintained order table.

## Complete Feature Outcome

A working document in `dotlineform/projects` may declare zero or one of normalized `folder_path`, canonical `work_id`, and canonical `series_id`. This is an authoring convention rather than a save, Copy, viewability, or Publish requirement. Valid declarations project deterministic zero-to-many document associations without inferring identity from title, filename, body content, route state, destination, or current UI context. Malformed or conflicting declarations remain non-blocking authoring evidence and do not enter reverse lookups.

Project State scans immediate project directories to establish its rows, then joins canonical `works[]` by exact first-level `project_folder` and groups their current `series_ids`. It places Project documents through every valid exact subject kind: Folder to its exact row, Work to that Work's Folder, and Series to every scanned Folder containing a current member Work. Each placement retains declared-subject and applicable-Series provenance so Folder view deduplicates the document once per Folder and Series view does not repeat it under unrelated Series. Before a selected build renders Resolver Tokens that need Folder relationships, it refreshes the reclosed Project State product once and prepares exact subject-keyed relationship rows. Each token retains its hidden front-matter subject as the seed, then the containing collection projects allowed Folder, Work, and Series groups without serializing the subject in token source or scanning relationship owners during expansion. Projects may show all three groups; Analysis Works suppresses Folder results while retaining the Folder seed for private relationship resolution.

The Work/Series-to-document associations also satisfy a curator reporting requirement: Studio must be able to show catalogue document coverage by exact Work or Series and open the associated documents. The current [Catalogue Works](/docs/?scope=studio&doc=d-20260401-000000-ebf14a) index is the likely presentation family, while its eventual route and component shape may be chosen as part of a later Studio Works refactor. The reporting view consumes the shared derived associations rather than introducing another working collection or relationship authority.

Collection-aware copy takes a `dotlineform/projects` document into the exact `analysis/works` collection as an independent non-viewable editorial copy. Its existing identity, placement, link, media, and target-default transformations remain intact, while `folder_path`, `work_id`, or `series_id` is retained unchanged without interpreting its meaning. The destination build owns normalization, relationship resolution, and result projection; a no-subject document copies normally. Later private-source changes do not retarget the independent copy. Ordinary publication remains subject-agnostic, while exact public Work or Series by-ID payloads receive deterministic derived `doc_url[]` values only from a published document whose final source explicitly declares that exact catalogue subject.

## Boundary

Sub-Scope Publishing owns the cross-feature goal, SSP delivery sequence, shared typed-subject contract, and handoffs between working, derived, editorial, and public projections. The flat child documents own their exact schemas, builders, UI, reports, registries, tests, and review gates.

The feature does not make document titles or content into identity, impose one-to-one subject cardinality, make subject metadata a publication rule, synchronize document lifecycle with folders, Works, or Series, infer or rewrite a catalogue subject from a Project folder, roll exact document reverse associations from Work to Series or Series to member Works, add Studio/Docs mutation hooks for Project State, let individual Resolver Tokens refresh relationship data, publish Folder identities or Manage-only paths, or make copy and publication one mutation. Resolver display may project bounded one-hop related links without changing the document's declared subject or reverse-association identity. A later general relationship database for analysis would not replace explicit source authorities or focused consumer projections.

[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61) remains the link and usage owner for returned registered identities. The existing Analysis Publish workflow remains the only public publication authority.

## Delivery Discipline

The feature-level sense check is complete. Delivery `.0` steps confirm implementation fit, current broad owners, shared-customisation prerequisites, and stop conditions; they do not reopen the one-working-collection, optional-subject, subject-independent publication, or folder-to-Work Project State decisions.

Each SSP delivery begins with a short scope-and-spec sanity gate. That gate confirms scheduling dependencies, the fit with current broad owners, the likely blast radius, the intended deliverables, principal risks, and a concrete stop condition. It resolves only contradictions that would change the specified outcome; it does not require an exhaustive code audit, exact file inventory, line estimate, frozen implementation, implemented fixture, or complete test architecture before implementation approval.

Each implementation step remains independently reviewable. Before proceeding to the next step, focused evidence must prove the changed contract and an independent code/diff review must check scope, ownership, omissions, surviving boundaries, and whether the delivery documents remain accurate. The final transfer step retains the broader completion, documentation, and omission review.
