# Sub-Scope Publishing

## Purpose

Sub-Scope Publishing coordinates the path from private working documents to maintained contextual references and reviewed public documents. A sub-scope document declares the folder, Work, or Tag it represents in front matter; its registered customisation projects that typed subject into the collection manifest; focused relationship products then support collection reports, Project State, current-reference rendering, editorial copy, Registry policy, and public catalogue metadata.

The feature keeps one sequence because subject declaration, reverse association, Project State, Resolver Tokens, collection-aware copy, Tag primary-document selection, and Work-page document links are stages of one authoring-to-publication workflow. A broader relationship database may later support analysis, while consumer lookups remain lean, versioned, and focused.

[Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee) owns the complete cross-delivery model. All retained concept, architecture, and delivery documents are direct children of this feature. Delivery titles use SSP numbering, so the index tree expresses a possible implementation order without a separately maintained order table.

## Complete Feature Outcome

A working document in `dotlineform/projects` declares either one normalized `folder_path` or one canonical `work_id`. A Tag document declares one canonical `tag_id`. Each collection projects a typed subject and deterministic zero-to-many document association without inferring identity from title, filename, body content, route state, or current UI context.

Project State consumes Project subjects and canonical folder/Work/Series evidence to maintain one folder-centred report that exposes omissions and disorder. A context-aware Resolver Token renders the current folder, Work, Series, or Tag references for its containing document from one focused lookup without serializing the subject in token source or refreshing relationship data.

Collection-aware copy creates independent non-viewable editorial documents in exact Analysis sub-scopes. `folder_path` is omitted when unsupported; compatible `work_id` is retained and revalidated. Tag Registry replaces `doc_url[]` with one optional exact `primary_document`, selected from the derived Tag associations without making documents declare their own priority. Analysis Publish projects only reviewed viewable documents, and public Work by-ID payloads receive their current public document links through separate derived metadata.

## Boundary

Sub-Scope Publishing owns the cross-feature goal, SSP delivery sequence, shared typed-subject contract, and handoffs between working, derived, editorial, and public projections. The flat child documents own their exact schemas, builders, UI, reports, registries, tests, and review gates.

The feature does not make document titles or content into identity, impose one-to-one subject cardinality, synchronize document lifecycle with folders, Works, Series, or Tags, let Resolver Tokens refresh relationship data, publish Manage-only paths, or make copy and publication one mutation. It does not prohibit a later general relationship database for analysis; such a store does not replace explicit source authorities or focused consumer projections.

[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61) remains the link and usage owner for returned registered identities. The existing Analysis Publish workflow remains the only public publication authority.

## Delivery Discipline

Each SSP delivery begins with a short scope-and-spec sanity gate. That gate confirms scheduling dependencies, the fit with current broad owners, the likely blast radius, the intended deliverables, principal risks, and a concrete stop condition. It resolves only contradictions that would change the specified outcome; it does not require an exhaustive code audit, exact file inventory, line estimate, frozen implementation, implemented fixture, or complete test architecture before implementation approval.

Each implementation step remains independently reviewable. Before proceeding to the next step, focused evidence must prove the changed contract and an independent code/diff review must check scope, ownership, omissions, surviving boundaries, and whether the delivery documents remain accurate. The final transfer step retains the broader completion, documentation, and omission review.
