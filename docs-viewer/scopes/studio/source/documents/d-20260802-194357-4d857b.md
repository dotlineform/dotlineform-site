# Sub-Scope Publishing

## Purpose

Sub-Scope Publishing coordinates the path from private working documents to reviewed public documents and exact catalogue-page document links. Working documents may remain together in `dotlineform/projects` and optionally declare `folder_path`, `work_id`, `series_id`, or no subject. Focused projections support Manage subject cues, Project State, one explicit subject-link authoring action, editorial copy, publication-lineage status, curator coverage reporting, and public Work/Series metadata without making subject presence a save, copy, viewability, or publication gate.

[SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf) and [SSP-0 — Projects Subject Assignment Foundation Delivery](/docs/?scope=studio&doc=d-20260804-164519-c7ad4e) are complete prerequisites. [SSP-1 — Document Subject And Association Delivery](/docs/?scope=studio&doc=d-20260802-194426-087cfe) and [SSP-2 — Docs Viewer Project State Delivery](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) are complete. [SSP-3 — Insert Subject Link Delivery](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4), SSP-4 collection-aware copy, SSP-5 public Work/Series metadata, SSP-6 Project Media Audit, and [SSP-7 — Document Lineage And Publication State Delivery](/docs/?scope=studio&doc=d-20260805-231829-947705) remain proposed.

[Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee) owns the complete cross-delivery model. All retained concept, architecture, and delivery documents are direct children of this feature. Delivery titles use SSP numbering, so the index tree expresses a possible implementation order without a separately maintained order table.

## Complete Feature Outcome

A working document may declare zero or one normalized Folder, Work, or Series subject. The declaration means what the document is about. It is never inferred from title, filename, body content, route state, destination, selected UI state, or semantic-token usage. Malformed or conflicting declarations remain non-blocking authoring evidence and enter no exact subject association.

Project State scans immediate project directories, joins canonical Works by exact first-level `project_folder`, groups their current `series_ids`, and places Project documents through exact Folder, Work, or Series subjects. It remains an independently useful live, in-memory report. Resolver Tokens were retired before implementation, and SSP-2.6 removed the unused persisted resolver lookup; Project State now has neither a persisted relationship product nor a document-build consumer.

The Source editor offers one **Insert subject link** action. A Work or Series subject inserts the existing semantic-token syntax for that exact catalogue identity. A Folder subject inserts the existing `dlf-local:` Markdown link for that exact relative path. This is a revision-safe typing convenience: it does not expand related items, change front matter, or follow later subject reassignment. Manage may activate the local link; the existing publication boundary leaves local targets inert and exposes no local path or capability publicly.

Collection-aware copy takes a `dotlineform/projects` document into the exact `analysis/works` collection as an independent non-viewable editorial copy. It retains the canonical optional subject bytes without interpreting them. Later source changes do not retarget the copy, and ordinary publication remains subject-agnostic.

Document lineage records each exact working-source A to editorial-target B relationship in one private persisted table. A later Copy requires an explicit New or exact Replace choice: New creates another B; Replace preserves one selected B identity and publication gate while replacing its content without diff or merge. Scope-wide Publish alone records whether B currently has a public projection. Projects report cues show pre-publish and published stages, while Project State document cues continue to show subject-placement provenance.

Public Work and Series pages link only to published documents whose final canonical source explicitly declares that exact Work or Series subject. This is an aboutness projection owned by SSP-5. Semantic tokens record content mentions and relationships for analysis; a token occurrence alone never adds a document to Work/Series `doc_url[]` metadata.

## Boundary

Sub-Scope Publishing owns the SSP sequence, the shared typed-subject contract, and the handoffs between working, derived, editorial, and public projections. Individual deliveries own their schemas, builders, UI, reports, tests, and review gates.

The feature does not infer subject or lineage identity, impose one-to-one document cardinality, make subject metadata a lifecycle rule, synchronize working and editorial documents, synchronize documents with folders or catalogue records, compare or merge content during Copy, expand a subject into related targets, add a resolver parser or relationship lookup, use semantic mentions as public aboutness, roll Work associations up to Series or Series associations out to member Works, publish local Folder identities, or combine Copy and publication into one mutation.

[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61) remains the identity, link, and mention-usage owner. The existing Analysis Publish workflow remains the only public publication authority.

## Delivery Discipline

Each SSP delivery begins with a short scope-and-spec sanity gate and ends each implementation stage with focused evidence plus an independent code/diff review. A gate confirms current owners, blast radius, deliverables, risks, and a concrete stop condition without freezing an exhaustive file inventory or implementation. No delivery begins merely because the feature-level model is accepted.
