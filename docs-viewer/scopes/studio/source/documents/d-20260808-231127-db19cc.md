# Scope Media Storage Locations Concept

## Purpose

Where scope media is saved is a storage-policy decision, not a scope-type decision. A public scope may keep modest images in the repository while large files use R2. A local repository-backed scope may keep its media in an external-local workspace. The right choice can differ by media type and can change as a scope grows.

The product therefore needs one explicit scope-level way to see and change those configured destinations without changing access mode, canonical document location, media identity, metadata, or authored references.

## Independent Configuration Axes

The stable model separates:

| concern | examples | owner |
| --- | --- | --- |
| scope access/profile | local management or public projection; repository or external canonical workspace under current supported profiles | Scope Type Migration |
| canonical document workspace | `scope_root` with source and local document/search products | Scope Lifecycle and Scope Type Migration |
| media identity and metadata | `scope + media type + relative identity`, media record, producer and reference evidence | Scope Media Management |
| media storage policy | one configured location per media type | Scope Media Storage Locations |
| public document delivery | route plus public document/search projections and scope-wide Publish | Public Scopes |

The existing logical reference remains provider-neutral:

```text
docs/<scope>/<media-type>/<relative-identity>
```

Changing a provider or physical root does not change that identity. Builders and readers resolve it through the current scope configuration; they never search several providers for matching bytes.

## Destination Model

Each configured media type has exactly one active destination:

```text
published.media.<media-type>
  reference_prefix
  location.provider
  location.path
  served_path_prefix
  build_inputs
```

The supported provider vocabulary remains bounded:

| destination | local use | public use | important consequence |
| --- | --- | --- | --- |
| scope-local | yes | only when its resolved repository location is publicly delivered | Deliberately follows `scope_root`; omission of an explicit location expresses this policy. |
| repository | yes | yes when the configured path is inside the tracked public artifact and has a public-safe served prefix | Adds bytes to Git and the deployed `site/` artifact when public. |
| external-local | yes | not directly | Requires the configured external workspace and a local service route; the static public site cannot read it. |
| R2 | yes, with network and credential/availability consequences | yes when configured through the public media domain | Keeps large or provenance-sensitive bytes out of Git but may remain publicly addressable even for a local scope. |

Provider alone is not enough to prove public compatibility. Path ownership and served delivery must also be valid. Repository media below a local workspace is not automatically a public asset; repository media under the tracked public projection can be.

The first feature retains one destination per media type. Named destinations within one type, automatic size routing, and per-object provider choice remain separate future questions.

## Current Evidence And Constraint

Current configured scopes already prove the conceptual separation:

- Library and Analysis are public while keeping images and SVG in repository public paths and files in R2.
- Moments is public while using R2 for images/files and repository for SVG.
- local scopes use scope-local media beneath their repository or external scope roots.

The current lifecycle creation preset is narrower than that reality: it defaults new public image/file media to R2 and SVG to repository. Current validation also forces external scopes to keep media scope-local and rejects external-local media for repository-backed scopes. This feature turns those implementation policies into explicit defaults and compatibility rules rather than treating them as the semantic meaning of scope type.

## Creation Defaults

New-scope workflow may continue to present concise profiles, but the resulting media policy is inspectable and independently changeable.

Useful defaults include:

| creation profile | illustrative media defaults |
| --- | --- |
| local repository | scope-local repository media |
| local external | scope-local external media |
| public repository-oriented | repository images/SVG/HTML and R2 files |
| public R2-oriented | R2 images/files and repository SVG/HTML where required |

These are presets, not new scope types and not immutable policies. The first creation UI does not need a fully expanded provider matrix if the later **Media storage** action makes the chosen policy visible and changeable.

Ordinary Add Image, Add File, source-media build, import, replacement, and rendering workflows continue to use the configured destination. They must not prompt for repository, external-local, or R2 on every action.

## Operator Workflow

An eligible scope gains **Media storage** as a scope-level management action.

1. Open the current policy for the selected scope.
2. Review each media type, current provider/location label, object count, total bytes, availability, and public-delivery status.
3. Choose a supported target for one or more exact media types.
4. Request a server-owned migration preview.
5. Review byte inventory, conflicts, config/manifest changes, served-path consequences, public exposure changes, cleanup, and blockers.
6. Confirm the exact plan.
7. Apply revalidates current state, moves and verifies bytes, switches configuration authority, rebuilds affected products, cleans the former destination, and refreshes capability/inventory state.

The browser sends the scope, exact media types, and supported destination choice. The server derives paths, provider adapters, identity inventories, route consequences, and ownership. Arbitrary absolute paths and raw R2 prefixes are not browser-authoritative inputs.

## Preview Contract

The write-free plan reports:

- exact scope and selected media types;
- current and target provider, safe location label, served-path behavior, and availability;
- complete owned identity count and byte total, including referenced and unreferenced items;
- build-source/producer relationships relevant to regenerated outputs;
- missing configured bytes and unexpected target collisions;
- public-delivery compatibility before and after migration;
- configuration and lifecycle-manifest changes;
- objects to create, verify, retain, or delete;
- logical references and media records that remain unchanged;
- commit point, failure meaning, and exact cleanup retry; and
- a plan identity or source/provider snapshot that apply must revalidate.

Unreferenced does not mean disposable, so the complete owned inventory moves. Missing referenced bytes remain a visible blocker or explicit pre-existing deficiency; migration cannot manufacture them from references.

Preview blocks at least:

- unavailable or unsafe source/target providers;
- source ownership that cannot be established from configuration, registry/inventory, and lifecycle evidence;
- target path escape, symlink, collision, or non-empty ambiguous prefix;
- R2 authentication/list/read/write/delete capability missing for the requested direction;
- a target incompatible with current public delivery where the scope is public;
- competing producers or an unsupported media-type configuration;
- independently owned collections mixed into the selected destination; and
- any relevant config, media-record, source inventory, or object revision change before apply.

## Apply And Recovery

Apply uses an exact scope/media-type busy boundary. It does not require a general background migration system or multi-user locking framework.

The operation is:

1. Recompute the plan and verify source, target, configuration, ownership, and capabilities.
2. Stage or copy every selected owned object to the target through the provider-neutral location adapter.
3. Compare exact relative identities, sizes, and byte hashes at source and target.
4. Validate media records, build producers, served references, and target public compatibility.
5. Commit the transformed media-location configuration and lifecycle receipt.
6. Rebuild affected browser config, documents, media outputs, and reference/inventory projections without rewriting authored logical references.
7. Delete the former owned objects or prefix after the new destination is authoritative.
8. Refresh capabilities and the Scope Media surface and return an exact result.

Failure before configuration commit leaves the current destination authoritative and reports/removes only inactive staging. Failure after commit returns `committed: true`, the failed cleanup or rebuild stage, and an exact retry. The runtime never reads the old destination as fallback and never searches both providers.

If cleanup fails, verified bytes at the former provider are inactive orphans. The result must disclose whether they remain publicly served and retain the exact provider/location evidence needed for deliberate cleanup.

## Scope-Local Media

`scope-local` remains a useful explicit policy. Its media is a descendant of `scope_root`, so relocating the canonical workspace moves those bytes with the enclosing lifecycle-owned container. That is chosen location inheritance, not an inference from scope type.

An operator who wants media to remain external while moving documents into the repository first changes those media types to an explicit external-local destination. An operator who wants media to follow the documents leaves them scope-local. Scope Type Migration preview reports that distinction exactly.

## Interaction With Scope Type Migration

Scope-type migration preserves explicit media destinations:

- local repository -> public keeps every public-compatible repository or R2 destination;
- incompatible scope-local or external-local destinations block public enablement until Media storage moves them explicitly;
- public -> local removes public document/search delivery but does not automatically move or delete repository-public or R2 media;
- local access is not a promise that every media URL is private; preview reports any media that remains publicly served; and
- external <-> repository workspace relocation moves only scope-local media with the scope root, leaving independent destinations unchanged.

This makes scope-type migration smaller and more truthful. It validates media compatibility and reports consequences but does not choose a storage policy on the operator's behalf.

## Relationship With Scope Media Management

Scope Media Management owns intentional identity/metadata and the provider-neutral inventory or management surface. That surface can display current storage and launch this workflow, but listing files or discovering references does not itself authorize provider migration.

Scope Media Storage Locations owns:

- per-media-type destination configuration;
- provider compatibility and capability projection;
- byte-copy, verification, cutover, and old-location cleanup;
- served-path consequences; and
- migration receipts and recovery.

Replacement or deletion of one media identity, media metadata editing, semantic references, and unreferenced-item decisions remain with Scope Media Management.

## Ownership Boundaries

Only scope-owned media at registered destinations is eligible. Independently owned External Asset Collections and arbitrary project files are inventory/report inputs at most; this workflow cannot adopt, relocate, or delete them.

Repository paths, external-local roots, and R2 prefixes must remain deterministic and scope-confined. A provider change cannot accept a user-specific absolute path or shared prefix that makes later deletion ownership ambiguous. Shared config files are changed, never recorded as wholly owned migration targets.

## Proof Gate

A delivery is not complete without focused evidence that proves:

- public repository-backed media and public R2-backed media remain supported independently of scope type presets;
- a repository-backed local scope can use an exact external-local media destination without relocating canonical documents;
- every selected source identity, including unreferenced media, exists byte-identically at the target before cutover;
- media records, logical references, relative identities, metadata, and producer relationships remain unchanged;
- configuration resolves every migrated identity to exactly one destination after success;
- Add Image, Add File, build, render, import, inventory, and served-media reads use the new location without provider choice or fallback;
- public compatibility is enforced from provider, path, and served delivery rather than provider name alone;
- scope-type migration preserves explicit media policy and reports scope-local inheritance;
- exact old repository, external-local, and R2 objects are removed or reported as inactive cleanup failures;
- independently owned collections remain untouched; and
- injected failures on every side of the commit point produce the documented unchanged or committed-recovery result.

The proof should cover repository <-> external-local and repository/external-local <-> R2 directions only when each provider adapter has complete inventory, byte verification, and exact cleanup capability. A delivery must not claim a provider direction it cannot reverse or clean safely.

## Delivery Seams

The concept admits independently complete deliveries without pre-authorizing them:

- configuration-policy separation, capability projection, creation defaults, and preview contract;
- repository <-> external-local media migration for exact media types;
- R2 upload/download/delete migration with exact receipt and cleanup behavior;
- scope-level Media storage interaction integrated with the chosen media-management surface; and
- reconciliation of Scope Type Migration once compatible destination changes are independently available.

Any delivery should select one complete reversible provider boundary and stop rather than implementing a partial all-provider matrix.

## Exclusions

This concept does not introduce:

- arbitrary absolute paths or user-authored R2 prefixes;
- provider choice during ordinary Add/Import/Replace actions;
- automatic provider selection by file size, suffix, availability, or scope type;
- more than one active destination for an unqualified media identity;
- named destinations within a media type, per-object routing, or provider-search fallback;
- content rewriting or new media identities during migration;
- automatic deletion based on reference count;
- migration of independently owned collections or project files;
- changing the scope's access mode or canonical document workspace; or
- a background sync, replication, cache, or generic data-migration framework.

## Durable Transfer

[Scope Lifecycle](/docs/?scope=studio&doc=d-20260515-000000-f43740) should own migration preview/apply, lifecycle receipts, cleanup, and recovery.
