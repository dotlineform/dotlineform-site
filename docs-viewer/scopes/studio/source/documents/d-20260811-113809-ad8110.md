# Implementation Review

## Purpose

Define one maintained implementation-review model for deciding whether a completed change still agrees with the repository's intended responsibilities and architectural boundaries. The model separates behavioral testing from architectural conformance, makes mechanically observable contradictions automatic where useful, and keeps irreducible design judgments visible as human review rather than pretending they have been tested.

This feature does not create an all-purpose quality score. It gives each review question an owner, trigger, enforcement kind, evidence source, and explicit result so that "reviewed" has a bounded meaning at delivery closeout.

## Current Starting Point

[Development Checklist](/docs/?scope=studio&doc=d-20260523-190651-7157ec) already contains ownership gates for public/local applications, configuration and projection, browser JavaScript, Docs Viewer runtime, generated data, writes, and security. Its End-Of-Delivery Review asks an independent reviewer to inspect the changed contract and final diff for ownership drift, duplicated contracts, hidden coupling, compatibility residue, dead paths, and missing evidence.

[Testing](/docs/?scope=studio&doc=d-20260501-174746-efd581) owns behavioral and contract evidence selection. [Run Checks](/docs/?scope=studio&doc=d-20260501-174746-f92667) owns maintained executable check profiles. Focused audits under `tests/` or an application-owned test directory own any repeatable conformance evidence that is useful enough to retain.

These pieces are useful but do not yet form one implementation-review contract. There is no maintained inventory of review questions, no classification of which questions are automatic or human, no reliable trigger map from the changed contract to applicable review areas, and no single result that distinguishes a mechanical pass from a judgment still requiring review.

## Core Distinction

| Activity | Primary question | Result meaning |
| --- | --- | --- |
| behavioral testing | does the implementation produce the required behavior and reject invalid behavior? | the exercised contract behaved as asserted |
| architectural conformance | does mechanically visible code/config agree with a declared ownership or dependency rule? | the declared rule agrees with the inspected implementation evidence |
| human implementation review | are the declared responsibilities, boundaries, omissions, and tradeoffs themselves correct and complete? | a reviewer accepted or challenged the design judgment within the stated scope |

A feature may work perfectly while violating an intended responsibility boundary. An implementation may also satisfy every static boundary while behaving incorrectly. Neither result substitutes for the other.

## Review Rule Contract

Each maintained review rule should state:

- a stable rule id and review-area owner;
- one precise review question;
- the change or contract conditions that trigger it;
- whether enforcement is `automatic`, `human`, or `hybrid`;
- the exact code, config, manifest, diff, report, or runtime evidence inspected;
- the durable document that defines the intended boundary;
- the result vocabulary and failure or review-required message; and
- any narrow exception mechanism, including its owner and removal or reconsideration condition.

The exact storage schema and runner are delivery decisions. The conceptual result states are:

- **pass** — the applicable automatic rule agrees with its declared evidence, or the required human judgment has been recorded as accepted;
- **fail** — an automatic contradiction or rejected human review blocks closeout;
- **review required** — automation can collect evidence but cannot establish the governing judgment; and
- **not applicable** — the rule's documented trigger does not intersect the changed contract.

An unresolved `review required` result is not a green review. Automatic evidence may narrow the human question, but it cannot silently answer it.

## Area/Delivery Children

The default planning unit beneath this feature is one combined **area/delivery** document. It owns one coherent family of review questions, classifies its automatic and human parts, identifies the implementation evidence and likely integration, records any staged checkpoints, and defines its own acceptance boundary.

This intentionally avoids creating a concept, architecture document, delivery record, and audit specification for every small review area. Split an area into separate concept, architecture, or delivery children only when it has multiple independently complete outcomes, materially different owners, an unresolved design that must outlive one implementation, or enough implementation sequence that one document would stop being a readable current plan.

Each area/delivery child should contain, as applicable:

1. the review question and why successful behavior alone cannot answer it;
2. current durable owners and mechanically inspectable evidence;
3. the automatic, human, and hybrid rule boundary;
4. triggers that make the area applicable to a change;
5. proposed command, report, manifest, or review-prompt integration;
6. bounded implementation checkpoints and stop conditions;
7. acceptance evidence and known unautomatable claims; and
8. the durable documentation destinations required at closeout.

The child can move through `draft`, `proposed`, `in-progress`, and `done` as its delivery state. Completion means that review area is implemented and durably documented; it does not imply that every review area under this parent exists or is complete.

## Initial Review Areas

Create area/delivery children only when the review contract is concrete enough to implement. The likely set currently includes:

1. **Capability composition** — public-safe, shell-composed, and named-adopter agreement across modules, stylesheets, loaders, and registries. [Docs Viewer Capability Composition Audit](/docs/?scope=studio&doc=d-20260811-112331-1f131b) is the first child.
2. **Frontend/backend responsibility** — presentation and ephemeral interaction versus authoritative validation, policy, writes, path confinement, service orchestration, and exact read-model projection.
3. **Source/config/projection ownership** — one canonical owner, positive browser-safe projection, named consumer, and no duplicated application model.
4. **Write authority and failure handling** — capability gates, exact targets, preview/apply boundaries, partial failure, rollback, retry, logging, and cleanup.
5. **Lifecycle and state ownership** — construction, registration, refresh, stale-result replacement, release, navigation, and teardown responsibility.
6. **Cohesion and residue** — duplicated contracts, hidden coupling, compatibility aliases, obsolete callbacks, dead paths, and responsibilities accumulating in coordinators.
7. **Evidence and completion claims** — agreement between the delivery's claims, inspected surface, automated evidence, manual review, omissions, and durable documentation transfer.

This list is a review map, not permission to create empty placeholder documents or implement a generic rule engine. An area should become a child when a current delivery or repeated review problem supplies a real question and useful evidence.

## Frontend/Backend Review Boundary

Frontend/backend responsibility is a hybrid review area rather than a universal rule that all domain logic belongs on one side. The browser may own presentation, local interaction state, request coordination, and exact read-model adaptation. The backend owns authoritative validation, write permission, filesystem and source confinement, private policy, mutation ordering, and failure-safe application. Shared domain calculations may have a focused owner on either side when their inputs, authority, and duplication boundary are explicit.

Automation can inspect imports, endpoint and capability registration, projected fields, browser-visible paths, duplicated identifiers, and configured owners. Human review must still decide whether the workflow has the correct authoritative owner, whether validation is duplicated or merely defended at both boundaries, whether a browser projection is necessary, and whether orchestration has drifted into a route controller or oversized backend service.

## End-Of-Delivery Use

For a material implementation, the delivery declares its changed contracts and relevant review areas. A maintained review command or report may combine those declarations with changed-path evidence to select applicable rules, execute automatic checks, and print the exact human or hybrid questions that remain. Changed paths alone are insufficient because a small code diff can alter a broad contract and generated or watcher output can obscure the authoritative source change.

The resulting review record should identify the delivery or bounded change, applicable areas and rules, automatic evidence, recorded human judgments, failures, omissions, and durable follow-through. It should be cheap enough to use before closeout and should not require every application smoke, browser route, external workspace, or broad repository audit unless the selected review area genuinely needs that evidence.

"Automatic and maintained" means that an automatic rule has checked source/config ownership, a stable executable owner, focused verification of the auditor itself, documented profile or review-runner integration, and an identified durable rule owner. It does not mean that every implementation judgment is converted into a regular expression, test, Git hook, or background process.

## System Ownership

- Development Checklist owns when implementation review is required and the concise human closeout gate.
- This feature and its eventual durable successor own the review-rule model, enforcement kinds, result meanings, and area navigation.
- Run Checks owns reusable command/profile execution where an automatic rule belongs in normal developer evidence.
- Focused test/audit owners retain reusable conformance evidence when a report is more useful than a binary gate.
- Testing owns behavioral evidence selection and remains separate even when the same low-level script technology is used.
- Application and architecture documents own the actual boundaries being reviewed; the review system references them rather than becoming a second architecture authority.

## Boundaries

- No aggregate code-quality score, risk leaderboard, or application-wide green badge is introduced.
- A passing automatic rule never represents unresolved human review as complete.
- The framework does not require every delivery to run every rule or broad profile.
- The review inventory does not become runtime configuration or grant application capability.
- Review rules inspect and report; they do not rewrite implementation code, configuration, manifests, tests, or documentation.
- Heuristic evidence such as file size, churn, import count, or repeated tokens may prompt review but does not by itself prove bad architecture.
- The feature does not require pull requests, a hosted forge, continuous integration, or multiple human reviewers; those may consume the same review contract later without defining it.

## Suggested Internal Order

1. Use Capability Composition to prove the combined area/delivery shape and the automatic/human distinction on one concrete boundary.
2. Freeze the minimal shared rule vocabulary, trigger model, result shape, and relationship to Development Checklist, Run Checks, focused audits, and Testing.
3. Add Frontend/Backend Responsibility as the next area only after the first child shows which evidence can be maintained without building a generic dependency engine.
4. Add further children in response to repeated concrete review problems, keeping each independently useful and closeable.
5. Transfer the stable review method into a durable methodology owner before treating the parent feature as complete.

## Success Meaning

The feature succeeds when a material implementation can identify the review areas it touches, run one maintained review path for the automatic portions, see the remaining human questions explicitly, and produce a bounded review result whose claims cannot be confused with behavioral test coverage. Each implemented area has its own concise child plan and durable rule owners, while the parent remains a navigable framework rather than an ever-growing checklist or generic quality engine.
