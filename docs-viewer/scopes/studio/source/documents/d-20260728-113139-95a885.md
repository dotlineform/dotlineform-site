# Independent Canonical Documents

## Purpose

Docs Viewer can own canonical documents and document relationships whose
initial identity or content came from canonical data in another application.
Creation establishes a new Docs Viewer source; it does not establish an
ongoing replica.

This lets Studio remain canonical for structured records while Docs Viewer
becomes canonical for the documents that explain, interpret, or refer to those
records.

## Mental Model

```text
Studio canonical record
    -> optional creation-time validation and one-time seed
    -> canonical Docs Viewer source

Studio record -------------------- independent later lifecycle
Docs Viewer source --------------- independent later lifecycle

optional cross-application identity
    -> may resolve
    -> may become stale
    -> is diagnosed or repaired by its owning workflow
```

Canonical ownership is contextual rather than global:

- Studio JSON is canonical for the Studio record.
- Docs Viewer Markdown/front matter is canonical for the document.
- Generated document payloads, public projections, search indexes, reports, and
  usage indexes are rebuildable projections of their owning source.

Calling the document canonical does not make it authoritative for the Studio
record, and calling the Studio record canonical does not make the document a
generated cache.

## One-Time Seeding Is Not Synchronization

A producing workflow may:

- allocate a stable document identity;
- create a source document from selected record fields;
- validate the initial association;
- store a one-way document reference; and
- rebuild the resulting Docs Viewer projections.

After creation:

- editing the Studio record does not edit the document;
- editing the document does not edit the Studio record;
- deleting the Studio record does not delete the document;
- deleting the document does not edit the Studio record; and
- neither side infers a replacement from title, content, or other mutable data.

A later workflow may offer explicit inspection or repair, but repair is a user
action over an acknowledged stale relationship. It is not background
synchronization.

## Structural Validation And Tolerant References

Docs Viewer validates the contracts it owns:

- source and front-matter structure;
- identity shape and configured collection confinement;
- token or reference syntax;
- safe generated and public payload structure; and
- the paths and capabilities of its own mutations.

It does not become the business-data validator for every application named by
a document relationship. A cross-application identity may no longer resolve,
and that state does not by itself invalidate the document or block publication.

[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61)
already follows this pattern. Authoring validates a selected target at
insertion, while rebuilding is tolerant: an unresolved occurrence does not
block the document build, and diagnosis belongs to Docs Broken Links rather
than a synchronization process.

[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c)
uses the complementary direction. A tag stores a one-way `doc_id`, while the
document carries no tag back-reference. Either side may be deleted
independently, leaving an unreferenced document or a stale registry identity.

## Consequences For Collection Management

A Docs Viewer collection must manage its documents on their own terms:

- list every locally manageable document, including unreferenced and
  non-viewable documents;
- use Docs metadata such as title, Status, and visibility rather than copying
  Studio fields into the collection index;
- allow exact document edits and deletions without consulting an external
  canonical owner;
- preserve stale external relationships as diagnosable states;
- avoid background repair, cascading deletes, or inferred associations; and
- keep public publication independent from local management metadata.

The collection may contain duplicate titles, independently authored documents,
or documents with no external association. Those are valid document states,
not evidence that the collection must be synchronized with another registry.

## Invariants

- One application does not become a write proxy for another merely because it
  consumed its canonical data at creation.
- Every ongoing mutation has one canonical owner and one explicit write path.
- Cross-application identities are references, not shared ownership.
- Initial validation does not imply permanent referential integrity.
- Stale or broken references are visible and repairable without blocking
  unrelated document management or publication.
- Generated outputs remain derived even when their source was initially seeded
  from another canonical system.
- Public readers receive only the projection required for reading; they do not
  receive canonical Studio data or local repair capability.

## Non-Goals

- bidirectional synchronization;
- automatic propagation of edits or deletes;
- a cross-application transaction bus;
- inferred matching by mutable labels or content;
- background stale-reference repair;
- copying complete Studio records into Docs Viewer; or
- making Docs Viewer responsible for validating Studio's domain semantics.

The [Sub-Scope Index feature](/docs/?scope=studio&doc=d-20260728-113139-285eae)
applies this concept to generic collection navigation and management.
