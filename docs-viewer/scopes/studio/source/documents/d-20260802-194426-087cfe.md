# SSP-1 — Sub-Scope Subject And Association Delivery

## Status And Purpose

Proposed as **SSP-1**, the first [Sub-Scope Publishing](/docs/?scope=studio&doc=d-20260802-194357-4d857b) delivery. [Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee) owns the typed-subject, cardinality, projection, access, refresh, and failure contracts implemented by this delivery.

SSP-1 establishes source-to-manifest identity before Project State, Resolver Tokens, collection-aware transfer, Tag primary selection, or public Work metadata consume it.

## Complete Outcome

The registered `dotlineform/projects` customisation accepts zero or one of `folder_path` and `work_id`; the registered `analysis/tags` customisation accepts optional canonical `tag_id` alongside its existing group metadata. Each customisation validates and projects one normalized typed subject into its exact manifest row.

Generated focused associations map each normalized folder, Work, or Tag subject to deterministic arrays of exact document targets. Several documents may declare one subject. Missing declarations, malformed values, duplicates, unknown external identities, non-viewable documents, and unavailable public locations retain explicit bounded behavior. SSP-1 adds no Resolver rendering, Project State scan, copy workflow, Registry primary mutation, or Work-page presentation.

## Delivery Discipline

SSP-1 extends the two existing registered sub-scope customisations and their current manifest builders. It must not introduce a generic metadata framework, graph database, relationship query language, registry scanner, nested sub-scopes, or cross-system lifecycle synchronization.

SSP-1.0 records exact files, reused customisation/build/location seams, and rough production/test diff before implementation. If the shared subject representation requires widespread generic builder changes rather than bounded customisation composition, stop for review.

## Rough Delivery Steps

### SSP-1.0 — Trace And Freeze Subjects

- [ ] Trace Projects `folder_path` validation/edit/import/manifest behavior, Analysis Tags group projection, sub-scope public and Manage manifests, document-location projection, and targeted collection rebuilds.
- [ ] Freeze scalar string syntax and normalization for `work_id` and `tag_id`, at-most-one Project subject validation, missing/unknown identity states, and exact typed manifest shape.
- [ ] Freeze Manage and public association schemas, deterministic ordering, duplicate documents, visibility filtering, exact document target identity, generation metadata, and stale/unavailable behavior.
- [ ] Freeze customisation-owned metadata transfer declarations needed later by SSP-4: `folder_path` remains Projects-only while `work_id` uses one explicit compatible contract for Projects and `analysis/works`.
- [ ] Record exact files, reused seams, rough production/test diff, and any proposed expansion before implementation approval.

**Checkpoint:** reviewed fixtures cover no Project subject, folder subject, Work subject, both Project fields, malformed and unknown Work IDs, zero/one/many documents per folder or Work, Tag with and without `tag_id`, duplicate Tag associations, viewable/non-viewable documents, and unavailable public locations. Stop before implementation.

### SSP-1.1 — Implement Project Subjects

- [ ] Extend the Projects customisation with scalar-string `work_id` validation, metadata read/write, import handling, and at-most-one subject enforcement.
- [ ] Project normalized `{kind, key}` subject data while retaining the current `folder_path` behavior and exact `{scope, sub_scope, doc_id}` targeting.
- [ ] Produce deterministic folder-to-documents and Work-to-documents association products without reading live folder or catalogue relationships during manifest projection.
- [ ] Keep local paths and non-viewable working document locations out of public products.

### SSP-1.2 — Implement Tag Subjects

- [ ] Extend the Analysis Tags customisation with explicit scalar-string `tag_id` validation and typed manifest projection without inferring identity from title or group.
- [ ] Produce deterministic Tag-to-documents associations through exact document targets and public-safe locations where available.
- [ ] Preserve existing group filtering and report behavior independently from canonical Tag identity.
- [ ] Publish the complete Tag association set for Registry/editor and analysis consumers without reading Registry `doc_url[]` as membership input.
- [ ] Do not mutate Tag Registry `doc_url[]` or choose a primary document in SSP-1; SSP-5 owns migration to the scalar `primary_document` policy.

### SSP-1.3 — Verify And Transfer

- [ ] Run focused customisation, source metadata, import, manifest, location, public-isolation, targeted-build, lint, and whitespace checks.
- [ ] Prove several documents may declare one subject while ordinary creation may remain temporarily unlinked.
- [ ] Prove no subject is inferred from title, filename, body, route, selected row, report host, or UI state.
- [ ] Update SSP-2, SSP-3, SSP-4, and SSP-5 with the accepted subject and association schemas before any of those deliveries begins.

## Completion Evidence

- Project source accepts exactly zero or one normalized folder/Work declaration and rejects both without precedence.
- Tag source uses explicit canonical `tag_id`; existing group metadata remains a separate concern.
- Manifests project one typed subject per declaring document and preserve zero-to-many association cardinality.
- Manage products retain exact working document targets; public products contain only allowed public-safe locations and no local folder paths.
- Association generation performs no Project State scan, Resolver expansion, copy, Registry mutation, or Work payload mutation.
- The accepted transfer contract makes later `work_id` retention explicit rather than relying on matching field names.

The [Sub-Scope Publishing feature](/docs/?scope=studio&doc=d-20260802-194357-4d857b) owns sequencing. SSP-1 stops after source, manifest, and focused association foundations; each downstream consumer retains its own delivery gate.
