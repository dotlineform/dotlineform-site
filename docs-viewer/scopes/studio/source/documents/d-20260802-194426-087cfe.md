# SSP-1 — Document Subject And Association Delivery

## Status And Purpose

Proposed as **SSP-1**, the first [Sub-Scope Publishing](/docs/?scope=studio&doc=d-20260802-194357-4d857b) delivery. [Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee) owns the typed-subject, cardinality, projection, access, refresh, and failure contracts implemented by this delivery.

SSP-1 establishes source-to-manifest identity before Project State, Resolver Tokens, collection-aware transfer, Tag primary selection, or public Work/Series metadata consume it.

The feature-level sense check is settled by the architecture. SSP-1.0 confirms implementation fit and current owners only; it does not reopen the one-working-collection, optional-metadata, or non-gating publication decisions.

## Complete Outcome

All working documents may remain in `dotlineform/projects`. Its documents follow the authoring convention of zero or one of `folder_path`, `work_id`, and `series_id`. `folder_path` remains Projects-specific; `work_id` and `series_id` become optional document-level catalogue association fields understood in any managed or published collection. The registered `analysis/tags` customisation continues to accept optional canonical `tag_id` alongside its existing group metadata.

The source reader projects normalized subject state and deterministic folder-, Work-, Series-, or Tag-to-document associations without inferring identity. Several documents may declare one subject. Missing metadata is ordinary. Malformed or conflicting catalogue declarations are excluded from associations and exposed as non-blocking authoring evidence; they never prevent saving, Copy, viewability changes, or publication.

Manage indexes show a compact subject cue derived from the normalized manifest row: folder icon for `folder_path`, catalogue icon for `work_id` or `series_id` with an exact accessible label, and no icon when no subject is declared. The cue is not lifecycle status, eligibility, or target-existence proof. The same exact Work/Series association output becomes the input to curator-facing catalogue document coverage; Studio Works reporting retains presentation and scheduling ownership. SSP-1 adds no Resolver rendering, Project State scan, copy workflow, Registry primary mutation, public reverse lookup, or catalogue-page presentation.

## Delivery Discipline

SSP-1 extends the existing Projects and Tags customisations, adds one bounded document-level Work/Series metadata reader, and composes the current manifest and Manage-index owners. It must not introduce a generic metadata framework, graph database, relationship query language, registry scanner, new working sub-scope, nested sub-scopes, or cross-system lifecycle synchronization.

SSP-1.0 is a short scope-and-spec sanity gate. It confirms the current broad owners, likely blast radius, deliverables, risks, and stop condition without freezing an exact implementation. Each implementation step ends with focused evidence and an independent code/diff review before the next step begins. If the shared subject representation requires widespread generic builder changes rather than bounded source-reader and manifest composition, stop for review.

## Delivery Steps

### SSP-1.0 — Confirm Scope And Delivery

- [ ] Sanity-check optional Projects/Work/Series/Tag authoring subjects, focused associations, and Manage index cues against the current registered customisations, source readers, manifest builders, Index presentation, document-location projection, and targeted collection rebuild model; resolve only contradictions that would change the result.
- [ ] Confirm the broad blast radius across shared and Projects-specific front matter, customisation validation/import, Manage manifests, focused association products, Index cues, locations, and downstream SSP transfer dependencies.
- [ ] Confirm the deliverables: optional scalar subjects, deterministic exact-target associations, non-blocking invalid/conflict evidence, Manage-only folder/catalogue cues, public isolation, focused evidence, and concise durable owner updates.
- [ ] Stop for review if the result requires a generic metadata framework, widespread generic builder changes, live relationship scans during manifest projection, or another boundary excluded above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, scheduling dependency, broad owners, blast radius, deliverables, risks, public/Manage boundary, and stop condition. Stop before implementation approval.

### SSP-1.1 — Implement Authoring Subjects And Manage Cues

- [ ] Retain scalar-string `folder_path` metadata read/write, import handling, and exact `{scope, sub_scope, doc_id}` targeting in `dotlineform/projects`; add shared scalar-string `work_id` and `series_id` reads without tying them to a collection.
- [ ] Project normalized `none`, valid folder, valid Work, valid Series, malformed, and conflicting authoring states while preserving raw canonical source and keeping every state saveable, copyable, and publishable.
- [ ] Produce deterministic folder-, Work-, and Series-to-documents associations for valid declarations, with exact document-location descriptors usable by later Studio Works coverage reporting, without reading live folder or catalogue relationships during manifest projection or broadening Work/Series identity through membership.
- [ ] Add Manage-index folder and catalogue subject cues from normalized manifest metadata, with exact accessible labels and no icon for a no-subject document; use a bounded authoring warning for malformed/conflicting declarations.
- [ ] Keep local paths, private association products, invalid-source detail, and Manage cue data out of public products.

**Checkpoint:** focused source metadata, Projects customisation, import, manifest, association, Index presentation, location, targeted-build, lifecycle-non-gating, and public-isolation evidence passes. An independent code/diff review confirms folder meaning remains Project-specific, Work/Series metadata remains collection-independent, no-subject publication survives, cues remain observational, and Project State/public reverse lookup retain downstream ownership. Stop before SSP-1.2.

### SSP-1.2 — Implement Tag Subjects

- [ ] Extend the Analysis Tags customisation with explicit scalar-string `tag_id` validation and typed manifest projection without inferring identity from title or group.
- [ ] Produce deterministic Tag-to-documents associations through exact document targets and public-safe locations where available.
- [ ] Preserve existing group filtering and report behavior independently from canonical Tag identity.
- [ ] Publish the complete Tag association set for Registry/editor and analysis consumers without reading Registry `doc_url[]` as membership input.
- [ ] Do not mutate Tag Registry `doc_url[]` or choose a primary document in SSP-1; SSP-5 owns migration to the scalar `primary_document` policy.

**Checkpoint:** focused Tag customisation, manifest, association, group-filtering, location, targeted-build, and public-isolation evidence passes. An independent code/diff review confirms canonical Tag identity remains declaration-owned, Registry membership/primary mutation remains SSP-5-owned, and shared subject composition stayed bounded. Stop before SSP-1.3.

### SSP-1.3 — Verify And Transfer

- [ ] Run focused customisation, source metadata, import, manifest, location, public-isolation, targeted-build, lint, and whitespace checks.
- [ ] Prove several documents may declare one subject while ordinary creation, Copy, viewability, and publication remain valid with no declaration.
- [ ] Prove no subject is inferred from title, filename, body, route, selected row, report host, or UI state.
- [ ] Perform the independent final code/delivery review, reconcile the completion claims with exact evidence and omissions, and record any bounded follow-up trigger.
- [ ] Update SSP-2, SSP-3, SSP-4, SSP-5, and SSP-6 with the accepted subject, association, Manage-cue, and transfer schemas before any of those deliveries begins.

## Completion Evidence

- `dotlineform/projects` remains the one normal working collection and accepts zero or one folder/Work/Series declaration by authoring convention.
- `work_id` and `series_id` are optional document metadata in any collection; neither absence, malformed input, nor a conflict prevents ordinary lifecycle or publication.
- Tag source uses explicit canonical `tag_id`; existing group metadata remains a separate concern.
- Manifests project normalized authoring state and preserve zero-to-many association cardinality for valid declarations.
- The Work/Series association product supplies exact document targets and current location descriptors for the curator catalogue-document coverage requirement; the eventual Studio Works route remains presentation-owned.
- Manage indexes show observational folder/catalogue cues without creating another report, subject picker, or eligibility control.
- Manage products retain exact working document targets; public products contain only allowed public-safe locations and no local folder paths.
- Association and cue generation performs no Project State scan, Resolver expansion, copy, Registry mutation, or public Work/Series payload mutation.
- The accepted transfer contract makes generic `work_id`/`series_id` retention and Projects-specific `folder_path` omission explicit.

The [Sub-Scope Publishing feature](/docs/?scope=studio&doc=d-20260802-194357-4d857b) owns sequencing. SSP-1 stops after source, manifest, and focused association foundations; each downstream consumer retains its own delivery gate.
