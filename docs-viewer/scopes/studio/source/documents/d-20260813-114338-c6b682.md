# Studio Documentation Maintenance

Restore a concise, trustworthy Studio documentation baseline and make exact document relationships easier to maintain as links change.

The current Studio subtree is broad and mostly flat. Some current owners are easy to find from the Studio entry page, while other low-level, overlapping, or manually maintained documents require deliberate review. This feature treats content authority and parent ownership separately: mentioning Studio code does not by itself make a document a Studio child.

## Delivery Order

1. [SDM-1 — Studio Documentation Rationalisation](/docs/?scope=studio&doc=d-20260813-114338-0e7cb9) reviews the current corpus, presents exact proposed document and link changes, and applies only an approved rationalisation.
2. [SDM-2 — Documents Linking Here Report](/docs/?scope=studio&doc=d-20260813-114338-95ca80) adds generated same-scope backlink visibility through the existing report-block contract.
3. [Search Mechanics](/docs/?scope=studio&doc=d-20260715-092247-6bbb5e) then owns the separate Studio full-text search delivery over the cleaned corpus.

SDM-2 is useful maintenance capability but is not a prerequisite for the SDM-1 audit. SDM-1 may use a one-off read-only link inventory so the product feature does not delay the baseline review.

## Current Starting Point

- the Studio subtree contains 39 documents, including 31 direct children of [Studio](/docs/?scope=studio&doc=d-20260423-000000-d015e6)
- the Studio entry page links to 15 of those 31 direct children
- current Studio-owned material also appears under cross-application Architecture, Search, Site, Testing, and Roadmap owners
- manually repeated inventories can drift; [Report Block Tokens](/docs/?scope=studio&doc=d-20260810-211748-1f8b6f) currently lists fewer reports than the source registry

These observations start the review; they are not automatic reparenting, consolidation, Notes-transfer, or retirement decisions.

## Boundaries

- Preserve exact `doc_id` identity when a retained document is reparented or revised.
- Decide ownership from the document's durable purpose and executable authority, not from its title, code-path mentions, or current parent alone.
- Keep durable current-state documentation distinct from Roadmap planning and completed feature history.
- Treat a move to external Notes, consolidation, or retirement as an explicit reviewed operation.
- Do not add search exclusions to hide documentation problems that should be resolved at source.
- Do not create a generic relationship graph, documentation database, or cross-application search layer.

## Success Meaning

The feature succeeds when the Studio entry and tree lead to the retained current owners without relying on stale manual inventories, a document can opt into an exact generated list of same-scope documents linking to it, and Studio full-text search can proceed over the accepted corpus as a separately bounded Search Mechanics delivery.
