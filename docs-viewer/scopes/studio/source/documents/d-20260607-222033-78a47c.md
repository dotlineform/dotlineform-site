# Docs Viewer Create And Import Endpoints

## `POST /docs/create`

Expected data:

```json
{
  "scope": "studio",
  "title": "New Doc",
  "parent_id": "d-20260424-000000-50b63f"
}
```

Actions:

- validates `scope` against configured docs scopes
- defaults blank titles to `New Doc`
- allocates an immutable `doc_id` and matching filename independently of the title
- validates `parent_id` inside the same scope when supplied
- writes a new Markdown source file under the configured scope root
- writes matching second-resolution `added_date` and `last_updated` values
- omits `viewable` for local-scope docs such as Studio, which makes them viewable by default
- writes `viewable: false` for public-scope docs such as Analysis, Library, and Moments
- rebuilds targeted generated docs payloads and targeted docs search for the new doc
- writes watcher-suppression markers for the new source file

Returned data includes the created doc identity, source path, viewer URL, mutation flags, rebuild diagnostics, summary text, and `dry_run`.

## Document Transfer Endpoints

### `POST /docs/document-transfer-preview`

Expected data:

```json
{
  "scope": "dotlineform",
  "sub_scope": "projects",
  "doc_ids": [
    "d-20260424-000000-50b63f"
  ],
  "target_scope": "analysis",
  "target_sub_scope": "works",
  "transfer_mode": "copy",
  "include_descendants": false
}
```

The preview is write-free. `doc_ids` is the exact checked set: there is no active-document or context-row fallback. Copy includes descendants only when requested and allocates fresh target identities. Move always expands the complete descendant closure, preserves identities, and requires writable source and target roots. Both modes remove parent/child overlap, retain included hierarchy, and place each effective root at the target scope root.

Planning inventories referenced source-scope media once, attaches registered build sources such as Mermaid `.mmd` inputs for referenced SVG, classifies retained external dependencies, and blocks missing bytes, incompatible roles/builds, and differing target bytes. Inline Mermaid remains canonical document source and creates no media-plan item.

The request resolves source and target as exact `{scope}` or `{scope, sub_scope}` collections. `sub_scope` and `target_sub_scope` are omitted for parent collections and required for configured child collections; neither may be inferred from a report host, title, filename, route, active document, or displayed row. The response records exact collection placement, target-default viewability, custom-metadata decisions, link decisions, blockers, warnings, and an `apply_plan` only when unblocked. Known inbound links from documents left in a parent source scope are title-based warnings rather than blockers: an explicit source-scope URL does not follow a moved identity automatically, but it can continue to work cross-scope after its `scope` value is updated. The apply plan is one bounded server-issued receipt containing exact collection identities, parent and collection configuration digests, document/media/build-source evidence, metadata and link decisions, parent-owned media roles, and the intended target rebuild owner. The browser returns it unchanged.

Manage exposes this Copy contract as **Copy to…** from checked parent-Index documents and from the default sub-scope report's immutable exact selection. The capability response lists each configured parent or child collection with its unambiguous label and Copy source/target flags. The browser excludes only the exact source collection, sends the registered selection target unchanged, and uses the same preview/confirmation workflow for both surfaces. Move remains parent-only.

### `POST /docs/document-transfer-apply`

Expected data:

```json
{
  "scope": "studio",
  "confirm": true,
  "apply_plan": {
    "schema_version": "docs_document_transfer_apply_plan_v2",
    "mode": "copy",
    "source": {
      "scope": "dotlineform",
      "sub_scope": "projects"
    },
    "target": {
      "scope": "analysis",
      "sub_scope": "works"
    },
    "operation_timestamp": "2026-07-24 15:20:00",
    "include_descendants": false,
    "requested_doc_ids": [
      "d-20260424-000000-50b63f"
    ],
    "source_parent_config_sha256": "...",
    "source_collection_config_sha256": "...",
    "target_parent_config_sha256": "...",
    "target_collection_config_sha256": "...",
    "media_owners": {
      "source": {"scope": "studio"},
      "target": {"scope": "notes"}
    },
    "target_rebuild_owner": {"scope": "analysis", "sub_scope": "works"},
    "target_default_viewable": false,
    "documents": [
      {
        "source_doc_id": "d-20260424-000000-50b63f",
        "source_sha256": "...",
        "target_doc_id": "d-20260724-152000-a1b2c3",
        "target_parent_id": ""
      }
    ],
    "media": [],
    "custom_metadata": [],
    "link_decisions": []
  }
}
```

Apply requires `confirm: true`, rejects `dry_run`, restores the previewed plan, and revalidates every bounded document, media, build-source, target, metadata, link, and configuration fact before mutation. Existing target bytes are reused only when exact; no document or media overwrite is permitted. Copy accepts exact parent or configured child collection receipts, creates documents only under that target root, and routes follow-through to the existing parent or exact child rebuild owner.

Copy transfers and verifies parent-owned media and registered build sources first, then creates fresh-identity documents. It applies the receipt's target-default viewability and custom-metadata decisions, preserves ordinary Folder/Work/Series fields without interpretation, rewrites only receipt-owned exact `doc` or `subdoc` links and planned media references, and rebuilds the exact target once. Its v2 result and activity payload identify exact `source` and `target` collection objects and return exact local target URLs. Move retains its parent-scope contract: it completes and rebuilds the target first, removes and rebuilds the exact source document set, then removes only transferred source media no longer referenced by remaining source documents.

Failures after a write return HTTP `409` with the exact collection and observed target media, build-source, and document state. Partial creates remain confined to the receipt's target collection and are never reported as success. This generalized pair is the only current Copy/Move route contract. There is no hidden rollback, retry, compatibility route, or success activity before required follow-through completes. The retired `/docs/copy-subtree-preview` and `/docs/copy-subtree-apply` paths are not aliases.

## `GET /docs/import-source-files`

Query parameters: none.

Returned data:

```json
{
  "ok": true,
  "candidates": [
    {
      "filename": "example.md",
      "source_format": "markdown",
      "candidate_kind": "ordinary_document",
      "validation_state": "ready",
      "target_mode": "ordinary_context",
      "target": null,
      "supports_docs_review": false,
      "supports_return_import": false,
      "docs_review_enabled": false,
      "import_enabled": true,
      "diagnostics": []
    },
    {
      "filename": "20260730-095512-document-content.jsonl",
      "source_format": "data_sharing_documents",
      "candidate_kind": "returned_package",
      "validation_state": "ready",
      "target_mode": "manifest_collection",
      "target": {
        "scope": "analysis",
        "sub_scope": "tags"
      },
      "target_label": "Analysis / Tags",
      "scope": "analysis",
      "sub_scope": "tags",
      "supports_docs_review": true,
      "supports_return_import": true,
      "docs_review_enabled": true,
      "import_enabled": true,
      "diagnostics": [],
      "document_count": 2
    }
  ]
}
```

Used for:

- rendering the context-independent app-level Import candidate list
- projecting candidate kind, exact target mode, effective Review/Import
  actions, safe disabled reasons, and display-only destination labels

The retained `files` array remains a compatibility projection; the
consolidated browser consumes `candidates`. Neither projection exposes source
bodies, returned records, trusted metadata payloads, or arbitrary paths.

Supported staged source formats:

- `html`: `.html`, `.htm`
- `docx`: `.docx`
- `markdown`: `.md`, `.markdown`
- `markdown_package`: direct child package folders containing exactly one Markdown file
- `text`: `.txt`
- `data_sharing_documents`: trusted supported Data Sharing `.json` or `.jsonl` document collections
- `edited_review_sources`: one complete trusted Docs Review `source/` folder

Standalone raster, SVG, and downloadable files are excluded. They belong to the active source editor's **Add image…** and **Add file…** actions.

Collection recognizers inspect untouched staged candidates before generic
normalization. A valid edited folder receives its retained review-folder label,
exact collection provenance, and return-Import capability in the listing while
`filename` remains the only staged request identity. Invalid claimed packages
remain blocked candidates when a safe diagnostic is available; an individually
selected review source is rejected before ordinary Markdown conversion.

Trusted returned document packages are classified directly from their staged
header and internal export metadata. Preparing Docs Review never preselects an
Import source.

## `POST /docs/import-source`

Expected data:

```json
{
  "scope": "studio",
  "sub_scope": "tags",
  "staged_filename": "example.md",
  "include_prompt_meta": false,
  "confirm_interactive_html_overwrite": false,
  "preview_only": false
}
```

`sub_scope` is omitted for a parent-scope run and required for one fixed
configured child destination.

Actions:

- validates `scope` and resolves `staged_filename` as a direct child of the W0-configured shared import drop-zone
- parses staged HTML, Markdown, Markdown packages, text, and trusted document collections
- converts import output to Markdown source
- validates generated Markdown with the shared Docs Viewer Markdown renderer
- uses the staged filename/title as source context and always allocates a fresh local document identity
- does not load target-scope documents or infer document replacement from filenames or titles
- atomically creates a new source document and refuses a last-moment target-path conflict
- uses `confirm_interactive_html_overwrite: true` only to confirm replacement of a colliding role-marked interactive HTML companion
- sets `last_updated` when the new document is created
- materializes inline raster or sanitized SVG media, package media, and interactive HTML assets only during write operations
- supports `preview_only: true` for non-writing preview responses
- rebuilds targeted generated docs payloads and targeted docs search after successful writes
- logs import-source activity when a create actually writes
- dispatches trusted returned packages and edited review-source folders to
  their complete collection planner/apply owners before ordinary formats

Returned data can include preview Markdown, allocated document identity,
operation type, media plans, interactive HTML plans, written media records,
created source path, rebuild diagnostics, summary text, `dry_run`, exact
`target`, and a validated local `viewer_url`. Ordinary results link to the
exact parent or child document. Collection results link to the exact owning
scope or sub-scope report. The browser must not synthesize or broaden that
route.

## Returned-Package Collection Import

Schema-aware Data Sharing JSON/JSONL collection planning and synchronous apply reuse `POST /docs/import-source`. The user selects the trusted server-listed staged package from the normal Docs Viewer Import Action.

The endpoints now use the shared `$DOTLINEFORM_PROJECTS_BASE_DIR/data-sharing/import-staging/` drop-zone. Endpoint services resolve it through `configured_workspace_paths(repo_root).import_staging`, return marker-rooted paths, and report import unavailable through the W0 workspace capability contract when the root cannot be used. They do not fall back to repo-local staging.

The service resolves a safe immutable staged-file identity through Data Sharing
metadata, detects supported package headers before the generic JSON/JSONL file
fallback, and normalizes document records before shared validation, media
planning, source writes, and rebuild work. This returned-package path never
uses the derived Docs Review `source/*.md` projection as content.

Collection planning uses the ordinary request identity with `preview_only: true`:

```json
{
  "scope": "library",
  "staged_filename": "returned-documents.jsonl",
  "preview_only": true
}
```

The body-free response covers every package record and includes package identity, server-planned create or overwrite actions, collisions, content intent, parent resolution, new-parent dependencies, media summaries, blockers, warnings, and confirmation readiness. Any invalid record or hierarchy error blocks the package. Planning never writes source or media and never invokes generation.

Confirmed apply uses `preview_only: false`, explicit confirmation, and the package identity, planned local identities, and planned package actions returned by the server:

```json
{
  "scope": "library",
  "staged_filename": "returned-documents.jsonl",
  "preview_only": false,
  "confirm": true,
  "export_id": "ds_...",
  "source_sha256": "...",
  "planned_identities": [
    {
      "record_index": 0,
      "source_doc_id": "package-doc",
      "doc_id": "d-20260715-120000-a1b2c3",
      "added_date": "2026-07-15 12:00:00"
    }
  ],
  "planned_actions": [
    {
      "record_index": 0,
      "action": "overwrite",
      "doc_id": "d-20260101-120000-b2c3d4",
      "target_doc_id": "d-20260101-120000-b2c3d4"
    }
  ]
}
```

`planned_actions` contains only server-issued `create` or `overwrite` actions for the complete valid package. Collection apply rejects record decisions, browser-authored target paths, generated source, and fields outside the request allowlist. `planned_identities` and `planned_actions` are confirmed-plan receipts, not browser allocation or selection surfaces.

Apply rereads the staged package and recomputes the current plan. Changed package identity, server-planned actions, hierarchy validity, or blocker state returns `preview_only: true`, `reconfirmation_required: true`, and a refreshed plan without writes. If the confirmed plan remains valid, records are written synchronously in package order. A source-write failure preserves earlier writes, stops later writes, and marks remaining records not attempted; asset failures warn and continue. Docs and search generation runs once after mutation and is reported separately from source outcomes.

The final response includes `outcome`, `source_mutation`, `generation`, ordered `records`, grouped and counted created/overwritten/failed/not-attempted records, warnings, and manual-copy instructions. The browser presents that result directly. Confirmed apply does not create a separate result document or result-specific log.

## Edited Review-Source-Folder Import

The same endpoint accepts one server-listed `edited_review_sources` folder.
Preview uses the normal collection request:

```json
{
  "scope": "analysis",
  "sub_scope": "tags",
  "staged_filename": "edited-tags-review",
  "preview_only": true
}
```

The recognizer validates direct Markdown membership, strict review provenance,
the retained `docs_review_validated_package_v1` manifest, trusted export
metadata, `supports_return_import: true`, exact prepared `doc_id` membership,
scope/sub-scope routing, and complete prepared `source_last_updated` evidence.
The browser-visible `display_name` is presentation only and is never accepted
as `staged_filename`.

The body-free preview is overwrite-only and contains the exact collection,
document count, folder hashes, prepared versions, every canonical target,
blockers, planned overwrite actions, and one `derived_markdown_fidelity`
warning. Creates, record decisions, nested source, standalone reviewed
Markdown, and cross-collection fallback are rejected.

Confirmed apply submits `preview_only: false`, `confirm: true`, and the exact
`export_id`, `source_sha256`, `trusted_metadata_sha256`,
`planned_identities`, and `planned_actions` returned by preview. The service
rereads the folder and metadata, replans against current canonical sources, and
returns a refreshed preview with `reconfirmation_required: true` if either
source side changed.

An unchanged confirmed plan enters one atomic destination boundary. Parent
scope apply snapshots every exact source and performs the targeted Docs/search
rebuild. Child apply reuses the configured sub-scope snapshot and confined
rebuild with no parent search rebuild. Any source-write or rebuild failure
restores every source in the selected collection set, rebuilds the restored
projection, and reports no successful overwrite.

Only edited body, title, and summary advance canonical `last_updated`; unchanged
documents preserve it. Review transport dates never replace canonical
`added_date` or `last_updated`. Parent and visibility may apply only for a
parent collection; configured child hierarchy, `group`, `ui_status`, and
visibility remain destination-owned.
