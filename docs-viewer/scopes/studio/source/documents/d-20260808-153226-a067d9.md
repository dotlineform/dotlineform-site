# SSP-8 — Revised Model

## Status And Purpose

SSP-8.0 is complete and the delivery is stopped before SSP-8.1 schema implementation. The [SSP-8.0 sanity note](/docs/?scope=studio&doc=d-20260808-154427-50f717) confirms the existing mutation owners, independent state contract, `dotlineform` home and private boundary for the complete report, broad blast radius, risks, and stop conditions. SSP-8 follows the manual lifecycle review at the [SSP-7.4 review gate](/docs/?scope=studio&doc=d-20260808-134503-a4caeb) and supersedes SSP-7.5 verification and transfer. SSP-7 remains the historical delivery and evidence for the shipped `publishable` cutover, exact **Set Publishable…** action, lineage-aware New/Replace Copy, successful-Publish reconciliation, and initial Projects presentation. SSP-8 owns the revised state model, Delete participation, highest-state presentation, complete lineage reporting, migration, and final verification.

The revision starts from one clarified rule: a lineage is not an always-present working-to-editorial pair with optional publication evidence. It is a record whose **Working**, **Editorial**, and **Published** states are mutated independently by their existing owning actions. Deleting one state does not delete or rewrite another state.

## Revised Lineage Model

A lineage begins only when the configured lineage-aware Copy workflow copies an exact document from `dotlineform/projects` into `analysis/works`. A document created directly in either collection does not acquire lineage merely because it exists or is published.

The three states are:

- **Working** — the exact originating document in `dotlineform/projects`;
- **Editorial** — the exact independent document created or replaced in `analysis/works`; and
- **Published** — the current public projection recorded by the existing Analysis Publish workflow.

Working and Editorial are canonical documents. Published is a projection rather than a third canonical document. Once a lineage exists, any non-empty combination of its states may be valid. In particular, deleting Working does not remove Editorial or Published, and deleting Editorial does not remove Working or Published.

State presence in the canonical lineage record is sufficient. SSP-8 adds no parallel `present`, `deleted`, tombstone, or inferred filesystem-state field. A confirmed workflow action updates only the state it owns. The lineage record remains while at least one state remains and is retired only when its final state is removed.

## Mutation Owners

| Existing action | Exact lineage effect | States it must not change |
| --- | --- | --- |
| **Copy to… → New** | Starts a lineage branch for the exact Working document and adds its new Editorial document. | Published remains absent; other branches remain unchanged. |
| **Copy to… → Replace** | Replaces one exact current Editorial document and advances its existing copy evidence. | Working and Published remain unchanged. |
| **Delete Working** | Removes the exact Working state from every lineage branch containing that document. | Editorial and Published remain unchanged. |
| **Delete Editorial** | Removes that exact Editorial state from its lineage branch. | Working and Published remain unchanged. |
| **Publish** | After the ordinary successful scope-wide public mutation, records or clears Published state for each affected lineage branch. | Working and Editorial remain unchanged. |
| **Set Publishable…** | Changes only the Editorial document's next-Publish inclusion gate. | No lineage state changes until a later Publish changes Published state. |

These are extensions of the existing Copy, Delete, and scope-wide Publish actions. SSP-8 adds no lineage-specific Copy, Delete, unpublish, or per-document Publish control. Each action completes its ordinary document or public mutation first, then performs the small exact lineage follow-through appropriate to that action. It does not compare content, infer identity, scan the filesystem, repair another state, or repeat the initiating action.

## Required Lifecycle Results

The highest recorded promotion state is ordered **Working → Editorial → Published**.

### Editorial Delete While Published

```text
Working + Editorial + Published
  -- Delete Editorial --> Working + Published
  -- next Publish -----> Working
```

The Editorial Delete leaves the public projection and its recorded `{public_url}` intact. The Projects summary therefore remains **Published**. The next successful scope Publish removes the no-longer-sourced public projection and clears Published state, leaving **Working**.

### Exclude From The Next Publish

```text
Working + Editorial + Published
  -- publishable=false --> Working + Editorial + Published
  -- next Publish ------> Working + Editorial
```

`publishable: false` is a gate rather than a lineage state. The document remains **Published** until Publish removes its public projection, after which its highest state is **Editorial**.

### Working Delete

```text
Working + Editorial + Published
  -- Delete Working --> Editorial + Published
```

This is a valid continuing lineage. The Editorial document may remain editable and publishable, and a later Publish may retain or change Published state without reconstructing Working. Deleting Editorial later leaves Published until the next Publish; after the final Published state is cleared, the empty lineage record is retired.

### Editorial Delete Before Publication

```text
Working + Editorial
  -- Delete Editorial --> Working
```

Only Editorial is removed. The lineage continues to record the current Working state; a future explicit New Copy may add another Editorial state without recovering or inferring the deleted document.

## Unavailable Meaning

**Unavailable** is not a fourth promotion state and is not written by Copy, Delete, or Publish. It means a state identity remains recorded in the lineage JSON but the existing exact document-location owner cannot resolve that document. The expected cause is an out-of-workflow change such as manually deleting a source file from the filesystem.

The mutation workflow never checks physical file existence to decide what the lineage should contain. Reports may use the existing read-only exact resolver to decorate a recorded identity as unavailable, but they do not mutate, prune, repair, replace, or fall back from that identity. A state removed through the confirmed Delete workflow is absent, not unavailable.

Availability is diagnostic and does not automatically demote another surviving state. For example, a lineage with recorded Published evidence remains **Published** even if a lower recorded state is unavailable. The dedicated report design must decide how the highest state and any availability warning appear together without treating the warning as another promotion level.

## Reporting Ownership

### Projects Summary

The normal `dotlineform/projects` report remains a convenient summary for documents currently present in that collection. For each displayed Working document it derives one highest recorded promotion state across its lineage branches: **Working**, **Editorial**, or **Published**. Lesser stages do not replace the highest status.

Projects is not the complete lineage authority. Once Working is removed, the Projects report has no document row from which to show the surviving Editorial or Published states. It must not be used to count, audit, or reconstruct every document still participating in the workflow.

### Complete Document Lineage Report

SSP-8 adds a separate private report whose row source is the canonical lineage JSON itself. SSP-8.0 accepts the local `dotlineform` scope as its home; the exact host document, route, report customisation, columns, filters, narrow-layout treatment, and action boundaries remain a dedicated design decision.

The design must at least support:

- every current lineage branch, including Editorial-only, Published-only, and Editorial-plus-Published records whose Working state has been deleted;
- separate Working, Editorial, and Published state presentation without reconstructing a state from another state;
- exact stored identities and the existing `{public_url}` evidence, with absent states distinct from unresolvable recorded identities;
- one derived highest-state summary ordered Working, Editorial, Published;
- explicit unavailable diagnostics through the existing exact resolver, with no fallback or automatic repair; and
- complete private isolation from public Docs payloads, search, routes, and publication.

The report is initially read-only. SSP-8 does not add Copy, Delete, Replace, Publish, Set Publishable, filesystem-repair, or lineage-edit controls to it merely because it can see every lineage record.

## Persisted Contract Direction

SSP-8 retains one schema-versioned private canonical product at `docs-viewer/data/canonical/document-publication-lineage.json`. The revised schema represents independently optional Working, Editorial, and Published states. Absence of a state is the result of its owning workflow action; no explicit presence marker is required. Published state continues to need only its current `{public_url}` evidence and survives an Editorial Delete until the next Publish clears it.

The exact revised row shape, stable branch identity, zero-to-many behavior, ordering, and one-time migration from `docs_document_publication_lineage_v1` are frozen at SSP-8.1 rather than guessed in this proposal. The cutover must remain single-reader and single-writer: no alias, dual schema reader, inferred migration from file availability, or generic provenance registry.

The current table produced during SSP-7 review is explicit migration input. Any known workflow Delete that the v1 table failed to record is corrected deliberately during the cutover; it is not classified by scanning for missing files.
