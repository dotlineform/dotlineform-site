# SSP-8 — Revised Model

## Status And Purpose

SSP-8 is complete and parked at closeout review. The strict Working-owned table, exact New/Replace follow-through, Delete and Publish ownership, and Projects Editorial/Published presentation agree across the durable Sub-Scope Publishing, Sub-Scope Customisation, and Public Scopes owners. The earlier independently nullable Working, Editorial, and Published model was rejected after review exposed two simpler product facts:

1. lineage exists to trace what happened to a current Working document in `dotlineform/projects`; and
2. deleting editable canonical source must immediately remove its now-unmaintainable public projection rather than waiting for scope Publish.

## Working-Owned Lineage

The exact Working `doc_id` is the lineage key. Working is not a promotion state, carries no status, and needs no icon. SSP-8.2 removed the separate `lineage_id` because it duplicated the only identity that makes the record relevant.

One Working document may have zero, one, or several exact Editorial children in `analysis/works`. Every child exists only because the configured lineage-aware Copy created it. Directly created Working or Editorial documents do not acquire lineage from location, title, subject, public URL, or later publication.

The conceptual record is:

```json
{
  "working_doc_id": "d-working",
  "editorials": [
    {
      "doc_id": "d-editorial",
      "created_at": "YYYY-MM-DDTHH:MM:SSZ",
      "last_copied_at": "YYYY-MM-DDTHH:MM:SSZ",
      "published_url": null
    }
  ]
}
```

The exact persisted envelope is `docs_document_publication_lineage_v3` with required `working_collection`, `editorial_collection`, and `records` fields. Records sort by exact `working_doc_id`; Editorial children sort by exact `doc_id`. Both configured collection identities are stored once in the envelope, every record has at least one child, Working IDs are unique, and an Editorial ID belongs to only one Working record. There is no separate branch ID, nullable Working state, independent Published state, empty Working-only record, or v2 compatibility reader.

## Action Rules

### Copy

Copy looks up the exact Working `doc_id`:

- no Editorial children means the ordinary choice is **New**;
- one or more current Editorial children provide the exact **New** or **Replace** choices;
- New creates a fresh Editorial document and child;
- Replace selects one exact current Editorial `doc_id`, preserves its identity and `publishable` gate, and updates its copy evidence; and
- Copy performs no comparison, diff, merge, automatic choice, or publication.

### Publish

Scope-wide Publish remains the manually instigated positive promotion action. It sets or retains `published_url` for current publishable Editorial children and clears it only when an explicit `publishable: false` gate excludes that surviving child or its required public host. Editing content or setting `publishable: false` leaves the existing URL in place until Publish runs because the Editorial source still exists and remains editable. Publish no longer checks for missing source, removes source-deleted projections, or reports deletes; DPD-1 has already completed those removals.

### Delete Editorial

DPD-1 makes confirmed Editorial Delete immediately remove any exact current public projection and every impacted public inventory. SSP-8 follow-through then removes that exact Editorial child from its Working record. There is no Published-without-Editorial lineage state and no wait for a later Publish.

If the final Editorial child is removed, the record is removed: the still-existing Working document itself is enough to derive the absence of lineage and needs no empty table entry.

### Delete Working

Confirmed Working Delete removes its whole lineage record. It does not delete any Editorial child document or public projection. Those artifacts remain useful because the Editorial document is independently editable canonical source; they simply cease to be relevant to tracing a Working document that no longer exists.

An out-of-workflow filesystem deletion performs no lineage mutation. No builder or report scans for missing files to repair the table.

## Projects Presentation

Projects remains the complete presentation surface for this Working-owned purpose because every relevant lineage record has a current Working row.

For each Projects document:

- no Editorial child: no lineage status or icon;
- one or more Editorial children and no current `published_url`: Editorial status;
- any child with a current `published_url`: Published status.

When several children exist, Published is the highest displayed state. Exact child detail may expose every current Editorial target without inventing a primary child. At SSP-8 closeout, Projects retained no Folder, Work, or Series subject icon and Project State was their only owner; the later Projects Subject-column refinement deliberately superseded that presentation detail while keeping the icon meanings distinct. Analysis retains only its existing `publishable: false` exclusion icon.

SSP-8 no longer adds a complete orphan-lineage report. Once Working is deleted, the workflow has no lineage question to report. Editorial and public documents continue through their ordinary Analysis and public surfaces.
