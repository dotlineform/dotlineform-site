# Authoring Directives Concept And Examples

## Purpose

Some presentation and publication decisions are deliberate authoring choices rather than facts a runtime can infer. An Authoring Directive records that choice next to the affected Markdown block as an ordinary namespaced HTML comment.

The first consumer is Content Detail table eligibility and the second is table-to-SVG publication. A consumer acts only when it recognises the exact comment form and can associate it with the expected next table. Everything else is ignored and the Markdown renders normally. This is deliberately narrower than a validated Markdown extension language.

## Illustrative Source

The first maintained source shape is:

```markdown
<!-- dotlineform:table-detail -->

| Project | Folder | Series |
| --- | --- | --- |
| Nerve | projects/nerve | Series 105 |
```

The second maintained source shape is:

```markdown
<!-- dotlineform:table-publish format=svg id=project-state -->

| Project | Folder | Series |
| --- | --- | --- |
| Nerve | projects/nerve | Series 105 |
```

Each comment applies only when the next non-blank source block is the expected Markdown table. Intervening prose, another comment, a fence, or another block leaves it inert. This also makes stacked or contradictory comments harmless: only the comment immediately associated with the table can be considered. The SVG directive’s `id` is a stable author-supplied key within the document for generated-artifact ownership; it is not a DOM ID, URL fragment, or Content Detail table identity.

Working and exported Markdown retain the comment and table. Rendered HTML may also retain the ordinary invisible comment; comment removal is not a contract. When TE-2 exists, it adds a narrow marker to a table associated with the exact `table-detail` form. When TE-6 exists and has a complete current artifact, the public projection replaces the table associated with the exact `table-publish` form. Before those consumers exist, both comments do nothing.

## Recognition And Harmless No-Op

Recognition belongs to each consumer rather than a central directive subsystem:

- comments outside the exact `dotlineform:` namespace remain ordinary comments and are never interpreted;
- a malformed, unknown, misplaced, duplicated, or unsupported `dotlineform:` comment is ignored without failing the build;
- the underlying Markdown table remains ordinary semantic HTML whenever no consumer acts;
- the table-detail consumer recognises only its maintained comment and projects `data-docs-content-detail="table"` onto the associated semantic table;
- the Content Detail adapter queries that projected marker and never parses source comments or decides whether an unmarked table is large;
- the table-publication consumer recognises only its maintained comment, keeps local and Manage content semantic, and substitutes a complete current SVG only in the public projection; and
- no consumer needs to report comments it does not understand.

The `dotlineform:` namespace prevents accidental collisions but does not make a comment valid or mandatory. A document can move through scopes that have no consumer for it; the comment remains source text and the table remains usable.

## Table Authoring Outcomes

| authored state | result when the relevant consumer exists |
| --- | --- |
| ordinary Markdown table | semantic HTML table with no Content Detail control |
| table with `table-detail` directive | semantic HTML table carrying the narrow Content Detail eligibility marker |
| table with `table-publish format=svg` directive | linked SVG figure replaces that table in the public payload |

Both enhanced routes are explicit and opt-in. There is no size threshold, overflow measurement, automatic detection, or question at Publish time. Removing `table-detail` removes the detail control on the next build. Removing `table-publish` restores ordinary HTML publication on the next current build and publish. A typo has the same visible result as removing the comment: the table renders normally.

A document using `viewer_content_detail: table` declares that its sole semantic table is the default presentation. Its build independently projects the same table-detail eligibility marker, so a redundant `table-detail` comment is unnecessary. If a table-publication candidate is incompatible with that document-level presentation, the SVG consumer leaves the semantic table unchanged rather than failing the build.

## Prepared Projection Sequence

```text
canonical Markdown
  directive + semantic table
        |
        v
ordinary Docs build/watch
  recognise exact supported comments
  render the ordinary semantic table
  attempt SVG + manifest preparation
        |
        v
existing Publish preview/apply
  use only complete current preparation
  otherwise retain the semantic table
  copy an SVG only when consumed
        |
        v
public document
  linked SVG preview -> raw SVG in a new tab
```

The exact preparation owner is confirmed against the current media-producer and public-projection seams in TE-6.0. The architectural invariant is that authoring builds may render, while the Publish gate remains renderer-free. Publish never uses missing, partial, unsafe, stale, or source-mismatched preparation; it simply retains the ordinary semantic table for that candidate.

This follows the current public Mermaid boundary without requiring Mermaid’s light/dark family model. A table SVG should initially be one neutral, self-contained artifact unless visual testing proves a theme pair necessary.

## Public Figure Contract

The projected result is conceptually:

```html
<figure class="docsTableSvg">
  <a href="/path/project-state.svg" target="_blank" rel="noopener">
    <img src="/path/project-state.svg" alt="Project state table">
  </a>
  <figcaption>Project state</figcaption>
</figure>
```

The preview fits the ordinary document measure; clicking it opens the raw SVG in a new tab for full-viewport inspection and browser zoom. The SVG uses a `viewBox`, selectable native text rather than outlined glyphs, safe links only if explicitly supported, and the configured public SVG sanitization and media role.

The delivery must freeze how caption and alternative text are authored or derived for SVGs that are successfully projected. A large SVG table is not semantic HTML, so a useful adjacent summary or alternative description remains required. It must also decide whether table cell text remains in public Docs search or is replaced by caption/summary text; a search match that cannot be located in the visible document is not acceptable by accident.

## Identity And Regeneration

Generated identity is derived from the immutable document ID plus the recognised comment’s document-local `id`. A prepared manifest also records the recognised comment, semantic rendered-table digest, renderer/config version, and output digest. Editing table content, comment options, rendering rules, or relevant style makes the preparation ineligible for reuse; the ordinary table remains the fallback.

The exact public filename may be stable and versioned through existing media cache policy or content-addressed; TE-6.0 confirms that choice with stale-file cleanup. The source comment never contains the generated path.

## Copy, Move, And Source Authoring

Copy and Move preserve the comment because they preserve canonical Markdown. A target consumer may recognise it or ignore it independently. No transfer workflow generates SVG or rewrites the comment.

[TE-1 — Directive Insertion](/docs/?scope=studio&doc=d-20260802-163320-9015b0) is delivered first and adds one **Directives** control to the existing Manage Source main-view toolbar. It uses an Actions-style menu to list maintained source snippets and inserts the chosen predefined bytes at the captured insertion point. It is a typing shortcut, not the owner of directive recognition or validity.

The detail command inserts the complete `<!-- dotlineform:table-detail -->` form. The SVG command inserts `<!-- dotlineform:table-publish format=svg id=table-name -->` and selects only `table-name` for immediate replacement in the source. The menu does not guess an ID, open a modal, save, rebuild, report a success message, locate a target table, or detect an existing directive. Removal and correction remain ordinary source editing.

The UI is only a source-writing convenience. TE-1.0 may keep a blank-line or immediate-next-line pipe-table hint only if it is a trivial local check; neither is required and neither is validation. Save/Rebuild delegates recognition to the dedicated consumer, which ignores unsupported source quickly and cleanly. The implementation reuses the Source adapter’s revision-bound capture and `setRangeText` editing seam; it must not use `execCommand`, add a fake undo history, or promise undo behavior the native textarea does not provide.

## No-Op And Safety Contract

- unknown, malformed, misplaced, unsupported, or unassociated comments are ignored;
- an incomplete or unsafe SVG ID produces no artifact or substitution;
- duplicate generated identities are not consumed and their tables remain semantic;
- SVG rendering, sanitization, geometry, font, or media-publication failure produces no current consumable record for that table;
- stale preparation is never reused, but it does not block Publish;
- an incompatible document-level Content Detail hint leaves the semantic table unchanged; and
- an unmarked table is never converted because of width, row count, title, scope, or previous artifacts.

## Not In Scope

- executable directives, templates, macros, conditions, includes, variables, or arbitrary build commands;
- a central directive grammar, validator, capability registry, or diagnostics system merely because two bounded table consumers recognise adjacent comments;
- runtime comment scanning in public or Manage JavaScript;
- automatic conversion based on table size or viewport;
- changing canonical Markdown into an image reference;
- table editing, sorting, filtering, pagination, or SVG interaction beyond browser navigation and zoom;
- using a successfully projected SVG table as an accessible equivalent of semantic HTML without an explicit alternative-text/summary contract; or
- adding options, progress controls, or conversion decisions to Publish.

The initial Source action does not validate directive meaning, edit attributes after insertion, remove directives, offer a directive-management modal, infer or locate a target table, detect duplicates, or expose unshipped directive ideas.
