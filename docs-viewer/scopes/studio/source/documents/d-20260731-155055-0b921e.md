# New Sub-Scope Default Report Lifecycle Delivery

## Status And Purpose

Proposed as **SSR-2**, after SSR-1 has shipped the accepted default and
customisation framework.

This delivery makes the existing **New sub-scope** lifecycle create the normal
management surface needed to reach and populate that collection. The recreated
external-local `dotlineform` scope and its `projects` sub-scope are the focused
acceptance scenario, not a reason for Projects-specific lifecycle code.

## Complete Outcome

One confirmed New sub-scope apply creates:

- the configured one-level collection and confined source/output roots;
- one ordinary parent-scope report document explicitly associated with that
  collection;
- a parent index entry using the supplied collection title;
- valid empty local `manifest.json` and `manage-manifest.json` projections;
- refreshed parent docs/search and browser configuration; and
- an exact management URL that opens the default report.

The empty report shows a normal zero-document state and exact-collection New.
The user can create or import the first child without manually writing a host
document or running a builder.

## Fixed Boundaries

- This delivery consumes SSR-1's default; it does not copy Analysis/Tags
  configuration or implement another report scaffold.
- The host is an ordinary parent document, not a synthetic tree node or new
  route identity.
- The lifecycle records one exact collection/host association and never
  reconstructs it from title, filename, active document, or URL text.
- Creation uses the existing planned identity and atomic create-only boundary.
- Post-commit rebuild or presentation failure returns committed identities and
  retries follow-through only; it cannot create a duplicate.
- A new sub-scope omits customisation identity and therefore receives the
  default.
- Child documents remain excluded from parent Index, Recently Edited, and
  search payloads.
- Public visibility remains governed by existing scope and publication
  configuration.
- Delete preview/apply accounts for the exact lifecycle-associated host and
  fails closed on detached, ambiguous, changed, or missing association state.

## Delivery Checkpoints

### [ ] SSR-2.0 — Freeze Lifecycle Plan

- [ ] Trace current local, external-local, and public-parent preview/apply and
  delete paths.
- [ ] Freeze host front matter/body, planned identity, association owner,
  empty manifest pair, result fields, rebuilds, and final management URL.
- [ ] Define pre-commit versus committed follow-through failure responses.
- [ ] Define symmetric delete consequences and user-authored host-change
  presentation.

**Checkpoint:** preview names every identity, write, generated projection,
refresh, navigation result, and deletion consequence. Stop before mutation
work.

### [ ] SSR-2.1 — Service Apply And Empty Projections

- [ ] Extend write-free preview with the host and projection plan.
- [ ] Apply configuration, roots, host source, and empty projections through
  their existing mutation/build owners.
- [ ] Refresh parent docs/search and browser config without adding child rows
  to parent discovery.
- [ ] Preserve exact committed identities across build/follow-through failure.
- [ ] Cover confinement, collision, stale preview, partial failure, public
  isolation, and association deletion with focused service tests.

**Checkpoint:** direct service evidence creates exactly one collection, one
host, and complete empty projections. Stop before browser flow.

### [ ] SSR-2.2 — Browser Follow-Through

- [ ] Show host and projection consequences in the existing lifecycle
  preview/result workflow.
- [ ] After apply, reload configuration, refresh the parent index, and select
  only the returned host `doc_id`.
- [ ] Mount the empty default report with its correct toolbar and unavailable
  states.
- [ ] Prove New and app-level Import use the mounted `{scope, sub_scope}` with
  no parent, displayed-document, or URL fallback.

**Checkpoint:** the newly created collection is immediately usable through its
returned report URL.

### [ ] SSR-2.3 — External-Local Acceptance And Closeout

- [ ] Recreate the `dotlineform` external-local scope and `projects` sub-scope
  through the real lifecycle.
- [ ] Create or import a first Projects child and verify exact refresh and
  Source entry follow-through.
- [ ] Verify symmetric deletion and duplicate-prevention failure paths.
- [ ] Run focused lifecycle, builder, route/module, lint, whitespace, and
  generated-projection checks.
- [ ] Update the durable Scope Lifecycle and manifest owners, then stop for
  review before SSR-3.

## Out Of Scope

- Projects-specific fields, filters, row treatment, or actions;
- migration of existing manually hosted collections;
- recursive sub-scopes, rename, or broader scope-lifecycle redesign;
- automatic public promotion; and
- changing the default or customisation contract accepted in SSR-1.

## Completion Gates

- One apply creates exactly one configured sub-scope and one indexed host.
- Empty public-safe and Manage manifests load as normal zero-document state.
- New and Import receive only the mounted exact collection.
- Refresh/navigation failure cannot cause duplicate creation.
- Delete uses the exact stored association and cannot guess a host.
- Focused external-local acceptance proves the recreated workflow without
  implying every provider or report has received visual review.
