# New Sub-Scope Default Report Lifecycle Delivery

## Status And Purpose

Active as **SSR-2** after SSR-1 shipped the accepted default and customisation
framework. SSR-2.0 is frozen below; mutation work has not started.

This delivery makes the existing **New sub-scope** lifecycle create the normal
management surface needed to reach and populate that collection. The recreated
external-local `dotlineform` scope and its `projects` sub-scope are the focused
acceptance scenario, not a reason for Projects-specific lifecycle code.

## Complete Outcome

One confirmed New sub-scope apply creates:

- the configured one-level collection and confined source/output roots;
- one ordinary parent-scope report document explicitly associated with that
  collection;
- a parent index entry using the supplied collection title;
- valid empty local `manifest.json` and `manage-manifest.json` projections;
- refreshed parent docs/search and browser configuration; and
- an exact management URL that opens the default report.

The empty report shows a normal zero-document state and exact-collection New.
The user can create or import the first child without manually writing a host
document or running a builder.

## Fixed Boundaries

- This delivery consumes SSR-1's default; it does not copy Analysis/Tags
  configuration or implement another report scaffold.
- The host is an ordinary parent document, not a synthetic tree node or new
  route identity.
- The lifecycle records one exact collection/host association and never
  reconstructs it from title, filename, active document, or URL text.
- Creation uses the existing planned identity and atomic create-only boundary.
- Post-commit rebuild or presentation failure returns committed identities and
  retries follow-through only; it cannot create a duplicate.
- A new sub-scope omits customisation identity and therefore receives the
  default.
- Child documents remain excluded from parent Index, Recently Edited, and
  search payloads.
- Public visibility remains governed by existing scope and publication
  configuration.
- Delete preview/apply accounts for the exact lifecycle-associated host and
  fails closed on detached, ambiguous, changed, or missing association state.

#### SSR-2.0 current trace

- `docs_sub_scope_lifecycle.py` currently plans the same derived child source
  and output roots for local, external-local, and public parents. Public
  parents additionally receive their configured publication root. Create
  writes those roots and one config record; it allocates no document identity,
  writes no host or manifest, and runs no builder.
- Current delete accepts any configured sub-scope, removes its child source,
  local output, and configured public projection, then removes the config
  record. It has no exact host association, host-change check, or parent
  discovery rebuild.
- `SubScopeDocsBuilder` already owns the canonical empty
  `manifest.json`/`manage-manifest.json` pair as `{"docs": []}`. The parent docs
  builder owns the host by-ID payload, Index, Recent, and browser configs; the
  parent search builder owns the search row.
- The browser currently submits only parent scope, sub-scope, and title. After
  apply it reloads configuration/capabilities, but it carries no planned host
  identity and does not refresh/select a returned parent document.

#### Frozen create contract

The form remains `{parent_scope, sub_scope, title}`. Preview allocates and
returns `planned_report_host_identity: {doc_id, added_date}`. Apply must return
that exact object; the service recomputes the complete plan and rejects a
changed identity, stale config, or any path/source collision before writing.

The host is a root-level ordinary parent document at
`<parent source documents>/<doc_id>.md`. It uses the supplied title and this
source shape:

```yaml
---
doc_id: <planned doc_id>
title: <supplied title>
added_date: <planned added_date>
last_updated: <planned added_date>
viewable: false
viewer_report: docs_subscope
viewer_report_access: local
viewer_report_subscope: <sub-scope id>
---
# <supplied title>
```

It has no `parent_id`, `ui_status`, customisation identity, or copied report
configuration. Local parents omit `viewable`; public parents retain the
ordinary document-create default of `viewable: false`. Public visibility and
later report promotion therefore remain explicit existing workflows.

The new sub-scope config record owns the exact lifecycle association:

```json
{
  "sub_scope": "projects",
  "title": "Projects",
  "public_projection": null,
  "lifecycle": {
    "tool_id": "docs-viewer-scope-lifecycle",
    "report_host_doc_id": "d-*",
    "report_host_source_revision": "sha256:*"
  }
}
```

The normalized config validates this strict object. Absence means a manually
configured collection, not an association to infer. New records omit
`report_customisation`, so canonical `docs_subscope` resolves the default.

One preview names these consequences:

1. create the confined child source/documents and local output/by-ID roots;
2. atomically create only the planned host source and atomically append the
   associated config record;
3. run the child builder to create local `manifest.json` and
   `manage-manifest.json`, both `{"docs": []}`;
4. rebuild the planned host in parent docs and search, which also regenerates
   Manage and public browser configuration; and
5. return `/docs/?scope=<parent_scope>&doc=<host_doc_id>`.

For a public parent, preview also lists the configured public child projection.
Create does not publish a child manifest, host, or report there: the existing
parent Publish workflow remains the only public snapshot writer.

Preview and result expose the exact `collection_target: {scope, sub_scope}` and
`report_host_target: {scope, doc_id}`, the host source revision, config
association, created/changed/publication path records, both rebuild results,
browser-config refresh, and `urls.management`. `urls.public` stays empty.

#### Failure and follow-through contract

The atomic config change is the canonical commit point. Before it, any paths
created or staged by this attempt are restored/removed and the response is
`committed: false`; the UI returns to a fresh preview and has no target from
which to navigate. An unprovable rollback is reported as indeterminate with
the exact affected paths and is never presented as safe to retry.

After config commit, the collection and host are created. A child build,
parent docs/search build, browser refresh, index refresh, selection, or
navigation failure returns `committed: true`, `retry_create: false`, the two
exact targets, association, per-stage status, and management URL. Recovery may
retry only unfinished build/refresh/select/navigation stages against those
identities. It never invokes create again.

#### Frozen delete contract

Delete preview resolves the config-owned lifecycle object and then the exact
parent source `<report_host_doc_id>.md`. It permits deletion only when:

- the association is present, strict, and owned by the lifecycle tool;
- the host exists with the recorded immutable ID and source revision;
- its report fields still name canonical `docs_subscope`, local access, and the
  exact collection; and
- no second parent document claims that collection.

Missing, detached, ambiguous, or revision-changed state returns
`allowed: false`. A revision change is presented as **Report host edited since
creation** with the exact host target plus recorded/current revisions. Preview
does not relabel the edit as lifecycle-owned and apply cannot guess or delete a
different host.

An allowed preview lists removal of the exact unchanged host source, child
source tree, local manifests/by-ID output, and any configured public snapshot
tree; the config association change; removal of the host from parent by-ID,
Index, Recent, and search; browser-config regeneration; and navigation to
`/docs/?scope=<parent_scope>`.

Apply recomputes that plan and treats config removal as the delete commit point.
Pre-commit failure restores staged owned paths or reports indeterminate state.
After commit, cleanup/rebuild/presentation failure returns `committed: true`,
`retry_delete: false`, the deleted collection/host identities, exact remaining
follow-through, and the parent management URL. Recovery never runs collection
deletion again.

## Out Of Scope

- Projects-specific fields, filters, row treatment, or actions;
- migration of existing manually hosted collections;
- recursive sub-scopes, rename, or broader scope-lifecycle redesign;
- automatic public promotion; and
- changing the default or customisation contract accepted in SSR-1.

## Completion Gates

- One apply creates exactly one configured sub-scope and one indexed host.
- Empty public-safe and Manage manifests load as normal zero-document state.
- New and Import receive only the mounted exact collection.
- Refresh/navigation failure cannot cause duplicate creation.
- Delete uses the exact stored association and cannot guess a host.
- Focused external-local acceptance proves the recreated workflow without
  implying every provider or report has received visual review.
