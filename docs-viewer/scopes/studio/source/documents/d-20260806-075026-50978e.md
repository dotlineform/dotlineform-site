# SSP-3.0 — Insert Subject Link Sanity Note

## Outcome

SSP-3 fits the shipped Docs Viewer owners as one bounded Source-editor action. It can read the exact managed document's current normalized subject, plan one Work, Series, or Folder reference, and commit those bytes through the existing ordinary Source replacement owner. Work and Series reuse the exact Catalogue target lookup and semantic-token serializer; Folder reuses canonical local-target encoding, local-link validation, Manage activation, and public sanitization. No resolver parser, Project State read, relationship lookup, build prerequisite, new token family, generic Source-command framework, concurrency protocol, or automatic reference maintenance is required.

The checkpoint is complete at its review gate and stopped before SSP-3.1 approval. This note records implementation fit and risks without freezing an exhaustive file inventory or detailed implementation.

## Existing Owners And Small Production Shape

- The Source editor already exposes the exact document target, current selection replacement, ordinary input/dirty projection, and focus return. Existing code-owned Source control definitions and handlers can host one action without adding a registry or extending the Directives menu into a generic command system.
- `GET /docs/metadata` already resolves current canonical front matter for one exact `{scope, sub_scope, doc_id}` target. The shared browser subject normalizer accepts only the SSP-1 none, valid Folder/Work/Series, malformed, or conflicting shapes. A response-target mismatch, missing normalized state, or unsupported document context is an unavailable input rather than permission to infer a subject.
- The existing Semantic Tokens support loads current target rows, filters exact Catalogue identities, finds one target by `catalogue`, kind, and ID, and serializes the current title into ordinary `[[catalogue:<kind>:<id>|<title>]]` source. An absent Work or Series row produces no reference and no URL fallback.
- The local-folder owner validates decoded relative targets, canonically percent-encodes them, derives the existing final-segment label, and renders ordinary `dlf-local:` Markdown. Its service already separates validation from OS activation through dry-run behavior; SSP-3 must keep validation non-opening and contained within this owner if current target availability is checked before insertion.
- Manage rendering turns a valid local reference into the existing activation marker. The publication gate removes both target and activation capability while retaining inert safe label text. SSP-3 therefore needs no public Folder payload, runtime, route, or author-controlled safety convention.

The likely production shape is one code-owned action contribution, one small pure subject-to-insertion planner, and narrow composition with the existing metadata, Catalogue, Source replacement, and local-link owners. The broad blast radius covers the Source control, exact metadata response validation, subject planning, current title lookup, local target encoding and availability, ordinary Source replacement, focused pure/module/service checks, public isolation, and concise owner-document transfer.

## Exact No-Fallback Contract

| current input | only permitted insertion | contained failure |
| --- | --- | --- |
| valid Work | exact current Work target serialized by the Catalogue token owner | missing identity, unavailable lookup, mismatched type or invalid serialization inserts nothing |
| valid Series | exact current Series target serialized by the Catalogue token owner | missing identity, unavailable lookup, mismatched type or invalid serialization inserts nothing |
| valid Folder | final-segment-labelled Markdown with the exact canonically encoded relative `dlf-local:` target | unavailable local capability, invalid path, failed validation or encoding inserts nothing |
| none, malformed, conflicting, absent state or target mismatch | no insertion | show one contained reason and retain current source and front matter |

Docs management is single-user and modal workflows complete serially. SSP-3 therefore adds no canonical source-revision comparison, captured-buffer receipt, optimistic locking, or concurrency-specific failure state. The action performs one current metadata and target plan within that workflow and hands the resulting bytes to the Source editor's ordinary replacement owner.

Insertion is a source snapshot. Later subject reassignment never rewrites, removes, or retargets existing bytes. Later Work or Series presentation refresh remains ordinary Semantic Tokens behavior; a Folder reference retains its authored encoded path. The action does not save, rebuild, change front matter, open a local target, refresh Project State, or display a routine success message.

## Risks And Required SSP-3.1 Evidence

- The action remains one serial workflow. Focused evidence must prove exact response targeting and zero insertion after an explicit metadata, Catalogue, local-target, or replacement failure without adding concurrency simulations or canonical-drift handling.
- Catalogue support contains other target types. The planner must accept only exact Work or Series identity from the normalized subject and must never use search ranking, title text, route state, selected rows, or related membership as identity.
- Structural Folder validity and current local availability are different facts. The action must keep canonical relative encoding, configured-base confinement, non-opening validation, and missing-target behavior in the local-link owner without consulting Project State.
- Metadata contexts that cannot expose normalized subject state must not gain a guessed None state or a broadly available action. None and invalid states that are explicitly exposed remain contained non-mutating outcomes.
- Public safety belongs to publication sanitization, not action visibility or an author's process. Verification must prove the exact inserted Folder source activates only in Manage and projects to inert label text publicly.

Focused SSP-3.1 evidence must cover Work, Series, Folder, None, malformed, conflicting, unavailable metadata, unknown Catalogue identity, invalid or unavailable Folder target, target mismatch, exact inserted bytes, dirty state, focus return, no success message, and no mutation after a failure.

## Retired Resolver Boundary And Stop Condition

The current runtime, services, builders, configuration, and focused tests contain no Resolver Token parser, registry, usage origin, collection result policy, relationship expansion, or build-refresh consumer. Retained Resolver documents and earlier checkpoint notes are historical records only. SSP-2.6 removed the unused persisted Project State lookup, and SSP-3 reads neither Project State nor SSP-1's private subject-association product.

Stop before or during SSP-3.1 if the action needs relationship expansion, front-matter mutation, a generic Source-command framework, public local targets, automatic rewriting after subject changes, Project State or association reads, a new token family, or hundreds of lines beyond the existing insertion and link seams. Any such result changes the accepted product and requires separate review.
