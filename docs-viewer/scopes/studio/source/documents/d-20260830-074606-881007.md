# Docs Viewer Runtime Ownership And Site Projection Delivery

## Requirements

This is the proposed first delivery of [Scope, Data, And Site Foundations](/docs/?scope=studio&doc=d-20260830-074605-dc4f11). Its complete result is that shared/public Docs Viewer runtime code has one canonical owner outside `site/`, while `site/docs-viewer/` retains the exact tracked code projection required by local public-site preview and GitHub Pages.

Developers edit only canonical shared/public runtime code outside `site/`. Local Manage and Review routes serve that canonical code directly, while local public-site preview and GitHub Pages serve the tracked projection at the existing URLs. Canonical runtime and projected `site/` changes are reviewed and committed together as one code delivery.

The projection must be deterministic, idempotent, safe to rerun, and explicit about every destination it owns. It must not copy management-only code or private configuration into the public artifact. The initial projection must be byte-identical to the current public runtime so this ownership cutover does not change visible behavior.

This is an internal code-development mechanism, not a Docs Viewer user process. It must not expose an Update Site action or become part of document Build, Publish, Deploy Repo, or Deploy Public. It preserves the public `/docs-viewer/...` URL contract and the current Analysis route.

This delivery does not move or change scope source, generated output, published output, public document/search payloads, public route or scope configuration, Catalogue assets, media, or route shells. It does not change scope types, implement scope Publish or document Deploy, or add Swift code.

## Process

The repository-internal developer command is `bin/site-code-update`, backed by `site-tools/site_code_update.py` and an explicit projection manifest under `site-tools/config/`. The command writes only the tracked runtime code destinations owned by that manifest. `bin/site-code-update --check` verifies the same mapping without writing.

It is a delivery gate only when a change touches canonical code represented in the site-code manifest. It is not a gate for ordinary document edits, scope Build, Publish or Deploy, Catalogue-only work, or unrelated repository changes.

The normal sequence is:

```text
edit canonical runtime
  -> test Manage and Review against canonical code
  -> run bin/site-code-update
  -> inspect the tracked site/ delta
  -> run bin/site-code-update --check
  -> run projection and public-site validation
  -> perform local public-site preview when warranted
  -> commit canonical and projected code together
```

Tests that exercise canonical Manage or Review code can run before projection. Projection checks, deploy-root validation, and local public-site preview run after projection because they consume tracked `site/`. If testing or review causes another canonical runtime change, rerun `bin/site-code-update` and the affected post-projection evidence before closeout.

The gate is complete when the canonical runtime and tracked site projection match exactly and appear in the same delivery diff. The command is not exposed in Docs Viewer and is not part of the user-facing document lifecycle.

## Deliverables

| `site-tools/config/site-code-update.json` | New explicit canonical-to-site projection manifest for the JavaScript and stylesheet families in this delivery. |
| `site-tools/tests/test_site_code_update.py` | New focused coverage for complete copying, check-mode drift, stale-file removal, idempotence, unrelated-file preservation, and public/private exclusion. |
| `docs-viewer/runtime/js/public/` and `docs-viewer/runtime/js/shared/` | New canonical homes for the corresponding runtime currently under `site/docs-viewer/runtime/js/`. |
| `docs-viewer/runtime/js/reports/docs-viewer-public-reports.js` | New canonical home for the public report runtime currently projected under `site/docs-viewer/runtime/js/reports/`. |
| `docs-viewer/static/css/{docs-viewer.css,docs-viewer-theme.css,docs-viewer-reports.css}` | New canonical homes beside the existing local-only Docs Viewer stylesheets. |
| `site/docs-viewer/runtime/js/{public,shared,reports}/` and `site/docs-viewer/static/css/` | Existing tracked deployment destinations, thereafter written only by the internal projection for the files in its manifest. Public paths and module URLs remain unchanged. |
| `docs-viewer/services/docs_viewer_service.py` and `docs-viewer/services/docs_public_mermaid_producer.py` | Read canonical runtime and theme code rather than treating projected `site/` files as local authority. Any further direct consumers confirmed by readiness receive the same cutover. |
| `site-tools/site_tools/validation.py` and `site-tools/config/site-tools.json` | Validate that the tracked projection matches canonical code and contains no management-only assets. |
| `.github/workflows/public-site.yml` | Add canonical runtime paths to its pull-request path filter; keep manual public deployment and the workflow's non-mutating behavior unchanged. |
| `.github/workflows/source-lint.yml` and maintained lint targets | Retain existing `docs-viewer/runtime/js/**` coverage and add the newly canonical stylesheet paths required by the final source boundary. |
| Existing Docs Viewer runtime, static-asset, search, report, lint, and projection contract tests | Change source-level expectations to canonical paths and retain deploy-root expectations against tracked `site/`. Readiness confirms the exact affected files before implementation. |
| Durable Docs Viewer runtime and source-tree documentation | Describe canonical runtime, internal projection, local canonical serving, public preview, and deployment; remove statements that identify projected runtime files as code authority. |

No document, search, media, Catalogue, scope, public-route, or public-browser-config data changes in this delivery. Runtime configuration and document deployment remain owned by later stages.

### Processes To Be Run

- Relocate the shared/public JavaScript and stylesheet files to their canonical paths without changing their initial bytes, public URLs, or relative module relationships.
- Cut local runtime consumers over to canonical paths with no fallback to `site/`.
- Implement and exercise `bin/site-code-update` in write and check modes against only the manifest-owned destinations.
- Generate and inspect the tracked `site/` projection, confirming that unrelated site-owned artifacts remain untouched.
- Run focused canonical-source tests, projection tests, public/private runtime-boundary checks, maintained lint for the changed source boundary, and deploy-root validation.
- Run local Manage and Review checks against canonical code and, when warranted, local public-site preview against the projected code.
- Update the pull-request path filters and durable documentation owners named above.
- Review canonical and projected changes as one bounded development diff before commit and closeout.

No compatibility alias or fallback may allow local code to keep reading canonical runtime from `site/`. The tracked projection remains because it is deployed code, not as an alternate source tree.

## Delivery Steps

### 1.0 — Readiness

- [ ] Confirm the complete shared/public JavaScript and stylesheet projection and the current producer and consumer of each file family.
- [ ] Confirm that the proposed canonical destinations preserve relative module relationships and do not collide with local-only modules.
- [ ] Record the current bytes of the managed runtime projection and the public/private runtime boundary.
- [ ] Confirm the implementation sequence and stop if a required change would move document data or configuration, redesign scope behavior, add a user-facing site operation, or broaden the projection beyond the named runtime code paths.

**Gate:** present the confirmed code projection boundary, credible blast radius, verification budget, and any required change to these deliverables before editing runtime or tooling.

### 1.1 — Canonical Runtime Cutover

- [ ] Relocate the shared/public JavaScript and stylesheets to their code-owned canonical directories.
- [ ] Update local static serving, asset versioning, lint targets, source-level tests, and code references to use those canonical paths.
- [ ] Preserve public URLs, module imports, public behavior, and management-only exclusion.

**Gate:** local Manage and Review load from canonical code, and the canonical public runtime graph contains the same deployable modules without depending on `site/`.

### 1.2 — Internal Site Projection

- [ ] Implement `bin/site-code-update`, `site-tools/site_code_update.py`, and the explicit manifest with write and consistency-check behavior.
- [ ] Project only runtime JavaScript and stylesheets into their existing tracked `site/` destinations.
- [ ] Prove that the initial projection preserves current bytes, a second write is a no-op, `bin/site-code-update --check` detects drift, stale managed files are removed, and unrelated site files are untouched.
- [ ] Keep canonical and projected runtime changes together in the normal development diff and commit boundary.

**Gate:** review the exact canonical-to-deployment mapping and tracked generated delta before accepting the projection owner.

### 1.3 — Development And Validation Integration

- [ ] Point maintained source checks at canonical runtime code and deploy-root checks at the tracked projection.
- [ ] Retain Source Lint pull-request coverage for `docs-viewer/runtime/js/**` and include any newly canonical runtime stylesheet paths required by the final source boundary.
- [ ] Add canonical runtime paths to the Public Site workflow's pull-request path filter so projection validation also runs when the corresponding tracked `site/` files were omitted from a change.
- [ ] Preserve manual deployment as the normal public-release operation; pull-request validation does not deploy and is not required to perform a manual deployment.
- [ ] Keep the GitHub Pages workflow non-mutating: it validates and deploys the committed `site/` snapshot without generating or committing files.

**Gate:** a stale or unsafe projection is rejected, while a current tracked projection passes the existing deployment path without external scope access.

### 1.4 — Code Review

- [ ] Review the bounded source, projection tooling, service, validation, test, documentation, and generated-site diff for split ownership, duplicate producers, compatibility residue, unsafe deletion scope, hidden `site/` reads, and accidental public management assets.
- [ ] Resolve findings and rerun only the evidence affected by review changes.

**Gate:** present the reviewed change set and focused evidence for approval before closeout.

### 1.5 — Closeout

- [ ] Confirm that the complete runtime-ownership and projection result works while document Build, Publish, deployment, scope storage, and GitHub Pages behavior remain unchanged.
- [ ] Update the durable documentation owners and record any separate Stage 2 prerequisite discovered during implementation.
- [ ] Recommend whether this delivery document should be retained for review or retired after its stable conclusions have moved to durable documentation.

**Gate:** close only after the user accepts the shipped outcome and the feature points clearly to the next scope Build and Publish delivery rather than extending this one.
