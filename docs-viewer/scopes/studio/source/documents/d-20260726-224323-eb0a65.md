# Manage Sub-Scope Documents

## Result

Local Docs Viewer management can find, open, and Markdown source-edit documents
in a configured one-level sub-scope without adding those documents to the
parent scope's index panel.

Public report-hosted viewing remains unchanged. The capability is reusable for
sub-scopes rather than being part of the Tag Registry workflow.

## Why this is separate

[Embedded Detail Documents](/docs/?scope=studio&doc=d-20260623-221357-a97b66)
deliberately leaves the indexed parent report selected while its report owns the
active `subdoc`. The current Markdown Source mode instead targets the selected
indexed document. Bridging those identities is a Docs Viewer management
capability, not a tag-document association concern.

[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c)
can author either `viewable` state and its current migration contract chooses
public documents. The migration nevertheless depends on this feature: direct
source editing in an external editor is not a sufficient management workflow
for the large document set it will create.

## Current starting point

- The public `docs_subscope` report already lists configured sub-scope
  documents and renders a listed `subdoc` without putting it in the sidebar.
- Sub-scope manifests are intentionally small list and existence contracts,
  not index trees.
- The local Markdown Source editor currently resolves only a parent
  `{ scope, doc_id }` identity.
- Docs Viewer reports are read-oriented surfaces. They may drive navigation,
  but they should not become owners of source-write workflows.

## UI decision

The interaction is not yet fixed. The leading direction is a local management
report that provides dense discovery, filtering, and navigation, then hands the
chosen document to viewer-owned rendered and Markdown Source modes.

The first design checkpoint must compare:

1. extending the current `docs_subscope` report with local-only management
   navigation; and
2. using a separate local manage report that can select a configured parent
   scope and sub-scope.

In either case, the report remains the navigation host. The existing Docs
Viewer source editor owns loading, dirty-state protection, revision checking,
Save/Rebuild, and return to rendered view.

The choice must be tested with hundreds of documents, group/text filtering,
direct deep links, browser Back/Forward, narrow layouts, and an unavailable
document. No delivery should commit to a host before that interaction pass.

## Required identity and write boundary

- A focused document is identified by
  `{ scope, sub_scope, doc_id }`; raw `doc_id` is insufficient.
- The parent report remains selected in the index panel, and no sub-scope
  records are merged into the parent `index-tree.json`.
- Local source read and rebuild requests carry the explicit `sub_scope`.
- The service resolves only configured one-level sub-scope roots, validates the
  document identity, preserves the existing source revision contract, and
  performs the targeted sub-scope document and search rebuild.
- Missing or unlisted targets show a contained unavailable state and cannot
  resolve an arbitrary source path.

## Initial boundary

In scope:

- dense local discovery and navigation;
- rendered detail viewing;
- the existing body-only Markdown Source mode;
- dirty-state, stale-revision, save, rebuild, and return behavior; and
- unchanged public report/detail behavior.

Not in scope:

- creating, deleting, moving, or transferring sub-scope documents;
- editing front matter, metadata, or `viewable`;
- adding sub-scope documents to the parent index, Recent, or global search;
- public source editing; or
- turning reports into general write-capable workflow hosts.

## First checkpoint

Before delivery documents are proposed:

- sketch both report-host options against the current viewer composition;
- choose the smallest route and active-document identity contract;
- verify that Source mode can target the focused sub-scope document while the
  sidebar remains on the parent report;
- define capability projection and unavailable states; and
- record the selected UI with its focused service and runtime blast radius.

## Downstream consequence

The future Tag semantic-token target waits indirectly on this feature because
the tag-document migration is blocked here. Semantic-token registration is not
part of this feature; it follows only after tag targets have stable document
associations and workable public detail URLs.

## Durable destinations

If shipped, the stable embedded-detail identity and navigation behavior belongs
in
[Embedded Detail Documents](/docs/?scope=studio&doc=d-20260623-221357-a97b66).
The stable report-host boundary belongs in
[Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b).
Source-editor behavior belongs with the existing Docs Viewer management and
source-editing documentation.
