# Manage Sub-Scope Documents

## Result

Local Docs Viewer management can open the existing Markdown source editor and
Edit metadata modal for a displayed document in a configured one-level
sub-scope without adding that document to the parent scope's index panel.

The public report UI and minimal payload schema remain unchanged; edited
content, metadata, and visibility flow through their normal projections. The
management capability is reusable for sub-scopes rather than being part of the
Tag Registry workflow.

## Why this is separate

[Embedded Detail Documents](/docs/?scope=studio&doc=d-20260623-221357-a97b66)
deliberately leaves the indexed parent report selected while its report owns the
active `subdoc`. Source and metadata editing must therefore receive an explicit
target rather than treating the displayed or selected document as an implicit
write target. That identity bridge is a Docs Viewer management capability, not
a tag-document association concern.

[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c)
can author either `viewable` state and its current migration contract chooses
public documents. The migration nevertheless depends on this feature: direct
source editing in an external editor is not a sufficient management workflow
for the large document set it will create.

## Current starting point

- The public `docs_subscope` report already lists configured sub-scope
  documents and renders a listed `subdoc` without putting it in the sidebar.
- A sub-scope manifest is a flat public list and existence payload, not an
  index tree. A sub-scope may contain hundreds of documents, so the payload
  stays tight: it exposes only fields required by public report listing,
  validation, navigation, and deliberately supported filtering. Its flat
  structure and its cardinality are independent.
- The local Markdown Source editor currently derives its target from the
  selected parent document.
- Edit metadata currently hydrates and saves an indexed parent-scope document
  and always includes the Parent field.
- Docs Viewer reports are read-oriented surfaces. They may drive navigation,
  but they should not become owners of source-write workflows.

## Selected UI contract

The existing `docs_subscope` report remains the navigation and rendered-detail
host. It does not become a source editor.

The management toolbar projects the rendered document and source-mode actions
explicitly:

| state | Edit metadata | report source | subdoc source | Return to doc |
| --- | --- | --- | --- | --- |
| rendered report list | parent report | enabled for the parent report | disabled | unavailable |
| rendered valid subdoc detail | displayed subdoc | enabled for the parent report | enabled for the displayed subdoc | unavailable |
| Markdown source | unavailable | disabled | disabled | enabled |

The existing report Source action always supplies the parent report's
`{ scope, doc_id }`, including while a subdoc detail is displayed. The new
subdoc Source action is enabled only after the report has validated and
displayed a listed detail; it supplies `{ scope, sub_scope, doc_id }`.

The existing **Edit metadata** action follows the rendered target. On the
report list it receives the explicit parent `{ scope, doc_id }`; on a validated
subdoc detail it receives the explicit `{ scope, sub_scope, doc_id }`. The
sub-scope modal keeps every existing metadata control except **Parent**:
Title, Summary, Date, Date display, Status, and **non-viewable** remain
editable. It neither sends nor mutates `parent_id`.

The report has separate public and management data inputs. Public mode receives
only the tight public manifest and renders no Status or non-viewable icons.
Manage mode receives one compact local inventory of every sub-scope document,
keyed by `doc_id`, with `title`, `ui_status`, and `viewable`; it uses the
existing icons for those two states. It does not fetch hundreds of by-ID
payloads to construct the list.

Source entry is no longer a toggle. In source mode both entry actions remain
visible but disabled, and the explicit **Return to doc** action restores the
unchanged rendered route. The parent report remains selected and the `subdoc`
query parameter is preserved.

The existing source editor remains the only editor surface. Its body-only
buffer, dirty-state prompt, stale-revision protection, Save/Rebuild,
Add image, Add file, **Add catalogue token**, contextual token Info view, and
other registered source-editor contributions remain valid. Save/Rebuild keeps
its current successful return to rendered view; **Return to doc** owns the
explicit leave-without-rebuild path and its existing dirty-state prompt.

## Required identity and write boundary

- The source editor and metadata workflow require a supplied target. Neither
  defaults to the displayed document, selected index document, URL `doc`, or
  URL `subdoc`.
- A parent target is `{ scope, doc_id }`.
- A sub-scope target is `{ scope, sub_scope, doc_id }`.
- The parent report remains selected in the index panel, and no sub-scope
  records are merged into the parent `index-tree.json`.
- Every source-file action uses the active supplied target. Read, rebuild, and
  Open in VS Code carry `sub_scope` for a sub-scope target; buffer-only
  contributions act on the same active editor adapter.
- The service resolves only configured one-level sub-scope roots, validates the
  document identity, preserves the existing source revision contract, and
  performs the targeted sub-scope document and search rebuild.
- Edit metadata hydrates the full source record through the local management
  service using the supplied target. It does not add management fields to the
  tight public manifest or compact public by-ID payload.
- The local management inventory includes all sub-scope documents, including
  non-viewable documents. The public manifest contains only publicly eligible
  basic identities and remains `{ doc_id, title }`.
- Sub-scope metadata writes preserve the existing Title, Summary, Date, Date
  display, Status, and `viewable` contracts. They reject `parent_id`, preserve
  any source value unchanged, and retain the existing public projection
  behavior for `viewable`.
- A successful sub-scope rebuild refreshes the embedded detail payload without
  selecting the subdoc in the parent index or treating it as a parent-scope
  document.
- Missing or unlisted targets show a contained unavailable state and cannot
  resolve an arbitrary source path.

## Boundary

In scope:

- the current report list and rendered detail navigation;
- explicit parent and subdoc source-entry controls;
- explicit source and metadata target handoff;
- the existing body-only Markdown Source mode;
- dirty-state, stale-revision, save, rebuild, source contributions, and return
  behavior;
- the existing Edit metadata modal for configured sub-scope documents, with
  only Parent omitted;
- Title, Summary, Date, Date display, Status, and `viewable` editing;
- the compact manage-only inventory and existing Status/non-viewable icons in
  the manage report;
- focused source read, metadata read/write, rebuild, open, and rendered-detail
  refresh support for configured one-level sub-scopes; and
- unchanged public report UI and minimal manifest schema.

Not in scope:

- a separate local manage report;
- creating, deleting, moving, or transferring sub-scope documents;
- adding sub-scope documents to the parent index, Recent, or global search;
- public source editing; or
- turning reports into general write-capable workflow hosts; or
- a second or reduced-capability source editor.

## Downstream consequence

The future Tag semantic-token target waits indirectly on this feature because
the tag-document migration is blocked here. Semantic-token registration is not
part of this feature; it follows only after tag targets have stable document
associations and workable public detail URLs.

## Possible future enhancement

A separate low-priority enhancement may add optional `ui_status` to the public
by-ID payload of a publicly eligible sub-scope document and render the existing
status badge in that document's detail header. It would not add `ui_status` or
`viewable` to the public manifest, add icons to public report rows, or make the
parent document's info panel subdoc-aware. This delivery keeps `ui_status`
management-only.

## Durable destinations

If shipped, the stable embedded-detail identity and navigation behavior belongs
in
[Embedded Detail Documents](/docs/?scope=studio&doc=d-20260623-221357-a97b66).
The stable report-host boundary belongs in
[Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b).
Source-editor behavior belongs with the existing Docs Viewer management and
source-editing documentation. Metadata mutation and `viewable` behavior belong
with their existing maintained contracts.
