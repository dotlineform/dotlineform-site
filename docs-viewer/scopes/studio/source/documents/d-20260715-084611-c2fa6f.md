# SM-1 — Studio Full-Text Search Delivery

## Complete Result

Studio Docs Viewer search returns one deterministic document result for title, section-heading, body-text, and authored code queries. Ranking strongly prefers title over headings and headings over body or code matches, while the static index stops treating document identity or update dates as searchable content and avoids duplicate search text.

SM-1 is the first Docs Viewer Search mechanics delivery. It does not change Catalogue Search or enable full text for another Docs Viewer scope.

## Why Now

[Studio Documentation Maintenance](/docs/?scope=studio&doc=d-20260813-114338-c6b682) first establishes an accepted corpus and generated backlink visibility. Search then makes that current material discoverable without amplifying documents already identified for consolidation, reparenting, Notes transfer, or retirement.

## Current Baseline

At planning time the Studio index contains 242 document records and is 194,398 uncompressed bytes. Each record searches title, parent title, `last_updated`, and exact `doc_id`; it does not read headings, body prose, or authored code.

Numeric-only derived terms account for about 11 percent of the current uncompressed payload, not half. The index also repeats the complete `search_terms` list in `search_text`. Removing `last_updated` from search inputs while retaining it for display, and choosing one canonical searchable representation, are the first efficiency decisions before full-text fields are added.

Observed current behavior:

| query | current result |
| --- | --- |
| `studio runtime` | finds **Studio Runtime** by title |
| `report block tokens` | finds **Report Block Tokens** by title |
| `known weak spots` | no result although it is a section heading |
| `compatibility key` | no result although it appears in Studio body text |
| `DOCS_VIEWER_BASE_URL` | no result although it is an authored code term |
| `docs_subscope` | no result although it is an authored code term |

## Search Contract

- Retain exact `doc_id` as the result record's structural identity, navigation target, targeted-update key, and deterministic tie-breaker, but do not match or score queries against it.
- Rank title matches first, section-heading matches second, and body-text or code-term matches third.
- Retain parent title as result context and a lower-confidence retrieval aid; it does not outrank a matched heading in the document itself.
- Keep `last_updated` and parent metadata available for display but do not index dates or their derived numeric fragments.
- Do not emit numeric-only derived tokens. Authored mixed alphanumeric code terms remain searchable.
- Return at most one row per document. Heading matches do not create section records, deep links, or repeated results.
- Keep the existing client-side static-index architecture and deterministic ranking.
- Enable the new full-text policy only for the Studio scope in this delivery. Other local, external-local, and public Docs Viewer scopes retain their current search contract.
- Keep the initial result presentation compact. Snippets, match highlighting, field filters, and section navigation are outside SM-1.

## Inclusion Boundary

Include the authored document title, Markdown headings, readable body prose, inline code, fenced code terms, and parent title at lower confidence. Retain `doc_id`, viewer URL, `last_updated`, and `parent_id` only as non-searchable identity, navigation, display, and update metadata. Exclude other front-matter fields, generated HTML markup, link destination URLs, report-block configuration, media paths, timestamps, and token fragments created only by punctuation splitting.

The exact body/code normalization and compact payload shape are fixed at the sanity gate against representative real documents. The implementation must not create a general tokenizer framework or a second browser search engine.

## SM-1.0 — Sanity Gate

Before implementation, present:

- the exact Studio opt-in configuration or existing scope-policy seam
- the proposed index schema and elimination of duplicated searchable representation
- representative title, heading, prose, and code queries plus negative full-`doc_id` and date-derived queries
- projected uncompressed and compressed payload sizes against the recorded baseline
- the exact builder, runtime, config, test, and durable-document files
- the rough production and test diff

Stop for review if Studio-only adoption requires hard-coded scope branching, mixed schemas require a compatibility reader, full text exposes another scope's source, or the change expands into shared Catalogue search machinery.

## Implementation Outcome

After SM-1.0 approval:

1. add the smallest explicit Studio full-text policy seam;
2. build compact field-aware document records from canonical Studio Markdown;
3. update the Docs Viewer runtime to match and rank the optional fields deterministically;
4. remove document-ID retrieval, date-derived search noise, and redundant emitted search data;
5. add focused builder and ranking evidence for the representative queries; and
6. rebuild and inspect the exact Studio index delta.

## Completion Evidence

- existing title queries retain deterministic known-item behavior
- representative heading, body, and code queries find the intended document
- a full `doc_id` does not match solely because it is the result record's identity
- timestamp-derived queries such as `2026`, `08`, and `13` do not match merely because of metadata dates
- one document produces no more than one result
- non-Studio Docs Viewer indexes and Catalogue Search are byte-for-byte unchanged unless a separately reviewed generated timestamp is their only difference
- focused Python search-builder tests, JavaScript ranking tests or the current equivalent pure runtime checks, relevant lint, Studio docs/search builds, JSON inspection, and `git diff --check` pass
- before/after uncompressed and compressed Studio index sizes are recorded without claiming that full text must be smaller than the metadata-only baseline
