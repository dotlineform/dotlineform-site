# SM-1 — Studio Full-Text Search Delivery

## Status

Eligible for SM-1.0 readiness. [DSI-1 — Docs Viewer Search Index v2 Delivery](/docs/?scope=studio&doc=d-20260813-171341-8bfa80) is complete, and its common metadata-only schema, tokenizer, field-policy, whole-index rebuild, and browser-query contracts are the accepted baseline. SM-1.0 has not begun; production and test implementation remain gated behind its separate readiness review and explicit approval.

## Complete Result

Studio Docs Viewer search returns one deterministic document result for title, section-heading, body-text, and authored code queries. Ranking strongly prefers title over headings and headings over body or code matches. Document identity and update dates remain available as structural or display metadata but are not searchable Studio terms.

## Boundary

SM-1 adds Studio headings, readable body prose, inline code, and fenced code to the common v2 inverted index. It retains parent title as lower-confidence context, rebuilds the complete Studio search index after a search-relevant document change, and keeps result presentation compact.

It does not change the v2 schema or shared browser query path established by DSI-1, enable body text for another scope, change Catalogue Search, add snippets or highlighting, create section results or deep links, add stemming/synonyms/typo correction, index link destinations or report configuration, or introduce another tokenizer or search engine.

[Studio Full-Text Search Index](/docs/?scope=studio&doc=d-20260813-161942-b1e9e1) owns the proposed data shape, extraction boundary, ranking, representative examples, and prototype payload findings. [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-163802-5ca41f) owns shared term semantics.

### SM-1.1 — Studio Source Extraction And Field Inclusion

- [ ] Enable heading, body, and code fields only in Studio's shared v2 search policy.
- [ ] Extract the authored title, non-duplicate Markdown headings, readable body prose, inline code, and fenced code through the shared Markdown rendering/parsing contract.
- [ ] Exclude front matter other than approved display/context fields, generated markup, report-block declarations, link destinations, media paths, scripts, styles, timestamps, and punctuation-only fragments.
- [ ] Apply the shared tokenizer without adding Studio-only normalization or query behavior.
- [ ] Retain `doc_id`, viewer URL, `last_updated`, and `parent_id` only for identity, navigation, display, rebuild ownership, or deterministic tie-breaking.
- [ ] Make an affected Studio search build recompute the complete Studio v2 index while leaving safe document-payload builds targeted.

| contract or credible risk | lowest adequate evidence | permanent test change? | why this evidence is needed |
| --- | --- | --- | --- |
| headings, prose, inline code, and fenced code are omitted or assigned the wrong rank field | focused Python builder/extractor assertions over one representative Markdown document | extend the current search-builder test | proves the new Studio source boundary without a browser or corpus-wide fixture |
| front matter, URLs, report declarations, media paths, scripts, styles, dates, or document IDs leak into ordinary terms | focused negative assertions in the same representative extractor fixture | extend the same test rather than add a separate exclusion suite | protects privacy/noise boundaries with one owned fixture |
| authored technical identifiers such as `docs_subscope` or `DOCS_VIEWER_BASE_URL` diverge from the shared tokenizer | add only the missing Studio examples to the accepted DSI-1 tokenizer fixture | extend the shared fixture only if these cases are not already covered | proves technical vocabulary without duplicating tokenizer coverage |
| Studio policy changes another scope's generated content | exact before/after comparison of non-Studio indexes during the focused build | none unless an existing scope-policy contract lacks this assertion | scope isolation is a generated-output property, not a new test suite |

**Gate:** Studio extraction and field inclusion work through the shared v2 owners, focused evidence passes, and non-Studio outputs are unchanged. Stop before acceptance and payload review.

### SM-1.2 — Query Acceptance And Payload Review

- [ ] Rebuild the complete Studio v2 search index and record document count, vocabulary/posting counts, generation time, raw bytes, and compressed bytes against the accepted DSI-1 baseline.
- [ ] Confirm existing title queries such as `studio runtime` and `report block tokens` retain deterministic known-item behavior.
- [ ] Confirm representative heading, prose, and code queries such as `known weak spots`, `compatibility key`, `DOCS_VIEWER_BASE_URL`, and `docs_subscope` find the intended document.
- [ ] Confirm a full `doc_id` and date-derived queries such as `2026`, `08`, and `13` do not match solely because of structural identity or update metadata.
- [ ] Confirm a multi-term query intersects terms, ranking remains title → heading → body/code → parent, and one document appears at most once.
- [ ] Inspect representative high-frequency terms and confirm the payload remains acceptable for the local Studio route without inventing a smaller-than-baseline requirement.
- [ ] Perform one temporary manual Studio search check for compact result presentation; do not add a permanent browser test unless a browser-only contract failure is discovered and separately approved.
