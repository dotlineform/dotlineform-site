# SM-1 — Studio Full-Text Search Delivery

## Status

SM-1.1 is complete and parked for review. Studio extraction and field inclusion use the accepted DSI-1 schema, tokenizer, field policy, whole-index rebuild, and browser-query path. SM-1.2 query acceptance and payload review have not begun.

## Complete Result

Studio Docs Viewer search returns one deterministic document result for title, section-heading, body-text, and authored code queries. Ranking strongly prefers title over headings and headings over body or code matches. Parent title, document identity, and update dates remain available as structural or display metadata but are not searchable Studio terms.

## Boundary

SM-1 adds Studio headings, readable body prose, inline code, and fenced code to the common v2 inverted index. It retains parent title only as non-searchable display context, rebuilds the complete Studio search index after a search-relevant document change, and keeps result presentation compact.

It does not change the v2 schema or shared browser query path established by DSI-1, enable body text for another scope, change Catalogue Search, add snippets or highlighting, create section results or deep links, add stemming/synonyms/typo correction, index link destinations or report configuration, or introduce another tokenizer or search engine.

[Studio Full-Text Search Index](/docs/?scope=studio&doc=d-20260813-161942-b1e9e1) owns the proposed data shape, extraction boundary, ranking, representative examples, and prototype payload findings. [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-163802-5ca41f) owns shared term semantics.

**Record:** Completed 2026-08-13. DSI-1 is complete and closed. The accepted Studio baseline is the single `docs_viewer_search_index_v2` producer in `build_search.py`, the flat `search_fields` policy in `docs_scopes.json` and `docs_scope_config.py`, the sole postings query and scorer in `docs-viewer-search.js`, and the existing whole-index search rebuild owned by the write service and watcher. Studio currently indexes `title`, `parent_title`, exact `identity`, and exact `last_updated`; its current generated baseline is 236 documents, 630 terms, and 140,666 raw bytes. The document table already retains identity, URL, update, parent, and display metadata independently of which fields emit postings.

The existing field-policy allowlist already contains `heading`, `body`, and `code`, `build_search_index_v2` accepts those fields generically, and the browser query owner already intersects and scores their postings. SM-1 therefore needs only a Studio policy change: enable `title`, `heading`, `body`, and `code`, while removing `parent_title`, `identity`, and `last_updated` from Studio postings. Parent title remains in the document table for compact result context. Other scopes retain their explicit metadata-only field lists. No schema, tokenizer, loader, query-path, scope-name branch, or full-text mode is required.

`studio/shared/python/markdown_renderer.py` is the broad Markdown authority. Its common Markdown-it parser exposes heading, inline, inline-code, fence, code-block, raw-HTML, script, and style boundaries, and its HTML text projection already ignores attributes and script/style contents. The exact report-source owner in `docs_report_source.py` can project a validated structural report declaration away before extraction. Together these existing seams can expose non-duplicate authored headings, readable prose, inline code, and fenced code without indexing front matter, link destinations, media attributes, raw markup, report configuration, or script/style contents. SM-1.1 should add one small field-aware extraction result to that shared renderer and consume it from the current search builder; it must not read generated by-ID payloads as a second source model or duplicate report parsing.

Readiness correction 2026-08-13: `parent_title` is not a useful Studio full-text retrieval field because it can make every child match a broad hierarchy label without matching its own authored content. It remains display metadata only. The existing scorer's relative `parent_title` and `body`/`code` weights are therefore inactive for Studio and need no production change. SM-1.2 remains acceptance-only: it owns generated query evidence, deterministic rank confirmation, corpus measurements, non-Studio path comparison, and the temporary manual presentation check.

The expected SM-1.1 review shape is the existing Studio scope record, shared Markdown renderer, search builder, and their current focused Python/shared-query fixtures: roughly 100–180 production/config lines and 80–140 focused test/fixture lines, plus the regenerated Studio index and delivery evidence. Stop before absorbing the change if exact visible-source extraction would require duplicating Markdown/report/media resolution, if the shared renderer cannot separate eligible text without indexing non-visible configuration, if a schema/tokenizer/reader/cache or scope-name branch becomes necessary, if another scope or Catalogue path changes, or if the production/test shape materially exceeds this estimate. Gate outcome: ready for SM-1.1 implementation review and explicit approval; no production code, tests, prototype, implementation search build, or executable verification changed or ran during readiness. The routine docs watcher regenerated only this delivery record's existing by-ID, Recent, and metadata-only search projections.
