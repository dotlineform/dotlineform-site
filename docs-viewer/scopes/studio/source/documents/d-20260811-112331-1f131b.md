# Docs Viewer Capability Composition Audit

## Purpose

Create one checked, printable declaration of which reusable Docs Viewer capabilities are public-safe, which application shells currently compose them, and which named consumers currently adopt them. The declaration exists for design review and audit; it never imports, enables, configures, or loads runtime behavior.

[Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd) owns the durable distinction between safety, composition, and adoption for reports. [Expanded Report View](/docs/?scope=studio&doc=d-20260810-165949-ee4d35) exposed the practical problem: neither a shared module path nor an entry in the site runtime inventory reveals whether a public browser downloads that capability. This feature generalises the missing audit surface without turning the report-specific decision into a generic capability engine.

## Area/Delivery Role

This is the first combined area/delivery child of [Implementation Review and Architectural Conformance](/docs/?scope=studio&doc=d-20260811-113809-ad8110). It owns one concrete review family, its automatic and human boundary, its implementation checkpoints, and its acceptance evidence in one document. The parent owns the shared review vocabulary, end-of-delivery method, and relationship to Testing, Run Checks, Admin Checks, and Development Checklist.

The automatic portion can prove declared composition and adoption contradictions. The human portion decides whether a capability is genuinely public-safe, whether the capability inventory is conceptually complete, and whether the proposed ownership is architecturally correct. A passing audit must not collapse those judgments into behavioral test coverage.

## Problem

The current facts are distributed across several different owners:

- `site-tools/config/site-tools.json` inventories files present in the deployable public Docs Viewer runtime, but presence is not public composition.
- Public, Manage, and Review entrypoints and their transitive import graphs determine which JavaScript each shell composes.
- Route shell stylesheet links and the selectors within those stylesheets determine which CSS each shell composes.
- Report metadata, executable loader allowlists, contribution registries, and returned module handles determine adoption.
- Focused boundary tests prove selected negative and positive contracts, but they do not provide one readable statement of the intended design.

This means code review can establish the current answer, but there is no quick command that prints the intended answer and checks it against the implementation. It is particularly easy to mistake `site/...` for "publicly downloaded" or `docs-viewer/...` for "local-only" even though composition is decided by actual imports and shell stylesheet links.

## Proposed Contract

Add a checked audit manifest for reusable Docs Viewer capabilities whose composition or adoption crosses, or could cross, a public, Manage, or Review shell boundary. Each registered capability has a stable audit id, a durable documentation owner, an explicit required `public_safe` boolean, the application kinds that currently compose it, the named consumers that currently adopt it, and sufficient module and stylesheet ownership evidence for the auditor to test those claims.

The exact JSON schema and file owner are delivery decisions, but the semantic distinctions are not:

- `public_safe: false` is a hard prohibition. The declared implementation modules and selectors must be absent from the public import graph, public-loaded stylesheets, public loaders, and public adopters.
- `public_safe: true` is a reviewed architectural claim that permits public composition. It does not compose the capability, prove semantic safety by itself, or predict a future public adopter.
- `composed_by` states actual current shell composition and must agree with the resolved entrypoint/import and stylesheet graphs.
- `adopted_by` names actual consumers and is always narrower than composition: a consumer cannot adopt a capability in a shell that does not compose it.
- Missing required fields, unknown application kinds, duplicate capability ids, nonexistent declared paths, and contradictions fail the audit rather than receiving permissive defaults.

An illustrative record may resemble:

```json
{
  "id": "expanded_report",
  "owner_doc_id": "d-20260810-165949-ee4d35",
  "public_safe": true,
  "composed_by": ["manage"],
  "adopted_by": {
    "public": [],
    "manage": []
  },
  "implementation": {
    "modules": ["docs-viewer/runtime/js/reports/docs-viewer-report-presentation.js"],
    "styles": ["expanded-report selector family"]
  }
}
```

This example shows the target state after unused public composition is removed; it does not freeze field names, replace the feature owner with runtime configuration, or claim that Expanded Report View has already reached that state.

## Audit Meaning And Limits

The manifest is an assertion ledger, not a source of authority for application composition. Entrypoints, imports, stylesheet links, loaders, registries, and runtime code remain the executable authority. No runtime module reads the audit manifest, and adding a manifest record cannot make a capability available.

The audit can mechanically verify the implementation evidence for every declared capability, including the hard negative for `public_safe: false`. It cannot discover every conceptual capability hidden in arbitrary JavaScript or prove that an omitted capability should have been registered. Completeness is therefore a design and review obligation: any implementation that introduces or changes a reusable capability with a public/local composition decision must add or update its audit record.

Likewise, a green audit cannot prove the semantic claim behind `public_safe: true`. That claim still requires ordinary dependency, data, authority, and code review plus focused tests where warranted. The audit proves that the declared safety/composition/adoption model is internally complete and agrees with the mechanically visible code and stylesheet boundaries.

The existing public runtime manifest remains a deployable-file inventory and should not acquire these semantics. Combining the two would blur "available at a public URL" with "downloaded by a public route" and would risk making audit metadata look like runtime configuration.

## Required Audit Rules

The delivery should establish one deterministic, read-only auditor that:

1. validates the manifest schema, identities, required explicit booleans, known application kinds, and declared owners;
2. resolves the maintained public, Manage, and Review JavaScript entrypoints, including explicitly modelled dynamic loader edges rather than assuming that every runtime file is reachable;
3. resolves the stylesheets loaded by each shell and checks the declared capability selector ownership against them;
4. fails when `public_safe: false` intersects any public module, stylesheet, loader, registry, or adopter edge;
5. fails when `composed_by` disagrees with the resolved module or stylesheet graph;
6. fails when an adopter exists outside a composing shell or when a declared consumer identity cannot be found in its maintained registry or metadata owner;
7. prints a compact table of capability id, public safety, composers, adopters, and durable owner; and
8. exits non-zero with exact contradictions and file evidence suitable for code review and automated checks.

Static imports can be followed directly. Dynamic imports, loader maps, and selector families need explicit maintained evidence rather than heuristic whole-repository text matching. The delivery sanity pass must identify the smallest stable seams for that evidence before freezing the schema.

## When It Runs

There should be one cheap standalone project-local command for focused implementation and debugging. It must require no browser, local service, network access, generated public-site build, or writable external scope.

The same audit implementation should run automatically in maintained validation rather than relying on someone to remember a second bespoke command at closeout:

- add it to the `quick` check profile because the default profile is the cheap repository/configuration confidence gate;
- include it in the Docs Viewer validation path used by `docs-viewer-smoke`, directly or through one shared `site-validate` integration, without maintaining two divergent auditors; and
- require the standalone command or an inheriting profile at the end of any delivery that changes a registered capability, Docs Viewer entrypoint, dynamic loader, route stylesheet list, capability-owned selector family, or adopter registry.

"Automatic at the end of each implementation" therefore means inclusion in the maintained end-of-delivery check path, not a runtime hook, browser startup task, Git commit hook, or audit that silently edits the manifest. A delivery whose blast radius does not touch Docs Viewer capability composition need not run a Docs Viewer browser profile merely to satisfy this feature.

## Documentation Ownership

The shipped documentation should have four deliberately different owners:

- the checked audit manifest is the concise current inventory and the standalone command is the printable view;
- [Runtime Module Ownership](/docs/?scope=studio&doc=d-20260605-125108-1d1ef3) owns the durable entrypoint/import-graph model and should link to the audit contract;
- [Development Checklist](/docs/?scope=studio&doc=d-20260523-190651-7157ec) owns when an implementation must register or update a capability and which closeout evidence is required; and
- [Run Checks](/docs/?scope=studio&doc=d-20260501-174746-f92667) owns the exact standalone command and maintained profile placement.

[Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd) remains the durable report-specific interpretation. It should carry a concise link to the general audit instead of duplicating the manifest schema or command inventory.

At closeout, this feature should either become the concise durable conceptual owner and move beneath Docs Viewer Runtime, or transfer its current-state contract into a new durable child there. The Roadmap feature and any delivery record must not remain the only explanation of how the audit works.

## Boundaries

- No runtime capability registry, plug-in system, flag service, loader, or composition engine is introduced.
- Runtime code never reads the audit manifest and the auditor never rewrites source, imports, stylesheets, registries, or the manifest.
- `public_safe: true` never substitutes for source review, public-data review, or an explicit public adopter.
- The feature audits Docs Viewer application composition; it does not become a repository-wide JavaScript bundler or general dependency analyser.
- The feature does not merge the public deploy-file inventory with the composition audit.
- The initial delivery should seed a small reviewed set of meaningful cross-shell capabilities rather than classifying every helper function as a capability.
- Browser behavior and visual fit remain with focused feature verification; this audit protects static ownership and graph boundaries.

## Potential Delivery Shape

1. **Audit fit and schema** — inventory the first registered capabilities, identify stable static/dynamic JavaScript and stylesheet evidence, choose the manifest and command owners, and confirm that the check remains cheap and deterministic.
2. **Manifest and auditor** — implement schema validation, graph and selector checks, the hard public-negative rule, adopter consistency, compact printing, focused tests, and the initial reviewed records including Expanded Report View.
3. **Maintained check integration** — compose the single auditor into `quick` and the Docs Viewer validation path without duplicate implementations, then prove both focused and inherited command behavior.
4. **Durable handoff** — update Runtime Module Ownership, Development Checklist, Run Checks, and the report-specific composition owner; close only when the Roadmap record is no longer the sole operational authority.

## Acceptance Boundary

The feature is complete when a developer can run one documented command and see the declared safety, current composers, current adopters, and owner for every registered Docs Viewer capability; contradictory implementation edges fail with exact evidence; `public_safe: false` is mechanically enforced as absence from all public composition and adoption surfaces; the same auditor runs in the maintained cheap and Docs Viewer check paths; and durable documentation says both when to update the manifest and what a passing audit does and does not prove.
