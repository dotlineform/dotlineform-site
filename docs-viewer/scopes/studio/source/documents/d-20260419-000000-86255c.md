# Tag Source Data

## Canonical Owners

All four sources live under `studio/data/canonical/tags/`.

| Source | Owns | Why separate |
| --- | --- | --- |
| `tag-registry.json` | flat canonical tag identity, one scalar group, ordered document-location references, allowed-group policy | classification and references can change without changing tag identity |
| `tag-aliases.json` | shorthand keys and canonical tag targets | alias curation can evolve independently of canonical identity |
| `tag-assignments.json` | series tags and nested per-work override deltas | assignment state changes independently of vocabulary |
| `tag-groups.json` | ordered descriptive taxonomy prose | explanatory content is not registry or assignment state |

The exact schemas and limits are enforced by
`studio/services/tags/tag_source_model.py`; the JSON files are current data,
not documentation examples.

## Relationship Model

```text
tag-groups descriptions
        |
tag-registry canonical IDs + group + doc_url[]
        ^
tag-aliases shorthand targets
        |
tag-assignments series rows
        -> nested work override deltas
        -> public series/work membership indexes

registry doc_url[]
        -> zero or more canonical public document placements
        -> documents remain independently owned
```

Durable rules:

- registry IDs are globally unique slug-safe names; each row has exactly one
  independently validated scalar group;
- registry rows use `tag_registry_v5` and contain exactly `tag_id`, `group`,
  `doc_url`, and `updated_at_utc`; consumers display `tag_id`, and there is no
  registry-row label or description;
- `doc_url` is an ordered array. An empty array is a valid unlinked state;
  exact URLs cannot repeat within one row, but several tags may reference the
  same URL;
- supported values are canonical root-relative Analysis, Library, or
  configured `/docs/` routes. They contain no origin, fragment, or incidental
  viewer state;
- URL identity preserves placement context. One source document may therefore
  appear through more than one report URL;
- a stored URL may become unavailable. It remains canonical source data until
  an explicit edit removes it; no title or current UI context repairs it;
- documents contain no tag back-reference. Tag and document group, title,
  content, and lifecycle remain independent after any creation-time seed;
- aliases and assignments store flat canonical IDs;
- alias targets must be canonical tags and may not duplicate a registry-
  resolved group within one alias;
- a work override belongs under one series row, not in a global work table;
- effective work tags combine series tags with the override delta;
- an override that duplicates a series tag is removed during normalization;
- series/work membership comes from public catalogue indexes and remains externally owned.

## Write Boundary

The browser reads and writes through the allowlisted `/studio/api/tags/...`
boundary. Mutation planners validate cross-file effects before
`studio/services/tags/tag_write_transactions.py` atomically replaces one or
more canonical files.

`tag-groups.json` is currently read-only through the app. Registry, aliases, and assignments are writable.

New Tag validates its submitted tag and destination, creates one Analysis
`tags` source document, stores that document's canonical published placement at
`doc_url[0]`, rebuilds the exact child projection, and records the action as one
transaction. It does not audit, deduplicate, or repair other rows.

Edit Tag submits the immutable `tag_id`, accepted scalar group, and complete
ordered `doc_url[]`. The write validates supported URL shape and within-row
duplicates, but not current document-location-provider membership: a selected
location may become unavailable before Save and stale references must remain
removable. Delete removes the tag and its accepted alias/assignment effects;
it never deletes a referenced document.

The title picker and Registry presentation read the compact public
document-location projections. Those projections are rebuilt from published
search/report/sub-scope data during the owning publication flow; unpublished
source or manage-only data is not an authoring option.

## Change Method

- vocabulary change: start with Registry/Aliases planners and inspect assignment effects;
- assignment change: preserve series-first ownership and validate catalogue membership;
- registry location change: preserve exact URL order and identity; do not infer
  a replacement from title, selected parent, displayed document, or another
  placement;
- schema change: update loaders, focused mutation paths, migrations, audits,
  public location projections, and focused tests;
- catalogue membership change: use the Studio catalogue synchronization path,
  then run the narrow consistency check.

## Weak Spots

- cross-file referential integrity is enforced in services/audits rather than by one transactional database;
- assignment validity depends on generated public catalogue indexes;
- aliases can preserve historical selection context in assignments, creating a subtle dependency even after canonical IDs are resolved;
- deleting or unpublishing a document does not update `tag-registry.json`;
  unavailable URLs remain until an explicit tag edit;
- URL validation proves canonical supported shape, not live provider
  membership or continued resolution;
- Studio currently offers an Analysis-only link picker and no bulk repair,
  reorder, or Library/Studio association UI;
- hand-editing JSON bypasses planners and activity records.

[Site Consistency Audit](/docs/?scope=studio&doc=d-20260331-000000-cdc571) is the cross-boundary check. Focused schema behaviour lives in the tag service tests.
