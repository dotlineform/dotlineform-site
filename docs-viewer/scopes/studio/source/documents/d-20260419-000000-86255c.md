# Tag Source Data

## Canonical Owners

All four sources live under `studio/data/canonical/tags/`.

| Source | Owns | Why separate |
| --- | --- | --- |
| `tag-registry.json` | flat canonical tag identity, one scalar group, optional exact primary-document override, allowed-group policy | classification and primary preference can change without changing tag identity or document membership |
| `tag-aliases.json` | shorthand keys and canonical tag targets | alias curation can evolve independently of canonical identity |
| `tag-assignments.json` | series tags and nested per-work override deltas | assignment state changes independently of vocabulary |
| `tag-groups.json` | ordered descriptive taxonomy prose | explanatory content is not registry or assignment state |

The exact schemas and limits are enforced by
`studio/services/tags/tag_source_model.py`; the JSON files are current data,
not documentation examples.

## Relationship Model

```text
tag-groups descriptions
        |
tag-registry canonical IDs + group + optional primary_document
        ^
tag-aliases shorthand targets
        |
tag-assignments series rows
        -> nested work override deltas
        -> public series/work membership indexes

Analysis Tags document tag_id declarations
        -> private ordered tag-associations.json
        -> Studio read-only document pills
```

Durable rules:

- registry IDs are globally unique slug-safe names; each row has exactly one
  independently validated scalar group;
- registry rows use `tag_registry_v6` and require `tag_id`, `group`, and
  `updated_at_utc`; they may additionally store one exact Analysis Tags
  `primary_document` target and contain no row label, description, or
  association-membership array;
- Analysis Tags document front matter owns optional exact `tag_id` membership.
  The private `docs_tag_associations_v1` product groups valid declarations and
  orders documents by exact `{scope, sub_scope, doc_id}` identity;
- a missing primary is valid. A stored primary may become unavailable and is
  retained until another current associated document replaces it or the
  complete Tag row is deleted; there is no clear-primary mutation;
- Tag Registry group and document group, title, content, publication, and
  lifecycle remain independent;
- aliases and assignments store flat canonical IDs;
- alias targets must be canonical tags and may not duplicate a registry-
  resolved group within one alias;
- a work override belongs under one series row, not in a global work table;
- effective work tags combine series tags with the override delta;
- an override that duplicates a series tag is removed during normalization;
- series/work membership comes from public catalogue indexes and remains externally owned.

## Write Boundary

The browser reads and writes through the allowlisted `/studio/api/tags/...`
boundary. Mutation planners validate cross-file effects before
`studio/services/tags/tag_write_transactions.py` atomically replaces one or
more canonical files.

`tag-groups.json` is currently read-only through the app. Registry, aliases, and assignments are writable.

New Tag creates only the Registry row. It does not create a document or an
association.

Edit Tag submits the immutable `tag_id`, accepted scalar group, and only an
explicitly changed exact current `primary_document`. Omitting the primary
preserves an existing current or stale value; null is not a clear operation.
The editor reads the private association product and cannot search, add,
remove, or reorder document membership.

Delete Tag and Demote Tag re-read current Analysis Tags source declarations and
are blocked while any document declares the Tag. They never rewrite or delete
document source. Conversely, document delete and `tag_id` assignment,
reassignment, or clear rebuild associations without inspecting or mutating the
Registry primary.

## Change Method

- vocabulary change: start with Registry/Aliases planners and inspect assignment effects;
- assignment change: preserve series-first ownership and validate catalogue membership;
- association change: edit the exact Analysis Tags document declaration and
  rebuild its private projection; do not mutate membership in Studio;
- primary change: accept only one exact current association and preserve stale
  stored identity on unrelated edits;
- schema change: update loaders, focused mutation paths, migrations, audits,
  private association consumers, and focused tests;
- catalogue membership change: use the Studio catalogue synchronization path,
  then run the narrow consistency check.

## Weak Spots

- cross-file referential integrity is enforced in services/audits rather than by one transactional database;
- assignment validity depends on generated public catalogue indexes;
- aliases can preserve historical selection context in assignments, creating a subtle dependency even after canonical IDs are resolved;
- deleting or disassociating a selected document does not update
  `tag-registry.json`; the unavailable primary remains visible until explicit
  replacement or Tag deletion;
- the displayed association product is generated, so a source mutation must
  rebuild it before Studio reflects new membership; primary writes and
  destructive guards still revalidate current source;
- Studio has no membership picker, reordering, or bulk association repair UI;
- hand-editing JSON bypasses planners and transaction safeguards.

[Site Consistency Audit](/docs/?scope=studio&doc=d-20260331-000000-cdc571) is the cross-boundary check. Focused schema behaviour lives in the tag service tests.
