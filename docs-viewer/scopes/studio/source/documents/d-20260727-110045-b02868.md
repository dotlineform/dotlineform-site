# Flat Tag Identity Delivery

## Complete Result

Studio reads, assigns, creates, edits, deletes, promotes, and demotes canonical
tags using globally unique flat IDs such as `moss`. Every tag retains exactly
one scalar group such as `subject`.

No canonical source, assignment, alias rule, service contract, route, or
analysis behavior parses the tag ID to recover group. Group-dependent behavior
continues by resolving the scalar group from the registry. Registry labels and
descriptions remain available, including the results of manual collision
editing, so Tag-document linking can transfer descriptions into documents.

The transitional registry record after this delivery is:

```json
{
  "tag_id": "moss",
  "group": "subject",
  "label": "moss",
  "description": "<temporary document seed content>",
  "updated_at_utc": "<timestamp>"
}
```

## Migration Gate

Before mechanical migration, verify that every current label is globally
unique. Any remaining labels with more than one namespaced registry row require
manual resolution before IDs are rewritten.

For each collision, decide:

- the resulting flat `tag_id` and its one group;
- the combined or rewritten registry description retained for document seeding;
- assignment references that collapse to the flat ID;
- alias targets and historical selection context; and
- whether any genuinely different concept needs a genuinely different name.

Keep the reviewed decisions inspectable until exact reconciliation proves that
the proposed flat IDs are unique and all references have one intended target.
Do not infer unresolved outcomes from matching labels or descriptions.

## In Scope

- Change canonical registry identity from `<group>:<slug>` to one globally
  unique normalized tag name.
- Require exactly one scalar `group` on every registry row and reject a
  `groups` array.
- Preserve registry `label`, allowed-group policy, the canonical tag-group
  taxonomy source, and group-derived configuration.
- Preserve one registry `description` per resulting tag as temporary semantic
  source for Tag-document linking.
- Migrate canonical series and work assignment references without changing
  their record shape, series-first ownership, or override semantics.
- Migrate alias targets and historical selection context; preserve one-target-
  per-group constraints by resolving target groups through the registry.
- Update first-class create, edit, rename, delete, promotion, demotion,
  validation, transaction, rollback, activity, and manual-patch behavior.
- Replace every group-prefix parse with a registry lookup while retaining group
  selection, filtering, ordering, chips, styling, configuration, group routes,
  coverage/scoring, and group-derived analytics.
- Update focused services, APIs, frontend modules, audits, checks, and tests to
  the flat identity contract.

## Not In Scope

- Creating, linking, editing, or publishing tag documents.
- Adding `doc_id` to the registry or removing registry `description`.
- Removing registry `label`, group policy, group taxonomy, or group-dependent
  UI and analysis.
- Replacing scalar `group` with `groups`, categories, facets, senses,
  namespaces, or a compatibility prefix.
- Inferring collision outcomes automatically.
- Changing catalogue membership or the series/work assignment ownership model.
- Adding Tag semantic-token targets.

## Delivery Steps

1. [ ] **Close prerequisites and freeze the migration input.** Complete Tag
   Vocabulary Import Retirement, then snapshot the registry, aliases, and
   assignments used for the cutover. Reject the input unless every tag has one
   allowed scalar group, every alias and assignment target resolves, and every
   proposed flat ID is globally unique.
2. [ ] **Change the domain contract against fixtures.** Replace namespaced
   `tag_id` validation with flat slug-safe validation, validate `group`
   independently, and bump the affected canonical source versions. Change
   one-target-per-group alias validation to resolve each target through the
   registry. Keep assignment row shape, weights, inheritance, and historical
   alias context unchanged.
3. [ ] **Produce a read-only migration preview.** Generate the exact
   old-`tag_id` to flat-`tag_id` map and project its effects across registry
   rows, alias targets, series assignments, and work overrides. Report
   pre/post counts, merges, unresolved references, duplicate outputs, and
   preserved group/label/description values. Apply nothing until the preview
   reconciles cleanly.
4. [ ] **Update mutation and HTTP contracts.** Make create accept flat `tag_id`
   and scalar `group` as separate values; make promotion use the alias key as
   the flat ID while retaining its separately chosen group. Update edit, rename,
   delete, promotion, demotion, preview, apply, activity, rollback, and
   manual-patch paths without weakening their current cross-file planning or
   atomic-write guarantees.
5. [ ] **Update browser consumers.** Remove prefix parsing from registry,
   aliases, assignment editing, and series reporting. Continue to require one
   group choice for creation and promotion, and preserve group filters, chips,
   ordering, alias constraints, coverage, and scoring by using registry group
   data.
6. [ ] **Perform one code-and-data cutover.** Apply the reviewed registry,
   aliases, and assignments projection with the corresponding service and
   browser changes. Do not introduce a dual-read mode, compatibility IDs, or
   prefix aliases. The cutover must either replace every affected canonical
   source or restore the original bytes.
7. [ ] **Reconcile and close.** Prove that every registry ID is flat, every tag
   has one allowed group, every alias and assignment resolves, no executable
   path derives group from an ID, and mapped effective series/work tags retain
   their intended weights and inheritance. Run focused model/planner/API tests,
   the `studio-tag-smoke` profile, scoped source searches, and a manual pass
   through Registry, Aliases, Series Tags, and Series Tag Editor before
   updating the durable destination documents.

## Completion And Evidence

- Every canonical registry row has one unique flat `tag_id` and exactly one
  allowed scalar `group`.
- Registry labels and all descriptions needed by the next feature survive
  under the reconciled flat identities.
- Every canonical assignment and alias target resolves to a current flat tag.
- No executable path parses a tag ID prefix to recover group.
- Group filters, styles, alias constraints, reports, coverage, and scoring
  resolve group from the registry.
- New Tag and promotion create flat IDs while requiring one group choice.
- Rename, delete, demotion, and assignment writes preserve their existing
  cross-file planning, atomic replacement, rollback, and activity guarantees.
- Focused model/planner/API tests, route/module checks, exact canonical-data
  reconciliation, scoped source searches, a manual UI pass, and
  `git diff --check` support only this bounded migration.
