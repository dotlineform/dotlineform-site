# Docs Viewer Search Relevance

## Status And Purpose

This document retains the proposed relevance model for all Docs Viewer full-text scopes. It is not implemented: the current v2 scorer still uses broad field tiers and alphabetical ties. [SM-2 — Docs Viewer Search Relevance Delivery](/docs/?scope=studio&doc=d-20260813-222008-35fcfa) is the gated implementation vehicle.

The aim is modest: make the useful part of a broad result list easier to find while preserving one small static-index system. Docs Viewer Search is not intended to reproduce a web search engine.

## Shared Policy, Corpus-Specific Evidence

Every parent scope that adopts full text should converge on the same basic policy:

- index eligible visible `title`, `heading`, `body`, and `code` content through the shared extractor;
- use the same tokenizer, query semantics, scorer, and deterministic tie-breaks;
- keep structural identity, parent context, update time, routes, and publication metadata outside ordinary vocabulary; and
- let the scope continue to own document membership, public/private projection, payload acceptance, and publication timing.

The search algorithm should not contain scope-name branches. A biology article, metaphysics essay, Studio delivery, and Processing note should all pass through the same mechanics.

What changes naturally is the corpus statistics. A term occurring in one Analysis parent or sub-scope article is more distinctive there than a term occurring in nearly every document in the combined Analysis corpus, regardless of how common either term is in Studio. Those statistics should be generated independently inside each scope index and consumed by the same scorer. [DSI-2 — Scope-Level Sub-Scope Search Delivery](/docs/?scope=studio&doc=d-20260813-225547-cd82d8) retains the implemented combined-corpus membership and exact child-navigation evidence.

## Vocabulary And Language

Domain terms do not need registration. The shared Unicode tokenizer already retains ordinary names and specialist vocabulary, plus technical compounds and useful components. For example, `Charles Darwin` supplies `charles` and `darwin`; `quantum-mechanics` supplies the compound and its components; terms such as `metaphysics`, `DNA`, `p53`, and Latin biological names remain eligible.

Do not create per-scope dictionaries, person registries, curated scientific vocabularies, domain stop-word lists, or a term-management UI. Such lists would require continual editorial maintenance, create unexplained omissions, and make the same query behave differently between scopes.

Keep the shared stop-word list small and limited to genuinely general function words. A common word should normally remain searchable and contribute less ranking weight through corpus frequency rather than disappear. For example, `not` is common and often unhelpful in Studio but can be conceptually important in philosophy.

Actual language mechanics remain shared evidence-led extensions:

- accent-insensitive query aliases could let `Schrodinger` find `Schrödinger` while retaining the authored spelling;
- scientific single-character symbols such as `ψ` are currently excluded and should be considered only with representative demand;
- multi-word names currently work as an all-term intersection, not as an exact phrase;
- stemming, singular/plural folding, possessive handling, transliteration, and language-specific stop-word packs should not be added without failures from real corpus queries.

These are tokenizer or query capabilities, not scope vocabulary customisation.

## Current Baseline

The shared v2 query path currently gives each matching document one categorical score: exact identity 1000, exact full title 900, title 800, heading 700, parent title 500, body or code 400, and update metadata 300. Only configured searchable fields participate. Full-text Studio therefore uses exact title, title, heading, and body/code; body/code ties sort alphabetically by title and then document ID.

Postings record that a term occurs in a document field, not how often it occurs. They contain no document length, positions, phrase proximity, or exact-versus-prefix match strength. One body occurrence and ten body occurrences therefore rank equally.

Body and code retrieval are principal reasons to adopt full text. A body-only result is not inherently low relevance, so the current field tiers must not be relabelled as `High`, `Medium`, and `Low`.

## Candidate Ranking Signals

Evaluate each signal independently before combining them:

| idea | possible value | cost or risk | disposition |
| --- | --- | --- | --- |
| exact indexed-token matches before prefix-expanded matches | reduces noise for short broad queries such as `reg` while retaining useful prefix search | must remain deterministic for multi-term queries | primary candidate |
| inverse document frequency within the active scope | lets uncommon names and specialist terms contribute more than corpus-wide vocabulary without a dictionary | needs a clear bounded formula and representative-query evidence | primary candidate |
| capped per-field term frequency such as 1, 2, or 3+ | distinguishes a substantive discussion from a passing mention without rewarding repetition linearly | increases generated data and can favour boilerplate or long documents | primary candidate |
| light document-length normalisation | reduces the advantage of long documents | can over-correct concise reference documents and adds complexity | conditional; use only if frequency evidence exposes length bias |
| same-field or concentrated multi-term matches before matches scattered across fields | may improve multi-term intent without phrase positions | needs careful interaction with field priority | secondary candidate |
| phrase or positional proximity | can distinguish a person's full name or compact concept from scattered terms | materially expands index and scorer complexity | park unless simpler signals demonstrably fail |
| date as a tie-break | surfaces recently changed material | recency is not relevance and may bury established authority documents | park |
| alternate `Rank` / `Updated` result ordering | makes recent matching documents easy to reach | abandons the relevance order instead of improving it | park as a separate need, not SM-2 follow-through |

A likely small model is field importance plus exact-token preference, inverse document frequency, capped frequency, and at most light length normalisation. That is a hypothesis for measurement, not an accepted formula.

## Result Explanation

Do not add a relevance badge by default. `High`, `Medium`, and `Low` would overstate the scorer and mischaracterise deliberate body searches.

If improved ordering still needs explanation, use factual presentation only: `Title`, `Heading`, or `Text/code` match labels, a divider when the field band changes, or aggregate counts by match source. These explain where a match occurred; they do not claim to measure user intent.

## Diagnostics, Not Term Management

A read-only vocabulary audit can help validate extraction and payload without becoming configuration. Useful columns are term, document frequency, contributing fields, scope document percentage, and approximate payload cost. It can reveal structural leakage, boilerplate, or a surprisingly dominant term.

High frequency alone is not a deletion rule. Representative query results should decide whether a term is harmful. Evaluation sets should include known titles, headings, body prose, code or scientific notation where relevant, short prefixes, broad body-only terms, multi-term concepts, names of people, and specialist domain terms.

Studio is the first available full-text test corpus. Analysis should become the public validation corpus once it contains enough eligible parent and sub-scope articles, including representative biology, metaphysics, quantum-mechanics, and named-person queries. Relevance statistics and evaluation must cover that combined corpus without boosting or penalising a document merely because it belongs to a sub-scope. Later full-text scopes should adopt the same policy rather than repeat a vocabulary-design exercise.

## Boundaries

This model does not add semantic search, embeddings, a remote service, query logging, click or popularity scoring, personalisation, synonyms, spelling correction, automatic ontology expansion, result snippets, highlighting, section-level results, or a generic ranking framework. Catalogue Search remains a separate domain-owned search system.

[Docs Viewer Search Index](/docs/?scope=studio&doc=d-20260813-214350-4c7a21) owns payload structure and fields. [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-214351-98d3f0) owns term recognition. This document owns the proposed shared relevance behavior and its deliberately rejected vocabulary-management alternatives.
