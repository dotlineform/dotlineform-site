# iPad Docs Viewer Concept And Feasibility

## Feasibility Claim

The current evidence supports a serious real-device proof: most Docs Viewer manage behavior should be able to run locally on iPad through a Linux environment, with Safari as the UI and an iCloud Drive folder mounted as `DOTLINEFORM_PROJECTS_BASE_DIR`. This is a feasibility hypothesis, not a confirmed platform contract, until [iPad Docs Viewer Installation And Proof](/docs/?scope=studio&doc=d-20260808-205416-9f6d6c) passes on the target iPad.

The likely result is a useful session-based Docs Viewer with external-scope access, not unchanged macOS parity. The application already has a loopback Python service, browser-managed UI, generated static products, explicit external-local paths, and subprocess-based rebuilds. Those are a better fit for [iSH](https://ish.app/) than for a native Python editor sandbox.

## Proposed Stack

| component | role | status |
| --- | --- | --- |
| iPadOS Files and iCloud Drive | expose the existing external projects base and keep its contents available locally | required |
| iSH | provide local Alpine Linux, Python, child processes, sockets, Git, native packages, and the iOS File Provider mount | required runtime |
| Safari | open the manage UI on `http://127.0.0.1:8776/docs/` | required UI |
| Git in iSH | clone and operate the proof checkout in iSH's Linux filesystem | baseline source-control path |
| Working Copy | optional Git UI if it can safely access the same checkout without moving the runtime clone onto a less reliable File Provider path | optional after the baseline gate |
| Textastic or another Files-aware editor | optional direct source editor for folders the app can access | optional convenience |
| Codespaces | remote fallback for repo-local development and checks | complementary, not an external-scope solution |

The baseline keeps the Git checkout inside iSH and mounts only the external project tree from iCloud. This avoids putting `.git`, the Python environment, caches, and frequent generated writes on a File Provider filesystem while still giving Docs Viewer the external root it actually needs.

```text
Safari
  -> http://127.0.0.1:8776/docs/
      -> Python Docs Viewer service in iSH
          -> repository checkout and repo-backed scopes in iSH storage
          -> /mnt/dlf-projects
              -> Files provider
                  -> iCloud Drive external scopes and workspaces
```

[Working Copy](https://workingcopyapp.com/) can clone, inspect, commit, and push repositories on iPad, and [Textastic external folders](https://www.textasticapp.com/v10/manual/managing_files/local_files_icloud.html) can open folders exposed through Files. Neither is required to prove Docs Viewer. A shared clone between those apps and iSH is an additional File Provider behavior to verify rather than an assumed part of the stack.

## Why iSH Is The Baseline

Docs Viewer uses `ThreadingHTTPServer`, loopback sockets, subprocesses for document and search rebuilds, compiled Python dependencies such as lxml and Pillow, and ordinary repository paths. iSH supplies an emulated x86 Linux userspace with Alpine packages and supports mounting a folder selected from Files through `mount -t ios`.

Native iPad Python IDEs and shell apps remain useful for focused scripts or editing, but they are not interchangeable with this runtime. For example, [a-Shell](https://github.com/holzschu/a-shell) documents WebAssembly limits including no sockets or forks and permits `pip` installation only for pure-Python packages. Any alternative app must prove the same required sockets, subprocess, native-extension, path, and Files-provider behavior before replacing iSH in the baseline.

## Current Repository Fit

The current integrated service is a Python `ThreadingHTTPServer` started from `docs-viewer/services/docs_viewer_service.py`. It serves the manage shell and tracked browser assets directly from the checkout. Managed saves run the document and search builders as child Python processes through `docs_write_rebuild.py`. The local manage route does not need Jekyll or Ruby.

External-local scope paths are resolved below `DOTLINEFORM_PROJECTS_BASE_DIR`; the same base also owns adjacent `data-sharing` and `projects` workspaces used by integrated workflows. iSH can ask the Files picker to mount the exact iCloud parent at a stable Linux mount point, as described by the [iSH File Provider mount guide](https://github.com/ish-app/ish/wiki/Mounting-other-file-providers).

This fit is for the current integrated checkout. It does not prove the package boundary proposed by Standalone Docs Viewer and should not be described as the standalone application.

## Expected Working Slice

| capability | expectation before device proof | qualification |
| --- | --- | --- |
| service health and manage shell | should work | Python service and static browser assets are self-contained in the checkout |
| repository-backed Studio and Processing scopes | should work | normal generated products must be present or rebuildable |
| configured iCloud-backed external scopes and sub-scopes | should work | depends on complete local download and correct File Provider mount behavior |
| index, document rendering, recent activity, and search | should work | generated reads and browser assets are ordinary local files |
| Source editor save and managed document/search rebuild | should work | subprocess execution is supported; atomic writes and renames across the iCloud mount must pass the gate |
| Markdown and HTML import | should work | ordinary Python parsing and source writes |
| DOCX import | expected with Mammoth installed | must pass one real import including any extracted image behavior used by the test document |
| JPEG and PNG document-package media | expected with Pillow installed | HEIF, video, and macOS-specific media tools are not implied |
| Docs Review and document-package workflows | expected with the integrated workspaces mounted | the proof must use disposable packages and must not infer success from the route merely loading |
| inline Mermaid rendering in Manage | should work | it uses the tracked browser Mermaid bundle rather than server-side Chromium |
| tracked public-site preview | should work through a second Python server | this previews `site/`; it is not a Jekyll rebuild |
| Git status, diff, commit, fetch, and push | should work through Git in iSH | remote authentication and a Working Copy UI are separate concerns |

## Known Or Likely Exclusions

- **Open Source and local-folder activation:** current source-open actions invoke platform applications, and `docs_local_links.py` deliberately enables local-folder activation only on Darwin. Local targets can still be authored and validated, but iSH cannot claim Finder-style reveal/open behavior.
- **Server-produced Mermaid SVG:** public projection and related build paths require the checked Node `mmdc` toolchain, Puppeteer, and Chromium. Installing that stack inside iSH is not part of the baseline and is likely impractical. Browser-side Manage rendering remains separate.
- **Always-on service:** iPadOS may suspend iSH when it is backgrounded or the device is locked. The feature promises a foreground or multitasking session that can be restarted safely, not a persistent daemon.
- **Complete desktop toolchain:** Jekyll production builds, the full repository test/lint toolchain, macOS `sips`, HEIF conversion, video workflows, and other platform utilities are outside the first proof.
- **Unproved public and remote publication paths:** static preview can be tested locally, but credentialed R2 publication and other network side effects require a later explicitly authorized proof.

These exclusions are honest platform boundaries, not automatic reasons to reject the feature. A device proof fails only when the required working slice is unreliable or unsafe for external data.

## iCloud Data Boundary

The selected Files folder must be the exact parent represented by `DOTLINEFORM_PROJECTS_BASE_DIR`, normally containing `docs-viewer/`, `data-sharing/`, and `projects/`. Mark the required tree **Keep Downloaded** before the proof. Placeholder-only files, partial downloads, or an accidentally selected child folder invalidate the test.

The service writes source and generated files atomically and may use temporary siblings and renames. The gate therefore tests the actual iSH-to-Files-to-iCloud path rather than only confirming that Python can list a mounted directory. It must prove write, rebuild, restart, Mac-side synchronization, and cleanup with a disposable external document.

Do not edit the same proof document concurrently on the Mac and iPad. iCloud remains synchronization transport, not locking, Git, or transaction coordination. A conflict copy, resurrected temporary file, partial generated tree, or lost rename is a platform blocker until understood.

## Configuration Decision

An iPad-specific environment file is useful operationally, but a new tracked `env.ipad` contract is not needed for the first proof. The repository already ignores and loads clone-local `.env.local`, which is the correct place for the device-specific iSH mount path and local capability switches. It must contain no credentials and must remain untracked.

The current loaders do not read `env.ipad` automatically. Adding one now would create a second configuration convention without a launcher, precedence rule, ignore rule, or test. If repeated iPad use later demonstrates a need for named profiles, add a bounded delivery for an explicit non-secret example, untracked active file, launcher, precedence contract, and focused verification. Until then, use `.env.local` and keep the installation guide authoritative for its minimal iPad values.

## Success Meaning

Passing the proof establishes that the current integrated Docs Viewer is practically usable on the tested iPad for the required local and iCloud-backed scope slice, with recorded platform exclusions. It does not establish support for every iPad model, every iPadOS or iSH release, unattended background operation, the future standalone composition, or full desktop development parity.
