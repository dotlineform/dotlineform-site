# First-class Alias Creation Delivery

## Complete Result

New Alias creates exactly one canonical alias through a first-class server
mutation and no longer calls the bulk tag-alias import route.

The user-visible workflow remains the same: enter an alias key and description,
select canonical targets, create, then reload canonical aliases and record
activity evidence.

## Why This Comes Before Removal

The current browser create path sends a one-alias payload to the import endpoint
in `add` mode. Bulk alias import cannot be removed safely until ordinary
creation has its own contract.

## In Scope

- Add a focused alias-create planner and server request/response contract through
  the Studio tag mutation boundary.
- Enforce slug-safe alias identity, duplicate rejection, description
  normalization, canonical target existence, and one target per group.
- Add one alias without rewriting unrelated alias records.
- Use the existing allowlisted atomic write and activity owners, with a distinct
  create action rather than import-shaped evidence.
- Switch the New Alias browser workflow to the create operation.
- Preserve the supported manual JSON patch fallback when the local write service
  is unavailable.
- Cover service, route, browser payload, runtime configuration, and activity
  behavior with focused tests.

## Not In Scope

- Removing bulk alias or registry import UI and endpoints; that belongs to the
  final removal delivery.
- Changing alias edit, delete, promotion, tag demotion, or assignments.
- Adding new alias semantics or changing existing canonical alias records.
- Changing the offline assignment-session workflow.

## Likely Authority

- `studio/services/tags/tag_source_model.py`
- `studio/services/tags/tag_alias_mutations.py`
- `studio/services/tags/tag_write_transactions.py`
- `studio/app/server/studio/studio_tag_api/aliases.py`
- `studio/app/server/studio/studio_tags_api.py`
- `studio/app/frontend/js/tag-aliases-service.js`
- `studio/app/frontend/js/tag-aliases.js`
- Studio runtime service and activity configuration
- focused alias planner, route, workflow, and smoke tests

These are inspection starting points, not a requirement to change every file.

## Completion And Evidence

- A valid request adds exactly one normalized alias and leaves all existing
  aliases unchanged.
- Invalid key, duplicate key, missing target, unknown target, duplicate target,
  and repeated target-group requests fail before any write.
- New Alias no longer requests the alias-import endpoint in direct-write mode.
- Successful creation reloads canonical aliases and records one create-alias
  activity action.
- Manual patch mode still produces one valid alias fragment without implying
  that it was written.
- Focused planner/API tests, route/module integration checks, and a manual New
  Alias interaction pass support only these claims.
- `studio/data/canonical/tags/tag-aliases.json` is unchanged by delivery
  implementation and verification.

## Durable Destination

Transfer the shipped create workflow and extension boundary to
[Tag Aliases](/docs/?scope=studio&doc=d-20260331-000000-519b1e).
