# Docs Viewer Scope Type Migration

## Purpose

Allow a lifecycle-owned Docs Viewer scope to change between the supported external, local-repository, and public profiles while preserving its exact scope identity, document identities, source relationships, sub-scopes, and logical media references.

This is a migration feature, not editable configuration. Changing type can relocate the canonical scope root, add or remove public document routes and projections, normalize publication-only metadata, and rebuild consumer products. Explicit media storage policy is independent and remains unchanged; only media deliberately configured as scope-local follows a relocated scope root.

## Concept

[Docs Viewer Scope Type Migration Concept](/docs/?scope=studio&doc=d-20260808-225258-245f13) owns the supported profiles, transition contracts, migration transaction, publication boundary, recovery model, delivery seams, and proof gate.

No delivery has been proposed and no implementation has started.

## Feature Contract

- Management exposes one **Change scope type** workflow for eligible scopes; it does not expose arbitrary `scope_type`, provider, path, route, or projection editing.
- The three supported profiles remain `local_external`, `local_committed`, and `public_readonly`. Public external storage is not introduced.
- The immutable `scope_id` and every document identity remain unchanged. Type migration is not Copy, rename, import, or semantic transformation.
- Canonical source and scope-local media are copied and byte-verified before a relocated target root becomes authoritative. Generated documents and search are rebuilt rather than treated as migration source.
- A successful migration leaves exactly one configured canonical scope root and no runtime fallback to the former root.
- Entering public mode does not publish existing content. The existing scope-wide Publish remains the only positive public document mutation.
- Leaving public mode removes the exact public route, document/search projections, and derived Catalogue document URLs. It reports but does not change independently configured repository, external-local, or R2 media destinations; local scope access is not a media-privacy claim.
- The parent scope and all configured one-level sub-scopes migrate as one topology. Partial conversion is blocked.
- Failure before the commit point leaves current authority unchanged. Failure after it reports committed state and exact follow-through instead of attempting an ambiguous rollback.

## Relationship And Boundaries

[Scope Lifecycle](/docs/?scope=studio&doc=d-20260515-000000-f43740) remains the durable current-state owner for create, rename, delete, configuration/manifest ownership, public isolation, and known transaction limitations. [Public Scopes](/docs/?scope=studio&doc=d-20260331-000000-f992b9) remains the durable owner of working-to-public publication. [Scope Media Storage Locations](/docs/?scope=studio&doc=d-20260808-231126-6a5d72) separately owns per-media-type destination policy and provider migration. A completed implementation must transfer the shipped scope-migration contract into the durable lifecycle/publication owners rather than leaving this feature as current-state authority.

This feature does not add arbitrary roots, an external-public profile, media destination changes, automatic link rewriting, content comparison, a second Publish flow, provider fallback, duplicate canonical locations, background synchronization, or a generic migration framework. Built-in or backfilled scopes are outside the first eligibility boundary unless a separate exact adoption decision is made.

## Success Meaning

The feature succeeds when every offered transition can be previewed from current server-owned topology, applied without identity change, media-policy change, or implicit publication, and proven by byte identity for relocated scope-owned material, rebuilt target products, exact public document cleanup, and fault-path evidence. Merely changing `docs_scopes.json` or moving a directory manually is not completion.
