# SSP-2.1 — Project State Producer Evidence

## Outcome

SSP-2.1 is complete at its review gate. `docs_project_state.py` owns one server-side full reconciliation that scans the immediate children of `projects/`, validates matching Projects subject receipts and exact collections, reads canonical Works and Series through the existing catalogue source owner, returns one `docs_project_state_report_v1` response, and atomically publishes the matching `docs_project_state_folder_lookup_v1` under `var/docs/project-state/folder-lookup.json`. Both products carry the same content generation and subject generation.

The implementation contains 524 physical production lines after the standalone service bootstrap correction and 405 focused test lines. This exceeds the initial rough 300–400 production-line estimate. The size review was accepted before the real-data run because the retained code is confined to exact input validation, typed reconciliation, identity-only lookup projection, atomic replacement, and stale-state retention; SSP-2.2 retains the route, report registry, browser module, and visual presentation owners.

## Accepted Product Contract

The physical scan uses the existing confined Projects directory owner and accepts only readable, non-symlink, non-hidden immediate directories below `projects/`. Those exact keys establish every report and lookup row. Project documents join independently through exact valid `folder_path` associations after the Manage manifest and subject-association generation and collection agree. Canonical Works join independently through `projects/<project_folder>` and project only `work_id`, `project_folder`, and `series_ids`; Studio catalogue/media retains the remaining Work fields.

Each live row carries exact folder presentation, ordered Project-document targets and links, semantic Work targets with current Series membership, canonical Series targets with exact Work IDs and counts, exceptional Series evidence, a distinct matched-Work count, and explicit reconciliation/document/Series states. The persisted folder lookup retains only the exact folder subject, semantic Work and Series targets with membership IDs, exact Project-document targets, generation receipts, and current/stale status. Presentation labels, routes, Work status, and media fields retain their existing owners.

On a successful run, a validated complete lookup replaces the prior file atomically. A failed write-enabled refresh retains the prior complete generation and relationships and atomically changes its status to stale with the failed time and bounded reason. A read-only run creates no lookup.
