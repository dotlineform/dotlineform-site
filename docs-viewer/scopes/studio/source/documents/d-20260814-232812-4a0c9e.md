# Clone-Ready Docs Viewer

## Purpose

Make the repository checkout a real, documented Docs Viewer composition. After cloning the repository and installing its declared dependencies, someone can run one command and receive a coherent application using only data and services available in that clone.

This is source-checkout portability, not a separately packaged product. It is one concrete motivation and proof scenario for [Docs Viewer Core and Integration Architecture](/docs/?scope=studio&doc=d-20260814-225646-8f7d2a).

## Scenario

A person clones the repository because they want to inspect, develop, or understand Docs Viewer. They have no `.env.local`, private Projects workspace, Studio process, public-site preview, R2 credentials, document-package workspace, or Docs Review context. They follow short checked-in instructions and start Docs Viewer successfully.

The resulting application exposes a deliberately selected clone-safe scope set and only the capabilities backed by that composition. It does not advertise private scopes, invent localhost destinations for absent applications, or fail while resolving integrations the person did not select.

## Current Gap

The present checkout has no supported clean-clone run path. Its broad runner starts the public preview, Studio, Docs Viewer, and Review together; the direct launcher enters the same repository-integrated service; the tracked scope registry includes external-local scopes and an external managed-media workspace; optional package, Review, Studio, and full-registry dependencies are imported or resolved before a minimal application can start.

The first missing external workspace can therefore prevent startup before the route exists. If startup dependencies are supplied, the Manage composition still receives Studio and public-preview origins whether those applications are running or not. The problem is not inadequate instructions alone; the selected application composition is not yet a clean-clone boundary.

## Desired Experience

The checked-in instructions should produce this sequence:

1. clone the repository;
2. install the explicitly declared Docs Viewer runtime dependencies;
3. run one project-local command; and
4. open one reported local URL.

No private path, credential, untracked config file, adjacent application, or public-site server is required. The command reports the selected composition, scopes, enabled integrations, and any required value that is genuinely missing. An unavailable optional integration does not affect startup.

The clone-safe scope set must be deliberate. It may contain selected repository-owned documentation or a small example scope, but it must not be the incidental result of loading the complete dotlineform development registry. Every displayed scope, action, link adapter, report, and service has a resolvable owner in the selected composition.

## Composition Model

Clone-ready and dotlineform development use the same runtime code, schemas, builders, services, and browser modules.

```text
shared code + checked clone-safe composition
shared code + dotlineform integrated composition + machine-local values
```

These are selections within one configuration contract, not two copied applications or complete configuration trees that can drift independently.

- immutable defaults and schemas remain shared;
- the composition chooses scope descriptors and optional integrations;
- `.env.local` supplies only machine-specific values needed by the integrated composition;
- private scope registrations and data remain outside the clone-safe composition;
- scope-owned settings remain with their data; and
- capability output is derived from the components constructed at startup.

## Document Workspace Boundary

The scenario must not depend on canonical document data living beneath the Docs Viewer application directory. A composition supplies exact source, generated-output, media, and scope-owned configuration locations.

Repository documentation may live in an explicit content root or beside its owning project. Private or user workspaces remain external. Reproducible local output may use an application-local runtime area or a scope-owned output root. Public projections retain their public-site owner. `docs-viewer/` owns the application implementation rather than every workspace it can display.

The exact relocation of current repository scopes is not part of this concept. The required architectural change is that Docs Viewer stops enforcing `docs-viewer/scopes/<scope>` as the meaning of a repository scope and resolves only the scope descriptors selected by the active composition.

## Acceptance Boundary

The concept is realised when, in an environment without the dotlineform local configuration:

- one documented command starts Docs Viewer from a clean checkout;
- startup does not require `DOTLINEFORM_PROJECTS_BASE_DIR`, Studio, public preview, R2, packages, or Review;
- only clone-safe scopes and capabilities appear;
- absent integrations contribute no origins, routes, controls, loaders, or scope records;
- selected repository content and generated reads load successfully;
- the full dotlineform composition continues to use the same code with its explicit integrations and local values; and
- focused evidence proves composition selection and the first durable service/browser boundary without reproducing the complete application in tests.

## Boundaries

- No installer, bundled runtime, release archive, upgrade system, or general standalone product is introduced.
- No automatic discovery of arbitrary local folders or scopes is introduced.
- No private data or machine-specific paths are copied into the repository.
- No generic plug-in platform or universal composition language is required.
- No immediate bulk move of existing document workspaces is implied.
- No promise is made that the public site or Studio works unless the selected composition explicitly includes and configures them.

## Status

Proposed concept. It motivates a future bounded delivery beneath the parent architecture feature; it does not authorize implementation or document relocation.
