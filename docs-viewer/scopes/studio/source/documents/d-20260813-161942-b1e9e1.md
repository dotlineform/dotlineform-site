# Studio Full-Text Search Index Concept

This Roadmap concept is retained as the design and prototype record that led to SM-1. The shipped current-state contract now belongs to the durable [Docs Viewer Search Index](/docs/?scope=studio&doc=d-20260813-214350-4c7a21).

## Purpose

“Full text” means that words from the complete authored document can retrieve that document. It does not require the search payload to contain raw Markdown, rendered HTML, body paragraphs, link destinations, report configuration, or complete code blocks.

For the current client-side static architecture, the browser must still receive a generated representation of the searchable content. The preferred representation is a compact **inverted term index** rather than a second copy of every document body. [DSI-1 — Docs Viewer Search Index v2 Delivery](/docs/?scope=studio&doc=d-20260813-171341-8bfa80) establishes this as the single format and query path for every Docs Viewer scope before Studio adds full-text fields.

“Inverted” means the index maps **words to documents**, instead of documents to all their words.

Normal document representation:

```text
Document A → search, studio, ranking
Document B → studio, reports, blocks
```

Inverted index:

```text
search  → Document A
studio  → Document A, Document B
ranking → Document A
reports → Document B
blocks  → Document B
```

So searching for `studio ranking` is quick: retrieve both word lists and intersect them. Only Document A appears in both.

This lets us search every authored word without putting every document’s full body into the browser index. The browser receives a vocabulary plus compact document references—essentially the index at the back of a book.

## Proposed Shape

Keep one compact document table for identity, navigation, visible context, and heading ranking, then map each normalized body or code term to the document positions containing it:

```json
{
  "header": {
    "schema": "docs_viewer_search_index_v2",
    "scope": "studio",
    "count": 237
  },
  "docs": [
    {
      "id": "d-example",
      "title": "Example document",
      "href": "/docs/?scope=studio&doc=d-example",
      "parent_title": "Parent document",
      "last_updated": "2026-08-13 16:00:00",
      "headings": ["Known weak spots"]
    }
  ],
  "terms": {
    "compatibility": {"body": [4, 18, 93]},
    "docs_subscope": {"body": [27]},
    "runtime": {"title": [2], "body": [27, 81]}
  }
}
```

The integers are positions in `docs`. A term is written once and its posting lists are deterministic and deduplicated. The exact common schema remains a DSI-1.0 sanity-gate decision; the example fixes the intended ownership and data structure, not field names that implementation evidence may improve. SM-1 does not introduce a Studio-specific schema.

`doc_id` remains required record identity, navigation input, targeted-update identity, and deterministic tie-breaker, but it is not searchable. `last_updated` and parent title remain optional display metadata and are not searchable. Titles and headings remain readable strings because they are displayed or ranked separately; body prose and code are represented only by their term postings.

The `docs` array contains every document once, while `terms` points back to their array positions.

## Example

Given three documents:

```text
0: Search Mechanics
   Heading: Ranking
   Body: Studio search ranks titles first.

1: Report Blocks
   Heading: Backlinks
   Body: Studio reports can list linking documents.

2: Document Identity
   Heading: Stable IDs
   Body: Document IDs identify exact targets.
```

The proposed index could look like:

```json
{
  "docs": [
    {
      "id": "doc-search",
      "title": "Search Mechanics",
      "headings": ["Ranking"],
      "href": "/docs/?doc=doc-search"
    },
    {
      "id": "doc-reports",
      "title": "Report Blocks",
      "headings": ["Backlinks"],
      "href": "/docs/?doc=doc-reports"
    },
    {
      "id": "doc-identity",
      "title": "Document Identity",
      "headings": ["Stable IDs"],
      "href": "/docs/?doc=doc-identity"
    }
  ],
  "terms": {
    "backlinks": {
      "heading": [1]
    },
    "document": {
      "title": [2],
      "body": [1, 2]
    },
    "ranking": {
      "heading": [0]
    },
    "reports": {
      "title": [1],
      "body": [1]
    },
    "search": {
      "title": [0],
      "body": [0]
    },
    "studio": {
      "body": [0, 1]
    },
    "targets": {
      "body": [2]
    }
  }
}
```

The numbers are positions in `docs`:

- `0` means Search Mechanics.
- `1` means Report Blocks.
- `2` means Document Identity.

Searching for `studio reports` would:

1. Read `studio.body` → `[0, 1]`.
2. Read `reports.title/body` → `[1]`.
3. Intersect them → `[1]`.
4. Use `docs[1]` to display Report Blocks.

Keeping postings separated by `title`, `heading`, and `body` also supplies the ranking: a match in `title` can score more highly without storing the full source text.

## Build

Term recognition and normalization are defined separately in [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-163802-5ca41f) so every scope's index builder and the browser query path share one testable contract.

The Studio field-adoption path in the shared search builder should:

1. parse the current canonical Markdown with the shared Markdown rendering/parsing contract;
2. retain the authored title, retain parent title only for display context, and collect rendered headings separately without repeating the title heading;
3. extract readable prose, inline code, and fenced code while excluding front matter, generated markup, report-block declarations, link destinations, media paths, and scripts or styles;
4. apply the shared tokenizer to eligible title, heading, body, and code values;
5. deduplicate terms within each document and serialize document records, term keys, and posting lists deterministically; and
6. regenerate the complete Studio term map whenever the single Studio search index changes.

A separate incremental posting cache is not warranted for the current corpus. The search builder already reads the selected scope, and rebuilding one index from roughly 237 documents is simpler and less prone to stale removals than merging per-document postings.

## Query And Ranking

The browser normalizes the query into terms, resolves exact or prefix term keys, intersects their posting lists, and returns at most one row per document. Ranking remains:

1. title;
2. heading; and
3. body prose or authored code.

Title and heading strings can be checked directly for their ranking tier. Body and code use the inverted postings. Parent title remains visible result context but emits no postings, avoiding child results that match only through a broad hierarchy label. A query such as `known weak spots` finds documents containing both terms and receives heading rank when the stored heading confirms the match. A query such as `docs_subscope` resolves the preserved authored code term.

## Config

Studio opts in through the existing flat `search_fields` policy. Its fields become `title`, `heading`, `body`, and `code`; parent title, identity, and update metadata remain in the document table without emitting Studio postings. No separate full-text mode or scope-name branch is required.

## Initial Findings

A read-only prototype on 2026-08-13 used the current 237 Studio search entries and current rendered by-ID content. It removed script, style, and inert report-host content; separated headings and code; normalized visible text; omitted numeric-only terms; and serialized compact JSON. The figures are evidence for choosing a shape, not final payload budgets:

| representation | raw bytes | gzip bytes |
| --- | ---: | ---: |
| current metadata-only index | 193,025 | 20,074 |
| normalized per-document title/heading/body/code fields | 1,521,165 | 439,763 |
| basic field-aware inverted term index | 477,003 | 117,435 |

The current Studio Markdown source set is about 1.61 MB. Copying normalized document text into each search entry therefore approaches a second body corpus, while the prototype inverted index is about 477 KB raw and 117 KB compressed. The final schema may be smaller because body and code share one ranking tier and readable headings can remain in the document table rather than repeat field-specific postings.

SM-1.0 should repeat these measurements with the production extractor and final compact schema, record generation time, and inspect representative high-frequency terms rather than treating the prototype as an accepted performance result.

## Search Semantics And Limits

The first implementation is token-based full-text retrieval. A multiword query requires all normalized query terms but does not promise exact phrase positions inside arbitrary body prose. Exact body phrases, term frequency scoring, stemming, synonyms, typo tolerance, snippets, highlighting, and section deep links would require additional data or behavior and remain outside the first delivery.

The generated term dictionary exposes the vocabulary present in searchable documents even though it does not expose complete prose. The common v2 format is used by every Docs Viewer scope, but SM-1's heading/body/code field policy is local Studio-only. Enabling body text for another local, external-local, or public scope requires its own inclusion, privacy, payload, and publication decision.

[Analysis Full-Text Search Extension](/docs/?scope=studio&doc=d-20260813-165124-16b0ab) records the principal likely extension: reuse the same Docs Viewer search machinery for a body-text corpus while keeping public document membership, vocabulary exposure, payload, and publication policy explicit.
