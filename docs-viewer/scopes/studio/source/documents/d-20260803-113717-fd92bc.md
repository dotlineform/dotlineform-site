# IFS-1 — Docs Import Folder Source Selection Delivery

## Status And Purpose

Started as **IFS-1** on 2026-08-03 under [Docs Import Folder Source Selection](/docs/?scope=studio&doc=d-20260801-190502-6927fb). IFS-1.0 is complete. IFS-1.1 is implemented and verified, and the delivery is stopped at its review gate before IFS-1.2 frontend integration. The [Concept And Architecture](/docs/?scope=studio&doc=d-20260803-113716-8ef8e5) is the authority for component ownership, modal handoff, confinement, and source-selection behavior.

This delivery establishes an honest shared folder-navigation capability with Docs Viewer as its first consumer, then integrates it into ordinary Docs Import without changing classification, targeting, or apply semantics.

## Complete Delivery Outcome

Manage Import shows the current relative source with **Choose folder…** and **Use import staging** actions. Choosing opens a dedicated folder-picker modal backed by lazy, server-confined directory listing. Confirming one validated folder restores Import and refreshes its direct-child ordinary candidates; cancelling restores Import unchanged.

The shared frontend component contains only app-neutral folder navigation. A shared Studio Python capability contains only Projects-base confinement and child-directory listing. Docs Viewer explicitly exposes the shared frontend asset, and its Import adapter retains all staging, candidate, recognizer, destination, preview, and apply policy.

## Delivery Discipline

- A shared component may have one initial consumer when its responsibility and dependency direction are genuinely shared.
- Docs Viewer receives an explicit supported shared-asset boundary; there is no copied or accidental private import.
- Folder selection has a dedicated modal and deliberate handoff; the existing Import modal does not become a second application view.
- The Works Editor picker is not migrated merely to manufacture a second consumer.
- The delivery adds narrow folder navigation and confinement seams, not a generic filesystem framework.

## Current Seams And Expected Shape

IFS-1.0 re-traced these seams on 2026-08-03 before implementation:

- the existing shared frontend file picker and its Works Editor wrapper;
- Docs Viewer static asset routing and module boot boundaries;
- the Import modal, controller, candidate inventory, recognizer dispatch, marker paths, preview/apply requests, and local preference patterns;
- the existing collection-modal handoff and focus-restoration behavior; and
- shared Studio external-workspace path helpers and Docs Viewer server adapters.

The trace found one material expansion. Current ordinary Import uses the Data Sharing workspace root for both confinement and provider-safe source-path projection. An arbitrary Projects directory must separate those responsibilities so a non-staging preview cannot fall back to a physical path. The frozen estimate is therefore 900–1,230 production lines and 650–950 focused test lines. This is above the proposed 600–850 production and 450–700 test ranges, so IFS-1 stops at this checkpoint for explicit review. The expansion is confined to the existing Import path projection and modal handoff; it does not justify a generic filesystem framework.

### Frozen Directory Identity And Confinement

- The request and browser identity field is `source_directory`. Its canonical value is a POSIX path relative to `$DOTLINEFORM_PROJECTS_BASE_DIR`, with no leading or trailing slash. The Projects-base navigation root is the exact marker `.` and the default is `data-sharing/import-staging`.
- Blank values, absolute paths, backslashes, empty segments, parent segments, missing paths, non-directories, and unreadable directories are rejected. `.` is accepted only as the exact root marker.
- The configured Projects base is the trust anchor. Every requested relative segment is checked without following a symlink; a symlink in any requested segment is rejected before final containment is confirmed. A direct-child symlink, unreadable directory, or non-directory is omitted from listing rather than exposed.
- The root is navigable but has `current_selectable: false`. Every accepted nested real directory has `current_selectable: true`. The shared browser submits only a server-returned selectable current marker.
- Validation failure is an HTTP error, not a server-side silent redirect. The browser owns remembered-source recovery: it clears the invalid preference, validates `data-sharing/import-staging`, and retries candidate listing without changing destination.

### Frozen Docs Import HTTP Contract

`GET /docs/import-source-directories?source_directory=<marker>` lists one validated directory lazily:

```json
{
  "ok": true,
  "current_directory": "projects/architecture",
  "current_selectable": true,
  "parent_directory": "projects",
  "directories": [
    {
      "label": "references",
      "source_directory": "projects/architecture/references"
    }
  ]
}
```

At `source_directory=.`, `parent_directory` is `null` and `current_selectable` is false. Directory rows contain only a display label and canonical relative marker.

`GET /docs/import-source-files?source_directory=<marker>` keeps the existing body-free `candidates` and `files` projections and adds the canonical accepted `source_directory`. The field is required by the current client. Candidate discovery is one level deep and standalone media remains ignored.

`POST /docs/import-source` keeps the existing exact destination fields and requires:

```json
{
  "scope": "studio",
  "source_directory": "projects/architecture",
  "staged_filename": "notes.md"
}
```

`sub_scope`, prompt metadata, preview, collision, and collection fields retain their current meanings. The server resolves the directory and then the direct-child filename on every request. A missing, moved, symlinked, nested, traversal, changed-format, or otherwise mismatched pair fails before preview or apply.

Registered collection and edited-review recognizers inspect the untouched direct child before generic suffix or Markdown-package handling. Inside `data-sharing/import-staging`, trusted candidates retain the existing integrated workflow. Outside staging, a recognized trusted package or edited review source is returned as a blocked candidate with the `trusted_source_requires_import_staging` diagnostic, and direct POST receives the same staging-only error. It never falls through as an ordinary document. A normal directory containing exactly one Markdown document remains an ordinary Markdown-package candidate, and that candidate directory remains the media-resolution root.

### Frozen Shared Folder Picker And Asset Boundary

The shared export is:

```text
createFolderPicker(root, {
  initialDirectory,
  loadDirectory,
  onSubmit,
})
```

`loadDirectory({directory})` supplies the frozen directory-list response. `onSubmit({directory})` receives only the current server-returned selectable marker. The returned controller exposes `ready`, `focusPreferred()`, `getDirectory()`, `submit()`, and `destroy()`. The component owns breadcrumb and parent/direct-child navigation, loading, empty/error presentation, list keyboard behavior, and submit validation. It contains no route, storage key, Projects-base, staging, candidate, destination, or Docs Import knowledge.

The module and component-owned styles are `shared/frontend/js/folder-picker.js` and `shared/frontend/css/folder-picker.css`, using the `.sharedFolderPicker` namespace. Docs Viewer exposes only these exact supported URLs:

```text
/docs-viewer/runtime/js/shared-frontend/folder-picker.js
/docs-viewer/static/css/shared-folder-picker.css
```

Import source controls remain under `.docsViewerImport` in `docs-viewer-import.css`. The existing shared file-picker module, configuration, styles, and Works wrapper are unchanged.

### Frozen Modal, Preference, And Fallback Contract

- The storage key is `dotlineform-docs-import-source-directory`. It is global to local Docs Import rather than scope-keyed because source and destination are independent. The value is one canonical server-returned nested marker; absent means import staging. Storage read/write/remove failures are treated as an unavailable preference, not an Import failure.
- Opening Import reads the preference, revalidates it through the directory endpoint, and only then lists candidates for the accepted marker. Invalid state is removed before staging is validated and listed. If staging itself is unavailable, the existing Import error/status owner reports the failure.
- **Choose folder…** suspends Import without restoring focus, opens `docsViewerImportFolderModal`, and initializes the shared picker at the accepted current source. Navigation failure stays in that modal. Cancel closes the folder modal, restores Import unchanged, and focuses the Choose launcher.
- Confirm submits one selectable server-returned marker, closes the folder modal without independent destination state, restores Import, refreshes candidates for the exact marker, and focuses the Choose launcher. The accepted marker becomes visible even if candidate refresh later fails; the existing Import status/retry owner reports that failure.
- The preference is written only after server acceptance. **Use import staging** validates and refreshes `data-sharing/import-staging`, then removes the preference and returns focus to its own launcher. Neither action changes the frozen parent or sub-scope destination.
- Closing the restored Import modal still returns focus to the original Manage Import launcher. The folder modal cannot preview, apply, select files, retain a destination, or create a second Import identity.
