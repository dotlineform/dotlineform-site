# SSP-4.0 — Collection-Aware Copy Sanity Note

## Outcome

SSP-4 fits the shipped Docs Viewer owners as a bounded generalisation of the existing independent Copy workflow. SSC-1 already supplies one registered sub-scope customisation contract with a typed transfer aspect, and SSP-1 supplies the shared optional Folder, Work, and Series subject fields plus collection-independent read projection. Exact managed collection resolution, flat sub-scope roots, `doc`/`subdoc` navigation, child-only rebuilds, checked sub-scope selection, media ownership, and parent publication already have separate owners that SSP-4 can reuse.

The checkpoint is complete at its review gate. SSP-4.1 may create and configure `analysis/works`, then extend Copy planning and its receipt after explicit implementation approval. No runtime, configuration, collection, route, or browser change is authorized by this note.

## Confirmed Fit And Owners

- Exact document-target services already resolve configured `{scope}` and `{scope, sub_scope}` collections without using the current route or displayed document as identity. The document-location owner already composes parent `doc` and child `subdoc` URLs from a validated collection URL.
- The existing transfer planner owns checked IDs, parent hierarchy expansion, fresh Copy identities, target-root allocation, link/media planning, blockers, warnings, and one stale-safe receipt. Its current source, target, capability, route, and result shapes are top-level-scope-only; SSP-4 extends those Copy shapes to exact collections while Move retains its current scope and subtree contract.
- The Copy apply owner already removes source viewability, applies the target scope default, rewrites copied-set links, transfers media before canonical source writes, creates files without overwrite, performs one coordinated rebuild, and returns exact observed failure evidence. SSP-4 selects the existing parent or child write/rebuild transaction from the frozen target collection and reuses the document-location owner for results.
- Sub-scope lifecycle owns the flat source/output roots, report host, collection configuration, and optional public projection. The existing child rebuild updates only that sub-scope and no search index. SSP-4.1 can therefore create `analysis/works` through the established lifecycle/configuration boundary and register its read-only subject projection without inventing collection storage or publication behavior.
- The unified customisation registry already reserves one code-owned transfer declaration per registered definition, but no current definition advertises one. SSP-4.1 activates the smallest accepted declaration on this seam. It does not add loose config fields, infer compatibility from matching names, or give the Analysis target the Projects `authoring_subject` assignment group.
- Main Index Copy already consumes checked selection through the shared action definition and transfer workflow. The default sub-scope contribution owns a separate exact checked selection and Actions menu. SSP-4.3 connects that owner to the same Copy workflow beside Prepare Package; it does not use the report host, active document, or another selection owner as a fallback.

## Blast Radius And Deliverables

The implementation blast radius covers exact collection capability projection; flat child inventory and hierarchy rejection; Copy preview, receipt, restoration, apply, activity, and result identity; target-owned structural defaults; registered non-subject metadata decisions; parent-owned media and build-source planning; parent/child URL rewriting and coordinated rebuild selection; the main and sub-scope action surfaces; focused contract evidence; and durable endpoint and sub-scope architecture updates at closeout.

The complete delivery must preserve current parent-to-parent Copy and all Move behavior. It must create flat, initially non-viewable documents in `analysis/works`; retain raw `folder_path`, `work_id`, or `series_id` source values unchanged when present; leave no-subject documents valid; omit unsupported customisation-owned fields visibly; block a value rejected by an advertised target contract; keep source bytes and media unchanged; and leave editorial viewability and the existing Analysis Publish workflow as later explicit actions.

## Risks And Required Evidence

- Collection identity must remain explicit in browser requests, service inputs, receipts, activity, and results. The current route scope, report host, selected row, filename, and parent scope are never substitute source or target identity.
- A child of a public parent may accept non-viewable canonical source without making the public parent a general Copy target. Capability projection must distinguish collection write roots and operation policy rather than weakening the current public-scope guard.
- Child document roots and rebuilds differ from parent-owned media and publication roots. Planning and revalidation must freeze both responsibilities so apply cannot write one collection and rebuild or navigate another.
- Current Copy preserves every non-structural front-matter field. SSP-4 must replace that implicit behavior for customisation-owned fields with explicit retained, omitted, rejected, or blocked decisions while leaving shared subject bytes non-gating and uninterpreted.
- Child sources and targets are flat. Descendant inclusion and internal parent/child selections must be rejected where the contract forbids them, never silently flattened. Parent-source hierarchy behavior must remain unchanged.
- The browser and server move together to one current receipt schema. Stale source, target, configuration, metadata, media, or build-source evidence must fail before mutation; no alias, dual reader, overwrite, retry, or partial-success claim is added.

Focused implementation evidence must prove the four parent/child source-target shapes, same-parent different-child Copy, parent hierarchy regression, flat-child rejection, exact subject retention, non-subject metadata decisions, link/media ownership, target-default viewability, stale receipt containment, correct `doc`/`subdoc` results, child-only rebuild behavior, UI exact-selection ownership, and public isolation. Each stage retains its independent code/diff review before the next approval gate.

## Collection And Publication Boundary

SSP-4 ends after create-only independent Copy is available between eligible exact collections. It does not make a copied document viewable, publish it, persist lineage, offer Replace, compare or merge content, synchronize later edits, interpret subject meaning, expand Move, or alter the parent Analysis Publish transaction. SSP-7 remains the later owner of exact A-to-B lineage, New-or-Replace choice, and publication-state reconciliation.

## Stop Condition

Stop before or during SSP-4.1 if the result requires nested collections, arbitrary source directories, a second transfer workflow, compatibility aliases, a parallel metadata registry, field-name compatibility inference, literal Projects/Analysis availability branches, Move expansion, publication coupling, overwrite or lineage persistence, changed media/publication semantics, or fallback from any route, title, filename, row, report host, or active document. Those outcomes require a separately reviewed delivery boundary.
