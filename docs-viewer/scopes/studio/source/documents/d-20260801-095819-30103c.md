# Projects

## Purpose

Give current, historical, and prospective project folders a flexible notes
layer, and replace the Studio Project State pipeline with Docs Viewer
reconciliation while keeping Studio Works stable catalogue records.

The feature keeps three deliberately different worlds visible:

| world | role |
| --- | --- |
| Studio | strict database owner of Works, Series, publishing workflow, and recorded source-path history |
| Docs Viewer | semi-structured owner of Project notes and optional convenience links, which may drift |
| folders | fluid human working world with no canonical identity or enforced lifecycle |

Project State observes disagreement among them. It does not make one system
manage the other two.

PRJ-1 and PRJ-2 are entirely Docs Viewer-owned and do not change Studio.
PRJ-3 is the narrow integration exception: Project State reads the existing
Work fields through a Studio-read-only post-commit observer, but it never adds
`folder_path` to Studio, rewrites Work data, or participates in Studio's
catalogue workflow.

## Delivery Order

| order | delivery | complete outcome |
| --- | --- | --- |
| 1 | PRJ-1 — Docs Viewer Local Folder Links | A pasted Finder or terminal path becomes a marked base-relative link: clickable through confined local Manage and inert in public output. |
| 2 | PRJ-2 — Projects Sub-Scope Customisation And Seed | Project documents own optional `folder_path` metadata in their local Manage manifest, and the current folder inventory can seed explicitly confirmed notes. |
| 3 | PRJ-3 — Docs Viewer Project State | One Docs Viewer report reconciles current folders, Project documents, and historical Works while publishing the Project resolver lookup and retiring the Studio implementation. |
| 4 | PRJ-4 — Resolver Tokens | Any permitted managed document can expand one exact folder or Work subject into its precomputed one-hop Project relationships. |

The deliveries are sequential. PRJ-2 consumes PRJ-1's path contract. PRJ-3
consumes PRJ-2's structured Manage-manifest projection. PRJ-4 begins only after
the Project State lookup, refresh, failure, and access contracts work
independently through the report.

## Feature Boundary

In scope:

- ordinary body links for local folder paths;
- one optional Project-document `folder_path` convenience field;
- no Studio dependency for local links or Project-document metadata;
- `$DOTLINEFORM_PROJECTS_BASE_DIR` as the containment boundary for local links,
  while `projects/` remains the initial Project discovery and seeding area;
- a registered Manage-only Projects sub-scope customisation;
- explicit preview/apply seeding from a confined folder inventory;
- three-way, read-only Docs Viewer reconciliation;
- targeted post-commit updates plus explicit full refresh;
- retirement of the existing Studio Project State route and static report; and
- bounded one-hop Resolver Tokens backed by Project State data.

Not in scope:

- a canonical folder registry or folder/document synchronization;
- automatic rename, move, merge, repair, or deletion;
- use of `folder_path` by Studio's media or publishing workflows;
- adding `folder_path` to Works or mapping it onto `project_folder`;
- continuation of the old primary-image audit;
- recursive relationship chaining or a global graph database; or
- public activation of local targets or public projection of Project
  relationship data.
