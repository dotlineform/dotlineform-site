# Projects

## Purpose

Give current, historical, and prospective project folders a flexible notes layer while keeping Studio Works and Series as stable catalogue records. A dedicated Project State feature derives folder-centred relationships for a persistent Docs Viewer report and downstream Resolver Tokens. The useful image-level report currently called Project State is preserved separately as Project Media Audit.

The feature keeps three deliberately different worlds visible:

| world | role |
| --- | --- |
| Studio | strict database owner of Works, Series, publishing workflow, and recorded source-path history |
| Docs Viewer | semi-structured owner of Project notes, optional convenience links, saved Project State, and local audit documents |
| folders | fluid human working world with no canonical identity or enforced lifecycle |

Project State observes disagreement among them. It does not make one system manage the other two.

PRJ-1 and PRJ-2 are entirely Docs Viewer-owned and do not change Studio. PRJ-3 is the narrow integration exception: Project State reads existing Work folder and Series evidence through a Studio-read-only post-commit observer, but it never adds `folder_path` to Studio, rewrites Work data, or participates in the canonical catalogue transaction.

## Delivery Order

| order | delivery | complete outcome |
| --- | --- | --- |
| 1 | PRJ-1 — Docs Viewer Local Folder Links | A pasted Finder or terminal path becomes a marked base-relative link: clickable through confined local Manage and inert in public output. |
| 2 | PRJ-2 — Projects Customisation And Apple Notes Migration | Project documents own optional `folder_path` metadata in their local Manage manifest, and a checked-in one-off command imports the reviewed Apple Notes corpus without inventing folder matches. |
| 3 | PRJ-3 — Docs Viewer Project State | One persistent Docs Viewer Markdown document reports Doc/Folder/Series rows and publishes the versioned folder lookup from the same relationship generation. |
| 3a | PMA-1 — Project Media Audit | The current image audit is preserved under its accurate name in Docs Viewer, then the old Studio Project State route and static Markdown output are retired. |
| 4 | PRJ-4 — Resolver Tokens | Any permitted managed document can expand one exact folder subject into its precomputed Series and Project-document relationships. |

PRJ-2 supplies PRJ-3's Project-document evidence. PRJ-4 begins only after PRJ-3's lookup, generation, freshness, failure, and access contracts work independently. PMA-1 should follow PRJ-3 so it can reuse the saved generated-document seam, but it is not a semantic dependency or gate for PRJ-4.

## Project State Relationship

```text
Project documents[] <- folder_path -> Series[]
```

One normalized folder is one row. Several Project documents may share it, and the Works historically sourced from it may contribute several Series. Works are derivation evidence, not Project State result items. Series resolver results carry semantic catalogue identity rather than copied titles or URLs.

## Feature Boundary

In scope:

- ordinary body links for local folder paths;
- one optional Project-document `folder_path` convenience field;
- no Studio dependency for local links or Project-document metadata;
- `$DOTLINEFORM_PROJECTS_BASE_DIR` as the local-link containment boundary while `projects/` remains the initial Project discovery area;
- a registered Manage-only Projects sub-scope customisation;
- a write-free plan and exact create-only apply for the dated Apple Notes export;
- one folder-centred, read-only Project State generation and persistent Docs Viewer report;
- targeted post-commit relationship follow-through plus explicit full refresh;
- a separate read-only Project Media Audit migration and retirement of the misleading Studio route/output; and
- bounded one-hop folder Resolver Tokens backed by Project State `series[]` and `documents[]`.

Not in scope:

- a canonical folder registry or folder/document synchronization;
- automatic rename, move, merge, repair, import, or deletion from a report finding;
- use of `folder_path` by Studio media or publishing workflows;
- adding `folder_path` to Works or mapping it onto `project_folder`;
- Work subjects or Work result groups in the initial Project resolver;
- recursive relationship chaining or a global graph database; or
- public activation of local targets or public projection of Project relationship/audit data.
