# Projects

## Purpose

Give current, historical, and prospective project folders an equally flexible notes layer, and replace the Studio Project State pipeline with a Docs Viewer reconciliation report while keeping Studio Works stable catalogue records.

## Problem

`$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` contains the real source images and files behind the catalogue. Its roughly 200 direct folders are relatively stable working groupings, but they are not permanent identities. As projects evolve, folders can be renamed, moved, split, or consolidated.

A Work's `project_folder`, optional `project_subfolder`, and `project_filename` record where its source was when the Work was created or its file was uploaded. That path is a useful historical snapshot. It is not a live pointer that should be silently rewritten whenever the working folder structure changes.

The folder tree, Project documents, and catalogue snapshots can all drift independently and disagree legitimately:

- Works can refer to folders or files that no longer exist at the recorded path;
- a Project document can be created before its intended folder exists, as a note about what could happen;
- a Project document can remain after its folder has moved, been renamed, or ceased to exist;
- a physical folder can exist without a Project document or any catalogue representation;
- a renamed or moved folder can remain represented by older Work snapshots;
- several older folders can become one current project, or one project can split;
- a current folder can relate to no Series, one Series, or several Series; and
- two documents can accidentally declare the same folder URL.

The problem is not to force these sources back into one shape. It is to make their current, prospective, and historical relationships visible and explicitly manageable.

## Mental Model

| world | character | ownership |
| --- | --- | --- |
| Studio | database: structured, managed, and stable | strict canonical ownership of Works and their recorded source history |
| Docs Viewer | semi-structured notes and metadata | owns its documents and projections, while allowing them to drift from external reality |
| folders | human working world: fluid and potentially chaotic | no canonical identity or lifecycle contract |

The Project State report observes the disagreement between these worlds; it does not make any one of them manage the other two.

- **Project documents represent folders.** Each document is a flexible notes record for one current, historical, or prospective folder and may store a literal local convenience link in source front matter, for example `folder_url: "file:///path/to/projects/nerve"`.
- **The URL is not identity or authority.** It helps a person navigate and helps the report compare evidence, but it does not decide which documents exist, where Studio uploads media, or how any lifecycle proceeds.
- **Existence is not a precondition.** A document may precede its folder, track a folder that exists now, or remain as evidence after that URL stops resolving.
- **Relationships are explicit.** A stored URL declares the intended folder association; it is never inferred from a document title, folder label, selected Work, or Series name.

The document, its stored URL, the physical folder, and catalogue path snapshots are separate records of reality. Like Analysis tag documents, Project documents may intentionally exist before or without the external thing they describe. Folder URLs should remain relatively stable so the notes stay understandable, but that is an authoring convention rather than a system-enforced canonical contract. Seeding documents from the current folder inventory is therefore a useful starting point, not a synchronization contract.

## Desired Capability

The `dotlineform/projects` Docs Viewer sub-scope holds Project documents and ordinary document-management workflows. A registered Manage-only Projects customisation adds folder-specific metadata and controls to that sub-scope report without changing the shared default.

A separate local Docs Viewer **Project State** report replaces the current Studio route and generated Markdown report. It reconciles three independent inputs:

1. folders that currently exist below `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`, from a confined folder-only inventory;
2. Project document rows and their customisation-owned `folder_url` values from the local sub-scope management manifest; and
3. folders historically recorded by canonical Studio Works, plus the Series reached through those Works.

The current-folder inventory is live evidence, not a canonical registry. It scans folder identity only and does not continue Studio's primary-image audit. The reconciliation report and document-seeding preview may consume the same confined inventory, but neither owns or synchronizes the folders.

The three inputs have deliberately different meanings: filesystem folders are current physical evidence, manifest URLs are user-maintained convenience links, and Work folder fields are historical catalogue facts. The report compares them without promoting the manifest URL into a canonical identifier or operational instruction.

The report should make these states reviewable:

- current folders with no Project document or historical Work reference;
- Project documents whose stored folder exists now;
- Project documents whose stored folder does not exist, without guessing whether the document is prospective, stale, or historical;
- Project documents with missing, malformed, out-of-root, or duplicate folder URLs;
- Work folder snapshots matching no current folder or Project document, one of them, or both;
- Project documents with no matching Work snapshot;
- incomplete Work folder snapshots;
- three-way agreement among a current folder, one Project document, and historical Works;
- unresolved moved, renamed, split, or consolidated history; and
- Project documents related through Works to more than one Series.

Rows link to the exact Project document, relevant Works and Series, and the literal folder target where one is declared. A validated local action opens an existing target in macOS Finder. Because a browser may not activate a `file:` URL from an HTTP page, Docs Viewer may provide that action through its local management service; the service must reread the URL from the exact document target and confine it below the allowed projects root. Missing, prospective, historical, and unmatched paths remain visible evidence and never fall back to another folder.

Bulk document seeding and later creation use a preview/apply management workflow. Creating a document does not require the folder to exist. The report remains an inspection surface rather than owning source writes or treating a mismatch as an instruction to repair it.

## Path Entry and Editing

The ordinary input is likely to be a pathname copied or dragged from Finder or a terminal, not a hand-authored URL. For example:

```text
/Users/dlf/Library/Mobile\ Documents/com\~apple\~CloudDocs/dotlineform/projects/3\ symbols
```

Docs Viewer should expose the same paste-and-normalize behavior in two explicit editing contexts:

- **Body content:** paste or insert the path as an ordinary clickable local link. It remains document prose and does not declare the document's folder, enter the sub-scope manifest, or affect reconciliation.
- **Folder Link metadata:** paste the path into the dedicated field. Saving writes normalized `folder_url` front matter and projects that structured value into the local Projects management manifest, where the reconciliation report can consume it.

Both contexts should accept:

- a local `file:` URL;
- an absolute POSIX pathname containing ordinary spaces; or
- an absolute POSIX pathname whose characters have been backslash-escaped for shell display.

The pasted value is data, never a shell expression. Docs Viewer performs constrained path decoding without shell evaluation, variable expansion, command substitution, or implicit home-directory expansion. It then previews the decoded path, confirms that it is below the configured projects root, and reports whether the folder currently exists. A body paste is inserted as a clickable link. A Folder Link paste stores one normalized URL form such as:

```yaml
folder_url: "file:///Users/dlf/Library/Mobile%20Documents/com~apple~CloudDocs/dotlineform/projects/3%20symbols"
```

An in-root Folder Link may be saved when it does not yet exist; the document is then prospective and the report shows that state. Relative paths, non-local authorities, non-`file:` schemes, and targets outside the configured root are rejected.

The front-matter field is the document's structured convenience link, not its identity or validity boundary. The registered Projects report customisation projects it into the exact document row's `customisation` namespace in local `manage-manifest.json`, for example:

```json
{
  "doc_id": "d-example",
  "title": "3 symbols",
  "customisation": {
    "folder_url": "file:///Users/dlf/Library/Mobile%20Documents/com~apple~CloudDocs/dotlineform/projects/3%20symbols"
  }
}
```

The shared default row schema, ordinary manifest, and any public projection exclude it. The Projects sub-scope customisation derives its visible link and exact-document Open in Finder action from that namespaced field. The broader reconciliation report can consume the same custom-owned projection alongside filesystem and Studio evidence. Body links can still use the validated local opener, but they remain ordinary links and are never silently promoted into front matter.

This is deliberately not a Semantic Tokens capability. Project documents are the notes records and their local management manifest is the reportable document inventory; `folder_url` is only optional convenience metadata on those records. Ordinary body links need no semantic identity, and the front-matter link needs no separate Project registry or target lookup.

## Ownership

| concern | authority |
| --- | --- |
| current-folder inventory and path existence | confined Docs Viewer scan below `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` |
| Work source-path snapshot | canonical Studio Work record |
| Work-to-Series membership | canonical Studio catalogue |
| Project notes and document identity | Project document source and membership in the `dotlineform/projects` Docs Viewer sub-scope |
| literal `folder_url` convenience link | optional Project document front matter |
| pasted-path parsing, normalization, and validation | exact-target Docs Viewer document creation and metadata editing |
| `folder_url` manifest projection and document-row controls | registered Manage-only Projects sub-scope report customisation |
| Project State reconciliation presentation | dedicated local Docs Viewer report and services |

Studio may provide read-only catalogue evidence to the report. It does not own or resolve `folder_url`. Docs Viewer must not copy or become the mutation authority for Works or Series.

## Invariants

- Folder changes never automatically rewrite Work records.
- A Project document may store one literal local folder URL; neither the field nor its target must exist when the document is created.
- A folder may exist without a Project document, a Project document may exist without a folder, and a Work snapshot may exist without either.
- Work, folder, document, or Series lifecycle never automatically creates, renames, merges, repairs, or deletes any of the others.
- A missing recorded path is a reconciliation state, not proof that a Work or document is invalid or permission to repair it.
- Moved, renamed, split, and consolidated relationships require explicit user decisions.
- One folder can relate to many Works and Series. One document per folder is the useful authoring convention, but missing and duplicate URLs remain reportable drift rather than enforced cardinality.
- Projects customisation and reconciliation actions use the URL stored on the exact Project document and projected in its local management-manifest `customisation` row. They never synthesize it from a title or obtain it through a Studio-owned lookup or fallback.
- A body link has no reconciliation meaning, even when it points to the same folder as `folder_url`.
- No Project semantic-token family or separate canonical folder registry duplicates the Project document manifest.
- The default `docs_subscope` manifest and report contracts remain unchanged and folder-unaware.
- The Projects customisation is additive to document membership; it does not make the sub-scope report invent rows for folders that have no documents.
- Sub-scope membership comes from the documents themselves. A missing, changed, duplicate, or non-resolving `folder_url` never creates, hides, invalidates, renames, or deletes a document.
- Studio media selection and upload destinations never read `folder_url`; Studio continues to own its publishing workflow and recorded Work path fields.
- The Docs Viewer Project State report is read-only and never repairs documents, folders, Works, or Series.
- Project State has one report owner. The retired Studio route and Markdown generator do not remain as a second implementation or compatibility surface.
- The replacement report does not write `var/studio/reports/project-state.md` or another static report snapshot.
- The report's filesystem input enumerates folders, not primary images, and remains observation rather than a continuously synchronized source of Project identity.
- Reconciliation and seeding reuse the same current-folder inventory contract; the report is read-only and the seeding workflow remains explicit preview/apply.
- Pasted path text is parsed as inert data and never evaluated by a shell.
- Successful normalization writes only the exact Project document being created or edited and shows the normalized URL before commit.
- `folder_url` is intentionally local source data. It may appear in local Docs Viewer management data but must not enter a public projection; activation remains confined below the configured projects root.
- Changing a document URL is an explicit notes-side edit and never moves a folder or rewrites catalogue data.
- The feature remains local-only unless a separate public-safe projection is deliberately designed.
- Findings are review prompts, not permission to clean up files or catalogue data.

## Existing Baseline

[Project State](/docs/?scope=studio&doc=d-20260427-223830-ad1ab0) describes the current implementation. `studio/services/catalogue/project_state_report.py` scans project folders and primary images, compares them with Work `project_folder`, `project_subfolder`, and `project_filename` values, and writes `var/studio/reports/project-state.md`. `/studio/project-state/` provides the Studio UI for running that generator and opening its Markdown output through catalogue API endpoints.

The Projects delivery retires that machinery rather than narrowing or sharing it: the Studio route, frontend, report/open endpoints, activity contract, Markdown writer/opener, generated report, and focused route/report tests are removed or rerouted to the Docs Viewer owner. Folder inventory survives only as one input to the new three-way Docs Viewer report and seeding preview. The image-level findings from the old scan do not survive as an implicit residual Studio report; any future image audit needs its own explicitly justified owner and contract. `IMAGE_EXTENSIONS` is also imported by the catalogue detail-section service today, so that reusable policy must move to an appropriate neutral owner before the old report module is deleted.

[Docs Viewer Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) owns the local report boundary. [Sub-Scope Report Customisation Architecture](/docs/?scope=studio&doc=d-20260731-155053-3929e2) owns additive controls and validated collection or detail actions inside the existing Projects document report.

The current generic sub-scope manifests do not project arbitrary document front matter, and `dotlineform/projects` does not yet select a registered customisation. Projects therefore needs a narrow Manage-only report customisation whose controlled projector reads `folder_url` and emits it as namespaced row data; this is planned behavior, not an existing contract. That customisation is sufficient for document-level folder links and supplies the Project-document input to reconciliation without changing the default report or introducing another registry.
