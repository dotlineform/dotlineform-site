# Analysis Full-Text Search Extension

## Purpose

The inverted index, tokenizer, and posting-list query path are common Docs Viewer infrastructure established by [DSI-1 — Docs Viewer Search Index v2 Delivery](/docs/?scope=studio&doc=d-20260813-171341-8bfa80). Analysis is the main plausible full-text extension because it is another document corpus with authored body text. The extension question is therefore about public projection, corpus inclusion, vocabulary exposure, ranking fields, and payload cost rather than another index structure or search algorithm.

DSI-1 migrated Analysis to the common v2 structure with metadata retrieval only, and SM-1 established body-text extraction in Studio. Analysis is intended to adopt the same full-text field, tokenizer, and relevance policy once it contains enough articles for representative public-corpus and payload evidence. The later delivery decides timing and proves the boundary; it does not revisit whether Analysis receives a custom search system.

## Reusable Core And Scope Policy

| concern | Studio adoption | Analysis extension |
| --- | --- | --- |
| audience | local and private | public |
| index structure | shared Docs Viewer v2 | the same shared Docs Viewer v2 |
| indexed corpus | current canonical Studio parent documents | eligible Analysis parent documents plus eligible documents from visibly hosted sub-scopes |
| vocabulary exposure | acceptable within the local tool | must not reveal terms from unpublished or excluded content |
| payload | local tooling can tolerate a larger index | public download size, caching, and mobile performance require an explicit budget |
| output | Studio search projection | tracked public `site/assets/data/search/analysis/index.json` projection |
| full-text adoption | complete through SM-1 | planned measured rollout when the Analysis corpus is ready |

DSI-1 supplies the shared tokenizer, deterministic inverted postings, and identical query normalization. SM-1 adds reusable extraction of eligible authored headings, prose, and code plus their field-aware ranking. [DSI-2 — Scope-Level Sub-Scope Search Delivery](/docs/?scope=studio&doc=d-20260813-225547-cd82d8) defines the required combined parent/sub-scope corpus, exact child navigation, collection context, and rebuild behavior. [Docs Viewer Search Relevance](/docs/?scope=studio&doc=d-20260813-223337-e6c261) defines how names, specialist terms, and combined-corpus frequency should be handled without an Analysis vocabulary registry. Analysis adoption should reuse these seams without adding another payload shape, tokenizer, scorer, browser path, or independent child index.

Scope policy must continue to own document membership, searchable fields, viewer URLs, output location, public/private status, and acceptable payload. Common v2 migration must not turn full-text fields on automatically.

## Public Projection Boundary

Analysis is configured as a public Docs Viewer scope, served at `/analysis/`, with its search index projected to `site/assets/data/search/analysis/index.json`. DSI-1 changes this public artifact to the common v2 schema while retaining metadata-only retrieval. A later full-text delivery changes the fields and vocabulary within that already-common structure.

The Analysis full-text index must use exactly the parent and child document set permitted by the authoritative public projections. Include a registered sub-scope only through one eligible public `docs_subscope` report host, and include only child documents present in its accepted public manifest and by-ID projection. It must not independently infer eligibility or include terms from local-only, non-publishable, Manage-only, hidden, orphaned, unplaced, unresolved, or otherwise excluded documents. The public search builder may share source parsing with Studio, but its membership decision must reuse the public projection decision rather than create a parallel filter.

Sub-scope results retain exact `{scope, sub_scope, doc_id}` identity and explicit report-host placement. The active public or Manage route constructs the appropriate URL. Beneath the title, display update date plus the configured public collection/report title, such as `2026-07-27 • Concepts`; collection context remains non-searchable metadata.

An inverted index does not reproduce complete prose, but its term dictionary exposes the vocabulary of the indexed corpus in one downloadable artifact. The eligible-content extractor must therefore retain the same exclusions for front matter, generated markup, report declarations, link destinations, media paths, scripts, styles, and other non-visible configuration. This is a publication boundary, not just an optimization.

## Payload Gate

Studio’s prototype figures do not establish an Analysis budget because corpus size, vocabulary, document length, cache behaviour, and visitor network conditions differ. Before an Analysis delivery is approved, a read-only prototype should record:

- eligible public parent and per-sub-scope document counts;
- current metadata-index raw file size and actual transferred size under the target public host;
- proposed combined full-text-index raw file size and actual transferred size under the target public host; deterministic compression figures are supplementary unless that host serves compressed responses;
- vocabulary and posting counts;
- representative high-frequency terms;
- browser parse and representative query time; and
- confirmation that excluded documents contribute no identities or terms.

One static index may remain sufficient. Splitting, lazy loading, or other public delivery changes should be considered only if the measured public payload or browser cost warrants them.

## Catalogue Boundary

[Catalogue Search](/docs/?scope=studio&doc=d-20260602-160839-4ebe27) remains a separate domain-owned search system. Works and Series are structured known-item and metadata records rather than a corpus of authored document bodies, so the main reason for an inverted full-text index is absent.

The Works Catalogue may continue to improve its own field selection, normalization, and ranking without adopting the Docs Viewer body-text index or creating a cross-domain shared search application. Any future genuinely long-form Catalogue field would be assessed within Catalogue Search rather than making Catalogue an automatic adopter of this extension.

## Adoption Sequence

1. Complete DSI-1 and confirm the metadata-only Analysis v2 public projection.
2. Complete SM-1 and record the production Studio extractor, field policy, payload, and query evidence.
3. Complete DSI-2 so scope-level Search can include eligible documents from visibly hosted sub-scopes with exact active-route navigation.
4. Create a bounded Analysis delivery that changes its v2 field policy, updates the public projection, and updates durable Docs Viewer Search documentation.

This concept does not authorize public publication changes, a global cross-scope search UI, or a Catalogue Search migration.
