# Scope Media Management

## Purpose

Give Docs Viewer authors one truthful read-only view of how a scope's documents, published media, and recorded source files relate. The useful questions are:

- which media a document references (i.e. all the media in one document),
- which documents reference a specific media item,
- which references have no published object,
- which published items have no recorded or currently available source.

## Feature Documents

- [Concept](/docs/?scope=studio&doc=d-20260720-100017-e094d8) — the joined inventory model, document/media views, report-host direction, and deliberately small first UI.
- [Scope Media Report Delivery](/docs/?scope=studio&doc=d-20260720-100017-7e52de) — proposed read-only report outcome following the first [Media Sources](/docs/?scope=studio&doc=d-20260812-102047-a3c9e7) delivery.

## Boundary

- Scope configuration remains the ownership and location authority.
- The existing provider-independent media inventory, document references, and the small Media Sources evidence table are the starting points.
- The first useful surface is local and read-only.
- Unreferenced is an inspection state, not permission to delete.
- No source recorded is an ordinary truthful state, not an import failure or a demand for inferred provenance.
- Storage-provider choices remain hidden from ordinary authoring actions.
- Arbitrary Processing project source, user workspaces, and independently owned file trees are not Docs Viewer media merely because an inventory would be useful.
- The report does not hash, continuously verify, repair, mutate, delete, republish, or roll back media or source files.

The feature is proposed and deliberately UI-led. The first delivery begins with a short report-host/list-layout trial, then implements only the smallest read model and report that remain easy to use. Its specification may change after that trial; no lifecycle contract or generic media-management framework should be designed in advance.
