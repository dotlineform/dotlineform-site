# Publish And Deploy Model

## Purpose

This concept defines the document lifecycle that follows the runtime-ownership work in [Scope, Data, And Site Foundations](/docs/?scope=studio&doc=d-20260830-074605-dc4f11). It records what the current Analysis **Publish** action actually does, preserves that behaviour during the Stage 1 runtime cutover, and separates consumer-neutral scope publication, repository deployment, Git commit and push, and public deployment in the target model.

The separation is useful repository architecture whether or not a Swift application is built. It gives each operation a clear input, output, capability, and side-effect boundary. A future Swift application benefits by adopting those boundaries incrementally rather than requiring a different document lifecycle.

## Current Analysis Publish Behaviour

The current Analysis **Publish** action combines publication with repository deployment. The Docs builders write the current reviewable document and Search output beneath `docs-viewer/scopes/analysis/published/`; Publish then promotes selected site-ready content into the tracked public projection beneath `site/assets/data/`.

```text
current builder output
docs-viewer/scopes/analysis/published/
        -> current Publish
tracked public projection
site/assets/data/
        -> explicit manual Git commit and push
committed repository snapshot
        -> separate manual GitHub Action
dotlineform.com
```

The button first calls `POST /docs/publish/confirm`. This is a read-only preview that compares the current Analysis output with its configured public projection and reports document, Search, media, and exclusion changes. Confirmation calls `POST /docs/publish/apply` with an explicit `confirm: true`.

Apply performs the following work:

- project the Analysis document payloads into `site/assets/data/docs/scopes/analysis/`;
- project the configured `tags` and `works` sub-scopes into their corresponding Analysis site folders;
- include documents by default and omit roots and descendants with explicit `publishable: false`, removing only the exact currently public document files owned by those exclusions rather than treating arbitrary missing source files as deletions;
- omit Manage-only artifacts including management manifests, backlinks, references, semantic-token indexes, and publication preparation files;
- create public-safe document payloads by removing local-only report configuration and folder activation data, rewriting managed-media URLs, and using prepared public Mermaid variants;
- copy the existing Analysis Search index byte-for-byte to `site/assets/data/search/analysis/index.json` when it differs;
- generate the Analysis public document-location projection;
- reconcile referenced image, SVG, HTML, and file media against their configured tracked-site or R2 destinations, including removal of exact stale unreferenced public media;
- reconcile publication-lineage evidence; and
- refresh the exact Catalogue document URL projections as post-publication follow-through.

Media status or application errors are reported without rolling back a completed document projection. The Search index is copied but is not rebuilt: Publish deploys whichever manually rebuilt Search output currently exists.

Current Publish does not build documents, rebuild Search, update runtime code, commit repository changes, trigger the GitHub Pages workflow, or deploy dotlineform.com. The manually triggered GitHub Action separately validates and deploys the tracked `site/` snapshot.

## Stage 1 Boundary

[Docs Viewer Runtime Ownership And Site Projection Delivery](/docs/?scope=studio&doc=d-20260830-074606-881007) does not change the current Analysis Publish behaviour, button, endpoints, service, configuration, data paths, publishability rules, or resulting `site/assets/data/` delta.

The internal `site-code-update` manifest owns only projected runtime JavaScript and CSS. It must never own document, Search, media, scope configuration, or other `site/assets/data/` paths. Source-level runtime tests may move from projected `site/` paths to canonical runtime paths, but public projection assertions remain against `site/`; this is not a document Publish change.

Renaming, splitting, or otherwise changing Analysis Publish during Stage 1 would cross into the later scope/data and document-deployment stages. Stage 1 closeout must therefore confirm that the current Publish preview and apply boundaries remain intact.

## Target Lifecycle

The target model gives Build, Publish, Deploy Repo, the ordinary Git commit and push, and Deploy Public distinct owners and outputs:

```text
canonical source
        -> Build
replaceable generated output
        -> Publish
accepted external published snapshot -----> Swift or another direct consumer
        -> Deploy Repo, Analysis only
tracked site/assets/data/ projection
        -> explicit Git commit and push
committed repository snapshot
        -> Deploy Public
GitHub Pages and dotlineform.com
```

### Build

Build transforms canonical Markdown, metadata, and source media into replaceable generated document, Search, and media output. Generated output is the working-review surface in Manage mode. Rebuilding does not publish or deploy anything.

Search remains a manual whole-index rebuild unless a later feature explicitly changes that contract.

### Publish

Publish promotes generated output into the scope's accepted external published snapshot. Every in-scope Docs Viewer scope has this operation, regardless of whether it can be deployed publicly.

Publish owns document eligibility. Documents are included by default; `publishable: false` keeps a document in generated working output but excludes it and its owned descendants from the accepted published snapshot. A document that is not in the published snapshot cannot be deployed.

Published output is consumer-neutral. Manage mode can review it directly, and Swift or another application can consume it without requiring the repository, `site/`, a local web server, GitHub Pages, or dotlineform.com. Every consumer sees the same published document set. Publish performs the payload preparation required by those consumers but does not copy into `site/` or perform destination-specific deployment work.

### Deploy Repo

Deploy Repo is available only for Analysis. It projects the accepted Analysis published snapshot into tracked `site/`, producing the exact data and media snapshot used by local public-site preview and a later public release.

Deploy Repo copies the complete accepted published document set without applying another eligibility rule or producing a differently filtered edition. The repository projection can lag behind Swift, Manage's Published view, or another direct consumer until Deploy Repo is run, but after deployment it contains the same documents.

The current Analysis Publish implementation combines the two future operations and is therefore the starting seam for their separation. Its publishability filtering and common consumer-ready payload preparation move to Publish. Its destination-specific responsibilities remain with Deploy Repo: materialising the accepted snapshot at the configured site paths, reconciling public media destinations, and performing follow-through that depends on the repository projection. The later delivery must classify the current URL, document-location, lineage, and Catalogue follow-through steps against that boundary without changing the shared published document set.

Deploy Repo does not rebuild or publish the scope, commit or push repository changes, or deploy GitHub Pages. Its current implementation writes the local repository working tree. A future provider may perform the same repository-projection operation through Swift and GitHub capability, but repository commit remains an explicit subsequent action.

### Commit And Push

The intended tracked `site/` delta is reviewed, committed, and pushed through the ordinary explicit Git workflow. This is not part of Build, Publish, or Deploy Repo and is never an implicit side effect of them.

The current workflow leaves this as a manual user action. A future Swift application may acquire an explicit repository commit and push capability, but it must retain the same visible boundary rather than silently committing as part of Publish or Deploy Repo.

### Deploy Public

Deploy Public is the existing manually triggered GitHub Pages workflow. It assumes that the intended `site/` state has already been committed and pushed. It validates and deploys that committed snapshot without reading external scopes, rebuilding documents or Search, publishing a scope, generating runtime, modifying `site/`, or committing changes.

Deploy Repo, commit and push, and Deploy Public remain independent manual operations. Local preview can inspect an uncommitted or not-yet-public repository projection; Deploy Public releases only the committed snapshot supplied to the workflow. A future Swift application may explicitly perform the repository commit and trigger the GitHub Action, but those capabilities do not collapse the lifecycle boundaries or make either step automatic.

## Capability-Based Workflow

The conceptual separation does not require extra friction in the current local workflow. The Publish modal composes the operations that the active environment can perform:

```text
Publish changes

[x] Publish
[x] Deploy Repo
```

Publish and Deploy Repo are both selected by default when both capabilities are available. Deploy Repo is shown unchecked and disabled when the environment cannot write the repository projection. At least one available operation must be selected.

The selections remain independent:

- **Publish only** promotes generated output for every published-data consumer without updating `site/`.
- **Deploy Repo only** copies an already-published Analysis snapshot into `site/`.
- **Publish and Deploy Repo** is the normal current local workflow and runs Publish first, then deploys the exact published revision produced by that operation.

The primary action label follows the selection: **Publish**, **Deploy Repo**, or **Publish And Deploy**. If Publish succeeds and Deploy Repo fails, the published snapshot remains valid while the repository projection is stale; the result reports that partial completion and permits Deploy Repo to be retried without republishing.

Capability availability supports an incremental application path:

| Environment | Publish | Deploy Repo | Normal behaviour |
| --- | --- | --- | --- |
| Current local Manage | Available | Available | Publish and Deploy Repo together |
| Read-only Swift | Not exposed | Not exposed | Read the published snapshot |
| Swift with Manage capability | Available | Unavailable | Publish only |
| Swift with repository and GitHub capability | Available | Available | Publish and Deploy Repo, with separate explicit commit, push, and Deploy Public actions |

Deploy Public remains outside the Publish modal because it is a separate manual release action against committed repository state.

## Migration Implications

The later scope/data and deployment deliveries need to:

- establish separate external `generated/` and `published/` ownership for every migrated scope;
- migrate the current builder output now named `published/` into the generated layer;
- introduce a genuine scope Publish operation that applies `publishable`, performs common consumer-ready payload preparation, and promotes generated output to the accepted external published snapshot;
- allow Manage mode to view generated and published output without treating either as a public-site projection;
- replace the current single-purpose Analysis Publish control with the capability-based Publish and Deploy Repo workflow;
- split the existing public projection service so Publish owns document eligibility and shared payload preparation, while Deploy Repo reads accepted external Analysis published output and applies no further document filtering;
- make Deploy Repo capability-dependent while keeping Publish available independently;
- keep destination-specific storage, transfer, and public-projection follow-through out of the consumer-neutral published payload;
- keep repository commit and push explicit and outside the document lifecycle; and
- preserve the existing manually triggered, non-mutating GitHub Pages release workflow as Deploy Public, with future application triggering treated as an explicit capability rather than automation.

The precise recovery boundary required before canonical scope source leaves repository Git belongs to the external-scope delivery. Document version history beyond that minimum recovery requirement remains a separate future concern.

## Settled Ownership

| Concern | Owner |
| --- | --- |
| Canonical Markdown and source media | External scope source |
| Replaceable working payloads | Build and external generated output |
| Accepted application-ready payloads and document eligibility | Publish and external published output |
| Site materialisation of the complete accepted Analysis snapshot | Deploy Repo for Analysis |
| Tracked public document and media snapshot | `site/` |
| Repository commit and push | Explicit Git action |
| Public release | Deploy Public through the manual GitHub Pages workflow |
| Canonical shared/public runtime code | Repository code outside `site/` |
| Tracked public runtime projection | Internal `site-code-update` development process |

Runtime projection and document deployment share `site/` as their destination but remain separate processes. Neither is an implicit side effect of the other.
