# Semantic Tokens Source Editor UI

## Outcome

Make the UI the normal way to add and maintain semantic tokens. An author should
not need to remember token syntax, manually edit ids, or discover required fields
after insertion fails.

This is a manage-only feature hosted by the existing Markdown source editor,
modal lifecycle, and Info panel. It does not add another editor or write path.

This document describes the UI side of the
[Architecture](/docs/?scope=studio&doc=d-20260714-234030-434069): when meaning
is chosen, what identity is stored, and which data the discovery and Info
surfaces consume.

## Surface Responsibilities

| surface | responsibility |
| --- | --- |
| family-specific add modal | search all accepted target types in the family, choose the concrete target identity, collect required occurrence data, and create the token |
| family-specific Info view | inspect an existing occurrence, edit only its mutable occurrence fields, and display declared read-only target-lookup context |

Target search and identity selection exist only during creation. An Info view
does not contain a target search control, a target result list, or any other
control capable of changing the existing token's identity.

The Catalogue modal hosts title-weighted keyboard-navigable Work and Series results. The separate Tag modal searches canonical IDs and aliases and shows group plus resolved-document context. The Info panel is reserved for inspection and occurrence editing.

## Source-Mode States

The source editor has three relevant contextual states:

| source state | toolbar | Info panel |
| --- | --- | --- |
| no active token | one add action per accepted family | ordinary source/document information |
| caret inside a valid token | add actions remain available | matching family-specific token view |
| exact active-token range selected by the feature | add actions remain available | same token view remains active |

Adding begins from a toolbar action and modal. Inspecting begins from the caret
and never becomes another route into identity selection.

## Add A Token

Catalogue contributes two separate source-editor actions:

- **Add catalogue token** inserts a text occurrence; and
- **Add Catalogue image** inserts a linked Work or Series image occurrence.

Tag contributes **Add tag token** as a separate text action and discovery modal. It is never mixed into Catalogue search.

All three semantic actions remain distinct from staged **Add image**, which publishes Docs-owned media.

Clicking the button:

1. captures the current selection text and range before focus moves;
2. opens the family's add modal;
3. prefills the title or equivalent field from the selected text;
4. collects and validates every required field;
5. inserts the serialized token at the captured caret or replaces the captured
   selection;
6. returns focus to the source editor with the normal dirty state.

The modal does not write or rebuild the document. The source editor owns the
buffer mutation and existing dirty-state workflow.

## Insert The Document Subject Link

**Insert subject link** is a distinct Manage Source action, not another route
into Catalogue search. It rereads normalized subject metadata for the exact
mounted document. A Work or Series subject supplies the immutable Catalogue
identity, while the current target lookup supplies the occurrence Title; the
existing serializer then emits an ordinary semantic token. A Folder subject
uses the existing local-folder Markdown serializer and validation owner.

Insertion uses the current selection and the Source editor's normal input,
dirty-state, and focus lifecycle. The inserted token is an ordinary authored
mention snapshot: it has no usage origin marker, conveys no aboutness, and is
not rewritten if the document subject changes later. Unavailable or invalid
inputs leave the buffer unchanged and expose a contained reason.

### Catalogue Text Modal

The Catalogue modal contains:

- one search across Work and Series targets;
- result type, id, and distinguishing target-lookup projection fields;
- the selected target type and id as the identity to insert;
- a required Title field for this occurrence;
- a compact selected-target summary;
- **Add** and **Cancel** actions.

Selected source text seeds the catalogue search and initially prefills
**Title**. Selecting a result refreshes Title from that target; the author can
then edit it. The author does not choose Work or Series before
searching. Result labels and lookup-projected context help decide what the
selected words mean. For example, `nerve` may surface Work `00008` and Series
`105`.

Choosing a result establishes the pending target type and id. The author may
compare and change results until confirming **Add**. After insertion that
concrete identity is immutable.

If there was no source selection, choosing a target prefills Title from its
canonical title. Confirming a current lookup result and satisfying the declared
required fields is the feature's only semantic validation gate. It guarantees
what this modal inserts at this moment; it does not constrain later direct source
editing or turn save/rebuild into document-wide validation.

### Tag Text Modal

The Tag modal searches only current resolved Tag target rows. Canonical `tag_id`, aliases, group, and the exact currently resolved document title are discovery context; selecting an alias still chooses the canonical ID. The modal never joins Tag results to Catalogue discovery.

Selected source text seeds search and remains the occurrence Title when a Tag is selected; an empty Title is filled from the canonical ID. Confirming **Add** serializes `[[tag:tag:<tag_id>|<Title>]]` and replaces only the captured revision-guarded range. A stale capture leaves Source unchanged and keeps the modal open with the error.

### Catalogue Image Modal

**Add Catalogue image** searches the existing mixed Catalogue projection but lists only current Work and Series rows carrying a valid image projection. Selecting a result writes its current Catalogue title into Search Catalogue, alt text, and caption; the result list is then emptied and collapsed. Editing Search Catalogue discards the pending selection and reopens current matches.

The modal collects:

- optional **Work Detail ID**, enabled only for a selected Work whose lookup row carries `has_details` and disabled and cleared otherwise;
- required alt text;
- optional caption and summary;
- full-column, image-left, or image-right placement; and
- fill available width or natural width.

Work Detail ID accepts a positive padded or unpadded digit value such as `001` or `1` and serializes it canonically as `detail_id=001`. The modal validates only that source shape; the ordinary Docs rebuild validates the exact Work Detail record and media. Blank retains the Work primary image. Series never accepts a detail id.

When a Work Detail ID reaches canonical shape, the browser makes one exact current-source read through the configured Local Studio `catalogue_work_detail_record` API. If that record has a title and the suggested caption has not been manually edited, the modal replaces the Work-title suggestion with the detail title; for example, Work `00638` plus `003` suggests **3 symbols (detail 1)**. The per-detail result is cached for the modal session. This suggestion does not read or require a generated `site/` payload, does not add details to Semantic Target Lookup, and does not replace rebuild-time validation. A failed suggestion read leaves the current caption editable while rebuild remains authoritative.

With no caption it inserts a plain linked image occurrence. With a caption it inserts a semantic figure occurrence carrying explicit placement and fill-width values. Canonical source stores the exact Catalogue target identity, optional Work `detail_id`, and authored presentation snapshots, not the resolved media URL.

The action inserts through the captured source selection and normal dirty-state path. It does not save, rebuild, publish media, or mutate Catalogue data independently.

## Recognize A Token

Recognition runs against the current textarea buffer, including unsaved edits.
It uses the accepted token grammar and parsed occurrence ranges, not a separate
loose regular expression.

A collapsed caret activates a token only when it is strictly inside the token's
outer opening and closing delimiters:

- before the opening delimiter: no token;
- inside the token definition: activate it;
- after the closing delimiter: no token;
- at the shared boundary between adjacent tokens: no token.

Malformed forms and token-like text in fenced or inline code do not activate a
token. A user-selected range does not activate a token unless it is the exact
range selected by the feature for the already-active occurrence.

## Token Info View

The recognized family selects its corresponding hosted Info-panel view. For every Catalogue occurrence the view shows:

- **Family**: Catalogue, read-only;
- **Target type**: Work or Series, read-only;
- **Target id**: immutable and read-only;
- declared target context when a lookup projection is available;
- the exact Catalogue destination when available; and
- editable fields belonging only to the active occurrence.

A text occurrence exposes **Title**, **Update token**, and **Remove token**. A Catalogue image occurrence exposes optional **Work Detail ID**, alt text, and the same caption, summary, placement, and fill-width presentation used during insertion, with **Update image** and **Remove image**. Work Detail ID is enabled only for a Work with the compact availability capability; it changes the selected image and activation page but not the immutable Work identity. Image update/remove retains the same immutable identity and exact-range stale guard as text-token editing.

The view edits fields encoded in this occurrence. It does not edit the canonical
target record. It cannot change target type or id. Re-targeting is deliberately
**Remove token**, followed by **Add catalogue token**.

The Catalogue Info view has no catalogue search or replacement-target control.
The resolved summary is context for the immutable identity, not a selectable
result.

The Tag Info view shows immutable canonical ID plus current aliases, group, resolved-document title, and destination from the private lookup. Only occurrence Title is editable. Unknown or unavailable lookup state keeps source identity and Title visible with unresolved context; update and exact-range removal still use the same stale guard. Successful mutation adds no redundant status message.

The current view presents three field groups:

- immutable identity;
- editable occurrence fields parsed from the current buffer;
- read-only target-lookup context, currently the Catalogue title and
  destination.

Only fields declared as occurrence fields render editable controls. The Info
view resolves target context by immutable identity through the shared target
lookup. It does not read the usage index, inspect raw canonical records, traverse
arrays, or infer additional fields. If lookup context is unavailable, the view
retains the identity and occurrence Title parsed from source and reports that
the target or destination is unresolved.

Each family owns its own Info view. Shared rendering is extracted only when
fields and behaviour are genuinely common.

## Broken-Link Repair

The manage-only Docs Broken Links report is the repair entrypoint for an
existing token that no longer resolves. A semantic-token issue row opens the
owning document in source mode. The current route handoff does not select the
exact occurrence.

The author then removes the broken token and uses the family add modal to choose
a current target. The Info view does not gain identity replacement controls for
this workflow. Rebuild applies the repaired source and rerunning the audit
confirms the issue is gone.

## Highlight, Update, And Remove

Activating a token selects its exact source range in the existing textarea.
That native selection is the highlighting contract; the feature has no
syntax-highlighting overlay or separate editor.

The active occurrence retains:

- start and end offsets;
- the raw token text;
- a buffer revision or equivalent stale-range guard.

Before update or removal, the source editor confirms that the expected raw token
still occupies the range. If not, it re-resolves the occurrence or cancels the
action rather than mutating stale offsets.

**Update token** or **Update image** serializes the same immutable identity with the edited occurrence metadata and replaces only that exact range.

**Remove token** or **Remove image** deletes only the occurrence source. It does not remove adjacent whitespace or punctuation and it does not preserve or unwrap displayed text. The change remains local and undoable through the normal editor until the document is rebuilt.

After either action, focus returns to the source editor and dirty state is
projected normally. Updating selects the replacement token and keeps its Info
view available; removing it returns the panel to ordinary source context.

## Reused UI And Current Composition

Semantic Tokens reuse:

- the Markdown textarea and local dirty-state workflow;
- the narrow active source-editor adapter;
- title-weighted target search and keyboard-navigable result rows;
- the staged-image presentation controls, reused without staged-media publication;
- manage-only hosted Info-panel views;
- the management action and modal lifecycle;
- token construction and local selection replacement.

The target results component is shared visually while Catalogue and Tag own separate filtering, discovery context, modal identity, action, and serializer. Source mode shows ordinary metadata until the caret activates a supported token, when contextual routing selects the matching Catalogue or Tag Info view.

## Extension Rules

- Family actions register through focused contributions; source-editor
  lifecycle code does not branch on token families.
- Target search/results remain independent of Info-panel lifecycle and
  insertion ownership.
- The Info host selects family-specific views through contextual routing.
- The generic source adapter owns current-buffer snapshots, captured
  selections, exact-range selection, and guarded replacement.
- Selection text and range are captured before modal focus moves.
- Native textarea selection remains the active-range presentation. A richer
  editor is not part of this capability.

## Accessibility And Review

- Toolbar and modal controls use the exact token-family name.
- Identity and editable fields have visible labels; read-only identity is not
  presented as a disabled editable input.
- Result selection supports keyboard navigation and announces target type, identity, and the selected family item.
- Modal cancellation makes no buffer change and returns focus predictably.
- Caret boundaries, selection highlighting, update, removal, stale-range handling, and Info-panel fit at representative laptop/desktop widths are reviewed manually when those interactions change.
- Permanent automated checks should protect parser/range behavior, adapter
  mutation contracts, required-field validation, and view registration rather
  than modal timing or visual choreography.
