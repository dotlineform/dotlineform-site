# Semantic Tokens Source Editor UI

## Outcome

Make the UI the normal way to add and maintain semantic tokens. An author should
not need to remember token syntax, manually edit ids, or discover required fields
after insertion fails.

This is a manage-only feature hosted by the existing Markdown source editor,
modal lifecycle, and Info panel. It does not add another editor or write path.

This workflow is accepted before token syntax and
[Architecture](/docs/?scope=studio&doc=d-20260714-234030-434069). It determines
when meaning is chosen, what identity must be stored, and which data discovery
must provide.

## Responsibility Change From The Pilot

The pilot hosts target search, mixed-target results, target selection, and
immediate token insertion in the Info panel. That proves the Info panel can host
substantial manage-mode UI, but it is not the target responsibility split.

The new contract is:

| surface | responsibility |
| --- | --- |
| family-specific add modal | search all accepted target types in the family, choose the concrete target identity, collect required occurrence data, and create the token |
| family-specific Info view | inspect an existing occurrence, edit only its mutable occurrence fields, and display declared read-only usage or target-lookup context |

Target search and identity selection exist only during creation. An Info view
does not contain a target search control, a target result list, or any other
control capable of changing the existing token's identity.

The current title-weighted search and keyboard-navigable result component remain
useful. They should be extracted from the pilot Info-panel view and hosted in the
family-specific add modal. For Catalogue, the mixed Work, Series, and Moment
results are useful and remain. The pilot's Info-panel placement and immediate
select-to-insert composition are retired.

## Source-Mode States

The source editor has three relevant contextual states:

| source state | toolbar | Info panel |
| --- | --- | --- |
| no active token | one add action per accepted family | ordinary source/document information |
| caret inside a valid token | add actions remain available | matching family-specific token view |
| exact active-token range selected by the feature | add actions remain available | same token view remains active |

Adding begins from a toolbar action and modal. Inspecting begins from the caret
and never becomes another route into identity selection.

## Add A Token

Each accepted family contributes one clearly named source-editor toolbar button.
The first is **Add catalogue token**. Tags later receive **Add tag token** rather
than being mixed into Catalogue discovery.

Clicking the button:

1. captures the current selection text and range before focus moves;
2. opens the family's add modal;
3. prefills the title or equivalent field from the selected text;
4. collects and validates every required field;
5. inserts the serialized token at the captured caret or replaces the captured
   selection;
6. returns focus to the source editor and reports the local change.

The modal does not write or rebuild the document. The source editor owns the
buffer mutation and existing dirty-state workflow.

### Catalogue Modal

The first modal contains:

- one search across Work, Series, and Moment targets;
- optional type filters for narrowing results after search begins;
- result type, id, and distinguishing target-lookup projection fields;
- the selected target type and id as the identity to insert;
- a required Title field for this occurrence;
- a short target-lookup summary or preview where declared;
- **Add catalogue token** and **Cancel** actions.

Selected source text seeds the catalogue search and prefills **Title**, which
remains editable. The author does not choose Work, Series, or Moment before
searching. Result labels and lookup-projected context help decide what the
selected words mean. For example, `nerve` may surface Work `00008` and Series
`105`.

Choosing a result establishes the pending target type and id. The author may
compare and change results until confirming **Add catalogue token**. After
insertion that concrete identity is immutable.

If there was no source selection, choosing a target prefills Title from its
canonical title. Confirming a current lookup result and satisfying the declared
required fields is the feature's only semantic validation gate. It guarantees
what this modal inserts at this moment; it does not constrain later direct source
editing or turn save/rebuild into document-wide validation.

## Recognize A Token

Recognition runs against the current textarea buffer, including unsaved edits.
It uses the accepted token grammar and parsed occurrence ranges, not a separate
loose regular expression.

A collapsed caret activates a token only when it is strictly inside the token's
outer opening and closing delimiters:

- before the opening delimiter: no token;
- inside the token definition: activate it;
- after the closing delimiter: no token;
- at the shared boundary between adjacent tokens: no token.

Malformed forms and token-like text in fenced or inline code do not activate a
token. A user-selected range does not activate a token unless it is the exact
range selected by the feature for the already-active occurrence.

## Token Info View

The recognized family selects its corresponding hosted Info-panel view. The
Catalogue view shows:

- **Family**: Catalogue, read-only;
- **Target type**: Work, Series, or Moment, read-only;
- **Target id**: immutable and read-only;
- declared target context when a lookup projection is available;
- editable occurrence **Title**;
- **Update token** and **Remove token** actions.

The view edits fields encoded in this occurrence. It does not edit the canonical
target record. It cannot change target type or id. Re-targeting is deliberately
**Remove token**, followed by **Add catalogue token**.

The Catalogue Info view has no catalogue search or replacement-target control.
The resolved summary is context for the immutable identity, not a selectable
result.

The view may present four field groups:

- immutable identity;
- editable occurrence fields parsed from the current buffer;
- read-only attributes from the rebuilt usage index;
- read-only target-lookup projections such as destinations or preview images.

Only fields declared as occurrence fields render editable controls. A simple
new optional occurrence field can use a token-definition-declared supported
control type. Usage-index attributes never override fields parsed from the
current buffer and may be stale until rebuild. Canonical and derived target
fields appear only when the active token-kind definition declares their lookup
projections. The Info view reads that projection by immutable identity; it does
not inspect the raw canonical record, traverse arrays such as Work `files[]`, or
infer additional fields. A Work preview image is lookup context, not occurrence
data. If lookup context is unavailable, the view retains the identity and
occurrence fields parsed from source without presenting the failure as a source
validation result.

Each later family gets its own Info view through its own specification and
delivery. Shared rendering may be extracted only after the fields and behavior
are genuinely common.

## Broken-Link Repair

The manage-only Docs Broken Links report is the repair entrypoint for an
existing token that no longer resolves. A semantic-token issue row opens the
owning document in source mode and should select the exact occurrence where the
available source/range contract permits.

The author then removes the broken token and uses the family add modal to choose
a current target. The Info view does not gain identity replacement controls for
this workflow. Rebuild applies the repaired source and rerunning the audit
confirms the issue is gone.

## Highlight, Update, And Remove

Activating a token selects its exact source range in the existing textarea. That
native selection is the first highlighting contract; the feature does not need
a syntax-highlighting overlay or richer editor.

The active occurrence retains:

- start and end offsets;
- the raw token text;
- a buffer revision or equivalent stale-range guard.

Before update or removal, the source editor confirms that the expected raw token
still occupies the range. If not, it re-resolves the occurrence or cancels the
action rather than mutating stale offsets.

**Update token** serializes the same immutable identity with the edited
occurrence metadata and replaces only that exact range.

**Remove token** deletes only the token source. It does not remove adjacent
whitespace or punctuation and it does not preserve or unwrap the displayed
title. The change remains local and undoable through the normal editor until
the document is rebuilt.

After either action, focus returns to the source editor, dirty state is
projected normally, and the Info panel returns to ordinary source context unless
another token is active.

## Existing UI To Reuse

The pilot already demonstrates useful parts:

- the Markdown textarea and local dirty-state workflow;
- the narrow active source-editor adapter;
- title-weighted target search and keyboard-navigable result rows;
- manage-only hosted Info-panel views;
- the management action and modal lifecycle;
- token construction and local selection replacement.

The delivery should extract the mixed target search/results component for use
inside the Catalogue modal, then replace the hosted picker with the caret-driven
Catalogue Info view. It should not preserve the pilot picker placement or
immediate insertion workflow merely because they are shipped.

## Refactoring Triggers

Call out and resolve these before the Catalogue UI is implemented:

- If family actions require hardcoded branches in source-editor lifecycle code,
  add a focused contribution mechanism.
- If target search/results cannot move out of the hosted picker without carrying
  Info-panel lifecycle or insertion ownership with them, separate the reusable
  result component from the pilot view first.
- If the Info host cannot switch safely from ordinary source context to a
  family-specific view, extend its contextual view routing.
- If the adapter cannot select or guarded-replace an arbitrary exact range, add
  those generic buffer operations without adding token knowledge to core.
- If modal focus loses the original selection, capture selection text and range
  before opening.
- If native textarea selection does not remain sufficiently visible while the
  Info view has focus, review a small active-range presentation enhancement
  before considering a richer editor.

## Accessibility And Review

- Toolbar and modal controls use the exact token-family name.
- Identity and editable fields have visible labels; read-only identity is not
  presented as a disabled editable input.
- Result selection supports keyboard navigation and announces target type,
  identity, and the selected catalogue item.
- Modal cancellation makes no buffer change and returns focus predictably.
- Caret boundaries, selection highlighting, update, removal, stale-range
  handling, and narrow/mobile Info-panel fit need manual UI review.
- Permanent automated checks should protect parser/range behavior, adapter
  mutation contracts, required-field validation, and view registration rather
  than modal timing or visual choreography.
