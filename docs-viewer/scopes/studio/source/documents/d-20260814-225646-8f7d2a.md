# Docs Viewer Core and Integration Architecture

## Purpose

Make Docs Viewer progressively easier to extend by giving its invariant product rules, standard capabilities, adjacent-domain integrations, and application composition distinct executable owners.

The immediate aim is not a separately packaged Docs Viewer. It is that each real integration can attach through one explicit seam without teaching the invariant layers about the adjacent domain, duplicating product behavior, or requiring a separate manifest to describe what the runtime code supposedly composed.

## Feature Documents

- [Clone-Ready Docs Viewer](/docs/?scope=studio&doc=d-20260814-232812-4a0c9e) — one concrete motivation and proof scenario: the checked-out source can run a coherent Docs Viewer composition without private workspaces or adjacent applications.

## Problem

Docs Viewer already combines several application shells, storage environments, workflows, and adjacent domains. Public, Manage, and Review routes share some behavior but own different authority. Repository-backed and external-local scopes use different locations. Publishing, R2, Studio data, document packages, semantic references, reports, media producers, and future integrations attach at different depths.

Useful seams exist, but composition is not consistently authoritative. Some browser assembly is explicit while backend startup, builders, configuration globals, paths, and optional workflows still carry repository or adjacent-application assumptions. Code review and tests can detect individual consequences after implementation, but they do not make those couplings difficult to introduce.

The architectural goal is therefore to improve the construction of Docs Viewer, not to add a review system around the current construction.

## Core Definition

Core is the part that integrations depend upon, which contains no knowledge of those integrations and whose invariants remain true whichever supported capabilities are composed around it.

A responsibility belongs in core only when:

- it defines what a Docs Viewer document, scope, source, generated read, or confined operation means;
- its inputs and outputs can be stated without repository layout or adjacent-domain context;
- supported capabilities can depend on it without reverse imports or mode-specific branches;
- removing an integration leaves the responsibility and its authority unchanged; and
- current product behavior demonstrates the need for the contract.

An extension seam may be core when multiple real consumers demonstrate it. A hypothetical consumer is not sufficient reason to create a generic interface.

## Structural Model

### Kernel Invariants

The kernel owns exact document and scope identity, source and metadata rules, confined artifact identities, rendering and build contracts, mutation rules, and the smallest application-environment contracts needed to supply paths, scopes, providers, and services explicitly.

### Standard Capabilities

Reader, search, Recent, management, Import, Export, reports, media workflows, and other first-party product behavior may use the kernel without all becoming kernel invariants. A capability can be standard and reusable while still being optional in a particular route or composition.

### Integrations

Repository and public publication, R2, Studio and Catalogue data, semantic targets, document packages, Docs Review, specialised reports, storage providers, and other adjacent-domain behavior remain owned outside the kernel. Each integration adapts its domain to exact Docs Viewer contracts and retains its own policy, data authority, and failure behavior.

### Composition Roots

Each application shell constructs its available routes, services, providers, views, actions, reports, formats, and workflows once. Capability truth is derived from the components actually registered and available there. An excluded integration is not imported and hidden; it is absent from that composition's dependency closure.

## Composition And Configuration

There is one Docs Viewer codebase and one configuration contract. Different uses select different compositions; they do not fork the application or maintain complete parallel configuration models.

```text
Docs Viewer code + clone-safe composition = clone-ready Docs Viewer
Docs Viewer code + integrated composition + local values = dotlineform development Docs Viewer
```

Configuration ownership is layered:

- code-owned defaults and schemas define valid configuration and immutable behavior;
- a composition selects scope descriptors, providers, routes, services, sites, and optional integrations;
- machine-local environment supplies values such as ports, absolute workspace roots, and credentials, but does not assert conceptual capability;
- scope-owned configuration travels with the scope data whose lifecycle it governs; and
- browser-safe runtime configuration is a derived projection of the accepted composition, never an independently edited authority.

Capability availability follows the components successfully constructed from that configuration. An absent Studio, public-preview, R2, package, Review, or external-workspace integration contributes no origin, action, service, scope, or loader. Missing values fail only when the selected composition actually requires them.

## Scope Data Ownership

Docs Viewer is an application that consumes document workspaces; placing a repository scope beneath `docs-viewer/` must not make the application the conceptual owner of that content.

The application source tree should own code, immutable defaults and schemas, runtime assets, templates, build and service machinery, and application tests. Repository-owned documentation may live in an explicit content area or beside its owning project; private and user scopes remain in external workspaces; reproducible local output belongs in a configured scope output or local runtime area; public projections remain with their public owner.

Every composition supplies exact scope descriptors and locations. Core code must not require a repository scope to use `docs-viewer/scopes/<scope>`, infer content roots from its own installation path, or load every scope known to another composition. Exact physical moves remain bounded delivery decisions rather than a prerequisite big-bang reorganisation.

## Executable Rules

1. Dependencies point inward: integrations and standard capabilities may depend on kernel contracts; the kernel does not import them.
2. Application composition is selected at explicit browser and service composition roots rather than through scattered mode flags or ambient repository discovery.
3. Configuration is authoritative only when the owning runtime, builder, or service consumes it to construct behavior. Descriptive mirrors, duplicated complete config sets, and manually maintained composition ledgers are not introduced.
4. Application paths, selected scope descriptors, artifact providers, processes, and adjacent services are supplied explicitly. Process-global mutable registries, application-owned content-path conventions, and implicit `repo_root` discovery are transition debt, not target contracts.
5. Integrations preserve exact scope, sub-scope, document, subject, and artifact identity across the boundary. Titles, filenames, selected UI state, and route context are not substitute identity.
6. Public and browser-facing data remains a positive projection of the minimum accepted fields; integrations do not expose canonical or private application models for convenience.
7. An integration can be removed by deleting its composition contribution and owned implementation without changing kernel behavior or leaving compatibility aliases, dormant loaders, duplicated configuration, or test-only application models.

## Integration Method

New integration work starts from one actual consumer and one concrete outcome:

1. name the adjacent-domain authority and the exact identity crossing the boundary;
2. identify the existing kernel or standard-capability seam that can accept it;
3. if no seam exists, extract only the smallest general contract justified by this integration and at least one existing consumer;
4. attach the provider, service adapter, route, action, view, report, format, or workflow at the owning composition root;
5. derive visible capability from that accepted registration and project only the data required by the consumer;
6. remove the superseded direct dependency or special case in the same bounded change; and
7. prove the invariant, adapter behavior, and one composition boundary with the smallest adequate evidence.

A new integration does not trigger a general plug-in framework, a repository-wide registry, a parallel capability inventory, or speculative interfaces for future adopters.

## Testing And Review Consequences

Tests follow the executable ownership:

- kernel tests prove invariant data, validation, and mutation contracts;
- integration tests prove adaptation from one exact external authority into one accepted Docs Viewer contract;
- composition evidence proves that the intended shell constructs the contribution and that an excluded shell does not acquire its dependency;
- browser evidence remains limited to route, module, service, and public/private integration boundaries.

Tests do not reproduce the application composition as a second model or preserve ordinary UI choreography. When review repeatedly finds the same class of coupling, the preferred outcome is to strengthen the owning construction seam. A narrow test is retained only when structure or validation cannot make that regression difficult directly.

There is no separate implementation-review framework or audit ledger. The Development Checklist retains the concise human questions: where is authority, through which seam does the behavior enter, where is invalid use rejected, who owns lifecycle and cleanup, and what is the smallest evidence required?

## Relationship To Existing Architecture

[Docs Viewer Core Definition Baseline v1](/docs/?scope=studio&doc=d-20260724-213457-6e1cf7) remains useful evidence about current mixed ownership and candidate seams, but its classifications must be reconsidered against current code and real integration needs. A future standalone distribution is no longer the definition of core or a required proof consumer.

[Runtime Architecture](/docs/?scope=studio&doc=d-20260331-000000-c313fd) and [Configuration And Extension Points](/docs/?scope=studio&doc=d-20260512-142027-54b354) remain the durable current-state owners. This Roadmap feature proposes changes to their executable boundaries; it does not override them before implementation and closeout.

## Delivery Direction

Do not begin with a whole-application extraction, a new worktree, a content-tree move, or a complete capability classification. Select the next real integration or composition that currently pressures a weak boundary. Its readiness step should identify one concrete dependency or authority problem and the smallest composition seam that resolves it.

The [Clone-Ready Docs Viewer](/docs/?scope=studio&doc=d-20260814-232812-4a0c9e) scenario is the first concrete candidate because it requires selected scope loading, optional adjacent services, explicit data roots, and an application that starts without the private integrated environment. A first delivery may use that scenario or another selected real integration, but it must end with the existing integrated application still working, the superseded coupling removed, and no standalone package or generic framework created.

## Boundaries

- No standalone packaging, installer, migration, or release work is part of the current aim.
- No generic plug-in platform, capability engine, dependency analyser, review runner, score, dashboard, or maintained composition ledger is introduced.
- No big-bang reorganisation is justified merely to make folders resemble the structural model.
- No two complete scope, capability, or route configurations are copied and maintained as independent models of the same facts.
- No interface is extracted without a current consumer and a bounded implementation need.
- Existing behavior is preserved unless the selected integration delivery explicitly changes its product contract.
- Core classification remains adjustable when implementation evidence exposes a better owner; the code and canonical configuration remain the exact current authority.

## Success Meaning

Docs Viewer becomes easier to extend when a real integration can be added or removed through one explicit composition-owned contribution; invariant layers remain unaware of its domain; capability availability follows the constructed application; configuration drives rather than describes behavior; and focused evidence protects the boundary without recreating the application in tests.

## Status

Proposed. No core refactor or implementation delivery is authorized by this document. The next step, when a real integration is selected, is a bounded readiness check against current code and current durable architecture.
