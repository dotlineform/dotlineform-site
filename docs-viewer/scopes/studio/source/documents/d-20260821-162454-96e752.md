# Pandoc EPUB Export from Docs Viewer HTML

## Purpose

This document outlines a simpler EPUB export approach using **Pandoc** rather than building EPUB structure directly in Python.

The key point is that the Docs Viewer already produces HTML. Markdown does not need to be introduced into the EPUB pipeline.

The intended architecture is:

```text
Docs Viewer generated HTML
          │
          ▼
small HTML preparation step
          │
          ▼
Pandoc
          │
          ▼
EPUB 3
          │
          ▼
EPUBCheck
```

Pandoc is responsible for understanding EPUB packaging.

The preparation step is responsible only for translating the existing Docs Viewer HTML collection into a form Pandoc can convert reliably.

---

## Why Pandoc is attractive

A direct EbookLib implementation would require the project to understand and construct EPUB-specific concepts such as:

- package manifests;
- navigation documents;
- spine order;
- XHTML content files;
- asset registration;
- EPUB metadata;
- final EPUB packaging.

Pandoc already implements these concerns.

This gives a much cleaner division of responsibility:

```text
Docs Viewer / small Python helper
    understands Docs Viewer documents

Pandoc
    understands EPUB
```

This is closer to the original goal of a simple external snapshot exporter.

---

## Existing input

The current HTML snapshot already resembles:

```text
studio-docs/
├── index.html
├── styles.css
└── docs/
    ├── d-....html
    ├── d-....html
    └── ...
```

The index contains the complete nested document hierarchy and links to the individual document files.

The current export contains more than 200 documents, so the process must be deterministic and automated rather than assembled manually.

---

## Pandoc can accept HTML directly

Pandoc supports HTML as an input format and EPUB 3 as an output format.

A basic single-file conversion is therefore:

```bash
pandoc   document.html   --from=html   --to=epub3   --output=document.epub
```

There is no Markdown stage:

```text
HTML → Pandoc → EPUB
```

---

## Pandoc can accept multiple HTML files

Pandoc also accepts multiple input files:

```bash
pandoc   docs/a.html   docs/b.html   docs/c.html   --from=html   --to=epub3   --output=studio-docs.epub
```

By default, Pandoc concatenates multiple input files before parsing them.

This is potentially useful, but there are two important issues for the Docs Viewer export:

1. the exported files may each be complete standalone HTML documents rather than HTML fragments;
2. the existing document hierarchy is not encoded simply by the order of the input files.

These issues need to be tested rather than assuming that a raw `docs/*.html` invocation will produce the intended book.

---

## Important: `--file-scope` is probably not appropriate

Pandoc provides:

```bash
--file-scope
```

which parses each input file independently before combining the resulting documents.

That initially appears attractive for a collection of standalone HTML documents.

However, Pandoc explicitly documents an important limitation:

> cross-file footnotes and links do not work when `--file-scope` is enabled.

Pandoc also prefixes identifiers from separate files to avoid collisions.

Because cross-document links are important in the Docs Viewer snapshot, `--file-scope` should **not** be adopted as the default solution without a specific proof that all required links survive.

The safer working assumption is therefore:

```text
do not rely on --file-scope
```

Instead, prepare one coherent HTML publication before passing it to Pandoc.

---

## Recommended pipeline

The likely robust implementation is:

```text
existing HTML export
├── index.html
├── styles.css
└── docs/*.html
          │
          ▼
small Python preparation script
          │
          ├── read index.html
          ├── recover hierarchy and ordering
          ├── read document HTML
          ├── extract document content
          ├── assign stable document anchors
          ├── represent hierarchy with headings
          ├── rewrite cross-document links
          └── write temporary book.html
          │
          ▼
book.html
          │
          ▼
Pandoc
          │
          ▼
studio-docs.epub
          │
          ▼
EPUBCheck
```

The temporary `book.html` is generated output. It is not a new canonical source format.

---

## The Python step should remain small

The preparation script should not know anything about EPUB package internals.

It should only understand the HTML export.

Conceptually:

```python
index = load_index()
tree = parse_document_tree(index)

for document in tree:
    html = load_document(document)
    content = extract_content(html)
    content = rewrite_links(content)

    append_to_book(
        document=document,
        content=content,
    )

write_book_html()
run_pandoc()
run_epubcheck()
```

This is very different from implementing an EPUB generator.

---

## Key issue 1: document hierarchy

The existing `index.html` contains a nested tree such as:

```text
Architecture
├── Data Models Diagrams
│   ├── Catalogue Data Model Map
│   ├── Cross-System Relationship Map
│   └── Docs Viewer Projection Map
├── Knowledge System Vision
└── ...
```

Pandoc's generated table of contents is based primarily on the heading hierarchy in its input document.

It will not automatically interpret the nested `<ul>` in the existing index as the desired EPUB contents structure.

The preparation stage therefore needs to convert tree depth into document heading depth.

For example:

```html
<h1 id="d-architecture">Architecture</h1>

...

<h2 id="d-data-models">Data Models Diagrams</h2>

...

<h3 id="d-catalogue-map">Catalogue Data Model Map</h3>

...
```

Pandoc can then generate a nested EPUB table of contents from that hierarchy.

---

## Key issue 2: document headings versus internal headings

Each exported document may already have its own heading structure:

```html
<h1>Document title</h1>
<h2>Section</h2>
<h3>Subsection</h3>
```

But the same document may sit at depth 2 or 3 in the Docs Viewer tree.

If the hierarchy is represented directly through heading levels, the exporter must decide how the internal headings are shifted.

For example, a document placed at level 3 might need:

```html
<h3>Document title</h3>
<h4>Section</h4>
<h5>Subsection</h5>
```

This needs an explicit rule.

Possible approach:

```text
document tree depth
    determines document title heading

internal heading levels
    are shifted relative to the document title
```

This transformation should be mechanical and tested.

---

## Key issue 3: cross-document links

Current HTML links may look like:

```html
<a href="d-20260802-205910-533be0.html">
    Catalogue Data Model Map
</a>
```

or, depending on location:

```html
<a href="docs/d-20260802-205910-533be0.html">
```

If the preparation step produces one logical HTML document, these can be rewritten to stable fragment links:

```html
<a href="#d-20260802-205910-533be0">
```

and the destination document title receives:

```html
<h2 id="d-20260802-205910-533be0">
    Catalogue Data Model Map
</h2>
```

This is preferable to trying to predict the internal filenames Pandoc will create inside the EPUB.

Pandoc can then adjust internal references when it splits the logical publication into EPUB content files.

---

## Preserve fragment links

A source link might point to a section inside another document:

```text
d-document.html#validation
```

The preparation step should preserve the fragment relationship.

A possible transformed identifier scheme is:

```text
#d-document--validation
```

This avoids collisions between common section IDs such as:

```text
#overview
#testing
#architecture
```

which may occur in many documents.

A deterministic identifier namespace is worth establishing early.

---

## Key issue 4: EPUB splitting

Pandoc's:

```bash
--split-level=N
```

controls the heading level at which the EPUB is internally divided into separate content files.

The default is level 1.

For example:

```bash
--split-level=2
```

may be useful if top-level sections contain many documents.

This option does **not** define what users see as the hierarchy. It affects the internal composition of the EPUB.

Therefore keep these concepts separate:

```text
heading hierarchy
    → table of contents structure

--split-level
    → EPUB internal file boundaries
```

The correct split level should be determined empirically once the full snapshot is tested in Apple Books.

---

## Key issue 5: CSS

Pandoc supplies basic EPUB styling by default.

A project-specific stylesheet can be supplied using:

```bash
--css=epub.css
```

The existing `styles.css` should probably not be imported wholesale.

The Docs Viewer stylesheet contains application presentation as well as document presentation.

Create a dedicated EPUB stylesheet containing only semantic document rules such as:

```text
body
headings
paragraphs
lists
links
tables
code
pre
blockquote
figure
figcaption
images
```

Avoid:

```text
toolbars
buttons
panels
menus
hover states
manage-mode UI
application layout
```

The EPUB should look like a publication, not a frozen browser application.

---

## Key issue 6: images and other media

Pandoc's EPUB writer normally includes media referenced by supported media elements in the generated EPUB, producing a self-contained publication.

This is useful for the snapshot requirement.

Typical local assets should therefore become part of the EPUB:

```text
generated SVG diagram
local image
illustration
document figure
```

External links can remain external when they genuinely reference external information.

An explicit policy is useful:

```text
required snapshot asset
    → embed in EPUB

external reference
    → preserve external link
```

If Pandoc has difficulty locating local assets, resource lookup paths need to be considered.

---

## Key issue 7: relative asset paths

The existing HTML documents may reference resources relative to their own location:

```text
docs/document.html
    ↳ ../assets/image.svg
```

Once content is extracted into `book.html`, those paths may no longer resolve correctly.

The preparation step should either:

1. rewrite asset paths relative to the temporary publication root; or
2. arrange the temporary file so existing relative paths remain valid.

Pandoc has resource-search options, but path rewriting should still be deterministic rather than relying on the process working directory accidentally matching the export structure.

---

## Key issue 8: JavaScript

The EPUB snapshot should not attempt to carry the Docs Viewer runtime into the book.

Remove or statically replace:

```text
application scripts
dynamic document loading
runtime JSON fetching
management controls
interactive navigation
```

Where JavaScript currently produces a visual result, prefer a pre-rendered static equivalent.

For example:

```text
Mermaid source
    ↓ build stage
SVG
    ↓ EPUB export
embedded SVG
```

rather than:

```text
Mermaid JavaScript runtime inside EPUB
```

---

## Key issue 9: HTML conversion can be lossy

Pandoc parses source formats into its internal document model before writing the target format.

Its own documentation cautions that conversions from richer formats such as HTML may lose constructs that do not map cleanly into that model.

This should not be treated as a reason not to use Pandoc.

Instead, test the actual semantic HTML used by the Docs Viewer.

Representative cases should include:

- headings;
- paragraphs;
- emphasis;
- links;
- lists;
- nested lists;
- code blocks;
- tables;
- block quotes;
- images;
- SVG diagrams;
- figures/captions;
- any custom semantic tokens rendered into HTML.

The proof should identify unsupported cases before a production exporter is built.

---

## Key issue 10: metadata

Pandoc can add normal EPUB metadata including:

```text
title
creator
date
language
identifier
description
```

A snapshot should have a deterministic identity rather than relying on an automatically generated identifier.

For example:

```text
Title: Studio Docs
Identifier: studio-docs-2026-08-16
Date: 2026-08-16
Language: en-GB
```

A metadata file or command-line options can provide this without modifying the input HTML.

---

## Recommended command shape

After preparation, a command might eventually resemble:

```bash
pandoc   build/epub/book.html   --from=html   --to=epub3   --toc   --toc-depth=6   --split-level=2   --css=build/epub/epub.css   --metadata-file=build/epub/metadata.yaml   --output=dist/studio-docs-2026-08-16.epub
```

The precise `toc-depth` and `split-level` values should come from testing.

They should not be treated as fixed architectural decisions yet.

---

## A Pandoc defaults file may be cleaner

Once the proof is stable, static command options can move into a Pandoc defaults file.

Conceptually:

```yaml
from: html
to: epub3
toc: true
toc-depth: 6
split-level: 2

css:
  - epub.css
```

The export script can then concentrate on:

```text
prepare HTML
prepare metadata
call Pandoc
validate result
```

rather than constructing a long command line.

## Validation

The generated EPUB should be checked with **EPUBCheck**.

EPUBCheck is the W3C EPUB conformance checker.

The pipeline should become:

```text
prepare HTML
    ↓
Pandoc
    ↓
EPUB
    ↓
EPUBCheck
    ↓
snapshot complete
```

A conforming EPUB is not guaranteed merely because Pandoc successfully produced a file.

Any EPUBCheck errors should fail the snapshot build.

---

## Suggested proof of concept

Do not begin with the complete document collection.

Choose approximately 5–10 representative documents that include:

- at least three navigation depths;
- links between documents;
- a link to a subsection in another document;
- code;
- a table;
- an image;
- an SVG diagram if used;
- ordinary external links.

The proof should answer:

```text
Can the existing HTML content survive Pandoc conversion?

Does the hierarchy appear correctly in Apple Books?

Do cross-document links work?

Do fragment links work?

Are local images/SVGs embedded?

Does the CSS produce a readable publication?

Does EPUBCheck pass?
```

Only then scale up to all documents.

---

## Suggested implementation stages

### Stage 1 — raw Pandoc experiment

Try a small number of existing HTML files directly.

Purpose:

- understand how Pandoc parses the current generated HTML;
- identify whether standalone document wrappers are a problem;
- inspect styling and media behaviour.

Do not build infrastructure yet.

### Stage 2 — minimal preparation script

Add only what the proof demonstrates is necessary:

- extract document body/main content;
- establish document IDs;
- rewrite internal links;
- establish hierarchy headings.

Produce:

```text
book.html
```

Then pass that to Pandoc.

### Stage 3 — asset and style handling

Add:

- EPUB-specific CSS;
- image/SVG path handling;
- validation for missing local assets.

### Stage 4 — complete hierarchy

Use the existing `index.html` tree to generate:

- full document order;
- correct heading depth;
- deterministic navigation.

### Stage 5 — production snapshot

Add:

- metadata;
- timestamp/version naming;
- EPUBCheck;
- concise export reporting.

## Expected production pipeline

The likely final pipeline remains small:

```text
Docs Viewer HTML export
          │
          ▼
prepare_epub.py
          │
          ├── parse index hierarchy
          ├── extract document content
          ├── normalize heading levels
          ├── rewrite internal links
          ├── normalize asset paths
          └── produce book.html
          │
          ▼
Pandoc
          │
          ▼
studio-docs-YYYY-MM-DD.epub
          │
          ▼
EPUBCheck
```

Pandoc remains the EPUB implementation.

Python remains only the adapter between the Docs Viewer HTML structure and Pandoc's logical-document model.

---

## Recommended position

Pandoc should be tested before implementing a dedicated EPUB library integration.

The existing system already has the hard part — the generated documents and their hierarchy.

The export problem is therefore not primarily:

> How do we construct an EPUB?

Pandoc already solves that.

The actual project-specific problem is:

> How do we present the existing HTML collection to Pandoc as one coherent hierarchical publication while preserving document identity, links and assets?

A small HTML preparation step is likely sufficient.

This keeps EPUB export simple, local and disposable: if the publication format or tool changes later, no EPUB-specific model becomes embedded deeply in the Docs Viewer architecture.
