# Filesystem Edit Timestamp Capture Delivery

## Status And Purpose

Proposed as FET-1 under
[Docs Viewer](/docs/?scope=studio&doc=d-20260424-000000-50b63f).

FET-1 closes one local-authoring gap: when the running live watcher observes a
direct filesystem edit to an existing canonical Markdown source, it advances
`last_updated` if and only if the body, `title`, or `summary` changed.

This is independent of Docs Import. New, Import, the managed Source editor, and
the metadata editor already own timestamps inside their mutation boundaries;
FET-1 does not insert the watcher into those paths or add format-specific
Import behavior.

## Complete Outcome

While the local watcher is running, an author can edit an existing parent-scope
or configured sub-scope Markdown file in VS Code and save it. After the normal
debounce, the watcher:

1. compares the previous and current parsed canonical source;
2. recognises only body, `title`, or `summary` as recent-edit content;
3. preserves a valid full `last_updated` already supplied by the author;
4. otherwise rewrites only the timestamp fields with one full local timestamp;
5. adopts its own source rewrite into the current watcher state; and
6. performs the existing affected-collection rebuild once.

The source file remains canonical. Builders continue to project source without
mutating it, and the watcher does not enter a self-triggered rewrite/rebuild
loop.

## Timestamp Contract

- The positive allowlist is the shared `recent_edit_content` comparison: body,
  `title`, and `summary`, with no second definition in the watcher.
- A change only to `parent_id`, `viewable`, `ui_status`, `group`, ordering,
  `added_date`, `last_updated`, filename, or other front matter does not qualify.
- The watcher acts only when one current document can be matched to one
  previous document with the same immutable `doc_id`. Rename-only changes do
  not advance the timestamp.
- If qualifying content changed and the current `last_updated` is a valid full
  timestamp different from the previous value, it is explicit author evidence
  and is preserved.
- Otherwise the watcher supplies a full `YYYY-MM-DD HH:MM:SS` local timestamp.
  It must be strictly later than the previous full timestamp; a same-second
  save uses the earliest representable later second without sleeping.
- One debounce batch captures one timestamp for all qualifying files so their
  write evidence is internally consistent.
- Existing `added_date` is preserved. If it is missing, the existing shared
  timestamp rewrite helper may restore it according to the current source-model
  rule; FET-1 adds no provenance inference.

New files are not silently repaired by this feature. Their creator or importer
owns initial identity and date metadata, and invalid or ambiguous source
continues through existing validation and error reporting rather than a
best-effort mutation.

## Watcher And Rebuild Contract

- The mutation occurs after a successful parsed comparison and before the
  existing docs/search rebuild for the affected collection.
- Parent scopes retain targeted affected-ID calculation and fallback behavior.
  Configured sub-scopes gain the same parsed previous/current comparison while
  retaining their confined rebuild owner.
- Timestamp rewriting is atomic and preserves unrelated raw front-matter
  spelling, quoting, ordering, comments, and body bytes.
- The watcher updates its file and parsed snapshots after its own rewrite so
  the next poll does not treat that rewrite as new author work.
- One author save batch produces at most one timestamp rewrite per qualifying
  document and one normal rebuild pass for the collection.
- If timestamp writing fails, the watcher reports the failure and does not
  present the timestamp as captured. The existing source remains available for
  correction and a later save/retry.
- If the source rewrite succeeds but the projection rebuild fails, the
  timestamp remains canonical source evidence. Existing rebuild retry behavior
  handles projection recovery without rewriting the timestamp again.
- Docs-management suppression markers remain the owner for New, Import,
  Source, and metadata writes. A fully suppressed managed batch is adopted
  without FET-1 comparison or mutation.

## Boundary

In scope:

- direct edits observed while the local watcher is running;
- existing top-level and configured sub-scope Markdown documents;
- the shared body/title/summary positive allowlist;
- valid manual timestamp preservation;
- atomic timestamp-only source rewriting;
- deterministic same-second advancement;
- self-write adoption and no-loop behavior; and
- focused source-model, watcher, parent-scope, and sub-scope evidence.

Not in scope:

- changes to ordinary, package, returned-package, or edited-review Import;
- changes to New, managed Source, or metadata-editor timestamp ownership;
- builder-side source mutation;
- edits made while the watcher is stopped, startup backfill, Git-history
  inference, or filesystem-mtime inference;
- automatic repair of new, malformed, duplicate, or identity-changing source;
- widening Recently Edited beyond body, `title`, and `summary`;
- timezone, timestamp format, or date-provenance migration; or
- production/public runtime behavior.

## Likely Authority

- `docs_source_model.py` retains the shared recent-edit comparison, timestamp
  validation, advancement, and raw-front-matter rewrite helpers.
- `docs_live_rebuild_watcher.py` owns observed previous/current snapshots,
  exact-document matching, batch timestamp choice, self-write adoption, and
  rebuild sequencing.
- `docs_write_rebuild.py` retains management-write suppression and collection
  rebuild ownership.
- Existing create, import, Source, and metadata services remain the exclusive
  timestamp owners for their managed mutations.
- The docs and search builders remain read-only consumers of canonical source.

## Completion Gate

FET-1 is complete only when a realistic running-watcher exercise proves all of
the following for both a top-level scope and a configured sub-scope:

- direct body, title, and summary saves advance `last_updated` exactly once and
  publish the edited result in one collection rebuild;
- a supplied valid full timestamp is preserved;
- non-qualifying metadata and rename-only saves do not advance;
- same-second qualifying saves receive deterministic later timestamps;
- managed New, Import, Source, and metadata writes remain single-owner and do
  not receive a second watcher timestamp;
- watcher-authored timestamp rewrites do not schedule another mutation or
  rebuild pass; and
- builders remain projection-only.

**Current state:** FET-1 is proposed. Stop before FET-1.0 implementation.
