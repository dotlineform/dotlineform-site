# Tag Registry

## Capability

`/studio/tag-registry/` maintains canonical tags: browse/filter, import,
create, edit, delete, and demote a tag into an alias.

Canonical identity has wider consequences than visible registry rows. Rename/delete/demotion can affect aliases and assignments, so the server planners own impact calculation and cross-file mutation.

## Workflow

```text
load registry + aliases + assignments
  -> filter/search or open mutation modal
  -> validate candidate ID/group/description
  -> preview destructive or cross-file impact
  -> confirm
  -> server planner + atomic apply
  -> reload canonical data + activity evidence
```

When the Local Studio tag service is unavailable, supported simple operations
produce manual JSON patch guidance. That is a fallback handoff, not a canonical
write or guaranteed multi-file transaction.

New Tag sends `{group, slug, description}` to the focused `/create-tag`
operation. The server constructs `<group>:<slug>`, rejects invalid or duplicate
identity before writing, owns timestamps, atomically appends one row, and
records `create-tag` activity. Server validation failures stay in the create
workflow; only service unavailability switches creation to manual patch mode.

## Durable Rules

- canonical IDs are `<group>:<slug>` and group must match the ID prefix;
- ordinary creation has its own single-record planner and API rather than
  registry-import semantics;
- imports support the modes implemented by the registry workflow; server validation remains authoritative;
- deletion and demotion must account for alias/assignment references;
- demotion replaces a canonical tag with an alias targeting selected remaining canonical tags;
- local-server mutations record one initiating action context in Admin activity.

Exact limits, import shapes, and effect payloads live in `tag_source_model.py`, focused planners, and tests.

## Code Map

- template/controller: `tag-registry.html`, `tag-registry.js`
- state/render/modal/import/save modules:
  `studio/app/frontend/js/tag-registry-*`
- HTTP boundary: `studio/app/server/studio/studio_tag_api/registry.py`,
  `studio_tag_api/promotions.py`
- planners: `studio/services/tags/tag_registry_mutations.py`,
  `tag_promotion_mutations.py`
- canonical source: `studio/data/canonical/tags/tag-registry.json`

The route root follows the shared Studio ready/busy contract. Import/edit modal
state is route mode; service availability reflects direct-write capability.

## Weak Spots And Change Method

- Manual patch fallback cannot safely reproduce every cross-file server mutation; keep its supported surface explicit.
- The controller remains a large coordinator even after state/render/workflow modules were split.
- Visible copy is code-owned in `tag-ui-text.js`, so it can drift from server
  terminology.

Change the domain planner and tests before the modal/controller. Add UI detail here only when it reveals a durable workflow or ownership boundary.
