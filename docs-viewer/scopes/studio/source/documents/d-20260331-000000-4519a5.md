# Tag Registry

## Capability

`/studio/tag-registry/` maintains canonical tags: browse/filter, create, edit,
delete, and demote a tag into an alias. The table presents each tag's ordered
document associations as current title links.

Canonical identity has wider consequences than visible registry rows.
Delete/demotion can affect aliases and assignments, so server planners own
impact calculation and cross-file mutation. Document associations are one-way
references and never make Tag Registry the owner of document lifecycle.

## Workflow

```text
load registry + aliases + assignments
  -> filter/search or open mutation modal
  -> validate candidate ID/group/complete doc_url draft
  -> preview destructive or cross-file impact
  -> confirm
  -> server planner + atomic apply
  -> project the response + record activity evidence
```

Manual patch guidance exists only for explicitly supported fallback paths such
as create and demote. Edit Tag document associations and destructive writes
require the Local Studio tag service.

### New Tag

New Tag submits `{tag_id, group}`. The server validates only the new candidate
and configured Analysis `tags` destination, allocates a fresh immutable
document ID, creates the source document, appends the registry row with its
canonical Analysis URL at `doc_url[0]`, rebuilds that exact child projection,
and records `create-tag` activity as one transaction.

Creation does not audit or repair unrelated registry associations. The
exclusive-create document write is the collision boundary and refuses to
overwrite an existing destination.

### Edit Tag

Edit keeps `tag_id` readonly while allowing the scalar group and complete
ordered `doc_url[]` draft to change together. A group change validates affected
alias constraints before the registry write.

The document editor:

- renders current document titles as linked pills in stored URL order;
- uses each pill's × to remove that exact association from the draft;
- keeps an Analysis-only title picker visible with a fixed four-row scrolling
  result area;
- fills the search field from one exact provider result and enables the
  adjacent + to append it; and
- saves the complete array atomically or discards all draft changes on Close.

The picker exposes no free-form URL or ID entry and excludes exact URLs already
in the draft. Equal visible titles are allowed because exact canonical URLs
remain the association identity. Tag Registry intentionally suppresses report
context in this compact picker; the committed provider record still retains
it.

A title pill and the table link resolve against Studio's configured public
preview base. An unresolved stored URL is shown as `Unavailable document`,
remains linked to its exact location, and can be removed. A successful edit
closes without echoing the verbose backend audit summary into the page; errors
and warnings remain visible.

The route displays `tag_id` directly; canonical rows do not have a separate
label. The Edit Tag modal uses the tag ID as its heading and exposes the four
group pills as a single-choice control. It has no disabled identity field or
duplicate current-group badge.

## Durable Rules

- canonical IDs are globally unique slug-safe names;
- registry rows use `tag_registry_v5` and contain exactly `tag_id`, `group`,
  `doc_url`, and `updated_at_utc`; they contain no tag-row `label` or
  `description`;
- `doc_url` is an ordered array of zero or more supported canonical
  repository-relative Docs Viewer URLs;
- exact URLs may be shared by several tags but cannot repeat within one row;
- URL order is preserved but does not imply document ownership, uniqueness, or
  synchronization;
- every tag has exactly one allowed scalar group, which is not part of the ID;
- stale URLs remain valid stored associations and are not inferred, repaired,
  or replaced from titles or current context;
- ordinary creation has its own focused planner/API and does not use registry
  import semantics or certify unrelated associations;
- deletion and demotion must account for alias/assignment references;
- deletion never deletes a linked document;
- demotion replaces a canonical tag with an alias targeting selected remaining
  canonical tags; and
- local-server mutations record one initiating action context in Admin activity.

Exact limits, request shapes, and effect payloads live in
`tag_source_model.py`, focused planners, and tests.

  `studio/app/frontend/js/tag-registry-*`

  `tag_promotion_mutations.py`

The route root follows the shared Studio ready/busy contract. Mutation modal
state is route mode; service availability reflects direct-write capability.

## Weak Spots And Change Method

- Provider titles depend on published document-location projections; a newly
  created or moved document is unavailable to the picker until the owning
  public projection is published.
- Stale association inspection is present, but there is no automatic repair or
  bulk link workflow.
- The compact Analysis-only picker can show equal titles without report
  disambiguation. That is accepted while collisions remain rare.
- There is no UI for reordering URLs or adding Library/Studio URLs, even though
  the canonical schema supports their configured canonical routes.
- Manual patch fallback cannot safely reproduce every cross-file mutation; keep
  its supported surface explicit.
- The controller remains a large coordinator even after
  state/render/workflow modules were split.
- Visible copy is code-owned in `tag-ui-text.js`, so it can drift from server
  terminology.

Change the domain planner and tests before the modal/controller. Add UI detail
here only when it reveals a durable workflow or ownership boundary.
