# Tag Registry

## Capability

`/studio/tag-registry/` maintains canonical tags: browse/filter, create, edit,
delete, and demote a tag into an alias. The table presents each Tag's complete
current document associations as ordered title links from the private TDL-1
projection.

Canonical identity has wider consequences than visible registry rows.
Delete/demotion can affect aliases and assignments, so server planners own
impact calculation and cross-file mutation. Document source owns association
membership and lifecycle. Registry owns only canonical Tag data and one
optional exact primary override.

## Workflow

```text
load registry + private associations + aliases + assignments
  -> filter/search or open mutation modal
  -> validate candidate ID/group or one explicit current primary replacement
  -> preview destructive or cross-file impact
  -> confirm
  -> server planner + atomic apply
  -> project the response + record activity evidence
```

Manual patch guidance remains only for New Tag. Primary writes, Delete, and
Demote require the Local Studio service because they validate current document
declarations.

### New Tag

New Tag submits `{tag_id, group}` and creates one Registry row. It creates no
document and no association; documents opt into existing canonical Tags from
their own Tag-fields editor.

### Edit Tag

Edit keeps `tag_id` readonly while allowing the scalar group and an optional
primary-document replacement. A group change validates affected alias
constraints before the Registry write.

The document editor:

- renders the complete current TDL-1 document list in exact canonical order;
- opens each current document from its pill label;
- exposes a hollow/filled accessible primary circle on every current pill;
- has no search, add, remove, reorder, or clear-primary control; and
- saves only an explicitly selected replacement through the atomic Registry
  mutation boundary.

No filled circle means no current primary is selected; later target resolution
uses the first displayed current document automatically. Clicking the filled
circle is a no-op, while clicking another circle replaces the stored primary.
A stale stored primary is shown as `Unavailable document — <doc_id>` with no
filled current circle until replacement or complete Tag deletion.

The route displays `tag_id` directly; canonical rows do not have a separate
label. The Edit Tag modal uses the tag ID as its heading and exposes the four
group pills as a single-choice control. It has no disabled identity field or
duplicate current-group badge.

### Semantic Token Destination

Docs Viewer **Add tag token** discovery reads a private generated projection of canonical Tag ID, aliases, group, and the currently resolved document. An alias finds the canonical row but never enters token identity. Source stores only canonical `tag_id` plus occurrence Title; it does not store group, alias, primary, or document identity.

The lookup uses a current associated Registry primary when present, otherwise the first document in the private canonical association order. An absent or stale primary returns to that first current association. After choosing the exact candidate, an unusable public location leaves the Tag unresolved; it never scans a later document. This resolution does not mutate Registry primary, document declarations, or lifecycle state.

## Durable Rules

- canonical IDs are globally unique slug-safe names;
- registry rows use `tag_registry_v6`, require `tag_id`, `group`, and
  `updated_at_utc`, and may contain one exact Analysis Tags
  `primary_document`; they contain no membership array, label, or description;
- exact document `tag_id` declarations own membership; the private association
  product owns ordering and presentation locations;
- a missing or unavailable primary is valid, and the editor offers replacement
  only from current associations;
- every tag has exactly one allowed scalar group, which is not part of the ID;
- ordinary creation has its own focused planner/API and does not use registry
  import semantics or create a document;
- deletion and demotion are blocked by current source associations before
  accounting for their accepted alias/assignment effects;
- deletion and demotion never rewrite or delete document source;
- demotion replaces a canonical tag with an alias targeting selected remaining
  canonical tags; and
- local-server mutations record one initiating action context in Admin activity.

Exact limits, request shapes, and effect payloads live in
`tag_source_model.py`, focused planners, and tests.

The route root follows the shared Studio ready/busy contract. Mutation modal
state is route mode; service availability reflects direct-write capability.

## Weak Spots And Change Method

- Studio display depends on the rebuilt private association projection; live
  primary writes and destructive guards independently re-read source.
- There is intentionally no Studio association repair, search, add/remove, or
  reorder workflow; association problems are fixed at the document.
- Stale primary identity is diagnostic state rather than an automatic repair
  trigger.
- Manual patch fallback cannot safely reproduce every cross-file mutation; keep
  its supported surface explicit.
- The controller remains a large coordinator even after
  state/render/workflow modules were split.
- Visible copy is code-owned in `tag-ui-text.js`, so it can drift from server
  terminology.

Change the domain planner and tests before the modal/controller. Add UI detail
here only when it reveals a durable workflow or ownership boundary.
