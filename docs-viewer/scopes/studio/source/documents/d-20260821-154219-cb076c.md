# iPad Lightweight Workflow

**Date:** 20 August 2026  
**Related proof:** `d-20260808-205416-9f6d6c` — *iPad Docs Viewer Installation And Proof*

## Purpose

- Background iSH,
- Shortcuts,
- CLI Services,
- Inbox for ChatGPT

The iPad does not need to reproduce the full desktop Studio environment.

A more useful role is:

> **capture → convert → ingest → package → sync**

with more complex organisation, curation, development, and publication left for the desktop.

This reduces mobile UI requirements while making the iPad a practical low-friction entry point into the dotlineform knowledge system.

It also creates another route for sharing material with ChatGPT: once material is ingested into the Git repository and pushed to GitHub, it can be inspected directly through the connected GitHub integration without separately uploading the same document into a chat.


## 1. Background iSH

The first iPad proof established that Docs Viewer can run locally in iSH and be used through Safari.

The main lifecycle constraint is that iPadOS can suspend or heavily deprioritise iSH when Safari is full-screen.

Observed behaviour:

```text
iSH visible
→ Python service continues running
→ Safari localhost requests complete
→ Docs Viewer navigation and managed actions work

Safari full-screen
→ iSH may stop executing
→ existing Safari content remains visible
→ new localhost requests may stall
→ restoring iSH to a visible window normally allows them to continue
```

A deeper suspension was also observed where the Python process survived but its HTTP listener on port `8776` was lost. In that state, the service had to be restarted.

### iSH background-running workaround

The iSH project documents a background-running workaround based on keeping `/dev/location` active:

```sh
cat /dev/location > /dev/null &
```

Source:

- <https://github.com/ish-app/ish/wiki/Running-in-background>

A cautious test procedure is:

```sh
cat /dev/location > /dev/null &
echo $!
```

Record the PID printed by `echo $!`.

Then test Docs Viewer with Safari fully full-screen:

1. load several documents;
2. use Search;
3. use Recent;
4. make a metadata change;
5. leave Safari full-screen for several minutes;
6. test `/health` again.

Stop the background process afterwards with:

```sh
kill <PID>
```

If this works reliably, full-screen Safari may become viable without keeping an iSH window visible.

The iSH wiki also describes configuring this through OpenRC, but that should only be considered after the manual mechanism has proved useful and stable.


## 2. iSH Shortcuts Integration

iSH does not expose a direct Apple Shortcuts action, but the iSH project documents a workaround using SSH.

Source:

- <https://github.com/ish-app/ish/wiki/Shortcuts-Integration-Workaround>

Conceptually:

```text
Apple Shortcut
    ↓
Open iSH
    ↓
wait briefly for SSH
    ↓
Run Script over SSH
    ↓
execute command inside iSH
```

This is relevant because many useful dotlineform operations do not require a large interactive UI.

Examples:

```text
Markdown → HTML
DOCX / HTML / Markdown import
create or return JSON document packages
rebuild a scope
validate generated outputs
check service health
restart a local service
stage media
copy or normalize files
```

For these tasks, Shortcuts can provide the native iPad interaction while iSH performs the underlying work.


## 3. Native iPad UI Outside iSH

A Linux shell inside iSH can provide command-line prompts and menus, but it is not the best place to implement native iPad file selection.

Apple Shortcuts can provide:

- Choose File
- Share Sheet input
- folders in Files/iCloud
- prompts and menus
- notifications
- opening iSH
- SSH command execution

This suggests a layered design:

```text
Files / Share Sheet
        ↓
Apple Shortcut
        ↓
iSH command
        ↓
thin shell wrapper
        ↓
existing Python service/library
        ↓
canonical output
```

The Shortcut should handle the iPad-native interaction.

The shell/Python layer should handle deterministic processing.


## 4. Thin Linux Wrappers Around Existing Python Services

The repository already contains service and library code for Docs Viewer operations.

The iPad should not gain a second implementation of those operations.

Instead, expose selected existing capabilities through a small command-line interface.

Possible commands:

```sh
dlf import document.docx --scope notes
dlf import notes.md --scope studio

dlf convert document.md --to html

dlf package-export d-20260808-205416-9f6d6c
dlf package-return returned-package.zip

dlf rebuild notes
dlf health
dlf server-start
```

The shell command should be a thin entry point, for example:

```sh
#!/bin/sh
exec python3 /root/src/dotlineform-site/tooling/ipad/dlf.py "$@"
```

The Python dispatcher should then call existing repository service functions.

The important rule is:

> **Do not reimplement import, rebuild, package, or mutation logic in the shell script or Shortcut.**

Those layers should only provide orchestration.


## 5. CLI Versus HTTP Service

There are two possible CLI patterns.

### Pattern A — CLI calls the running Docs Viewer HTTP API

```text
dlf import ...
    ↓
localhost:8776/docs/import-source
    ↓
existing service
```

Advantages:

- almost identical to the browser path;
- minimal new integration code;
- all validation remains in one HTTP contract.

Disadvantages:

- requires the long-running Docs Viewer service to be alive;
- inherits the iSH background/listener lifecycle problem.

### Pattern B — CLI calls the underlying Python service directly

```text
dlf import ...
    ↓
Python management/import service
    ↓
existing source write + rebuild pipeline
```

Advantages:

- one-shot operation;
- no dependency on Safari;
- no dependency on a persistent localhost listener;
- likely better for Shortcuts;
- easier to run as an isolated background task.

Disadvantages:

- requires a deliberate supported CLI entry point into the service layer.

For iPad automation, **Pattern B is likely the stronger long-term design**.

The browser and CLI can still share the same underlying Python services.


## 6. Example: iPad Import Shortcut

A future Shortcut could look like:

```text
Receive file from Share Sheet
        ↓
Choose destination scope
        ↓
Copy file into dotlineform staging/inbox
        ↓
Open iSH
        ↓
Run Script over SSH
        ↓
dlf import <file> --scope <scope>
        ↓
show result
```

Possible source apps include:

- Files
- Safari
- Mail
- ChatGPT downloads
- another document editor
- any app exposing a file through the Share Sheet

This may be substantially easier on iPad than navigating a full import modal for every operation.

The existing Docs Viewer import UI should still be tested first because it remains part of the formal iPad proof.

The CLI/Shortcut route becomes justified when it clearly reduces friction or avoids lifecycle/UI limitations.


## 7. One-Shot Processing Is a Good iPad Fit

Many dotlineform operations are naturally bounded jobs:

```text
input file
    ↓
conversion / validation
    ↓
output file(s)
    ↓
finish
```

Examples include:

```text
Markdown → HTML
HTML normalization
DOCX → Markdown/HTML
package export
package return parsing
JSON generation
search/index rebuild
small media conversion
validation
```

A one-shot CLI job only needs iSH to remain active for the duration of the operation.

This is a better match for iPadOS than unnecessarily keeping a local HTTP service alive all day.


## 8. Division of Work: iPad and Desktop

| iPad | Desktop |
|---|---|
| capture files | large-scale organisation |
| import documents | restructuring hierarchies |
| Markdown → HTML | bulk metadata editing |
| package export/return | detailed package review |
| simple metadata edits | complex metadata work |
| quick rebuilds | full test suite |
| reading/searching | development/refactoring |
| staging files | Git review and release work |
| Share Sheet workflows | publication |
| lightweight Git operations | heavy media/toolchain work |

The iPad therefore does not need a complete replica of Studio.

It needs a small number of reliable entry points into the existing system.


## 9. The Inbox Concept

A dedicated **Inbox** is a useful extension of this model.

The purpose would be to let material enter dotlineform without requiring an immediate decision about its final place in the hierarchy.

```text
external document
    ↓
Share / Import
    ↓
Inbox
    ↓
normalized canonical document
    ↓
later organisation on desktop
```

The guiding principle is:

> **Capture it, normalize it, identify it, and make it available. Organise it later.**

Possible implementation forms include:

```text
Docs Viewer scope:
    inbox

or

Docs Viewer sub-scope:
    studio / inbox
```

The exact location should follow the existing scope/sub-scope architecture rather than being added as an unrelated storage convention.

### Minimal Inbox metadata

An Inbox item might initially need only:

```text
doc_id
title
source/import provenance
added date
source format
optional source filename
basic ui_status
canonical body
```

It does not need complete classification at capture time.

Later desktop work can add:

```text
parent/hierarchy
tags
semantic tokens
cross-links
publishability
final scope/sub-scope
additional metadata
```


## 10. Inbox as a Share Sheet Destination

The Inbox becomes especially useful when combined with Shortcuts.

```text
File / webpage / document
        ↓
Share
        ↓
"Send to dotlineform Inbox"
        ↓
Shortcut
        ↓
iSH
        ↓
dlf inbox-add <file>
        ↓
canonical Inbox document created
```

The Shortcut could optionally ask:

```text
Title?
Keep original file?
Target scope?
Add note?
```

But the default should remain low-friction.


## 11. Inbox and ChatGPT

The Inbox also creates a useful path for sharing documents with ChatGPT.

### Local/private Inbox

```text
iPad
    ↓
Docs Viewer / CLI
    ↓
iCloud-backed external Inbox
```

This is useful for private/local working material.

It does **not** automatically make the material visible through the connected GitHub integration.

### Repository Inbox

```text
iPad
    ↓
Docs Viewer / CLI
    ↓
repository Inbox
    ↓
commit + push
    ↓
GitHub
    ↓
ChatGPT can inspect it through the connected repo
```

This removes the separate chat-upload step.

A conversation could then be as simple as:

> “I just put the new research document in the Inbox. Review it.”

ChatGPT can locate the repository material, inspect it, and work from the canonical version.


## 12. Import Versus Share

It may be useful to distinguish two explicit actions.

### Import

```text
dlf import ...
```

Meaning:

- ingest into dotlineform;
- normalize and rebuild;
- remain local unless already in a repository-backed scope.

### Share

Conceptually:

```text
dlf share ...
```

Meaning:

1. ingest;
2. rebuild;
3. show changed files;
4. optionally commit;
5. optionally push.

Commit and push should remain explicit.

A normal import should never silently publish material to GitHub.


## 13. GitHub as Shared Working Context

Once a document has been pushed to the repository, ChatGPT can use the connected GitHub integration to work with it directly.

The connected GitHub capability also supports focused repository changes, including:

- reading and searching files;
- creating branches;
- creating text files;
- updating existing text files;
- deleting files;
- committing changes;
- opening pull requests;
- reviewing and commenting on pull requests.

This makes a workflow possible where an Inbox item can move from capture to discussion to a concrete repository change without repeatedly moving copies between tools.

```text
iPad Share Sheet
    ↓
Inbox
    ↓
GitHub
    ↓
ChatGPT discussion
    ↓
focused branch
    ↓
implementation/documentation change
    ↓
draft pull request
```

Large cross-cutting refactors are still better suited to Codex or a full local checkout, but small bounded changes can be handled directly through the GitHub integration.


## 14. Possible `dlf` Command Surface

A future command might expose only operations that are useful outside the full UI:

```sh
dlf health

dlf inbox-add file.docx
dlf inbox-add notes.md

dlf import file.docx --scope notes
dlf import file.html --scope studio

dlf convert file.md --to html

dlf rebuild studio
dlf rebuild notes

dlf package-export <doc-id>
dlf package-return <package>

dlf server-start
dlf server-stop
dlf server-status
```

This should remain deliberately small.

It is not intended to replace Docs Viewer.


## 15. Three Interfaces to One Service Layer

```text
                    Python service layer
                           │
             ┌─────────────┼─────────────┐
             │             │             │
         Docs Viewer      CLI        Shortcuts
          rich UI      thin wrapper   iPad-native
```

### Docs Viewer

Best for:

- browsing;
- reading;
- search;
- metadata;
- hierarchy;
- visual inspection;
- interactive management.

### CLI

Best for:

- deterministic one-shot operations;
- scripts;
- debugging;
- automation;
- conversion;
- rebuilds.

### Shortcuts

Best for:

- Share Sheet input;
- Files integration;
- file pickers;
- prompts;
- quick actions;
- launching/waking iSH;
- running a CLI operation from ordinary iPad workflows.

No layer should duplicate the underlying business logic.


## 16. Immediate Next Experiments

### 1. Background-running test

Run:

```sh
cat /dev/location > /dev/null &
echo $!
```

Then test Docs Viewer in full-screen Safari.

Determine whether:

- document navigation works;
- Search works;
- Recent works;
- managed writes work;
- `/health` remains available after several minutes;
- the listener survives longer background periods.

### 2. Existing Docs Viewer import

Use the current Import UI to import one small disposable file.

Preferably test:

1. Markdown;
2. HTML;
3. later, a small DOCX with an embedded image.

This establishes whether the existing rich UI is already sufficient on iPad.

### 3. Identify CLI-worthy friction

Do not build a CLI because it is theoretically attractive.

Use the proof to identify operations that are actually awkward in the browser.

Those are the first candidates for `dlf`.

### 4. Prototype an Inbox

Once import behaviour is understood, define the minimum Inbox contract:

```text
where it lives
what metadata is required
what source formats it accepts
how items move out of it
whether it is repository-backed, external, or both
```


## 17. Design Direction

The emerging iPad strategy is not:

> “Make the entire desktop Studio fit onto an iPad.”

It is:

> **Give the iPad several low-friction ways to enter the same canonical service layer.**

That allows the iPad to be useful for:

```text
capture
conversion
ingestion
light editing
packaging
sync
sharing
```

while retaining the desktop for:

```text
organisation
curation
development
bulk work
publication
```

The Inbox can become the bridge between those two modes.

It also provides a natural bridge into AI-assisted work: once an Inbox item reaches the repository, ChatGPT and Codex can work from the same canonical material without another manual upload step.
