# Semantic Tokens

## Purpose

Extend the shipped semantic-reference path so a registered work, tag, asset, or
later supported object can be projected as ordinary text or media while retaining
its stable identity and queryable relationships.

The main implementation outcome is a durable, extensible registry and JSON
contract. Editor assistance and reports should remain small, focused projections
of that data rather than defining its complete shape.

This is planning direction, not implementation approval.

## Product Contract

A semantic token is an authored reference to a registered target plus a permitted
projection. The rendered result may look like an ordinary link or image, but its
source retains structured intent.

```text
registered target
    -> Add token assistance in the Docs Viewer source editor
    -> source token
    -> builder resolution
    -> ordinary rendered HTML + generated usage JSON
    -> Docs Viewer report and future JSON consumers
```

A manually authored Markdown link remains valid, but it carries only its literal
label and URL. A semantic token identifies the target, follows target-kind rules,
and can be reported without searching document prose.

## Registry Contract First

The canonical and generated JSON must be designed before widening the UI. The
contract should provide:

- a schema-versioned envelope and stable target identities;
- a small required core for target kind, title, ownership, and current
  representation or destination identity;
- typed optional metadata and registered-target relationships without making
  every conceivable field mandatory;
- room for media representations or variants without making provider paths the
  semantic identity;
- generated target lookup and relationship projections kept separate from
  canonical records and reproducible from them.

Consumers should request or derive the focused projection they need. A report
does not need to display every registry field merely because the field is
available to another report, build, or future consumer.

## One Docs Viewer Surface

Keep the existing composition:

- the Docs Viewer source editor owns authoring and the local source buffer;
- the Info panel searches registered targets and assists token insertion;
- the builder resolves supported projections and emits relationship artifacts;
- Docs Viewer reports reconcile registered targets, stored bytes, document usage,
  stale targets, and related data.

Do not create a separate route, asset portal, or management application for this
workflow.

## Targets And Projections

Canonical records remain with their domain owners. The semantic-token layer
provides common identity, projection, insertion, rendering, and relationship
contracts.

| target | example projections | example destinations |
| --- | --- | --- |
| Studio work | title, representative image | work page, associated Analysis document |
| Studio tag | title | tag document in the configured Analysis sub-scope |
| Scope asset | title, image, download | asset bytes, associated describing document |

The semantic-reference registry declares supported kinds and their capabilities;
it does not become the canonical store for every target record.

## Registered Assets

A scope asset needs a stable identity independent of its filename, storage
provider, or current served URL. A scope-owned JSON registry should hold the
canonical record, including the published object identity, a small stable core,
and optional typed metadata and relationships. The registry schema should make
future metadata possible without preloading the first UI or report with fields
that have no current use.

Every media object added through the source-editor UI should be registered
automatically. Registration is not an optional authoring choice:

- **Add image/file** publishes and verifies the bytes, creates the asset record,
  then inserts its semantic token;
- **Insert existing asset** searches registered assets and inserts another token
  for the selected identity.

If an author abandons the document edit after adding media, the result is a valid
registered but unused asset rather than unregistered bytes.

Document usage is derived from tokens rather than maintained manually in the
asset record:

```text
document -> embeds -> asset -> tagged-with -> tag:randomness
```

Storage inspection remains useful for reconciliation: registered bytes may be
available or missing, and bytes may exist without a registered record. It is not
the authority for deciding which assets exist as registered data objects.

## Focused Media Report

The intended steady state is complete registration:

- every stored scope media object has one registered asset identity;
- every displayed document usage refers to that identity through a semantic
  token rather than a manually authored path or link.

One focused built-in Docs Viewer report should join the scope asset registry,
configured filesystem or R2 inventory, and generated document-usage JSON. This
supports registration progress and practical troubleshooting; it is not the
primary authority or a general runtime health system.

| registered asset | stored bytes | document usage | report meaning |
| --- | --- | --- | --- |
| yes | yes | semantic token | fully registered usage |
| yes | yes | none | registered but unused |
| yes | yes | raw path or link | registered asset with unstructured usage |
| no | yes | raw path or link | used but unregistered media |
| no | yes | none | unregistered stored media |
| yes | no | token or none | registered asset with missing bytes |
| missing target | unknown | semantic token | dangling semantic relationship |

Unused is not independently an error. The first report should show only the
identity, registration, availability, and usage fields needed for this
reconciliation, with focused filters such as **Unregistered**, **Raw
references**, **Missing bytes**, and **Unused**. Tag- or metadata-specific reports
can read the same JSON later without widening this report.

## Work Needed

- [ ] Define the canonical registry envelope and target-record schema first:
      immutable identity, target kind, ownership, title, representations,
      optional typed metadata, relationships, and schema evolution.
- [ ] Define which JSON is canonical, generated, local-only, or safe for future
      consumers, and keep derived document usage out of canonical target records.
- [ ] Define one source-token contract for target kind, stable id, projection,
      destination, and occurrence-specific presentation data.
- [ ] Extend the semantic kind registry with declared target-source, projection,
      and destination capabilities without hardcoding kinds in route or editor
      controllers.
- [ ] Add focused target-source adapters for tags and assets, then include their
      safe records in the generated target lookup used by the Info panel.
- [ ] Extend source-editor assistance to select an existing registered asset or
      automatically register newly added media before inserting its token.
      Registration must not become an optional checkbox. Keep source writes and
      rebuilds in the existing editor workflow.
- [ ] Extend builder resolution beyond text links to supported text, image, and
      file projections while preserving typed rendering and sanitization rules.
- [ ] Emit stable generated JSON for document-to-target and target-to-target
      relationships, with an explicit missing or stale target policy.
- [ ] Add one Docs Viewer media report that reconciles registry records, stored
      bytes, semantic-token usage, and transitional raw references, then supports
      the smallest useful registration and usage filters.
- [ ] Reconcile existing path-based media tokens and unregistered stored bytes,
      and plan any migration without retaining two permanent media identities.
- [ ] Prove the JSON contracts, target resolution, source-editor integration, and
      focused report inputs without building an exhaustive runtime audit or
      validation matrix.

## Boundaries

- No separate semantic-token or asset-management route.
- No generic graph database, background crawler, or content-search dependency.
- No background registry-health process or broad runtime reconciliation regime.
- No universal report that exposes every available metadata field.
- No central replacement for the canonical Studio work, tag, document, or
  scope-asset owners.
- The Docs service may enforce JSON parseability, required identity fields, and
  safe reads or writes, but it surfaces registry data rather than judging its
  semantic completeness or continuously validating cross-record truth.
- No guarantee that a target exists forever; insertion confirms current
  availability, while generated reports expose later drift.
- No new projection becomes a registry entry alone: its target source, builder
  resolver, editor assistance, generated relationship data, and report behavior
  must be accepted together.

The existing [Semantic References Editor](/docs/?scope=studio&doc=d-20260623-180405-631ef4)
is the working text-link baseline. [Scope Media Management](/docs/?scope=studio&doc=d-20260720-100017-9855dd)
should be reshaped around registered assets rather than physical inventory before
an asset delivery is promoted.
