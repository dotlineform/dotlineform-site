# Semantic Tokens

## Purpose

Make semantic tokens a coherent manage-mode Docs Viewer feature rather than a
piece of source syntax an author must understand and maintain by hand.

Each accepted token family has:

- one clearly named source-editor toolbar action and discovery workflow;
- a modal that collects and validates the data needed to add it;
- an Info-panel view that recognizes and edits an existing occurrence without
  changing its identity;
- generated local relationship data and report behavior.

Catalogue is the first family. Its discovery modal helps an author choose among
Work, Series, and Moment targets without deciding the target type before
searching. Tag is a separate later family because it associates an abstraction
rather than a catalogue entity.

Every later token family needs its own specification and delivery document.

CT-P1 Catalogue creation and CT-P2 recognition, contextual Info, tolerant link
projection, and local usage data are accepted. CT-P3 broken-link repair,
migration, and pilot cleanup are implemented and awaiting final review.

## Validation Boundary

The add-token modal is the only semantic validation gate. It requires a current
lookup selection, validates the fields needed by that token kind, and inserts a
well-formed string.

Source Markdown remains directly editable, so save and rebuild never validate
the document's tokens. During rebuild, Docs Viewer opportunistically projects a
recognized string only when its configured lookup supplies a workable link. If
the string is malformed, unsupported, or unresolved, the builder leaves it as
ordinary source text and emits no semantic link or usage relationship. It does
not fail or warn merely because token-like text cannot be resolved.

Repair belongs to the existing manage-only [Docs Broken
Links](/docs/?scope=studio&doc=d-20260423-165116-e7f7e9) report. Its read-only
audit independently scans for semantic-token link failures, then opens the
owning source document so the author can remove the broken occurrence and add
the correct target through the modal. This diagnostic workflow does not turn
save or rebuild into validation.

The manage-only [Semantic Tokens
Report](/docs/?scope=studio&doc=d-20260726-181045-a7c2e1) lists resolved
occurrences from a selected scope's generated usage index and links each row to
its owning document. Broken Links remains the diagnostic surface for unresolved
occurrences.

## Feature Boundary

Semantic tokens are an integrated Docs Viewer capability:

- source-editor core continues to own the Markdown buffer, selection, dirty
  state, save, rebuild, and ordinary media insertion;
- the semantic-token layer contributes family-specific actions, modals, Info
  views, parsing, a token-definition registry, configured target projections,
  a derived usage index, and reports;
- canonical target records remain with their domain owners.

Generic core has no token-definition registry. Core **Add image** and **Add
file** save the media and insert ordinary Markdown links; they do not wrap those
links in semantic tokens.

The feature is manage-only. It adds no public token UI, token-definition
registry, usage index, token-aware runtime, or report.

The document builder may resolve a supported token to an ordinary anchor inside
a public document JSON payload. Its `data-semantic-token-*` attributes are inert
metadata; the public reader does not load the registry, lookup, usage index, or
token-aware runtime. Unresolved strings remain ordinary text.

## Design Gate

Design proceeds from the authoring decision to its representation:

```text
source-editor workflow
    -> token syntax
    -> family and target data structure
    -> integration and refactoring decisions
    -> Catalogue token delivery
```

The UI establishes when the author chooses meaning and which information helps
that choice. The syntax then records the selected concrete identity. The data
structure supplies discovery, configured projections, and usage data for that
workflow. If
required data cannot be entered, explained, inspected, or edited through the
modal and Info view, neither syntax nor token-kind definition is ready.

## Internal Order

1. Accept the Source Editor UI workflow.
2. Derive and accept the token syntax from that workflow.
3. Accept the family/target data structure and integration architecture.
4. Promote and implement the Catalogue Token Delivery as one vertical slice.
5. Write a separate specification and delivery before adding another family.
