# TE-5 — Default Presentation

## Status And Purpose

Stopped on 2026-08-04 by explicit product decision. This delivery will not proceed as part of [Table Enhancements](/docs/?scope=studio&doc=d-20260802-150245-4e7f85). Indexed documents continue to enter the ordinary rendered-document view, and an eligible table enters Content Detail through its explicit control. The proposal below remains as the decision record; reconsideration begins with a new explicit lifecycle decision.

TE-5 was sequenced after TE-4 but depended only on [TE-2 — Table Detail View](/docs/?scope=studio&doc=d-20260802-162149-3ba013) establishing the public-safe `content-detail` view, exact table targets, expanded-main layout, return context, and cleanup lifecycle.

The delivery lets an ordinary document declare that its one authored Markdown table is its preferred initial presentation. It is intended for dedicated child documents reached through a parent’s ordinary **More…** link, but it adds no special parent/child runtime relationship. Its defining requirement is a coordinated entry sequence: the reader must not see the normal document appear briefly and then resize or switch into Content Detail View.

## Complete Outcome

A public or Manage document with the validated presentation hint opens directly into the existing table Content Detail View from an ordinary document link, sidebar, search result, Recent result, direct URL, reload, history traversal, cold payload fetch, or payload cache hit.

The route and index metadata identify the intended presentation before document rendering begins. Docs Viewer projects the final expanded-main geometry while the destination is pending, prepares the ordinary rendered HTML outside the visible and accessible presentation, resolves its sole eligible table through the TE-2 adapter, and reveals the Content Detail table in one coordinated commit. No frame exposes the destination’s ordinary document before the detail view, and the visible panel does not change width after the table appears.

**Back to document** reveals the already-prepared destination document without another fetch or Markdown render and suppresses the authored default for that current document visit. Browser Back still follows ordinary route history, so a parent **More…** link can return directly to the parent without adding a detail-view history entry.

## Proposed Authoring And Projection Contract

The proposed scalar front-matter field is:

```yaml
viewer_content_detail: table
```

The proposed name is part of the TE-5.0 sanity check. The first contract accepts only `table`, requires exactly one eligible table in document-owned rendered HTML, and rejects unknown values or ambiguous documents during the Docs build. The field is projected into the index/tree document entry for preflight routing and repeated in the by-id payload for consistency validation. It is reader-safe and available to public and Manage composition.

The hint does not identify a table by heading, cell text, ordinal supplied by the author, or persistent ID. Build validation requires one authored Markdown table and implicitly projects the same `data-docs-content-detail="table"` eligibility marker established by TE-2; the author does not add a redundant `table-detail` comment. The single marked table is then registered from the existing rendered `content_html` by the TE-2 adapter. The parent uses a normal document link; link text such as **More…** is authoring choice rather than a new control.

## Indexed Documents Only

The initial delivery applies only to documents represented in the active scope’s ordinary Docs index. This is a routing and ownership boundary, not a claim that sub-scope document content can never use Content Detail View.

A sub-scope document is absent from the parent index and remains embedded detail owned by its `docs_subscope` report. The selected Docs Viewer document is still the indexed parent report, `subdoc` is report-owned URL state, and the child payload renders only after the report and its manifest have loaded. TE-5’s ordinary index preflight therefore cannot know the child hint or exact table target before the report presentation begins.

A later exception would need a separately delivered report-to-Content-Detail contract: project the hint in the sub-scope manifest, let the report preflight the selected child, hand off an exact `{scope, sub_scope, doc_id}` table target, preserve list/detail/filter state, and solve direct-`subdoc` no-flash entry. TE-5 does not infer this behavior from child front matter or scan dynamic report DOM.

## Flash-Free Rendering Sequence

The existing route flow normally selects `rendered-document`, clears the content mount for loading, inserts `content_html`, and then mounts document adapters. Reacting after that sequence would expose the ordinary document and cause a visible normal-to-expanded layout change. TE-5 instead requires the following sequence:

1. The router resolves the destination’s index entry and presentation hint before inspecting the payload cache or starting a fetch.
2. The document-view coordinator records a new visit generation, selects the final expanded `content-detail` layout, clears the previous document, and projects one inert pending body at the final geometry. It must not select or reveal `rendered-document` as an intermediate view.
3. A cached or fetched payload is passed through the existing Markdown-generated `content_html` path into a temporary non-visible preparation mount owned by the document lifecycle. The mount is excluded from focus, pointer interaction, live-region announcement, and the accessibility tree.
4. Before dynamic document extras mount, the TE-2 table adapter validates and registers the sole eligible table against the current document target and visit generation.
5. The coordinator commits the exact table target to the already-selected Content Detail View, replaces the pending body, and reveals the presentation. The expanded shell, toolbar position, and main-panel width are unchanged across that commit.
6. After the first visible commit, ordinary diagram or report extras remain unmounted unless and until the user chooses **Back to document**. Back completes the prepared rendered-document mount, mounts its applicable extras, restores ordinary panel state, focuses the invocation destination where valid, and marks the default suppressed for the current visit before revealing it.
7. Navigation, scope change, superseding payload request, build refresh, or disposal invalidates both the pending target and preparation mount through the existing request and document-mount generations.

Implementation may select an equivalent staging mechanism, but it must preserve these observable guarantees. A second visible document pane, persistent hidden reader, parallel view host, full duplicate application mount, or CSS-only late concealment after the document has painted is not acceptable.

## State, Failure, And History

- The authored default applies once per fresh document visit. Explicit **Back to document** suppresses it before the ordinary document is revealed, preventing an immediate reopen loop.
- The suppression state remains visit-local. Its implementation owner must support same-visit re-projection without becoming cross-document preference or persisted user state.
- Content Detail entry does not push or replace route history. The canonical document URL remains the child document URL, so browser navigation keeps ordinary document semantics.
- An unavailable view, stale generation, missing table, multiple tables, malformed payload, or adapter failure releases the pending state and atomically presents the ordinary document with an explicit error. It never selects an arbitrary table.
- Cold loads and cache hits use the same preflight and commit sequence; the cache path must not bypass the no-flash guarantee.
- Hash targets are incompatible with automatic table entry in the initial contract and must cause a defined ordinary-document fallback rather than applying an invisible scroll target.

## Current Seams And Scope Guard

The likely blast radius is document metadata projection, navigation preflight before cache/fetch, the TE-2 target and view/layout lifecycle, a temporary preparation state, and the visible/accessibility commit boundary.

If implementation introduces a second content mount as a durable reader, duplicates document extras, changes URL semantics, creates general per-document view routing, or cannot preserve one coordinated reveal, stop for review and split the result.

## Rough Delivery Steps

### TE-5.0 — Confirm Scope And Delivery

- [ ] Sanity-check the authoring hint and flash-free entry sequence against current metadata projection, cold/cache navigation, and the shipped TE-2 target/view model; resolve only contradictions that would change the outcome.
- [ ] Confirm the broad blast radius across build validation, navigation preflight, preparation/commit lifecycle, outer layout geometry, and accessible exposure.
- [ ] Confirm the deliverables: validated document hint, implicit table eligibility, shared cold/cache commit path, Back completion, focused no-flash evidence, and concise durable contract updates.
- [ ] Stop for review if the result crosses the scope guard above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, broad owners, deliverables, objective no-flash observation needed at completion, and stop condition. Stop before implementation approval.

### TE-5.1 — Project And Validate The Document Hint

- [ ] Add the accepted field to canonical document records and validate the supported value during Docs builds.
- [ ] Validate that the rendered document owns exactly one eligible pre-extras Markdown table; fail the build for zero, multiple, dynamic-only, or otherwise unsupported targets.
- [ ] Project the hint into the reader-safe index/tree entry and by-id payload and project the implicit table-detail marker onto its sole table without projecting unrelated management metadata.
- [ ] Add focused source parsing, validation, public/local projection, targeted-build, and generated-payload tests.

### TE-5.2 — Add Coordinated Default Entry

- [ ] Let the router pass the indexed presentation intent into navigation preflight before both payload-cache and fetch branches.
- [ ] Extend the existing coordinator and panel-layout lifecycle with the coordinated pending-to-content-detail commit; do not register another main view or route.
- [ ] Prepare the existing rendered HTML without visual or accessible exposure, then request the exact table target through the TE-2 adapter.
- [ ] Make the cached and cold paths share the same target validation, atomic reveal, cancellation, and fallback behavior.
- [ ] Implement **Back to document** completion and same-visit suppression before ordinary content is revealed, without adding a history entry or refetching the payload.
- [ ] Release preparation, target, listeners, and suppression state on the implemented lifecycle boundaries.

### TE-5.3 — Verify And Transfer

- [ ] Run focused build-validation and cold/cache preflight checks through the production owners changed, including Back completion and one representative failure fallback.
- [ ] Use an intentionally slow payload plus frame/geometry instrumentation to verify the defining no-flash and stable-geometry contract.
- [ ] Manually review representative direct and linked entry in public and Manage desktop readers, the public narrow case, and **Back to document**; add history, hash, theme, focus, or screen-reader cases only where the implementation changed those owners.
- [ ] Exercise ordinary-document entry through the shared path as the focused compatibility check.
- [ ] Update only the durable metadata or panel/view owner whose shipped contract changed.

## Not In Scope

- automatic detail presentation for multiple tables, a selected ordinal, diagrams, media, reports, search results, or arbitrary content kinds;
- sub-scope documents rendered as `docs_subscope` embedded detail; a future exception requires an explicit report-owned preflight and restoration delivery;
- a special **More…** component, inferred parent/child relationship, automatic summary-table generation, or source splitting;
- stable table IDs, table fragments, detail query parameters, shareable detail state, or a new route/history entry;
- reparsing Markdown in the browser, fetching another data source, lazy row loading, virtualization, or avoiding the full child payload download;
- persistent user preference, remembering Back across visits or sessions, or making Content Detail the route-wide default;
- a second visible or persistent hidden document reader, alternate panel, overlay, modal, or parallel view host; or
- managed resizing/CSV behavior owned by TE-3 or diagram migration owned by TE-4.

The completed [Table Enhancements feature](/docs/?scope=studio&doc=d-20260802-150245-4e7f85) owns the stopped decision. [Content Detail View Concept And Architecture](/docs/?scope=studio&doc=d-20260802-150246-bb3f88) owns the shipped explicit-entry presentation model.
