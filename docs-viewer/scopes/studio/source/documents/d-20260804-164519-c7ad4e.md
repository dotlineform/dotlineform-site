# SSP-0 — Projects Subject Assignment Foundation Delivery

## Status And Purpose

Proposed as a standalone prerequisite to [SSP-1](/docs/?scope=studio&doc=d-20260802-194426-087cfe), after [SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf). This delivery keeps the Info panel read-only while removing Projects subject assignment from the app-level **Edit metadata** form.

The current metadata modal combines universal document fields with a sub-scope customisation host used by Projects `folder_path`. The current Info view is passive but does not receive the exact active sub-scope document or understand authoring-subject state. SSC-1 first turns the current report-named extension seam into the single accepted sub-scope customisation contract. SSP-0 then adds a bounded Projects assignment aspect before SSP-1 adds `work_id` and `series_id`; it must not turn Info into an inline editor or add those fields to the generic metadata modal.

## Complete Outcome

On the local Manage route, `metadata-info` displays one compact read-only authoring-subject summary for the exact active `{scope, sub_scope, doc_id}` target. It may show None, Folder, Work, Series, malformed, conflicting, or unavailable evidence as supplied by the accepted source projection. It contains no form fields, picker results, save lifecycle, revision receipt, or write service. Public routes retain their current compact metadata policy and receive no private subject projection or management capability.

Only a sub-scope whose resolved `sub_scope_customisation` declares an assignable authoring-subject group offers the quick **Assign subject** action. `dotlineform/projects` is currently the only registered sub-scope intended to gain that capability. Availability is derived from the declared assignable field group rather than a separate boolean that could drift from the supported front matter. The action and modal never compare the active scope or sub-scope with those literal names. The action opens a focused modal; no subject field is edited inline in Info or through **Edit metadata**. The modal owns its option selection, value acquisition, confirmation, exact target, source revision, mutation feedback, and cancellation.

SSP-0 moves the existing Projects `folder_path` editor into that modal and initially supports **None** or **Folder** using the current source contract. SSP-1 later extends the same modal to the complete **None**, **Folder**, **Work**, or **Series** authoring group when it adds `work_id` and `series_id` meaning, normalized state, associations, and Manage cues.

An independent `analysis/works` copy retains a valid `work_id` or `series_id`, and Manage Info displays it read-only. Its resolved metadata projection understands those fields, but its configuration does not advertise the assignable authoring-subject capability. It therefore has no **Assign subject** action or quick-edit modal, so the copied subject is effectively locked through the normal UI. This is a workflow boundary rather than a build or publication constraint: an author may still deliberately edit canonical Markdown source, and a document remains saveable and publishable with no subject or unusable source evidence.

Analysis Tags `group` and future `tag_id` editing remain owned by the independent Tag feature. [TDL-0 — Tag Document Metadata Authoring Refactor Delivery](/docs/?scope=studio&doc=d-20260804-170901-b2e74c) removes the remaining Tag `group` exception from **Edit metadata** through its own configured modal. SSP-0 does not move Tags controls, create a cross-collection metadata editor, or make TDL depend on this delivery.

## Assignment Modal Reuse

The two subject value families reuse accepted interaction and normalization components rather than creating new discovery behavior:

- **Folder** accepts a Finder-copied absolute path or local `file:` URL, reusing the local-folder paste normalizer to confine it beneath the configured Projects base and store only the decoded portable relative `folder_path`. The pure resolver may be extracted from its current Source Editor owner so the modal does not import an insertion workflow.
- **Work** and **Series**, added in SSP-1, reuse the existing Catalogue target support, matching, and accessible picker-list components behind **Add catalogue token**. The subject modal writes only the selected canonical ID; it does not ask for token title text or insert Markdown.
- **None** explicitly clears the current subject fields through the same confirmed mutation.

The Info panel previously hosted Semantic Token search controls before catalogue discovery moved to the focused **Add catalogue token** modal. Subject assignment follows that accepted direction: Info reports the current value; the modal performs search, resolution, selection, and confirmation.

## Projects Subject Rules

The complete Projects modal presents one option group because all choices answer the same authoring question: what is this document about?

```text
None
Folder  -> paste and resolve a Finder URL/path
Work    -> search and select one canonical Work
Series  -> search and select one canonical Series
```

An explicit save writes the selected canonical field and removes the other subject fields. Existing malformed or conflicting source remains visible in read-only Info until the author explicitly opens the modal and resolves it; opening Info or opening/cancelling the modal never assigns precedence or repairs source.

The quick action is currently available only in `dotlineform/projects` because that resolved sub-scope contribution declares the assignable subject group. It is not activated by a literal collection-name comparison, inferred from the mere presence of a subject field, copied into `analysis/works`, exposed by public routes, or generalized to every collection. Read/display support and quick-assignment support remain separate capabilities.

## Delivery Discipline

This is a bounded Projects UI and mutation-foundation delivery. It consumes SSC-1's accepted Info, assignable-field-group, exact-target, and access-projection seams, then reuses the Projects customisation normalizer, local-folder resolver, management modal shell, revision receipts, atomic source mutation, and targeted rebuild seams. The browser action, modal, and service resolve availability and accepted fields from the exact sub-scope capability rather than branching on `dotlineform/projects`. It does not introduce a generic schema editor, editable Info contribution, unrestricted cross-collection assignment service, relationship framework, internal Info navigation, or public runtime capability.

SSP-0.0 is a short scope-and-spec sanity gate. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

## Delivery Steps

### SSP-0.0 — Confirm Scope And Delivery

- [ ] Confirm SSC-1 has accepted the unified `sub_scope_customisation`, read-only metadata, assignable-field-group, exact-target, and access-projection contracts; then sanity-check focused subject assignment, local-folder URL/path resolution, revision-safe mutation, generic metadata separation, and public isolation against current broad owners.
- [ ] Confirm the likely blast radius across hosted-view context, active sub-scope target projection, Projects report/detail contribution, management modal shell, folder normalizer, Projects mutation, targeted rebuild, and current metadata/customisation tests.
- [ ] Confirm the deliverables: read-only subject summary, Projects-only **Assign subject** action and modal, None/Folder assignment, generic-modal Projects cleanup, SSP-1 Work/Series extension seam, focused evidence, and durable Info/management documentation transfer.
- [ ] Stop for review if the outcome requires inline Info editing, a generic field-schema engine, broad application-state access, literal scope/sub-scope name checks, an unrestricted cross-collection write service, duplicated folder normalization, public subject controls, or Tag workflow changes.

**Checkpoint:** a concise sanity note confirms implementation fit, broad owners, blast radius, deliverables, risks, exact-target behavior, public isolation, and the SSP-1 handoff. Stop before implementation approval.

### SSP-0.1 — Add Exact Read-Only Subject Information

- [ ] Project the exact active managed-document target into `metadata-info`, including a sub-scope detail document rather than its parent report or currently selected index row.
- [ ] Render a compact read-only subject summary from explicit projected state without reparsing Markdown or hydrating write-capable services in the Info view.
- [ ] Project **Assign subject** action availability from the exact sub-scope's declared assignable subject group; prove the current Projects registration enables it while the Analysis Works read-only metadata projection, other collections, and public routes remain action-free.
- [ ] Preserve current outside-context view selection and the Info shell's view-agnostic hosting model.

**Checkpoint:** focused exact-target, wrong-target, subject-state, view lifecycle, Projects action eligibility, Analysis read-only, and public-isolation evidence passes. An independent code/diff review confirms Info remains a passive exact-document projection. Stop before SSP-0.2.

### SSP-0.2 — Move Projects Folder Assignment Into The Modal

- [ ] Add the focused Projects **Assign subject** modal with initial None/Folder options, exact target and source revision, confirmation, cancellation, and contained status/error behavior.
- [ ] Reuse or cleanly extract the existing local-folder resolver so a pasted absolute path or `file:` URL becomes the canonical portable `folder_path`; retain confinement and invalid-input behavior.
- [ ] Add a capability-restricted subject mutation that resolves the exact sub-scope configuration, accepts only its declared assignable subject keys, preserves revision conflict and atomic replacement, and triggers the exact required rebuild without a collection-name branch.
- [ ] Remove Projects `folder_path` rendering and payload handling from **Edit metadata** after focused equivalence evidence confirms the modal owner.
- [ ] Preserve a clear extension seam for SSP-1 to add Work/Series options using the existing Catalogue target search and picker components without changing Info into an editor.

**Checkpoint:** focused modal, capability registration, folder resolution, invalid/outside path, clear, cancel, stale revision, exact-target, atomic-write, targeted-build, generic-metadata independence, Analysis action absence, and public-boundary evidence passes. An independent code/diff review confirms current quick-assignment availability comes from the Projects capability declaration rather than collection-name logic. Stop before SSP-0.3.

### SSP-0.3 — Verify And Transfer

- [ ] Run focused service, browser-module, route-boundary, source-lint, generated-doc, search, and whitespace checks proportional to the changed contracts.
- [ ] Verify rendered-document and Markdown-source contexts, Projects and Analysis copies, no-subject and malformed states, unavailable management service, stale revision, cancel/clear behavior, and public read-only presentation.
- [ ] Perform the independent final code/delivery review and reconcile completion claims with exact evidence and omissions.
- [ ] Update [Info Panel](/docs/?scope=studio&doc=d-20260623-000000-c99cef), [Management Operations](/docs/?scope=studio&doc=d-20260519-202931-66c794), and the current Projects customisation owner with the shipped read-only projection, modal assignment, mutation, reuse, and public-isolation rules.
- [ ] Update SSP-1 to consume the accepted modal and read-only Info contracts before adding Work/Series assignment and associations.

## Completion Evidence

- Info displays exact current subject evidence without inline controls or write services.
- Only the currently registered `dotlineform/projects` assignable-subject capability exposes the quick **Assign subject** action and modal; the implementation contains no literal collection-name availability branch.
- Projects None/Folder assignment retains accepted portable path normalization through its focused mutation.
- **Edit metadata** no longer reads, renders, or submits Projects `folder_path`.
- `analysis/works` displays retained Work/Series subject information read-only and exposes no quick assignment action.
- Public routes retain their compact passive Info policy without subject metadata or management capability.
- SSP-1 can extend the Projects modal with Catalogue Work/Series search while leaving Info read-only.
- Tag group and Tag identity workflows remain outside SSP-0.
