# SSP-0 — Projects Subject Assignment Foundation Delivery

## Status And Purpose

SSP-0.1 is complete at its review gate as a standalone prerequisite to [SSP-1](/docs/?scope=studio&doc=d-20260802-194426-087cfe), consuming the completed [SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf). The accepted [SSP-0.0 sanity note](/docs/?scope=studio&doc=d-20260804-192419-9c2f64) keeps this delivery on the currently configured Projects None/Folder foundation, and the [SSP-0.1 checkpoint evidence](/docs/?scope=studio&doc=d-20260804-194710-24329a) records the exact read-only projection. SSP-1 owns Work/Series subject meaning and state projection; SSP-4 owns explicit creation and acceptance of the later `analysis/works` collection. Work is stopped before SSP-0.2, which moves Projects assignment out of the app-level **Edit metadata** form.

The current metadata modal combines universal document fields with a sub-scope customisation host used by Projects `folder_path`. The current Info view is passive but does not receive the exact active sub-scope document or understand authoring-subject state. SSC-1 shipped the single accepted sub-scope customisation contract. SSP-0 adds the `authoring_subject` `DocsSubScopeAssignableFieldGroup` before SSP-1 extends its server-owned fields with `work_id` and `series_id`; Info remains read-only and those fields remain outside the generic metadata modal.

## Complete Outcome

On the local Manage route, `metadata-info` displays one compact read-only authoring-subject summary for the exact active `{scope, sub_scope, doc_id}` target. SSP-0 supplies None or Folder evidence from the current Projects projection. SSP-1 extends the same passive view contract with Work, Series, malformed, and conflicting subject states after it owns those meanings. Info contains no form fields, picker results, save lifecycle, revision receipt, or write service. Public routes retain their current compact metadata policy and receive no private subject projection or management capability.

Only a sub-scope whose resolved definition declares `DocsSubScopeAssignableFieldGroup(group_id="authoring_subject", ...)` offers the quick **Assign subject** action. `dotlineform/projects` is currently the only registered sub-scope intended to gain that declaration. The server resolves it with `sub_scope_customisation_assignable_field_groups()` and the browser checks its projected ID with `hasDocsViewerAssignableFieldGroup()`; the concrete field names remain server-owned. The action opens a focused modal whose owners include option selection, value acquisition, confirmation, exact target, source revision, mutation feedback, and cancellation.

SSP-0 moves the existing Projects `folder_path` editor into that modal and initially supports **None** or **Folder** using the current source contract. SSP-1 later extends the same modal to the complete **None**, **Folder**, **Work**, or **Series** authoring group when it adds `work_id` and `series_id` meaning, normalized state, associations, and Manage cues.

SSP-4 explicitly creates and configures the later `analysis/works` collection when collection-aware Copy is delivered. That stage proves retained Work/Series metadata displays through the SSP-1 read projection while the collection advertises no assignable authoring-subject capability. SSP-0 neither creates that collection nor treats it as current acceptance evidence.

Analysis Tags `group` and future `tag_id` editing remain owned by the independent Tag feature. [TDL-0 — Tag Document Metadata Authoring Refactor Delivery](/docs/?scope=studio&doc=d-20260804-170901-b2e74c) removes the remaining Tag `group` exception from **Edit metadata** through its own configured modal. SSP-0 does not move Tags controls, create a cross-collection metadata editor, or make TDL depend on this delivery.

## Assignment Modal Reuse

The two subject value families reuse accepted interaction and normalization components rather than creating new discovery behavior:

- **Folder** accepts a Finder-copied absolute path or local `file:` URL, reusing the local-folder paste normalizer to confine it beneath the configured Projects base and store only the decoded portable relative `folder_path`. The pure resolver may be extracted from its current Source Editor owner so the modal does not import an insertion workflow.
- **Work** and **Series**, added in SSP-1, reuse the existing Catalogue target support, matching, and accessible picker-list components behind **Add catalogue token**. The subject modal writes only the selected canonical ID; it does not ask for token title text or insert Markdown.
- **None** explicitly clears the current subject fields through the same confirmed mutation.

The Info panel previously hosted Semantic Token search controls before catalogue discovery moved to the focused **Add catalogue token** modal. Subject assignment follows that accepted direction: Info reports the current value; the modal performs search, resolution, selection, and confirmation.

## Projects Subject Rules

The complete Projects modal presents one option group because all choices answer the same authoring question: what is this document about?

```text
None
Folder  -> paste and resolve a Finder URL/path
Work    -> search and select one canonical Work
Series  -> search and select one canonical Series
```

An explicit save writes the selected canonical field and removes the other subject fields. Existing malformed or conflicting source remains visible in read-only Info until the author explicitly opens the modal and resolves it; opening Info or opening/cancelling the modal never assigns precedence or repairs source.

The quick action is currently available only in `dotlineform/projects` because that resolved sub-scope contribution declares the assignable subject group. It is not activated by a literal collection-name comparison, inferred from the mere presence of a subject field, copied into `analysis/works`, exposed by public routes, or generalized to every collection. Read/display support and quick-assignment support remain separate capabilities.

## Delivery Discipline

This is a bounded Projects UI and mutation-foundation delivery. It consumes SSC-1's `DocsSubScopeAssignableFieldGroup`, exact-target, metadata, browser-composition, and access-safe capability projection, then reuses the Projects customisation normalizer, local-folder resolver, management modal shell, revision receipts, atomic source mutation, and targeted rebuild seams. The browser action, modal, and service resolve availability and accepted fields from the exact sub-scope definition and projected `authoring_subject` group. It does not introduce a generic schema editor, editable Info contribution, unrestricted cross-collection assignment service, relationship framework, internal Info navigation, or public runtime capability.

SSP-0.0 is a short scope-and-spec sanity gate. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.
