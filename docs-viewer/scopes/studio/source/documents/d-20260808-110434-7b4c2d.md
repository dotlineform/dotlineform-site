# SSP-7.2 — Lineage And New/Replace Copy Evidence

## Outcome

SSP-7.2 is complete. The one tracked private `docs_document_publication_lineage_v1` table now records exact `dotlineform/projects` A to `analysis/works` B relationships. The existing **Copy to…** workflow remains the only transfer path: a matching typed source/editorial customisation contract adds explicit per-source **New** or exact **Replace** choice, while every other Copy and Move route retains its prior behavior.

## Contract Proved

- The private table is a small schema-versioned row list containing exact identities, `created_at`, `last_copied_at`, and nullable reserved `publication`. The service checks the basic schema it needs, keeps writes stable, and leaves the table outside generated scope data and `site/`.
- A source with no available B takes New because no alternative exists. One or several available B rows block the first preview until the browser explicitly chooses New or one exact Replace target. Unavailable rows remain listed as unavailable and cannot be selected.
- The v3 receipt adds only the chosen per-source action and matching lineage contract to the existing Copy receipt. Replace re-resolves the selected exact current B by identity; it does not compare B content or bind the table or B bytes to concurrency digests.
- New retains the shipped fresh-identity transformation and adds a row only after the exact target rebuild succeeds. Replace is confined to one current exact A-to-B row and preserves B's filename, `doc_id`, collection placement, `parent_id`, `added_date`, and exact `publishable` representation while replacing source-derived body and transferable metadata and advancing `last_updated`.
- New and Replace use the ordinary per-file Markdown writers and existing targeted child rebuild. After it succeeds, the small lineage row list is updated. SSP-7.2 adds no multi-file rollback transaction, recovery rebuild, whole-table validation/digest, or lineage-specific partial-commit state.
