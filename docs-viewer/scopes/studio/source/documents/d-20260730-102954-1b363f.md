# Sub-Scope Returned Package Import Delivery

## Status And Order

Delivered as SRR-2 after both the completed
[Sub-Scope Returned Package Review Delivery](/docs/?scope=studio&doc=d-20260728-173227-bb7426)
and completed
[Sub-Scope Ordinary Document Import Delivery](/docs/?scope=studio&doc=d-20260730-121423-469e54).

SRR-1 proved that one complete returned package from an exact
`{ scope, sub_scope }` collection can reach faithful, immutable Docs Review.
SSO-1 first establishes one exact-collection Import control and shared ordinary
source target. SRR-2 then extends that workflow with one separately confirmed
path from an eligible returned JSON/JSONL package back to the same canonical
flat collection.

This is not a Save control in Docs Review and does not broaden ordinary
scope-level Docs Import.

## Complete Outcome

A local Manage `docs_subscope` report uses the compact 📥 **Import** icon and
exact mounted-collection workflow introduced by SSO-1. SRR-2 adds trusted
returned packages as a separate source type; it does not add a second report
button. Scope-level and sub-scope package Import share one sequential package
plan confirmation modal after the existing Import chooser.

The action:

1. freezes the mounted `{ scope, sub_scope }` collection;
2. lists only trusted returned packages that match that exact collection and
   explicitly support return Import;
3. previews one complete package against current canonical sources;
4. requires one package-level confirmation;
5. applies every accepted source update or none; and
6. rebuilds and refreshes only the owning sub-scope projection.

Import is a collection action. It never consumes checked IDs, the displayed
detail document, the parent report document, URL text, the latest staged file,
or the package currently open in Docs Review.

## Report Toolbar Contract

- The 📥 button remains the one local management contribution introduced by
  SSO-1, with **Import** as its accessible label and title. Public reports
  receive no control, service probe, or Import module.
- Import is a sibling toolbar control, not an item in the selection-owned
  Actions menu. Activating it does not enter selection mode, reveal checkboxes,
  or change checked IDs.
- The existing 🔧 Actions control keeps its current behavior: opening it enters
  selection mode and **Prepare package…** remains checked-ID-backed.
- Import availability remains independent of collection rows. SRR-2 adds
  package availability to the existing exact-collection Import surface without
  changing ordinary staged-source availability.
- Activating the button lazily loads a focused sub-scope package workflow using
  the exact mounted collection and restores focus to the same button on close.
- The package chooser shows file, configured collection label, and document
  count. It includes only packages whose trusted `scope` and `sub_scope` match
  the frozen collection and whose `supports_return_import` is `true`.
- **Preview collection** remains in the existing Import chooser. A successful
  preview closes or hides that chooser before opening one shared package-plan
  confirmation modal; the modals are sequential and never nested.
- Scope-level `{ scope }` package Import and sub-scope
  `{ scope, sub_scope }` package Import use that same confirmation modal and
  collection controller. Only their explicit validated target shapes differ.
- The confirmation modal contains the complete reviewed plan and a visible
  fixed footer with only **Cancel** and **Confirm import**. There is no
  **Back** control: Cancel closes the complete Import workflow and applies
  nothing; choosing another package requires reopening Import.
- No package is silently preselected from another route or workflow. Confirming
  Import always follows an explicit package choice and reviewed preview.
- Cancel applies nothing. Failure retains a safe retry path for the same frozen
  collection and never falls back to the parent scope.
- Success refreshes the report inventory and rendered detail from the confined
  sub-scope build. It does not open Source or change the main Index selection.

## Package Eligibility

Sub-scope Import is opt-in per configured collection. Analysis/Tags is the
first consumer; removing the current blanket blocker must not make every
configured sub-scope importable.

For an opted-in sub-scope:

| package profile | `supports_docs_review` | `supports_return_import` |
| --- | --- | --- |
| `document-content` | `true` | `true` |
| `document-tree` | `false` | `false` |

Trusted metadata must retain the exact `scope`, `sub_scope`, profile,
`selected_doc_ids`, and prepared source-version map. Returned rows must equal
the complete prepared ID set. Missing, extra, duplicate, malformed,
cross-collection, or capability-invalid records block the whole package.

Existing sub-scope packages prepared under SRR-1 remain review-only because
their trusted metadata says `supports_return_import: false`. They require
regeneration after SRR-2; there is no metadata migration or compatibility
fallback.

## Canonical Apply Contract

- Every returned ID must still identify one existing document in the frozen
  configured child collection. SRR-2 is overwrite-only: it does not create,
  delete, move, or rename documents.
- The configured collection remains flat. Non-empty returned hierarchy fields
  block Import rather than inventing or mutating `parent_id`.
- Returned title, summary, and document content may update. Canonical
  collection metadata not owned by the package—such as `group`, `ui_status`,
  `viewable`, immutable `doc_id`, and `added_date`—is preserved.
- Trusted prepared source versions are compared with current canonical sources
  during preview and again immediately before apply. Any stale target refreshes
  or blocks the plan and requires a new confirmation.
- Preview is write-free and exposes the complete planned document set. There is
  no record selection, skip, create/overwrite choice, or partial confirmation.
- Apply precomputes and validates every target before entering one confined
  write boundary. A source-write or rebuild failure restores the pre-apply
  source snapshot and reports no successful Import.
- The grouped terminal result is returned and presented directly. The shared
  scope and sub-scope package workflow creates no standalone result document,
  `results/` directory, result-path response field, or result-specific log.
- The existing sub-scope write/rebuild owner performs the confined projection
  follow-through. Parent Index, Recent, global search, and other collections
  remain unchanged.

## Ownership

- The SSO-1 sub-scope contribution retains ownership of the toolbar button,
  availability projection, and explicit mounted-collection request.
- The document-report management host retains validation of that request and
  lazy loading of the shared Import workflow.
- Existing returned-package listing and trusted validation remain the package
  discovery and whole-package identity owners.
- The document-package Import planner and normalized `ImportContent` boundary
  are extended with an explicit sub-scope collection target; a second parser or
  parallel document mutation model is not added.
- The sub-scope source write/rebuild service owns confined apply, rollback, and
  generated follow-through.
- The ordinary Docs Import modal, top-level collection planner, and Docs Review
  route retain their current behavior.

## Boundary

In scope:

- explicit per-sub-scope returned-package Import opt-in;
- exact-collection package listing, preview, confirmation, apply, and result;
- a returned-package source type inside the existing 📥 **Import** report
  workflow, still independent of checkbox selection;
- strict package capability, identity, membership, and flatness validation;
- overwrite-only title, summary, and content updates;
- stale-source revalidation and all-or-nothing source/rebuild behavior;
- retirement of the unused standalone result artefact across the shared scope
  and sub-scope package workflow;
- confined report refresh and focused service, module, route, and realistic
  acceptance evidence.

Not in scope:

- Docs Review Save, Import, or query-string handoff;
- public Import controls or local-service access;
- ordinary HTML, DOCX, Markdown, text, or media Import redesign;
- top-level package target, planning, or apply redesign;
- document creation, deletion, hierarchy, moves, `doc_id` changes, or partial
  package apply;
- Tag Registry reads, link repair, title synchronization, or group inference;
- automatically enabling other sub-scopes; or
- compatibility support for SRR-1 review-only package metadata.
