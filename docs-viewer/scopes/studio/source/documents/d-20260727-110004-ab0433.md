# Flat Tag Identity

## Result

A canonical tag has one globally unique normalized `tag_id` such as `moss` and
exactly one scalar `group` such as `subject`. The group is classification data,
not part of identity: `subject:moss` is no longer a canonical ID, and a
`groups` array is not supported.

Assignments and aliases continue to refer directly to `tag_id`. Group filters,
alias constraints, styling, coverage, and scoring resolve the tag's group from
the registry instead of parsing the ID. Interpretative meaning belongs in the
tag's document after
[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c);
that document does not create additional identities or group memberships.

## Why this is separate

Flattening identity changes canonical registry keys and every assignment and
alias that refers to them. It also requires verification that earlier
namespaced collisions have been resolved to one globally unique name and one
group. That is a coherent vocabulary migration, not part of document
association or group-based reporting.

The existing registry `description` remains available through this feature so
Tag-document linking can use it as one-time seed content. Removing that field
before the documents exist would discard the current semantic source.

## Boundary

- [Tag Vocabulary Import Retirement](/docs/?scope=studio&doc=d-20260726-214250-28ae69)
  removes obsolete bulk paths before this feature changes canonical identity.
- This feature owns flat IDs, collision-decision verification, reference
  migration, the one-group invariant, and removal of group-prefix parsing.
- It retains the group taxonomy, allowed-group policy, group-driven UI and
  analysis, and the current series/work assignment model.
- It does not create or associate documents, remove registry descriptions, or
  implement semantic-token targets.
- Tag-document linking follows this feature and establishes the required
  registry-to-document relationship.
