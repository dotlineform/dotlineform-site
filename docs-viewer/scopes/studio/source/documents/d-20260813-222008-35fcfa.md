# SM-2 — Docs Viewer Search Relevance Delivery

## Status

Proposed follow-on to the completed [All-Scope Full-Text Search Baseline](/docs/?scope=studio&doc=d-20260813-165124-16b0ab). No implementation is approved. SM-2.0 may inspect representative queries across the shared baseline and compare small ranking signals, then must stop for review so that only ideas which demonstrably help are retained.

## Purpose

Establish one modest relevance policy for Docs Viewer full-text scopes. Studio, Analysis, Notes, Processing, and Dotlineform now supply the common field baseline; any future evaluation should use representative evidence from the relevant complete scope corpora. Each scope supplies its own corpus statistics through the common static-index contract; no scope receives a custom vocabulary, tokenizer, or search algorithm.

[Docs Viewer Search Relevance](/docs/?scope=studio&doc=d-20260813-223337-e6c261) owns the proposed shared model, language and specialist-vocabulary reasoning, candidate signals, diagnostics, presentation options, and non-goals. This delivery owns only the gated comparison, implementation, review, and closeout sequence.

## Current Baseline

The shared v2 query path intersects every query term and gives each matching document one categorical score. Studio's active tiers are exact full title 900, title 800, heading 700, and body or code 400. Within a tier, results are ordered by title and then document ID.

Postings record only that a term occurs in a document field. They do not record occurrence count, document length, positions, phrase proximity, or which prefix expansion was the strongest match. One body occurrence and ten body occurrences therefore rank equally.

Body and code retrieval are principal reasons full-text search exists, so a body-only result must not be presented as inherently low relevance. A field tier describes where a match occurred, not how useful it is for the user's intent.

## Boundaries

SM-2 may change v2 generated ranking data, the shared Docs Viewer query scorer, and compact result presentation only when a selected signal requires them. The same algorithm must apply to every full-text scope using statistics generated from that scope's complete eligible corpus; do not add scope-name branches. DSI-2 owns parent/sub-scope corpus composition, structured child navigation, and collection context, so SM-2 must not absorb that work.

SM-2 does not add stemming, synonyms, typo correction, embeddings, semantic or remote search, click analytics, query logging, personalisation, popularity scoring, positional phrase search, result snippets, highlighting, section-level results, or a generic ranking framework. It does not change Catalogue Search.

## Delivery Steps

### SM-2.0 — Representative Query And Signal Review

- [ ] Select a small set of known-item, heading, body, code, short-prefix, and broad body-only Studio queries, including the observed `reg` case; define the corresponding combined Analysis parent/sub-scope domain-query categories without inventing unavailable corpus evidence.
- [ ] Record the current field tier and tie order for representative results; identify actual weak ordering rather than treating result count alone as failure.
- [ ] Compare exact-token preference, inverse document frequency, and capped frequency independently, with length normalisation only if the frequency comparison exposes a credible long-document bias.
- [ ] Confirm names and specialist terms are handled through shared tokenisation plus corpus statistics rather than scope dictionaries or curated term lists.
- [ ] Measure any proposed generated-payload increase and identify the smallest affected builder, schema, scorer, and focused-test seams.
- [ ] Recommend one signal, a smaller presentation-only follow-through, or no change.

**Gate:** Present the representative before/after order, payload cost, exact proposed owners, and rough production/test diff. Stop for explicit approval before changing production code, the generated index contract, or the UI.

### SM-2.1 — Selected Minimal Ranking Change

- [ ] Implement only the signal approved at the SM-2.0 gate.
- [ ] Preserve all-term intersection, one result per document, deterministic ordering, and the accepted title → heading → body/code field priority unless the gate explicitly changes one of those contracts.
- [ ] Keep exact-token, frequency, normalisation, and multi-field rules in one shared scorer contract rather than distributing ranking logic across the builder and controller.
- [ ] Rebuild only the affected Docs Viewer search projections and confirm the shared policy does not create scope-name behavior or change Catalogue Search.

**Gate:** Present focused generated-query evidence and the measured payload delta. Stop for user review before presentation work or code review.

### SM-2.2 — Optional Result Explanation

- [ ] Add no relevance badge by default.
- [ ] If user review shows that the selected order still needs explanation, test the smallest factual presentation: match-source label, tier divider, or aggregate tier counts.
- [ ] Keep the existing relevance order; do not add alternate sorting as incidental follow-through.
- [ ] Leave visual and interaction acceptance to the user; do not add or run a browser check unless explicitly requested.

**Gate:** Stop for direct user feedback on whether the results are both useful and understandable.

### SM-2.3 — Code Review And Closeout

- [ ] Review the bounded scorer, generated-data, query, test, documentation, and optional presentation diff.
- [ ] Check for repetition bias, long-document bias, prefix regressions, scope-name branching, payload growth, rank instability, and duplicated scoring logic.
- [ ] Transfer settled behavior to the durable Search Index, Tokenizer, and Search Relevance documents; keep delivery evidence in this Roadmap record.
- [ ] Run only the focused accepted checks and stop for explicit closeout approval.

**Gate:** Present review findings, resolutions, final scope, and remaining limitations. Stop for explicit closeout approval.
