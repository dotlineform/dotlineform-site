# TE-2 — Table Detail Eligibility Directive Delivery

## Status And Purpose

Proposed as **TE-2**, after [TE-1](/docs/?scope=studio&doc=d-20260802-163320-9015b0) provides convenient comment insertion, and required before TE-3 table integration. [Authoring Directives Concept And Examples](/docs/?scope=studio&doc=d-20260802-160429-69a5f6) owns the exact-comment, next-table, working-source, projection, and harmless no-op boundaries implemented by this delivery.

TE-2 adds one deliberately small consumer: an author marks an exact Markdown table as eligible for Content Detail View. The build recognises that exact comment immediately before a table and annotates the rendered semantic table. Every other comment is ignored, and the browser never parses comments or decides whether a table is large enough.

## Complete Outcome

The initial source form is:

```markdown
<!-- dotlineform:table-detail -->

| Project | Folder | Series |
| --- | --- | --- |
| Nerve | projects/nerve | Series 105 |
```

Canonical Markdown and Markdown export retain the comment. Supported rendered payloads contain the same semantic table with `data-docs-content-detail="table"`; retaining the ordinary invisible HTML comment is acceptable. Unmarked tables receive no marker and therefore no **Open table** control.

The document-level `viewer_content_detail: table` contract remains owned by TE-6. Its independent build behavior projects the same marker onto the sole eligible table without requiring a redundant comment. If another comment intervenes between `table-detail` and the table, `table-detail` simply does not associate and has no effect.

## Current Seams And Scope Guard

The likely blast radius is the Markdown build path that associates source comments with tables, projects rendered item payloads, and preserves export/public-local parity. TE-3 separately owns the runtime adapter that consumes the projected marker.

If implementation requires a central directive parser, diagnostics framework, browser parser, Markdown AST replacement, source mutation, or another consumer’s runtime behavior, stop for review and split the result.

## Rough Delivery Steps

### TE-2.0 — Confirm Scope And Delivery

- [ ] Sanity-check the specified comment shape, next-table association, projected marker, and ordinary fallback against the current Markdown build path; resolve only contradictions that would change the outcome.
- [ ] Confirm the broad blast radius across source recognition, rendered payload projection, and export/public-local parity, with runtime presentation remaining TE-3-owned.
- [ ] Confirm the deliverables: exact recognition and association, one projected marker, focused evidence for the changed build contract, and a concise durable authoring/payload update.
- [ ] Stop for review if the result crosses the scope guard above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, broad owners, deliverables, and stop condition. Stop before implementation approval.

### TE-2.1 — Recognise, Associate, And Project

- [ ] Recognise only the exact maintained comment without interpreting ordinary HTML comments or attempting to classify malformed lookalikes.
- [ ] Associate it with one immediately following source Markdown table through maintained renderer/source-position seams rather than matching rendered HTML.
- [ ] Project only `data-docs-content-detail="table"` onto the associated semantic table without requiring comment removal.
- [ ] Preserve canonical Markdown, Markdown export, table cell HTML, links, alignment, headings, captions, unrelated authored attributes, and ordinary rendering for every no-op case.
- [ ] Apply the same marker independently for the TE-6 document-default case; if its own validation does not apply, leave the ordinary document unchanged through that feature’s fallback.

### TE-2.2 — Verify And Transfer

- [ ] Run the smallest focused builder checks that prove exact association, marker projection, and representative ordinary fallback through the production path actually changed.
- [ ] Inspect a representative generated payload or export only when that projection changed or its freshness is uncertain; let expected watcher output stand. Add broader builds, search checks, lint, or diff checks only for a concrete failure they can catch.
- [ ] Update the concise Markdown authoring and payload contracts, then hand the projected marker to TE-3 without implementing Content Detail runtime behavior or a directive diagnostics system here.

## Not In Scope

- scanning table size, overflow, row count, headings, or viewport state;
- adding **Open table**, Content Detail lifecycle, cloning, layout, toolbar, or Back behavior owned by TE-3;
- table-to-SVG comment recognition, rendering, manifests, media, or public replacement owned by TE-7;
- the Source toolbar action for inserting comments, already owned by [TE-1](/docs/?scope=studio&doc=d-20260802-163320-9015b0);
- validation or reporting for unknown, malformed, misplaced, duplicate, contradictory, or unsupported comments;
- a general directive registry, reserved-name catalogue, runtime comment metadata, or browser comment parser;
- applying directives to dynamic report/component tables or arbitrary HTML; or
- stable table URLs, IDs, occurrence numbers, or persistent runtime identity.

The [Table Enhancements feature](/docs/?scope=studio&doc=d-20260802-150245-4e7f85) owns the sequence. [TE-3](/docs/?scope=studio&doc=d-20260802-150247-b5dffe) begins its table integration only after TE-2 supplies exact marker projection and focused evidence.
