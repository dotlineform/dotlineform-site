# SSP-2.0 — Project State Sanity Note

## Outcome

SSP-2 fits the shipped SSP-1 subject products, canonical catalogue readers, local Docs Viewer report mechanism, exact local-folder links, and generated-product writers as one Project-specific producer plus one versioned lookup. The existing owners support the specified report and lookup without a reporting framework, generic graph, event bus, repair system, catalogue-reader replacement, result cache, or image-audit migration. The checkpoint is complete at its review gate and stopped before SSP-2.1 approval.

**Subsequent closeout:** this note preserves the accepted SSP-2.0 planning evidence. Resolver Tokens were later retired before implementation, SSP-3 became **Insert subject link**, and SSP-2.6 subsequently removed the persisted lookup that no longer had a consumer.

The sanity pass resolved one row-boundary contradiction. Project State rows are the immediate project directories under `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`. Nested directories remain contents of their owning project row. The Work projection reads only `work_id`, `project_folder`, and `series_ids`; `project_subfolder`, `project_filename`, and exact media resolution remain catalogue/media organization. This matches the 206-row planning snapshot, all 193 current Folder association keys, and the existing Studio audit's default scan boundary. A recursive walk currently finds 484 directories and would turn 278 internal directories into additional project rows.

## Closeout Note

SSP-2.4 superseded this sanity note's tentative post-commit follow-through plan and correctly closed without Studio or Docs mutation hooks. Its transfer of consumption-time freshness to SSP-3 is now historical: the consumer proposal was retired, so no build refreshes Project State.

## Accepted Inputs And Scheduling

SSP-1 is complete and currently publishes matching `subject_generation` receipts in the private Projects Manage manifest and `docs_subject_associations_v1` product. The observed generation contains 241 documents, 193 exact Folder keys, and 194 total subject associations. Project State consumes only the 193 Folder associations whose exact key matches the immediate-child scan.

The current canonical inputs contain 1,940 Works and 143 Series. Every Work has `project_folder`; the current direct-project inventory matches 144 Work folder keys, including two folders with Works in more than one Series. Eight Works currently use `project_folder: wa` with `project_subfolder: ink`; all eight physical images are present below `projects/wa/ink/`, and all eight retain the `projects/wa` Project State relationship because `project_subfolder` is absent from the Project State key and input projection. Their Series `140` membership is then counted from `series_ids`. Work identity and current `series_ids` remain explicit in Project State, while catalogue status, media filenames, and presentation URLs retain their existing catalogue owners.

At this checkpoint, the proposed SSP-3 depended on the versioned folder lookup accepted in SSP-2.1 and the planned closeout transferred one relevant-build refresh instead of adding committed-mutation hooks. That dependency was subsequently retired as recorded above. The Folder-first report remains an independently useful SSP-2.2 checkpoint; Series grouping, search, sorting, and clipboard transforms remain SSP-2.3. The current image audit remains SSP-6-owned.

## Timing And Mount Decision

On 2026-08-05, eleven read-only trials over the real immediate-child inventory returned 206 rows with a 0.725 ms median and 0.934 ms maximum scan time. Seven read-only trials that scanned those rows and loaded the current Manage manifest, subject associations, Works, and Series inputs took a 10.767 ms median and 12.464 ms maximum. These are warm local measurements of the bounded inputs rather than an implemented producer benchmark.

Automatic run-on-mount is suitable at the observed scale. SSP-2.1 retains deterministic validation and atomic lookup publication as the likely material work; SSP-2.2 must recheck end-to-end run timing before accepting mount behavior.

## Current Owners And Blast Radius

- The Projects sub-scope builder owns the private Manage manifest, normalized authoring subjects, matching generation receipt, and exact subject associations. SSP-2 reads those generated products as one generation.
- Canonical catalogue source readers own Work and Series identity. SSP-2 builds a focused independent join and retains semantic identities rather than copying catalogue titles, URLs, or status into the lookup.
- The local report registry, allowlisted loader map, report service, and ordinary document metadata own report mounting. SSP-2 adds one registered local report and one focused service operation through those seams.
- The local-link service owns normalized `projects/<project-directory>` activation. Exact Docs Viewer document targets and Semantic Tokens catalogue targets retain link composition.
- Existing source-write/rebuild and catalogue commit paths retain canonical mutations without Project State hooks. The checkpoint's proposed SSP-3 build refresh was subsequently retired; no build now consumes the derived lookup.
- The public report projection currently carries public report entries only. The Project State host, input products, lookup, service operation, and folder activation remain in Manage/local products.

The broad blast radius therefore covers immediate project-folder inventory and reconciliation, canonical Works/Series reads, matching Projects products, one versioned lookup and stale marker, report registry/loader/service composition, the live Folder/Series/Docs response, browser projections and clipboard transforms, exact local/document/Series links, committed Work and Project-document impact classification, focused evidence, and concise durable owner updates.

## Risks And Required Evidence

The principal risks are joining mismatched subject generations, allowing recorded-only paths or nested directories to establish rows, making a document mediate the Work join, double-counting multi-Series Works, copying catalogue presentation into the resolver lookup, returning live rows from a partially published generation, replacing a complete lookup after failure, and making a canonical mutation depend on derived follow-through.

SSP-2.1 must prove immediate-child inventory ownership, Project-document exact-key joins, Work keys projected solely from `project_folder`, subfolder-resident Work retention, no Project State impact from `project_subfolder` or `project_filename` changes, receipt agreement, semantic Work/Series retention, multi-Series counts, deterministic ordering, validated live/lookup generation, stale-state retention, and public isolation. Later checkpoints retain their delivery-owned report, browser-projection, interaction, and mutation evidence rather than expanding SSP-2.1.

## Stop Condition

Stop before or during implementation if the outcome requires recursive project rows, a detail-level `project_subfolder` report, another report mechanism, a generic relationship graph or query service, an event bus, automatic repair, a rewritten catalogue reader, persisted report presentation, a result cache, public Project State products, or partial migration of the Studio image audit. Any such result changes the accepted boundary and requires a separate review.
