# Sub-Scope Index

## Result

A configured one-level Docs Viewer sub-scope can use `docs_subscope` as its
canonical collection index without adding its documents to the parent scope's
Index, Recent, global search, or scope selector.

The shared report retains public list/detail navigation and `subdoc` URL state.
Manage mode may contribute a deliberate subset of the main Index capabilities,
including document-state icons, collection-local checkbox selection,
selection-backed actions, and validated detail-document controls.

The Analysis `tags` collection is the first substantial consumer and review
surface. The feature itself is generic and contains no Tag Registry behavior.

## Why This Is A Separate Feature

[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c)
owns creation-time association between one tag registry record and one
independently managed document. It does not own later document navigation,
selection, deletion, package export, or other collection management.

[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65)
delivered explicit-target source and metadata editing for a displayed sub-scope
document. This feature starts from that shipped boundary and gives the
collection itself a coherent generic index and action model.

## Shipped Baseline

- `docs_subscope` owns manifest/inventory-ordered list state, `subdoc`
  navigation, validated detail loading, and embedded detail rendering.
- Public mode reads the minimal public manifest.
- Manage mode reads a compact local inventory containing `doc_id`, title,
  `ui_status`, and `viewable`.
- The existing Status and non-viewable icons already render from that local
  inventory.
- The management host can edit source and metadata using an exact
  `{ scope, sub_scope, doc_id }` target.
- Sub-scope documents remain independently canonical and excluded from the
  parent scope's main discovery payloads.

## Boundary

In scope:

- treating `docs_subscope` as a collection index rather than a tag-specific
  report;
- one collection identity shared by browser state and applicable services;
- optional manage-only list and detail control contributions;
- collection-local checkbox selection with checked IDs as the only selection
  action target;
- explicit adoption by functions that can truthfully operate on a sub-scope
  collection or document;
- unchanged public read-only behavior and management-module isolation; and
- focused delivery slices for validated detail deletion and sub-scope package
  export after the architecture is accepted.

Not in scope:

- Tag Registry creation, editing, deletion, association repair, or
  synchronization;
- making sub-scopes top-level selectable scopes;
- merging sub-scope documents into the parent Index, Recent, or global search;
- making every scope-level function automatically accept a sub-scope;
- turning all report types into workflow hosts;
- public management controls or local service access; or
- returned-package review/import without a separately complete sub-scope
  contract.

## Likely Delivery Split

1. Establish the collection target and manage-only report contribution
   contract while preserving the public import boundary.
2. Add exact sub-scope document deletion from the validated detail header.
3. Add collection-local selection and an export-only Prepare Package adoption.

Each outcome should be reviewed as its own delivery. Filtering, search,
responsive refinement, bulk deletion, and further function adoption remain
separate decisions rather than implied completion criteria.
