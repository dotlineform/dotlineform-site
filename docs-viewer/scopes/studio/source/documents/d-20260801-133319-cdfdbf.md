# PRJ-4 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **PRJ-4** after [PRJ-3](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) independently publishes the versioned Project State folder lookup.

This delivery lets an author insert one explicit folder reference and render that folder's current Series and Project-document relationships at build time. It establishes a reusable bounded resolver capability without creating a global graph or extending Semantic Tokens beyond identity-link presentation and usage evidence.

## Complete Outcome

A managed document can contain a validated Resolver Token whose subject is one exact base-relative Project folder key. Building that document performs one exact Project State lookup read and renders deterministic groups:

```text
folder -> Series[] + Project documents[]
```

The source token remains unchanged. Zero matches, unavailable lookup, stale generation, and invalid subject states render explicitly. Expansion never scans the filesystem, Projects Manage manifest, canonical Works, canonical Series, tags, Moments, or another relationship registry.

Every Series result carries the semantic identity `(catalogue, series, canonical id)` from Project State and renders through the existing Semantic Tokens target lookup and link projector. The resolver does not carry or emit a plain catalogue URL and does not fabricate Semantic Token syntax in source. Every successfully rendered Series link creates one resolver-derived semantic usage row at the containing Resolver Token occurrence. Project-document results retain exact Docs Viewer target identity.

## Source And Usage Examples

The reader-facing Series link can be equivalent in all three cases. Source and generated usage evidence distinguish how it came to exist.

### Manually Authored Markdown Link

```md
[nerve](/series/?series=105)
```

This is an ordinary authored URL. The Markdown renderer produces an anchor, but there is no semantic identity in source and no semantic usage row.

### Authored Semantic Token

Using **Add catalogue token** inserts:

```md
[[catalogue:series:105|nerve]]
```

The builder resolves `(catalogue, series, 105)`, renders the current semantic destination, and records one authored-token usage row at that exact source range.

### Resolver-Generated Semantic Link

The exact Resolver Token syntax is a PRJ-4.0 decision. Until then this source is illustrative only; the angle-bracket value is not proposed serialization:

```md
[[resolver:<project-resolver-id>:folder:projects/nerve]]
```

The exact Project State row may contain:

```json
{
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

The builder passes that descriptor through the shared semantic target lookup and link projector. It records one resolver-derived usage row for Series `105` at the containing Resolver Token range. The source contains no fabricated `[[catalogue:series:...]]` text.

The usage rows below are illustrative; PRJ-4.0 freezes their exact schema and field names:

```json
{
  "origin": "authored_token",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 155},
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

```json
{
  "origin": "resolver_result",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 178},
  "resolver_id": "<project-resolver-id>",
  "subject_kind": "folder",
  "subject_key": "projects/nerve",
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

## Fixed Design Notes

- A small global definition registry contains capability metadata only: resolver ID, access, accepted subjects, lookup/schema, and result groups.
- Project State is the only producer of the Project lookup. The initial Project resolver accepts only exact folder subjects and returns only `Series[] + Project documents[]`.
- Resolver depth is exactly one; returned items are never resolved again.
- Resolution order is exact parse, access check, lookup load, exact folder-key read, declared-group rendering, and semantic-link projection for Series identities.
- Series results sort by canonical Series ID. Project documents sort by normalized title then `doc_id`.
- The Project lookup stores Series semantic identity, not a second title or URL authority.
- The existing generated Semantic Tokens target lookup is the only secondary data source allowed for Series presentation. A missing, stale, or unusable semantic target renders an explicit unavailable result, never falls back to a plain resolver-owned URL, and produces no resolved usage row.
- Every successfully projected Series adds one row to the containing scope's generated semantic usage index. One Resolver Token may produce several rows with the same containing source range and different Series identities.
- Usage rows distinguish authored Semantic Tokens from resolver-derived results while retaining source scope/document, containing source range, displayed title, semantic family/type/id, resolved `href`, and resolver/subject provenance.
- The Semantic Tokens report includes resolver-derived rows and links back to the managed document and containing Resolver Token location.
- Folder subject keys are normalized paths relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, so exact declared contained folders outside `projects/` remain addressable without widening discovery scans.
- The initial Project resolver is Manage-only. Resolver output is read-only presentation and grants no mutation authority.
- Lookup refresh and containing-document rebuild are separate operations. Resolver expansion never refreshes Project State.
- The token syntax serializes one exact folder subject without pretending the path is permanent identity.
- Resolver Tokens keep their own parser, authoring contribution, resolver contract, group renderer, and access policy. They reuse semantic target/link/usage owners only for returned registered identities.
- A later resolver may return another registered catalogue target type, but that does not add Works, Moments, or other groups to the initial Project resolver.

## Delivery Discipline

PRJ-4 should remain a bounded lookup consumer: a small resolver-definition registry, exact token parser, one-row relationship reader, declared-group renderer, bounded semantic-link projector, and thin Source insertion workflow. It must not become a graph database, query language, registry scanner, recursive traversal engine, or live relationship service.

PRJ-4.0 must record the exact proposed files, reused builder/editor seams, and rough production/test diff. If the generic core grows beyond what the single folder-to-Series resolver requires, pause for review and defer the abstraction until another proven consumer needs it.

## Not In Scope

- Work subjects or Work result groups in the initial Project resolver;
- recursive traversal or adjustable depth;
- `folder -> Series -> Works/tags` chaining;
- relationship-path explanations or graph visualization;
- a global relationship database;
- automatic rebuilding of every document that uses a changed resolver row;
- public exposure of local Project relationships; or
- migration of Semantic Tokens into Resolver Tokens.

## Completion Evidence

- One exact folder occurrence produces only the precomputed `Series[] + Project documents[]` groups.
- Every returned Series uses its semantic identity and the shared semantic-link projection, never a plain URL owned by the Project lookup.
- Every resolver-generated Series link creates one derived usage row tied to its containing Resolver Token range, and the Semantic Tokens report can distinguish its origin and open the owning document at that location.
- Maintained examples prove that a manual Series URL, authored Series Semantic Token, and Resolver-generated Series semantic link can present the same destination while retaining different source and usage contracts.
- Resolver-derived usage rows never fabricate Semantic Token source syntax. An unavailable Series target produces neither a link nor a resolved usage row and does not fall back to an unvalidated URL.
- Instrumented tests prove no build-time scan or chained relationship resolution; semantic projection is bounded to exact returned Series identities.
- Source remains byte-stable across successful, empty, stale, and unavailable expansion.
- Authoring always inserts an explicit validated folder subject and never uses a UI fallback.
- Public builds and runtime remain free of the Manage-only Project definition, lookup, local paths, and rendered local results.
