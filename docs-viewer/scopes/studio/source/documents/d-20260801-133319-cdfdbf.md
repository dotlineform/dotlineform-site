# PRJ-4 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **PRJ-4** after Project State independently publishes a trustworthy
Project resolver lookup.

This delivery lets an author insert one explicit folder or Work reference into
a document and render its current direct Project relationships at build time.
It establishes a reusable bounded resolver capability without creating a
global graph or extending Semantic Tokens beyond their identity-link purpose.

## Complete Outcome

A managed document can contain a validated Resolver Token whose subject is an
exact Project folder key or Work ID. Building that document performs one exact
read from the Project State lookup and renders deterministic groups:

```text
folder -> Works[] + Project documents[]
Work   -> folders[] + Project documents[]
```

The source token remains unchanged. Zero matches, unavailable lookup, stale
snapshot, and invalid subject states render explicitly. Expansion never scans
the filesystem, Project manifest, Works, Series, tags, or another registry.

## Fixed Design Notes

- A small global definition registry contains capability metadata only:
  resolver ID, access, accepted subjects, lookup/schema, and result groups.
- Relationship rows remain in resolver-owned generated lookups. Project State
  is the only Project lookup producer.
- Resolver depth is exactly one; returned items are never resolved again.
- Resolution order is exact parse, access check, lookup load, exact key read,
  and declared-group rendering.
- Project results sort deterministically: Works by normalized Work ID,
  documents by title then `doc_id`, and folders by normalized relative path.
- Project folder subject keys are relative to
  `$DOTLINEFORM_PROJECTS_BASE_DIR/`, so explicitly linked contained folders
  outside `projects/` remain addressable without widening discovery scans.
- The initial Project resolver and local folder links are Manage-only.
- Resolver expansion is read-only build presentation, not stored relationship
  truth or permission to mutate an input.
- Lookup refresh and containing-document rebuild are separate operations.
- The token syntax must serialize an exact subject without pretending that a
  folder path is permanent identity.
- Resolver Tokens have their own parser, authoring contribution, resolver
  contract, renderer, and access policy. They do not reuse Semantic Token
  occurrence or target-registry semantics.

## Delivery Discipline

PRJ-4 should remain a bounded lookup consumer: a small resolver-definition
registry, exact token parser, one-row lookup reader, declared-group renderer,
and thin Source insertion workflow. It must not become a graph database,
general query language, registry scanner, recursive traversal engine, or live
relationship service.

PRJ-4.0 must record the exact proposed files, reused builder/editor seams, and
rough production/test diff size. If the generic core grows beyond what the
single Project resolver needs, pause for review and defer the additional
abstraction until a second proven consumer requires it. Line count remains a
scope signal rather than an optimization target.

## Rough Delivery Steps

### PRJ-4.0 — Freeze Syntax And Generic Resolver Contract

- [ ] Trace the current Markdown build pipeline, Source token insertion,
  Semantic Token parser/renderer/usage boundaries, access projection, and
  dependency-aware rebuild behavior.
- [ ] Freeze exact token syntax for resolver ID, subject kind, and subject key;
  escaping; invalid/unavailable/stale output; and source preservation.
- [ ] Freeze the global definition schema, lookup interface, result-group
  schema, ordering, and Manage/public access failure.
- [ ] Record the exact file list, reused seams, rough production/test diff
  estimate, and any proposed expansion before implementation approval.
- [ ] Prove the Project State lookup can answer every example with one keyed
  read and no downstream lookup.

**Checkpoint:** reviewed fixtures cover zero, one, many, duplicate-document,
missing-folder, invalid-subject, missing-lookup, stale-lookup, and public-access
cases. Stop before parser or renderer implementation.

### PRJ-4.1 — Implement Resolver Core And Project Adapter

- [ ] Add the strict code-owned definition registry and schema/version checks.
- [ ] Add the builder parser and one-lookup resolver interface.
- [ ] Register the Project resolver against the PRJ-3 generated lookup.
- [ ] Render accessible deterministic groups and explicit empty/error states
  without mutating source.
- [ ] Keep resolver lookup paths, local URLs, and service capabilities out of
  public build/runtime data.

### PRJ-4.2 — Add Authoring Workflow

- [ ] Add a Source-editor contribution that selects or pastes an exact allowed
  subject, previews current matches, and inserts the validated token.
- [ ] Preserve the committed subject exactly; do not infer it from the current
  document, selected Work, title, or displayed URL.
- [ ] Reuse existing authoring space and target validation where suitable, but
  keep Resolver and Semantic Token modes distinct.

### PRJ-4.3 — Verify And Transfer

- [ ] Run focused parser, registry/lookup agreement, builder, rendering,
  authoring, stale/unavailable, access-isolation, lint, and whitespace checks.
- [ ] Manually review a Project document with realistic Work/document counts,
  empty groups, long labels, stale data, and narrow layout.
- [ ] Prove that building a token-bearing document performs no filesystem or
  canonical registry scan and does not refresh Project State.
- [ ] Document the generic shipped resolver extension seam in a durable Docs
  Viewer architecture owner; retain Project-specific result meaning here.

## Not In Scope

- recursive traversal or adjustable depth;
- `folder -> Work -> Series/tags` chaining;
- relationship-path explanations or graph visualization;
- a global relationship database;
- automatic rebuilding of every document that uses a changed resolver row;
- public exposure of local Project relationships; or
- migration of Semantic Tokens into Resolver Tokens.

## Completion Evidence

- One exact occurrence produces only the precomputed one-hop groups declared by
  its resolver.
- Instrumented tests prove no build-time scan or chained registry lookup.
- Source remains byte-stable across successful, empty, stale, and unavailable
  expansion.
- Authoring always inserts an explicit validated subject and never uses a UI
  fallback.
- Public builds and runtime remain free of the Manage-only Project definition,
  lookup, local paths, and rendered local results.
