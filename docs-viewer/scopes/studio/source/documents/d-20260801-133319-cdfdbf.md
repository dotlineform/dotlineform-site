# PRJ-4 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **PRJ-4** after Project State independently publishes a trustworthy
Project resolver lookup.

This delivery lets an author insert one explicit folder or Work reference into
a document and render its current direct Project relationships at build time.
It establishes a reusable bounded resolver capability without creating a
global graph or extending Semantic Tokens beyond their identity-link purpose.

## Complete Outcome

A managed document can contain a validated Resolver Token whose subject is an
exact Project folder key or Work ID. Building that document performs one exact
read from the Project State lookup and renders deterministic groups:

```text
folder -> Works[] + Project documents[]
Work   -> folders[] + Project documents[]
```

The source token remains unchanged. Zero matches, unavailable lookup, stale
snapshot, and invalid subject states render explicitly. Expansion never scans
the filesystem, Project manifest, canonical Works, Series, Moments, tags, or
another relationship registry.

Any returned item that identifies a registered Catalogue Work, Series, or
Moment renders through the existing Semantic Tokens target identity, generated
target lookup, and semantic-link projector rather than carrying or emitting a
plain URL. It does not create Semantic Token syntax in source, but every
successfully rendered semantic result does create a derived semantic usage row
pointing to the containing Resolver Token occurrence. Project documents and
validated folders retain their existing Docs Viewer and local-folder link
contracts.

## Source And Usage Examples

The reader-facing result is deliberately similar in all three cases: readable
text links to Work `00008`. The source and generated usage evidence distinguish
how the link came to exist.

### Manually Authored Markdown Link

```md
[nerve](/works/?series=105&work=00008)
```

This is an ordinary authored URL. The Markdown renderer produces an ordinary
anchor, but there is no semantic identity in source and no semantic usage row.
Changing or auditing the target depends on the URL text.

### Authored Semantic Token

Using **Add catalogue token** inserts:

```md
[[catalogue:work:00008|nerve]]
```

The builder resolves `(catalogue, work, 00008)`, renders the current semantic
destination, and records one authored-token usage row at that exact source
range.

### Resolver-Generated Semantic Link

The exact Resolver Token syntax is a PRJ-4.0 decision. Until then this source is
illustrative only; the angle-bracket value is not proposed serialization:

```md
[[resolver:<project-resolver-id>:folder:projects/nerve]]
```

The Project lookup row selected by that Resolver Token may contain the semantic
result descriptor:

```json
{
  "family": "catalogue",
  "target_type": "work",
  "target_id": "00008"
}
```

The builder passes that descriptor through the same semantic target lookup and
link projector. It records one resolver-derived usage row for Work `00008` at
the containing Resolver Token range. The source contains no fabricated
`[[catalogue:work:...]]` text.

The usage rows below are also illustrative; PRJ-4.0 freezes their exact schema
and field names:

```json
{
  "origin": "authored_token",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 153},
  "family": "catalogue",
  "target_type": "work",
  "target_id": "00008"
}
```

```json
{
  "origin": "resolver_result",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 178},
  "resolver_id": "<project-resolver-id>",
  "subject_kind": "folder",
  "subject_key": "projects/nerve",
  "family": "catalogue",
  "target_type": "work",
  "target_id": "00008"
}
```

The visible link may be equivalent even when its exact route differs: a manual
URL may preserve explicit Series context, while both semantic cases receive
their current destination from the semantic target lookup. The same distinction
applies to registered Series and Moment results.

## Fixed Design Notes

- A small global definition registry contains capability metadata only:
  resolver ID, access, accepted subjects, lookup/schema, and result groups.
- Relationship rows remain in resolver-owned generated lookups. Project State
  is the only Project lookup producer.
- Resolver depth is exactly one; returned items are never resolved again.
- Resolution order is exact parse, access check, lookup load, exact key read,
  declared-group rendering, and semantic-link projection for registered
  Catalogue targets. Semantic-link projection resolves presentation for one
  returned identity; it does not expand another relationship edge.
- Project results sort deterministically: Works by normalized Work ID,
  documents by title then `doc_id`, and folders by normalized relative path.
- A Work, Series, or Moment result carries the registered semantic identity
  `(catalogue, target type, canonical id)`. Project State does not become a
  second canonical owner of its URL or title.
- The existing generated Semantic Tokens target lookup is the only secondary
  data source allowed for those catalogue result links. A missing, stale, or
  unusable semantic target renders the resolver's explicit unavailable state;
  it never falls back to a plain URL stored in the Project lookup and produces
  no resolved usage row.
- Reusing semantic-link projection does not imply that the initial Project
  resolver must return Series or Moment groups. It governs any Work, Series, or
  Moment item a declared resolver group already returns, without adding a new
  relationship or chained lookup.
- Each successfully projected catalogue result adds one row to the containing
  scope's generated semantic usage index. One Resolver Token may therefore
  produce several rows with the same containing source range and different
  semantic target identities.
- The usage row distinguishes an authored Semantic Token from a
  resolver-derived result. Its common fields retain source scope/document,
  containing source range, displayed title, semantic family/type/id, and
  resolved `href`; its resolver origin records enough resolver and subject
  identity to explain why the link was generated. It does not invent a raw
  Semantic Token string.
- The Semantic Tokens report includes resolver-derived rows and links back to
  the managed document and containing Resolver Token location, so every
  generated semantic link remains discoverable.
- Project folder subject keys are relative to
  `$DOTLINEFORM_PROJECTS_BASE_DIR/`, so explicitly linked contained folders
  outside `projects/` remain addressable without widening discovery scans.
- The initial Project resolver and local folder links are Manage-only.
- Resolver expansion is read-only build presentation, not stored relationship
  truth or permission to mutate an input.
- Lookup refresh and containing-document rebuild are separate operations.
- The token syntax must serialize an exact subject without pretending that a
  folder path is permanent identity.
- Resolver Tokens have their own parser, authoring contribution, resolver
  contract, group renderer, and access policy. They do not reuse Semantic Token
  syntax or authoring semantics. Their renderer reuses the registered semantic
  target identity, link projection, and usage-index owner for catalogue result
  items instead of implementing parallel link or relationship inventories.

## Delivery Discipline

PRJ-4 should remain a bounded lookup consumer: a small resolver-definition
registry, exact token parser, one-row relationship reader, declared-group
renderer, bounded semantic-link projector, and thin Source insertion workflow.
It must not become a graph database, general query language, registry scanner,
recursive traversal engine, or live relationship service.

PRJ-4.0 must record the exact proposed files, reused builder/editor seams, and
rough production/test diff size. If the generic core grows beyond what the
single Project resolver needs, pause for review and defer the additional
abstraction until a second proven consumer requires it. Line count remains a
scope signal rather than an optimization target.

## Rough Delivery Steps

### PRJ-4.0 — Freeze Syntax And Generic Resolver Contract

- [ ] Trace the current Markdown build pipeline, Source token insertion,
  Semantic Token parser/renderer/usage boundaries, access projection, and
  dependency-aware rebuild behavior.
- [ ] Freeze exact token syntax for resolver ID, subject kind, and subject key;
  escaping; invalid/unavailable/stale output; and source preservation.
- [ ] Freeze the global definition schema, lookup interface, result-group
  schema, ordering, semantic-target descriptor, semantic-link projection, and
  Manage/public access failure.
- [ ] Freeze the rule that Work, Series, and Moment results use the existing
  semantic target lookup and link projector without producing source token
  syntax or falling back to plain URLs.
- [ ] Freeze the semantic usage-index schema evolution: authored and
  resolver-derived origins, common fields, resolver/subject provenance, one
  row per rendered result, containing source range, targeted-build
  preservation, and report presentation.
- [ ] Freeze one shared comparison fixture covering the manual Work URL,
  authored Work Semantic Token, and Resolver-generated Work semantic link
  above, including their rendered anchors and different usage-index outcomes.
- [ ] Record the exact file list, reused seams, rough production/test diff
  estimate, and any proposed expansion before implementation approval.
- [ ] Prove the Project State lookup can answer every example with one keyed
  relationship read and no downstream relationship lookup; semantic link
  projection may resolve only the exact returned Catalogue identities.

**Checkpoint:** reviewed fixtures cover zero, one, many, duplicate-document,
missing-folder, invalid-subject, missing-lookup, stale-lookup, and public-access
cases, plus resolved and unavailable Work, Series, and Moment semantic targets.
Fixtures also prove the exact derived usage rows for one Resolver Token that
renders multiple semantic links. Stop before parser or renderer implementation.

### PRJ-4.1 — Implement Resolver Core And Project Adapter

- [ ] Add the strict code-owned definition registry and schema/version checks.
- [ ] Add the builder parser and one-lookup resolver interface.
- [ ] Register the Project resolver against the PRJ-3 generated lookup.
- [ ] Render accessible deterministic groups and explicit empty/error states
  without mutating source.
- [ ] Route every declared Work, Series, or Moment result through the existing
  semantic target lookup and semantic-link projector; emit no resolver-owned
  plain catalogue URL or fabricated Semantic Token source text.
- [ ] Extend the generated semantic usage index and report with explicit
  resolver-derived occurrences tied to the containing Resolver Token range,
  while preserving untouched documents during targeted builds.
- [ ] Keep resolver lookup paths, local URLs, and service capabilities out of
  public build/runtime data.

### PRJ-4.2 — Add Authoring Workflow

- [ ] Add a Source-editor contribution that selects or pastes an exact allowed
  subject, previews current matches, and inserts the validated token.
- [ ] Preserve the committed subject exactly; do not infer it from the current
  document, selected Work, title, or displayed URL.
- [ ] Reuse existing authoring space and target validation where suitable, but
  keep Resolver and Semantic Token modes distinct.

### PRJ-4.3 — Verify And Transfer

- [ ] Run focused parser, registry/lookup agreement, builder, rendering,
  authoring, semantic-link projection, derived usage indexing/reporting,
  targeted-build preservation, stale/unavailable, access-isolation, lint, and
  whitespace checks.
- [ ] Manually review a Project document with realistic Work/document counts,
  empty groups, long labels, stale data, and narrow layout.
- [ ] Prove that building a token-bearing document performs no filesystem or
  canonical registry scan and does not refresh Project State.
- [ ] Document the generic shipped resolver extension seam in a durable Docs
  Viewer architecture owner, and update Semantic Tokens Architecture and its
  report contract for resolver-derived usage; retain Project-specific result
  meaning here.

## Not In Scope

- recursive traversal or adjustable depth;
- `folder -> Work -> Series/tags` chaining;
- adding Work, Series, or Moment relationship groups that are not already
  present in the resolver-owned lookup;
- relationship-path explanations or graph visualization;
- a global relationship database;
- automatic rebuilding of every document that uses a changed resolver row;
- public exposure of local Project relationships; or
- migration of Semantic Tokens into Resolver Tokens.

## Completion Evidence

- One exact occurrence produces only the precomputed one-hop groups declared by
  its resolver.
- Every returned Work, Series, or Moment uses its registered semantic identity
  and the shared semantic-link projection. It never renders from a plain URL
  owned by the resolver lookup.
- Every resolver-generated semantic link creates one explicit derived usage
  row tied to its containing Resolver Token range. The Semantic Tokens report
  can distinguish its origin and open the owning document at that location.
- Maintained examples prove that a manual Work URL, authored Work Semantic
  Token, and Resolver-generated Work semantic link can present the same useful
  reader destination while retaining their different source and usage
  contracts.
- Resolver-derived usage rows never fabricate Semantic Token source syntax.
  An unavailable semantic target produces neither a link nor a resolved usage
  row and does not fall back to an unvalidated URL.
- Instrumented tests prove no build-time scan or chained relationship
  resolution; semantic target projection is bounded to exact returned
  identities.
- Source remains byte-stable across successful, empty, stale, and unavailable
  expansion.
- Authoring always inserts an explicit validated subject and never uses a UI
  fallback.
- Public builds and runtime remain free of the Manage-only Project definition,
  lookup, local paths, and rendered local results.
