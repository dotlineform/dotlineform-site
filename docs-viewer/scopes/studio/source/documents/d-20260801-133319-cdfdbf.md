# Resolver Tokens

## Purpose

Resolver Tokens let an author insert one explicit subject that expands into a current ordered relationship result at build time. They provide a bounded reusable relationship seam without creating a global graph, query language, recursive traversal engine, or live relationship service.

The initial consumer resolves one exact Project folder through the versioned Project State lookup and returns its associated Series and Project documents. Series results reuse the existing Semantic Tokens target, link, and usage owners so resolver-generated links retain semantic identity and produce locatable derived usage evidence.

## Complete Feature Outcome

A managed document may contain a Resolver Token with one explicit registered resolver, subject kind, and subject key. Its build loads the declared versioned lookup, performs one exact subject read, and renders deterministic result groups without scanning live source systems or mutating the token.

The initial Project resolver expands `folder -> Series[] + Project documents[]`. Every Series result carries semantic catalogue identity and is rendered through the existing Semantic Tokens projection. Each successful Series link adds one resolver-derived usage row tied to the containing Resolver Token range. Project-document results retain exact Docs Viewer target identity.

Empty, stale, unavailable, invalid, and denied results remain explicit. Resolver output is read-only, depth is exactly one, returned results are never recursively resolved, and public builds remain free of the initial Manage-only Project lookup and local relationships.

## Delivery Order

| order | delivery | complete outcome |
| --- | --- | --- |
| 1 | RT-1 — Resolver Tokens | One exact Project folder subject expands through one Project State lookup row into ordered semantic Series links and exact Project-document links with derived usage evidence. |

RT-1 begins only after the Project State lookup’s generation, freshness, failure, and access contracts work independently. Resolver Tokens consume that lookup but never own or refresh it. Future resolver adapters require their own bounded subject, lookup, result-group, access, and evidence review before extending the feature.

## Feature Boundary

In scope:

- a small code-owned resolver definition registry;
- exact token parsing and source preservation;
- one exact versioned lookup read per token;
- declared deterministic result groups;
- bounded reuse of Semantic Tokens target/link/usage projection for returned registered identities;
- resolver-derived usage rows tied to the containing source range;
- explicit Source authoring with no inferred subject fallback; and
- Manage/public access isolation.

Not in scope:

- a global relationship registry or database;
- recursive or adjustable-depth resolution;
- live filesystem, manifest, Works, Series, tag, or Moments scans during expansion;
- resolver-owned catalogue URLs or fabricated Semantic Token source;
- automatic dependent-document rebuilds;
- mutation authority from resolver output; or
- public exposure of local Project relationships.

[Project State](/docs/?scope=studio&doc=d-20260802-121104-530958) owns the initial folder lookup. [Semantic Tokens Architecture](/docs/?scope=studio&doc=d-20260714-234030-434069) owns semantic target projection and usage evidence. Resolver Tokens remain a downstream sibling feature rather than part of Projects or Project State.
