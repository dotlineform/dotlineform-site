# Cross-System Relationship Map

## Purpose And Reading Guide

This map separates two shipped cross-system projections from proposed Project State, Resolver Token, and Tag Semantic Token behavior. Solid edges are verified current generation or consumption. Dashed edges and labels containing **proposed** describe architecture only; they must not be read as shipped files or services.

## Notes

- Semantic target refresh and document rebuild are separate. Refreshing the target lookup does not silently rebuild every token-bearing document.
- The public document contains ordinary resolved links. It does not receive the management target lookup or a client-side semantic resolver.
- Tag Registry `doc_url[]` is the current ordered canonical association. `document-locations.json` supplies public-safe titles and locations for selection; it is not Tag authority.
- Document lifecycle remains independent of Tag links. Stale URLs can remain valid stored associations and are not inferred or repaired from titles or current UI context.
- The proposed Project State model is folder-centred. Docs Viewer `folder_path` and Studio Work `project_folder` remain different identities connected only through the planned read-only relationship observer.
- The existing `var/studio/reports/project-state.md` workflow is an image audit, not the proposed Project State relationship model.
- Proposed Resolver expansion is one hop and read-only. It does not scan live owners, mutate source, recursively traverse relationships, or refresh Project State.
