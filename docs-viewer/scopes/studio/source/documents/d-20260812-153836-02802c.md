# External Media Workspace

## Purpose

Docs Viewer separates a retained authorial original, the private managed artifact used by Docs Viewer, and an optional public projection. Every scope's managed media lives outside the repository; repository media bytes exist only when they are current public `site/` projections.

## Three Media Roles

| role | owner and lifetime |
| --- | --- |
| Retained original | Author-owned file beneath a configured Projects-relative source root such as `analysis/` or `processing/`. Add never moves, rewrites, or deletes it. |
| Managed media | Scope-owned consumer-ready artifact in the external Docs Viewer media workspace. Manage, inventory, build relationships, Copy, and future media management use it. It survives unpublish and document deletion. |
| Public projection | Replaceable byte-for-byte or derived copy under tracked `site/` or R2. It exists only through explicit Publish for a public scope. |

The managed artifact is deliberately distinct from the retained original. A raster image or file may be byte-identical, while sanitized SVG or rendered output may differ. The separate managed copy gives Docs Viewer a stable scope-owned identity even if the author later reorganises the original source tree.

## Folder Model

The external workspace is rooted beneath the configured Projects base with this shape:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/
  docs-viewer/
    media/
      <scope>/
        img/
        svg/
        files/
        html/
        build-source/
          mermaid/
        media-source-evidence.json
```

Each parent scope has one exact namespace. Media types remain separate logical subdirectories and identities remain flat within each type unless another feature deliberately changes that contract. Sub-scopes use the parent scope namespace; there is no inferred sub-scope media ownership.

A repository-backed scope container becomes document-centred:

```text
docs-viewer/scopes/<scope>/
  source/
    documents/
    sub-scopes/<sub-scope>/documents/
  published/
    documents/
    search/
```

An external-local document scope keeps the same document/search roles beneath its external scope root, but its media uses the shared external media workspace rather than being nested inside that document container. Repository and external-local scope containers therefore carry documents and their document/search projections, not ordinary media bytes or media build sources.

## Stable Identity And URLs

Canonical Markdown continues to store one provider-neutral reference:

<pre><code>&#91;&#91;media:docs/analysis/img/algorithm.jpeg&#93;&#93;</code></pre>

The logical identity is:

```text
scope + media type + relative identity
```

Physical roots and served URLs are projections of that identity:

| surface | example |
| --- | --- |
| Managed file | `$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/analysis/img/algorithm.jpeg` |
| Manage URL | `/docs/media/analysis/img/algorithm.jpeg` |
| Public repository file | `site/assets/data/docs/scopes/analysis/media/img/algorithm.jpeg` |
| Public URL | `/assets/data/docs/scopes/analysis/media/img/algorithm.jpeg` |
| Public R2 key | configured from the same `analysis + img + algorithm.jpeg` identity |

Manage and public payloads may therefore contain different rendered URLs without changing canonical Markdown. A raw physical path or public URL is never the authored ownership identity.

## Add And Manage Workflow

```text
analysis/algorithm.jpeg
        ↓ Add image
external Docs Viewer media/analysis/img/algorithm.jpeg
        ↓ local Manage serving
/docs/media/analysis/img/algorithm.jpeg
```

1. Add image or Add file selects an eligible original beneath the scope's configured source root.
2. Preview computes the stable logical identity and any existing collision without changing public storage.
3. Apply copies or derives the managed artifact in the external scope namespace and verifies the result.
4. Successful apply records the exact source association beside that namespace and inserts the logical token into canonical Markdown.
5. Manage resolves the token through the local media route backed by the external workspace.

Scopes without a configured retained-original root may continue to select from import staging, but their successful Add result still enters the same external managed workspace. Document and package Import follow the same destination rule for materialised media.

A document-only build does not need to copy or publish media. When the external workspace is unavailable, media Add, inventory, serving, Copy, build-source work, and public Publish fail or report unavailable at their own boundary rather than silently falling back to repository or public bytes.

## Build Sources And Editorial Copy

Standalone Mermaid `.mmd` is a registered media build source, not a document. It lives in the external namespace's `build-source/mermaid/`; its consumer-ready SVG lives in `svg/`. Inline Mermaid fenced inside Markdown remains document source and keeps its separate public projection contract.

Editorial Copy transfers exact managed media identities between the source and target scope namespaces through the existing provider-neutral media plan. It carries recorded source evidence when present, preserves an existing target evidence row, performs no filename inference, and does not publish the target scope publicly.

## Explicit Public Publish

For a public scope, Publish owns documents and media as one reconciled projection:

```text
external Docs Viewer media/analysis/img/algorithm.jpeg
        ↓ explicit Publish
site/assets/data/docs/scopes/analysis/media/img/algorithm.jpeg
        or configured R2 projection
```

Publish derives the exact referenced media set across the complete publishable parent and sub-scope document set. A media identity referenced by several public documents is projected once and remains public until no included document references it.

Preview derives the referenced media set and reports the public media copies and removals it can perform. A missing or unavailable managed object does not block confirmation: the document is still publishable and its media reference may return `404`.

Apply keeps the current document and search projection behavior and independently copies available referenced media to `site/` or R2. Successful media copies are byte-verified, but document publication does not depend on media availability or copy success. Exact stale public media projections are removed from the complete remaining public reference set. Repository and R2 mechanics stay behind their existing location adapters; ordinary Publish orchestration does not branch on provider.

The public target policy remains configuration-owned and may differ by media type. Its repository or R2 location is always a replaceable public projection rather than the private managed authority.

## Unpublish, Delete, And Orphans

Setting `publishable: false` changes eligibility for the next scope-wide Publish. That Publish removes the document projection and removes a public media projection only when the identity is absent from every remaining publishable document. The external managed artifact, retained original, and source-evidence row remain.

Ordinary document Delete likewise has no authority to delete managed media. Immediate document-publication cleanup must not infer exclusive media ownership or delete shared media. The next exact scope-wide Publish may reconcile now-unreferenced public projections; future Scope Media Management may expose the managed artifact as unreferenced, but deletion remains a separate explicit action.

## Operational Invariants

- Resolve every configured scope, media type, build source, evidence row, and public projection through the strict scope configuration.
- Keep managed media, registered build sources, and source evidence in the exact external scope namespace.
- Reconcile repository and R2 public projections only through confirmed scope-wide Publish.
- Do not add path aliases, fallback reads, dual writes, or provider searches.
- Keep repository scope containers document-centred, with no private ready-media or build-source objects.
- Preserve logical tokens and document source unchanged.

## Boundaries

- The external media workspace is not itself a backup promise; backup and synchronization remain user-owned policies.
- No shared physical object or deduplication across scope identities.
- No automatic import of arbitrary files from retained-original trees.
- No automatic managed-media deletion, orphan cleanup, source repair, or public publication during Add or Copy.
- No provider selector in ordinary authoring UI.
- No nested identity migration, asset registry, checksum catalogue, content-addressing, CDN cache invalidation, or background publication worker.
- No change to public document eligibility, lineage, or the meaning of `publishable`.
