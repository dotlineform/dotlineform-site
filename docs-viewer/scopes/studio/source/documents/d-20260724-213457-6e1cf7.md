# Docs Viewer Core Definition Baseline v1

## Status And Authority

Accepted on 2026-07-24 as the initial boundary for Transition Architecture. Current source-documentation conventions and maintained lint commands are owned by the [Development Checklist](/docs/?scope=studio&doc=d-20260523-190651-7157ec) and [Run Checks](/docs/?scope=studio&doc=d-20260501-174746-f92667).

This is an adjustable architectural baseline, not a module manifest or implementation approval. Current code and canonical configuration remain the exact behavior authority. Any implementation evidence that changes a classification must update this document and record the consequence before the boundary drifts in code.

No Core Refactor implementation, standalone packaging, lint dependency installation, or worktree creation is authorized by this baseline.

## Composition Definitions

- **Integrated composition:** the existing repository-based Docs Viewer application. It is broader than the `docs-viewer/` directory because it currently also depends on `site/docs-viewer/`, Studio helpers, repository configuration, public projection, R2, document packages, and Docs Review.

- **Core:** the accepted architectural boundary for behavior shared by integrated and standalone compositions. It currently has no enforced filesystem, Python package, JavaScript package, or dependency boundary. Some useful seams exist, but several modules still mix core and integrated responsibilities.

- **Standalone composition:** a future working application assembled from the extracted core plus standalone-specific configuration, external-local storage, launcher, app data, migrations, and packaging. Its installed runtime will not depend on a repository checkout or integrated-only modules.

The intended transition is:

```text
current integrated application
        ↓ refactor
core + integrated adapters/composition
        ↓
recomposed integrated application

core + standalone shell/providers/packaging
        ↓
standalone application
```

So the baseline defines what “core” means. Transition Architecture must decide where that boundary physically lives and how the existing integrated application is separated and recomposed.

 **the core is what we are extracting; the standalone app is a later consumer of it.** - it is the concrete document product behavior shared by the integrated and standalone compositions:

- document and scope identity, hierarchy, metadata, source, and generated-payload rules;
- scope-aware reading, rendering, search, recent activity, local reader state, and manage UI;
- source editing, document and scope lifecycle, rebuild, provider-neutral document transfer, and scope-owned media workflows;
- ordinary direct import and export;
- configuration schemas, capability records, and route, view, action, provider, and workflow contracts required to assemble those behaviors;
- explicit access to application paths, configured scopes, artifact locations, processes, and services supplied by a composition.

The core is not a generic documentation framework. Add a core interface only for a demonstrated integrated or standalone consumer. The dependency direction is:

```text
integrated composition ─┐
                        ├─> Docs Viewer core
standalone composition ─┘
```

Core must not import either composition. Providers and optional integrations may depend on core contracts; hiding an already imported integration does not remove it from the dependency closure.

## Inclusion And Exclusion Tests

A responsibility is core when all of the following are true:

- both compositions need the product behavior or the contract that makes it available;
- its inputs and outputs can be stated without discovering a repository checkout or adjacent application;
- filesystem, process, provider, and service access can be supplied explicitly;
- current behavior provides evidence for the contract;
- keeping it once avoids a fork, global standalone-mode branch, or duplicate workflow.

A responsibility is not core when any of the following is essential to its meaning:

- repository project layout, GitHub Pages projection, site publishing, or R2 authentication;
- Data Sharing, reviewed document packages, Docs Review, Studio, or another adjacent application's domain context;
- installer, bundled-runtime, app-data migration, release, or upgrade behavior;
- a public-only or repository-only workflow that can consume core read, render, build, or mutation primitives through a composition-owned adapter;
- a hypothetical extension with no current consumer.

## Composition Matrix

| composition | core use | composition-owned additions |
| --- | --- | --- |
| integrated manage `/docs/` | full reader and management behavior across registered scopes | repository and external-local scopes, repository/R2 providers, public publishing, package workflows, Docs Review handoff, Studio bootstrap, local development services |
| integrated public routes | shared reading, rendering, search, recent, view, and route primitives | fixed public access policy, projected static config and payloads, public reports, public media routes, GitHub Pages delivery |
| integrated review `/docs-review/` | only reusable shell and rendering primitives | package identity, review sessions, materialization, decisions, review routes, and review assets |
| standalone manage | full reader and management behavior for external-local scopes | standalone composition root, app-owned config/state/logs/staging/exports/cache, bundled runtime, launcher, migrations, and release packaging |

Standalone remains `app_kind: manage`; it is not a fourth browser route kind. The integrated application may register more capabilities, but both manage compositions use one source implementation for shared behavior.

## Inputs, Outputs, And Environment

Core may depend only on explicit inputs owned by an application composition:

| role | core-visible contract | composition ownership |
| --- | --- | --- |
| application code, immutable defaults, and schemas | read-only paths or bundled resources | integrated checkout or standalone install |
| scope registry | parsed declarations and selected operational scope records | tracked repository config or standalone app-data overlay plus scope-owned config |
| scope source, generated data, search, media, and build media | logical roles resolved through registered artifact locations | external-local, repository, or R2 provider selected by the composition |
| browser assets and route config | explicit asset roots and route records | integrated site/local service or standalone bundle |
| staging, exports, temporary files, cache, logs, and durable application state | separate named roots or services | integrated local environment or standalone app-data/cache roots |
| optional workflows and providers | registrations whose availability produces capability truth | integrated or standalone composition root |
| adjacent workspaces | opaque integration inputs, never ambient core state | document-package, Data Sharing, Docs Review, or Studio owner |

Current `repo_root` parameters may temporarily map these roles, but `repo_root` is not the target core contract. `DOCS_SCOPE_CONFIGS` and `DOCUMENT_SOURCE_ROOTS` are lazy mutable process globals, not accepted long-term ownership. External-local operations continue to fail loudly when their selected workspace is unavailable; unrelated scope providers must not be resolved merely because another operation starts.

## Existing Seams To Preserve

- `docs-viewer-routes.json` separates `app_kind`, features, access, service locations, payload locations, and view policy.
- `docs-viewer-app-boot.js` and `docs-viewer-app-composition.js` accept route, provider, adapter, renderer, view, and shell contributions.
- `docs-viewer-manage.js` is a thin manage composition entry rather than a second reader implementation.
- `docs-viewer-management-source-adapter.js` confines browser source operations behind an injected service location.
- `ArtifactLocation`, provider capabilities, and confined artifact identities already separate logical workflow from most I/O details.
- `docs_scopes_v3` separates scope-owned source and publication from public projection.
- staged import listing already accepts `registered_source_formats`, and `ImportContent` plus per-document plan/apply are package-neutral.
- targeted Docs and search builders select requested scope ids before operational provider resolution.
- focused service and route tests already cover many document, scope, builder, artifact, import, and management contracts without requiring browser choreography.

## Current Ownership Violations

These are Transition Architecture inputs, not reasons to redefine the mixed modules as core:

- `docs_viewer_service.py` discovers the repository and imports document-package and Docs Review services at startup.
- `docs_management_service.py` combines core mutations with public publishing, repository-oriented export, and mutable global scope refresh.
- `docs_management_capabilities_service.py` derives package and review capability truth directly from the integrated workspace.
- `docs_import_source_service.py` imports package recognition, collection plan/apply, and the integrated package workspace directly.
- `docs-html-import.js` imports the collection controller eagerly even though the outer management controller lazy-loads Import.
- common builder code derives repository and site-owned paths from `__file__`.
- `docs_artifact_locations.py` contains the core artifact contract, filesystem providers, R2 provider, and Studio-owned R2 authentication in one module.
- static HTML export rejects external-local scopes and owns an integrated Projects-drive destination, so it does not yet satisfy the core direct-export outcome.
- several services and tests mutate `DOCS_SCOPE_CONFIGS` and `DOCUMENT_SOURCE_ROOTS` across module boundaries.

## Roadmap Assessment

| proposal | Baseline v1 assessment |
| --- | --- |
| Scope Media Management | compatible and constraining: provider-neutral inventory and scope-owned lifecycle remain core; physical provider and public projection stay composition-owned |
| Standalone Docs Viewer | required proof consumer; packaging remains downstream and may not fork core behavior |
| Share Sub-Scope Documents | core may retain sub-scope source/build primitives; sharing and public projection are integrated contributions |
| Mermaid Authoring And Publication | managed inline authoring/rendering can use core behavior; dual public SVG projection is integrated-only |
| Public Docs Viewer Mobile Experience | integrated public-reader outcome; preserve shared reader/view seams without imposing a mobile contract on local management |
| Semantic Tokens | token registry, target data, authoring UI, generated relationships, and reports are integrated-only; core may expose generic action, modal, Info-view, and source-range seams, while Add image/file remains ordinary media and Markdown behavior |
| Dated Export Snapshots | does not define core export; it remains an integrated external-destination policy that may consume reusable export primitives later |
| Portable Document Packages | integrated-only package semantics; may consume core source, media, and per-document primitives |

No proposal requires a global mode flag or a second implementation of shared behavior. If a proposal cannot attach through a demonstrated seam, Transition Architecture must either define that seam or record a baseline adjustment.

## Initial Evidence Map

Durable current evidence includes:

- scope and provider contracts: `test_docs_scope_config.py`, `test_docs_artifact_locations.py`, and external-scope builder tests;
- source, identity, mutation, lifecycle, transfer, media, and rebuild behavior: focused `test_docs_*` service tests;
- build and generated-data behavior: `test_build_docs_*`, search checks, and generated-read tests;
- ordinary import primitives and formats: `test_docs_import_content.py`, ordinary document/import tests, and media-package tests;
- public dependency separation: `test_docs_viewer_public_runtime_boundaries.py`;
- integrated package and review behavior: document-package and review service/route tests;
- route/service wiring: Docs Viewer service tests and focused browser smokes.

Owner-coupled evidence that must move or be replaced with its owner includes tests that assert repository paths, global config mutation, integrated capability payload shape, package-aware ordinary Import composition, or the monolithic local service bootstrap.

Known evidence gaps are:

- an executable standalone or package-free service composition;
- a mechanical standalone dependency-closure check excluding repository, public, R2, package, Data Sharing, and Docs Review modules;
- explicit application-environment/configuration ownership without mutable process globals;
- ordinary direct export from an external-local scope;
- an injected browser and service registration seam for document-package Import;
- parity proof that the recomposed integrated application retains current behavior.

These gaps block extraction closeout, not the source-documentation pilot.

## Proof Required From The Refactor

The core boundary is executable only when:

1. a manage composition can start with an explicit external-local workspace and no repository, public, R2, document-package, Data Sharing, or Docs Review modules present;
2. it can create or open a scope; browse, search, edit, move, copy, delete, and rebuild documents; manage local media; and complete one ordinary import and export;
3. builders and generated reads operate from explicit scope and output roles;
4. capability truth is derived from registered, available components;
5. static dependency checks prove core does not import either composition;
6. the integrated composition recomposes the same core with repository/public/R2/package/review contributions and preserves current behavior.

## Source-Documentation Pilot Surfaces

Baseline v1 nominates these exact surfaces for SDL-P0 confirmation:

| requirement | surface | reason |
| --- | --- | --- |
| exported browser contract with non-trivial object and callback shapes | `site/docs-viewer/runtime/js/shared/docs-viewer-app-composition.js` | central core composition seam already consumed by manage and public routes |
| Python domain boundary with meaningful validation and failure behavior | `docs-viewer/services/docs_import_content.py` | package-neutral normalized input shared by ordinary and integrated package adapters |
| builder/filesystem boundary with side effects | `docs-viewer/build/docs_builder/write_plan.py` | separates proposed generated-output changes from write and stale-output removal |
| documentation showing that a split is preferable to a long comment | `docs-viewer/services/docs_artifact_locations.py` | core artifact contracts and filesystem behavior currently share a module with integrated R2 authentication and provider code |

SDL-P0 must confirm the exact exported functions, Python interpreter, direct-browser module environment, exclusions, and tool owners before installing dependencies. It may narrow a surface if the same representative boundary remains covered; widening beyond these four files requires an explicit delivery decision.

### Rationale

The selected surfaces are specimens for testing the documentation conventions—not a proposed core module manifest.

| Surface | Why it was selected | What the pilot should prove |
| --- | --- | --- |
| `site/docs-viewer/runtime/js/shared/docs-viewer-app-composition.js` | It is a real browser composition seam used across route compositions, with exported factories, injected callbacks, providers, adapters, and stateful collaborators. | Whether concise JSDoc can make non-trivial JavaScript object and callback contracts understandable without restating the implementation. Focus on the exported composition factories, not every internal function. |
| `docs-viewer/services/docs_import_content.py` | `ImportContent` is a small, package-neutral domain contract used by ordinary Import and integrated package adapters. It has explicit validation and failure behaviour but no filesystem side effects. | The Python convention for documenting meaningful invariants, normalized data, mutation guarantees, and validation failures on a clear core candidate. |
| `docs-viewer/build/docs_builder/write_plan.py` | It sits at the important boundary between calculating generated-output changes and performing writes, directory creation, and stale-file removal. | How to document lifecycle and side effects in builder code, and whether Ruff finds useful correctness issues without turning the pilot into formatting work. |
| `docs-viewer/services/docs_artifact_locations.py` | It contains a valuable core contract, but currently mixes confined artifact operations and filesystem behavior with repository/R2 providers and Studio-owned authentication. | The “do not explain away mixed ownership” rule: documentation should expose the responsibility split and route it to Transition Architecture, rather than burying it beneath a long module comment. |

Together they cover:

- JavaScript and Python.
- Composition, pure domain validation, generated-output mutation, and provider/filesystem behavior.
- A strong core candidate, an orchestration seam, a side-effect boundary, and a deliberately mixed current owner.
- Modules with focused existing evidence, so documentation claims can be checked without adding a broad test harness.
- Enough variation to evaluate JSDoc, docstrings, Ruff, and ESLint while keeping the pilot to four files.

The deliberate exclusions are equally important: package/review modules are integrated-only, feature-specific UI modules risk documenting transitional choreography, and service launchers are too mixed to be useful first examples.

## Transition Questions

Transition Architecture must resolve:

1. the concrete application-environment and scope-registry objects that replace repository discovery and cross-module global mutation;
2. the module/package split between artifact contracts, external-local filesystem support, repository support, and R2 authentication;
3. the package-safe builder and browser-asset layout without duplicating site-owned shared runtime code;
4. the service and browser composition roots that register optional routes, capabilities, providers, Import formats, and UI contributions;
5. the core ordinary-export contract and the ownership of current static HTML destination policy;
6. the boundary between generic logical references and Studio/domain semantic-token registrations;
7. watcher, rebuild, process, logging, staging, and temporary-file ownership in both compositions;
8. the smallest independently integrable first extraction slice and its parity and recovery evidence.

These questions are bounded enough that they do not prevent SDL-P0 or the source-documentation examples from starting. They must be resolved before an implementation delivery is readied.
