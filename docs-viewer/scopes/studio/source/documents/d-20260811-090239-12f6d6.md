# ERV-1 — Expanded Report View Delivery

## Status And Purpose

ERV-1.1, ERV-1.1R, and ERV-1.2 are complete. The locally owned `catalogue_works` report is the first and only adopter: Manage can rehost its one live seven-column semantic table, reveal and copy its two expanded-only medium columns, and apply temporary accessible widths. Public routes neither own nor compose the capability. ERV-1 is parked at the ERV-1.2 review gate before ERV-1.3 verification and durable ownership transfer.

ERV-1 delivers the first complete [Expanded Report View](/docs/?scope=studio&doc=d-20260810-165949-ee4d35) outcome: an explicitly eligible live report can open in the existing full-width Content Detail layout without cloning, remounting, or losing report-owned state. Manage additionally gives an eligible semantic table temporary accessible column widths. The local `catalogue_works` report is the sole product adoption in this delivery.

## Complete Outcome

- A report or preset opts in only through an explicit successful module-mount result. Registry metadata, rendered width, overflow, row count, headings, and DOM shape never grant eligibility.
- The open control appears only after the exact report has mounted successfully and its presentation result has passed validation.
- Content Detail moves the exact live report root into one bounded full-width viewport. Search, sorting, current rows, report actions, event listeners, and route-owned state remain on the same DOM and report instance.
- **Back to document** restores the root to its exact authored host position, restores page scroll and invocation focus, and keeps the report state. Document navigation releases the expanded target without restoring stale content.
- The adapter remains free of management and service authority but is locally owned while only Manage composes it. Public routes download neither the adapter module nor its control and viewport selectors; a named public adopter requires an explicit complete ownership migration.
- Manage can resize only a presentation that declares one exact semantic table and an ordered stable column model. Pointer and keyboard resizing use one managed `colgroup`; **Reset widths** returns to the report's natural responsive table.
- A semantic-table presentation can declare each stable column as visible in `both` presentations or in `expanded` presentation only. The report renders each column once in the same live table; ordinary document presentation hides expanded-only headers and cells, while the expanded viewport reveals them before widths are measured.
- A report-owned export follows the active presentation when its contract requires that distinction. Catalogue Works Copy table exports the established five columns while embedded and all seven visible columns while expanded; Content Detail does not add a second copy action.
- Widths exist only for the active expanded presentation. They are not written to source, registry JSON, URLs, browser storage, canonical data, or generated payloads.
- Widening columns produces horizontal scrolling inside the expanded viewport. The ordinary embedded report retains its current fit-and-reflow presentation.

## Selected Capability Contract

Eligibility is code-owned by the mounted report module rather than added to `reports.json`. A successful eligible mount resolves with this focused browser handle:

```js
{
  expandedPresentation: {
    kind: "flow" | "semantic-table",
    label: "Catalogue Works",
    table: tableNode,
    columns: [
      { id: "work", label: "Work", visibility: "both" },
      { id: "medium_type", label: "Medium type", visibility: "expanded" }
    ],
    subscribe: subscribePresentationRefresh
  }
}
```

`flow` opts the exact live report root into shared expansion and omits `table`, `columns`, and `subscribe`. `semantic-table` additionally supplies the exact table, a non-empty ordered immutable column model of `{id, label, visibility}`, and a subscription that notifies the presentation adapter after any header or row reconstruction. `visibility` is explicitly `both` or `expanded`; it is presentation metadata rather than source Report Block configuration. The subscription returns its cleanup callback.

The report controller already owns the exact generated report host and normalized report descriptor. After a module mount resolves, it validates this optional handle and registers it with the entrypoint-supplied report-presentation adapter. An absent or invalid handle leaves the successfully mounted report embedded and undecorated; it does not infer a fallback presentation.

The exact expanded target freezes:

- host document identity `{viewer scope, doc_id}`;
- document-mount generation;
- report id;
- report descriptor scope, preset, and sub-scope values; and
- the one registered live root.

There is no report-instance id because a document has at most one Report Block. Selected rows, visible labels, current route alone, and the first matching report are never identity inputs.

`catalogue_works` returns `kind: "semantic-table"` only after its canonical inputs and first complete render succeed. Its one ordered presentation model contains the existing Work, Year, Title, Series, and Storage columns with `visibility: "both"`, followed by Medium type and Medium caption with `visibility: "expanded"`. Headers, body cells, and widths use all seven stable ids. Search and sorting retain their existing five-column contracts. The report-owned TSV projection uses five columns while embedded and all seven visible columns while expanded. The report notifies after its current header/body rerender. The adapter does not learn Catalogue fields or report-specific state.

## Delivery Boundary

ERV-1 includes:

- one shared report-presentation adapter and open-control lifecycle;
- explicit Manage composition through the existing Content Detail view, with public composition deferred until a named public report adoption;
- exact live-root rehosting, placeholder restoration, Back/navigation release, scroll/focus restoration, and stale-target rejection;
- one shared bounded expanded-report viewport with horizontal scrolling;
- one Manage-only semantic-table width extension reusing the current managed-table sizing seam;
- `catalogue_works` presentation-handle and stable-column adoption, including Medium type and Medium caption as expanded-only display columns in the same live table;
- focused shared, public-boundary, Manage-width, and Catalogue Works module evidence; and
- concise durable transfer to Reports, Report Capability and Composition, and Catalogue Works at closeout.

ERV-1 excludes:

- cloning, a second report mount, refetching report data, or a parallel report-state owner;
- adding eligibility or column configuration to source Report Blocks, report registry JSON, generated document payloads, or public registry projection;
- applying the Markdown `Table detail` marker or clone adapter to reports;
- adding **Copy table** to Content Detail for reports; `catalogue_works` keeps its report-owned Copy action inside the moved live root;
- persisted or URL-owned widths, saved views, user-defined columns, or an editor for report layout;
- changing Catalogue Works Search or sorting to include the first expanded-only fields;
- resizing in the ordinary embedded report;
- a generic report plugin, dashboard, presentation registry, DOM scanner, or geometry/overflow observer;
- converting another report to semantic table markup;
- `project_state`, `works`, `docs_subscope`, public report, or composite sub-scope-customisation adoption; and
- a tabular CSS Grid width projector before an accepted report requires one.

#### ERV-1.0 Sanity Record

ERV-1 fits the current runtime without changing Report Block source, registry metadata, generated payloads, services, report data, or route state. The selected optional module-mount result is the only new capability declaration. No unresolved design decision remains.

**Current lifecycle and reused seams.** The shared document controller assigns a positive mount generation, renders the exact payload host, mounts Table and Diagram adapters synchronously, then starts report mounting through the asynchronous document-extras hook. Both local and public report controllers validate one generated host, registry access, and one allowlisted loader, but currently discard the module's resolved value. The extras path already receives the document generation; ERV-1.1 needs only to pass that generation, `requestContentDetail`, and the entrypoint-supplied report adapter through the existing public/Manage report calls.

Back already requests `rendered-document` with reason `back`. Route loading, payload replacement, missing-document state, Search, and Recent leave Content Detail through reason `document-navigation`; the hosted-view unmount runs synchronously before the accepted render callback changes or hides document content. ERV-1.1 therefore adds one explicit report-adapter release at the current pane-hide, loading, replacement, and status boundaries beside their existing presentation releases. A late module result must repeat the existing host-current check after its promise resolves and cannot register a control for a detached root or newer mount generation.

Content Detail currently captures scroll after calling an adapter. That is safe for cloned Table and Diagram presentations but too late for a live-root move, which can change document geometry. ERV-1.1 captures scroll before `mountPresentation`, passes the release reason to the presentation, restores the report only on Back or a same-document presentation failure, and releases without restoring stale report content on `document-navigation`. Existing Table and Diagram presentations ignore the added release context and retain their behavior.

**Frozen capability and target.** A module opts in only by resolving a successful mount with own property `expandedPresentation`. `flow` requires one visible label and no table fields. `semantic-table` additionally requires one exact descendant `TABLE`, a non-empty ordered unique list of `{id, label, visibility}`, and `subscribe(listener)`, which returns one cleanup callback. Each `visibility` is explicitly `both` or `expanded`. Headers and every current body row use the same ordered `data-report-column-id` values with no row or column spans; a table that cannot meet that contract can still declare `flow` but receives no widths.

An absent handle is ordinary and produces no warning or control. An invalid explicit handle leaves the successfully mounted report embedded and undecorated and emits one development warning; it never replaces the report with an unavailable state. The post-mount control is inserted immediately before the exact generated root and requests target kind `report` with immutable `{viewer scope, doc_id}`, document generation, report id, and descriptor scope/preset/sub-scope. The control label is **Open [report label] in expanded view**. No selected row, displayed text, current route alone, or instance fallback participates.

The shared adapter stores one registration per document content root. Opening inserts one exact placeholder before the report root, moves that same root into a focusable `docsViewerReport__expandedViewport`, and exposes no new-tab target. Back moves the root before the placeholder, removes the placeholder and expanded section, restores the captured scroll, and focuses the still-connected invocation control. Navigation removes the expanded section/root and then releases the registration, control, and any active subscription exactly once.

**Managed widths and Catalogue Works.** The current Manage table owner already supplies pointer capture, Left/Right keyboard steps, measured widths, one direct `colgroup`, Reset, release cleanup, and shared Content Detail control projection. It currently snapshots one header row once and always exposes its own Copy control. `catalogue_works` reconstructs its header on every search and sort render, so direct reuse without a refresh path would orphan resize handles.

ERV-1.2 keeps one sizing owner and adds a report presentation extension to it. The extension validates the declared ids against current headers and rows, hides the Content Detail Copy control, subscribes only while the report is expanded, removes old handles and binds current headers after a notified rerender, and retains the existing `colgroup` widths while exact correspondence remains valid. A mismatch clears widths and handles and fails closed. The existing Table Detail extension keeps inferred simple-header eligibility for its accepted static clone plus its current Reset and Copy controls.

`catalogue_works` replaces its parallel key/label constants with one seven-column presentation model. Work, Year, Title, Series, and Storage use `visibility: "both"`; Medium type and Medium caption use `visibility: "expanded"`. The report normalizes the two fields already present in the canonical Works payload, renders all seven headers and cells once with exact `data-report-column-id` values, owns a small listener set, and notifies after `renderCurrent`. Local report CSS hides both expanded-only headers and cells in the ordinary document and reveals them under the moved root's expanded-viewport ancestor. The initial empty-search table may remain hidden; entering search reveals the same table, and the notification binds and measures all currently presented headers. A successful data load and first render return the capability. Failed or invalid input retains its existing contained report state and returns no capability. Existing Work/Series Search, five sortable columns, links, and counts remain unchanged. The report-owned Copy table projection derives from the exact current presentation: five columns embedded and seven columns expanded.
