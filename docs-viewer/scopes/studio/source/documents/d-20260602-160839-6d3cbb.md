# Docs Viewer Search

Docs Viewer Search provides one static inverted-index format and one browser query path for every configured parent scope. Each index contains the scope's eligible ordinary documents plus eligible documents from its visibly hosted registered sub-scopes. Every configured scope now uses the same authored full-text field policy before further Search improvements are considered.

## Durable Contracts

- [Docs Viewer Search Index](/docs/?scope=studio&doc=d-20260813-214350-4c7a21) owns payload structure, per-scope field policy, Studio source extraction, ranking inputs, complete rebuilds, and the extension boundary.
- [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-214351-98d3f0) owns normalization, technical-term derivation, exclusions, stop words, query prefix semantics, and Python/JavaScript parity.
- [Docs Viewer Search Relevance](/docs/?scope=studio&doc=d-20260813-223337-e6c261) owns the proposed shared corpus-adaptive ranking model, language and specialist-vocabulary policy, diagnostics, presentation options, and non-goals.

`docs-viewer/build/build_search.py`, `docs-viewer/config/scopes/docs_scopes.json`, `site/docs-viewer/runtime/js/shared/docs-viewer-search.js`, and the generated JSON remain exact code/config authority.

## Scope Policies

Studio, Analysis, Notes, Processing, and dotlineform enable `title`, `heading`, `body`, and `code`. Parent title, identity, update time, and route remain document-table metadata for display, navigation, and deterministic ordering but emit no postings. Shared source extraction includes visible authored headings, prose, inline code, fenced code, image alt text, and visible raw-HTML text; it excludes front matter, report declarations, link destinations, media paths, attributes, scripts, styles, document IDs, date fragments, and 64-character hexadecimal digests. Newly created scopes use the same default policy.

Manage-only roots, non-publishable documents, and their descendants do not enter the scope index. An eligible registered sub-scope contributes the documents in its public-safe working manifest when it has one exact eligible `docs_subscope` report host. Those child documents join the parent Search corpus but remain outside parent Index and Recent.

## Scope-Level Corpus

One main search covers the complete visible documentation experience for its active scope. Parent documents and eligible documents from registered, visibly hosted sub-scopes share one index, query, and relevance order. Report-local title search remains a list filter, not another full-text engine.

Sub-scope results retain exact `{scope, sub_scope, doc_id}` identity plus explicit `report_doc_id` placement. The shared route workflow uses that structured target to create the active Manage or public parent URL and preserve the child as `subdoc`; stored `href`, title, selected report, and UI state are not navigation authority. Configured collection/report title is display-only context beneath the result title and emits no postings.

## Build And Publication

The builder reconstructs one complete selected-scope index. Automatic authoring follow-through, including Source-editor saves, external watcher passes, metadata changes, imports, moves, deletes, publishability changes, and sub-scope edits, rebuilds document projections only. The explicit Manage Rebuild control is the sole normal authoring owner for refreshing the active scope's Docs and complete parent Search artifact; structural scope bootstrap, migration, and repair commands may invoke the same complete builder directly. No path patches postings or maintains a separate child index. The content version excludes generation time, so an identical rebuild skips its write, and no build touches an unrelated scope.

Working indexes live at their configured published-search locations. External-local scopes are served through the Docs Viewer service. A public scope's explicit Publish copies its accepted working index to the configured public destination together with its accepted document products. Analysis working and public Search use the common full-text policy after the accepted Search-only Publish on 2026-08-14.

## Browser Query Path

Generated browser config declares the Docs Viewer domain, v2 schema, index URL, and `whole_index` rebuild policy. The collection provider reads the active scope's URL, `docs-viewer-search-controller.js` validates v2 and owns query/history/loading/paging state, and `docs-viewer-search.js` is the sole tokenizer, postings-intersection, ranking, and tie-breaking owner.

A multi-term query requires one matching posting set per normalized term. Prefix matching begins at three characters. Generic ranking prefers exact identity, exact title, title, heading, parent title, body/code, and update metadata; only enabled fields participate. Every configured scope therefore ranks exact title, title, heading, then body/code. Ties sort by title and identity, and each exact parent or child target appears at most once.

## Extension Boundary

Adding a normal parent scope is configuration work, not a new builder or browser branch. Full-text scopes should converge on one field and relevance policy while continuing to own corpus membership and publication boundaries. Visibly hosted sub-scopes extend that parent scope's corpus; they do not receive another schema, tokenizer, cache, reader, query engine, vocabulary registry, domain dictionary, or separately queried index.

[All-Scope Full-Text Search Baseline](/docs/?scope=studio&doc=d-20260813-165124-16b0ab) retains the implementation and accepted Analysis Publish record. Catalogue Search retains its separate builder, records, runtime, and roadmap.

The practical ceiling remains one client-loaded static index. Short prefixes can return broad result sets after full-text adoption; snippets, highlighting, stemming, synonyms, spelling correction, phrase positions, and section results remain outside the current contract.
