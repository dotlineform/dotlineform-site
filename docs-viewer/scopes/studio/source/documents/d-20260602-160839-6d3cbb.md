# Docs Viewer Search

Docs Viewer Search provides one metadata search index and one browser query path for every configured parent scope.

## Shipped Index Contract

`docs-viewer/build/build_search.py` emits `docs_viewer_search_index_v2`. Each index contains a deterministic document table plus a term map whose field-specific posting lists reference positions in that table. The content hash excludes generation time, so an identical rebuild skips its write.

`docs-viewer/config/scopes/docs_scopes.json` owns each scope's source, working and optional public destinations, viewer route, membership exclusions, and ordered `search_fields`. Studio, Analysis, Notes, Processing, and dotlineform currently enable the same metadata fields: `title`, `parent_title`, `identity`, and `last_updated`.

Title and parent title are tokenized. Unicode and case are normalized; useful technical compounds and their components are retained; a small fixed stop-word list, URLs, paths, markup, file-extension-only components, numeric-only fragments, and full document IDs are excluded from ordinary terms. Full document identity remains available through its explicit exact field, and `last_updated` remains one field value rather than date fragments.

Manage-only roots, non-publishable documents, and their descendants do not enter the parent index. Registered sub-scope documents remain in their own collection products rather than the parent search corpus.

## Build And Publication

The builder always reconstructs one complete selected-scope search index. Watcher and write-service plans may still compute affected identities to target document payloads or decide whether search needs to run, but they do not patch postings. No build touches an unrelated scope.

Working indexes live at their configured published-search locations. External-local scopes are served through the Docs Viewer service. A public scope's explicit Publish copies its accepted working index to the configured public destination; Analysis currently projects the same metadata-only v2 bytes to `site/assets/data/search/analysis/index.json`.

## Browser Query Path

Generated browser config declares the Docs Viewer domain, v2 schema, index URL, and `whole_index` rebuild policy. The collection provider reads the active scope's URL, `docs-viewer-search-controller.js` validates v2 and owns query/history/loading/paging state, and `docs-viewer-search.js` is the sole tokenizer, postings-intersection, ranking, and tie-breaking owner.

A multi-term query requires one matching posting set per normalized term. Prefix matching begins at three characters. Ranking prefers exact identity, exact title, title, parent title, and update metadata in that order for the fields currently enabled; ties sort by title and then exact identity. Each document appears at most once.

## Extension Boundary

Adding a normal parent scope is configuration work, not a new builder or browser branch. A scope-specific field decision changes that scope's `search_fields` and any shared source extraction needed to supply the field; it does not create another schema, tokenizer, or query engine.

[SM-1 — Studio Full-Text Search Delivery](/docs/?scope=studio&doc=d-20260715-084611-c2fa6f) is eligible for its readiness step and separately owns proposed Studio heading, body, and code adoption. [Analysis Full-Text Search Extension](/docs/?scope=studio&doc=d-20260813-165124-16b0ab) remains a separate public vocabulary, membership, payload, and publication decision. Notes, Processing, and dotlineform remain metadata-only until an equivalent scope-owned decision is approved. Catalogue Search retains its separate builder, records, and runtime.

The intentionally small normalization is expressed once in Python generation and once in browser JavaScript, with one shared contract fixture proving parity. Current weak spots are the duplicated scalar/nested browser search URL projection and the practical payload ceiling of one client-loaded static index.
