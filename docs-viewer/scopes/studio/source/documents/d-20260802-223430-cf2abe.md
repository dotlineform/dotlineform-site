# DMM-2 — Mermaid And D2 Evaluation

## Status And Purpose

Proposed follow-on investigation after the completed [DMM-1 — Data Model Maps Foundation Delivery](/docs/?scope=studio&doc=d-20260802-123452-6a2fd3). DMM-1 and its three retained maps remain accepted current documentation; DMM-2 does not reopen that delivery merely because their first layouts can be improved.

The investigation must distinguish three possible causes of diagram difficulty before recommending another renderer:

1. the question or view is insufficiently bounded;
2. Mermaid has not yet been given a fair iteration using an appropriate diagram type, partition, and layout engine; or
3. the retained diagram has a recurring layout or author-control need that D2 satisfies materially better.

## Intended Outcome

DMM-2 produces a practical renderer recommendation and may retain bounded local-Studio improvements found during the comparison. It compares the same subject matter after a deliberate Mermaid pass and a free D2 with ELK spike. The result records where Mermaid remains the default, whether D2 is useful in a specialist role, and which integration is worth keeping.

A successful investigation may conclude that Mermaid is sufficient. D2 adoption is not a required outcome.

## Evaluation Subjects

- **Cross-System Relationship Map:** the primary layout-pressure case because its current Mermaid source uses invisible links to influence placement across shipped and proposed groups.
- **Catalogue Data Model Map:** the primary information-design case because one flowchart currently combines logical record relationships with projection lineage. Test a logical ERD and lineage split before attributing the result to renderer capability.
- **Docs Viewer Projection Map:** the hierarchical control case. It should remain understandable in Mermaid and prevents a specialist renderer from winning merely by improving an unusually difficult graph.

Use temporary evaluation copies. Do not silently replace the accepted retained diagrams during the comparison.

## Current ELK Availability

ELK is an official separate Mermaid layout plugin rather than part of the core browser package.

- **CLI and build rendering:** the pinned `@mermaid-js/mermaid-cli` dependency already brings in `@mermaid-js/layout-elk` and `elkjs` and registers the ELK layouts. Temporary CLI renders and the existing `.mmd` to SVG path can therefore evaluate `layout: elk` without adding another package.
- **Managed inline rendering:** Studio currently serves only the standalone `mermaid.min.js` browser asset. It exposes the layout-registration API but does not bundle or register the ELK plugin, so an inline fence cannot use `layout: elk` until the local runtime also serves and registers that plugin.

Because Studio is local, adding that managed-only plugin registration is an ordinary useful extension rather than a public trust problem. DMM-2 may retain it if it improves the real diagrams and remains reasonably small. It does not automatically place the plugin in the public browser runtime; public fenced-diagram preparation already renders through the CLI and public browsers continue to receive prepared SVG rather than Mermaid source or runtime.

## Comparison Criteria

Use the following as comparison prompts rather than a pass/fail scorecard:

- the diagram answers one bounded architecture question without reconstructive prose;
- current, proposed, canonical, generated, management, and public boundaries remain semantically explicit;
- full-screen Studio and Diagram Detail presentation are materially readable;
- meaningful edges do not cross or detour unnecessarily, and source contains no layout-only fake relationships;
- authoring source remains concise enough to review and maintain after a major feature delivery;
- repeated rendering is deterministic enough for useful source and SVG review;
- accessibility title and description survive the complete output path;
- light and dark presentation remain usable without duplicating semantic source;
- generated SVG survives the current sanitizer without losing labels, geometry, or required styling; and
- dependency installation, version pinning, builds, publication, and editor support are proportionate to the demonstrated benefit.

## Delivery Discipline

DMM-2 begins as an investigation but may deliver a bounded local-Studio integration when it is plainly useful. This may include making the already-installed Mermaid ELK plugin an explicit dependency, serving and registering its managed asset, adding focused coverage, or retaining a small local D2 source-to-SVG path. It does not need a separate delivery merely because Studio gains a useful local tool.

The first D2 comparison uses the free D2 distribution with its bundled ELK engine. Proprietary TALA is excluded from this bounded comparison so the open tool can be understood on its own terms. Do not check a platform-specific D2 binary into the repository; record the evaluated version and ordinary installation path instead.

The initial comparison has no production or test diff. Before retaining a local integration, record the exact runtime, dependency, asset, builder, and focused-test files plus a rough diff estimate. Pause only if the useful shape expands materially into public runtime ownership, public publication, a sanitizer-policy change, a generic renderer framework, or another broad capability.

## Rough Delivery Steps

### DMM-2.0 — Give Mermaid A Fair Second Pass

- [ ] Preserve the accepted source and rendered state of the three retained maps as the comparison baseline.
- [ ] Record the current split: Mermaid CLI/build rendering already registers the ELK plugin, while managed inline Studio does not.
- [ ] Reframe the Catalogue example as separate logical ERD and projection-lineage views before evaluating layout quality.
- [ ] Try Mermaid ELK through the existing CLI on the bounded Catalogue and Cross-System candidates, recording the exact configuration rather than relying on the default Dagre layout.
- [ ] If ELK is useful for retained inline diagrams, record the exact files and rough diff, then add the smallest managed-only plugin asset and registration needed to inspect it in the real Studio surface.
- [ ] Try another installed Mermaid diagram family only when it better matches the question; do not change grammar merely to obtain a different visual style.
- [ ] Remove invisible or layout-only links from the comparison candidates and record any relationship that cannot be presented clearly without them.
- [ ] Review the candidates in a full-screen Studio-sized viewport and Diagram Detail, with source clarity considered alongside the SVG.

**Checkpoint:** classify each remaining problem as information design, ordinary authoring iteration, Mermaid layout limitation, or unresolved. Keep any small local Mermaid improvement that is useful. Continue to D2 when the comparison remains informative; Mermaid does not need to fail first.

### DMM-2.1 — Compare Free D2 With ELK

- [ ] Pin and record the evaluated D2 version and bundled ELK invocation without checking a platform-specific binary into the repository.
- [ ] Recreate only the hardest remaining bounded candidate, adding a second candidate only if one result cannot demonstrate a recurring class of problem.
- [ ] Compare D2 containers, orthogonal routing, SQL-table or class shapes, source structure, and explicit styling with the best Mermaid candidate rather than the original first draft.
- [ ] Render deterministic SVG and probe it through the current sanitizer, recording removed elements, attributes, styles, accessibility metadata, and visible losses. D2 Markdown labels and SVG `foreignObject` output receive no assumed exception.
- [ ] Compare light and dark behavior, standalone detail presentation, source editing, and the operational cost of a native renderer dependency.
- [ ] If D2 is useful, describe the smallest local source-to-SVG integration and its exact files, rough production/test diff, and retained authoring contract.

**Checkpoint:** decide pragmatically whether D2 is useful enough to retain, defer, or leave as an occasional external tool. It does not need to win every criterion; the improvement only needs to justify its actual local maintenance cost.

### DMM-2.2 — Decide And Transfer

- [ ] Record concise comparison notes covering the prompts above and the evidence behind the material conclusions.
- [ ] State where Mermaid remains the default and whether D2 is rejected, deferred, or recommended for a bounded specialist role.
- [ ] If Mermaid refinements should replace a retained map, present the exact source-only changes for review before updating current documentation.
- [ ] Retain a bounded local Mermaid ELK or D2 integration within DMM-2 when it is useful and its exact shape has been reviewed. Use canonical `.d2` source producing persistent SVG before considering a second inline browser renderer.
- [ ] Update [Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565) for any retained local authoring, rendering, accessibility, SVG, or Diagram Detail contract. Route broader public ownership into a follow-on only if it is actually wanted.

**Completion gate:** record what was tried, what proved useful, what was retained or deferred, and how the current diagrams should be authored. Any retained local integration has focused verification and an honest maintenance note; no broader public capability is implied.

## Reference Baseline

- [Data Models Diagrams](/docs/?scope=studio&doc=d-20260802-123451-d0e52e) owns the retained-map method, viewport priority, useful Mermaid types, and maintenance model.
- [Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565) owns the shipped Mermaid and SVG lifecycle.
- [Mermaid layouts](https://mermaid.js.org/config/layouts.html) documents ELK as an available alternative to the default Dagre layout.
- The official [`@mermaid-js/layout-elk`](https://www.npmjs.com/package/@mermaid-js/layout-elk) package documents the separate install-and-register contract. The current local dependency is visible through `docs-viewer/build/mermaid/package-lock.json`; the managed asset copy is owned by `docs-viewer/build/mermaid/scripts/sync-browser-asset.mjs`.
- [D2 layout engines](https://d2lang.com/tour/layouts/) and [D2 ELK](https://d2lang.com/tour/elk/) describe the free comparison surface.
- [D2 SVG exports](https://d2lang.com/tour/exports/) records injected CSS and possible `foreignObject` output that must be assessed against `docs-viewer/services/docs_svg_sanitizer.py`.

## Not In Scope

- replacing Mermaid as the general-purpose diagram language by assumption;
- checking a platform-specific D2 binary into the repository;
- evaluating proprietary TALA during the first bounded comparison;
- automatically expanding a useful local integration into public runtime or publication ownership;
- changing every retained diagram or producing an exhaustive renderer benchmark;
- relaxing public SVG sanitization or trust boundaries merely to accommodate a candidate;
- treating visual novelty as evidence of maintainability; or
- adding automatic graph generation, schema extraction, or drift enforcement.
