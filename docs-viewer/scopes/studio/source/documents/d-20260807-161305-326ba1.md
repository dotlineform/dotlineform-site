# SSP-6.0 — Uncataloged And Missing Source Files Sanity Note

## Outcome

SSP-6 fits the current architecture as two independent local Docs Viewer reports. **Uncataloged Files** starts from exact existing Work source directories and compares their direct ordinary files with complete canonical Work source paths. **Missing Source Files** starts from each complete canonical Work source declaration and checks its exact file. They share catalogue and contained filesystem inputs but not a response, row grain, report mode, or presentation module.

The gate is complete. SSP-6.1 may begin only after explicit implementation approval; no producer, endpoint, report registry, browser module, external report-host document, Studio retirement, or generated report behavior changes at SSP-6.0.

## Confirmed Report Contracts

- Uncataloged Files derives each distinct represented directory from `project_folder` plus optional `project_subfolder`, scans only that directory's direct ordinary non-hidden files regardless of extension, and excludes known Work-detail directory trees. Folder displays the real directory relative to the `projects/` root, such as `wa/ink`; File name preserves the discovered filesystem spelling.
- A discovered file is catalogued when it is the same existing filesystem object as at least one complete canonical Work source path. The producer must compare resolved identity rather than raw Unicode path strings and must not rewrite the canonical record or displayed filesystem name.
- Activating an Uncataloged Files filename uses the existing encoded target `projects/<represented-directory>/<actual-filename>` and `/docs/open-local-target`. The existing service revalidates configured-base containment and calls Finder reveal with `open -R` for a file; no absolute path enters the response or browser state.
- Missing Source Files independently constructs `project_folder[/project_subfolder]/project_filename` for each complete Work declaration and applies direct file semantics. It emits one row per missing Work, including when several Works name the same missing path; incomplete source declarations remain outside this report rather than becoming a third diagnostic.
- Missing Source Files displays Work ID, Work title, and the expected path relative to the `projects/` root. Only Work ID links, using `/studio/catalogue-work/?work=<five-digit-id>`; a nonexistent file has no Finder target.
- Each response contains its versioned report identity and ordered typed rows but no count, total, timestamp, environment/path summary, statistical warning, prose recap, or generated Markdown presentation. The browser renders only the specified columns and rows plus ordinary Run/Refresh, empty, busy, and contained current-error states.

## Confirmed Owners And Fit

- `records_from_json_source` remains the canonical Work and Work-detail reader. SSP-6 composes paths only from the existing canonical fields and does not add `doc_url[]`, file inventory, audit status, or filesystem evidence to `studio/data/canonical/catalogue/*.json`.
- `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` remains the contained source root. The reports do not scan the configured base, unrelated sibling trees, unrepresented project directories, or arbitrary recursive descendants.
- The existing local report registry, loader, management report service, `POST` dispatch, report-host front matter, and report CSS classes are sufficient. SSP-6 adds two explicit report IDs, endpoints, producers, and modules; it does not change or consume the `docs_project_state_report_v2` producer or response.
- The existing local-target service remains the only Finder activation authority. The Uncataloged Files browser module supplies one encoded base-relative file target; the Missing Source Files module has no local activation path.
- The two ordinary parent/report-host documents belong to the local external `dotlineform` scope, have local report access, and remain separate from the `dotlineform/projects` child collection and its lifecycle-created report host.
- The old Studio generator remains untouched until SSP-6.3. Its `IMAGE_EXTENSIONS` constant is currently imported by Work-detail and catalogue API code, so that media-policy owner must be relocated before `studio/services/catalogue/project_state_report.py` can be deleted.

## Current Evidence

The current legacy dry run still scans only top-level image candidates and reports nested canonical paths as missing. A separate read-only exact-path check found that every current complete Work source path resolves to a file; in particular, all current `wa/ink` primary-source paths resolve. This is a current verification snapshot, not a permanent empty-report expectation, so SSP-6.2 requires a genuinely missing fixture.

Work `00894` records the NFC spelling `doll moiré reduced.jpg`, while Finder exposes a canonically equivalent decomposed spelling. The raw filename strings differ, NFC comparison agrees, and `samefile` confirms one filesystem object. SSP-6 must therefore use filesystem identity for existing-file reconciliation and preserve the discovered name for display.

The direct represented-directory inspection found uncataloged candidates with image, video, audio, document, spreadsheet, and working-file extensions, including `.jpg`, `.mp4`, `.wav`, `.pdf`, `.docx`, `.xlsx`, and `.psd`. This confirms that an image allowlist would discard useful evidence; exact filenames and rows matter, aggregate extension counts do not.

Existing focused seams pass when collected against an isolated writable external workspace: `docs-viewer/tests/python/test_docs_local_links.py` and `docs-viewer/tests/python/test_project_state_report_contract.py` completed with 15 passing tests. The initial run against the configured external Docs root stopped during collection because the sandbox cannot write that root; no product assertion ran or failed.

## SSP-6.1 Proposed Footprint

The bounded production change is expected to add `docs-viewer/services/docs_uncataloged_files.py` and `docs-viewer/runtime/js/reports/uncataloged-files-report.js`; extend `docs-viewer/services/docs_management_routes.py`, `docs-viewer/services/docs_management_service.py`, `docs-viewer/config/reports/reports.json`, `docs-viewer/runtime/js/reports/docs-viewer-reports.js`, and `docs-viewer/runtime/js/reports/docs-viewer-report-service.js`; and create one new local external `dotlineform` parent document titled **Uncataloged Files**. Existing Project State source, response, report module, host document, and Studio workflow remain unchanged at this stage.

Focused coverage is expected in new `docs-viewer/tests/python/test_docs_uncataloged_files.py`, `docs-viewer/tests/python/test_uncataloged_files_report_contract.py`, and `docs-viewer/tests/smoke/docs_viewer_uncataloged_files_report_modules.py`, with the existing route-constant test extended only if required. The stage should remain roughly 350–450 production lines plus 300–450 focused test and smoke lines. Material expansion beyond this, a shared mode-driven audit, a generic filesystem report framework, or changes to Project State is a stop-and-review signal.

SSP-6.1 verification should cover complete and incomplete Work declarations, distinct represented directories, optional subfolders, all ordinary extensions, hidden/detail exclusions, duplicate canonical references, filesystem-equivalent Unicode spellings, deterministic ordering, containment, exact Finder reveal targets, table-only response and presentation, current-run failure clearing, report registry/loader/service wiring, local-only access, external report-host generation, focused Python and JavaScript lint, and `git diff --check`.

## Later Blast Radius And Retirement Risks

SSP-6.2 repeats the explicit producer/endpoint/module/report-host shape for Missing Source Files and must not consume the Uncataloged Files response or candidate scan. Its focused evidence must prove row-per-Work behavior, nested paths, Unicode-equivalent existing files, genuinely absent files, exact editor routes, table-only presentation, and public isolation.

SSP-6.3 owns removal of the old Studio route, frontend, APIs, activity contract, configuration, generator entry point, static Markdown, tests, and admin-check registration only after both replacement reports are accepted. It must first move the unrelated image-extension policy to an appropriate catalogue-media owner, then prove that Work-detail and catalogue media behavior is unchanged. It does not delete the Docs Viewer Project State report, producer, endpoint, module, tests, or local report host.

## Stop Condition

Stop before or during SSP-6.1 if implementation requires recursive or arbitrary filesystem discovery, persisted inventories, result counts or generated Markdown, repair/delete/import actions, continuous watching, mutation hooks, a registry or generic audit framework, a combined mode-driven report, Project State relationship changes, browser absolute paths, Unicode rewriting, inferred Work identity, or early retirement of any Studio workflow. Those outcomes require a separately reviewed delivery boundary.
