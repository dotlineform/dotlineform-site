# Edited Docs Review Source Round-Trip

## Result

A user can edit the persistent Markdown sources of one validated Docs Review
package, rebuild its retained preview, visually accept the round trip, and
import the complete edited `source/` folder back to the exact canonical scope
or sub-scope from which the package was prepared.

The edited Markdown folder is the content authority for this Import. The
original returned JSON/JSONL package and trusted export metadata retain
provenance, capability, exact membership, routing, and prepared-source version
evidence; Import does not take document bodies from that original package.

This is one feature because **Build** alone only refreshes a preview, while
source-folder Import without that refreshed preview would remove the user's
explicit review step.

## Workflow

```text
returned JSON/JSONL
  -> validated Docs Review package
  -> edit package-local source/*.md
  -> Build and inspect the retained preview
  -> copy the complete source folder into Import staging
  -> preview and confirm one edited-source-folder Import
  -> overwrite the exact canonical document set
```

Generic Markdown Import remains body-oriented and create-only. A review source
folder is a distinct trusted collection format, not a new interpretation of
arbitrary standalone `.md` files.

## Dependency Order

The feature has completed its authority and explicit Build checkpoints. Its
two sub-scope Import-parity prerequisites are shipped:

1. [Sub-Scope Ordinary Document Import Delivery](/docs/?scope=studio&doc=d-20260730-121423-469e54)
   adds exact-collection ordinary file Import.
2. [Sub-Scope Returned Package Import Delivery](/docs/?scope=studio&doc=d-20260730-102954-1b363f)
   adds exact-collection returned JSON/JSONL package Import through that same
   report workflow.
3. [Edited Docs Review Source Round-Trip Delivery](/docs/?scope=studio&doc=d-20260730-112029-799346)
   has completed ERS-1.1 and is stopped before ERS-1.2 review; it adds one
   shared edited-source format for both top-level scopes and configured
   sub-scopes, together with the Docs Review **Build** action.

Implementing the edited-source format before both parity deliveries would
create a special sub-scope mutation path instead of extending the shared Import
target, planning, confirmation, apply, and rebuild boundaries.

## Stable Contract

- The staged input is one complete `source/` folder materialized by a validated
  Docs Review package. Individual review-source Markdown files are not accepted
  through ordinary Markdown Import.
- Every direct Markdown child has strict canonical front matter and consistent
  review package, profile, export, scope, and optional sub-scope provenance.
- Trusted prepared membership remains authoritative. Missing, extra, duplicate,
  nested, malformed, mixed-package, or cross-collection documents block the
  complete folder.
- The format is overwrite-only. Every `doc_id` must resolve to one existing
  exact `{ scope, doc_id }` or `{ scope, sub_scope, doc_id }` target; title,
  filename, displayed document, and folder name never provide fallback
  identity.
- Review transport fields are validated and removed. Edited body, title, and
  summary may apply; immutable identity, `added_date`, and destination-owned
  metadata remain canonical.
- Preview is write-free and one confirmation covers the complete folder.
  Canonical source versions are revalidated immediately before an all-or-
  nothing source write and the appropriate scope or confined sub-scope rebuild.
- Docs Review **Build** always regenerates the complete active retained preview
  through its existing synthetic Docs Viewer builder. Ordinary reads retain
  conditional repair behavior.
- No automatic watcher, stale-file inference, selected-document Import, partial
  apply, or direct canonical mutation is added to Docs Review.

## Import Dispatch Order

Recognition order is part of the feature contract:

1. integrated edited-review-source recognition receives the untouched staged
   directory and source front matter before generic Markdown handling;
2. one complete valid review source folder enters trusted collection preview;
3. an individual review source is rejected with guidance to stage its complete
   folder; and
4. only an unclaimed ordinary Markdown file or one-document Markdown package
   reaches generic front-matter stripping and create-only Import.

Generic normalization must never strip `review_*` provenance before the
integrated recognizer can validate it, and stripped ordinary front matter must
never become overwrite identity or collection routing.

## Fidelity Boundary

Current `document-content` review source is derived Markdown. Rendering,
conversion, or omitted package assets may have lost source-only or rich
content. The user accepts that result by rebuilding and visually reviewing the
edited package before staging its source folder.

Import reports the derived-source warning and does not reconstruct tokens,
assets, comments, raw embeds, or dependencies from the original JSON/JSONL.

[Full Document Export Delivery](/docs/?scope=studio&doc=d-20260711-012238-8a04a6)
is the separate proposed owner for source-faithful outbound Markdown and asset
transport. It is not a prerequisite for this feature and remains export-only
unless a later delivery explicitly changes its return capability.

## Boundary

In scope:

- one explicit Docs Review Build-to-Import workflow;
- complete edited review-source-folder validation and confirmation;
- overwrite-only scope and sub-scope canonical apply;
- explicit user acceptance of current derived-Markdown fidelity; and
- shared service and browser ownership after sub-scope Import parity.

Not in scope:

- changing generic Markdown Import or treating arbitrary front matter as
  overwrite authority;
- editing or replacing the original returned JSON/JSONL package;
- automatic asset restoration or rich-content reconstruction;
- making the proposed full-source export profile returnable;
- partial folder Import, creates, deletes, moves, or identity changes; or
- implementing either prerequisite inside this feature.
