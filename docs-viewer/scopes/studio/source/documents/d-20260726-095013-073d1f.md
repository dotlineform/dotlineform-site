# Repository Source Documentation And Linting Adoption Delivery

## Complete Result

JavaScript and Python applications across the repository can use one
reproducible source-documentation and lint capability without treating Docs
Viewer as their tooling owner.

The completed result provides:

- repository-owned Ruff and ESLint pins, configuration, installation, and
  direct commands;
- maintained application source boundaries with explicit runtime contexts and
  exclusions;
- useful JSDoc and Python docstrings on new, materially changed, and
  high-value existing contracts;
- clean adopted boundaries for Studio, Admin, Docs Viewer, public-site,
  shared-frontend, and site-tools source;
- normal check-profile coverage that reports its exact maintained targets;
- path-filtered CI enforcement only after the relevant maintained boundary is
  clean.

This delivery was approved for implementation on 2026-07-26.

## Why This Delivery Exists

The Docs Viewer pilot proved practical conventions and low-noise Ruff and
ESLint rules on four representative files. It deliberately located tooling
under `docs-viewer/`, force-excluded other applications, required
delivery-specific explicit paths, and did not join a normal check profile.

Those decisions were correct for the pilot but now prevent Studio and other
applications from adopting the capability without duplicating or
misrepresenting ownership. Repository adoption must replace that pilot
boundary rather than merely remove exclusions from Docs Viewer configuration.

## Benefits And Risks

### Benefits

- New and unfamiliar code gains concise contract information at its source.
- Cheap correctness and unused-code defects are caught before broader tests or
  manual review.
- Studio and other applications can adopt one pinned toolchain while retaining
  their actual runtime and ownership boundaries.
- Maintained scope checks replace fixed specimens and false application-wide
  confidence.
- Local, cloud, check-profile, and CI command shapes become reproducible.

### Risks

- A broad first run can turn historical debt into noisy unrelated churn.
- Generic browser or Python assumptions can hide real application contexts.
- Existing path-bootstrap imports and suppressions can be excused too broadly
  instead of reviewed.
- Automatic fixes can conceal behavioural changes or delete intentionally
  side-effectful imports.
- Premature CI enforcement can block unrelated work before an application
  boundary is clean.

Mitigate these risks through named maintained targets, audit-first cleanup,
bounded source-area adoption, local justified suppressions, and profile or CI
promotion only after a whole maintained boundary passes.

## Decisions

### Repository Tool Owner

Create one repository development-tool owner under `tooling/lint/`. It owns:

- the Ruff development dependency pin and shared Python baseline;
- the private ESLint package, direct dependency pins, and lockfile;
- labelled ESLint configuration blocks for each real JavaScript context;
- maintained target definitions for application and shared source;
- ignored local environments, dependency trees, and caches.

This is a repository development-tool package, not a runtime JavaScript
application or a replacement for feature-local packages. The isolated Mermaid
renderer keeps its own package and lifecycle.

### Commands

Provide repository-root commands with two truthful modes:

- `bin/lint-python <path> [path ...]` and
  `bin/lint-js <path> [path ...]` lint exact submitted new or changed paths;
- `bin/lint --scope <scope-id>` lints the complete maintained boundary for one
  adopted scope.

All commands fail on missing or empty targets and report the resolved paths.
The scope command resolves checked configuration rather than embedding a
historical fixed-file list.

Cut over current documentation and callers and remove the Docs Viewer lint
wrappers in the same change. Do not retain compatibility aliases.

### Shared Baseline And Application Context

The repository owns the initial low-noise rules:

- Ruff `E4`, `E7`, `E9`, and `F`;
- ESLint recommended correctness rules;
- no automatic fixes;
- unused ESLint disable directives are errors.

Applications own:

- maintained source roots;
- browser ESM, Node, worker, or test globals and module settings;
- path-specific exclusions;
- justified local or per-path exceptions;
- the point at which a whole boundary joins normal checks.

Do not use one generic JavaScript globals set across unrelated code. Do not
enable broader Ruff categories, formatting, complexity limits, TypeScript, or
missing-documentation enforcement in this delivery.

### Source Documentation

Retain the proven authoring rules:

- types describe types; comments explain meaning;
- document exported or public APIs when callers need lifecycle, ownership,
  ordering, side effects, failure, invariant, unit, or constrained-value
  information;
- use JavaScript typedefs for stable shared object and callback shapes;
- let Python annotations carry types and use docstrings for domain behaviour;
- do not document trivial helpers or restate signatures;
- simplify or split confused ownership rather than explain it with a long
  comment;
- update a source comment in the same change as its contract.

This delivery does not select or publish generated API/reference pages. JSDoc
and docstrings must be useful in source and editor help without a generator.

## Maintained Target Model

The exact paths are confirmed in RSDL-P0. The initial model is:

| Scope | Python source | JavaScript source |
| --- | --- | --- |
| `studio` | Studio server, services, shared Python, commands, and checks | Studio frontend modules and route modules |
| `admin` | Admin server, checks, commands, and reports | Admin frontend modules and route modules |
| `docs-viewer` | Docs Viewer services and Python builders | Manage-owned and site-owned Docs Viewer browser modules |
| `public-site` | Site validation tooling where not owned by `site-tools` | Public catalogue, search, shell, and theme modules |
| `shared` | Any later repository-shared Python boundary | Shared frontend modules |
| `site-tools` | Site validation package and commands | None currently |

Tests use separate target contexts. Generated data, published payloads, vendor
source, dependency trees, caches, retired source, recovery archives, and
canonical data remain excluded.

The Admin target map is useful ownership evidence but is not itself lint
configuration: it includes non-code families and overlapping public/shared
surfaces. RSDL-P0 should reconcile the two configurations and add a focused
drift check rather than make one silently derive unsupported runtime settings
from the other.

## Starting Evidence

A read-only audit using the pilot's low-noise Python rules and a common browser
ESM ESLint baseline produced the following indicative findings:

| Maintained area | Python | JavaScript |
| --- | ---: | ---: |
| Studio | 59 | 104 |
| Admin | 15 | 12 |
| Docs Viewer active services/build/runtime | 73 | 31 |
| Public-site JavaScript | — | 22 |
| Shared frontend | — | 0 |
| Site tools | 0 | — |

These are planning evidence, not accepted baselines. Tests were excluded and
the JavaScript audit did not yet model every final application context.

Studio's Python findings included undefined names, unused imports and
variables, import placement, and loop-variable shadowing. Its JavaScript
findings were mainly unused variables and useless assignments, with smaller
numbers of caught-error preservation, empty-block, escape, and undefined-name
findings.

Every finding must be classified as:

- genuine defect;
- safe mechanical cleanup;
- design or ownership review;
- justified local exception;
- configuration or runtime-context error.

Do not use a checked blanket baseline file to hide known findings. Adopt clean
directories progressively if a whole application cannot be cleaned in one
reviewable batch.

## Implemented Baseline

RSDL-P0 replaced the indicative scan with checked application contexts. The
accepted audit before cleanup was:

| Maintained scope | Files | Python findings | JavaScript findings |
| --- | ---: | ---: | ---: |
| `shared` | 5 | — | 0 |
| `site-tools` | 4 | 0 | — |
| `studio` | 184 | 30 | 48 |
| `admin` | 41 | 5 | 3 |
| `public-site` | 25 | — | 3 |
| `docs-viewer` | 240 | 122 | 15 |
| `tests` | 209 | 43 | — |

The accepted maintained total is 708 files: 436 Python and 272 JavaScript.
The checked target map is `tooling/lint/targets.json`. A focused contract test
keeps application roots visible to the broader Admin target map without
deriving lint globals or source roles from it. Shared frontend and the
multi-owner test context remain explicit lint-only boundaries.

Findings resolved as:

- genuine defects: missing Catalogue lookup-refresh imports, an undefined
  Studio Tag Registry status call, and stale direct-script test invocations;
- safe cleanup: unused imports, values, assignments, and unreachable local
  wrappers;
- reviewed exceptions: exact path-bootstrap entrypoints and active façade
  re-exports only;
- configuration: separate browser ESM blocks and explicit generated, vendor,
  canonical, retired, dependency, cache, and Processing exclusions.

No baseline file, automatic fix, formatter, TypeScript, or compatibility alias
was introduced.

## Shipped Capability

- `tooling/lint/` owns Ruff `0.16.0`, ESLint `10.8.0`, `@eslint/js`
  `10.0.1`, `globals` `17.7.0`, both configurations, the lockfile, and
  maintained targets.
- `bin/lint-python` and `bin/lint-js` require eligible explicit paths.
  `bin/lint --scope <scope-id>` resolves a complete checked boundary and
  reports its language, file count, and roots.
- `.codex/setup.sh` and the dev container install the isolated lint
  environments; the Mermaid renderer remains independent.
- `source-lint` is the intentional aggregate profile and is a child of
  `full`. App-owned profiles include their relevant maintained scope without
  duplicating execution in combined runs.
- `.github/workflows/source-lint.yml` installs from the checked pins and runs
  all adopted scopes when their source, configuration, setup, or lint tooling
  changes.
- New runner and profile contracts prove missing, empty, excluded, unknown,
  Python-defect, JavaScript-defect, scope-drift, coverage-summary, and
  aggregate-deduplication failures.
- The new runner contracts carry source docstrings for path rejection,
  repository-local tool ownership, and evidence reporting. Other cleanup did
  not change exported contracts and did not justify documentation churn.

## Backfill Order

Backfill source documentation by value and risk:

1. shared and cross-application contracts;
2. exported JavaScript options, callbacks, events, controllers, and lifecycle
   boundaries;
3. Python services, adapters, value objects, write plans, builders, commands,
   and error translation;
4. stateful or side-effectful modules that repeatedly require source
   archaeology;
5. complex code where documenting the contract exposes a useful
   simplification.

Do not backfill trivial accessors, obvious wrappers, generated/vendor source,
or test functions whose names and fixtures already state the contract.

## Processing Boundary

`processing/` remains a separate Java/Processing project. Its recovered
sketches, bundled library examples, templates, and active projects cannot be
treated as one maintained application source root.

This delivery records but does not invent its future lifecycle:

- identify active first-party Processing source separately from recovered,
  example, library, and template material;
- use Javadoc rather than JSDoc for Java-mode public contracts;
- select Processing-aware Java formatting, linting, build, and test commands
  only when that project lifecycle is defined.

Repository-wide Python/JavaScript adoption must not claim Processing coverage.

## Out Of Scope

- Java/Processing tool selection or source cleanup
- generated API/reference pages
- repository-wide TypeScript, `checkJs`, or `jsconfig.json`
- Python or JavaScript formatting
- broad automatic fixes
- complexity, nesting, parameter-count, or missing-documentation enforcement
- runtime bundling or transpilation
- changes to the Mermaid renderer package
- comments on every public symbol or historical source file
- behavioural refactors that are not required to resolve a reviewed finding

## Completion Gates

- Tool pins, lockfiles, configuration, setup, and commands are repository-owned
  and reproducible from a clean supported environment.
- No application depends on Docs Viewer paths to run source linting.
- Explicit-path commands fail on empty or fully ignored targets.
- Maintained scope commands resolve checked, reviewable source boundaries.
- Studio, Admin, Docs Viewer, public-site, shared-frontend, and site-tools
  maintained boundaries pass their selected low-noise rules.
- Runtime globals and module settings match each JavaScript context.
- Generated, vendor, canonical-data, retired, recovery, dependency, and cache
  paths cannot create false coverage.
- New and materially changed high-value contracts follow the proven JSDoc and
  docstring conventions.
- Existing suppressions reached by enabled rules have been reviewed and are
  fixed or locally justified.
- Normal profile and CI claims name their actual maintained surfaces.
- Processing remains explicitly outside the Python/JavaScript coverage claim.
- Stable documentation reflects the shipped commands, ownership, extension
  method, and remaining gaps.
- No compatibility aliases, generated reference site, formatting churn,
  TypeScript adoption, or unrelated behavioural cleanup entered the delivery.

Checks, Runtime Dependencies, Local Setup Toolchain, Source Tree Ownership,
repository guidance, and generated Studio docs payloads.

- command/profile contracts: 15 tests passed;

- Docs profile: 403 tests passed, 1 skipped; source lint, Studio docs build,

backfill, and Processing lifecycle/tool selection remain separate outcomes.
