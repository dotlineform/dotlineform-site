# Folder Picker

Use Folder Picker to choose one directory from the configured Projects-root tree through lazy parent and direct-child navigation. It is app-neutral but intentionally Projects-domain-specific; it is not a generic filesystem browser.

## Authority

- behaviour: `shared/frontend/js/folder-picker.js`
- styles: `shared/frontend/css/folder-picker.css`
- current consumer state: `docs-viewer/runtime/js/import/docs-import-source-selection.js`
- current module handoff: `docs-viewer/runtime/js/management/docs-viewer-management-import-controller.js`

Docs Viewer serves the component through the explicit `/docs-viewer/runtime/js/shared-frontend/folder-picker.js` route. Search that route and direct imports of `shared/frontend/js/folder-picker.js` for the current consumer set.

## Stable Structure

`createFolderPicker(root, options)` owns:

- lazy loading of one current directory and its direct-child directories
- the current Projects breadcrumb and parent navigation
- empty-folder presentation inside the control
- active-descendant keyboard navigation through direct children
- submission only when the current server-returned marker is selectable
- teardown of its rendered control

The caller owns:

- the service route, authorization, confinement, and directory validation
- initial or remembered source state and invalid-state recovery
- modal or page composition, action buttons, and focus handoff
- message-modal presentation for load or submission failures
- persistence, destination, file selection, mutations, and workflow status
- mapping the returned directory marker into app state

## Returned Boundary

The injected loader receives `{directory}` and returns the exact current marker, its selectable state, its parent marker, and direct-child rows. The current record shape uses `source_directory` for child markers. `onSubmit({directory})` receives only the loaded current marker after `current_selectable: true`.

The controller exposes `ready`, `focusPreferred()`, `getDirectory()`, `submit()`, and `destroy()`. Exact payload validation, option names, status text, and controller behaviour remain code-owned.

## Relationship To File Picker

[File Picker](/docs/?scope=studio&doc=d-20260614-155753-e87844) chooses files from a loaded folder and one optional subfolder level, including single/multiple selection. Folder Picker chooses a directory at arbitrary depth and never lists or selects files. Neither component extends the other.

Do not migrate the Works Editor merely to create a second consumer. If a future workflow needs both arbitrary-depth directory navigation and file selection, first decide whether composition preserves the two contracts more clearly than extending either component.

## Method And Weak Spots

- The exact root marker `.` and visible root label `Projects` are currently component-owned. Parameterize or adapt those values before claiming a non-Projects consumer.
- Direct-child records currently use the `source_directory` field introduced by Docs Import. A future consumer should use an explicit adapter or a reviewed contract change rather than adding record aliases.
- The component has one current consumer. Its shared placement reflects a reviewed cross-app Projects-navigation responsibility, not speculative reuse.
- Loader and submission failures are reported to the caller; service errors, message presentation, and security policy remain caller-owned.

## Verification

Protect loader-response agreement, empty-folder state, propagated load errors, parent and root navigation, keyboard active selection, selectable-marker submission, and destroy behaviour in a focused module check. Use manual browser checks for modal density, pointer feel, and final focus handoff owned by the consumer.
