# Data Model Maps

## Purpose

Data Model Maps make the repository's growing set of canonical JSON, Markdown sources, manifests, lookups, indexes, and runtime projections understandable as one system without collapsing their different responsibilities into one enormous schema diagram. Their primary use is to explain important current relationships and to give feature specifications a consistent way to show a small current-state **before** map beside a clearly proposed **after** map.

The feature combines small logical ERDs with projection-lineage diagrams and concise artefact registers. ERDs explain identity and cardinality. Lineage diagrams explain which authority produces which projection and who consumes it. Registers preserve the file, ownership, visibility, and refresh details that neither diagram type expresses well.

## Complete Feature Outcome

One durable **Data Models Diagrams** document beneath Architecture explains how to produce and interpret the maps, including shared notation and commentary that applies across diagrams. Each child document owns one concern-specific diagram, its associated notes, explicit omissions, and possible later enhancements. The Docs index tree is the available-diagram list, so the parent does not duplicate it as a separately maintained table.

A reader can identify canonical source, generated projections, producers, consumers, access boundary, and refresh behavior without searching independently through every builder, registry, and payload directory.

The initial map set covers:

- the Catalogue logical model;
- Docs Viewer document and projection lineage; and
- cross-system relationship projections such as Semantic Tokens, Tags, and Project State.

Each child remains subordinate to current code, configuration, schemas, and focused tests. The maps explain the system; they do not become a second executable schema authority or an exhaustive diagram inventory. Feature specifications may reuse the notation for before/after diagrams without registering every diagram beneath the durable parent.

## Delivery Position

DMM-1 completed on 2026-08-02. The durable Architecture parent and three diagram children are published in the Studio working projection, their full-screen presentation and authority links have been reviewed, and their explicit omissions are recorded. Studio-only diagram acceptance prioritises a laptop or monitor viewport and Diagram Detail; narrow readability is required only by an owning public scope. No production implementation was part of the feature.

DMM-2 is proposed as a follow-on investigation. It gives Mermaid a bounded second pass using better view partitioning and the ELK plugin before comparing the strongest remaining case with free D2 and ELK. The CLI/build path already includes Mermaid's ELK plugin, while managed inline Studio needs a small explicit registration before it can use that layout. Because Studio is local, DMM-2 may retain a bounded Mermaid ELK or D2 integration when it is useful; broader public runtime, publication, or trust-boundary changes remain explicit follow-ons only when they are actually wanted.

## Boundary

The feature does not introduce a graph database, schema registry, query language, interactive explorer, automatically generated whole-repository graph, exhaustive diagram catalogue, or replacement for existing architecture and contract documents. Automatic generation or new lint infrastructure requires a later independently justified delivery.

[Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565) owns Mermaid authoring and rendering. [Projection Contract](/docs/?scope=studio&doc=d-20260523-222005-1085b2) remains the authority for canonical, Studio, Docs Viewer, and public projection boundaries.
