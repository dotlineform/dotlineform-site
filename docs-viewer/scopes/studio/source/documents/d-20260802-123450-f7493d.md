# Data Model Maps

## Purpose

Data Model Maps make the repository's growing set of canonical JSON, Markdown sources, manifests, lookups, indexes, and runtime projections understandable as one system without collapsing their different responsibilities into one enormous schema diagram.

The feature combines small logical ERDs with projection-lineage diagrams and concise artefact registers. ERDs explain identity and cardinality. Lineage diagrams explain which authority produces which projection and who consumes it. Registers preserve the file, ownership, visibility, and refresh details that neither diagram type expresses well.

## Feature Documents

- [Data Model Maps Concept And Examples](/docs/?scope=studio&doc=d-20260802-123451-d0e52e) — map types, notation, a Catalogue ERD, a Docs Viewer projection example, and boundaries between logical entities and physical artefacts.
- [DMM-1 — Data Model Maps Foundation Delivery](/docs/?scope=studio&doc=d-20260802-123452-6a2fd3) — inventory the current authorities, freeze the notation through a readability spike, and publish the first bounded durable map set.

## Complete Feature Outcome

One durable Data Model Maps index routes to a small set of concern-specific maps. A reader can identify canonical source, generated projections, producers, consumers, access boundary, and refresh behavior without searching independently through every builder, registry, and payload directory.

The initial map set covers:

- the Catalogue logical model;
- Docs Viewer document and projection lineage; and
- cross-system relationship projections such as Semantic Tokens, Tags, and Project State.

Each map remains subordinate to current code, configuration, schemas, and focused tests. The maps explain the system; they do not become a second executable schema authority.

## Delivery Position

DMM-1 is proposed documentation work. Its first checkpoint must prove that the mixed ERD, flowchart, and register format remains legible with the pinned Mermaid renderer before the complete inventory is written. No implementation work begins merely because this feature exists.

## Boundary

The feature does not introduce a graph database, schema registry, query language, interactive explorer, automatically generated whole-repository graph, or replacement for existing architecture and contract documents. Automatic generation or new lint infrastructure requires a later independently justified delivery.

[Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565) owns Mermaid authoring and rendering. [Projection Contract](/docs/?scope=studio&doc=d-20260523-222005-1085b2) remains the authority for canonical, Studio, Docs Viewer, and public projection boundaries.
