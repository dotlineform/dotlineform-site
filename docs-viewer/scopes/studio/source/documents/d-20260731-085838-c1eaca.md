# Source Editor Image Presentation Delivery

## Status And Purpose

Proposed as **SIP-1** under
[Roadmap](/docs/?scope=studio&doc=d-20260428-000000-f5ff18).
This document defines a bounded delivery; it does not start implementation.

SIP-1 extends the source editor's existing **Add image…** workflow with one
consistent figure presentation. Caption, summary, and image placement stay in
the Add image modal. A separate format chooser is deferred until more than one
real fragment format exists.

## Complete Outcome

An author can add a staged image and choose:

- required image alt text;
- the existing checked-by-default **Add caption** option;
- independently editable caption text, initially suggested from the alt text;
- optional short summary text; and
- **Full column**, **Image left**, or **Image right** from one grouped placement
  control.

Unchecked **Add caption** preserves the current plain Markdown image insertion.
When it is checked, the server returns one semantic `<figure>` /
`<figcaption>` source fragment. Full-column presentation places the text below
the image. Left and right presentation use equal visual columns for the image
and text, then collapse to image followed by text on narrow screens.

The inserted source remains readable and manually editable. Existing authored
images and caption spans are not migrated.

Text is aligned left or right so that it mirrors the image, as shown in the image below:

## Fragment Ownership

- The browser sends semantic values only: alt text, caption, summary, and one
  allowlisted placement value. It does not send HTML, CSS classes, inline
  styles, or arbitrary dimensions.
- A focused server module owns validation, escaping, and source-fragment
  generation. The staged-media service continues to own publication,
  preview/apply orchestration, and response shaping.
- Preview and apply call the same fragment builder so the confirmed source is
  the source inserted after publication.
- The initial module uses explicit small builder functions for plain images,
  figure images, and file links. It does not load template files or introduce
  a general template, registry, or plugin framework.
- A future fragment may add another explicit builder and allowlisted format
  only when that format has a concrete user contract. The Add image modal
  gains no format selector in SIP-1; a separate format modal is considered
  only after multiple formats make it useful.
- The portable Docs Viewer stylesheet owns figure layout and responsive
  behavior so Manage, public, and embedded-detail readers share one result.
  Management CSS owns only the modal controls.

Caption and summary are plain text in SIP-1. The server escapes both because
the current trusted authored-content renderer permits raw HTML and does not
sanitize generated source fragments.

## Modal Contract

The existing Add image modal remains the only workflow surface.

- **Staged file** and **Alt text** retain their current roles.
- **Add caption** retains its current default.
- When captioning is enabled, caption, summary, and placement controls are
  conditionally enabled in the same modal.
- Caption begins with the suggested alt text but becomes independent once
  edited. It is required while **Add caption** is checked, and changing visible
  caption copy must not silently rewrite alt text.
- Summary is optional supporting copy, not general document prose, and renders
  at the Docs Viewer caption size.
- **Full column** means the complete Docs Viewer prose measure, not a
  viewport-bleed layout.
- **Image left** and **Image right** describe visual placement. Source and
  accessible reading order remain image, caption, then summary.
- **Add file…** remains unchanged.

## Boundary

In scope:

- one semantic figure fragment;
- modular code-owned fragment generation without template files;
- caption text separate from alt text;
- optional plain-text summary;
- three fixed placement choices;
- equal-column desktop presentation and narrow-screen stacking;
- server-side value validation and HTML escaping;
- identical preview/apply fragments;
- portable reader CSS; and
- focused service, fragment, runtime-module, and manual visual evidence.

Not in scope:

- a separate format modal or format selector;
- a general fragment/template registry, schema-driven modal, or plugin system;
- arbitrary HTML, Markdown summary, CSS classes, widths, alignment, or style
  input;
- viewport-bleed, galleries, carousels, overlays, lightboxes, crop controls,
  focal points, or responsive source selection;
- rewriting existing document source;
- changing media storage, publication, collision, SVG sanitization, Mermaid,
  logical-token, or source-editor save behavior; or
- any change to **Add file…**.

## Likely Authority

- `source-editor-media.js` owns the Add image modal controls and semantic
  request values.
- A focused `docs_staged_media_fragments.py` module owns fragment validation,
  escaping, and code-based builders.
- `docs_staged_media_service.py` retains staged-media preview/apply and
  provider-independent publication.
- `site/docs-viewer/static/css/docs-viewer.css` owns the portable figure
  component and responsive layout.
- Existing staged-media Python tests own exact fragment and request behavior;
  a focused runtime-module check should protect semantic request projection
  without asserting ordinary modal choreography or visual layout.
- [Media And Asset Handling](/docs/?scope=studio&doc=d-20260514-184303-7914e2)
  receives the durable extension method. [Source Editor Endpoints](/docs/?scope=studio&doc=d-20260607-222033-4b1d77)
  receives only the shipped request/response fields.

Implementation may adjust filenames after inspection, but must retain these
ownership boundaries.

## Delivery Checkpoints

### [ ] SIP-1.0 — Fragment And Service Contract

- [ ] Add the focused code-owned fragment module with explicit plain-image,
  figure-image, and file-link builders.
- [ ] Validate caption, summary, and placement once and escape every generated
  HTML text or attribute boundary.
- [ ] Route preview and apply through the same builder while preserving plain
  unchecked images and all existing file behavior.
- [ ] Prove exact full-column, left, right, absent-summary, invalid-placement,
  and hostile-text output with pure/service tests.

Stop for review of generated source shape and service boundaries before UI and
CSS work.

### [ ] SIP-1.1 — Add Image Controls And Reader Presentation

- [ ] Keep caption, summary, and grouped placement controls in the existing Add
  image modal; do not add a format workflow.
- [ ] Pass semantic values through the current staged-media preview/apply
  request and insert only the returned server fragment.
- [ ] Add portable full-column and split figure styles with equal columns,
  caption-size text, and narrow-screen image-first stacking.
- [ ] Confirm current collision confirmation, dirty-buffer insertion, SVG and
  Mermaid paths, and **Add file…** remain unchanged.

Stop for manual review of the real modal and representative full, left, right,
and narrow-screen rendering.

### [ ] SIP-1.2 — Focused Verification And Authority Transfer

- [ ] Run fragment/service tests, explicit Python and JavaScript lint, the
  smallest route/module check that proves request wiring, and
  `git diff --check`.
- [ ] Inspect generated source plus rendered Manage, public, and embedded-detail
  examples without treating one visual sample as subsystem-wide evidence.
- [ ] Update the durable media extension method and exact staged-media endpoint
  contract from shipped behavior.
- [ ] Independently review the final diff for duplicated fragment ownership,
  unsafe interpolation, public/manage CSS drift, compatibility residue, and
  unplanned format machinery before changing status.

## Completion Evidence

SIP-1 is complete only when:

- unchecked images still insert ordinary Markdown;
- captioned images insert one escaped semantic figure fragment;
- preview and apply return identical source for the same request;
- all three placements render consistently in Manage, public, and
  embedded-detail content;
- split layouts stack image-first at a narrow width;
- existing raster, SVG, Mermaid, collision, dirty-buffer, and file-link
  contracts remain working;
- no template files, format modal, arbitrary styling input, or generic fragment
  framework were introduced; and
- durable media and endpoint documentation describe only the shipped contract.

No implementation begins from this document until SIP-1 is accepted for
delivery.
