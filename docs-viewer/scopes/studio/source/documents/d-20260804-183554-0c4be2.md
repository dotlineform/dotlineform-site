# SSC-1.1 — Contract Rename Checkpoint Evidence

## Outcome

The configured extension and its source/consumer vocabulary now use `sub_scope_customisation` in Python/JSON and `subScopeCustomisation` in browser state. The configuration shape remains exactly `{id, settings}`. Default sub-scopes still receive no descriptor, current manifest contribution data remains under its distinct `customisation` namespace, and no user-visible report, metadata, import, action, or publication behavior changed.

The registry module is now `docs_subscope_customisations.py`. Its config/definition types, helpers, callers, browser configuration, fixtures, and access-agreement checks use the unified term. Unknown sub-scope configuration fields fail strictly, so a stale or parallel extension key cannot silently select the default.

The Projects registration is selected by the configured exact collection. Its former Python collection allowlist and browser comparison with the literal `dotlineform/projects` target have retired. The browser factory still requires an exact non-empty `{scope, sub_scope}` target, and the configured registry ID still selects the Projects definition and loader.

- Analysis Tags and Projects retain the same IDs, normalized settings, manifest data, metadata/import hooks, browser factories, and Manage-only access.

- Analysis Tags public and Manage manifests were rebuilt with zero writes; their contribution envelopes and document rows are byte-current.
