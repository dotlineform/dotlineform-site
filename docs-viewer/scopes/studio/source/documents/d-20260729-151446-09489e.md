# Tag Link Management Delivery

## Target Result

Tag Registry stores an ordered array of optional one-way canonical document
locations for each tag. Tag Registry and Edit Tag present current document
titles, Edit Tag can search published document titles and add a selected
location through a reusable picker or remove an association, and the registry
no longer stores or presents a tag `description`. Tag Editor searches published
Analysis locations only. Shared results retain report context, while Tag
Registry's compact title-only rows suppress it; scope context appears only for
consumers configured with more than one scope.

The relationship and independent-lifecycle boundary remains owned by
[Tag-document linking](/docs/?scope=studio&doc=d-20260726-211842-cc8f6c).

As a prerequisite, New Tag stopped auditing every existing registry
association. Its job remains one atomic result: validate the submitted tag,
allocate and create one fresh Analysis `tags` document, append the new linked
registry row, rebuild the child projection, and report the outcome. The later
schema cutover records that freshly created canonical location at `doc_url[0]`.

## Status And Order

**Current state:** TLM-0 through TLM-5 are complete. The shipped behavior and

## Frozen Data Contract

The next registry schema uses `doc_url` as an ordered array of canonical
same-origin Docs Viewer locations:

```json
{
  "doc_url": [
    "/analysis/?doc=d-20260624-213316-478639&subdoc=d-20260727-225608-63967a",
    "/docs/?scope=studio&doc=d-20260729-151446-09489e"
  ]
}
```

- `doc_url: []` means the tag is not linked. New Tag writes its newly created
  Analysis `tags` location at index `0`; later picker selections append in
  commit order.
- The URL is the association identity because it preserves the chosen report
  context. The same source document may therefore appear more than once through
  different canonical report URLs.
- The same canonical URL cannot occur twice within one tag, but any number of
  tags may reference it. Add and remove operations identify the complete URL
  rather than relying on a mutable array index.
- A canonical URL is a normalized repository-relative viewer route produced by
  Docs ownership. It includes the configured viewer base and scope behavior,
  the exact report-host document where applicable, and the exact displayed
  document. It excludes fragments, transient filters, and arbitrary query
  state unless a later contract deliberately makes them part of location
  identity.
- It never stores a scheme or host. The same root-relative value resolves
  against the local origin while working locally and the public origin after
  publication.
- Each scope uses its configured canonical viewer base. Analysis locations use
  `/analysis/?doc=<report-doc-id>&subdoc=<document-id>`; they do not store a
  local `/docs/?scope=analysis...` alternative. A scope whose canonical base is
  `/docs/` still uses that configured route.
- Tag Registry UI can add only a URL returned by the supported
  document-location provider; it exposes no free-form URL or ID input. The
  write API validates the complete array's supported canonical shape and
  duplicates, but does not recheck current provider membership because a
  selected location may become unavailable before confirmation.
- Stale URLs remain stored, visible, and removable. No title match, selected
  parent, displayed document, or alternative report may silently replace them.

The registry does **not** store document or report titles. A shared
document-location provider resolves each stored URL to current presentation
data such as
`{url, scope_id, document_title, report_title, available}`. Picker results
represent actual report placements, not just documents: the same source
document may appear as separate choices such as `bird-nerve — All Tags` and
`bird-nerve — Made-up Tags`.

The provider searches public projections, not management or source
collections. Its initial coverage is published Analysis and Library documents
plus their configured published sub-scopes. The picker adapter requires a
non-empty consumer-supplied `scopeIds` allowlist and has no implicit
all-supported-scopes default. Tag Editor supplies `["analysis"]`. The provider
loads and returns only records from the requested supported scopes. Top-level
public search records and sub-scope placement records contribute one searchable
result per canonical URL. Hidden, manage-only, local-only, and unpublished
documents are absent, so every new selection has a public route that also
resolves against the local origin during local work.

Provider records always retain `scope_id`. A picker configured with one scope
omits the redundant scope label; a picker configured with more than one shows
it. Report context remains visible when present because distinct report
placements can have distinct canonical URLs. Scope-label visibility follows
the configured allowlist length, not the scopes represented by the current
query results. Consumers may suppress report context in their presentation
without removing it from the committed record; Tag Registry does so while
duplicate visible titles remain uncommon.

The picker commits one reusable result such as
`{url, scope_id, document_title, report_title}`. Consumer adapters determine
how it is written:

- Tag Registry stores `url` in `doc_url[]` and renders it as a title link in
  the Registry table.
- Ordinary document authoring inserts `url` as the destination of a Markdown
  link.
- A future document-capable Semantic Token adapter uses `url` as the generated
  target-lookup `href`; Semantic Token source continues to store its registered
  token identity rather than embedding a raw URL in token syntax.

These are three uses of the same selected canonical URL, not three picker or
route contracts. Plain-link and Semantic Token authoring remain later
consumers; this delivery proves the shared result through Tag Registry first.

## Frozen Interaction Contract

- Edit Tag shows `doc_url[]` as title-only pills in array order. Each pill title
  links to its exact configured public-preview location; identical visible
  titles need no extra disambiguation.
- The picker is permanently visible with `scopeIds: ["analysis"]`. It searches
  published Analysis titles in a fixed four-result scrolling viewport and
  omits redundant scope and report context. Selecting a result fills the search
  field and enables the adjacent **+**; **+** appends that exact URL to the
  draft. The placeholder explains the field without a separate visible label;
  the input retains an accessible label. Results use the input font size, with
  a paler pointer hover than the committed selection highlight.
- The picker excludes an exact URL already present in the draft. A different
  URL with the same document title remains a valid result.
- Each pill owns a direct **×** removal action. It changes only the modal draft;
  it does not navigate, delete the document, or mutate canonical data.
- Edit Tag **Save** writes the complete revised `doc_url[]` with the other
  accepted tag edits in one atomic registry mutation. Cancel discards all draft
  additions and removals. A successful save closes without echoing the backend
  audit summary into the page; errors and warnings remain visible.
- A URL that no longer resolves is shown as `Unavailable document`, remains
  linked to its exact stored location, and can be removed. The stored URL is not
  repaired or replaced.
- The Tag Registry table replaces **description** with **documents**. It renders
  document titles as comma-separated links in `doc_url[]` order and renders
  `—` for an empty array. Equal titles remain equal; no report label is added.
  Local hrefs resolve against Studio's configured public-preview base.
- Pill **×** is deliberately distinct from Tag or document deletion.

This is the current TLM-4 review contract. Ordinary-width and narrow-width fit,
tactile selection behavior, and final wording are decided against the working
UI.

The schema cutover retires the tag-row `description` field. This does not alter
alias descriptions or the independent contents of existing linked documents.

## TLM-0 Prerequisite Contract

Before TLM-0, the creation planner called `registry_document_ids`, which
validated the complete registry as though New Tag owned association integrity.
It rejected creation when any existing row had a missing, duplicate,
non-immutable, or non-resolving `doc_id`.

That is wider than the creation responsibility:

```text
submitted New Tag
  -> validate new tag_id, scalar group, and description
  -> reject an existing tag_id
  -> allocate one fresh document identity
  -> create one new document and linked row atomically
  -> rebuild the exact Analysis/tags projection

existing registry associations
  -> preserve unchanged
  -> do not audit or repair during New Tag
```

TLM-0 is deliberately limited to that current-schema prerequisite.
`description` removal and `doc_url[]` creation start after its review gate.

New Tag retains the guards required for its own write:

- require the supported registry version and a registry `tags` array;
- validate the submitted fields and reject an existing `tag_id`;
- resolve the configured direct-child document root and confine the new path;
- allocate the immutable ID directly from the document timestamp and
  cryptographic token, without supplying registry or source identities; and
- preserve the existing atomic Registry/document write, targeted rebuild,
  compensation, activity, response, and manual-patch contracts.

The planner does not inspect any existing registry `doc_id`, inventory document
IDs for allocation, compare the generated ID with registry rows, or preflight
the destination's existence. `write_text_atomic_new` is the sole collision
boundary: it refuses to overwrite a real destination if the generated identity
does collide. That create-only write is filesystem safety, not registry
association validation. Focused association audit and repair belong to the
later link-management workflow.
