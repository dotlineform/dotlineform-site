# Docs Import Folder Source Selection Concept And Architecture

## Purpose

This document owns the product and architecture contracts for [Docs Import Folder Source Selection](/docs/?scope=studio&doc=d-20260801-190502-6927fb). It separates reusable folder navigation from Docs Import policy without requiring an existing modal to absorb a second interaction or hiding shared capability inside one consumer.

## Product Invariants

- Import staging remains the default source.
- The user can browse and select a real directory only beneath `$DOTLINEFORM_PROJECTS_BASE_DIR`.
- The browser and responses hold only canonical base-relative directory markers, never absolute machine paths.
- Directory browsing and candidate discovery are lazy and one level deep; selecting a folder does not recursively scan it.
- Changing the source cannot change the frozen destination or any downstream import semantics.
- The selected source is read-only. Import does not move, delete, or synchronize source material.
- A remembered directory is a local convenience, not authority. The server revalidates it before use and falls back to staging if it is no longer valid.

## Shared Capability Boundary

Sharedness is determined by responsibility and dependency direction, not by the number of current consumers. The folder browser is an app-neutral capability and may be placed under the existing shared frontend owner with Docs Viewer as its first and only consumer. This is preferable to either duplicating the capability or silently importing one application's private implementation.

Docs Viewer must gain an explicit supported route or build boundary for the shared frontend asset. The dependency is named and tested; the component is not copied into Docs Viewer and is not reached through an accidental relative path.

The shared component owns:

- the current base-relative breadcrumb and direct-child directory list;
- navigation, loading, empty, and error presentation;
- keyboard and focus behavior inside the picker;
- selection and submission events; and
- small component-owned styles and state classes.

It does not know about Docs Import, import staging, candidate formats, local-storage keys, application routes, `$DOTLINEFORM_PROJECTS_BASE_DIR`, or server confinement. Its injected boundary is equivalent to:

```text
createFolderPicker(root, {
  initialDirectory,
  loadDirectory,
  onSubmit,
})
```

The exact exported names are frozen at the delivery's contract checkpoint. The important contract is that loading and submission remain consumer-provided and the component never constructs application URLs or interprets an empty marker as permission to select a filesystem root.

The existing Works Editor file picker remains a separate consumer-specific control during IFS-1. It currently owns a fixed folder/subfolder/file workflow rather than arbitrary directory navigation. Migrating it is not required to justify shared ownership and is not part of this delivery.

## Modal Ownership And Handoff

Folder selection uses a dedicated folder-picker modal. The Import modal continues to own destination, selected candidate, preview/apply status, result links, and the visible source summary. It does not gain a folder-browser subview.

The controller uses the existing modal-handoff pattern: choosing a folder suspends or hides Import, opens the folder-picker modal, then restores Import on confirm or cancel. Confirm passes one server-accepted relative marker back to Import and refreshes candidates. Cancel preserves the previous source. Focus returns to the launching control in both cases.

The folder-picker modal owns only directory navigation and confirmation. It cannot select files, apply an import, retain an independent destination, or leave Import state partially reset.

## Server Ownership

A shared Studio Python capability owns Projects-base directory confinement and lazy child-directory listing. It receives the configured base and a relative marker, then:

- rejects blank or absolute inputs, parent traversal, missing paths, non-directories, and unreadable directories;
- rejects symlinks and symlinked path segments rather than merely checking final string containment;
- confirms the resolved directory remains beneath the configured base;
- returns one canonical base-relative marker; and
- lists only validated direct-child real directories, returning relative markers and display names without absolute paths.

This capability knows nothing about Docs Import, trusted formats, candidate allowlists, destinations, or browser state. Docs Import's server adapter owns the staging default, trusted-format restriction, candidate classification, and exact preview/apply binding.

## Docs Import API Contract

The delivery freezes endpoint names against the existing server conventions, but the logical operations are:

- list a validated current directory and its validated direct-child directories;
- list ordinary import candidates in one validated source directory; and
- preview or apply one exact `{source_directory, staged_filename}` pair.

Directory-list responses return the canonical current marker, an optional parent marker, and direct-child markers with display labels. The Projects-base root is a navigation location, not an implicitly selectable source. Candidate and result rows use relative provenance only.

The Import controller persists a directory only after the server accepts and returns its canonical marker. On every Import session it revalidates the remembered marker before listing candidates. Missing, unreadable, symlinked, changed, or out-of-root values clear the preference and fall back to `data-sharing/import-staging/` without changing the current destination.

Registered collection recognizers continue to inspect untouched candidates before generic Markdown or suffix handling. A trusted package or edited review source encountered outside staging is rejected with the staging-only diagnostic; it never falls through as an ordinary candidate. Standalone-media exclusions and existing source-format allowlists remain authoritative.

A one-document Markdown-package directory remains a direct-child candidate of the selected source and retains its own directory as the package root for relative media resolution.

## Failure Boundaries

- Directory navigation failure remains in the folder-picker modal and does not replace Import's current source.
- Candidate refresh failure leaves the accepted source visible and uses the existing Import retry/status owner.
- A stale or mismatched source-directory and filename pair is rejected before preview or apply.
- Absolute local paths never appear in UI text, browser persistence, public payloads, or diagnostics.
- Post-commit presentation or rebuild recovery follows the existing exact-target Import contract; source selection cannot allocate a second identity or repeat creation.

## Deliberate Omissions

Standard browser file and directory inputs do not provide a stable server-side directory path, while browser filesystem handles are browser-owned capabilities rather than Projects-base-relative server identities. Operating-system dialogs would add a local desktop server integration outside the current web architecture. IFS-1 therefore uses the confined server-backed browser and does not introduce a native-dialog abstraction.

The feature does not establish a generic filesystem framework. It adds the narrow shared directory-navigation component and confined-directory capability needed by this workflow, with reuse available when a real second consumer appears.

After acceptance, shipped Import behavior moves into [Docs Import](/docs/?scope=studio&doc=d-20260424-000000-fc8b5d) and [Docs Import Architecture](/docs/?scope=studio&doc=d-20260514-164722-3de65e). This document remains the feature's design owner rather than a delivery log.
