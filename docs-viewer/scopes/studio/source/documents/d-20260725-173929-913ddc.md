# Tag Management Studio Cutover And Analytics Retirement Delivery

## Status

Complete. Studio owns the canonical tag source, retained policy, domain
services, transactions, activity integration, `/studio/api/tags/...` boundary,
and all five retained browser workflows. The cutover has exact data and
behavioral parity evidence, the standalone Analytics application/runtime are
retired, and durable documentation routes to the shipped owners.

## Outcome

Studio is the sole owner of canonical tags, aliases, assignments, group
descriptions, tag policy, and their current maintenance workflows. The
standalone Analytics application, server, routes, runner, tests, and check
ownership are removed.

This is a lift-and-shift ownership cutover, not a tag-model or UI redesign.
Stable tag, Series, and Work identities and all current assignment relationships
remain unchanged.

Completion unblocks implementation of
[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61), but no
semantic-token registry, authoring, rendering, relationship, or report work is
part of this delivery.

## Benefits And Risks

Benefits:

- canonical catalogue and tag data share one Studio owner and runtime;
- Studio catalogue generation no longer imports an Analytics package;
- one local app, API surface, port, runner, route shell, and check family can be
  retired;
- later tag consumers, including Semantic Tokens, can read a stable Studio-owned
  source without preserving an application due for removal.

Main risks:

- changing canonical IDs, normalization, assignment inheritance, or alias
  history during what should be an ownership move;
- weakening preview/apply, multi-file atomicity, rollback, or activity evidence;
- losing staged offline assignment sessions during the route move;
- moving only the visible editors while leaving catalogue generation, Admin
  audits, tests, configuration, or runners coupled to `analytics-app/`;
- carrying Analytics shell, Data Sharing, stale CSS, or compatibility routes into
  Studio unnecessarily.

## Current Boundary

Studio owns:

- the four unchanged canonical files under `studio/data/canonical/tags/`;
- retained group-order, coverage, and RAG policy in
  `studio/data/config/tags/tag-management.json`;
- the model, source paths, planners, transaction and rollback boundary,
  activity integration, and route constants under `studio/services/tags/`;
- tag request/result adapters and dispatch under
  `/studio/api/tags/...`;
- focused Python tests and fixtures, plus catalogue and Admin consumers of the
  Studio source-path package.

Studio also owns the five route templates, browser workflows, focused tag UI
text and CSS, runtime configuration, and their positive API/browser smokes.
There is no Analytics runtime, route, API, service, policy, config, or smoke
profile.

The existing offline assignment session already uses
`dotlineform.studio.tagAssignmentsOffline.v1`; preserve that storage key and the
`tag_assignments_offline_v1` payload contract so valid staged work survives the
route move.

## Shipped Ownership

Studio owners:

```text
studio/
├── data/
│   ├── canonical/tags/
│   │   ├── tag-registry.json
│   │   ├── tag-aliases.json
│   │   ├── tag-assignments.json
│   │   └── tag-groups.json
│   └── config/tags/
│       └── tag-management.json
│           group order, coverage policy, and other retained tag policy
├── services/tags/
│   model, path, planners, transactions, activity, and route constants
├── app/
│   ├── server/studio/
│   │   └── Studio tag API adapters and dispatch
│   └── frontend/
│       ├── routes/
│       └── js/
│           Studio-hosted tag workflows
└── tests/
    tag model, mutation, transaction, API, route, and browser contracts
```

The exact module split may follow existing Studio server conventions, but these
roles must not remain under an Analytics namespace. Studio route paths use
`/studio/...`; tag APIs use a Studio-owned `/studio/api/tags/...` boundary.

The public `/analysis/` Docs Viewer scope is unaffected. Its name does not imply
an Analytics application.

## Preserved Contract

- The four canonical JSON schemas and current records move without semantic
  transformation.
- Canonical tag IDs remain `<group>:<slug>`.
- Series-first assignments, nested Work override deltas, weights, alias context,
  and effective-tag derivation remain unchanged.
- Registry and alias import, create, edit, delete, promote, and demote behavior
  remain available.
- Destructive or cross-file changes retain preview before apply.
- Multi-file writes retain validation, atomic replacement, rollback, and one
  initiating activity context.
- Series coverage and the one-series editor retain their present meaning.
- Direct writes, supported manual-patch fallback, and the versioned offline
  assignment session retain their current boundaries.

Presentation may be adapted only as required to fit the Studio shell, route,
ready/busy, modal, transport, and styling conventions.

## Not In Scope

- redesigning tag schemas, groups, weights, scoring, assignments, aliases, or
  editor workflows;
- adding Tag Dimensions, LLM-assisted tagging, Semantic Tokens, public tag pages,
  or new analysis features;
- restoring tag-package or generic Data Sharing behavior;
- retaining `/analytics/...` redirects, proxies, aliases, a shell stub, or a
  second canonical source;
- moving the whole Analytics stylesheet or shell infrastructure when only
  attributed tag-route rules are live;
- broad Studio visual polish unrelated to functional route integration.
