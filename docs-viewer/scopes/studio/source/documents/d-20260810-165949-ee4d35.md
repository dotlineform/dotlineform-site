# Expanded Report View

## Purpose

Allow an explicitly eligible Docs Viewer report to open from its ordinary report-host document in a full-width view. The expanded view preserves the live report and its current sorting, filtering, selection, actions, and report-owned route state rather than treating the report as a static table.

In Manage, an eligible tabular report can additionally expose temporary manual column-width controls. This brings the useful interaction from Markdown Table Detail to reports without applying the Markdown `Table detail` directive to code-generated content or assuming that every report uses the same semantic markup.

## Shipped State

[Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) owns the current report registry, metadata, implementations, and exact report-host model. [Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd) owns the shared, public, local-only, contribution, data, and stylesheet boundaries. Reports mount asynchronously into the generated host and choose semantic tables, lists, or sections from their own data relationship while remaining inside the normal document measure.

[Report Blocks](/docs/?scope=studio&doc=d-20260810-180114-003d2a) has shipped. One exact Report Block now supplies the validated descriptor and generated host; the retired document-level report front matter and append-after-content behavior are no longer supported.

[Catalogue Works Report Migration](/docs/?scope=studio&doc=d-20260810-181816-dc9891) has also shipped. Its search-driven local `catalogue_works` report is the motivating wide tabular report and already supplies semantic HTML table structure, stable columns, sorting, and an explicit clipboard projection. Expanded Report View remains the sole owner of rehosting, horizontal scrolling, and temporary manual widths.

[Docs Viewer Panel Hosts and Control Surfaces](/docs/?scope=studio&doc=d-20260528-224754-964108) owns the existing public/Manage Content Detail view and its `expanded-main` layout. Markdown Table Detail registers one exact marked semantic table, clones it into that view, and adds Manage-only resize and copy tools through the presentation lifecycle.

Reports cannot safely reuse the table clone. They are live components whose event listeners and internal state belong to the mounted report, and some reports rebuild their header and rows after sorting or filtering. The expanded report must therefore rehost the exact live report root and restore it on Back.

Current report layouts are designed to fit or reflow within the document measure. They have no general report-owned horizontal scroll viewport, so a future report with meaningful minimum column widths needs an explicit expanded presentation rather than accidental page overflow.

[ERV-1 — Expanded Report View Delivery](/docs/?scope=studio&doc=d-20260811-090239-12f6d6) shipped the complete bounded outcome. Manage composes the locally owned authority-free adapter and its separate managed-width extension; public routes compose neither. `catalogue_works` is the first and only adopter, and further report adoption is deferred.

## Safety, Composition, And Adoption

[Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd) distinguishes three states that file paths do not reveal:

- **Public-safe:** the adapter and its dependencies are permitted to execute over public data and carry no local or management authority. A file under `site/docs-viewer/runtime/js/shared/` can have this property without being downloaded by a public route.
- **Publicly composed:** the public entrypoint imports and wires the adapter, or the public shell loads CSS containing its selectors. This causes the code or CSS bytes to be downloaded even when no report invokes them.
- **Publicly adopted:** an explicitly promoted public report returns the capability handle and uses the composed adapter. Adoption still requires its own public data, metadata, executable loader, and report contract.

The equivalent local states are independent. Manage can compose and adopt one public-safe implementation without the public entrypoint composing it and without creating a public report.

`docs-viewer/runtime/js/reports/docs-viewer-report-presentation.js` is locally owned because Manage is its only current composer. It has no management or service authority, but possible future public safety does not place it in the public artifact: the site runtime manifest, public entrypoint and transitive import graph do not include it; the public report path contains no expanded-presentation registration; and the public-loaded shared report stylesheet contains no expansion selectors. Manage loads its selectors through `docs-viewer/static/css/docs-viewer-local-reports.css`. `catalogue_works` returns `expandedPresentation`, so the capability is locally composed by Manage and locally adopted by that one report.

Public safety alone does not authorize public composition or public-artifact ownership. Expanded Report View remains locally owned while only Manage composes it, and `catalogue_works` is its first Manage adopter without public composition. If a future public report needs expansion, its delivery must migrate the one canonical adapter and selectors into public/shared owners, retarget Manage, and add the public runtime-inventory, import, controller, data, metadata, loader, and adopter edges together.

## Report Presentation Boundary

New reports choose their semantic structure from the report requirement rather than inheriting one universal visual implementation.

- A stable rectangular dataset whose rows share named columns should normally use a semantic HTML table with `thead`, `tbody`, column headers, rows, and cells. Sorting links, selection controls, and other interactive content can remain inside that structure.
- A navigable collection, heterogeneous list, grouped summary, card-like result, or composition whose rows do not share one stable column relationship should use the corresponding list or section semantics and may use CSS Grid for layout.
- CSS remains responsible for presentation in either case. The distinction is semantic HTML table versus list/section markup laid out with Grid, not CSS versus HTML.

An existing report may change representation when its requirement evolves. In practice, the likely direction is list/Grid to semantic table when a report acquires durable columns, header relationships, resizing, or tabular export. Table to list/Grid remains possible when a report stops being meaningfully rectangular, but that is a broader requirements change and may be clearer as a new report presentation rather than a silent rewrite. Representation is not report identity: a conversion retains the report id, exact data authority, access boundary, and route-state contract unless a separate feature changes them.

## Feature Contract

- Eligibility is declared explicitly by a report or report preset. Width, row count, headings, DOM shape, or measured overflow never grants eligibility.
- The report or preset declares the presentation kind required by its data relationships. Expanded Report View does not impose Grid or semantic table markup on every report.
- The open control becomes available only after the exact report has mounted successfully. Its target retains the current scope, parent `doc_id`, report id, preset or collection context where applicable, and document-mount generation. A document hosts at most one report, so the target has no report-instance identity or instance-prefixed state.
- Opening the report uses the existing public/Manage Content Detail view and `expanded-main` layout. The sidebar and Info panel are projected away temporarily while their state is retained.
- The presentation rehosts the live report root; it does not clone the report, mount a second copy, refetch its data, or create a parallel report state owner.
- Back restores the live report to its original document position, scroll position, and invocation focus. Document navigation releases the expanded target without restoring stale context.
- The ordinary embedded report keeps its current fit-and-reflow presentation. Expanded Report View does not make horizontal scrolling the default for normal report documents.
- The expansion adapter remains free of management and service authority, but its source owner follows current composition. Manage adoption does not imply public ownership; a future public adopter requires a complete ownership migration plus explicit public runtime-inventory, import, controller, stylesheet, data, metadata, loader, and adopter decisions.
- When public composition exists, public runtime must not import Manage-only resizing tools or gain write-capable handles.
- Manage-only manual resizing requires an explicit tabular column model with stable column ids, labels, and ordered header/row correspondence. Non-tabular reports remain expandable without resize handles.
- Each semantic-table column declares `visibility: "both"` or `visibility: "expanded"`. The report renders one live table; the embedded presentation hides expanded-only headers and cells, and the expanded presentation reveals them before sizing.
- Resize handles support pointer dragging and keyboard Left/Right adjustment. Widths are applied through the presentation's single column owner: a `colgroup` for a semantic table or one root-owned track template for an explicitly tabular Grid presentation. Every current or subsequently rendered row retains the same widths.
- Increasing the total column width beyond the available expanded view produces bounded horizontal scrolling inside the expanded report viewport.
- **Reset widths** removes the temporary override and restores the report or preset's natural responsive table or Grid layout.
- Manual widths are presentation-session state only. They are not written to source front matter, report registry data, URLs, browser storage, canonical data, or generated payloads, and they are discarded when the expanded view closes.
- Report-owned exports may follow the active presentation when declared by that report. Catalogue Works Copy table exports five embedded columns and all seven visible expanded columns; Content Detail does not add a parallel copy control.

## Boundaries

This feature does not:

- apply the Markdown `Table detail` directive or `data-docs-content-detail="table"` marker to reports;
- require a wholesale conversion of existing reports to one markup model or retain parallel Grid/table renderers for compatibility;
- infer report identity, eligibility, or columns from labels, rendered child counts, geometry, overflow, the selected row, or the current route alone;
- add column resizing to the normal embedded report presentation;
- persist personal layouts or introduce saved report views;
- add a generic dashboard, arbitrary report plugin registry, report designer, or user-defined columns;
- give public routes management controls, local services, source access, or write authority;
- treat the existing Markdown **Copy table** action as automatic report functionality, because a report's interactive DOM is not itself a semantic export contract;
- require every current report to opt in, including non-tabular reports and sub-scope child-detail states; or
- broaden local Docs Viewer into a phone-specific layout. Public report presentation retains its existing mobile responsibility.

## Discussion Position

The preferred ownership shape is one exact locally owned report-presentation adapter plus a Manage-only column-width extension, following [Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd). The report supplies its semantic presentation kind and, when tabular, its stable column model; the adapter owns expanded presentation and lifecycle; the Manage extension owns representation-aware resize interaction, Reset widths, and its local stylesheet; each report remains the sole owner of its data, rows, filters, sorting, selection, actions, and route state. If a named public adopter appears, its delivery promotes the one canonical adapter into a public/shared owner and retargets Manage rather than adding public edges around a local or prospectively deployed file.

The Report Blocks and Catalogue Works prerequisites and [ERV-1](/docs/?scope=studio&doc=d-20260811-090239-12f6d6) are shipped. ERV-1 adopts `catalogue_works`, which supplies the semantic table, stable columns, search, sorting, exact links, and presentation-aware Copy table. `project_state` remains a possible later adoption rather than a prerequisite conversion. `docs_subscope` customisations should be assessed separately because their visual columns can be composed from collection-specific contributions and selection state.

[ERV-1](/docs/?scope=studio&doc=d-20260811-090239-12f6d6) implements the declaration as an optional `expandedPresentation` handle returned by a successful report-module mount. The handle owns the presentation kind and, for a semantic table, its stable column model and rerender subscription. It does not duplicate the report registry or project management configuration to public routes.

## Shipped Ownership Result

The durable Reports and Report Capability and Composition owners now carry these implemented points:

- `docs-viewer/runtime/js/reports/docs-viewer-report-presentation.js` is the one canonical implementation; it has no management or service authority but remains local until a named public adopter justifies promotion.
- The public entrypoint and its transitive import graph do not import or construct the adapter until a named public report adopts it.
- The public document-extras and report-controller path does not receive or register `expandedPresentation`; those explicit edges belong to a future public adoption.
- The public-loaded `site/docs-viewer/static/css/docs-viewer-reports.css` contains no expansion control or viewport selectors. Manage receives those selectors from its local report stylesheet.
- Manage imports, constructs, supplies, and releases the exact local adapter through the retained shared Content Detail and lifecycle injection seams.
- No report adoption, column model, resize handle, width state, data request, registry, payload, service, or route change is part of ERV-1.1R, so visible product behavior remains unchanged.
- A future public adoption must move the one canonical adapter and required selectors into public/shared owners, add the runtime-manifest, entrypoint, controller, data, metadata, loader, and adopter edges together, and retarget Manage without retaining a local copy or alias.
- [Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b), [Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd), and [Catalogue Works](/docs/?scope=studio&doc=d-20260401-000000-ebf14a) carry the shipped runtime, composition, adoption, column, export, and temporary-width contracts; the delivery record is evidence rather than the sole durable authority.

## Success Meaning

The shipped feature lets the eligible Catalogue Works report open in the full-width Content Detail layout without losing or duplicating its live state, return safely to the ordinary document, and remain exact across navigation. In Manage, its declared column model can be resized accessibly, remains aligned through report rerendering, scrolls within the expanded viewport when widened, and returns to its natural responsive template through Reset widths. Public routes carry no expansion code or selectors merely because the implementation is public-safe; they compose the read-only presentation only when a named public report adopts it, and they never receive management capability.
