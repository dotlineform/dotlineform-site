# Catalogue Data Visualisation

## Purpose

This is a slow-burning investigation into data-driven visualisation of the Works Catalogue, with D3 as the initial candidate toolkit. The aim is to discover which views reveal useful patterns, relationships, concentrations, gaps, or outliers in the catalogue and what bounded data projections those views need.

This is separate from Data Model Maps. Authored architecture diagrams explain how the system works; Catalogue Data Visualisation uses catalogue records and relationships as data to explore the collection itself. It does not make D3 another architecture-diagram renderer or require these visualisations to live inside documentation.

## Intended Outcome

The investigation should establish whether D3 is useful in local Studio, the smallest maintainable way to run it, and a short catalogue of visualisation questions worth pursuing. It may retain small local prototypes when they are useful, but it does not need to produce a general visualisation platform or pass a formal adoption test.

If a substantial retained capability becomes clear, add one bounded delivery child with its exact host, data contract, dependencies, files, and verification. Until then, this feature is the place to accumulate useful experiments and decisions without implying a delivery schedule.

## Starting Catalogue Shape

The current canonical snapshot contains approximately 1,940 Works and 143 Series. These counts are sizing evidence for the first experiments, not model invariants.

- A Work has stable `work_id`, ordered `series_ids[]`, publication state, dates, title, year, medium, dimensions, project-media evidence, and other optional metadata.
- A Series has stable `series_id`, descriptive and publication metadata, a primary Work, and a member-ordering policy.
- Series membership is many-to-many and Work-owned through `series_ids[]`. A hierarchy must not silently pretend every Work has one parent.
- Work details are optional Work-owned aggregates with section and detail identities. They can be introduced only when a visualisation question needs that depth.
- Canonical, public, and Studio read models expose different fields for different consumers. A convenient generated index is not automatically the right authority or sufficient visualisation input.

## Candidate Questions And Data Shapes

| question family | candidate views | likely input shape | important qualification |
| --- | --- | --- | --- |
| How does the catalogue develop over time? | timeline, histogram, stacked area, scatter plot | one typed row per Work with dates, year, status, Series, medium, and chosen measures | distinguish creation, publication, and represented year rather than merging them into one time field |
| How are Works distributed across Series and other groupings? | bars, dots, treemap, packed circles | grouped rows or an explicitly derived hierarchy with counts and measures | multi-Series Works need an explicit duplication, allocation, or primary-group rule |
| Which Works and Series form meaningful relationship clusters? | force-directed network, adjacency view, radial network | `nodes[]` plus typed `links[]` using stable IDs | the complete bipartite graph may be too dense; filtering and aggregation are part of the question |
| Which Series overlap through shared Works? | matrix, chord diagram, weighted network | ordered Series IDs plus an aggregated co-membership matrix or weighted links | derived overlap is analytical evidence, not a canonical stored relationship |
| Where are metadata gaps, unusual values, or physical outliers? | scatter plot, beeswarm, heatmap, small multiples | typed Work rows with explicit missing-value states and numeric measures | absence, unknown, not applicable, and zero must remain distinguishable |

These are prompts, not a required gallery. Begin with a real catalogue question and derive the smallest input that answers it; do not choose a data structure solely because a D3 example looks attractive.

## Data Contract Hypotheses

D3 should not require one universal repository graph or a new canonical catalogue schema. Different visualisation families naturally consume different shapes:

- **Rows:** stable identity plus typed dimensions and measures for plots, bins, timelines, and tables.
- **Hierarchy:** `{id, label, children, value}`-like data for trees, treemaps, and packing, with an explicit policy wherever the source is not truly hierarchical.
- **Graph:** `nodes[]` and typed `links[]` for Work-Series or other relationship views.
- **Matrix:** a stable ordered key list plus derived numeric cells for pairwise overlap or flow views.

Prefer a visualisation-owned adapter or server projection that reads existing catalogue authorities and emits only the exact local-safe fields needed by the view. Do not make browser code parse canonical file wrappers, depend on private source paths, or mutate a shared service response. This matters particularly for D3 force layouts, which add position and velocity state to node objects.

Every retained data shape should record its subject, schema version when persistence requires one, stable identity fields, field meanings, missing-value rules, ordering, filtering, refresh trigger, and source authority. Avoid a generic schema until two or more retained visualisations demonstrate a genuinely shared contract.

## Integration Hypotheses

The first useful host is likely a focused local Studio page, report, or component that runs alongside the Docs Viewer diagram lifecycle. It can load an explicit locally managed D3 dependency and consume a focused Studio endpoint or generated read model. This preserves interaction, filtering, inspection, and possible Canvas rendering without forcing D3 into Mermaid fences or static Markdown.

The Mermaid build lock currently contains D3 transitively. That is not an owned D3 integration seam: a retained feature should declare and pin the D3 modules it actually uses rather than relying on another renderer's dependency tree.

Alternative outputs remain open:

- a local interactive SVG or Canvas view for exploration;
- a prepared static SVG or image snapshot embedded in documentation when the result itself needs explanation;
- a reusable Studio visualisation host if several proven views share lifecycle and controls; or
- a separate public feature if a specific public-facing visualisation later justifies its payload, accessibility, performance, and publication costs.

Local Studio removes most distribution barriers, but it does not erase data boundaries. Canonical project paths, filenames, storage information, provenance, or other management-only fields must not enter a public asset accidentally.

## Slow-Burning Investigation

### 1. Collect Questions And Inspect Existing Inputs

- [ ] Record concrete catalogue questions as they arise and identify the current canonical or generated authority for each required field.
- [ ] Inspect whether an existing Studio or public read model already supplies the correct semantics before proposing another projection.
- [ ] Note current corpus size, sparsity, many-to-many relationships, and fields that need normalization or derived measures.

### 2. Run Two Complementary D3 Spikes

- [ ] Try one row- or hierarchy-shaped view that reveals distribution, chronology, grouping, or missing metadata.
- [ ] Try one graph- or matrix-shaped view that explores Work-Series membership or overlap.
- [ ] Use bounded filters or samples where the full corpus obscures the question, while keeping the selection rule visible.
- [ ] Compare SVG and Canvas only where corpus size or interaction makes the choice material.

### 3. Learn The Integration Shape

- [ ] Record the D3 modules actually needed, local dependency and asset options, host lifecycle, data loading, resize behavior, theming, interaction, and accessibility.
- [ ] Decide whether each useful view should read a small runtime endpoint, a generated Studio projection, or a prepared static artefact.
- [ ] Keep visual state, layout coordinates, filters, and derived aggregates outside canonical catalogue records unless another feature explicitly gives them durable meaning.

### 4. Decide What Is Worth Retaining

- [ ] Keep useful experiments as local tools or documented examples when their maintenance cost is proportionate.
- [ ] Add a bounded delivery child only when one complete retained outcome and its data contract are clear.
- [ ] Record rejected and deferred ideas briefly enough to prevent repeated investigation without turning the feature into an exhaustive D3 catalogue.

## Practical Review Prompts

- Does the view answer a real catalogue question more clearly than an existing table, filter, or static diagram?
- Can a reader understand what each mark, link, size, colour, position, and omission means?
- Are multiple Series membership, missing values, unpublished records, and filtered records represented honestly?
- Does interaction add discovery rather than hide essential interpretation behind hovering or dragging?
- Is the input a focused projection with stable identity and explicit derivation rather than a convenient accidental payload?
- Does the view remain responsive and inspectable at current catalogue scale?
- Can keyboard, text, summary, or tabular alternatives carry the important result where visual interaction is inaccessible?

These prompts support judgment; they are not a pass/fail exam.

## Boundary

This feature does not own diagrams of system architecture, canonical Catalogue schema, Catalogue editing, public publication by assumption, a graph database, a universal relationship model, a generic notebook environment, or an automatically generated visualisation gallery.

The existing Catalogue services remain authoritative for source records and mutations. Visualisation projections are read products. Derived grouping, coordinates, cluster membership, overlap weights, and interaction state do not become canonical merely because a useful view computes them.
