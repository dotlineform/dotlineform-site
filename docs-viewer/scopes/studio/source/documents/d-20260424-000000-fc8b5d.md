# Docs Import

Docs Import turns source material beneath the configured Projects base into canonical Markdown documents and associated media. It runs inside Docs Viewer management and can target a top-level scope or a configured one-level sub-scope collection.

Choose the app-level **Import** action from any local Manage Docs Viewer state. The same modal lists every recognized document candidate in the accepted source folder. Ordinary sources use the validated parent or sub-scope collection displayed when the modal opened; trusted packages and edited review-source folders use their manifest-owned collection even when another context is displayed.

## Workflow

![Document sources and standalone media use separate workflows, while both publish required media before canonical source is written and rebuilt.]([[media:docs/studio/svg/docs-import-media-boundaries.svg]])

The browser presents choices. The local Docs Viewer service resolves the exact source directory and direct child, validates targets, creates the authoritative plan, performs writes, and rebuilds published payloads.

## Choose The Source Folder

Import staging is the default source:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/data-sharing/import-staging/
```

The modal shows the current Projects-relative source. **Choose folder…** opens a dedicated browser for real directories beneath the Projects base; confirming one folder refreshes its direct-child candidates without changing the destination. The accepted relative folder is remembered locally and revalidated whenever Import opens. If it is no longer accepted, Import clears it and falls back to staging. **Use import staging** validates the default again and clears the preference.

Ordinary document sources may be direct children of any accepted nested source folder. A Markdown package is a direct-child folder containing one Markdown file plus its local images or attachments. Returned packages and complete edited Docs Review `source/` folders are trusted collection formats and remain importable only from staging. Recognizers inspect each untouched direct child before generic format handling; a recognized trusted source outside staging stays visible but blocked rather than falling through as an ordinary document.

The candidate list shows only formats the server currently accepts. Standalone raster, SVG, Mermaid `.mmd`, and download sources belong to the source editor's **Add image…** and **Add file…** actions. [Docs Import Architecture](/docs/?scope=studio&doc=d-20260514-164722-3de65e) owns the source, format-adapter, and staging-gate boundaries, while [HTML Import Mapping](/docs/?scope=studio&doc=d-20260719-182348-492a48) documents the current semantic conversion rules.

Docs Import always creates the target document front matter. For an ordinary Markdown source, a well-formed leading front-matter block is stripped after trusted collection recognition. Its scalar `title` may be used only when the body has no H1; every other field is ignored with a warning. Malformed or unterminated apparent front matter blocks the import instead of becoming body text.

## Import Documents

The single-select list contains ordinary Word `.docx`, HTML, Markdown, text, and one-document Markdown folders plus trusted returned JSON/JSONL packages and complete edited review-source folders when staging is selected. It has no source-type or destination selector. Each row shows its kind and effective destination; blocked claimed packages remain visible with a safe diagnostic. Standalone media and unrelated files are absent.

1. Select one source candidate.
2. Check its read-only kind, destination, and any disabled reason.
3. For HTML, decide whether obvious prompt/meta sections belong in the document.
4. Import an ordinary source, or preview and confirm a complete collection.
5. Inspect the result and use its explicit destination link.

Opening the modal freezes one validated `{ scope }` or `{ scope, sub_scope }` destination for ordinary sources. Source choice is independent: every candidate request, preview, and apply carries the exact accepted source directory beside the direct-child name. Checked rows, selected parents, titles, URL text, prior destinations, and the displayed document are not target inputs. Package rows retain their trusted manifest destination and are never filtered or rerouted by the current display.

HTML can supply the title; Markdown uses its first H1 when present. Word uses the mapped `Title` style and falls back to the humanized source filename without promoting its first section heading. [Word Import Style Mapping](/docs/?scope=studio&doc=d-20260719-182348-f326fd) owns the exact Word heading rules. The source name remains conversion context. A genuinely new document receives an immutable local `doc_id` and matching Markdown filename when the service plans the write.

Every ordinary source import creates a new document with a fresh immutable identity. Importing the same source file again creates another independent document; the workflow does not scan target documents or offer document overwrite. New documents in public scopes are created non-viewable so they can be checked in management mode before publication.

### Create-Only Document Imports

Ordinary Word, HTML, Markdown, text, and Markdown-package sources are intake material, not update identities. Their source filenames and titles remain conversion context only. Update an existing canonical document through the source editor or another workflow that explicitly identifies that document; ordinary import never infers an update from a filename or title.

This create-only rule does not remove collision handling from returned collections or stable-name assets. Trusted collection records carry explicit document identities: matching canonical identities are planned as overwrites and new records receive local create identities. Role-marked interactive HTML companions retain explicit asset replacement confirmation.

## Import A Trusted Collection

With import staging selected, choose either a trusted returned documents package or a complete edited Docs Review source folder in the same app-level chooser. A reviewable returned package also enables **Open in Docs Review** on that selected row. Review prepares or reuses the separate read-only projection in a new tab; it neither confirms Import nor changes the package's manifest-owned destination.

The server recognizes both collection formats before ordinary Markdown or
generic JSON/JSONL handling. A standalone reviewed Markdown file is rejected
with guidance to stage and select the complete source folder. Missing, extra,
duplicate, malformed, unsafe, or invalid records block either collection as a
whole. There is no record selection, skip, or partial apply.

The collection path is deliberately plan-first:

1. Choose the package and inspect its manifest-owned target.
2. Review every record, parent resolution, warning, and blocker.
3. Review the server-planned creates and overwrites for the complete package.
4. Confirm the complete package, or cancel without writing.

The plan covers the whole collection. A package record that creates a document receives a planned local identity; the package identifier remains source provenance and parent references are remapped to the local identities. A record matching an existing canonical identity is planned as an overwrite. There is no subset selection, record skip, replacement `doc_id`, or `Create as new` choice. Missing undeclared parents, hierarchy cycles, unsafe identities, invalid records, and package-shape errors block confirmation.

For returned JSON/JSONL, content, summary, `parent_id`, and viewability are
planned together. Creates receive fresh local identities; matching canonical
identities are overwrites. Omitted body or permitted metadata preserves its
current value.

For an edited review-source folder, the displayed name is
`<review_folder_id> (reviewed)` but requests retain the exact staged folder
identity. Trusted export metadata and the retained review manifest must prove
return-Import capability, exact membership, original scope or configured
sub-scope, and prepared `source_last_updated` values. The folder is
overwrite-only: every `doc_id` must already exist in that exact collection.
Edited body, title, and summary may apply. Immutable identity, `added_date`,
review transport fields, and destination-owned `group`, `ui_status`, hierarchy,
and child visibility do not.

On confirmation the service rereads the selected collection and recomputes its
target plan. Changed package/folder hashes, prepared versions, planned actions,
hierarchy, or blockers return a refreshed non-writing plan for reconfirmation.

Returned JSON/JSONL apply remains synchronous and partially durable: a
source-write failure preserves earlier writes and leaves later records not
attempted; generation failure does not undo successful source changes. Edited
review-source apply is intentionally atomic. It validates and prepares every
overwrite, rechecks the complete canonical snapshot inside the owning scope or
sub-scope boundary, writes and rebuilds once, and restores the complete source
snapshot and projection after any write or rebuild failure.

### Optional Edited-Source Workflow

1. Select a reviewable returned package in Import and open it in Docs Review.
2. Open exact package sources in VS Code, edit them, and choose **Build**.
3. Visually accept the complete retained preview.
4. Copy the complete package `source/` folder into Import staging.
5. Select its `(reviewed)` entry, inspect the exact overwrite plan and
   derived-Markdown fidelity warning, then confirm once.

Steps 1–3 are optional for ordinary returned-package Import. Docs Review never
applies canonical changes and its Build endpoint never advances source or
canonical timestamps.

## Media And Companion Assets

Media behavior comes from the target scope configuration:

- each logical media type selects its configured published location
- repository, external-local, and R2 locations use the same provider-independent import plan
- the chosen provider must complete and byte-verify the media write before canonical source is committed

Markdown packages convert supported images to readable, 800px-maximum WebP outputs and copy supported attachments unchanged. HTML and Markdown can extract inline raster data URLs, and HTML-inline SVG is sanitized and published as deterministic image media. Word imports pass embedded PNG, JPEG, GIF, and WebP through the same inline-raster publication path; missing alt text receives a deterministic `Word image NN` label, while unsupported, unreadable, or empty images are omitted with warnings. Exact paths, location providers, collision rules, and media limitations belong to [Media Handling](/docs/?scope=studio&doc=d-20260514-184303-7914e2).

A standalone HTML file marked with:

```html
<meta name="dlf:docs-import-role" content="interactive-html">
```

is treated as a companion asset rather than a selectable source. A normal document import copies marked companions directly to the target scope's configured published `html` root after any required overwrite confirmation. Add the resulting `html-media` token to the document manually; import does not decide where the sandboxed iframe belongs.

## Results And Recovery

An ordinary result identifies the created document, exact parent or child
target, media actions, conversion warnings, and an explicit link to that
document. A collection result presents created, overwritten, failed, and
not-attempted records plus an explicit link to its owning scope or sub-scope
surface. A successful edited review-source result contains overwrites only and
reports its atomic rollback state. Docs Import does not create a separate
result document or result-specific log.

The app refreshes only an exact currently mounted result target. A parent
document reloads by its returned identity; a mounted child report refreshes
the returned document or collection through separate callbacks. A
cross-context package result does not navigate or refresh the displayed
collection; its link is the explicit handoff.

The terminal result remains in the modal until `Close`. Reopen the modal to revalidate the remembered source, refresh its candidate list, and start another run.

An ordinary one-source failure leaves the selected source and destination in place so that source can be retried. Import reads source material without moving, deleting, or rewriting it. After a partial multi-file run, select only failed or unattempted sources; retrying a completed create makes another independent document. If the source write succeeded but the target projection or Source presentation failed, do not import again: use the committed exact target to retry only that presentation step.

Docs Import is best-effort conversion. Normal prose, headings, lists, links, simple tables, Markdown, and supported media are reliable inputs. Word layout, presentation-heavy HTML, interactive UI, unresolved package links, and unsupported assets may need source editing after import. Conversion HTML and inline media bodies remain inside the local service; the generated canonical Markdown is always checked by the shared Python renderer before a source write.

For implementation boundaries, extension methods, and known structural weak spots, see [Docs Import Architecture](/docs/?scope=studio&doc=d-20260514-164722-3de65e).
