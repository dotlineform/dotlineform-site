# Docs Viewer Search Index

Docs Viewer uses one static inverted-index format for every configured parent scope. The browser receives one compact document table plus term-to-document posting lists rather than a second copy of each document body.

## Payload Contract

`docs-viewer/build/build_search.py` emits `docs_viewer_search_index_v2` with:

- a header containing the schema, scope, content version, generation time, and document count;
- an ordered `fields` list copied from the scope's `search_fields` policy;
- a deterministic `docs` table containing identity, title, route, update, parent, and display context; and
- a `terms` map whose field-specific sorted posting lists reference zero-based positions in `docs`.

Each document occurs once. A term occurs once, and a document position occurs at most once in each term/field posting list. The content version excludes generation time, so an identical complete rebuild skips its write.

Parent title, document identity, and update time may remain in the document table without emitting postings. Searchable fields are decided explicitly per scope:

- Studio: `title`, `heading`, `body`, and `code`;
- Analysis, Notes, Processing, and dotlineform: `title`, `parent_title`, `identity`, and `last_updated`.

Studio therefore supports authored full-text retrieval while the other scopes retain metadata-only retrieval. Analysis publishes its accepted metadata-only index through its explicit public projection; enabling its body text remains a separate public vocabulary and payload decision.

## Proposed Scope Corpus Composition

The current index contains parent documents only. [DSI-2 — Scope-Level Sub-Scope Search Delivery](/docs/?scope=studio&doc=d-20260813-225547-cd82d8) proposes that the same selected-scope artifact also contain eligible documents from registered sub-scopes placed by eligible parent `docs_subscope` report hosts.

Child records need exact `{scope, sub_scope, doc_id}` identity, explicit report-host placement for active-route navigation, and configured collection/report title for display context. The working Analysis bytes can also be projected publicly, so one stored route string must not be treated as universally canonical across Manage and public consumers. The browser should construct the target from structured identity and the active route without inferring from titles or current UI state.

The proposed combined index remains one atomic artifact and one relevance corpus. It does not create per-sub-scope indexes, make collection context searchable, or merge child documents into parent Index or Recent.

## Studio Source Boundary

Studio full text is derived from canonical Markdown through existing owners. Validated report declarations are projected away, semantic references contribute their visible title, configured media tokens are removed, and the shared Markdown renderer separates non-duplicate headings, readable prose, inline code, and fenced code.

The index excludes front matter, generated report hosts, link destinations, media paths, raw markup attributes, scripts, styles, complete document IDs, date fragments, and exact 64-character hexadecimal content digests. Image alt text and visible raw-HTML text remain searchable.

## Query And Ranking

`site/docs-viewer/runtime/js/shared/docs-viewer-search.js` is the sole browser postings, ranking, and tie-breaking owner. A multi-term query intersects its normalized term matches; prefix matching begins at three characters; each document appears at most once; ties sort by title and then identity.

The generic score order is exact identity, exact title, title, heading, parent title, body/code, then update metadata. Only fields enabled by the selected scope participate. Studio's active order is therefore exact title, title, heading, then body/code; parent context is display-only.

Short prefix searches can be broad after full-text adoption. For example, the accepted Studio `reg` query returns 145 documents while its two established title matches remain first. Snippets, highlighting, stemming, synonyms, typo correction, term-frequency scoring, phrase positions, section results, and deep links are not part of this index.

## Build And Extension

Every search-relevant parent change rebuilds the complete selected-scope index. Sub-scope writes currently rebuild their collection payloads without Search; DSI-2 proposes that an eligible child content or membership change rebuild the same complete parent-scope index while keeping document payload work collection-targeted. No build touches an unrelated scope.

To add or change searchable content, update the owning scope's ordered `search_fields`, supply eligible source values through the shared extraction boundary, extend the focused Python/query contract, rebuild the complete scope index, and measure any public or unusually large payload. Do not add a second schema, tokenizer, cache, reader, query engine, or scope-name branch.

Exact code and generated JSON remain the authority for current keys and values. [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-214351-98d3f0) owns term recognition. [Docs Viewer Search Relevance](/docs/?scope=studio&doc=d-20260813-223337-e6c261) owns proposed scoring. [DSI-2 — Scope-Level Sub-Scope Search Delivery](/docs/?scope=studio&doc=d-20260813-225547-cd82d8) owns proposed combined-corpus identity and navigation. [SM-1 — Studio Full-Text Search Delivery](/docs/?scope=studio&doc=d-20260715-084611-c2fa6f) retains the first full-text implementation evidence.
