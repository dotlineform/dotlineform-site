# Dotlineform Projects Report Customisation Decision Delivery

## Status And Purpose

Proposed as **SSR-3**, after SSR-2 has recreated `dotlineform/projects` through
the real lifecycle and populated it with representative documents.

This is an evidence-led product and architecture decision. It does not assume
that Projects is a Tags-style preset or that every sub-scope requires a custom
module.

## Complete Outcome

The working Projects collection is reviewed against the shipped default. The
delivery records one of two accepted outcomes:

1. the default is sufficient, with no Projects customisation identity; or
2. Projects has specific justified needs, expressed as a bounded
   customisation contract and separate implementation delivery.

The decision identifies the actual user tasks, data required, controls or
presentation involved, exact targets, capability gates, and public/Manage
boundary. It does not leave a vague list of desirable report features.

## Assessment Questions

- Which Projects tasks are not adequately served by title search, list/detail
  navigation, New, and app-level Import?
- Which document fields are stable collection data rather than body content or
  temporary workflow state?
- Is `last_updated` useful for visible recency, sorting, or filtering in this
  collection, and should that use remain Projects-specific or revise the
  default?
- Does Projects need filtering, sorting, grouping, row metadata, selection, a
  package workflow, or validated-detail actions?
- Is each proposed action collection-, checked-selection-, or
  validated-document-targeted?
- Can a generic helper already provided by the framework satisfy the need, or
  is Projects-specific presentation/behaviour required?
- Does any public Projects view need the same customisation, or is the need
  Manage-only?

## Decision Method

### [ ] SSR-3.0 — Representative Use

- [ ] Populate the recreated collection with enough real Projects documents to
  expose meaningful differences in status, dates, metadata, and workflow.
- [ ] Use the default report for ordinary discovery, opening, creation,
  editing, and Import.
- [ ] Record concrete failed or awkward tasks without treating preference or
  anticipated scale as a requirement.

**Checkpoint:** review evidence names real documents and tasks while preserving
their exact collection identity. Stop before proposing controls.

### [ ] SSR-3.1 — Customisation Options

- [ ] Map each evidenced need to default behaviour, a reusable optional helper,
  a Projects-owned contribution, or a non-report workflow.
- [ ] Reject additions that duplicate title search, app-level Import, source
  editing, or another established owner.
- [ ] For each retained addition, define its data source, placement, target,
  capability, empty state, refresh effect, and public/Manage access.
- [ ] Review representative dense, empty, and narrow-screen states where the
  decision depends on presentation.

**Checkpoint:** every proposed Projects difference has an owner and measurable
outcome; none relies on a Projects conditional in the default engine.

### [ ] SSR-3.2 — Accept Default Or Create Delivery

- [ ] If the default is sufficient, record that result and leave Projects
  customisation unset.
- [ ] If customisation is justified, freeze one registered Projects identity
  and create a separate bounded implementation delivery under the feature
  parent.
- [ ] Revisit the default only when evidence shows the behaviour is appropriate
  for an ordinary new collection, not merely useful to Projects.
- [ ] Update the feature parent and stop for review.

## Fixed Boundaries

- No Projects behaviour is inferred from Analysis/Tags groups or actions.
- No implementation begins inside this decision delivery beyond disposable
  review fixtures or explicitly approved diagnostic prototypes.
- The report manifest remains data, not executable action configuration.
- The decision cannot weaken exact-target, capability, public-isolation, or
  app-level Import contracts.
- A Projects need owned by another surface becomes a separate feature or
  delivery rather than widening `docs_subscope`.

## Completion Gates

- The decision is based on the recreated working collection, not hypothetical
  parity with Tags.
- Every accepted difference has a concrete task, owner, data contract, target,
  and access boundary.
- The outcome explicitly says either **default sufficient** or links one new
  implementation delivery.
- Projects remains comparable to other sub-scopes through the standard
  customisation framework, without becoming a new report type.
