# SSC-1 — Unified Sub-Scope Customisation Contract Delivery

## Status And Purpose

In progress as the shared prerequisite to [SSP-0](/docs/?scope=studio&doc=d-20260804-164519-c7ad4e) and [TDL-0](/docs/?scope=studio&doc=d-20260804-170901-b2e74c). This delivery aligns configuration and code with the responsibility the current `report_customisation` seam already has: one registered collection extension spanning report projection, metadata, actions, validation, import, and future transfer support.

The current [Sub-Scope Report Customisation Architecture](/docs/?scope=studio&doc=d-20260731-155053-3929e2) is the implementation baseline. SSC-1 changes its misleading report-only vocabulary and makes supported aspects explicit; it does not add a second field registry or change current user-visible behaviour.

SSC-1.0 and SSC-1.1 are complete. The [contract and cutover sanity note](/docs/?scope=studio&doc=d-20260804-182355-7ac901) accepts the bounded aspect model and migration boundary. The [SSC-1.1 checkpoint evidence](/docs/?scope=studio&doc=d-20260804-183554-0c4be2) records the coordinated no-alias rename, unchanged generated behavior, focused checks, and diff review. The next gated step is SSC-1.2; explicit aspect work has not started.

## Complete Outcome

Configured sub-scopes use one optional `sub_scope_customisation: {id, settings}` property. Python definitions, registries, configuration readers, generated payloads, services, and browser composition use matching sub-scope-customisation terminology in one no-alias cutover. Missing customisation continues to mean the canonical default.

Each registered definition explicitly owns the smallest validated aspects it supports. The accepted model must cover current manifest and row projection, document groups, source validation, metadata read/update, import front matter, and access-specific browser composition, while providing bounded seams for assignable field groups and Copy transfer contracts. Concrete fields and allowed values stay code-owned by the registered definition and its validated settings; `docs_scopes.json` does not gain loose field arrays or duplicated capability booleans.

Browser availability derives from the resolved exact collection's registered aspects. The server retains settings and write authority and projects only access-safe identity, data, and capabilities. Public routes continue to receive only explicitly registered public-safe contributions and no Manage metadata or mutation controls.

The existing `analysis_tags` and `dotlineform_projects` registrations migrate to the unified contract with the same current report, manifest, validation, metadata, import, and action behaviour. SSP-0 and TDL-0 may then extend their respective registered definitions with focused assignable field groups without name checks or another configuration system.

## Delivery Discipline

SSC-1 is a bounded terminology, configuration, registry, and projection refactor. It does not implement Assign subject, Tag fields, collection-aware Copy, a generic field renderer, or new publication behaviour. SSC-1.0 is a short scope-and-spec sanity gate; each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

## Delivery Steps

### SSC-1.0 — Confirm Contract And Cutover

- [x] Sanity-check the intended model against current configuration loading, registered definitions, default report/manifests, metadata and import hooks, browser composition, access isolation, and existing customisation fixtures.
- [x] Confirm the smallest explicit aspect shape needed by existing behaviour and the later assignable-field and transfer seams without designing a generic schema language.
- [x] Confirm the no-alias cutover boundary across source config, Python and browser naming, generated payloads, tests, and durable documentation.
- [x] Stop for review if the result requires a parallel field registry, duplicated availability flags, literal collection-name checks, a generic form engine, public management projection, or user-visible behaviour changes.

**Checkpoint:** a concise sanity note records the accepted configuration shape, aspect ownership, migration surface, public boundary, risks, and stop condition. Stop before implementation approval.

### SSC-1.1 — Rename The Shared Contract

- [x] Replace `report_customisation` with `sub_scope_customisation` in configured sub-scope records, configuration models, service types, registry vocabulary, generated payloads, browser config, and focused fixtures.
- [x] Keep `{id, settings}` as the only configured extension shape, validate IDs and settings through the registered definition, and preserve the canonical no-customisation default.
- [x] Perform one coordinated source and consumer cutover without a compatibility alias, dual reader, fallback key, or collection-name branch.
- [x] Preserve exact collection identity, default report ownership, report-host reachability, generated membership, and current public/Manage access boundaries.

**Checkpoint:** focused config, build, payload, module, default-collection, unknown-ID/settings, and public-isolation evidence passes. An independent code/diff review confirms one vocabulary and no behaviour drift. Stop before SSC-1.2.

### SSC-1.2 — Make Registered Aspects Explicit

- [ ] Express current manifest projection, document groups, validation, metadata read/update, import normalization, and access-specific browser composition as explicit registered aspects under the unified definition.
- [ ] Add the bounded declaration seams needed for assignable field groups and transfer contracts while leaving both behaviours unimplemented until their owning SSP/TDL and Copy deliveries.
- [ ] Project only the minimum access-safe registered identity, data, and capabilities; keep raw settings and mutation authority server-side.
- [ ] Prove that actions and future focused modals can resolve availability from the exact collection's declared aspect rather than a separate boolean or literal scope/sub-scope name.

**Checkpoint:** focused registry, aspect-presence/absence, exact-target, browser-composition, server-settings, and public-isolation evidence passes. An independent code/diff review confirms the aspect model is bounded and additive. Stop before SSC-1.3.

### SSC-1.3 — Migrate Registrations, Verify, And Transfer

- [ ] Migrate `analysis_tags` and `dotlineform_projects` definitions and configured records to the unified contract while preserving current report, manifest, validation, metadata, import, and action behaviour.
- [ ] Run focused service, builder, browser-module, route-boundary, source-lint, generated-doc, search, and whitespace checks proportional to the refactor.
- [ ] Perform the independent final code/delivery review and reconcile completion claims with exact evidence and omissions.
- [ ] Rename and update [Sub-Scope Report Customisation Architecture](/docs/?scope=studio&doc=d-20260731-155053-3929e2) as the durable **Sub-Scope Customisation Architecture** owner, then update SSP-0 and TDL-0 to consume the shipped aspect names.

## Completion Evidence

- Every configured sub-scope has the default lifecycle/report contract and at most one optional `sub_scope_customisation: {id, settings}` extension.
- Source config, Python, generated payloads, services, browser composition, tests, and durable documentation use one current term with no compatibility alias.
- Existing Analysis Tags and Projects report, manifest, metadata, import, validation, and action behaviour remains intact.
- Registered definitions, rather than loose config fields or booleans, own their supported aspects and values.
- Exact collection resolution selects all custom behaviour without scope/sub-scope name inference.
- Public routes receive only registered public-safe contributions and no Manage metadata or mutation capability.
- SSP-0 and TDL-0 can add their focused assignable field groups through the accepted shared contract.
