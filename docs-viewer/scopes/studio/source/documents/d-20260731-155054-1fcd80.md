# Default Report And Analysis Tags Refactor Delivery

## Status And Purpose

Proposed as **SSR-1**, the first delivery under
[Sub-Scope Report Defaults And Customisations](/docs/?scope=studio&doc=d-20260731-150644-3dfab5).

This delivery defines the default `docs_subscope` report, implements one
standard registered customisation boundary, and refactors Analysis/Tags to use
default behaviour plus explicit customisations. It does not change the
sub-scope lifecycle or decide Projects behaviour.

Development uses an isolated local-only candidate so the shipped
Analysis/Tags report remains on the current canonical implementation until
default and Tags parity are both ready for one cutover.

## Complete Outcome

A minimally configured sub-scope renders the same list/detail engine with
title search, normal empty/error states, compact Manage rows, and an
exact-collection **New document** action. It needs no Analysis/Tags config or
module.

`studio/default` is the reference collection. Its feature-child report host
and builder-generated empty/populated manifests exercise the candidate during
development. At completion that host uses canonical `docs_subscope`; no
candidate report identity remains.

Analysis/Tags selects one known customisation identity. Its current public and
Manage behaviour is preserved, but group filtering and optional management
features are composed through its own module rather than direct wiring in the
shared report or one globally active Tags-shaped contribution.

## Fixed Boundaries

- One shared `docs_subscope` engine remains the rendering and navigation
  owner.
- A temporary local-only candidate may copy the shared report module and use a
  separate minimal Manage contribution; it is removed during accepted cutover
  and is never a compatibility layer or second shipped report.
- The current canonical `docs_subscope` and Analysis/Tags contribution remain
  unchanged until the candidate and Tags customisation pass their respective
  gates.
- The candidate reuses the normal sub-scope builder, manifests, and generic
  helpers. It does not fork data generation or exact-target semantics.
- Config selects only a known customisation identity; the registry owns module
  resolution.
- Public routes import no Manage customisation code or capability data.
- Title search is default. Additional filters are customisations.
- New is default Manage behaviour. Selection, Prepare Package, validated
  detail Delete, and any non-default row treatment are explicit opt-ins.
- Import remains app-level and consumes only a mounted exact collection.
- No Analysis/Tags identifier, label, group value, or manifest filename may be
  a dispatcher condition.
- No compatibility adapter remains after the Analysis/Tags path reaches
  parity unless separately justified with removal criteria.

## Delivery Checkpoints

### [ ] SSR-1.0 — Freeze Default And Module Contract

- [ ] Trace current shared report, filter toolbar, Manage contribution, action
  definitions, capability projection, and Analysis/Tags config.
- [ ] Freeze the customisation config field, safe registry shape, public/Manage
  loading boundary, and unknown-identity failure.
- [ ] Freeze default row fields and decide whether `last_updated` has one
  visible use with deterministic missing-value behaviour.
- [ ] Classify status/viewability, group filtering, selection, Prepare
  Package, Delete, and Import-context publication as default or optional, with
  an explicit owner for each.
- [ ] Freeze row, filter, list-toolbar, selection, detail-toolbar, and lifecycle
  contribution payloads.

**Checkpoint:** one reviewed contract names the default, every retained Tags
feature, its target, owner, access boundary, and refresh effect. Stop before
runtime edits.

### [ ] SSR-1.1 — Build The Isolated Default Candidate

- [ ] Register one explicitly temporary local-only candidate loader over a copy
  of the current shared report module; add no public loader entry.
- [ ] Configure `studio/default` with no customisation identity and create one
  feature-child host pointing at the candidate during development.
- [ ] Build its normal empty `manifest.json` and `manage-manifest.json`, then add
  only the representative child fixtures needed to prove accepted row fields
  and states.
- [ ] Give the candidate a separate minimal default Manage composition so
  changes do not affect the existing Analysis/Tags toolbar.
- [ ] Make the minimally configured candidate render without Analysis/Tags
  fields.
- [ ] Keep title search in the shared default and place non-default filters
  behind the customisation boundary.
- [ ] Add the controlled identity resolver and public-safe/Manage module split.
- [ ] Render capability-gated exact-collection New for empty and populated
  manageable collections.
- [ ] Cover missing config, unknown identity, empty collection, unavailable
  capability, invalid target, remount, and public isolation.

**Checkpoint:** the candidate works independently on `studio/default`, the
canonical Analysis/Tags path is unchanged, and the contract can add one row
feature, filter, list action, selection action, and detail action. Stop before
moving Analysis/Tags.

### [ ] SSR-1.2 — Refactor Analysis/Tags And Cut Over

- [ ] Register the Analysis/Tags customisation through sub-scope config.
- [ ] Move group controls and filtering out of the default engine.
- [ ] Compose the accepted status/viewability, selection, Prepare Package,
  Delete, and Import-context features through the standard module boundary.
- [ ] Preserve configured Tags/Concepts titles, group order, manifest

- [ ] After default acceptance and Tags parity, make the accepted candidate the

- [ ] Remove the candidate report registry row, loader entry, temporary Manage

**Checkpoint:** Analysis/Tags is a consumer of the default, owns its additional
composition, and has no separate report implementation, candidate alias, or
hidden dispatcher.

### [ ] SSR-1.3 — Verification And Authority Transfer

- [ ] Run focused generator/config, runtime-module, contribution, action-target,
  public-import-boundary, lint, and whitespace checks.
- [ ] Manually review default empty/list/detail and current Analysis/Tags

- [ ] Inspect the final diff independently and separate fixture coverage from
  live-route observation.
- [ ] Update the durable Sub-Scope Index architecture, manifest, and toolbar
  owners only where shipped contracts changed.
- [ ] Stop for review before starting SSR-2.

## Out Of Scope

- creating report hosts or manifests from lifecycle mutation;
- changing child inclusion in parent discovery;
- Projects-specific config or behaviour;
- Tag Registry mutation or field synchronisation;
- a customisation framework for unrelated reports; and
- additional toolbar actions without an accepted exact target and capability
  contract.

## Completion Gates

- The default works with no collection customisation.
- `studio/default` uses canonical `docs_subscope`, and no temporary candidate
  registry, loader, dispatch, or module identity remains.
- Analysis/Tags uses a configured registered module and preserves accepted
  behaviour.
- The default and dispatcher contain no Analysis/Tags special case.
- Public projections and imports remain isolated from Manage code and data.
- Every action consumes only its explicit collection, checked IDs, or
  validated document target.
- Any accepted `last_updated` field has a visible report use and deterministic
  missing-value handling.
- Durable documentation matches the shipped extension rule.
