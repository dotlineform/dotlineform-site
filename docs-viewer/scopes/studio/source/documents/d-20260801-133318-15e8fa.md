# PRJ-3 — Docs Viewer Project State Delivery

## Status And Purpose

Proposed as **PRJ-3** after Project documents expose their folder links through
the local Manage manifest.

This delivery replaces Studio's Project State machinery with a Docs Viewer
report that compares current folders, Project-document metadata, and historical
Work folder snapshots. The same normalized refresh publishes the bounded
lookup that PRJ-4 will consume.

## Complete Outcome

One report-host document in scope `dotlineform` opens a current three-way
reconciliation. It shows exact agreement and drift states, links to matching
Project documents, Works, Series, and validated folder targets, and supports an
explicit full Refresh.

Known Docs Viewer and Studio mutations update only affected relationship rows
after their canonical commits. Full refresh remains available for direct
Finder changes and recovery. The report is read-only.

The old `/studio/project-state/` route and static Markdown pipeline no longer
exist as a second owner.

## Fixed Design Notes

- The three inputs retain different meanings: current physical evidence,
  user-maintained convenience links, and historical catalogue facts.
- Folder identity is relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`. The initial
  discovery scan is rooted at `projects/`, while exact declared Project links
  elsewhere below the base directory still receive existence and relationship
  state.
- Project State normalizes relative folder keys once and publishes report data
  plus resolver data from one generation.
- The folder scan observes folder identities, not primary-image completeness.
- Report open and explicit Refresh perform a full scan so direct Finder changes
  are visible; no filesystem watcher is introduced.
- Trusted application mutations default to targeted delta updates.
- The exact Work observer is server-side after canonical commit and read-only
  with respect to Studio. It uses `current_record`, `updated_record`, and
  `changed_fields`, not a browser event or publication transition.
- The observer responds to existing Work fields by writing derived Docs Viewer
  state only. It never adds or reads `folder_path`, rewrites `project_folder`,
  or makes the canonical Work commit depend on Project State refresh.
- `project_folder` and `project_subfolder` change topology; `title` updates
  displayed Work labels; `series_ids` updates report enrichment;
  `project_filename` and unrelated metadata do not change folder relations.
- Derived-projection failure never rolls back or repeats a committed Work or
  document mutation. The prior complete snapshot is retained and marked stale.
- The Project resolver lookup is Manage-only and unusable as canonical data.

## Delivery Discipline

PRJ-3 is inherently larger than PRJ-1 or PRJ-2, so its size must be controlled
per sub-delivery rather than hidden in one replacement diff. It should compose
the existing canonical readers, Docs Viewer report host, generated-payload
writer, and exact post-commit seams around one Project-specific reconciliation
model.

PRJ-3.0 must record the exact proposed files and rough production/test diff for
PRJ-3.1, PRJ-3.2, and PRJ-3.3 separately. A new generic graph, event bus,
reporting platform, repair framework, or rewritten catalogue reader is scope
creep and requires its own accepted delivery. Each stage stops at its review
checkpoint if the observed diff or dependencies materially exceed the estimate.

## Rough Delivery Steps

### PRJ-3.0 — Trace And Freeze The Replacement

- [ ] Trace the existing Studio route, service, report/open APIs, activity
  integration, Markdown writer/opener, tests, and all consumers of shared
  image-extension policy.
- [ ] Freeze normalized folder identity, three input schemas, report rows and
  states, exact links, snapshot metadata, resolver lookup schema, and stale
  presentation.
- [ ] Freeze configured discovery roots separately from the broader base-root
  containment and exact-existence policy.
- [ ] Freeze full-refresh triggers, targeted delta shapes, transaction/publish
  boundary, and mutation failure response.
- [ ] Record exact files, reused seams, and separate rough production/test diff
  estimates for PRJ-3.1, PRJ-3.2, and PRJ-3.3 before implementation approval.

**Checkpoint:** one fixture explains every report state and the precise output
rows affected by Work create, edit, move, title change, Series change, delete,
Project URL change, and Project document delete.

### PRJ-3.1 — Build The Three-Way Producer And Report

- [ ] Implement the confined folder-only inventory and normalized
  reconciliation service.
- [ ] Read Project-document evidence from the customisation-owned Manage
  manifest and Studio evidence from canonical Works/Series readers.
- [ ] Atomically publish report and Project resolver payloads from one snapshot.
- [ ] Register the local report and create its ordinary `dotlineform` host
  document.
- [ ] Render summary, filters, exact links, duplicate/malformed/missing states,
  explicit Refresh, and contained unavailable/stale states.

### PRJ-3.2 — Add Targeted Refresh Hooks

- [ ] Add one Project State impact classifier at the shared server-side Work
  committed-mutation boundary.
- [ ] Route create, save, delete, bulk save, and import through complete exact
  before/after deltas or the explicit full-rebuild fallback.
- [ ] Add equivalent exact Project-document metadata/create/delete follow-through.
- [ ] Update affected subject and reverse-index rows under one atomic snapshot
  generation.
- [ ] Preserve the last complete snapshot and report follow-through failure
  without retrying the canonical mutation.

### PRJ-3.3 — Retire Studio Ownership And Verify

- [ ] Move any still-shared `IMAGE_EXTENSIONS` policy before deleting the old
  report module.
- [ ] Remove or reroute the Studio route, frontend, APIs, activity contract,
  Markdown generator/opener, generated file, and obsolete tests/config.
- [ ] Run focused reconciliation, normalization, report, mutation-delta,
  atomic-publish, stale-state, exact-link, public-isolation, lint, and
  whitespace checks.
- [ ] Manually review real agreement, orphan, prospective, stale, duplicate,
  moved/renamed, empty, error, long-path, and narrow-screen states.
- [ ] Transfer the shipped report contract to the durable Docs Viewer Reports
  owner and keep Projects-specific architecture here.

## Not In Scope

- automatic repair or synchronization;
- mutation controls in the report;
- primary-image auditing;
- continuous folder watching;
- public Project State data; or
- Resolver Token parsing and rendering, which belongs to PRJ-4.

## Completion Evidence

- Fixture and real-data evidence prove all three input classes and explicit
  unmatched/duplicate/incomplete states.
- Targeted update tests show the bounded rows touched for every relevant Work
  and Project-document mutation class.
- Full refresh observes direct Finder changes and atomically publishes matching
  report/lookup generations.
- Studio has no remaining Project State route, generator, static report, or
  hidden second implementation.
- Public projections contain no local folder paths, lookup data, service URL,
  or report loader.
