# SSP-2 — Docs Viewer Project State Delivery

## Status And Purpose

Proposed as **SSP-2** after SSP-1 projects normalized authoring subjects through the local `dotlineform/projects` Manage manifest. [Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9) owns the folder-only filter and reconciliation model consumed by this delivery.

This delivery builds Project State as a persistent generated Docs Viewer document plus a versioned folder relationship snapshot and Manage-only resolver lookup. It does not retire the existing image-audit workflow; that belongs to [SSP-7 — Project Media Audit Delivery](/docs/?scope=studio&doc=d-20260802-121106-15ea55).

## Complete Outcome

One stable document in scope `dotlineform` contains the last successfully generated Project State Markdown. Its primary table has exactly four relationship columns: **Doc**, **Folder**, **Works**, and **Series**. Each normalized folder row may contain several exact Project-document, Work, and Series links. Work IDs and their canonical draft/published evidence remain explicit because the folder-to-Work connection shows whether physical source media has been represented through Studio.

Running or explicitly refreshing Project State computes the folder-centred snapshot, saved report source, and resolver lookup from one generation, then rebuilds the exact report document. Opening the saved document does not scan the filesystem. Known Docs Viewer and Studio mutations update only affected relationships after their canonical commits; full refresh remains available for direct Finder changes and recovery.

SSP-3 can consume the accepted lookup as soon as its generation, failure, and access contracts are proven. The current `/studio/project-state/` route and `var/studio/reports/project-state.md` remain until SSP-7 preserves and renames their image-audit capability.

## Fixed Design Notes

- The normalized relationship is `documents[] <- folder_path -> works[] -> series[]`.
- One row represents one base-relative folder path. Multiple Project documents, Works, and Series remain ordered arrays rather than duplicate rows or scalar shortcuts.
- Only documents with one valid `folder_path` participate. No-subject, Work-subject, and Series-subject documents in the same sub-scope are ordinary non-participants rather than Project State exceptions.
- Every canonical Work matching the normalized folder remains explicit by semantic Work identity with its current canonical status and available publication date. Work titles and URLs remain catalogue-owned presentation rather than copied truth.
- Matched Works contribute the deduplicated ordered union of their `series_ids`; Series context does not replace exact Work evidence.
- Folder identity is relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`. Initial discovery is rooted at `projects/`, while exact declared contained targets elsewhere still receive existence and relationship state.
- The saved report is generated Markdown with a stable `doc_id`, not a dynamic report module. Manual edits to its generated body are not preserved.
- Opening displays the last complete report. Explicit Run/Refresh performs the full scan; no filesystem watcher is introduced.
- The folder lookup returns `Work[] + Series[] + Project documents[]` for one exact folder subject. Work and Series items carry semantic catalogue identity rather than stored titles or URLs; Work items also retain the bounded status evidence emitted by Project State.
- Trusted application mutations default to targeted follow-through. Work create/delete, folder fields, `series_ids`, status, and publication date can change row evidence; Work title is presentation-only and `project_filename` is unrelated.
- The exact Work observer is server-side after canonical commit and read-only with respect to Studio. It uses exact before/after records, never rewrites Studio, and never makes the canonical commit depend on Project State.
- Derived-generation failure never rolls back or repeats a committed Work or document mutation. The prior complete generation remains readable and is marked stale.
- Project State is Manage-only derived data and unusable as canonical truth.

## Delivery Discipline

SSP-2 is inherently larger than the completed Projects glue deliveries, so its size must be controlled per checkpoint rather than hidden in one replacement diff. It should compose existing canonical readers, the Projects Manage manifest, exact Docs Viewer source/build seams, generated-payload writers, and server-side post-commit boundaries around one Project-specific producer.

SSP-2.0 is a short scope-and-spec sanity gate over the producer/lookup, saved report workflow, and targeted follow-through. It confirms broad owners, blast radius, deliverables, risks, and stop conditions without freezing exact files, fixtures, estimates, or implementation. A dynamic report framework, generic graph, event bus, repair system, rewritten catalogue reader, or media-audit migration is scope creep. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

## Delivery Steps

### SSP-2.0 — Confirm Scope And Delivery

- [ ] Sanity-check the folder-centred Project State, explicit Work publication evidence, saved-report, focused-lookup, and targeted-follow-through outcome against the accepted SSP-1 Projects subject contract and current catalogue, Projects manifest, generated-document, and post-commit models; resolve only contradictions that would change the result.
- [ ] Confirm the broad blast radius across folder inventory/reconciliation, canonical Works and Series reads, Project associations, versioned snapshot/lookup, generated Markdown, explicit Run/Refresh, exact builds, and post-commit impact handling.
- [ ] Confirm the deliverables: one matching report/snapshot/lookup generation, stable Doc/Folder/Works/Series document, exact folder lookup, full refresh, bounded follow-through, stale-state retention, focused evidence, and concise durable owner updates.
- [ ] Stop for review if the result requires a dynamic report framework, generic graph, event bus, repair system, rewritten catalogue reader, media-audit migration, or another boundary excluded above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the revised typed-subject spec, scheduling dependencies, broad owners, blast radius, deliverables, risks, local/public boundary, and stop condition. Stop before implementation approval.

### SSP-2.1 — Build The Folder-Centred Producer And Lookup

- [ ] Implement the confined folder-only inventory and normalized reconciliation service.
- [ ] Read Project-document evidence from the customisation-owned Manage manifest and retain each exact canonical Work whose recorded source folder matches the row, including its semantic identity, status, and available publication date.
- [ ] Derive each folder's deduplicated ordered `series[]` union from the retained Works' canonical `series_ids`.
- [ ] Retain current, declared, catalogue-only, missing, duplicate-folder-document, malformed-folder, and incomplete-catalogue evidence without treating other authoring-subject kinds as Project State records.
- [ ] Publish one versioned snapshot and exact folder-keyed lookup whose groups are `Work[] + Series[] + Project documents[]`.
- [ ] Prove lookup rows contain semantic Work/Series identities and bounded Work status evidence without Work/Series document associations, stored catalogue URLs, or live-scan fallbacks.

**Checkpoint:** focused inventory, normalization, folder-to-Work reconciliation, publication evidence, Series-union, lookup-schema, generation, and public-isolation evidence passes. An independent code/diff review confirms the producer reads existing authorities, retains exact Work identity without copying catalogue presentation, emits one bounded generation, and leaves saved-document UI, mutation hooks, Resolver behavior, and media-audit migration with their later delivery owners. Stop before SSP-2.2.

### SSP-2.2 — Publish The Saved Docs Viewer Report

- [ ] Create one stable generated Markdown document in scope `dotlineform` with a clearly owned body and ordinary Docs Viewer reachability.
- [ ] Render the Doc/Folder/Works/Series table, compact freshness/count context, exact links, multiple values per cell, canonical Work status evidence, and explicit empty/exception states.
- [ ] Add the explicit Run/Refresh workflow that computes and validates one generation, saves the report source, publishes its matching snapshot/lookup, and rebuilds the exact document.
- [ ] Preserve the previous complete report and lookup on generation failure; opening the document must never trigger a scan.
- [ ] Verify Source readability, normal word wrapping, search/bookmark behavior, long cells, and table presentation at representative laptop/desktop widths.

**Checkpoint:** focused generated-document, source-write, exact-build, report/lookup agreement, failure-retention, opening-without-scan, and representative presentation evidence passes. An independent code/diff review confirms stable document ownership while targeted mutation follow-through remains SSP-2.3-owned and Studio media-audit retirement remains SSP-7-owned. Stop before SSP-2.3.

### SSP-2.3 — Add Targeted Follow-Through And Verify

- [ ] Add one Project State impact classifier at the shared server-side Work committed-mutation boundary.
- [ ] Route create, save, delete, bulk save, and import through complete exact before/after deltas or the explicit full-rebuild fallback.
- [ ] Add equivalent exact Project-document metadata/create/delete follow-through for valid `folder_path` declarations only.
- [ ] Recompute affected folder memberships for Work folder/Series changes and Project-document folder changes; refresh Work evidence for status/publication-date changes; prove Work filename changes and document `work_id`/`series_id` changes do nothing while Work title changes affect presentation only.
- [ ] Regenerate the compact saved Markdown from the updated snapshot without scanning unrelated inputs.
- [ ] Preserve the last complete generation and report follow-through failure without retrying the canonical mutation.
- [ ] Run focused model, normalization, folder-to-Work, publication-evidence, Series-union, generated-document, mutation-delta, generation-agreement, stale-state, exact-link, semantic-descriptor, public-isolation, lint, and whitespace checks.
- [ ] Manually review real agreement, no-folder-document, no-Series, prospective, stale, duplicate, moved/renamed, malformed-folder, error, and long-cell states at representative laptop/desktop widths.
- [ ] Perform the independent final code/delivery review, reconcile completion claims with exact evidence and omissions, and update only durable owners whose shipped contracts changed.

## Not In Scope

- automatic repair or synchronization;
- mutation controls in the report;
- image discovery or primary-image auditing, which belongs to SSP-7;
- continuous folder watching;
- public Project State data;
- Work/Series reverse associations, Manage index subject cues, editorial copy, or public Work/Series `doc_url[]` projection;
- retirement of `/studio/project-state/` or `var/studio/reports/project-state.md`, which belongs to SSP-7; or
- Resolver Token parsing and rendering, which belongs to [SSP-3](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4).

## Completion Evidence

- Fixture and real-data evidence prove folder-keyed `documents[]`, `works[]`, and `series[]` plus every unmatched, duplicate, malformed-folder, draft/published, and incomplete state while no-subject/Work-subject/Series-subject documents remain absent.
- The saved Docs Viewer document persists the latest successful Doc/Folder/Works/Series Markdown and opens without scanning.
- Full refresh observes direct Finder changes and publishes one matching report/snapshot/lookup generation.
- Targeted tests show bounded relationship effects for every relevant Work and Project-document mutation class, no effect for Work filename changes, and title handling confined to explicit presentation refresh or the next full run without relationship mutation.
- SSP-3 can resolve one folder row to semantic Work/Series descriptors and exact Project-document targets without a live scan.
- Public projections contain no local folder paths, Project State data, lookup path, service URL, or refresh capability.
- The current Studio image-audit workflow remains unchanged for SSP-7 rather than being partially retired here.
