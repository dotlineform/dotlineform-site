# SSP-2 — Docs Viewer Project State Delivery

## Status And Purpose

Proposed as **SSP-2** after the completed SSP-1 subject foundation. [Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9) owns the folder-only filter and reconciliation model consumed by this delivery.

This delivery builds Project State with the existing local Docs Viewer report-host mechanism plus a versioned Manage-only resolver lookup. It does not introduce generated report Markdown, persist report presentation, or retire the existing image-audit workflow; that belongs to [SSP-6 — Project Media Audit Delivery](/docs/?scope=studio&doc=d-20260802-121106-15ea55).

## Accepted SSP-1 Input

SSP-2 consumes the private `dotlineform/projects` `manage-manifest.json` and `subject-associations.json` as one generation. The Manage manifest supplies `subject_generation` plus exact document rows whose `authoring_subject` is `{state, kind, key, fields}` with optional private `evidence`. The association product uses `docs_subject_associations_v1`, repeats that generation and exact collection, and groups each valid `{kind, key}` to ordered exact document targets and current Manage locations. SSP-2 must require matching receipts before joining document presentation to folder associations.

Only associations whose subject is `{kind: "folder", key: "projects/<path>"}` and whose exact key matches a scanned real-folder row enter Project State. Valid folder assignments elsewhere under the base root are ordinary non-participants, as are Work, Series, None, malformed, and conflicting subject rows. The Folder icon, Catalogue icon, warning cue, and Info presentation are Manage UI projections rather than Project State inputs. SSP-2 takes subject identity exclusively from normalized state and the matching association receipt.

## Complete Outcome

One ordinary human-authored document in scope `dotlineform` declares `viewer_report: project_state` and `viewer_report_access: local`. When the report mounts, it runs a fresh server-side reconciliation and renders a three-column table: **Folder**, **Docs**, and **Works by Series**. Each row originates from one scanned real folder. Project documents and canonical Works join independently by exact normalized folder identity; a document never mediates the Work relationship. Each linked canonical Series label is followed by the number of matching canonical Works whose current `series_ids` include that Series. Project State counts records in `works.json`; it does not enumerate files or distinguish draft from published Works.

The producer scans `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` only; it never scans the base root or sibling trees. Every row therefore has an exact normalized key beginning `projects/`. Report labels remove that guaranteed prefix and prepend `/`, so `projects/curve/poems (2025)` appears as `/curve/poems (2025)`. Finder activation and all lookup joins continue to use the complete normalized key.

Each successful run returns one complete versioned Project State JSON response containing generation/run context and the typed data needed to render and activate every row. The browser holds that response as one ephemeral row set; it never joins the authoritative inputs. Dynamic case-insensitive substring search covers the visible text in all three columns after every input change, and every column supports deterministic ascending/descending sorting without another server request. Folder path is the initial ascending sort; Docs sorts from the first ordered document title and exact ID; Works by Series sorts from the distinct matched-Work count rather than the potentially double-counted sum of Series memberships.

For example:

| Folder | Docs | Works by Series |
| --- | --- | --- |
| `/curve/poems (2025)` opens in Finder | one or more exact Project-document links | [`curve poems`](/series/?series=036) — 87 works |
| `/example/document-only` opens in Finder | one or more exact Project-document links | no canonical Works |
| `/example/works-only` opens in Finder | no document | [`series 1`](/series/?series=001) — 12 works |
| `/example/folder-only` opens in Finder | no document | no canonical Works |

If a folder's Works belong to two Series, the final cell renders one linked line per Series, such as `series 1 — 87 works` and `series 2 — 1 work`. A Work belonging to both Series contributes once to both membership counts; the figures are not a physical-file count or an implied unique total.

Opening Project State and selecting Run/Refresh perform the same complete server operation: scan, join, validate, return live rows, and atomically publish the matching resolver lookup. A successful refresh replaces the browser row set and reapplies the active search and sort. A failed run shows a contained error rather than an older result; the previous complete resolver lookup remains available and is marked stale. Known Docs Viewer and Studio mutations update only affected lookup relationships after their canonical commits.

The mounted report offers **Copy table** and **Copy Markdown**. Both serialize the currently filtered rows in their current sort order, including the three headings and keeping one physical folder per output row. Copy table emits semantic TSV with visible link text for direct spreadsheet paste. Copy Markdown emits a Markdown table retaining exact Folder, Project-document, and Series links. Multiple documents or Series values remain ordered in one cell and use `; ` separators; neither transform duplicates rows, performs a network request, persists report state, or shows a success message.

SSP-3 can consume the accepted lookup as soon as its generation, failure, and access contracts are proven. The current `/studio/project-state/` route and `var/studio/reports/project-state.md` remain until SSP-6 preserves and renames their image-audit capability.

## Fixed Design Notes

- The normalized relationship is `scanned real folder -> documents[]` and, independently, `scanned real folder -> works[] -> series memberships[]`.
- One row represents one real folder established by the current scan. Multiple Project documents, Works, and Series remain ordered arrays rather than duplicate rows or scalar shortcuts.
- Only documents with one valid `folder_path` beginning `projects/` and exactly matching a scanned row participate. Valid assignments elsewhere under the base root, no-subject, Work-subject, Series-subject, malformed, conflicting, and recorded-only paths remain outside Project State.
- Every canonical Work whose recorded source folder matches the normalized row remains explicit by semantic Work identity and current canonical `series_ids`. Draft/published status and publication date are outside Project State.
- Matched Works are grouped by canonical Series ID for report presentation. Each Series count is the number of matched Work records whose `series_ids` include that ID; one Work may contribute to more than one Series count.
- Folder identity is relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, while the complete scan boundary is its `projects/` subtree. The report omits the guaranteed leading `projects/` from the displayed label; identity and activation retain it.
- Project State is a local report module mounted by an ordinary stable Docs Viewer document through the existing report registry, allowlisted loader, and report service.
- Mount and explicit Run/Refresh perform the full scan. Rendered rows are ephemeral browser state; no generated Markdown, persisted presentation snapshot, report-source rewrite, or filesystem watcher is introduced.
- One complete live JSON response supplies the browser row set. Search, column sorting, and both clipboard transforms operate only on that current in-memory projection and never join or reread authoritative inputs.
- Search is a dynamic case-insensitive substring match over the visible Folder, Docs, and Works-by-Series cell text. Every column sorts in both directions with normalized folder identity as the deterministic final tie-break.
- Copy table emits semantic TSV for Excel; Copy Markdown emits a Markdown table with exact links. Both include headings, use the current filtered/sorted projection, retain one folder per row, join multiple cell entries with `; `, and produce no success message.
- The folder lookup returns `Work[] + Series[] + Project documents[]` for one exact folder subject. Work and Series items carry semantic catalogue identity rather than stored titles or URLs; Series membership is retained without Work publication status.
- Trusted application mutations default to targeted follow-through. Work create/delete, folder fields, and `series_ids` can change row evidence; Work title, status, publication date, and `project_filename` are unrelated.
- The exact Work observer is server-side after canonical commit and read-only with respect to Studio. It uses exact before/after records, never rewrites Studio, and never makes the canonical commit depend on Project State.
- Derived-lookup failure never rolls back or repeats a committed Work or document mutation. The prior complete lookup remains readable to SSP-3 and is marked stale.
- Project State is Manage-only derived data and unusable as canonical truth.

## Delivery Discipline

SSP-2 is inherently larger than the completed Projects glue deliveries, so its size must be controlled per checkpoint rather than hidden in one replacement diff. It should compose existing canonical readers, the Projects Manage manifest, exact Docs Viewer source/build seams, generated-payload writers, and server-side post-commit boundaries around one Project-specific producer.

SSP-2.0 is a short scope-and-spec sanity gate over the live producer/lookup, existing report-host fit, and targeted follow-through. It confirms broad owners, blast radius, deliverables, risks, real scan timing, and stop conditions without freezing exact files, fixtures, estimates, or implementation. A new reporting framework, generic graph, event bus, repair system, rewritten catalogue reader, or media-audit migration is scope creep. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

## Not In Scope

- automatic repair or synchronization;
- mutation controls in the report;
- image discovery or primary-image auditing, which belongs to SSP-6;
- scanning `$DOTLINEFORM_PROJECTS_BASE_DIR/` itself or reporting physical folders and recorded paths outside its `projects/` subtree;
- reverse reconciliation of document or Work paths that do not match a scanned real folder, which belongs to a separate report;
- continuous folder watching;
- downloaded CSV/TSV files, saved export history, or automatic clipboard persistence;
- public Project State data;
- Work/Series reverse associations, Manage index subject cues, editorial copy, or public Work/Series `doc_url[]` projection;
- retirement of `/studio/project-state/` or `var/studio/reports/project-state.md`, which belongs to SSP-6; or
- Resolver Token parsing and rendering, which belongs to [SSP-3](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4).

- The ordinary report host automatically runs and renders the live Folder/Docs/Works-by-Series response, presents `projects/` paths without that prefix, and offers explicit Run/Refresh.
- The browser consumes one complete live JSON response, searches visible text across all columns after each input change, sorts every column deterministically, and reapplies active search/sort state after refresh without joining inputs or making interaction-time requests.
- Copy table produces semantic TSV suitable for Excel and Copy Markdown produces a linked Markdown table from the same current filtered/sorted projection, with one folder per row and no persisted report state.
- Each full run observes direct Finder changes, returns current rows, and publishes one matching resolver-lookup generation without persisting report presentation.
- Targeted tests show bounded relationship effects for exact scanned-folder matches, no Project State row creation from recorded-only paths, and no effect from Work filename, title, status, or publication-date changes.
- SSP-3 can resolve one folder row to semantic Work/Series descriptors and exact Project-document targets without a live scan.
- Public projections contain no local folder paths, Project State data, lookup path, service URL, or refresh capability.
- The current Studio image-audit workflow remains unchanged for SSP-6 rather than being partially retired here.
