# SSP-2 — Docs Viewer Project State Delivery

## Status And Purpose

SSP-2.6 is complete and SSP-2 is reclosed. The producer emits one v2 live response with all-subject placement and provenance-aware browser projections; the unused persisted Resolver lookup, schema, write/stale-retention machinery, service/browser fields, and dedicated tests are gone. [SSP-2.5 — Project State Document Tracing Evidence](/docs/?scope=studio&doc=d-20260805-202742-c6e13d) retains the accepted tracing correction, [SSP-2.6 — Project State Lookup Retirement Evidence](/docs/?scope=studio&doc=d-20260806-073328-5c55a3) records the bounded cleanup, and [Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9) owns the durable report contract.

This delivery builds Project State with the existing local Docs Viewer report-host mechanism and removes its now-unused persisted lookup. It does not introduce generated report Markdown or persist report presentation. The separate Studio file-reconciliation workflow remained outside SSP-2 and was later retired by [SSP-6 — Uncataloged And Missing Source Files Reports Delivery](/docs/?scope=studio&doc=d-20260802-121106-15ea55).

## Accepted SSP-1 Input

SSP-2 consumes the private `dotlineform/projects` `manage-manifest.json` and `subject-associations.json` as one generation. The Manage manifest supplies `subject_generation` plus exact document rows whose `authoring_subject` is `{state, kind, key, fields}` with optional private `evidence`. The association product uses `docs_subject_associations_v1`, repeats that generation and exact collection, and groups each valid `{kind, key}` to ordered exact document targets and current Manage locations. SSP-2 must require matching receipts before joining document presentation to folder associations.

Every valid Folder, Work, or Series association is retained as exact document-subject evidence before Project State placement. A Folder subject reaches its exact scanned Folder key. A Work subject reaches the scanned Folder containing that canonical Work through `projects/<project_folder>`. A Series subject reaches every scanned Folder containing at least one current canonical member Work. None, malformed, conflicting, unknown, and currently unplaceable subjects enter no real-folder row. The Folder, single-Work, Series-list, warning, and Info cues remain Manage UI projections rather than Project State inputs. SSP-2 takes subject identity exclusively from normalized state and the matching association receipt; catalogue relationships decide placement without rewriting the declared subject.

## Complete Outcome

One ordinary human-authored document in scope `dotlineform` declares `viewer_report: project_state` and `viewer_report_access: local`. When the report mounts, it runs a fresh server-side reconciliation and renders a three-column table: **Folder**, **Series**, and **Docs**. Each row originates from one scanned real folder. Canonical Works join independently through the row key `projects/<project_folder>`; documents then reach those established rows through exact Folder, Work, or Series subject relationships. A document never creates a Folder row or mediates the Work relationship. The Project State Work projection reads only `work_id`, `project_folder`, and `series_ids`; Studio catalogue/media retains `project_subfolder`, `project_filename`, and exact media resolution. The displayed Series cell projects only exact linked Series names and remains blank when none exist. The response retains canonical Work, Series-membership, document-placement, and exact declared-subject evidence without turning absent or incomplete membership into a browser diagnosis. Project State counts records in `works.json`; it does not enumerate files or distinguish draft from published Works.

The producer scans the immediate project directories under `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` only; nested directories remain contents of their owning project row. Every row therefore has an exact normalized key beginning `projects/` with one project-directory segment. Report labels remove that guaranteed prefix, so `projects/curve poems (2025)` appears as `curve poems (2025)`. Finder activation and all producer joins continue to use the complete normalized key.

Each successful run returns one complete versioned Project State JSON response containing generation/run context and the typed data needed to render and activate every row. The browser holds that response as one ephemeral source; it never joins the authoritative inputs. Folder is the default projection, with one row per real folder and every distinct document reaching that Folder shown once. The bounded icon-pill toggle retains Folder and Series projections. Series view derives one row per Series-folder relationship and filters document placements through retained subject provenance: a Series-subject document appears only under its exact Series, a Work-subject document appears under each current Series membership of that Work in the Folder, and a Folder-subject document remains Folder-wide context. A document placed in the Folder without a current Series route remains visible in a blank-Series row. Dynamic case-insensitive substring search covers the visible text in all three columns after every input change, and every column supports deterministic ascending/descending sorting without another server request.

For example:

| Folder | Series | Docs |
| --- | --- | --- |
| `curve poems (2025)` opens in Finder | [`curve poems`](/series/?series=036) | one or more exact Project-document links |
| `example/document-only` opens in Finder |  | one or more exact Project-document links |
| `example/works-only` opens in Finder | [`series 1`](/series/?series=001) |  |
| `example/folder-only` opens in Finder |  |  |

If a folder's Works belong to two Series, the Series cell renders one exact linked name per Series. The response retains the underlying Work identities and membership counts for validation, but the displayed report does not present those counts or interpret missing Series membership.

Opening Project State and selecting Run/Refresh perform the same complete server operation: scan, join, validate, and return live rows. A successful refresh replaces the browser row set and reapplies the active search and sort. A failed run shows a contained error rather than an older result. SSP-2 adds no Docs Viewer or Studio mutation hook, and no document build depends on Project State freshness.

The mounted report offers **Copy table** and **Copy Markdown**. Both serialize the current grouping's filtered rows in their current sort order and visible column order. Copy table emits semantic TSV with visible link text for direct spreadsheet paste. Copy Markdown emits the plain-text line `Project State - YYYY-MM-DD HH:MM`, using the report generation time in GMT, then one blank line and a Markdown table retaining exact Folder, Project-document, and Series links. Folder view keeps one physical folder per output row and joins multiple cell values with `; `; Series view emits one row per Series-folder relationship plus any required blank-Series document row, and its Docs cell follows the same provenance-aware placement as the visible report. Neither transform performs a network request, persists report state, creates an archive, or shows a success message.

[SSP-3](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4) is independent of Project State and inserts one authored subject reference without reading or refreshing this report. SSP-6 later replaced the former `/studio/project-state/` route and `var/studio/reports/project-state.md` with separate Uncataloged Files and Missing Source Files reports; that retirement did not change Docs Viewer Project State.

## Fixed Design Notes

- The normalized relationship is `scanned real folder <- exact Folder subject | Work.project_folder | Series member Work.project_folder`. The physical scan remains the only row authority; the three declared subject kinds provide deterministic document placements into those rows.
- One scanned real folder is one immediate project directory under `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`; its nested directories remain contents rather than Project State rows.
- One row represents one real folder established by the current scan. Multiple Project documents, Works, and Series remain ordered arrays rather than duplicate rows or scalar shortcuts. One document appears at most once per Folder even when several member Works establish the same Series placement.
- Folder subjects participate by exact scanned key, Work subjects through the canonical Work's exact first-level `project_folder`, and Series subjects through every scanned Folder containing a current member Work. Valid but currently unplaceable subjects remain outside real-folder rows without being retyped or treated as invalid.
- Every canonical Work projects to `projects/<project_folder>` for its Project State join. Project State reads only `work_id`, `project_folder`, and `series_ids`; Studio catalogue/media retains `project_subfolder`, `project_filename`, exact media resolution, draft/published status, and publication date.
- Matched Works are grouped by canonical Series ID. Each Series count retained in the response is the number of matched Work records whose `series_ids` include that ID; one Work may contribute to more than one Series count. Browser presentation uses only exact linked Series names.
- Folder identity is relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, while the complete scan boundary is its `projects/` subtree. The report displays only the remaining first-level name after omitting `projects/`; identity and activation retain the complete key.
- Project State is a local report module mounted by an ordinary stable Docs Viewer document through the existing report registry, allowlisted loader, and report service.
- Mount and explicit Run/Refresh perform the full scan. Rendered rows are ephemeral browser state; no generated Markdown, persisted presentation snapshot, report-source rewrite, or filesystem watcher is introduced.
- One complete live JSON response supplies both browser projections. Each document placement retains exact declared-subject provenance plus the Series identities through which it applies. Folder view uses one row per scanned Folder; Series view derives provenance-aware Series-folder rows and retains a blank-Series row when required for documents with no current Series route. Displayed document links prefix the title with the Folder, single-Work, or Series-list cue for the exact declared subject through which the document entered Project State; the cue is provenance, not status or row identity.
- Search is a dynamic case-insensitive substring match over the visible Folder, Series, and Docs text. Every column sorts in both directions with normalized folder identity as the deterministic final tie-break.
- Copy table emits semantic TSV for Excel. Copy Markdown emits `Project State - YYYY-MM-DD HH:MM` from the report generation time in GMT, one blank line, then a Markdown table with exact links. Both include the current visible headings and filtered/sorted projection. Folder view retains one Folder per row; Series view retains one Series-folder relationship plus any required blank-Series document row and serializes only the Docs placed in that visible projection row. Subject cues remain display-only and copied document link text stays plain.
- `docs_project_state_report_v2` versions the changed document-placement semantics rather than silently changing v1 `documents[]`. Each projected document retains exact target, presentation, declared subject, and bounded Folder/Series placement provenance. Work and Series items continue to carry semantic catalogue identity rather than stored titles or URLs.
- Report mount and explicit Run/Refresh are the only SSP-2 reconciliation operations. Studio and Docs mutations retain their existing owners and add no Project State observer or synchronization hook.
- SSP-2.6 removed the former `docs_project_state_folder_lookup_v2` product and freshness machinery after Resolver Tokens were retired; Project State now returns only the live report and bounded run diagnostics.
- A failed Project State run never rolls back or repeats a Work or document mutation and never presents older browser rows as current.
- Project State is Manage-only derived data and unusable as canonical truth.

## Delivery Discipline

SSP-2 is inherently larger than the completed Projects glue deliveries, so its size was controlled per checkpoint rather than hidden in one replacement diff. It composes existing canonical readers, the Projects Manage manifest, and exact Docs Viewer report seams around one Project-specific producer. SSP-2.6 removed only the unused lookup output and its dedicated machinery without invalidating the accepted physical scan, canonical Work/Series projection, report host, interaction, clipboard, or public-isolation evidence.

SSP-2.0 was a short scope-and-spec sanity gate over the live producer and existing report-host fit. SSP-2.4 correctly removed tentative mutation hooks; the later retirement of the only proposed lookup consumer made the persisted lookup unnecessary, and SSP-2.6 removed it. A new reporting framework, generic graph, event bus, repair system, rewritten catalogue reader, or media-audit migration remains scope creep.

SSP-2.2 delivered an independently useful Folder-first basic report. SSP-2.3 added the bounded Folder/Series grouping control, search, sorting, and both clipboard formats over the accepted v1 response. SSP-2.5 preserves those controls while versioning the live response and making Series projection and clipboard rows follow exact document-placement provenance. SSP-3 has no dependency on this delivery.
