# SSP-2 — Docs Viewer Project State Delivery

## Status And Purpose

SSP-2 is in progress after the completed SSP-1 subject foundation. [SSP-2.0 — Project State Sanity Note](/docs/?scope=studio&doc=d-20260805-141842-8115c8) records the accepted implementation fit, direct-project-folder boundary, live scan timing, risks, and review gate. [SSP-2.1 — Project State Producer Evidence](/docs/?scope=studio&doc=d-20260805-153653-597788) records the completed producer, versioned lookup, real-data reconciliation, failure retention, and review evidence. [Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9) owns the folder-only filter and reconciliation model consumed by this delivery.

This delivery builds Project State with the existing local Docs Viewer report-host mechanism plus a versioned Manage-only resolver lookup. It does not introduce generated report Markdown, persist report presentation, or retire the existing image-audit workflow; that belongs to [SSP-6 — Project Media Audit Delivery](/docs/?scope=studio&doc=d-20260802-121106-15ea55).

## Accepted SSP-1 Input

SSP-2 consumes the private `dotlineform/projects` `manage-manifest.json` and `subject-associations.json` as one generation. The Manage manifest supplies `subject_generation` plus exact document rows whose `authoring_subject` is `{state, kind, key, fields}` with optional private `evidence`. The association product uses `docs_subject_associations_v1`, repeats that generation and exact collection, and groups each valid `{kind, key}` to ordered exact document targets and current Manage locations. SSP-2 must require matching receipts before joining document presentation to folder associations.

Only associations whose subject is `{kind: "folder", key: "projects/<path>"}` and whose exact key matches a scanned real-folder row enter Project State. Valid folder assignments elsewhere under the base root are ordinary non-participants, as are Work, Series, None, malformed, and conflicting subject rows. The Folder icon, Catalogue icon, warning cue, and Info presentation are Manage UI projections rather than Project State inputs. SSP-2 takes subject identity exclusively from normalized state and the matching association receipt.

## Complete Outcome

One ordinary human-authored document in scope `dotlineform` declares `viewer_report: project_state` and `viewer_report_access: local`. When the report mounts, it runs a fresh server-side reconciliation and renders a three-column table: **Folder**, **Series**, and **Docs**. Each row originates from one scanned real folder. Project documents join by exact normalized `folder_path`, while canonical Works join independently through the row key `projects/<project_folder>`; a document never mediates the Work relationship. The Project State Work projection reads only `work_id`, `project_folder`, and `series_ids`; Studio catalogue/media retains `project_subfolder`, `project_filename`, and exact media resolution. The displayed Series cell projects only exact linked Series names and remains blank when none exist. The response retains canonical Work and Series-membership evidence without turning absent or incomplete membership into a browser diagnosis. Project State counts records in `works.json`; it does not enumerate files or distinguish draft from published Works.

The producer scans the immediate project directories under `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` only; nested directories remain contents of their owning project row. Every row therefore has an exact normalized key beginning `projects/` with one project-directory segment. Report labels remove that guaranteed prefix, so `projects/curve poems (2025)` appears as `curve poems (2025)`. Finder activation and all lookup joins continue to use the complete normalized key.

Each successful run returns one complete versioned Project State JSON response containing generation/run context and the typed data needed to render and activate every row. The browser holds that response as one ephemeral source; it never joins the authoritative inputs. Folder is the default projection, with one row per real folder. SSP-2.3 adds a bounded **Group by Folder/Series** control: Series view derives one row per Series-folder relationship from the same response and changes the visible order to **Series**, **Folder**, **Docs**. Dynamic case-insensitive substring search covers the visible text in all three columns after every input change, and every column supports deterministic ascending/descending sorting without another server request.

For example:

| Folder | Series | Docs |
| --- | --- | --- |
| `curve poems (2025)` opens in Finder | [`curve poems`](/series/?series=036) | one or more exact Project-document links |
| `example/document-only` opens in Finder |  | one or more exact Project-document links |
| `example/works-only` opens in Finder | [`series 1`](/series/?series=001) |  |
| `example/folder-only` opens in Finder |  |  |

If a folder's Works belong to two Series, the Series cell renders one exact linked name per Series. The response retains the underlying Work identities and membership counts for validation and later purpose-specific consumers, but the displayed report does not present those counts or interpret missing Series membership.

Opening Project State and selecting Run/Refresh perform the same complete server operation: scan, join, validate, return live rows, and atomically publish the matching resolver lookup. A successful refresh replaces the browser row set and reapplies the active search and sort. A failed run shows a contained error rather than an older result; the previous complete resolver lookup remains available and is marked stale. Known Docs Viewer and Studio mutations update only affected lookup relationships after their canonical commits.

The mounted report offers **Copy table** and **Copy Markdown**. Both serialize the current grouping's filtered rows in their current sort order and visible column order. Copy table emits semantic TSV with visible link text for direct spreadsheet paste. Copy Markdown emits the plain-text line `Project State - YYYY-MM-DD HH:MM`, using the report generation time in GMT, then one blank line and a Markdown table retaining exact Folder, Project-document, and Series links. Folder view keeps one physical folder per output row and joins multiple cell values with `; `; Series view intentionally emits one row per Series-folder relationship and repeats folder/Docs context for multi-Series folders. Neither transform performs a network request, persists report state, creates an archive, or shows a success message.

SSP-3 can consume the accepted lookup as soon as its generation, failure, and access contracts are proven. The current `/studio/project-state/` route and `var/studio/reports/project-state.md` remain until SSP-6 preserves and renames their image-audit capability.

## Fixed Design Notes

- The normalized relationship is `scanned real folder -> documents[]` and, independently, `scanned real folder -> works[] -> series memberships[]`.
- One scanned real folder is one immediate project directory under `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`; its nested directories remain contents rather than Project State rows.
- One row represents one real folder established by the current scan. Multiple Project documents, Works, and Series remain ordered arrays rather than duplicate rows or scalar shortcuts.
- Only documents with one valid `folder_path` beginning `projects/` and exactly matching a scanned row participate. Valid assignments elsewhere under the base root, no-subject, Work-subject, Series-subject, malformed, conflicting, and recorded-only paths remain outside Project State.
- Every canonical Work projects to `projects/<project_folder>` for its Project State join. Project State reads only `work_id`, `project_folder`, and `series_ids`; Studio catalogue/media retains `project_subfolder`, `project_filename`, exact media resolution, draft/published status, and publication date.
- Matched Works are grouped by canonical Series ID. Each Series count retained in the response is the number of matched Work records whose `series_ids` include that ID; one Work may contribute to more than one Series count. Browser presentation uses only exact linked Series names.
- Folder identity is relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, while the complete scan boundary is its `projects/` subtree. The report displays only the remaining first-level name after omitting `projects/`; identity and activation retain the complete key.
- Project State is a local report module mounted by an ordinary stable Docs Viewer document through the existing report registry, allowlisted loader, and report service.
- Mount and explicit Run/Refresh perform the full scan. Rendered rows are ephemeral browser state; no generated Markdown, persisted presentation snapshot, report-source rewrite, or filesystem watcher is introduced.
- One complete live JSON response supplies both browser projections. Folder view uses one row per scanned folder; Series view derives one row per Series-folder relationship without changing the response, reconciliation, or resolver lookup.
- Search is a dynamic case-insensitive substring match over the visible Folder, Series, and Docs text. Every column sorts in both directions with normalized folder identity as the deterministic final tie-break.
- Copy table emits semantic TSV for Excel. Copy Markdown emits `Project State - YYYY-MM-DD HH:MM` from the report generation time in GMT, one blank line, then a Markdown table with exact links. Both include the current visible headings and filtered/sorted projection. Folder view retains one folder per row; Series view retains one Series-folder relationship per row and repeats folder/Docs context when required.
- The folder lookup returns `Work[] + Series[] + Project documents[]` for one exact folder subject. Work and Series items carry semantic catalogue identity rather than stored titles or URLs; Series membership is retained without Work publication status.
- Trusted application mutations default to targeted follow-through. Work create/delete, `project_folder`, and `series_ids` can change row evidence. Changes to `project_subfolder`, `project_filename`, Work title, status, or publication date produce no Project State impact or follow-through and remain owned by catalogue/media concerns.
- The exact Work observer is server-side after canonical commit and read-only with respect to Studio. It uses exact before/after records, never rewrites Studio, and never makes the canonical commit depend on Project State.
- Derived-lookup failure never rolls back or repeats a committed Work or document mutation. The prior complete lookup remains readable to SSP-3 and is marked stale.
- Project State is Manage-only derived data and unusable as canonical truth.

## Delivery Discipline

SSP-2 is inherently larger than the completed Projects glue deliveries, so its size must be controlled per checkpoint rather than hidden in one replacement diff. It should compose existing canonical readers, the Projects Manage manifest, exact Docs Viewer source/build seams, generated-payload writers, and server-side post-commit boundaries around one Project-specific producer.

SSP-2.0 is a short scope-and-spec sanity gate over the live producer/lookup, existing report-host fit, and targeted follow-through. It confirms broad owners, blast radius, deliverables, risks, real scan timing, and stop conditions without freezing exact files, fixtures, estimates, or implementation. A new reporting framework, generic graph, event bus, repair system, rewritten catalogue reader, or media-audit migration is scope creep. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

SSP-2.2 intentionally stops with an independently useful Folder-first basic report whose data, links, states, and layout can be accepted before browser refinements. SSP-2.3 adds the bounded Folder/Series grouping control, search, sorting, and both clipboard formats over that accepted live response without changing the server reconciliation or resolver lookup. SSP-3 need not wait for those presentation refinements once the lookup's generation, failure, and access contracts are accepted.

## Not In Scope

- automatic repair or synchronization;
- mutation controls in the report;
- image discovery or primary-image auditing, which belongs to SSP-6;
- a detail-level report whose rows or grouping follow `project_subfolder`, which would be a separate future report and delivery;
- scanning `$DOTLINEFORM_PROJECTS_BASE_DIR/` itself or reporting physical folders and recorded paths outside its `projects/` subtree;
- reverse reconciliation of document or Work paths that do not match a scanned real folder, which belongs to a separate report;
- continuous folder watching;
- downloaded CSV/TSV files, saved export history, or automatic clipboard persistence;
- arbitrary column layouts, user-authored grouping definitions, or a second Series-keyed server response;
- public Project State data;
- Work/Series reverse associations, Manage index subject cues, editorial copy, or public Work/Series `doc_url[]` projection;
- retirement of `/studio/project-state/` or `var/studio/reports/project-state.md`, which belongs to SSP-6; or
- Resolver Token parsing and rendering, which belongs to [SSP-3](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4).
