# PRJ-2 — Projects Customisation And Apple Notes Migration Delivery

## Status And Purpose

Active as **PRJ-2** after the local-link contract in PRJ-1. PRJ-2.0 is
complete and awaiting review; no product implementation or migration apply has
started.

Detailed file scope, owner tracing, estimates, implementation deviations, and
verification evidence are retained in the
[PRJ-2 Implementation And Verification Record](/docs/?scope=studio&doc=d-20260801-193557-78fd17).

This delivery turns `dotlineform/projects` into a useful folder-notes
collection. It adds one Manage-only registered customisation, one optional
`folder_path` metadata field, and a checked-in one-off migration for the
exported Apple Notes project corpus. It does not add a generic batch-import or
folder-seeding UI.

## Complete Outcome

Every Project document can store and edit one normalized **Folder Link**. The
exact value is written to source front matter and projected into that
document's namespaced row in local `manage-manifest.json`. The Projects report
can show the link and offer its exact Open in Finder action while the shared
default report and public manifest stay unchanged.

A write-free migration plan imports every exported Markdown file as a separate
Project document. A reviewed mapping from each exported top-level project
folder to a current `projects/` folder supplies `folder_path` where there is an
exact or explicitly accepted correspondence. Several documents may share the
same path. Notes without a current-folder match remain valid pathless Project
documents for later Project State review.

Apply consumes the exact reviewed plan, creates only its preallocated targets,
and can resume without allocating new identities or duplicating committed
documents. The migration produces a gap and exception report; it does not
consolidate notes, create empty documents for uncovered folders, or synchronize
the collection with the filesystem.

## Fixed Design Notes

- The configured collection selects a known `projects` customisation; no
  runtime branch infers behavior from scope, sub-scope, title, or filename.
- `folder_path` is optional convenience metadata, not identity, validity, or a
  lifecycle condition.
- `folder_path` belongs only to Project document source and the namespaced
  Docs Viewer Manage projection. PRJ-2 neither reads nor changes Studio Works
  and adds no Studio field, UI control, payload, hook, or service dependency.
- Project-specific row data lives only in the `customisation` namespace of the
  local Manage manifest.
- The ordinary/public manifest remains `{doc_id, title}` and imports no Manage
  customisation module.
- Edit Metadata reads and writes the exact validated Project document.
- Documents may be created with no path or with an in-root relative path that
  does not yet exist.
- The path validity and activation root is `$DOTLINEFORM_PROJECTS_BASE_DIR/`;
  a Project document may deliberately represent a contained folder outside
  `projects/`.
- The migration source is the exact dated Apple Notes export above. It does
  not scan other Notes exports or treat the general import staging area as
  migration input.
- Folder association uses the exported top-level project folder as provenance.
  Exact names may be proposed automatically; every unmatched folder requires
  an explicit reviewed mapping or an explicit no-current-folder result. There
  is no fuzzy matching.
- Every Markdown file is a separate Project document. All documents beneath
  one reviewed exported folder may deliberately share the same `folder_path`.
- Existing collection documents are not overwritten, consolidated, or adopted
  by title or body similarity. Any metadata update to an existing document is
  a separate exact-target action.
- Supported referenced assets use the existing import media pipeline.
  Unsupported, missing, `applenotes:`, and `sandbox:` references are preserved
  where safe and reported; PRJ-2 does not infer replacement targets or attempt
  link recovery.
- Pathless imported documents and current folders with no Project document are
  retained as visible reconciliation gaps for the later Project State report.
- Existing, missing, duplicate, and prospective documents remain untouched
  unless they are exact confirmed mutation targets.

## PRJ-2.1 Contract: Project Metadata, Editor, And Projection

PRJ-2.1 is one exact source-to-projection workflow, not merely an extra field
in `manage-manifest.json`:

```text
Edit Metadata -> Folder Link field
  -> exact Project document metadata save
  -> normalize and validate
  -> write folder_path to source front matter
  -> rebuild Projects
  -> project customisation.folder_path into manage-manifest.json
  -> refresh the Projects report
```

### Source Authority

- Project document source front matter is authoritative. The stored value is
  one optional decoded POSIX path relative to
  `$DOTLINEFORM_PROJECTS_BASE_DIR/`, for example
  `folder_path: projects/architecture`.
- `manage-manifest.json` is a generated read model, not storage or mutation
  authority. Its exact Project-document row receives only
  `customisation.folder_path` after source validation and rebuild.
- Blank metadata removes `folder_path` from source. The field may point to a
  missing or prospective contained folder, and several documents may store the
  same value.

### Registered Projects Customisation

- The configured `dotlineform/projects` collection selects one explicit
  Manage-only Projects customisation ID. The server registry, controlled
  manifest projector, and Manage browser registry use that same identity.
- The Projects browser contribution adds report row/detail presentation and a
  narrow Edit Metadata contribution. The generic report and metadata modal do
  not infer Projects behavior from scope, sub-scope, title, or path.
- PRJ-2.1 adds one additive customisation host/contract to Edit Metadata because
  the current report contribution seam does not own modal fields. It does not
  add a generic custom-field schema engine or hardcode `folder_path` into every
  metadata form.
- No public customisation loader is registered. Default reports, other
  sub-scopes, ordinary manifests, and public manifests retain their existing
  shapes and behavior.

### Exact Edit Metadata Flow

- Opening Edit Metadata for a Project document hydrates the exact canonical
  source through `{scope: "dotlineform", sub_scope: "projects", doc_id}` and
  retains its source-revision receipt. It does not populate the field from the
  index row or Manage-manifest projection.
- The read response exposes the source-owned value to the registered
  contribution as `record.customisation.folder_path`. The contribution renders
  one text field labelled **Folder Link** and displays the decoded relative
  value, such as `projects/architecture`.
- Save retains the same exact target and source revision and submits only the
  Projects contribution's strict `customisation.folder_path` value. Unknown
  customisation fields, missing target data, stale revisions, and use on an
  unconfigured collection fail closed.
- The server-owned Projects metadata adapter normalizes and validates the input,
  updates only the exact document's `folder_path` front matter, advances the
  canonical write timestamp when changed, and invokes the existing confined
  sub-scope rebuild owner.
- A successful response returns the exact committed target and normalized
  value. If source commit succeeds but report refresh or presentation fails,
  retry only that follow-through; never repeat the metadata mutation against an
  inferred or replacement document.

### Folder Link Input And Paste

- The field accepts an already normalized decoded relative value such as
  `projects/architecture`.
- It also accepts an absolute Finder/POSIX path, a local `file:` URL, or an
  absolute POSIX path with ordinary shell-display backslash escapes. Save uses
  the PRJ-1 server normalizer to remove the configured base and store only the
  decoded relative target.
- Markdown such as `[Architecture](dlf-local:projects/architecture)` and raw
  `dlf-local:` values are rejected. Those are body-link representations, not
  structured metadata values.
- Paste remains the browser's native text-input operation. There is no custom
  clipboard interception, `execCommand`, synthetic Undo, or paste status
  message. Normalization occurs on Save. The current modal closes before its
  asynchronous server write; an invalid or out-of-root value makes no source
  change and appears through the existing Manage error presentation.
- Validation proves a canonical contained target but does not require the
  target folder to exist.

### Manage Projection And Report Controls

- After the exact source write and rebuild, the local Manage manifest row is:

  ```json
  {
    "doc_id": "d-example",
    "title": "Architecture",
    "customisation": {
      "folder_path": "projects/architecture"
    }
  }
  ```

- A document with no `folder_path` has no projected folder value. Malformed
  source values fail controlled projection rather than leaking into the report.
- The Projects report contribution reads only its validated namespaced row
  data. It shows the exact path, an explicit no-link state, and duplicate use of
  one path without changing collection membership or repairing it.
- PRJ-2.1 does not scan the filesystem or project a derived existence flag.
  A stored path may be current, missing, or prospective; Project State owns
  that classification later. Open in Finder may report a missing target when
  the user explicitly invokes it.
- **Open in Finder** submits the exact projected relative target through the
  PRJ-1 local activation owner. It never falls back to the selected parent,
  displayed document, title, URL text, or another document's path.

## Delivery Discipline

PRJ-2 should remain one registered sub-scope customisation plus one checked-in
migration command under `docs-viewer/migrations/`. The command reuses existing
Apple Notes normalization, media, import planning/apply, atomic document
creation, and confined rebuild owners. It must not write source through a
parallel document writer or introduce another manifest format, generic
registry, folder synchronization service, batch-import endpoint, or general
bulk-workflow framework.

PRJ-2.0 must record the exact proposed files, reused owners, durable migration
plan/receipt shape, and rough production/test diff size. If the implementation
materially exceeds the one-field projector, exact-target controls, and
one-source migration described here, pause for review and move the extra
capability into a separately accepted delivery. Line count is a scope signal,
not a reason to compress or duplicate code.
