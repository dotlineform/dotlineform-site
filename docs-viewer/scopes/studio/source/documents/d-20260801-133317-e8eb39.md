# PRJ-2 — Projects Customisation And Apple Notes Migration Delivery

## Status And Purpose

Proposed as **PRJ-2** after the local-link contract in PRJ-1.

This delivery turns `dotlineform/projects` into a useful folder-notes
collection. It adds one Manage-only registered customisation, one optional
`folder_path` metadata field, and a checked-in one-off migration for the
exported Apple Notes project corpus. It does not add a generic batch-import or
folder-seeding UI.

## Complete Outcome

Every Project document can store and edit one normalized **Folder Link**. The
exact value is written to source front matter and projected into that
document's namespaced row in local `manage-manifest.json`. The Projects report
can show the link and offer its exact Open in Finder action while the shared
default report and public manifest stay unchanged.

A write-free migration plan imports every exported Markdown file as a separate
Project document. A reviewed mapping from each exported top-level project
folder to a current `projects/` folder supplies `folder_path` where there is an
exact or explicitly accepted correspondence. Several documents may share the
same path. Notes without a current-folder match remain valid pathless Project
documents for later Project State review.

Apply consumes the exact reviewed plan, creates only its preallocated targets,
and can resume without allocating new identities or duplicating committed
documents. The migration produces a gap and exception report; it does not
consolidate notes, create empty documents for uncovered folders, or synchronize
the collection with the filesystem.

## Observed Migration Inventory

The planning snapshot at
`$DOTLINEFORM_PROJECTS_BASE_DIR/Notes export - 2026-05-18/iCloud/dotlineform/projects`
contains:

- 240 Markdown files across 201 exported top-level project folders;
- 206 current direct child folders under `projects/`;
- 192 exact top-level folder-name matches, covering 228 Markdown files;
- 12 Markdown files in 9 unmatched exported folders;
- 19 exported folders containing more than one Markdown file; and
- 346 referenced exported assets.

The migration planner must recompute and hash the real inventory rather than
treat these counts as immutable. The current exceptional-reference snapshot
includes one `applenotes:` link, nine likely unrecoverable `sandbox:` links,
and referenced RTF and TXT files outside the ordinary attachment allowlist.

## Fixed Design Notes

- The configured collection selects a known `projects` customisation; no
  runtime branch infers behavior from scope, sub-scope, title, or filename.
- `folder_path` is optional convenience metadata, not identity, validity, or a
  lifecycle condition.
- `folder_path` belongs only to Project document source and the namespaced
  Docs Viewer Manage projection. PRJ-2 neither reads nor changes Studio Works
  and adds no Studio field, UI control, payload, hook, or service dependency.
- Project-specific row data lives only in the `customisation` namespace of the
  local Manage manifest.
- The ordinary/public manifest remains `{doc_id, title}` and imports no Manage
  customisation module.
- Edit Metadata reads and writes the exact validated Project document.
- Documents may be created with no path or with an in-root relative path that
  does not yet exist.
- The path validity and activation root is `$DOTLINEFORM_PROJECTS_BASE_DIR/`;
  a Project document may deliberately represent a contained folder outside
  `projects/`.
- The migration source is the exact dated Apple Notes export above. It does
  not scan other Notes exports or treat the general import staging area as
  migration input.
- Folder association uses the exported top-level project folder as provenance.
  Exact names may be proposed automatically; every unmatched folder requires
  an explicit reviewed mapping or an explicit no-current-folder result. There
  is no fuzzy matching.
- Every Markdown file is a separate Project document. All documents beneath
  one reviewed exported folder may deliberately share the same `folder_path`.
- Existing collection documents are not overwritten, consolidated, or adopted
  by title or body similarity. Any metadata update to an existing document is
  a separate exact-target action.
- Supported referenced assets use the existing import media pipeline.
  Unsupported, missing, `applenotes:`, and `sandbox:` references are preserved
  where safe and reported; PRJ-2 does not infer replacement targets or attempt
  link recovery.
- Pathless imported documents and current folders with no Project document are
  retained as visible reconciliation gaps for the later Project State report.
- Existing, missing, duplicate, and prospective documents remain untouched
  unless they are exact confirmed mutation targets.

## Delivery Discipline

PRJ-2 should remain one registered sub-scope customisation plus one checked-in
migration command under `docs-viewer/migrations/`. The command reuses existing
Apple Notes normalization, media, import planning/apply, atomic document
creation, and confined rebuild owners. It must not write source through a
parallel document writer or introduce another manifest format, generic
registry, folder synchronization service, batch-import endpoint, or general
bulk-workflow framework.

PRJ-2.0 must record the exact proposed files, reused owners, durable migration
plan/receipt shape, and rough production/test diff size. If the implementation
materially exceeds the one-field projector, exact-target controls, and
one-source migration described here, pause for review and move the extra
capability into a separately accepted delivery. Line count is a scope signal,
not a reason to compress or duplicate code.

## Rough Delivery Steps

### PRJ-2.0 — Freeze Customisation And Migration Contracts

- [ ] Trace current `dotlineform/projects` config, default report host,
  manifests, metadata schema/modal, document creation, and sub-scope
  customisation registries.
- [ ] Freeze `folder_path` source validation, Manage-manifest row shape, browser
  descriptor, row/detail controls, and public exclusion.
- [ ] Trace the ordinary Markdown/Apple Notes normalization, media rewrite,
  import plan/apply, document creation, rebuild, and existing migration seams.
- [ ] Freeze export inventory ownership, one-file/one-document title rules,
  stable identity allocation, source and asset hashes, reviewed top-level
  folder mapping, pathless output, exception reporting, and result locations.
- [ ] Freeze exact-plan apply, resumable receipt, collision refusal, supported
  asset handling, and committed rebuild retry behavior.
- [ ] Record the exact file list, reused seams, rough production/test diff
  estimate, and any proposed expansion before implementation approval.

**Checkpoint:** one reviewed contract covers a manually created prospective
document, a linked existing document, several imported documents sharing one
path, an unmatched pathless import, an exceptional reference, and an existing
collection document that the migration leaves untouched.

### PRJ-2.1 — Project Metadata And Projection

- [ ] Register the Manage-only Projects Python and browser customisation pair.
- [ ] Add exact-target `folder_path` read/write through the existing metadata
  owner and PRJ-1 normalizer.
- [ ] Project only validated namespaced row data into `manage-manifest.json`.
- [ ] Render Project-specific link state and exact Open in Finder without
  changing default membership or navigation.

### PRJ-2.2 — Apple Notes Migration Plan And Apply

- [ ] Add a checked-in one-off migration command with explicit `plan` and
  `apply` modes and the exact `dotlineform/projects` destination.
- [ ] Plan every Markdown file and referenced asset without collection writes,
  allocate stable document identities, hash the inputs, and emit a sanitized
  review report plus machine-readable plan.
- [ ] Propose exact folder-name mappings, require explicit decisions for all
  unmatched folders, allow multiple documents to share one path, and retain
  explicit no-current-folder results without inventing a match.
- [ ] Reuse the existing Apple Notes normalization and supported-media rewrite
  per Markdown file even when its export folder contains other Markdown files.
- [ ] Report preserved unsupported, missing, `applenotes:`, and `sandbox:`
  references without recovery guesses or silent loss.
- [ ] Apply only the exact reviewed create-only plan. Revalidation rejects
  changed inputs and unexpected target or media collisions.
- [ ] Persist enough exact receipt state to recognize already committed plan
  targets on retry, fail on mismatched content, and never allocate replacement
  identities or create duplicates.
- [ ] Rebuild the collection once after the planned source writes. A
  post-commit rebuild failure retries the rebuild only.

### PRJ-2.3 — Apply Real Migration And Review Gaps

- [ ] Run focused config, projector, metadata, customisation registry,
  migration-plan, exact-target, resume, exception-report, public-boundary,
  lint, and whitespace checks.
- [ ] Plan the real dated export before any apply and review representative odd
  names, explicit unmatched-folder decisions, multi-note folders, source/media
  collisions, and exceptional references.
- [ ] After explicit acceptance, apply the exact plan and inspect the real
  default/list/detail behavior at realistic density.
- [ ] Produce the reconciliation report: current folders with zero, one, or
  several associated documents; pathless imports; unmatched export folders;
  untouched existing documents; and unresolved asset/link exceptions.
- [ ] Transfer the shipped extension contract to the durable sub-scope
  customisation architecture and retain Projects-specific product meaning in
  the Projects Concept.

## Not In Scope

- continuous folder/document synchronization;
- a generic batch-import UI, API, or reusable bulk-workflow framework;
- automatic empty-document creation for current folders without an imported
  note;
- automatic note consolidation or existing-document deduplication;
- recovery or inferred replacement of `applenotes:` and `sandbox:` links;
- automatic rename, merge, delete, or stale-link repair;
- Work or Series reconciliation;
- Project State report generation;
- Resolver Tokens; or
- public folder metadata.

## Completion Evidence

- Manual and imported Project documents share the same front-matter and
  manifest contract.
- Default and public sub-scope payloads remain byte-compatible and folder-blind.
- The customisation uses exact document targets and handles missing/duplicate
  paths as visible states.
- The migration plan is write-free, identifies every source and target, and
  records explicit pathless and exceptional-reference results.
- Apply is create-only for the exact reviewed plan; retry recognizes committed
  targets and cannot allocate replacements or duplicate documents.
- The final report distinguishes zero, one, many, and no-current-folder states
  without repairing them ahead of Project State.
- Real collection review distinguishes generated projection evidence from
  manual UI acceptance.
