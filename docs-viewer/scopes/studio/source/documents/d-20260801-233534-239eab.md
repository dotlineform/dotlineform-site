# SSP-4 — Collection-Aware Document Copy Delivery

## Status And Purpose

Proposed as **SSP-4** in the [Sub-Scope Publishing](/docs/?scope=studio&doc=d-20260802-194357-4d857b) sequence, after [SSC-1](/docs/?scope=studio&doc=d-20260804-172012-5d91bf) establishes the unified customisation contract. It is not yet active and does not authorize implementation. SSP-4.0 must reconcile this retained transfer plan with SSP-1's accepted subject-transfer contract before implementation.

The current **Copy to scope…** workflow starts from the main Index selection and addresses only top-level scopes. This delivery makes Copy operate between exact managed document collections, so either end can be a configured parent scope or one-level sub-scope.

The immediate workflow is:

```text
dotlineform/projects working documents
  -> an Analysis editorial sub-scope, initially non-viewable
  -> manual content cleanup and review
  -> viewable documents included by the existing Analysis Publish workflow
```

Folder notes, Work/Series writing, and generic notes can therefore remain in one working collection. Any of them can become an independent editorial copy; shared `work_id`/`series_id` metadata is retained when present, unsupported `folder_path` is omitted and reported, and no subject is required for Copy or later publication.

## Complete Outcome

In Manage mode, **Copy to…** is available from checked main-Index documents and checked sub-scope documents. Its picker lists every exact configured collection that can accept the proposed copy. A target may be `{scope}` or `{scope, sub_scope}`; a sub-scope source is likewise carried explicitly rather than inferred from the report host or current URL.

Preview and confirmed apply preserve the existing independent-copy guarantees: fresh immutable document identities, create-only writes, target-owned default viewability, bounded media transfer, internal-link remapping, stale receipt revalidation, one coordinated target rebuild, and an exact result URL.

The normal `dotlineform/projects`-to-`analysis/works` copy creates flat, non-viewable Analysis sub-scope documents. Shared `work_id` or `series_id` front matter is retained as ordinary document metadata; neither its absence nor unusable authoring value blocks the copy. `folder_path` is omitted when the target lacks the Projects contract. The user can then edit the independent copies, make reviewed documents viewable, and use the existing parent Analysis **Publish** action. SSP-4 does not automate editorial review or publication, and later source-subject edits do not retarget the independent copy.

## Fixed Contracts

### Exact Collection Identity

- Source and target are exact collection records: `{scope}` or `{scope, sub_scope}`. Checked source documents add `doc_ids` to that frozen source identity.
- No route text, report host, displayed document, active parent, filename, or selected row is a fallback target.
- A source and target may share the same parent scope when their exact collections differ. Copy to the same exact collection is rejected.
- Only configured one-level sub-scopes participate. SSP-4 does not introduce nested collections or arbitrary source directories.
- Collection eligibility is server-owned and based on the exact source root, target root, provider capabilities, and selected operation. An eligible managed child of a public scope can accept non-viewable canonical source without making every public parent scope a transfer target.
- Copy planning, actions, and apply contain no scope/sub-scope name branches. Configuration and projected capabilities determine eligible exact collections; the Projects-to-Analysis path is one normal use of the generic workflow.

### Flat And Hierarchical Sources

- Existing parent-scope-to-parent-scope Copy retains its optional descendant closure, included hierarchy, and target-root placement.
- Sub-scope sources are flat. Their Copy surface has no descendant option and every selected document becomes an independent target root.
- A sub-scope target is also flat. The planner rejects descendant inclusion or a source selection containing an internal parent/child relationship; it never silently flattens a hierarchy.
- Copy remains based only on the exact checked set after those declared expansion rules. It never falls back to the active document.

### Identity, Viewability, And Publication

- Every copied document receives a fresh immutable `doc_id`, matching filename, copy-time `added_date`, and copy-time `last_updated`.
- Source identity, source bytes, and source media are unchanged.
- Source `viewable` is not carried across. The copy uses the target collection's existing default derived from its owning scope. A copy into an Analysis editorial sub-scope is therefore non-viewable until explicitly changed.
- SSP-4 does not add a new publishing action or publish automatically. Public sub-scope output remains owned by the parent scope's existing Publish preview, confirmation, gate, and apply workflow.

### Target-Supported Custom Metadata

- Generic document front matter continues to follow the shared Copy transformation. Customisation-owned front matter follows registered transfer support, not a field-name exception or an interpretation of the field's meaning.
- A registered sub-scope customisation definition must explicitly declare the canonical front-matter fields it owns and a stable transfer-compatibility contract. SSP-4.1 implements the smallest transfer declaration on SSC-1's accepted aspect seam and reviews it at that step's checkpoint.
- A source-owned custom field is copied only when the target collection advertises the same registered transfer contract and accepts the value under its current settings.
- When the target does not support that contract, the field is omitted. The preview, apply receipt, and result report the exact document, field, source customisation, and omission reason.
- When the target advertises the contract but rejects the current value, preview is blocked. Apply never silently drops a value that the target claims to support.
- `folder_path` is owned by the `dotlineform_projects` customisation. It is omitted when the target does not support that contract; it is not hard-coded as a universally disposable field.
- `work_id` and `series_id` are shared optional document metadata owned by the common source transformation, not a collection customisation. Copy retains their source values without using them as eligibility, destination, or blocker inputs; SSP-1 and SSP-5 own normalized authoring and reverse-association behavior.
- SSP-4 does not infer compatibility from matching field names and does not translate between customisation meanings.

### Links, Media, And Rebuild

- Links between documents in the copied set are remapped whether the source or target uses a normal `doc` URL or a report-host `subdoc` URL. Links outside the copied set remain unchanged and are reported under the existing retained dependency rules.
- Document roots belong to the exact source and target collections. Published media and registered build-media sources remain owned by their parent scopes and use the current provider-neutral collision and byte-verification rules.
- A parent target receives the existing scope rebuild and targeted search follow-through. A child target receives the existing sub-scope rebuild only; its documents remain excluded from the parent Index, Recent, and global search.
- A successful result returns exact target document URLs. Parent targets use `doc`; child targets use the configured report host plus `subdoc`.

### Preview, Receipt, And Apply

- Preview is write-free and returns a bounded plan only when no blocker exists.
- The receipt records exact source and target collections, document and media digests, copied identities, retained and omitted custom metadata, link decisions, configuration revisions, and the intended rebuild owner.
- The owned browser and server move together to one current receipt schema. No alias or old-client compatibility bridge is introduced.
- Apply requires explicit confirmation, restores the receipt, and revalidates every bounded fact before writing. Documents remain create-only and are never overwritten.
- Media completion still precedes canonical document writes. Post-write failures return exact observed evidence and do not claim success or retry the mutation implicitly.

## Likely Authority To Inspect

This is a routing map for delivery work, not a required entry audit or fixed file-change list.

| boundary | likely current owners | delivery pressure |

| Sub-scope Copy action | default Manage sub-scope contribution, selection registrar, and management composition callbacks | add one checked-selection action beside Prepare Package using the existing exact `{scope, sub_scope, doc_ids}` target |

| Copy transformation and apply | `docs_document_transfer_apply.py` and `docs_write_rebuild.py` | use collection roots, `doc`/`subdoc` rewriting, parent-owned media, and the correct coordinated rebuild |

## Delivery Discipline

SSP-4.0 is a short scope-and-spec sanity gate over exact collection identity, planning/receipt, apply, custom metadata, route surfaces, and rebuild ownership. It confirms broad owners, blast radius, deliverables, risks, and stop conditions without freezing exact files, fixtures, estimates, or implementation. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

## Delivery Steps

### SSP-4.0 — Confirm Scope And Delivery

- [ ] Confirm SSC-1's accepted customisation and transfer-aspect seam, then sanity-check exact parent/sub-scope Copy against the accepted SSP-1 transfer contract and current selection, capability, preview/receipt/apply, link/media, result-navigation, and parent/child rebuild models; resolve only contradictions that would change the result.
- [ ] Confirm the broad blast radius across exact collection targets, capability projection, flat/hierarchical planning, target-owned metadata/viewability, receipt revalidation, copy apply, route surfaces, and coordinated rebuilds.
- [ ] Confirm the deliverables: exact collection planning and apply, shared Work/Series metadata retention, explicit collection-specific metadata decisions, correct links/media/rebuilds, main and sub-scope actions, focused evidence, and concise durable owner updates.
- [ ] Stop for review if the result requires nested collections, a second transfer workflow, Move expansion, publication coupling, compatibility aliases, or another boundary excluded above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, SSP-1 dependency, broad owners, blast radius, deliverables, risks, collection/publication boundary, and stop condition. Stop before SSP-4.1 implementation approval.

### SSP-4.1 — Exact Collection Planner And Receipt

- [ ] Generalize Copy planning from top-level scopes to exact managed collections while keeping Move on its current parent-scope contract.
- [ ] Add child-source inventory, flat-child validation, exact target capability evaluation, target-root allocation, and parent-owned media plans.
- [ ] Extend customisation definitions with the reviewed ownership/transfer contract and project exact retained, omitted, rejected, and blocked fields while keeping shared `work_id`/`series_id` in the ordinary non-gating document transformation.
- [ ] Issue and restore one new stale-safe Copy receipt containing the complete collection and custom-metadata plan without writing.

**Checkpoint:** focused planner and receipt evidence passes for the specified collection and metadata matrix. An independent code/diff review confirms that apply, UI, Move, publication, and current parent-copy behavior retain their existing owners and values. Stop for approval before SSP-4.2.

### SSP-4.2 — Collection-Aware Copy Apply

- [ ] Transform documents using target-default viewability, reviewed custom metadata decisions, and exact parent/child link remapping.
- [ ] Transfer and verify parent-scope-owned media and registered build sources under the existing create/reuse/collision rules.
- [ ] Create documents only in the exact target collection and invoke the correct coordinated parent or sub-scope rebuild.
- [ ] Return exact target URLs and activity/failure evidence, then revalidate the complete receipt against stale source, target, config, metadata, media, and build-source changes.

**Checkpoint:** direct service/apply evidence proves byte-preserving source behavior, fresh target identities, correct omission and blocker behavior, `doc`/`subdoc` links, target-only rebuild, and contained partial failure. An independent code/diff review confirms writes remain create-only, receipt-bound, and exact-collection-owned while UI, Move, and publication retain their existing owners. Stop for approval before SSP-4.3.

### SSP-4.3 — Main And Sub-Scope Copy Surfaces

- [ ] Rename the existing Manage action to **Copy to…** and retain its exact checked main-Index selection contract.
- [ ] Add the same action to the default sub-scope selection Actions menu using the registered exact selection target and independent selection owner.
- [ ] List writable parent and child collections with unambiguous labels, preserve server-owned capability truth, and prevent the current exact collection from being chosen.
- [ ] Adapt the existing preview and confirmation workflow to collection placement, custom-metadata omissions, blockers, flat-child constraints, and exact result navigation.

**Checkpoint:** focused module/route evidence passes and manual acceptance copies checked Work-subject, Series-subject, folder-subject, and no-subject documents from `dotlineform/projects` into `analysis/works`. Each new non-viewable `subdoc` keeps shared Work/Series metadata when present, visibly omits unsupported `folder_path`, preserves no-subject state, and leaves its working source unchanged. An independent code/diff review confirms exact selection ownership, server-owned collection eligibility, subject-independent Copy, the existing action workflow, and current publication authority. Stop for approval before SSP-4.4.

### SSP-4.4 — Regression, Publication Acceptance, And Closeout

- [ ] Re-run current parent-scope Copy planner/apply and main-Index action evidence to prove no regression.
- [ ] Verify all four source/target collection shapes, same-parent child copy, unsupported/supported custom metadata, mixed links, media, target defaults, stale receipts, provider failures, and parent/child generated follow-through.
- [ ] Manually clean one copied Analysis document, make it viewable, run the existing parent Analysis Publish preview/apply, and confirm only existing public-projection rules were used.
- [ ] Run focused service, API, module, lint, whitespace, generated-projection, and public-isolation checks, then perform the mandatory end-of-delivery diff and omission review.
- [ ] Update the durable document-transfer endpoint and sub-scope architecture owners with shipped behavior, then prepare the Roadmap closeout list.

## Not In Scope

- Move from or into a sub-scope, or any change to Move's current hierarchy and source-removal guarantees;
- nested sub-scopes, arbitrary directories, cross-application documents, or a second transfer workflow;
- overwrite, merge, synchronization, provenance coupling, return import, or automatic source cleanup;
- semantic translation between different customisations or compatibility based only on identical field names;
- automatic editorial decisions, content redaction, folder-note assessment, viewability promotion, or publication;
- automatic Work-to-Series roll-up, Series-to-Work fan-out, or post-copy synchronization of subjects;
- relaxing all public top-level scopes into writable Copy targets;
- new media identity, provider, collision, build, publication, or rollback semantics;
- batch jobs, progress persistence, resumable queues, or multi-user locking; or
- compatibility aliases for the replaced scope-only Copy receipt.

## Completion Evidence

- The current parent-scope Copy workflow still produces the same independent copies, hierarchy, media, target rebuild, and exact result behavior.
- Parent and child sources can copy checked flat documents into eligible parent or child targets, including a different child of the same parent scope.
- The source and target are explicit in every browser request, server plan, receipt, apply check, result, and activity record.
- A Projects-to-Analysis child copy receives a fresh identity, is non-viewable, retains shared `work_id`/`series_id` when present, opens through `subdoc`, and does not alter or remain synchronized with the working document.
- A folder-subject copy into a collection without the Projects contract omits `folder_path` visibly rather than translating it into a catalogue subject, while a no-subject copy remains fully valid.
- A fixture customisation supported by both ends retains and validates its declared front matter; unsupported fields are visibly omitted and supported invalid values block before mutation.
- Child-target rebuilds do not add their documents to the parent Index, Recent, or global search, while the existing parent Publish workflow can later publish reviewed viewable child documents.
- Move, public runtime dependencies, publication policy, and unrelated selection owners remain unchanged.
