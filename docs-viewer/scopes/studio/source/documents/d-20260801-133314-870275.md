# Projects Concept

## Problem

`$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` is the human working world behind
the catalogue. Its roughly 200 project folders are relatively stable, but they
can be renamed, moved, split, or consolidated as the work evolves.

That directory is the feature's main discovery and seeding area, not its
absolute validity boundary. A Project note or ordinary document link may
legitimately refer to any folder below `$DOTLINEFORM_PROJECTS_BASE_DIR/`. The
broader base directory is therefore the containment boundary for normalization,
saved `folder_path` values, existence checks, and local activation. Treating a
folder as a valid target does not make it an automatic Project seed candidate.

Studio Works retain the folder and filename used when media was selected or
uploaded. That is valuable historical evidence, not a live pointer that should
be rewritten to follow later filesystem changes. At the same time, notes about
a project need to exist before, during, or after the corresponding folder.

The feature therefore makes disagreement visible instead of trying to keep the
three systems synchronized.

The similarly named fields are deliberately different. Docs Viewer owns
Project-document `folder_path`; Studio Works retain their existing
`project_folder` source snapshot. Local links and Project metadata never add,
read, or write a Studio field. Project State is the narrow exception at the
feature level: it reads the existing Work evidence through a Studio-read-only
post-commit observer and writes its derived Docs Viewer snapshot without
changing the committed Work.

## Mental Model

| world | character | ownership |
| --- | --- | --- |
| Studio | database: structured, managed, stable | canonical Works, Series, publishing workflow, and recorded source-path history |
| Docs Viewer | semi-structured notes and metadata that may drift | Project documents, their membership, and their optional convenience links |
| folders | human working world: fluid and potentially chaotic | no canonical identity or lifecycle contract |

Studio does not track live folders. Docs Viewer does not become a canonical
folder registry. Folders do not control the lifecycle of Works or documents.

## Project Documents

The `dotlineform/projects` sub-scope is a notes collection whose documents
represent current, historical, or prospective folders. A Project document may:

- be seeded from a folder that exists now;
- be created before its intended folder exists;
- remain after a folder has moved, been renamed, or disappeared;
- coexist with another document that declares the same folder; or
- have no folder link at all.

The document can store one base-relative `folder_path` as a navigation
convenience. For example, `projects/3 symbols` is the entire stored value;
`$DOTLINEFORM_PROJECTS_BASE_DIR` is configuration known only to the local
runtime.

The field is not the document's identity, proof that a folder exists, an upload
destination, or permission to create, move, repair, or delete anything.
Relative stability is an authoring convention because unstable links would be
confusing; it is not enforced canonicality.

Body links and metadata have different meanings. A path pasted into prose is
an ordinary clickable link. Its source uses the explicit `dlf-local:` marker
so the renderer can distinguish it from an ordinary relative web link. A path
saved through **Folder Link** metadata is normalized into `folder_path` front
matter and becomes structured local
management data available to the Projects report customisation and Project
State. A body link is never silently promoted into metadata.

## Three-Way Reconciliation

Project State compares three independent kinds of evidence:

1. folder paths found in configured Project discovery areas, initially
   `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`, plus existence state for exact
   declared targets anywhere below the base directory;
2. Project documents and their optional `folder_path` values; and
3. folder paths historically recorded by canonical Studio Works.

Useful states include:

- a current folder with no Project document or Work history;
- a Project document whose folder exists, is missing, malformed, duplicated,
  or not yet created;
- a Work path matching a current folder, a Project document, both, or neither;
- complete three-way agreement;
- incomplete Work folder data; and
- evidence of a move, rename, split, or consolidation that needs a human
  decision.

The report is a review surface. It does not decide that a mismatch is an error
or turn a finding into an automatic repair.

## Resolver Tokens

A Resolver Token is an explicit reference that expands at document-build time
into the things directly connected to its subject. The first Project forms are:

```text
folder -> Works[] + Project documents[]
Work   -> folders[] + Project documents[]
```

This is useful at the top of a Project note and in any other managed document
that needs the same current relationship view. Expansion is one hop only. It
does not continue from a Work to Series or tags, and it never scans canonical
registries while building an individual document.

Resolver Tokens are adjacent to, but distinct from, Semantic Tokens. A
Semantic Token resolves one registered identity to one link. A Resolver Token
expands one explicit query subject into a current, ordered related-items list.

## Experience

The [Local File And Folder Links Concept](/docs/?scope=studio&doc=d-20260801-150013-f26b87)
owns the shared paste, `dlf-local:`, activation, and public-projection
experience. Projects consumes only its normalized base-relative target, such
as `projects/3 symbols`. A prospective contained `folder_path` can be saved
when the target does not exist.

## Invariants

- Folder changes never automatically rewrite Work records or Project documents.
- Work, folder, document, and Series lifecycle never cascades into another
  owner.
- A missing path is evidence, not proof that a Work or document is invalid.
- Project-document membership comes from documents, never from folder scans or
  `folder_path` validity.
- Studio upload and publishing workflows never read `folder_path`.
- `folder_path` never enters Studio Works, Studio UI, or Studio mutation
  payloads.
- The Project State post-commit observer is read-only with respect to Studio.
  It responds to an existing Work change by writing derived Docs Viewer state;
  it never mutates the Work or makes its commit depend on that refresh.
- Project State and Resolver Token output are derived, read-only presentation.
- Resolver expansion is bounded to one declared lookup row and performs no
  live scan or recursive chaining.
- Local paths and Finder actions remain Manage-only.

## Non-Goals

- a canonical JSON registry of folders;
- automatic synchronization or repair;
- inferred folder identity from titles, Series names, or selected UI context;
- recursive relationship traversal such as `folder -> Work -> tags`;
- public activation of local folder targets; or
- content-wide public path redaction inside this Projects delivery; or
- retention of the old Project State primary-image audit without a separately
  justified feature.
