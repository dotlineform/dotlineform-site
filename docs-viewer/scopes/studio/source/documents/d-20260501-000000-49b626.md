# Browser Smoke Testing

## When A Smoke Is Appropriate

Use a permanent browser smoke only when the durable risk exists in the browser integration boundary:

- route shell/config/template/controller boot;
- browser module loading and public/private asset separation;
- local service reachability and request/response agreement;
- shared ready/busy state;
- public read-only versus management capability separation.

Use pure/service/API tests for deterministic data behavior. Use manual or temporary browser checks for copy, layout, hover/focus, modal timing, and pointer feel. Mobile ergonomics is acceptance only for public `site/` routes under their owning public feature.

Do not add a smoke as routine follow-through from a UI change. Its review must identify the single browser-only boundary at risk, the regression it catches, and why lower-level or manual evidence is inadequate.

## Ownership

| Owner | Location | Profile |
| --- | --- | --- |
| Docs Viewer | `docs-viewer/tests/smoke/` | `docs-viewer-smoke` |
| Studio/public catalogue | `studio/tests/smoke/` | `studio-smoke` |

Keep niche/expensive/recent-fix scripts focused rather than adding everything to a profile. A retained smoke should have a clear trigger for when to run it.

The retained Docs Viewer profile contains exactly four browser boundaries:

- standalone Manage route boot and configured service projection;
- Docs Review route and API authority;
- public Analysis read-only isolation and compact payload reads;
- external-local scope build addressability and lazy Mermaid rendering.

Adding another boundary requires an explicit test-policy decision. Do not collect these scripts through the broad `docs` pytest profile.

The retained Studio profile contains exactly three browser boundaries:

- local Catalogue route boot and same-origin service isolation;
- local Tag route boot and same-origin service isolation;
- one representative checked public Catalogue Work route without local Studio capability.

Catalogue and Tag mutations, rendering helpers, projections, and configuration remain deterministic Python or source contracts. Adding another Studio browser boundary requires an explicit test-policy decision.

## Size And Structure

Each executable smoke owns one route or integration boundary. Shared startup/readiness code lives in a small non-executable support module; executable smokes are not fixture libraries.

A browser script over 500 lines, or one that spans more than one route/workflow owner, requires deletion or split review before it can be extended. Test-file size is not evidence of assurance.

## Correct Runtime Target

- local app route: owning local server/API;
- public site or public Docs Viewer: checked-in `site/` served over HTTP;
- module-contract smoke: explicit source-module fixture root;
- route-specific fixture: only when the script owns its setup.

Do not use `file://`, repo root, or a stale `_site` as public evidence. A pass proves only the target/profile actually run.

Run local route smokes at a representative laptop/desktop viewport. Do not add phone-width or touch-specific passes for local routes. A public mobile check must use the checked public artifact and belongs to the public route's feature and test owner.

## Readiness

1. Navigate and wait for DOM content.
2. For participating routes, call `tests/smoke/route_ready_helpers.py::wait_for_route_ready` with the app root and ready/busy attributes.
3. Assert only the route-specific mode, service, asset, or request condition named by the smoke.

Do not add arbitrary sleeps or additional UI choreography after semantic readiness unless the interaction itself is the approved browser-only boundary.

## Public Docs Viewer Contract

The public Analysis smoke should prove public payload reads and absence of management assets/services. It should use the configured public tree/recent/by-id/search contracts rather than local management indexes.

## Ready-State Audit

Template-level ready/busy structure is cheaper to prove with:

```bash
$HOME/miniconda3/bin/python3 tests/audits/route_ready_state.py --strict
```

The audit does not replace a smoke when runtime controller behavior is the risk.

## Manual Pairing

When the result also depends on visual fit or tactile behavior, state the manual follow-up separately. Automated evidence should not claim to prove what it did not inspect.

## Limits

- Browser fixtures can duplicate runtime config/data and drift from production owners.
- Profile names do not imply exhaustive app coverage.
- Local ports/process cleanup can create false failures unrelated to the product contract.
