# Docs Viewer External Scope Availability

## Purpose

Make external-local availability an exact scope capability rather than an all-registry startup dependency. With a valid configured projects base and Docs workspace, one missing or unreadable external scope must be reported as unavailable without terminating Docs Viewer, disabling unrelated scopes, or creating a partial replacement directory.

This feature addresses a current integrated-runtime gap exposed during the iPad local-authoring assessment but is not iPad-specific. iCloud Drive remains local filesystem storage after synchronization; paused network sync is not an application outage when the configured local files remain readable.

## Delivery

[ESA-1 — Graceful Per-Scope Availability Delivery](/docs/?scope=studio&doc=d-20260808-222436-4f7c81) owns the service, live-watcher, capabilities, browser reporting, targeted-resolution, non-materialization, verification, and durable-contract transfer needed for the complete outcome.

No implementation has started. The delivery is proposed and requires its sanity gate before implementation approval.

## Feature Contract

- Configured scope identity can be read without resolving every provider path.
- With a valid `DOTLINEFORM_PROJECTS_BASE_DIR` and external Docs workspace, each exact external scope reports its own source and generated-data availability.
- Docs Viewer health, shell, repository scopes, and other available external scopes remain usable while one scope is unavailable.
- Operations targeting the unavailable scope fail explicitly and cannot infer, fall back to, create, or mutate another target.
- Service or watcher startup does not create a missing external scope through media-directory materialization.
- A selected external operation and an intentional all-scope command still report non-success when required scope coverage is unavailable.
- A missing or unmounted projects base remains a separate whole-environment configuration condition.

## Ownership And Relationship

[Local Authoring Service And Publication Boundaries](/docs/?scope=studio&doc=d-20260808-215338-6b1e8c) owns the durable cross-system decision and availability terminology. [Core Definition Baseline v1](/docs/?scope=studio&doc=d-20260724-213457-6e1cf7) already requires unrelated providers not to be resolved merely because another operation starts. This feature delivers that independently useful behavior in the current integrated runtime without starting the broader [Docs Viewer Core Refactor](/docs/?scope=studio&doc=d-20260718-114645-7b9d24) or bypassing its Transition Architecture gate.

The feature does not change external scope lifecycle, storage ownership, publication, iCloud synchronization, standalone packaging, or the canonical configuration registry. It does not add a second scope registry, compatibility loader, generic provider framework, persistent availability database, background synchronization, or automatic target substitution.

## Success Meaning

Passing ESA-1 means an exact unavailable external scope is visible and contained while every unrelated available Docs Viewer capability retains its ordinary behavior. It does not mean the unavailable scope can be read or mutated, that an absent projects base is supported, that every all-scope command succeeds with incomplete coverage, or that File Provider synchronization failures are repaired by Docs Viewer.
