# iPad Docs Viewer Installation And Proof

## Status

This is the proposed first-install and proof procedure. It has been reconciled with the current repository and app documentation but has not yet passed on the target iPad. Record exact deviations and evidence from the real device; do not silently rewrite a failed step into a claimed success.

The gate uses a fresh shallow clone and disposable proof content. Do not run it against the only copy of uncommitted work or while the same external proof files are being edited on another device.

## 1. Install The Apps

Install [iSH](https://ish.app/). Safari and Files are built into iPadOS. Working Copy is optional after the core proof, and a Files-aware editor such as Textastic is optional because Docs Viewer already contains its own Source editor.

In Files, locate the exact iCloud Drive folder that corresponds to the Mac's `DOTLINEFORM_PROJECTS_BASE_DIR`. Confirm that it contains the expected `docs-viewer`, `data-sharing`, and `projects` children, then choose **Keep Downloaded** for the required tree and allow downloads to complete.

## 2. Confirm A Supported iSH Filesystem

In iSH, record the runtime baseline:

```sh
uname -a
cat /etc/alpine-release
cat /etc/apk/repositories
```

The target is a currently supported Alpine x86 release with working `main` and `community` repositories and Python 3.12. Alpine 3.23 is the initial known candidate. If `apk update` reports end-of-life or missing repositories, install or upgrade to a current iSH Alpine filesystem through the supported iSH filesystem workflow before continuing; do not blindly redirect an old filesystem to a newer package branch.

## 3. Mount The External Projects Base

Create a stable mount point and invoke the iOS folder picker:

```sh
mkdir -p /mnt/dlf-projects
mount -t ios . /mnt/dlf-projects
```

Select the exact iCloud parent identified in Files. The source argument is intentionally `.`; iSH ignores it and uses the folder selected in the picker.

Verify the selected boundary without changing it:

```sh
test -d /mnt/dlf-projects/docs-viewer
test -d /mnt/dlf-projects/data-sharing
test -d /mnt/dlf-projects/projects
find /mnt/dlf-projects -maxdepth 1 -type d -print
```

Stop if one of the required children is absent, if files still show download placeholders, or if the mount resolves to a child inside the projects base. Remounting uses the same command after `umount /mnt/dlf-projects` when necessary.

## 4. Install The Runtime Dependencies

Install the shell, Git, Python, environment tooling, and Alpine builds of the native Python packages:

```sh
apk update
apk add bash git ca-certificates python3 py3-pip py3-virtualenv py3-lxml py3-beautifulsoup4 py3-markdown-it-py py3-pillow
```

Create a virtual environment that can use those system packages, then install the remaining checked runtime dependencies:

```sh
mkdir -p /root/venvs
virtualenv --system-site-packages /root/venvs/dotlineform
. /root/venvs/dotlineform/bin/activate
python3 -m pip install mammoth==1.12.0 bleach==6.3.0 openpyxl==3.1.5
python3 -m pip check
```

Confirm that the imports needed by the initial working slice load:

```sh
python3 -c "import bleach, bs4, lxml, mammoth, markdown_it, openpyxl, PIL; print('Docs Viewer Python imports: ok')"
```

Do not begin with `pip install -r requirements.txt`. The checked file pins desktop versions of native packages for the primary development environment, while iSH needs Alpine's x86 builds for lxml and Pillow. The proof receipt must record the actual Alpine and Python package versions. A later delivery may add an explicitly tested iPad dependency contract if the divergence proves stable and useful.

## 5. Clone Into iSH Storage

Keep the repository, `.git`, virtual environment, and caches in iSH's Linux filesystem rather than iCloud Drive:

```sh
mkdir -p /root/src
cd /root/src
git clone --depth 1 https://github.com/dotlineform/dotlineform-site.git
cd dotlineform-site
git status --short
```

The first output from `git status --short` should be empty. Create a disposable proof branch before any managed write:

```sh
git switch -c ipad-proof
```

A full-history clone can replace the shallow clone after the workflow is proven. Working Copy may be evaluated later as a GUI for the same checkout only if that sharing arrangement preserves service performance and Git/filesystem correctness; do not maintain two writable clones and assume they are one working tree.

## 6. Create The Device-Local Environment

Create `/root/src/dotlineform-site/.env.local` with these minimal non-secret values:

```sh
DOTLINEFORM_PROJECTS_BASE_DIR=/mnt/dlf-projects
DOCS_VIEWER_MANAGEMENT_ENABLED=1
DOCS_VIEWER_REVIEW_ENABLED=1
```

`.env.local` is already ignored and is loaded by the current repository runtime. Do not add credentials to it for the initial proof. Do not create `env.ipad`: the current service does not load that filename, and this guide should not imply a configuration contract that does not exist.

Confirm the active path without printing unrelated environment values:

```sh
test -f .env.local
test -d /mnt/dlf-projects/docs-viewer
git status --short
```

The Git status should remain empty because `.env.local` is ignored.

## 7. Start Docs Viewer

Activate the environment from the repository root and start the service in the foreground:

```sh
. /root/venvs/dotlineform/bin/activate
cd /root/src/dotlineform-site
python3 docs-viewer/services/docs_viewer_service.py
```

Expected startup output includes the manage URL and enabled management, review, and generated-read capabilities. In Safari, open:

```text
http://127.0.0.1:8776/health
http://127.0.0.1:8776/docs/
```

The health response must report `ok: true`. Keep iSH active in a foreground or multitasking window while using Safari. If the server stops responding after iSH is backgrounded or the device is locked, return to iSH and restart it; record this lifecycle behavior in the receipt.

## 8. Optional Static Public Preview

After the manage gate passes, a second iSH window may serve the already tracked public site:

```sh
. /root/venvs/dotlineform/bin/activate
cd /root/src/dotlineform-site
python3 site-tools/site_preview.py --host 127.0.0.1 --port 4000 --directory site
```

Open `http://127.0.0.1:4000/` in Safari. This proves only the tracked static preview. It does not run Jekyll, produce server-side Mermaid SVG, or authorize remote publication.

## Proof Gate

Use a unique proof marker such as `IPAD-PROOF-YYYYMMDD-HHMM` in all disposable content so its source, payload, search entry, and synchronized copy can be identified exactly.

### A. Runtime And Startup

- [ ] Record iPad model, iPadOS version, iSH version/build, Alpine version, `uname -m`, Python version, installed dependency versions, Git commit, and whether the clone is shallow.
- [ ] Start the service without an import, bind, configuration, media-directory, or port error.
- [ ] Confirm `/health` reports management, generated reads, and review enabled.
- [ ] Load `/docs/` in Safari, refresh once, and confirm there are no blocking browser errors.

### B. Read And Search

- [ ] Open one repository-backed Studio document and one Processing document.
- [ ] Open one configured external scope and, where applicable, one external sub-scope from the iCloud mount.
- [ ] Search for a known unique term in a repository-backed document and a different term in an external document; open the exact results.
- [ ] Confirm recent activity, index hierarchy, document body, metadata, and ordinary local media load for the chosen records.

### C. Repository-Backed Managed Write

- [ ] On the disposable proof branch, create one clearly named Studio proof document through Manage, save the unique marker, and confirm the post-save document and search rebuilds succeed.
- [ ] Reload the document and find the marker through search.
- [ ] Use `git status --short` and `git diff --check` in iSH to confirm that only the expected source and generated products changed and that no `.env.local`, temporary, cache, or iCloud file entered Git.
- [ ] Delete the disposable document through its supported UI only after its evidence is captured; record any remaining generated diff rather than forcing the tree clean.

### D. iCloud-Backed Managed Write And Synchronization

- [ ] Create one clearly named document in a disposable or explicitly safe external collection, save the unique marker, and confirm its document and search rebuilds succeed.
- [ ] Stop and restart the service, then reopen the external document and its search result.
- [ ] In Files, confirm the exact source and generated products exist below the selected iCloud tree without conflict copies, leaked temporary files, or partial siblings.
- [ ] On the Mac, wait for iCloud synchronization and confirm the same marker and expected generated record arrive at the exact external scope path.
- [ ] Delete the proof document through Manage, allow synchronization to complete, and confirm the source, generated record, and search entry are removed on both devices without resurrection.

### E. Import, Review, And Media

- [ ] Import one disposable Markdown file and one HTML file; confirm their rendered bodies and saved sources.
- [ ] Import one small DOCX containing text and one ordinary embedded image; confirm Mammoth conversion, saved source, and the expected image result.
- [ ] Run one disposable document-package or Docs Review round trip using the mounted `data-sharing` workspace and confirm that exact package identity and routing are preserved.
- [ ] Exercise one JPEG or PNG package-media path and confirm Pillow can read and write the required output.
- [ ] Open a document containing inline Mermaid and confirm Manage renders it in Safari without invoking the server-side `mmdc` pipeline.

### F. Platform Boundary And Session Recovery

- [ ] Confirm local-folder target authoring or validation remains bounded, and record that Finder-style activation or reveal is unavailable rather than treating the button as working.
- [ ] Background iSH briefly, use Safari in multitasking, lock and unlock the device once, and record when the loopback service is suspended.
- [ ] After any suspension, restart the service and confirm the repository-backed and external proof documents remain consistent.
- [ ] Record static-site preview separately if tested; do not record Jekyll, server-side Mermaid production, HEIF/video tooling, full desktop checks, R2 publication, or Working Copy integration as passed unless each receives its own explicit evidence.

## Pass Rule

The feature passes its initial feasibility gate only when all required A-E checks succeed and F shows restartable session behavior without data loss. The repository-backed and external managed-write checks are both mandatory. A route that merely loads, an iCloud directory that can only be read, or a save that cannot be confirmed after restart and Mac synchronization is not a pass.

Known exclusions in the concept do not fail the gate when they remain contained and accurately presented. Unexpected source loss, conflict copies, partial or resurrected generated files, inability to run child rebuilds, unreliable loopback access while iSH is active, or inability to install/load required native Python packages blocks the working-slice claim.
