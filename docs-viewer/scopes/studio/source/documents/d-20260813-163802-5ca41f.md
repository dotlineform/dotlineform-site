# Docs Viewer Search Tokenizer Concept

This Roadmap concept is retained as the proposal and reasoning record used by DSI-1 and SM-1. The shipped current-state term contract now belongs to the durable [Docs Viewer Search Tokenizer](/docs/?scope=studio&doc=d-20260813-214351-98d3f0).

## Purpose

A search term is a normalized prose word or authored technical identifier that remains useful as a retrieval key after predictable noise has been removed. Full-text retrieval does not require indexing every string separated by spaces.

The tokenizer is a shared Docs Viewer contract: every scope's index generation and browser queries must pass text through the same normalization rules. This lets a query such as `subscope` find a document containing `docs_subscope`, while the complete `docs_subscope` query remains more precise.

## Proposed Contract

For each eligible title, parent title, heading, body-prose, inline-code, or fenced-code value, the tokenizer should:

1. normalize Unicode and case so equivalent authored forms produce the same term;
2. recognize compound technical identifiers before discarding punctuation;
3. retain the normalized complete identifier and add useful components split on underscore, hyphen, dot, and camel-case boundaries;
4. retain mixed alphabetic and numeric identifiers such as `r2`, `h1`, and `sm-1.0`;
5. omit numeric-only tokens, one-character tokens, known document IDs, URLs, paths, markup artifacts, and file-extension-only components from ordinary term derivation;
6. omit a small, fixed, versioned stop-word list rather than deriving stop words from the current corpus; and
7. deduplicate the resulting terms within each document field before adding its document position to the inverted index.

Each scope's field policy owns which source values reach the tokenizer. Exact structural identifiers or metadata retained by an existing scope are explicit policy fields rather than ordinary derived terms. Studio body extraction remains owned by [Studio Full-Text Search Index](/docs/?scope=studio&doc=d-20260813-161942-b1e9e1); the tokenizer receives its eligible authored text after front matter, generated markup, report declarations, link destinations, media paths, scripts, and styles have been excluded.

### Exact tokenizer edges

- Unicode-aware lowercase normalization.
- Preserve and split technical compounds.
- Prefix matching from three characters.
- A query reduced entirely to stop words returns no results.

## Stop words

The initial stop-word candidate should remain deliberately small: `a`, `an`, `and`, `are`, `as`, `at`, `be`, `by`, `for`, `from`, `in`, `is`, `it`, `of`, `on`, `or`, `that`, `the`, `to`, and `with`. DSI-1.0 should confirm the shared list against representative scope metadata, and SM-1.0 should confirm it against representative Studio body and code queries.

These are deliberately selected grammatical glue words, rather than a standard NLP list containing hundreds of common words.

A word should be excluded only when:

- Searching for it alone would provide no useful result.
- Removing it from a longer query would not materially change the query’s intent.
- It has no important meaning in the relevant Docs Viewer corpus.

Candidates like `before`, `after`, and `while` are interesting because generic search systems often treat them as stop words, but in technical documentation they may be meaningful:

- `before publish`
- `after import`
- `while saving`

Removing them would reduce those queries to `publish`, `import`, and `saving`, losing the lifecycle distinction. Their posting lists cost little, especially after compression, so I would initially **retain all three**.

The initial stop list in the doc contains 20 words:

```text
a, an, and, are, as, at, be, by, for, from,
in, is, it, of, on, or, that, the, to, with
```

Even that should be treated conservatively. I’d call it a **minimal function-word list**, and test every proposed addition against the question: “Could this word distinguish two useful technical searches?” If yes, retain it.

## Deliberate Limits

The first tokenizer should not add stemming, synonyms, spelling correction, or language detection. `report`, `reports`, and `reporting` therefore remain distinct terms, although query-side prefix matching can still let `report` retrieve the longer forms.

It should not remove terms merely because they occur in many documents. Corpus-frequency pruning would make the contract change as documents are added and could silently remove common but meaningful technical vocabulary.
