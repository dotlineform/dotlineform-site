# SSP-8.0 — Superseded Independent-State Sanity Note

## Outcome

Subsequent product review superseded this independently nullable-state proposal. The current [SSP-8 — Revised Model](/docs/?scope=studio&doc=d-20260808-153226-a067d9) makes Working `doc_id` the lineage owner, removes lineage when Working is deleted, drops the orphan-lineage report and separate `lineage_id`, and depends on [DPD-1 — Immediate Public Projection Cleanup On Document Delete](/docs/?scope=studio&doc=d-20260808-165751-1f159a). This note remains review history and is not an implementation authority.

SSP-8 fits the current Docs Viewer owners as a bounded revision rather than a replacement workflow. The canonical table must change because `docs_document_publication_lineage_v1` requires both source and editorial identities, but the existing Copy, Delete, Publish, exact-location, report-host, and private-report mechanisms already provide the required mutation and presentation boundaries.

The accepted model is one lineage branch with independently optional **Working**, **Editorial**, and **Published** states. State presence in the lineage record is canonical. **Copy**, **Delete**, and **Publish** update only the state they own after their ordinary successful mutation; **Set Publishable…** remains an Editorial publication gate and does not mutate lineage. No action infers, scans, repairs, or removes another state.

SSP-8.0 changes no runtime code, canonical data, external `dotlineform` source, or report registration. It approves SSP-8.1 schema design and migration only after this review gate.

## Current Owner Fit

- **Canonical table:** `docs_document_publication_lineage.py` is already the single strict reader/writer for the private JSON, supplies deterministic atomic writes, and rejects another schema. SSP-8.1 can perform one clean schema cutover here without a dual reader, alias, loose registry, or new storage product.
- **Copy:** the existing exact collection contract enables lineage only for configured `dotlineform/projects` to `analysis/works` Copy. New and Replace already update lineage after the exact target write and targeted rebuild, then refresh the source collection. The revised shape changes the follow-through data, not the Copy action, selection, transformation, or response owner.
- **Delete:** Working and Editorial are both configured sub-scope documents and already use the same exact, revision-checked Delete apply followed by the owning sub-scope rebuild. SSP-8 adds state-specific lineage follow-through only after this existing success boundary. Deleting one Working identity removes that state from every branch that contains it; deleting one Editorial identity affects only its exact branch. Other states remain unchanged.
- **Publish:** the existing Analysis scope-wide Publish remains the only public mutation. Its current post-success reconciliation already updates the private table after public files and document locations succeed. SSP-8 adapts that step to add or clear Published state without reconstructing, removing, or checking Working or Editorial state.
- **Projects:** the current Projects manifest projector starts from current `dotlineform/projects` documents and joins matching lineage rows. That row grain is inherently partial once Working is deleted. It remains the correct owner for one highest-state summary beside each current Working document, but it cannot become the complete lineage inventory.
- **Availability:** the current exact document-location path can decorate a recorded identity with title, Manage link, or unavailable presentation. This remains read-only presentation. A missing file or generated target never causes a lineage write, inferred Delete, fallback identity, or cleanup.

## Accepted Mutation Rules

| Action | State changed | Retained examples |
| --- | --- | --- |
| New/Replace Copy | Editorial | Working and any existing Published state are unchanged. |
| Delete Working | Working | Editorial plus Published, Editorial only, or Published only may remain valid. |
| Delete Editorial | Editorial | Working plus Published, Working only, or Published only may remain valid. |
| Publish | Published | Working and Editorial are unchanged whether public output is added, retained, or removed. |
| Set Publishable… | none | Published remains until a later Publish; Editorial remains after that public removal. |

A lineage record is retired only when its final state is removed. Directly created `dotlineform/projects` or `analysis/works` documents remain outside lineage until the configured Copy action starts a branch. Manual filesystem deletion does not update the table; a recorded identity that can no longer be resolved is **Unavailable**, which is a diagnostic rather than a promotion stage or repair trigger.

The highest recorded promotion state is **Working → Editorial → Published**. Published wins while its public evidence survives even when Editorial has been removed through Delete. After the next Publish clears that public evidence, the highest remaining state is derived from the states still recorded.

## Complete Report Decision

The complete report belongs in the local `dotlineform` scope. This is the operator-facing workflow scope and already hosts local Project State, Uncataloged Files, Missing Source Files, and Projects reporting. Its scope has no public projection, while the existing report registry, local access gate, dynamic loader, report service, and ordinary human-authored report-host pattern can add one focused lineage report without a new reporting mechanism.

The report's canonical row source is the lineage JSON, not the Projects manifest or current filesystem inventory. Its accepted row grain is one current lineage branch. It must remain able to show a branch after Working, Editorial, or both have been removed through the workflow. It reads exact recorded identities, copy evidence, and nullable `{public_url}` evidence; it may ask the existing exact resolver for presentation and unavailable diagnostics, but that decoration never changes the row set or canonical state.

The report is Manage-only and read-only. Its registry entry defaults to local access, its host declares `viewer_report_access: local`, its live response travels through the local management service, and its ID, response, module, and assets stay absent from public report configuration and public Docs output.

SSP-8.4 retains the presentation design. It must decide the exact host document, report name, columns, links, highest-state treatment, unavailable warning, ordering, filters, empty state, refresh behavior, and narrow layout before SSP-8.5 implementation. SSP-8.0 freezes only the `dotlineform` home, lineage-branch row grain, minimum information, read-only behavior, and private boundary.

## Blast Radius And Risks

The bounded implementation crosses the canonical table/schema and focused fixtures; existing Copy, Delete, and Publish follow-through; Projects projection and highest-state browser presentation; a local report producer/route/service/registry/loader; one external-local report host; and focused generated/private/public-boundary checks. These are existing owners rather than a reason to introduce a generic lifecycle engine or reporting framework.

The principal schema risk is stable exact branch identity after one or two states have been removed, especially with zero-to-many New copies from one Working document. SSP-8.1 must settle that row shape and deterministic ordering without adding presence booleans, tombstones, inferred history, or duplicate Published identity. The known v1 review row is explicit migration input; its prior workflow Delete must be represented deliberately rather than inferred from current file availability.

The principal mutation risk is accidental cross-state cleanup. Focused tests must prove each action changes only its owned state, including Working Delete across its exact branches, Editorial Delete while Published, `publishable: false` before and after Publish, and Published-only retention. Lineage follow-through does not broaden the existing Delete recovery behavior or add a table-wide rollback/retry protocol.

The principal presentation risk is treating Projects as complete or treating Unavailable as a fourth promotion stage. Projects remains current-Working-grained; the complete report remains JSON-grained; highest state and availability remain distinct meanings.

## Gate

SSP-8.0 is superseded and supplies no further implementation approval. DPD-1.0 is the next review gate. The current SSP-8 document owns the later Working-owned replacement.
