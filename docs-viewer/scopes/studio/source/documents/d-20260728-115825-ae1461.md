# Sub-Scope Package Preparation Delivery

## Status And Order

In progress as SSI-3, after
[Sub-Scope Detail Delete Delivery](/docs/?scope=studio&doc=d-20260728-115825-e2561b).
SSI-3.0 freezes the selection, collection, package, provenance, and export-only
boundaries below. Runtime implementation has not started and remains at the
SSI-3.0 review gate.

SSI-3 is the broadest delivery. It follows SSI-2 so the manage controller,
capability projection, busy/error handling, collection refresh, public
isolation, and realistic header/list layout have already been proved by a
smaller exact-target workflow.

## Complete Outcome

Manage mode gives a `docs_subscope` list the same compact selection language as
the main Index:

- an Actions control enters selection mode;
- checkboxes appear as siblings to row navigation;
- Select all, Clear, and Done control the current collection selection; and
- the sub-scope Actions menu offers **Prepare package…** for one or more checked
  documents.

The package workflow reads exact sources from `{ scope, sub_scope }`, validates
checked IDs against that collection, and records the complete collection
identity in package provenance.

Every package prepared from a sub-scope is export-only in this delivery. It is
not actionable in Returned Packages, Docs Review, or Docs Import.

This completes outbound preparation of the seeded tag documents, not an
automated round trip.
[Sub-Scope Returned Package Review Delivery](/docs/?scope=studio&doc=d-20260728-173227-bb7426)
separately allows a complete returned package to stop at immutable Docs Review;
SSI-3 does not imply that enriched package records can be applied back to the
child sources.

## Change Classification

| kind | work |
| --- | --- |
| shipped and retained | compact Index Actions/selection interaction; pure selection transitions; Prepare Package modal; package profiles and engine |
| refactored | isolate collection-neutral selection transitions and package source-context mechanics while preserving current Index behavior |
| extended | add a separate sub-scope selection owner and optional `sub_scope` package request/source/provenance support |
| genuinely new | sub-scope checkboxes, list Actions/selection controls, and package preparation from checked child documents |

The same interaction system is reused; the Index and sub-scope collection keep
separate state owners and cannot supply targets to one another.

## Selection Contract

The sub-scope selection owner is keyed by `{ scope, sub_scope }`.

- Only checked IDs are action targets.
- Opening Actions enters selection mode but does not preselect the parent report
  or an unvalidated detail target.
- Checkbox clicks do not navigate.
- Shift-check extends from the collection's range anchor across currently
  visible eligible rows.
- Row navigation remains available while selection is active.
- Returning from detail to the same mounted collection may preserve selection.
- Inventory refresh prunes missing IDs and retains eligible checked IDs.
- Collection change, report unmount, leaving manage mode, or Done clears the
  owner according to the accepted lifecycle.
- Select all replaces checked IDs with the currently visible eligible rows
  supplied by the collection projection. Before SSI-4 filtering, every
  eligible collection row is visible, so this remains whole-collection
  selection.
- Clear empties checked IDs.
- Done exits and clears selection.
- The compact command group does not add a selected-count label.

The sub-scope action menu contains only capabilities deliberately adopted by
this feature. Copy, Move, bulk Delete, scope actions, and Review Package do not
appear merely because the main Index menu supports them.

## Package Contract

The existing Prepare Package workflow remains the modal and export owner. A
sub-scope request adds one normalized collection field:

```text
scope:     <parent scope>
sub_scope: <configured child>
doc_ids:   <effective checked IDs>
```

The browser and service must:

- list and validate documents from the configured child source root;
- treat the collection as flat and never infer parent-scope descendants;
- derive effective IDs after supported visibility/summary options;
- never add an ID excluded by the submitted checked selection;
- resolve selection and source records by `doc_id`, never title;
- render content through the existing package engine;
- include `scope`, `sub_scope`, selected/exported IDs, profile, and generated
  time in internal provenance and result payloads;
- project sub-scope runs as `supports_return_import: false`, even when the same
  profile supports return for a top-level scope;
- omit or replace return/import instructions in external context for that
  export-only projection; and
- exclude the resulting metadata/files from actionable returned-package
  listing and review.

Top-level scope package preparation remains unchanged when `sub_scope` is
absent.

## In Scope

- One sub-scope Actions control and menu containing Prepare Package only.
- Collection-local checkbox gutters and Select all/Clear/Done.
- Reuse or extraction of pure selection transitions without changing main
  Index behavior.
- A separate collection-keyed selection owner and lifecycle.
- Optional `sub_scope` support across the package browser client, config,
  documents, context, prepare request, source loader, engine handoff, result,
  activity, and metadata.
- Flat-collection effective-selection rules.
- Explicit export-only projection and returned-review exclusion.
- Non-viewable, missing-summary, stale-ID, empty-selection, cancel, success,
  failure, and retry evidence.
- Public/manage module isolation and narrow/dense UI review.

## Not In Scope

- Returned-package review, Docs Review materialization, or Docs Import from a
  sub-scope package.
- Copy, Move, bulk Delete, or any other selection action.
- Parent/descendant expansion inside a flat sub-scope.
- Selecting the parent report or documents from another collection.
- Package profile redesign, new external service adapters, or a new package
  engine.
- Tag Registry reads, group-based filtering, deduplication, or synchronization.
- General report filtering/search or main Index interaction redesign.

## Frozen SSI-3.0 Contract

### Selection Ownership

The current `docs-viewer-index-selection.js` combines two different concerns.
SSI-3.1 may extract only these collection-neutral immutable transitions:

- normalize and deduplicate IDs while retaining input order;
- enter, toggle, Shift-range, Select all, Clear, Done, and reconcile; and
- replace selection with caller-supplied visible eligible IDs.

The main Index retains its own scope/view lifecycle owner, DOM gutter and
projection helpers, active displayed-document preselection, and
`documentIndex` eligibility. Existing Index control IDs, action resolution,
range behavior, reload reconciliation, and package invocation remain unchanged.

The sub-scope contribution adds a separate owner keyed by normalized
`{ scope, sub_scope }`. It receives collection membership only from the shared
report's explicit documents and lifecycle events. It:

- enters empty when the collection Actions control opens;
- never preselects the parent report, displayed child, URL `subdoc`, focused
  row, or main Index selection;
- uses the report's ordered visible eligible IDs for range and Select all;
- preserves checked IDs while list/detail state changes within the same mounted
  collection;
- prunes missing IDs on an explicit report refresh; and
- exits and clears on Done, report unmount, collection-key change, or leaving
  manage mode.

`docs-viewer-action-definitions.js` and its `SELECTION` / `ALL` resolver are
already collection-neutral and remain the sole Prepare Package target
resolver. The main Index and sub-scope controllers supply their own checked IDs
to separate resolver contexts.

### Collection And Request Boundary

The normalized collection identity is:

```text
top-level: { scope }
child:     { scope, sub_scope }
```

An absent `sub_scope` preserves every current top-level request and response.
When present, `sub_scope` must be a non-blank configured one-level child of the
submitted parent `scope`. Unknown children, extra collection fields, path-like
IDs, and implicit fallback to the parent source reject.

The browser extends the existing endpoints rather than adding parallel package
routes:

```text
GET  /docs/packages/config?scope=<scope>&sub_scope=<sub_scope>
GET  /docs/packages/documents?scope=<scope>&sub_scope=<sub_scope>
POST /docs/packages/prepare
     { scope, sub_scope, profile_id, doc_ids, select_all: false,
       missing_summary_only, include_non_viewable, target_format,
       content_format, dry_run, activity_context }
```

For the child branch, `select_all: true` rejects. `doc_ids` must be the non-empty
effective checked selection calculated by the modal. The service revalidates
every ID against the exact configured child source; an ID found only in the
parent scope or another sub-scope is unknown.

The config response validates the requested child and projects every enabled
profile as `supports_return_import: false` for that request without modifying
the stored profile. The documents response repeats `scope` and `sub_scope`,
identifies a flat sub-scope selection model, and returns source-derived title,
summary, viewability, and content-length records required by the existing
modal. The compact report inventory is not a package source because it does
not contain that data.

### Flat Effective Selection

The package source loader reuses configured collection resolution, then loads
and validates Markdown directly under the child document root. It does not
load parent-scope documents or infer hierarchy from parent IDs.

- The descendants control is absent for a sub-scope package.
- Profile descendant defaults or tree requirements never add child IDs.
- Missing-summary and non-viewable choices may only subtract from submitted
  checked IDs.
- Profile limits may truncate that already confined sequence.
- The service orders resolved records by the child source projection and
  rejects any submitted stale or cross-collection ID.
- `selected = exported + failed + skipped` remains the auditable package
  accounting rule.

The `document-content` profile remains the intended tag-document enrichment
profile. `document-tree` may project the exact checked flat records as roots,
but it gains no descendant semantics.

### Result, Provenance, Activity, And Context

A successful or failed child prepare result repeats:

```text
scope
sub_scope
profile_id
supports_return_import: false
selected_doc_ids
exported_doc_ids
counts and issues
```

Internal metadata records mandatory `scope`, `sub_scope`, and
`supports_return_import: false` beside the existing export identity and checked
IDs. External context records the same collection identity and export-only
flag, and includes a non-editable notice that returned-package review/import is
unsupported. Existing editable profile context remains profile-owned; SSI-3
does not introduce per-sub-scope context persistence or mutate the stored
profile merely to create an export-only projection.

The management event and Studio Activity entry retain the parent `scope`,
`sub_scope`, profile, export ID, and effective document IDs. They do not label
the package as a top-level scope package or an importable result.

### Return And Public Boundary

The run-scoped export-only projection is service-enforced even when the stored
profile normally supports return import. A staged child package:

- cannot enter the actionable returned-package `files` collection;
- is reported as blocked with an export-only sub-scope reason;
- is rejected by direct Review Package and Docs Import entrypoints before
  source materialization or writes; and
- cannot become importable by removing `sub_scope` from a browser request,
  because trusted internal metadata remains authoritative.

Public routes retain the shared read-only report, load no selection/package
management module, and expose no package endpoints or controls.

### Test-Owned Fixture Matrix

| case | fixture expectation |
| --- | --- |
| ordinary flat collection | two checked synthetic child documents export exactly once in child source order |
| visible eligibility | Select all receives the report's explicit visible eligible IDs and replaces, rather than extends, the checked set |
| non-viewable | inclusion choice may retain or subtract the checked child but never add another record |
| missing summary | filter may subtract a checked child with a summary and keeps exact accounting |
| stale or missing ID | an ID absent from the exact child rejects without package output |
| cross-collection | parent-only and sibling-sub-scope-only IDs reject even when valid elsewhere |
| no descendants | parent-like front matter and the tree profile do not expand beyond checked child IDs |
| owner isolation | Index and two different sub-scope collection owners cannot exchange checked IDs or anchors |
| cancel/failure/retry | cancellation writes nothing; failure retains selection and a retry uses the same exact collection |
| returned package | trusted child metadata remains blocked and direct review/import writes nothing |
| public isolation | public report renders without importing management selection or package modules |

All write and route evidence uses temporary configured sources and an isolated
writable projects base. The real Analysis `tags` collection is a later manual
read/review surface; SSI-3 tests do not package or mutate its documents.
