# Docs Viewer Scope Type Migration Concept

## Purpose

Changing a Docs Viewer scope type should preserve one established body of work while changing its canonical workspace profile and whether its documents can be publicly projected. It must feel like one management action, but the service must treat it as a planned migration of scope-root storage, configuration, routing, publication capability, and generated products.

The operation preserves the exact `scope_id`, document and report-host identities, parent relationships, sub-scope identities, authored Docs links, and logical `docs/<scope>/...` media references. It does not create a replacement scope or reinterpret content.

## Supported Profiles

The current type choices bundle two distinct concerns:

| profile | canonical and local-published provider | exposure |
| --- | --- | --- |
| external (`local_external`) | `external_local` | local management only |
| local repository (`local_committed`) | `repository` | local management only |
| public (`public_readonly`) | `repository` | local management plus public route and projections |

External storage with public exposure is not a supported fourth profile. The management UI may present the three familiar types, but migration planning should distinguish two exact changes:

1. **Relocate storage** between `external_local` and `repository` while remaining local.
2. **Change public exposure** between local-repository and public while remaining repository-backed.

A later interaction may compose these stages, but their ownership and proof remain separate.

## Independent Media Policy

Per-media-type storage is not part of scope type. [Scope Media Storage Locations](/docs/?scope=studio&doc=d-20260808-231126-6a5d72) owns repository, external-local, and R2 destination policy plus verified provider migration.

Scope Type Migration preserves every explicit media destination. Media configured as scope-local follows `scope_root` when that root moves because following the root is its chosen location policy. Entering public mode validates that referenced media destinations are publicly deliverable and blocks when they are not; it does not select or move a provider. Leaving public mode reports media that remains publicly served but does not move or delete it. Local scope access is not a promise that all media bytes are private.

## Operator Workflow

An eligible scope gains **Change scope type** beside its existing lifecycle actions.

1. Choose one of the other supported target profiles.
2. For a public target, choose and validate the public route.
3. Request a server-owned preview.
4. Review canonical-root movement, any scope-local media that follows it, preserved explicit media destinations, regenerated products, config/manifest changes, routes and public projections, publication consequences, cleanup, and blockers.
5. Confirm the exact previewed target profile.
6. Apply recomputes and revalidates the plan, performs the migration, refreshes capabilities, and returns an exact result and navigation target.

The browser submits identities and choices, never authoritative paths or a filesystem plan. There is no in-place form for `scope_type`, scope-root provider, or `public_projection`; media destination changes use their separate lifecycle workflow.

## Transition Contracts

| transition | required result |
| --- | --- |
| external -> local repository | Copy the lifecycle-owned scope container into `docs-viewer/scopes/<scope>`, including media configured as scope-local; byte-verify relocated canonical/scope-local material, preserve explicit media destinations, rebuild documents/search, switch config and manifest ownership, then remove the inactive external root. Git may show additions without becoming migration authority. |
| local repository -> external | Verify that the configured external provider is available and the exact target is unoccupied, copy and byte-verify the scope container including scope-local media, preserve explicit media destinations, rebuild under the target configuration, switch authority, then remove the repository root. Git may show removals. |
| local repository -> public | Keep canonical source and media policy unchanged; require publicly deliverable destinations for media needed by public documents; add the exact public route and parent/child document/search projections; rebuild the local workspace; establish an unpublished public capability; do not promote document content. |
| public -> local repository | Preserve repository source and media policy; remove public-only document metadata, route, document/search projections, and derived Catalogue document locations; report any media that remains publicly served; rebuild the local-only workspace. |
| external <-> public | Compose the relevant storage relocation and public-exposure stages through local repository. The first implementation should not offer a direct combined transition. |

Each direction is an explicit supported transition, not the inverse invocation of Create or Delete. Create defaults cannot reconstruct an established scope, and Delete cannot serve as the commit mechanism for an identity that must continue to exist.

## Migration Inventory

Preview classifies current state by ownership rather than assuming every file should be moved:

| class | migration treatment |
| --- | --- |
| canonical Markdown and scope-local source/published media | copy with `scope_root` when workspace storage changes; byte-verify before commit |
| explicitly located published media | preserve the configured destination; validate public-delivery compatibility without relocating bytes |
| reproducible documents, search, manifests, Recent, Index, and derived references | rebuild from canonical source using the target configuration |
| scope configuration and lifecycle manifest | transform only migration-owned topology fields while preserving the established scope record and ownership history |
| public route, route registry, public document/search snapshots, and derived Catalogue URLs | add or remove exactly when exposure changes |
| independently owned external asset collections | report but do not move, delete, or adopt |

The target configuration must be derived from the current record, not generated afresh from scope-creation defaults. Existing default document identity, configured sub-scopes, report hosts, source build inputs, media types, custom published locations, non-loadable ids, manage-only roots, and other unaffected settings remain intact unless the target profile makes one explicitly invalid.

## Preview And Blockers

The write-free plan should include:

- current and target profiles and their storage/exposure axes;
- exact current and target canonical roots;
- canonical file and scope-local-media counts, sizes, providers, and verification method;
- explicit media destinations that remain unchanged and their public-delivery compatibility;
- generated roots to rebuild rather than copy;
- config, manifest, route registry, route shell, public document/search projection, and Catalogue changes;
- all configured one-level sub-scopes and their report hosts;
- exact documents whose publication-only front matter must be normalized;
- documents that omission would make eligible at the next public Publish;
- the proposed commit point, cleanup stages, and recovery meaning;
- management and public URLs after success; and
- a server-issued plan identity or source snapshot that apply can revalidate.

The plan blocks at least:

- a missing, unreadable, unsafe, or unavailable current source;
- a missing or unwritable target provider;
- an occupied target root, route collision, or escaping/symlink path;
- incomplete lifecycle ownership or unexpected state that makes cleanup ambiguous;
- unsupported recursive sub-scope topology or a child that cannot receive the target projection contract;
- invalid source/front matter or a target rebuild failure;
- a public target with referenced media whose configured destination is not publicly deliverable; and
- any source/config revision change between preview and apply.

Unavailable does not mean empty. Migration must never create a replacement source at an unavailable current root or infer content from stale generated products.

## Apply And Recovery

Apply should use one exact scope-level busy boundary so the live watcher cannot rebuild or publish that scope during migration. Local services do not need a multi-user transaction framework.

The normal sequence is:

1. Recompute and revalidate the preview against current config, manifest, source revision, paths, route ownership, and provider capabilities.
2. Create a lifecycle-owned staging location under the target provider. It must not use a sync-excluded generic `tmp` directory name.
3. Copy canonical source and scope-local media that follows a relocated `scope_root`.
4. Compare the complete relocated source/scope-local inventories and byte hashes.
5. Build target local documents and search without changing current configured authority.
6. Validate target configuration and generated products.
7. Revalidate that preserved explicit media destinations remain compatible with the target document-access profile.
8. Commit transformed config, route records, route shell, and lifecycle manifest as the new authority.
9. Remove or retire the old root and perform exact negative public document/search cleanup where required.
10. Refresh browser config, capabilities, indexes, watcher state, and navigation for the unchanged scope identity.

Before the commit point, failure removes or reports the inactive stage and leaves current authority unchanged. After the commit point, the service does not restore the old config or read from both roots. It returns `committed: true`, the failed stage, completed verification, exact remaining follow-through, and whether the same cleanup action is safely retryable. If old-root cleanup fails, the old bytes remain an explicitly inactive orphan rather than a fallback source.

## Public Exposure And Publish

Type migration must not become a second positive publication workflow.

### Entering Public

The transition creates the public-capable configuration, route shell, and empty or absent-safe public projections. The public route reports **Not published yet** until the existing scope-wide Publish promotes content. It must not copy the complete local working projection merely because the type changed.

Local documents cannot already contain `publishable`, so their omission means included at the next Publish under the established false-only exclusion contract. Preview reports the exact eligible document counts for the parent and every sub-scope. After migration, the operator may use the existing Set Publishable action before choosing Publish; migration does not invent an initial all-excluded state or an additional approval gate.

### Leaving Public

Local collections do not accept `publishable` front matter. Preview therefore lists every exact document containing the field, and confirmed migration removes that field as type normalization without changing title, body, identity, relationships, or other front matter.

Leaving public is complete when the route shell/registry, public document and search projections, parent and child document-location records, and derived Catalogue document URLs are removed. Existing negative public-delete planning can inform this cleanup, but the continuing scope identity requires a dedicated migration receipt.

Configured repository-public or R2 media remains at its explicit destination. Preview reports those remaining public URLs so the operator does not mistake local document access for media privacy. Moving or deleting that exposure is a separate confirmed Scope Media Storage Locations operation.

## Sub-Scopes And Identity

The migration unit is the top-level scope plus all configured one-level sub-scopes. Storage relocation moves their canonical source and local products inside the common container. Public exposure adds or removes each child projection and preserves its exact report host.

If any child cannot be planned exactly, the parent transition is blocked. The service cannot migrate only the parent, drop a child, infer a report host from title or route, or materialize recursive sub-scopes.

Because `scope_id`, `sub_scope`, and `doc_id` do not change, authored Docs links and logical media references remain stable. Generated viewer URLs and public locations are rebuilt from the target configuration; source text is not searched or rewritten.

## Eligibility

The first eligibility boundary is user-created, lifecycle-created scopes whose manifest and configured topology agree. System/backfilled scopes remain visible but cannot be migrated through this workflow. Supporting them later requires an explicit ownership/adoption decision rather than weakening the manifest check.

The UI projects eligible targets per scope. A scope may support workspace relocation but not public exposure when one or more configured media destinations are not publicly deliverable. Capability absence is truthful product state and should route the operator to the separate media-location action rather than silently changing policy during scope migration.

## Proof Gate

A delivery is not complete without focused evidence that proves:

- canonical source and scope-local media inventories are byte-identical across workspace relocation;
- the immutable scope, document, sub-scope, and report-host identities and relationships are unchanged;
- established unaffected configuration fields survive transformation;
- one and only one configured canonical root remains after success;
- target local documents, search, media reads, browser config, and capabilities rebuild successfully;
- generated products were rebuilt rather than accepted as migration authority;
- entering public exposes no document content until the existing Publish action is applied;
- the first Publish uses the established `publishable` false-only contract for parent and child collections;
- entering public preserves compatible explicit media destinations and blocks incompatible ones without moving bytes;
- leaving public removes exact document routes, projections, locations, and Catalogue URLs while reporting unchanged public media exposure;
- independently owned external asset collections are untouched;
- watcher suppression and refresh prevent mixed-profile products; and
- injected failures before and after the commit point produce the documented unchanged or committed-recovery result without dual-root fallback.

The proof should cover all four adjacent directed transitions. External-to-public composition is not claimed until both stages can be executed and recovered independently.

## Delivery Seams

The concept admits independently complete deliveries without pre-authorizing them:

- common migration preview, transformed-config, receipt, and fault/recovery contract;
- external/local-repository storage relocation;
- local-repository-to-public enablement while preserving the single positive Publish workflow;
- public-to-local-repository conversion with publication-only metadata normalization and exact public document cleanup; and
- optional composed external/public interaction after the adjacent transitions are proven.

Any future delivery must choose one complete outcome, begin with the Roadmap sanity gate, inspect the current owners, and stop rather than silently absorbing another transition.

## Exclusions

This concept does not introduce:

- external public scopes or arbitrary source roots;
- a generic provider matrix exposed to operators;
- Create-target-then-Delete-source composition;
- scope, document, or media-reference renaming;
- document comparison, merge, synchronization, or automatic editorial decisions;
- automatic public publication during migration;
- media destination changes or R2/repository/external-local byte migration, which belong to Scope Media Storage Locations;
- duplicate config readers, aliases, fallback roots, or compatibility routing;
- migration of independently owned asset collections;
- a persistent migration daemon, background queue, or iCloud/R2 synchronization service; or
- a claim that a partial config edit or remaining public document/search projections constitute success.
