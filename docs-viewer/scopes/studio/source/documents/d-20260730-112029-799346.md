# Edited Docs Review Source Round-Trip Delivery

## Status And Dependencies

Proposed as ERS-1 under
[Edited Docs Review Source Round-Trip](/docs/?scope=studio&doc=d-20260730-121423-78b0f6).
It replaces the former independent Docs Review Build delivery.

Build and edited-source-folder Import are one complete feature outcome. This
delivery must not start until both sub-scope Import-parity prerequisites ship:

1. [Sub-Scope Ordinary Document Import Delivery](/docs/?scope=studio&doc=d-20260730-121423-469e54);
2. [Sub-Scope Returned Package Import Delivery](/docs/?scope=studio&doc=d-20260730-102954-1b363f).

The exact package-source **Open in VS Code** action and the synthetic Docs
Review builder are already shipped. The prerequisites establish shared
scope/sub-scope Import targets before this delivery adds another trusted
collection format.

## Complete Outcome

For a validated, import-capable review package from either a top-level scope or
a configured sub-scope, the user can:

1. edit package-local `source/*.md` files in VS Code;
2. select **Build** in Docs Review to regenerate and inspect the complete
   retained preview;
3. copy the package's complete `source/` folder into Import staging;
4. choose that folder in Docs Import as an **Edited review source** collection;
5. preview the complete exact overwrite plan and accept the derived-Markdown
   fidelity warning once; and
6. apply every edited source to its original canonical collection or none.

The edited Markdown sources are the content authority for this Import. The
original JSON/JSONL and trusted export metadata remain authority for provenance,
capability, exact prepared membership, routing, and prepared canonical source
versions.

## Docs Review Build Contract

- The disabled **Built** status becomes an enabled **Build** action whenever one
  valid package is active and no build request is running.
- The request freezes only the validated active `package_id`; it accepts no
  source path, configured scope, URL fallback, or canonical target.
- Explicit **Build** always regenerates the complete package-local projection,
  even when existing generated JSON is structurally complete.
- The existing review-specific synthetic configuration and Docs Viewer builder
  remain the only renderer and compiler.
- Build reads package-local `source/*.md` and writes only package-local
  generated projection. It does not rewrite source front matter, advance the
  package-local or canonical `last_updated`, or mutate canonical documents.
- Success reloads the same `package` and selected `doc`. Failure reports the
  error, stays on the current preview, and re-enables **Build** for retry.
- Ordinary reads retain conditional repair: damaged generated output may be
  repaired, while healthy output is not rebuilt merely by navigation.
- No watcher registration, source-freshness inference, background rebuild, or
  per-document incremental build is added.

## Edited Review Source Folder Contract

- The format recognizer runs before generic Markdown-package handling and
  accepts one staged folder containing the complete set of direct Markdown
  children materialized by a validated Docs Review package.
- Every source must have strict canonical front matter and the same
  `review_folder_id`, profile, export ID, source scope, and optional source
  sub-scope. Filename stems and `doc_id` values must agree and remain unique.
- Package-local `added_date` and `last_updated` remain validated review
  transport metadata. Editing or building the package does not make either
  value canonical or eligible to overwrite destination date provenance.
- Trusted export metadata and the original validated review manifest establish
  package capability and the exact prepared document set. Missing, extra,
  duplicate, nested, symlinked, malformed, mixed-package, or cross-collection
  sources block the folder.
- A standalone review-source file selected through ordinary Markdown Import is
  rejected with guidance to stage and select the complete source folder. Its
  front matter is never rendered as body text.
- Generic `.md` files and ordinary one-document Markdown packages retain their
  current body-oriented create-only behavior.
- The folder is overwrite-only. Every source `doc_id` must resolve to exactly
  one existing `{ scope, doc_id }` or `{ scope, sub_scope, doc_id }` target.
  There is no create, skip, record selection, title match, or parent fallback.

## Dispatch Precedence

The integrated recognizer must receive the untouched staged candidate before
ordinary Markdown normalization:

1. inspect a directory and its unmodified source front matter for one complete
   edited review package;
2. accept a valid complete folder into trusted collection planning;
3. reject an individually selected review source with guidance to stage the
   complete folder; then
4. pass only unclaimed ordinary `.md` files and one-document Markdown packages
   to the generic normalizer, which may strip a well-formed leading front-matter
   block before create-only preview.

The generic normalizer may use a scalar `title` only as an ordinary title
fallback. It ignores `doc_id`, `review_*`, hierarchy, lifecycle, and status
fields and never converts them into overwrite or routing authority.

## Canonical Apply Contract

- Review transport fields, including package-local `added_date` and
  `last_updated`, are validated but never written to canonical front matter.
- Edited body, title, and summary may replace their canonical counterparts.
  Immutable `doc_id`, original `added_date`, and destination-owned fields such
  as `group`, `ui_status`, and collection configuration remain canonical.
- Apply compares edited body, title, and summary with the current canonical
  source through the shared recent-edit comparison. A qualifying change
  advances canonical `last_updated` inside the Import mutation boundary; a
  non-qualifying apply preserves the existing canonical timestamp.
- Parent and visibility fields apply only where the exact destination
  collection already permits them. Flat sub-scopes reject hierarchy rather
  than inventing it.
- Preview is write-free and shows folder identity, exact collection, document
  count, all target documents, stale-source state, and the fidelity warning.
- One explicit confirmation accepts the complete overwrite plan. Prepared
  canonical versions are revalidated immediately before apply.
- Apply validates and prepares every write before entering one scope or
  confined sub-scope mutation boundary. A write or rebuild failure restores
  the complete pre-apply source snapshot and reports no successful Import.
- Success refreshes the relevant top-level Docs Viewer state or mounted
  sub-scope report without changing selection in another surface.

## Fidelity Boundary

`document-content` review source is derived Markdown. Rich content, tokens,
comments, raw embeds, source formatting, or package assets may have been lost
during rendered conversion. The user owns that acceptance decision by
rebuilding and visually inspecting Docs Review before staging the folder.

The Import preview repeats that warning but does not compare with, restore
from, or merge content from the original JSON/JSONL package.

[Full Document Export Delivery](/docs/?scope=studio&doc=d-20260711-012238-8a04a6)
separately proposes exact canonical Markdown and asset/dependency export. ERS-1
does not duplicate that work or make the proposed export-only profile
returnable.

## Likely Authority

- The Docs Review controller and provider own Build state, exact active package
  identity, status, retry, and route-preserving reload.
- The existing review package service and synthetic builder own explicit
  regeneration versus conditional read-time repair.
- The integrated Import format registry owns edited-source-folder recognition
  before generic Markdown formats.
- Existing trusted export metadata, returned-package validation, and review
  manifests own capability, provenance, and exact membership.
- Shared `ImportContent`, collection planning, scope/sub-scope target
  resolution, mutation, rollback, and rebuild owners perform the complete
  overwrite without a second document parser or mutation model.
- Scope and report Import controllers reuse one modal, preview, confirmation,
  busy, retry, and result lifecycle.

## Boundary

In scope:

- explicit complete-package Build in Docs Review;
- staged edited-review-source-folder discovery and strict validation;
- one fidelity warning and whole-folder confirmation;
- overwrite-only exact scope and sub-scope apply;
- stale-source revalidation, rollback, and appropriate rebuild/refresh;
- rejection of individual review sources through ordinary Markdown Import; and
- focused service, module, route, and realistic browser evidence for both
  destination kinds.

Not in scope:

- implementing either sub-scope Import prerequisite;
- editing or regenerating the original returned JSON/JSONL;
- arbitrary front-matter-aware Markdown Import;
- creates, partial apply, record selection, moves, deletes, or identity changes;
- automatic rich-content, token, embed, dependency, or asset restoration;
- extending `docs-watcher`; or
- making `document-full-source` returnable.

## Completion Gate

One scope package and one configured sub-scope package are edited in VS Code,
rebuilt and visually accepted in Docs Review, staged as complete source
folders, revalidated against their exact prepared and current canonical sets,
and applied completely through one shared Import format. Both destinations show
the edited content after their appropriate rebuild. Docs Review Build leaves
package-local and canonical timestamps untouched; Import advances canonical
`last_updated` exactly when body, title, or summary changed. Generic Markdown,
the original JSON/JSONL, unrelated metadata, other collections, and public
surfaces remain unchanged.
