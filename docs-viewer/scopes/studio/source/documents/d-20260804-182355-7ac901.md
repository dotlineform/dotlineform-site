# SSC-1.0 — Contract And Cutover Sanity Note

## Decision

The unified contract fits the current system without a second registry, generic schema language, public management projection, compatibility alias, or user-visible behaviour change. SSC-1.1 may perform the coordinated terminology cutover after explicit implementation approval. This note changes no runtime contract.

The two current Projects-only collection-name checks in the Python definition and Manage browser factory are migration risks, not accepted availability owners. The configured exact sub-scope selects the registered definition; the resolved exact target then flows through its aspects. SSC-1 must retire those redundant name checks rather than preserve them behind the renamed contract.

## Accepted Configuration

The configured sub-scope retains one optional extension property and no loose field or capability declarations:

```yaml
sub_scope_customisation:
  id: <registered snake-case id>
  settings: <definition-validated object>
```

An absent property selects the canonical default report host, manifests, navigation, list/detail behavior, and Manage actions. The registry validates the ID, settings, and any collection prerequisites. Raw settings remain server-side.

## Accepted Definition Aspects

The registered definition keeps identity, settings normalization, and any capability-based collection prerequisites at its root. Existing and reserved behavior is expressed through the following optional code-owned aspects:

| aspect | owner and boundary |
| --- | --- |
| `manifest_projection` | projects strict root and row data for each enabled access without redefining membership |
| `document_groups` | owns the ordered document-group values used by current validation and metadata behavior |
| `source_validation` | validates custom source front matter during build, package, and mutation flows |
| `metadata` | pairs the exact-target read projection with its optional revision-safe update normalizer |
| `import_front_matter` | normalizes only custom create-time front matter owned by the definition |
| `browser_composition` | declares the enabled access set used for descriptor projection and exact Python/JavaScript registry agreement |
| `assignable_field_groups` | reserves code-owned focused-workflow declarations; current registrations contribute none until SSP-0 or TDL-0 owns them |
| `transfer` | reserves a code-owned field-ownership and compatibility contract; current registrations contribute none until the Copy delivery owns it |

The access set has one registered owner rather than separate public and Manage availability booleans. Manifest projection and browser descriptor emission consume that same set. Assignable field groups and transfer contracts are typed registration slots, not config arrays or data-driven form schemas. Later field-group values must reuse the owning definition's normalized values instead of duplicating choices.

The generated manifest and metadata `customisation` envelopes remain contribution-data namespaces. The no-alias cutover renames the selected contract descriptor and report-named implementation vocabulary to `sub_scope_customisation` or `subScopeCustomisation`; it does not rename every contribution-data field merely because it contains custom data.

## Migration Surface

The coordinated cutover covers:

- configured sub-scope records, normalized config types, strict errors, and the maintained group-seeding utility;
- the Python registry module, definition/config types, helper names, builders, source validation, metadata mutation/read, import, returned-package, and review-source callers;
- generated browser configuration and its checked-in default, while preserving default and custom manifest membership and data values;
- browser config normalization, shared report state, Manage report and modal composition, focused registries, factories, fixtures, and access-agreement checks;
- focused configuration, builder, metadata, import, package, runtime-boundary, migration, and module evidence; and
- active feature/delivery references, followed by the durable architecture rename and consumer transfer at SSC-1.3.

The cutover is one source-and-consumer change. There is no dual key, fallback reader, compatibility property, or mixed generated payload.

## Access Boundary

`analysis_tags` and `dotlineform_projects` remain Manage-only. Their current public browser configuration omits the descriptor, public manifests retain the standard public-safe rows, the public registry has no loaders for them, and the public import graph has no edge to their Manage modules. Settings, metadata mutation authority, focused actions, and future assignable-field declarations remain local to Manage. Any later public contribution requires an explicit public access registration and matching public loader; it cannot arrive through a hidden control or runtime branch.

## Risks And Stop Gate

The main risks are a partial vocabulary cutover, stale generated browser config, access declarations drifting from loader registries, custom metadata callers escaping the aspect owner, the current Projects name checks surviving, and future field values being declared twice. SSC-1.1 and SSC-1.2 must use focused exact-key, default, unknown-ID/settings, registry-agreement, exact-target, generated-payload, and public-isolation evidence to contain those risks.

Stop and return for review if implementation requires a compatibility alias, parallel field registry, duplicated action flag, literal collection-name availability check, generic form engine, public management data or controls, changed report membership, or other user-visible behavior. SSC-1.1 has not started.
