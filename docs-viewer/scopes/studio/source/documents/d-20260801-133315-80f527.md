# Projects Architecture

## Purpose

This document is the implementation reference for Project documents, their optional folder links, and the boundary between Docs Viewer, Studio, and local folders. The derived relationship model now has its own owner: [Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9).

The governing flow is:

```text
Project source document -> Projects customisation -> namespaced folder_path projection
body path paste --------> dlf-local link ---------> confined Manage activation

folders + Projects Manage manifest + canonical Works/Series
    -> Project State generation
    -> saved Doc/Folder/Series report + folder resolver lookup
```

No arrow grants mutation authority over an input.

## Authorities

| concern | authority |
| --- | --- |
| local path containment and existence | exact targets confined below `$DOTLINEFORM_PROJECTS_BASE_DIR/` |
| Project discovery and seed inventory | configured discovery roots, initially `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` |
| Work source-path snapshot | canonical Studio Work record |
| Work-to-Series membership | canonical Studio catalogue |
| Project notes and collection membership | document source in `dotlineform/projects` |
| literal convenience target | optional Project document `folder_path` front matter |
| normalized manifest projection and Projects controls | registered Manage-only Projects sub-scope customisation |
| folder relationship model, saved report, and Project lookup | Project State producer |
| Project resolver parsing/rendering and semantic usage | [Resolver Tokens Architecture](/docs/?scope=studio&doc=d-20260802-174339-53877d) plus existing Semantic Tokens owners |
| current image-level project audit and its retirement | SSP-7 |

## Studio Boundary

`folder_path` and `project_folder` are not aliases. `folder_path` belongs only to Project document source and the namespaced Docs Viewer Manage manifest. PRJ-1 local links and PRJ-2 metadata/seeding add no Studio field, UI control, read path, write path, or service dependency.

Project State has one explicit integration seam because Studio owns historical Work folder and Series evidence. The server-side post-commit observer reads exact committed Work before/after records and writes derived Docs Viewer state only. It never writes `folder_path`, rewrites `project_folder`, changes the catalogue transaction, or makes a successful Work commit contingent on follow-through.

SSP-7 may read canonical Work media fields for its audit but likewise has no Studio mutation authority.

## Project Document Data Contract

`folder_path` is an optional normalized POSIX path relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`:

```yaml
folder_path: "projects/3 symbols"
```

The configured `dotlineform/projects` collection selects the Projects customisation. Its controlled projector adds the value only to the exact row's namespaced local management data:

```json
{
  "doc_id": "d-example",
  "title": "3 symbols",
  "customisation": {
    "folder_path": "projects/3 symbols"
  }
}
```

The default manifest fields, public manifest, and public browser descriptor do not gain `folder_path`. Missing, malformed, duplicate, or non-resolving values remain reportable evidence and never alter collection membership.

The Projects Edit Metadata contribution reads and writes the field only for an explicit validated `{scope, sub_scope, doc_id}` target. Creation and the one-off Apple Notes migration use the same normalizer and exact-target document writer.

## Local Path Contract

The shared parser accepts local `file:` URLs, absolute POSIX paths with ordinary spaces, and absolute POSIX paths whose characters are backslash-escaped for shell display.

Input is parsed as data. There is no shell evaluation, environment-variable or home expansion, command substitution, relative-path resolution, remote file authority, or non-`file:` scheme.

Normalization strips the configured root and produces one decoded base-relative POSIX target plus an encoded link representation. Body Markdown uses `dlf-local:projects/3%20symbols`; structured metadata stores only `projects/3 symbols`. The Projects feature supplies `$DOTLINEFORM_PROJECTS_BASE_DIR/` as its allowed root. Metadata may save a non-existing contained target; activation requires the target to exist.

A local Open in Finder service receives the exact relative target, resolves and reconfines it below the configured base root, and never falls back to a displayed document, parent collection, title, or URL text from a different target.

Containment and discovery are separate policies. Links and `folder_path` may target any contained folder. Automatic Project candidate discovery scans only configured Project discovery roots, initially `projects/`; it does not recurse through Docs Viewer scopes, configuration, or every other base-root directory.

PRJ-1 renders `dlf-local:` links as clickable only in local Manage. Public projection recognizes the marker and retains a safe inert label or placeholder while removing the marker and target. General redaction of absolute paths authored as prose, raw HTML, or code is a separate public-build concern.

## Project State Integration

Projects supplies one input to Project State: the exact `dotlineform/projects` Manage manifest with its namespaced `folder_path` values. It does not own the normalized relationship schema, report source, resolver lookup, refresh policy, or stale-generation behavior.

Project State owns the folder-centred relationship:

```text
Project documents[] <- folder_path -> Series[]
```

Works remain historical derivation evidence. Individual Works are neither Project State report results nor initial Project resolver subjects/results. The saved report and lookup are generated from the same versioned row model, but downstream Resolver Tokens do not depend on the Markdown layout.

Project-document create/delete and `folder_path` changes may trigger bounded Project State follow-through after the canonical Docs Viewer mutation. Failure does not undo or repeat that document mutation.

## Project Media Audit Integration

The current Studio Project State report is actually an image-level audit. [SSP-7 — Project Media Audit Delivery](/docs/?scope=studio&doc=d-20260802-121106-15ea55) preserves that useful behavior as a separate generated Docs Viewer document and owns retirement of `/studio/project-state/`, its APIs/activity, generator placement, opener, and `var/studio/reports/project-state.md`.

Project Media Audit does not write or enrich Project State rows. Project State does not inherit image-extension policy, image inventories, missing-image exceptions, or audit repair semantics.

## Failure And Freshness

Project document, Studio Work, Project State, and Project Media Audit writes retain separate commit boundaries. A derived follow-through failure never rolls back or retries its source mutation. The prior complete derived generation remains available and reports stale state.

Relationship freshness and rendered Resolver Token freshness are separate:

```text
input mutation -> Project State generation
document rebuild -> rendered Resolver Token output
```

Project State does not silently rebuild every document containing a Resolver Token. A dependent-document refresh requires its own explicit usage-owned workflow.

## Architectural Invariants

- There is no canonical Project-folder registry.
- Folder identity is explicit normalized path evidence, never inferred from title, Series name, filename, or UI context.
- `folder_path` remains Docs Viewer-only and never becomes a Studio field or alias.
- Project document membership is independent of folder existence and `folder_path` validity.
- Local activation is exact, contained, and Manage-only.
- Project State has one dedicated data-model owner and one complete generated generation.
- Project Media Audit remains a separate read-only capability.
- Resolver expansion is one-hop and never refreshes Project State.
- No derived relationship or audit result authorizes mutation of a Work, document, Series, or folder.
