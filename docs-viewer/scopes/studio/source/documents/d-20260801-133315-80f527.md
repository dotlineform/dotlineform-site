# Projects Architecture

## Purpose

This document is the implementation reference for the Projects feature. It
defines how folder links enter documents, how the Projects customisation
projects them, how Project State reconciles three independent inputs, and how
Resolver Tokens consume one bounded generated lookup.

The governing flow is:

```text
current folders -----------+
Project document manifest -+-> Project State snapshot -> report data
canonical Studio Works ----+                         \-> Project resolver lookup

explicit Resolver Token -> exact keyed lookup -> one-hop rendered groups
```

No arrow grants mutation authority over an input.

## Authorities

| concern | authority |
| --- | --- |
| local path containment and existence | exact targets confined below `$DOTLINEFORM_PROJECTS_BASE_DIR/` |
| Project discovery and seed inventory | configured discovery roots, initially `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/` |
| Work source-path snapshot | canonical Studio Work record |
| Work-to-Series membership | canonical Studio catalogue |
| Project notes and membership | document source in `dotlineform/projects` |
| literal convenience target | optional Project document `folder_path` front matter |
| normalized manifest projection and Projects controls | registered Manage-only Projects sub-scope customisation |
| reconciliation model, report payload, and Project resolver lookup | Docs Viewer Project State producer |
| resolver capability definition and access | small global Docs Viewer resolver-definition registry |
| rendered Resolver Token result | document builder reading one declared lookup row |

## Studio Boundary

`folder_path` and `project_folder` are not aliases. `folder_path` belongs only
to Project document source and the namespaced Docs Viewer Manage manifest.
PRJ-1 local links and PRJ-2 metadata/seeding add no Studio field, UI control,
read path, write path, or service dependency.

Project State has one explicit integration seam because Studio owns the
historical evidence it reconciles. PRJ-3 reads existing Work/Series data and
uses the Studio-read-only server-side post-commit Work observer described below
to refresh the derived Docs Viewer snapshot. The observer writes Project State
only. It never writes `folder_path`, rewrites `project_folder`, changes the
catalogue transaction, or makes a successful Work commit contingent on Project
State follow-through.

## Project Document Data Contract

`folder_path` is an optional normalized POSIX path relative to
`$DOTLINEFORM_PROJECTS_BASE_DIR/`:

```yaml
folder_path: "projects/3 symbols"
```

The configured `dotlineform/projects` collection selects a known Projects
customisation. Its controlled projector adds the value only to the exact row's
namespaced local management data:

```json
{
  "doc_id": "d-example",
  "title": "3 symbols",
  "customisation": {
    "folder_path": "projects/3 symbols"
  }
}
```

The default manifest fields, public manifest, and public browser descriptor do
not gain `folder_path`. Missing, malformed, duplicate, or non-resolving values
remain reportable states and never alter document membership.

The Projects Edit Metadata contribution reads and writes the field only for an
explicit validated `{scope, sub_scope, doc_id}` target. Creation and bulk seed
use the same normalizer and exact-target document writer.

## Local Path Contract

The shared parser accepts:

- local `file:` URLs;
- absolute POSIX paths with ordinary spaces; and
- absolute POSIX paths whose characters are backslash-escaped for shell
  display.

Input is parsed as data. There is no shell evaluation, environment-variable or
home expansion, command substitution, relative-path resolution, remote file
authority, or non-`file:` scheme.

Normalization strips the configured root and produces one decoded
base-relative POSIX target plus an encoded link representation. Body Markdown
uses `dlf-local:projects/3%20symbols`; structured metadata stores only
`projects/3 symbols`. The Projects feature supplies
`$DOTLINEFORM_PROJECTS_BASE_DIR/` as its allowed root. Metadata may save a
non-existing contained target; activation requires the target to exist. A
local Open in Finder service receives the exact relative target, resolves and
reconfines it below that base root, and never falls back to a displayed
document, parent collection, title, or URL text from a different target.

Containment and discovery are separate policies. Links and `folder_path` may
target any contained folder. Automatic Project candidate discovery scans only
configured Project discovery roots, initially `projects/`; it does not recurse
through Docs Viewer scopes, configuration, or every other directory merely
because they share the same base root.

PRJ-1 renders `dlf-local:` links as clickable only in local Manage. Public
projection recognizes the explicit marker and retains a safe inert label or
placeholder while removing the marker and target. General redaction and
verification of absolute paths authored as prose, raw HTML, or code is a
separate public-build delivery.

## Project State Inputs And Model

A full Project State refresh reads:

```text
configured Project discovery inventory
    + exact existence checks for declared base-contained targets
    + current dotlineform/projects Manage manifest
    + current canonical Works
    -> normalized relationship snapshot
```

Folder keys are normalized relative paths below
`$DOTLINEFORM_PROJECTS_BASE_DIR/`, so an ordinary project key begins with
`projects/` and an explicitly linked folder elsewhere remains representable.
Work folder evidence is derived from `project_folder` plus optional
`project_subfolder` and normalized into that same base-relative namespace;
`project_filename` is not part of folder topology. The model retains
incomplete and unmatched evidence instead of discarding it.

The same snapshot atomically publishes:

- the read-only Project State report payload; and
- the Manage-only Project resolver lookup.

The report is hosted by one ordinary report document in scope `dotlineform`.
It links to exact Project documents, Works, Series, and validated folder
targets. It owns no repair action.

## Resolver Contract

Resolver addressability is global, but relationship data is not one global
graph. A small code-owned definition registry declares:

- resolver ID and access level;
- accepted subject kinds and key normalization;
- lookup location and schema version; and
- ordered result groups.

Each resolver's domain producer owns its generated lookup. Project State is
the only producer of the Project lookup. Rows are precomputed for exact folder
and Work subjects, carry snapshot generation metadata, and contain only the
declared one-hop groups:

```text
folder -> Works[] + Project documents[]
Work   -> folders[] + Project documents[]
```

Expansion parses the exact resolver and subject, enforces access, loads that
single lookup, performs one exact-key read, and renders the row's groups in
configured order. There is no fuzzy match, contextual fallback, canonical
registry scan, or traversal from returned items.

Within the initial resolver, Works sort by normalized Work ID, Project
documents by title then `doc_id`, and folders by normalized relative path. A
missing or stale lookup produces an explicit unavailable state rather than a
live scan.

## Refresh And Mutation Contract

### Full Refresh

A full refresh reads all three inputs and atomically replaces the complete
report and resolver snapshot. It runs when:

- the Project State report opens or the user chooses explicit Refresh;
- the snapshot is missing, corrupt, or version-incompatible;
- a mutation cannot supply trusted before/after data; or
- the user explicitly requests Rebuild All.

Direct Finder changes have no reliable application event and become visible
at the next full refresh. That refresh scans configured discovery roots and
checks exact declared contained targets; it does not inventory the entire base
directory indiscriminately. A filesystem watcher is not part of the initial
contract.

### Targeted Update

Known committed changes use exact deltas and recompute only affected subject
and reverse-membership rows. A compact JSON lookup may still be atomically
rewritten; that is not a logical full rebuild when relationship computation
was confined to the supplied delta.

Examples include:

- Work create/delete: add or remove the exact Work subject and affected folder
  rows;
- Work folder change: update the Work row and the union of old/new folder rows;
- Work title change: update result labels that display that Work;
- Work `series_ids` change: update report enrichment without adding a Resolver
  Token Series edge; and
- Project `folder_path` change/delete: update the document row and its old/new
  folder reverse memberships.

Batch mutations with complete before/after records publish one targeted
multi-record generation.

### Exact Studio-Read-Only Observer

The Work observer runs at the server-side committed mutation boundary and is
read-only with respect to Studio. It is not a browser Save event, media upload
event, or publication status transition. The Work
editor currently calls `POST /studio/api/catalogue/work/save`;
`work_save_payload()` holds `current_record`, `updated_record`, and
`changed_fields` around the canonical `works.json` transaction.

After a successful canonical commit, one Project State impact classifier uses
those exact values:

| field class | fields | effect |
| --- | --- | --- |
| folder topology | `project_folder`, `project_subfolder` | targeted Work and old/new folder update |
| rendered Work label | `title` | targeted displayed-link update |
| report enrichment | `series_ids` | targeted report update only |
| irrelevant | `project_filename`, status, dates, other metadata | no Project State update |

Work create, save, delete, bulk save, and import paths call the same classifier.
Browser code never decides whether to rebuild Project State.

This is the only new Studio integration in Projects. It responds to the
existing canonical fields after commit and writes derived Docs Viewer data; it
grants Docs Viewer no mutation authority over Studio.

## Failure And Freshness

If post-commit Project State follow-through fails, the Work or Project document
remains committed. The previous complete snapshot is retained and marked stale;
the response reports a derived-projection failure and must not cause the source
mutation to repeat.

Relationship freshness and rendered-document freshness are separate:

```text
input mutation -> Project State snapshot update
document rebuild -> rendered Resolver Token list update
```

Project State does not silently rebuild every document containing a Resolver
Token. A future dependent-document refresh would require its own explicit
usage index and bounded workflow.

## Retirement Boundary

Project State moves completely out of Studio. Delivery removes or reroutes
`/studio/project-state/`, its report/open endpoints, frontend, activity
contract, Markdown generator/opener, focused tests, and
`var/studio/reports/project-state.md`.

The new folder inventory observes folder identity only. The old primary-image
audit is not retained implicitly. `IMAGE_EXTENSIONS` currently has another
catalogue consumer, so reusable policy must move to a neutral owner before the
old report module is deleted.

## Architectural Invariants

- There is no canonical Project-folder registry.
- Project State has one Docs Viewer owner and one generated snapshot.
- Report and resolver data come from the same normalized generation.
- Targeted updates are the default for trusted application mutations; full
  refresh is the explicit fallback and filesystem-observation path.
- Resolver expansion has depth one and never refreshes its lookup.
- Local folder data and activation do not enter public projections.
- Projects does not implement a general public-content path redactor or public
  private-path verifier.
- No relationship result authorizes mutation of a Work, document, Series, or
  folder.
