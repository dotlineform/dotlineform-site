# Semantic Tokens Architecture

## Outcome

Provide one manage-only Docs Viewer extension path from a registered token family
to source-editor authoring, current-buffer inspection, local rendering,
generated relationships, and a focused report.

The accepted [Source Editor UI](/docs/?scope=studio&doc=d-20260623-180405-631ef4)
is the input to this architecture. It first determines when an author searches,
compares, selects, and locks a target. Token syntax records that decision. The
token-definition registry selects the configured workflow and target projection.
Generated data records actual document usage.

## Token Syntax

CT-P0 accepts this deterministic source form:

```md
[[<family>:<target-type>:<canonical-id>|<escaped-title>]]
```

The first accepted examples are:

```md
[[catalogue:work:00638|3 symbols]]
[[catalogue:work:00008|nerve]]
[[catalogue:series:105|nerve]]
[[catalogue:moment:d-20260215-000000-02a1a4|13 moments in october]]
```

Family and target-type keys are lower-case identifiers matching
`[a-z][a-z0-9-]*`. A lexical id matches
`[A-Za-z0-9][A-Za-z0-9._-]*`; its accepted canonical form is then owned by the
target-type id policy. Catalogue Work uses five digits, while Series and Moment
use lower-case alphanumeric-and-hyphen ids. The modal may normalize accepted
input, but serialization always records the canonical id.

Title is a required, single-line occurrence field. The modal trims its outer
whitespace before serialization and preserves its remaining Unicode text. The
serializer escapes backslash, pipe, and closing bracket as `\\`, `\|`, and
`\]`, in that order. The parser decodes only those three escapes; an unknown
escape, an empty Title, an invalid identity component, or an unterminated token
is malformed. Identity components are never escaped.

Serialization emits no optional whitespace around separators. Parsing returns
the raw token and a zero-based half-open `[start, end)` source range. Inline
code, fenced code, and HTML comments are inactive. A collapsed caret activates a
supported occurrence only when `start < caret < end`; a shared boundary between
adjacent tokens activates neither. Malformed and unsupported kinds never
activate a token.

The immutable identity is `(family, target type, target id)`. The author need not
choose the type before searching; selecting a result supplies it. The displayed
Title remains occurrence metadata and does not edit the canonical target.

The versioned shared contract fixture is
`docs-viewer/tests/fixtures/semantic_tokens_catalogue_v1.json`. Python and
browser implementations must consume its same raw strings, decoded fields,
ranges, inactive contexts, and caret expectations rather than maintaining
separate examples.

## Authoring Validation And Tolerant Build

The add-token modal is the only semantic validation owner. At confirmation it:

- requires a target selected from the current family lookup;
- normalizes and validates the concrete identity;
- validates required occurrence fields;
- serializes the accepted syntax deterministically.

This validates the new string being inserted, not the whole document. Markdown
source remains directly user-editable before or after insertion.

The builder is a tolerant projector, not a semantic validator. It may recognize
a syntactically plausible string and attempt to resolve its identity. It emits a
link and usage-index occurrence only when the configured target lookup returns a
safe, workable destination. Otherwise it:

- leaves the original source substring unchanged for ordinary Markdown
  rendering;
- emits no semantic link;
- emits no usage or reverse-relationship row;
- does not warn or fail the document build.

This applies to malformed syntax, unsupported token kinds, missing identities,
and lookup results without a usable destination. Grammar recognition and
best-effort resolution are implementation steps, not validation outcomes. The
normal build records no broken-link result; the separate read-only audit owns
diagnosis.

## Token-Definition Registry

Proposed checked-in location:

```text
docs-viewer/config/semantic-tokens/families.json
```

Use a schema-versioned envelope with one record per accepted family. A family
and target-type pair forms one token-kind definition, such as
`catalogue:work`. The registry is checked-in configuration describing supported
token kinds; it is not a collection of tokens found in documents and it does
not contain canonical target records.

A family record defines:

- stable family key and author-facing action name;
- required and optional occurrence fields;
- occurrence fields the Info view may edit;
- add-action, modal, and Info-view contribution ids;
- generated relationship and report meaning.

Each accepted target type within the family defines:

- stable type key and author-facing result label;
- canonical owner and target-lookup adapter;
- immutable id field plus modal-time normalization and validation;
- distinguishing result metadata and optional preview data;
- projection adapter id and the named fields it supplies;
- the presentation type and destination for each projected field.

The Catalogue family initially declares Work, Series, and Moment. Its discovery
adapter returns them in one result set; optional filters narrow that set without
requiring a type choice before search.

The registry selects declared capabilities. Parser, normalizer, resolver, and UI
implementations remain code-owned; JSON must not become an executable plugin
framework.

## Configured Target Projection

An individual token resolves its identity through its token-kind definition. It
does not receive a canonical record and interpret that record itself:

```text
token occurrence: catalogue:work + 00008
    -> catalogue:work definition
    -> configured Work projection adapter
    -> named projection fields
    -> add modal, Info view, renderer, or report
```

The definition declares the projection interface. Its adapter owns canonical
data access, array selection, URL construction, and other domain logic. For
example, a Work token need not inspect `series_ids[]` or `downloads[]`. If the
definition exposes `url`, `media`, or `file`, the adapter supplies those named
values according to the Work contract and the consuming UI simply reads or
displays them.

A definition may deliberately expose a list, but canonical arrays are not
implicitly projected and a token never traverses arbitrary canonical JSON.
Changing the canonical storage shape therefore affects the focused adapter, not
token syntax or every token consumer.

## Metadata Sources

Use **metadata** only with its source qualified. The Info panel can combine
values from different places, but those places do not have the same authority
or freshness:

| qualified term | stored where | access path | Info-panel use |
| --- | --- | --- | --- |
| token identity and occurrence fields | current Markdown source | parse the current editor buffer | identity is read-only; declared occurrence fields are editable |
| usage-index attributes | generated semantic-token usage JSON | match the rebuilt occurrence | optional read-only context; never overrides the current buffer |
| canonical target fields | target owner, such as the Work record | target adapter only | not read directly by the Info panel |
| target-lookup projection fields | generated lookup or focused adapter result keyed by target identity | token-kind lookup contract | declared read-only context, destinations, and previews |

Field authority and delivery source are separate questions. An occurrence field
may be repeated in the usage index, while a canonical or derived target field
may be materialized in the target lookup. Those copies do not acquire authority
from the JSON file that happens to deliver them.

The usage index may denormalize useful attributes for reports or the Info panel,
but it represents the last rebuild and is not the source of truth for an
unsaved active occurrence. A target field is not available merely because some
usage JSON contains a similarly named value.

For example, `files[]` remains canonical Work data. Showing a file, file count,
or selected download requires a declared `catalogue:work` lookup projection
whose adapter reads the Work record and supplies the agreed shape. A preview
image follows the same lookup path: `work_id` selects a Work lookup row or
focused result containing the declared preview projection. Neither the token nor
the usage index discovers the preview by traversing Work media fields.

## Field Authority

Each family/target-type definition must classify its fields before deciding
which values appear in source tokens, canonical JSON, generated lookup data, or
the Info panel:

| field class | authority | token storage | Info-panel behavior |
| --- | --- | --- | --- |
| identity | selected concrete target | required and immutable | read-only |
| occurrence | this use in this document | stored when set | editable when declared |
| canonical target | existing domain owner | never copied into the token | read-only projection |
| derived | resolver using identity, occurrence context, and canonical data | never stored as a full derived value | read-only projection |

The token-kind definition declares field names, types, source class, required
state, whether an occurrence field is editable, and which named target
projections may be displayed. It does not become the value owner for canonical
target fields.

### Work Example

For Work `00008`:

| field | class | treatment |
| --- | --- | --- |
| `work_id: "00008"` | identity | store in the token and never edit in the Info view |
| canonical title, `series_ids`, downloads, and media source/version fields | canonical target | remain behind the Studio Work projection adapter; the token does not inspect them |
| `series_id: "105"` used to open the Work within one Series | occurrence context | store only when that contextual destination is chosen; validate against canonical membership |
| `url` | derived projection | adapter resolves it from Work identity plus optional Series context |
| `media` | derived projection | adapter supplies the configured media representation |
| `file` | derived projection | adapter selects the configured canonical download representation; the token does not resolve `downloads[]` |
| displayed Title | occurrence | store in the token and allow editing |

The current `nerve` Work belongs to both Series `105` and `026`. That makes a
singular Series choice occurrence context, not a copied canonical Work field.
Changing that context may change the destination without changing Work identity.

### Tag Example

For a future Tag family:

| field | class | treatment |
| --- | --- | --- |
| `tag_id`, such as `domain:nerve` | identity | store in the token and keep immutable |
| group, label, and description | canonical target | remain with the Studio Tag owner and are exposed only when declared by the Tag projection |
| associated sub-scope `data_doc` | canonical target relationship if it is the same for every use | add to the canonical Tag owner or a focused canonical Tag-to-document mapping, then expose it through the Tag projection |
| displayed Title or usage-specific relation metadata | occurrence | store in the token and expose through the Tag Info view |
| detail URL | derived | resolve from the canonical document relationship and route contract |

If a new field describes the target everywhere, extend its canonical owner and
the token-kind lookup projection only when a consumer needs it. If it describes
only this document occurrence, extend the token-kind field schema and source
syntax. If it is computable, extend the projection adapter. Generated lookup and
usage JSON may denormalize values for use, but remains reproducible and
non-authoritative.

Adding an optional occurrence field should require only a declared field schema,
syntax/parser support, a supported Info-panel control type, and focused fixtures.
Complex fields or new canonical ownership still require a specific design; an
arbitrary JSON property must not silently become editable UI.

## Generated Lookup And Usage Data

Proposed locations:

```text
docs-viewer/data/generated/semantic-tokens/target-lookup.json
docs-viewer/scopes/<scope>/generated/semantic-tokens/index.json
docs-viewer/scopes/<scope>/generated/semantic-tokens/by-doc/<doc_id>.json
docs-viewer/scopes/<scope>/generated/semantic-tokens/by-target/<family>/<target-type>/<id>.json
```

Each lookup row includes family, target type, id, title, and the compact declared
projection needed for discovery or Info-panel context. That projection may
include a preview image. The Catalogue lookup combines Work, Series, and Moment
rows without exposing their raw canonical records.

Per-scope occurrence and relationship files form the derived **token usage
index**: what token occurrences are actually present in documents. This index is
reproducible local relationship data, not a registry, a canonical target store,
or published data. Each resolved row needs catalogue target type/id, occurrence
title, source document, and resolved target. Ignored token-like strings do not
enter this index.

## Broken-Link Audit And Repair

Extend the existing [Docs Broken
Links](/docs/?scope=studio&doc=d-20260423-165116-e7f7e9) audit and report rather
than creating a second Semantic Tokens report.

The semantic-token audit is an explicit, read-only management action. It scans
source Markdown with the accepted token parser because unresolved occurrences
are deliberately absent from the generated usage index. For each identifiable
token-like occurrence, it uses the token-definition registry and target lookup
to report at least:

- unsupported token kind;
- missing target identity;
- resolved target without a safe, workable destination.

A result includes source scope/document, raw token text, parsed
family/type/identity where available, failure reason, and enough source location
to return to the occurrence. Conservatively identifiable malformed syntax may
be included, but arbitrary bracketed prose must not be classified as a token.

Repair is user-controlled:

```text
run Docs Broken Links audit
    -> open owning document in source mode
    -> select broken occurrence where possible
    -> Remove token
    -> Add <family> token through the validated modal
    -> rebuild
    -> rerun audit
```

The audit never writes source, retargets an occurrence, blocks save/rebuild, or
adds broken occurrences to the usage index. An unavailable target can also
require repair in its canonical owner or projection adapter rather than a
source edit; the report exposes the reason without choosing that repair.

## Native, Generated, And Published

Apply the repository [Projection
Contract](/docs/?scope=studio&doc=d-20260523-222005-1085b2):

| role | semantic-token example | authority or purpose |
| --- | --- | --- |
| checked configuration | token-kind definitions | declares supported capability; not content |
| native or canonical source | Markdown token occurrences and canonical Work, Series, Moment, or Tag records | editable source of truth in the owning domain |
| built/generated working data | manage target lookup and usage index | reproducible enrichment, authoring, and resolved relationship input |
| published public projection | a future focused document or report payload | complete browser-safe input for one accepted public consumer |

**Generated** describes how an artifact is produced; **published** describes an
intended consumer. A public payload is therefore generated too, but it is not
the manage lookup or usage index copied into a public directory.

Any future public token surface performs its joins while building the public
projection:

```text
canonical document + resolvable token occurrences + canonical targets
    -> build-time token resolution and public filtering
    -> focused document or report payload
    -> public reader
```

The focused payload contains all display fields, destinations, preview
references, and related rows required by that document or report. The public
reader may fetch that payload, but it does not then consult the token-definition
registry, canonical source, manage target lookup, or manage usage index, and it
does not issue one metadata request per token. A target-focused report should,
for example, package its eligible document rows and the exact Catalogue context
needed to render them.

This deliberate denormalization is a publication contract, not a change of
authority. Public filtering, visibility, field allowlisting, payload ownership,
and rebuild triggers require a separate specification and delivery. The current
Catalogue delivery creates no public semantic-token projection.

## Ownership

| responsibility | owner |
| --- | --- |
| canonical Work, Series, Moment, and later target records | existing domain owners |
| supported family and target-type definitions | integrated Docs Viewer token-definition registry |
| manage-safe target lookup | focused generator and generated lookup |
| named target projections | code-owned adapter selected by each token-kind definition |
| token grammar | shared contract with Python and browser conformance fixtures |
| source selection and buffer mutation | generic source-editor adapter |
| family actions, modals, detection, and Info views | manage-only semantic-token feature |
| rebuild parsing and usage-index generation | Docs Viewer builder semantic-token owner |
| usage and reverse relationships | per-scope generated semantic-token data |
| broken-token diagnosis and source repair handoff | existing manage-only Docs Broken Links service and report |

Use **registry** only for token-definition configuration. Use **usage index** for
the generated inventory of occurrences in documents. Catalogue is one semantic
and UI family with Work, Series, and Moment token kinds. Their target records
remain with their current domain owners. Tag is a separate future family.

## Wiring

```text
Catalogue token-kind definitions + projection adapters
    -> combined Work/Series/Moment lookup
    -> Add catalogue token toolbar action
    -> discovery and required-data modal
    -> selected concrete target type + id
    -> catalogue token serialization
    -> source-editor range replacement
    -> current-buffer token parser
    -> Catalogue Info-panel view
    -> normal Rebuild doc
    -> builder parsing + generated usage index

source Markdown
    -> explicit Docs Broken Links audit
    -> semantic-token issue row
    -> source-editor repair workflow
```

Insertion, update, and removal change only the local source buffer. The normal
source-editor workflow remains the sole write and rebuild owner.

Target identity has one UI owner at each stage:

- before insertion, the family-specific modal owns target lookup and selection;
- after insertion, the parsed token owns identity and the Info view receives it
  as read-only context.

The Info panel does not reload the target picker to change an identity. This
keeps creation validation inside one modal transaction and prevents occurrence
editing from becoming an implicit re-targeting workflow. It may still perform a
read-only lookup for the existing identity to obtain declared preview or target
context.

## UI-Driven Refactoring Gate

CT-P1 resolved the creation pressures:

- the source adapter now exposes current-buffer revision, captured selection,
  and guarded captured-range replacement;
- generic main-view action and source-action-state contributions allow
  Catalogue to register its toolbar action without a family branch in the
  source-editor lifecycle;
- the pilot mixed-target result list is rehosted in the Catalogue add modal,
  and the fixed source-mode Info picker is retired.

P2 still needs:

- exact-range selection and guarded update/removal for a recognized current
  occurrence;
- contextual Info routing from ordinary source metadata to a family-specific
  occurrence view;
- the accepted parser and token-definition registry.

The remaining presentation and conformance constraints still apply:

- The native textarea can highlight one active token with
  `setSelectionRange`; persistent syntax decoration is not required for the
  first delivery.
- Python and browser parsers cannot share implementation code, so shared grammar
  fixtures must prove identical occurrence and boundary behavior.

If existing hosted-view or exact-range extension points cannot meet the P2
contracts cleanly, refactor the generic plumbing first within the Catalogue
delivery. Do not move token knowledge into core to avoid that refactor.

## Pilot Disposition

Reuse evidence from the shipped
[Semantic References Implementation](/docs/?scope=studio&doc=d-20260602-210246-394018):

- token parsing and rendering behavior;
- declarative kind normalization;
- generated title-weighted target lookup;
- target search and picker-list behavior, rehosted inside add modals;
- generated by-document and by-target relationships;
- the existing Docs Broken Links audit/report surface.

Do not preserve pilot structure merely because it exists:

- replace `semantic-references` names and schemas with the accepted
  semantic-token contract;
- retire the Info-panel search-and-insert view after its reusable mixed-target
  result behavior has moved into the Catalogue modal;
- move relationship output out of `published/documents/references/`;
- remove the unowned public reference copies and add no public replacement;
- migrate the active `3 symbols` Work occurrence into the Catalogue family;
- retire the pilot behavior that constructs a link from an unknown id using
  only a route template;
- retain Work, Series, and Moment as concrete Catalogue target types;
- require a separate later specification for the Tag family;
- add no compatibility paths or registry aliases.

## Boundaries

- No token-definition registry, family list, or token-specific view in generic
  core.
- No source-save or rebuild target-existence gate.
- No service endpoint solely for token lookup or editing.
- No public token-definition registry, manage usage index, token-resolution
  runtime, or report in this delivery.
- No automatic semantic wrapping of ordinary links, images, or files.
- No executable directives, generic graph, background crawler, or continuous
  reconciliation service.
