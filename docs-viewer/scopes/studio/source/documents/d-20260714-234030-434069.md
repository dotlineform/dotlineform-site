# Semantic Tokens Architecture

## Outcome

Semantic Tokens provide one manage-only Docs Viewer path from a registered token
family to source-editor authoring, current-buffer inspection, local rendering,
generated relationships, and a focused report.

The [Source Editor UI](/docs/?scope=studio&doc=d-20260623-180405-631ef4)
documents how an author searches, compares, selects, and locks a target. Token
syntax records that decision, the registry declares supported kinds and lookup
adapters, and generated data records resolvable targets and actual document
usage.

## Relationship Meaning

Each resolved occurrence records that a document mentions or relates to one exact semantic target in body content. It is not evidence that the document is about that target. Optional `folder_path`, `work_id`, or `series_id` front matter owns aboutness for Project State, curator coverage, and public Work/Series document metadata. Neither the usage index nor rendered links may be promoted into subject associations or `doc_url[]` without a separate explicit metadata-model decision.

[SSP-3 — Insert Subject Link Delivery](/docs/?scope=studio&doc=d-20260802-174340-2fe9f4) uses the existing Catalogue lookup and serializer to insert one Work or Series token from the current document subject and current target title. The result is an ordinary authored occurrence with the existing usage schema and no origin marker. It remains a mention snapshot: semantic resolution does not become the subject owner, later subject reassignment does not rewrite it, and no automatic relationship expansion is introduced.

## Token Syntax

Semantic Tokens use this deterministic source form:

```md
[[<family>:<target-type>:<canonical-id>|<escaped-title>]]
```

Catalogue examples are:

```md
[[catalogue:work:00638|3 symbols]]
[[catalogue:work:00008|nerve]]
[[catalogue:series:105|nerve]]
```

A Tag example is:

```md
[[tag:tag:nerve|Nerve]]
```

Family and target-type keys are lower-case identifiers matching
`[a-z][a-z0-9-]*`. A lexical id matches
`[A-Za-z0-9][A-Za-z0-9._-]*`; its accepted canonical form is then owned by the
target-type id policy. Catalogue Work uses five digits, while Catalogue Series and Tag use
lower-case alphanumeric-and-hyphen ids. The modal may normalize accepted
input, but serialization always records the canonical id.

Title is a required, single-line occurrence field. The modal trims its outer
whitespace before serialization and preserves its remaining Unicode text. The
serializer escapes backslash, pipe, and closing bracket as `\\`, `\|`, and
`\]`, in that order. The parser decodes only those three escapes; an unknown
escape, an empty Title, an invalid identity component, or an unterminated token
is malformed. Identity components are never escaped.

Serialization emits no optional whitespace around separators. Parsing returns
the raw token and a zero-based half-open `[start, end)` source range. Inline
code, fenced code, and HTML comments are inactive. A collapsed caret activates a
supported occurrence only when `start < caret < end`; a shared boundary between
adjacent tokens activates neither. Malformed and unsupported kinds never
activate a token.

The immutable identity is `(family, target type, target id)`. The author need not
choose the type before searching; selecting a result supplies it. The displayed
Title remains occurrence metadata and does not edit the canonical target.

The versioned shared contract fixture is
`docs-viewer/tests/fixtures/semantic_tokens_catalogue_v1.json`. Python and
browser implementations must consume its same raw strings, decoded fields,
ranges, inactive contexts, and caret expectations rather than maintaining
separate examples.

## Authoring Validation And Tolerant Build

The add-token modal is the only semantic validation owner. At confirmation it:

- requires a target selected from the current family lookup;
- normalizes and validates the concrete identity;
- validates required occurrence fields;
- serializes the accepted syntax deterministically.

This validates the new string being inserted, not the whole document. Markdown
source remains directly user-editable before or after insertion.

The builder is a tolerant projector, not a semantic validator. It may recognize
a syntactically plausible string and attempt to resolve its identity. It emits a
link and usage-index occurrence only when the configured target lookup returns a
safe, workable destination. Otherwise it:

- leaves the original source substring unchanged for ordinary Markdown
  rendering;
- emits no semantic link;
- emits no usage-index occurrence;
- does not warn or fail the document build.

This applies to malformed syntax, unsupported token kinds, missing identities,
and lookup results without a usable destination. Grammar recognition and
best-effort resolution are implementation steps, not validation outcomes. The
normal build records no broken-link result; the separate read-only audit owns
diagnosis.

## Token-Definition Registry

The checked-in registry is:

```text
docs-viewer/config/semantic-tokens/registry.json
```

It uses a schema-versioned envelope with one record per registered family. A
family and target-type pair forms one token-kind definition, such as
`catalogue:work`. The registry describes supported token kinds; it is not a
collection of tokens found in documents and it does not contain canonical
target records.

A family record currently defines:

- stable family key and author-facing labels;
- required and optional occurrence fields;
- occurrence fields the Info view may edit;
- add-action, modal, and Info-view contribution ids.

Each target type within the family defines:

- stable type key and author-facing result label;
- target-lookup adapter;
- immutable id normalization and validation policy;
- the named lookup fields it consumes.

The Catalogue family declares Work and Series and returns them in one result set without requiring a type choice before search. The separate Tag family declares one `tag` target type and its own Source action, modal, and Info view; aliases are discovery input only and never token identity.

The registry selects declared capabilities. Parser, normalizer, resolver, and UI
implementations remain code-owned; JSON must not become an executable plugin
framework.

## Configured Target Projection

An individual token resolves its identity through the generated target lookup.
It does not receive or interpret a canonical record:

```text
token occurrence: catalogue:work + 00008
    -> catalogue:work definition
    -> catalogue target-lookup row
    -> named title, href, and meta fields
    -> Add modal, Info view, builder, or Broken Links audit
```

The lookup generator owns canonical data access, identifier normalization, URL
construction, and selection of compact metadata. A token consumer sees only the
declared row; it never traverses arbitrary canonical JSON or arrays.

## Metadata Sources

Use **metadata** only with its source qualified. The current surfaces consume
values with different authority and freshness:

| qualified term | authority | current consumers |
| --- | --- | --- |
| token identity and occurrence fields | current Markdown source | source parser and family Info view |
| canonical target fields | Catalogue or another target owner | target-lookup generator only |
| target-lookup fields | generated row keyed by token identity | family Add modal and Info view, builder, and Broken Links |
| usage-index occurrence | last successful document build | Semantic Tokens report and targeted-build preservation |

Field authority and delivery source are separate questions. An occurrence field
may be repeated in the usage index, while a canonical or derived target field
may be materialized in the target lookup. Those copies do not acquire authority
from the JSON file that happens to deliver them.

Each family Info view parses identity and Title from the current buffer and reads only its declared destination context from the target lookup. It does not read the usage index. The report reads the usage index, not the target lookup.

## Field Authority

The current Catalogue fields have these authority boundaries:

| field class | authority | token storage | Info-panel behavior |
| --- | --- | --- | --- |
| identity | selected concrete target | required and immutable | read-only |
| occurrence | this use in this document | stored when set | editable when declared |
| canonical target | existing domain owner | never copied into the token | read-only projection |
| derived | lookup generator using canonical data | not stored in the token | read-only projection |

The token-kind definition declares occurrence fields, editable state, identity
policy, and named lookup fields. It does not become the value owner for
canonical target fields.

### Work Example

For Work `00008`:

| field | class | treatment |
| --- | --- | --- |
| `work_id: "00008"` | identity | store in the token and never edit in the Info view |
| canonical title, Series membership, downloads, and media fields | canonical target | remain with Catalogue; the token does not inspect them |
| displayed Title | occurrence | store in the token and allow editing |
| lookup title, `href`, and compact `meta` | derived projection | generate from canonical Catalogue data for read-only consumption |

New fields follow the same classification: target-wide values remain with their
canonical owner, occurrence-specific values extend token syntax, and computed
values enter the lookup only for a concrete consumer.

## Generated Lookup And Usage Data

Working locations:

```text
docs-viewer/data/generated/semantic-tokens/target-lookup.json
docs-viewer/scopes/<scope>/published/documents/semantic-tokens/index.json
```

Each lookup row includes family, target type, id, title, `href`, and compact
`meta`. Catalogue rows cover Work and Series. Tag rows carry one canonical `tag_id`, one selected-primary-or-first `href`, compact group/document-title context, and private aliases without exposing canonical Tag or document records.

The per-scope file is the derived **token usage index**: what resolved token
occurrences are actually present in documents. It is reproducible local manage
data, not a registry, canonical target store, or public projection. Each row
needs semantic family/type/id, occurrence title, source document, and resolved
target. Ignored token-like strings do not enter this index.

There are no per-document or per-target usage payloads. Targeted builds preserve
untouched occurrences by grouping the existing scope index by source document.
Any future document- or target-specific projection requires a concrete consumer.

The manage-only Semantic Tokens report reads the selected scope's usage index,
shows occurrence Title and concrete identity, and resolves its source document
against that scope's index tree to provide the managed document link.

## Broken-Link Audit And Repair

Keep failure diagnosis in the existing [Docs Broken
Links](/docs/?scope=studio&doc=d-20260423-165116-e7f7e9) audit and report. The
separate manage-only [Semantic Tokens
Report](/docs/?scope=studio&doc=d-20260726-181045-a7c2e1) is an inventory of
resolved usage-index occurrences; it does not diagnose unresolved source.

The semantic-token audit is an explicit, read-only management action. It scans
source Markdown with the accepted token parser because unresolved occurrences
are deliberately absent from the generated usage index. For each identifiable
token-like occurrence, it uses the token-definition registry and target lookup
to report at least:

- unsupported token kind;
- missing target identity;
- resolved target without a safe, workable destination.

For Tag occurrences, the audit additionally distinguishes an unknown canonical Tag, a known Tag with zero current document associations, and a selected-primary-or-first document without a workable public destination. A stale primary that falls back to a workable first current association is resolved, not broken.

A result includes source scope/document, raw token text, parsed
family/type/identity where available, failure reason, and enough source location
to return to the occurrence. Conservatively identifiable malformed syntax may
be included, but arbitrary bracketed prose must not be classified as a token.

Repair is user-controlled:

```text
run Docs Broken Links audit
    -> open owning document in source mode
    -> locate the reported occurrence
    -> Remove token
    -> Add <family> token through the validated modal
    -> rebuild
    -> rerun audit
```

The audit never writes source, retargets an occurrence, blocks save/rebuild, or
adds broken occurrences to the usage index. An unavailable target can also
require repair in its canonical owner or projection adapter rather than a
source edit; the report exposes the reason without choosing that repair.

## Native, Generated, And Published

Apply the repository [Projection
Contract](/docs/?scope=studio&doc=d-20260523-222005-1085b2):

| role | semantic-token example | authority or purpose |
| --- | --- | --- |
| checked configuration | token-kind definitions | declares supported capability; not content |
| native or canonical source | Markdown token occurrences, canonical Work/Series records, canonical Tags, and document-owned Tag declarations | editable source of truth in the owning domain |
| built/generated working data | manage target lookup and usage index | reproducible enrichment, authoring, and resolved relationship input |
| published public projection | resolved ordinary anchors in eligible document payloads | browser-safe rendered content with no public token-data dependency |

**Generated** describes how an artifact is produced; **published** describes an
intended consumer. A public payload is therefore generated too, but it is not
the manage lookup or usage index copied into a public directory.

Public document projection resolves supported tokens during the ordinary build:

```text
canonical document + resolvable token occurrences + focused target lookup
    -> build-time token resolution
    -> ordinary document HTML anchor
    -> public reader
```

The anchor may retain inert `data-semantic-token-*` attributes, but the public
reader does not consult the token-definition registry, canonical source, manage
target lookup, or local usage index. The usage index remains local generated
data and the publish gate omits its directory.

## Ownership

| responsibility | owner |
| --- | --- |
| canonical Work and Series records | Catalogue |
| canonical Tag identity, group, aliases, and optional primary override | Tag Registry |
| Tag association membership and order | Analysis Tag document declarations and private association projection |
| supported family and target-type definitions | integrated Docs Viewer token-definition registry |
| manage-safe target lookup | focused generator and generated lookup |
| named target projections | code-owned adapter selected by each token-kind definition |
| token grammar | shared contract with Python and browser conformance fixtures |
| source selection and buffer mutation | generic source-editor adapter |
| family actions, modals, detection, and Info views | manage-only semantic-token feature |
| rebuild parsing and usage-index generation | Docs Viewer builder semantic-token owner |
| resolved usage occurrences | per-scope generated semantic-token index |
| resolved-token inventory and owning-document links | manage-only Semantic Tokens report |
| broken-token diagnosis and source repair handoff | existing manage-only Docs Broken Links service and report |

Use **registry** only for token-definition configuration. Use **usage index** for the generated inventory of occurrences in documents. Catalogue and Tag are separate semantic and UI families. Their target records remain with Catalogue, Tag Registry, and Analysis Tag documents; the semantic registry does not acquire canonical-data authority.

## Wiring

```text
Catalogue token-kind definitions + projection adapters
    -> combined Work/Series lookup
    -> Add catalogue token toolbar action
    -> discovery and required-data modal
    -> selected concrete target type + id
    -> catalogue token serialization
    -> source-editor range replacement
    -> current-buffer token parser
    -> Catalogue Info-panel view

Tag token-kind definition + exact primary-or-first projection adapter
    -> canonical-ID and alias Tag lookup
    -> Add tag token toolbar action
    -> separate Tag discovery and required Title
    -> canonical tag identity serialization
    -> guarded source-editor range replacement
    -> current-buffer Tag parser
    -> Tag Info-panel view

Catalogue or Tag authored source
    -> normal Rebuild doc
    -> builder parsing + generated usage index
    -> manage-only Semantic Tokens report

source Markdown
    -> explicit Docs Broken Links audit
    -> semantic-token issue row
    -> source-editor repair workflow
```

Insertion, update, and removal change only the local source buffer. The normal
source-editor workflow remains the sole write and rebuild owner.

Target identity has one UI owner at each stage:

- before insertion, the family-specific modal owns target lookup and selection;
- after insertion, the parsed token owns identity and the Info view receives it
  as read-only context.

The Info panel does not reload the target picker to change an identity. This
keeps creation validation inside one modal transaction and prevents occurrence
editing from becoming an implicit re-targeting workflow. It performs only a
read-only lookup for the existing identity's title and destination context.

## Current Extension Seams

- the source adapter exposes current-buffer revision, captured selection,
  and guarded captured-range replacement;
- generic main-view action and source-action-state contributions allow Catalogue and Tag to register separate toolbar actions without a family branch in the source-editor lifecycle;
- contextual Info routing switches between ordinary metadata and the matching Catalogue or Tag token view;
- exact-range guarded update and removal stay in the generic source adapter;
- the native textarea highlights one active token with `setSelectionRange`;
- Python and browser parsers cannot share implementation code, so shared grammar
  fixtures prove identical occurrence and boundary behavior.

These seams remain generic. Token-family knowledge stays in the manage-only
Semantic Tokens modules rather than moving into source-editor core.

## Boundaries

- No token-definition registry, family list, or token-specific view in generic
  core.
- No source-save or rebuild target-existence gate.
- No service endpoint solely for token lookup or editing.
- No public token-definition registry, manage usage index, token-resolution
  runtime, or report.
- No automatic semantic wrapping of ordinary links, images, or files.
- No executable directives, generic graph, background crawler, or continuous
  reconciliation service.
