# Single-HTML Snapshot: Document Tree vs Internal Heading Hierarchy

## Purpose

When multiple HTML documents are compiled into a single snapshot file, there are two different hierarchies that must not be confused:

1. the **document collection hierarchy** — where a document sits in the Docs Viewer tree;
2. the **internal document hierarchy** — the document's own `h1`, `h2`, `h3`, and other headings.

Trying to represent both with the same HTML heading levels quickly breaks down.

---

## The problem

Suppose the Docs Viewer tree contains four levels:

```text
Architecture                    depth 1
└── Data Models                 depth 2
    └── Catalogue Model         depth 3
        └── Detailed Notes      depth 4
```

Each source document may independently contain normal headings such as:

```html
<h1>Document title</h1>
<h2>Section</h2>
<h3>Subsection</h3>
```

If tree depth is converted directly into HTML heading depth, a depth-4 document would need something like:

```html
<h4>Detailed Notes</h4>
<h5>Section</h5>
<h6>Subsection</h6>
```

and any additional nested heading would require an invalid `h7`.

Even before reaching that limit, the document's internal structure has been distorted merely because of where it happens to sit in the collection tree.

The two hierarchies should therefore remain separate.

---

## Recommended model

Use different HTML structures for the two kinds of hierarchy.

```text
DOCUMENT COLLECTION HIERARCHY
Architecture
└── Data Models
    └── Catalogue Model

represented by:
    nested <nav>/<ul>
    document wrapper metadata
    optional data-depth attributes


INTERNAL DOCUMENT HIERARCHY
Document title
├── Section
└── Subsection

represented by:
    <h1>
    <h2>
    <h3>
```

A document at collection depth 4 can therefore still contain completely normal document headings.

---

## Collection hierarchy: navigation tree

The collection hierarchy can be represented by a nested table of contents:

```html
<nav class="snapshot-toc">
  <ul>
    <li>
      <a href="#d-architecture">Architecture</a>

      <ul>
        <li>
          <a href="#d-data-models">Data Models</a>

          <ul>
            <li>
              <a href="#d-catalogue-model">Catalogue Model</a>

              <ul>
                <li>
                  <a href="#d-detailed-notes">Detailed Notes</a>
                </li>
              </ul>
            </li>
          </ul>
        </li>
      </ul>
    </li>
  </ul>
</nav>
```

The nested lists preserve the Docs Viewer tree without consuming HTML heading levels.

---

## Document wrappers

Each compiled source document can be wrapped in its own section:

```html
<main>

  <section
    class="snapshot-document"
    id="d-architecture"
    data-tree-depth="1"
  >
    ...
  </section>

  <section
    class="snapshot-document"
    id="d-data-models"
    data-tree-depth="2"
  >
    ...
  </section>

  <section
    class="snapshot-document"
    id="d-catalogue-model"
    data-tree-depth="3"
  >
    ...
  </section>

  <section
    class="snapshot-document"
    id="d-detailed-notes"
    data-tree-depth="4"
  >
    ...
  </section>

</main>
```

`data-tree-depth` is optional, but it can be useful for styling, diagnostics, or displaying collection depth without changing semantic heading levels.

For example:

```css
.snapshot-document[data-tree-depth="2"] {
    /* optional presentation only */
}
```

The collection depth remains metadata rather than document semantics.

---

## Internal headings remain unchanged

A source document can keep its own structure:

```html
<section
  class="snapshot-document"
  id="d-detailed-notes"
  data-tree-depth="4"
>
  <h1>Detailed Notes</h1>

  <p>Introduction...</p>

  <h2>Background</h2>

  <p>...</p>

  <h3>Data relationships</h3>

  <p>...</p>

  <h2>Implementation</h2>

  <p>...</p>
</section>
```

Although this document is at collection depth 4, its title remains `h1`.

Its internal sections remain `h2` and `h3`.

This preserves the semantics of the original document.

---

## Why not shift heading levels?

A tempting transformation is:

```text
collection depth 1
    document h1 → h1
    document h2 → h2

collection depth 2
    document h1 → h2
    document h2 → h3

collection depth 3
    document h1 → h3
    document h2 → h4

collection depth 4
    document h1 → h4
    document h2 → h5
```

This should be avoided.

Problems include:

- documents deeper in the tree acquire weaker heading semantics;
- internal hierarchy becomes dependent on collection placement;
- heading depth can exceed `h6`;
- moving a document in the tree would unnecessarily alter all its headings;
- accessibility and document-outline semantics become harder to reason about;
- the collection hierarchy and document hierarchy become artificially coupled.

The source document should remain a document in its own right.

---

## Two independent structures

The compiled HTML therefore has two independent structures.

### 1. Global navigation

```html
<nav class="snapshot-toc">
  ...
</nav>
```

This answers:

> Where is this document in the collection?

### 2. Local document structure

```html
<section class="snapshot-document">
  <h1>Document title</h1>
  <h2>Section</h2>
  <h3>Subsection</h3>
</section>
```

This answers:

> How is this document internally organised?

These are different questions and should have different representations.

---

## Duplicate IDs become important

Separate HTML documents can safely contain the same fragment IDs.

For example:

```text
architecture.html
    #overview
    #testing

data-models.html
    #overview
    #testing
```

Once the documents are merged into one HTML file, those IDs collide:

```html
<h2 id="overview">Overview</h2>
...
<h2 id="overview">Overview</h2>
```

IDs must be unique within the combined document.

The compiler therefore needs to namespace local IDs.

---

## Namespaced internal anchors

A simple convention is:

```text
<document-id>--<original-id>
```

For example:

```text
source document:
d-20260802-123451-d0e52e

source fragment:
#overview

combined fragment:
#d-20260802-123451-d0e52e--overview
```

The compiled heading becomes:

```html
<h2 id="d-20260802-123451-d0e52e--overview">
  Overview
</h2>
```

Another document can safely contain:

```html
<h2 id="d-20260720-161657-0f6696--overview">
  Overview
</h2>
```

The fragment names no longer collide.

---

## Rewriting links within the same document

Suppose the original document contains:

```html
<a href="#testing">Testing</a>
```

If the containing document is:

```text
d-20260802-123451-d0e52e
```

the compiler rewrites the link to:

```html
<a href="#d-20260802-123451-d0e52e--testing">
  Testing
</a>
```

The destination heading is rewritten in the same way:

```html
<h2 id="d-20260802-123451-d0e52e--testing">
  Testing
</h2>
```

---

## Rewriting links to another document

Suppose one source document links to another:

```html
<a href="d-20260720-161657-0f6696.html">
  Site Overview
</a>
```

In the single-file snapshot, it becomes:

```html
<a href="#d-20260720-161657-0f6696">
  Site Overview
</a>
```

The target document wrapper provides the destination:

```html
<section
  class="snapshot-document"
  id="d-20260720-161657-0f6696"
>
  <h1>Site Overview</h1>
  ...
</section>
```

---

## Rewriting links to a section in another document

An original cross-document fragment link might be:

```html
<a href="d-20260720-161657-0f6696.html#architecture">
  Site architecture
</a>
```

The compiler can translate that to:

```html
<a href="#d-20260720-161657-0f6696--architecture">
  Site architecture
</a>
```

The destination is:

```html
<h2 id="d-20260720-161657-0f6696--architecture">
  Architecture
</h2>
```

This gives a simple deterministic mapping:

```text
document.html
    → #document-id

document.html#fragment
    → #document-id--fragment

#fragment within current document
    → #current-document-id--fragment
```

---

## Example combined snapshot

A simplified compiled result could therefore look like:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <title>Studio Docs Snapshot</title>
</head>

<body>

  <nav class="snapshot-toc">
    <ul>
      <li>
        <a href="#d-architecture">Architecture</a>

        <ul>
          <li>
            <a href="#d-data-models">Data Models</a>

            <ul>
              <li>
                <a href="#d-catalogue-model">Catalogue Model</a>
              </li>
            </ul>
          </li>
        </ul>
      </li>
    </ul>
  </nav>


  <main>

    <section
      class="snapshot-document"
      id="d-architecture"
      data-tree-depth="1"
    >
      <h1>Architecture</h1>

      <h2 id="d-architecture--overview">
        Overview
      </h2>

      <p>...</p>
    </section>


    <section
      class="snapshot-document"
      id="d-data-models"
      data-tree-depth="2"
    >
      <h1>Data Models</h1>

      <h2 id="d-data-models--purpose">
        Purpose
      </h2>

      <p>...</p>

      <h3 id="d-data-models--relationships">
        Relationships
      </h3>

      <p>...</p>
    </section>


    <section
      class="snapshot-document"
      id="d-catalogue-model"
      data-tree-depth="3"
    >
      <h1>Catalogue Model</h1>

      <p>
        See
        <a href="#d-data-models--relationships">
          Data Models — Relationships
        </a>.
      </p>

      <h2 id="d-catalogue-model--overview">
        Overview
      </h2>

      <p>...</p>
    </section>

  </main>

</body>
</html>
```

The important properties are:

```text
collection hierarchy
    preserved in <nav>

document identity
    preserved in section IDs

internal headings
    remain h1/h2/h3 as authored

fragment IDs
    namespaced by document ID

cross-document links
    converted into internal fragment links
```

---

## What the compiler actually needs to do

The single-HTML compiler therefore has a relatively small set of structural responsibilities:

```text
1. Read the existing document tree.

2. Generate the nested navigation tree.

3. Read each source HTML document.

4. Extract its document content.

5. Wrap it in a uniquely identified <section>.

6. Preserve its internal h1/h2/h3 hierarchy.

7. Namespace every local id.

8. Rewrite local and cross-document links.

9. Combine all sections into one HTML file.
```

Assets and styling are separate concerns.

The heading problem itself does not require flattening or restructuring the documents.

---

## Recommended rule

The central rule is:

> Never use collection depth to rewrite the semantic heading levels inside a document.

Instead:

```text
collection hierarchy
    → navigation tree + document metadata

internal document hierarchy
    → headings
```

This makes the compiled snapshot structurally predictable even when the Docs Viewer tree has several levels and individual documents also have several levels of internal headings.
