# Run Checks

## Role

`tests/run_checks.py` coordinates optional repo check profiles and writes one local evidence snapshot under `var/test-runs/`.

It is not a mandatory gate. Use a focused command when one owner changed; use a profile when several checks form useful evidence for one blast radius.

## Commands

```bash
$HOME/miniconda3/bin/python3 tests/run_checks.py --list
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile quick
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile quick --profile catalogue
```

`--list` and the profile definitions in code are the exact current command inventory.

## Repository Source Lint

`tooling/lint/` owns the pinned repository lint tools, rules, lockfile, and
maintained boundaries. Install its isolated tool environments with:

```bash
$HOME/miniconda3/bin/python3 -m venv tooling/lint/.venv
tooling/lint/.venv/bin/python -m pip install -r tooling/lint/python-requirements.txt
npm ci --prefix tooling/lint
```

Use explicit paths for new or materially changed source:

```bash
bin/lint-python <path> [path ...]
bin/lint-js <path> [path ...]
```

Use the checked maintained boundary for an application-wide claim:

```bash
bin/lint --list
bin/lint --scope studio
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile source-lint
```

Explicit commands fail without eligible targets. Scope commands resolve
`tooling/lint/targets.json`; Ruff and ESLint rules remain in that package.
Command output reports language, file count, and maintained roots. Processing,
generated/vendor source, dependency trees, caches, canonical data, and retired
source remain outside the Python/JavaScript coverage claim.

## Profile Intent

- `quick` — cheap repo/config/projection/readiness/Python confidence.
- `studio` — complete Studio deterministic Python coverage plus Studio source lint.
- `catalogue` — catalogue Python contracts plus representative build preview.
- `docs` — Docs Viewer/Data Sharing Python contracts plus Studio docs/search generation.
- `source-lint` — all six adopted maintained Python/JavaScript boundaries.
- `docs-viewer-smoke`, `studio-smoke` —
  app-owned browser/runtime boundaries.
- `full` — the broad configured aggregate, including `source-lint`; inspect
  `--list` because it does not imply every app smoke or Processing coverage.

Do not mirror every child command here; that list changes with code.

## Outputs

Each run writes:

- `var/test-runs/<run-id>/summary.md`
- `var/test-runs/<run-id>/summary.json`
- one log per command

Closeout should report profile, pass/fail, and the Markdown summary path.

## Extension Method

- add a command only when it proves a durable contract;
- assign it to the app/profile that owns the behavior;
- add a source root to `tooling/lint/targets.json` only after its runtime
  context, exclusions, findings, and complete clean boundary are reviewed;
- require a maintained target boundary before promoting a lint check into a normal profile; a fixed specimen or toolchain smoke is not app-wide evidence;
- keep expensive/niche checks focused unless routine grouped confidence is valuable;
- do not add UI choreography merely because a browser harness exists;
- keep `source-lint`, app-profile placement, and `full` composition intentional
  and visible in `--list`.
