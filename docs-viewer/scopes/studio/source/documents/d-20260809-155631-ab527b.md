# CII-1 — Catalogue Image Source Insertion Delivery

## Status

CII-1 is complete. **🏞️ Add Catalogue image** now supports exact Work primary, optional Work Detail, and Series primary images through ordinary save/rebuild, exact activation, semantic usage, and fail-closed Broken Links behavior. The completed delivery remains parked under the [Roadmap](/docs/?scope=studio&doc=d-20260428-000000-f5ff18) pending explicit retirement approval.

## Complete Result

The Docs source editor adds **Add Catalogue image** beside **Add image** and **Add catalogue token**. An author searches the existing mixed Catalogue target set, selects an exact published Work or Series, applies the current image presentation options, and inserts one semantic Catalogue image occurrence into the source buffer.

After the ordinary source save and rebuild, the occurrence displays the target's current Catalogue image. Clicking the image opens the exact Catalogue destination: a Work primary image opens that Work, while a Series image opens that Series even though its displayed image comes from the Series' primary Work. CII-1.4 extends a selected Work with an optional Work Detail ID whose exact detail image opens its Work Detail page while semantic identity remains the Work.

This is one source-authoring and rendering workflow. CII-1.0 selected rebuild-time resolution because canonical source should retain semantic identity and authored presentation rather than a detached image URL. The ordinary save and rebuild remains the only author-facing flow; there is no separate mode, phase, or concurrency requirement.

## Accepted Contract

### Identity, Image, And Destination

The source occurrence preserves three distinct meanings:

- semantic identity is the selected Catalogue family, target type, and canonical target id;
- primary image presentation is resolved from the exact target lookup row, while optional Work Detail image presentation is resolved exactly during rebuild; and
- activation uses the selected target's exact Catalogue destination unless an authored Work Detail ID selects that exact Work Detail page.

For a Work without `detail_id`, the image projection comes from that Work's current primary Catalogue image and the destination remains the Work page. For a Work with `detail_id`, CII-1.4 preserves Work identity while resolving the exact Work Detail image and destination during rebuild.

For a Series, the image projection comes from the Work identified by the Series' exact `primary_work_id`, while semantic identity and destination remain the Series. The image source must not retarget the occurrence to the primary Work.

Only current published lookup targets are selectable. Missing image data, a missing or invalid Series `primary_work_id`, a primary Work that is not a current Series member, or an unusable destination fails closed. The workflow does not fall back to the first member, infer identity from title or route, or choose another image.

### Source And Rendering

The new occurrence belongs to the existing Catalogue semantic family but has an explicit image presentation. Existing text Catalogue tokens keep their current grammar and rendering.

Canonical source stores the exact target identity and authored presentation values rather than copying Catalogue media into the Docs scope. Rebuild resolves primary images and destinations through the existing generated target lookup; an optional Work `detail_id` is instead resolved against that Work's exact canonical detail file during rebuild. The builder emits a linked image or linked semantic figure.

The lookup remains the focused Work/Series projection shared by authoring and primary-image rendering. Its allowlisted image projection and optional one-bit Work Detail availability capability must not expose canonical records, detail collections, filesystem paths, provider credentials, or unrelated media metadata.

The occurrence contributes the same exact Catalogue identity to semantic usage and broken-link behavior as a text occurrence. Image presentation does not create a second relationship family or usage index.

### Authoring Surface

**Add Catalogue image** reuses the current mixed Work and Series search, result identity, keyboard navigation, and exact selection contract from **Add catalogue token**.

Its toolbar glyph is **🏞️**, with **Add Catalogue image** retained as the visible tooltip and accessible label.

After target selection it provides the current **Add image** presentation values:

- required alt text;
- optional caption;
- optional summary when a caption is present;
- full-column, image-left, or image-right placement; and
- fill available width or natural width.

Target selection may suggest the current Catalogue title for alt text and caption, but those values are authored occurrence snapshots. A later Catalogue title change does not rewrite source text automatically.

Confirmation inserts at the captured source selection, returns focus, and uses the normal dirty state. It does not save or rebuild independently, publish media, or mutate Catalogue data.

Placing the caret inside an image occurrence opens the Catalogue Info view with immutable target identity and editable presentation fields. Update and Remove retain the existing exact-range stale guard; changing the Work or Series target remains Remove followed by **Add Catalogue image**.

### Frozen Source Form

Existing text occurrences remain byte-compatible:

```text
[[catalogue:work:00638|3 symbols]]
```

An image occurrence adds an explicit `image` presentation segment and one canonical RFC 3986 percent-encoded field string:

```text
[[catalogue:image:work:00638|alt=3%20symbols]]
[[catalogue:image:series:005|alt=3%20symbols&caption=3%20symbols&summary=intangible%0Ashifting%20boundaries&placement=left&fill_width=true]]
```

The identity is `catalogue:image:<target type>:<canonical target id>`. Fields serialize once in the order `alt`, optional `caption`, optional `summary`, `placement`, and `fill_width`. `alt` is always required. Caption absence produces a linked plain image; caption presence requires `placement` and explicit boolean `fill_width`, while `summary` remains optional. Text normalization, allowed placement values, and HTML escaping reuse the current staged-image presentation contract.

The parser rejects unknown, duplicate, empty, non-canonical, or contradictory fields. It recognizes the complete occurrence as one exact source range outside fenced code, inline code, and HTML comments. Existing three-part text parsing and serialization do not reinterpret the four-part form.

The visual occurrence's usage-index `title` is its caption when present and otherwise its alt text. The current usage-index row shape remains sufficient because relationship identity, source range, raw source, title, and destination are unchanged; image presentation does not enter the relationship schema.

### Frozen Lookup And Rendering Contract

The existing generated file cuts over in place to `docs_semantic_token_target_lookup_v2`; there is no v1 reader, compatibility writer, second lookup, or fallback. Every current published target keeps its existing identity, title, `href`, and metadata. An optional `image` object adds only one browser-safe `src`.

Work `image.src` is the public 1600-pixel primary WebP URL assembled from `site-tools/config/site-tools.json`, `_data/pipeline.json`, the canonical Work id, and positive `media_version`, including the existing `?v=<media_version>` cache version. A Work row without complete published media remains a valid text target but has no image projection.

Series `image.src` is copied from the exact canonical Work named by `primary_work_id` only when that Work exists, is published, belongs to the Series through `series_ids`, and has a valid Work image projection. The Series row retains its Series identity and `/series/?series=<id>` destination. Missing or invalid image data never removes an otherwise valid text target and never falls back to another member.

The image picker lists only rows with a valid image projection. A visual source occurrence whose target later loses its image remains source text, emits no resolved usage, and appears in Docs Broken Links as `missing_image`; text occurrences for the same target continue to resolve normally.

Rendering emits one escaped semantic anchor with the existing target identity data attributes, `_blank`/`noopener noreferrer`, and either a plain image or the current `docsViewerFigure` classes. Manage rebases that anchor through the existing public-preview link mount; public Docs use the same root-relative Catalogue destination. A focused linked-image wrapper extends the current figure selectors for width, natural-width, left/right placement, mobile stacking, and keyboard focus without redesigning the layout.

The source occurrence is not rewritten when the target image, title, or Series primary Work changes. A later target-lookup refresh plus ordinary Docs rebuild updates rendered image and destination projection; CII-1 adds no background rebuild or synchronization owner.

## CII-1.4 Extension Contract

After an author selects a Catalogue target, **Add Catalogue image** exposes **Work Detail ID** immediately after Search Catalogue. The field is optional. It is enabled only for a selected Work whose canonical `work_details/<work_id>.json` file exists, and is disabled and cleared before selection, for a Series, or for a Work without that file.

The field accepts a positive digit-only padded or unpadded value such as `001` or `1` and serializes the canonical value as `001`. The source occurrence remains a Catalogue Work occurrence and carries optional `detail_id`; Work Detail does not become another semantic target type.

The target lookup must not contain Work Detail rows, ids, titles, or image projections. It may add only one compact Work capability flag such as `has_details` so the authoring field can be enabled without loading canonical data into the browser. Exact detail existence and image validation happen during the ordinary Docs rebuild.

With no `detail_id`, current Work primary-image behavior remains unchanged. With `detail_id`, the builder resolves only the exact `<work_id>-<detail_id>` record from that Work's canonical detail file, emits its public Work Detail image, and activates `/work-details/?detail=<detail_uid>&from_work=<work_id>`. Semantic identity and usage remain the selected Work. A missing file, missing detail, or unusable detail image remains literal source and must not fall back to the Work primary image.
