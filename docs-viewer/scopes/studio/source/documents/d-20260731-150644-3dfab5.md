# Sub-Scope Report Defaults And Customisations

## Purpose

Make `docs_subscope` useful for every configured one-level document collection
without making Analysis/Tags the implicit definition of that report.

The feature establishes:

- one documented default report that works without collection-specific config;
- one isolated `studio/default` reference collection on which that report is
  developed before it becomes canonical;
- one standard way for a configured sub-scope to add its own presentation and
  actions through a registered customisation module;
- Analysis/Tags as the first refactored consumer of that framework;
- automatic creation of a default report host and empty manifests from the
  **New sub-scope** lifecycle; and
- a later decision about what, if anything, the `dotlineform/projects`
  collection needs beyond the default.

Sub-scope child documents remain outside the parent Index, Recently Edited,
and global search. The parent report document is the normal indexed entry that
makes the collection reachable.

## Delivery Order

| order | delivery | complete outcome |
| --- | --- | --- |
| 1 | Default Report And Analysis Tags Refactor | An isolated Studio candidate proves the default, the candidate becomes canonical, and Analysis/Tags uses it without a hidden Tags path. |
| 2 | New Sub-Scope Default Report Lifecycle | A newly created sub-scope immediately has one indexed host, valid empty projections, and the default report. |
| 3 | Dotlineform Projects Report Customisation Decision | Real Projects content and workflow evidence decides whether the default is enough or a separate Projects customisation delivery is needed. |

The deliveries are sequential. Lifecycle work must consume the accepted
default rather than inventing a second scaffold, and Projects must be assessed
after the default can be exercised through the real lifecycle.

SSR-1 is delivered. SSR-2 is active with SSR-2.2 exact returned-host landing
delivered, stopped at review before SSR-2.3 external-local acceptance. SSR-3
has not started.

## Reference Collection

SSR-1 creates `studio/default` as an ordinary configured sub-scope with no
customisation identity. One report-host document beneath this feature exposes
it for development and review.

The host and Analysis/Tags now load the same canonical `docs_subscope`. The
reference collection uses the normal builder and generated
`manifest.json`/`manage-manifest.json`; `default` is not a magic runtime
selector or report type. The temporary development candidate and its loader,
registry entry, and dispatch have been removed.

## Current State

`docs_subscope` owns shared collection validation, title search,
title-ascending initial order, list/detail rendering, empty/error states,
validated by-ID loading, and `subdoc` navigation. Manage composes the standard
sort, row, New, selection, Prepare Package, Copy Link, Delete, and Import
context behavior without collection-specific config.

Analysis/Tags selects the registered Manage-only `analysis_tags`
customisation. Its ordered group projection and controls are namespaced and
module-owned; public Concepts remains the default reader with title search and
no group data or controls.

The **New sub-scope** service lifecycle now creates one exact associated parent
report host, valid empty local manifests, and targeted parent docs/search plus
browser-config projections. After the existing result closes, Manage reloads
configuration and the parent index, then opens only the returned host `doc_id`;
it adds no lifecycle-specific modal or report UI. Real external-local workflow
proof remains the next delivery checkpoint.

## Feature Boundary

In scope:

- `docs_subscope` only, not a generic plugin framework for every report type;
- a small default suitable for an ordinary flat document collection;
- known configuration identities resolved through a controlled module
  registry, never arbitrary module paths;
- explicit public-safe and Manage-only contribution boundaries;
- exact collection, selection, and validated-document action targets;
- lifecycle creation and deletion consequences for the report host; and
- a separate evidence-led Projects decision.

Not in scope:

- adding child documents to parent discovery payloads;
- nested or recursive sub-scopes;
- Tag Registry behaviour or document/tag synchronisation;
- automatically copying Analysis/Tags fields or controls into new
  collections;
- manifest-declared executable actions;
- automatic public promotion; or
- guessing Projects filters, metadata, or actions before its real collection
  is available for review.

The [Sub-Scope Index](/docs/?scope=studio&doc=d-20260728-113139-285eae)
remains the shipped collection-index feature. This feature standardises its
default and extension model and connects that model to lifecycle creation.
