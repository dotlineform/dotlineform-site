## Frozen Configuration Split

`docs_scopes_v4` should express one global external workspace, one provider-free managed contract per scope, and optional public media projections. Unchanged document, search, route, and sub-scope fields are omitted from this schematic.

```json
{
  "schema_version": "docs_scopes_v4",
  "media_workspace": {
    "location": {
      "provider": "external_local",
      "path": "$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media"
    }
  },
  "scopes": [
    {
      "scope_id": "analysis",
      "source": {},
      "media": {
        "types": {
          "img": {"build_inputs": []},
          "svg": {"build_inputs": ["mermaid"]},
          "files": {"build_inputs": []},
          "html": {"build_inputs": []}
        },
        "build_sources": {
          "mermaid": {"producer": "mermaid", "publishes_to": "svg"}
        }
      },
      "public_projection": {
        "documents": {"location": {"provider": "repository", "path": "site/assets/data/docs/scopes/analysis"}},
        "search": {"location": {"provider": "repository", "path": "site/assets/data/search/analysis/index.json"}},
        "media": {
          "img": {"location": {"provider": "repository", "path": "site/assets/data/docs/scopes/analysis/media/img"}, "served_path_prefix": "/assets/data/docs/scopes/analysis/media/img"}
        }
      }
    }
  ]
}
```

The scope ID and registered type derive the managed location `<workspace>/<scope>/<type>`, logical reference `docs/<scope>/<type>`, and Manage prefix `/docs/media/<scope>/<type>`. A registered build-source type derives `<workspace>/<scope>/build-source/<type>`. Evidence derives `<workspace>/<scope>/media-source-evidence.json`. These paths and prefixes are invariants, not repeated provider choices.

For a public scope, `public_projection.media` must contain the same type keys as `media.types`; each record owns one `repository` target beneath the exact tracked `site/.../<scope>/media/<type>` path or one R2 target at `docs/<scope>/<type>`, plus its public served prefix. A local scope keeps `public_projection: null`. The loader rejects the v3 `published.media`, `source.build_media`, managed `location`, and combined managed/public served-prefix fields after the cutover; there is no alias, old-schema reader, fallback, or dual write.

## Manage And Public Rendering Seam

- Main-scope and sub-scope working payloads render every same-scope logical token to the derived Manage prefix. The builder does not require the managed byte to exist and does not use a public target as a read fallback.
- The generated Manage browser config publishes Manage prefixes. The generated public browser config publishes the corresponding `public_projection.media` prefixes; no physical path is browser-visible.
- Publish already computes the exact prospective parent and sub-scope payload files after publishability and report/Mermaid projection. EMW-1.2 should reuse that set, inspect real HTML `src` and `href` attributes under exact Manage prefixes, union `{type, identity}`, and rewrite those attributes to the configured public prefixes. Fenced examples, code text, comments, foreign-scope URLs, and arbitrary prose are not references.
- The current `docs_media_inventory.py` source regex is not sufficient for Publish: it scans only parent source in its top-level helper, counts literal/commented examples, and the R2 adapter currently rejects a prefix marker. The existing inventory boundary should be corrected to consume exact parent/sub-scope payloads and marker-safe adapters rather than adding a second registry.
- `html-media` keeps the existing sandboxed iframe. Manage adds exact `/docs/media/<scope>/html/<filename>.html` serving from the external workspace with `text/html`, `no-store`, `nosniff`, and a response CSP matching the existing review-asset sandbox boundary; ordinary file downloads remain attachments. Public HTML continues to use the frozen public target and iframe sandbox.
- Publish projects public URLs even when the managed object is missing. It copies and byte-verifies each available referenced object independently, retains an existing public object while its identity remains referenced, and deletes only public identities absent from the complete prospective reference set. Media absence or copy failure is reported but does not roll back or block document/search publication.
- Document Delete and unpublish do not delete managed bytes. Scope-wide Publish owns shared public-media reconciliation; explicit whole-scope lifecycle remains the only scope-level deletion boundary.

## Superseded Migration Plan

This was the pre-approval migration proposal. It was not executed. The user explicitly selected a direct manual move/copy with counts-only acceptance and no migration manifest or hashes. The steps below are preserved solely to explain the earlier review assumptions.

1. Stop Docs Viewer media writers and the watcher, regenerate the exact manifest, compare this checkpoint's counts and fingerprints, and stop for review on any drift that changes the accepted shape.
2. Preflight the configured Projects base, real non-symlink workspace/scope/type paths, available space, user-owned backup expectation, empty-or-byte-identical targets, and read capability for every repository, external-local, and R2 source.
3. Copy every manifest row to its final external identity while v3 remains the sole active authority. Retrieve both configured R2 objects; never infer them from `site/`, another identity, or matching bytes.
4. Re-read every external target and verify size plus SHA-256. Any missing, different, unreadable, or unlisted source blocks cutover. No partial target becomes active.
5. With v4 code and focused tests prepared and the service still stopped, atomically replace the one scope config, restart once, and verify Add/Import destinations, inventory, evidence, registered build sources, Manage serving, Copy, static snapshot/export, and lifecycle paths through the new namespace. No process runs a mixed schema.
6. Preserve all existing Analysis `site/` and R2 objects. They are public projections after cutover and remain untouched until an EMW-1.2 Publish preview and confirmation.
7. After every active owner verifies against v4, remove only manifest-owned obsolete private roots: repository Studio/Processing `published/media`, repository build-source/evidence remnants, and external-local Notes/Dotlineform `source/media` or `published/media`. Remove their exact markers, `.DS_Store`, and empty directories; do not touch retained originals, current public `site/`/R2 bytes, or unconfigured R2 namespaces.

Before configuration cutover, rollback means discarding only exact manifest-created targets while the unchanged v3 authority remains live. After cutover but before old-root cleanup, rollback restores the single config/code set and restarts against the untouched old roots. After cleanup, recovery may rehydrate an old root from the verified external rows and manifest, but runtime never gains a dual reader or generic transaction framework.

## Risks And Stop Conditions

- The first media-aware Analysis Publish may have a large stale-public diff because 38 public media objects exist while the current public payload snapshot references two. EMW-1.1 preserves all 38; EMW-1.2 requires an explicit fresh preview.
- Scope Create, Rename, and Delete currently treat scope-local media as part of the document scope root. Leaving those owners on v3 would create orphaned or wrongly deleted external namespaces, so lifecycle is part of the cutover rather than optional cleanup.
- Eager external path resolution would make repository-backed document builds depend on workspace availability. V4 must keep configuration and URL projection read-only/lazy and fail only at the media operation boundary.
- HTML local serving is a security boundary. If it cannot reuse the current sandbox/CSP model without changing public HTML trust, stop and review that separately.
- A public copy must never become private authority merely because an external target is missing. A copy failure reports degraded media while document publication continues.
- Stop before implementation if the result needs a general asset registry, nested identity migration, content-addressing, deduplication, provider fallback, background synchronization, backup installation, arbitrary R2 cleanup, dual authority, or a generic transaction/recovery framework.
