# Sub-Scope Document Editing Delivery

## Complete Result

On a configured sub-scope report, the ordinary Source action edits the parent
report document and a separate subdoc Source action edits the currently
displayed, validated sub-scope document.

The existing **Edit metadata** action edits the current rendered target: the
parent report on its list view or the validated sub-scope document on its detail
view. The sub-scope modal retains every existing editable field except Parent,
including **non-viewable**.

The manage report lists every sub-scope document and shows the existing Status
and non-viewable icons from a compact management-only inventory. The public
report continues to receive only its minimal public manifest and shows neither
icon.

Both Source actions supply an explicit target. The existing Markdown source
editor never derives its target from the displayed document. Source mode has
an explicit **Return to doc** action instead of using either Source action as a
toggle.

## Control-state contract

Rendered report list:

- Edit metadata supplies the parent report target;
- parent report Source is enabled;
- subdoc Source is disabled; and
- **Return to doc** is unavailable.

Rendered valid subdoc detail:

- Edit metadata supplies the validated sub-scope target;
- parent report Source remains enabled and supplies the parent `doc_id`;
- subdoc Source is enabled and supplies the configured `sub_scope` and displayed
  `subdoc`; and
- **Return to doc** is unavailable.

Markdown source:

- Edit metadata is unavailable;
- both source-entry actions are visible and disabled;
- **Return to doc** is enabled;
- Save/Rebuild and all existing registered source-editor actions keep their
  current availability rules; and
- the toolbar does not permit switching source targets inside a dirty editor.

An unknown, unlisted, loading, or failed `subdoc` never enables subdoc Source or
targets Edit metadata. The report announces valid rendered-detail state through
an explicit management integration boundary; toolbar code does not infer
validity by scraping report markup or trusting the URL parameter alone.

## Explicit managed document target

Source mode and Edit metadata each receive exactly one required target:

```text
parent target:    { scope, doc_id }
sub-scope target: { scope, sub_scope, doc_id }
```

Neither workflow falls back to selected-document state, displayed payload,
`doc`, or `subdoc`. Ordinary non-report editing also supplies its target
explicitly.

The source target remains fixed for the mounted editor session. Read, rebuild,
and Open in VS Code use it. Add image, Add file, **Add catalogue token**, token
inspection/editing, and future registered contributions act through the same
active editor context rather than resolving another document.

Edit metadata loads the full record through the local management service using
the supplied target. It does not hydrate from the minimal public manifest or
compact public by-ID payload.

Public and manage list data remain separate. Public mode receives publicly
eligible `{ doc_id, title }` records. Manage mode receives all sub-scope
documents with `doc_id`, `title`, `ui_status`, and `viewable` in one local
inventory rather than issuing one by-ID request per row.

## Route and return behavior

Entering either source action does not rewrite the document route. For example,
editing the subdoc at:

```text
/docs/?scope=analysis&doc=d-20260624-213316-478639&subdoc=d-20260624-204534-0d6ae2
```

preserves both `doc` and `subdoc`.

Successful Save/Rebuild retains the current source-editor behavior of returning
to rendered view. **Return to doc** requests the same rendered mode without
changing the route and reuses the existing unsaved-change prompt. Browser
Back/Forward continues to own report detail state, not source target state.

Opening or saving Edit metadata also preserves the route. A successful subdoc
metadata save refreshes the displayed detail and the manifest row when an
existing manifest field changes, without selecting the subdoc in the parent
index.

## Service and rebuild boundary

- Source read, rebuild, and open requests accept optional `sub_scope` alongside
  `scope` and `doc_id`.
- Metadata read and `POST /docs/update-metadata` accept the same explicit
  target.
- An absent `sub_scope` preserves the current parent-scope behavior exactly.
- A present `sub_scope` must identify a configured one-level child of `scope`;
  the service resolves only that child document root.
- The requested `doc_id` must exist in that sub-scope and match its source front
  matter.
- Rebuild preserves the current revision, timestamp, atomic-write, suppression,
  diagnostics, and activity contracts while invoking the targeted sub-scope
  document and search builders.
- The sub-scope metadata request supports Title, Summary, Date, Date display,
  Status, and `viewable`. It omits `parent_id`; the service rejects that field
  for a sub-scope target and never introduces or changes sub-scope parentage.
- Metadata hydration reads full source front matter locally. It does not expand
  the public manifest beyond its existing minimal record contract.
- The local management inventory includes all sub-scope documents and the two
  fields required for existing Status/non-viewable icons. It is not copied to
  the public projection.
- A `viewable` change retains the existing visibility contract and refreshes
  the local management inventory and public eligibility without adding
  `viewable` to public manifest rows.
- Successful subdoc rebuild refreshes the by-ID detail payload and remounts the
  report detail without changing parent index selection.
- Invalid or unavailable targets fail before source access and leave rendered
  state recoverable.

## In Scope

- Add the subdoc Source and **Return to doc** toolbar controls.
- Convert the current Source control from a rendered/source toggle into a
  one-way explicit-target entry action.
- Project the exact control states above.
- Let the mounted report publish validated subdoc detail state to the management
  layer through a narrow callback or event contract.
- Supply explicit targets to both editing workflows and retain the source target
  for one editor session.
- Make the existing Edit metadata action target the parent report on list view
  and the displayed subdoc on a validated detail view.
- Hydrate a full sub-scope source record without projecting management metadata
  into public payloads.
- Supply one compact manage-only inventory containing all identities,
  `ui_status`, and `viewable`, and render the existing Status/non-viewable icons
  in manage report rows.
- Present the existing metadata modal without Parent for a sub-scope target,
  while preserving Title, Summary, Date, Date display, Status, and
  **non-viewable**.
- Extend metadata mutation and targeted reload behavior for optional
  `sub_scope`.
- Extend the source client, adapter, resolver, rebuild, open-source, activity,
  and rendered-refresh boundaries for optional `sub_scope`.
- Preserve all current source-editor controls and contribution contracts.
- Add focused service, control-state, module-integration, and route/request
  evidence.

## Not In Scope

- Changing the public report UI or exposing source controls publicly.
- Selecting sub-scope documents in the parent index.
- A second editor, reduced subdoc editor, or report-owned write form.
- Sub-scope document create, delete, move, transfer, Recent, or global search
  adoption.
- Encoding source mode or source target as a new URL parameter.
- Changing semantic-token syntax or Catalogue target behavior.
- Publishing or rendering subdoc `ui_status`; that remains the separate
  low-priority detail-header enhancement recorded by the parent feature.

## Completion And Evidence

- Parent Source always reads the supplied parent report `doc_id`, even while a
  subdoc is displayed.
- Subdoc Source is enabled only for a successfully displayed listed detail and
  sends the exact `{ scope, sub_scope, doc_id }`.
- The source editor has no selected/displayed-document fallback.
- Edit metadata receives the parent target on report list view and the exact
  sub-scope target on a valid detail view, with no selected/displayed fallback.
- The sub-scope modal contains every existing editable metadata field except
  Parent; its request contains no `parent_id`.
- A sub-scope metadata request that supplies `parent_id` is rejected without a
  write.
- Full metadata hydration comes from the local source record and does not add
  fields to the public manifest or compact public by-ID payload.
- Manage report rows show existing Status/non-viewable icons from one local
  inventory that also retains non-viewable documents.
- The public manifest contains only publicly eligible `{ doc_id, title }`
  records, and the public report renders neither icon.
- Both source-entry controls are disabled in source mode and **Return to doc**
  is the only explicit toolbar exit.
- Dirty return, successful rebuild, stale revision, and rebuild failure retain
  their current recoverable behavior.
- Save/Rebuild, Add image, Add file, **Add catalogue token**, token Info, and
  Open in VS Code operate on the active supplied target.
- Parent source requests remain byte-for-byte compatible apart from internal
  target construction.
- Sub-scope source requests cannot escape the configured sub-scope root or
  resolve an unlisted ID.
- Title and other metadata changes rebuild the targeted detail and any affected
  existing manifest/search projection; `viewable` retains its public
  visibility behavior without becoming a manifest field.
- A subdoc rebuild refreshes the detail without adding it to the parent index,
  Recent, or global search.
- Focused pure control-state, source-service, metadata-service, builder, and
  public-projection tests; direct request/response checks; module wiring checks;
  one durable manage-route smoke; manual toolbar/modal/dirty-state review; and
  `git diff --check` support only this delivery.
