# Report Blocks

## Purpose

Replace document-level report assignment front matter with one report block in the authored Markdown body. The block positions the document's report exactly among its surrounding content while retaining the document as the sole report host.

This feature changes report assignment and placement. It does not turn a document into a container for multiple or parameterised report instances.

## Current Starting Point

[Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) owns the current report registry, metadata, implementations, inventory, and front-matter report-host model. A source document currently declares `viewer_report` and optional `viewer_report_scope`, `viewer_report_access`, `viewer_report_preset`, and `viewer_report_subscope` fields. The browser normalises that singular document-level descriptor and appends one asynchronously mounted report after the rendered Markdown content.

[Report Capability and Composition](/docs/?scope=studio&doc=d-20260810-173738-703ecd) owns the durable shared, public, local-only, data, contribution, and stylesheet boundaries. A report block does not alter those boundaries or promote a local report.

The `docs_subscope` report-host declaration is additionally consumed by sub-scope lifecycle, document-location, publication, deletion, and transfer services. Its exact parent document remains the route and lifecycle host for the configured child collection.

No implementation or delivery is authorised by this feature document.

## Feature Contract

- A document contains zero or one report block. More than one report block in one document is invalid source and fails validation; blocks are never merged, ordered as instances, or resolved by first match.
- The report block is a block-level authored component at one exact Markdown position. It is not an inline link, a semantic-token occurrence, or an instruction to infer placement from neighbouring content.
- The document's immutable `doc_id` remains the report-host identity. There is no separate report-instance id or instance registry.
- The block selects one registered report and may express only the existing closed, code-owned assignment context: access intent, scope, preset, and sub-scope where applicable. The exact source syntax remains to be fixed at the first delivery sanity check.
- A preset remains a registered report variation. It is not an arbitrary parameter envelope.
- Report blocks do not accept free-form arguments, JSON configuration, initial filters, query expressions, column choices, or report-specific ad hoc attributes.
- Filtering, sorting, paging, selection, refresh state, and other interactions remain report-owned browser or route state. They are not persisted in the report block.
- Report identity, access, preset, scope, and sub-scope are validated against code-owned contracts. The block cannot name a loader path, module URL, service endpoint, data file, or stylesheet.

## Source And Projection Boundary

One report-source owner parses and validates the authored block, then exposes one normalised document-level report descriptor to builders and services. Report consumers do not independently scan raw Markdown or interpret token strings.

The docs builder replaces the valid block with one inert report host at that exact content position and emits the normalised descriptor in the document payload. Browser composition mounts the allowed report into that generated host; it does not append another report root or treat arbitrary authored HTML as executable report configuration.

Manage projection may retain public or local report descriptors according to the existing local loader and access rules. Public projection emits only the report assignment and host allowed by the existing public metadata, loader, data, and module boundaries. `access: public` remains intent rather than promotion, and a local-only block cannot make local code or data available publicly.

Source workflows that copy, import, review, export, or rewrite a complete document must treat the report block as structural source. The implementation sanity check must preserve or deliberately replace each current report-host behavior; the block must not bypass report validation merely because it is stored in the Markdown body.

## Sub-Scope Host Boundary

A `docs_subscope` block selects one exact configured sub-scope and remains constrained to one parent report-host document. Lifecycle configuration continues to record the immutable host `doc_id`, and child routes continue to compose through that document plus the exact `subdoc` target.

Sub-scope lifecycle, document-location, publication, deletion, and transfer services consume the same normalised report descriptor as the builder. They do not retain private front-matter readers or add their own report-token parser.

Creating a sub-scope writes its ordinary parent document with the report block at the canonical body position. Deleting or validating a lifecycle-owned sub-scope verifies the recorded host against the normalised block declaration before mutation. This feature does not change child collection ownership, public eligibility, manifests, customisations, or report contributions.

## Explicit Cutover

The implementation uses one source contract after migration:

- convert every current report-host source document from the five `viewer_report*` front-matter fields to one report block;
- update lifecycle-created report-host source and every builder or service consumer to use the normalised block descriptor;
- remove the retired front-matter fields, payload construction paths, and direct service readers; and
- reject a document that mixes retired report front matter with a report block.

There is no permanent dual reader, compatibility alias, precedence rule, or silent fallback between front matter and report blocks. A bounded migration may recognise the old fields only inside an explicit conversion step whose completion removes that recognition.

## Boundaries

This feature does not:

- support multiple reports in one document;
- introduce report parameters, saved filters, initial query state, dashboards, or user-defined report composition;
- merge report blocks into the semantic-token registry, semantic usage indexes, or Broken Links;
- add a generic report engine, arbitrary plugin loader, or report-specific source grammar;
- change report data authority, public promotion, loader allowlists, management contributions, or stylesheet ownership;
- implement Expanded Report View, horizontal scrolling, semantic-table conversion, or manual column widths; or
- make report-host documents transferable to a new collection without an explicit existing or newly approved transfer contract.

Multiple or parameterised report instances would require a separate feature covering parameter schemas, data-query authority, route-state namespacing, lifecycle ownership, and public validation. This feature deliberately creates no latent instance mechanism for that possibility.

## Relationship To Expanded Report View

This feature is delivered before [Expanded Report View](/docs/?scope=studio&doc=d-20260810-165949-ee4d35). It establishes the one exact live report host and authored restoration position that the expanded presentation will rehost.

Because a document can host at most one report, the expanded target remains document-owned. It retains the exact scope and `doc_id` plus the normalised report identity and preset or collection context needed for validation; it does not introduce `report_instance_id` or instance-prefixed state.

## Potential Delivery Shape

1. **Contract sanity check** — fix the exact block syntax, confirm ignored Markdown contexts and validation errors, inventory all current report hosts and direct `viewer_report*` consumers, decide how complete-source workflows preserve current behavior, and restate the bounded migration and focused evidence before editing implementation.
2. **Source and projection cutover** — add the single report-source parser and normalised descriptor, render the exact inert host, mount into that host in public and Manage composition, migrate current report documents, and retire the front-matter builder/runtime path.
3. **Lifecycle and service cutover** — move sub-scope creation, discovery, location, publication, deletion, and transfer to the shared normalised descriptor and remove remaining direct report front-matter readers.
4. **Closeout** — verify every report host and the public/local import boundary, update Reports with the shipped source and runtime contract, then make Expanded Report View eligible for its own implementation sanity check.

These are candidate complete outcomes, not active deliveries or permission to implement them. The first checkpoint must stop if the token requires parameter schemas, multiple-instance state, a generic directive engine, or a compatibility layer beyond the bounded conversion.

## Success Meaning

The feature succeeds when every report is assigned and positioned by one valid report block, every document has at most one report, the immutable document remains the exact host across public and Manage routes, and all builders and services consume one normalised descriptor. Current reports and sub-scope routes retain their data, access, lifecycle, and interaction behavior; retired report front matter and direct readers are absent. Expanded Report View can then target and rehost that one exact live report without inventing instance identity.
