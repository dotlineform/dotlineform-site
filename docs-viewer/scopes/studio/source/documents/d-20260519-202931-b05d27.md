# Catalogue Indexes And Payloads

## Public Read Models

| Artifact | Purpose | Main consumers |
| --- | --- | --- |
| `site/assets/data/series_index.json` | lean published Series list identity, title/year fields, primary Work, and optional single-Work destination | unselected `/series/` |
| `site/assets/data/recent_index.json` | publication snapshots with resolved public `href` destinations | `/recent/` |
| `site/assets/series/index/<series_id>.json` | selected Series metadata, derived public document URLs, and ordered lightweight member Works | selected Series and exact Work navigation |
| `site/assets/works/index/<work_id>.json` | selected Work metadata, downloads, links, grouped details, and derived public document URLs | Work and Work-detail runtimes |
| `site/assets/data/search/catalogue/index.json` | flat search records for current catalogue kinds | `/catalogue/search/` |

All public Catalogue projections contain published records only. The former flat Works aggregate is retired; a future flat Works report must be a separate, explicitly owned projection.

These are generated payloads. Their schema builders under `studio/services/catalogue/catalogue_generation_*.py` and the consuming route modules are the exact authority.

Catalogue prose is retired. Exact Work and Series payloads do not include a `content_html` field.

## Published Document URLs

`work_record_v4` and `series_record_v3` include `doc_url` as a deterministic array of public document URL strings. Empty arrays are ordinary output. The field is derived by joining exact current-public Docs identities and locations to each document's final canonical `work_id` or `series_id` declaration; it is not authored in canonical Catalogue source, inferred from Work membership, Series membership, titles, routes, filenames, rendered links, or Semantic Token mentions.

Work subjects contribute only to the exact Work payload, and Series subjects contribute only to the exact Series payload. The public Work and Series routes do not consume this field yet; presentation remains a separate Catalogue delivery.

After a successful Docs Publish, the follow-through compares the complete current derived projection with existing non-empty Work/Series payload evidence and writes only exact changed by-ID targets. `catalogue_generation_records.py` owns the shared complete Work and Series payload finalizers used by normal generation, cleanup, and this follow-through; the exact multi-payload write is atomic. A derivation or write failure leaves Docs publication successful, retains the prior complete Catalogue payloads, and returns explicit stale evidence without retrying or rolling back publication. Aggregate Catalogue indexes, search, media, canonical Catalogue source, authored links, and public route presentation are not part of this follow-through.

## Why There Are Lean And Exact Files

The Series list needs many small records; selected routes need one exact rich record.

- The unselected Series grid reads only `series_index.json`.
- A selected Series reads its exact Series payload and ordered lightweight member Works.
- A selected Work loads one Work payload containing its local detail sections.
- Exact Work-to-Series navigation reads the exact relevant Series payload rather than a global membership map.
- A selected detail derives its parent Work from `detail_uid` and reuses that Work payload rather than requiring a global detail index.
- Recent owns frozen snapshot destinations; Catalogue Search generation reads canonical source and the browser reads only its Search projection.
- Search uses its own flattened representation instead of forcing list or selected-record payloads to carry search-only text.

## Studio Read Models

Studio also uses `studio/data/generated/catalogue-lookup/` for Work and Series search plus Series-focused list data. Rich focused Work/detail payloads are built by the catalogue service at read time.

This distinction is intentional:

- generated list data is cheap to serve and cache;
- service projections can combine current canonical data and generated context without creating another per-record file family;
- the browser still has one logical configuration map in `studio-config.json`.

## Publication And Versioning

Public indexes include published runtime data and stable content versions needed by their consumers. Per-Work payloads carry confirmed media versions where primary remote media can be independently replaced. Aggregate indexes generally point to repo-owned thumbnails and do not need those primary-media version fields.

Recent entries are publication snapshots rather than a normalized view of current titles. That is why recent history remains a separate artifact.

## Retired Moments Boundary

There is no current public Moments route, Docs Viewer scope, Local Studio catalogue source, or editor family. The current catalogue search index contains Series and Works.

Do not restore retired Moment catalogue payloads merely because historical delivery notes or generic fixtures still mention them. Follow the current route and scope registries.

## Change Rule

- unselected Series-list context: change the lean Series serializer;
- selected Series content: change the Series record serializer;
- selected Work or detail content: change the Work record/section serializer;
- Recent snapshot or destination context: change the Recent serializer;
- search-visible content: change the catalogue search builder;
- Studio-only editing/search context: change the lookup or focused service projection.

Then update the field registry so build and lookup planning selects the affected artifact family.
