# SSP-7 — Project Media Audit Delivery

## Status And Purpose

Proposed after SSP-2 establishes the generated saved-document seam. The current `var/studio/reports/project-state.md` is useful, but it is an image audit rather than the folder-centred Project State model.

SSP-7 preserves that capability under the accurate name **Project Media Audit** and is the only delivery that retires the current `/studio/project-state/` route, report/open APIs, activity contract, generator placement, and static Markdown output.

## Complete Outcome

One persistent generated Docs Viewer document runs the existing project media audit and saves its latest Markdown result. It retains the useful inventory of source folders, source images, catalogue primary-image references, unrepresented images and folders, missing source files, and incomplete Work media fields.

The new audit is read-only. It does not modify Works, files, Project documents, Project State rows, or resolver data. Once accepted parity is demonstrated, the misleading Studio Project State name and duplicate static output are removed.

## Boundary With Project State

Project State owns:

- `documents[] <- folder_path -> works[] -> series[]` relationships;
- the saved Doc/Folder/Works/Series report;
- the folder-keyed resolver lookup; and
- targeted relationship follow-through.

Project Media Audit owns:

- image-extension and folder/image scan policy;
- comparison with canonical Work `project_folder`, optional `project_subfolder`, and `project_filename` evidence;
- image-level exception sections and counts; and
- retirement of the current Studio report workflow.

Neither output is an input to the other.

## Delivery Discipline

SSP-7 should migrate the existing proven audit rather than redesigning it inside Project State. SSP-7.0 is a short scope-and-spec sanity gate over the current Studio workflow, saved Docs Viewer document seam, parity target, and retirement boundary. It confirms broad owners, blast radius, deliverables, risks, and stop conditions without freezing exact files, fixtures, estimates, or implementation. Each implementation stage ends with focused evidence and an independent code/diff review before the next stage begins.

A generic audit framework, repair workflow, automatic deletion action, continuous watcher, or new media registry is scope creep and requires separate approval.

## Delivery Steps

### SSP-7.0 — Confirm Scope And Delivery

- [ ] Sanity-check parity-preserving Project Media Audit migration against the current Studio report behavior and the saved generated Docs Viewer document seam established by SSP-2; resolve only contradictions that would change the retained audit outcome.
- [ ] Confirm the broad blast radius across the current route/API/activity/generator/output, shared image-extension policy, audit scan/result behavior, saved document Run/Refresh, exact build, failure retention, and old-workflow retirement.
- [ ] Confirm the deliverables: one accurately named saved audit, demonstrated parity, retained prior output on failure, complete old-workflow retirement after acceptance, focused evidence, and concise durable owner updates.
- [ ] Stop for review if the result requires audit redesign, Project State relationship changes, a generic audit framework, repair/deletion workflow, watcher, media registry, or another boundary excluded above. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, SSP-2 dependency, broad owners, blast radius, deliverables, parity risks, local-only boundary, and stop condition. Stop before implementation approval.

### SSP-7.1 — Publish Project Media Audit

- [ ] Move reusable image-extension policy to a neutral owner if the trace confirms another catalogue consumer.
- [ ] Rehome the audit producer without changing canonical catalogue readers or folder containment.
- [ ] Generate and validate one persistent local Docs Viewer Markdown document from the audit result.
- [ ] Add the explicit Run/Refresh action and retain the prior saved report on failure.
- [ ] Verify real and fixture output against the current report before retirement.

**Checkpoint:** focused audit, containment, saved-document, source-write, exact-build, failure-retention, and real/fixture parity evidence passes. An independent code/diff review confirms canonical catalogue readers, Project State relationships, and the existing Studio workflow retain their current values until retirement is approved. Stop before SSP-7.2.

### SSP-7.2 — Retire The Studio Project State Workflow

- [ ] Remove or reroute the Studio page, report/open endpoints, frontend, activity contract, old generator entry point, and obsolete focused tests.
- [ ] Remove `var/studio/reports/project-state.md` only after the accepted Docs Viewer audit contains the required evidence.
- [ ] Update durable report, catalogue, and Projects documentation to the new owner and name.
- [ ] Run focused audit, containment, generated-document, source-write, exact-build, failure-retention, lint, and whitespace checks.
- [ ] Perform the independent final code/delivery review, reconcile parity and retirement claims with exact evidence and omissions, and record any bounded follow-up trigger.

## Not In Scope

- Project State folder rows, `works[]`, `series[]`, or resolver lookups;
- changing Work media metadata;
- deciding that an unrepresented or missing file should be imported, moved, renamed, or deleted;
- Work-detail auditing beyond the current explicit exclusions; or
- public audit output.

## Completion Evidence

- The saved Project Media Audit accounts for every retained current summary and exception class.
- Real-data comparison records any accepted differences from the final `var/studio/reports/project-state.md` generation.
- The previous complete saved audit remains available when a new run fails.
- Studio has no remaining Project State page, report/open API, activity entry, generator entry point, or static Markdown output.
- Project State report and resolver fixtures remain unchanged by the audit migration.
