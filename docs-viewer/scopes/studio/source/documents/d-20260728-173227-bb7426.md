# Sub-Scope Returned Package Review Delivery

## Result

Proposed as SRR-1 after
[Sub-Scope Package Preparation Delivery](/docs/?scope=studio&doc=d-20260728-115825-ae1461).

One complete returned package prepared from an exact `{ scope, sub_scope }`
collection can be validated and materialized as an immutable, read-only
Docs Review package. It does not mutate canonical sub-scope documents.

The delivery stops after real Docs Review acceptance. That review decides
whether the proposed content is copied into canonical sources manually or
whether a separate whole-package sub-scope Import delivery is justified.

## Capability Split

Reviewability and importability are separate trusted capabilities:

| package capability | `supports_docs_review` | `supports_return_import` |
| --- | --- | --- |
| normal `document-content` | `true` | `true` |
| sub-scope `document-content` | `true` | `false` |
| fully export-only package | `false` | `false` |

`false` / `true` is invalid: an importable returned package must also be
reviewable.

SSI-3 remains honestly export-only for canonical mutation. SRR-1 allows its
trusted returned package to enter Docs Review without making it actionable in
Docs Viewer Import. Existing top-level package behavior remains unchanged, but
its profile projection, export metadata, returned-package listing, Docs Review
manifest, and endpoint validation are retrofitted to carry and enforce both
flags explicitly.

Review Package checks `supports_docs_review`; Docs Viewer Import independently
checks `supports_return_import`. Neither capability is inferred from the other.
Existing stored packages that carry only `supports_return_import` from the
prior single-flag contract are deprecated and must be regenerated. SRR-1 adds
no compatibility fallback or metadata migration.

## Review-Only Contract

- Trusted metadata retains `scope`, `sub_scope`, export/profile identity, and
  the exact prepared `selected_doc_ids`.
- Returned rows must equal that complete prepared set. Missing, extra,
  duplicate, malformed, or cross-collection IDs block the package.
- The configured child collection is flat. Returned parent hierarchy is not
  applied or used to invent sub-scope structure.
- The existing scope-owned **Review Package** Action lists the staged package
  with its parent scope and sub-scope label. This is not another sub-scope
  selection action.
- Review materialization remains idempotent and publishes one
  `docs_review_validated_package_v1` folder containing the complete returned
  record set and provenance.
- Docs Review remains isolated and read-only. It has no canonical Save, Import,
  or query-string handoff.
- Docs Viewer Import and direct import endpoints continue to reject the package
  while `supports_return_import` is false.

## Optional Import Decision

SRR-1 is complete when the returned tag-document package can be inspected
faithfully in Docs Review. If source editing is clearer or safer manually, the
round trip ends there.

Only a later approved SRR-2 may add canonical Import. It must retain exact
`{ scope, sub_scope }` provenance, flat document semantics, whole-package
validation, one package-level confirmation, stale-source protection, and
all-or-nothing apply. SRR-1 does not pre-approve or partially implement it.

package, cannot reach canonical Import, and leaves a deliberate manual-versus-
automated source-editing decision rather than an implied second workflow.
