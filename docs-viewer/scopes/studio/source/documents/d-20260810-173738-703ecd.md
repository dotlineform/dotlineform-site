# Report Capability and Composition

## Purpose

This document owns the durable boundary between genuinely shared report capability, public report composition, and local-only report composition.

[Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) owns report metadata, the registry, current report behavior, and the implemented report inventory. Individual feature documents own changes to a report or its presentation. They reference this document rather than redefining the public/local boundary.

The governing rule is:

> Public reports are a separate module graph, not local reports with capabilities switched off.

## Current Position

The current public report registry and executable loader allowlist expose only `docs_subscope`. Its shared report reads a public manifest and exact by-ID payloads, owns collection membership and detail validation, and imports no management module.

Manage loads the same shared sub-scope report and explicitly supplies management contributions. Those contributions own private inventory presentation, selection, actions, source and metadata bridges, packages, and collection-specific browser customisations.

The public sub-scope customisation loader registry is empty. `analysis_tags` and `dotlineform_projects` have Manage-only browser contributions. `analysis_works` has service-owned subject and lineage aspects but no browser report contribution.

`viewer_report_access: public` remains access intent. It does not project metadata, install a loader, publish data, move CSS, or make a module executable.

## Runtime Layers

### Shared report capability

A capability is genuinely shared only when the same implementation is safe and useful in public and local composition.

Shared report code may own:

- exact report mount, loading, error, refresh, and unmount lifecycle;
- accessible list, table, detail, and expanded presentation structure;
- read-only filtering, sorting, paging, browser-local presentation state, and report-owned route state;
- exact collection, row, and detail identity validation;
- stable column identity and a representation-owned layout surface;
- detached contribution hosts and narrow lifecycle notifications; and
- adapters over explicit browser-safe read models.

Shared report code must not import or resolve local services, source paths, filesystem targets, private Studio lookups, mutation clients, selection actions, package workflows, or management CSS.

Shared capability does not require one generic report engine. A report may keep a focused shared module when its data, presentation, and lifecycle are specific to that report.

### Public composition

Public composition owns:

- the public report entrypoint and executable loader allowlist;
- explicitly promoted public report metadata;
- published or otherwise explicitly public browser projections;
- public-only adapters and read-only report contributions; and
- the shared report stylesheet plus any explicitly promoted report stylesheet.

Public modules may perform complex read-only presentation over public data. Complexity, row count, sorting, filtering, paging, deep links, or browser-local state do not make a report local. Data authority and dependencies do.

Public composition must not import from local report, management, package, import, review, or local-service module roots. A missing control, false capability flag, hidden element, or unavailable service is not a module boundary.

### Local-only composition

Local composition owns:

- the full local report loader registry;
- private manifests, generated-data readers, and Studio or Catalogue lookups;
- local report implementations with no public data contract;
- management contributions and collection-specific customisations;
- selection, source, metadata, create, copy, delete, publishability, package, filesystem, and other local actions; and
- local report and management stylesheets.

A report can be local-only while remaining read-only. The Works report, for example, is local because it composes private Projects inventory and Studio lookups, not because it writes data.

## Dependency Direction

```text
Public entrypoint
  -> public loader registry
    -> shared report module
      -> public projection

Manage entrypoint
  -> local loader registry
    -> shared report module
    + management contribution
      -> private data, local services, and actions
```

Dependencies point inward toward shared read-only code. Shared modules do not import their local callers. Manage may supply a narrow contribution or adapter to a shared module; public composition cannot receive a management contribution because the corresponding module and loader are absent from its graph.

## Data Boundary

Public reports read only data deliberately present in the public browser contract, such as public report metadata, public scope configuration, published manifests, and public by-ID payloads.

Manage may replace a public read adapter with an exact private adapter while retaining shared presentation and identity validation. Private records must not leak into the public projection merely because the renderer can display them.

Public report promotion therefore requires a data decision as well as a module decision. Reusing a local report renderer is insufficient when its input is a private manifest, local endpoint, source file, credential, or repository path.

## Customisation And Contribution

`sub_scope_customisation` is a collection-level service definition. Depending on its registered aspects, it may own manifest projection, document groups, validation, metadata, import front matter, assignable fields, subject fields, transfer, lineage, or browser composition.

A **report contribution** is only the optional browser-composition aspect. The terms are not interchangeable.

- A **public report contribution** is a separately allowlisted read-only module over public projection data.
- A **management report contribution** is a local module that may compose private data and local actions.
- A customisation with no browser-composition aspect contributes nothing to report rendering.
- Declaring browser access in service configuration does not create an executable browser loader.

The current browser exposure is:

| Customisation | Browser report contribution | Other registered ownership |
|---|---|---|
| `analysis_tags` | Manage only | groups, manifest projection, transfer |
| `dotlineform_projects` | Manage only | manifest projection, metadata, import, subject, lineage |
| `analysis_works` | none | subject, lineage |
| public customisations | none currently | none |

## Stylesheet Ownership

Styles follow the same composition boundary as JavaScript.

- `site/docs-viewer/static/css/docs-viewer-reports.css` contains genuinely shared report shell, sub-scope list/detail, search, link, and public responsive presentation.
- `docs-viewer/static/css/docs-viewer-local-reports.css` contains controls, layouts, and report-specific selectors used only by local report modules.
- `docs-viewer/static/css/docs-viewer-manage.css` contains management shell, selection, action, and management-contribution presentation.

The Manage shell loads shared report CSS, then local report CSS, then management CSS. Public route shells load only shared report CSS.

When a local report is promoted, its required presentation is reviewed deliberately. Genuinely shared selectors move to shared CSS; public-specific selectors receive a public owner. Local implementation CSS is not preloaded publicly in anticipation of possible promotion.

## New Report Decision

Before implementing a report, decide:

1. Is its data already public, deliberately projectable, or private/local?
2. Is the complete report public-capable, local-only, or a shared read-only core with separate public and local adapters?
3. Does it need a public contribution, a management contribution, neither, or both as separate modules?
4. Is the content a stable rectangular dataset requiring semantic table structure, or a list, group, summary, or composite better represented with list/section semantics and CSS Grid?
5. Which module and stylesheet own each report-specific behavior?
6. Does the result remain an inspection surface, or has it become a workflow that belongs outside the report mechanism?

An existing report may move from local-only to shared/public composition when its data and dependencies become public-safe. That is an explicit promotion slice, not a registry edit or an access-flag change.

## Promotion Requirements

Promoting a report or contribution to public requires all of the following:

- an explicit public data contract and projection;
- a public-safe metadata projection;
- a public executable loader entry;
- a public or shared implementation with no local imports;
- deliberately owned public/shared CSS;
- contained unavailable behavior when promotion is incomplete; and
- focused verification of imports, requested data, route state, and absence of management UI or services.

## Verification

Changes to this boundary should verify, in proportion to the slice:

- projected public report ids have matching public loader entries;
- projected public customisation ids have matching public contribution loaders and manifest data;
- public entrypoints and their transitive report imports contain no local management dependency;
- public report requests remain within public projections and never request private inventory or local APIs;
- public route shells do not load local report or management CSS;
- Manage loads shared, local-report, and management CSS in that order; and
- the affected report still passes its focused behavior smoke.
