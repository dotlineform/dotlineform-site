# Sub-Scope Customisation

## Purpose

Sub-Scope Customisation names the one optional registered extension contract for a configured sub-scope. The current `report_customisation` seam already contributes manifest data, document grouping, source validation, metadata reads and writes, import normalization, browser presentation, and actions as well as report rendering. This feature makes that actual responsibility explicit without adding a second configuration workflow.

The intended model is:

```text
configured sub-scope
  -> default report host + manifests + standard collection behaviour
  -> optional sub_scope_customisation {id, settings}
       -> manifest and row projections
       -> read-only Info metadata
       -> focused actions and modals
       -> source validation and import rules
       -> Copy transfer contract
```

The configured sub-scope remains the single lifecycle record. Creating one still establishes its default report host and manifests. An optional registered customisation on that same record adds only the collection-specific aspects it owns; there is no parallel declared-fields config, action flag, or report-only registration.

## Complete Feature Outcome

The configuration key and implementation vocabulary become `sub_scope_customisation`. Its compact configuration shape remains `{id, settings}`. The registered definition owns the validated settings schema and explicit aspect declarations for its supported manifest projections, read-only metadata, assignable field groups, focused actions, source validation, import normalization, and transfer contract. A field group therefore determines the values a focused workflow can display or assign; a separate availability boolean cannot drift from it.

The server keeps settings and mutation authority private. Browser configuration receives only the registered identity and the minimum access-safe projections or capabilities needed by the active report, Info view, or action. Availability always derives from the resolved exact collection and registered aspect; it is never inferred from a scope name, sub-scope name, route, title, filename, field presence, or displayed document.

Sub-scopes with no customisation retain the complete default report, manifest, navigation, and Manage behaviour. A customisation adds to those defaults and does not become a replacement report engine. Public access receives only explicitly registered public-safe contributions and no Manage metadata or mutation capability.

## Boundary

This feature owns the shared configuration and registry terminology, aspect model, access-safe projection, and migration of existing registrations. It does not create a generic JSON-schema form engine, make Info editable, make every custom field transferable, change report membership or document lifecycle, add nested sub-scopes, or implement Projects subjects, Tag associations, collection-aware Copy, or a new report engine.

The current [Sub-Scope Report Customisation Architecture](/docs/?scope=studio&doc=d-20260731-155053-3929e2) remains the truthful shipped-state reference until the cutover is implemented. Closeout renames and rewrites that durable owner as **Sub-Scope Customisation Architecture**, retaining the default-report and exact-target contracts while documenting the broader accepted seam.

## Delivery

[SSC-1 — Unified Sub-Scope Customisation Contract Delivery](/docs/?scope=studio&doc=d-20260804-172012-5d91bf) performs the single no-alias cutover and migrates the current Analysis Tags and Projects registrations without behaviour drift. It is a shared prerequisite to [SSP-0](/docs/?scope=studio&doc=d-20260804-164519-c7ad4e) and [TDL-0](/docs/?scope=studio&doc=d-20260804-170901-b2e74c), so those deliveries consume one accepted configuration model rather than inventing local field declarations.

## Delivery Discipline

The feature-level decision is settled: default lifecycle assets and optional collection-specific extensions are one configuration workflow. SSC-1.0 sanity-checks the smallest concrete aspect shape against current owners before implementation. Each implementation checkpoint requires focused evidence and an independent code/diff review, with the durable architecture transfer reserved for closeout.
