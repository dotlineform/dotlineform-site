# Catalogue Token Delivery

## Complete Result

Deliver Catalogue as the first complete semantic-token family:

- combined Work, Series, and Moment discovery;
- accepted catalogue-token syntax and family/target data contracts;
- **Add catalogue token** toolbar action and required-data modal;
- caret recognition, exact-range highlighting, Catalogue Info view, update, and
  removal;
- builder parsing and manage-only usage-index generation;
- migration of the active Work occurrence into the Catalogue family;
- semantic-token diagnosis and repair through the existing manage-only **Docs
  Broken Links** report.

This delivery proves that an author can begin with ambiguous text, compare
different catalogue entity types, choose the best association, and then maintain
the occurrence without changing its identity. It does not add Tag, asset, image,
file, or another token family.

CT-P0 is active. It freezes shared fixtures and contracts only; production
behavior remains unchanged. P1 is not approved until the P0 review gate is
accepted.

## Delivery Rule

Deliver the smallest complete vertical capability that replaces the existing
Work token and leaves an additive path for later fields and token families.
This delivery does not need to predict the final registry, every projection, or
the next refactor.

Work, Series, and Moment share one minimal Catalogue lookup shape. The active
`3 symbols` Work occurrence is the migration and completion specimen. Richer
type-specific fields are added only when a later UI or consumer requires them.

## CT-P0 Scope And Impact

The versioned contract fixture at
`docs-viewer/tests/fixtures/semantic_tokens_catalogue_v1.json` is the exact P0
authority. It records the grammar, Catalogue definition, resolved and broken
specimens, ambiguous `nerve` discovery rows, and minimum lookup, usage, and
broken-link shapes. The fixture is test input, not runtime configuration.

This checkpoint prevents Python/browser grammar drift and gives the later UI,
builder, usage, and audit work one additive contract. The main risk is freezing
syntax before tactile UI review; P1 therefore remains a separate review gate.
There is no public, write-service, security, semantic-token generated-output, or
production runtime change in P0. Routine Studio document and search projections
may update from these source-document edits.

Required later refactors are deliberately limited:

- contribute `source-add-catalogue-token` without adding a Catalogue branch to
  generic source-editor lifecycle code;
- keep the existing management modal shell and extract the pilot mixed-target
  search/list into the Catalogue-owned add-modal workflow;
- replace the fixed `semantic-token-picker` Info default with contextual routing
  between ordinary source information and `catalogue-token-info`;
- extend the source adapter with a current-buffer snapshot and monotonic local
  revision;
- add exact-range selection and guarded replacement/removal that verify the
  expected raw token before mutation.

The fixture, its README entry, and
`test_semantic_tokens_catalogue_contract.py` are the complete P0 fixture/test
surface. Their versioned envelopes require minimum fields but permit additive
fields. Removing or changing a required field, grammar rule, reason value, or
meaning requires a new schema version.

P0 may add contract fixtures and focused conformance tests. It does not change
production behavior. Stop for review after P0 and do not start P1 until the
fixtures and minimal shapes are accepted.

## CT-P1 — Catalogue Creation UI

**Outcome:** an author can select or type text, search Catalogue in one modal,
choose the concrete target, and insert the accepted token into the local source
buffer.

- [ ] Add one **Add catalogue token** source-editor toolbar action.
- [ ] Extract the pilot title-weighted search and keyboard-navigable result list
      from its Info-panel host and place it in the Catalogue modal.
- [ ] Search Work, Series, and Moment together using the shared minimal lookup
      row; show type, id, title, and compact `meta`.
- [ ] Capture selection text and range before modal focus; use the text to seed
      search, prefill Title, and replace the captured range.
- [ ] Let the author compare and change results until confirming the concrete
      target type and id.
- [ ] Make modal confirmation the only semantic validation gate: require a
      current result, required Title, and successful serialization.
- [ ] Add only the generic action/modal/source-adapter contribution points
      required by this workflow; keep Catalogue knowledge outside core.
- [ ] Preserve local dirty state, focus return, cancellation, keyboard behavior,
      and the existing Rebuild ownership.

**P1 review:** manually review ambiguous `nerve` search, result distinction,
selection prefilling, insertion, cancellation, keyboard use, modal fit, and
narrow layout. Stop before P2 if the UI cannot express the P0 contract cleanly.

## Explicitly Deferred

- Series context on a Work occurrence;
- preview images and other richer lookup presentation;
- media, file, or download projections and canonical array handling;
- occurrence fields beyond Title or a general field-control system;
- type-specific metadata beyond the shared minimal Catalogue lookup row;
- Tag, asset, image, file, or another token family;
- canonical Work, Series, or Moment editing;
- a standalone Semantic Tokens report, route, service, or validation system;
- public semantic relationships, related-content UI, or focused public payloads;
- automatic conversion or semantic wrapping of ordinary Markdown links or
  media;
- a general plugin architecture or compatibility layer for a possible future
  refactor.
