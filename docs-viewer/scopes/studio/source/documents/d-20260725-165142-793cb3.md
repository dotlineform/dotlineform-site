# Semantic Tokens File And Data Structure

## Direction

Treat the existing semantic-reference implementation as a pilot, not as the
target file contract. Reuse useful parsing, picker, rendering, and report code,
but do not preserve a path merely because the pilot wrote data there.

Current roles are literal:

- `source/` contains canonical authored or registered data;
- `generated/` contains reproducible indexes and report inputs;
- `published/` contains material deliberately published for a consumer;
- `site/assets/` contains an explicit public-site projection.

Semantic-token usage indexes are generated data. They do not belong in
`published/` unless a firm publication consumer is accepted later.

This is a proposed structure, not implementation approval.

## How The Pilot Reached Its Current Paths

The path history explains the present duplication:

1. The May 2026 pilot generated reference data directly under the then shared
   `assets/data/docs/scopes/<scope>/` tree. The report itself was manage-only,
   but working and public document data had not yet been separated.
2. The June publish gate introduced `docs-viewer/generated/docs/<scope>/` as
   working output and copied filtered document payloads, including nested
   `references/`, into the public site.
3. The July scope-first storage refactor moved the whole working document tree
   from `generated/docs/<scope>/` to
   `scopes/<scope>/published/documents/`. The reference files moved with it;
   their role was not reconsidered independently.

This produced two current locations:

```text
docs-viewer/scopes/<scope>/published/documents/references/
site/assets/data/docs/scopes/<public-scope>/references/
```

Neither location establishes a current publication requirement. The only active
authored occurrence is the Work token in the non-viewable Analysis document
[3 symbols](/analysis/?doc=d-20260518-180700-214487). The local report can read
its working relationship data. The public Analysis reference index is empty
after viewability filtering, and Semantic References is absent from the public
report registry.

The current pilot components should therefore be classified separately:

| pilot component | actual role | status |
| --- | --- | --- |
| `config/semantic-references/registry.json` | checked-in kind, normalization, route, and picker rules | Useful starting point, not the object registry. |
| `data/generated/semantic-references/target-lookup.json` | repository-wide picker projection | Correctly generated in role; schema and name remain provisional. |
| scope Markdown `[[ref:...]]` | canonical authored token occurrence | Retain the active meaning. |
| `published/documents/references/` | generated usage and reverse-reference indexes | Misplaced; relocate. |
| local Semantic References report | pilot reader of the usage indexes | Indicative UI, not a foundational data contract. |
| `site/assets/data/docs/scopes/*/references/` | filtered public copy | No accepted consumer contract; do not treat this pilot copy as the target public projection. |

The existing `index.json`, `by-doc/`, and `by-target/` split is one indexing
strategy. It must not dictate the canonical registry schema.

## Proposed Target Structure

```text
docs-viewer/
├── config/semantic-tokens/
│   └── kinds.json
│       checked-in kind, target-source, projection, destination,
│       normalization, and source-editor capability rules
├── data/generated/semantic-tokens/
│   └── target-lookup.json
│       reproducible repository-wide picker projection
└── scopes/<scope>/
    ├── source/
    │   ├── documents/*.md
    │   │   canonical authored semantic-token occurrences
    │   └── media/
    │       ├── registry.json
    │       │   canonical scope-owned asset records
    │       └── <build-source-type>/...
    │           optional canonical media build sources
    ├── generated/
    │   └── semantic-tokens/
    │       ├── index.json
    │       ├── by-doc/<doc_id>.json
    │       └── by-target/<kind>/<id>.json
    │           reproducible occurrence and relationship indexes
    └── published/
        ├── documents/...
        │   rendered documents may contain resolved token projections
        └── media/<type>/...
            deliberately published media representations
```

The exact `by-doc/` and `by-target/` materializations can be retained initially
if they remain useful, but they are generated indexes beneath one semantic-token
contract. They are not canonical records and do not automatically receive a
published or public copy.

External-local scopes use the equivalent configured scope source and generated
roots. An R2-backed asset still has a scope-owned canonical registry record;
provider path and served URL are representations, not its identity.

## Intended Public Consumer

A public semantic-relationship consumer remains part of the intended product:
a user can select a Work or Tag on the public site and open a Docs Viewer report
showing related public documents, works, or other accepted targets.

That intent does not yet define the publication contract. The internal generated
relationship data should be the derivation source, but the public projection
still needs explicit decisions about:

- the public route and report interaction;
- which target kinds and relationship directions it exposes;
- viewability and target-publication filtering;
- the smallest payload needed for a target-focused report;
- whether its public files are organized by target, report, or scope;
- ownership of the deployed `site/assets/` projection.

The eventual public payload may reuse a focused `by-target` idea from the pilot,
but it should not publish the complete internal registry or generated graph by
default. Once the consumer is accepted, its deliberately filtered data belongs
in an explicit published/public projection; until then, the final path and
schema remain open.

## Authority And File Responsibilities

| data | authority | expected change |
| --- | --- | --- |
| Semantic kind rules | proposed `config/semantic-tokens/kinds.json` | Reshape the pilot config; add Tag and Asset only with accepted target adapters and projections. |
| Work and Series records | Studio catalogue JSON | No semantic-token copy or migration. |
| Moment records | Moments canonical Docs source | Keep domain ownership; improve the adapter only if needed. |
| Tag records | Current tag registry, later Studio | Consume through a focused adapter; do not create a Docs Viewer copy. |
| Asset records | proposed `<scope>/source/media/registry.json` | Add canonical JSON with immutable asset ids, representations, optional metadata, and relations. |
| Token occurrences | Scope Markdown source | Retain the active text-link meaning; add registered media syntax deliberately. |
| Picker data | `data/generated/semantic-tokens/target-lookup.json` | Rebuild from accepted target sources. |
| Usage relationships | `<scope>/generated/semantic-tokens/` | Rebuild from source tokens; keep out of canonical target records and publication. |
| Published representations | Configured scope media location | Reconcile with asset records; never infer semantic identity from a path alone. |

## Asset Registry Boundary

The asset registry is distinct from the kind-capability file. It should use a
schema-versioned envelope and one record per stable asset identity. Its required
core should remain small:

- immutable asset id;
- scope ownership;
- title and media type;
- one or more typed representations.

Optional typed metadata and registered-target relationships may include tags,
description, credit, rights, dates, alternate representations, and an associated
document. Representation records may carry provider, storage reference, served
URL, MIME type, dimensions, or role where needed. None becomes the asset id.

Derived document usage belongs in `<scope>/generated/semantic-tokens/`, not in
the canonical asset record.

The exact record schema is the first implementation decision. The path above is
proposed so the registry remains scope-owned beside canonical media inputs while
published representations continue to follow their configured repository,
external-local, or R2 destination.

## Pilot Disposition

- Preserve the active `3 symbols` Work reference as the migration specimen.
- Decide the canonical registry and token schemas before moving generated data.
- Move per-scope usage output from `published/documents/references/` to the
  accepted scope `generated/` path and rewire any retained local report.
- Replace the pilot `site/assets/data/docs/scopes/*/references/` copy only when
  the intended public related-content consumer and its safe projection schema
  are accepted.
- Rebuild generated lookup and occurrence indexes; do not migrate generated JSON
  record by record.
- Do not retain compatibility aliases between the pilot and accepted paths.
- Register current path-based media, reconcile each stored object to its asset
  identity, then rewrite accepted media tokens in one reviewed migration.

The Docs service should surface these checked-in and generated JSON contracts to
the source editor and reports. It does not need a separate database, management
route, continuous semantic-validation system, or publication contract.
