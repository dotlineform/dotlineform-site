# Catalogue Token Delivery

## Complete Result

Deliver Catalogue as the first complete semantic-token family:

- combined Work, Series, and Moment discovery;
- accepted catalogue-token syntax and family/target data contracts;
- **Add catalogue token** toolbar action and required-data modal;
- caret recognition, exact-range highlighting, Catalogue Info view, update, and
  removal;
- builder parsing and manage-only usage-index generation;
- migration of the active Work occurrence into the Catalogue family;
- manage-only resolved-token inventory by selected scope with owning-document
  links;
- semantic-token diagnosis and repair through the existing manage-only **Docs
  Broken Links** report.

This delivery proves that an author can begin with ambiguous text, compare
different catalogue entity types, choose the best association, and then maintain
the occurrence without changing its identity. It does not add Tag, asset, image,
file, or another token family.

CT-P1 and CT-P2 are accepted after tactile review. Broken-link repair, migration,
and pilot cleanup are implemented in P3 and await final review.

## Delivery Rule

Deliver the smallest complete vertical capability that replaces the existing
Work token and leaves an additive path for later fields and token families.
This delivery does not need to predict the final registry, every projection, or
the next refactor.

Work, Series, and Moment share one minimal Catalogue lookup shape. The active
`3 symbols` Work occurrence is the migration and completion specimen. Richer
type-specific fields are added only when a later UI or consumer requires them.

## CT-P0 Scope And Impact

The versioned contract fixture at
`docs-viewer/tests/fixtures/semantic_tokens_catalogue_v1.json` is the exact P0
authority. It records the grammar, Catalogue definition, resolved and broken
specimens, ambiguous `nerve` discovery rows, and minimum lookup, usage, and
broken-link shapes. The fixture is test input, not runtime configuration.

This checkpoint prevents Python/browser grammar drift and gives the later UI,
builder, usage, and audit work one additive contract. The main risk is freezing
syntax before tactile UI review; P1 therefore remains a separate review gate.
There is no public, write-service, security, semantic-token generated-output, or
production runtime change in P0. Routine Studio document and search projections
may update from these source-document edits.

### P2 Scope And Impact

The accepted registry and 2,130-row combined target lookup now live under
`semantic-tokens`. The lookup exposes only family, concrete target type,
canonical id, title, workable `href`, and compact `meta`; the document builder
uses that lookup as its only link-resolution authority.

Python and browser parsers share the P0 grammar behavior, including exact
zero-based half-open ranges and inactive code/comment contexts. In source mode,
ordinary selections retain metadata information while a supported Catalogue
occurrence routes to Catalogue Info and selects the exact current-buffer range.
Update and removal both require the captured revision and raw source to remain
unchanged.

Entering Markdown source automatically opens its configured Metadata Info view.
Closing Info remains a direct user choice for the rest of that source session:
caret movement does not reopen it, while leaving and re-entering source starts a
new session and opens it again. Token recognition and exact-range selection
remain owned by the mounted Catalogue Info contribution rather than generic
source-editor core.

If the Add action captures one complete Catalogue token, the modal parses that
structured input, displays its type-qualified id as the search query, restores
only the exact family/type/id target, and preserves the occurrence Title. A
missing exact identity produces a specific unavailable-target state with no
Title fallback. Ordinary modal discovery remains fuzzy but now accepts bare ids
and type-qualified ids as well as Titles.

Resolved occurrences render as links. Managed working builds produce
deterministic index, by-document, and by-target usage envelopes under
`semantic-tokens`. A public read-only scope may therefore contain the ordinary
resolved anchor and its inert `data-semantic-token-*` attributes in document
JSON, while its working tree retains private usage output. The publish
projection excludes that usage directory, so the public snapshot needs no
registry, lookup, usage dataset, or token-aware runtime. Unsupported, malformed,
missing, or destination-less targets remain literal source with no usage row or
warning.

Local manage-mode destinations keep their portable lookup `href`, but the Info
view and rendered semantic-token anchors resolve that path against the
environment-backed public-preview base. They therefore open the separate local
site preview rather than the Docs Viewer service origin.

### P3 Scope And Impact

Docs Broken Links now parses source Markdown directly and classifies supported
token-like failures as `unsupported_kind`, `missing_target`, or
`missing_destination`. Its report shows the raw occurrence and reason, links the
actual failed destination when one exists, and opens the owning Docs Viewer
document in Markdown source mode. Exact-range selection is deliberately omitted:
the existing route handoff has no occurrence-selection contract, and adding one
would widen P3 beyond the optional P0 extension point.

The Semantic Tokens report is the complementary resolved-occurrence inventory.
It reads the selected scope's local usage index and presents three sortable
columns: Title, Identity, and Document. Document links to the owning managed
document. It performs no audit, source parsing, or write.

The Analysis source specimen now uses
`[[catalogue:work:00638|3 symbols]]`. Its managed working build contains one
resolved anchor and one local usage occurrence. The anchor retains inert
`data-semantic-token-*` attributes. The public publish contract excludes the
lookup and usage directory, so no public token registry, data dependency,
runtime, report, or compatibility path was added.

The parallel pilot builder, registry, lookup, usage outputs, read routes,
Semantic References report, picker placement, tests, documents, and public
copies are removed. The reusable mixed-target list remains under Catalogue
ownership; the accepted Semantic Tokens report reads only the replacement usage
contract.
