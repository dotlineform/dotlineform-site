# DMM-1 — Data Model Maps Foundation Delivery

## Status And Purpose

Proposed as **DMM-1**. [Data Model Maps Concept And Examples](/docs/?scope=studio&doc=d-20260802-123451-d0e52e) defines the mixed logical ERD, projection-lineage, and artefact-register approach tested by this delivery.

The delivery creates the first durable, reviewable orientation layer for current canonical entities and generated projections. It begins with a bounded notation and readability spike because Mermaid syntax support is already proven, while large-diagram legibility and correct partitioning remain the material risks.

## Complete Outcome

One durable Data Model Maps index under the existing Architecture documentation routes to three bounded current-state maps:

1. Catalogue logical model and read-model boundary.
2. Docs Viewer main-scope, sub-scope, manage, search, and public projection lineage.
3. Cross-system relationship projections for Semantic Tokens, Tags, Project State, and Resolver Tokens, with proposed relationships labelled separately from shipped ones.

Each map combines only the diagram types it needs with a concise artefact register naming exact source, producer, primary consumers, visibility, refresh behavior, and code/config/test authority. A reader can follow a canonical record into its relevant projections without mistaking generated files for canonical entities.

## Delivery Discipline

DMM-1 is documentation-only by default. It reuses fenced Mermaid and Diagram Detail View in Studio Docs Viewer and does not add production runtime, schemas, builders, registries, or UI.

DMM-1.0 must inventory the exact proposed document paths, mapped code/config/test owners, and expected documentation diff before the full map set is approved. The likely production and test diff is **zero**. If useful completion requires a generator, parser, schema registry, new lint target, or runtime interaction, stop and propose a separate delivery rather than widening DMM-1.

## Rough Delivery Steps

### DMM-1.0 — Inventory And Freeze The Mapping Language

- [ ] Inventory the current canonical, authored, generated, runtime-only, manage-only, and public artefact families needed by the three proposed maps.
- [ ] Trace exact producers, primary consumers, refresh triggers, visibility boundaries, and existing durable owners from current code, configuration, schemas, and focused tests.
- [ ] Freeze the distinction between logical entity relationships, physical derivation/publication edges, and register-only operational detail.
- [ ] Render representative Catalogue ERD and Docs Viewer lineage examples with the pinned Mermaid version in ordinary and narrow layouts, using Diagram Detail View for inspection.
- [ ] Decide the smallest readable partition for each map and record intentional omissions rather than creating one master diagram.
- [ ] Record the exact new or promoted document list, current links to update, and rough documentation diff. Record production and test files explicitly as none unless the reviewed shape changes.

**Checkpoint:** the reviewed spike can trace one Catalogue relationship and one main/sub-scope Docs Viewer source through their projections without ambiguous authority, crossed-edge reconstruction, unreadable labels, or unsupported Mermaid behavior. Stop before writing the complete inventory.

### DMM-1.1 — Publish The Durable Map Set

- [ ] Create or promote one concise durable Data Model Maps index beneath the existing Architecture documentation.
- [ ] Publish the Catalogue logical model and its adjacent canonical/public/Studio artefact register.
- [ ] Publish the Docs Viewer projection-lineage map and register, separating main scope, sub-scope, manage, search, and explicit public publication.
- [ ] Publish the cross-system relationship-projection map and register, distinguishing shipped Catalogue Semantic Token projections and Tag Registry document associations from proposed Tag Semantic Token, Project State, and Resolver Token behavior.
- [ ] Link each map to current implementation and contract owners without copying exhaustive schemas or code inventories into unrelated durable documents.
- [ ] Add only the minimum inbound navigation needed from the Architecture index or an existing focused owner.

**Checkpoint:** every displayed entity and artefact has one unambiguous classification and owner; every generated edge identifies its producer; every access boundary and proposed relationship is explicit; omitted families are named.

### DMM-1.2 — Verify, Review, And Transfer

- [ ] Render every Mermaid block through the current Studio Docs Viewer runtime and inspect the ordinary document view plus Diagram Detail View.
- [ ] Review wide and narrow presentation, long paths, edge crossings, labels, accessibility titles/descriptions, and source readability in a normal Markdown editor.
- [ ] Verify all document and code-authority links, exact artefact paths, canonical/derived classifications, and shipped/proposed states against the current repository.
- [ ] Rebuild the exact Docs documents and Studio search projection, run `git diff --check`, and perform a final source/diff/omission review.
- [ ] Rewrite the retained concept as current durable orientation material if it remains the best owner; present the feature parent, concept, and delivery closeout list for explicit retirement or promotion approval.

## Focused Evidence

- the pinned Mermaid renderer accepts every maintained ERD and flowchart;
- each diagram remains usable in the rendered document and Diagram Detail View at realistic density;
- register paths and producer/consumer claims resolve to current repository owners;
- Docs Viewer build and search projections contain the new hierarchy and rendered examples; and
- final review confirms that no runtime, canonical data, generated application payload, or public site behavior changed.

## Not In Scope

- a whole-repository master ERD or unrestricted dependency graph;
- field-by-field reproduction of every JSON or front-matter schema;
- automatic Mermaid generation, source-code introspection, or a schema registry;
- a graph database, query language, interactive explorer, filters, collapsing, or runtime traversal;
- new projection, mutation, publication, refresh, or watcher behavior;
- declaring authored documentation to be executable schema authority;
- changing existing canonical or generated artefacts to make the diagrams simpler; or
- mapping unrelated filesystem, code-import, CSS, or UI-component dependencies.

The [Data Model Maps feature parent](/docs/?scope=studio&doc=d-20260802-123450-f7493d) owns planning and navigation. At completion, [Architecture](/docs/?scope=studio&doc=d-20260331-000000-4a16b0) should own the durable map entry point.
