# DMM-1 — Data Model Maps Foundation Delivery

## Status And Purpose

In progress at the **DMM-1.0 checkpoint**. [Data Model Maps Concept And Examples](/docs/?scope=studio&doc=d-20260802-123451-d0e52e) defines the mixed logical ERD, projection-lineage, and artefact-register approach tested by this delivery. DMM-1.1 has not started.

The delivery creates the first durable, reviewable orientation layer for current canonical entities and generated projections. It begins with a bounded notation and readability spike because Mermaid syntax support is already proven, while large-diagram legibility and correct partitioning remain the material risks.

## Complete Outcome

One durable Data Model Maps index under the existing Architecture documentation routes to three bounded current-state maps:

1. Catalogue logical model and read-model boundary.
2. Docs Viewer main-scope, sub-scope, manage, search, and public projection lineage.
3. Cross-system relationship projections for Semantic Tokens, Tags, Project State, and Resolver Tokens, with proposed relationships labelled separately from shipped ones.

Each map combines only the diagram types it needs with a concise artefact register naming exact source, producer, primary consumers, visibility, refresh behavior, and code/config/test authority. A reader can follow a canonical record into its relevant projections without mistaking generated files for canonical entities.

## Delivery Discipline

DMM-1 is documentation-only. It reuses fenced Mermaid and Diagram Detail View in Studio Docs Viewer and does not add production runtime, schemas, builders, registries, or UI.

DMM-1.0 must inventory the exact proposed document paths, mapped code/config/test owners, and expected documentation diff before the full map set is approved. The likely production and test diff is **zero**. If useful completion requires a generator, parser, schema registry, new lint target, or runtime interaction, stop and propose a separate delivery rather than widening DMM-1.

- **Shipped Semantic Tokens:** canonical Catalogue records and the published Moments Docs projection feed `docs-viewer/data/generated/semantic-tokens/target-lookup.json` through `SemanticTargetLookupBuilder`. A scope Docs build consumes that management lookup while rendering tokens and replaces its generated `semantic-tokens/index.json`; target refresh and document rebuild are separate. `test_semantic_target_lookup.py` and the semantic-token catalogue tests own focused evidence.
- **Shipped Tag document associations:** `studio/data/canonical/tags/tag-registry.json` (`tag_registry_v5`) owns ordered `doc_url[]`; `tag_source_model.py`, registry mutation services, and transaction services own writes. Public `document-locations.json` projections are separately built from already-published Docs search, parent payloads, and sub-scope manifests for the Tag picker; they are not Tag authority. `test_tag_source_model.py`, `test_tag_registry_mutations.py`, and `test_build_document_locations.py` are the focused evidence.

Their nodes and edges must be labelled **proposed**. The existing `var/studio/reports/project-state.md` image-audit output is a different shipped workflow and is intentionally excluded from the proposed relationship map.

### Mapping Language And Partitions

- ERDs contain logical identity and cardinality only. Array-backed references may be shown as logical foreign keys, but files, builders, indexes, and access modes do not become entities.
- Lineage diagrams contain physical reads, builds, publication, and consumption. Every artefact node carries one of **canonical**, **authored**, **generated projection**, or **runtime-only**; arrows use an explicit verb where direction alone could be ambiguous.
- Registers carry exact path or path family, producer, primary consumer, refresh trigger, visibility, and code/config/test authority. Operational detail does not migrate into diagram labels merely to make the register shorter.
- Shipped edges are solid. Proposed nodes say **proposed** in their label and use dashed edges inside a visibly separate proposed section. A proposal does not enter a current-state diagram merely because planning exists.
- A feature-spec before/after pair reuses stable node names. **Before** is verified current state; **after — proposed** is a design claim until delivery updates the current map.
- The Catalogue map uses one logical ERD plus one small read-model boundary flow. The Docs Viewer map is split into main working projections, sub-scope projections, and explicit public publication. The cross-system document contains separate mini-lineages for Semantic Tokens, Tags, and proposed Project State/Resolver behavior. No master graph is created.

### Readability Spike

The representative concept diagrams rendered successfully in managed Studio with pinned Mermaid `11.16.0`, accessibility titles/descriptions, graphics-document roles, and no Mermaid warnings. In the ordinary layout, the Catalogue ERD rendered at 238 × 308 inside a 560-pixel host and the Docs lineage at 530 × 554. At a 390 × 844 narrow viewport, they rendered at 238 × 308 and 324 × 339 inside a 354-pixel host without clipping. The lineage remains readable but is at the acceptable density ceiling, which supports the three-way Docs partition above.

Both rendered diagrams expose **Open diagram in new tab** controls and stable SVG `viewBox` metadata. The automated browser was prevented from following the Blob detail target by its navigation security policy, so manual Diagram Detail visual review remains the one open DMM-1.0 evidence item; this is not a product failure.

## Focused Evidence

- the pinned Mermaid renderer accepts every maintained ERD and flowchart;
- each diagram remains usable in the rendered document and Diagram Detail View at realistic density;
- register paths and producer/consumer claims resolve to current repository owners;
- Docs Viewer build and search projections contain the new hierarchy and rendered examples; and
- final review confirms that no runtime, canonical data, generated application payload, or public site behavior changed.

## Not In Scope

- a whole-repository master ERD or unrestricted dependency graph;
- field-by-field reproduction of every JSON or front-matter schema;
- automatic Mermaid generation, source-code introspection, or a schema registry;
- a graph database, query language, interactive explorer, filters, collapsing, or runtime traversal;
- new projection, mutation, publication, refresh, or watcher behavior;
- declaring authored documentation to be executable schema authority;
- changing existing canonical or generated artefacts to make the diagrams simpler; or
- mapping unrelated filesystem, code-import, CSS, or UI-component dependencies.

The [Data Model Maps feature parent](/docs/?scope=studio&doc=d-20260802-123450-f7493d) owns planning and navigation. At completion, [Architecture](/docs/?scope=studio&doc=d-20260331-000000-4a16b0) should own the durable map entry point.
