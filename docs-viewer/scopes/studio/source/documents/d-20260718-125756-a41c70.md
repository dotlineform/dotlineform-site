# Docs Viewer Source Documentation And Linting Pilot Delivery

## Outcome

Establish and prove the smallest useful source-documentation and linting conventions needed for new or materially changed Docs Viewer core code.

This is a bounded pilot, not repository-wide backfill. It begins after Core Definition Baseline v1 identifies representative boundaries and completes before the long-lived Core Refactor worktree is created.

## Scope

- Select a small set of representative JavaScript and Python Docs Viewer boundaries from the accepted core definition.
- Inventory the active Docs Viewer source roots, delivery environments, generated/vendor exclusions, and current check owners before configuring tools.
- Agree practical JSDoc and Python docstring conventions from those real modules.
- Document contracts, intent, non-obvious data shapes, lifecycle, side effects, and failure behavior without commenting obvious code.
- Add Docs Viewer-owned, pinned Ruff and ESLint development tooling with explicit, reviewable configuration.
- Begin with correctness, unused-code, and other low-noise rules appropriate to the selected surfaces.
- Provide short project-local commands that lint the pilot area and can later target new or changed Core Refactor files.
- Resolve genuine findings inside the selected pilot surfaces and record any justified local suppressions.
- Update stable repository guidance only after the examples and commands have proved useful.

## Decisions

- Current code and canonical configuration remain exact behavior authority. Source comments explain and route; tests and schemas provide executable evidence; accepted architecture and delivery documents own intended change.
- The pilot toolchain is owned by Docs Viewer rather than a new repository-wide JavaScript project. It may target both `docs-viewer/runtime/js/` and site-owned public/shared Docs Viewer modules through explicit paths.
- The existing Mermaid renderer package remains isolated and does not acquire repository lint dependencies.
- `jsconfig.json`, TypeScript, and `// @ts-check` are not initial pilot requirements. The delivery includes one bounded evaluation and persists them only if the selected surface proves useful, low-noise checking.
- Normal completion remains compatible with the existing focused `run_checks.py` profiles. The pilot does not introduce one repository-wide `npm run check`.
- Java/Processing, unrelated applications, semantic retrieval infrastructure, generated reference pages, formatting, and broad automatic fixes remain separate outcomes.

## Planned Tooling

Required when the delivery becomes active:

- one exact Ruff version in a Python development-dependency owner;
- exact ESLint, `@eslint/js`, and `globals` versions in a private Docs Viewer-owned JavaScript tooling package and lockfile;
- focused commands that run from the repository checkout without relying on global Ruff or ESLint installations.

Conditional:

- pin TypeScript only if the selective JSDoc type-checking evaluation is retained;
- add no JSDoc coverage plugin by default; syntax or tag validation must prove useful before becoming another dependency.

SDL-P0 selects the file locations and supported environments. SDL-P2 selects and pins exact versions while installing and running them together. Do not copy version, target, module-resolution, or global settings from background research without verifying them against the application.

## Representative Surfaces

The pilot must include enough variety to test the conventions without becoming a backfill project:

- one exported browser/module contract with a non-trivial object or callback shape;
- one Python service or domain boundary with meaningful inputs, outputs, or failure behavior;
- one builder, filesystem, configuration, or process boundary with side effects;
- one current example where documentation reveals that simplification or splitting is preferable to a longer comment.

[Core Definition Baseline v1](/docs/?scope=studio&doc=d-20260724-213457-6e1cf7) nominates the exact SDL-P0 surfaces so the pilot documents likely future boundaries rather than fossilizing accidental current structure.

## Adoption Rules

- Require the proven conventions for new or materially changed exported/public APIs in Core Refactor deliveries.
- Use types for types and documentation for meaning; do not repeat signatures in prose.
- Treat lint as focused feedback, not as authority for mechanical redesign.
- Review each failure or suppression in the context of the current contract.
- Keep behavioral edits separate from broad formatting where practical.
- Do not add compatibility code merely to satisfy a lint rule or documentation tool.
- Use canonical repository terminology rather than adding synonyms for agent retrieval.
- Update affected source documentation in the same change as a documented contract.
- Require each material documented claim to have a current code/config owner and executable evidence or an explicitly named evidence gap.

## SDL-P1 Proven Conventions

- Add a module-responsibility comment only when it clarifies ownership. The composition module now distinguishes dependency assembly and startup ordering from feature-controller behavior and generated-payload authority.
- Document exported JavaScript boundaries when callers need lifecycle, injection, ordering, cleanup, or failure information. `DocsViewerCollectionProvider`, its factory context, and the injected factory callback are the one shared JSDoc shape; obvious internal helpers and the defaults object remain undocumented.
- Keep JavaScript types broad where the runtime intentionally accepts route-specific implementations. SDL-P1 does not imply TypeScript, `checkJs`, or a stricter provider schema.
- Let Python annotations carry types. Add docstrings only for domain invariants, detached-copy behavior, plan-versus-write ownership, create-versus-replace semantics, containment, staging lifetime, remote I/O, and translated failures.
- Use plain source docstrings without documentation-generator markup or repeated argument lists. The only type-support edit was restoring the missing `Path` import used by the builder's existing annotation.
- Do not comment through an ownership problem. The provider-neutral location protocol, adapters, identity confinement, and `artifact_location_adapter()` remain candidate Core. Automatic R2 credential discovery and client construction must move out of `docs_artifact_locations.py` into integrated composition, which can inject the existing `RemoteArtifactClient` boundary.

Current evidence directly covers provider validation and successful startup ordering, ImportContent validation and projection, builder dry-run/write behavior, and filesystem/R2 adapter workflows. Two precise evidence gaps remain for SDL-P4: rejected startup-phase cleanup is not directly asserted, and the automatic Studio-backed R2 authentication path has no focused unit test.

## SDL-P2 Tooling Baseline

- Python linting is pinned to Ruff `0.16.0` in `python-requirements.txt`, installed in the ignored lint-local virtual environment, and configured for Python 3.12. The explicit `E4`, `E7`, `E9`, and `F` selection covers syntax, import placement, undefined names, and unused code without formatting, docstring coverage, or automatic fixes.
- JavaScript linting is pinned to ESLint `10.8.0`, `@eslint/js` `10.0.1`, and `globals` `17.7.0` in the private package and lockfile. The flat configuration applies the recommended correctness rules to current browser ESM with browser globals and no Node runtime globals, JSDoc plugin, TypeScript, or stylistic rule set.
- `docs-viewer/bin/lint-python` and `docs-viewer/bin/lint-js` default to the three Python specimens and one JavaScript specimen respectively. Explicit path arguments replace those defaults so later Core files can use the same commands.
- Both configurations retain the SDL-P0 generated, vendor, Mermaid, test, and unrelated exclusions. Ruff also forces those exclusions for explicit paths and keeps its cache inside the ignored lint-tool directory.
- Initial command output was classified in temporary delivery evidence. SDL-P2 introduced no source fix, suppression, formatter, repository-wide package, or check-profile change.

## SDL-P3 Type-Checking Decision

- TypeScript `7.0.2` was installed temporarily without package or lockfile changes and run only against `site/docs-viewer/runtime/js/shared/docs-viewer-app-composition.js`. The evaluation used `allowJs`, `checkJs`, `noEmit`, browser DOM types, and ESM-preserving settings; it added no `jsconfig.json`, `tsconfig.json`, or runtime build step.
- A non-strict `noResolve` run produced 9 local diagnostics with one root cause: the `createDocsViewerCollectionProvider()` options JSDoc names only `createCollectionProvider`, while the implementation also consumes eight route and service context properties. This is a genuine documentation finding, but `noResolve` cannot validate the imported contracts.
- Normal non-strict resolution produced 14 diagnostics across 3 files: the same 9 local diagnostics plus 5 off-target findings in imported modules. Strict checking expanded to 498 diagnostics across 26 files, including 443 in imports, so retaining it would turn the single-module pilot into a broad annotation backfill.
- The pilot therefore retains documentation-only JSDoc. The temporary TypeScript installation was removed; TypeScript, a type-check command, `jsconfig.json`, and `checkJs` remain deferred until extraction creates a stable module boundary or a later delivery explicitly accepts the wider typed dependency graph.
- SDL-P4 carries the one genuine finding: document the complete collection-provider options shape without adding a broad suppression or changing runtime behavior.

## Out Of Scope

- Repository-wide JSDoc or docstring backfill
- Repository-wide zero-warning lint baselines
- A root JavaScript package, repository-wide `jsconfig.json`, or repository-wide `checkJs`
- Missing-documentation enforcement across historical code
- Broad reformatting
- Formatter adoption or broad automatic-fix batches
- Generated source-reference documentation
- Semantic retrieval infrastructure or agent-retrieval benchmarking
- Complexity-driven mechanical rewrites
- Processing or unrelated application adoption
- Changes to the isolated Mermaid renderer toolchain
- Expansion of rule sets beyond what the pilot proves

Those remain separate outcomes under the owning repository feature.
