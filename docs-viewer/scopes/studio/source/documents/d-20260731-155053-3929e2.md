# Sub-Scope Customisation Architecture

## Purpose

This document is the current implementation reference for the default `docs_subscope` report and its one optional registered collection extension. It fixes configuration, aspect ownership, generated data, browser composition, exact targets, access projection, and the checks required when a registration changes.

```text
configured sub-scope
  -> default report host, manifests, by-ID records, and standard Manage contribution
  -> optional sub_scope_customisation {id, settings}
       -> registered server aspects
       -> access-safe manifest and browser projections
       -> access-specific browser contribution
```

The configured sub-scope is the lifecycle and collection record. The default remains complete; a customisation adds only the collection-specific aspects owned by its registered definition.

## Default Report And Exact Identity

Every configured sub-scope receives the shared flat list/detail reader and normal lifecycle assets. The report owns configured collection validation, complete supplied membership, list/filter/sort projection, by-ID identity validation, `subdoc` navigation, history, empty/unavailable/error states, and contribution hosts.

Manage composes the standard contribution first. It owns lifecycle presentation, collection-local selection, New, Prepare Package, Copy Link, Delete, refresh reconciliation, and app-level Import handoff. A registered browser contribution is composed second in its own hosts.

The exact targets are:

```json
{"scope": "<scope-id>", "sub_scope": "<sub-scope-id>"}
```

```json
{"scope": "<scope-id>", "sub_scope": "<sub-scope-id>", "doc_id": "<document-id>"}
```

A selection target adds an immutable, de-duplicated `doc_ids` array to the exact collection. Collection, selection, and validated-detail actions receive these targets from the report/action registrar. Titles, filenames, routes, parent documents, displayed rows, and current UI selection remain presentation inputs rather than identity authorities.

The indexed report host is an ordinary parent-scope document with `viewer_report: docs_subscope` and `viewer_report_subscope: <sub-scope-id>`. The host selects the report and collection; the configured sub-scope selects the optional customisation. Child documents remain outside the parent Index, Recent, and global search projections.

## Configuration Contract

A default collection uses its ordinary configured record:

```json
{
  "sub_scope": "default",
  "title": "Default",
  "ui_statuses": ["draft", "done"],
  "public_projection": null
}
```

A customised collection adds exactly one `sub_scope_customisation` object:

```json
{
  "sub_scope": "tags",
  "title": "Tags",
  "public_title": "Concepts",
  "sub_scope_customisation": {
    "id": "analysis_tags",
    "settings": {
      "groups": ["subject", "domain", "form", "theme"]
    }
  }
}
```

The Python registry owns valid IDs and the exact settings normalizer. Configuration contains data only; executable names, field arrays, and availability flags remain code-owned by the registered definition.

## Registered Definition

`DocsSubScopeCustomisationDefinition` owns `customisation_id`, `normalize_settings`, and the smallest optional aspect records required by the collection:

| Aspect | Registered responsibility |
| --- | --- |
| `manifest_projection` | Project the strict custom root and row data for an enabled browser access. |
| `document_groups` | Resolve ordered document-group values from validated settings. |
| `source_validation` | Validate custom source front matter during document loading/building. |
| `metadata` | Read custom metadata and optionally normalize its existing revision-bound update. |
| `import_front_matter` | Normalize custom create-only import front matter. |
| `browser_composition` | Declare the `public` and/or `manage` accesses with a browser implementation. |
| `assignable_field_groups` | Declare typed group IDs and server-owned field names for future focused authoring. |
| `authoring_subject` | Declare which canonical subject fields the exact collection reads, independently of assignment availability. |
| `transfer` | Declare a typed server-owned non-subject transfer contract, its owned field names, and target-settings validator. |

Registry validation checks definition identity, aspect record types and callbacks, supported browser accesses, manifest/browser coupling, unique group and field identities, Manage access for assignable groups, canonical subject field declarations, transfer identity, and the prohibition on claiming shared subject fields as custom transfer fields.

`sub_scope_customisation_authoring_subject_fields()`, `sub_scope_customisation_assignable_field_groups()`, and `sub_scope_customisation_transfer_contract()` expose the server declarations to their owning services. Projects and Analysis Works both read the exact `folder_path`, `work_id`, and `series_id` subject field set, but only Projects declares the assignable `authoring_subject` group. Copy planning freezes each declared non-subject field as retained, omitted, or rejected; apply executes only retained and omitted decisions from the revalidated receipt while ordinary subject fields remain outside this custom seam.

## Collection Copy Apply Ownership

The shared document-transfer apply service writes fresh identities to the resolved collection source root. Parent targets use the coordinated parent docs/search rebuild; child targets use the existing exact sub-scope rebuild, so child documents remain outside the parent Index, Recent, and global search. Parent scope configuration continues to own media and registered build sources for either target shape.

Copy composes exact target URLs through the configured parent report host: parent documents use `doc`, and child documents use the report `doc` plus copied `subdoc`. Receipt-owned internal links are transformed between those shapes without resolving titles or subjects. Apply results, activity, and failure evidence carry the exact `{scope}` or `{scope, sub_scope}` collection, while browser selection and destination surfaces remain separate owners.

## Generated And Browser Projection

The server retains normalized settings, concrete field names, validation, metadata, import, and transfer authority. Browser configuration receives only the access-safe descriptor selected for the exact configured collection.

Manage descriptors contain the selected identity and any access-safe capabilities declared by that exact registration. Analysis Tags currently projects identity only:

```json
{"sub_scope_customisation": {"id": "analysis_tags"}}
```

Projects additionally projects its assignable group identity:

```json
{
  "sub_scope_customisation": {
    "id": "dotlineform_projects",
    "capabilities": {
      "assignable_field_groups": ["authoring_subject"]
    }
  }
}
```

The shared config controller normalizes those IDs to `capabilities.assignableFieldGroups`. `hasDocsViewerAssignableFieldGroup()` is the browser availability check for focused actions and modals. Concrete field names and accepted values remain with the exact server definition and its validated settings.

The public manifest contains public-eligible `{doc_id, title}` rows. The Manage manifest contains complete collection rows plus compact lifecycle metadata. An access-enabled `manifest_projection` may add the existing strict `customisation` data envelope:

```json
{
  "customisation": {
    "id": "analysis_tags",
    "data": {"groups": ["subject", "domain", "form", "theme"]}
  },
  "docs": [
    {
      "doc_id": "d-example",
      "title": "Example",
      "ui_status": "draft",
      "viewable": true,
      "last_updated": "2026-08-01 08:00:00",
      "customisation": {"group": "subject"}
    }
  ]
}
```

The descriptor and manifest IDs agree exactly. Custom row data targets supplied manifest members and remains namespaced from builder-owned fields. Browser routes consume the configured manifest and by-ID URLs rather than constructing storage paths.

### Authoring Subjects And Private Associations

The shared source reader normalizes the exact raw `folder_path`, `work_id`, and `series_id` declarations into one `authoring_subject` object. Its states are `none`, valid Folder, valid Work, valid Series, `malformed`, or `conflicting`. A valid Work ID is an exact five-digit string; a valid Series ID is an exact lowercase alphanumeric-or-hyphen string. Folder is valid only when the exact collection registers `folder_path` in an assignable field group. Work and Series reading is collection-independent. Invalid declarations retain their raw field/value evidence as private observational state and remain ordinary source.

Private Manage sub-scope manifests carry `authoring_subject` on every row participating in this projection and one top-level `subject_generation` receipt. The matching `subject-associations.json` uses `docs_subject_associations_v1`, repeats the exact collection and receipt, and groups each valid `{kind, key}` subject to a deterministically ordered list of documents. Every document entry contains the exact `{scope, sub_scope, doc_id}` target and its current composed Manage location. Several documents may share one subject. Association generation reads only canonical front matter and already-composed document locations; current folder existence, Catalogue membership, titles, filenames, body text, route selection, and UI state remain separate owners.

The builder writes the Manage manifest and private association product from one normalized generation. Later exact rebuilds remove retired declarations and leave an empty association set when the final declaration is cleared. A consumer that reads both products must require matching `subject_generation` values. Public-readonly building retains its public-safe manifest, internal Manage manifest, and by-ID schemas, while private subject state, invalid evidence, local paths, assignment capability, and `subject-associations.json` stay with local Manage delivery.

## Browser Contribution Contract

The access-specific JavaScript registry resolves the descriptor ID to one lazy factory. The factory validates the descriptor and returns only its needed contribution callbacks:

| Callback | Ownership |
| --- | --- |
| `createFilters(context)` | Add collection-specific filters. |
| `renderRow(context)` | Populate detached row contribution hosts. |
| `renderListToolbar(context)` | Add exact-collection controls. |
| `renderSelectionToolbar(context)` | Add controls for the immutable exact selection snapshot. |
| `renderDetailToolbar(context)` | Add controls after manifest/by-ID identity validation. |
| `mountMetadataEditor(context)` | Mount the current strict metadata contribution and return `read`/`destroy` owners. |
| `notify(event)` | Observe explicit collection-scoped lifecycle events. |

The shared report supplies detached hosts and immutable context. The default contribution keeps its own lifecycle and action ownership. Custom callbacks contribute additively and retain exact targets supplied by the host.

An explicitly selected descriptor resolves through its access registry. Unknown IDs, unavailable loaders, invalid factories, descriptor/manifest mismatches, and callback failures produce a contained report error under the selected collection identity.

## Current Registrations

| ID | Server aspects | Browser access and contribution |
| --- | --- | --- |
| `analysis_tags` | settings normalization, manifest projection, document groups, browser composition, `analysis_tag_fields` transfer validation over `group` | Manage group filter using projected ordered groups and row group values |
| `analysis_works` | empty settings normalization and read-only `folder_path`/`work_id`/`series_id` subject declaration | No custom browser descriptor, assignable group, or contribution; uses the shared reader |
| `dotlineform_projects` | settings normalization, manifest projection, metadata projection and assignment normalization, import front matter, `authoring_subject` over `folder_path`/`work_id`/`series_id`, browser composition | Manage Folder/Work/Series/None and invalid subject state, exact-detail read-only Subject information, capability-gated **Assign subject**, compact row cues, and Folder-only **Open in Finder** |

Analysis Tags and Projects declare Manage browser composition. Analysis Works deliberately declares none, so its Manage and public projections use the shared reader without custom controls. All public projections retain the shared public manifest and by-ID boundary. `studio/default` remains the default-only reference.

## Access Boundary

Python `browser_composition.accesses` is the access authority. Builder descriptor projection, manifest projection, and JavaScript loader registration agree with it. Public code imports the shared report and public registry; Manage code owns the default contribution, management registries, services, actions, and mutation-capable factories.

Current public descriptors and custom manifest namespaces are empty for Analysis Tags and Projects. Public rows retain their ordinary public fields and routes. Manage settings, normalized subjects, private associations, field declarations, metadata, and controls remain in local server/Manage owners.

## Adding Or Extending A Registration

1. Confirm the requirement is additive to the default membership, list/detail, navigation, and Manage behavior.
2. Add or extend one registered definition with a stable ID, strict settings normalizer, and the smallest aspect records.
3. Register a lazy browser factory only for each declared browser access.
4. Configure the exact sub-scope with `{id, settings}` and rebuild its generated projections.
5. Inspect the default collection, descriptor, public/Manage manifests, by-ID payloads, exact targets, access registries, and report host.
6. Add focused pure/service, builder, registry-boundary, module, and route coverage proportional to the new behavior.

For assignable workflows, the registered `DocsSubScopeAssignableFieldGroup` is the availability and server field authority. The browser consumes its projected group ID; `POST /docs/assign-field-group` resolves the exact collection again, accepts only the registered server-owned fields, requires the current source revision, and performs the exact atomic source write and sub-scope rebuild. The focused collection contribution owns value acquisition and response validation. A registration's read-only `DocsSubScopeAuthoringSubjectAspect` enables Folder meaning for that exact collection without granting assignment; raw `work_id` and `series_id` continue to use the collection-independent subject reader. For transfer workflows, `DocsSubScopeTransferAspect` remains server-side, validates an explicitly matching contract against target settings, and cannot own shared subject fields.
