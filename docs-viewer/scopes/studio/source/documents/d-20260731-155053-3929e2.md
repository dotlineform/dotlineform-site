# Sub-Scope Report Customisation Architecture

## Architecture Outcome

Every configured one-level sub-scope uses the same `docs_subscope` engine and
one useful default. A sub-scope may select a registered customisation module
when its own content or workflow needs more than that default.

```text
configured collection
  -> docs_subscope engine
  -> default presentation and Manage actions
  -> optional registered collection customisation
```

The customisation is an explicit property of the collection, not an inferred
variant of `viewer_report`, a filename convention, or a condition on a known
scope or sub-scope ID.

## Collection And Host Identity

The collection remains `{scope, sub_scope}`. Child documents remain exact
`{scope, sub_scope, doc_id}` targets.

The indexed host is an ordinary parent-scope document containing:

```yaml
viewer_report: docs_subscope
viewer_report_access: local
viewer_report_subscope: <sub-scope-id>
```

The host selects the engine and collection only. The configured sub-scope
record selects a known customisation identity; absence means the default.
Config must never contain an arbitrary JavaScript module path.

## Definition Of The Default

The default is the complete minimum useful report for an ordinary flat
document collection. It is not Analysis/Tags with optional labels removed.

Shared public-safe behaviour:

- collection validation and ordered membership;
- list, detail, empty, unavailable, and error states;
- title search over the loaded collection;
- validated by-ID loading and `subdoc` navigation; and
- clean absence of management controls.

Default Manage behaviour adds:

- status and non-viewable presentation from the compact Manage row;
- title-ascending initial order and a two-state sort control switching between
  title ascending and `last_updated` descending;
- exact-collection **New document**, including for an empty collection;
- collection-local checkbox selection, Select all, Clear, and Done;
- the **Actions** menu and checked-ID **Prepare Package**;
- validated-detail Delete and **Copy Link**;
- mounted collection/detail publication for the app-level Import owner; and
- capability-aware omitted or disabled states without target fallback.

The recency order places missing or unusable `last_updated` values after dated
records, then uses title ascending and `doc_id` as deterministic tie-breakers.
Changing sort does not change checked IDs. Select all and Shift-range consume
the current visible sorted projection.

**Copy Link** follows the existing main-index convention: it copies a Markdown
link whose label is the document title and whose destination is the exact
viewer URL for the validated sub-scope document, including its report host and
`subdoc` identity. It does not copy a source, payload, or management-service
URL.

Filters beyond title search, additional columns, additional row fields, and
additional actions are customisations. A customisation may add to the default;
it does not silently remove or replace default behaviour.

The public manifest remains:

```json
{
  "docs": [
    {"doc_id": "d-*", "title": "Title"}
  ]
}
```

The standard Manage row is:

```json
{
  "doc_id": "d-*",
  "title": "Title",
  "ui_status": "",
  "viewable": true,
  "last_updated": "YYYY-MM-DD HH:MM:SS"
}
```

`last_updated` is standard because the default visibly consumes it for
recency sorting. The Manage manifest remains a data projection, not an action
registry.

## Isolated Candidate And Cutover

SSR-1 develops the default through an explicitly temporary local-only report
identity, provisionally `docs_subscope_candidate`.

The candidate copies the current shared report module so work on its structure
cannot regress the canonical `docs_subscope` used by Analysis/Tags. Copying the
report module alone is insufficient: the Manage host currently gives every
`docs_subscope` the same contribution containing New, selection, Prepare
Package, Delete, row state, and Import-context publication. The candidate must
therefore receive its own default Manage composition as well.

The isolation boundary is narrow:

- copy the shared report module that is being reworked;
- add a local-only loader and explicit temporary Manage dispatch;
- create a new default Manage contribution rather than changing the
  existing Tags-shaped contribution in place;
- reuse generic filter, URL, target, action, selection, and lifecycle helpers
  where their contracts already fit; and
- reuse the one sub-scope builder and its public/Manage manifest generation.

The candidate is not added to the public report loader. Its Studio host uses
the temporary report ID only while SSR-1 is active; final host front matter
uses canonical `viewer_report: docs_subscope`.

Because the builder is shared, SSR-1.1 may add the harmless standard
`last_updated` field and dormant registered-projector support, but it preserves
the existing root `groups` and row `group` output for the still-live Tags path.
It does not reinterpret `document_groups` as the new settings object. SSR-1.2
switches Tags config, builder projection, and browser composition together,
then removes the old direct group projection in that same cutover.

Cutover occurs only after the `studio/default` empty/list/detail/action surface
is accepted and Analysis/Tags passes parity through its registered
customisation. In the same delivery:

1. canonical `docs_subscope` resolves the accepted implementation;
2. the Studio fixture host switches to canonical `docs_subscope`;
3. Analysis/Tags switches to canonical default plus its customisation; and
4. the candidate report registry row, loader entry, temporary Manage dispatch,
   and superseded module/contribution wiring are removed.

There is no permanent alias and no runtime condition on `sub_scope: default`.

## Persistence And Propagation

The default is persisted as one canonical implementation, not as a copied
report attached to each sub-scope. `studio/default` remains a permanent local
reference instance, but it is not the source of the implementation.

| concern | canonical authority |
| --- | --- |
| Shared list/detail behaviour | Canonical `docs_subscope` runtime module |
| Default Manage controls and lifecycle publication | Canonical default Manage contribution |
| Default public and Manage manifest fields | Shared sub-scope builder |
| One collection instance | Sub-scope config, report-host document, and child source documents |
| Additional collection behaviour | Registered customisation selected by that sub-scope |
| Default review and regression surface | Permanent `studio/default` reference instance |

An ordinary live instance persists only its collection and host identity:

```text
report host: viewer_report = docs_subscope
report host: viewer_report_subscope = projects
sub-scope config: no customisation identity
```

It does not receive a JavaScript copy or version of the default. Each mount
loads the current canonical `docs_subscope` implementation. Absence of a
customisation identity selects the default path, so an uncustomised
`dotlineform/projects` and any later lifecycle-created collection receive the
same implementation automatically.

Generated `manifest.json` and `manage-manifest.json` files persist one
collection's current data projection. They are not templates, code, or the
definition of the default and must not be hand-maintained as such.

Changes propagate through their owning layer:

- a shared list/detail or presentation change updates the canonical report
  module and reaches every mounted instance when current assets are loaded;
- a default management change updates the canonical default Manage
  contribution and reaches every manageable instance;
- a default manifest-field change updates the shared builder and requires the
  affected configured sub-scopes to be rebuilt so their generated projections
  match the runtime contract;
- a customisation change updates its registered builder/browser parts and
  affects only collections selecting that identity; and
- a configuration-shape change also regenerates browser configuration before
  affected reports are reviewed.

Runtime and builder changes to one manifest contract ship as one coordinated
change. The runtime may define contained missing-value behaviour, such as
undated rows sorting last, but stale manifests are not a second supported
implementation.

Default changes are first exercised on `studio/default`, then checked against
Analysis/Tags as a customised consumer. Changes that alter the public-safe
path also receive public-route evidence. After cutover the Studio host uses
canonical `docs_subscope` permanently; only the development candidate and its
temporary registry/dispatch are removed.

## Customisation Resolution

A sub-scope selects a customisation with one strict object:

```json
{
  "report_customisation": {
    "id": "analysis_tags",
    "settings": {
      "groups": ["subject", "domain", "form", "theme"]
    }
  }
}
```

Absence of `report_customisation` means the default. The object accepts only
`id` and `settings`; `id` matches `[a-z][a-z0-9_]*`, and `settings` is an
object validated by that identity's registry entry. It may be empty only when
that entry permits it. Analysis/Tags requires one ordered, non-empty,
duplicate-free `groups` list. Its existing top-level `document_groups` field
is removed during SSR-1.2 rather than retained as an alias. Metadata
validation, mutation, package validation, builder projection, and browser
controls all consume the same normalized customisation settings.

A controlled registry maps each known customisation identity to its allowed
parts:

```text
sub-scope config identity and validated settings
  -> builder projector for each permitted access
  -> browser-config descriptor for each permitted access
  -> public browser factory, when registered
  -> Manage browser factory, when registered
```

The Python registry owns settings validation and data projection. Separate
static JavaScript registries own public and Manage factories. A focused
agreement check requires the IDs and declared access surfaces to match; config
never contains a module path, export name, field list, or handler. The first
registered identity is `analysis_tags`.

The generated Manage browser config carries the normalized descriptor needed
to resolve `analysis_tags`. Because that customisation has no public
contribution, its public browser config omits the descriptor and the public
report follows the default path. A later public contribution must be declared
public in the Python registry and the public JavaScript registry; only its
public-safe descriptor is projected.

For Analysis/Tags the generated Manage record contains only:

```json
{
  "report_customisation": {"id": "analysis_tags"}
}
```

The browser-config controller normalizes that to `reportCustomisation: {id}`.
Raw source settings are not copied into browser config; browser-required data
comes from the access-specific manifest projector.

Unknown identities or malformed settings fail scope-config loading. A missing
builder projector or registry disagreement fails generation or its focused
contract check. If generated browser config names an unavailable module, or a
module import/factory fails, the report renders a contained error and does not
silently fall back to the default. Absence is the only default selector.

## Builder Projection Contract

The default builder always creates the public `{doc_id, title}` row and the
standard Manage row. `last_updated` is always present in a Manage row as a
string; an absent source value projects as `""` and sorts after dated rows.

One selected customisation projector may add data only inside the
`customisation` namespace. It receives the normalized settings and ordered
source documents separately for public and Manage access. It cannot remove,
rename, reorder, or overwrite `docs` membership or a default row field.
Unknown document IDs, non-object output, or a namespace collision fail the
build.

The Analysis/Tags Manage shape becomes:

```json
{
  "customisation": {
    "id": "analysis_tags",
    "data": {"groups": ["subject", "domain", "form", "theme"]}
  },
  "docs": [
    {
      "doc_id": "d-*",
      "title": "Title",
      "ui_status": "",
      "viewable": true,
      "last_updated": "YYYY-MM-DD HH:MM:SS",
      "customisation": {"group": "subject"}
    }
  ]
}
```

Rows without a group omit the row `customisation` object. Analysis/Tags has no
public projector, so its public manifest contains neither root nor row
customisation data. The manifest ID must equal the resolved browser descriptor
ID before a browser module receives the data.

## Browser Contribution Contract

The engine resolves at most one collection customisation, but the resolved
module may compose reusable helpers. In Manage, a composer always applies the
default contribution first and the optional collection contribution second.
Each owner receives its own detached host; content is attached only when
populated. A custom module cannot replace or clear a default host.

Version 1 freezes these positions and payloads:

| Position | Payload and rule |
| --- | --- |
| Row | `access`, exact `collection`, immutable normalized `document`, and detached `leading`, `titlePrefix`, and `trailing` hosts; may return `accessibleLabels` |
| Filter | `access`, exact `collection`, immutable customisation `data`, and a filter descriptor with stable `id`, `initialValue`, `render({host, value, setValue})`, and pure `matches({document, value})` |
| List toolbar | `access`, exact `collection`, current visible sorted `documents`, detached `host`, `{mode, setMode}` sort controller, action registrar, and exact refresh callbacks |
| Selection | exact `collection`, current visible sorted `documents`, immutable `{active, eligibleDocIds, checkedDocIds}` snapshot, detached selection-action host, and action registrar |
| Detail toolbar | `access`, exact `collection`, manifest `document`, validated by-ID `target`, detached `host`, action registrar, and exact refresh callbacks |
| Lifecycle | `mount`, `refresh`, `projection`, `selection`, `state`, and `unmount` events carrying exact collection identity and the event-specific fields below |

The default title predicate and all active custom predicates are applied before
the selected sort. The engine owns the complete manifest records, filter
state, sorting, and projection. A custom filter changes its own value only
through `setValue`; it cannot mutate records or selection. Selection consumes
the current visible sorted projection, while checked IDs remain stable across
filter and sort changes.

Lifecycle event fields are:

- `mount`: `access`, `collection`, and `root`;
- `refresh`: complete normalized `documents`, customisation `data`, and
  `reason`;
- `projection`: visible sorted `documents`, active `sort`, immutable filter
  values, and `reason`;
- `selection`: the immutable selection snapshot and `reason`;
- `state`: `state`, `reason`, nullable validated `target`,
  `refreshDocument(target)`, and `refreshCollection(collection)`; and
- `unmount`: `reason`.

Callback or predicate failure is contained as a report error. The composer
cleans up all mounted owners and does not rerun the report without the selected
customisation.

Version 1 provides row adornment/metadata hosts rather than an arbitrary table
schema. If Projects later proves that true additional columns are required,
the generic contribution contract can add a versioned column position without
putting Projects fields or conditions into the default engine.

## Action, Target, And Refresh Contract

Every default or custom action is registered in code with `id`, `placement`,
`targetKind`, `capability`, `emptyState`, `handler`, and `refreshEffect`.
Configuration and manifests cannot register actions.

The report target kinds are deliberately more specific than the current
generic action resolver:

- `collection`: exactly `{scope, sub_scope}`;
- `selection`: exactly `{scope, sub_scope, doc_ids}`, where IDs are the
  explicitly checked collection members; and
- `validated-detail`: exactly `{scope, sub_scope, doc_id}` after membership
  and by-ID payload identity agree.

The report may use the generic action definitions to resolve an action ID and
selection policy, then must wrap the result in the mounted collection and
validate the exact keys. It never falls back to the parent scope, active index
document, report host, URL text, or an unchecked row.

| Default action | Placement | Target | Empty state | Availability owner | Refresh effect |
| --- | --- | --- | --- | --- | --- |
| New | List toolbar | `collection` | Enabled when creation is available | Manage host's exact-collection create handler | Rebuild, refresh complete manifest, verify one created target, open it |
| Prepare Package | Selection menu | `selection` | Disabled with no checked IDs | Document-package capability and handler | None |
| Delete | Detail toolbar | `validated-detail` | Not rendered outside validated detail | Delete workflow capability check | Commit exact deletion, reconcile membership, return to list |
| Copy Link | Detail toolbar | `validated-detail` | Not rendered outside validated detail | Browser clipboard support | None |

Custom actions use the same target kinds and refresh effects. A missing
capability produces only the action's declared omitted or disabled state; it
does not prevent the default report or unrelated contributions from mounting.
Import remains app-level and receives exact lifecycle targets rather than a
registered report action.

## Toolbar Ownership

The default Manage contribution owns New, sorting, status/viewability row
presentation, selection, Prepare Package, validated-detail Delete and Copy
Link, plus collection publication for app-level Import.

An optional customisation owns only its additional controls and presentation.
It may reuse common helpers, but those helpers do not activate themselves
based on manifest shape or a known collection ID.

The single app-level **Import** action remains outside the report toolbar. A
mounted report may publish its exact collection and refresh callbacks through
the standard lifecycle seam; it does not create another Import button.

## Analysis/Tags Retrofit

Analysis/Tags becomes one registered customisation of the default report.

The default provides the complete baseline defined above. The Analysis/Tags
module adds only its configured group field, group order, and group filter.
The builder-side customisation projects `group` into the Manage manifest; the
browser-side customisation renders and applies the group controls. The public
manifest remains `{doc_id, title}` and therefore has no group filter.

Manage title **Tags** and public title **Concepts** remain resolved collection
configuration, not a new report type. No `analysis`, `tags`, `concept`, or
known group value belongs in the default engine or customisation dispatcher.

The refactor removes superseded direct wiring after parity is proven. It does
not retain a hidden legacy Tags route alongside the registered module.

## Lifecycle Integration

The **New sub-scope** lifecycle creates a collection with no customisation
identity. It also creates one associated parent report host and valid empty
public-safe and Manage projections, then refreshes configuration and parent
discovery before navigating to the exact returned host.

The association between lifecycle-created collection and host is explicit and
stable. Later deletion previews and applies against that exact association; it
must not infer the host from title, filename, active document, or URL text.

Post-commit refresh or navigation failure returns the committed identities and
retries follow-through only. It never creates another collection or host.

## Projects Decision Boundary

The `dotlineform/projects` collection first receives the default through the
normal lifecycle. Its real documents and management workflow are then reviewed
before any Projects module is designed.

Possible differences—metadata, grouping, status, sorting, filters, or
actions—are evidence prompts, not assumed requirements. The decision may be
that the default is sufficient. If customisation is justified, Projects uses
the same config identity, registry, contribution positions, exact targets, and
public/Manage boundary as Analysis/Tags.

## Decisions Owned By Delivery

SSR-1.0 freezes:

- the exact sub-scope config field and registry shape;
- the paired builder/browser registration contract for a customisation;
- contribution placement and lifecycle payloads; and
- the final module ownership and filenames after current-code inspection.

The default surface, standard Manage row including `last_updated`, initial
title order, recency toggle, Copy Link semantics, and Analysis/Tags group-only
customisation are part of that contract. SSR-1.1 implements it through the
isolated candidate; SSR-1.2 moves Analysis/Tags and cuts over only after parity.

The second delivery freezes the lifecycle association and failure shape. The
third decides only the Projects-specific needs that can be justified from the
working default.

The [feature parent](/docs/?scope=studio&doc=d-20260731-150644-3dfab5)
owns delivery order and status.
