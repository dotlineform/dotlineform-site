# Sub-Scope Report Customisation Architecture

## Purpose

This document is the implementation reference for extending a configured
one-level sub-scope report. It defines the shared default, the registered
customisation seam, the generated-data contract, browser composition, exact
targets, public isolation, failure behaviour, and the checks required when a
new customisation is added.

The governing rule is:

```text
configured sub-scope
  -> generated manifest and by-ID records
  -> docs_subscope report engine
  -> public-safe shared behaviour
  -> Manage default contribution
  -> optional registered access-specific customisation
```

The customisation is an explicit property of the configured collection. It is
not inferred from `scope`, `sub_scope`, a filename, a title, or a special case
inside the shared report.

## Choose The Smallest Extension Point

Use the existing `docs_subscope` default when a collection needs the standard
flat list/detail reader and standard Manage document actions.

Add a registered customisation when the collection needs additive behaviour
such as:

- projected collection or row metadata;
- another list filter;
- row decoration or an additional column;
- an additional collection, selection, or validated-detail action; or
- collection-specific lifecycle observation.

Add a different report engine only when the collection has fundamentally
different membership, navigation, or detail semantics. Do not add
scope/sub-scope branches to the shared engine or make a customisation replace
its core list, detail, validation, and navigation ownership.

## Identity And Report Host

The collection target is exactly:

```json
{"scope": "<scope-id>", "sub_scope": "<sub-scope-id>"}
```

A child-document target is exactly:

```json
{
  "scope": "<scope-id>",
  "sub_scope": "<sub-scope-id>",
  "doc_id": "<document-id>"
}
```

The indexed parent report host is an ordinary parent-scope document with:

```yaml
viewer_report: docs_subscope
viewer_report_access: local
viewer_report_subscope: <sub-scope-id>
```

The host selects the report engine and exact collection. The configured
sub-scope record selects the customisation. Config must not contain a module
path or executable name.

New sub-scopes receive this parent report host through the normal sub-scope
lifecycle. Child documents remain excluded from parent Index, Recent, and
search results; the indexed host is their durable entry point.

## Configuration Contract

No `report_customisation` field means the canonical default:

```json
{
  "sub_scope": "default",
  "title": "Default",
  "ui_statuses": ["draft", "done"],
  "public_projection": null
}
```

A customisation record has exactly `id` and `settings`:

```json
{
  "sub_scope": "tags",
  "title": "Tags",
  "public_title": "Concepts",
  "report_customisation": {
    "id": "analysis_tags",
    "settings": {
      "groups": ["subject", "domain", "form", "theme"]
    }
  }
}
```

Customisation IDs match `[a-z][a-z0-9_]*`. The Python registry validates the
ID and owns the exact settings schema. Unknown IDs, unknown fields, missing
fields, and invalid settings fail configuration loading.

Settings are server-side input. Browser config exposes only
`report_customisation: {"id": "..."}` for an access level that has a
registered browser implementation. Browser code consumes projected manifest
data, not raw settings.

## Canonical Default

The shared public-safe engine owns:

- configured collection validation and complete manifest membership;
- list, detail, empty, unavailable, invalid, and contained error states;
- NFKC-normalized case-insensitive title-prefix search;
- deterministic title-ascending or `last_updated`-descending order;
- by-ID payload loading and document identity validation;
- `subdoc` URL navigation and browser history; and
- the clean absence of management controls in public access.

The recency order puts missing or invalid timestamps after dated documents,
then uses title and `doc_id` as stable tie-breakers.

The Manage default contribution adds:

- status and non-viewable presentation from the compact Manage manifest row;
- collection-local checkbox selection;
- Select all, Clear, and Done selection controls;
- exact-collection **New document**, including for an empty collection;
- checked-ID **Prepare Package**;
- validated-detail **Copy Link** and Delete; and
- publication of the mounted exact collection or detail for the app-level
  Import owner.

Changing sort or filters does not rewrite checked IDs. Select all and
Shift-range operate on the current visible sorted projection. **Copy Link**
produces a Markdown link to the exact report host URL with `subdoc`; it does
not copy a source or management-service URL.

Import is an app-level action. It consumes the exact collection published by
the mounted report and is not registered as a report-toolbar action.

Customisations add to these behaviours. They do not remove, replace, or clear
the default contribution.

## Generated Data Contract

The builder owns the manifest, by-ID records, and browser route values. The
browser does not discover membership from source folders.

The public manifest contains viewable documents only:

```json
{
  "docs": [
    {"doc_id": "d-example", "title": "Example"}
  ]
}
```

The Manage manifest contains every collection document with compact lifecycle
metadata:

```json
{
  "docs": [
    {
      "doc_id": "d-example",
      "title": "Example",
      "ui_status": "draft",
      "viewable": false,
      "last_updated": "2026-08-01 08:00:00"
    }
  ]
}
```

An access-enabled customisation may add a strict root namespace and per-row
data:

```json
{
  "docs": [
    {
      "doc_id": "d-example",
      "title": "Example",
      "customisation": {"group": "subject"}
    }
  ],
  "customisation": {
    "id": "analysis_tags",
    "data": {"groups": ["subject", "domain", "form", "theme"]}
  }
}
```

Projection rules are strict:

- the descriptor ID and manifest customisation ID must match exactly;
- custom row data may target only a document already in that manifest;
- custom data cannot collide with builder-owned fields;
- invalid custom values fail the build;
- no configured customisation produces no custom namespace; and
- an empty collection still produces a valid empty manifest and report.

Public data is generated at the configured `public_projection`. Manage data is
generated with the working scope. External-local Manage routes use
`/docs/published/external/<scope>/<sub_scope>`; consumers use generated browser
config rather than constructing either route.

## Registration And Access

Registration is explicit on both sides of the build/browser boundary.

The Python definition supplies:

- `customisation_id`;
- `normalize_settings`;
- optional `document_groups` metadata support;
- `public_browser` access; and
- `manage_browser` access.

`project_report_customisation_manifest()` owns the allowed manifest projection
for the ID. A new projector must be added to its controlled dispatch; config
must never name a projector.

Each enabled browser access needs a lazy loader with the same ID:

- public loaders live in
  `site/docs-viewer/runtime/js/shared/docs-subscope-customisation-registry.js`;
- Manage loaders live in
  `docs-viewer/runtime/js/management/docs-viewer-management-subscope-customisation-registry.js`.

The Python access registry and JavaScript loader registries are tested for
exact agreement. At present `analysis_tags` is Manage-only and the public
loader registry is intentionally empty.

An absent descriptor resolves to the default. An unknown descriptor, missing
loader, invalid factory, descriptor/manifest mismatch, or callback failure is
a contained report error. It must not silently fall back to the default after
a customisation was explicitly selected.

## Browser Contribution Contract

A browser factory validates its descriptor and returns an object containing
only the callbacks it needs:

| Callback | Use |
| --- | --- |
| `createFilters(context)` | Return additive filter descriptors. |
| `renderRow(context)` | Populate detached leading, title-prefix, or trailing row hosts. |
| `renderListToolbar(context)` | Add collection or selection controls. |
| `renderSelectionToolbar(context)` | Add controls tied to the current immutable selection snapshot in Manage. |
| `renderDetailToolbar(context)` | Add controls only after a by-ID record has been validated. |
| `notify(event)` | Observe explicit collection-scoped lifecycle events. |

The shared report supplies detached contribution hosts. A host enters the DOM
only when populated. Manage renders the default owner first and the custom
owner second, preserving ownership and CSS boundaries.

`renderRow` may return `accessibleLabels`; the engine incorporates them into
the row's accessible name. It must not replace the row's document identity or
navigation.

A filter descriptor contains a unique `id`, a boolean-returning `matches`
function, a `render` function, and optionally `initialValue`. The render
callback receives its host, current value, and `setValue`. Filters receive the
complete normalized records and produce the visible projection only; they do
not redefine collection membership.

The current `analysis_tags` contribution is deliberately small: it reads
projected `data.groups` and row `customisation.group`, then contributes a group
filter. It is not the source of the default report behaviour.

## Action, Target, And Refresh Contract

Manage toolbar actions are declared through the supplied registrar. Each
definition requires:

| Field | Contract |
| --- | --- |
| `id` | Non-empty action identity. |
| `placement` | Must match `list-toolbar`, `selection`, or `detail-toolbar` host ownership. |
| `targetKind` | `collection`, `selection`, or `validated-detail`. |
| `emptyState` | `enabled`, `disabled`, or `omitted`. |
| `refreshEffect` | `none`, `collection`, `open-created-document`, or `commit-deleted-document`. |
| `capability` | Boolean or `{available, reason}`; omitted means available. |
| `handler` | Function accepting the registrar's exact validated target and refresh helpers. |

Target resolution is central and has no fallback:

- `collection` receives exact `{scope, sub_scope}`;
- `selection` receives exact `{scope, sub_scope, doc_ids}` with a frozen,
  de-duplicated checked-ID snapshot and is unavailable when it is empty; and
- `validated-detail` receives exact `{scope, sub_scope, doc_id}` only after the
  manifest and by-ID payload identities agree.

Handlers receive `refreshCollection`, `refreshDocument`, and the declared
`refreshEffect`. Creation must refresh and open the committed returned target.
Deletion must reconcile the committed exact target. A presentation failure
after a successful mutation must retry presentation only; it must not repeat
the mutation.

## Lifecycle Events

`notify(event)` receives explicit events scoped to `access` and `collection`:

| Event | Important fields |
| --- | --- |
| `mount` | `root` |
| `refresh` | complete immutable `documents`, projected customisation `data`, `reason` |
| `projection` | visible immutable `documents`, `filterValues`, `sort`, `reason` |
| `selection` | immutable `selection` with `active`, `checkedDocIds`, and `eligibleDocIds`, plus `reason` |
| `state` | `state`, nullable validated `target`, `reason`, `refreshDocument`, `refreshCollection` |
| `unmount` | `reason` |

Use `refresh` when logic needs complete collection membership and
`projection` when it needs the current filtered/sorted rows. Do not derive an
action target from an event's displayed text, URL, parent document, or current
selection unless that exact target is present in the event or action context.

## Public And Manage Isolation

The shared report and public registry must remain safe for the published
import graph. Public code must not import management modules, management
services, or Manage-only customisations.

Access is decided in the Python definition and reflected in browser config,
manifest projection, and the matching JavaScript registry. A Manage-only
customisation therefore has:

- no public descriptor;
- no public custom manifest namespace;
- no public loader; and
- no public import edge.

Do not rely on a hidden button or runtime branch as the isolation boundary.

## Adding A Customisation

Use this sequence:

1. Define the collection requirement and confirm that it is additive to the
   shared membership, list/detail, navigation, and default Manage behaviour.
2. Choose a stable snake-case ID and an exact settings schema.
3. Add the Python definition, settings normalization, access flags, optional
   document metadata choices, and controlled manifest projector.
4. Add a small browser factory and register a lazy loader only for each
   enabled access.
5. Add the sub-scope config record with the registered ID and valid settings.
6. Rebuild the affected scope and inspect browser config, public/Manage
   manifests, by-ID records, and the published report host.
7. Add focused configuration, builder, registry-boundary, module, route, and
   browser acceptance coverage in proportion to the added surface.

Before considering the extension complete, verify:

- the collection without a descriptor still uses the unchanged default;
- malformed config and projection data fail deterministically;
- browser descriptor and manifest IDs must agree;
- public and Manage access match the Python registry;
- empty, populated, filtered, detail, invalid-detail, and error states render;
- custom content is additive and uses detached owned hosts;
- every mutation receives an exact target and applies the declared refresh
  effect; and
- selection remains collection-local across sort, filters, refresh, and
  detail navigation.

## Current Reference Implementations

`studio/default` is the default-only reference. It has no customisation
descriptor and demonstrates the generic report and standard Manage actions.

`analysis/tags` is the registered customisation reference. Its Manage manifest
projects allowed groups and per-document group values; its Manage factory adds
the group filter. Its public Concepts projection remains on the shared default
and receives no Manage-only metadata or module.

These examples demonstrate the seam. Neither collection identity should be
hard-coded into the shared report.

## Verification Reference

The primary focused checks are:

```bash
python -m pytest \
  docs-viewer/tests/python/test_docs_scope_config.py \
  docs-viewer/tests/python/test_build_docs_subscopes.py \
  docs-viewer/tests/python/test_docs_viewer_public_runtime_boundaries.py -q

python docs-viewer/tests/smoke/docs_viewer_subscope_report_modules.py \
  --site-root .

python admin-app/commands/run_checks.py --profile docs-viewer-smoke
```

Use an isolated writable `DOTLINEFORM_PROJECTS_BASE_DIR` when a focused test
imports scope config or writes generated external-local data. After source
changes, rebuild the affected document/search projection and finish with
`git diff --check` plus a bounded diff review.
