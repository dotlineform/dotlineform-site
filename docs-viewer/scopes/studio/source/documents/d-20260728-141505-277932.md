# Sub-Scope Report List Filter Delivery

## Status And Order

Proposed as SSI-4, after
[Sub-Scope Package Preparation Delivery](/docs/?scope=studio&doc=d-20260728-115825-ae1461).
Implementation has not started.

SSI-4 is a shared report improvement. It does not widen SSI-2 Delete, SSI-3
package preparation, or the Docs Viewer search subsystem.

## Complete Outcome

The `docs_subscope` list view offers a search-style input that filters its
already loaded collection records, like the local filter on
[Tag Registry](/studio/tag-registry/).

Filtering is immediate and client-side:

```text
public: loaded manifest records
manage: supplied management-inventory records
```

It issues no search request, builds no index, fetches no by-ID payload for
matching, and does not make the child collection a separate search surface.

## Data And Matching Boundary

The report retains the complete loaded collection as source state and derives a
filtered row projection from it.

- Match only fields present in both projections: `doc_id` and title.
- Treat the query case-insensitively with normalized whitespace.
- An empty query shows the complete loaded collection.
- Status, viewability, body content, metadata not present in the manifest, and
  rendered detail HTML are not search inputs.
- The public manifest and manage inventory remain unchanged.

The exact token/substring rule and clear-control behavior are frozen at SSI-4.0
against realistic IDs and titles before UI implementation.

## Report State

- Filter state belongs to one mounted `{ scope, sub_scope }` report instance.
- Opening a filtered row and returning to the same list preserves the query.
- Changing collection or unmounting the report clears it.
- Filtering does not add URL state or change `subdoc`.
- The list status distinguishes matching rows from total loaded rows and
  provides a contained no-match state.
- Detail validation continues to use the complete loaded collection, not only
  the currently visible rows.

## Selection Interaction

SSI-4 follows SSI-3 so filtering must compose with collection selection:

- filtering never silently checks, unchecks, or prunes IDs;
- checked IDs remain the only package-action target even when a checked row is
  filtered out;
- Select all replaces the checked set with all currently visible eligible
  matching rows, clearing any checked IDs excluded by the filter; and
- Clear still clears the complete collection selection.

These rules keep filtering presentational and prevent a query from broadening
or silently changing a mutation/export target.

## In Scope

- One accessible search-style list filter in the shared report.
- Local matching over already loaded `doc_id` and title values.
- Matching/total count, clear, empty, no-match, detail-return, and remount
  behavior.
- Public and manage parity without a management import.
- Composition with the delivered contribution and selection boundaries.
- Focused pure filter, report-module, public-isolation, and realistic list
  evidence.

## Not In Scope

- Docs Viewer overall search or `build_search.py`.
- A sub-scope-specific search index, endpoint, route, or results page.
- Full-text body search or eager by-ID loading.
- Server-side pagination, ranking, highlighting, fuzzy matching, or saved
  queries.
- Filtering the parent Index, Recent, scope selector, or another report type.
