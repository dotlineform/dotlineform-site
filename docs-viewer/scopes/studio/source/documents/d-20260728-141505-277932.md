# Sub-Scope Report List Filter Delivery

## Status And Order

Active as SSI-4, after
[Sub-Scope Package Preparation Delivery](/docs/?scope=studio&doc=d-20260728-115825-ae1461).
SSI-4.0 and SSI-4.1 are accepted. SSI-4.1a absorbs first-class Tag Editor
**New Tag** document creation into this delivery and is implemented at its
review gate before generated projections continue.

SSI-4 gives public and Manage reports one generated-manifest loading model.
Both receive shared title-prefix filtering. The Analysis Tags Manage manifest
additionally carries document-owned group metadata for group-filter buttons.

SSI-4 does not widen SSI-2 Delete, SSI-3 package preparation, the Docs Viewer
search subsystem, or Tag Registry ownership.

## Complete Outcome

Every `docs_subscope` list offers a search-style input that filters its already
loaded records by title prefix. Typing `p` shows titles beginning with `p`;
typing `pri` narrows that result further.

The Manage report for `{ scope: analysis, sub_scope: tags }` additionally
offers **All tags**, **subject**, **domain**, **form**, and **theme** buttons
with counts, matching the established group-filter treatment on
[Tag Registry](/studio/tag-registry/). Public routes do not receive or render
the group facet and present the collection as **Concepts**, not Tags.

Filtering is immediate and client-side over one loaded manifest:

```text
public: manifest.json
        -> title-prefix filter

manage: manage-manifest.json
        -> title-prefix filter + optional document-group filter
```

It issues no search request, builds no search index, fetches no by-ID payload
for matching, and does not make the child collection a separate search surface.

The projection architecture is documented in
[Sub-Scope Public And Manage Manifests](/docs/?scope=studio&doc=d-20260728-205013-41deb8).

## Presentation Identity

The stable technical identity remains:

```text
scope: analysis
sub_scope: tags
```

`tags` remains in source paths, manifest paths, URL/report parameters, service
targets, configuration lookup, and Tag Editor integration. This delivery does
not rename or alias that identity.

Presentation is route-specific:

```text
Manage collection title: Tags
Public collection title: Concepts
```

The canonical sub-scope configuration owns both labels. The browser-config
builder resolves the Manage label into the local config and the public label
into the public config, so the shared report receives one already resolved
title for its route. Report headings, loading/count/empty states, Back copy,
filter labels, clear controls, and accessible names must use that resolved
title. Shared runtime code must not hardcode `tag` or `tags`, or derive
presentation copy from `sub_scope`.

The report-host document
`d-20260624-213316-478639` may safely change its source title, Markdown heading,
and introductory copy from **Tags** to **Concepts**. Its `doc_id`,
`viewer_report`, and `viewer_report_subscope` continue to own routing. Because
the host document has one shared source, **Concepts** will also be its title in
Manage Index, Recent, search, and rendered content. That accepted shared
document title is independent of the Manage report collection label **Tags**.

## Meaning Of Concept

`tag` remains the semantic-token kind and Tag Registry identity. Its resolver
continues to follow the registry relationships:

```text
text
  -> semantic token: tag
  -> Tag Registry tag
  -> work_id / series_id / doc_id
```

**Concept** names the additional editorial context represented by a linked
document. When SSI-4.1a makes Tag Editor create a tag and its document in one
transaction, the tag retains its registry identity while the document becomes
its concept context.
After creation, that document is canonical Docs Viewer content and may diverge
from the originating tag.

This language introduces no `concept` semantic token, registry, identifier,
resolver, relationship table, or route. The public report is called
**Concepts** because it presents contextual documents rather than Tag Registry
rows. A standalone sub-scope document can therefore also be presented as a
concept without acquiring a Tag Registry identity.

## Dual-Manifest Boundary

One sub-scope document build writes sibling projections from the same validated
source snapshot.

The working publication manifest retains only viewable public-safe records:

```json
{
  "docs": [
    {"doc_id": "<id>", "title": "<title>"}
  ]
}
```

Publish continues to copy that manifest to `site/` unchanged.

The local Manage manifest contains every source document:

```json
{
  "groups": ["subject", "domain", "form", "theme"],
  "docs": [
    {
      "doc_id": "<id>",
      "title": "<title>",
      "ui_status": "",
      "viewable": true,
      "group": "subject"
    }
  ]
}
```

`groups` is present only when the owning sub-scope config defines an ordered
document-group vocabulary. `group` is optional on each document.

The builder writes the Manage projection to:

```text
docs-viewer/scopes/<scope>/published/documents/sub-scopes/<sub-scope>/manage-manifest.json
```

Manage browser config points to that local file. Public browser config keeps
pointing to the public-safe manifest. The publication gate must explicitly
exclude the Manage manifest.

The shared report loads both through the same manifest path and normalization
mechanism. The current source-backed `GET /docs/sub-scope-documents` override is
retired as the report list source after an exact consumer audit. It must not
remain as a silent fallback.

## Document Group Ownership

Analysis Tags documents gain one optional scalar front-matter field:

```yaml
group: subject
```

The configured allowed values are:

```text
subject
domain
form
theme
```

The Analysis `tags` sub-scope config owns those values and their display order.
Blank is valid and removes the field.

`group` is Docs Viewer document metadata:

- the source model reads and validates it;
- the focused sub-scope **Edit metadata** workflow hydrates it and presents the
  configured values;
- metadata save writes or removes it through the exact
  `{ scope, sub_scope, doc_id }` target;
- the ordinary targeted sub-scope build updates the Manage manifest and local
  detail payloads; and
- the public manifest and public detail projection omit it.

The metadata workflow rejects an array, an unknown value, or `group` on a
collection that has no configured document groups. Parent-document metadata
behavior remains unchanged. Group-only and status-only writes follow the
existing recent-edit rule: they change the source revision but do not advance
`last_updated`. Title, summary, or body changes continue to advance it.

## Metadata Editing Boundary

Sub-scope documents use a focused metadata editor rather than adding
sub-scope-only switches and fields to the ordinary document modal.

The Analysis Tags recipe contains the metadata valid for those documents,
including `group`, and has no document-parent control. Its effective
`ui_status` choices are resolved for the exact sub-scope from Docs Viewer
configuration and returned with the metadata read; the editor does not assume
the ordinary-document status list. Analysis Tags may initially configure the
same values deliberately, while retaining independent ownership and the
ability to diverge later.

This is a UI and metadata-contract boundary, not a duplicate persistence path.
The ordinary and sub-scope editors reuse the exact-target metadata read/write
transport, field controls where suitable, revision protection, source mutation,
and rebuild transaction. The service validates the fields and choices allowed
for `{ scope, sub_scope }`; hiding a control in the browser is not the
authorization boundary.

SSI-4 does not introduce an arbitrary schema-driven form framework or a second
sub-scope metadata endpoint. The focused workflow belongs here because
document-owned group must be editable before the Manage report can filter its
generated projection.

## No Tag Registry Synchronization

`doc.group` and `tag.group` are independent canonical fields in different
domains.

A one-time migration may use the current Tag Registry relationship to seed the
245 generated Analysis Tag documents:

```text
tag_registry row --doc_id--> generated document
tag.group        --seed once--> doc.group
```

The three pre-existing independent documents remain without `group` so their
classification can be chosen explicitly through Docs Viewer later.

The Tag Editor **New Tag** path makes Registry and document creation one
first-class transaction. The new document receives its initial `group` from the
new tag and the new Registry row receives its immutable `doc_id`.

These are two create-only seed paths, not synchronization:

- the migration initializes the 245 existing generated documents once; and
- SSI-4.1a makes each future tag creation initialize its new document once.

After an Analysis Tag document exists:

- ordinary document builds do not read Tag Registry;
- later Tag Editor edits do not mutate document group or trigger a Docs Viewer
  build for that purpose;
- Docs Viewer does not compare, repair, or synchronize the two fields;
- a later `tag.group` change leaves `doc.group` unchanged; and
- neither seed path overwrites an existing document or becomes a repair or
  synchronization path.

A document that does not fit one group can remain ungrouped and appears under
**All tags**. Multiple document groups are not introduced by this delivery.

## Matching And Facet Semantics

The report retains the complete loaded manifest as source state and derives a
visible row projection from it.

- Search matches the normalized displayed title only.
- Matching is case-insensitive and requires the whole title to begin with the
  normalized query.
- `doc_id`, status, viewability, group, body content, other metadata, and
  rendered detail HTML are not text-search inputs.
- An empty query shows every row allowed by the active group.
- **All tags** removes only the group constraint; it does not clear the query.
- Choosing a group preserves the query and shows the intersection of both
  filters.
- Clearing the search preserves the active group.
- Group-button counts describe the complete Manage manifest: **All tags**
  counts every document, while each group counts documents carrying that
  document-owned value.
- Ungrouped documents appear only under **All tags**.
- The list status distinguishes visible matches from the complete loaded
  collection and provides a contained no-match state.

## Report State

- Filter state belongs to one mounted `{ scope, sub_scope }` report instance.
- Opening a filtered row and returning to the same list preserves the query and
  active group.
- Changing collection or unmounting the report clears it.
- Filtering does not add URL state or change `subdoc`.
- Detail validation continues to use the complete loaded manifest, not only
  currently visible rows.
- Public collections have no active group state or group controls.

## Selection Interaction

SSI-4 follows SSI-3 so filtering must compose with collection selection:

- filtering never silently checks, unchecks, or prunes IDs;
- checked IDs remain the only package-action target even when a checked row is
  filtered out;
- Select all replaces the checked set with every currently visible eligible row
  after applying both filters, clearing checked IDs excluded by either filter;
  and
- Clear still clears the complete collection selection.

These rules keep filtering presentational and prevent a query from broadening
or silently changing a mutation/export target.
