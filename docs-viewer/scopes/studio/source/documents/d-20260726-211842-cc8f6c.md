# Tag-document linking

## Relationship Contract

A `tag_registry_v5` row owns an ordered `doc_url` array of zero or more
canonical Docs Viewer locations:

```json
{
  "tag_id": "moss",
  "group": "subject",
  "doc_url": [
    "/analysis/?doc=d-20260624-213316-478639&subdoc=d-20260727-225608-63967a"
  ],
  "updated_at_utc": "<timestamp>"
}
```

```text
tag registry row
  -> optional ordered location references
      -> independently owned documents and report placements

other tag registry rows
  -> may reference the same exact locations
```

- `doc_url: []` is the unlinked state. The field itself is required.
- URL order is meaningful presentation order. The same exact URL cannot repeat
  within one row, but may be shared by any number of tags.
- A URL identifies the chosen public placement, not only the source document.
  One document can therefore have several valid locations through different
  report hosts.
- Documents contain no `tag_id` back-reference and may exist without a tag.
  Neither side has exclusive ownership of the other.
- Deleting a tag leaves every referenced document intact. Deleting or
  unpublishing a document does not rewrite the Registry and may leave an
  unavailable URL.
- Tag group and document group are independently canonical. Creation may seed
  document metadata once; later edits never compare, synchronize, repair, or
  trigger builds across those owners.
- Title and content are presentation, never association identity. No title
  match, selected parent, displayed document, or alternate route may silently
  replace a stored URL.

## Creation And Editing

New Tag creates one Registry row and one fresh Analysis `tags` source document
as one transaction. The new document receives its immutable ID, tag title,
submitted group metadata, public visibility, and a heading containing the tag
ID. Its canonical Analysis placement is stored at `doc_url[0]`.

Creation validates only the new candidate and its configured destination. It
does not inspect existing URL arrays for uniqueness, resolution, or repair.
The create-only source write is the collision boundary and will not overwrite
an existing destination.

Edit Tag keeps `tag_id` immutable and submits the complete accepted scalar
group plus ordered URL array. The UI can append one exact published Analysis
location returned by the shared provider or remove one exact URL from the
draft. Save commits the complete array atomically; Close discards the draft.
It does not create, edit, delete, or repair a document.

The Registry schema validates supported canonical URL shape and within-row
duplicates, but deliberately does not require current provider membership.
This lets an association selected moments earlier survive publication churn
and lets an unavailable stored URL remain visible and removable.

## Resolution And Presentation

The Registry stores no document or report title. Studio resolves current
presentation from compact public `docs_document_locations_v1` projections
built from each owning scope's published search, report, and sub-scope data.
Management/source-only documents are absent.

The table and Edit Tag modal render current titles in stored order. A resolving
title opens against Studio's configured public-preview origin, so local work
uses the site preview server rather than the Studio server. An unresolved URL
is shown as `Unavailable document`, retains its exact href, and may be removed.

The shared provider covers published Analysis and Library locations. The Tag
Registry picker deliberately requests Analysis only, shows title-only results,
and exposes no free-form URL or document-ID input. Schema support for canonical
Library and Studio routes does not imply that the current Tag Registry UI can
author them.

## History And Boundaries

The one-off [Tag Document Bootstrap Delivery](/docs/?scope=studio&doc=d-20260727-224141-d28e4c)
created distinct Analysis documents for the 245-row cutover set and initially
linked them through scalar `doc_id` values. The subsequent
[Tag Link Management Delivery](/docs/?scope=studio&doc=d-20260729-151446-09489e)
migrated those references to ordered canonical URLs, retired tag-row
descriptions, and delivered current inspection, append, and removal behavior.
Distinct bootstrap allocations describe that migration, not an ongoing
one-tag-to-one-document rule.

There is no automatic stale-link repair, bulk mutation, drag reorder, or
Library/Studio picker workflow. Tag semantic-token support is also separate;
if added later it must consume an explicit resolving canonical location and
must not infer one from mutable text or UI context.

Docs Viewer owns document lifecycle and dense source-management controls:
[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65).
The canonical Registry schema/write boundary lives in
[Tag Source Data](/docs/?scope=studio&doc=d-20260419-000000-86255c), and the
current tag workflow lives in
[Tag Registry](/docs/?scope=studio&doc=d-20260331-000000-4519a5).
