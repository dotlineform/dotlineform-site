# Tag-document linking

## Result

A canonical tag registry record may contain a `doc_id` identifying a document
in the Analysis `tags` sub-scope. The field is optional, and the relationship
does not give the tag exclusive ownership of the document: more than one tag
may reference the same document.

The registry owns the one-way association. A document does not carry a
`tag_id` back-reference, and documents that are not referenced by a tag remain
valid. Either side may be deleted independently, so a document can become
unreferenced and a registry link can become stale.

The document owns long-form contextual meaning. The registry `description`
remains independent concise metadata: it may seed a newly created document
once, but neither side synchronizes later edits to the other.

A linked registry record is:

```json
{
  "tag_id": "moss",
  "group": "subject",
  "description": "<independent registry description>",
  "doc_id": "d-<immutable document ID>",
  "updated_at_utc": "<timestamp>"
}
```

An unlinked record omits `doc_id`.

## Relationship contract

```text
tag registry record
  -> optional doc_id
      -> one existing Analysis/tags document
      -> or stale after independent document deletion

other tag registry records
  -> may reference the same document
```

- A registry record may omit `doc_id`.
- When present, `doc_id` is an immutable Docs Viewer document identity intended
  to resolve within the configured Analysis `tags` sub-scope.
- Multiple registry tags may reference the same document. The link is a
  reference, not an ownership or one-tag-to-one-document constraint.
- Documents contain no `tag_id` field and may exist without a registry
  reference.
- Deleting a tag leaves its document intact; the document may still be
  referenced by other tags.
- Deleting a document does not update the tag registry. It may leave a stale
  `doc_id`.
- `tag_id` is not editable through Edit Tag.
- Neither document title nor content is used to infer or repair an association.

The checked-in registry currently has a nonblank, distinct `doc_id` on every
row because of the completed bootstrap and the current New Tag workflow. That
is the present dataset and workflow output, not the relationship cardinality.

## Completed one-off bootstrap

The bootstrap took the 245 then-current flat registry rows, each without
`doc_id`, allocated one new immutable ID per row, created 245 Analysis `tags`
documents, and stored the IDs in `tag_registry_v4`.

Those allocated IDs were deliberately distinct so the migration could create
new source files safely. The three pre-existing Analysis `tags` documents were
left independent. Neither fact makes uniqueness between registry references an
ongoing invariant.

Each generated document received the tag ID as its initial title, the registry
description as one-time body content, and public visibility. The later
Sub-Scope Report List Filter delivery seeded the registry group into
document-owned `group` metadata once. Registry description/group and document
content/group are independent after those seeds.

The sub-scope manifest remains the existing minimal public document-list
contract. Public rows remain `{ doc_id, title }`; canonical tag data is not
projected into them.

## Current creation and mutation behavior

- New Tag creates a fresh Analysis `tags` document and the registry row in one
  transaction. The new row therefore receives a nonblank ID that is distinct
  from every existing document and registry ID.
- The new document receives initial title, group, description content, and
  visibility from the creation request. Later registry and document edits do
  not synchronize.
- Ordinary Edit Tag changes scalar group and description while preserving the
  existing `doc_id`. The modal does not expose, clear, replace, repair, or open
  the association.
- Tag deletion removes the registry row and its existing alias/assignment
  effects. It does not delete the document.
- Document deletion does not consult or update the registry.

The current New Tag planner also preflights the complete registry and rejects a
missing, non-immutable, duplicate, or non-resolving existing `doc_id`. This is a
stricter implementation boundary of the current create workflow. It must be
relaxed before the UI can author the optional or shared-reference states
allowed by the relationship contract; it does not make those states invalid
registry relationships.

There is currently no focused association-inspection or repair workflow.
Where a resolving link is consumed, its detail URL is derived rather than
stored:

```text
/docs/?scope=analysis&doc=d-20260624-213316-478639&subdoc=<document ID>
```

## Related Docs Viewer workflow

Dense sub-scope navigation and Markdown source editing belong to
[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65),
not this feature. That workflow was the management prerequisite for the
completed bootstrap. Tag-document linking owns the optional registry
association and derived public deep link; Docs Viewer owns the document
lifecycle.

Collection-local selection, document controls, and adoption by applicable
collection functions belong to
[Sub-Scope Index](/docs/?scope=studio&doc=d-20260728-113139-285eae).
The Analysis `tags` collection is a consumer and review surface for that
generic Docs Viewer feature, not its owner.

## Downstream semantic-token dependency

A future Tag semantic-token target can derive a stable destination from a
resolving registry `doc_id` and the public `subdoc` route. An unlinked or stale
association has no available document destination. Multiple tags may resolve
to the same destination.

Tag semantic-token support remains separate follow-on work. It must not infer
or repair a target from mutable document title, description, or content, and it
must not add placeholder target-lookup rows without a usable `href`.
