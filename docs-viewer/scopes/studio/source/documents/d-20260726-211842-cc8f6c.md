# Tag-document linking

## Result

Every canonical tag registry record contains one required, unique `doc_id`
that resolves to an existing document in the Analysis `tags` sub-scope.

The registry owns the one-way association. A document does not carry a
`tag_id` back-reference, and documents that are not referenced by a tag remain
valid. Tag meaning lives in document content rather than a registry
`description`.

The final registry record is:

```json
{
  "tag_id": "moss",
  "group": "subject",
  "doc_id": "d-<immutable document ID>",
  "updated_at_utc": "<timestamp>"
}
```

## Prerequisites

[Flat Tag Identity](/docs/?scope=studio&doc=d-20260727-110004-ab0433) must
complete first. It produces globally unique flat `tag_id` values, verifies the
namespaced collision decisions, retains exactly one scalar group per tag, and
deliberately retains one registry description per resulting tag for this
feature to transfer.

[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65)
must complete before the one-off migration. Creating a large document set is
not a useful outcome while Docs Viewer management cannot navigate, view, and
source-edit that set coherently.

[Tag Vocabulary Import Retirement](/docs/?scope=studio&doc=d-20260726-214250-28ae69)
is an indirect prerequisite through Flat Tag Identity. Obsolete bulk
replacement paths must not be taught either new schema.

## Relationship contract

```text
tag registry record
  -> required unique doc_id
  -> one existing Analysis/tags document
```

- Every registry record has exactly one nonblank `doc_id`.
- The referenced ID must resolve within the configured Analysis `tags`
  sub-scope.
- No two registry tags may reference the same document.
- Documents contain no `tag_id` field and may exist without a registry
  reference.
- Deleting a tag leaves its document intact and unreferenced.
- Deleting a referenced document is blocked.
- Renaming a tag preserves its document association.
- Neither document title nor content is used to infer or repair an association.

## One-off migration contract

The migration is driven only by flat tag registry records and their explicit
document-ID field. For each tag without that field, it allocates a new immutable
`doc_id`, creates one document in the Analysis `tags` sub-scope, and writes the
new ID back to that registry record.

Each new document starts with:

```markdown
---
doc_id: <allocated immutable document ID>
title: "<tag_id>"
added_date: <migration timestamp>
last_updated: <migration date>
parent_id: ""
viewable: true
---
# <tag_id>

**<group>**

<tag registry description>
```

The registry `description` is copied once as initial content. After every tag
has a valid unique document association and the created sources are verified,
`description` is removed from the registry schema and its create, edit, sort,
API, mutation, activity, and test surfaces. There is no synchronization
contract after that transfer.

The migration explicitly chooses `viewable: true` because the tag documents are
intended to be public. This is an outcome choice, not a technical limitation:
the migration could author `viewable: false`, and either value could later be
changed directly in source. This feature does not add a visibility control.

Migration remains blocked until the management prerequisite is complete.
External source editing is available, but it is not a substitute for a usable
Docs Viewer workflow for the resulting document set.

The three documents already in the `tags` sub-scope are not inspected, matched,
reused, moved, or updated by the migration. Their unique `doc_id` values remain
their identities. Unless a registry record is linked to one separately through
an explicit document ID, they remain independent documents and do not reduce
the migration's create set.

The sub-scope manifest remains the existing minimal public document-list
contract. It may contain hundreds of records, so this feature does not project
canonical tag data into every public row. The manifest does not receive
`tag_id`, `group`, `groups`, or registry description, and this feature adds no
group filtering or styling to the report.

## Ongoing creation and mutation contract

The required relationship continues after the migration:

- New Tag must create or resolve an Analysis `tags` document before committing
  the registry row. Creating the document first is safe because unreferenced
  documents are allowed; committing a tag first would violate the invariant.
- A tag edit may replace `doc_id` only with an existing, currently unreferenced
  Analysis `tags` document. It cannot clear the field.
- A tag delete removes only the registry record and its assignment/alias effects
  already owned by the tag mutation planner; it does not delete the document.
- Future document-delete workflows must reject a document referenced by the
  registry.

The Tag Registry modal is the association inspection and navigation surface:

- It exposes the required document ID and can replace it within the constraints
  above.
- Save persists the exact ID through the ordinary tag edit mutation. It does
  not update the document.
- The field accepts immutable Docs Viewer `doc_id` values for the Analysis
  `tags` sub-scope.
- Open derives
  `/docs/?scope=analysis&doc=d-20260624-213316-478639&subdoc=<document ID>`;
  the URL is not stored in the registry.
- Open is available only when the current field value resolves to a listed
  Analysis `tags` document. An invalid value shows a contained unavailable
  state and does not render a dead link.
- The modal can inspect, replace, save, and open an association. It does not
  edit or delete document content.

## Related Docs Viewer workflow

Dense sub-scope navigation and Markdown source editing belong to
[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65),
not this feature. That feature is a prerequisite for the migration.
Tag-document linking then owns the public document creation, registry
association, and public deep link.

## Downstream semantic-token dependency

A Tag semantic-token target cannot be registered until it can resolve to a
stable, workable destination. The registry `doc_id` association and public
`subdoc` URL produced by this feature provide that destination.

Tag token work therefore waits for this feature and its prerequisites. It must
not resolve a target by mutable document title or content, and it must not add
placeholder target-lookup rows without a usable `href`.
