# Tag-document linking

## Prerequisites

[Tag Vocabulary Import Retirement](/docs/?scope=studio&doc=d-20260726-214250-28ae69)
removes bulk registry and alias import before this feature extends the per-tag schema.
It is a separate Roadmap feature and must complete before the document
association delivery changes registry records.

[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65)
must complete before the one-off migration. Creating a large document set is
not a useful outcome while Docs Viewer management cannot navigate, view, and
source-edit that set coherently.

tags are defined in tag registry `studio/data/canonical/tags/tag-registry.json` and may also have associated documentation in `docs-viewer/scopes/analysis/source/sub-scopes/tags/documents`.

the documentation is not intended to be kept in sync with the summary information in the tag registry, nor be deleted when a tag is deleted from the registry.

the following is however needed:

- a one-off process to create a document for each existing tag whose registry record does not already contain an explicit document ID.
- the document link recorded in the tag registry record, and editable in the Studio tag registry modal for a tag.
- a way of linking from a tag in `/studio/tag-registry/` to the document in `/docs/?scope=analysis...`

## One-off migration contract

The migration is driven only by tag registry records and their explicit
document-ID field. For each tag without that field, it allocates a new immutable
`doc_id`, creates one document in the Analysis `tags` sub-scope, and writes that
new ID back to the tag record.

Each new document starts with:

```markdown
---
doc_id: <allocated immutable document ID>
title: "<tag label>"
added_date: <migration timestamp>
last_updated: <migration date>
parent_id: ""
group: "<tag group>"
viewable: true
---
# <tag label>

<tag registry description>
```

The registry `description` is copied once as the initial paragraph. It is seed
content, not a synchronization contract.

The migration explicitly chooses `viewable: true` because the tag documents are
intended to be public. This is an outcome choice, not a technical limitation:
the migration could author `viewable: false`, and either value could later be
changed directly in source. This feature does not add a visibility control.

Migration remains blocked until the management prerequisite is complete.
External source editing is available, but it is not a substitute for a usable
Docs Viewer workflow for the resulting document set.

The three documents already in the `tags` sub-scope are not inspected, matched,
reused, moved, or updated by the migration. Their unique `doc_id` values remain
their identities. Unless a registry record is linked to one separately through
an explicit document ID, they remain independent documents and do not reduce
the migration's create set.

Neither title nor `title + group` is ever used for reconciliation. `group`
exists only to support filtering, visible group presentation, and styling in
the Tags report.

## Tag edit modal contract

The existing Tag Registry edit modal is the initial association and navigation
surface.

- It exposes one optional editable document-ID field.
- Save persists the exact ID, or clears it when empty, through the ordinary tag
  edit mutation. It does not update the document.
- The field accepts immutable Docs Viewer `doc_id` values for the Analysis
  `tags` sub-scope.
- Open derives
  `/docs/?scope=analysis&doc=d-20260624-213316-478639&subdoc=<document ID>`;
  the URL is not stored in the registry.
- Open is available only when the current field value resolves to a listed
  Analysis `tags` document. Empty or unresolved values show a contained
  unavailable state and do not render a dead link.
- The modal can set, change, clear, save, and open an association. It does not
  create, import, edit, or delete sub-scope documents.

## Related Docs Viewer workflow

Dense sub-scope navigation and Markdown source editing belong to
[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65),
not this feature. That feature is a prerequisite for the migration.
Tag-document linking then owns the public document creation, registry
association, and public deep link.

## Downstream semantic-token dependency

A Tag semantic-token target cannot be registered until it can resolve to a
stable, workable destination. The registry `doc_id` association and public
`subdoc` URL produced by this feature provide that destination.

Tag token work therefore waits for this feature and its prerequisites. It must
not resolve tags by mutable label or `title + group`, and it must not add
placeholder target-lookup rows without a usable `href`.

there is also currently a structural problem: the registry recognises that tags are in groups, and a tag label can be in multiple groups. this is why `tag_id` is a concatination of `group` and `label`. the current sub-scope documents do not recognise this structure. documents can be listed in `/docs/?scope=analysis&doc=d-20260624-213316-478639` but cannot be filtered (or styled) by group. To do this, we would need an additional front-matter field 'group'.

## Current schema

tag-registry:
```
{
  "tag_id": "subject:bird",
  "group": "subject",
  "label": "bird",
  "description": "Depicted bird: an observable element the viewer can point to. Useful for content-level linking across media; keep separate from domain framing and theme inference to reduce ambiguity.",
  "updated_at_utc": "2026-03-03T17:43:04Z"
}
```

document:
```
---
doc_id: d-20260624-204534-0d6ae2
title: "bird"
added_date: 2026-06-24 20:45:34
last_updated: 2026-06-24
parent_id: ""
---
```
