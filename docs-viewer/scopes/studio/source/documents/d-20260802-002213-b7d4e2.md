# TST-1 — Tag Semantic Token Delivery

## Status And Purpose

Proposed as **TST-1**, a standalone delivery beneath
[Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61). It is not
active and does not authorize implementation.

The delivery adds Tag as a second Semantic Tokens family after the Tag Registry
acquired canonical document associations. It keeps Tag separate from
Catalogue: a Work, Series, or Moment resolves to one concrete catalogue
destination, while a Tag resolves to its complete ordered set of associated
documents.

## Complete Outcome

In Manage Source, an author selects meaningful text, chooses **Add tag token**,
searches canonical Tags and aliases, and selects one exact canonical `tag_id`.
The built document retains the authored text and follows it with the Tag's
current associated document links:

```text
nerve ([Nerve], [Neural pathways])
```

The source records stable Tag identity rather than copying document URLs. A
normal rebuild resolves the current ordered `doc_url[]` projection, emits the
bounded parenthesised link group, and records one Tag-token occurrence in the
scope usage index. The public document contains ordinary resolved links and no
Tag Registry, target lookup, or client-side semantic resolver.

## Fixed Product Direction

### Separate Family And Action

- Tag is a separate Semantic Tokens family with its own **Add tag token**
  action, discovery modal, parser contribution, and Info view.
- Tag is not added to **Add catalogue token** search. Catalogue continues to
  combine only Work, Series, and Moment.
- The Tag family reuses the generic source selection, guarded range mutation,
  modal lifecycle, token registry, target lookup, build projection, usage
  index, report, and Broken Links seams.
- The canonical identity is `tag_id`. Aliases are discovery inputs only and
  always resolve to a selected canonical Tag.
- Group and current association titles are distinguishing lookup context; they
  are not copied into source identity.

### Associations Are The Target

- A Tag target is its complete ordered `doc_url[]` association set. There is no
  separate Tag landing page and no privileged primary document.
- `doc_url[0]` occupies the first position in display order; it is not a unique
  canonical destination and not evidence of document ownership.
- The Tag Registry remains authoritative for canonical Tag identity, group,
  aliases, and association order. Semantic Tokens consume a focused generated
  target projection and do not inspect or mutate canonical Tag JSON directly.
- Document-location projection supplies current public-safe titles and URLs.
  A token never infers an association from document title, content, current
  route, report host, or neighbouring source.
- The complete association set remains available to Manage target and usage
  data even when the rendered inline group has a smaller display limit.

## Source And Authoring Alternatives

TST-1.0 must choose between two deliberate source contracts. Both produce the
same visible result and preserve immutable canonical Tag identity.

### Option A — Wrapped Selection

The action replaces the captured selection with a token containing the
occurrence text:

```markdown
[[tag:tag:nerve|nerve]]
```

The builder renders:

```text
nerve ([Nerve], [Neural pathways])
```

This option fits the current three-part Semantic Token grammar. The token owns
both the visible occurrence text and Tag identity; its Info view can edit the
occurrence text while keeping identity readonly.

### Option B — Postfix Token

The action leaves the selected prose in place and inserts a Tag marker after
it:

```markdown
nerve [[tag:tag:nerve]]
```

The postfix token renders only the parenthesised association group:

```text
nerve ([Nerve], [Neural pathways])
```

This option matches the literal authoring model that the association group
follows existing prose rather than replacing it. It requires a reviewed
family-specific occurrence contract because the current grammar requires a
Title field. TST-1 must not infer, rewrite, or repair the prose before a postfix
token after ordinary source edits. Authored proximity is accepted as written;
the author remains responsible for keeping it intelligible.

TST-1.0 must freeze the exact postfix syntax, whitespace ownership, punctuation
behaviour, empty-selection behaviour, caret activation range, Info-view fields,
and source-removal result. It must compare these costs with the wrapped form
before selecting either option.

## Association Rendering

- The rendered suffix is one space followed by a parenthesised,
  comma-delimited sequence of ordinary document anchors.
- Link labels use resolved document titles, not Tag IDs, array indexes, source
  filenames, or copied occurrence text.
- Links follow exact `doc_url[]` order. They are never alphabetized or ranked
  during target generation or rendering.
- The provisional inline display limit is three links. TST-1.0 must freeze the
  exact limit and the explicit overflow treatment; truncation must never be
  silent.
- An over-limit occurrence should retain the complete ordered association set
  in Manage data and expose the omitted count in rendered or report state. The
  freeze decides whether excess links are represented by a non-link count,
  accessible disclosure, or an unavailable/over-limit result.
- The zero-association, all-stale, and partially unavailable cases require
  explicit fixtures. The implementation must not silently select a different
  association, reorder the set, fabricate a landing page, or imply that a
  partial set is complete.
- Public output is resolved at build time. Public readers receive ordinary
  anchors and no registry, lookup, usage index, or resolution runtime.

## Tag Registry Ordering

Association order becomes user-visible whenever a Tag token is rendered,
especially when a display limit applies. TST-1 therefore includes an explicit
way to change `doc_url[]` order in **Edit Tag**.

- Reordering edits the complete local association draft and is committed by
  the existing atomic Tag mutation boundary.
- The UI must expose deliberate accessible ordering controls. TST-1.0 decides
  between move-up/move-down controls and another equally explicit interaction;
  drag-only ordering is insufficient.
- Removing, adding, and reordering remain independent draft operations until
  Save. Close discards all of them.
- No automatic title sort, availability sort, recently-used ranking, or
  semantic-token usage may rewrite canonical order.
- Ordering conveys presentation priority only. It does not transfer document
  lifecycle ownership to Tag Registry or synchronize a document with Tag
  identity.
- TST-1.0 must decide whether the display limit is presentation-only or whether
  Tag Registry should also enforce an association-count limit. The starting
  assumption is a presentation limit because canonical associations may have
  non-token consumers.

## Target And Usage Projection

The current Semantic Tokens target row assumes one workable `href`. TST-1 must
extend that contract deliberately rather than placing one Tag URL into the
Catalogue shape.

A proposed Tag target row contains:

```json
{
  "family": "tag",
  "target_type": "tag",
  "target_id": "nerve",
  "title": "nerve",
  "meta": ["subject"],
  "associations": [
    {"title": "Nerve", "href": "/analysis/?doc=...&subdoc=..."},
    {"title": "Neural pathways", "href": "/analysis/?doc=...&subdoc=..."}
  ]
}
```

The exact field names and unavailable-record representation remain a TST-1.0
freeze decision. Required semantics are:

- one lookup row per canonical Tag;
- ordered associations resolved from the exact stored URLs;
- canonical aliases available to discovery without becoming target identity;
- one usage occurrence per authored Tag token, not one fabricated token per
  linked document;
- enough usage data to distinguish the complete target set, rendered subset,
  display limit, and overflow count; and
- exact source document and source range for report navigation and targeted
  build preservation.

The Semantic Tokens report must find where the Tag token occurs without
duplicating the occurrence merely because the Tag has several associations.
Docs Broken Links remains the read-only diagnosis owner for unknown Tags and
the association failure states frozen in TST-1.0.

## Delivery Discipline

TST-1 is one complete second-family vertical slice. It should extend the proven
generic Semantic Tokens seams only where Tag's one-to-many target genuinely
requires it. It must not turn the registry into executable plugins, combine
Tag and Catalogue search, add a generic graph, create a public Tag application,
or move Tag Registry authority into Docs Viewer.

TST-1.0 must record the exact proposed files, reused seams, and rough
production/test diff per later checkpoint. Any proposed generic multi-target
framework must remain no larger than the Tag consumer needs and stop for review
before implementation.

## Likely Authority To Inspect

This is a routing map for TST-1.0, not a frozen file-change list.

## Delivery Steps

### TST-1.0 — Trace And Freeze The Tag Family

- [ ] Trace current Tag Registry ordering, aliases, document-location
  resolution, Semantic Token grammar, target lookup, Source contributions,
  builder projection, usage preservation, report, Broken Links, and public
  isolation.
- [ ] Compare wrapped-selection and postfix-token fixtures, including source
  insertion, whitespace, punctuation, manual edits, Info activation/update,
  removal, save, rebuild, and public output.
- [ ] Freeze canonical Tag identity, alias discovery, complete association-set
  semantics, ordered lookup shape, zero/stale/partial failure behaviour, and
  the rule for resolved usage.
- [ ] Freeze the inline display limit, over-limit presentation, exact link
  labels, and whether the limit constrains only rendering or also canonical
  association count.
- [ ] Freeze Edit Tag reordering interaction and complete-draft Save behaviour.
- [ ] Record the exact files, reused seams, rough production/test diff, and any
  generic-contract expansion before implementation approval.

**Checkpoint:** reviewed fixtures cover wrapped and postfix source, collapsed
and non-empty selections, punctuation, one/two/three/over-limit associations,
reordered links, zero associations, stale first/middle/last associations,
duplicate visible titles, alias discovery, targeted rebuild, usage rows, and
public output. Stop before implementation.

### TST-1.1 — Tag Lookup And Multi-Target Projection

- [ ] Add the focused Tag target generator over canonical Registry, aliases,
  and public-safe document-location projections.
- [ ] Extend the target schema and shared consumers only as required for one
  ordered association set.
- [ ] Register the Tag family and implement tolerant build rendering for the
  chosen source contract, display limit, and frozen failure states.
- [ ] Generate one usage occurrence with complete and rendered association
  evidence while preserving untouched documents during targeted builds.
- [ ] Keep Tag canonical data, aliases, target lookup, and usage data out of
  public output.

**Checkpoint:** focused lookup, parser, builder, usage, targeted-build, and
public-isolation evidence passes for the frozen fixtures. Stop for approval
before TST-1.2.

### TST-1.2 — Authoring, Info, And Association Ordering

- [ ] Add the separate **Add tag token** Source action and Tag discovery modal
  with canonical ID, alias, group, and association context.
- [ ] Insert the frozen wrapped or postfix source form through captured,
  revision-guarded Source mutation only.
- [ ] Add the family-specific Info view with immutable identity, current target
  context, permitted occurrence editing, and exact-range removal.
- [ ] Add accessible association reordering to the Edit Tag draft without
  changing its atomic complete-array mutation boundary.
- [ ] Preserve validation, unavailable-target, and stale-range errors without
  adding redundant successful-mutation status messages.

**Checkpoint:** focused module and route evidence passes, and manual acceptance
adds a Tag token from selected prose, reorders two associated documents, saves,
rebuilds, and observes the same new order in the parenthesised links. Stop for
approval before TST-1.3.

### TST-1.3 — Reports, Regression, And Transfer

- [ ] Extend the Semantic Tokens report and Docs Broken Links diagnosis for the
  frozen Tag occurrence and association states.
- [ ] Prove Catalogue Work, Series, and Moment insertion, Info, rendering,
  usage, and unresolved behaviour are unchanged.
- [ ] Verify one/two/three/over-limit associations, ordering, aliases,
  zero/stale/partial data, source edits, targeted rebuild preservation, public
  links, and public isolation.
- [ ] Run focused Python, browser-module, lint, whitespace, generated docs, and
  search checks, then perform the mandatory final diff and omission review.
- [ ] Transfer shipped behaviour to the concise Semantic Tokens, Tag Registry,
  Source Editor UI, Architecture, Target Lookup, and Usage Index owners.

## Not In Scope

- combining Tag targets with Catalogue discovery or the Catalogue toolbar
  action;
- a unique primary Tag document or inferred `doc_url[0]` ownership;
- automatic Tag-document creation, repair, deletion, or synchronization;
- deriving associations from document titles, content, source proximity, or
  usage rows;
- recursive relationship resolution or Resolver Token behaviour;
- a public Tag registry, target lookup, usage index, or client-side resolver;
- automatic repair of confusing postfix placement after manual source edits;
  or
- changing document lifecycle because a URL is added, removed, or reordered.
