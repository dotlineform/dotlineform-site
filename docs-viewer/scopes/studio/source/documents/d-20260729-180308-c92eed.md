# New Document Source Entry Delivery

## Result

A configured `docs_subscope` report has a management-only **New** button on
its list toolbar. The action creates one document in that report's exact
`{ scope, sub_scope }` collection, routes the report to the new document, and
immediately opens the existing Source editor with the returned
`{ scope, sub_scope, doc_id }` target.

The ordinary scope-level **New**, **New Child**, and **New Sibling** actions
adopt the same post-create rule: after a successful create and projection
refresh, open the new document in Source mode.

The generated heading remains the committed starting source, but the user does
not have to perform a second action before writing useful content.

This extends the exact-target editor delivered by
[Manage Sub-Scope Documents](/docs/?scope=studio&doc=d-20260726-224323-eb0a65)
and the management contribution boundary maintained by
[Sub-Scope Index](/docs/?scope=studio&doc=d-20260728-113139-285eae). It remains
a generic Docs Viewer capability rather than Tag Registry behavior.

## Starting Gap

- At the start of this delivery, `POST /docs/create` created only a parent-scope
  document.
- The existing scope-level New actions create, refresh the main index, select
  the new document, and leave it in rendered mode.
- The source editor already accepts one exact parent or configured sub-scope
  target and freezes that target for the mounted session.
- The manage-only sub-scope report contribution already owns list-toolbar
  controls, but its current controls are selection-backed actions. It has no
  collection-level New action.

The new report action therefore needs a bounded sub-scope create seam. Opening
Source after the create should be one shared interactive post-create behavior,
not a report-specific imitation of source entry.

## User Contract

### Report New

- **New** appears as a compact `📄` icon button only in the local management
  report list, with **New** retained as its accessible label. Public reports
  retain no create control and import no management module.
- The button is a collection action. It uses the mounted report's validated
  `{ scope, sub_scope }`; it never derives a destination from a checked row,
  displayed detail, selected parent, URL text, or tag registry record.
- **New** remains available for an empty collection and is independent of
  checkbox-selection mode and selection-backed Actions.
- The action opens the existing title modal with the **New** heading, ordinary
  New-document defaults, and a compact label row that gives the title input
  more width. Cancel creates nothing.
- Confirm creates one new flat sub-scope document. Sub-scope documents do not
  accept `parent_id`.
- After the commit, the manage inventory refreshes, the canonical report route
  becomes `?doc=<report-doc-id>&subdoc=<new-doc-id>`, and Source opens with the
  exact returned child target.
- Save/Rebuild and **Return to doc** return to that new document's rendered
  report detail without changing the parent report selection.

### Shared Post-Create Source Entry

The interactive document-creation rule is:

```text
create
  -> receive exact committed target
  -> refresh the owning projection
  -> establish the new rendered route/selection
  -> open Source with that exact target
```

It applies to:

- the new sub-scope report **New** action;
- the existing scope-level **New** action;
- **New Child**; and
- **New Sibling**.

For parent-scope actions the committed target is `{ scope, doc_id }`. For the
report action it is `{ scope, sub_scope, doc_id }`.

Source mode remains local presentation state. It is not encoded as a URL
parameter, and source entry does not weaken the existing fixed-target, dirty
buffer, stale-revision, rebuild, or Return contracts.

### Committed-Create Failure Boundary

Creation and post-create presentation are separate outcomes.

- A create failure reports **Create failed** and does not enter Source.
- If creation commits but refresh, routing, or Source mounting fails, the UI
  reports that the document was created but could not be opened in Source.
- Recovery may retry refresh or source entry for the returned target. It must
  not retry document creation silently.
- The created heading-only source remains a valid recoverable document.

## Create Service Contract

The existing `POST /docs/create` mutation family accepts an optional
`sub_scope`.

Parent request:

```text
{ scope, title, optional parent_id }
```

Sub-scope request:

```text
{ scope, sub_scope, title }
```

The service:

- preserves the current parent behavior when `sub_scope` is absent;
- requires a configured one-level child when `sub_scope` is present;
- resolves and confines the configured child source-document root;
- rejects `parent_id` for a sub-scope create;
- allocates the immutable document identity within the destination collection
  and retains the atomic create-only collision boundary;
- writes the standard source front matter and `# <title>` body;
- preserves the existing scope creation default for `viewable` rather than
  introducing a report-specific publication policy;
- runs the normal targeted sub-scope document projection without adding parent
  search membership;
- returns the committed record plus an exact `target`; and
- records the exact `scope`, optional `sub_scope`, `doc_id`, and source path in
  its activity result.

The create path does not read or validate the Tag Registry. New Tag bootstrap,
registry compensation, and `doc_url[]` association remain separate owners.

## Ownership

- `docs_management_mutations.py` owns parent and optional sub-scope create
  planning. It reuses the configured managed-target/root rules rather than
  introducing an unconfined path lookup.
- `docs_management_mutation_service.py` and the existing `/docs/create` route
  own write/rebuild execution and the committed response.
- `docs-viewer-management-subscope-contribution.js` owns the management-only
  report-list button and passes the mounted collection identity outward.
- `docs-viewer-management-document-reports.js` bridges that collection action
  to the local management create workflow and report refresh/navigation.
- The shared sub-scope report continues to own list/detail navigation and
  `subdoc` route state. It does not become a source editor or mutation client.
- `docs-viewer-management-actions.js` owns the reusable interactive
  create-to-Source transition used by existing parent creation actions.
- `docs-viewer-management.js` and the existing source-mode service retain
  exact-target Source entry; no second editor or target resolver is added.

## Boundary

In scope:

- optional exact `sub_scope` support in the existing create mutation family;
- one management-only, collection-level **New** report-list control;
- creation in configured flat one-level sub-scopes;
- refreshing the manage inventory and routing to the created `subdoc`;
- opening the existing Source editor immediately after successful interactive
  creation;
- applying that post-create rule to scope **New**, **New Child**, and
  **New Sibling**;
- committed-create recovery that never duplicates the write; and
- focused service, pure module, route, and manual UI evidence.

Not in scope:

- public creation controls or public write-service access;
- using the selected, displayed, checked, or URL document as an implicit
  creation target;
- nested sub-scope documents or `parent_id` inside a flat sub-scope;
- adding sub-scope documents to the parent Index, Recent, or global search;
- changing `viewable` defaults or automatically publishing a new document;
- entering Source after imports, transfers, package operations, migrations,
  New Tag bootstrap, or other non-interactive creation;
- changing the source editor, Markdown/front-matter split, or metadata model;
- adding title/source synchronization beyond existing metadata behavior; or
- Tag Registry `doc_url[]`, document picker, or semantic-token work.
