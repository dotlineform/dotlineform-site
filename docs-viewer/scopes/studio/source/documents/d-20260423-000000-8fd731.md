# Docs Viewer Source Organisation

Each Docs Viewer scope is an independent canonical Markdown collection. Shared reader and management code does not merge scopes into one corpus.

## Source, Build, Published, Location, And Exposure

### Core Terms

| term | meaning |
| --- | --- |
| **Document** | The conceptual entity identified by `doc_id`, not any one file or rendered representation. |
| **Source** | The one canonical application/build input retained by Docs Viewer for an artifact that must be transformed. A file is not source merely because it originated elsewhere or sits below a path named `source`. |
| **Build** | A manual or automated transformation from source to a published artifact. |
| **Published** | The one consumer-ready artifact. Published means ready for Docs Viewer to reference, render, serve, or download; it does not mean publicly accessible on the internet. |
| **Managed media** | The private consumer-ready media artifact owned under the external media workspace. Add, Import, builds, Manage, inventory, and editorial Copy use this authority. |
| **Location** | The registered physical root and backing provider where a source or published artifact is held: repository, external-local filesystem, or R2. |
| **Public projection** | An optional repository or R2 copy served by a public scope. It is never a fallback authority for managed media. |
| **Rendered view** | The readable or interactive result composed by the viewer from document payloads and referenced published media. It is not the document source. |
| **Retained media original** | A file selected beneath a configured external Projects-relative media source root and left unchanged after intake. Its recorded path is private source evidence, not a second published copy or a Docs Viewer build source. |

`generated` describes provenance: an artifact was produced by a build. It is not the umbrella term for consumer-ready artifacts because images, HTML, files, and other published media may require no generation.

For a normal document, the Markdown file is document source, the Docs Viewer build produces published document payloads, and the viewer composes the rendered document. The document itself persists across those representations.

### Per-Media-Type Contract

The source/build/managed decision is made per configured media type within a scope, such as `img`, `svg`, `files`, `html`, or a future build-source type. It is not one all-or-nothing scope setting. Intake may use a suffix to select an already-defined contract, but the type owns delivery and handling rather than merely mirroring that suffix.

Each configured managed media type has:

- zero or one registered build relationship;
- exactly one derived external managed location.

If no build is required, there is no Docs Viewer build source for that media type. Import or Add writes the ready bytes directly to the managed location without creating a second private copy. A manually selected external original may remain under a configured media source root and have private path evidence without becoming an application/build input.

If a build is required, one source feeds one managed target. Source is read-only to the build, and output is written directly to the managed location. Changing a producer from manual to Docs Viewer automation does not change either identity or path; competing producers for one managed identity are rejected.

Document and search payloads have separately configured working and public projections. A public scope may also configure a public target per media type, but that projection is separate from private managed-media authority.

### Roles Do Not Choose Locations

Roles use the common location boundary, but `docs_scopes_v4` fixes which providers can own each role.

Current configured support is:

| artifact role | repository | external-local filesystem | R2 |
| --- | --- | --- | --- |
| Canonical document source | Supported. | Supported. | Not supported. |
| Media build source | Not configured. | Supported beneath the external media workspace. | Not supported. |
| Document/search published workspace | Supported. | Supported. | Not supported. |
| Managed media | Not configured. | Supported beneath the external media workspace. | Not supported. |
| Public media projection | Supported beneath `site/assets/data/`. | Not supported. | Supported. |
| Public document/search projection | Supported beneath `site/assets/data/`. | Not supported. | Not supported. |

Provider capability and scope policy remain separate. The strict `docs_scopes_v4` configuration fixes private managed media to the external workspace and reserves repository/R2 media locations for optional public projection.

### Location Adapter Contract

Build, import, inventory, and publish orchestration address a logical scope, artifact role, media type, and confined filename identity. Location helpers own provider-specific details:

- resolving and confining repository paths, external workspace paths, or R2 object keys;
- listing, reading, writing, replacing, deleting, statting, and byte-verifying artifacts;
- acquiring remote authentication and clients;
- temporary local staging when a workflow needs a filesystem path;
- resolving the served reference independently of physical backing;
- reporting required capabilities before mutation.

Repository and external-local providers share filesystem mechanics but retain different root and lifecycle policies. R2 implements the same artifact operations through object storage. A provider's capability does not itself authorize a role/location combination; scope policy and workflow requirements still apply.

### Scope Root And Published Workspace

Every repository or external-local scope has one configured document root. Its canonical source and local document/search publication use fixed descendants:

```text
docs-viewer/scopes/<scope>/published/documents/
docs-viewer/scopes/<scope>/published/search/index.json
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/scopes/<scope>/published/documents/
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/scopes/<scope>/published/search/index.json
```

All scopes derive private media from the separate configured workspace:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/<type>/
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/build-source/<producer>/
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/media-source-evidence.json
```

Scope configuration is the topology authority. Builders, readers, serving code, validators, lifecycle operations, manifests, and browser-config generation resolve registered locations rather than constructing a literal workspace root.

Public website snapshots remain beneath `site/assets/data/`, and R2 objects remain at their configured public locations. Service routes such as `/docs/index-tree`, `/docs/doc`, and `/docs/search` are logical interfaces and do not mirror physical directory names. No compatibility route or filesystem alias exists for retired private-media roots.

Public scopes have a working document/search projection plus separately configured public document/search and media projections.

### Folder And Scope Shape

A repo-backed scope makes its source and local publication roles visible beneath one ownership container:

```text
docs-viewer/scopes/<scope>/
  source/
    documents/
      *.md
    sub-scopes/
      <sub-scope>/
        documents/
          *.md
  published/
    documents/
      by-id/
      references/
      sub-scopes/<sub-scope>/
    search/
      index.json
      sub-scopes/<sub-scope>/index.json
```

`documents/` is flat. Document hierarchy remains in `parent_id`; structural directories do not define navigation. A sub-scope is a one-level leaf document set. It does not repeat media or `sub-scopes/`, and it remains excluded from the parent's normal tree and search.

Directly usable media has no redundant private copy. Its managed root is derived from the external workspace. A public scope may separately project the same logical identity, for example:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/<type>/
site/assets/data/docs/scopes/<scope>/media/<type>/
R2: docs/<scope>/<type>/
```

An external-local scope uses the identical scope-relative shape beneath the external Docs Viewer workspace:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/
  scopes/<scope>/
    source/
      documents/             # document source
      sub-scopes/
    published/
      documents/by-id/       # consumer-ready document payloads
      search/index.json
```

The document scope container and external media namespace are separate lifecycle-owned roots. Scope create, rename, and delete handle both exact namespaces. Sub-scopes continue to share their parent scope's media namespace.

### Examples

| artifact | source | build | published artifact |
| --- | --- | --- | --- |
| Markdown document | Canonical `.md`. | Docs Viewer document build. | Document/search payload consumed by the viewer or public route. |
| Mermaid diagram | `build-source/mermaid/diagram.mmd`. | Mermaid to SVG through the registered Docs media producer. | `svg/diagram.svg` in the external managed namespace. |
| JPEG or WebP image | None. | None. | Image placed once at the configured `img` location. |
| Ready SVG image | None. | Sanitization occurs at intake, not as a retained build relationship. | SVG placed once at the configured `svg` location. |
| Ready HTML companion | None. | None. | HTML placed once at the configured `html` location; sandbox behavior is separate. |
| PDF, Word file, or archive | None. | None. | File placed once at the configured `files` location. |
| Video requiring transcoding | Retained canonical master. | Registered transcode. | Delivery video at the configured `video` location. |
| Ready video | None. | None. | Delivery video placed directly at its configured location. |

### Ownership And Inventory

A scope owns its configured document root plus its exact external media namespace and any configured public destinations. The document root contains document source and document/search payloads. The external media namespace contains ready media, registered build sources, and source evidence. Repository/R2 media destinations are public projections only.

Provider-independent inventory records the logical scope/type/filename identity, semantic role, provider, producer relationship, served path, references, and byte evidence. An owned artifact need not currently be referenced. Conversely, a document reference alone does not prove that Docs Viewer owns the target bytes.

For scopes with `media_source_root`, successful manual Add records private source evidence at `<media workspace>/<scope>/media-source-evidence.json`. Each canonical row binds one managed `{media_type, identity}` to an exact configured `source_root` and Projects-relative `source_path`. It records no absolute path, document identity, hash, timestamp, or public payload. The retained original remains separate; evidence neither imports nor verifies it.

The proposed [Scope Media Management](/docs/?scope=studio&doc=d-20260720-100017-9855dd) feature surfaces this existing scope-owned inventory and may later add explicit lifecycle workflows. Arbitrary project trees outside registered scope locations are not Docs Viewer media.

### Repository And R2 Policy

Private managed storage is fixed; public projection remains a per-type decision:

| scope and media type | current location |
| --- | --- |
| All managed media | `$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/<type>/`. |
| Registered Mermaid source | `$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/media/<scope>/build-source/mermaid/`; output uses managed `svg`. |
| Analysis public `img`, `svg`, and `html` | Repository beneath `site/assets/data/docs/scopes/analysis/media/`. |
| Analysis public `files` | R2 beneath `docs/analysis/files`. |

Logical `docs/<scope>/<type>/<filename>` identity stays independent of provider. Changing a public media target between repository and R2 requires a config change, explicit projection reconciliation, dependent public-payload rebuild, and removal only of the old public copy; it does not move private authority or require canonical document rewriting.

R2 is chosen for practical size and provenance, not because a suffix inherently belongs there. Existing cache behavior remains unchanged; Docs Viewer adds no automatic cache purge, fingerprint, or remote lifecycle cleanup.

### Build Direction

A full Docs Viewer build follows one direction:

1. inventory canonical document source, registered external media build source, and existing managed media;
2. run registered media builders from external source directly into the external managed target;
3. render document payloads against logical media identities and the appropriate Manage or public URL projection;
4. publish document and search projections where configured.

The build never writes reproducible output back into source. Media requiring no build bypasses the producer stage and remains at its one managed location.

## Other Consumers

Data Sharing and Docs Import read or produce canonical document content through Docs Viewer-owned source and rendering boundaries. Returned-package previews and export artifacts are working data in the external Data Sharing workspace, not configured Docs Viewer scopes or alternative canonical roots.

## Weak Spots

- Flat `documents/` keeps discovery simple but makes `doc_id` and front matter the only structural organization.
- Canonical source, local published payloads, and public snapshots may temporarily disagree until rebuild or Publish completes.
- Scope config is centralized, so manual path edits can affect builders, management reads, media, lifecycle, and public delivery together.
- Directory-level lifecycle ownership is coarser than semantic ownership of every future file below that directory.
- Remote cleanup remains explicit and inventory-backed; there is no reference-counted R2 lifecycle.
- Mermaid is the first registered build-source producer. Each participating scope opts in through `media.build_sources.mermaid` plus reciprocal `media.types.svg.build_inputs`; [Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565) owns the authoring, dependency, build, and reader boundary.
- Retained-original evidence can become stale when an external source is moved or removed. Normal build and rendering do not scan or verify external source roots.
