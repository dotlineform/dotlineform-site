# SSP-3 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **SSP-3** after [SSP-2](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) independently publishes the versioned Project State folder lookup. [Resolver Tokens Architecture](/docs/?scope=studio&doc=d-20260802-174339-53877d) owns the resolver, semantic-link, derived-usage, access, lifecycle, and non-goal contracts implemented by this delivery.

[TE-1 — Source Editor Directive Actions Delivery](/docs/?scope=studio&doc=d-20260802-163320-9015b0) provides the Source-toolbar **Directives** menu and guarded source-text insertion entry point used by SSP-3.2. SSP-3 contributes one later code-owned **Insert current references** snippet. TE-1 does not decide whether the containing collection or subject can resolve it; SSP-3's build consumer owns that fast, clean validation. The resolver core in SSP-3.0–3.1 does not depend on TE-1.

SSP-3 delivers the smallest reusable Resolver Token seam together with one complete context-aware current-references consumer.

## Complete Outcome

A managed sub-scope document can contain one fixed Resolver Token carrying no resolver seed, subject kind, or subject key. At build time the registered collection supplies the containing document's SSP-1 normalized subject, selects its code-owned resolver adapter, performs one exact focused lookup-row read, and renders the declared deterministic groups without mutating source or scanning live relationship owners.

For the initial Project folder context, those groups include `Series[]` and Project documents. Folder, Work, and Tag contexts may declare different bounded groups through their registered adapters. Every returned Series uses its semantic identity and the shared Semantic Tokens target/link projection. Each successful Series link creates one resolver-derived semantic usage row tied to the containing Resolver Token source range. Project-document results retain exact Docs Viewer target identity. Missing subject, empty, unavailable, stale, invalid, and denied states remain explicit and bounded.

## Delivery Discipline

SSP-3 remains a bounded lookup consumer: a small resolver-definition registry, exact context-aware token parser, one-row relationship reader, declared-group renderer, bounded semantic-link projector, derived usage projection, and one predefined TE-1 Source-menu snippet. It must not become a graph database, query language, registry scanner, recursive traversal engine, live relationship service, or generic Source-command plugin system.

SSP-3.0 must record the exact proposed files, reused builder/editor/Semantic Tokens seams, and rough production/test diff. If the generic core grows beyond what the reviewed contextual consumers require, pause for review and defer the abstraction until another proven consumer needs it.

## Rough Delivery Steps

### SSP-3.0 — Freeze Syntax And Resolver Contract

- [ ] Trace the current Markdown build pipeline, TE-1 Directives control and guarded text-insertion seam, Semantic Token parser/renderer/usage boundaries, access projection, registered collection context, and dependency-aware rebuild behavior.
- [ ] Freeze exact subject-free token syntax, source placement and selection behavior, duplicate-token policy, invalid/unavailable/stale output, and source preservation. Token source must not serialize resolver ID, subject kind, or subject key.
- [ ] Freeze context dispatch from exact containing `{scope, sub_scope, doc_id}` through its registered collection and normalized SSP-1 subject to one code-owned adapter and exact lookup row.
- [ ] Freeze the code-owned definition schema, lookup interface, folder/Work/Tag result-group declarations, ordering, semantic-target descriptor, semantic-link projection, and Manage/public behavior.
- [ ] Freeze semantic usage-index evolution: authored and resolver-derived origins, common fields, resolver/subject provenance, one row per rendered Series, containing source range, targeted-build preservation, and report presentation.
- [ ] Freeze one comparison fixture covering a manual Series URL, authored Series Semantic Token, and Resolver-generated Series semantic link, including equivalent rendered anchors and different usage evidence.
- [ ] Record the exact file list, reused seams, rough production/test diff estimate, and any proposed expansion before implementation approval.
- [ ] Prove each contextual example reads only its exact focused lookup row; semantic presentation may resolve only returned registered identities.

**Checkpoint:** reviewed fixtures place identical token source in folder-, Work-, Tag-, and no-subject documents and cover zero/one/several results, duplicate documents, missing or invalid subjects, missing/stale lookups, resolved/unavailable semantic targets, and public denial. They prove context changes results without changing token source and prove all derived usage rows for one token that renders multiple Series. Stop before implementation.

### SSP-3.1 — Implement Resolver Core And Project Adapter

- [ ] Add the strict code-owned definition registry and schema/version checks.
- [ ] Add the builder parser, registered containing-context dispatch, and one-lookup resolver interface.
- [ ] Register the initial Project resolver against the SSP-2 generated lookup and add only the folder/Work/Tag adapters whose focused products have accepted contracts.
- [ ] Render accessible deterministic Series and Project-document groups plus explicit empty/error states without mutating source.
- [ ] Route every Series result through the existing semantic target lookup and link projector; emit no resolver-owned catalogue URL or fabricated Semantic Token source text.
- [ ] Extend the generated semantic usage index and report with resolver-derived Series occurrences tied to the containing Resolver Token range while preserving untouched documents during targeted builds.
- [ ] Keep lookup paths, local folder targets, and service capabilities out of public build/runtime data.

### SSP-3.2 — Add Authoring Workflow

- [ ] Contribute one code-owned **Insert current references** predefined snippet to the [TE-1 Directives menu](/docs/?scope=studio&doc=d-20260802-163320-9015b0) wherever that Source menu is available.
- [ ] Insert the frozen subject-free token through TE-1's captured-revision, guarded `setRangeText`, ordinary input/dirty-state, focus-return, and no-success-message workflow.
- [ ] Reuse TE-1's frozen insertion-point behavior without adding Resolver-specific blank-line, collection, subject, lookup, or result eligibility checks, opening a subject picker, or previewing relationship groups.
- [ ] Do not read or serialize `folder_path`, `work_id`, `tag_id`, resolver ID, selected row, displayed URL, rendered document, or other UI context during insertion. Build-time registered document context is the only subject source.
- [ ] Keep the two TE-1 table snippets and the Resolver snippet as predefined source conveniences; this bounded code-owned composition does not create a generic directive/plugin registry.
- [ ] Make the dedicated build consumer recognise the exact token, resolve registered context, and fail quickly and cleanly to the frozen inert/unresolved state for malformed, misplaced, unsupported, missing-subject, or unavailable cases.

### SSP-3.3 — Verify And Transfer

- [ ] Run focused parser, registry/lookup agreement, builder, rendering, authoring, semantic-link projection, derived usage indexing/reporting, targeted-build preservation, stale/unavailable, access-isolation, lint, and whitespace checks.
- [ ] Prove the TE-1 menu item inserts the exact predefined bytes with the same keyboard, Escape/outside-click, route cleanup, stale-revision rejection, dirty-state, and focus-return behavior as the existing snippets, without invoking resolver validation.
- [ ] Manually review realistic zero/one/multiple Series and Project-document groups, long labels, stale data, and narrow layout.
- [ ] Prove building a token-bearing document performs no filesystem, manifest, Works, or Series scan and does not refresh Project State.
- [ ] Document the shipped generic resolver seam in a durable Docs Viewer architecture owner and update Semantic Tokens architecture/report contracts for resolver-derived usage; retain Project-specific result meaning in Project State.

## Completion Evidence

- One subject-free token in a folder-context document produces only the precomputed `Series[] + Project documents[]` groups; copying that same source into another registered context intentionally changes its results.
- Every returned Series uses its semantic identity and the shared semantic-link projection, never a plain URL owned by the Project lookup.
- Every resolver-generated Series link creates one derived usage row tied to its containing Resolver Token range, and the Semantic Tokens report can distinguish its origin and open the owning document at that location.
- Maintained examples prove that a manual Series URL, authored Series Semantic Token, and Resolver-generated Series semantic link can present the same destination while retaining different source and usage contracts.
- Resolver-derived usage rows never fabricate Semantic Token source syntax. An unavailable Series target produces neither a link nor a resolved usage row and does not fall back to an unvalidated URL.
- Instrumented tests prove no build-time scan or chained relationship resolution; semantic projection is bounded to exact returned Series identities.
- Source remains byte-stable across successful, empty, stale, and unavailable expansion.
- Authoring inserts one fixed token through the TE-1 Directives menu and never asks for, infers, previews, validates, or serializes a subject; the dedicated build consumer owns recognition and clean failure.
- Public builds and runtime remain free of the Manage-only Project definition, lookup, local paths, and rendered local results.

## Not In Scope

SSP-3 does not add recursive traversal, adjustable depth, relationship chaining, graph visualization, a global relationship database, automatic dependent-document rebuilds, public Project relationships, Semantic-to-Resolver Token migration, table-directive recognition, or a generic Source-command registry. [Resolver Tokens Architecture](/docs/?scope=studio&doc=d-20260802-174339-53877d) owns the durable boundary.

[Sub-Scope Publishing](/docs/?scope=studio&doc=d-20260802-194357-4d857b) owns the flat SSP sequence.
