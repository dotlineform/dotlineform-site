# SSP-3 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **SSP-3** after [SSP-2](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) independently publishes the versioned Project State folder lookup. [Resolver Tokens Architecture](/docs/?scope=studio&doc=d-20260802-174339-53877d) owns the resolver, semantic-link, derived-usage, access, lifecycle, and non-goal contracts implemented by this delivery.

SSP-3.0 must replace explicit token subject entry with the containing document's SSP-1 normalized subject and revise result groups for folder, Work, and Tag contexts before implementation; the detailed stages below preserve the earlier trace but do not authorize its superseded syntax.

SSP-3 delivers the smallest reusable Resolver Token seam together with one complete context-aware current-references consumer.

## Complete Outcome

A managed document can contain one validated Resolver Token whose subject is an exact base-relative Project folder key. Building the document performs one exact lookup-row read and renders deterministic `Series[]` and `Project documents[]` groups without mutating source or scanning live relationship owners.

Every returned Series uses its semantic identity and the shared Semantic Tokens target/link projection. Each successful Series link creates one resolver-derived semantic usage row tied to the containing Resolver Token source range. Project-document results retain exact Docs Viewer target identity. Empty, unavailable, stale, invalid, and denied states remain explicit and bounded.

## Delivery Discipline

SSP-3 remains a bounded lookup consumer: a small resolver-definition registry, exact token parser, one-row relationship reader, declared-group renderer, bounded semantic-link projector, derived usage projection, and thin Source insertion workflow. It must not become a graph database, query language, registry scanner, recursive traversal engine, or live relationship service.

SSP-3.0 must record the exact proposed files, reused builder/editor/Semantic Tokens seams, and rough production/test diff. If the generic core grows beyond what the reviewed contextual consumers require, pause for review and defer the abstraction until another proven consumer needs it.

## Rough Delivery Steps

### SSP-3.0 — Freeze Syntax And Resolver Contract

- [ ] Trace the current Markdown build pipeline, Source token insertion, Semantic Token parser/renderer/usage boundaries, access projection, and dependency-aware rebuild behavior.
- [ ] Freeze exact token syntax for resolver ID, folder subject kind, and subject key; escaping; invalid/unavailable/stale output; and source preservation.
- [ ] Freeze the code-owned definition schema, lookup interface, `Series[]` and Project-document group schema, ordering, semantic-target descriptor, semantic-link projection, and Manage/public behavior.
- [ ] Freeze semantic usage-index evolution: authored and resolver-derived origins, common fields, resolver/subject provenance, one row per rendered Series, containing source range, targeted-build preservation, and report presentation.
- [ ] Freeze one comparison fixture covering a manual Series URL, authored Series Semantic Token, and Resolver-generated Series semantic link, including equivalent rendered anchors and different usage evidence.
- [ ] Record the exact file list, reused seams, rough production/test diff estimate, and any proposed expansion before implementation approval.
- [ ] Prove the Project State lookup answers every example with one exact folder-row read; semantic presentation may resolve only the returned Series identities.

**Checkpoint:** reviewed fixtures cover zero, one, and several Series; one and several Project documents; duplicate documents; missing folder; invalid subject; missing/stale lookup; resolved/unavailable semantic Series; and public denial. Fixtures prove all derived usage rows for one Resolver Token that renders multiple Series. Stop before implementation.

### SSP-3.1 — Implement Resolver Core And Project Adapter

- [ ] Add the strict code-owned definition registry and schema/version checks.
- [ ] Add the builder parser and one-lookup resolver interface.
- [ ] Register the Project resolver against the SSP-2 generated lookup.
- [ ] Render accessible deterministic Series and Project-document groups plus explicit empty/error states without mutating source.
- [ ] Route every Series result through the existing semantic target lookup and link projector; emit no resolver-owned catalogue URL or fabricated Semantic Token source text.
- [ ] Extend the generated semantic usage index and report with resolver-derived Series occurrences tied to the containing Resolver Token range while preserving untouched documents during targeted builds.
- [ ] Keep lookup paths, local folder targets, and service capabilities out of public build/runtime data.

### SSP-3.2 — Add Authoring Workflow

- [ ] Add a Source-editor contribution that selects or pastes one exact allowed folder subject, previews its current Series/document groups, and inserts the validated token.
- [ ] Preserve the committed folder subject exactly; do not infer it from the current document, title, selected row, displayed URL, Series, or Work.
- [ ] Reuse existing authoring space and target validation where suitable, but keep Resolver and Semantic Token modes distinct.

### SSP-3.3 — Verify And Transfer

- [ ] Run focused parser, registry/lookup agreement, builder, rendering, authoring, semantic-link projection, derived usage indexing/reporting, targeted-build preservation, stale/unavailable, access-isolation, lint, and whitespace checks.
- [ ] Manually review realistic zero/one/multiple Series and Project-document groups, long labels, stale data, and narrow layout.
- [ ] Prove building a token-bearing document performs no filesystem, manifest, Works, or Series scan and does not refresh Project State.
- [ ] Document the shipped generic resolver seam in a durable Docs Viewer architecture owner and update Semantic Tokens architecture/report contracts for resolver-derived usage; retain Project-specific result meaning in Project State.

## Completion Evidence

- One exact folder occurrence produces only the precomputed `Series[] + Project documents[]` groups.
- Every returned Series uses its semantic identity and the shared semantic-link projection, never a plain URL owned by the Project lookup.
- Every resolver-generated Series link creates one derived usage row tied to its containing Resolver Token range, and the Semantic Tokens report can distinguish its origin and open the owning document at that location.
- Maintained examples prove that a manual Series URL, authored Series Semantic Token, and Resolver-generated Series semantic link can present the same destination while retaining different source and usage contracts.
- Resolver-derived usage rows never fabricate Semantic Token source syntax. An unavailable Series target produces neither a link nor a resolved usage row and does not fall back to an unvalidated URL.
- Instrumented tests prove no build-time scan or chained relationship resolution; semantic projection is bounded to exact returned Series identities.
- Source remains byte-stable across successful, empty, stale, and unavailable expansion.
- Authoring always inserts an explicit validated folder subject and never uses a UI fallback.
- Public builds and runtime remain free of the Manage-only Project definition, lookup, local paths, and rendered local results.
