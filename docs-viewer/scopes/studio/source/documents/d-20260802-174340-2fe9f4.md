# SSP-3 — Resolver Tokens Delivery

## Status And Purpose

Proposed as **SSP-3** after the current [SSP-2.5 review checkpoint](/docs/?scope=studio&doc=d-20260805-202742-c6e13d) is accepted and [SSP-2](/docs/?scope=studio&doc=d-20260801-133318-15e8fa) recloses its versioned v2 Project State report/lookup with Folder-, Work-, and Series-subject document tracing. SSP-2.0–2.4 remain accepted; SSP-3 implementation waits only for acceptance of the revised product contract and does not absorb that producer correction. The completed SSP-1 foundation supplies normalized optional authoring subjects. [Resolver Tokens Architecture](/docs/?scope=studio&doc=d-20260802-174339-53877d) owns the resolver, build-time lookup-refresh scheduling, semantic-link, derived-usage, access, lifecycle, and non-goal contracts implemented by this delivery.

[TE-1 — Directive Insertion](/docs/?scope=studio&doc=d-20260802-163320-9015b0) provides the Source-toolbar **Directives** menu and guarded source-text insertion entry point used by SSP-3.2. SSP-3 contributes one later code-owned **Insert current references** snippet. TE-1 does not decide whether the containing collection or subject can resolve it; SSP-3's build consumer owns that fast, clean validation. The resolver core in SSP-3.0–3.1 does not depend on TE-1.

SSP-3 delivers the smallest reusable Resolver Token seam together with one complete context-aware current-references consumer.

## Accepted SSP-1 Input

The containing document supplies one normalized SSP-1 object with exact `state`, `kind`, `key`, and `fields`, plus `evidence` only for malformed/conflicting state. SSP-3 extends normalized read support so a canonical `folder_path`, `work_id`, or `series_id` retained in any participating collection remains an exact relationship seed; collection assignment capability remains separate and `dotlineform/projects` stays the only normal **Assign subject** owner. None and invalid states remain explicit unresolved inputs.

Resolver authoring inserts only the fixed subject-free token. The build consumer obtains normalized state from the registered containing-document source context. A relevant build prepares one subject-keyed relationship view from the reclosed SSP-2 Folder evidence and focused catalogue membership projection, then each Folder, Work, or Series dispatch reads one exact row. SSP-2.5 document-placement provenance remains Project State/report evidence and does not make Project documents a Resolver output group. SSP-1's private `subject-associations.json` remains a document-association product, while rendered resolver output uses its focused relationship and semantic-link owners.

## Complete Outcome

A managed document can contain one fixed Resolver Token carrying no resolver seed, subject kind, or subject key. A build whose selected documents contain Folder-seeded Resolver Tokens runs the Project State producer once after current subject products are available and before relationship preparation. SSP-1's normalized metadata then supplies the containing document's optional subject, the resolver reads one exact prepared row, and the destination collection projects deterministic allowed groups without mutating source or scanning live relationship owners during token expansion.

Relationship resolution first returns the exact seed plus related Folder, Work, and Series identities. `dotlineform/projects` may project all three groups; `analysis/works` may consume the same subject row but projects only Work and Series. A retained Folder subject in Analysis is therefore a valid private lookup seed, while the Folder seed, local link, path, lookup row, and capability remain absent from public output. An allowed seed appears first under Subject. Related Work links appear when there is one Work or when a Work is not represented by a successfully projected Series; otherwise the Series link represents the member set without a long duplicate Work list.

Every returned Work or Series uses its semantic identity and the shared Semantic Tokens target/link projection. These identities exist only as in-memory resolver results and generated usage evidence; the builder never fabricates Semantic Token source text. Each successful catalogue link creates one resolver-derived semantic usage row tied to the containing Resolver Token source range and marked with its result group plus `seed` or `related` role. Missing subject, empty, unavailable, stale, invalid, and denied states remain explicit and bounded. A disallowed result group is cleanly absent rather than presented as an error.

## Delivery Discipline

SSP-3 remains a bounded lookup consumer: one relevant-build dependency refresh, a small resolver-definition registry, exact context-aware token parser, one-row relationship reader, declared-group renderer, bounded semantic-link projector, derived usage projection, and one predefined TE-1 Source-menu snippet. It must not become a graph database, query language, registry scanner, recursive traversal engine, continuous synchronization service, or generic Source-command plugin system.

SSP-3.0 is a short scope-and-spec sanity gate over the builder, registered-context, Semantic Tokens, focused-lookup, and Source insertion boundaries. It confirms broad owners, blast radius, deliverables, risks, and stop conditions without freezing exact files, fixtures, estimates, or implementation. Each implementation stage ends with focused evidence and an independent code/diff review. If the generic core grows beyond what the specified contextual consumers require, pause for review and defer the abstraction until another proven consumer needs it.

## Delivery Steps

### SSP-3.0 — Confirm Scope And Delivery

- [ ] Sanity-check the subject-free Resolver Token outcome against the accepted SSP-1 optional authoring-subject projection, SSP-2 producer/lookup, current Markdown build stages, Semantic Tokens projection/usage, containing-document context, and TE-1 Directives insertion seam; resolve only contradictions that would change the result.
- [ ] Confirm that a selected Manage or publication build can recognise exact Resolver Tokens and normalized subject kinds, make current subject products available, refresh Project State once when Folder relationships are required, and render against that exact generation without a metadata/rendering cycle. Stop if the existing stage order cannot support this bounded prerequisite cleanly.
- [ ] Confirm the broad blast radius across exact token recognition, collection-independent normalized subject reads, relevant-build dependency scheduling, subject-keyed relationship preparation, one-row dispatch, collection-specific group projection, semantic-link projection, resolver-derived usage, targeted-build preservation, access isolation, and one code-owned Source convenience.
- [ ] Confirm the deliverables: fixed subject-free token, one per-build Project State refresh only when selected Folder seeds require it, bounded resolver definition/adapter seam, Folder/Work/Series relationship results, Projects/Analysis projection policies, exact Work/Series semantic usage evidence, explicit stale/unavailable failure, focused verification, and concise durable owner updates.
- [ ] Stop for review if the result requires recursive traversal, Studio/Docs mutation hooks, public refresh capability, per-token refresh, a graph/query system, a generic Source-command registry, or a broader abstraction than the specified contextual consumers need. Do not produce an exact file inventory, line estimate, frozen implementation, fixture implementation, or complete test architecture at this gate.

**Checkpoint:** a concise sanity note confirms the spec, scheduling dependencies, broad owners, blast radius, deliverables, risks, access boundary, and stop condition. Stop before implementation approval.

### SSP-3.1 — Implement Resolver Core With Folder And Catalogue Adapters

- [ ] Add the strict code-owned definition registry and schema/version checks.
- [ ] Add the builder parser, registered containing-context dispatch, and one-lookup resolver interface.
- [ ] Add one private build dependency that scans only the selected source set for exact Resolver Tokens and their normalized subject kinds, refreshes Project State once when at least one selected token needs Folder relationships, and supplies the resulting generation to bounded subject-keyed relationship preparation. Builds without a Folder-dependent selected token perform no Project State work.
- [ ] Prepare exact Folder, Work, and Series rows from the SSP-2 Folder lookup plus a focused catalogue membership projection without changing either canonical owner or scanning them during token expansion.
- [ ] Register collection policies separately from subject resolution: Projects allows Folder, Work, and Series result groups; Analysis Works allows Work and Series while suppressing Folder results.
- [ ] Require the refreshed lookup generation during every Folder-dependent token render. A failed prerequisite produces the declared stale/unavailable result and never silently presents a previous lookup as current.
- [ ] Render accessible deterministic Subject and Related sections from allowed Folder, Work, and Series groups plus explicit empty/error states without mutating source or crossing projection boundaries.
- [ ] Keep allowed seed subjects visible, show one related Work directly, omit larger Work sets represented by projected Series, and retain direct links for Works not represented by a successfully projected Series.
- [ ] Route every Work and Series result through the existing semantic target lookup and link projector; emit no resolver-owned catalogue URL or fabricated Semantic Token source text.
- [ ] Extend the generated semantic usage index and report with resolver-derived Work/Series occurrences tied to the containing Resolver Token range while preserving untouched documents during targeted builds.
- [ ] Permit publication builds to consume an exact private Folder relationship row when needed while keeping `folder_path`, lookup rows and paths, local Folder targets, Folder results, and service capabilities out of public payload/runtime data.

**Checkpoint:** focused build-dependency, parser, context-dispatch, generation-agreement, subject-keyed one-row lookup, collection projection, singleton/unrepresented Work rendering, semantic-link, derived-usage, targeted-build, stale/unavailable, and public-isolation evidence passes. An independent code/diff review confirms the build refreshes once only when selected Folder relationships require it, the core then reads one focused row, returned identities use shared Semantic Tokens projection, authored source bytes remain stable, Analysis suppresses Folder output, and authoring workflow remains with SSP-3.2. Stop before SSP-3.2.

### SSP-3.2 — Add Authoring Workflow

- [ ] Contribute one code-owned **Insert current references** predefined snippet to the [TE-1 Directives menu](/docs/?scope=studio&doc=d-20260802-163320-9015b0) wherever that Source menu is available.
- [ ] Insert the specified subject-free token through TE-1's captured-revision, guarded `setRangeText`, ordinary input/dirty-state, focus-return, and no-success-message workflow.
- [ ] Reuse TE-1's frozen insertion-point behavior without adding Resolver-specific blank-line, collection, subject, lookup, or result eligibility checks, opening a subject picker, or previewing relationship groups.
- [ ] Do not read or serialize `folder_path`, `work_id`, `series_id`, resolver ID, selected row, displayed URL, rendered document, or other UI context during insertion. Build-time registered document context is the only subject source.
- [ ] Keep the existing TE-1 table-detail item and the Resolver snippet as predefined source conveniences; this bounded code-owned composition does not create a generic directive/plugin registry.
- [ ] Make the dedicated build consumer recognise the exact token, resolve registered context, and fail quickly and cleanly to the specified inert/unresolved state for malformed, misplaced, unsupported, missing-subject, or unavailable cases.

**Checkpoint:** focused insertion-plan, stale-revision, dirty/focus, menu lifecycle, exact-token, clean-failure, and route-composition evidence passes. An independent code/diff review confirms the Source contribution reuses the existing owner, the build-time registered document context remains the subject authority, and the two bounded actions remain code-owned definitions. Stop before SSP-3.3.

### SSP-3.3 — Verify And Transfer

- [ ] Run focused parser, registry/lookup agreement, builder, rendering, authoring, semantic-link projection, derived usage indexing/reporting, targeted-build preservation, stale/unavailable, access-isolation, lint, and whitespace checks.
- [ ] Prove the TE-1 menu item inserts the exact predefined bytes with the same keyboard, Escape/outside-click, route cleanup, stale-revision rejection, dirty-state, and focus-return behavior as the existing table-detail item, without invoking resolver validation.
- [ ] Manually review realistic Folder/Work/Series subjects in Projects and Analysis, visible and suppressed seeds, singleton and multi-Work Series, an unrepresented Work, no-subject state, long labels, and stale data at representative laptop/desktop widths.
- [ ] Prove a relevant build refreshes Project State exactly once before relationship preparation when selected tokens need Folder relationships; token rendering performs no filesystem, manifest, canonical Works, or canonical Series scan, and builds without selected Folder-dependent tokens perform no refresh.
- [ ] Perform the independent final code/delivery review, reconcile completion claims with exact evidence and omissions, and record any bounded follow-up trigger.
- [ ] Document the shipped generic resolver seam in a durable Docs Viewer architecture owner and update Semantic Tokens architecture/report contracts for resolver-derived usage; retain Project-specific result meaning in Project State.

## Completion Evidence

- One subject-free token in a Folder-context document projects its Folder seed plus current Series and bounded Work results in Projects; the same unchanged source copied to Analysis retains the Folder seed for resolution but projects only Series and bounded Work links.
- Work and Series subjects return the exact seed plus their declared one-hop Folder/Work/Series relationships; token expansion never chains through returned results.
- Work `00635`, multi-Work Series `001`, singleton Series `003`, and retained Folder `projects/10000` examples prove seed visibility, collection-specific Folder suppression, and the bounded Work-list rule.
- Every returned Work or Series uses its semantic identity and the shared semantic-link projection, never a plain URL owned by the Project or Works lookup.
- Every resolver-generated Work/Series link creates one derived usage row tied to its containing Resolver Token range, and the Semantic Tokens report can distinguish its origin and open the owning document at that location.
- Maintained examples prove that a manual catalogue URL, authored Work/Series Semantic Token, and Resolver-generated semantic link can present the same destination while retaining different source and usage contracts.
- Resolver-derived usage rows never fabricate Semantic Token source syntax. An unavailable Work or Series target produces neither a link nor a resolved usage row and does not fall back to an unvalidated URL.
- Instrumented tests prove token expansion performs no relationship-owner scan or chained resolution; only bounded per-build preparation reads focused products, and semantic projection remains bounded to exact returned Work/Series identities.
- Instrumented tests prove one Project State producer run per relevant Folder-dependent build, generation agreement across all selected Folder rows, and no producer run for builds whose selected tokens require only catalogue relationships.
- Source remains byte-stable across successful, empty, stale, and unavailable expansion.
- Authoring inserts one fixed token through the TE-1 Directives menu and never asks for, infers, previews, validates, or serializes a subject; the dedicated build consumer owns recognition and clean failure.
- Publication builds may privately consume a current Folder relationship row, while public payloads and runtime remain free of Folder identities, Project State lookup data, local paths, Folder results, and refresh capabilities.
