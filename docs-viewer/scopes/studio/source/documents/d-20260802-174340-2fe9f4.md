# SSP-3 — Insert Subject Link Delivery

## Status And Purpose

Proposed as **SSP-3** after the completed SSP-1 foundation supplies normalized optional authoring subjects. SSP-3 replaces the retired Resolver Tokens proposal with one bounded Source-editor convenience: **Insert subject link**.

The action reads the current document's exact normalized subject and inserts one ordinary authored reference. It does not resolve related folders, Works, or Series; create a current-references block; schedule Project State; or add a new build-time token family.

## Accepted Inputs And Existing Owners

SSP-1 supplies one normalized state: valid Folder, Work, Series, none, malformed, or conflicting. Subject identity comes only from the exact managed document target and its current canonical front matter. The action never infers from title, body, route, selected row, copied destination, or current UI text.

Work and Series insertion reuses the existing Semantic Tokens target lookup and serializer. Folder insertion reuses the existing normalized `dlf-local:` link serializer and local-open contract. The Source editor's captured-revision replacement seam owns safe insertion, dirty state, focus return, and stale-selection rejection. SSP-3 adds no generic directive/plugin registry.

## Complete Outcome

While editing Markdown source, the author can select **Insert subject link**:

- a valid Work subject inserts the existing semantic-token syntax for that exact Work ID and current target title;
- a valid Series subject inserts the existing semantic-token syntax for that exact Series ID and current target title;
- a valid Folder subject inserts a labelled Markdown link whose `dlf-local:` target is the exact encoded relative folder path; and
- none, malformed, conflicting, missing, or unavailable targets produce no insertion and a clear contained reason without fallback.

The inserted reference is a source snapshot. Later subject reassignment does not rewrite or retarget it. A later Work/Series title or route refresh may update normal semantic-token presentation while retaining the inserted identity; Folder identity remains the encoded path in authored source.

Manage builds render a valid local Folder reference through the existing local-target activation marker. Public promotion applies the existing sanitization boundary, removing the target and activation capability and leaving inert text. SSP-3 does not introduce collection-specific build filtering, publish Folder data, or rely on the author's publication process for safety.

An inserted Work or Series semantic token enters the ordinary semantic-token usage index as a content mention. That usage supports relationship analysis only. SSP-5 public Work/Series document metadata continues to read the document's exact subject front matter as aboutness evidence and never treats semantic-token occurrences as document associations.

## Delivery Steps

### SSP-3.0 — Confirm Scope And Retire Resolver Inputs

- [ ] Confirm the existing Source action/selection seam, SSP-1 normalized subject read, Semantic Token target/serializer, local-folder link serializer, and Manage/public local-link boundary can deliver the action without a resolver parser, Project State read, relationship lookup, build prerequisite, or new token family.
- [ ] Confirm the broad blast radius across the Source control, exact document metadata read, subject-to-insertion planning, current target-title lookup, captured-revision replacement, local-link encoding, focused checks, and concise owner updates.
- [ ] Confirm Resolver Tokens remain unimplemented and retired; no proposed resolver registry, usage-row origin, collection result policy, relationship expansion, or lookup-refresh contract survives into SSP-3.
- [ ] Stop for review if the result requires relation expansion, front-matter mutation, a generic Source-command framework, public local targets, automatic rewriting after subject changes, or hundreds of lines beyond the existing insertion/link seams.

**Checkpoint:** a concise sanity note confirms the existing owners, small production shape, risks, exact no-fallback behavior, snapshot semantics, and retired resolver boundary. Stop before implementation approval.

### SSP-3.1 — Implement Insert Subject Link

- [ ] Add one code-owned **Insert subject link** Source action available only for an exact managed document context that can expose normalized subject state.
- [ ] Plan one insertion from the current exact subject: Work/Series through the existing semantic target and token serializer; Folder through the existing local-link serializer.
- [ ] Use the Source editor's captured revision and replacement owner so stale source, changed selection, unavailable adapters, invalid targets, or failed lookups never insert partial or fallback text.
- [ ] Preserve ordinary input/dirty-state and focus behavior without changing front matter, saving automatically, rebuilding automatically, or showing a success message.
- [ ] Keep none, malformed, conflicting, unknown catalogue identity, invalid Folder path, and unavailable target states explicit and non-mutating.

**Checkpoint:** focused pure planning and Source-action integration evidence passes for Work, Series, Folder, none, invalid, unavailable, stale-revision, exact inserted bytes, dirty state, and focus return. Independent review confirms existing serializers and mutation seams remain the only owners. Stop before SSP-3.2.

### SSP-3.2 — Verify And Transfer

- [ ] Verify inserted Work/Series tokens resolve and create ordinary authored semantic usage rows without new usage schema or origin values.
- [ ] Verify inserted Folder links activate only in Manage, use one exact validated relative target, and become inert through the existing public sanitization boundary.
- [ ] Verify subject reassignment leaves prior inserted source unchanged and no build reads current subject to reinterpret existing references.
- [ ] Run the smallest relevant pure, service/module, lint, whitespace, generated-payload, and public-isolation checks plus a realistic Source-editor review.
- [ ] Perform the independent final code/delivery review and transfer only stable behavior to the Source editor, Semantic Tokens, and local-folder-link owners.

## Completion Evidence

- Work and Series subjects insert exact existing semantic-token syntax and use current target presentation without a resolver-owned URL.
- Folder subjects insert exact existing `dlf-local:` Markdown and expose no absolute or public local target.
- None, invalid, conflicting, missing, and unavailable subjects insert nothing and never infer a fallback.
- Source replacement remains revision-bound and uses the current Source editor's ordinary dirty/focus lifecycle.
- Subject reassignment never rewrites an inserted reference.
- Semantic usage continues to mean content mention; SSP-5 aboutness remains front-matter-owned.
- Project State is never read or refreshed by this action or by later rendering of its inserted source.

## Not In Scope

Relationship expansion, current-reference blocks, Resolver Tokens, Project State lookups, recursive traversal, semantic-to-subject inference, front-matter editing, automatic reference maintenance, public Folder activation, generic Source-command registration, and public Work/Series metadata are outside SSP-3.
