# Data Models Diagrams

## Purpose

These diagrams explain selected logical relationships and projection flows that are difficult to reconstruct from filenames alone. They are an orientation layer, not a complete repository graph, executable schema, or inventory that must be continuously reconciled.

Use a diagram when it materially clarifies identity, cardinality, authority, derivation, publication, or consumption. Feature specifications may use the same mechanics for a small verified **before** diagram and a clearly labelled **after — proposed** diagram.

## Three Complementary Views

| view | answers | suitable content |
| --- | --- | --- |
| logical ERD | What is the identity, relationship, and cardinality? | Series, Works, documents, folders, Tags, and semantic targets |
| projection lineage | Which authority and producer create this artefact, and which consumer reads it? | canonical files, builders, manifests, lookups, indexes, public snapshots, and runtime projections |
| artefact register | Where is it, how is it classified, when is it refreshed, and who owns the exact contract? | paths, authority class, producer, consumers, access, refresh trigger, and code/document links |

An ERD must not show an index, manifest, or lookup as if it were a canonical domain entity. A lineage diagram must not imply that a generated edge is a stored foreign-key relationship. An adjacent register carries operational detail without forcing it into diagram labels.

## Production Method

1. **Bound the question.** Name the relationship or flow the reader needs to understand. Do not begin from every parseable file in a directory.
2. **Trace current authority.** Confirm source, producer, consumers, access boundary, refresh trigger, focused tests, and durable contract owner in the current repository.
3. **Choose the view.** Use an ERD for logical identity and cardinality, a directional flowchart for physical derivation and consumption, and an adjacent register for operational facts.
4. **Partition early.** Split by concern or access boundary before labels, crossed edges, or one giant node make the reader reconstruct the graph.
5. **Author for the intended Studio surface.** Prioritise a full-screen laptop or monitor viewport and Diagram Detail. The ordinary inline view should remain usable for orientation, but it does not need to make a dense diagram readable at narrow widths. Every Mermaid block needs an accessibility title and description.
6. **State the limits.** Record what the diagram does not include and which enhancement ideas remain deliberately uncommitted.
7. **Verify and hand off.** Render through the current Studio Docs Viewer, inspect full-screen and Diagram Detail presentation, then link the exact code, configuration, tests, and contract documents used as evidence. Add narrow acceptance only when the diagram is intended for a public scope that requires it.

## Viewport Priority

Studio documentation diagrams target the space available on a full-screen retina-display laptop or monitor. Choose direction, partition, and label density for that surface and for Diagram Detail. Phone-width containment and readability are not Studio acceptance requirements.

Public-scope diagrams follow the owning public scope's responsive requirements. A public delivery may therefore add its own narrow-view acceptance without turning that condition into a rule for Studio-only diagrams.

## Classification And Notation

- Label sources and artefacts as **canonical**, **authored**, **generated projection**, or **runtime-only**.
- Use a logical relationship only for stable identity and cardinality. An array-valued JSON reference can be shown logically without pretending the repository uses relational storage.
- Use arrows for reads, generation, publication, or consumption. Add a verb when direction alone is ambiguous.
- Keep management-only, public, and shared products visibly distinct.
- Name the producer and primary consumer; directory placement alone does not establish ownership.
- Use solid edges for verified current behavior. Put proposed nodes in a visibly separate section, include **proposed** in their labels, and use dashed edges.
- Link prose or a register to current implementation and evidence. Diagram labels remain explanations, not authorities.

## Child Document Shape

Each child owns one diagram and the context needed to use it responsibly:

- **Purpose and reading guide** — the exact question and how to interpret nodes and edges;
- **Diagram** — one bounded Mermaid block;
- **Artefact register** — only when paths, refresh, visibility, or code ownership would overload the diagram;
- **Notes** — important qualifications and current-state details;
- **What this does not include** — omitted families, fields, workflows, or access modes;
- **Possible enhancements** — ideas that may be useful later but are not shipped or promised; and
- **Authorities** — current code, configuration, tests, and durable documents.

The Docs index tree is the available-diagram list. This parent does not duplicate the child hierarchy in a maintained table.

## Before And After In Feature Specifications

- **Before** is a verified slice of current behavior and links to its authorities.
- **After — proposed** is a design claim until delivery changes the current implementation and retained diagram.
- Reuse node names when identity is intended to survive. Rename nodes when the proposal changes identity or authority.
- Show only the relationships changed or needed to understand the feature. A feature diagram does not need to become a durable child.
- At closeout, update a retained child only when the delivered relationship belongs to that system explanation.

## Mermaid Mechanics

- Use fenced `mermaid` blocks supported by the pinned renderer documented in [Document Diagrams](/docs/?scope=studio&doc=d-20260719-123719-fb7565).
- Add `accTitle` and `accDescr` immediately after the diagram declaration.
- Prefer short conceptual labels in nodes and put long paths in the register.
- Use `<br/>` only where a deliberate two-line label improves scanning.
- Inspect the full-screen Studio document and Diagram Detail before treating a Studio-only diagram as accepted. Inspect narrow readability only when an owning public scope requires it.
- Split a diagram when scaling makes text technically visible but practically difficult to follow.

### Useful Diagram Types To Consider

This is a prompt for choosing a view, not an exhaustive list of available Mermaid diagrams or a required set for every document:

- **Entity relationship — `erDiagram`:** identities, references, and cardinality between logical records.
- **Class — `classDiagram`:** type structure, responsibilities, and dependencies when those distinctions matter more than stored cardinality.
- **Flowchart — `flowchart`:** authority, production, projection, publication, and consumption paths.
- **Sequence — `sequenceDiagram`:** ordered requests, mutations, builds, refreshes, and interactions across actors or services.
- **Architecture — `architecture-beta`:** system topology, services, stores, integrations, and their boundaries when a lineage flow alone is insufficient.

Other diagram families in the pinned Mermaid renderer may be used when they answer the bounded question more clearly. Newer or beta-prefixed syntax should be checked against the pinned version and rendered through Studio before adoption.

## Maintenance Model

Keep a few diagrams whose explanatory value justifies authored maintenance. Review a child after a major delivery changes one of its displayed relationships. Routine repository changes do not require maintaining an exhaustive diagram inventory, and the parent does not mirror the child tree in a hand-maintained table.

Path-existence lint may be considered only after the authored map set proves useful. Automatic graph generation, field-level schema extraction, and drift enforcement are separate capabilities with their own maintenance costs.

## Boundary

Data Models Diagrams do not replace [Projection Contract](/docs/?scope=studio&doc=d-20260523-222005-1085b2), [Catalogue Indexes And Payloads](/docs/?scope=studio&doc=d-20260519-202931-b05d27), [Generated Data Contracts](/docs/?scope=studio&doc=d-20260605-125108-c68916), or executable builders and tests. They explain selected relationships across those owners.
