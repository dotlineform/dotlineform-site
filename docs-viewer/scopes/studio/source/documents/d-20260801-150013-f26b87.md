# Local File And Folder Links Concept

## Purpose

Docs Viewer supports links that can open local files or folders without saving a machine-specific absolute path in document source, front matter, manifests, or Studio data.

The configured `$DOTLINEFORM_PROJECTS_BASE_DIR/` is runtime infrastructure. The durable target is only a normalized POSIX path relative to that root:

```text
projects/3 symbols
```

This is a navigation convenience, not a filesystem identity, registry entry, upload destination, or promise that the target exists.

## Target And Link Syntax

Structured fields already supply the local-target meaning, so they store the plain relative value:

```yaml
folder_path: "projects/3 symbols"
```

An ordinary Markdown destination such as `projects/3%20symbols` is ambiguous: it already means a relative web or document link. Body links therefore use an explicit behaviour marker:

```markdown
[3 symbols](dlf-local:projects/3%20symbols)
```

`dlf-local:` says how Docs Viewer should activate or project the link. It is not part of the target identity. After parsing and decoding, the local service receives only `projects/3 symbols`.

This avoids both problematic alternatives:

- a `file:///Users/...` link embeds private, machine-specific configuration;
- treating every relative Markdown link as local would break ordinary relative web, document, image, and attachment links.

## Paste Experience

There is no clipboard monitoring. When the author presses Command-V in an eligible Source editor, the browser supplies `text/plain` on that one `paste` event. Docs Viewer may intercept that event without polling the clipboard or requesting continuing clipboard-read permission.

The recognizer accepts one complete `file:` URL, absolute POSIX path, or shell-backslash-escaped absolute path. It treats the text as inert data and checks whether the decoded path is contained below the configured base root.

```text
paste event
    -> recognize one supported absolute local path
    -> verify it is below DOTLINEFORM_PROJECTS_BASE_DIR
    -> strip the configured root
    -> normalize to a relative POSIX target
    -> insert a dlf-local Markdown link
```

For example, this pasted text:

```text
/configured/base/projects/3\ symbols
```

produces:

```markdown
[3 symbols](dlf-local:projects/3%20symbols)
```

If the pasted text is outside the configured root, mixed with other prose, multiline, ambiguous, or in a code context, Docs Viewer does not intercept it; the browser performs the ordinary paste. Manually authored `dlf-local:` links must pass the same relative-target validation when rendered or activated.

Conversion is silent and does not enter the browser's native Undo history. A body paste never writes front matter. A dedicated metadata field may reuse the same normalizer but saves only the relative target.

## Manage Rendering And Activation

The Markdown renderer recognizes `dlf-local:` as an explicit local-link kind. In local Manage it produces a normal visible anchor carrying the relative target. The Docs Viewer runtime intercepts its click and sends that exact target to the local management service instead of asking the browser to invoke a custom protocol.

The server:

1. rejects empty or absolute targets, URL schemes, NUL bytes, and `..` traversal;
2. joins the relative target beneath the configured base root;
3. resolves the existing file or folder and rechecks containment, including symlink resolution; and
4. only then invokes the platform action, initially Open in Finder on macOS.

### What Server Confinement Means

The server does not sandbox Finder or the macOS `open` command. “Confinement” means server-side contained path resolution before `open` is called. The endpoint must not trust a browser-supplied string merely because the ordinary UI created it.

Without that validation, a manually authored or directly requested target could attempt to escape the configured root:

```text
../../Desktop
%2e%2e/%2e%2e/Desktop
projects/link-to-somewhere-else
```

The server decodes first, rejects traversal and absolute input, joins the relative value to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, and verifies the resolved existing target still lies below that root. It then calls `open` with the validated path as one direct process argument, never by interpolating it into a shell command.

This check confines the **local-link endpoint**, not `open`. It prevents the endpoint from becoming an arbitrary-filesystem opener while leaving the final platform action very simple.

The shipped symlink policy is strict: an in-root symlink whose resolved target is outside the configured base is rejected. The configured root is therefore the real activation boundary, not only a lexical authoring boundary.

A contained target may be stored before it exists. Activation of a missing target returns an explicit not-found response and never falls back to another folder, the current document, its parent, or a browser URL.

The configured base root is the activation boundary. The Projects feature usually targets `projects/...`, but any valid relative target below `$DOTLINEFORM_PROJECTS_BASE_DIR/` is permitted.

## Public Projection

Local activation is Manage-only, but a `dlf-local:` link may be authored in a document that also has a public projection. The public builder must recognize the marker and emit inert output rather than a clickable custom-scheme link.

| authored link | public result |
| --- | --- |
| safe descriptive label | retain the label as inert text |
| empty label | emit an explicit local-link placeholder |
| label that itself exposes a disallowed path | emit the placeholder rather than the label |

This is a bounded link-projection refinement. The generated source and target contain no absolute base path, and the public payload contains neither the `dlf-local:` marker nor an activation endpoint.

It does not solve the wider private-content problem. An absolute path pasted as prose, raw HTML, or fenced code is deliberately not converted by the local-link recognizer and still needs the general public-build secret/path verification policy. That policy is a separate delivery because it applies to all content, not only explicit local links.

## Invariants

- The canonical target is a normalized base-relative POSIX path.
- `$DOTLINEFORM_PROJECTS_BASE_DIR` is never stored in authored or generated Project link data.
- `dlf-local:` is a link-behaviour marker, not a registry or semantic token.
- Structured metadata stores the target, not the marker or a `file:` URL.
- Local links and `folder_path` are Docs Viewer concerns; this link contract neither reads nor writes Studio records, fields, UI, routes, or services.
- Body links are never silently promoted into metadata.
- Storage does not assert existence; every activation revalidates it.
- Local activation is available only through the local Manage service.
- Public projection makes explicit local links inert.
- Ordinary relative and external links retain their existing meaning.
