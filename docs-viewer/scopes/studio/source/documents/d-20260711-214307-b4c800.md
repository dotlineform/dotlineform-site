# Docs Review

## Purpose

Docs Review is the local isolated read-only browser preview for document packages that the integrated Docs Viewer document-package service has validated and materialized. It can hand the exact selected package source file to VS Code without exposing a browser source editor.

It is served at `/docs-review/` by the standalone Docs Viewer service. It reuses the shared Docs Viewer tree, document renderer, panel layout, route state, and public-safe CSS through the explicit `review` app context and a returned-package provider.

Docs Review is not:

- a configured Docs Viewer scope
- a copy of the Docs Viewer frontend
- a returned-package validator or transport owner
- a canonical import, promotion, merge, or commit tool

## Ownership Boundary

Prepare Package owns:

- export provenance and portable package contracts
- returned-package staging and validation
- materializing validated source and asset files under the external workspace root

[Docs Import](/docs/?scope=studio&doc=d-20260424-000000-fc8b5d)
independently discovers trusted returned JSON/JSONL packages and complete edited
review-source folders in staging. Direct returned-package Import uses the
original package as content authority. The optional edited-source round trip
instead uses the reviewed Markdown as content authority, while retaining
trusted package metadata for capability, exact membership, routing, and
prepared-source versions.

The app-level Docs Import chooser is the browser entrypoint for preparing this
projection. **Open in Docs Review** is enabled only on a selected server-declared
reviewable returned package. It publishes or reuses one matching immutable
review package and opens `/docs-review/?package=<package_id>` in a new tab.
The action does not confirm Import or reroute the selected package. The retired
scope-level **Review package** action, Returned Packages page, and inspector
endpoint have no role in Docs Review.

Docs Review owns only:

- listing validated review packages
- reading retained package-local generated previews
- explicitly rebuilding the complete retained preview from package-local source
- repairing missing or damaged derived output during reads
- rendering package documents and inventoried assets
- package inventory visibility
- opening the exact selected package-local source file in VS Code
- links to canonical counterparts for manual comparison

Canonical source remains outside Docs Review authority. The route exposes no canonical write, management, publish, promotion, Import control, or import-apply capability. A user returns to the app-level Docs Viewer **Import** chooser when they decide to accept a package.

## Enablement And Route

`DOCS_VIEWER_REVIEW_ENABLED` independently enables the route and its package-rooted APIs.

[Docs Review Endpoints](/docs/?scope=studio&doc=d-20260711-214307-6d6d46) owns the exact API surface.

- `bin/local-all` enables Docs Review by default.
- `DOCS_VIEWER_REVIEW_ENABLED=0` suppresses the route and API family.
- launching `docs-viewer/bin/docs-viewer` directly keeps review disabled unless it is explicitly enabled.

Review URLs use package identity rather than configured scope identity:

```text
/docs-review/?package=<package_id>&doc=<doc_id>
```

- `package` selects one validated package and is preserved in internal route changes.
- `doc` selects one package record and preserves its package-local identity; it is not canonical local document identity.
- links to canonical counterparts use `/docs/?scope=<source_scope>&doc=<doc_id>`.

## Current Interface

The single Docs Viewer toolbar row contains:

- the validated-package selector
- `Build`, which is enabled for the active valid package and disabled only
  while its request is running
- `Assets`
- the VS Code icon, which directly opens the selected package document source
- `Open canonical` when the selected package and document identify a counterpart
- the document information control

The index panel renders the hierarchy supplied by the validated package. Document metadata retains returned summaries. Docs Review does not provide parent, summary, or hierarchy editing. Managed Docs Import maps package parents and applies supplied summary metadata without making the review route an editor.

Validated-package publication builds and retains the package-local generated
preview before exposing the timestamped package. Ordinary navigation reads that
retained output and repairs missing or malformed generated JSON only when
needed. Explicit **Build** always regenerates the complete retained projection,
including when the existing generated set is healthy, then reloads the same
package and selected document.

`Assets` reports which optional package inventories are present. Docs Review does not provide a binary asset editor.

## Validated Package Contract

Packages live outside the repository under:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/data-sharing/import-preview/<package_id>/
  manifest.json
  source/
    <doc-id>.md
  assets/
    ...
  inventories/
    assets.json
    links.json
    embedded-content.json
  generated/
    index-tree.json
    by-id/
      <doc-id>.json
```

`generated/` is part of a newly published complete package. Legacy or manually damaged packages may temporarily lack derived files until repair. Inventory files are optional.

The trusted `manifest.json` must:

- use `schema_version: docs_review_validated_package_v1`
- contain a `package_id` matching the folder name
- use `status: validated`
- identify `source_scope`
- optionally provide `title` and `default_doc_id`

The source contract requires:

- at least one direct `source/*.md` child
- no nested source Markdown or symlinks
- a safe, unique front-matter `doc_id`
- a filename stem matching `doc_id`
- any `default_doc_id` to identify a package document
- a valid package-local hierarchy for building

The Docs Viewer document-package service is responsible for producing this trusted handoff. Invalid folders remain outside the selectable package list and are returned as rejected-package diagnostics.

## Build And Asset Rendering

The review builder uses a synthetic local-external Docs Viewer configuration.
Initial publication builds beside the final package path and exposes the
complete package with one rename. Explicit Build and conditional read repair
read only persistent package-local source and write only that package's
`generated/` folder. Neither path registers the package in scope config or
writes repository source, normal generated scope output, public assets, or
search output for another scope.

Build accepts only the active validated `package_id`. It never rewrites
package-local source, advances review transport dates, changes canonical
timestamps, or takes a configured scope target. Failure leaves the current
preview in place and re-enables the same-package retry.

Package media and interactive HTML are served only when they are declared in `inventories/assets.json` and resolve to safe files under `assets/`.

Asset inventory records support:

- `kind: media` or `kind: interactive`
- a required `token_path`
- a safe `package_path` under `assets/`

Package-local interactive HTML is rendered in a sandboxed iframe with scripts allowed but without same-origin authority.

## Read-Only Source Projection

Package-local `source/*.md` is persistent derived build input. It is inspectable
and editable in the external workspace. Docs Review exposes one identity-only
source-open command: it validates the active `package_id` and displayed
`doc_id`, resolves that exact direct `source/<doc_id>.md` member, and opens it
in VS Code without confirmation or canonical fallback.

The browser still exposes no source display mode, source-content provider
methods, source-read/write capabilities, revision tokens, or save workflow.
Editing in the external application does not automatically refresh retained
output; the user chooses **Build**, visually accepts the result, and may then
copy the complete `source/` folder into normal Import staging.

Docs Review cannot edit bodies or front matter in the browser, create or delete
documents, change hierarchy, initiate Import, or mutate canonical source. The
only configured-source mutation path remains the separate app-level Docs Viewer
**Import** chooser. Docs Review is optional: the original returned JSON/JSONL
package can still be imported directly without preparing or rebuilding a
review projection.

## Optional Edited-Source Round Trip

After external edits and an accepted Build, copy the complete package
`source/` folder into
`$DOTLINEFORM_PROJECTS_BASE_DIR/data-sharing/import-staging/`. Import recognizes
it before generic Markdown handling and displays
`<review_folder_id> (reviewed)` while retaining the exact staged folder name in
requests.

The complete folder is overwrite-only. Trusted export metadata and the retained
manifest must prove return-Import capability, exact document membership, source
scope or configured sub-scope, and prepared canonical versions. Import applies
edited body, title, and summary to that exact collection through one
confirmation and one atomic write/rebuild boundary. It rejects standalone
review-source Markdown, incomplete folders, stale canonical versions, creates,
partial selection, and cross-collection fallback. The preview warns that
derived Markdown may have lost rich source content or package assets.

## Capability And Security Boundary

Review capabilities are independent from `/docs/` management capabilities:

```text
review_packages_list
review_manifest_read
review_asset_inventory_read
review_generated_read
review_build
review_source_open
```

The review capability response always reports these authority exclusions:

```text
canonical_write: false
management: false
publish: false
```

The service remains loopback-only, validates allowed origins, rejects unsafe package/document/path values, forbids symlink traversal, and serves only inventoried package assets.

## Failure Behavior

- A missing or unavailable external workspace disables review capabilities with workspace setup diagnostics.
- A package with an invalid manifest, source set, or package-local hierarchy is rejected rather than partially loaded.
- A missing or malformed generated tree or payload is repaired from persistent
  package-local source when possible; healthy generated output is not rebuilt
  by ordinary reads but is regenerated by explicit Build.
- Explicit Build failure leaves package source and canonical source untouched,
  keeps the active route, and permits retry.
- A manually deleted package produces an ordinary not-found response.
- A source-open request for a document outside the validated package fails before any application is launched.
- No package failure falls back to canonical source or a configured Docs Viewer scope.

## Verification

The `docs-viewer-smoke` profile includes the fixture-backed Docs Review route
check plus real manage-route coverage for the selected-row Review handoff.
Focused package tests live in:

```text
docs-viewer/tests/python/test_docs_review_packages.py
docs-viewer/tests/smoke/docs_viewer_consolidated_import_route.py
docs-viewer/tests/smoke/docs_viewer_service_review.py
```

These checks cover validated package discovery, package-root containment,
persistent generated reads and conditional repair, explicit complete Build,
inventoried assets, returned summary metadata and hierarchy, absence of a
browser source editor and Import control, exact package-source opening, route
boot, and canonical comparison without canonical writes. Edited-folder Import
acceptance additionally covers a scope and Analysis/Tags-style child package
from retained edit and Build through staged preview, confirmation, atomic
apply, and rendered canonical output.
