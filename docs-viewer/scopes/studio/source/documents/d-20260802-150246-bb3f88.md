# Content Detail View Concept And Architecture

## Purpose

Markdown tables and diagrams belong to documents, but some need substantially more space and interaction than flowing prose can provide. Content Detail View gives one exact presentation the main panel without leaving Docs Viewer or creating a second shell model.

The architectural commitment is stronger than a visual preference: this is a registered main hosted view, not a full-screen modal disguised as a view. It participates in the current panel state, view lifecycle, control registry, main-view toolbar, route composition, and public/manage ownership boundaries.

## Static Source Boundary

“Static source” means that the content belongs to the saved document rather than to a live report or application query. Its presentation may still be generated or rendered:

| source presentation | qualifies | reason |
| --- | --- | --- |
| Markdown table | yes | authored document source renders a semantic HTML table |
| configured SVG media token | yes | the document owns a stable presentation reference |
| authored Mermaid fence rendered in the browser | yes | saved Mermaid source owns the presentation even though SVG is produced at mount time |
| authored Mermaid projected to themed public SVG | yes | the public image is a projection of document-owned source |
| dynamic Docs Viewer report list | no | the mounted report component owns live data, controls, and lifecycle |
| `docs_subscope` list/detail surface | no | the report owns collection state and selected detail presentation |

The table target scan occurs over explicitly marked tables in the rendered document content from the current payload before dynamic document extras mount. [TE-2](/docs/?scope=studio&doc=d-20260802-162149-3ba013) consumes the authoring comment and projects `data-docs-content-detail="table"` onto the exact semantic table. Diagram adapters register only their already-supported rendered surfaces through the owning diagram lifecycle. Unmarked tables, report rows, and later component DOM are therefore not inferred as content-detail targets.

## Existing Model Extension

Docs Viewer already has index, main, and info panels; registered main views for rendered documents, search, and Recent; hosted lifecycle; and the stable `main-view` toolbar surface. The feature adds:

- one main view definition, proposed as `content-detail`;
- one transient exact target context supplied when that view is requested;
- one expanded-main layout state owned and projected by the existing panel layout;
- view-owned Back and presentation-action controls on the existing `main-view` surface; and
- focused table and diagram target adapters supplied through normal app composition.

It does not add a panel, toolbar mount, modal host, route shell, or global detail-state service.

```text
existing Docs Viewer shell
  index panel
  main panel
    rendered-document view
      exact table/diagram control
        -> request content-detail with validated target
    content-detail view
      existing main-view toolbar: Back | presentation actions
      expanded main-panel presentation
  info panel
```

## Expanded Main Layout

The detail view needs a named main-panel layout state because changing only the document content measure would leave the index and info rails consuming the viewport. The exact state identifier is frozen in TE-3.0; its behavior is:

- the existing main panel occupies the app's available width and usable viewport height;
- index and info presentation are temporarily absent from the projected layout without deleting their prior state;
- the top bar and `main-view` toolbar remain part of the ordinary shell;
- leaving Content Detail View restores the prior index state, info state, rendered-document view, scroll position, and invocation focus where still valid; and
- document or scope navigation invalidates the transient target and returns through the normal route workflow.

This is an extension of panel layout projection. Individual table or diagram adapters must not toggle shell classes, hide panels, or own restoration independently.

## Exact Target Context

One request identifies the current rendered presentation rather than searching again from titles, text, URLs, or arbitrary DOM:

```json
{
  "document_target": {
    "scope": "studio",
    "sub_scope": "",
    "doc_id": "d-example"
  },
  "document_mount_generation": 42,
  "kind": "table",
  "adapter_target_id": "table-1",
  "occurrence": 1
}
```

The exact representation is adapter-owned and frozen during delivery. `adapter_target_id` illustrates an opaque key into adapter-owned state; it has meaning only within the named document mount. The invariant is that the target belongs to the current document mount, has a supported content kind, and becomes invalid when that mount is replaced. `occurrence` is ephemeral presentation context for labels such as **Table 2**, not the mechanism used to search for the table or a persistent table identity.

The hosted-view request contract may be extended to carry a narrow immutable target context into `load`, `mount`, `update`, `beforeLeave`, and `unmount`. It must not expose broad runtime state or create a second view registry. With only table and diagram consumers, composition can supply focused adapters directly; a generic adapter registry requires separate evidence.

## Table Registration And Presentation Construction

The table adapter queries only `table[data-docs-content-detail="table"]` in the accepted rendered-document content before dynamic document extras mount. It does not parse authoring comments, measure table geometry, or decide whether a table is large. For each marked table it creates one record in a registry owned by that document mount:

```text
document mount generation 42
  table-0 -> exact rendered <table> element
  table-1 -> exact rendered <table> element
  table-2 -> exact rendered <table> element
```

The adapter adds the component-level **Open table** control while it holds the exact element. The button closes over or otherwise carries the opaque record key; clicking it does not rescan by heading, cell text, occurrence, URL, selected document, or currently displayed DOM. Document replacement disposes the registry and makes every old key fail its mount-generation check.

`content-detail` owns the generic hosted-view lifecycle, expanded shell, toolbar surface, and presentation mount. It does not understand table rows or construct table markup. After validating the target, it asks the active table adapter to mount the presentation for that record.

The initial table adapter constructs the presentation from the already-rendered semantic DOM, not from Markdown or an HTML string. The expected shape is:

```text
content-detail body
  bounded table viewport
    cloned semantic <table>
```

The adapter clones the accepted table, removes document-only controls and transient markers, applies the small presentation class/label set, and strips or remaps duplicate IDs while preserving valid `headers`, ARIA, link, and text relationships. The original rendered document remains intact for **Back to document**. TE-3.0 freezes whether the registry retains the exact element until entry or stores an immutable semantic clone at registration, but it must not independently regenerate cell meaning.

Most improvement comes from context and CSS rather than new HTML: the expanded panel supplies space; the viewport supplies unified horizontal and vertical scrolling; and table styles supply natural widths, sticky header cells, sticky first-column cells, and the top-left intersection layer. TE-4 may later add adapter-owned resize handles and a `<colgroup>` to the detail clone without changing the source table or generic view.

## Main-View Toolbar

Controls that act on Content Detail View belong to the existing `main-view` surface with `ownerViewId: "content-detail"`. Eligibility and live state may additionally hide controls that do not apply to the active content kind.

Shared controls include:

- **Back to document** — returns through the main-view coordinator;
- a concise presentation label such as **Table 2** or the diagram title; and
- presentation-specific controls contributed by the focused adapter.

TE-3 gives a static table only Back and its presentation label. TE-4 may contribute **Copy as CSV** and **Reset column widths** from the Manage entrypoint; a resize handle inside a header cell remains a component control. TE-5 may contribute **Open in new tab** for diagrams when the adapter has an existing stable URL or temporary SVG resource.

Later successful copy or reset actions require no status message. Clipboard failure remains explicit through the existing status/error surface.

## Table Presentation Example

An author marks a table in canonical Markdown:

```markdown
<!-- dotlineform:table-detail -->

| Project | Folder | Series |
| --- | --- | --- |
| Nerve | projects/nerve | Series 105 |
```

When the table-detail consumer recognises the exact adjacent comment, the Docs build projects the narrow eligibility marker onto the same semantic table; removing the ordinary invisible comment from rendered HTML is unnecessary. The rendered document then adds a subtle component-level **Open table** control. Invoking it changes the active main view:

```text
main-view toolbar
  Back to document     Table 2

content-detail body
  +-------------------------------------------------------------+
  | sticky header                                               |
  +----------------+----------------------+---------------------+
  | sticky column  | horizontally and vertically scrollable     |
  |                | table body                                 |
  |                |                                            |
  +----------------+----------------------+---------------------+
```

The initial table contract is:

- require the projected table-detail marker rather than applying a size or overflow heuristic;
- use the semantic HTML table produced from Markdown;
- use natural content width rather than forcing the table into the prose measure;
- use one bounded viewport for horizontal and vertical scrolling;
- keep the header row and first column visible, including the top-left intersection;
- keep the static presentation free of resizing, export, and persisted table state; and
- preserve ordinary links and text selection.

The first delivery deliberately tests whether natural sizing, full available width, sticky context, and unified scrolling solve the reading problem before adding tools.

## Dedicated Table Documents And Default Entry

A large table may live in an ordinary child document while its parent retains a summary table and a normal document link such as **More…**. TE-6 proposes one public-safe scalar front-matter hint for a dedicated document:

```yaml
viewer_content_detail: table
```

The exact field name is frozen in TE-6.0. Its initial contract supports only a document with exactly one authored Markdown table and implicitly projects the same table-detail eligibility marker without requiring a redundant comment. The hint is projected into document-index metadata as well as the document payload so the router knows the intended initial presentation before a cold payload fetch or cached render begins. Child status is conventional organisation, not a runtime requirement, and the parent link needs no special component or table target.

The initial contract applies only to indexed scope documents. A sub-scope document remains embedded detail owned by its `docs_subscope` report: it is absent from the parent index, the parent report remains the selected Docs Viewer document, and its `subdoc` payload renders after the report mounts. Sub-scope content is not intrinsically ineligible, but supporting it would require a separate report-owned hint projection, preflight, exact `{scope, sub_scope, doc_id}` handoff, and report-state restoration design.

The hint must not be implemented as an after-render click. Navigation first projects the final expanded-main layout and an inert pending content state. The existing Markdown pipeline then supplies `content_html` to a non-visible preparation mount, where the TE-3 table adapter registers the exact rendered table. One coordinated commit mounts that target in `content-detail` and reveals it; the ordinary rendered document is never visible in between and the outer panel geometry does not resize after content appears.

**Back to document** reveals the already-prepared ordinary document without refetching it and records a suppression decision for the current document visit so the default does not immediately reopen. A later fresh navigation or reload may apply the authored default again. Missing or ambiguous targets fail explicitly and atomically to the ordinary document rather than leaving a blank or partially expanded view.

This remains presentation of rendered HTML, not a Markdown reparse, direct table URL, persistent table identity, dynamic report, or second document renderer.

## Managed Table Tools

TE-4 extends the same active table presentation through Manage composition. It adds pointer and keyboard-accessible header-boundary resizing, session-local Reset, and **Copy as CSV** on the existing main-view toolbar. It does not register a second view or replace the shared table renderer.

TE-4.0 freezes CSV header inclusion, visible-text extraction, whitespace and line-break normalization, empty cells, quotes, delimiters, link labels, and clipboard failure behavior. CSV generation never reads Markdown source or a report data model; it serializes the exact table presentation accepted by the view. Persistent widths, Download CSV, and public promotion remain later decisions.

## Diagram Presentation Example

The existing persistent and inline diagram wrappers already identify supported diagram surfaces. TE-5 changes their primary detail action from an external target to an exact `content-detail` request:

```text
rendered document diagram
  Open diagram
    -> content-detail(kind=diagram)
       -> expanded main panel
       -> Back to document
       -> optional Open in new tab
```

Persistent SVG continues to use its stable served target. Inline Mermaid continues to use the adapter-owned rendered SVG and temporary-resource lifecycle. Public themed Mermaid continues to use its active light or dark projection. Content Detail View changes presentation ownership; it does not add another Mermaid renderer, source format, media identity, or publication path.

## Access And Composition

The main-view and panel-layout primitive should remain public-safe because it carries presentation and no management authority. Each route composition still decides which target adapters and controls it imports:

- TE-3 explicitly composes the static table view in public and Manage readers through a public-safe shared module and public import-boundary evidence;
- TE-4 contributes resizing and CSV controls only from the Manage entrypoint unless a later public promotion is separately approved;
- TE-5 decides the exact public/manage diagram composition from the existing Diagram Detail surfaces; and
- Review remains excluded until its returned-package rendering and navigation context are deliberately assessed.

Registering or showing a detail presentation never grants document, clipboard, source, filesystem, or management authority. The public static view reads only the already-rendered public table. Clipboard access exists only when TE-4 contributes the explicit Copy action.

## State And Failure

- Only one Content Detail target is active; nested detail views are unsupported.
- A stale mount generation, missing presentation, unsupported kind, or unavailable adapter rejects entry and leaves the rendered document usable.
- Failure while mounting the detail view returns to the rendered document with an explicit error; it does not navigate away or fall back to an arbitrary presentation.
- Back and normal document navigation release adapter-owned resources and transient width/scroll state.
- Source rebuild or theme re-render invalidates or refreshes the target only through the owning document/diagram lifecycle; the content-detail view does not rescan the document.

## Not In Scope

- a modal, overlay, popup window, secondary app shell, or independent navigation stack;
- editing Markdown, table cells, diagrams, or canonical source from the detail view;
- spreadsheet formulas, sorting, filtering, grouping, row selection, charts, or virtualized data grids;
- persistent column widths or stable table IDs;
- automatic table eligibility based on dimensions, overflow, row count, headings, or viewport;
- default Content Detail presentation for documents with zero, multiple, dynamic, or unsupported targets;
- dynamic report lists, report toolbars, search results, Recent, or sub-scope collection and embedded-detail presentation;
- arbitrary raw page tables or SVG outside the accepted current document mount; or
- a general content-plugin registry before another proven content kind needs it.
