# SSP-0.0 — Projects Subject Assignment Sanity Note

## Decision

The Projects None/Folder foundation fits the shipped sub-scope customisation, exact managed-document target, metadata, modal, local-folder normalization, revision-safe mutation, targeted rebuild, and access-projection owners. Info can remain passive, the registered definition can remain the single capability and field authority, exact managed targets can remain the mutation authority, and public routes can retain their current compact metadata policy.

The original SSP-0 outcome also required Work/Series display, malformed/conflicting subject states, and acceptance evidence for an `analysis/works` copy. Those outcomes did not fit the current schedule: SSP-1 introduces `work_id` and `series_id` meaning and normalized subject states, while SSP-4 owns the later `analysis/works` editorial workflow. The configured Analysis scope currently contains only the `tags` sub-scope.

The approved resolution keeps SSP-0 responsible for passive exact-target Info, the Projects `authoring_subject` capability, None/Folder assignment, generic metadata cleanup, and the SSP-1 extension seam. SSP-1 adds and proves Work/Series display and invalid/conflicting state projection; SSP-4 explicitly creates `analysis/works` and proves the eventual copy remains read-only. SSP-0.1 may proceed on that boundary.

## Scheduling And Accepted Foundation

SSC-1 is complete. The registered customisation definition owns typed `DocsSubScopeAssignableFieldGroup` declarations, validates unique group and field identities, requires Manage browser access, exposes the server declarations through `sub_scope_customisation_assignable_field_groups()`, and projects only group IDs to the browser. The shared browser configuration already normalizes those IDs and provides `hasDocsViewerAssignableFieldGroup()` as the focused-action availability check.

The `dotlineform_projects` registration remains the exact current owner of Projects manifest data, source validation, metadata read/update, import normalization, and Manage-only browser composition. SSP-0 may add `authoring_subject` with server-owned `folder_path`; other registrations retain their own declared capabilities. Browser availability derives only from the resolved registered group.

The shared source model does not yet own normalized Work/Series authoring subjects. The configured Analysis scope has the `tags` sub-scope and no current `works` collection. Pulling either responsibility into SSP-0 would reverse the feature sequence and broaden this UI/mutation foundation into SSP-1 or SSP-4 implementation.

## Broad Owners And Blast Radius

| concern | current owner and SSP-0 boundary |
| --- | --- |
| Info hosting | the shared hosted-view context, Info panel host, and `metadata-info` view retain view-agnostic passive presentation; SSP-0 supplies an explicit active managed-document target and a Projects None/Folder read projection |
| exact sub-scope detail | the shared sub-scope report owns validated detail identity and exact `{scope, sub_scope, doc_id}` actions; the Info bridge must use that active detail rather than the parent report document or Index selection |
| capability and subject fields | the registered sub-scope customisation definition owns availability and server field names; Projects adds only `authoring_subject` and `folder_path` in SSP-0 |
| folder normalization | the shared local-link service owns confined absolute path, local `file:` URL, and portable relative-target normalization; the focused workflow reuses that result rather than adding another parser |
| focused interaction | the Manage modal shell and exact customisation composition own lifecycle, focus return, contained status, cancellation, and capability-selected contribution loading |
| mutation and rebuild | exact managed-target resolution, source revision checks, front-matter formatting, atomic source write, and sub-scope rebuild remain with the management service owners; the subject mutation restricts accepted keys through the resolved assignable group |
| generic metadata separation | the app-level metadata workflow retains universal document fields; its Projects custom editor is removed only after the focused None/Folder workflow proves equivalent ownership |
| assurance | focused customisation, exact-target metadata/mutation, sub-scope report module, metadata Info, service-route, and public-runtime boundaries cover the changed contracts without policing modal choreography |

The credible SSP-0 blast radius is therefore limited to the shared hosted-view target context, sub-scope detail contribution, Projects registration and projection, Manage focused-action/modal composition, the existing folder normalizer and mutation planner, generic metadata cleanup, targeted rebuild follow-through, and their focused tests. Public configuration and runtime remain passive consumers of their current compact document metadata. Work/Series normalization and Analysis Works configuration remain outside this blast radius under the current sequence.

## Accepted Deliverables

- `metadata-info` shows one compact read-only None or Folder summary for the exact active Projects document using the accepted current source projection.
- Only a resolved sub-scope declaring `authoring_subject` exposes **Assign subject**. Projects initially offers None and Folder; currently configured collections retain their own declared capabilities.
- The modal carries the exact target and source revision, reuses the existing folder normalizer, confirms clear or replacement explicitly, contains cancellation and error state, and delegates atomic write plus the required rebuild to existing service owners.
- The app-level **Edit metadata** workflow stops reading, rendering, and submitting Projects `folder_path` after the focused owner is proven.
- SSP-1 can extend the same Projects group and modal with server-owned `work_id` and `series_id` plus existing Catalogue search components while Info remains read-only.

The delivery now defers Work, Series, malformed/conflicting multi-field states, and the future `analysis/works` copy to SSP-1 and SSP-4 rather than treating them as current SSP-0 acceptance targets.

## Exact Target And Access Boundary

The action target is always the explicit `{scope, sub_scope, doc_id}` resolved from the active validated sub-scope detail. A parent report document, selected Index row, title, route label, filename, or previously active document never substitutes for that target. Opening Info or opening and cancelling the modal performs no repair, precedence choice, or mutation.

Projects customisation browser composition remains Manage-only. Public routes retain their current compact metadata projection and passive runtime. Read/display support and quick-assignment support remain separate capabilities, allowing SSP-1 and SSP-4 to add a read-only Analysis Work/Series subject later while the quick editor remains selected by the registered Projects group.

## Risks And Stop Gate

The main implementation risks are projecting the parent report instead of the active sub-document, leaving two `folder_path` editors, accepting unregistered fields through a generic mutation, duplicating folder normalization between Source and modal workflows, losing stale-revision protection, leaking private subject data into public payloads, or activating the workflow through a Projects name check. The sequencing risk is importing Work/Series normalization or Analysis Works creation merely to satisfy premature SSP-0 evidence. Focused exact-target, wrong-target, group-presence, invalid/outside-path, clear/cancel, stale-revision, atomic-write, targeted-build, generic-metadata, and public-isolation evidence must contain the implementation risks at the owning stages.

The scheduling contradiction is resolved through the accepted delivery split. Stop and return for review if the revised slice requires inline Info editing, a generic field-schema engine, broad application-state access, literal scope/sub-scope name checks, an unrestricted cross-collection write service, duplicated folder normalization, public subject controls, Tag workflow changes, or another parallel metadata owner.
