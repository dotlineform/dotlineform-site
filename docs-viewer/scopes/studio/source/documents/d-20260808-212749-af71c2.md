# iPad Studio Working Slice And Proof

## Status

This document extends [iPad Docs Viewer](/docs/?scope=studio&doc=d-20260808-205414-91040a) with a Studio-focused feasibility claim. It records what the current repository architecture suggests should work and what must be proved on the target iPad. It is not evidence that Studio has already passed in iSH, a promise of complete desktop parity, or an implementation delivery.

The Studio gate is incremental. [iPad Docs Viewer Installation And Proof](/docs/?scope=studio&doc=d-20260808-205416-9f6d6c) must first establish the checkout, Python environment, iCloud mount, loopback browser access, and external-scope safety. A Docs Viewer pass remains independently useful even if the Studio gate later exposes a blocker.

## Feasibility Claim

The Studio server is a credible addition to the iPad stack because it is another repository-local Python `ThreadingHTTPServer`, serves its browser assets directly from the checkout, and performs ordinary Catalogue and Tag mutations through Python services and atomic JSON writes. Opening existing Work and Series records, editing classified metadata, and maintaining tags should fit the same iSH and Safari session as Docs Viewer without Node, Ruby, Jekyll, or a second clone.

The main uncertainties are not basic server startup. They are the field-aware public build automatically requested when an already-published Catalogue record is saved, project-media access through the iCloud mount, platform-specific media tools, remote publication side effects, and whether Studio's dense desktop-oriented layout remains practical in the exact supported iPad posture.

## Intended Composition

```text
Safari
  -> http://127.0.0.1:8776/docs/
      -> Docs Viewer Python service
          -> exact Studio links
  -> http://127.0.0.1:8765/studio/
      -> Studio Python service
          -> canonical Catalogue and Tag JSON in the iSH checkout
          -> targeted generated Catalogue products in the iSH checkout
          -> read-only project-media browsing through /mnt/dlf-projects
```

The baseline uses one checkout and one active Python environment. The checkout, `.git`, generated repository products, and caches remain inside iSH storage. Only the configured external projects base is mounted from iCloud. This preserves Git-visible Studio mutations on a Linux-native filesystem and avoids moving high-churn repository state onto File Provider storage.

## Recommended Service Profile

After the Docs Viewer gate passes, activate the same environment and start the bounded two-service profile from the repository root:

```sh
. /root/venvs/dotlineform/bin/activate
SITE_ENABLED=0 ADMIN_APP_ENABLED=0 DOCS_WATCH_ENABLED=0 bin/local-all
```

This retains Studio and Docs Viewer while disabling the public-site preview, Admin, and the continuous Docs watcher. The watcher is unnecessary for the initial linked-editing proof because Docs Viewer managed saves and Studio Catalogue saves already invoke their own follow-through. Disabling it reduces background polling and makes iCloud write evidence easier to attribute.

The current launcher is Bash-based and chooses the active `python3` when Miniconda is absent, so it should fit the iSH environment proposed by the installation guide. This remains a device hypothesis until the exact command starts both services and stops them cleanly in iSH.

## Expected Working Slice

| area | expectation before device proof | qualification |
| --- | --- | --- |
| Studio health, shell, and runtime config | should work | repository-local Python server and tracked browser assets |
| Docs Viewer to Work Editor links | should work | the existing link contains the exact Work id and uses the configured Studio loopback base |
| search and open existing Works and Series | should work | canonical records and lookup projections are repository-local |
| edit classified textual Work metadata | should work | atomic source write plus field-aware lookup and public-product refresh |
| edit classified textual Series metadata and membership | should work | the same published-record build qualification applies |
| Catalogue drafts, status, and field-registry reads | should work | ordinary repository JSON reads and browser rendering |
| Tag Registry, aliases, groups, and Series assignments | expected | mostly atomic repository JSON mutations; exact keyboard-and-trackpad behavior must pass |
| Git status and diff review after a save | should work | mutations remain inside the iSH checkout |
| project-media folder and file listing | expected read-only | depends on the mounted iCloud projects tree and complete local downloads |
| committed local and remote media display | expected with qualifications | local files must exist; remote media requires network access |

This slice is centred on maintaining existing records reached from Docs Viewer. Bulk import or onboarding new Works is not required to establish useful iPad Studio operation.

## Published-Record Save Boundary

The Work and Series editors request a build automatically when the edited record is published. The server then applies the Catalogue field registry to the exact changed fields. Known textual fields select bounded JSON, page, index, lookup, or search products; `provenance` is editor-only; project-media source fields select local-media work. Draft saves do not request the published build.

This makes ordinary published metadata editing plausible but not automatically supported. The proof must exercise representative classified fields and inspect the exact source and generated diff. Unknown fields or mixed dependency classes can use the conservative fallback, so a successful title edit does not prove every Work field. Changes to `project_folder`, `project_subfolder`, `project_filename`, Work Detail media identity, or media versions remain outside the initial write claim.

Absence of macOS `sips` is not by itself a blocker for ordinary generation because dimension reads return no value when the tool is unavailable. A pending media plan that requires `ffmpeg`, HEIF or video handling, or other unavailable media machinery is a separate failure and must not be hidden by describing the overall save as supported.

## Project And iCloud Boundary

Studio's canonical Catalogue and Tag JSON is repository-owned and therefore does not depend on iCloud for ordinary metadata editing. The project-media picker and any workflow that reads original project files cross into the mounted external base. The initial proof permits exact read-only folder and file listing there; it does not authorize media generation, source-file mutation, or remote publication.

The external root must remain the same exact `DOTLINEFORM_PROJECTS_BASE_DIR` established by the Docs Viewer gate. Keep required project folders downloaded and do not concurrently mutate the same external files from the Mac and iPad. A placeholder, conflict copy, resurrected temporary path, partial listing, or unstable rename is a File Provider issue to understand before broadening Studio's external-write claim.

Project State remains Docs Viewer-owned read-only reconciliation of physical folders, Project documents, and historical Studio Work paths. Running Studio on iPad adds an exact editing destination for existing Work or Series links; it does not make Project State a Studio mutation path or permit identity inference from titles, filenames, routes, or selected rows.

## Supported Interaction And Layout Boundary

The initial supported posture is the target latest-generation 11-inch iPad Air with its hardware keyboard and trackpad attached, Safari running full-window in landscape, and pointer-and-keyboard interaction treated as primary. Touch is incidental rather than a supported primary workflow. The proof receipt must record the exact iPad model, keyboard and trackpad, iPadOS version, Safari page zoom, and any display setting that materially changes the available viewport.

Studio is not required to support portrait, Split View, a narrow Stage Manager window, touch-only editing, or another iPad size. No responsive or touch-optimisation delivery is implied. The device proof assesses pointer targets, trackpad scrolling, keyboard entry, selection, save feedback, popovers, and double-click-dependent actions only in the supported posture. If a core control remains unusable there, record the exact compatibility defect; do not broaden the task into general mobile interaction design.

## Deferred Or Excluded Workflows

- Bulk Add Work, workbook import, and routine creation of new Works or Series are not initial iPad use cases.
- Project-media source changes, derivative generation, HEIF and video handling, and media-version workflows are deferred.
- R2 publication, remote media deletion, credentials, and any other external side effect are excluded from the initial proof.
- Publish, unpublish, delete, and broad Catalogue rebuild actions require separate evidence because their blast radius exceeds an ordinary metadata save.
- Admin, Jekyll production builds, the complete public-site development toolchain, and full repository test profiles are outside this Studio slice.
- Always-on background service operation is not promised; the restartable foreground-session boundary from the Docs Viewer concept still applies.

These exclusions are deliberate scope boundaries. They do not prevent Studio from being useful as an existing-record metadata and tag editor.

## Configuration Decision

Studio strengthens the case for an eventual named iPad profile because the useful session has explicit service toggles and two ports. It does not yet justify adding an unproved `env.ipad` reader. For the device gate, keep non-secret device values in the ignored `.env.local` and pass the bounded service switches directly to `bin/local-all` as shown above.

If repeated use proves the shape, a later delivery may add a committed `.env.ipad.example`, an ignored active `.env.ipad`, and a small `bin/local-ipad` launcher with explicit loading precedence. That delivery must prove that it reduces setup error without duplicating `.env.local`, committing device paths or credentials, or creating two competing configuration authorities.

## Studio Proof Gate

Use the disposable `ipad-proof` branch created by the installation guide. Do not push the branch, invoke remote publication, or edit the same proof records concurrently on another device.

### A. Composition And Exact Links

- [ ] Start the bounded profile with `SITE_ENABLED=0 ADMIN_APP_ENABLED=0 DOCS_WATCH_ENABLED=0 bin/local-all` and record both service URLs and process output.
- [ ] Confirm Docs Viewer and Studio health endpoints respond in Safari while iSH remains active.
- [ ] Open the Studio home, Work Editor, Series Editor, Tag Registry, and Series Tags routes without a blocking browser or API error.
- [ ] Follow one existing Docs Viewer report link into Studio and confirm the exact expected Work id is loaded rather than inferred from display text or route context.
- [ ] Stop the launcher once with Ctrl+C and confirm both services exit cleanly, then restart it and reopen both apps.

### B. Repository Reads

- [ ] Search for and open one existing Work and one existing Series; confirm their ids, titles, status, and membership agree with the canonical repository records.
- [ ] Open Catalogue status and field-registry views and confirm their API-backed content loads.
- [ ] Open Tag Registry, aliases, groups, and Series assignments and confirm existing exact identities are preserved.
- [ ] Run `git status --short` before the first mutation and confirm the proof checkout is clean apart from any separately recorded setup evidence.

### C. Safe Catalogue Writes

- [ ] On a pre-designated disposable draft or local proof record, change one classified non-media textual field through the Work Editor and confirm the save response, reloaded record, canonical source diff, and lookup projection.
- [ ] Repeat with one classified non-media Series field or membership change and confirm the exact affected source and lookup products.
- [ ] On the unpushed proof branch, make one temporary classified text-only change to an existing published record and confirm the field-aware build succeeds without selecting local-media work.
- [ ] Inspect `git status --short`, the exact diff, and `git diff --check`; record every changed generated product and treat an unexpected broad or media diff as a failed check.
- [ ] Restore the proof values through an understood reversible workflow or discard the disposable clone after evidence capture; do not publish the proof branch.

### D. Tag Writes

- [ ] Perform one disposable Tag Registry, alias, group, or Series-assignment mutation that has an exact before and after identity.
- [ ] Reload the relevant route and confirm the canonical repository JSON and browser state agree.
- [ ] Reverse the disposable mutation through the supported Studio action and confirm the final diff contains no unrelated Tag changes.

### E. Project-Media Read And Platform Boundary

- [ ] From an existing Work, open the project-media picker or equivalent exact browser and list one known iCloud-backed project folder and file without changing a media-source field.
- [ ] Confirm the listed path corresponds to the configured mounted base and was not reconstructed from the Work title or filename display text.
- [ ] Confirm no media derivative, R2 request, external source mutation, or unexpected temporary iCloud file is produced.
- [ ] Record remote-thumbnail behavior separately from local project-file access and note whether loss of network connectivity affects only remote media display.

### F. Target-Posture And Session Usability

- [ ] Record the exact 11-inch iPad Air model, attached hardware keyboard and trackpad, iPadOS version, full-window landscape posture, Safari page zoom, and any relevant display setting.
- [ ] Complete the Work, Series, and Tag read/edit checks using the hardware keyboard and trackpad; record any inaccessible pointer target, broken trackpad scroll, blocked keyboard entry, or double-click dependency that fails with the trackpad.
- [ ] Confirm the core routes remain practical at the recorded full-window landscape viewport without requiring portrait, Split View, touch-only operation, or a narrower-window workaround.
- [ ] Background and resume iSH once during a Studio session, restart the bounded profile if suspended, and confirm the last completed repository mutation remains consistent.
- [ ] Distinguish a server/runtime failure from a target-posture interaction problem; do not mark either one passed because the other layer works.

## Pass Rule

The initial Studio slice passes only when A and B succeed, the exact linked Work opens, at least one draft or proof-record Work save and one Series save survive reload with an explained repository diff, one classified published text-only save completes without media work, D round-trips without unrelated mutation, and the read-only project-media check in E produces no external side effect. On the recorded 11-inch iPad Air with hardware keyboard and trackpad, full-window landscape must support the core Work, Series, and Tag interactions without an inaccessible required control.

Portrait, Split View, narrow Stage Manager windows, touch-only operation, and other iPad sizes are outside the gate and need not be tested. Passing makes no claim about them and creates no responsive-design obligation. The other exclusions above remain excluded even after the gate passes.

A startup-only result, successful reads without safe writes, a save with unexplained broad output, accidental local-media selection, identity inferred from UI text, an iCloud side effect during the read-only check, or a core editor that cannot be operated with the required keyboard and trackpad in full-window landscape is not a pass.

## Candidate Deliveries After Proof

Create no implementation delivery until device evidence identifies an independently useful repository outcome. Plausible evidence-led deliveries include:

- a tested `bin/local-ipad` and environment-profile contract;
- an Alpine/iSH dependency profile when the installed package set is stable;
- a narrowly targeted compatibility fix for a core control that fails with the required keyboard and trackpad in full-window landscape;
- a platform-capability boundary that disables unavailable media actions without changing desktop behavior;
- a File Provider robustness fix tied to a reproduced external-path failure.

Do not create a generic mobile abstraction, second Studio server, duplicate Catalogue writer, parallel configuration authority, or broad media compatibility layer merely because iPad support is being evaluated.
