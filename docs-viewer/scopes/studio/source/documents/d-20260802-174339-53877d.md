# Resolver Tokens Architecture

## Purpose

Resolver Tokens let an author insert a current-references marker that expands the containing sub-scope document's normalized subject into an ordered relationship result at build time. The initial adapter resolves one exact Folder, Work, or Series subject through focused relationship data, then the destination collection projects only its declared result groups. A relevant build refreshes the required private relationship data once before consumption rather than depending on manual report use or continuous mutation hooks.

This is a retained component draft. SSP-3.0 must reconcile its initial folder result groups with the accepted typed-subject and focused-lookup contracts in [Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee). Its one-hop lookup, source preservation, semantic projection, usage, access, freshness, and non-mutation boundaries remain inputs to that revision.

Resolver Tokens are adjacent to, but distinct from, Semantic Tokens. A Semantic Token resolves one registered identity to one link. A Resolver Token expands the containing document's normalized subject into one or more declared result groups. Returned registered identities reuse the Semantic Tokens target, link, and usage owners; the resolver retains its own parser, context contract, lookup adapter, group renderer, and access policy.

## Core Model

The initial process is:

```text
Resolver Token + normalized containing subject
    -> one subject-keyed relationship result in memory
    -> seed and related semantic target identities
    -> collection-specific result-group projection
    -> ordinary HTML links in content_html
```

The source token remains unchanged and carries no manually authored seed. The containing document's front matter supplies the seed subject; relationship preparation returns that exact seed plus related Folder, Work, and Series identities. Work and Series identities are semantic target descriptors held in memory, not fabricated `[[catalogue:...]]` source. The shared Semantic Tokens projector resolves them directly to ordinary anchors, and only those anchors enter built `content_html`.

Relationship resolution and result projection are separate decisions. Copy preserves canonical subject front matter without interpreting it. The destination collection decides at build time which resolved groups may appear:

| subject | `dotlineform/projects` projection | `analysis/works` projection |
| --- | --- | --- |
| Folder | seed Folder, related Series, singleton or otherwise unrepresented Works | related Series, singleton or otherwise unrepresented Works; Folder suppressed |
| Work | seed Work, related Folder, related Series | seed Work, related Series; Folder suppressed |
| Series | seed Series, related Folders, singleton or otherwise unrepresented Works | seed Series, singleton or otherwise unrepresented Works; Folders suppressed |

A Folder subject retained by Copy therefore remains a valid relationship seed in `analysis/works`; the Analysis projection suppresses the Folder result rather than deleting or ignoring the subject. Resolver depth remains exactly one: the prepared row contains the complete declared relationship result, and token expansion never follows a returned Series to discover Works or a returned Work to discover another Folder.

The seed subject is explicit result provenance rather than hidden presentation state. When its result type is allowed by the destination projection, it appears first as a link under the Subject part of the current-references block. A Work or Series seed uses the shared semantic link projector; a Folder seed uses the local Project link owner and can appear only in an allowed private projection.

Related Works remain concise without silently losing navigation. A seed Work always appears when Work results are allowed. Otherwise one related Work appears directly; when several Works are already represented by successfully projected Series links, those Work links are omitted. Any related Work not represented by a projected Series remains eligible for a direct Work link.

Resolution reads one normalized subject from the containing document's registered collection context, performs one exact subject-row read, and never scans the filesystem, collection manifest, canonical Works, canonical Series, Moments, or another relationship registry during token expansion. Before rendering, the build prepares current subject-keyed relationship rows once from their focused owners. Folder relationships originate in the current Project State generation; Work/Series membership remains catalogue-owned and enters only the focused resolver preparation. Zero matches, unavailable lookup, stale generation, invalid subjects, unavailable semantic targets, and denied access have explicit reader outcomes. Individual Resolver Token expansion never refreshes relationship data or mutates source.

## Source And Usage Examples

The reader-facing Series link can be equivalent in all three cases. Source and generated usage evidence distinguish how it came to exist.

### Manually Authored Markdown Link

```md
[nerve](/series/?series=105)
```

This is an ordinary authored URL. The Markdown renderer produces an anchor, but there is no semantic identity in source and no semantic usage row.

### Authored Semantic Token

Using **Add catalogue token** inserts:

```md
[[catalogue:series:105|nerve]]
```

The builder resolves `(catalogue, series, 105)`, renders the current semantic destination, and records one authored-token usage row at that exact source range.

### Resolver-Generated Semantic Link

The exact Resolver Token syntax is an SSP-3.0 decision. Until then this source is illustrative only:

```md
[[resolver:current-references]]
```

For a document declaring `series_id: "105"`, the in-memory result may contain:

```json
{
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

The builder passes that descriptor through the shared semantic target lookup and link projector. It records one resolver-derived usage row for Series `105` at the containing Resolver Token range. The source and built HTML contain no fabricated `[[catalogue:series:...]]` text; readers see an ordinary link, while maintainers can inspect its semantic identity and `resolver_result` origin in the Manage Semantic Tokens report.

### Collection Projection Examples

The examples use current catalogue identities to illustrate the rule; titles and membership remain current lookup values rather than copied resolver data.

`work_id: "00635"` identifies Work **10,000 (1)**, which belongs to Series `001` **10,000** and Project Folder `projects/10000`:

```text
dotlineform/projects -> Subject: Work 00635; Related: Folder projects/10000, Series 001
analysis/works       -> Subject: Work 00635; Related: Series 001
```

`series_id: "001"` identifies Series **10,000**, currently containing Works `00635`, `00636`, and `00637` in Folder `projects/10000`. The Series is the seed link and already represents all three Works, so individual Work links are omitted:

```text
dotlineform/projects -> Subject: Series 001; Related: Folder projects/10000
analysis/works       -> Subject: Series 001
```

`series_id: "003"` identifies Series **16 forms**, which currently has one Work, `00639`, in Folder `projects/16 forms`. The singleton Work remains useful as a direct link:

```text
dotlineform/projects -> Subject: Series 003; Related: Folder projects/16 forms, Work 00639
analysis/works       -> Subject: Series 003; Related: Work 00639
```

A copied document retaining `folder_path: "projects/10000"` uses that Folder as its relationship seed in both collections:

```text
dotlineform/projects -> Subject: Folder projects/10000; Related: Series 001
analysis/works       -> Related: Series 001
```

The Analysis build consumes the private Folder relationship only to obtain allowed catalogue identities. It emits no Folder seed, local link, `folder_path`, lookup row, or Project capability into the public projection.

The usage rows below are illustrative; SSP-3.0 freezes their exact schema and field names:

```json
{
  "origin": "authored_token",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 155},
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

```json
{
  "origin": "resolver_result",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 178},
  "resolver_id": "<project-resolver-id>",
  "subject_kind": "folder",
  "subject_key": "projects/nerve",
  "result_group": "series",
  "result_role": "related",
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

## Resolver Definition And Lookup Contract

- A small code-owned definition registry contains capability metadata only: resolver ID, access, accepted subjects, lookup/schema, and result groups.
- Project State remains the only producer of physical Folder-to-Work/Series evidence. SSP-3 prepares the bounded subject-keyed resolver view once per relevant build from that current generation and the focused catalogue membership projection; token expansion reads one exact row.
- Resolution order is exact parse, access check, normalized subject read, current relationship-row read, seed/related classification, collection result-group projection, and semantic-link projection for allowed registered identities.
- Folder subject keys are normalized paths relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`. The initial Project relationship view accepts the immediate `projects/<project-directory>` identities established by Project State without widening its discovery scan. Work and Series subjects retain exact canonical string identity.
- Folder results sort by normalized key, Series by canonical Series ID, and Works by canonical Work ID. The seed precedes related groups when its type is allowed.
- A selected build containing a Resolver Token that needs Folder relationships refreshes Project State once after current subject products are available and before resolver preparation. It uses the resulting generation for every selected token; individual token expansion never refreshes it again.
- The token syntax serializes no subject; the registered collection supplies the exact normalized kind and key at resolve time.
- A later resolver may define another exact subject and returned registered target type, but that does not widen the initial Project resolver.

## Semantic Link And Usage Contract

- The resolver view stores Work and Series semantic identities, not a second title or URL authority.
- Every Work and Series result, including an allowed seed, passes through the existing Semantic Tokens target lookup and link projector. The resolver never carries or emits a plain catalogue URL and never fabricates Semantic Token syntax in source.
- A missing, stale, or unusable semantic target renders an explicit unavailable result, never falls back to a resolver-owned URL, and produces no resolved usage row.
- Every successfully projected Work or Series adds one resolver-derived row to the containing scope's generated semantic usage index. One Resolver Token may produce several rows with the same containing source range and different identities.
- Usage rows distinguish authored Semantic Tokens from resolver-derived results while retaining source scope/document, containing source range, displayed title, semantic family/type/id, resolved `href`, resolver/subject provenance, result group, and `seed` or `related` role.
- The Semantic Tokens report includes resolver-derived rows and links back to the managed document and containing Resolver Token location.

## Access And Lifecycle

Resolver output is read-only presentation and grants no mutation authority. A local Manage projection may render Folder links. A publication build may privately consume an exact Folder relationship row when a retained Folder subject seeds an `analysis/works` Resolver Token, but its allowed projection contains only Work and Series anchors. Public payloads and runtime remain free of Folder identities, local paths, private lookup data, resolver definitions, and refresh capabilities.

Resolver definitions are code-owned and loaded through explicit build composition. The system does not discover resolvers by scanning registries, documents, files, or runtime modules. Targeted builds preserve untouched usage rows and update only occurrences in rebuilt documents.

Build planning recognises the exact token and normalized subject kinds in the selected source set before scheduling dependencies. Builds whose selected tokens need no Folder relationship perform no Project State work. A publication build may execute the same private prerequisite for a Folder-seeded token, but neither its generated payload nor public runtime receives the lookup, refresh capability, local relationships, or Folder results. A failed prerequisite renders the accepted stale/unavailable outcome for affected tokens and does not silently consume an older lookup as current.

## Architecture Boundary

Not in scope:

- unbounded or inferred subject kinds and result groups;
- recursive traversal or adjustable depth;
- relationship chaining during individual token expansion;
- relationship-path explanations or graph visualization;
- a global relationship database, query language, registry scanner, or live relationship service;
- Studio or Docs post-commit synchronization hooks for the Project State lookup;
- per-document or per-token Project State refresh;
- automatic rebuilding of every document that uses a changed resolver row;
- public projection of local Folder relationships; or
- migration of Semantic Tokens into Resolver Tokens.

[Project State Concept And Architecture](/docs/?scope=studio&doc=d-20260802-121105-c574f9) owns the initial lookup meaning, producer, generation, and failure semantics. Resolver Tokens owns scheduling that producer immediately before relevant build-time consumption. [Semantic Tokens Architecture](/docs/?scope=studio&doc=d-20260714-234030-434069) owns semantic target projection and usage evidence. [Sub-Scope Publishing](/docs/?scope=studio&doc=d-20260802-194357-4d857b) owns overall sequencing; this document retains resolver-specific architecture.
