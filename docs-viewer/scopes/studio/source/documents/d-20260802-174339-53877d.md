# Resolver Tokens Architecture

## Purpose

Resolver Tokens let an author insert a current-references marker that expands the containing sub-scope document's normalized subject into an ordered relationship result at build time. The initial adapter resolves one exact Project subject through a versioned focused lookup and returns its declared result groups.

This is a retained component draft. SSP-3.0 must reconcile its initial folder result groups with the accepted typed-subject and focused-lookup contracts in [Sub-Scope Publishing Concept And Architecture](/docs/?scope=studio&doc=d-20260802-194358-7717ee). Its one-hop lookup, source preservation, semantic projection, usage, access, freshness, and non-mutation boundaries remain inputs to that revision.

Resolver Tokens are adjacent to, but distinct from, Semantic Tokens. A Semantic Token resolves one registered identity to one link. A Resolver Token expands the containing document's normalized subject into one or more declared result groups. Returned registered identities reuse the Semantic Tokens target, link, and usage owners; the resolver retains its own parser, context contract, lookup adapter, group renderer, and access policy.

## Core Model

The initial relationship is:

```text
folder -> Series[] + Project documents[]
```

The source token remains unchanged and carries no manually authored seed. Resolution reads one normalized subject from the containing document's registered collection context, performs one exact focused lookup-row read, and never scans the filesystem, collection manifest, canonical Works, canonical Series, Moments, or another relationship registry. Resolver depth is exactly one and returned items are never resolved again.

Zero matches, unavailable lookup, stale generation, invalid subjects, unavailable semantic targets, and denied access have explicit reader outcomes. Resolver expansion never refreshes Project State or mutates source.

## Source And Usage Examples

The reader-facing Series link can be equivalent in all three cases. Source and generated usage evidence distinguish how it came to exist.

### Manually Authored Markdown Link

```md
[nerve](/series/?series=105)
```

This is an ordinary authored URL. The Markdown renderer produces an anchor, but there is no semantic identity in source and no semantic usage row.

### Authored Semantic Token

Using **Add catalogue token** inserts:

```md
[[catalogue:series:105|nerve]]
```

The builder resolves `(catalogue, series, 105)`, renders the current semantic destination, and records one authored-token usage row at that exact source range.

### Resolver-Generated Semantic Link

The exact Resolver Token syntax is an SSP-3.0 decision. Until then this source is illustrative only:

```md
[[resolver:current-references]]
```

The exact Project State row may contain:

```json
{
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

The builder passes that descriptor through the shared semantic target lookup and link projector. It records one resolver-derived usage row for Series `105` at the containing Resolver Token range. The source contains no fabricated `[[catalogue:series:...]]` text.

The usage rows below are illustrative; SSP-3.0 freezes their exact schema and field names:

```json
{
  "origin": "authored_token",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 155},
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

```json
{
  "origin": "resolver_result",
  "source_doc_id": "d-...",
  "source_range": {"start": 120, "end": 178},
  "resolver_id": "<project-resolver-id>",
  "subject_kind": "folder",
  "subject_key": "projects/nerve",
  "family": "catalogue",
  "target_type": "series",
  "target_id": "105"
}
```

## Resolver Definition And Lookup Contract

- A small code-owned definition registry contains capability metadata only: resolver ID, access, accepted subjects, lookup/schema, and result groups.
- Project State is the only producer of the initial Project lookup. The Project resolver accepts declared Project subject kinds and returns only the registered groups frozen for each kind; the first folder view remains `Series[] + Project documents[]`.
- Resolution order is exact parse, access check, lookup load, exact subject read, declared-group rendering, and semantic-link projection for registered identities.
- Folder subject keys are normalized paths relative to `$DOTLINEFORM_PROJECTS_BASE_DIR/`, so exact declared contained folders outside `projects/` remain addressable without widening discovery scans. Work subjects retain exact canonical string identity.
- Series results sort by canonical Series ID. Project documents sort by normalized title then `doc_id`.
- Lookup refresh and containing-document rebuild are separate operations. Resolver expansion never refreshes Project State.
- The token syntax serializes no subject; the registered collection supplies the exact normalized kind and key at resolve time.
- A later resolver may define another exact subject and returned registered target type, but that does not widen the initial Project resolver.

## Semantic Link And Usage Contract

- The Project lookup stores Series semantic identity `(catalogue, series, canonical id)`, not a second title or URL authority.
- Every Series result passes through the existing Semantic Tokens target lookup and link projector. The resolver never carries or emits a plain catalogue URL and never fabricates Semantic Token syntax in source.
- A missing, stale, or unusable semantic target renders an explicit unavailable result, never falls back to a resolver-owned URL, and produces no resolved usage row.
- Every successfully projected Series adds one resolver-derived row to the containing scope’s generated semantic usage index. One Resolver Token may produce several rows with the same containing source range and different Series identities.
- Usage rows distinguish authored Semantic Tokens from resolver-derived results while retaining source scope/document, containing source range, displayed title, semantic family/type/id, resolved `href`, and resolver/subject provenance.
- The Semantic Tokens report includes resolver-derived rows and links back to the managed document and containing Resolver Token location.
- Project-document results retain exact Docs Viewer target identity and do not masquerade as Semantic Token targets.

## Access And Lifecycle

The initial Project resolver is Manage-only because its lookup and result documents expose local Project relationships. Resolver output is read-only presentation and grants no mutation authority. Public builds and runtime must remain free of the Project definition, lookup, local paths, and rendered local results.

Resolver definitions are code-owned and loaded through explicit build composition. The system does not discover resolvers by scanning registries, documents, files, or runtime modules. Targeted builds preserve untouched usage rows and update only occurrences in rebuilt documents.

## Architecture Boundary

Not in scope:

- unbounded or inferred subject kinds and result groups;
- recursive traversal or adjustable depth;
- `folder -> Series -> Works` chaining;
- relationship-path explanations or graph visualization;
- a global relationship database, query language, registry scanner, or live relationship service;
- automatic rebuilding of every document that uses a changed resolver row;
- public exposure of local Project relationships; or
- migration of Semantic Tokens into Resolver Tokens.
