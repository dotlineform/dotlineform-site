# First-class Tag Creation Delivery

## Complete Result

New Tag creates exactly one canonical tag through a first-class server mutation
and no longer calls the bulk tag-registry import route.

The user-visible creation workflow remains the same: choose a group, enter a
slug and description, create, then reload the canonical registry and record
activity evidence.

## Why This Comes First

The current browser create path sends a one-row registry payload to the import
endpoint in `add` mode. Bulk import cannot be removed safely until ordinary
creation has its own contract.

## In Scope

- Add a focused create planner and server request/response contract through the
  Studio tag mutation boundary.
- Enforce allowed group, `<group>:<slug>` identity, duplicate rejection,
  description normalization, and server-owned timestamps.
- Add one row without rewriting unrelated registry rows.
- Use the existing allowlisted atomic write and activity owners, with a distinct
  create action rather than import-shaped evidence.
- Switch the New Tag browser workflow to the create operation.
- Preserve the supported manual JSON patch fallback when the local write
  service is unavailable.
- Cover service, route, browser payload, runtime configuration, and activity
  behavior with focused tests.

## Not In Scope

- Removing or changing bulk import UI and endpoints; that belongs to the final
  removal delivery.
- Changing edit, delete, demotion, aliases, assignments, or tag groups.
- Adding document associations or other registry fields.
- Changing existing canonical tag records.

## Likely Authority

- `studio/services/tags/tag_source_model.py`
- `studio/services/tags/tag_registry_mutations.py`
- `studio/services/tags/tag_write_transactions.py`
- `studio/app/server/studio/studio_tag_api/registry.py`
- `studio/app/server/studio/studio_tags_api.py`
- `studio/app/frontend/js/tag-registry-service.js`
- `studio/app/frontend/js/tag-registry.js`
- Studio runtime service and activity configuration
- focused tag registry planner, route, workflow, and smoke tests

These are inspection starting points, not a requirement to change every file.

## Completion And Evidence

- A valid request adds exactly one normalized registry row and leaves all
  existing rows unchanged.
- Invalid group, malformed slug, duplicate ID, and malformed payload requests
  fail before any write.
- New Tag no longer requests the import endpoint in direct-write mode.
- Successful creation reloads canonical data and records one create-tag activity
  action.
- Manual patch mode still produces one valid row without implying that it was
  written.
- Focused planner/API tests, route/module integration checks, and a manual New
  Tag interaction pass support only these claims.
- `studio/data/canonical/tags/tag-registry.json` is unchanged by delivery
  implementation and verification.

## Durable Destination

Transfer the shipped create workflow and extension boundary to
