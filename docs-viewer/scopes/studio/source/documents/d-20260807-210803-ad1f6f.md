# SSP-7.0 — Document Lineage And Publication State Sanity Note

## Outcome

SSP-7 fits the shipped Docs Viewer owners as a bounded extension of exact selection, collection-aware Copy, scope-wide Publish, and opt-in sub-scope report composition. SSP-4 already preserves exact source and target collection identities and returns exact source-to-target document mappings. SSP-7 can persist those mappings without comparing content, inferring identity, or creating another transfer or publication workflow.

The gate was amended after review of the legacy `viewable` field in local scopes. The accepted replacement is one clean-cut, public-scope-only `publishable` contract. Local and local-external scopes have no Publish projection and therefore receive neither this field nor **Set Publishable…**. This materially expands SSP-7.1 beyond the original UI-focused estimate, so the first implementation step is split into contract cutover and action batches with a review between them.

The amended gate is complete. SSP-7.1a may begin only after explicit implementation approval; no runtime behavior, metadata endpoint, source front matter, generated management projection, public projection, or lineage table changes at SSP-7.0.

## Confirmed Owners And Fit

- The current one-document **Edit metadata** path reads and writes legacy `viewable`, removes the explicit field for true, writes `viewable: false` for false, and rebuilds the exact parent scope or sub-scope. It is not an acceptable checkbox-aware batch boundary because repeated calls could commit only part of a selection.
- The parent Index action owner already resolves the exact checked `doc_ids` under one `{scope}`. The default sub-scope contribution separately owns exact checked `doc_ids` under one `{scope, sub_scope}` and registers selection actions through the shared composition. Neither owner needs a route, title, filename, active document, report host, or displayed-row fallback.
- Legacy `viewable` currently combines two meanings: public Publish eligibility and local search/default discovery suppression. A local document remains generated and Manage-loadable when false, so the name does not describe access and **Set Publishable…** would be false in a scope with no Publish capability.
- `publishable` therefore exists only on an exact parent or child collection with a configured public projection owned by a scope that supports Publish. **Set Publishable…** uses that same server-owned capability. The existing scope-level **Publish** action remains separately capability-gated, scope-wide, and unchanged.
- The existing choice-modal primitive already supplies the required radio option group, **OK**, **Cancel**, focus lifecycle, and contained error presentation. The focused workflow supplies the exact selected-count label; SSP-7.1b needs no new modal framework.
- Copy planning and apply already carry exact source and target collections, fresh target IDs, source-to-target mappings, target publication eligibility, viewer URLs, stale-safe receipts, and durable activity evidence. A small registered customisation aspect can opt `dotlineform/projects` and `analysis/works` into one lineage contract with explicit source and editorial roles; no loose scope config or literal browser branch is needed.
- Publish already computes and applies the complete public parent, sub-scope, search, and document-location projection. The internal document-location producer retains exact `{scope, sub_scope, doc_id}` while deriving the public URL, so SSP-7.3 can reconcile actual public B projections without parsing URLs or exposing private identity publicly.
- The normal Projects list composes the default sub-scope row with the `dotlineform_projects` Manage customisation. Its manage-only manifest projection is the bounded place to attach lineage rows to exact A. The Analysis Works list already owns B identity and the legacy exclusion icon; a separate Manage-only `analysis_works` contribution can add publication presentation without changing that icon's distinct role or Project State.

## Private Table Authority

Docs Viewer owns `docs-viewer/data/canonical/document-publication-lineage.json`. It is repository-tracked canonical operational data, outside `docs-viewer/data/generated/`, every scope output, and `site/`. Its exact contract is:

```json
{
  "schema_version": "docs_document_publication_lineage_v1",
  "rows": [
    {
      "source": {"scope": "dotlineform", "sub_scope": "projects", "doc_id": "A"},
      "editorial": {"scope": "analysis", "sub_scope": "works", "doc_id": "B"},
      "created_at": "2026-08-07T20:00:00Z",
      "last_copied_at": "2026-08-07T20:00:00Z",
      "publication": {
        "public_url": "/analysis/?doc=d-20260807-082735-54d9d5&subdoc=B",
        "published_at": "2026-08-07T20:30:00Z",
        "generation": "sha256:..."
      }
    }
  ]
}
```

Every row contains exactly those five fields. `source` and `editorial` each contain exactly `scope`, `sub_scope`, and `doc_id`. `publication` is either `null` or contains exactly `public_url`, `published_at`, and `generation`. UTC timestamps use the shown second-precision `Z` form. `generation` is `sha256:` plus the SHA-256 hex digest of the UTF-8 public URL, one null byte, and the exact public by-ID projection bytes. Rows are unique by exact source/editorial pair and sort deterministically by source scope, sub-scope, doc ID, then editorial scope, sub-scope, doc ID. A may own zero, one, or several rows; no row is primary.

One table service validates the complete file, compares its pre-write digest, renders the complete next table deterministically, and atomically replaces it. Copy writes lineage only after the exact target mutation and rebuild succeed. If table follow-through then fails, Copy returns explicit stale lineage evidence and preserves the exact successful source-to-target mapping in its result/activity as the only recovery input; it never guesses or records a target that did not commit. Publish similarly mutates public output first, then reconciles the table from exact current public inventory. A post-public table failure is explicit and recoverable from that inventory, while a failed public mutation never advances publication evidence.

Rows survive an unavailable or deleted B as exact historical lineage. Reports show that exceptional target as unavailable; they do not delete the row, choose a substitute B, or infer repair. The table, its digests, A identities, and recovery evidence never enter public configuration, manifests, locations, search, or by-ID payloads.

## Copy, Replace, And Publish Boundary

The opt-in seam is one typed `document_lineage` customisation aspect with exact `contract_id`, `role`, and collection ownership. `dotlineform_projects` advertises contract `dotlineform_projects_to_analysis_works` with role `source`; `analysis_works` advertises the same contract with role `editorial`. Copy exposes New/Replace only when the exact source and target collection aspects match. Other Copy routes remain unchanged.

New retains the shipped fresh-identity Copy transformation. Replace is allowed only for one B selected from A's current exact table rows and binds the confirmation receipt to B's collection, ID, and source digest. It preserves B's ID, filename, collection placement, `added_date`, and current `publishable`; replaces content and transferable metadata; advances `last_updated`; and rebuilds the exact target collection. It performs no diff, merge, synchronization, automatic choice, or arbitrary overwrite.

Scope-wide Publish remains the only public mutation. Its desired public inventory is the authority for adding, retaining, changing, or clearing B publication evidence. The Projects stage uses exact current public projection, not `publishable`: a still-public B excluded from the next Publish remains 🟢 Published until successful Publish removes it; an editorial B without an exact public projection is 🟠 Pre-publish.

## Report Row Grain

The normal `dotlineform/projects` list remains one row per working document A. With no B row it shows **Working**. With lineage, it shows one exact cue per B: **🟠 Pre-publish** when B exists locally without a current public projection, and **🟢 Published** when B has an exact current public projection. Mixed stages remain separate; focused detail exposes each B identity and Manage link. Unavailable is exceptional presentation, not a fourth lifecycle stage.

The normal `analysis/works` list remains one row per B. Its existing exclusion icon is renamed to mean `publishable: false` with the accessible label **Excluded from next Publish**; any later actual-publication cue is separate. Local scopes show no publication-exclusion icon. Project State subject-route icons and clipboard text remain unchanged.

Tracked sources also contain roughly 485 explicit-true declarations, five current public false records, and one local false fixture; configured external-local sources still require a read-only preflight. ## SSP-7.1b Proposed Footprint

The action batch should add `docs-viewer/services/docs_management_publishable.py` and `docs-viewer/runtime/js/management/docs-viewer-management-publishable-workflow.js`; extend `docs_management_routes.py`, `docs_management_service.py`, `docs-viewer-management-client.js`, `docs-viewer-action-definitions.js`, `docs-viewer-management-control-renderers.js`, `docs-viewer-management-index-controller.js`, `docs-viewer-management-document-reports.js`, `docs-viewer-management-subscope-default-contribution.js`, and `docs-viewer-management.js`; and complete removal of the legacy metadata input wiring from `docs-viewer-management-shell-renderer.js`, `docs-viewer-management-modals.js`, `docs-viewer-management-modal-composition.js`, and `docs-viewer-management-metadata-workflow.js`.

The endpoint accepts one exact publish-capable collection, non-empty exact `doc_ids`, and one boolean `publishable`; it validates every target before writing, maps true to omission, maps false to `publishable: false`, and uses the existing source-snapshot parent or sub-scope atomic write/rebuild boundary once. It does not loop over `/docs/update-metadata`, publish, alter descendants' fields, or add another front-matter key. The action batch remains roughly 300–450 production lines plus 300–450 focused test and smoke lines.

## Risks, Evidence, And Stop Condition

SSP-7.1a evidence must cover complete legacy-name absence, tracked and external-local source migration, public parent/child false values, local false-value review, creation defaults, hidden descendants, search, Publish, import, returned packages, reports, configuration, runtime projections, old-package rejection, and durable-document agreement. SSP-7.1b evidence must cover public parent and sub-scope targets, one and many checked documents, mixed and already-matching values, full prevalidation, stale/unavailable targets, atomic failure recovery, one exact rebuild, retained exclusion icons, metadata-modal removal, local-scope omission, and unchanged scope Publish. Later stages require focused table, Copy/Replace, Publish, generation, report, unavailable-target, and public-isolation evidence at their own gates.

Stop before or during implementation if a local false value represents intentional discovery policy, the external-local source migration cannot be coordinated with the code cutover, an in-flight package cannot be regenerated, or the change appears to require a `viewable` alias, dual reader, inferred `discoverable` replacement, or mixed schema. The existing SSP-7 stops also remain: content comparison, diff, merge, synchronization, automatic New/Replace choice, title/subject/URL inference, one-to-one lineage, arbitrary overwrite, a generic provenance graph, a loose registry, a second Copy or Publish workflow, per-document Publish, selection fallback, public A identity, or changes to Project State or SSP-5 ownership.
