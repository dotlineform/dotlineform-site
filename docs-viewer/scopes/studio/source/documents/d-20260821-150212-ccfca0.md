# iPad Docs Viewer — Installation Proof Results

**Test date:** 20 August 2026  
**Source procedure:** `d-20260808-205416-9f6d6c` — *iPad Docs Viewer Installation And Proof*  
**Target:** iPad + iSH + Safari, using the dotlineform repository and iCloud-backed external workspaces.

## Overall result so far

The core iPad working slice is viable, with important platform constraints and a few installation/runtime deviations from the original procedure.

Confirmed working:

- iSH can mount the real iCloud `dotlineform` projects base and access its expected children.
- The mount point can be named `/mnt/dotlineform`, matching the real folder name.
- The iOS-backed mount persisted across iSH relaunches during this test.
- Git can clone the repository into iSH local storage and create the disposable `ipad-proof` branch.
- A Python virtual environment can be created and the required Docs Viewer Python imports can be installed under the stock iSH Alpine environment.
- Docs Viewer starts successfully and `/health` reports management, generated reads, and review enabled.
- The full Docs Viewer Manage UI loads in Safari.
- Repository-backed documents load.
- A configured `local_external` scope loads from the mounted iCloud workspace.
- The Edit Metadata modal opens.
- A metadata change (`ui_status`) was successfully saved, although with noticeable latency.
- Safari and iSH can be used side-by-side; with iSH kept visible, Docs Viewer continues responding without repeated restarts.

Important constraints:

- Stock iSH currently uses Alpine 3.14.3, not Alpine 3.23.
- Stock Alpine 3.14 provides Python 3.9.16, not Python 3.12.
- `py3-markdown-it-py` is not available from the pinned Alpine 3.14 repositories.
- `bleach==6.3.0` is not compatible with Python 3.9, so the proof used `bleach==6.2.0`.
- `.env.local` is not applied early enough for external workspace resolution during service imports; the file must currently be exported into the shell before starting Docs Viewer.
- iSH must remain visible/active while Safari is making localhost requests. Full-screen Safari commonly leaves new Docs Viewer requests stalled until iSH becomes visible again.
- In one observed longer/deeper background interval, the Python process survived but the HTTP listener on port 8776 was lost. That instance required a service restart.

## 2. External projects mount

The real iCloud projects base is named `dotlineform`, so the Linux-side mount was changed from the document's proposed `/mnt/dlf-projects` to:

```sh
mkdir -p /mnt/dotlineform
mount -t ios . /mnt/dotlineform
```

The folder picker was used to select the real iCloud `dotlineform` folder.

Expected/confirmed shape:

```text
/mnt/dotlineform/
├── docs-viewer/
├── data-sharing/
└── projects/
```

Verification:

```sh
test -d /mnt/dotlineform/docs-viewer
test -d /mnt/dotlineform/data-sharing
test -d /mnt/dotlineform/projects
find /mnt/dotlineform -maxdepth 1 -type d -print
```

During this test, the mount persisted across iSH relaunches and did not need to be manually recreated.

If it is ever absent after a restart, remount with:

```sh
mount -t ios . /mnt/dotlineform
```

and select the same iCloud folder.

### Current startup-order issue

Starting Docs Viewer directly initially failed with:

```text
ValueError: DOTLINEFORM_PROJECTS_BASE_DIR is required for external local Docs Viewer scopes
```

The file existed, but the external workspace resolver was being imported before `.env.local` had been applied to `os.environ`.

Current proof workaround:

```sh
cd /root/src/dotlineform-site

set -a
. ./.env.local
set +a
```

Confirm:

```sh
printf '%s
' "$DOTLINEFORM_PROJECTS_BASE_DIR"
```

Expected:

```text
/mnt/dotlineform
```

This should be treated as a candidate repository fix rather than a permanent manual requirement.

## 10. iSH focus and cursor behaviour

A hollow iSH caret by itself is not evidence that the shell has frozen.

Observed behaviour:

- when iSH is visible but does not have keyboard focus, the caret becomes hollow;
- when iSH regains focus, the caret normally becomes solid again;
- while this normal focus transition occurs, no restart is needed.

Treat the state as a real failure only if iSH regains focus but keyboard interaction still does not recover.

## 11. Safari full-screen versus iSH-visible operation

This was the most important platform finding.

### Working mode

With Safari and iSH visible side-by-side:

```text
iSH visible
→ Python service continues running
→ Safari localhost requests complete
→ document navigation and managed actions work
```

### Full-screen Safari

When Safari becomes full screen and iSH is no longer visible:

```text
Safari full screen
→ iSH is suspended or heavily deprioritised
→ existing Safari content remains visible
→ new localhost requests may stall
→ making iSH visible again allows requests to continue
```

This means the practical working mode is currently:

```text
Safari + iSH side-by-side
```

rather than relying on a hidden/background iSH process.

A useful working rhythm is:

1. keep Safari and iSH windowed while navigating/editing;
2. make Safari full screen only after the required document has already loaded;
3. restore the split/windowed layout before requesting a different document or performing a managed action.

## 12. Lost-listener failure

One deeper lifecycle failure was captured in detail.

Safari `/health` stopped responding.

From a second iSH window:

```sh
wget -qO- http://127.0.0.1:8776/health
```

returned:

```text
Connection refused
```

But:

```sh
ps | grep '[d]ocs_viewer_service.py'
```

still showed the Python service process.

Process state:

```text
42 RW   python3 docs-viewer/services/docs_viewer_service.py
```

`netstat` was not useful under iSH because `/proc/net/tcp` and `/proc/net/tcp6` were unavailable.

`/proc/42/fd` showed:

```text
0 -> /dev/pts/0
1 -> /dev/pts/0
2 -> /dev/pts/0
3 -> anon_inode:[unknown]
```

The decisive test was whether another process could bind port 8776:

```sh
python3 -c "import socket; s=socket.socket(); s.bind(('127.0.0.1',8776)); print('port 8776 is free'); s.close()"
```

Result:

```text
port 8776 is free
```

Therefore:

- the original Python process still existed;
- it was no longer listening on port 8776;
- the HTTP listener had been released/lost;
- merely bringing iSH back into focus could not recover that instance;
- the Docs Viewer service had to be restarted.

This is distinct from the ordinary short background-suspension behaviour, where requests merely wait and then continue when iSH becomes visible again.

## 13. BrokenPipeError

One server-side message was observed:

```text
BrokenPipeError: [Errno 32] Broken pipe
```

This occurred while Safari was making/cancelling localhost requests.

The Docs Viewer continued working afterwards.

For the proof, this should be recorded but not treated as a failure unless it correlates with missing or failed user-visible operations.

## 14. Search and Recent observations

At one point Search and Recent immediately displayed:

```text
Load failed
```

At the same time `/health` was no longer responding and the service listener was later confirmed lost.

Therefore that specific failure was not established as a Search/Recent implementation bug; it occurred while the localhost service itself was unavailable.

A separate UI issue was observed:

- the iPad Safari search field did not expose an obvious `×` clear button;
- the current UI relies on the browser-native behaviour of `input type="search"`.

An explicit application-level clear control may be preferable for iPad/mobile use.

## 15. Recovery commands

### A. Normal iSH reopen

If the mount has persisted:

```sh
. /root/venvs/dotlineform/bin/activate
cd /root/src/dotlineform-site

set -a
. ./.env.local
set +a
```

Then start Docs Viewer:

```sh
python3 docs-viewer/services/docs_viewer_service.py
```

### B. Check whether the iCloud mount is still available

```sh
test -d /mnt/dotlineform/docs-viewer
```

If that succeeds, no remount is required.

If it fails:

```sh
mount -t ios . /mnt/dotlineform
```

and select the real iCloud `dotlineform` folder again.

### C. Check whether Docs Viewer is responding

From a second iSH window:

```sh
wget -qO- http://127.0.0.1:8776/health
```

Expected: JSON with `"ok": true`.

### D. Check whether the service process still exists

```sh
ps | grep '[d]ocs_viewer_service.py'
```

### E. Distinguish "temporarily suspended" from "listener lost"

First make iSH visible again and retry:

```sh
wget -qO- http://127.0.0.1:8776/health
```

If it responds after iSH becomes active, the service was only suspended/deprioritised.

If it still returns `Connection refused`, check whether port 8776 is free:

```sh
python3 -c "import socket; s=socket.socket(); s.bind(('127.0.0.1',8776)); print('port 8776 is free'); s.close()"
```

If the command prints:

```text
port 8776 is free
```

while `ps` still shows `docs_viewer_service.py`, the server process is stale and has lost its listener.

### F. Restart a stale Docs Viewer process

Find the PID:

```sh
ps | grep '[d]ocs_viewer_service.py'
```

Kill it:

```sh
kill <PID>
```

Confirm it has gone:

```sh
ps | grep '[d]ocs_viewer_service.py'
```

Then restart:

```sh
. /root/venvs/dotlineform/bin/activate
cd /root/src/dotlineform-site

set -a
. ./.env.local
set +a

python3 docs-viewer/services/docs_viewer_service.py
```

Test from the second iSH window:

```sh
wget -qO- http://127.0.0.1:8776/health
```

## 16. Practical operating procedure

For the current proof environment:

```text
1. Open iSH.
2. Confirm /mnt/dotlineform is still available.
3. Activate the dotlineform virtualenv.
4. cd to /root/src/dotlineform-site.
5. Export .env.local into the shell.
6. Start docs_viewer_service.py.
7. Open Safari beside iSH rather than hiding iSH.
8. Use http://127.0.0.1:8776/docs/.
9. If a request stalls, make sure iSH is visible.
10. If requests return connection refused, check /health and the service process.
11. If the process exists but port 8776 is free, kill and restart the service.
```

## 17. Candidate follow-up changes

The proof has identified several bounded improvements worth considering after the test is complete:

1. **Early `.env.local` application**
   - Ensure `DOTLINEFORM_PROJECTS_BASE_DIR` is available before modules resolve external workspaces.

2. **Explicit iPad dependency profile**
   - Document/test the stock iSH Alpine 3.14 / Python 3.9 path, or deliberately adopt a newer supported iSH filesystem if required.
   - Current tested divergence:
     - `bleach==6.2.0`
     - `markdown-it-py==3.0.0` via pip
     - native lxml/Pillow from Alpine.

3. **iPad launcher/helper**
   - Reduce the repeated activation, directory, environment-export, and service-start commands once the proof stabilises.

4. **Mobile search clear control**
   - Add an explicit clear button instead of relying solely on Safari's native `type="search"` affordance.

5. **Responsive CSS fixes**
   - Address the already-visible narrow-window layout issues in the Docs Viewer management UI.

6. **Lifecycle documentation**
   - State clearly that iSH must remain visible/active for reliable localhost service operation on iPad.
   - Document the difference between recoverable suspension and the observed lost-listener state.

## Current assessment

The central feasibility claim has been demonstrated: Docs Viewer can run locally on the iPad through iSH, access repository-backed and iCloud-backed documents, and perform at least one real managed metadata write.

The principal constraint is not basic Python/Git/File Provider compatibility. It is iPadOS lifecycle behaviour around a localhost server hosted by iSH.

At present, the most reliable working mode is to keep iSH visible alongside Safari. Short suspension appears recoverable; a deeper suspension can leave the Python process alive without its HTTP listener, in which case the service must be restarted.
