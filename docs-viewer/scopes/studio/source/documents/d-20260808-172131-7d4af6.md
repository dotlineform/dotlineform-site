# DPD-1.0 — Delete And Public-Projection Ownership Sanity Note

## Outcome

DPD-1 fits the current management, publication, document-location, and Catalogue owners without another Delete or Publish workflow. The bounded implementation target is one exact public-cleanup plan shared by ordinary parent and child document Delete, plus focused follow-through inside the existing scope and sub-scope lifecycle owners where those broader operations remove public roots or a report host.

The configured snapshot has three public parent scopes (`library`, `analysis`, and `moments`), two public child collections (`analysis/tags` and `analysis/works`), and no public projection for `studio`, `processing`, `notes`, `dotlineform`, or `dotlineform/projects`. Public capability comes only from resolved configuration. Current public-file presence, not `publishable`, lineage, title, route text, or source existence, proves that a deletion target has an exact public projection.

DPD-1.0 is complete as a documentation-only gate. No runtime, source, generated public, browser, lineage, or Catalogue behavior changes here. DPD-1.1 requires explicit implementation approval.

## Exact Public Product Map

The cleanup baseline is the current public snapshot, not the newer working projection. Targeted cleanup removes or rewrites only products that currently contain the exact deletion identities, so pending edits, newly publishable documents, unrelated exclusions, and unrelated Mermaid or media products cannot be promoted.

| deletion target | exact removals | exact inventory follow-through | deliberately retained |
| --- | --- | --- | --- |
| One public parent document | Its public `by-id/<doc_id>.json` and any public Mermaid variant pair owned by that document | Filter the exact identity from public tree, Recent, search, and document locations; refresh affected Work/Series `doc_url[]` payloads | Unrelated public documents, child collections, and shared media |
| A parent plus owned descendants | The same by-ID and owned Mermaid products for the effective descendant-expanded set | Rebuild the same parent inventories once from the current public snapshot minus the complete exact set; refresh Catalogue once | Documents outside the existing hierarchy-owned deletion set |
| One public sub-scope document | Its child `by-id/<doc_id>.json` and any Mermaid pair owned by that child | Filter the child manifest, derived document location, and affected Catalogue URLs | Report host, sibling child files, parent tree/Recent/search, collection configuration, and shared media |
| One published report host | The host's parent by-ID and owned Mermaid products | Filter the host from parent tree, Recent, search, and document locations. Removing the host location also removes every child URL derived through that host and refreshes the corresponding Catalogue URLs | Surviving child manifest, child by-ID files, child Mermaid products, child source, and collection configuration |

The report-host result is explicit: child public files remain independently owned projections while their canonical child sources survive. Reachability is host-derived, so deleting the host removes child document-location and Catalogue URL records, but route shape does not authorize a cascade into child files. The checked current Analysis example confirms the distinction: public host `d-20260807-082735-54d9d5` supplies the route for child `d-20260807-094819-5712bd`, while the child has its own manifest/by-ID projection and Series `001` currently carries the derived URL.

Document-location and Catalogue planning must retain exact internal `{scope, sub_scope, doc_id}` identities. Catalogue refresh is a required Delete invariant, not the current Publish path's non-fatal stale follow-through. A Delete response is not successful while any affected Catalogue payload still carries a removed URL.

## Publish Cutover

The current `docs_publish_gate.py` computes `removed` by comparing every file below a public root with the complete desired working projection. `docs_diff`, parent `docs.removed`, each sub-scope `removed` and `removed_count`, aggregate `removed_count`, `summary_text` with `stale`, `copy_tree` unlinking, and the browser's **Stale files to remove** line therefore combine explicit publishability exclusions, source-deleted projections, and unrelated extra files.

DPD-1.1 performs one clean response/schema cutover rather than retaining ambiguous aliases:

- replace `removed` and `removed_count` with `excluded` and `excluded_count` in the Publish plan and response;
- report summaries as changed and excluded, and label the browser count **Files removed by current Publish exclusions**;
- derive every exclusion only from a surviving canonical document's explicit `publishable: false`, including the established parent-descendant rule and route/location consequences of an explicitly false public report host;
- unlink only exact paths owned by those current exclusions; and
- ignore and retain public files that are absent from source for any other reason, including unsupported out-of-workflow filesystem deletion, without reporting them as Publish work.

Search, tree, Recent, document-location, and Catalogue bytes changed by a current exclusion remain ordinary changed products. `excluded_count` counts exact public files removed by the explicit gate. Publish retains positive promotion and unchanged-copy ownership; it gains no filesystem repair or Delete follow-through.

## Delete Preview And Apply Contract

Delete preview retains its existing target and warning fields and adds one `public_cleanup` object. For a public-capable exact target it reports the exact projected `doc_id` subset, public paths to remove, inventory paths whose bytes would change, affected Catalogue targets, and the report-host child-route consequences. For a local or local-external target it reports `applicable: false` with no public paths. Preview derives this evidence from resolved configuration and actual public products and remains write-free.

Apply re-runs ordinary target, hierarchy, revision, and public-product planning. The frozen order is:

1. validate the exact request and current public cleanup plan;
2. run the existing canonical source deletion and exact working Docs/search or child rebuild boundary;
3. remove the planned exact public by-ID/Mermaid files and rewrite only affected public inventories from the pre-delete public baseline;
4. refresh exact Catalogue `doc_url[]` targets from the resulting public locations; and
5. return success with the applied `public_cleanup` result, then let the existing browser refresh owner reconcile its current surface.

This sequence never calls scope-wide Publish and never copies working payloads into public output. Parent Delete keeps its current committed-source failure behavior. Sub-scope Delete keeps its existing source restoration only when the source/working rebuild stage fails; DPD adds no cross-product rollback. A later public-cleanup or Catalogue failure returns a non-success result with `committed: true`, the failed stage, and exact remaining impact. It must not claim retry safety or a successful immediate cleanup. Focused fault evidence is required before closeout because this deliberately preserves the no-new-rollback boundary.

## Expected Implementation Footprint And Risks

The direct server owners are `docs_management_mutations.py`, `docs_management_mutation_service.py`, `docs_publish_gate.py`, `docs_document_location_projection.py`, `docs_catalogue_document_urls.py`, the existing Catalogue URL refresh owner, and the two lifecycle services. Browser follow-through belongs to the existing parent Delete modal, sub-scope Delete workflow, and Publish confirmation copy. Focused tests belong with management mutation/service, sub-scope Delete, scope/sub-scope lifecycle, Publish gate, document locations, Catalogue URLs, and the existing management module smokes.

The main implementation risk is accidentally rebuilding public output from newer working bytes. The second is treating a report route as ownership of child source or files. The third is returning success after non-fatal Catalogue follow-through. Tests must falsify all three, alongside public/local capability isolation, existing revision and descendant rules, already-absent projections, exact Mermaid ownership, next-Publish idempotence, and out-of-workflow stale-file retention.

No additional Delete control, per-document Publish/Unpublish, public-file browser, scope-wide scan, shared-media cleanup, lineage condition, generic projection-deletion engine, compatibility response alias, or rollback/retry framework is approved.
