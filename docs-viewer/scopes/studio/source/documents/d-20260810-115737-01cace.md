# WRK-1 — Published Series Documentation Coverage Report Delivery

## Status

Proposed and not started. This delivery defines one complete local report and does not authorize runtime implementation. Begin with WRK-1.0, record the exact implementation shape and focused evidence plan, then stop for approval.

## Complete Result

An ordinary local report-host document titled **Works** in scope `dotlineform` renders one **Series | Docs** row for every exact Series classified as published in canonical source and carried by the Studio Series search projection. Series titles link to the exact Series page on the configured local site preview. Docs link to exact `dotlineform/projects` documents and retain the shared Series or Work subject cue.

For a published Series, Docs is the deduplicated union of exact valid Series-subject documents for that `series_id` and exact valid Work-subject documents for published Works whose current canonical `series_ids` includes that Series. Any one document makes the Series written about; draft Works contribute no coverage, and other undocumented member Work IDs do not create gaps. Rows with no document remain present with a blank Docs cell.

## Why This Matters Now

Project State, Projects, and Works become three deliberately different views over the folders-Series-documents relationship:

- Project State begins with physical folders;
- Projects begins with Project documents; and
- Works begins with published Series.

The third view exposes Series with no written coverage without widening Project State, restoring a Studio reporting obligation, or displaying private Projects associations on the public site.

Project State currently retains canonical Work/Series relationships without a publication-status filter. WRK-1 does not alter that existing contract. Restricting the folder-first report to published Series would be a separate Project State refinement.

## Delivery Boundary

WRK-1 includes:

- browser reads of the existing Studio Series and Work search projections through the current Local Studio Catalogue read boundary;
- a browser read of the current private Projects Manage manifest, with no second subject-association input;
- exact published-Series and published-Work filtering plus exact current `series_ids` membership;
- one local registry/loader/browser-module path and one ordinary external-local report host;
- frontend-only filtering, joining, de-duplication, ordering, and table composition;
- a two-column Series/Docs table with exact local-preview and Projects links;
- shared Series/Work subject cues, deterministic ordering, empty rows, automatic mount, full-input refresh, and contained current-mount failure;
- focused input-contract, registry/loader, module, external-host, and local/public-isolation evidence; and
- transfer of shipped behavior to the durable coverage and reporting owners.

WRK-1 excludes:

- Work-grained rows, per-Work gap reporting, completeness scores, or a requirement that every member Work be documented;
- Folder subjects, semantic-token mentions, content comparison, title/filename inference, or unknown-target fallback;
- `analysis/works`, editorial/public lineage, `publishable`, public `doc_url[]`, or public Work/Series page presentation;
- public Catalogue JSON as a report input or publication authority, and Catalogue projection-integrity auditing;
- a Works producer, persisted/versioned report response, Docs Viewer report-service method, or management route;
- Project State response or presentation changes;
- search, grouping, filters, clipboard/export, persisted results, saved report Markdown, watching, or mutation hooks;
- a generic report engine, relationship database, compatibility alias, dual reader, or new canonical store; and
- report-driven subject, Catalogue, Copy, Publish, or Delete mutations.

## Likely Owners To Inspect

The sanity gate should inspect and narrow these current owners:

- `studio/services/catalogue/catalogue_lookup.py` for the existing Series/Work search projection shapes and `studio/app/server/studio/studio_catalogue_api.py` only to confirm the existing read keys and loopback-origin transport; neither is expected to change;
- the private Projects Manage manifest and `docs-viewer/runtime/js/management/docs-viewer-management-subscope-dotlineform-projects.js` for its normalized `authoring_subject`, existing Catalogue-title read pattern, preview URL composition, and shared subject cues;
- `docs-viewer/config/reports/reports.json` and `docs-viewer/runtime/js/reports/docs-viewer-reports.js` for local report registration and explicit browser loading;
- one new focused browser report module using the existing shared report table/link styles and `project-subject-icons` vocabulary; and
- the Projects sub-scope and focused report-module smokes as browser-composition references, not as an invitation to create a generic report abstraction.

The expected implementation is roughly 250–350 production lines plus 250–400 focused test/smoke lines, one external report-host source, and small explicit registry/loader wiring. No Python report production or Docs Viewer route work is expected. WRK-1.0 must restate the final file list and estimate. Stop for review if the current Studio lookup reads or Projects manifest cannot supply the frozen inputs, or if the result needs new server transport, a general subject query service, shared mode-driven report framework, persisted coverage product, Project State refactor, public payload consumer, or materially larger footprint.

## Completion Gate

WRK-1 is complete only when every Studio lookup Series with exact published status appears once; a Series Project document or published-Work Project document reaches exactly the published Series rows defined by its declared subject and current membership; one matching document is sufficient coverage; blank rows remain visible; Series and document targets are exact; the report is browser-composed, read-only, local-only, and independently reachable; and focused evidence protects the input contracts, wiring, presentation, external host, and public/server isolation.
