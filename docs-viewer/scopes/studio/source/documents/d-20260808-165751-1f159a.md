# DPD-1 — Immediate Public Projection Cleanup On Document Delete

[DPD-1.1 — Shared Server Cleanup Evidence](/docs/?scope=studio&doc=d-20260808-182844-3e9b7c) records the implemented exact cleanup path and Publish exclusion cutover. [DPD-1.2 — Browser And Refresh Follow-Through Evidence](/docs/?scope=studio&doc=d-20260808-184353-0f9c24) records the existing-browser completion. [DPD-1.3 — Verification And Contract Transfer Evidence](/docs/?scope=studio&doc=d-20260808-185725-9520b6) records the final verification matrix, durable transfer, generated projections, and closeout review. The prerequisite for [SSP-8 — Revised Model](/docs/?scope=studio&doc=d-20260808-153226-a067d9) is satisfied; SSP-8 has not started in this delivery.

The outcome is one shared document-Delete rule across configured parent scopes and sub-scopes: when confirmed Delete irreversibly removes a canonical document, the same successful action must also remove any exact current public projection of that document and update every affected public inventory. A later scope Publish must not be required to make the deleted document disappear publicly. Consequently, Publish no longer discovers, removes, or reports source-deleted documents.

## Product Rule

The distinction is whether canonical source still exists:

| action | public result |
| --- | --- |
| Edit document content | Current public projection remains until explicit scope Publish. |
| Set `publishable: false` | Current public projection remains until explicit scope Publish. |
| Delete canonical document | Any exact current public projection is removed immediately. |

Scope-wide **Publish** remains the only positive promotion action. **Delete** becomes an immediate negative cleanup owner because the deleted source can no longer be edited or republished. This is not a per-document Publish or Unpublish action.

The rule applies whether or not the document has a lineage record. A directly created document in a public parent scope or public sub-scope receives the same cleanup as a lineage-tracked Editorial document. Deleting a local `dotlineform/projects` Working document does not remove an Analysis document or its public projection; those remain backed by their own editable canonical source.

## Consequential Publish Simplification

After DPD-1 ships, Publish has no source-deletion reconciliation responsibility:

- a document absent because confirmed Delete removed its canonical source has already been removed from public output and every affected public inventory;
- Publish must not compare source and public inventories to discover deleted documents;
- Publish must not include source-deleted documents or paths in its preview, removal count, response, or completion summary;
- the only surviving canonical documents whose public projections Publish removes are those excluded by explicit `publishable: false`, including descendants or child routes excluded by an owning false parent/report host; and
- that negative result is an **exclusion from Publish**, not a delayed Delete.

Publish continues to promote new or changed publishable projections and to retain unchanged publishable projections. Its negative plan is derived from current canonical publishability gates, not from missing source. DPD-1.0 must inventory the current `removed`/stale response fields and browser copy, then either narrow them to publishability exclusions or replace them with explicit exclusion terminology without retaining a source-delete meaning.

An out-of-workflow filesystem deletion is not repaired by Publish. DPD-1 adds no filesystem reconciliation path; the supported immediate guarantee begins with confirmed Docs Viewer Delete.

## Current Owners And Entry Points

The delivery extends existing owners rather than adding a Delete workflow:

- parent Index selection Delete already previews and applies an exact set of requested documents plus owned descendants through `/docs/delete-preview` and `/docs/delete-apply`;
- default sub-scope detail Delete already carries exact `{scope, sub_scope, doc_id}` identity and a source-revision receipt through the same routes;
- the shared management mutation service already owns confirmed source deletion and the exact working Docs/search or sub-scope rebuild;
- configured scope and sub-scope public projections already identify their public roots and public-safe products;
- the existing Publish owner already knows how parent and sub-scope by-ID files, tree/Recent, manifests, search, document locations, and Catalogue document-URL follow-through compose into public output; and
- existing browser Delete buttons, confirmation workflows, target ownership, and refresh events remain the UI owners.

DPD-1.0 must separately inventory scope-lifecycle and sub-scope-lifecycle Delete controls. They are broader configuration/tree operations and are not silently treated as ordinary document Delete unless the checkpoint proves they share the same exact cleanup contract.

## Required Apply Result

Preview must determine from the exact configured target and current public products whether the effective deletion set has public projections. It may report those exact public impacts in the existing confirmation response; it must not infer publication from `publishable`, titles, routes, or lineage.

A successful apply must leave these invariants true before returning success:

- every deleted parent or child source is absent from its normal working projection;
- every exact current public by-ID projection of those deleted documents is absent;
- affected public parent tree, Recent, search, sub-scope manifest, document-location, and downstream Catalogue URL products no longer reference the deleted public document;
- unaffected public documents and inventories are byte-for-byte or semantically unchanged according to their existing producer contract;
- local and local-external scopes perform no public cleanup; and
- the next ordinary scope Publish sees no stale deleted projection and remains idempotent for this removal.

The implementation must reuse exact configured builders and public-product owners. It must not run a scope-wide Publish, copy unrelated pending edits, promote newly publishable documents, or infer and delete shared media merely because one document referenced it.

## Hierarchy And Host Review

Parent Delete may already expand to owned descendants. DPD-1.0 must map that effective deletion set to exact public parent projections before mutation.

Sub-scope public routes depend on an ordinary public report host. The checkpoint must decide the exact result when deleting a published report host: whether its public child inventory remains a valid independently owned projection or must be removed as an impacted route dependency. No cascade is assumed from route shape alone.

Deleting one sub-scope document removes only that child and its exact manifest/location/search consequences. It must not delete its report host, sibling children, collection configuration, or shared public media.
