# Scope, Data, And Site Foundations

## Purpose

Make code, private document data, consumer-ready published data, and the deployed public site separate ownership layers. These changes are useful repository foundations in their own right and are delivered through the Studio Roadmap even though they also prepare for the Swift application described in [App Architecture And Migration Approach](/docs/?scope=app&doc=d-20260829-212459-c17eb8).

The target repository contains code and the exact tracked `site/` deployment snapshot. `site/` directly owns public-only static website artifacts and contains deployed projections of shared runtime and public document data. It is not the authority for shared runtime code or for scope source, generated output, or published output.

## Stage 1 — Runtime Ownership And Site Projection

Move canonical public/shared Docs Viewer runtime code outside `site/`. Add one deterministic internal development projection that copies the deployable runtime code assets into tracked `site/` whenever the runtime changes. Canonical and projected changes are reviewed and committed together, while local Docs Viewer routes read canonical runtime directly.

This is a code-development process, not a Docs Viewer user action. It does not introduce Update Site, Publish, or Deploy controls and does not move document data. The GitHub Pages workflow remains a validator and deployer of the tracked `site/` snapshot; it does not generate or commit runtime changes.

This stage is first because it removes the immediate code/deployment ambiguity without anticipating the final scope model. It also creates a clean runtime source for later WebKit and Swift work.

- [Docs Viewer Runtime Ownership And Site Projection Delivery](/docs/?scope=studio&doc=d-20260830-074606-881007) is the completed first delivery.

## Stage 2 — External Scope Build And Publish Model

Give every in-scope Docs Viewer scope the same external, application-independent storage model. Storage provider and public exposure become separate configuration concerns rather than different scope types.

Each scope owns:

- canonical Markdown and source media;
- replaceable generated document, search, and media output created by Build; and
- an accepted, consumer-ready published snapshot promoted through Publish.

Manage mode can read generated output for working review and published output for accepted-output review. Swift and other application consumers read published output directly without requiring `site/`. Published payloads therefore remain consumer-neutral and do not encode GitHub Pages or dotlineform.com as their owner.

Publish owns document eligibility. A document with `publishable: false` remains available in generated working output but does not enter the published snapshot and therefore cannot be deployed. Every consumer of published output sees the same accepted document set.

Analysis is the only scope eligible for document deployment into the public site. Studio and the other private scopes use the same Build and Publish lifecycle without becoming publicly deployable. Before repository-backed canonical Markdown leaves Git, this stage must establish the minimum recoverable snapshot boundary. The `processing/` Java/Processing code project remains separate and this feature does not define its development lifecycle. The `processing` Docs Viewer scope participates in the same external storage, Build, and Publish migration as the other Docs Viewer scopes.

- [External Scope Build And Publish Delivery](/docs/?scope=studio&doc=d-20260830-151155-8eadce) is the planned Stage 2 delivery.

## Stage 3 — Document Deployment And Pages Release

Introduce two separate deployment operations for document content, with an explicit ordinary Git boundary between them:

- **Deploy Repo** copies the complete accepted published Analysis output into tracked `site/` without applying another document-eligibility rule. The resulting repository projection can be reviewed immediately through the local site preview server.
- **Commit and push** remains an explicit manual Git action outside the document lifecycle. Deploy Repo does not perform it implicitly.
- **Deploy Public** validates and deploys the committed and pushed `site/` snapshot to GitHub Pages through the existing manually triggered workflow.

Deploy Repo does not rebuild or publish a scope, commit or push changes, or deploy GitHub Pages. Deploy Public does not read external scopes, rebuild content, publish content, alter `site/`, or commit changes; it deploys only the committed snapshot it receives. These remain independent manual operations. A future application may gain explicit repository, commit, push, and GitHub Action capabilities without collapsing their boundaries or making them automatic.

The current local workflow will normally compose Publish and Deploy Repo in one capability-based Publish modal, with both selected by default. Publish remains usable without Deploy Repo where repository capability is unavailable. [Publish And Deploy Model](/docs/?scope=studio&doc=d-20260830-092438-f0c9d2) defines the detailed current behaviour, target ownership, modal composition, capability progression, and partial-failure handling.

Public-only static HTML, CSS, JavaScript, images, and other website artifacts remain maintained directly in `site/`. They are not duplicated into another source tree merely so a build can copy them back. No canonical scope source, replaceable generated output, non-Analysis scope data, or private configuration is deployed.

## Lifecycle Vocabulary And Order

The user-facing document lifecycle is:

1. **Build:** canonical source to replaceable generated output for working review in Manage mode.
2. **Publish:** generated output to the accepted, consumer-ready scope-local published snapshot for published review and direct application consumption.
3. **Deploy Repo:** accepted published Analysis output to the tracked `site/` document projection for local public-site preview.
4. **Deploy Public:** the validated committed and pushed `site/` snapshot to GitHub Pages.

The explicit Git commit and push occurs between Deploy Repo and Deploy Public but is not itself a Docs Viewer document-lifecycle operation.

Runtime projection is deliberately outside that lifecycle:

```text
runtime code change
  -> internal runtime projection
  -> tracked site runtime

scope source
  -> Build
  -> generated
  -> Publish
  -> published -----> Swift or another direct consumer
  -> Deploy Repo
  -> tracked site document projection
  -> explicit Git commit and push
  -> committed repository snapshot
  -> Deploy Public
  -> dotlineform.com
```

Stage 1 establishes runtime ownership. Stage 2 establishes consumer-ready scope output. Stage 3 deploys only accepted Analysis output and keeps local preview separate from public release.

The feature does not itself implement the Swift application, migrate Catalogue data, introduce document version history beyond the required recovery boundary, or absorb the `processing/` code project into the website lifecycle.
