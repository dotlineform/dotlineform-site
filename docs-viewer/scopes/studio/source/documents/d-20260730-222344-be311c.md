# Consolidated App-Level Docs Import Delivery

## Status And Purpose

Started as CAI-1 under
[Roadmap](/docs/?scope=studio&doc=d-20260428-000000-f5ff18).
CAI-1.2 is complete and at its review gate. CAI-1.3 remains unstarted.

CAI-1 replaces separate parent-scope Import, sub-scope report Import, and
**Review package** entrypoints with one manage-only app-level **Import** action.
The chooser lists every recognized staged document candidate without filtering
the list by the currently displayed scope or sub-scope.

The selected source kind decides how its destination is resolved:

- an ordinary standalone document imports into the frozen current display
  context; and
- a trusted package or edited review-source folder imports into the exact
  collection declared by its associated trusted manifest and metadata.

[Prepare Package](/docs/?scope=studio&doc=d-20260722-151224-7b61c4)
remains a separate checked-document action. Docs Review remains optional.

## Complete Outcome

One app-level **Import** action opens a shared staged-source modal from any
local Manage Docs Viewer state.

The modal:

1. lists every recognized ordinary document, returned package, and edited
   review-source folder in Import staging;
2. does not filter that inventory by the displayed context;
3. has no **Import** type or **Publish into** dropdown;
4. shows each source kind and its read-only effective destination;
5. offers **Open in Docs Review** only for a server-declared reviewable returned
   package;
6. previews and confirms Import through the existing ordinary or collection
   workflow; and
7. ends with an explicit link to the exact destination affected by the result.

The selected candidate already determines the Import workflow. Its destination
is either the frozen display context for an ordinary document or the trusted
manifest target for a package, so neither value is user-selectable.

Standalone image, SVG, Mermaid, downloadable, and other media files are ignored
by Import. They remain owned by the Source editor's **Add image…** and
**Add file…** workflows.

## Candidate Model

“Package” means a staged source with an associated trusted manifest or metadata
record linked through `export_id` and the existing package provenance contract.
Filename shape, extension, directory shape, or the mere presence of an
unvalidated `manifest.json` does not grant package behavior.

| candidate kind | destination authority | Import | Open in Docs Review |
| --- | --- | --- | --- |
| ordinary DOCX, HTML, Markdown, text, or one-document Markdown folder | frozen current display context | create-only | disabled |
| trusted returned JSON/JSONL package | associated trusted manifest and metadata | according to `supports_return_import` | according to `supports_docs_review` |
| complete edited review-source folder | retained review manifest and trusted export metadata | overwrite-only | disabled |
| invalid, incomplete, unsupported, or capability-blocked candidate | none | disabled with reason | disabled |

The server projects candidate kind, validation state, capabilities, target
mode, exact target, display label, and disabled reason. The browser does not
infer them from filenames or reconstruct manifest associations.

The capability rule remains fail closed:

- `supports_docs_review: true` enables **Open in Docs Review** for a valid
  returned package;
- `supports_return_import: true` enables Import for a valid package and exact
  eligible collection;
- `false` / `true` remains invalid; and
- a complete edited review-source folder is already the output of the review
  workflow, so it never receives another Review action.

An ordinary one-document Markdown folder remains an ordinary create-only
source. Being folder-shaped does not make it a trusted package.

## Package Naming

Newly prepared document package names do not repeat the document domain:

- a package file uses `{timestamp}-{profile_id}.{format}`, for example
  `20260730-095512-document-content.jsonl`; and
- its retained review package id and folder use `{timestamp}-{profile_id}`, for
  example `20260730-095512-document-content`.

The profile ids remain `document-content` and `document-tree`. Trusted metadata
still carries `adapter_id: documents`, `data_domain: documents`, `profile_id`,
and `export_id`; removing the redundant physical-name segment does not change
trusted export identity, validation, capability, or routing authority.

This is a forward-only naming change. CAI-1 does not migrate, alias, or preserve
compatibility for files or review folders already staged under
`{timestamp}-documents-{profile_id}`; they may be cleared and regenerated.

## Listing Contract

The app-level listing is context-independent:

- every recognized document candidate appears from parent-scope, sub-scope
  report, and sub-scope detail states;
- package rows retain their manifest-owned destination even when another
  collection is displayed;
- ordinary rows show the frozen current-context destination supplied for
  this modal session;
- invalid claimed packages remain visible but disabled when the service can
  provide a safe diagnostic;
- standalone media and unrelated drop-zone files are omitted; and
- recognition still runs before generic Markdown normalization so `review_*`
  and package provenance cannot be stripped before classification.

Removing list filtering does not weaken source validation or expose arbitrary
filesystem paths. Candidates remain confined to the configured shared staging
root and retain their exact staged request identities.

## Ordinary Document Context

Opening Import freezes one explicit validated ordinary destination:

- `{ scope }` when the main scope is displayed; or
- `{ scope, sub_scope }` when a configured sub-scope report or one of its
  validated detail documents is displayed.

That target is supplied by the app/report context owner. It is not inferred
from the selected tree parent, checked IDs, title, staged filename, URL text,
most recently used destination, or a package row.

The frozen target applies only to ordinary standalone documents. It is retained
through preview, create, failure, retry, rebuild, and result presentation.
Invalid or unavailable display context disables ordinary Import rather than
falling back to the parent scope. There is no destination selector that can
replace this target.

## Manifest-Owned Package Routing

A trusted returned package or edited review-source folder ignores the display
context for destination routing. Its associated manifest and trusted metadata
must resolve one exact configured `{ scope }` or `{ scope, sub_scope }`
collection before preview.

The modal displays that destination prominently, including when it differs from
the current screen. Confirmation states the target and planned create or
overwrite count. Missing, stale, ambiguous, unconfigured, capability-invalid,
or cross-collection provenance blocks Import without a context fallback.

Existing semantics remain unchanged after routing:

- returned JSON/JSONL packages retain complete package planning and their
  current create/overwrite and failure policy;
- edited review-source folders remain complete, overwrite-only, stale-checked,
  and atomic; and
- ordinary sources remain create-only and never gain overwrite identity from
  front matter.

## Open In Docs Review

The selected-row secondary action is labelled **Open in Docs Review**.

It is enabled only when the server projects a valid returned package with
`supports_docs_review: true`. The action uses the selected exact staged package
identity to prepare or reuse its validated Docs Review package and opens the
returned review URL in a safe new tab.

The button is disabled for:

- ordinary sources;
- edited review-source folders;
- packages with `supports_docs_review: false`;
- invalid or unassociated manifests; and
- any candidate whose review identity cannot be resolved exactly.

The action does not select an Import target, confirm Import, or change the
candidate's manifest-owned destination. Returning from Docs Review leaves
Import optional.

## Result And Refresh Contract

Every successful result includes one explicit destination link:

- an ordinary create links to the exact new `{ scope, doc_id }` or
  `{ scope, sub_scope, doc_id }` document; and
- a collection Import links to its exact owning scope or sub-scope surface.

If the destination is currently mounted, the app refreshes that exact owner.
If the package imported into another collection, the current screen is not
treated as its refresh target; the result link provides the explicit
navigation handoff.

Result routing never falls back to the displayed document, selected parent,
current report, or package title. Failure retains the selected candidate and
its resolved target for a safe retry.

## Entry-Point Consolidation

After behavior parity is proven:

- retain one app-level **Import** action in local Manage Docs Viewer;
- remove the sub-scope report's separate Import contribution;
- remove the separate scope-level **Review package** action and chooser;
- keep **Prepare package** in its selection-backed Actions workflow;
- keep Docs Review free of Import or canonical-write controls; and
- keep all public Docs Viewer routes unchanged and read-only.

Old controls are removed only after the consolidated route proves ordinary
parent, ordinary child, returned-package, edited-folder, Review, refresh, focus,
retry, and result-link parity. There is no compatibility alias that leaves two
active UI owners.

## Likely Authority

- The manage app toolbar and lazy Import controller own the single entrypoint,
  modal lifecycle, frozen ordinary context, selected candidate, focus, busy,
  retry, and terminal result.
- The staged-source listing service owns the global recognized inventory and
  server-projected candidate kind, manifest association, capabilities, exact
  target, and disabled reason.
- The document-package profile config and review-source materializer own the
  shortened `{timestamp}-{profile_id}` file, package-id, and folder names while
  retaining the document-domain metadata.
- The existing managed collection resolver owns validated display-context
  targets for ordinary sources.
- Existing document-package and edited-review-source recognizers own trusted
  provenance, capability, membership, and manifest-routed targets.
- Existing ordinary and collection planners retain preview, confirmation, and
  mutation semantics.
- The existing Review package service owns prepare-or-reuse and returns the
  exact Docs Review URL.
- Existing scope/sub-scope refresh and document-location owners provide the
  explicit destination result link.

These are inspection starting points, not permission to add a second target
resolver or package registry.

## Boundary

In scope:

- one manage-only app-level Import entrypoint;
- one context-independent recognized staged-source inventory;
- removal of the Import-type and Publish-into dropdowns;
- explicit ordinary-context versus manifest-owned target modes;
- shortened document package file, package-id, and review-folder names;
- exclusion of standalone media and unrelated staged files;
- **Open in Docs Review** for reviewable returned packages only;
- unchanged ordinary, returned-package, and edited-folder mutation semantics;
- exact destination refresh and result links;
- retirement of duplicate Import and Review package entrypoints after parity;
- focused service, module, route, and realistic parent/Analysis-Tags evidence;
  and
- durable Docs Import, Docs Review, endpoint, architecture, ownership, and
  Sub-Scope Index updates at closeout.

Not in scope:

- merging or redesigning Prepare Package;
- reviewing a staged edited review-source folder;
- importing standalone media through Docs Import;
- changing package schemas, capability semantics, or manifest contents;
- migrating or retaining compatibility for already staged
  `{timestamp}-documents-{profile_id}` files and review folders;
- changing ordinary create-only or collection atomicity rules;
- adding public Import controls;
- importing arbitrary or unsupported staging files;
- automatic Import after Docs Review; or
- using display context to filter or reroute package candidates.
