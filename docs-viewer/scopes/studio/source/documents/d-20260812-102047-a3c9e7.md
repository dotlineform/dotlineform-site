# Media Sources

## Purpose

Help authors retain an identifiable original for manually added Docs Viewer media before a copy or derived artifact is published. A published repository, external-local, or R2 object is a delivery artifact, not an automatic backup of its source.

The current **Add image** and **Add file** workflows select direct-child files from the shared import-staging drop-zone. They publish or derive the configured media artifact but do not establish a durable relationship back to an organised original. Authors can preserve originals separately, but Docs Viewer neither requires that step nor helps verify it later.

## Proposed Model

Each participating scope may configure one external-local **media source root**. More than one scope may deliberately share the same root. The source root is distinct from the scope's one published-media location defined by [Media Locations](/docs/?scope=studio&doc=d-20260812-095531-6fd2b1).

| role | responsibility |
| --- | --- |
| Media source | Retained original selected through a scope's configured source root. It remains unchanged after intake and is the material included in the author's real backup or sync policy. |
| Published media | Consumer-ready copy or derived artifact written to the scope's configured repository, external-local, or R2 published-media root. |
| Import staging | Shared transient drop-zone for document and package imports. A scope with a configured media source does not require authors to copy manually added media through it. |
| Backup | An external policy covering the media source root. Docs Viewer can expose source evidence but does not claim that local, repository, or R2 storage is itself a backup. |

The source-editor workflow becomes:

```text
save original in the configured media source root
    -> choose Add image or Add file
    -> select an eligible source from that root
    -> preview the published identity and any transformation
    -> retain the original and publish or verify the output
    -> insert the logical media reference
```

Ordinary authoring does not choose a published storage provider. The configured source root answers where the original is retained; Media Locations independently answers where consumer-ready media is published.

## Initial Scope Adoption

Analysis, Dotlineform, and Processing adopt the source workflow up front:

| scope | configured media source root | current published-media outcome | later location question |
| --- | --- | --- | --- |
| Analysis | `$DOTLINEFORM_PROJECTS_BASE_DIR/analysis/` | Continue the current configured repository locations for `img`, `svg`, and `html` and R2 location for `files`; Media Sources does not move providers. | Media Locations may later move the complete published root to one provider. |
| Dotlineform | `$DOTLINEFORM_PROJECTS_BASE_DIR/analysis/` | Continue to publish media inside the external-local Dotlineform scope. | Copy may later carry the document, referenced media, and any recorded source evidence into Analysis. |
| Processing | `$DOTLINEFORM_PROJECTS_BASE_DIR/processing/` | Continue to publish against the current local Processing scope contract. | Large generated images make R2 plausible, but whether they ultimately belong to Analysis or a separate public Processing scope is deliberately undecided. |

These roots sit alongside the Studio Catalogue Works source root at `$DOTLINEFORM_PROJECTS_BASE_DIR/projects/`. **Add image** and **Add file** use the active scope's configured media source root rather than require a duplicate in `data-sharing/import-staging`.

Sharing `analysis/` is intentional. An author may add an original to a working document in `dotlineform/projects` before editorial Copy, or add the same original directly to an Analysis document. Dotlineform is an optional working gate for Analysis, not a second originals store. The media-source folder name is explicit configuration and is not derived from `scope_id`, so this model creates no `$DOTLINEFORM_PROJECTS_BASE_DIR/dotlineform/` requirement and gives no folder-layout reason to rename the Dotlineform scope.

Authors may save media directly in the scope root or organise originals in any confined subfolder beneath it. Source subfolders do not become published subfolders: repository or R2 media keeps the existing flat per-type filename identity. This follows the Studio Catalogue Works separation between source organisation and delivery identity, keeps private organisation out of public URLs, and allows source files to be reorganised without rewriting document references. Duplicate basenames from different source folders remain one published-identity collision and must be shown by the existing preview/confirmation boundary.

Processing's source workflow does not decide its future public scope, route, or provider. The exact Processing source evidence remains useful whichever published-media ownership is deliberately adopted later. Its external media source root is for Docs Viewer media originals; it is not the Processing Java project, a generated-output directory, or a reason to apply website lifecycle assumptions to that project.

All three adoptions preserve current media handling:

- raster images and opaque files publish byte-identical copies;
- standalone SVG retains its original while publishing the sanitized SVG;
- Mermaid retains its existing explicit source-to-rendered-SVG contract;
- source files are not consumed, moved, renamed, rewritten, or automatically deleted; and
- changing or removing a source does not silently replace or delete the published artifact.

## Source Evidence

Publishing should save one small provider-neutral row for the published media identity. The first contract needs only the configured source-root identity and exact Projects-relative source path, such as `analysis/reference/portrait.jpg` or `processing/studies/study-01.png`. Absolute local paths do not belong in browser payloads or portable records.

When a Dotlineform document is copied into Analysis, Copy carries an exact source-evidence row for each transferred media identity when one exists. It does not search for, infer, or fabricate an original. Existing media and media introduced through workflows that have not recorded an original truthfully remain **no source recorded** until a later explicit association capability is designed.

This deliberately small evidence allows [Scope Media Management](/docs/?scope=studio&doc=d-20260720-100017-9855dd) to distinguish:

- source recorded and currently present;
- no source recorded;
- recorded source missing or its source root unavailable; and
- published artifact present or missing.

The first outcome does not hash originals, compare source and published bytes, track source changes, monitor folders, or continuously verify provenance. Those capabilities should be added only if the report demonstrates a practical need. These are inspection states, not automatic mutation authority.

## Folder Selection Direction

The two source-editor media modals replace their staged-file dropdowns with accessible, single-selection file lists. Each modal displays its current source folder and a **Choose folder…** button. Image and file actions filter the same folder through their existing supported-format rules.

**Choose folder…** hands off to the existing app-neutral folder-picker in a dedicated modal. Navigation is rooted at the active scope's configured `analysis/` or `processing/` directory: authors may choose that root or navigate through descendants, but neither the browser nor the service can move above it. Dotlineform and Analysis therefore open the same `analysis/` tree. Choosing a folder returns to the media modal, displays the selected Projects-relative folder, refreshes the eligible direct-child file list, clears any selection and derived label from the former folder, and focuses the refreshed list. Cancelling returns without changing the current folder or selection.

An empty initial or selected folder still opens the media modal and keeps **Choose folder…** available. Preview and apply submit the scope, selected Projects-relative directory, and filename; the server recomputes and confines the exact source beneath the configured root. A scope that has not adopted Media Sources retains its current import-staging workflow until it receives an explicit source-root configuration.

Folder selection reuses the existing Projects-relative confinement and app-neutral picker responsibilities rather than accepting arbitrary absolute paths or browser-submitted filesystem authority. The shared picker needs a lower-root option and the Docs Viewer service must enforce the same root; an initial breadcrumb or browser restriction alone is insufficient.

Remaining UI details include whether the current subfolder is remembered per source root between modal sessions, which minimal file metadata appears in list rows, and whether the media modal also needs an explicit refresh control for files added while it is open. These details should be settled by trying the workflow rather than freezing a larger browser contract in advance.

## Delivery Order And Stance

This feature comes first in the current media-workflow delivery sequence. The read-only Scope Media report follows it so the report can use real source evidence; a later [Media Publication Check](/docs/?scope=studio&doc=d-20260812-114603-9706aa) may then reuse the report's simple byte aggregation.

The specification is provisional and should change when a simpler UI makes the authoring workflow clearer. The delivery should reuse the existing Add image/Add file preview and publication owners, add only the source-folder seam and small evidence record, and avoid a second media intake framework.

Verification should stay at the lowest useful layer: focused source-path confinement and evidence-record service cases, plus manual review of the folder/list interaction. Do not add a broad smoke profile or permanent browser choreography tests merely to exercise modal steps, focus, copy, or layout.

## Boundaries

- This feature does not implement backup, versioning, synchronization, R2 export, or disaster recovery.
- It does not change the published-media defaults or provider migration owned by Media Locations.
- It does not make import staging a source archive or search for originals across multiple folders.
- It does not change ordinary document/package Import in the first delivery; the durable source-folder choice applies to **Add image** and **Add file**.
- It does not automatically republish when a source changes.
- It does not delete source originals when media, documents, or scopes are deleted.
- It does not require every imported or generated document asset to have recorded source evidence; the first outcome concerns manually selected **Add image** and **Add file** media.
- It adds no checksum catalogue, background verification, automatic source repair, rollback, retry framework, or retained rollback copy.
- Scopes other than Analysis, Dotlineform, and Processing do not adopt a media source root in the first outcome. Their occasional **Add image** and **Add file** use continues through import staging.
