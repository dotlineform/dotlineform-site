# Publishing workflow concept

## Principle

purpose of `dotlineform` scope is to hold original 'working' documents. it is for:
- content creation and editing,
- catalogue assignments
- reconciliation with external media source

purpose of `analysis` scope is to display final content that is already written, but sanitise and check it ready for publishing.
i.e. it is a 'pre-publish' gate.
- it drops `subject:folder`
- it enables any corrections to be made, check for broken images or links etc

`published/`is a static snapshot of generated files for consumption by external apps (e.g. `app`, `site/`)
- no scopes read or display the `published/` files
- 'published' data is the same content as 'pre-publish'

Publish action:
- copies 'pre-publish' `generated/` -> 'published'

Site deploy action:
- copies `published/` to repo `site/` for onward deployment to public website

## problems with current workflow

- analysis scope exposes content editing capabilities that it shouldn't have for its role
- 'working' and 'pre-publish' copy is held in independent scopes and the workflow has to make them look integrated

## current structure

```
dotlineform
  - source
  - generated
  - published

analysis
  - source
  - generated
  - published
```

## target structure

analysis needs the following structure, where current `dotineform` scope becomes `analysis/working`

```
analysis
  - working
      source
      generated
  - pre-publish
      source
      generated
  - published
      
```

other scopes that don't participate in a 'working' -> 'published' workflow retain their current structure, which has a single scope-selected view.

```
studio
  - source
  - generated
  - published
```

## Sub-scopes

Sub-scope documents are treated exactly like normal documents. They exist physically as sub-folders of `documents/` in each stage of the workflow, i.e.
- `analysis/working/documents/sub-scopes/...`
- `analysis/pre-publish/documents/sub-scopes/...`
- `analysis/published/documents/sub-scopes/...`

They share the same state types as normal documents, e.g. `publishable`

## Relationship to Catalogue

`catalogue/` contains the current catalogue published, deployable files. It does not participate in any publishing workflow, e.g. 'draft' -> 'published'. It is always represented in its current state, independent of the state of any consumer. This is not because of an architectural limitation, it is a curatorial approach. analogy: a painting does not have any snapshots or non-destructive mutations, it is only defined by its current state.

Consequence of this:
- a 'working' doc will surface the current catalogue.
- a 'published' doc on the site will surface the current catalogue, even if the catalogue has changed since the doc was published. If a work changes and that causes a document consuming that work to become 'stale', the document needs to be updated if the conflict is meaningful.

Examples of meaningful catalogue changes that may require documents to be updated:
  - physical: deletion of works that have a subject association at `work_id`.
  - semantic: addition or removal of works in a series that change the meaning or context of the series.

[Catalogue Deployment](/docs/?scope=studio&doc=d-20260909-205938-3569d6) records the distribution boundary for this policy. Local consumers read current `catalogue/generated/`; public consumers read current deployed Catalogue data. Catalogue deployment must not require rebuilding or republishing unchanged documents. The record draft/Series Publish proposal and the later proposal to freeze Catalogue dependencies inside Analysis Published are superseded; exact deployment mechanics remain pending.

## Workflow actions

The existing actions are described in [Current Copy To Analysis And Publish Actions](/docs/?scope=studio&doc=d-20260906-154418-87d990), with separate document and media steps.

There are explicit promotion actions to move files through the new workflow:

### Pre-Publish action
- copies `analysis/working/source` to `analysis/pre-publish/source`
- copies `analysis/working/generated` to `analysis/pre-publish/generated`
- runs any Pre-publish processes

### Publish action
- copies `analysis/pre-publish/generated` to `analysis/published/generated`
- runs any Publish processes

These actions result in a direct replacement of existing files. Any edits made in Pre-publish are overwritten by the replacement docs. Therefore no authoring should take place in Pre-publish. The Pre-publish processes only include rule-based edits to content and indexes:
- sanitisation of subject `folder`.
- skips non-publishable documents. they are not included in the published indexes.
- excludes management files
- excludes projects media URLs.

## Deletion

Working and Pre-publish are stages of one document, so deleting a doc in Working results in **immediate deletion from Working and Pre-publish, followed by removal from Published at the next Publish**. The cascade should follow the explicit document-to-derivative relationship; shared Catalogue records and media should remain independently owned.

The deletion cascade is:

| Location | Deletion behaviour |
|---|---|
| Working | Delete the source and generated document. |
| Pre-publish | Delete the corresponding derivative and update its indexes. |
| Published | Remove it when the next Publish reconciles the accepted snapshot. |
| Public website | Remove it when that snapshot is deployed. |

This preserves the guarantee that Published represents the last accepted publication. Removing a published JSON file immediately would also require updating its indexes, references and snapshot manifest—it is effectively a publication operation.

The website remains unchanged until deployment.

## UI

The UI shows this not in a 'scope' dropdown, but two mutually exclusive 'Stage' buttons which show clearly which one is selected:
- working
- pre-publish

Each 'stage' has a button to promote content to the next stage:
- working: 'Pre-publish' button
- pre-publish: 'Publish' button

## End result

This architecture solves the current problems:

- it brings the content editing -> publishing workflow within a single semantic scope
- it enables editing capabilities to be set according to the data being edited, not the scope it is in.

## Data migration

- `dotlineform/source`: moves to `analysis/working/source`
- `dotlineform/generated`: moves to `analysis/working/generated`
- `dotlineform/published`: retired

- `analysis/source`: moves to `analysis/pre-publish/source`
- `analysis/generated`: moves to `analysis/pre-publish/generated`
- `analysis/published`: stays where it is
