# Document Link Strength

## Idea

Record how strongly one document is associated with another. The former Studio tags supported numeric weights on tag assignments; the new model places that meaning on an outgoing document-to-document connection. Strength belongs to the source document's relationship to the target. The same concept may therefore have different strengths in relation to different documents.

This idea was captured on 2026-09-13. Outgoing ownership and independent reciprocal strengths are agreed. The numeric scale, authoring persistence mechanics and detailed presentation remain to be designed. There is no implementation or delivery plan yet.

## Directed Strength

Save and show the numeric strength on the source document's **outgoing record** for the target document. A → B and B → A are two independently authored relationships and may have different strengths: the documents can have different feelings for each other.

- A → B may be **hot / red / strong**.
- B → A may be **cold / blue / weak**.
- Editing A's outgoing strength changes A → B only. It does not assign or overwrite B → A, and an absent reverse link remains absent.
- Preserve one strength for each outgoing document relationship. Repeated occurrences of the same link do not multiply the strength; how the insertion UI handles an already-existing outgoing relationship remains an authoring decision.
- Do not sum, average, choose the maximum, or otherwise collapse reciprocal values into a shared association strength. If an incoming projection includes a strength, it describes the source document's outgoing relationship and retains that direction; it is not the receiving document's own outgoing opinion.

A visualisation that fully expresses the reciprocal relationship must show both directed links between the same two documents, each with its own strength and colour. One may be red while the other is blue. A single undirected connection or single blended colour cannot express both values. This is the intended future visualisation behaviour, not a requirement to build that visualisation with the first strength-authoring implementation.

## Authoring And Presentation

- Extend **Insert doc link** with a slider that assigns a numeric strength to the current document's outgoing relationship with the selected target document.
- The visual scale runs from **cold / blue / weaker** to **hot / red / stronger**. This expresses association strength; cold does not mean opposition or a negative relationship.
- Show the selected number with the slider and support normal keyboard operation. The colour illustrates the numeric value rather than becoming the stored meaning.
- Save and display the value with the outgoing record, and carry that directed value through document-link data for UI consumers. The initial example is the colour treatment of linked concept pills in Info's **Related** section, showing the Info document's outgoing strength toward that concept.
- Keep document identity, title and navigation unchanged. A strength does not turn a link into a Catalogue or Media View destination.
- Keep concept labels readable across the scale and make the strength available through a numeric or textual cue, including accessible text, so colour is not the sole way to discover it.

For example, Doc A could have a stronger association with Concept B than with Concept C. Its Related pills could make that difference visible using the same blue-to-red mapping as the insertion control. Another document's association with B, and B's own outgoing association with A, remain independent.

The [Info Panel Related Links And Pinning delivery](/docs/?scope=studio&doc=d-20260913-151251-cbee5b) is the first intended presentation consumer, but its current scope remains unchanged. Strength authoring, persistence and weighted styling are a separate follow-on. The Related list still sorts A–Z and deduplicates by `doc_id`; this proposal does not change ordering or add a minimum-strength filter. While Info is pinned, any future strength styling must describe the pinned document's associations.

## Ownership

The author assigns a number to the outgoing record. [Insert doc link](/docs/?scope=studio&doc=d-20260607-222033-704641) owns the authoring interaction; [Document Build](/docs/?scope=studio&doc=d-20260423-000000-c9f3ea) owns prepared document-link records; presentation reads those records. The agreed saved/displayed location is the outgoing relationship. Before implementation, settle how that authored value is retained through source editing and rebuilding so the record cannot silently lose it or compete with a second editable authority. Browser state is not persistence.

The current authoring helper writes ordinary Markdown document links. The current relationship model retains outgoing and incoming connections and their individual authored occurrences, without strength fields. Adding a slider therefore needs an explicit source and generated-data design, not just a control or pill-colour change. The old Studio weights are historical inspiration and do not establish the new number range or storage model.

If strength is exposed publicly, preserve it through the owning Pre-publish, Published and deployment projections for the accepted document set. It does not alter document publication eligibility.

## Decisions Before A Delivery

- **Scale:** choose the numeric minimum, maximum, step and insertion default. Decide whether zero is a real weak association or has another meaning; absence of a weight must not silently become zero.
- **Persistence and editing:** design how the outgoing value survives Markdown round trips and ordinary Save/Build, and how an existing outgoing relationship's strength is changed or cleared. The outgoing record and independent reverse value are settled requirements.
- **Repeated insertion:** decide how Insert doc link displays or changes the existing A → B strength when another occurrence is inserted, and what happens when the final authored occurrence is removed. Do not create competing occurrence weights or overwrite the existing value with an unnoticed default.
- **Compact display:** confirm the pill treatment for the current Info document's outgoing strength and the appearance of incoming-only connections with no outgoing value. Deduplication by `doc_id` still produces one Related entry; fully showing both reciprocal strengths belongs to a visualisation with both directed links.
- **Unweighted and derived connections:** define the treatment of existing ordinary links and semantic-token-derived document connections, which have no author-assigned strength. Do not invent a numeric value from token frequency, Subject identity or Catalogue membership.
- **Consumers:** confirm the numeric readout on outgoing records and the first pill treatment. A future network view must preserve both directed links and their independently coloured strengths; its layout and any line-width encoding remain separate design work.

Once these choices describe one complete outcome, create a bounded delivery with authoring, data propagation, presentation, focused verification, review and closeout. Until then, this document preserves the idea without widening the Related/pinning delivery or restoring the retired Studio Tag system.
