# Catalogue Series Draft Preview And Publication

## Superseded

This proposal is superseded by [Catalogue Deployment](/docs/?scope=studio&doc=d-20260909-205938-3569d6) and the current-Catalogue policy in [Publishing workflow concept](/docs/?scope=studio&doc=d-20260906-141142-5200b2). Works and Series have no draft/published state or per-Series Publish action. [UAC 4](/docs/?scope=studio&doc=d-20260905-191231-547fa9) removed those fields and controls and established optional singular Work-to-Series membership.

The text below is retained as the historical proposal. Its draft states, publication gates, many-to-many membership assumptions and open questions are not current requirements or implementation authority. Current generated Catalogue data is deployed independently of document republication.

## Historical Proposal

## Purpose

Allow a new Catalogue Series to be developed as one complete draft collection before it becomes publicly discoverable. The draft may contain its full set of Works, Work Detail sections, Details, R2 media and document links, and the local site preview should present that material with the real public renderer.

The Series is the main editorial publication boundary. Publishing it should promote the complete prepared collection and update public discovery together; the later manual site deployment remains the point at which that prepared change becomes live.

## Problem

The local site preview currently serves the same published-only Catalogue projection as the public site. Draft Works cannot be reviewed in their eventual Series context, and the current Detail workflow requires a published parent Work, so a complete new Series cannot be assembled and inspected before publication.

The required distinction is discoverability rather than secrecy. Draft payloads may exist in the deployed site data and draft media may exist in R2. A person who guesses an exact draft URL may see it; that is an accepted tradeoff for this site.

## Intended Model

- A draft Series can own attached draft Works, Work Detail sections and Details as a complete previewable graph.
- Draft exact payloads and required media can be prepared through the normal site and R2 destinations rather than a separate persistent local preview-media store.
- Local site preview shows draft and published Series. The normal public Catalogue exposes published Series through its ordinary navigation and discovery surfaces.
- Details inherit their Work and Series publication boundary; they do not need an independent status field.
- Draft Catalogue Search and Recent are unnecessary. Publish rebuilds the public Series index, Search and Recent after promoting the Series and its attached draft Works.
- A published Series has no useful draft-member workflow. Adding or changing material after publication needs one explicit, coherent rule rather than a second hidden child-publication system.
- Work membership remains many-to-many. Publishing or unpublishing one Series must preserve the visibility and exact membership of a Work that also belongs to another published Series.

## Shared Preview Distribution

Putting prepared draft media in R2 has value before Series publication. Desktop preview can use the same real media URLs and rendering path as the public site without a local media intermediate, while an isolated app can load the same assets without mounting Studio storage, cloning the repository or reproducing the media pipeline.

Together, deliberately shipped exact draft payloads and R2 media form a shared preview distribution layer. They reduce the desktop/public preview mismatch immediately and remove one major dependency from a future iPad application. The distinction remains discoverability: R2 is not canonical Catalogue source, and the presence of a draft asset or exact payload does not add the Series to public indexes, Search, Recent or navigation.

This does not make the entire isolated-app problem disappear. The app still needs the public shell or an equivalent bundled runtime, exact payload access, document source access where editing is supported, and an explicit way to distinguish previewable drafts from ordinarily discoverable published records.

## Draft Document Subjects

A complete draft Series cannot be prepared with document links unless managed Docs can assign an exact draft Work or Series as their `work_id` or `series_id` subject. The document declaration should remain the same exact canonical ID field; it should not copy Catalogue status into Docs or introduce a second draft-subject model.

The current obstruction is not primarily source storage or identity. Canonical Catalogue lookup data already contains draft records, and the Docs metadata writer accepts canonical Work and Series IDs. A draft Work or Series is a real canonical object with a status flag, so it is a valid subject and a valid semantic-token target. The Assign subject picker currently reuses a semantic-token lookup whose Catalogue rows are deliberately published-only and always carry public destinations; that lookup currently conflates canonical target existence with public destination availability.

The intended behavior is:

- Manage subject search can select exact canonical draft and published Works or Series, with status shown clearly.
- Saving a draft subject mutates only the exact document source declaration and private subject projection; it does not publish the Catalogue target.
- Desktop and isolated-app preview can join that exact subject to a deliberately available draft by-ID payload and present the expected document link.
- Semantic tokens may reference exact draft or published Catalogue identities. Rendering decides whether the current route can offer a working destination; identity validity does not depend on publication status.
- Ordinary public discovery remains published-only even when an exact draft destination is deliberately reachable.
- When the Series is published, the existing exact document declaration remains valid; the publication workflow makes the prepared Catalogue payload and document relationship publicly effective without rewriting the document.

The follow-through needs lifecycle design. A public document may name a still-draft Catalogue target, while the current Catalogue document-URL refresh expects an exact generated target payload to exist. The feature must decide whether such a relationship is held only in preview data until Series Publish, can update a staged draft payload, or blocks a relevant readiness/publication action. Missing or deleted targets must be reported by exact identity rather than confused with canonical drafts, silently treated as published, inferred from a title or discarded.

## Canonical Identity And Destination Availability

Semantic resolution should distinguish at least three outcomes:

- The exact canonical target exists and an exact payload is available on the current route: render the normal link, whether the record is draft or published.
- The exact canonical target exists but no destination payload is available in the current context: retain the authored token and identity, then either render it without an active link or send the link to a deliberate, non-breaking unavailable state.
- The exact canonical target does not exist or is malformed: report a genuinely broken semantic target.

Hiding the complete token should not be the default because it removes authored meaning from the document. Removing only the active link, while retaining an identifiable token, is the cleaner fallback when a safe destination is unavailable. If the exact draft payload has already been staged, the simplest behavior is for the link to work normally while the record remains absent from discovery.

The public Work route already catches a missing by-ID payload and renders **info not available** rather than breaking the page. The current Series route instead reports **problem loading content**, so relying on safe destination fallback would require a uniform Work/Series unavailable-page contract. Preview mode may also choose a staged draft payload where the ordinary public route would use the unavailable state.

## Publish Result

One confirmed Series Publish should validate the complete prepared collection, promote the Series and its attached draft Works, rebuild the affected exact and discovery projections, and leave one reviewable tracked-site delta. It does not deploy the public site automatically.

Readiness should cover the Series record, primary Work, member Works, Detail sections and Details, required R2 media, document links, exact identities and affected shared projections. The feature does not yet decide whether **Ready** becomes an authored Series status or remains a validation/preflight action before Publish.

## Decisions Still Open

- Whether Series status is `draft | ready | published` or whether Ready is derived and action-owned.
- Which status fields the shared site payloads need and where public-versus-preview filtering belongs.
- How the target lookup represents canonical status and destination availability without making publication part of semantic identity.
- Whether a canonical draft token without an available payload renders as non-linking text or links to a uniform unavailable destination.
- Whether exact staged draft payloads are reachable from ordinary public links or only through an explicit preview context.
- How document links are represented in staged draft payloads and when they enter the public `documents[]` relationship.
- Whether a public document naming a draft Catalogue target is allowed generally or only while that target belongs to one prepared draft Series.
- How saves to an already-published Series and its existing Works or Details should refresh public output.
- How Series Publish reports partial media, document-link or projection failure without confusing preparation, publication and manual deployment.

## Boundary

This feature does not require draft Search or Recent, per-Detail publication status, private draft URLs, a second canonical Catalogue, a draft-specific document subject field, a separate durable local media tree, automatic Git operations, or automatic public deployment. It does not yet change Docs Viewer publication semantics; any required coordination must be designed explicitly rather than inferred from Catalogue status.

There is no delivery document or implementation authority yet. Add bounded deliveries only after the remaining publication and update rules have been considered against the current Catalogue owners.
