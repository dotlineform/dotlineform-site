# Gallery And Series Incremental Updates

This is the Gallery/Series follow-on to [Incremental Updates](Incremental_updates.md), parented to [Planned Features](../Planned_Features.md). Extend the existing two Catalogue queue files with exact Gallery and Series selections and the shared output that their mutations require. The queue structure below is a proposal for review; documenting it does not approve implementation or migrate the live v3 queues.

## Requirements

- Record Gallery/Series definition and relationship changes at their canonical mutation owner, including changes with zero affected Works.
- Preserve the existing contributions of affected Works and their Save → Refresh → Regenerate → Publish lifecycle.
- Generate or delete only selected Gallery by-ID records during Refresh. Select shared indexes and reports explicitly, building each required aggregate once per Refresh.
- Publish selected Gallery changes and shared aggregates in the existing final shared-output pass after queued Works complete.
- Replace the coarse `header.shared_refresh_pending` boolean with the actual pending Gallery/Series identities and shared-output selections.
- Preserve unchanged generated bytes and timestamps using the existing content comparison. Selection comes from known mutation effects, not a whole-Catalogue comparison, output-directory deletion scan or freshness hash.

The outcome is incremental selection and completion for Gallery/Series output within the current awaited operations. Incremental merging of every aggregate index's rows is a separate follow-on; a selected aggregate may still require complete assembly and serialization. Canonical inputs can still be loaded and validated as required by their owning operation.

## Why Extend The Existing Files

Works, Galleries and Series have the same Catalogue owner, Working storage boundary and explicit Refresh/Publish actions. Keeping their selections in the existing queue files lets one mutation save its complete pending effects together and gives each operation one Catalogue pending-state owner.

Separate Gallery/Series queue files would add cross-file coordination and separate failure bookkeeping. They become useful only if those families acquire independently operated lifecycles. That is outside this proposal.

The families retain different completion rules. A Work needs metadata/media handoff, document Regenerate and per-Work Preview/Deploy. A Gallery has by-ID JSON and shared relationships but no Catalogue Markdown document of its own. Series definitions contribute to existing indexes, private reports and affected Work presentation; there is currently no generated Series by-ID JSON artifact.

## Proposed Workflow

```text
Studio mutation   canonical definitions/memberships + exact updates selections
Refresh           selected Work handoffs + selected Gallery JSON + required aggregates
                  Gallery/Series/shared selections → publication queue
Regenerate        refreshed Work source/documents → publication queue
Docs Publish      each queued Work's Preview/Deploy, then selected shared output
```

For a definition-only change with no affected Works, use **Save/Delete → Refresh → Publish**. When a Gallery/Series change also contributes affected Works, complete **Save/Delete → Refresh → Regenerate → Publish**. Refresh can complete the shared selections independently, while the Work entries remain pending for their own document work. Finish the relevant Work Regenerate before Publish so shared membership output does not advance ahead of its required Work documents.

Operations remain synchronous and edits remain unavailable until the active action completes. Queue files record pending selections between explicit actions; they do not schedule background jobs. Publish consumes completed Working inputs and performs neither implicit Refresh nor Regenerate.

## Working Catalogue Updates Queue

File: `working/catalogue-updates-pending.json`.

### Proposed JSON Shape

Propose `catalogue_updates_pending_v4`. Preserve the existing Work entry fields and the last successful Refresh timestamp. Remove `shared_refresh_pending`, and add current/deleted Gallery and Series ID arrays plus `shared_outputs`.

```json
{
  "header": {
    "schema": "catalogue_updates_pending_v4",
    "last_refreshed_at_utc": null
  },
  "current_works": {
    "00008": {
      "metadata": true,
      "image": false,
      "file_names": [],
      "refreshed": false
    },
    "04625": {
      "metadata": true,
      "image": true,
      "file_names": [
        "04625-notes.pdf"
      ],
      "refreshed": true
    }
  },
  "deleted_works": {
    "03181": {
      "image": true,
      "file_names": [],
      "refreshed": false
    }
  },
  "current_galleries": [
    "003"
  ],
  "deleted_galleries": [
    "009"
  ],
  "current_series": [
    "007"
  ],
  "deleted_series": [
    "011"
  ],
  "shared_outputs": [
    "galleries/galleries_index.json",
    "reports/series-galleries/metadata.json",
    "series-galleries-index.json",
    "works/works_index.json"
  ]
}
```

This illustrative queue asks Refresh to hand off Work `00008`, remove Work `03181`, update Gallery `003`, delete Gallery `009`, reconcile Series `007`/`011` effects and complete the named aggregates. Work `04625` has already completed Refresh and awaits Regenerate. The example does not describe live canonical or queue contents.

Gallery/Series selections use sorted distinct ID arrays because identity and current/deleted membership carry their complete operation selection. Empty per-ID records or Work-style image/file flags would add no information. These arrays have no `refreshed` field: successful shared completion forwards their publication selection and removes them during Refresh, without a document-generation step.

For each family, a current and deleted selection are mutually exclusive. Delete supersedes a queued current selection; recreation supersedes a queued deletion. Work flags/filenames keep their existing merge rules. An unchanged Save contributes no new selection and does not reset completed Work readiness.

### What Updates It

Each mutation records the actual effects it knows from the validated before/after records and relationships already used for that mutation. Capture removed relationship endpoints and former membership before discarding them. Do not derive selection later by comparing the full Catalogue or scanning generated output.

| Mutation | Gallery/Series selection | Work contribution | Required aggregate selection |
| --- | --- | --- | --- |
| Gallery create | Current Gallery and any explicitly associated Series, even with no member Works. | Existing affected Works if association changes their presentation. | Gallery index; Series/Galleries report; relationship index when an association changes. |
| Gallery rename | Current Gallery and its associated Series. | Preserve current affected member/related-Series Work contributions. | Gallery index; Series/Galleries report; relationship index when it contains the renamed Gallery. |
| Gallery delete | Deleted Gallery and formerly associated surviving Series. | Preserve affected member/related-Series Work contributions. | Gallery index; relationship index and Series/Galleries report reflecting removed associations/definitions. |
| Work Gallery membership edit | Both former and new current Galleries whose membership changed. | The actually changed Work IDs. | Gallery index for counts. Membership alone does not change explicit Series–Gallery associations. |
| Work title/year/year-display edit | Current Galleries containing the changed Work, because their member rows embed these values. | The actually changed Work IDs, including their existing private Work-report handoff. | Work index. A title/year-only edit does not change Gallery counts or explicit association rows. |
| Work create/delete | Its assigned/former current Galleries and assigned/former Series as applicable. Work deletion does not delete those definitions. | Existing current Work or full Work deletion descriptor, including its private report-row update/removal. | Work index and Gallery index where counts change. Definition-only Series/Gallery report rows do not depend on Work membership. |
| Series create/rename | Current Series, including an empty Series. | Preserve actually changed member assignments and existing definition-dependent member-Work contributions, including private Work-report rows containing the Series title. | Series/Galleries report; relationship index for creation/association identity changes; Work index when its projected rows change. A Series title is not embedded in the public relationship index. |
| Empty Series delete | Deleted Series and formerly associated surviving Galleries. | No member Works, under the existing empty-Series deletion rule. | Relationship index and Series/Galleries report. Gallery definitions/member counts remain intact. |
| Series membership edit | Former and new current Series as applicable. | Actually changed Works and existing presentation-dependent/private report contributions. | Work index. Select Gallery records only if their projected member rows changed. |
| Series–Gallery association edit | Both endpoint identities, including removed endpoints captured before the edit. | Preserve existing affected-Work contributions. | Relationship index and Series/Galleries report. Gallery title/count indexes are unaffected by association alone. |

Field-level dependencies govern aggregate selection; membership in a family is not an instruction to rebuild every aggregate. A relationship edit can select a Gallery whose own by-ID bytes remain identical. The existing generated-content comparison prevents a timestamp-only rewrite of that selected record.

### What Reads It

**Refresh** reads false-readiness Work entries and all Gallery/Series/shared-output selections. It loads the required canonical definitions and relationships, completes the selected Work handoffs, builds only selected current Gallery records and removes only exact deleted Gallery files. It completes each required aggregate once, retaining unchanged bytes/timestamps. Private Catalogue Works report rows remain part of the existing selected-Work handoff and complete before the affected Work receives `refreshed: true`. They need no duplicate `shared_outputs` selection and do not authorize a full-corpus regeneration.

The shared completion unit is the selected Gallery/Series identities and required aggregate outputs for that Refresh. After all of that unit's Working output completes, Refresh merges the current/deleted identity selections and publicly inventoried aggregate identities into the publication queue, then removes that unit from the updates queue. Private report selections finish locally and are not forwarded as public files. No per-Gallery checkpoint or synthetic document-Regenerate step is required.

**Regenerate** continues to read only refreshed current/deleted Work entries. It completes their source/document work, merges their existing Work publication records and then removes those Work updates entries. It preserves every unprocessed Gallery/Series/shared selection and the updates header.

**Refresh status** is needed when any Work entry has `refreshed: false`, any Gallery/Series ID array is nonempty or `shared_outputs` is nonempty. Refreshed Work entries alone mean Regenerate is pending, not Refresh. No separate shared pending boolean or freshness receipt is required.

### Clearing And Failure

Persist publication selection before clearing shared updates selection. A failed Working write or publication-queue merge leaves the shared completion unit queued. A successful publication merge followed by a failed updates-queue write can leave the same selection in both files; the next explicit Refresh merges the same identities without duplicating operations. Completed effects remain in place for diagnosis and manual retry.

Earlier successful Work handoffs retain `refreshed: true` if a later shared step fails. Shared arrays/output selections remain until their complete unit succeeds, and the previous successful Refresh timestamp remains until the whole action completes. Missing/malformed queues or required inputs fail visibly; they do not create empty state or trigger discovery/reconciliation as a fallback.

Gallery/Series/shared entries have no `preview_done` field. They finish as one shared-output pass under the existing completed-snapshot owner, rather than individual Gallery Preview/Deploy transactions. Entry removal records that their required shared publication completed.

### What Updates It

Refresh contributes only the shared unit whose required Working output has completed. Series IDs and affected Gallery IDs remain explicit even when the result has unchanged public bytes or only private report changes. This lets Publish complete and clear a definition-only selection without inventing a Work entry.

Work contributors continue to forward only completed Work document work. They preserve all shared families and selections. Shared contributors preserve Work media flags, filenames, initialized `preview_done` progress and the publication timestamp. Mutations continue to write the updates queue; canonical Save does not forward unfinished data directly to publication.

### What Reads It

**Publish** first completes queued Works using the existing per-Work behavior. It then passes the shared selection to the existing Preview preparation owner. Preparation retains unselected Catalogue files from Preview, replaces selected current Gallery records and selected aggregate/policy files with completed Working bytes, and removes exact Gallery deletions. The resulting snapshot remains complete and validated against the existing artifact inventory.

Public aggregate files are complete JSON payloads, not row patches. For a selected aggregate, preparation copies the completed Working bytes without reopening canonical sources or recomputing definitions. A Series deletion is represented by its absence from those completed aggregates; there is no Series file to unlink.

Distribution consumes that same completed Preview and the selected owned Gallery/shared operations. Retained unselected Catalogue files remain part of the snapshot but do not become new Gallery write/deletion operations merely because they exist. Final preparation/distribution must carry the selection through their current owners; adding fields to queue JSON alone does not make the existing inventory-based full Gallery capture incremental.

The final pass continues to run for ordinary documents, other collections, Search copying and their existing publication requirements even when the Catalogue shared selection is empty. Private Catalogue report metadata remains Working-only. Public Gallery JSON has no additional R2 media operation; affected Work media remains owned by its Work record.

### Clearing And Failure

Remove shared Gallery/Series/output selections only after the required final shared preparation and distribution succeed. A shared failure retains those selections, earlier completed Work removals and the existing snapshot/failure semantics. The next explicit Publish repeats the required shared pass; there is no new per-Gallery progress flag, automatic retry, rollback or backup tree.

The user completes an interrupted Publish before normal authoring/Refresh/Regenerate resume, preserving the existing retained-Work-progress rule. A later shared failure does not undo the Work-queue completion timestamp. Gallery/Series-only completion does not advance that Work-specific time.

## Shared Output Selection

`shared_outputs` entries are exact relative identities resolved under the configured Catalogue output root, not arbitrary filesystem paths. The updates allowlist includes the existing public system files and the private Series/Galleries report. The publication allowlist is the public `system_files` inventory in `docs-viewer/config/workspace/catalogue-artifacts.json`. By-ID Gallery identities are selected by the Gallery arrays and do not occur in `shared_outputs`. Private Catalogue Works report rows retain their existing Work-entry handoff selection.

| Relative identity | Why it may need an update | Working completion owner | Public handoff |
| --- | --- | --- | --- |
| `works/works_index.json` | Work create/delete or a change to its projected discovery fields/Series assignment. | Existing Work-index builder, once per selected Refresh. | Same relative path under Preview Catalogue and repository Catalogue roots. |
| `galleries/galleries_index.json` | Gallery create/delete/rename or a changed member count. | Existing Gallery-index builder, once per selected Refresh. | Same relative path under Preview/repository Catalogue roots. |
| `series-galleries-index.json` | Series identity create/delete, explicit association changes or associated Gallery title changes. | Existing relationship-index builder, once per selected Refresh. | Same relative path under Preview/repository Catalogue roots. |
| `reports/series-galleries/metadata.json` | Definition titles, identity create/delete or explicit association changes, including empty/unassociated definitions. | Existing private Series/Galleries report builder, once per selected Refresh. | None; complete and clear its updates selection after local output and required shared identity forwarding. |
| `media-config.json` | Explicit media-policy/configuration maintenance. | Existing media-policy builder under a separately invoked maintenance action. | Same relative path under Preview/repository Catalogue roots. Ordinary Gallery/Series changes do not enqueue it. |

An empty `shared_outputs` array selects no additional shared aggregate work; Work entries still require their existing private report handoff. All selections are sorted and distinct; unknown paths, absolute paths and traversal are invalid. Identity arrays use the existing family validators rather than a new shared slug format.

## Cutover And Scope

The proposed v4 migration preserves current/deleted Work selections, readiness/progress and both existing timestamps. It introduces empty Gallery/Series/output selections only where the prior state is known complete. A live v3 `shared_refresh_pending: true` does not identify the missing Gallery/Series operations, so it cannot simply be discarded or guessed into an empty v4 queue. Resolve that state through an explicitly approved complete shared reconciliation/baseline before switching readers/writers together.

There are no runtime v3 aliases or fallback queues after cutover. Required missing or malformed v4 state fails visibly. One-time reconciliation is distinct from normal mutation-owned queue processing.

The proposal requires mutation contributions, queue validation/serialization/status, selected shared Refresh, completed shared publication merging and selected Catalogue handling inside Preview/distribution. Existing canonical schema, Work media, public artifact inventory, document eligibility and Search workflow remain with their current owners. Ordinary/non-Catalogue incremental publication and deeper index-row optimisation remain the separate follow-ons recorded in [Incremental Updates](Incremental_updates.md#follow-ons).
