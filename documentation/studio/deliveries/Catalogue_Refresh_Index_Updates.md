# Catalogue Refresh Index Updates

## Outcome And Status

Make normal Refresh update the rows affected by supplied Catalogue mutations, preserving unaffected rows. Remove fields and dependency updates whose consumer benefit does not justify maintaining them. A single changed record should not trigger projection of the complete Catalogue or complete relationship report.

This delivery is parented to [Planned Features](../Planned_Features.md), following the accepted [Gallery And Series Incremental Updates](Gallery_And_Series_Incremental_Updates.md). The user approved each production slice and accepted closeout on 2026-10-10, including Work Document Coverage as the final row merger. Gallery-member merging uses private updates v5 for explicit creation/member candidates; publication remains v4 and Gallery output remains v3. Catalogue Works metadata uses a schema-only v3 header. Normal Refresh loads selected dependencies once and trusts canonical checks completed by Save, as explicitly directed by the user. The three private report inputs and Work Document Coverage merge queued candidates under unchanged v1 schemas. All planned production work is complete. Acceptance does not add runtime evidence: unexercised mutation/failure and UI variants retain the recorded limits, and further test work requires separate approval. [Catalogue Save And Refresh](../Catalogue_Save_And_Refresh.md), [Catalogue Indexes And Payloads](../Catalogue_Indexes_And_Payloads.md), [Catalogue Works](../Catalogue_Works.md) and [Works Report](../Works_Report_Concept_And_Architecture.md) own shipped behavior and evidence limits. Retain this delivery for recent evidence lookup pending manual archive.

The reason for this work is an operation whose scope follows its supplied changes. A measured slowdown is not a prerequisite for removing unnecessary rebuilding. Performance claims still require evidence; this delivery makes no measured speedup claim.

Paths starting with `working/` or `preview/` are relative to the configured `$DOTLINEFORM_DOCS_BASE_DIR`. Paths starting with `studio/`, `docs-viewer/` or `site/` are repository-relative. `<work_id>` and `<gallery_id>` stand for exact canonical identities. [Workspace configuration](../../../docs-viewer/config/workspace/docs-workspace.json) owns these locations.

## What Happens Currently

- v5 updates queue, `working/catalogue-updates-pending.json`, selects current/deleted Works, Galleries and Series, exact shared output files, created Galleries and Work member candidates.
- **Refresh** writes:
    - selected Work records at `working/generated/catalogue/works/index/<work_id>.json` and 
    - Gallery records at `working/generated/catalogue/galleries/index/<gallery_id>.json`. 
- Selected compact Works/Gallery indexes read their saved maps once, project queued current rows and remove explicit deletions. Unaffected rows retain their values; unchanged candidates produce no write or generation-time change. A changed map still requires deterministic ordering and complete JSON serialization.
- Selected Series–Gallery index rows replace only queued current Series' links and remove explicit deleted Series. The private Series/Galleries report replaces only rows touching queued Series/Gallery endpoints, including their empty/unassociated placeholders. Each saved aggregate is read once; unaffected rows retain their values and unchanged candidates avoid writes.
- Selected existing Gallery records read/validate saved members once and merge only queued Work member candidates using final membership; unrelated rows are preserved. Gallery rename changes only its definition. Explicit new Galleries receive a complete initial list; unchanged content avoids a write.
- The three private report inputs read selected saved maps once, upsert queued current Work/Series rows and remove explicit deletions. Unrelated rows retain their values, unchanged candidates avoid writes and explicit maintenance retains full generation through the same row builders.
- Work Document Coverage reads/validates saved Series rows and memberships once, updates queued definitions and merges retained Work candidates into their former/new Series endpoints. It preserves empty Series and unrelated rows without complete canonical member projection; unchanged final rows avoid writes.
- Unselected aggregate files are skipped. Selected media policy retains complete projection; unchanged shared output retains bytes and time.

The focused compact-index, relationship index/report, [Gallery-record owner](../../../studio/services/catalogue/catalogue_gallery_records.py), [private report-input owner](../../../studio/services/catalogue/catalogue_report_inputs.py) and [coverage owner](../../../studio/services/catalogue/catalogue_work_document_coverage.py) share their row projections with explicit whole-output maintenance. Normal Refresh excludes those aggregates and Gallery records from the [complete generator](../../../studio/services/catalogue/generate_work_pages.py). Full scalar Work projection runs only for selected by-ID records. Only queued Gallery creations need a temporary complete member-ID map during normal Refresh. Existing Gallery candidates project ID/title directly from the loaded canonical Works map; unrelated members retain their saved rows. Coverage uses saved membership and supplied Work candidates, with no canonical whole-Work membership scan; Series-only coverage needs no Works authority unless another dependency requires it. Gallery generation no longer builds the general Series/Work context, enriched Work copies or project-folder groups. Studio's live Series lookup retains the grouping data it needs.

The [Refresh input owner](../../../studio/services/catalogue/catalogue_refresh_inputs.py) loads only queue-selected dependencies, once per required canonical authority. Work/Series loading no longer reads Galleries implicitly, plain readers perform no complete canonical audit and the shared projector does not repeat validation of Save-owned inputs. Save retains canonical checks, including Series/Gallery title uniqueness; explicit validation and complete maintenance retain full audits. Existing input-envelope, selected-row/reference and saved-output validators retain their owners.

The private [Catalogue Works metadata producer](../../../studio/services/catalogue/catalogue_works_metadata.py) replaces named Work rows in `working/generated/catalogue/reports/catalogue-works/metadata.json` and removes explicit deletions while preserving other rows. It is the data producer for the read-only Catalogue Works report; it does not edit canonical Catalogue data. Its v3 header contains only schema, with no persisted count/hash or added timestamp. It still parses and writes a complete aggregate file when needed, skipping unchanged-row writes.

Publish consumes completed Working output, retains unselected Preview output and applies selected destinations. This delivery changes Refresh construction, not that publication ownership.

## Consumer Findings And Field Decisions

### Gallery Counts

Before the cleanup, Gallery index `work_count`, in `working/generated/catalogue/galleries/galleries_index.json`, supplied an “N Work(s)” subtitle through the [Catalogue media-target service](../../../docs-viewer/services/docs_catalogue_media.py) to the [local Add Media View link picker](../../../docs-viewer/runtime/js/management/source-editor/catalogue-media-modal.js). The search target uses Gallery ID and title; the count did not determine Gallery identity, link resolution or member browsing. Gallery browsing continues to read `working/generated/catalogue/galleries/index/<gallery_id>.json` and its `member_works` rows.

**Implemented decision:** the picker count subtitle and persisted Gallery index `work_count` are removed. Gallery index rows contain only ID/title, now under `catalogue_galleries_index_v3`; the target reader requires that schema and emits empty Gallery metadata. Gallery membership changes update affected Gallery member output without selecting the Gallery search index. Gallery create, rename and delete still update that index. No count lookup, counter cache or older-schema reader alias replaces the removed field. Minimal compact and Gallery by-ID headers are implemented below.

Explicit Catalogue design maintenance also uses the Work index's Work-ID inventory, then reads each selected Work's by-ID payload at `working/generated/catalogue/works/index/<work_id>.json`. The retained fields are projected directly without constructing a full Work record. Selected-row merging is implemented below.

### Headers, Versions And Other Derived Fields

Former readers only validated shape/self-consistency; the former Python relationship reader recomputed a complete content hash while its browser reader did not use it. A validation requirement is not, by itself, a product reason to persist a field.

Require a named consumer or a specific integrity requirement before retaining a derived field. Prefer deriving a display total from the already loaded map/list. Remove fields used only to validate their own duplication, updating producers and consumers together with explicit schema changes. Preserve a content version only where a concrete cache, comparison or integrity contract needs it; any retained complete-payload hash remains an explicitly acknowledged whole-file cost. Schema and successful generation time have separate contract/diagnostic purposes. Do not change Work image `media_version` as part of this review.

**Implemented Gallery by-ID decision:** user approved removing header `count` and `version` on 2026-10-10. `count` only validated its duplication of member-list length; neither Gallery display nor navigation needed it. Gallery readers did not consume `version`, normal Refresh already compared content directly, and Publish verified artifact bytes independently. The standalone generator's version-comparison branch is replaced with the same timestamp-ignoring content comparison, removing its assumption that every payload has a version. Gallery generation computes no content hash. `gallery_record_v3` headers contain exactly `schema`, `generated_at_utc` and `gallery_id`; readers require that shape and a nonempty generation time. Member-list type, exact member fields, identities and ascending order remain validated.

**Aggregate-header review decision:** the inspected production readers used these counts only to compare with loaded map/list length. Compact index versions had no reader; private report readers validated version shape without consuming it. The former Series–Gallery Python reader recomputed the content hash, but no cache/comparison consumer used it and Publish separately verifies selected bytes. Compact indexes and the Series–Gallery index/report remove `count`/`version`, retaining schema and successful generation time. Catalogue Works report now removes both fields under v3 without adding a generation timestamp, because none has a demonstrated consumer or diagnostic purpose.

**Implemented compact-header decision:** `catalogue_works_index_v3` and `catalogue_galleries_index_v3` headers contain exactly `schema` and nonempty `generated_at_utc`. Saved output and lookup readers validate the envelope, exact ID/title rows and ascending identities without a content hash, canonical join or v2 reader alias. Totals derive from the loaded maps. Both queues retained v4 at this cutover; the later member slice changes only updates to v5.

**Implemented relationship-header decision:** `catalogue_series_galleries_index_v2` and `catalogue_series_galleries_report_v2` headers contain exactly `schema` and nonempty `generated_at_utc`. Producers, saved-row mergers, local/Python snapshot readers and the shared/public browser index reader require their current contracts without v1 fallbacks or content hashes. The private report browser requires v2 and minimal headers. Pair identities and deterministic report ordering remain validated; Series cells use the exact canonical identity rules. ## Normal Refresh Row Merging

Read `working/catalogue-updates-pending.json` once. The implemented input owner loads each required canonical authority once from `studio/data/canonical/catalogue/`: Work records in `works.json`, Series definitions in `series.json`, Gallery definitions in `galleries.json`, Work → Gallery membership in `galleries-by-work.json` and explicit Series → Gallery associations in `series-galleries.json`. Carry the loaded results through Refresh. Monolithic canonical files still require complete JSON parsing when needed; row updates do not make those reads random-access. An authority with no selected dependency is not opened; empty selection opens none.

Read each selected saved aggregate once. Validate the input envelope, exact identities and the rows/references consumed by the operation. Replace or remove rows using supplied identities and current authoritative values. Preserve unaffected rows and compare the old/new selected values to determine whether a write is needed. Serialize each changed aggregate once in its required deterministic order. An unchanged selected row must not lead to a timestamp-only write.

Keep one family-owned row projection and a straightforward merge into its saved map/list. The existing Works report updater is a useful pattern, not a requirement to introduce a generic patch engine, another queue or a database.

- **Works index — `working/generated/catalogue/works/works_index.json` (implemented):** upsert compact rows for queued current Works with metadata selected; remove queued deleted Works. Do not project other Works. Candidates include already refreshed entries while shared output remains unfinished; row comparison handles changes outside the compact fields without a new per-field history.
- **Gallery index — `working/generated/catalogue/galleries/galleries_index.json` (implemented):** upsert ID/title for selected current Gallery definitions; remove selected deleted Galleries. Select the file only for retained-field changes. Other reasons to update a Gallery's member payload do not automatically select its search index.
- **Series–Gallery index — `working/generated/catalogue/series-galleries-index.json` (implemented):** replace the association list only for selected current Series; remove selected deleted Series. A Gallery rename/delete uses the old/new associated Series endpoints already captured by mutation owners. A current empty Series remains an explicit empty list. Work Series assignment and direct Gallery membership do not alter this independent relationship map.
- **Series/Galleries report — `working/generated/catalogue/reports/series-galleries/metadata.json` (implemented):** replace rows involving selected Series/Gallery endpoints and preserve unrelated rows. Use exact pair identity, plus empty-Series and unassociated-Gallery identities, in a temporary in-memory map. Mutation owners capture both ends of removed pairs before removal so the remaining endpoint's placeholder can be restored. One pass over loaded associations builds a temporary lookup only when current Gallery endpoints are selected; Series-only projection reads those Series' lists directly. No persisted inverse index or association counter is added.
- **Gallery member rows — `working/generated/catalogue/galleries/index/<gallery_id>.json`, inside `member_works` (implemented):** merge explicit queued Work member candidates into existing selected Gallery records using final membership. - **Catalogue Works report — `working/generated/catalogue/reports/catalogue-works/metadata.json` (implemented):** retain selected-row updates through its existing owner, with explicit deletion and unchanged-write avoidance. Its v3 header contains only schema; the report stays read-only and private.

Membership queries may still require a pass over the loaded Work → Gallery map or Series → Gallery associations. If needed, build only the relevant temporary lookup once per action, with its purpose explicit. Do not manufacture a persistent reverse map, background cache or change journal to avoid that pass. The removed Gallery count dependency eliminates the count-only pass for its search index.

## Queue Completion And Failure

Reuse the existing queue files, identity families and selected output identities. Private updates v5 adds `created_galleries` and `gallery_member_works`; publication stays v4 with neither array. Explicit creation distinguishes initial generation from a missing existing record, and member candidates distinguish ID/title/membership changes from broad Work handoff caused by Gallery rename. Creation is retained across later edits and canceled by deletion; member candidates accumulate and refer to retained current/deleted Work entries. No new queue file, row-patch queue or publication progress flag is added. An output selector and its identity families together supply the operation's candidates; an identity array alone does not select every index.

Keep two selections distinct within Refresh: unfinished Work handoff and pending shared-row candidates. A Work can already have `refreshed: true` when a later shared-output failure occurs. A rerun still uses that Work's queued identity for an unfinished shared index or Gallery-member update. Compact Work candidates include every metadata-selected queued Work regardless of readiness; Gallery member candidates have their own retained array independent of readiness. Regenerate and explicit document-design reconciliation reject every nonempty Refresh selection before source/Build work, preserving Work IDs until shared Refresh succeeds.

Upserting a current value and removing an explicit deletion are safe to repeat. Preserve completed effects on failure, retain unfinished shared selections and report the point reached. Forward completed public selections before removing them from updates; preserve the existing timestamps and per-Work publication progress owners. No automatic rollback, backups or recovery scans are added.

Missing or malformed saved aggregates fail visibly. They do not trigger a complete rebuild during ordinary Refresh. A separately invoked maintenance operation creates a baseline, repairs output or applies a global schema/projection change. It uses the same row projections, but has explicit whole-output authority. Empty new definitions must still be handled without inventing affected Works.

## Validation, Storage And Real Costs

The user confirmed that Save has already completed the required canonical checks and whole-catalogue audits must not be part of normal operation. Normal Refresh trusts that boundary and retains only file envelopes, exact selected identities, consumed facts/references and saved-output validation through existing owners. It performs no complete Work/Series field, Gallery membership, Series–Gallery relationship or duplicate-title audit. The shared projector has no audit bypass flag. Save and complete maintenance explicitly own semantic validation; deliberate external canonical changes require the read-only `validate_catalogue_source.py` command. Current rules allow duplicate Work titles; Series titles and Gallery titles must each be unique within their own family, comparing Unicode case folding and collapsed whitespace. These Save rules are retained, not removed as part of the read/audit split.

One JSON aggregate remains one storage unit. Parsing the saved file, visiting its entries to establish a temporary keyed view, deterministic ordering and serialization can still scale with its size. A required membership query or retained content hash can also be a whole-input pass. The outcome is selected semantic projection and dependency work, not a claim of constant-time Refresh or an in-place JSON byte patch.

Do not add sharding, persistent indexes, a database or browser-side canonical access in this delivery. Reconsider storage only as a separate outcome if these acknowledged costs later warrant it. Avoid optional index reads/writes when their selected row values did not change.
