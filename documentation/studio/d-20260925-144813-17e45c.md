# Catalogue Save And Publish Action Map

This is the central action map for reviewing Studio Work Save and designing any later Save/Publish split. Current behavior was traced through the implementation on 2026-09-25. Proposed Publish rows describe the first delivery in [Catalogue Reports Shared Front-End Browsing And Search](d-20260925-134621-42c838.md); they are not implemented. [Catalogue Build And Lookup Refresh](d-20260519-202931-0c703e.md) remains the maintained overview of the existing completion service.

Direction update: [Catalogue Authoring In Docs Viewer End State](d-20260925-151229-341ee0.md) defines Catalogue Works as “what I have saved” and separates internal generation from Review and public publication. Current Save rows S01–S49 remain the observed inventory. Proposed rows P01–P12 retain the earlier standalone-generation specification for review; their Publish naming and manual-only refresh are not the final user workflow and require revision before implementation.

The earlier proposal adds a separate Publish operation for new Catalogue Works report files. Every existing Save action below stays with Save in that specification. Moving media, existing Catalogue output or private lookups into another operation remains a later decision. Its standalone generator uses saved canonical records; it neither saves the open editor nor includes unsaved changes. The direction update above changes the required final refresh workflow, without changing observed Save behavior.

Keep the action IDs stable so issues and later decisions can refer to individual rows. Update an observed row when its implementation changes, and explicitly change a proposed row's status when it ships. The review questions at the end are open questions, not an approved reassignment of responsibilities.

## Scope And Paths

The main sequence is Save in the Studio Work editor, including existing single Works, New Work and bulk Work selection. Rows describe the successful path in execution order, with conditional actions identified. File rows in the same source transaction are listed separately to expose ownership; they are not independent transactions. Generic HTTP handling and routine rendering internals are outside the inventory.

| Abbreviation | Current location / meaning |
| --- | --- |
| `S` | Canonical source: `studio/data/canonical/catalogue/`. |
| `C` | Generated Catalogue: `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`. |
| `M` | Catalogue media staging: `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/media-staging/`. |
| `L` | Private Studio lookups: `studio/data/generated/catalogue-lookup/`. |
| Original media | Work media resolved from the configured source and exact `media_source_id`, `project_folder`, `project_subfolder` and `project_filename`. |
| R2 | Configured Catalogue image/download objects. Remote prefixes and derivative policy come from their existing configuration owners. |

These abbreviations are documentation shorthand, not new configuration aliases. Configured external roots must be available; they are not replaced with repository fallbacks.

For S31–S38, the generator compares payload content versions and retains an unchanged file and its existing generated timestamp. The table groups output writes by file family; the implementation traverses selected paths rather than promising this family-by-family write order. Ordinary Work Save passes a focused selection, so it does not perform the complete generator's global stale-file/thumbnail sweep. Private lookup writes in S41, S42 and S44 instead replace all current files on each full refresh.

## Variants And Failure Boundaries

The current bulk editor submits Gallery replacement only when that field was touched, together with expected Work hashes and exact expected membership sets. The backend also supports allowlisted `set_fields`, but the current bulk UI does not submit them. An unchanged single or bulk Save still enters output completion for its selected Works; it can therefore repair output after a source-media issue is fixed.

New Work uses the same completion sequence after creation, but has no prior record revision or generated Work payload. Series definition modals and Gallery definition modals are separate user operations that share completion. Series changes can also update member Works. Definition-only Gallery operations update definitions/memberships, generated JSON and private lookups without Work media processing. Work deletion and imports also reuse completion; pressing Work Save does not invoke those operations.

| Boundary | Current result / consequence |
| --- | --- |
| Before canonical persistence | Validation or revision failure prevents the planned canonical transaction. |
| Canonical transaction, S07–S08 | The transaction stages files and replaces them, with an attempt to restore original files if a replacement fails. This transaction does not include subsequent media, generated JSON or lookup work. |
| Later canonical writes, S18 and S22 | Dimensions and media versions can change after the editorial transaction. A later failure does not roll them back. Complete image sets may have been promoted for some Works before another target fails. |
| Media failure, S11–S28 | The canonical save remains. The exception skips Catalogue JSON generation S29–S38; previously completed local/R2 effects remain. |
| Generated JSON failure, S29–S38 | Canonical/media changes remain. Selected generated files are written individually, so output may be partially refreshed. There is no operation-wide rollback. |
| Private lookup attempt, S39–S44 | This separate attempt still runs after an output/media failure. A lookup failure is reported as saved-but-incomplete and currently replaces the earlier `output` error if both phases fail. Private files are replaced individually; stale Series-file removal errors are currently ignored by that writer. |
| Editor refresh, S46–S49 | A confirmed saved server response remains a saved outcome even if the subsequent live lookup or editor refresh fails. |
| Proposed Publish, P08–P10 | Two new files must agree on one revision. Exact write mechanics remain an implementation choice within the delivery; do not assume an atomic pair or preservation of the last successful pair after a failed write. The report must fail cleanly on an incomplete/mismatched pair. |

The retired Detail editor is not part of this workflow. Empty internal Detail maps, the empty discovery index and cleanup of Detail references found in older generated output remain in the current implementation. These are recorded as existing residue, not a reason to recreate Detail authoring or add compatibility behavior.

## Questions For A Later Save/Publish Split

These are source-grounded review points. No timing measurements or live Save/Publish/R2 runs were performed for this document, and no row has been approved to move out of Save.

| Review point | Action IDs | Question to resolve / current consequence |
| --- | --- | --- |
| Save's completion boundary | S07–S49 | Which outputs must be ready before the author can continue editing? Today Save waits for all phases, including a focused editor read after the server response. |
| Original-media and network dependence of metadata edits | S12, S19–S25 | A title-only Save can still require the original image, inspect derivatives, hash staged bytes and contact R2. Decide which assurances belong to Save versus a later broader Publish. Conversion and upload are conditional, so do not equate these checks with a full image rebuild. |
| More than one canonical write | S07–S08, S18, S22, S39 | Dimensions and versions are currently published back into canonical records during completion. Any split must identify which operation owns those fields and when the editor receives the final revision. |
| Repeated whole-corpus work | S03, S06, S10, S18, S29, S39–S40 | Several owners reload/validate canonical data, and focused JSON generation projects the whole corpus. Measure the relevant operation before deciding whether to share an in-operation snapshot or change producer scope. |
| Private lookup value and rewrite cost | S40–S44, S47 | Save rewrites all persisted private lookups while the current Work editor reads live service projections. Confirm actual consumers and required refresh timing before retaining, replacing or retiring this work. |
| Affected selection can grow | S30–S33 | Gallery co-members can enlarge the set of compared Work outputs. Distinguish full projection cost, selected comparison cost and actual changed-file writes. |
| Generated history participates in cleanup | S11, S30 | Old generated records identify former memberships, media and download reuse. A later split must preserve exact removal/dependency information across multiple Saves before Publish, or choose an explicit complete reconciliation model. |
| Partial failure and diagnostic retention | S18–S45 | Source, local media, R2, reader JSON and lookups have different failure boundaries. Decide the useful saved/published status and preserve actionable errors; currently a lookup failure can replace an earlier output error. |
| Residual retired artifacts | S37, S11, S27 | Review the remaining empty Detail index and historical cleanup with their actual consumers before any separately scoped removal. |
| New report publication cost | P03–P09 | Complete report generation is intentionally independent of Save. Observe its cost and usefulness during development, then decide whether to keep explicit Publish, call the same generator from Save, or design a broader split. |
| Saved versus report versus document revision | S31–S38, P08–P09 | Existing Catalogue output follows Save, the new report files follow Publish, and Catalogue document projections follow Regenerate. The initial delivery intentionally leaves these distinct; later consolidation needs an explicit owner for each revision. |

Neither current Save nor proposed report Publish runs Catalogue Regenerate, Docs document generation, Docs Search, Prepare Preview, Deploy Repo, a public deployment, Git commit or push. Existing Save does publish media bytes to R2 as listed above. The new Publish name initially means generating the two local Catalogue Works reader files; it does not mean public-site deployment.
