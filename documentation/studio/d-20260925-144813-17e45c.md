# Catalogue Save And Publish Action Map

This map describes the implemented Save → Prepare Preview → Publish workflow. [Catalogue Build And Lookup Refresh](d-20260519-202931-0c703e.md) owns Save completion; [Catalogue Deployment](d-20260909-205938-3569d6.md) owns snapshot distribution. [Catalogue Works](d-20260401-000000-ebf14a.md) consumes the private report metadata maintained by the targeted S50 step.

Save row IDs S01–S49 are retained for existing references; S50 is the new report-metadata step, placed at its execution position. Changed rows describe their current owner; retired rows explicitly identify removed actions. P01–P12 are reserved for the superseded, unimplemented standalone report Publish proposal and are not reused for public distribution. There is no separate Studio report Publish button.

## Scope And Paths

The main sequence is Save in the Studio Work editor, including existing single Works, New Work and bulk Work selection. Rows describe the successful path in execution order, with conditional actions identified. File rows in the same source transaction are listed separately to expose ownership; they are not independent transactions. Generic HTTP handling and routine rendering internals are outside the inventory.

| Abbreviation | Current location / meaning |
| --- | --- |
| `S` | Canonical source: `studio/data/canonical/catalogue/`. |
| `C` | Working Catalogue JSON: `$DOTLINEFORM_DOCS_BASE_DIR/working/generated/catalogue/`. |
| `A` | Shared current assets: `$DOTLINEFORM_DOCS_BASE_DIR/assets/`. |
| `M` | Configured Catalogue media staging; retained as input for `works/files/<filename>` downloads. |
| `L` | Private Studio lookups: `studio/data/generated/catalogue-lookup/`. |
| Original media | Work media resolved from the configured source and exact `media_source_id`, `project_folder`, `project_subfolder` and `project_filename`. |
| R2 | Configured Catalogue image/download objects. Remote prefixes and derivative policy come from their existing configuration owners. |

These abbreviations are documentation shorthand, not new configuration aliases. Configured external roots must be available; they are not replaced with repository fallbacks.

## Central Action Table

S01–S50 describe Save and explicitly retired actions. Source persistence precedes output completion. S18 and S22 now share one transaction with prepared asset bytes; their row positions do not imply separate commits.

| --- | --- | --- | --- |
| S01 · Save | Validate the editor draft. | Single/New/bulk mode validates its applicable fields before sending a request. Field errors stop Save before server writes. | Editor |
| S02 · Save | Submit the save request and hold the editor busy. | Single uses `/studio/api/catalogue/work/save`; New uses `/work/create`; bulk uses `/bulk-save` under the same API base. Send the record and applicable expected revisions/memberships. Busy state lasts through completion and editor refresh. | Editor |
| S03 · Save | Capture the previous canonical corpus. | The mutation dispatcher reads all `S/works.json`, `S/series.json`, `S/galleries.json` and `S/galleries-by-work.json` before mutation. This snapshot supplies output/media change comparison. | Dispatcher / Source |
| S04 · Save | Check exact Work identity and metadata revision. | Existing single/bulk Works must exist and match their expected record hashes. New Work checks that the requested identity is available. Conflict or invalid identity stops the canonical mutation. | Work / Bulk |
| S05 · Save | Validate the requested Gallery membership replacement. | When supplied, validate Gallery IDs and compare the loaded memberships independently of the Work hash. Bulk expected memberships must cover exactly the selected Works. | Work / Bulk |
| S06 · Save | Construct and validate the proposed canonical records. | Single/New normalizes allowed fields and validates against the source corpus; Work ID stays immutable and a media-bearing record can initialize `media_version`. Bulk metadata updates use their own allowlist. Gallery-only bulk Save preserves Work metadata without normalization. | Work / Bulk / Source |
| S07 · Save | Persist Work metadata. | Write the complete `S/works.json` when metadata changed, or for New Work. No initial Work-file write for an unchanged or Gallery-only save. Shares the transaction with S08 when both files change. | Work / Bulk / Transaction |
| S08 · Save | Persist Work Gallery memberships. | Write `S/galleries-by-work.json` when memberships changed. Gallery titles/definitions remain in `S/galleries.json`, which Work Save does not edit. | Work / Bulk / Transaction |
| S09 · Save | Record the canonical mutation result. | Build the saved record/hash/membership response and log the mutation. Bulk returns every selected Work, including unchanged selections. Output completion has not yet succeeded at this point. | Work / Bulk |

| S15 · Save | Prepare primary renditions. | Convert pending primary outputs into temporary files and compare completed bytes with existing shared renditions. | Local media |
| S16 · Retired | No thumbnail copy into generated JSON storage. | Complete prepared sets go to shared assets through the transaction described in S18/S22. | Local media / Transaction |
| S17 · Retired | No persistent thumbnail-staging cleanup. | Operation-owned temporary files are removed after completion. | Local media |
| S18 · Save | Commit measured dimensions and prepared media. | The existing Catalogue transaction writes prepared primaries, thumbnails and downloads with any changed canonical dimensions/version. This is separate from editorial S07–S08 but shared with S22. | Media / Transaction |
| S19 · Retired | No Save R2 client. | Local completion has no network transport dependency. | Media |
| S20 · Retired | No Save remote primary comparison. | Publish compares referenced current local assets against its public destinations. | Media |

| S22 · Save | Finalize local media versions. | A difference in an existing rendition advances the Work version once. Unchanged bytes, missing-rendition repair and transfers do not. Commit with the complete local set and dimensions in S18 before JSON generation. | Media / Transaction |

| S24 · Save | Prepare staged download replacements. | Compare `M/works/files/<filename>` with the shared destination. Prepare changed nonempty bytes for the S18 transaction; leave unchanged files alone. This planning precedes the transaction. | Media |
| S25 · Retired | No Save download upload. | Public transfer belongs to Publish. | Media |
| S26 · Retired | No automatic remote image deletion. | Removed references do not delete remote bytes. | Media |
| S27 · Retired | No automatic shared image deletion. | Removed references leave shared assets for separately reviewed cleanup. | Media |
| S28 · Retired | No automatic remote download deletion. | Removed references leave remote downloads for separately reviewed cleanup. | Media |

| S48 · Save | Reset the saved editor baseline. | Restore the single/bulk draft, saved revisions and memberships from the result; clear applicable touched-field state and update the form/route context. | S49 · Save | Display the outcome and release busy state. | Show complete Save or saved-but-incomplete output/refresh status. Validation, revision conflicts and other errors use their corresponding failure path; controls become available after the action finishes. | Editor |

For S31–S38, the generator compares payload content versions and retains an unchanged file and its existing generated timestamp. The table groups output writes by file family; the implementation traverses selected paths rather than promising this family-by-family write order. Ordinary Work Save passes a focused selection, so it does not perform the complete generator's global stale-JSON sweep. Neither mode sweeps shared assets. Private lookup writes in S41, S42 and S44 instead replace all current files on each full refresh.

## Prepare Preview And Publish

These actions follow completed Save. They do not save an editor draft or implicitly regenerate Catalogue JSON.

| ID / operation | Read and effect | Owner |
| --- | --- | --- |
| PV01 · Prepare Preview | Plan eligible Working document sources and select the declared current Catalogue JSON, existing Search and Recents. Bind captured inputs to the preparation plan. | Preparation |
| PV02 · Prepare Preview | Build captured documents in temporary storage with explicit access to the shared asset root. Copy selected Catalogue/Search/Recents bytes unchanged. | Preparation / Snapshot |
| PV03 · Prepare Preview | Validate and replace Preview, record its completed JSON revision and sorted shared asset identities, then remove temporary inputs. No media bytes are copied into Preview. | Snapshot |
| PB01 · Publish | Read the valid complete Preview and its referenced current local assets. Produce a concrete revision-bound repository/R2 plan. | Distribution |
| PB02 · Publish | Verify the reviewed plan and reconcile its owned repository JSON and thumbnails; transfer referenced current media to configured destinations. Preserve canonical versions and the separately owned public-report registry. | Distribution |
| PB03 · Publish | Await completion and report errors truthfully. No automatic shared/remote asset deletion, source rebuild, commit, push or GitHub Actions run follows. | Distribution |

P01–P12, the former global Studio report-publication proposal, are superseded. Its proposed endpoint and control were never implemented. Future Catalogue Works report generation belongs to saved-output completion; exact outputs and their public eligibility remain subject to that delivery's readiness gate.

## Variants And Failure Boundaries

Single/New/bulk Work changes, imports, Work deletion and Series/Gallery definition operations share output completion with their exact affected selection. Definition-only Gallery operations do not run Work media preparation. An unchanged Work Save still enters completion; that does not establish recovery for every image failure.

| Boundary | Current result / consequence |
| --- | --- |
| Before canonical persistence | Validation/revision failure prevents the planned canonical transaction. |
| Editorial transaction, S07–S08 | Source writes are staged/replaced with restoration attempted on failure. Later output completion is separate. |
| Local media preparation and finalization, S12–S24 | Convert before committing complete local bytes and dimensions/versions together. Editorial source success remains if this phase fails. No network effects occur. |
| Generated JSON, S29–S38 | Writes are per selected file; completed canonical/media effects remain if JSON generation is partial. |
| Private lookup attempt, S39–S44 | Runs separately even after output/media failure. A lookup failure reports saved-but-incomplete and can replace the earlier output error. Private files are individually replaced; stale Series-file removal errors are currently ignored by that writer. |
| Editor refresh, S46–S49 | A confirmed saved server response remains saved even if the later live read or editor refresh fails. |
| Prepare Preview | Failure before replacement preserves the previous snapshot; failure during replacement leaves no valid completion receipt and requires preparation again. |
| Publish | Repository and R2 effects are not one atomic transaction. Fix the cause, inspect a fresh plan and retry the owning operation. Public image bytes can change before GitHub Actions releases the repository snapshot. |

Known inherited recovery weakness: after a source-image change fails, source fields already persisted by the editorial transaction can compare unchanged on retry. If old renditions are newer than the replacement original, timestamp planning can skip conversion and finalize new dimensions with old bytes/version. A separately specified recovery fix must address this without silently introducing a pending ledger or converting every image on metadata/bulk Save.

## Separate Follow-ons

- Inventory remaining private semantic and Studio lookup consumers before retiring their files, builders, loaders and refresh work. The Works Subject column and picker already use the generated stage-bound reader.
- Diagnose reported stage-switch latency by separating requests, server work and browser rendering before selecting an optimization.
- Specify image-failure/retry behavior and any separately approved executable verification.
- Convert Catalogue Works to generated reader data with saved-data freshness; pagination, search improvements and editor integration remain later work.

Save does not run Catalogue document Regenerate, Docs Build/Search, Prepare Preview or Publish. Complete JSON maintenance remains independently callable. Publish distributes Preview and current referenced assets; Deploy remains the separate public GitHub Actions operation.
