The outcome is a useful opening page for [Catalogue](/docs/?stage=working&doc=d-20260916-161504-f8c947), report `docs_collection`, collection `catalogue`: readers immediately see the most recently updated documents with Work thumbnails, can search the whole collection without rebuilding thousands of rows while typing, and can browse bounded pages. This is a document collection. Its membership remains distinct from the saved Works listed by [Catalogue Works](/docs/?stage=working&doc=d-20260810-222148-99daec).

## Requirements

### Public Runtime And Data Ownership

The report runs entirely in the browser over generated static files. There are no server-code changes, new endpoints, server queries or request-time report computation. Ordinary HTTP file hosting supplies the bytes. The offline document builder owns the small static-metadata change needed for sorting; that generation is separate from the runtime server.

Use the existing collection manifests as list data. Catalogue public-reader manifest rows require `doc_id`, `title`, `last_updated` and an explicit `work_id`. Replace the current `subject: {kind: "work", key: "…"}` object with `work_id`: every Catalogue row represents a Work, so the field name carries the type without repeating `kind`. The offline builder must require and project a valid five-digit string Work ID for every Catalogue row, preserving leading zeroes. The public reader consumes `work_id` directly; do not retain the old subject object, accept both row shapes or infer a missing Work ID.

Working management metadata already carries dates and authoring-subject identity. Map its declared fields explicitly into the same browsing inputs at the management boundary; management metadata is not a fallback for public rows. Public code must never read the private Catalogue Works report metadata or canonical Studio records. This simplification applies to Catalogue's public-reader list manifest. Other collections retain their generic subject structure, and selected-document payloads and management authoring diagnostics keep their existing contracts.

Document source metadata owns the title, `last_updated` and exact `work_id`; the collection build projects them. The explicit generated `work_id` connects a Catalogue list row to its Work. Existing Catalogue media policy and route-owned static asset locations own thumbnail resolution. Do not infer identities from titles, filenames, document-ID timestamps, artwork year or list position. Invalid required browsing data must fail visibly without an older-schema or canonical-data fallback. Change the offline builder and browser reader together, then refresh generated outputs through their owning lifecycle; do not hand-edit Preview's generated manifest.

Keep the existing collection membership, draft/publication eligibility and stage boundaries. Public and Preview list data remain products of the existing snapshot lifecycle. Catalogue-specific browsing must not silently change other collections' search, opening order or presentation. Reuse focused shared browser behavior where appropriate without introducing a general reports refactor.

### Opening Order And Pagination

- Open with an empty query and the first 20 documents, ordered by `last_updated` descending. “Most recent” means document update time. Equal timestamps use title ascending, then exact document ID, for stable order.
- Offer latest-updated and title-ascending sorting. Search and sort changes reset to page 1; clearing search restores all documents in the selected order, starting at page 1.
- Filter and sort the whole loaded collection before selecting a page. Render only the current page's rows and thumbnail elements. Retain the sorted match list so page turns do not repeat search/sorting or fetch the manifest again.
- Reuse the compact Catalogue Works pager pattern: existing left/right chevrons around current/total page count beneath the list. Disable arrows at the ends, show `1/1` for one page and hide the pager for no matches. Keep match counts distinct from the current page size.
- Opening a document and using the report's existing detail-return action retains query, sort, page and return position. A manifest refresh reconciles the current page with the new result count. Cross-reload persistence and a general browser-history redesign are outside this delivery.

### Search Responsiveness

Search uses normalized, case-insensitive substring matching across document title and the explicit five-digit Work ID, preserving leading zeroes. Matching covers every document in the selected stage's Catalogue collection. It requires no document-body reads, rendered-HTML scraping, Series expansion or private fields.

Prepare normalized search values once when the manifest loads or is replaced. Match the [Catalogue Works](d-20260401-000000-ebf14a.md) typing behavior: wait for a **180 ms pause** after the latest input before applying search, sorting and rendering. Cancel the previous timer when typing continues. Clearing search cancels any pending search and applies immediately. Pagination and sort controls must not act on stale results while the new query is pending. Cancel pending work when the report unmounts or changes context.

Use the existing manifest and in-memory prepared values for this delivery. A persistent search index is not justified by the inspected requirements. Pagination reduces DOM and image work; it does not reduce the initial metadata transfer. Consider a smaller generated projection or an index only if a remaining measured loading/search problem warrants separate work.

### Work Thumbnails

Show a 64px thumbnail with 6px rounded corners beside each document title using the existing 96px WebP Work thumbnail. Resolve its URL through the shared Catalogue thumbnail helper, exact Work identity and declared media policy. List rendering must not fetch an individual Work record or document body to obtain a thumbnail.

The title and thumbnail open the same exact collection document. Preserve a clear accessible document link and reserve image space while loading. Load images only for the rendered page, using lazy loading where appropriate. A failed image leaves the document title and navigation usable and does not substitute another Work. Public narrow layouts remain readable; visual size, spacing and image fit receive user review.

Read-only inspection on 2026-09-26 found 4,616 collection documents, a public manifest of approximately 776 KB and a management manifest of approximately 1.69 MB. All 4,616 existing thumbnails were present in local shared assets and tracked public output, with a median file size of 872 bytes. These findings establish available inputs, not browser latency or deployed-site evidence. Many documents share bulk-generation timestamps, making deterministic date ties necessary.

## Process

1. Open Catalogue in Working, Preview or the public reader. Read the stage's generated list metadata and the declared thumbnail configuration, then show the first 20 most recently updated documents.
2. Type a title fragment or Work ID. After 180 ms without further typing, show page 1 of all matching documents. Clearing the query restores the unfiltered listing immediately.
3. Change sort or turn pages using the compact pager. Page navigation uses the already prepared results.
4. Open a document through its title or thumbnail. Load its body on demand through the existing document reader; return to the retained list state with the report's Back action.
5. Metadata and public snapshots continue through their existing build/preparation/publication owners. This delivery adds no report refresh service or independent search-index lifecycle.
