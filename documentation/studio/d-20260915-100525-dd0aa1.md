# Deploy And Public Cutover - Delivery

## Requirements

### Complete Result

The public Analysis presentation serves the accepted document snapshot and current deployed Catalogue data through the existing Docs Viewer and Media View readers. Deploy Repo prepares the complete reviewed site artifact. Docs-only, Catalogue-only and combined deployment are available, with separate results; refreshing Catalogue does not rebuild or republish unchanged documents. The reviewed artifact is released through explicit Git commit/push and Deploy Public, then checked live while preserving the frozen Catalogue archive.

This delivery belongs to [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea). [Catalogue Deployment](/docs/?scope=studio&doc=d-20260909-205938-3569d6) owns the agreed current-Catalogue boundary and selected repo destination. The next step is **DPC-0 — Readiness**. This document is proposed; writing it does not start implementation or authorise a real Publish, deployment, Git operation or remote deletion.

### Input And Destination Ownership

- Docs deployment reads one complete, validated Analysis `published/` snapshot. Pre-publish owns preparation and eligibility; Publish owns acceptance. Deploy must not read Working or Pre-publish as an alternate input, run Build or Publish, or introduce a second document filter.
- Catalogue deployment reads current external `catalogue/generated/` consumer output. Studio remains its generation owner. Deployment must not rebuild Catalogue, edit canonical records, create a Catalogue Publish snapshot, add per-record publication states or pin Catalogue data to a document publication.
- Catalogue public records may expose document links only from the accepted public document set. Any existing Working links or local-only fields must be handled by the public projection owner. This constraint does not require a companion document for every Work, Series or Detail.
- Deploy writes the configured owned projections under tracked `site/` and the configured public media destinations. The public site has no deploy-time build. Runtime/configuration and the document snapshot must switch together so collection names, report hosts, Search and deep links agree.
- Public Work/Detail image bytes remain in R2 and are selected through Catalogue-supplied URLs. The minimum implemented Catalogue reader inventory is Work records containing Details, Series membership records and 96px Work thumbnails. Confirm any additional actual consumer requirement before extending that inventory; do not copy the entire external tree.

| Catalogue input below `catalogue/generated/` | Tracked public destination |
| --- | --- |
| `works/index/<work_id>.json` | `site/assets/data/catalogue/works/index/<work_id>.json` |
| `series/index/<series_id>.json` | `site/assets/data/catalogue/series/index/<series_id>.json` |
| `works/thumbs/<work_id>-thumb-96.webp` | `site/assets/data/catalogue/works/thumbs/<work_id>-thumb-96.webp` |

### Operations And Failure Behaviour

Reuse the existing preview/apply conventions and exact source/destination identities. A preview must identify its selected inputs and owned additions, changes and removals; apply must reject a stale reviewed operation. Decide the smallest adequate Catalogue revision contract during implementation. A failed or partial operation reports the affected projection accurately and preserves a separately successful outcome. Follow-through remains awaited before reporting ready.

Removal rules apply only to the selected operation's owned destinations. Preserve `site/archive/`, archived Catalogue media, unrelated site files and other R2 prefixes. [Analysis Media In R2](/docs/?scope=studio&doc=d-20260907-201225-db6e8a) holds legacy live-site dependencies until public cutover and live-reference verification release them; its exact hold manifest remains the removal authority. This delivery must not use an old public snapshot as an excuse to delete media still needed by the live release.

Recovery uses corrected input/code/configuration and the ordinary owning operation, with Git history for reviewed repository changes. Keep unavailable inputs and failed writes visible. Do not introduce compatibility collection aliases, alternate source roots, shadow copies or a generic transaction/recovery framework.

### Boundary

Use the current document and Catalogue models. [Separate Document Content And Metadata](/docs/?scope=studio&doc=d-20260915-094811-447f11) remains parked and is not a prerequisite. Public Related/Links enhancements, shared view caching/history, Catalogue schema redesign, JSON hosting in R2, document adoption/backfill, batch New doc and automatic publishing/deployment are outside this delivery. Existing public-reader correctness and ordinary HTTP freshness needed for this release remain in scope.

A current accepted snapshot and coordinated public configuration are required before cutover; the recorded counts are observations, not fixed acceptance totals.

- The GitHub Pages workflow exists, its deployment variable is enabled, and its latest recorded manual run succeeded on 13 July. Recheck the release configuration at the real release gate; this is not evidence that current code or content has been deployed.

## Deliverables

- [ ] Docs Deploy Repo supports the current scope lifecycle and projects the complete accepted Analysis snapshot, configured public media, navigation, document locations and required indexes.
- [ ] Catalogue Deploy prepares the defined public records and thumbnails, projects accepted public document links and removes only obsolete owned output.
- [ ] The local deployment workflow supports Docs-only, Catalogue-only and combined operations with exact previews, awaited completion and distinct outcomes.
- [ ] A fresh reviewed document snapshot and prepared public artifact pass focused contract checks and user public-preview review.
- [ ] The explicitly authorised public release is verified, legacy media holds are resolved or retained explicitly, and shipped ownership is transferred to durable documentation.

## Process

1. Save Catalogue changes in Studio; its existing generation process finishes the affected current output.
2. When changing public documents, run Pre-publish from Analysis Working, review the prepared set, then explicitly Publish it. A Catalogue-only refresh uses the existing accepted document set without repeating these actions.
3. Select Docs, Catalogue or both in the deployment workflow. Review the exact source snapshots and destination changes, then apply the selected deployment operations. Confirm the entry point and control composition at readiness; reuse the existing Publish/Deploy workflow where appropriate while keeping deployment independently accessible.
4. Review the prepared tracked artifact in public-site preview, including document navigation, Search, Catalogue Media View and the archive link. Confirm the separate operation outcomes before releasing.
5. On explicit instruction, commit the reviewed changes, push and trigger Deploy Public. Verify the resulting live release before considering any held legacy-media removal.
