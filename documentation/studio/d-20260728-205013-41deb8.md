# Sub-Scope Public And Manage Manifests

## Purpose

A configured Docs Viewer sub-scope should expose two inspectable list
projections built from the same document-source snapshot:

- a minimal public-safe manifest; and
- a richer local Manage manifest.

Public and Manage retain different data and configuration boundaries while the
shared `docs_subscope` report uses the same manifest-loading mechanism.

## Concepts

The active Analysis Working and Pre-publish collection is `concepts`, presented as Concepts and using the `concepts` customisation. A document optionally defines one `concept_id`; nonempty IDs must be unique within that stage. The document owns its title, group and content. Studio Tag registry, assignments, aliases, groups and editors are retired.

Semantic tokens use `concept:concept:`; existing authored references were migrated without a compatibility alias. Their destination comes from the exact Concept document, without a Studio lookup or primary-document choice. See [Semantic Tokens](/docs/?scope=studio&doc=d-20260725-153656-516b61) for the current stage boundary.

## Projection Flow

```text
source Markdown
  + optional document-owned group
  |
  +-- sub-scope build
        +-- manifest.json
        +-- manage-manifest.json
        `-- local by-ID payloads
                 |
                 `-- Publish copies only public-safe artifacts to site/

public list/detail: published manifest.json + public by-ID payloads
manage list/detail: manage-manifest.json + local by-ID payloads
```

Manage now loads its configured `manage-manifest.json` through the shared
manifest loader. The former source-backed list endpoint and browser override
are retired; there is no source-list fallback.

Confirmed **New sub-scope** apply runs this same builder immediately, so both
manifests exist as `{"docs": []}` before the first child is created. For an
external-local parent, Manage serves only the configured sub-scope's two
manifest filenames and immutable by-ID JSON through the local generated-read
route. The route does not expose canonical source or accept an arbitrary path.

## Public-Safe Manifest

The sub-scope builder writes:

```text
docs-viewer/scopes/<scope>/published/documents/sub-scopes/<sub-scope>/manifest.json
```

External-local scopes retain this path beneath their configured external scope
root; it is not copied into the repository.

It contains only publishable list records:

```json
{"doc_id": "<id>", "title": "<title>"}
```

For a public scope, Publish copies the configured sub-scope artifacts to:

```text
site/assets/data/docs/scopes/<scope>/<sub-scope>/manifest.json
```

Publication continues to copy this manifest unchanged. Management status,
publishability, recency, Analysis/Concepts groups, source paths, and full source
metadata do not enter the current public manifest.

## Manage Manifest

The same sub-scope build writes:

```text
docs-viewer/scopes/<scope>/published/documents/sub-scopes/<sub-scope>/manage-manifest.json
```

The Manage manifest contains every source document, including non-publishable
records. Every default row has the standard fields plus false-only `publishable` for an excluded row in a publish-capable collection. Local collection rows omit it:

```json
{
  "docs": [
    {
      "doc_id": "<id>",
      "title": "<title>",
      "ui_status": "<status>",
      "publishable": false,
      "last_updated": "YYYY-MM-DD HH:MM:SS"
    }
  ]
}
```

`last_updated` may be empty and is consumed by the default recency sort. A
registered customisation may add only namespaced root and row data. The
Analysis/Concepts Manage projection is therefore:

```json
{
  "customisation": {
    "id": "concepts",
    "data": {"groups": ["subject", "domain", "form", "theme"]}
  },
  "docs": [
    {
      "doc_id": "<id>",
      "title": "<title>",
      "ui_status": "<status>",
      "publishable": false,
      "last_updated": "YYYY-MM-DD HH:MM:SS",
      "customisation": {"group": "subject"}
    }
  ]
}
```

The root identity must match the browser descriptor selected for that access.
Custom projectors cannot replace membership or default fields.

The publication gate must explicitly exclude `manage-manifest.json`. Public
browser config points to the published public manifest; Manage browser config
points to the local Manage manifest.

## Document Group Ownership

For `{ scope: analysis, sub_scope: concepts }`, `group` is an optional scalar
document front-matter field:

```yaml
group: subject
```

Docs Viewer owns this field:

- `sub_scope_customisation.settings.groups` owns its allowed values and order;
- **Edit metadata** reads, validates, writes, or removes it;
- the registered `concepts` builder projector places it in the Manage
  manifest customisation namespace;
- an absent value leaves the document under **all** only; and
- the public manifest and public detail projection omit it.

The document owns `group` directly. There is no Tag Registry group to synchronize. The **Concept fields** modal edits optional `group` and `concept_id`; `concept-associations.json` is the private generated definition projection (`docs_concept_associations_v1`).

## List Filtering And Selection

The shared report loads one configured manifest and keeps that complete
snapshot for detail validation. Default visible rows use a case-insensitive
title prefix. In Analysis/Concepts Manage, the registered `concepts` module
adds one document-group constraint from the namespaced manifest data.

Public uses the same title filter but receives neither the Analysis/Concepts
browser descriptor nor its manifest data, so it renders no group controls.
Manage renders **all** followed by the configured group names. Changing one
constraint preserves the other; clearing the title preserves the group;
**all** removes only the group constraint; and detail/Back preserves the
mounted list state.

Manage contributions receive the current visible eligible rows separately from
the complete manifest. **Select all** therefore targets only that visible
projection. Existing checked IDs remain explicit selection state when a filter
hides them; filtering never replaces them with the parent, displayed detail,
or another fallback target.

The route-resolved collection title owns list and filter accessible names,
status and no-match copy, and detail Back naming. The public route therefore
uses the configured **Concepts** title, as does Manage.

## Freshness And Gates

Both manifests and local by-ID payloads reflect the last successful document
build. This deliberately follows the existing:

```text
source -> build -> publish -> GitHub Actions
```

Manage list and rendered detail therefore share one build snapshot. Source or
metadata edits become visible through the existing targeted build/rebuild
gate, rather than through an independent live list projection.

## Delivery Boundary

The list-filter delivery owns document-group metadata, dual-manifest
generation, the one-time seed, Manage runtime cutover, and filtering. It does
not make Tag Registry a Docs Viewer build dependency, introduce group
synchronization, or publish the Manage manifest.

Current and target code authority:

- source and metadata model:
  `docs-viewer/services/docs_source_model.py`
- metadata read/write:
  `docs-viewer/services/docs_management_document_target.py` and
  `docs-viewer/services/docs_management_mutations.py`
- manifest generation:
  `docs-viewer/build/docs_builder/sub_scope.py`
- customisation config and projector registry: `docs-viewer/services/docs_subscope_customisations.py`
- browser config generation:
  `docs-viewer/build/docs_builder/browser_config.py`
- external-local generated delivery:
  `docs-viewer/services/docs_generated_reads.py` and
  `docs-viewer/services/docs_viewer_service.py`
- publication:
  `docs-viewer/services/docs_publish_gate.py`
- Manage report handoff:
  `docs-viewer/runtime/js/management/docs-viewer-management-document-reports.js`
- Analysis/Concepts browser customisation:
  `docs-viewer/runtime/js/management/docs-viewer-management-subscope-concepts.js`
- shared report:
  `site/docs-viewer/runtime/js/shared/docs-subscope-report.js`
- pure list filter:
  `site/docs-viewer/runtime/js/shared/docs-subscope-report-filter.js`
