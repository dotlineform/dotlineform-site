The completed delivery replaces canonical-data API reads with one Studio-generated metadata file and keeps the report current after successful Save completion. Other browsing improvements remain separately scoped.

Its record set is not determined by document collection membership. Existing document links remain a navigation dependency, not a reason to combine the two reports' data requirements.

After the Catalogue Works refactor, review the other standard reports and their individual data requirements before proposing further changes. Collections, including the [Catalogue collection report](/docs/?stage=working&doc=d-20260916-161504-f8c947), report ID `docs_collection` with collection `catalogue`, belong to a separate review. This document does not specify their data models, browsing, search or migration. [Collection Search And Site Search](d-20260924-135214-baa9ec.md) remains separate.

The CSI storage/publication delivery in [Catalogue Authoring In Docs Viewer End State](d-20260925-151229-341ee0.md) is complete. Catalogue Works means “what I have saved”. Studio now produces Working Catalogue JSON in the Docs workspace and local media in shared assets; Prepare Preview captures declared JSON and Publish distributes the reviewed snapshot and referenced current assets. [Catalogue Build And Lookup Refresh](d-20260519-202931-0c703e.md), [Catalogue Deployment](d-20260909-205938-3569d6.md) and the [Save action map](d-20260925-144813-17e45c.md) describe the current implementation. ## Report Architecture Principle

Reports should generally run in the front end over prepared files. Filtering, sorting, pagination, result interpretation and reader navigation should work when those files are hosted publicly, without a query service or request-time server computation. Local HTTP file serving remains necessary; the restriction concerns application capabilities hidden behind local APIs.

There are two reasons for this direction:

1. A useful Manage report capability should be straightforward to promote to the public site. Its implementation should not depend on logic available only in a local server.
2. Performance should be comparable between public hosting and local hosting using the same front-end code and equivalent files. Server-side query processing obscures the cost of the reader and distorts the apparent capabilities of the public site.

Catalogue Works should perform ordinary browsing and search in the front end over its generated report data. Studio owns the Work/Series data projection; Docs Viewer owns search fields, normalization, matching, sorting and presentation. The report retains its table and management fields. Authoring operations can continue to use local write services.

The generated report metadata remains Manage-only because it includes private fields. Front-end implementation makes later reuse possible, but public exposure would need its own field and publication contract. No identical file layout, record set or reader model is required across other reports or collections.

The architecture principle can inform the later standard-report review. Its application here is limited to Catalogue Works; reuse should follow demonstrated overlap in requirements.

## Canonical Data And The Direction Of Studio Integration

Catalogue Works began as a Studio route report and was moved into Docs Viewer while retaining its dependency on Studio canonical data. That history exposes an ownership question beyond pagination: Docs Viewer should consume generated Catalogue reader files, with Studio owning the editable canonical records and producing the metadata those readers need. Missing reader metadata should be added to the generated `catalogue/` output through its owning generation operation.

This changes what Catalogue Works reads: the saved Work metadata available after report-output generation. A report whose purpose is to inspect the exact editable canonical records could be recreated in Studio if needed; it has a distinct authoring or diagnostic purpose. The relevant meanings of “truth” are:

| Authority | Meaning |
| --- | --- |
| Canonical Work | The saved editorial record owned by the authoring system. |
| Generated Catalogue files | The current data available to Catalogue consumers, including Docs Viewer. |
| Deployed public snapshot | The data actually available to public readers. |

The practical gap between saved and generated Catalogue data is already small in the normal workflow. The current [Save completion](../../studio/services/catalogue/catalogue_output_service.py) updates affected generated Catalogue JSON, indexes and media as part of Save. A successful complete Save therefore normally supplies the latest saved Work to generated-data readers without a separate Publish action. Canonical changes can remain saved when output generation fails, and the reported incomplete output must remain visible. Generated output and public deployment are separate boundaries.

Catalogue Regenerate introduces another existing boundary: it updates Catalogue document sources and their generated document projections from Catalogue output. Its Work-record generator writes literal title, caption and summary values into the document source. Catalogue Works metadata can therefore reflect the latest Save while a linked document still displays values from its last Regenerate; the user observed this during CWF-4 review. The report's generated Work metadata and existing document-link lookup retain their separate generation owners; this refactor does not change document freshness or collection membership. Dynamic Catalogue captions belong to the separate collections review.

Whether Studio should ultimately live within Docs Viewer remains an open architectural question. The direction of current changes should nevertheless support that possibility and make later integration easier. Avoid adding dependencies that pull the applications further apart, such as Studio-only report query capabilities, duplicated reader logic or components inseparable from a particular route shell. Prefer common generated data, shared front-end behavior, exact identity contracts and focused authoring components that can be hosted in either environment.

The recent change to a one-route Studio Work editor is a useful precedent. It produced a focused editing interface that is easy to envisage inside Docs Viewer, even though application integration was not the reason for that work. Preserve that direction as the editor develops. This is a criterion for current design choices, not a decision to move the editor or a reason to build an integration framework now.

The longer-term possibility is one content environment in which authoring and reading share navigation and Work identity. The implemented lifecycle already distinguishes saved Working data, prepared Preview and deployed public data, with current shared local assets. UI consolidation must preserve those owners; a different record-level draft/version model would require a separate decision.

The present feature can establish the generated Catalogue reader boundary independently of that larger decision. Its data and component choices should remain useful if authoring later moves into Docs Viewer. Integration is neither a prerequisite for these report improvements nor an implementation delivery approved by this document.

## Browsing And Search Direction

The initial conversion preserved visible behavior. After reviewing its search delay, the user approved preparing search values once, delaying search briefly while typing and rendering 20 results per page, with only `< 1/2 >` pagination beneath the report using the existing chevron SVGs. That follow-up is implemented. Search and sort changes return to page 1; all sorted matches remain available to Copy table. The initial empty list and ascending Work ID default remain unchanged.

- Open Catalogue Works with `work_id DESC`, showing the highest Work IDs first. Here “most recent” means Work ID order, independently of artwork year, document creation time or last edit time.
- Allow browsing without entering a search. Search covers the complete relevant record set, not only the current page.
- Once browsing without search is adopted, clearing search should restore the initial descending Work ID listing. The current search-required report clears the results instead.
- Returning from a Work preserves the list page, query, sort and return position.
- Preserve five-digit Work IDs as strings, including leading zeros. Resolve identity from explicit generated fields, never from a title, filename or list position.
- Use Work ID, title, Series ID and Series title as the starting search fields. Any additional field filters need a Catalogue Works requirement; whether a Medium filter uses `medium_type`, `medium_caption` or both remains a later field-policy decision.

Catalogue Works retains normalized substring matching across Work/Series IDs and titles, using values prepared once when the metadata loads. Later search changes should use generated report fields without fetching document bodies or reconstructing searchable fields from rendered HTML.

## Catalogue Works Generated Data Direction

Catalogue Works needs a generated read model containing the fields used by its current normal and expanded rows, search, sorting and Copy table output. The first conversion defines that model for this report alone. Other reports and collections do not have to adopt its files or determine its schema.

The model includes exact `work_id`, title, year/year display, storage location, medium type/caption and exact Series identity/title membership. These are domain fields used by the reader; Studio does not add normalized search strings or UI-specific sort keys. Docs Viewer derives the values needed for its existing filtering and sorting in memory. The existing Docs-generated association lookup continues to supply exact document destinations when present; absence of a document does not remove a Work from the report.

Catalogue already generates `works/works_index.json`, `series/series_index.json`, individual Work/Series records and media policy. The first conversion adds its own report metadata file and leaves files used by other consumers unchanged. Generation can produce several useful read models from the same source without duplicating canonical ownership. Any later sharing or consolidation should follow the relevant review and explicit consumer migration. Each new output has one owner and a defined refresh operation.

The report performs browsing and search in the front end; its GET requests serve generated bytes. Exact missing or ambiguous Work-to-document associations retain explicit behavior; a reader must not infer a destination from a title or select an arbitrary document.

## Data Generation And Search Ownership

Studio is responsible for deriving current Catalogue metadata from its canonical Work/Series records and completing that output after relevant saves. Docs Viewer consumes this generated data without reading canonical records. Search is a Docs Viewer UI capability: its field selection, normalization, matching and any search-specific prepared data belong to Docs Viewer.

| Data or behavior | Owner and refresh |
| --- | --- |
| Work/Series report metadata | Studio updates only affected entries in `metadata.json` during relevant saved-output completion. Complete generation is reserved for initial population or explicit regeneration. |
| Search, sort and presentation values | Docs Viewer derives them in memory from the loaded metadata and applies its current field and matching rules. |
| Exact Work-to-document destinations | Existing Docs-generated `subject-associations.json`, with its own Catalogue Regenerate boundary. |
| A future persistent report or collection search index, if justified | Docs Viewer generates it through the general explicit Search refresh, using that index's own inputs, search rules and membership. It is not generated by Studio Save or another domain-data save. |

Use the single metadata file with front-end filtering, sorting and pagination. Assess performance before deciding whether a persistent search index is needed. In-memory preparation is part of reading the current metadata and creates no saved index or additional refresh action. There are no generated pagination or initial-page artifacts.

The current [Search builder](../../docs-viewer/build/build_search.py) has site-search rules. It can later be extended to refresh other indexes with their own rules; a shared refresh operation does not require one schema, matching policy, corpus or public/private boundary. A report or collection's own search must remain independent of its membership in site search. This delivery does not extend the builder or introduce a general indexing framework; standard reports and collections retain their separate reviews.

A future persistent index would have a different freshness boundary from Studio-generated metadata. Its consumer would need an explicit stale-index policy and source revision, without requiring Studio Save to rebuild Search or treating an older index as invalid domain data. The first delivery has no paired metadata/index files or cross-file revision requirement: filtering and sorting use the metadata loaded by the report.

The report metadata needs explicit source inputs, targeted saved-output updates, deletion by exact Work ID and a dataset revision. Save uses the mutation's known affected identities; it adds no whole-catalogue comparison or reconciliation pass. Document associations retain their separate Regenerate boundary. A reader must fail visibly on missing or invalid required data rather than silently switching to a canonical API or rebuilding metadata at request time. The new Manage-only metadata remains outside Prepare Preview and public distribution.

The former standalone Studio report Publish button is superseded and was not implemented. The metadata generator is independently callable, while affected reader entries are part of the owning mutation's saved-output completion. The wider [Catalogue Save And Targeted Publish](d-20260923-211314-6e83f4.md) proposal remains deferred; this report conversion adds no pending-change ledger or public publication action.

4. Keep Prepare Preview and Publish as the separate reviewed public lifecycle. Neither operation repairs a missing Manage report dataset.
