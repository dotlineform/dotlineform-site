# Catalogue Reports Shared Front-End Browsing And Search

This proposed feature covers the Manage-only [Catalogue Works report](/docs/?stage=working&doc=d-20260810-222148-99daec), report ID `catalogue_works`, and the [Catalogue collection report](/docs/?stage=working&doc=d-20260916-161504-f8c947), report ID `docs_collection` with collection `catalogue`. The collection has both Working and public readers. The outcome is useful initial browsing and consistent search through a shared front-end implementation and generated data contract. Report conversion and browsing/search implementation have not started.

This document owns the Catalogue-specific direction discussed here, including the replacement of the empty initial result list proposed in [Collection Search And Site Search](d-20260924-135214-baa9ec.md). That feature continues to own the wider distinction between collection search, full-text search and site-search membership. This proposal does not change the search policy of other collections.

The CSI storage/publication delivery in [Catalogue Authoring In Docs Viewer End State](d-20260925-151229-341ee0.md) is complete. Catalogue Works means “what I have saved”. Studio now produces Working Catalogue JSON in the Docs workspace and local media in shared assets; Prepare Preview captures JSON and Publish distributes the reviewed snapshot and referenced current assets. [Catalogue Build And Lookup Refresh](d-20260519-202931-0c703e.md), [Catalogue Deployment](d-20260909-205938-3569d6.md) and the [Save action map](d-20260925-144813-17e45c.md) describe the current implementation. The first report conversion below remains proposed. Editor integration and canonical relocation are still open.

## Report Architecture Principle

Reports should generally run in the front end over prepared files. Filtering, sorting, pagination, result interpretation and reader navigation should work when those files are hosted publicly, without a query service or request-time server computation. Local HTTP file serving remains necessary; the restriction concerns application capabilities hidden behind local APIs.

There are two reasons for this direction:

1. A useful Manage report capability should be straightforward to promote to the public site. Its implementation should not depend on logic available only in a local server.
2. Performance should be comparable between public hosting and local hosting using the same front-end code and equivalent files. Server-side query processing obscures the cost of the reader and distorts the apparent capabilities of the public site.

The two Catalogue reports should have access to the same common generated files. Manage adds metadata and authoring controls to that shared reader model. It should not need a separate canonical-data query implementation to provide ordinary browsing or search. Shared behavior does not require identical layouts: Catalogue Works can retain its table and the collection its document list.

Working and a published snapshot can legitimately contain different revisions or eligible records. The shared contract must still be the same, with exact Work and document identities and explicit stage context. Public readers receive the prepared public data; Manage-only metadata is additional and stays outside that public data. Authoring operations can continue to use local write services.

This is the intended general direction for reports. The proposed implementation scope here is the two Catalogue reports, not an immediate migration of every existing report.

## Canonical Data And The Direction Of Studio Integration

Catalogue Works began as a Studio route report and was moved into Docs Viewer while retaining its dependency on Studio canonical data. That history exposes an ownership question beyond pagination: Docs Viewer should consume generated Catalogue reader files, with Studio owning the editable canonical records and producing the metadata those readers need. Missing reader metadata should be added to the generated `catalogue/` output through its owning generation operation.

This changes what a Docs Viewer report represents. It shows the data available to readers after output generation. A report whose purpose is to inspect the exact editable canonical records could be recreated in Studio if needed; it has a distinct authoring or diagnostic purpose. The relevant meanings of “truth” are:

| Authority | Meaning |
| --- | --- |
| Canonical Work | The saved editorial record owned by the authoring system. |
| Generated Catalogue files | The current data available to Catalogue consumers, including Docs Viewer. |
| Deployed public snapshot | The data actually available to public readers. |

The practical gap between saved and generated Catalogue data is already small in the normal workflow. The current [Save completion](../../studio/services/catalogue/catalogue_output_service.py) updates affected generated Catalogue JSON, indexes and media as part of Save. A successful complete Save therefore normally supplies the latest saved Work to generated-data readers without a separate Publish action. Canonical changes can remain saved when output generation fails, and the reported incomplete output must remain visible. Generated output and public deployment are separate boundaries.

Catalogue Regenerate introduces another existing boundary: it updates Catalogue document sources and their generated document projections from Catalogue output. Work metadata can therefore reflect the latest Save while a document title or summary still reflects the last Regenerate. The common reader contract should make those dependencies explicit and place shared Work metadata under one generation owner.

Whether Studio should ultimately live within Docs Viewer remains an open architectural question. The direction of current changes should nevertheless support that possibility and make later integration easier. Avoid adding dependencies that pull the applications further apart, such as Studio-only report query capabilities, duplicated reader logic or components inseparable from a particular route shell. Prefer common generated data, shared front-end behavior, exact identity contracts and focused authoring components that can be hosted in either environment.

The recent change to a one-route Studio Work editor is a useful precedent. It produced a focused editing interface that is easy to envisage inside Docs Viewer, even though application integration was not the reason for that work. Preserve that direction as the editor develops. This is a criterion for current design choices, not a decision to move the editor or a reason to build an integration framework now.

The longer-term possibility is one content environment in which authoring and reading share navigation and Work identity. The implemented lifecycle already distinguishes saved Working data, prepared Preview and deployed public data, with current shared local assets. UI consolidation must preserve those owners; a different record-level draft/version model would require a separate decision.

The present feature can establish the generated Catalogue reader boundary independently of that larger decision. Its data and component choices should remain useful if authoring later moves into Docs Viewer. Integration is neither a prerequisite for these report improvements nor an implementation delivery approved by this document.

## Later Browsing And Search Improvements

These remain the intended user-facing improvements after the initial data-source conversion. The first delivery below preserves the existing Catalogue Works UI behavior.

- Open both reports with `work_id DESC`, showing the highest Work IDs first. Here “most recent” means Work ID order, independently of artwork year, document creation time or last edit time.
- Show 20 records per page, with Previous/Next controls, the current range and the matching total.
- Allow browsing without entering a search. Search covers the complete relevant record set, not only the current page.
- Search and sort changes return to page 1. Clearing search restores the initial descending Work ID listing.
- Returning from a Work preserves the list page, query, sort and return position.
- Preserve five-digit Work IDs as strings, including leading zeros. Resolve identity from explicit generated fields, never from a title, filename or list position.
- Agree one Catalogue search rule for both surfaces. Work ID, title, Series ID and Series title are the proposed common starting fields; selected field filters such as Medium follow the existing collection-search direction. Whether Medium uses `medium_type`, `medium_caption` or both remains a field-policy decision.

The current searches differ: Catalogue Works uses normalized substring matching across Work/Series IDs and titles; the collection uses a normalized title-prefix filter. Pagination alone does not unify these semantics. Public search must not fetch every document body or reconstruct searchable fields from rendered HTML.

## Shared Generated Data Direction

Both reports should consume one common reader model with the same front-end normalization, filtering, ordering, paging and navigation logic. Prefer a common public-safe base plus separately loaded Manage enrichment keyed by exact Work/document identity. A generated management superset of the same contract is another possible layout; the implementation should choose one physical arrangement, without creating a second search engine or source of truth.

The common model needs enough information to list and search Works and open their exact destinations: `work_id`, display title, agreed search/filter fields, Series identity/title where relevant, and the exact Catalogue `doc_id`/collection identity when a document exists. Management fields such as storage and authoring state can extend that record. Stage-specific routes should be resolved through configured reader context rather than embedding a local-only URL as the common destination.

Catalogue already generates `works/works_index.json`, `series/series_index.json`, individual Work/Series records and media policy; Docs generates collection manifests and by-ID documents. Existing files can be consumed where their current contract fits. The first conversion adds its own output files and leaves files used by other consumers unchanged. Report-specific and collection-specific indexes are acceptable; generation can produce several useful read models from the same source. Later sharing or consolidation should follow explicit consumer migrations. Any new lookup is generated output with one owner and a defined refresh operation.

The public renderer must work without the Manage extension. Manage must gain metadata and controls without gaining a hidden server-only browsing or search capability. Exact missing or ambiguous Work-to-document associations need explicit behavior; a reader must not infer a destination from a title or select an arbitrary document.

## Move Repeatable Work Into Generation

There is no restriction on moving more work into Catalogue saved-output generation or Catalogue Regenerate when it improves reading performance. Additional indexes, lookup files or initial-page artifacts are acceptable. The tradeoff is generation and maintenance cost against repeated reader work, not a requirement to keep generation minimal.

| Candidate prepared data | Work removed from report opening or searching | Producer direction |
| --- | --- | --- |
| Compact browse/search projection | Downloading full canonical records, selecting fields and joining Series metadata on every report opening | Studio Catalogue generation owns Work/Series fields; share the resulting public-safe data between both reports. |
| Exact Work-to-document lookup or document identity embedded in list rows | Downloading and traversing the full management association structure merely to construct Work links | Catalogue Regenerate/Docs collection generation owns the exact document mapping. Coordinate it with Catalogue data by explicit Work IDs. |
| Precomputed normalized search values and sort values | Repeated Unicode/text normalization and reconstruction on every keystroke | Generate from the same agreed field/matching policy used by the front end. Keep original display strings. |
| Initial 20-row payload or ordered page files | Waiting for the complete searchable metadata before showing useful records | Generate from the same ordered dataset/revision as the full index. A first-page file can be small while the full search data loads on demand. |
| Optional field/filter dictionaries or a richer search index | Repeated field joins or query scans if they become a measured bottleneck | Add only the index structure needed by the agreed search semantics and measured workload. |

These are options, not a requirement to create every file. A single compact metadata file with 20-row rendering may be sufficient at the current scale. Static first-page or page files remain valid options if initial transfer is significant; pagination need not imply a server query. Search still needs access to the complete relevant search data, even when the first page is loaded separately.

Each chosen artifact needs explicit ownership, source inputs, saved-output completion trigger, deletion reconciliation and freshness/revision rules. Related page, search and document-mapping files must describe a consistent dataset. A reader must fail visibly on invalid required data rather than silently switching to a canonical API or rebuilding it at request time. Define how the new output participates in Prepare Preview and Publish; the public site still has no deploy-time build.

The former standalone Studio report Publish button is superseded and was not implemented. Keep the proposed generator independently callable, while making its reader outputs part of the owning mutation's saved-output completion. The wider [Catalogue Save And Targeted Publish](d-20260923-211314-6e83f4.md) proposal remains deferred; this report conversion adds no pending-change ledger or public publication action.

## Performance And Delivery Direction

Separate initial data transfer, JSON parsing/preparation, query work, sorting, row rendering and selected-document/media loading when evaluating performance. Rendering 20 rows addresses DOM work; reducing or deferring metadata addresses cold opening. Pre-normalizing fields addresses repeated query work. No measured performance target or dominant bottleneck has yet been established.

Compare the same front-end code against an equivalent generated dataset locally and on public hosting. Record cold and warm cache conditions and the Manage enrichment separately, so differences reflect hosting/transfer and additional metadata rather than server-side query work. Retain bounded rendering and on-demand document/media reads throughout.

The proposed sequence remains an isolated Catalogue Works data-source conversion, followed by browsing/search improvements and migration of other reports and collections. Its generation trigger must satisfy the saved-data requirement, including Work creation/deletion and Series changes that affect displayed rows. Descending Work ID order and 20-row pagination belong to a later delivery. Each migration should preserve unrelated consumers and move towards the shared front-end architecture. Manage browsing interfaces should read generated models, while authoring components access canonical records through their owning validation and persistence services.

The first conversion retains existing search, Copy table and missing-document behavior. Later deliveries must settle the shared searchable fields and matching rules, page-only versus all-matches copying, and collection selection across pages. Measure any material new Save cost before redesigning completion; keeping the generator independently callable must not leave the saved-data report stale until a manual Publish. New or changed tests require their own agreed specification under [Test Contract Discipline](d-20260627-212121-7cf7de.md).

### Process

1. Populate the initial reader dataset through the generator's reviewed owned write set.
2. Save Catalogue edits through the normal Studio operation and await complete saved-output status.
3. Open or reload Catalogue Works to use the current generated report files. Automatic refresh of an already mounted report is outside this first conversion.
4. Keep Prepare Preview and Publish as the separate reviewed public lifecycle. Neither operation repairs a missing Manage report dataset.
