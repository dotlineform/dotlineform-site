# Catalogue Build And Lookup Refresh

## Save Completes Output

Ordinary Work editing completes through Save; shared Gallery and Series definition modals complete through OK or confirmed Delete. Work, Series and Gallery create/save, Work bulk edits and deletion share the output-completion owner in `studio/services/catalogue/catalogue_output_service.py`. Single, New and bulk Work saves also own Work Gallery membership. Studio Detail reads, mutations and editor UI are retired; bulk Work creation remains separate.

After the validated canonical transaction, that owner determines changed Works and Series. It completes required media, refreshes affected exact Work/Series/Gallery JSON and their discovery indexes, updates the affected private Catalogue Works report entries and Works collection subject titles, then refreshes private Studio lookups and returns current records and revisions. Detail folders and indexes are retired: ordinary source reads, generation and Save do not probe or recreate them. Work output includes Gallery memberships; a Work label change also refreshes its Gallery member rows. An unchanged Work Save still attempts output completion; it is not proof of recovery after every failed source-image change.

Canonical persistence and output completion are separate results. An output or lookup failure keeps the saved canonical change and reports the incomplete step and error. The editor also preserves a confirmed saved outcome if a later refresh fails. Fix the reported cause and use the ordinary owning operation again. If output generation was interrupted or previous membership output is missing, use complete JSON maintenance to reconcile former memberships as well. There is no automatic rollback or retry workflow.

## Generated Catalogue

Working Catalogue JSON is configured at `$DOTLINEFORM_DOCS_BASE_DIR/working/generated/catalogue/` by `docs-viewer/config/workspace/docs-workspace.json`. The existing Docs root must be available; missing or escaping paths fail visibly without creating another tree or using the retired Projects-generated output.

`generate_work_pages.py` owns full payload projection and output reconciliation. It reads both canonical Gallery files, projects Gallery IDs/titles into each Work, and derives the inverse membership for individual Gallery files. `catalogue_output_selection.py` selects affected records: Work refresh includes its former/current Series and Galleries; Gallery refresh includes its former/current member Works, including removed members. Previous generated records supply invalidation targets only; current canonical sources determine every new payload. Gallery title changes therefore update embedded titles in member Work records, while Work labels update Gallery rows. Empty Galleries are emitted, and Gallery deletion removes the obsolete record and refreshes its former members.

The output service accepts a focused Gallery selection with `generate_catalogue_json(..., work_ids=(), gallery_ids=(...))`, using exact Gallery IDs without aliases. The existing Work Save caller continues to pass changed Work/Series IDs and gains Gallery refresh through the same owner. Omitting `work_ids` requests complete reconciliation, which also removes obsolete owned Work/Series/Gallery JSON. All modes refresh the discovery indexes and shared media policy. This includes `galleries/galleries_index.json`, whose IDs/titles and member counts come from the same canonical inputs as the individual Gallery records. Gallery creation, rename, membership changes and deletion therefore update the lookup during focused or complete generation. Unchanged payloads retain their existing generated timestamp.

Work membership saves explicitly pass the union of the previous and selected Gallery IDs to that output owner, including when only membership changed. The single Work service read and save response carry a separate `gallery_ids` array; Work record revisions continue to describe Work metadata, while `expected_gallery_ids` guards membership replacement. The editor's `catalogue_galleries` service read projects the canonical ID/title registry directly; it creates no additional lookup file or editable reverse membership map.

Bulk replacement uses the existing `/bulk-save` route with one `gallery_ids` set and `expected_gallery_ids_by_work` covering exactly the selected Works, alongside their metadata revisions. All checks precede one canonical transaction. Gallery-only mutations write `galleries-by-work.json` once without normalizing or rewriting Work metadata. Omitting `gallery_ids` preserves memberships and allows ordinary Save completion to run again. The bulk response includes every selected Work and its saved memberships; output completion refreshes metadata revisions without discarding those memberships. The live Work search response also carries Gallery IDs for list display, without changing the persisted lookup format. The [Work editor](d-20260422-000000-45a776.md) owns intersection and replacement interaction.

Gallery definition operations use `/gallery/create`, `/gallery/save` and `/gallery/delete`. Create allocates the next numeric Gallery ID from the canonical registry; save and delete require the exact ID and definition revision supplied by `catalogue_gallery_record`. Delete additionally compares the complete confirmed `expected_member_work_ids` with current canonical members and rejects a changed set before writing. The definition and its membership removals share the existing source transaction; Work metadata in `works.json` remains unchanged. The response carries every affected canonical Work ID and the Gallery ID into completion, so output refresh does not depend on the current editor selection or a complete former generated member list. Definition-only Gallery operations refresh JSON/indexes and private lookups without Work media processing. Work membership Save retains its existing media/output behavior. Series deletion also explicitly rechecks that no Works belong to it.

[Catalogue Indexes And Payloads](/docs/?scope=studio&doc=d-20260519-202931-b05d27) describes the output shape. Generated Catalogue data is not a public acceptance decision. The producer does not write the frozen archive, old public pages, Recent, Catalogue Search or Docs output.

## JSON Maintenance

Use a complete JSON regeneration for deliberate maintenance:

```bash
python3 studio/services/catalogue/catalogue_json_build.py
python3 studio/services/catalogue/catalogue_json_build.py --write
```

The default previews changes. `--write` writes current JSON and reconciles obsolete owned files. Both report missing referenced thumbnails; an incomplete report exits 1 even when the JSON write succeeded.

This path uses current canonical records and existing media references/versions. It does not convert or upload primary images, copy thumbnails, promote media versions or refresh private Studio lookups. Required thumbnails resolve from shared `assets/works/thumbs/`; ordinary Save maintains affected local media. JSON reconciliation never deletes shared assets.

## Private Catalogue Works Report Metadata

`catalogue_works_metadata.py` owns `reports/catalogue-works/metadata.json` beneath the configured Working Catalogue directory. The [Catalogue Works](d-20260401-000000-ebf14a.md) reader uses its `catalogue_works_report_metadata_v1` contract. This file contains domain metadata, including private storage fields; it is outside `catalogue-artifacts.json`, Preview and public distribution. Docs Viewer owns search normalization and sorting in memory.

Saved-output completion calls only the targeted updater. It derives the named Work's row, the selected bulk rows or a Series mutation's affected member rows, using the saved canonical snapshot. Explicit Work deletion removes its exact ID; Gallery definition changes do not update this report. It does not use the broader Gallery/media invalidation selection or regenerate unrelated rows. Matching report data skips the file write and version change. Changed rows require serializing/writing the aggregate once; the header version is the deterministic hash of the Work map. The Save response includes `report_metadata` diagnostics when this update runs.

The targeted updater checks the existing envelope/header and validates projected entries, without comparing every row to canonical data. Missing or invalid metadata reports saved-but-incomplete through the existing output-error result; it never triggers a complete rebuild. An earlier media/general-output failure prevents the report update, and later lookup failure still reports incomplete Save output. There is no rollback, retry ledger or backup file. Fix the cause and repeat the relevant owning operation, or explicitly regenerate the report aggregate. The separate explicit deletion option also permits completing a failed report removal without repeating an already completed canonical deletion.

Initial population and complete repair are explicit and touch only this metadata file:

```bash
python3 studio/services/catalogue/catalogue_works_metadata.py
python3 studio/services/catalogue/catalogue_works_metadata.py --write
```

For a deliberate targeted update, supply `--work-id <five-digit-id>` for saved Works or `--deleted-work-id <five-digit-id>` for removed Works. Both options can be repeated; a deletion is rejected while the Work still exists canonically. Commands preview by default and apply only with `--write`. Complete and targeted generation share the same row projector and perform no media, R2, Docs Build, Search or Catalogue document Regenerate work.

## Private Works Collection Metadata

[Works collection metadata](../../studio/services/catalogue/works_collection_metadata.py) owns `reports/works/manifest.json` beneath Working Catalogue output. The `works_collection_metadata_v1` payload contains `works` and `series` maps from exact IDs to titles, with a content revision in `header`. All identities, including empty Series, are present independently of Docs membership. The [Manage Works collection](d-20260728-113139-763354.md) joins these titles to its document-owned subject declarations in memory. The server serves saved bytes through the same origin-restricted report route as Catalogue Works; the private file stays outside the public Catalogue artifact inventory and Preview/Deploy Repo.

Save completion reuses its loaded records and affected Work/Series identities, including unchanged Save selections for output retry. It projects only those titles, removes affected IDs that were explicitly deleted, preserves other entries, and avoids a write/revision change when values match. Validation reads the saved aggregate without an extra canonical corpus read. Gallery-only definition changes do not affect these title maps. This runs inside the existing awaited completion/error boundary and returns `works_collection_metadata` diagnostics. Missing/invalid output is a saved-but-incomplete failure, never an automatic full rebuild or a reader fallback.

Initial population and explicit repair write only this file, with no Docs, Search, media or source changes:

```bash
python3 studio/services/catalogue/works_collection_metadata.py
python3 studio/services/catalogue/works_collection_metadata.py --write
```

For explicit selected maintenance, repeat `--work-id <five-digit-id>`, `--series-id <three-digit-id>`, `--deleted-work-id <five-digit-id>` or `--deleted-series-id <three-digit-id>`. Deletions require an absent canonical identity. Commands preview by default; `--write` applies. Normal Save already does the required targeted update, so Works list loading needs no additional operation.

The user confirmed Studio Save testing and accepted this behavior on 2026-09-26 after browsing review through Site Preview. Initial generation, targeted no-change preview, static serving and source review provide the other focused evidence. Bulk/create/delete permutations and output-failure recovery were not exercised as an automated mutation matrix.

## Private Studio Lookups

Studio search/list files live under `studio/data/generated/catalogue-lookup/`; rich focused reads are service projections. `catalogue_lookup.py` owns serialization, and `catalogue_lookup_refresh.py` owns refresh. The focused Work service projection uses `studio_catalogue_work_record_v3`, with Work data, revision, resources and Series summary but no Detail sections. Detail lookup builders and invalidation paths are retired. Save completion performs a full private lookup refresh after local media completion so revisions include current versions. This does not refresh Docs semantic lookups. Works list subject titles use the Save-maintained collection metadata above; its subject picker retains the stage-bound generated Catalogue provider. Neither depends on the private semantic lookup. Remaining lookup consumers must be migrated before their files, producers or refresh paths can be retired.

For a deliberate standalone complete export:

```bash
python3 studio/services/catalogue/export_catalogue_lookup.py
python3 studio/services/catalogue/export_catalogue_lookup.py --write
```

The exporter defaults to canonical Studio source and the private lookup directory. Its source/output overrides are for explicit controlled use.

## Media And Maintenance Boundaries

`catalogue_output_media.py` resolves exact Projects-owned originals and prepares required Work primaries and thumbnails in temporary storage. Final reader bytes live under the configured Docs workspace at `assets/works/primary/`, `assets/works/thumbs/` and `assets/works/media/files/`. Gallery definition-only output does not process media. Active Detail media processing is retired; historical conversion tooling and the frozen archive retain separate ownership.

Local preparation checks complete rendition sets. Differences in existing rendition bytes advance the Work's `media_version` once; unchanged bytes and missing-rendition repair do not. `catalogue_media_version.py` commits prepared media, measured dimensions and versions together through the existing Catalogue transaction owner, after the separate editorial transaction and before reader JSON generation. No retained asset history or hash sidecar is created.

A staged download at the configured Catalogue `media-staging/works/files/<filename>` replaces differing shared local bytes. Without a staged replacement, the exact existing nonempty shared file is retained. A required file absent from both locations fails completion; R2 is never a fallback. Removed references leave shared bytes for separately reviewed cleanup.

Save performs no R2 checks, uploads or remote deletion. [Catalogue Deployment](d-20260909-205938-3569d6.md) owns Prepare Preview and Publish; [Publish Media To R2](d-20260508-093841-3e27b1.md) describes the standalone maintenance transport. Transfers never change canonical dimensions or versions.

Known recovery limit: source-location fields are saved before media completion. If that image change fails, an unchanged retry no longer sees a source-field difference. Timestamp planning can retain old complete renditions when they are newer than the replacement original, then associate new dimensions with old bytes/version. Reliable recovery for this inherited case needs a separately specified fix; do not promise that another unchanged Save always repairs it or add an implicit pending-state store.

Focused writes still project the whole canonical corpus in memory and compare selected outputs by content version. Selecting a Work also considers current/former co-members of its affected Galleries; unchanged Work files are not rewritten. Large-collection Save latency has not been measured. Keep future performance work in these owners; do not introduce a second field planner or per-image whole-Catalogue refresh.
