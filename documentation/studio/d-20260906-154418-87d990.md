# Current Copy To Analysis And Publish Actions

Current implementation, checked on 6 September 2026, as input to the [Publishing workflow concept](/docs/?scope=studio&doc=d-20260906-141142-5200b2). “Copy” describes the workflow action; document contents may be transformed before destination files are written.

## Projects — Copy To Analysis

### Documents

1. Preview the selected `dotlineform/projects` documents for New editorial copies or replacement of explicitly selected linked documents in `analysis/works`.
2. Prepare destination Markdown in memory: adjust IDs, dates, parentage and mapped document/media links. New creates a new ID and defaults to publishable; Replace preserves the destination ID, creation date and publishability.
3. Retain subject metadata, including `work_id`, `series_id`, `detail_uid` or `folder_path` when present. Folder removal is not currently part of Copy.
4. Once media preparation is complete, write the new or replacement Markdown into Analysis source and rebuild `analysis/works` generated output.
5. Record the Working-to-Analysis document relationships and rebuild Projects so its copy links are current.

Working source documents remain unchanged. Destination generated documents are rebuilt from the written Markdown, not copied from Working generated output. Search is not rebuilt.

### Media

1. Identify the referenced Docs media and required build sources; preview availability and destination collisions.
2. Copy required build sources and ordinary media into the configured Analysis source media locations, reusing identical existing files. Conflicting destination bytes block the copy.
3. Run registered media producers where the plan requires missing outputs, then verify the required destination media exists.
4. Carry forward media source evidence before writing the destination documents.

Source media remains unchanged. Source Markdown media references are rewritten for Analysis as part of document preparation.

## Analysis — Publish

### Documents

1. Validate the existing `analysis/generated/` snapshot against its completed Build manifest. Publish does not run Build.
2. Select eligible document output, filter indexes and associations, and exclude management files. Publication eligibility includes the generated sub-scope document sets.
3. Prepare the published JSON in memory, including Docs media-URL rewrites. The original generated files remain unchanged.
4. After required media is validated, reconcile `analysis/published/`: write added or changed files, remove obsolete files and leave unchanged files alone.
5. Verify the resulting file set and bytes, then write the completed publication manifest.

Publish filters the existing Search index; it does not rebuild Search. It prepares JSON before writing it, rather than copying JSON and then editing it in place.

### Media

1. Collect referenced Docs media from the accepted document output and rewrite its URLs to the published-media routes during JSON preparation.
2. Read the required files from `analysis/generated/media/`. Missing required media blocks Publish; media producers are not run.
3. Include those bytes under `analysis/published/media/` in the same snapshot reconciliation, removing previously published media that is no longer required.

## Optional Copy To Local Repo

The Publish modal offers Publish and Copy to local repo, with both selected when available. After Publish, Copy to local repo separately previews and confirms deployment of the accepted snapshot to `site/` and configured public-media destinations, then updates publication links. It may also run alone against an existing accepted snapshot. Commit, push and public-site deployment remain separate actions.

The implementation owners are `docs-viewer/services/docs_document_transfer.py`, `docs-viewer/services/docs_document_transfer_apply.py`, `docs-viewer/services/docs_scope_publish.py` and `docs-viewer/services/docs_deploy_repo.py`.
