# UAC 3A - Implement A Simple Catalogue Media View

The original single-Work proof is accepted. Sections 3A.0–3A.3 retain that baseline; 3A.4 records the separately approved small gallery extension and its review gate.

## Purpose

Implement the smallest real Media View needed to test the central presentation decision in [UAC 3 - Explore Tokens, Reports And The Consumer Data Model](/docs/?scope=studio&doc=d-20260904-204816-0f31be): a canonical Catalogue Work can be presented through its exact identity, image and metadata without requiring a canonical document.

Use Work `00523` and the manually prepared Catalogue record under `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/works/index/00523.json` as the representative input. The view is a UI and presentation-contract proof. It must reveal whether the current Work JSON supplies a useful Media View, while avoiding premature decisions about the final token grammar, thumbnail galleries, Series presentation, Work Details or the completed Catalogue-to-Analysis build and publication flow.

## Requirements

1. Media View presents one exact Catalogue Work inside the existing Docs Viewer main pane. It displays the primary image and a restrained set of metadata taken from the representative Work record.
2. The presented identity is the exact `work_id`. The view is not a document, does not acquire a `doc_id`, does not require a Work-subject document and does not select or create a canonical document.
3. The first proof opens from an ordinary Analysis example document and returns to that document through the existing Content Detail lifecycle. The originating document supplies browsing context only; it does not own the Work.
4. The runtime consumes one complete, immutable media-presentation payload supplied by the mounted document output. It does not fetch canonical Studio data, infer identity from filenames or read the external Catalogue workspace in the browser.
5. The proof payload is prepared explicitly from the representative Work JSON. This temporary example does not establish final semantic-token syntax or an authoring workflow. A later accepted token or gallery projector may emit the same runtime presentation contract.
6. The view works in public and Manage Docs Viewer through shared runtime code. Docs Review may continue to show the ordinary static source presentation and does not need the interactive view.
7. Use the existing Content Detail Back and Open in new tab controls. Back restores the originating document and invocation focus. Open in new tab targets the accepted full-size media object.
8. The image is contained rather than cropped. Metadata remains real text and uses current Docs Viewer theme roles at narrow and wide widths.

## First Presentation

The first view should show only values already available from the representative Work record or the accepted media-path contract:

- primary image;
- title;
- `year_display`, falling back to `year` only when the display value is absent;
- `medium_caption`, falling back to `medium_type` only when the caption is absent;
- physical dimensions when present;
- Catalogue number from the exact `work_id`; and
- an explicit Open original action.

Do not add Series title, associated-document links, Detail thumbnails, downloads or other fields merely because they may be useful later. Their absence or awkwardness is evidence for the continuing consumer-model review.

## Deliberately Deferred

- thumbnail-gallery generation and layout;
- previous/next, position/total, wrapping and sequence ownership;
- Work Detail and Series Media View presentations;
- final token names, source syntax and source-editor modal choices;
- direct Media View URLs, browser history, bookmarks and external deep links;
- associated-document lists or document-selection behavior;
- runtime fetches from Catalogue JSON;
- integration with the final external Catalogue Build, Analysis Build, Publish or Deploy Repo flow; and
- public cutover or changes to the frozen archive.

This deliberately narrows the earlier [Catalogue Media View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) proposal, which required sequence navigation from its first delivery and still contains assumptions from the earlier one-Work-document model. Sequence behavior belongs with the later gallery delivery. This proof establishes the single-item view first.

## Readiness Decisions

Work `00523` is available as `work_record_v5`. The proof values are title `kylie structure 4`, year display `2023`, medium caption `digital c-type print`, dimensions `45 × 80 cm`, intrinsic image dimensions `9449 × 5315`, media version `1` and Catalogue number `00523`. Its full-size WebP at `https://media.dotlineform.com/works/img/00523-primary-1600.webp?v=1` responds successfully as `image/webp`. The nested Details and Series membership are deliberately excluded from the first presentation.

The proof document will contain one exact marked presentation. The marker is runtime input emitted in document HTML, not accepted authoring syntax:

~~~html
<figure data-docs-content-detail="media">
  <a data-docs-media-open href="https://media.dotlineform.com/works/img/00523-primary-1600.webp?v=1">...</a>
  <script type="application/json" data-docs-media-presentation>...</script>
</figure>
~~~

The immutable `docs_media_view_v1` payload contains:

- `target: {kind, id}` with `kind: catalogue-work` and exact five-digit `id`;
- `label` for the Media View toolbar;
- `image: {src, alt, width_px, height_px}`;
- an ordered `metadata: [{label, value}]` list containing only the first-presentation fields; and
- `new_tab_target` for the existing Open in new tab control.

The adapter parses and validates that payload when the current document mounts, associates it with the exact document mount generation and marker occurrence, and supplies an immutable target context to Content Detail. It writes all display values with DOM text properties, accepts only root-relative or credential-free HTTPS media targets, and fails closed when the marker, target identity, image dimensions or payload is invalid. The ordinary anchor remains the no-adapter fallback.

The current Content Detail lifecycle already hosts table, diagram and report adapters and can accept `kind: media` without routing changes. The document controller needs one explicit Media View mount/release owner, and the app boot/runtime plumbing must pass the adapter to that owner and Content Detail. No new view lifecycle is required.

The affected public projection is explicit. The new shared adapter must be added to `site-tools/config/site-code-update.json`; existing shared `docs-viewer-content-detail-view.js`, `docs-viewer-document-controller.js`, `docs-viewer-app-boot.js`, `docs-viewer-app-runtime.js`, public `docs-viewer-public.js` and `docs-viewer.css` are already projected. The Manage entrypoint remains local-only. The public runtime-boundary check should confirm the new shared adapter is reachable from public and Manage and absent from Review.

No readiness blocker remains. The implementation must not read the external Catalogue workspace in the browser, change Work JSON, introduce token syntax or extend into media sequences.
