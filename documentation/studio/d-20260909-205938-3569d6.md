# Catalogue Deployment

## Current Deployment Decision — 24 September 2026

Catalogue still needs its generated public consumer files copied into the required structure under `site/assets/data/catalogue/`. This is file distribution, with directory creation and reconciliation of the selected owned files. It does not require converting records into the legacy public Work/Series schema or refreshing document URLs inside that schema. The public destination and its copying operation remain pending under [Deploy And Public Cutover](d-20260915-100525-dd0aa1.md); no Catalogue files were deployed by this cleanup.

The UAC-1 pause protected the old Catalogue when it was frozen into `site/archive/` on 4 September. [Retire Public Document Locations](d-20260924-205346-c74d90.md) removes that obsolete URL-refresh machinery and its pause rather than resuming it. Docs Deploy Repo continues to distribute the complete Preview document snapshot independently. Refresh the older reader inventory below against current Work/Series/Gallery consumers when implementing Catalogue file deployment; the archive remains outside its ownership.

## Agreed Model

Catalogue represents the current Works, Series, Details and media. It has no per-record draft/published state, Series Publish action or separate accepted Catalogue snapshot. Studio owns canonical data and completes the affected generated output when a change is saved.

Document publication remains separate. Docs Publish accepts documents and their document-owned output; it does not freeze the Catalogue records those documents reference. A published document reads current deployed Catalogue data even when that data has changed since the document was published. If the change makes the authored commentary misleading, update the document deliberately. This is the curatorial policy in [Publishing workflow concept](/docs/?scope=studio&doc=d-20260906-141142-5200b2).

## Immediate Decision — Deploy Catalogue JSON To The Repo

Agreed on 2026-09-10: prepare the public Catalogue JSON projection under tracked `site/assets/data/catalogue/`, then use the existing explicit Git commit/push and Deploy Public workflow. The implemented Media View reader now defines exact Work, Series and thumbnail destinations below. Additional consumer indexes and the complete deployment inventory remain to be settled during deployment design.

The external `catalogue/generated/` tree remains Studio-owned current consumer output. Deploying a public copy into `site/` does not move that authority back into the repository or introduce a Catalogue Publish step. Local consumers continue to read external output directly. Public Work/Detail image bytes remain in R2, using the URLs supplied by Catalogue JSON; this decision does not require copying those images into the repo.

No performance, reliability or repository-capacity problem has been established that requires moving JSON to R2 now. Repo deployment is the selected approach, and R2 JSON deployment remains a future option. This records the destination decision; the Catalogue deployment operation is still to be implemented.

## Intended Deployment Flow

```text
Studio Save -> catalogue/generated/
            -> public JSON projection into tracked site/assets/data/catalogue/
            -> explicit Git commit/push and Deploy Public
            -> current Catalogue available to existing public documents

Analysis Published -> document projection into tracked site/
                   -> explicit Git commit/push and Deploy Public
                   -> accepted public documents
```

The deployment workflow may compose preparation of both projections, but their inputs remain distinct. Refreshing Catalogue must be possible without rebuilding or republishing unchanged documents. A Work, Series or Detail needs no companion document to exist or be available as Catalogue data. The accepted public document set remains authoritative for Catalogue-to-document links; Working document links must not leak into public output.

Local consumers read `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`. Public consumers read its deployed consumer projection. A local Save does not itself deploy the JSON to the public site. The public site has no deploy-time build: `site/` must already contain the prepared files before GitHub Pages deployment. Frozen `site/archive/` and its archived R2 media remain outside active Catalogue writes and cleanup.

## Repo Deployment And A Possible Future R2 Destination

External output separates data preparation and publication from the consumers that use it. The current and possible future access paths are:

| data | local consumer | public repo approach | possible future public R2 approach |
| --- | --- | --- | --- |
| Accepted Docs output | Read the scope's external `published/` snapshot directly when accepted data is required; local authoring retains its existing generated/stage reads. | Deploy the accepted snapshot into tracked `site/`, then release it through Git and Deploy Public. | Deploy the same accepted output to R2 and configure public readers to use it. Docs Publish keeps its existing acceptance role. |
| Current Catalogue JSON | Read external `catalogue/generated/` directly through the owning local reader. | Deploy a public projection into `site/assets/data/catalogue/`, then release it through Git and Deploy Public. This is the agreed next implementation. | Deploy a public projection from the same generated input to R2 and configure readers to use it. Catalogue gains no separate publication state. |
| Work/Detail image media | Load image bytes from the supplied R2 URLs. | Public JSON supplies the R2 image URLs; the image bytes stay in R2. | Continue using the supplied R2 image URLs alongside R2-hosted JSON. |

Local generated thumbnail copies remain available to their existing owners. Media View's required Work-thumbnail URL mapping is now fixed by route configuration, as listed below. The complete public thumbnail inventory, destination preparation and removal rules still belong to deployment design; this comparison does not authorize copying the entire external tree or changing selected-image sources.

| consideration | JSON deployed through the repo | JSON deployed to R2 |
| --- | --- | --- |
| Update lifecycle | Data updates use the established Git/site release workflow, while remaining independent of document Build and Publish. | Data can be released independently of website code and GitHub Pages deployment. This is useful when consumers need a shared online dataset with its own update cadence. |
| Change review and recovery | Git records exact deployed-source changes and supports review and recovery from an identified revision. | The deployment workflow must define equivalent change review and recovery for the public dataset. Uploading objects alone does not establish a reviewed release. |
| Repository growth | Generated JSON and repeated changes add repository size and history. This is a potential cost, not a measured problem requiring a migration today. | Keeps generated-data churn outside Git; storage and request costs still need to be considered. |
| Access by other consumers | Deployed Pages JSON is already readable by HTTP clients; browser consumers remain subject to cross-origin policy. | Provides a data-owned endpoint and object-storage tooling independent of the website. General HTTP readability is not unique to R2. |
| Performance and stability | Retains the current hosting arrangement; no observed failure or performance deficit has been established here. | No automatic improvement is assumed. Results depend on caching, request patterns and deployment behavior, and could be comparable or worse. Measurements would be needed to claim a gain. |
| Operational responsibilities | Reuses the existing site deployment and Git history. | Adds explicit data deployment, cache freshness, browser access configuration, removal rules and consistency between related objects. These need to be designed and maintained. |

Cloudflare supports edge caching for R2 through a custom domain, but JSON is not cached by default and needs an appropriate cache rule. R2 object operations are strongly consistent; a cached response can nevertheless retain an older object until expiry or purge. Cross-origin browser readers also need the intended CORS policy. These are delivery choices, not evidence that moving to R2 improves this site's performance or reliability. See [R2 caching](https://developers.cloudflare.com/cache/interaction-cloudflare-products/r2/), [R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/) and [R2 CORS](https://developers.cloudflare.com/r2/buckets/cors/).

The reason to reconsider R2 later would be a concrete need for independent shared-data releases, significant generated-data churn or measured hosting constraints. Conceptual tidiness alone does not require the migration. Website HTML, JavaScript and CSS could continue to use GitHub Pages even if public JSON moved to R2.

## Preserve The Deployment Boundary

Docs Publish owns accepted document output. Catalogue Save/Build owns current generated consumer output. Deployment owns the public projection, destination and transfer, and consumer configuration owns the endpoint used to read it.

Implement the repo destination behind that boundary. A later R2 move should primarily change deployment and consumer access configuration, including caching and related delivery policy. With the same payload contracts, it should not require changing authoring, document acceptance or Catalogue generation. This is a separation of responsibilities; the eventual migration need not be confined to a single source file, and no speculative second deployment implementation is needed now.

## Implemented Reader Boundary

[Catalogue Media View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) owns accepted Work/Detail/Series text links, Work/Detail image authoring and paginated Series galleries. The Series extension closed on 2026-09-12. Document Build retains exact Catalogue identity and authored text or image presentation fields. Inline images and selected Work/Detail presentations use current Catalogue consumer JSON; Series entry reads ordered membership and loads selected Works on demand.

The reader requirements are defined by `docs-viewer/config/routes/docs-viewer-routes.json` and projected into the public route config. Public browser URLs omit the leading `site/` from these destinations:

| required input | existing generated input beneath `catalogue/generated/` | tracked public destination |
| --- | --- | --- |
| Exact Work and its Details | `works/index/<work_id>.json` | `site/assets/data/catalogue/works/index/<work_id>.json` |
| Ordered Series membership and labels | `series/index/<series_id>.json` | `site/assets/data/catalogue/series/index/<series_id>.json` |
| Gallery Work thumbnail | `works/thumbs/<work_id>-thumb-96.webp` | `site/assets/data/catalogue/works/thumbs/<work_id>-thumb-96.webp` |

The route fields are `catalogue_paths.work_records_base_url`, `series_records_base_url` and `work_thumbnails`. Series IDs remain three digits and Work IDs five digits. The selected thumbnail variant is 96px, suffix `thumb`, format `webp`, matching the existing Catalogue producer. This gallery reader needs no complete Work index or separate Detail files, and no Series primary-image asset. It renders only the active page's thumbnails; selected image bytes continue to use Catalogue-supplied R2 URLs.

These reader paths are wired and tested, but the Catalogue deployment operation and public distribution remain pending. No public data or thumbnails were copied during the Media View delivery. Public records are revalidated with `no-cache`, with visible unavailable/retry behavior and protection against late responses; shared application-level caching/history remains separately planned.
