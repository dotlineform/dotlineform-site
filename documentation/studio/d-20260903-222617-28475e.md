# Catalogue Navigation

In the current public Catalogue, navigation between series, works and work details is built into the individual pages. When series and works are surfaced as documents in an Analysis sub-scope, this may not be the best design:

- for a normal sub-scope, there is no visible hierarchy. documents live in a flat structure.
- a flat index of series or works might be possible but would rely on search to navigate due to the large number of works.
- work details will not be represented comprehensively as individual documents.

## Scope And Ownership

The public document collection retains `analysis.works` and the name Works. [Catalogue Data Model](/docs/?scope=studio&doc=d-20260903-231534-b63aa9) owns the accepted subject fields, directly parseable composite Detail identity and Catalogue-owned membership; document `parent_id` does not define those relationships. These decisions do not settle the older document-navigation proposals below; [Concept](/docs/?scope=studio&doc=d-20260904-014334-f3dab5) owns the current Media View direction.

Series/Work previous/next and position/total belong on the sub-scope report's document toolbar. They change the selected sub-scope document.

[Catalogue Media Focus View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) owns a different implementation: its own previous/next and image position/total change the image and caption within the view, without changing documents. The gallery supplies an ordered image collection. The image view can be proved independently before real Catalogue galleries are connected; it must not wait for Series/Work document navigation.

[Nav Implementation](/docs/?scope=studio&doc=d-20260904-010247-b09f2e) records the current site's query, sequence and caching implementation and the proposed reuse for Docs.

## Membership Is Not Browsing Context

A Work's Series membership answers “which Series does this Work belong to?” It supplies a link to the corresponding Series document even on a direct Work visit, when that destination is available.

Gallery browsing context answers “which Series gallery am I browsing through?” It supplies the ordered Work sequence, position/total and return destination. Being a member of a Series does not automatically activate this context.

The existing URLs illustrate the distinction:

- `/works/?series=084&work=00520`: an exact Work plus explicit Series browsing context.
- `/works/?work=00520`: the same Work without browsing context.

Replicate those query-driven semantics using exact Docs Viewer document targets and optional gallery context. These legacy examples do not define the new URL syntax.

## Requirements And Acceptance Cases

1. **Gallery entry:** selecting a Work thumbnail opens the exact Work document with the originating Series document and gallery context. Its sub-scope report toolbar shows previous/next and position/total for that gallery, even though the gallery is no longer visible.
2. **Continued browsing:** previous/next follows the gallery's ordered Work sequence and cycles at both ends. Every destination retains the same context, rather than substituting another gallery or deriving a sequence from Work membership.
3. **Return:** the return link opens the originating Series document with its gallery page/context preserved. Exact scroll and focus restoration remain to be designed.
4. **Direct entry:** the same Work opened without gallery context has no sequence controls or counter. Its available membership-based Series link remains; following that link and selecting a thumbnail deliberately re-establishes browsing context.
5. **Portable context:** opening a context-bearing link in a new tab, copying it, reloading, or using browser Back/Forward preserves the selected document and its associated context.
6. **No stale context:** after contextual browsing, opening an unrelated direct Work link or Search result does not inherit the last-used gallery. A context-free URL remains context-free after reload.
7. **Media Focus round trip:** open a detail image from a contextual Work, traverse images and return. The Work's Series sequence, position and return link remain unchanged. Repeat from a direct Work: returning must not manufacture Series context.
8. **Invalid context:** invalid, unavailable or mismatched gallery context withholds sequence controls but leaves an otherwise valid Work readable. Do not silently substitute its membership-based Series as a browsing context.
9. **Unavailable documents:** missing or ambiguous Work documents remain clean unavailable gallery items, not broken links or automatically created documents. Build and Publish continue; the advisory coverage report prompts editorial follow-through.

The Work sequence comes from the accepted originating gallery, not the scope index, global Work order, visible DOM, Search results or document parentage. How unavailable Work destinations affect traversal and totals still needs an explicit rule; navigation must never invent a destination.

These are behaviour requirements and review cases, not a mandate for permanent browser tests. Deterministic route/context and sequence rules can be checked below the browser; presentation and interaction remain focused manual review.

## URL And History Requirements

Document identity and optional browsing context are separate route inputs. Preserve the exact selected sub-scope document, originating Series document and enough gallery identity to recover the accepted sequence and return destination. A Series ID alone is insufficient if a Series document can contain distinct galleries with different sequences.

Gallery and previous/next links must carry that context explicitly so opening in a new tab, copying the link and reloading can recover the same browsing mode. Browser Back/Forward must restore the selected document and its associated context. Do not rely on the browser referrer, an invisible last-gallery selection or mutable canonical Catalogue data.

Exact parameter names, encoding, gallery identifiers and accepted-payload lookup remain design decisions. Preserve existing document identity semantics, including the distinction between a report host and its selected sub-scope document; do not overload `subdoc` with gallery or image identity.

## Media Focus Boundary

Media Focus owns image traversal; the sub-scope report owns document traversal. While an image is focused, its controls describe only the image collection, not the Work's Series sequence. Retain the underlying Work document and optional URL context for return, and release focused-media state when navigating to another document. Preserving both contexts does not require a shared navigation controller.

## Remaining Design Decisions

- Exact query representation and how it resolves an accepted originating gallery.
- Navigation between Series documents, including how its browsing context is established.
- Treatment of unavailable Work destinations in sequences and totals, and single-item control presentation.
- Return-page, scroll and focus details, plus behaviour when a formerly valid gallery changes.
- How optional Work Detail documents participate in image galleries; they are not required for ordinary image traversal.

## Feature Boundary

Catalogue navigation builds on the accepted gallery and Media View data from [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea). Bulk source migration is abandoned and is not a navigation dependency. Batch New doc creates selected authored documents; their existence does not determine whether a Work or Detail can open in Media View. Ordinary document navigation remains distinct from image sequences.

[Doc Navigation](/docs/?scope=studio&doc=d-20260903-220300-694ee5) independently owns scope-level hierarchy traversal and sibling reordering. It neither supplies these Catalogue sequences nor blocks their implementation.

## Status

Proposed requirements. URL-carried gallery context, context-sensitive controls, cycling within the originating Work gallery and preservation across Media Focus are required. Exact query syntax and the remaining presentation choices are not yet frozen. No implementation is authorised here.
