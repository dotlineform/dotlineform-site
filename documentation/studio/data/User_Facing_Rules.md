# User Facing Rules

This reference describes the current Studio Catalogue and Docs Viewer system, inspected on 2026-10-12. Each rule starts with what the user can choose or do, then records the workflow consequence and the current enforcement point. Rule IDs provide stable references for examining what needs validation or enforcement, when it belongs and whether the frontend or server owns it.

On 2026-10-12 the user set the next direction: work through these rules and clean up their implementation before proceeding with incremental document Publish. The existing implementation is the review baseline, not a requirement to preserve every organically accumulated check or restriction. Agreed design conventions and possible UI improvements are identified separately from implemented behavior below.

Frontend means menu/action availability, editor choices and immediate feedback. Server means the owning local service, source writer or generator, including independently invoked maintenance commands. An editorial menu restriction is not automatically a server prohibition; a valid saved record is not proof that later media, generation or publication work completed. The tables distinguish these cases rather than prescribing new checks.

For each rule, distinguish a documented site-design convention, a frontend interaction choice, a necessary data/operation invariant and an obsolete mechanism. A design convention can be accepted without a hard-coded guard. A frontend/server difference is a decision to examine, not an automatic instruction to add server validation; changing the UI or removing redundant machinery can be the appropriate result.

Context is the displayed name of the configured `works` document collection. Catalogue Works, Studio Series and Galleries are separate from that collection's document Subjects. The public reader is read-only; the management rules below describe the local applications.

Studio owns canonical Work, Series and Gallery data, Catalogue authoring and Refresh. Docs Viewer owns document authoring, collection presentation, Catalogue document Regenerate and Publish. Their handoff is **Studio Save → Refresh Catalogue → Docs Viewer Catalogue Regenerate → Publish**; each application records its own responsibilities below.

For review, work through Studio and then Docs Viewer, taking Data rules before Manage rules within each part. Cite the affected rule ID, agree the intended rule and required responsibility, then specify each bounded cleanup or UI change. Record where any necessary check belongs and what failure means. The accepted rules and completed required cleanup become the prerequisite baseline for the Publish delivery.

The current frontend/server differences under D.03, M.02/M.03 and M.09 are explicit review inputs. Deciding whether to strengthen them, leave them as UI rules or change their workflow consequences is separate implementation scope. D.18 is an agreed convention requiring documentation only; broader bulk metadata editing remains a candidate. This document records behavior based on source inspection; it does not claim exhaustive manual UI or live failure-path verification.

## Studio

### Data Rules

#### Titles, Required Values And Identity

| Rule | What the UI allows or requires | Consequence | Current enforcement and timing |
| --- | --- | --- | --- |
| D.01 | Work titles may repeat. | Matching titles do not merge Works or make a Work invalid; exact Work IDs distinguish them. | Neither the Work editor nor the canonical validator imposes Work-title uniqueness. |
| D.02 | Series titles must be unique among Series; Gallery titles must be unique among Galleries. | A Series and Gallery may share a title. Within one type, case differences and repeated/leading/trailing whitespace do not make titles distinct. Saving a record with its own current title is valid. | Definition modals require nonblank titles; server create/save validates the proposed definition state. Uniqueness uses Unicode case folding and collapsed whitespace. The modal displays server conflicts; it has no separate uniqueness index or comparison. Explicit canonical validation also checks uniqueness; ordinary reads and Refresh do not repeat the audit. |
| D.03 | Single/New Work editing requires Series, Title, Year and Year display; New also requires an unused Work ID. Year must be a whole number; optional physical dimensions must be numeric when supplied. | Missing required values disable Save. The batch subfolder workflow supplies IDs and titles separately from its shared metadata. Other descriptive fields can be omitted. | The frontend field definitions and draft validator enforce these editor requirements. The server independently requires a valid existing Series and requires a nonblank Work title on creation. Its existing-Work save validator does not enforce nonblank Title, Year or Year display; see the enforcement distinction below. |
| D.04 | Work IDs identify records; an existing Work's ID is not editable. New may use a valid unused ID, including a deleted ID. | IDs survive title and membership changes. The suggested next ID is a default, not a reservation; a creation collision fails. Batch subfolder creation allocates IDs above the highest current Work ID and does not fill lower gaps. | Frontend ID suggestions/duplicate feedback; server create checks collision and save requires the submitted identity to match the target. Work IDs have canonical five-digit spelling. Series/Gallery identities also remain independent of their titles. |

D.03 records a current difference between UI requirements and server enforcement, not permission to clear required editor fields. [The Work frontend](../../../studio/app/frontend/js/catalogue-work-editor.js) checks required fields and numeric input; [the field definitions](../../../studio/app/frontend/js/catalogue-work-fields.js) declare required values. [Work mutation planning](../../../studio/services/catalogue/catalogue_source_mutation.py) requires Title for creation, while the shared [canonical validator](../../../studio/services/catalogue/catalogue_source.py) requires the Series reference but does not duplicate all editor requirements. This is a concrete boundary to examine before deciding which requirements should become server data invariants.

[Catalogue Save And Refresh](../Catalogue_Save_And_Refresh.md#save-boundary) owns title normalization and mutation validation. [Gallery validation](../../../studio/services/catalogue/catalogue_galleries.py) and [Series validation](../../../studio/services/catalogue/catalogue_source.py) are the current code owners.

#### Existence, Membership And Associations

| Rule | What the UI allows or requires | Consequence | Current enforcement and timing |
| --- | --- | --- | --- |
| D.06 | A Work must belong to exactly one existing Series. | Choosing another Series reassigns the Work; a Work cannot be saved with no Series or multiple Series. Browsing a Series does not by itself change a saved Work's membership. | Frontend membership picker and draft validation; server canonical validation checks one canonical Series ID and its existence before the mutation writes. |
| D.07 | A Work may belong to zero, one or several existing Galleries. | Clearing all Gallery pills is valid. Membership is independent of the Work's Series. Gallery IDs cannot repeat in one Work's membership set. | Frontend offers distinct saved Gallery choices; server membership validation rejects unknown Works/Galleries and duplicates at save. No membership entry means no Galleries. |
| D.08 | Empty Series and empty Galleries are valid. | Creating a definition need not create a Work. Removing the last Work or membership does not require a replacement or automatic definition deletion. | Definition services permit empty definitions; mutation owners retain them and queue their own affected output. Optional empty-Gallery cleanup asks the user to Delete or Keep. |
| D.09 | A Gallery can explicitly relate to a Series through “Relates to all works in this series”; the option needs an available Series context. | Series–Gallery relevance is optional and independent of direct Work membership. A related Gallery need not contain every Work in that Series. A Series can relate to several Galleries, and a Gallery can relate to several Series. | Frontend contextual checkbox; server saves exact existing Series/Gallery pairs and checks distinct valid relationships. ### Manage Rules

#### Authoring And Deletion

| Rule | What the UI lets the user do | Workflow consequence | Current enforcement and timing |
| --- | --- | --- | --- |
| M.07 | Save a changed single/New Work; unchanged drafts have Save disabled. Confirmed image regeneration and pending attachments also count as changes. | Save commits canonical metadata/membership, completes required staged media and queues known effects. It does not Refresh, Regenerate, build Search or Publish. A later local-completion failure leaves the canonical change saved and visible as incomplete. | Frontend dirty/valid/busy state; server revision checks, canonical validation, source transaction, media completion and queue persistence. |
| M.08 | OK in a Series/Gallery definition modal immediately saves that shared definition. | Creating a definition can add its assignment to the current Work draft, but Work Save persists that assignment. Discarding the Work draft does not undo the saved definition. A Gallery's Series-relevance checkbox is saved with its definition. | Frontend modal/draft owners; server definition mutations and revisions. Reader output advances later through Refresh. |
| M.09 | Bulk Work editing changes only Gallery membership; other metadata/media controls are read-only or unavailable. | The picker starts with the intersection of saved memberships. Saving replaces every selected Work's memberships with the final set; it is not an additive merge. An untouched selection preserves differences; removing all pills and saving clears memberships. | Gallery-only editing is a frontend restriction. The server bulk API also accepts its allowlisted metadata fields; it checks canonical validity, every Work revision and supplied prior membership before one combined write. |
| M.10 | Delete one or several selected saved Works after one confirmation of the exact IDs. | Delete uses current canonical records/memberships and retains Series/Gallery definitions, even if they become empty. It captures exact owned media deletion details; project originals remain. | Frontend confirmation; server rejects invalid/duplicate/absent IDs and validates the resulting state. Work deletion does not compare loaded Work/membership revisions. Queue/local cleanup completes after canonical deletion. |
| M.11 | Delete a Series only when it has no saved member Works. | Reassign or delete its Works first. Deleting an empty Series removes its explicit Gallery associations, not the Galleries or their Works. | Frontend disables Delete with a reason; server rechecks the Series revision and empty membership before writing. |
| M.12 | Delete a Gallery even when Works belong to it, after confirmation of the affected membership count. Removing a pill alone only edits the current Work draft. | Definition deletion removes that Gallery's saved Work memberships and explicit Series associations without deleting the Works. No subsequent Work Save is needed to complete the canonical deletion. Empty-Gallery cleanup remains an explicit Delete/Keep choice. | Frontend modal/confirmation; server checks the definition revision and current expected member IDs, then writes the affected canonical maps together. |

M.09's current [bulk service](../../../studio/services/catalogue/catalogue_bulk_service.py) accepts supported Work metadata such as Series, Title and Year through `set_fields`, although those controls are absent from bulk UI. The distinction is part of the current enforcement inventory; it does not authorize restoring those UI fields or removing service behavior without separate scope.

Possible UI improvement raised on 2026-10-12: allow editing other Work metadata while bulk-editing Gallery assignments. This is a candidate for the cleanup review, not implemented or an approved field list. Resolve which fields are useful, how mixed saved values are presented, and how the user explicitly chooses replacement or clearing. Untouched metadata should retain each Work's saved values; opening bulk mode must not silently copy one Work's metadata to all selected Works. Keep the existing Gallery replacement semantics distinct from those metadata decisions.

[Catalogue Work Editor](../Catalogue_Work_Editor.md#bulk-editing) owns single/bulk and definition workflows. [Work/Series delete planning](../../../studio/services/catalogue/catalogue_delete_plans.py), [Gallery mutations](../../../studio/services/catalogue/catalogue_gallery_service.py) and [Series management](../Catalogue_Series_Management.md) own the deletion boundaries. [Catalogue Save And Refresh](../Catalogue_Save_And_Refresh.md) owns completed canonical writes and subsequent queue/media handoffs.

### Manage Rules (Including Publish)

#### Document Menu Availability

The [frontend action registry/resolver](../../../docs-viewer/runtime/js/management/docs-viewer-action-definitions.js) supplies one visibility/enablement result to menus, shortcuts and collection actions. The following are editorial rules; temporary source-editing, loading, service and busy conditions can additionally disable an otherwise available action.

| Rule | UI target and available/restricted actions | Workflow consequence | Current responsibility |
| --- | --- | --- | --- |
| M.01 | Ordinary documents normally offer Source editing, Rebuild, source opening, Draft, Star, Copy link and the applicable Index operations. Non-Catalogue collection documents offer applicable flat-collection controls. | Ordinary subtree actions and collection exact-target actions have different scopes; the target is the invoked item, which can differ from the displayed document. | Frontend action/context/control owners select the affordance; server operations resolve exact configured targets and their concrete write requirements. |
| M.02 | Configured collection report hosts have no Delete, Draft or Star menu option. Source editing, Open in VS Code and Rebuild remain available. | The menu treats these hosts as maintained site structure. Hidden Draft does not remove the source's boolean field or its effect on publication. | Frontend restriction, keyed by configured host IDs. There is no matching server editorial-policy guard; direct Source Save and other concrete operations retain their own validation. |
| M.03 | The explicitly registered private-report document IDs have no Delete, Draft or Star option. | Protection is based on the action registry's exact identities. A new/unlisted public report has ordinary defaults, including Star; report type alone does not confer the restriction. | Frontend explicit private-report set. Server validation does not reproduce that editorial list. |
| M.04 | Catalogue Work documents offer only Star and Copy link. The Catalogue collection omits independent New/Delete and package/selection controls; Regenerate remains available. | Work edits, Refresh and Regenerate own the normal Catalogue document lifecycle. Source editing/opening, individual Rebuild and Draft are absent from the document UI. | Frontend editorial availability. Separately, the server's concrete Draft/source contract rejects a Catalogue draft field and the document-delete routes require Catalogue deletion through Regenerate. Direct permitted Source Save/build callers still contribute their completed document-only publication handoff. |
| M.05 | Workspace Import, Export, Rebuild, Publish and Settings remain available independently of the displayed document's editorial restrictions. | Displaying a protected host or Catalogue Work does not remove workspace operations. Their own capability/selection/busy requirements still apply. | Frontend workspace action/control gates; each server operation owns its request and execution requirements. |
| M.06 | Package selection can be entered with no checked collection rows; Prepare requires a nonempty supported selection. | Entry to selection mode is separate from preparing a package, and does not grant write authority to Review. | Frontend selection/capability state; server package owner validates the exact supported collection/profile and preparation inputs. |

M.02 and M.03 apply to the directly resolved menu target. They do not establish a rule protecting every descendant of another permitted target. Ordinary Delete expands the selected subtree; its current server planner does not check that expansion against the host/private-report editorial lists. Deleting an ancestor can therefore select those structural descendants. Likewise, Source editing remains available for a host/private report and the server does not prohibit a valid draft change merely because the Draft shortcut is hidden. These are current enforcement distinctions to examine, not new protection requirements introduced here.

[Docs Viewer Runtime](../Docs_Viewer_Runtime.md#document-action-policy) owns availability and transient controls. [Document mutation planning](../../../docs-viewer/services/docs_management_mutations.py), [management routes](../../../docs-viewer/services/docs_management_service.py) and [Draft writes](../../../docs-viewer/services/docs_management_draft.py) own the separate concrete service requirements. Menu restrictions must not be described as endpoint authorization.

Catalogue Regenerate receives the completed Studio Refresh handoff under M.23. [Catalogue Deployment](../Catalogue_Deployment.md) owns Catalogue publication behavior. Exact Publish behavior is owned by [Publish orchestration](../../../docs-viewer/services/docs_publish.py), [Preview preparation](../../../docs-viewer/services/docs_prepare_preview.py), [snapshot completion](../../../docs-viewer/services/docs_preview_snapshot.py) and [distribution](../../../docs-viewer/services/docs_deploy_repo.py).

Current Publish still reads the eligible ordinary/collection corpus and validates prepared data/snapshot output.
