# User Facing Rules

This index compares the target behavior for Studio and Docs Viewer with the current implementation inspected on 2026-10-12. The target column defines what the system should do; the **Current frontend (UI) behavior** and **Current server behavior** columns describe what the code currently does. **Gap** identifies a confirmed difference requiring review or a delivery decision. Current behavior is based on source inspection, not an end-to-end verification claim. Retained targets remain available for review; explicitly open choices are identified below. **Status** tracks the entry-by-entry work: **Review pending** means the entry has not yet been agreed in this review; **Gap** means a known implementation difference remains; **Decision open** means the behavior still needs a choice; **Implemented; manual check pending** means code and focused checks are complete, with the UI workflow still awaiting user confirmation.

Each application has three subsections: **Data Model Rules**, **Authoring Guidance** and **Manage Workflows**. In the target model, data model rules describe valid identities, representations and relationships. Each entry identifies the integrity boundary: the UI validates choices available in its loaded data, while the server owns the stated persistence and operation checks. Downstream operations consume completed handoffs without repeating complete audits. Authoring guidance describes preferences, warnings and consequences that help the user work with valid data; the frontend owns that feedback. A preference or documented design convention does not become a data invariant merely because the UI uses it.

Target responses are explicit: **reject** invalid model state or an invalid operation; **warn** about an authoring concern while allowing the user to proceed; **inform** about a consequence or convention without adding validation. The UI owns authoring validation within its loaded data; the server retains minimal persistence integrity without repeating that validation or auditing the whole Catalogue during Work writes. The server also owns valid, confined execution and required file/media processing; these are operation requirements rather than duplicate enforcement of authoring preferences.

Existing entry IDs are retained across classifications. The subsection determines an entry's meaning; the historical D/M prefix does not determine ownership. A model reference repeated under Authoring Guidance describes its consequence or interaction, not another invariant. D.19 makes document identity explicit as a model rule, separately from document-title guidance.

Studio owns canonical Work, Series and Gallery data, Catalogue authoring and Refresh. Docs Viewer owns document authoring, collection presentation, Catalogue document Regenerate and Publish. Their handoff is **Studio Save → Refresh Catalogue → Docs Viewer Catalogue Regenerate → Publish**. Context is the displayed name of the configured `works` document collection; its Subjects are independent of Studio membership.

Review and agree entries individually, implementing finishable changes as the review progresses and updating their current behavior and Status here. Keep a compact implementation/check/review record for a small completed change; use a grouped delivery when related entries need one larger outcome. Detailed inventories and execution evidence belong to that delivery when one is needed. Maintain this comparison after implementation and link an agreed delivery from its affected group.

The target review and required cleanup precede [Incremental Document Publish](../deliveries/Incremental_Document_Publish.md). Implementation proceeds for the entries agreed in this review; the remaining targets retain their recorded review status.
