# User Facing Rules

This is the active Docs Viewer review. [Studio User Facing Rules](Studio_User_Facing_Rules.md) retains the Studio review, agreements, implementation records and pending manual checks. The tables compare target behavior with inspected frontend/server behavior; they do not claim end-to-end verification.

The review continues to identify and remove unnecessary server calls, repeated checks and unnecessary server validation. The frontend owns choices and authoring feedback it can resolve from already loaded data. Server operations consume those choices and completed upstream handoffs without repeating that work. Required parsing, configured path confinement and actual file/media/transfer failures remain execution concerns.

Docs Viewer must use Refresh-owned generated Catalogue data and assume it is valid, without calling the Studio API, reading canonical Catalogue data or rechecking that handoff. Studio Save is the canonical mutation boundary; Refresh generates and copies the selected files and updates pending queues on that basis. A downstream need for Studio/canonical access is redundant or exposes a genuine Refresh gap to fix at its owner. The handoff remains **Studio Save → Refresh Catalogue → Catalogue Regenerate → Publish**.

Publish must likewise trust the validity and consistency of the artifacts and effects it is asked to publish. Previous document Imports, Saves and Builds own mutation and generation; Publish assumes no external mutation outside those processes and does not repeat their validation or discover and repair outside edits. Deliberate external edits require an explicit owning Build.

First review and remove unnecessary Docs Viewer and Publish work; then extend the existing incremental Catalogue publication to the whole corpus through [Incremental Document Publish](../deliveries/Incremental_Document_Publish.md). These principles guide the review; the current-behavior columns retain outstanding implementation differences.

Review entries individually or as finishable functional groups and update their behavior, status and focused implementation evidence. Data Model Rules describe identities, representations and relationships; Authoring Guidance describes frontend feedback and conventions; Manage Workflows describe operations. Entry IDs stay unchanged across the split. Context is the configured `works` collection; its Subjects are independent of Studio membership. **Review pending** means not yet agreed; **Agreed; no code changes** means existing behavior satisfies the agreed entry; **Gap** identifies an implementation difference; **Decision open** needs a choice; **Implemented; manual check pending** retains its manual verification gate.
