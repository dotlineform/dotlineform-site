# Test Contract Discipline

Tests are maintained software with implementation, runtime, resource, token, and diagnosis costs. They implement an agreed test specification; they do not establish product requirements by accident.

## Principle

Approval of a feature or bug fix does not authorize test creation or maintenance. New, changed, refactored, expanded, or deleted tests require an agreed test specification before implementation. Fixtures, harnesses, assertions, collection membership, and temporary regression scripts are part of that work. Calling a script a probe or one-off check does not remove its cost or the need to agree its scope.

The specification can be short for a small test. A coherent test collection can share one specification with clearly mapped cases; a separate document per assertion is unnecessary. Existing approval covers work within the agreed specification, so do not repeatedly request permission for its implementation steps.

A proposed test must be traceable to one of:

- an explicit requirement
- a confirmed bug
- a documented invariant
- a stable integration boundary
- a safety property that would be expensive or risky to verify manually

Traceability is necessary but does not itself authorize implementation. A confirmed bug is a reason to consider a test, not an instruction to create one automatically.

## Specification And Durable Coverage Record

Keep the specification and maintained coverage description under [Testing](/docs/?scope=studio&doc=d-20260501-174746-efd581), or the durable documentation for the owning app/domain, outside the Planned Features and delivery hierarchy. The same document may hold the approved specification and implemented coverage when their status is explicit. Test delivery plans and ordinary feature deliveries link to it; delivery logs are not its only home.

Document these points before implementing test work, then reconcile them with the delivered code:

| Item | Required description |
| --- | --- |
| Purpose and authority | The agreed behavior, concrete regression or failure, and why automation is worth its cost compared with existing evidence or manual review. |
| Scope and identity | Owning app/domain, exact files and test selectors, cases or parameter groups, and explicit additions, changes, or removals. A collection lists its members or an exact selection rule with exclusions and links to their coverage records. |
| Scenarios and assertions | For each case or coherent case group, the input and precondition, action, expected result, and observable assertion. State which error/write paths are exercised. |
| Test environment | Fixtures, mocks, substitutes, setup, dependencies, real components exercised, and differences from production. |
| Side effects | Files or generated output written, external workspaces, network/services, credentials or permissions needed, and cleanup ownership. |
| Coverage limits | What a pass proves, what it does not prove, and any manual acceptance still needed. |
| Operation | Exact run/selection command, when running is useful, output location, and how to interpret a failure. |
| Costs and limits | Expected authoring/review/maintenance effort, setup and runtime, compute or network use, token/context and diagnosis overhead, and a reasonable run/repeat budget. Use rough estimates or state unknowns; do not benchmark just to populate the record. |
| Acceptance and state | Approved proposed scope, completion criteria, and the implemented coverage or unresolved differences. Keep proposed, implemented, and unreviewed coverage distinct. |

A test name, count, source file link, or green profile result is not a coverage description. Collection documentation must reveal incidental work such as full builds, Search regeneration, browser/server startup, and real workspace access. Code and current runner selection must agree with the record; a description does not manufacture coverage that the test lacks.

This policy does not certify existing collections or start a repository-wide inventory. Review and document a bounded existing selection when it is needed; larger documentation or redesign work needs its own scope. Describing existing behavior read-only does not approve that behavior or authorize test edits.

## Test Failures

A failing test is not automatically a code requirement. First decide whether the test still describes agreed behavior and whether the failure comes from the product, fixture, or environment.

Ask:

- Is this behavior still desired?
- Is the test asserting implementation detail instead of product behavior?
- Is it preserving a fallback or compatibility path we do not want?
- Is it testing a scenario that was never agreed?

Only change production code when the behavior belongs to the authorized product work. If the test needs updating or deleting, record that proposed work in its specification and obtain approval unless it is already covered. Do not silently widen the fix, preserve obsolete behavior, or change expectations just to make the run green.

## Fallbacks

Fallback behavior requires explicit acceptance.

Tests must not create or preserve fallback behavior just because a fallback is easy to assert.
If a fallback is necessary, document:

- why the fallback exists
- what user or data condition it supports
- how it fails closed
- when it can be removed

No fallback means no fallback test.

## Scope

Prefer small, named contract tests over broad narrative files.

A good test file should make it obvious what contract it protects.
If a test file mixes parser rules, UI preview behavior, current-source lookup, filename generation, malformed input handling, legacy packages, and route behavior, propose a bounded split or deletion in its test specification.

For browser tests, one file owns one route or integration boundary. Executable smokes must not be imported as fixture libraries. Move only genuinely shared server/readiness mechanics into a small non-executable support module.

A browser script over 500 lines or spanning multiple route/workflow owners triggers a mandatory deletion/split review. Review the assertions individually: retain only assertions that prove the named boundary and move deterministic behavior to a lower layer when it still warrants automation.

For parser and import contracts, keep tests focused on:

- required metadata
- supported profile ids
- rejected unsupported profile ids
- accepted sparse returned changes
- security boundaries such as unsafe paths
- file-level parse blockers

Do not use parser tests to preserve old package shapes, legacy aliases, UI copy, or incidental preview formatting.

Do not compare report descriptions, menu labels, success messages or rendered UI text as permanent test expectations. Retain assertions for exact data identities, generated schemas, service requests/responses and route/module ownership. Authored document content remains data when testing parsing or export preservation. Presentation, wording and layout belong in manual review.

## Running Tests

Test development and test execution are separate decisions. Run an existing test only when its actual coverage is understood, it addresses a concrete risk in the current work, and its cost fits the accepted verification budget. Ordinary focused lint, syntax, whitespace, source/output inspection, and existing direct diagnostic commands can provide evidence without writing new tests.

Before a non-trivial run, identify the exact existing selection, its coverage record, the relevant failure it can detect, setup and side effects, estimated cost or unknowns, and the reason this evidence is sufficient. A short note is enough for a small selection; do not create another planning exercise to run a cheap understood check.

Do not run route smokes, API suites, or browser checks for a parser-only edit unless the changed behavior crosses that boundary.
Broad checks are useful when a boundary changes, not as a reflex after every local change.

Broad pytest profiles must not collect smoke scripts. Smoke profiles are explicit boundary audits and are run only when one of their named boundaries is at risk.

Stop when the agreed evidence is sufficient. Repeat or expand only for a changed implementation, a failure, or a newly identified unresolved risk. Do not run a profile merely because it exists, is called quick, or a delivery is closing.

A documentation-only or trivial change may need no executable tests. Complete an otherwise authorized fix using proportionate available evidence; an unapproved test proposal is separate work unless the user has made it an acceptance requirement. State any material coverage limitation rather than creating tests to eliminate every uncertainty.

## Legacy Tests

Older tests may not meet this standard. Mark undocumented or unexplained coverage as unreviewed; do not treat its presence as evidence of value or approval to extend it.

When a legacy test fails, decide whether it describes a still-valid contract before changing anything. If it preserves an accidental assumption, propose its removal or rewrite as scoped test work. Do not turn a product fix into an unrequested test cleanup or catalogue audit.
