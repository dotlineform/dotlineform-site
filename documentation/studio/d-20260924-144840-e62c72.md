# Document Action Context And Toolbar Placement

One bounded delivery under [Planned Features](d-20260428-000000-f5ff18.md). Status: **proposed; implementation has not started**. The main outcome is consistent action context through the existing document/report integration. Toolbar placement is the visible result of that refactor. The next step is a concise readiness review of current target handoffs and control resolution.

This delivery supersedes [Scope-configured Authoring Controls](d-20260910-151840-671351.md). The current single workspace needs a consistent way for existing controls to receive the displayed document, containing collection and applicable navigation context. The older proposal's per-scope availability configuration and Search/Find copy changes are not part of this delivery. Its completed breadcrumb removal remains in place.

## Requirements

The current split is deeper than button placement. Collection Edit and Delete receive the same underlying document identity through different integration paths. Edit consumes the collection report state forwarded into Manage and its common control resolver; Delete receives the target directly in the report's detail-toolbar contribution. New receives the collection target, because no document exists yet. Delete's operation is already management-owned; the report supplies its target, button mount and reconciliation callback.

The primary acceptance criterion is **one consistent resolution of the active document and collection context for the affected controls, independent of where their buttons are rendered**. Consolidate the duplicated handoffs and view-dependent target selection through the existing integration. Merely moving buttons while retaining separate target-resolution paths does not complete this delivery.

### Action Context

| Control | Context it needs |
| --- | --- |
| Edit, Delete, Draft/Ready and Copy Link for a displayed document | The exact current document target, including collection identity when applicable |
| New collection document and other whole-collection actions | The exact containing collection target; New has no existing document target |
| Actions on checked rows | The explicit current selection within its exact collection |
| Back from a collection subdocument | The current collection's return-to-list operation |

The displayed view supplies its validated document/collection state. The existing control integration resolves the appropriate context once for consumers. Management workflows retain operation-specific capability checks, service calls and outcomes; the toolbar presents the resulting controls. The report retains list membership, navigation, filtering, sorting and reconciliation after creation or deletion. These are responsibilities of the existing code, not a new ownership layer or persisted context store.

The visible acceptance criterion remains **a consistent subdocument Back position: the leftmost control in the top document row, aligned with the left edge of the document view, in Manage and Published**. Its position must remain stable as other buttons appear, disappear or wrap. When Back is the only available button, it stays at that left edge. The top document row is the action row above the displayed document, rather than the page-wide Home/Search/theme controls.

### Placement

| Context | Top document toolbar | Beside the collection or report |
| --- | --- | --- |
| Ordinary document | Its existing document actions | No additional document-action toolbar |
| Collection subdocument in Manage | Back at the left edge, followed by available document actions such as Edit, Source, Draft/Ready, Copy Link and Delete | Subdocument content; no duplicate action row |
| Collection list | Existing host-document actions and available collection actions such as New, Regenerate and Actions | Search, filters, A–Z/date sorting, and row selection controls |
| Published collection subdocument | Back in the same left-aligned position, plus applicable reader controls | Subdocument content; no duplicate Back button or empty toolbar |
| Other embedded reports | Existing document actions | Their existing report controls remain with the report |

The table specifies placement, not new capabilities. Existing route, stage and action availability remain authoritative. Shared placement does not turn collection actions into ordinary-document actions or add management controls to Published.

### Behaviour To Preserve

- Document actions use the consistently resolved displayed-document context. Collection detail targets include the exact collection and document identity; resolution must not substitute the outer report host, a checked row or an unrelated selection.
- Collection-list actions retain their collection or explicitly selected-document targets. Host-document actions and collection actions can share a row while retaining those distinct meanings.
- Back calls the collection's existing return-to-list operation, preserving filter state, sort state, scroll position and focus. Other existing Back operations, such as returning from content detail, keep their own destinations; the collection Back must not override them.
- List/detail transitions, loading, errors, Source editing, refresh and leaving the report update the action context and visible controls together through the existing lifecycle. Old targets and duplicate buttons must not survive a transition. Document actions require a valid current target, and an operation or Source session retains the exact target with which it started.
- Button labels, keyboard operation, disabled/busy state and service restrictions remain intact. Public Back remains shared reader behaviour without importing management code.
- Empty action groups leave no separators or empty second toolbar. Search, filters and sorting retain their current behaviour beside the collection list.

## Deliverables

- A focused refactor consolidating the active document/collection context consumed by the affected management and report controls, with one consistent target-selection and lifecycle handoff through the existing integration.
- Removal of the superseded duplicate target plumbing and per-control view-resolution branches within this boundary, while retaining operation-specific validation and capability checks.
- Consistent top-row placement for the existing collection list/detail action buttons and subdocument Back in local and public readers, retaining search, filters and sorting beside the collection list.
- Removal of the replaced inline action mounts and their placement-only styling where no longer used.
- The required tracked public runtime projection and a concise update to the durable [Docs Viewer Runtime](d-20260331-000000-c313fd.md) description when implementation ships.

### Refactor Boundary

Build on the current [report control resolver](../../docs-viewer/runtime/js/management/docs-viewer-management-report-controls.js), report-state handoff, [shared collection report](../../docs-viewer/runtime/js/shared/docs-collection-report.js), [management collection composition](../../docs-viewer/runtime/js/management/docs-viewer-management-collection-composition.js), and top document toolbar. The report already publishes its list/detail state and exact target; Edit and Delete do not need independent identity discovery. Use that existing source of truth consistently.

Preserve the meaningful boundaries between view state, management operations and report reconciliation while simplifying the wiring between them. Existing function/module placement is not a requirement to retain duplicate plumbing. Resolve the active context and control targets once at the existing integration boundary; renderers and operation callbacks consume that result. A focused helper within that responsibility is appropriate if it removes repetition. Avoid collection-name checks, route guesses, DOM-position inference or repeated list/detail target and placement conditionals across individual buttons and unrelated controllers.

This delivery adds no ownership layer, toolbar framework, placement configuration, per-collection control policy or availability system. It does not change search coverage, Recents, editorial stars, document data, action semantics or the broader page layout. Shared top-row placement does not require the code's ownership boundaries to become visible groups in the UI.

## Process

1. Open an ordinary document. Its validated document context supplies the existing top-row actions.
2. Open a collection report. The active context identifies both the report host and its collection, so host-document actions and collection actions receive their respective targets. Search, filters and sorting stay beside the list.
3. Open a collection subdocument. The active document context changes to that exact child, and document controls consistently consume it. Back appears at the left edge of the same top row with the collection's return operation.
4. Use Back to return to the retained collection list. The action context and top row return to their list state together, and the local search/filter controls are available again.
5. In Published, use the same Back position while only reader capabilities are available.
