# Semantic Tokens In Links View - Delivery

## Superseded

The direction changed on 2026-09-13. [Info Panel Related Links And Pinning - Delivery](/docs/?scope=studio&doc=d-20260913-151251-cbee5b) replaces this plan: semantic tokens contribute exact document connections, all Links/Info entries open documents, Info gains compact Related links and pinning, and Links View retains its existing grouped Manage-only presentation.

Implementation of this older delivery never started. The media entries, document/media icons and Media View → Links return sequence below are historical requirements and must not be implemented. The replacement delivery owns the current requirements and next readiness gate. Broader Media View hierarchy navigation remains separate follow-on work.

## Historical Requirements

Complete one outcome: the **Works** section in Links View combines existing document links with relevant Work, Series and Detail media destinations. A media entry opens the exact Catalogue target in Media View, replacing Links View; its outer Back action restores the invoking Links View. Document entries retain ordinary document navigation.

The requirements were agreed on 2026-09-12. Implementation has not started. The next step is **STLV-0 — Readiness**. [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea) is the feature parent; [Links View](/docs/?scope=studio&doc=d-20260910-202325-53b5f9) is the primary durable destination at closeout.

### Selection And Exact Identity

- Include every distinct supported Catalogue target mentioned by a semantic token in the current document, regardless of that document's Subject. Both Media View text links and Catalogue images contribute.
- Include targets mentioned elsewhere only when they match the current document's valid normalized Subject. Search the current scope/stage's shared usage index, including its configured child collections; preserve exact source identity `{scope, stage, sub_scope, doc_id}`.
- Match typed identities exactly: Work Subject to the same Work primary target, Series Subject to the same Series target, and Detail Subject to the exact Work/Detail identity. A Detail token's owning Work ID does not make it a Work-primary match. Series membership and Work ownership do not expand this selection.
- A document without a valid Catalogue Subject receives its own token targets only. Folder Subjects and document titles do not supply Catalogue identity. A report host does not substitute for the displayed child document.
- Body tokens remain mention evidence; they do not assign Subjects or create document relationships. Reuse the existing token-usage inclusion rules without adding publication-flag or draft filtering.

For example, Doc A contains a token for Work 00523, and Doc B has Work Subject 00523. Links View for B includes one media entry for Work 00523 even if B contains no token itself. A token for another Work in A does not appear in B's Links View. B's own tokens still contribute independently. A Detail of 00523 requires that exact Detail Subject to qualify through another document.

### Works Presentation

- Combine incoming/outgoing document entries as today, and add media destinations to **Works**, including Series and Details. Existing document classification and the Concepts/References sections retain their current rules.
- Deduplicate media entries by exact typed Catalogue target. Repeated occurrences, image/text forms and matches from both selection paths share one media entry. Individual occurrences remain intact in the Semantic Tokens report and usage index.
- Keep document and media identities separate. A document link and media link with the same displayed title both remain visible; different Catalogue targets with the same title also remain distinct.
- Use Catalogue titles for consolidated media entries rather than choosing among authored occurrence labels. Include the selected Detail identifier in a Detail label. Authored token labels remain unchanged in source and usage data.
- Prefix document entries with a document icon and media entries with an image/media icon. Expose the destination meaning in accessible link names as well. Reuse current icon primitives where suitable; this delivery does not require completion of the separate [Shared Icons](/docs/?scope=studio&doc=d-20260910-223116-9a1011) feature.
- Sort the combined entries A–Z by displayed title with a deterministic identity tie-break; icons and destination kinds do not create separate priority groups. Hide a section only when its combined result is empty.

### Data Ownership And Read Boundary

The semantic-token owner retains one scope/stage `semantic-tokens/index.json`, as described in [Semantic Tokens Architecture](/docs/?scope=studio&doc=d-20260714-234030-434069). Add a focused read path that selects the current document's targets and exact Subject matches from that index. Links View consumes those results alongside its existing document-link response; filtering belongs to the reader/presentation owners rather than the route shell.

Keep `links-by-id/<doc_id>.json`, aggregate `links.json` and their builders unchanged. Add no stored Work/Series/Detail lookup files, per-document token store, source scan, refresh operation or token-to-document relationship maintenance. The focused token read does not need the report reader's source-title and source-navigation enrichment. Resolve Catalogue labels and media through the current Catalogue provider without loading every referenced full image or every Series member's Work record merely to list links.

Read from the configured owners only. Missing data and unavailable Catalogue targets retain explicit failure feedback and exact identity; reads do not rebuild, repair, choose another target or search another scope/stage. Do not treat an unavailable input as evidence that there are no matches.

The delivery applies to the currently enabled **Analysis Working Links View**, including child documents. Public Links activation and a public token-reference projection remain separate. Shared runtime changes must preserve the public composition's isolation from local usage data and services, and follow the existing canonical-to-site code projection rules.

### Media View Return Context

Selecting a media entry replaces Links View with the exact Work, Detail or Series gallery in the existing Content Detail host. Catalogue data and target selection retain their existing owners. Media View requires no corresponding document for the Catalogue target; the underlying document identity belongs to the invoking Links context.

The outer action is **Back to Links** for this entry path. Restore the same Links presentation, scroll position and invoking entry focus without an intermediate document display. Links View's own **Back to document** then restores the original document or exact child and its original position. Existing navigation within a Series gallery keeps its current behavior and does not replace the outer Links return destination. Direct Media entry from document content continues to return to that document.

Keep this return context within the existing hosted-view lifecycle and clear it when the owning document/child context is released. Failed or superseded media reads must not replace the selected Links presentation or restore a stale document context. This bounded nested return does not implement page-session data caching, browser Back/Forward, shareable URLs or a general navigation stack; [View Caching and History - Delivery](/docs/?scope=studio&doc=d-20260910-193232-e511cd) owns those shared defaults. Reuse that delivery's owners if they have shipped before this work starts.

- [ ] A combined Works presentation with typed target deduplication, Catalogue labels and distinct accessible document/media icons.
- [ ] Exact Media View activation and return-to-Links behavior through the current host, retaining document/child identity and existing gallery navigation.
- [ ] Focused contract evidence, manual interaction review, code review and any required tracked public-runtime projection.
- [ ] Durable transfer to Links View, with concise Semantic Tokens Architecture or Catalogue Media View updates only where their owned contracts change.

## Process

1. Author supported semantic tokens and assign document Subjects through the existing workflows. Ordinary Save/Build maintains the shared token index.
2. Open Links for the displayed document or child. The reader combines that document's own token targets with exact Subject matches elsewhere in the current scope/stage.
3. Review Works alongside the existing sections. The icons distinguish ordinary document destinations from Media View destinations, including entries with identical titles.
4. Select a media entry to open its exact Work, Detail or Series gallery. Use existing gallery controls where supplied.
5. Use Back to Links to restore the same list and position, then Back to document to restore the invoking document. Selecting an ordinary document entry retains ordinary document navigation.

## Follow-on

### Media View navigation

Future Media View navigation may expose a Work's Series gallery, a Detail's owning Work-details gallery, and a path from that gallery to the Work. The intention is to navigate the Catalogue hierarchy within one Media View session regardless of entry point. The previous Series gallery delivery intentionally stopped short of that complete hierarchy; this delivery only preserves its outer Links return context while using navigation already available.

### Per-token lookups

Generated per-target token lookup files can be reconsidered if measured usage volume or read cost warrants them. Any such files should remain derived from the existing token owner and preserve exact Work/Series/Detail identities. 

If volume eventually warrants generated lookup files, favour one consistent structure, e.g.

```
semantic-tokens/by-target/work/00523.json
semantic-tokens/by-target/series/143.json
semantic-tokens/by-target/detail/00523-015.json
```

Those would be derived lookup files maintained by the existing token builder. Separate whole-index files for Work and Series still require loading a whole category and don’t cover exact Detail identity.
