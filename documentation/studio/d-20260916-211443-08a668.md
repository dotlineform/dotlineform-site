# Catalogue Work Record Regeneration

## Purpose And Status

The Catalogue collection surfaces existing Works owned by the Studio Works editor. Studio owns Work creation, metadata and generated Work JSON. Docs Viewer owns the documents that present those records, with Regenerate as their creation and maintenance action.

The first version uses one body generator defined in code. It reads a Work's generated JSON and produces an existing Catalogue image token containing the exact Work identity and resolved presentation text. There are no Markdown template files, JSON field-definition files or new template tokens. Changing the body structure or selected metadata means changing the code and regenerating the documents.

Delivery is complete and was accepted for closeout on 2026-09-17. The normal Regenerate action creates and maintains Catalogue documents from Studio-generated Work data; manual Catalogue New is removed. The initial run created 100 documents, a subsequent run selected those 100 for regeneration, and the full run created 1,834 further documents while skipping the 101 existing documents. The generated collection manifests contain 1,935 records. Modal corrections and retained list navigation are delivered. [Runtime](d-20260331-000000-c313fd.md) and [Collection architecture](d-20260728-113139-763354.md#catalogue-work-records) own the maintained behavior; [Semantic Tokens Architecture](d-20260714-234030-434069.md) owns the existing image-token behavior used here.

## Ownership And Inputs

| Owner or input | Responsibility |
| --- | --- |
| Studio Works editor | Creates and edits Works and produces their generated Catalogue data |
| `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/works/works_index.json` | Supplies the Work set for Regenerate |
| `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/works/index/<work_id>.json` | Supplies each Work's current title, summary metadata and media |
| Docs Viewer Catalogue generation code | Defines the document body, summary formatting and image presentation |
| `$DOTLINEFORM_DOCS_BASE_DIR/working/source/collections/catalogue/documents/<doc_id>.md` | Stores each document's identity, Work association, publication state and generated body |

Regenerate uses the existing configured Catalogue output reader, `read_catalogue_work` in `docs-viewer/services/docs_catalogue_media.py`, to read each needed Work by its exact five-digit `work_id`. Matching existing documents also uses `work_id`; titles, document IDs and selected rows do not supply an alternative Work identity.

Work metadata is edited in Studio and generated there before Regenerate consumes it. Regenerate does not write back to Studio.

## Body Generation

One shared function turns a generated Work record into the document body. The body contains a single explicit Catalogue image token, without a title heading. The document's front-matter title also comes from the current Work title.

| Token field | Value |
| --- | --- |
| Work identity | Exact `work_id`, preserving leading zeroes |
| `alt` | `work.title` |
| `caption` | `work.title` |
| `summary` | The multiline text described below |
| `placement` | `left` |
| `fill_width` | `true` |

The summary has this order:

```text
<year_display>
<medium_caption>
<dimensions>
cat. <work_id>
```

Use `year_display` and `medium_caption` directly. Format dimensions from `height_cm`, `width_cm` and optional `depth_cm` as height × width × depth followed by ` cm`. Include positive numeric dimensions, omit the dimensions line when height or width is absent, and display whole numbers without `.0`. Omit empty optional summary lines.

For Work `01942`, the example summary is:

```text
2026
digital c-type print
30 × 40 cm
cat. 01942
```

Use the existing Catalogue image-token serializer to encode literal field values and newlines. The corresponding source body is:

```md
[[catalogue:image:work:01942|alt=se2&caption=se2&summary=2026%0Adigital%20c-type%20print%0A30%20%C3%97%2040%20cm%0Acat.%2001942&placement=left&fill_width=true]]
```

The summary contains the resolved text. `summary=metadata` is not a command to load Work fields, and `alt=title` is not a title substitution. Field substitution happens in the generation code before serialization.

The document retains its exact `work_id` in front matter, and the generated token contains that same explicit identity. The existing token parser, renderer, usage reporting and Info editing continue to own the resulting ordinary image token.

## Regenerate And Collection Controls

The Catalogue collection exposes Regenerate as its record-creation and maintenance action and omits manual New. Its documents represent Works that already exist in Studio. The shared document-creation operation remains available internally for Regenerate; other collections retain their New action.

Regenerate inventories existing Catalogue documents once and matches them to the generated Work set by exact `work_id`. Its preview modal includes an **Only create new docs** checkbox and shows how many documents will be created, regenerated or skipped. Changing the checkbox updates the preview, and Apply uses the same selection.

| Only create new docs | Existing Catalogue documents | Works without a document |
| --- | --- | --- |
| Checked | Skip source replacement and document rendering | Generate the body, create and build the new documents, and initialize their Links files |
| Unchecked | Replace the body and update the title from current Work data, then rebuild | Generate the body, create and build the new documents, and initialize their Links files |

With the checkbox checked, existing sources, titles, timestamps, draft state, individual generated payloads and Links files remain unchanged. This is the routine way to add newly available Works. If no Works are missing documents, there are no source writes or document builds.

With the checkbox unchecked, each existing document receives the current generated body and Catalogue-owned title. It retains its source filename, `doc_id`, `work_id`, `added_date` and current `draft` state. Advance `last_updated` when its source changes. Existing authored body text is replaced. Documents whose Work is absent from the current generated index are not deleted.

New documents use the shared creation behavior: allocate a timestamp-plus-random immutable `doc_id`, set timestamps and initial draft state, store the exact Work association, and write the source. Creation does not inventory existing document IDs, check collection existence or read and validate existing collection documents. Regenerate owns the single inventory needed to identify missing Work documents; it must not repeat that scan for each new document.

Batch the selected document IDs into a targeted Catalogue build, merging the required shared manifests while preserving unselected document payloads. Existing Links files remain untouched, including their stored relationships. Only newly created document IDs enter the existing Links initialization path. Document-build and Links selections remain separate, including a replacement run with no new documents.

The action completes its source writes and required document projections before reporting completion. Document Source remains available through existing controls; manually authored body changes are replaced by a later Regenerate with Only create new docs unchecked.

## Build And Applying Changes

Regenerate captures the current Work title and summary metadata in document source. An ordinary Working or Pre-publish Build renders the explicit image token and its saved text; it does not rerun the body generator or refresh caption and summary from Work JSON. Existing browser image resolution and Media View activation continue to use the token's exact Work identity through the configured Catalogue data.

| Changed input | Required action |
| --- | --- |
| New Studio Works with generated JSON available | Regenerate with Only create new docs checked |
| Existing Work title or summary metadata | Generate the updated Work data in Studio, then Regenerate with Only create new docs unchecked |
| Body structure, summary fields or image presentation | Amend the generation code, then Regenerate with Only create new docs unchecked |
| Published document content | Prepare and review Pre-publish, then use the existing explicit Publish and deployment workflows |

Changing generation code or Work JSON does not itself rewrite documents or publish output. Regenerate performs the requested source replacement and document build. It does not create a versioned snapshot of Catalogue JSON or image bytes.

## Search Deferred

Search changes are outside the first version. Keep the current collection-report search and site Search behavior. Do not add generated `search_text`, metadata search contributions, subject-identity indexing or automatic Search rebuilds as part of this feature.

The relationship between collection-report search and site Search needs a separate decision before either is extended. A token-only body does not make its caption and summary automatically searchable.

## Modal Operation

1. Open Regenerate from the Working Catalogue collection. The modal owns one preview/apply operation over that exact collection.
2. Show **Only create new docs**, initially checked, and a read-only preview identifying the selected Works and the create, regenerate and skip counts. Use stable Work-ID ordering for repeatable selection.
3. Changing the checkbox refreshes the preview. Preview writes no documents. Apply remains unavailable until the current preview is complete.
4. Apply uses the exact previewed Work IDs and checkbox choice and never expands the selection. If relevant inputs have changed, require a new preview rather than silently changing the proposed operation.
5. Keep the modal and management workflow busy until source writes, the targeted build and required Links initialization have finished. Then show the actual outcome and refresh the owning collection report.
6. A failure identifies the affected Work and reports completed source changes and any incomplete build result. Do not report success or silently retry creation after a partial failure.

The initial live runs used a temporary cap of **100 affected documents**, applied after the checkbox filter. The user accepted continuation and the cap is now removed. The same normal button and modal preview the full eligible set. There is no delivery-limit selector, banner, separate delivery UI or automatic progression between runs.
