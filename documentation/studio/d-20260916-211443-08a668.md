# Catalogue Work Record Template

## Purpose And Status

Proposed specification for `[[catalogue:template:work-record]]`. The Catalogue collection presents records generated from Catalogue data. Its document bodies contain tokens, and the template owns their presentation and metadata selection. Catalogue remains the place to edit Work data. Regenerating these documents is a permanent maintenance action that replaces their source content while preserving document identities and existing Links records.

This specification defines the proposed files and behavior. The files, new token, template loading and Regenerate action are not implemented by writing this document. [Semantic Tokens Architecture](d-20260714-234030-434069.md) describes the existing explicit image and Media View tokens.

## File Ownership And Locations

Keep the two template files together in the tracked repository:

```text
docs-viewer/templates/catalogue/
  work-record.md
  work-record.json
```

| File | Contents | Reader |
| --- | --- | --- |
| `docs-viewer/templates/catalogue/work-record.md` | Default Markdown body for a Catalogue Work document | Catalogue New and Regenerate |
| `docs-viewer/templates/catalogue/work-record.json` | Work field selection, summary formatting, image presentation and searchable metadata | Docs Build when it encounters the template token |
| `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/works/index/<work_id>.json` | Current generated Catalogue Work data, including metadata and media | New/Regenerate for document metadata; Build for token expansion |
| `$DOTLINEFORM_DOCS_BASE_DIR/working/source/collections/catalogue/documents/<doc_id>.md` | Each actual document's front matter and token-only body | Ordinary Docs source and Build owners |

The template pair belongs to Docs Viewer because it defines document generation and presentation. It is maintained directly in the repository, outside the source-document collection, so the template itself is never indexed as a document. Both Working and Pre-publish Build use the same repository definition. Publish retains the resulting generated document output; the browser does not load the Markdown template or its JSON definition.

The exact registered name `work-record` selects this pair. Token text supplies no filesystem path. The initial implementation needs one named Catalogue template, without a template discovery system or a general template language.

## Markdown Template

The complete initial contents of `work-record.md` are:

```md
[[catalogue:template:work-record]]
```

This is a body template. It has no front matter, document ID, Work ID, title heading or copied Work metadata. New and Regenerate combine it with document front matter through the existing source formatter. This keeps ID allocation, timestamps and publication state with the document lifecycle owner.

For example, the existing `se2` document would retain its exact document identity and Work association, with the following body:

```md
---
doc_id: d-20260916-182813-39ce80
title: se2
collection: catalogue
added_date: "2026-09-16 18:28:13"
last_updated: "2026-09-16 21:14:43"
work_id: "01942"
draft: false
---
[[catalogue:template:work-record]]
```

The timestamp above is illustrative. The Work identity remains solely in front matter; all documents can share the same body. The template token occupies its own paragraph. Token-like text in code or comments remains inactive under the existing parser rules.

## JSON Definition

Proposed complete contents of `work-record.json`:

```json
{
  "schema_version": "catalogue_work_record_template_v1",
  "image": {
    "alt": { "field": "title" },
    "caption": { "field": "title" },
    "summary": {
      "parts": [
        { "field": "year_display" },
        { "field": "medium_caption" },
        {
          "format": "dimensions_cm",
          "fields": ["height_cm", "width_cm", "depth_cm"]
        },
        { "field": "work_id", "prefix": "cat. " }
      ],
      "separator": "\n"
    },
    "placement": "left",
    "fill_width": true
  },
  "search_fields": ["year_display", "medium_caption"]
}
```

All `field` names refer directly to properties of the generated record's `work` object. The JSON contains instructions shared by every Work; it contains no particular Work ID or copied values. The template renderer supplies the exact Work primary image from that record's existing media data.

| Setting | Meaning |
| --- | --- |
| `alt.field` | Read `work.title` as image alt text |
| `caption.field` | Read `work.title` as the visible caption |
| `summary.parts` | Produce the listed values in this order |
| `field` summary part | Read the named Work text field |
| `prefix` on a field summary part | Optional literal text prepended to a non-empty field value, preserving spaces; `cat. ` plus `work_id` produces the final summary line |
| `format: dimensions_cm` | Format the listed centimetre measurements as height × width × optional depth, followed by ` cm` |
| `summary.separator` | Join non-empty parts; `\n` displays each part on its own line |
| `placement` and `fill_width` | Use the existing captioned Catalogue image layout controls |
| `search_fields` | Read these Work fields into generated `search_text`, independently of the visible summary |

`dimensions_cm` is a small code-owned formatter. It uses positive numeric height and width, includes positive depth when present, and omits the dimensions part when height or width is absent. Whole numbers display without `.0`. Missing or blank optional summary values are omitted without empty lines. Use `year_display` directly and `medium_caption` directly; the template does not invent fallback metadata. Field values are plain text and receive the existing HTML escaping.

The supported definition is deliberately limited to these image settings, direct Work field reads with optional literal prefixes, ordered summary parts, the dimensions formatter and explicit search-field selection. There are no expressions, arbitrary HTML, includes or per-document overrides. Editing the JSON changes the common presentation without storing those decisions in every document token.

With the inspected generated Work `01942`, Build would produce:

```text
Alt: se2
Caption: se2
Summary:
2026
digital c-type print
30 × 40 cm
cat. 01942

Placement: left
Fill width: true
```

## Build Behavior

1. Recognize the exact `catalogue:template:work-record` token and select its registered JSON definition.
2. Read the containing document's exact five-digit `work_id` from front matter.
3. Read the generated Work record through the existing configured Catalogue output reader. Verify that it is the same Work, using the reader's existing identity check.
4. Evaluate the JSON against the `work` object, render the existing captioned Catalogue image structure with the resolved alt text, caption, summary, placement and width setting, and contribute the selected search fields to generated `search_text`.
5. Record the occurrence against the resolved Work identity while retaining the actual template token and source range. It represents one template occurrence, not an invented ordinary-image occurrence in authored source.

The existing `read_catalogue_work` reader in `docs-viewer/services/docs_catalogue_media.py` already loads `works/index/<work_id>.json` through the configured Catalogue output workspace. Build needs to connect this reader to the new template renderer; ordinary Catalogue tokens currently render references without loading Work metadata. Read each needed Work once per Build operation and share the definition within that operation.

Build expands into generated output only. The Markdown body remains `[[catalogue:template:work-record]]`; it is not rewritten into an explicit image token containing resolved metadata. Caption and summary are captured by that Build. Existing browser media resolution and Media View activation continue to use the exact Work identity and their configured Catalogue data. This feature does not create a versioned snapshot of Catalogue JSON or image bytes.

The new token's reader uses `work_id` wherever the token occurs, including prepared Catalogue documents in Pre-publish. It does not infer a Work from a title, document ID, route or selected row. Missing required template/Work input is reported through the owning action's existing failure path. No fallback identity, replacement template or extra modal validation workflow is introduced.

Token parsing, usage reporting and the source audit must recognize the dedicated template presentation and resolve its Work from that document. Ordinary Add Catalogue image, Add Media View link and their Info editing retain explicit identities and literal authored fields. The new template does not add `alt=title` or `summary=metadata` commands to those tokens, and has no separate authoring modal in this specification.

## Search

Search already indexes the document's front-matter `title`; a visible title heading is not required. Catalogue template metadata contributes additional searchable text through the generated document payload's `search_text` field. The template's `search_fields` selects `year_display` and `medium_caption`. Build joins their non-empty values with newlines using the Work record it already loaded. Search consumes this generated text alongside the document's ordinary searchable content. The visible summary is not copied wholesale into Search: dimensions and the literal `cat. ` display prefix are excluded from the template contribution.

Subject identities should be searchable through the common Search pipeline for every document that declares them. Reuse the existing safe reader subject projection from `docs_document_subjects.project_reader_subject`, covering `work_id`, `series_id` and `detail_uid`. Index the canonical subject key as text, preserving leading zeroes and the full composite Detail identity. This uses the declared document subject and requires no Catalogue lookup or template token. It retains the reader projection's existing boundary, which excludes local Folder paths.

For the `se2` example, Search receives `se2` from the document title, `01942` from its Work subject, and `2026` plus `digital c-type print` from generated `search_text`. The displayed `30 × 40 cm` is not contributed to Search. A Work, Series or Detail subject on an ordinary document is searchable through the same general subject handling, independently of this template.

This introduces no authored search field in front matter. The template selects descriptive Work metadata; the shared subject model supplies subject identities. Search continues to rebuild through its existing explicit operation and normal stage eligibility rules. A template search-field change requires a document Build followed by a Search rebuild to reach the Search index.

## New And Regenerate

Catalogue New continues to select a Work. It reads `work-record.md` for the body, stores the selected `work_id`, uses the current Catalogue title, and retains the existing New lifecycle: new immutable document ID, timestamps, initial draft state, source write, projection build and initial Links file. The current heading-only body is the part replaced by template loading.

Narrow the shared New operation to creating the requested document. It validates the request and its exact target, allocates an immutable ID without overwriting an existing file, writes the new source, builds that document and initializes its Links file. It must not read, parse or validate every existing source document, audit the collection, or render existing documents. Necessary identity checks and updates to shared collection manifests remain with their existing owners. This correction belongs in New itself and benefits single-document creation as well as regeneration.

Regenerate uses the generated Catalogue Work index as its Work set and matches existing Catalogue documents by exact `work_id`. Its preview modal includes an **Only create new docs** checkbox. The preview shows how many documents will be created, regenerated or skipped; changing the checkbox updates that preview, and Apply uses the same selection.

| Only create new docs | Existing Catalogue documents | Works without a document |
| --- | --- | --- |
| Checked | Skip source replacement and document rendering | Create from the current template, build the new documents and initialize their Links files |
| Unchecked | Replace source from the current template and rebuild | Create from the current template, build the new documents and initialize their Links files |

With the checkbox checked, existing source, titles, timestamps, draft state, individual generated payloads and Links files remain unchanged. Regenerate inventories the existing Work-to-document identities once to identify missing documents; that comparison belongs to Regenerate. It reuses the corrected New creation operation and batches the new document IDs into a targeted Catalogue build, merging their required collection indexes while preserving existing document payloads. If there are no missing documents, there are no source writes or document builds. This is the routine way to add a few new records once the template is stable.

With the checkbox unchecked, each existing record receives the Markdown template body and current Catalogue-owned title. It retains the source filename, `doc_id`, `work_id`, `added_date` and current `draft` state, and advances `last_updated` when source changes. Existing authored body text is discarded as part of the intended replacement. In both modes, each Work without a document uses the same creation behavior and initial draft state as New. Regenerate does not delete documents whose Work is absent from the current index.

Existing Links files remain untouched by Regenerate, including their stored relationships. Only newly created document IDs enter the existing New-document Links initialization path. Rebuilding document output must not silently select every replaced document for Links refresh: the present builder supports explicit Links selections separately from document-build selections. This separation is required by the replacement action, including a run with no new documents.

The action completes its source writes and required document projections before reporting completion. Catalogue metadata is edited in Catalogue and then regenerated there through its existing workflow. Document Source remains available through existing controls; manually authored body changes are replaced when Regenerate runs with Only create new docs unchecked. Locking the editor is outside this specification.

## Applying Changes

| Changed input | Required action |
| --- | --- |
| New Catalogue Works with a stable template | Regenerate with Only create new docs checked; create and build only missing records |
| Markdown template body | Regenerate with Only create new docs unchecked to replace existing Catalogue source bodies and build their output; New uses it immediately |
| JSON field selection or presentation | Build the Catalogue documents to refresh output; source bodies stay the same |
| Template `search_fields` | Build the affected documents, then explicitly rebuild Search |
| Generated Work metadata | Build to refresh the token's displayed metadata; Regenerate with Only create new docs unchecked also refreshes document titles and creates missing records |
| Published content | Prepare and review Pre-publish, then use the existing explicit Publish and deployment workflows |

Saving either template file does not itself regenerate source documents or publish output. A template change affecting all Catalogue records calls for an intentional complete Catalogue build; a single Work change can use the existing targeted document build. Regeneration does not automatically rebuild Search.

## Implementation Review Points

The implementation should demonstrate a new document using the token-only body and receiving its normal Links file; an existing document retaining its immutable identity and exact Links bytes after regeneration; and `se2` rendering the fields shown above from current generated Work JSON. Changing only the JSON must update generated presentation on Build while preserving source. Explicit image and Media View tokens must retain their current behavior.

Review New independently: creating one Catalogue document must not read or validate other source documents or render their payloads. Regenerate must reuse that same corrected creation path.

Review Search contributions: template output supplies year and medium without dimensions; the existing title remains searchable without a heading; and declared Work, Series and Detail identities are searchable on documents with or without the template token. Subject identity strings retain their canonical form.

Review both preview selections and their applied results. With Only create new docs checked, adding a few missing Works must create and build only those documents, initialize only their Links files, and preserve existing sources and individual generated payloads. A run with no missing Works must perform no source writes or document builds.

This is a specification review, with no executable changes or runtime verification. An implementation delivery should select proportionate existing checks after inspecting the affected owners; any new or changed tests require their own agreed specification. Visual review of the resulting image and summary remains manual.


## Impact of a 2000 doc collection

From the current code, three things deserve attention:

- **Collection list rendering.** It creates every matching row and recreates them when filtering or sorting. With 2,000 entries, this is the clearest potential interaction cost. Pagination would be a straightforward improvement if needed. [List renderer](../../docs-viewer/runtime/js/shared/docs-collection-report.js)
- **New responsibilities.** New currently reads and validates the existing collection before creating a document. Remove that work from New itself so single-document creation and Regenerate both use the corrected operation. Regenerate owns the one inventory needed to find missing Work documents. [Creation planner](../../docs-viewer/services/docs_management_mutations.py)
- **Search.** The extra records enlarge the shared index and may produce similarly titled Catalogue and Works results. Add the explicit template search contribution and general subject-identity handling described above; dimensions remain display-only for this template. [Search source](../../docs-viewer/build/build_search.py)

There are also proportional costs from the watcher checking more files and Pre-publish processing more records. Those don’t imply another optimisation project yet.

Individual document content already loads on demand, so opening one record doesn’t load 2,000 document bodies or images.

Narrow New's responsibilities, implement the specified Search contributions, and assess list responsiveness with the populated collection. These are code observations; performance at 2,000 documents has not been measured.
