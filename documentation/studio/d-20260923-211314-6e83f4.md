# Catalogue Save And Targeted Publish

Deferred on 2026-09-24 because the publication split is exposing further issues that cannot be addressed within the available time. Implementation has not started. Retain the current combined Save completion, including Catalogue output, required media and private Studio lookup refresh. The requirements below retain the deferred direction. Recheck readiness and the outstanding issues before resuming; the earlier readiness record is not current implementation approval.

## Requirements

### Save

- Persist canonical edits efficiently: write only changed source files, batch changes to multiple Works within each affected file, and skip unchanged writes. Retain validation and conflict checks. A shared canonical JSON file may require rewriting, but unrelated source files must remain untouched.
- Refresh the editor/list's affected in-memory data from canonical service responses. Keep the current API read path; Studio freshness does not depend on Publish or persisted lookup exports.
- Add changed Work, Series and Gallery identities and required membership dependencies to a persistent pending-publication record. It starts empty, accumulates actual saved changes and deletions, and survives application restarts. Repeated changes to the same identity need only one pending entry.
- Remove automatic regeneration of `studio/data/generated/catalogue-lookup/` from Save. Retain the existing files and exporter; the lookup-versus-API decision is deferred.
- The Studio editor and Save must not read or write the consumer-facing JSON under `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`. Canonical JSON under `studio/data/canonical/catalogue/` remains Save's data authority; retained Studio lookup files are a separate boundary and are not updated by Save.
- Handle new or changed images immediately, including required derivatives, thumbnails, canonical media metadata and R2 upload. Preserve immediate Studio preview updates during the editing session. Skip image processing and remote checks when an ordinary metadata or Gallery membership edit does not require them.
- Keep obsolete-media deletion with the existing Save/delete media owner, including affected R2 images/downloads and local thumbnails. Determine cleanup from canonical changes and owned media state without reading published Work JSON. Publish has no media-cleanup responsibility.
- Image publication and Work JSON publication are independent: a new image is available in R2 immediately, but a new Work's generated JSON is unavailable until Publish. Existing Work JSON retains its last published content until republished.
- Docs Viewer image freshness can wait for Publish. Temporary differences between uploaded image bytes, cached images and published metadata, including missing media referenced by stale JSON after deletion, are accepted between Save and Publish. Publish corrects the affected JSON references; no live canonical-media read or additional Docs Viewer cache-refresh mechanism is required.

### Studio Data Boundary

Current Work editor reads were traced through `studio-data.js`, `catalogue-work-editor.js`, `catalogue-work-series-modal.js` and `studio_catalogue_api.py`. The Work editor does not consume the persisted `catalogue-lookup` files: its API reads canonical data and returns search and focused record projections. If the service is unavailable, editor startup returns before loading lookup data, so the shared loader's file fallback is not reached by this route. The file paths below are distinct from published Catalogue output.

| Data | File or service source | Current Studio use |
| --- | --- | --- |
| Work records | `studio/data/canonical/catalogue/works.json` | Canonical input to Work search/list and focused Work API responses; Save updates affected records. |
| Series records | `studio/data/canonical/catalogue/series.json` | Canonical input to Series search/pickers and the Series edit modal. |
| Gallery titles and memberships | `studio/data/canonical/catalogue/galleries.json` and `galleries-by-work.json` | Gallery registry and focused Work membership API responses; no separate Gallery lookup file. |
| Work search/list lookup | `studio/data/generated/catalogue-lookup/work_search.json` | Exported and configured, but not read by the Work editor. The editor uses the live `catalogue_lookup_work_search` API projection and filters its member-Works list from that response. |
| Series search lookup | `studio/data/generated/catalogue-lookup/series_search.json` | Exported and configured, but not read by the Work editor. The editor uses the live `catalogue_lookup_series_search` API projection. |
| Focused Series lookup | `studio/data/generated/catalogue-lookup/series/<series_id>.json` | Exported and configured, but not read by the Work editor. Its Series modal explicitly uses the live `catalogue_lookup_series_base` API projection. |
| Focused Work lookup | `catalogue_work_record` API response | Built from canonical records and membership; no generated per-Work lookup file is needed by the current editor. |

Save currently rebuilds the complete persisted Studio lookup set, but that export is unnecessary for the Work editor's current API read path: its API reads fresh canonical data, and the editor patches its in-memory Work search data from Save responses. The agreed delivery removes this export from Save while retaining the files and exporter. The retained files may therefore lag canonical changes; the Work editor continues to obtain current data through the API. Their future use and refresh policy belong to the deferred lookup-versus-API review, not this delivery.

Runtime/media configuration remains read-only configuration for these operations. Studio thumbnails under `catalogue/generated/works/thumbs/` and R2 primary images are image dependencies, not Catalogue JSON dependencies, and remain part of immediate media handling. Generated Work, Series, Gallery and discovery JSON under `catalogue/generated/` belongs to Publish and its downstream consumers.

The current Save media helper also reads `catalogue/generated/works/index/<work_id>.json` for obsolete-media cleanup and download reuse. Remove that dependency from Save as part of this delivery, preserving the required media behavior through its proper owner. Publish may read previous Catalogue output to resolve dependencies for pending identities; Studio editing and Save must work independently of those JSON files.

### Publish

- Publish the accumulated pending changes, independently of the current editor selection. Start with an empty pending record; no initial reconciliation, baseline scan or full JSON rebuild is required. Existing output stays untouched until affected by a subsequent saved change.
- Identify affected records before constructing individual output payloads. Do not build approximately 5,000 record JSON files by default, even if unchanged writes would subsequently be skipped.
- Include affected Work, Series and Gallery outputs, both former and current membership dependencies, and required deletions. Update affected shared indexes once per Publish; reading the catalogue to calculate an affected aggregate index does not require regenerating every record payload.
- Keep record files and their indexes consistent, leave unrelated outputs untouched, and skip unchanged payloads. Clear the pending record only after successful Publish; a failure leaves it available for an ordinary later Publish.
- Use the media state already completed by Save. Publish updates JSON only: it does not generate, upload, check or delete media.
- Publish supplies current image versions and dimensions in Work JSON for Docs Viewer's next read. Retain its existing generated-JSON reader; Docs Viewer runtime changes are outside this delivery.

### Deploy

Deploy is a separate, later delivery. Catalogue Publish prepares the local generated Catalogue output; it does not copy output into the repository, commit, push or deploy the public site. A later modal can follow Docs Viewer's Publish / Copy to repo design while retaining separate actions and outcomes. This proposal does not change Docs Viewer's publication ownership.

## Deliverables

- Separate Save and Publish service operations and an explicit Studio Publish control.
- Targeted canonical writes, affected editor/list refresh and immediate image handling, with no persisted lookup regeneration during Save and Studio independent of published Catalogue JSON.
- An initially empty, persistent pending-change record and incremental Catalogue generation of those changes, including dependency updates and deletions.
- One global Publish control with an indication of saved changes awaiting Publish, independent of the selected Work.

## Process

1. Edit and Save one or more Works. Canonical data and editor/list values update immediately through the existing API path; new or changed images are prepared and uploaded, and obsolete media is removed by the existing Save/delete media owner. Persisted Studio lookup files remain untouched.
2. Continue editing and saving. Pending changes accumulate from an initially empty record. Consumer-facing Catalogue JSON remains at its last published state and can temporarily refer to changed or deleted media.
3. Click Publish to update all pending Catalogue changes and their affected indexes once, then clear the pending record on success. Docs Viewer then obtains current image versions, dimensions and other metadata through its existing JSON reads. For example, moving twenty Works from Gallery A to Gallery B updates those Works, the affected Gallery outputs and indexes, without image work.
4. Deploy the published result separately once that capability is implemented.
