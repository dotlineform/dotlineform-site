# Save/Build optimisations

## Collection-Wide Work During Save/Build

The following describes the current implementation inspected on 2026-09-11. It distinguishes the purpose of an output from the present cost of producing it. A collection-wide navigation file may legitimately need replacing after an edit without requiring every document's Markdown to be read or rendered again. These are code-path findings, not measured timings or additional approved implementation work.

## Targeted Parent-Collection Build

A parent collection is the scope's ordinary document collection. Its targeted build renders only the selected documents, but loads the complete collection before selecting them. The main sequence is in `docs-viewer/build/docs_builder/pipeline.py`; source loading and validation are in `source.py`, and tree/Recent projections are in `payloads.py` in the same directory.

| Work | Purpose | Why it currently spans the collection; possible reduction |
| --- | --- | --- |
| Source loading and validation | Establish document identity, metadata, parent relationships and report declarations; reject invalid or duplicate IDs and unknown parents. | `load_docs()` reads and parses every Markdown source in this collection. Duplicate and parent checks need knowledge of other document identities, but ordinarily need only their metadata. A maintained identity/metadata inventory could support validating the changed document without rereading every body. Creation, deletion and parent changes must still update and validate that inventory. |
| Targeted-build prerequisites | Ensure unchanged generated documents exist before reusing them alongside the newly rendered document. | Service/watcher preflight loads the collection and checks unselected by-ID files; the builder checks prerequisites again. Missing shared indexes or payloads can cause the service to select a full build. This supports initialisation and recovery, rather than rendering the edited document itself. Repeated whole-collection checks and automatic full-build fallback are separate candidates for review. |
| Document-link destination lookup during rendering | Preserve exact target identity while projecting local links into the current viewer route. | The renderer constructs its lookup from the complete loaded document list, although only the selected document's HTML is rewritten. Resolving the links actually present needs exact target records and route configuration; it does not inherently require every target's Markdown body. This lookup is distinct from incoming/outgoing Links maintenance. |
| `index-tree.json` | Supply the document hierarchy, title ordering, content locations and status metadata used by navigation. | The builder regenerates the whole tree from collection metadata. A title, parent, document membership, status or report change can legitimately alter it. A body-only edit with unchanged tree metadata need not alter the tree. Even if the tree remains one complete JSON file, it could be regenerated from maintained metadata without reading all source bodies. |
| `recent.json` and the configured publication Recent projection | Show the newest added or edited documents, including their parent titles; prepare the separately eligible public list. | The builder sorts the complete candidate set, applies the route's added/edited basis, and limits the result. A save can change edited ordering; a deletion may expose the next candidate beyond the current limit. Public eligibility also excludes hidden branches before limiting. This needs candidate dates, titles, parents and eligibility, rather than every document body. |
| `semantic-tokens/index.json` | Supply the collection's semantic-token usage records, including the Semantic Tokens report. | A targeted build reads the existing complete usage index, retains unselected documents' occurrences, replaces the selected documents' occurrences, and assembles the complete JSON again. It already avoids rescanning unchanged Markdown for token extraction. The remaining collection-wide work is aggregate JSON processing; changing that cost would require a separate decision about storage or update frequency. |
| `backlinks.json` | Supply the local Documents Linking Here report with same-collection incoming links. | The builder reads every current rendered payload, overlays the selected documents' new payloads, and scans all rendered anchors to reconstruct the reverse mapping. That full rendered-content scan is how this independent index currently discovers and removes incoming contributions. It could be reduced by maintaining source contributions incrementally, or by sharing Links data after an explicit scope and eligibility decision. The report's purpose alone does not require the current scan strategy. |

There are two further implementation costs worth separating from those product outputs. First, the builder prepares a flat in-memory `index_payload`, reading unchanged rendered JSON and deriving `content_text_length` for every document. The current CLI does not persist that flat index; the pipeline returns it and uses its document count, while the write plan persists the tree, Recent, semantic-token and backlinks outputs. The need for these rendered-content reads should be checked against actual consumers before carrying them into a revised Save path. Second, the write plan lists all generated by-ID filenames to identify obsolete files, then restricts removals to the selected IDs during a targeted build. Full reconciliation needs an inventory; a known document deletion could use its exact identity instead.

These operations do not all have the same cost. Reading and parsing hundreds of Markdown or rendered HTML files, sorting metadata already in memory, checking filenames, and rewriting one aggregate JSON file should be measured separately. Writing only changed output files does not remove the preceding reads and computation.

## Sub-Scope Collection Builds

The current child rendering path is broader than the targeted parent path. `SubScopeDocsBuilder.run()` renders every document in that child collection and regenerates the reader `manifest.json`, `manage-manifest.json`, and applicable `subject-associations.json`. Since the scoped Links change on 2026-09-12, `rebuild_sub_scope_outputs()` carries a separate exact Links target set from the source operation; rendering every child no longer means refreshing every child's Links. [Builder](/docs/?scope=studio&doc=d-20260423-000000-c9f3ea) owns that completed relationship-maintenance boundary. The ordinary parent tree/Recent/backlinks sequence is not this child builder's output sequence.

The manifests support the child document list, management fields, reader Subject summaries and configured collection-specific projections. Those outputs need a complete view of the child collection's membership and metadata. That does not inherently require rendering every unchanged child document. The current implementation combines both tasks in one full child build, so a targeted child rendering path would be a separate improvement.

Child viewer URLs also require the exact parent `docs_subscope` report host. The child builder currently loads the parent collection's Markdown to locate the matching report, caching the result only for that builder instance. The purpose is correct child navigation. Persisting or directly querying the validated report-host association could avoid rediscovering it through a parent source scan.

## Work That Is Conditional Or Explicit

Full-text Search is not rebuilt by ordinary source saves or the watcher. It remains an explicit whole-index operation. The current Analysis Working scope-level `links.json` aggregation and completed Build manifest are produced after the full docs-and-Search scope rebuild, not after every document save. Their collection-wide processing must not be counted as an unavoidable ordinary-save cost.

Registered media producers are another conditional step. Analysis Working rebuilds and the normal child-save rebuild path pass `--skip-media-builds`; other build invocations can run producers when that flag is absent. Media generation should therefore be attributed to the actual command and configured producer rather than assumed to happen on every Save.
