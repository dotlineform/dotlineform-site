## Requirements

Develop how authors and readers use Catalogue data inside Analysis documents through design and bounded implementation in the live application. Use the resulting evidence to decide canonical, editor and publication-workflow changes when they are needed.

Use the current Working examples under [tokens and identifiers](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-5c65a9) as the live evaluation surface, continuing in Analysis Working after the stage migration. Use the complete Studio-produced records under `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`. Current behavior is evidence, not a requirement to preserve every token, field, route or presentation choice.

The design must answer three connected questions:

1. How does Catalogue data appear within ordinary documents and the Analysis reading experience?
2. Does the current projected JSON give those consumers the right identities, relationships, media information and content?
3. Which current tokens change, which remain useful, and which new tokens are needed?

Keep Catalogue identity, optional Work `series_id`, document `parent_id`, document subject association and token composition independent. A Work, Series or Detail may be presented without having a corresponding document. A document may refer to several Catalogue entities, and several documents may refer to the same entity. Tokens resolve exact Catalogue identities and presentation variants; they do not choose a definitive document or manufacture membership and parentage.

The work may edit example documents and implement explicitly scoped runtime, token, report or document-subject changes. Keep generated Catalogue files producer-owned; demonstrate proposed payload changes with isolated fixtures before changing the producer in an agreed slice. Accepted components are maintained application code; manually supplied fixtures remain identified as fixtures. Continue with the existing projected JSON while it meets the demonstrated requirements, and revisit it when a concrete incompatibility appears. Canonical/editor migration and complete Studio output are finished. The remaining Docs provider/publication integration, Search, public cutover and archive changes require their own agreed scope.

## Deliverables

1. A consumer-presentation model describing the useful document and reading contexts for Work, Series, Detail, gallery, metadata, download, Media View and associated-document behavior.
2. A field-level decision for the example Catalogue JSON: retain, change, add, derive elsewhere or remove. This includes record headers/revisions, identity, membership, nested Details, thumbnail and primary-media resolution, downloads and document associations.
3. An accepted token set. For every retained, changed or new token, define exact target type and identity, source syntax, authoring options, rendered responsibility, navigation destination, dependency tracking and unresolved-target behavior.
4. A sub-scope report design for public reading and local management. Define the rows or cards, grouping and ordering, available actions, Catalogue/document association information and any distinct public and Manage responsibilities.
5. Updated concept and data-model decisions, with concrete manual or deferred implementation changes recorded in [UAC - Change Backlog](/docs/?scope=studio&doc=d-20260904-183853-65ffcb).
6. A maintained [Findings](/docs/?scope=studio&doc=d-20260904-213326-e93cc6) record separating confirmed current behavior from open design choices and accepted resolutions.
7. Live `detail_uid` subject support in Projects and Analysis Works, and direct subject assignment in Analysis Works, through the existing document metadata and assignment owners.
8. An icon and workflow-symbol design covering scope/sub-scope configuration and displaying manually assigned icons alongside workflow-generated symbols in the same document/list location, with both meanings visible at once.

The delivery does not require a token for every Catalogue field or one report for every entity type. Add a token or report only where it represents a distinct authoring or reading responsibility.

## Process

This work combines discovery with real implementation. The live application is the evaluation environment, and useful components may carry forward directly. Name each material branch and its intended changes before implementation; record what was accepted and which assumptions remain open. Do not silently add features under a discovery label or treat all exploratory code as disposable.

The steps below organise connected questions rather than impose a mandatory linear sequence. Branch into a gallery, report or token change when it resolves a current requirement. Use a detailed delivery sequence where it helps that branch; do not require the entire consumer model to be frozen before doing bounded useful work.

Put significant observations in Findings when they affect more than one token, report or payload decision. Keep the delivery checklist focused on progress and gates.

Use the example documents to show one question at a time and the complete external generated data to test the answer. Record accepted decisions in this delivery as they are made, including an example source form and expected presentation where that removes ambiguity.

For each presentation need, first identify its exact Catalogue or document identity and authoritative data source. Then decide whether an existing token can express it, whether the projected JSON supports it, and whether a report or Media View owns part of the experience. Do not solve missing data by duplicating canonical values into token text or document front matter without explicitly accepting that value as an authored override.

Assess current reports as reusable owners before proposing replacements. In particular, distinguish the public sub-scope collection presentation from local association, coverage and readiness work. Coverage describes actual associations; it does not require one document per Work or treat several associated documents as an error.

#### Icons And Workflow Symbols

Use the Working [tokens and identifiers](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-5c65a9) legend as the concrete review example: 📝 needs review and editing, 👀 under review, 🔬 potential new, 🚫 retire and ✅ ok. These are deliberately assigned editorial meanings. They must coexist with symbols generated from actual workflow state; an assigned ✅ must not imply that a workflow step has completed.

- [ ] Separate manually assigned icon meaning from generated workflow state and identify the owner of each. Review the current `ui_status` mapping without treating it as the final model.
- [ ] Assess different icon sets for Analysis and other scopes, and decide whether sub-scopes share a scope's set or define their own. Specify defaults and any override rules explicitly; distinct sets remain a design option to evaluate.
