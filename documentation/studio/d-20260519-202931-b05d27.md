# Catalogue Indexes And Payloads

## Generated Read Models

Studio owns the complete replaceable consumer output beneath `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`:

| Relative path | Contents |
| --- | --- |
| `works/index/<work_id>.json` | Complete Work metadata, optional `series_id`, links, downloads, media and ordered sections with nested Details |
| `series/index/<series_id>.json` | Independent Series metadata and ordered lightweight `member_works` |
| `works/works_index.json` | Compact Work identities, labels, membership and media references |
| `series/series_index.json` | Compact Series identities, labels and member count |
| `work_details/work_details_index.json` | Exact Detail identities, Work/section ownership and media references |
| `works/thumbs/` and `work_details/thumbs/` | Generated thumbnails referenced by Work and Detail media |

Ungrouped Works and empty Series are ordinary output. There is no Catalogue publication filter, primary-Work requirement, Recent projection or Catalogue Search output in this producer.

`studio/services/catalogue/generate_work_pages.py` owns the complete projection. `catalogue_generation_records.py` and `catalogue_generation_indexes.py` own record and index shaping. [Catalogue Build And Lookup Refresh](/docs/?scope=studio&doc=d-20260519-202931-0c703e) owns refresh and cleanup.

## Exact Identity And Versions

Work payloads use `work_record_v6`; Series payloads use `series_record_v5`. Headers carry the exact target ID, schema, content version, generation time and count. The Work count is its nested Detail count; the Series count is its member count. Index headers use `catalogue_works_index_v1`, `catalogue_series_index_v1` and `catalogue_work_details_index_v1`.

A Detail retains `work_id`, `detail_id` and composite `detail_uid`. Sections carry their exact identity and ordering; Series ordering follows its canonical `sort_fields`. No relationship is inferred from a document, title, route or thumbnail filename.

Content versions include schema and projected content. A generation timestamp alone does not force a rewrite. Confirmed per-image `media_version` is separate from the payload version.

## Media And Documents

Work and Detail `media` objects contain relative thumbnail paths with sizes and absolute primary-image URLs with widths and version queries. Records without configured image media have an empty media object. Work downloads retain their filenames and projected remote URLs.

Work and Series `documents` arrays are currently empty. Studio does not derive document associations or choose a canonical document. Accepted document dependencies and public associations belong to the later Docs integration. Catalogue prose has no parallel Markdown source or `content_html` field.

## Consumer Boundaries

Studio's private `studio/data/generated/catalogue-lookup/` remains separate from this consumer output. Studio serves generated thumbnails through its confined local `/studio/catalogue-output/` route.

The complete external data is available for Docs design. The coordinated switch of every local Docs reader, subject tool and lookup is not implemented. Public readers must eventually use the accepted Analysis snapshot; generating Catalogue data does not publish it. The frozen legacy payloads under `site/archive/` have their own historical shape and are outside active generation.

Change the owning serializer and focused evidence when a demonstrated consumer need changes this contract. Keep source-only metadata, Studio lookup fields and future publication dependencies under their respective owners.
