# Collection Search And Site Search

This feature records the agreed search and Recents direction, implemented site-search selection, and proposed collection search and editorial curation. It is maintained under [Planned Features](d-20260428-000000-f5ff18.md). The Search index build slice below is implemented; Recents and the remaining candidates are separate deliveries.

Here, **site search** means the Docs Viewer main search over the selected workspace stage, including the public reader of its accepted snapshot. **Collection search** means search within one collection report. The separate Catalogue Works report and public Catalogue Search are distinct consumers.

## Three Independent Decisions

### Collection-Scoped Search

A collection represents a cohesive set of related documents. Searching within that set is useful in its own right, even when its documents also participate in site search. Every collection should therefore have its own scoped search, including Works and Processing. Site-search inclusion does not remove that need.

Collection search returns only that collection's documents. Following links from those results may take the reader elsewhere, but linked documents do not automatically enter the collection's search results.

### Full Text Or Fields

The appropriate search type depends on what the reader is trying to find. Works, Concepts and Moments contain readable documents whose meaning extends beyond their titles, so their collection searches should cover full text. Site search also remains full text.

Catalogue surfaces a large set of structured Work records through generated by-ID payloads. Its useful retrieval surface is selected Catalogue metadata: Title and Series, with additional report filters for fields such as Medium. The distinction is the records' purpose and scale; generated by-ID JSON is also used to display the other collections and does not itself determine the search type.

Processing also needs collection-scoped search. Full text is the suggested starting point for its documentation, but its exact collection-search field policy has not yet been agreed.

### Site-Search Inclusion

Works and Processing belong in site search alongside ordinary documents. Their documents may connect to Library or other groups of reference documents, and readers should be able to discover that wider material through one search.

Catalogue, Concepts and Moments should be searched within their own collections and excluded from the site-search document corpus. This is an explicit collection policy based on the intended reading experience. It must not be inferred from whether individual documents currently contain links, their titles, or their Subject metadata.

The agreed corpus is ordinary documents plus Works and Processing, excluding draft and unpublishable ordinary roots and their descendants, and filtering flat collection entries individually by draft state. Every source document requires explicit boolean `draft`. [Preview Stage Consolidation](d-20260924-201824-a27c31.md) replaced Pre-publish and local Published with one Preview snapshot. [Copy Working Search Into Preview](d-20260924-210855-8b419e.md) made Working the sole Search builder and copies its existing file unchanged through Preview and repository projection. The Search selection delivery below now applies the agreed coverage during Working builds.

The user subsequently selected [Remove Stage Context From Search](d-20260924-203338-b9417d.md) as the prerequisite before other Search changes. Its v4 format removes embedded stage and result URLs while retaining document/collection identity, current corpus membership and postings. Readers supply route context. It does not implement the new coverage policy or consolidate build ownership.

[Retire Public Document Locations](d-20260924-205346-c74d90.md) removed the unused location index/picker and legacy Catalogue document-URL refresh. Deploy Repo counts accepted documents directly. The Search copy workflow removes the old equality check between Search membership and the complete prepared document set; no coverage or readiness filter is added by that ownership change.

### Build Sequence

1. **Resolve Working inputs and collection coverage.** Load the workspace configuration and the explicit inclusion policy. Select ordinary documents plus the exact `works` and `processing` collection IDs. Do not load Catalogue, Concepts or Moments manifests, sources or by-ID payloads for this Search build. Use configured host IDs; do not discover hosts by scanning document bodies, titles or routes.
2. **Account for `unpublishable.json`.** Read the current policy file once through `read_publication_ignore_ids` before selecting documents. Preserve its existing ordinary-document ownership and validation: an unreadable, absent or invalid file stops the build, and an empty JSON array means no explicit exclusions. Treat the returned IDs as ordinary subtree exclusion roots. Do not rewrite the file, turn its entries into a new per-collection policy, or assume that draft filtering covers this separate rule.
3. **Traverse the ordinary Working tree.** At each node, stop traversing that branch if its ID is in the unpublishable set or its explicit `draft` value is `true`. Otherwise retain its exact ID and display metadata, then visit its children. This single traversal inherits both kinds of exclusion through ordinary descendants. Collection report hosts participate as ordinary nodes, including when an excluded ancestor removes them. An ordinary collection landing page is not excluded merely because its subdocs are outside site-search coverage.
4. **Select flat collection entries.** For each included collection, first require its configured host to be among the selected ordinary IDs. If it is excluded, skip the entire collection without reading its manifest or content. Otherwise read that collection's Working `manage-manifest.json` and select each entry whose explicit `draft` value is `false`. Check subdocs individually: excluding one does not exclude its peers, and no descendant traversal or `parent_id` lookup occurs within a collection. Retain exact collection, subdoc and report-host IDs with each selected target.
5. **Load and validate selected content.** Only after metadata selection, read the selected Markdown files and the selected collection by-ID payloads needed by existing consistency checks. Adapt the current source loaders to accept the selected IDs instead of loading every source and filtering afterwards. Required metadata and selected source/output inconsistencies must fail clearly; do not fall back to a full source scan or silently substitute another identity. Search expects current Working document projections. Manage Rebuild already builds document outputs before Search; a direct Search build retains that prerequisite and does not rebuild documents itself.
6. **Extract fields and build postings.** Reuse the existing Markdown extraction, normalization, tokenization and field policy for Title, Heading, Summary, Body and Code. Construct the deterministic document table and term-to-document/field postings from the selected records only. Preserve exact target identity, ranking behavior and the v4 JSON shape. An excluded document contributes neither a result row nor searchable terms.
7. **Write the complete Working index.** Compute the existing content version over fields, document metadata and postings. Write the complete `working/generated/search/index.json` when its content changes; retain the current unchanged-content skip behavior. This remains a full index build, with no incremental posting updates and no Search rebuild on ordinary watcher or source-save events.
8. **Use the existing copy workflow.** Prepare Preview captures the saved Working index with its reviewed plan and copies its exact bytes while independently preparing eligible documents. Deploy Repo copies that same Search file onward. Coverage is decided during the Working Search build, never during copying or browser querying. [Copy Working Search Into Preview](d-20260924-210855-8b419e.md) owns the implemented copy and revision behavior.

### Implementation Boundary

The code change belongs primarily to `build_search.py`, the shared inclusion-policy owner and its workspace configuration. Reuse `docs_publication_ignore.py` for policy-file resolution and validation. Preserve the distinction between ordinary subtree exclusion and flat collection entry filtering; do not apply a generic descendant algorithm to subdocs. This section specifies the Search selection/build change only. Recents can consume the same collection inclusion decision through its separately described candidate-gathering change below; its date handling and build mechanics remain unchanged by this Search step.

Implementation should leave the existing v4 schema, text extraction, ranking and build/copy ownership intact. The observable result is an index containing only selected ordinary documents and non-draft Works/Processing subdocs whose ordinary hosts remain eligible. Tests, fixtures and harness changes require their separate agreed specification; this documentation update does not create or modify them.

## Recents And Editorial Selection

Recents should use the same document coverage as site search: ordinary documents, Works and Processing. Catalogue, Concepts and Moments entries are excluded from both. Use one explicit membership policy consumed by both builders, applying it before sorting and limiting Recents. Filtering an already truncated list could leave few or no entries even when other eligible recent documents exist. Shared coverage does not require Recents to load or rebuild the search index.

Recents remains an automatic view of document activity. Its existing date basis and full-stage build ownership are separate from the membership change. Matching site-search coverage removes bulk Catalogue activity from the list, but does not provide editorial selection for a site entry page.

The proposed solution is an editorial **star**: manually select any ordinary or collection document, then list the selected documents in a report embedded in a home-page document. Catalogue, Concepts and Moments documents can be starred even though they are excluded from site search and Recents. A star does not change either inclusion policy.

The intended workflow is simple: open a document in Working, toggle its star, and review the selected list. The public home page displays the resulting document list without a star icon, selection control or public starred-state indicator. Its heading can describe the editorial purpose, such as Selected Work; the internal mechanism need not be presented to readers as Starred.

Stars require durable editorial state with exact document identity, independent of browser-local bookmarks. Choose the storage owner during specification, including how selection survives Catalogue record regeneration. The report uses the existing document/report navigation model and must distinguish ordinary documents from exact collection targets.

A document may be selected while still a draft. The public report includes only selected documents present in the accepted published set, with valid destinations. Starring does not publish a document or bypass its collection host's publication eligibility. Changes to the public selection follow the normal preparation, Publish and deployment lifecycle.

Selection and ordering are separate decisions. A star alone says which documents belong, not which is newest or most important. Newest-starred-first is a useful initial proposal because content edits would not reshuffle the presentation; manual ordering is another option if editorial placement matters. Neither is agreed yet. Also decide whether a curation-only change affects the document's edited timestamp; the recommendation is to keep editorial selection changes from making unchanged content appear recently edited.

## Recents: Current Build And Coverage Change

Recents is generated during a full document build for the selected stage:

1. Reuse the ordinary document records already loaded from Markdown source by that build.
2. Read and parse the Markdown source files in every configured collection. This uses whole source files, although Recents mainly needs their metadata; it does not render the collection document bodies or scan generated by-ID JSON, collection manifests or search indexes.
3. Collect document identity, title, dates and navigation information, retaining exact collection and report-host identity for collection documents.
4. Sort by the configured date basis, currently `last_updated`, retain entries with valid timestamps, and select the newest 20 with deterministic tie-breaking.
5. Write the small `recent.json` reader payload and its configured publication projection. Opening Recents in the browser only loads this precomputed list; it does not scan documents.

Full-stage builds own generation. Targeted ordinary-document builds and collection-only builds leave Recents unchanged. Publication and deployment carry the prepared snapshot through their existing lifecycle.

The coverage change is to make the search and Recents builders consume the same explicit inclusion policy. Recents should gather ordinary document records and the Works and Processing collections, leaving Catalogue, Concepts and Moments out of its candidates before sorting and limiting. Apply the collection decision before calling its source loader. This is the membership boundary, without replacing the existing source-reading implementation.

Once configured, the input owners are a fixed set: ordinary documents, Works and Processing. Their document membership remains dynamic as documents are created or removed, and each stage contributes the documents present there. There is no manually maintained fixed list of document IDs and no dependency on reading the search index.

For this delivery, preserve the existing source readers, date basis, ordering, limit, payload shape, navigation and refresh ownership. The outcome is correct coverage. Metadata-only reads, reuse of compact generated manifests, and other scan-efficiency changes belong to the separate build-time review; no performance redesign or benchmark is required here.

## Design Direction

Represent the three search decisions independently in collection policy, with site search and Recents consuming the same inclusion decision. Keep membership selection separate from query matching and ranking. Reuse the existing full-text extraction and query engine for readable collections, while letting each search surface select its exact corpus. Separate collection indexes loaded on demand are a candidate design; choose their physical layout and shared build work during delivery specification rather than freezing that architecture here. Editorial stars form a separate selection across all collections.

Catalogue should use a compact generated search projection of its selected fields, linked to the exact collection document and canonical Work identity. Resolve Series and Medium from their authoritative Catalogue fields. Search should not fetch every document body or scrape rendered content to reconstruct metadata. A Medium filter should preferably use a structured classification such as `medium_type`; confirm whether readers also need the descriptive `medium_caption`.

For Catalogue, start with an empty result list and show a bounded page of matches after a query or useful filter selection. Decide separately whether to load the compact search data on opening or on first use. Distinguish initial transfer and parsing, query work, and result rendering when assessing speed. Payload measurements identify plausible costs, but browser responsiveness has not been measured and no performance target is yet agreed.

Preserve exact stage, collection and document identity when opening results. Site-search inclusion changes retrieval membership, not publication eligibility. Working, Preview and the public projection retain distinct owners; prepared snapshots must contain the appropriate search artifacts without exposing local-only data. Specify refresh and build ownership for new indexes explicitly, preserving the current separation between ordinary document saves and explicit Search rebuilds.
