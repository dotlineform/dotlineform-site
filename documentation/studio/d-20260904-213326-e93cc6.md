# UAC 3 - Findings

## Purpose

Record significant evidence from [UAC 3 - Explore Tokens, Reports And The Consumer Data Model](/docs/?scope=studio&doc=d-20260904-204816-0f31be) without turning the delivery record into a discussion transcript. Number findings permanently. Update their status and resolution in place as the concept develops.

A finding states observed behavior or an accepted consequence. Keep unresolved design choices under **Open questions**. Do not convert an observation into an implementation requirement until the user accepts the resulting direction.

## Major Findings

### F1 — Associated Documents Need Two Inputs

**Status:** confirmed current behavior; target composition unresolved.

A Catalogue entity can be connected to an Analysis document in two different ways:

1. the document declares the exact entity as its subject; or
2. the document body contains a semantic token referencing the exact entity.

These are separate generated products today. A sub-scope subject-associations.json groups exact subject declarations. The scope-level semantic-tokens/index.json records resolved token occurrences. Existing Catalogue document-URL enrichment uses accepted subject declarations only; it does not combine semantic-token references.

The current semantic-token occurrence index is also incomplete for a future Analysis-wide association list. A Series 001 token inside [10,000 - original text](/docs/?scope=analysis&stage=working&doc=d-20260801-073826-8865a8&subdoc=d-20260801-212422-3aa736) renders successfully but is absent from the scope-level occurrence index. The same token pasted into the top-level [Insert Subject Link](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-be8979) document is recorded there. The current index therefore cannot by itself answer “which Analysis documents refer to this Catalogue entity?”

**Implication:** the proposed associated-document list, currently called doc_urls[], needs a composed, deduplicated union of accepted public documents that either declare the entity as their subject or contain a resolved semantic reference to it. If one document supplies both forms, it appears once. The relationship retains exact {scope, sub_scope, doc_id} identity and must not select a definitive document.

**Open questions:**

- Which Analysis Build/Publish artifact owns the composition?
- How are top-level and sub-scope token occurrences brought into one complete input?
- Does the same association contract cover Work, Series and Work Detail, or do their consumer needs differ?
- Which token presentations count as document association evidence?
- At what point is the union filtered to the accepted public document set?
- Is doc_urls[] still the right consumer name and shape?

### F2 — Catalogue Tokens Need New Destinations

**Status:** token value retained; legacy destinations must change; subject-assigned documents are the likely replacement.

Current Catalogue Work and Series semantic text tokens resolve entity identity through the private target lookup, then render links such as /works/?work=00523 and /series/?series=001. [Add Catalogue Token](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-4236e7) and [Insert Subject Link](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-be8979) demonstrate these destinations. They belonged to the previous Catalogue site and are not the new document presentation.

**Finding:** existing tokens remain worthwhile. They must stop producing old-site links; the user's current direction is most likely documents whose exact subject matches the entity. The final destination and selection UI remain open for full-data review. [Catalogue Media View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) remains the accepted image presentation, and token responsibilities may differ by entity and presentation.

**Separate authoring decision:** the experience provided by a token does not determine how the author selects that experience. One model uses a general Catalogue token whose editing modal includes destination options such as `Go to document` and `Open Media View`, alongside presentation fields such as link text. The other model provides distinct document-link and Media View token types whose destination behavior is intrinsic. Both could produce the same reader-facing result, but they create different token grammar, editing, discovery and validation requirements.

**Open questions:**

- Which token forms open Media View and which link to documents?
- Can Media View present both an exact Work and an exact Detail, and what is the Series equivalent?
- When a token links to a document, how is that exact document chosen without a first-association or canonical-document fallback?
- Should the author configure the destination within a general token, or choose a distinct document-link or Media View token?
- If the token types are distinct, which presentation fields and validation rules belong to each one?
- What context and return state should Media View receive when it is opened from an inline token?

Treat subject-assigned documents as the likely direction, not a settled automatic routing rule. Do not choose the first association, infer from document titles or invent a canonical document. The answer must follow the token's intended experience and entity type.

### F3 — Work References Need Three Reader Experiences

**Status:** working direction; token grammar and authoring presentation open.

Three reader experiences are sufficient for references to a Catalogue Work:

1. **Document link:** link to one explicitly selected document whose subject identifies the exact Work. The authoring surface can list the documents with that `work_id` subject and the author selects the intended destination.
2. **Media View link:** open the exact Work's image and metadata in Media View without redirecting the reader to another document.
3. **Inline Catalogue Image:** render the Work image and metadata within the current document content. The rendered result may be a static image presentation rather than an interactive destination.

The document chooser has a narrower purpose than the associated-document composition in F1. A document becomes a candidate destination because its subject declares the exact Work; merely containing another semantic reference to that Work does not make it a document specifically about the Work.

This three-option boundary describes the reader experience. It does not yet decide whether authors choose among three distinct token types or select one of three modes within a shared Catalogue insertion flow.

**Invariant:** none of the three experiences requires or creates a canonical document for a Work. A document-link token records the author's exact destination choice for that occurrence. It does not make the selected document the Work's default, definitive or fallback presentation. Media View and inline Catalogue Image operate directly from the exact Catalogue identity without passing through a document.

**Open questions:**

- How should the document chooser account for a subject document that exists locally but is unavailable in the intended published context?
- Does the same three-option boundary apply to Series and Work Detail references?
- Which image and metadata fields are embedded in an inline Catalogue Image, and when are they resolved?
- What names make the three choices clear in the authoring interface?

### F4 — No Per-Entity JSON Change Has Been Demonstrated Yet

**Status:** accepted basis for moving to Stage 4; revisit only for a demonstrated consumer need.

None of the three Work-reference experiences in F3 currently requires a structural change to the representative Catalogue Work JSON:

- The document-link chooser reads exact document subjects and available document locations. The selected document belongs to that token occurrence, not to the Work record.
- Media View can use the existing Work identity, title, descriptive metadata, image dimensions, media version and nested Detail records. Media locations can be resolved through the accepted Catalogue media-path contract.
- Inline Catalogue Image can use the same fields and may compile them into static document output.

The existing `documents` array can already carry `{url, title}` entries. F1 may change which accepted associations populate that array and which product owns the composition, but that is a projection-content change rather than a demonstrated record-shape change. A schema change would become necessary only if an accepted consumer needs information the array cannot express, such as association type or exact document identity beyond its public URL.

There is no immediate need to change the Catalogue consumer JSON for Docs use. This does not freeze it against a demonstrated full-data need or cancel the agreed canonical/editor simplification of membership and publication states.

### F5 — The Simple Work Media View Is An Accepted Reference Presentation

**Status:** accepted architectural proof; minor visual refinements deferred.

[Media View - Work 00523](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-9892a8) proves that an ordinary Analysis document can open an exact Catalogue Work presentation and return to its own browsing context without turning the Work into a document. The view uses one immutable supplied payload and presents the primary image, title, year, medium, physical dimensions and Catalogue number. Open in new tab targets the media object directly; no legacy Work route or canonical document participates.

The representative `work_record_v5` JSON contains enough information for this first single-Work view. No missing or awkward field blocked the accepted presentation, so the proof adds evidence to F4 rather than establishing a by-ID schema change. The browser-ready payload remains a projection shaped for the view; the temporary HTML marker is not accepted token syntax or an authoring contract. The shared adapter is registered in public and Manage, its tracked public projection is current, and site validation passes.

**Implication:** use the real Media View as the reference point for the remaining token, gallery, report and consumer-data decisions. Minor styling and design changes can be made later without reopening the identity or data-ownership result. Series, Work Detail, sequences and richer consumer cases may still expose data-model needs that this single Work does not.

### F6 — Galleries And Work Lists Serve Different Reader Purposes

**Status:** accepted design finding.

| presentation | reader purpose | interaction |
| --- | --- | --- |
| thumbnail gallery | casually browse many Works visually | open images and continue browsing inside the same Media View context |
| Work list/report | find a specific Work using visible metadata, such as year, and search | expose separate Media View, document and file actions from the same visible row when those destinations exist |

These are distinct responsibilities, not merely two layouts with an identical click destination. A Work list row identifies one exact Work and may offer several actions simultaneously. It must not make one document definitive, invent a file destination or require the reader to enter Media View to reach another available resource.

Thumbnail galleries belong only inside Media View. Gallery Lists are appropriate for insertion into ordinary documents and require a new toolbar insertion button. The gallery and list can share Catalogue identity, membership, descriptive values and media presentation. Their visible information, controls and navigation responsibilities differ. Report search/filtering is a collection interaction; it does not by itself require changes to the global Docs Search index.

**Evidence and follow-on:** UAC 3B implements a Works-in-Series list through the existing Report Block infrastructure. Refine the production insertion, selection and row actions with the full generated Catalogue after Stages 4–5. Existing private Studio reads and old Catalogue-route links are not the new consumer contract.

**Open questions:** which fields belong in the first visible row, how available document/file actions are supplied, and which explicit gallery context accompanies a report's Media View action.

### F7 — The Small Series Gallery Is Accepted Working Code

**Status:** accepted interaction and data example; production loading remains open.

The user accepted [Media View - Series 143 Gallery](/docs/?scope=analysis&stage=working&doc=d-20260906-164429-756174). Its two thumbnails open Works `01941` and `01942`, and the Series metadata link returns to the gallery inside one Media View. The supplied set distinguishes an exact entry target from the Series and its ordered members.

The prepared Series and Work JSON supplied the values needed for this example without a structural record change. This adds evidence to F4; it does not settle future document/file actions or prove large-gallery performance. The shared runtime is maintained working code. Its hand-supplied embedded data and local thumbnail references remain explicit test inputs to replace when the public loading and projection workflow is decided.

### F8 — Works Remains The Public Collection Name

**Status:** accepted naming decision.

Retain `analysis.works` and the public name **Works**. Catalogue remains the internal domain term for Works and Series. Mixed Series/Work subjects do not require a collection rename or a separate public Catalogue collection.

**Consequence:** retain existing collection paths, document URLs, report-host identity and Copy-to-Analysis targets. Subject-field support and future report, token and Media View behaviour do not require a naming migration.

### F9 — Detail Subjects Use The Composite Identity Directly

**Status:** implemented in UAC 3C; the user confirms subject editing is available in Projects and Analysis Works. Specific branch review items remain separately recorded.

The subject choices are none, a real Folder only in `dotlineform`, `series_id`, `work_id` or `detail_uid`. The existing field-based model gains Detail subjects; the earlier common `subject`/`cat_id` proposal is replaced.

`detail_uid` encodes `<work_id>-<detail_id>`. Docs Viewer can obtain both exact IDs by parsing, with no formal ownership lookup. Studio owns the data-quality contract. Detail describes structure, not importance: the user's Series `023` example has one printed-list Work and 523 independent photographs recorded as Details.

**Consequence:** [Catalogue Data Model](/docs/?scope=studio&doc=d-20260903-231534-b63aa9) owns these rules. [Gallery List Design](/docs/?scope=studio&doc=d-20260905-141447-f72ef3) can use a Detail subject's encoded Work context without changing that subject or adding an ownership lookup.

### F10 — Further Refinement Needs The Full Catalogue

**Status:** accepted sequencing decision, 5 September 2026.

The small examples have established enough to begin Stage 4. Meaningful selection UI and identification of difficult Works and Series now need the full Catalogue. Proceed with canonical data and editor simplification, then replace the examples through the Stage 5 output workflow and coordinated reader switch. Revisit the unresolved consumer questions using that complete data. This does not mark every Stage 3 design item or branch review complete.
