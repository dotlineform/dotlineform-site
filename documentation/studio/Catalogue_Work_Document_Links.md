# Catalogue Work IDs and Portable Docs - Proposed Delivery

This proposed delivery belongs under [Planned Features](Planned_Features.md). In Work Media View, `cat. <work_id>` opens the definitive Catalogue collection document in a new browser tab while the invoking document and Media View stay in their original tab. Every current Work has exactly one definitive Catalogue document. Its five-digit Work ID becomes that document's one immutable `doc_id`; this replaces the current generated `d-...` identity rather than adding an alias or a Work-to-document lookup. Gallery Media View needs no document target until a Work is selected.

## Requirements

- Use the exact five-digit Work ID throughout the Catalogue document's identity: `00001.md` in source, `doc_id: "00001"` in front matter, `by-id/00001.json` in generated and public output, `doc_id: "00001"` in the collection manifest, and `subdoc=00001` in the viewer route. Quote the front matter value so leading zeroes remain part of the string. Retire the separate Catalogue source and manifest `work_id` fields; Work association and Catalogue report Work-ID search derive from the single `doc_id`. Keep `added_date`, `last_updated`, title, body and Links as document facts, not as a second identity.
- Keep `d-...` IDs for ordinary and other collection documents, including the ordinary Catalogue report host. Validate five-digit child IDs only in the exact Catalogue collection context; do not make numeric IDs valid for all Docs documents. Shared targets that contain `{collection, doc_id}` retain both parts, while the child `doc_id` is the Work ID. Source, Build, routes, Links, Search, Recents, Selected Documents, report readers and public projection must accept that exact Catalogue identity without a compatibility alias or a legacy-ID fallback.
- Re-key the existing Catalogue source files and their `doc_id` front matter in one explicit migration. Preserve each Work's current title, `added_date`, `last_updated`, `draft` and body, including its generated Catalogue image token; remove its redundant `work_id` front matter. Reconcile generated by-ID files, manifests, links and stored exact targets under the new IDs, then build the derived readers against that identity. The old `d-...` Catalogue IDs do not remain as parallel documents or routes. Any authored or already distributed direct links to old child IDs need to be identified before the cutover; do not silently redirect them through a lookup.
- Catalogue Regenerate creates, updates and deletes the document whose ID equals the exact Work ID. Pending targeted Build selects that same ID; Full reconciliation inventories by Work ID. A current Work without its definitive document is an error to repair in the owning source flow, not a normal optional lookup case.
- Keep the generated Catalogue image token and its existing rendering, including Work-derived alt text, caption, metadata and Media View activation. A Catalogue document's token targeting its own Work ID is a self-reference and does not contribute an occurrence to the semantic-token usage index. A token in that document targeting a different Work, or a Gallery, still contributes an occurrence. Other collections and ordinary documents keep their current occurrence behavior. After the identity cutover, compare the Catalogue document's `doc_id` directly with the token's Work target ID; the token target remains necessary rendering input, not a second document identity.
- Catalogue documents always have required `draft: false` front matter. Hide their Draft control, reject Catalogue Set Draft requests and reject Catalogue source with `draft: true` when read for an owning write or Build. Regenerate creates ready documents and preserves that state on updates. Other collections keep their existing draft controls and identity rules.
- Expose the configured Catalogue report host ID to the public reader. Media View composes a standard new-tab URL from the current viewer base, that host ID and the Work ID, without fetching a mapping file or the Catalogue list manifest. The destination `?doc=<report-host-id>&subdoc=<work-id>` loads the exact by-ID document before any list manifest. The normal Catalogue list still loads its manifest for search, sort and pagination.
- Remove redundant `viewer_url` from ordinary and collection by-ID JSON. Represent internal Docs links in rendered `content_html` by root-independent document targets; local and public runtimes compose their own viewer routes. Preserve authored external links. Static Export and Review must resolve internal targets for their own destinations.
- Keep Docs-owned media in document payloads as logical identities without a local served URL or R2 URL. Expose one Docs media served root in each local/public browser configuration and resolve identities before mounting content, including images, SVG, files and HTML media. Keep the existing source token identities and resolve media explicitly for static Export and Review.
- Align public Docs-owned media object paths with the local suffixes: `media/workspace/<type>/<identity>` for ordinary documents and `media/collections/<collection>/<type>/<identity>` for collection documents. The local served root remains `/docs/assets/media/`; the public root is configured on R2. Change public object locations, URL configuration, transfer inventory and readers together. Include Moments media currently under `sub-scopes/moments/media/`; retain no `sub-scopes` compatibility alias. Studio-owned Catalogue Work images and downloads keep their separate media ownership.
- Keep Preview Build in the publication workflow. Catalogue documents have no individual draft exclusion, while their ordinary report host and existing publication rules still govern collection inclusion. This delivery does not decide whether Preview can reuse more Working output or redefine why that Build exists.

## Public Payload And Path Decision

The present public Catalogue `manifest.json` is 757,411 bytes for 4,616 Works; the Working management manifest is 1,685,326 bytes. With Work ID as `doc_id`, Media View needs no additional Work-to-document payload. A direct child link should request the report host, the selected by-ID document and ordinary viewer assets, with no Catalogue list manifest. The full manifest remains available when browsing the searchable list. These local file measurements make no claim about GitHub Pages latency; assess the complete public site after publication.

The current Preview semantic-token usage index is 2,077,601 bytes with 4,626 occurrences: 4,616 generated Catalogue Work image tokens and 10 Work references in the `works` collection. All 4,616 Catalogue image tokens use the same presentation settings. The index is retained in Preview but the current repository publication projection does not copy it to `site/`, so its size is a Build/Preview and Working-report cost rather than a public browser download. The Working Semantic Tokens report resolves a generated source payload for each distinct indexed document. Keep the token renderer and generated Catalogue body intact; omit only self-targeting Catalogue Work tokens from the usage index. A complete Catalogue Build replaces the existing saved Catalogue self-reference rows while retaining genuine Catalogue references and other collections' occurrences.

Today a local Moments image is served from `/docs/assets/media/collections/moments/img/<identity>`, while its public counterpart is served from `https://media.dotlineform.com/docs/analysis/sub-scopes/moments/media/img/<identity>`. Ordinary public media similarly lacks the local `workspace/` segment. The target public URLs are `https://media.dotlineform.com/docs/analysis/media/workspace/<type>/<identity>` and `https://media.dotlineform.com/docs/analysis/media/collections/<collection>/<type>/<identity>`. The suffix then identifies the same Docs-owned bytes under either configured root. Root-independent viewer links and media identities remove these local/public URL differences from by-ID JSON without removing Preview Build.

## Deliverables

- One-time Catalogue document re-key from generated `d-...` IDs to exact Work IDs across source front matter and filenames, by-ID output, manifests and dependent exact targets. No lookup file, old-ID alias or parallel Catalogue identity remains.
- Existing Catalogue image-token rendering and source bodies retained, with only self-targeting Catalogue Work tokens omitted from the semantic-token usage index. A complete Catalogue Build clears their existing rows while preserving cross-Work, Gallery and other collections' usage.
- Catalogue-specific ID validation and Regenerate/Build behavior, public report-host configuration, a direct child-document route that avoids the list manifest, and a new-tab Media View Catalogue-number link.
- Catalogue Draft control removal and enforcement of `draft: false` while retaining the shared front matter field and other collections' existing behavior.
- Root-independent by-ID Docs viewer links and media identities, with the route and media root chosen by the consuming runtime. Update Search validation and static Export/Review handling where those contracts consume rendered content.
- Public Docs media destinations matching the local `workspace/` and `collections/` suffixes. Inventory existing referenced R2 objects, transfer bytes to their new keys, update public references and verify transferred bytes before retiring old configured paths. Include Moments without a `sub-scopes` alias.
- Updated durable [Catalogue Media View](Catalogue_Media_View.md), [Media and Asset Handling](Media_And_Asset_Handling.md) and collection/publication owner documents after implementation. This proposal does not itself change executable behavior or authorize Publish, Deploy Public, commit or push.

## Process

1. Studio Refresh generates changed Work records and updates the private pending list as it does now.
2. Catalogue Regenerate uses each Work ID as its document ID when creating, updating, deleting and selecting documents for Build. The one-time cutover replaces old Catalogue source identities first and rebuilds their generated readers; later ordinary Catalogue Builds continue with Work IDs.
3. Docs Build emits root-independent viewer and media references. Local Docs resolves them under local roots, while public Docs resolves them under public roots. Publish continues to run Preview Build and transfers referenced Docs media into the matching public `workspace/` or `collections/` path.
4. Work Media View already knows the exact Work ID, so it constructs the Catalogue document route directly and opens it in a new tab. The destination opens by ID; opening its searchable list loads the manifest then.
