# Catalogue Hosting And Storage Options

## Current Baseline

Studio serves the existing Works editor and owns validated Catalogue mutations. Git-tracked `studio/data/canonical/catalogue/` holds aggregate canonical Work, Series, Gallery and membership files. Save currently produces Working Catalogue JSON in the configured Docs workspace and local media in shared assets. Docs Publish prepares and distributes selected Catalogue JSON with its document snapshot; `site/` hosts public JSON and configured R2 holds referenced primary images and downloads. [Catalogue Save And Refresh](Catalogue_Save_And_Refresh.md) owns the nearer Save optimization and explicit local Refresh proposal. [Catalogue Deployment](Catalogue_Deployment.md) owns the current public path.

These are future architecture decisions, not prerequisites for implementing Save/Refresh. Each needs its own bounded delivery and evidence before storage or hosting changes.

## Local Editor Hosting

| Choice | Benefit | Cost or decision to resolve |
| --- | --- | --- |
| Keep the Studio page and server | Least migration work; existing editor behavior and services stay in place. | Two local server/shell experiences remain. A later move repeats integration work. |
| Host the existing Works editor beneath the Docs Viewer toolbar on one local server | One local entry point while preserving the editor's Series browser, Work panels, modals and services. The Docs shell owns placement and outer chrome. | Adapt page bootstrap to mount/release a view, compose request handlers, contain styles, and preserve unsaved/busy navigation protections. Public Docs must not acquire editor code or mutation capability. |
| Native Swift host | Could share the native application's navigation and local presentation. | Requires a separate Mac/iPad product and service-boundary decision; no native editor design or performance case is accepted here. |

The one-server Docs view is the intended direction from the prior discussion, but it has no approved implementation sequence. The Save/Refresh service boundary can be built in the current host and reused by a later host. Avoid a second copy of editor business logic or transitional request aliases.

## Canonical Catalogue Storage

| Choice | Benefit | Cost or decision to resolve |
| --- | --- | --- |
| Keep aggregate Git-tracked source files | Existing history, validation and multi-record transaction owner remain. One bulk write can replace each affected aggregate once. | A selected read or edit can still load and rewrite a large aggregate; moving generation out of Save does not remove this source cost. |
| Move complete canonical Work/Series records to exact by-ID files beneath the configured Docs `working/source/` | Selected records could be read and written directly, and a Working reader could expose direct source fields immediately after Save. | Requires migration/history/backup ownership, exact Gallery and membership authority, coordinated bulk writes, whole-corpus validation/search strategy and a public-safe projection. Derived indexes and relationships still need Refresh. |

Existing generated by-ID JSON cannot become canonical unchanged: it omits authoring fields such as project-media references and storage context and includes calculated presentation values. If by-ID source is chosen, preserve one editable authority, explicit exact IDs and path confinement; do not add fallback reads to the old aggregate files. Compare actual Save cost and recovery behavior before claiming a performance gain. [Catalogue Source Model](Catalogue_Source_Model.md) remains current authority until a migration is delivered.

## Public JSON Hosting

| Choice | Benefit | Cost or decision to resolve |
| --- | --- | --- |
| Keep JSON in tracked `site/` on GitHub Pages | Uses the accepted Preview-to-repository Publish path and static reader URLs. | Repository size and deployment timing remain coupled to public JSON; no measured limit currently requires a change. |
| Move public Catalogue JSON to R2 | Could decouple large JSON storage from the tracked site artifact. | Requires destination and URL configuration, public access/CORS, cache and revision rules, coherent releases with Docs/JSON/media, verification and recovery. A second distribution implementation must not appear implicitly. |

Primary media and downloads already have configured R2 destinations; this option concerns public Catalogue JSON. Keep private Catalogue Works report metadata and Works collection title metadata out of public distribution unless a separate public-safe contract is approved. Public browser filtering and pagination remain front-end concerns, not a reason to add request-time server queries.

## Decision Order

Complete the local Save/Refresh boundary first, including measured costs and actual editor/report dependencies. Then decide editor hosting from the accepted view/service seam, canonical storage from observed source I/O and recovery needs, and public JSON hosting from measured repository/hosting constraints. The old standalone Studio report Publish and pending-publication-ledger proposal is superseded by the current single Docs Publish lifecycle; it is not an option to revive by implication. [Related Galleries](Related_Galleries.md) depends on Save/Refresh, not on a hosting or storage migration.
