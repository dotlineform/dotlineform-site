# Publishing Workflow - Stage Structure And UI

## Requirements

Put the existing Working and Analysis content into the structure described by [Publishing workflow concept](/docs/?scope=studio&doc=d-20260906-141142-5200b2), and make both stages usable in the live application. The complete result is stage-aware browsing, document creation/editing/deletion in Working, and refresh of existing sub-scope reports. Pre-publish remains read-only for document authoring. This gives the user a concrete basis for deciding what each stage and its promotion action should do.

Preserve document IDs, content, metadata and sub-scope membership. Stage is separate from document identity and sub-scope. Other scopes keep their current layout and single selected view. Analysis `published/` stays in place and unchanged.

**Required scope identity:** when `dotlineform` is retired, Analysis takes its existing `䷑` icon in the scope selector. Use that exact icon for the Analysis option and selected-scope display, in both Working and Pre-publish. Remove the retired `dotlineform` option. This icon transfer is part of this delivery and must not wait for the broader UAC 3 icon review.

Working must support creating, editing and deleting both ordinary and sub-scope documents through the existing document tools, with the required generated follow-through. Reads, writes and refresh requests retain the exact stage and collection target. In this initial delivery, Delete acts within Working only, including the existing selected-document/descendant rules. It does not delete Pre-publish counterparts, alter the accepted snapshot or trigger public-site/media cleanup. This is a temporary delivery boundary: the concept's agreed deletion cascade will be implemented with the publishing actions. A derivative remaining in Pre-publish after a Working deletion is accepted during this interim period.

Pre-publish rejects document creation, editing and deletion at the service boundary as well as hiding those controls. Existing sub-scope reports can be refreshed in either stage against that stage's data; refresh does not author Pre-publish source or promote Working content. All continuing investigations into tokens, reports and editing tools take place in Working. Pre-publish needs basic display and read-only verification here, not a content-review or investigation workflow.

All migration folder creation and file moves in the real iCloud-backed scope workspace are performed manually by the user. Codex supplies the move map and implementation, but does not create migration folders, move or rename files, delete retired directories, or make fallback copies. The user and Codex do not edit scope files during the same period as the manual migration.

This delivery does not implement or redesign Pre-publish, Publish or Copy to Analysis, and does not implement deletion cascade. Promotion controls are unavailable in the new stage views, and old operations must not write through retired paths. Semantic-token definition and insertion, Catalogue-provider integration, report redesign and specialised subject tools remain deferred. Their limitations must not remove ordinary document creation/editing/deletion or existing sub-scope report refresh from the completion requirements. Editing preserves authored token text without requiring the new token design. No Catalogue schema change, publication filtering, Folder-subject removal, sanitisation, Search redesign, public content deployment or native App integration is included.

## Process

The user selects Analysis and uses Working for ordinary authoring and subsequent token/report investigations. Working supports browsing and Create/Edit/Delete for ordinary and sub-scope documents; completed writes update its generated output. Delete has no cascade in this delivery. Pre-publish is available as a read-only view of its separately migrated content and is not the continuing investigation surface. Refresh on an existing sub-scope report updates that stage's report through its current mechanism. Neither stage reads another stage as a fallback, uses `published/` as a third stage or promotes content yet.

Codex prepares repository changes and a concrete migration handoff. Before the user starts moving files, scope-file edits and affected watchers/builders are paused. Codex explicitly hands over; the user creates folders and moves files without concurrent Codex scope edits. Codex waits for the user's completion message, checks the new locations read-only, then activates the stage configuration and resumes agreed scope work. Elapsed time or partial folder visibility is not permission to resume.
