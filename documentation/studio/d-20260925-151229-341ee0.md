# Catalogue Authoring In Docs Viewer End State

Status: architectural exploration. Moving the Work editor into Docs Viewer remains an open decision. This document explores a coherent end state and the data boundaries that would make it possible; it does not authorize runtime implementation, storage migration or changes to current Save completion.

One requirement is now settled: **Catalogue Works means “what I have saved”.** It must show the saved Catalogue independently of any later review or public deployment. What is publicly available is already represented by the public Catalogue. A second internal meaning of “published” obscures that distinction.

This document develops [Catalogue Reports Shared Front-End Browsing And Search](d-20260925-134621-42c838.md). The [Catalogue Save And Publish Action Map](d-20260925-144813-17e45c.md) records current implementation and the earlier proposed standalone report-generation operation. Its observed Save rows remain current evidence. Its proposed Publish terminology and manual-only report refresh are subject to the clarified direction here.

## The End State In Use

The author opens Catalogue Works in Working, finds a Work and opens its editor within the same application. The editor loads the exact saved canonical record. Unsaved edits belong to the editor session; saving updates the canonical record and the Working data needed to find and display that Work. Returning to the report shows the saved values without another user action called Publish.

Review shows a prepared reader snapshot. Further Working edits do not silently change the snapshot being reviewed. Deployment distributes the selected reviewed revision, and the public Catalogue continues to represent the deployed content until that process completes. One Work may therefore have a newer saved revision than the one visible publicly, without either view being misleading.

For example, change a Work title from “Study A” to “Study B” and Save. Catalogue Works then lists and searches “Study B”. An existing Review snapshot and the live public Catalogue can still contain “Study A”. Preparing a new snapshot makes “Study B” available for Review; only the subsequent public release makes it the public title. Merely generating a local index has not published the change.

| Surface | Meaning of the data | Authority / input |
| --- | --- | --- |
| Work editor in Working | The saved Work plus its current unsaved form changes. | Canonical Work record and exact related canonical identities; unsaved state stays in the editor. |
| Catalogue Works in Working | The latest saved Catalogue, including Manage metadata needed by the report. | Generated Working reader data derived from saved canonical records. |
| Working Catalogue document collection | Current Working documents and their exact Work associations. | Working document sources/projections plus appropriate saved Work reader data. Work and document refresh ownership must be explicit. |
| Review | The prepared content being inspected for release. | A fixed reader snapshot, including its Catalogue dependencies. |
| Public Catalogue | Content actually available to public readers. | Deployed public document and Catalogue reader files. |

Saved Works and public Catalogue documents need not have identical membership. A saved Work can exist before its Catalogue document, and document eligibility can exclude a Work's public presentation. Common reader code and exact identities do not require every surface to show every saved record.

## Give Each Operation One Meaning

The current Studio/Docs Viewer split has allowed “published from Studio” to mean that Catalogue files have been generated for another local consumer. That is a generation boundary, not public publication. A generated file can be current, useful and ready to read while remaining wholly inside Working.

The terminology should follow the distinction already made in the Docs Viewer workflow by moving away from calling internal preparation Publish and describing the review step as Review. Reserve “published” for content made available on the public site. Describe internal preparation by the work it actually performs.

| Term | Intended meaning | Boundary |
| --- | --- | --- |
| Save | Persist editorial changes and complete the Working refresh required by that save operation. | Unsaved editor state becomes saved canonical data and current Working report data. |
| Generate / Build / Regenerate | Produce replaceable reader files, indexes or media from their owning inputs. Use the appropriate existing operation name for the specific task. | A transformation inside a lifecycle stage; no implication of public availability. |
| Rebuild Catalogue Works | Suggested name for an explicit development or recovery control that regenerates the report dataset from saved records. | Repairs or exercises the same generator; it is not a second acceptance step after every Save. |
| Review | Inspect a prepared reader snapshot before release. | Reviewable content remains separate from live Working changes and public availability. |
| Prepare Preview | The current technical preparation operation that creates the snapshot to review. | Produces `preview/`; it does not make that content public. |
| Deploy Repo | Distribute the prepared revision to its configured repository and media destinations. | A concrete release preparation/distribution operation, distinct from completion of the public-site deployment. |
| Publish / published | Make content available publicly / describe the content actually available publicly. | Public release, not a synonym for a local JSON write or an internal handoff. |

Review is the workflow meaning; `preview/` can remain the snapshot's storage name. This proposal adds no `review/` storage stage and does not rename existing code, endpoints or controls. It also does not merge this publication-review step with the separately owned Docs Review package workflow. Exact UI labels can be settled in their implementation delivery without giving internal generation another meaning of Publish.

## Canonical And Generated Data Both Remain Necessary

Hosting the editor and report together does not remove the distinction between editable source and data prepared for reading. The editor must read the exact canonical record and save through its validated authoring owner. Catalogue Works should read a compact generated representation suitable for listing, filtering, sorting and pagination. A dedicated source-inspection tool may legitimately inspect canonical records, but it has a different purpose from ordinary browsing.

The earlier statement that Docs Viewer should not consume canonical data needs that qualification: **ordinary reader components should consume reader data; authoring components must access their canonical source.** The application shell can host both. A component's responsibility determines its data access, rather than whether it lives under a folder named Studio or Docs Viewer.

Reading statically served canonical JSON in the front end is technically possible. It would still couple the report to the editable schema and require repeated selection, joining and normalization when the report opens. Moving the canonical files to `docs-viewer/studio/` alone would not address those costs. A generated projection can preserve exact saved values while changing their physical arrangement for efficient reading.

The generated report files are replaceable derived data. They never become a second editable authority. Save owns the required freshness; the report does not generate files, query canonical data on the server, or fall back to canonical reads when its inputs are missing or invalid.

The public and Manage readers should share common fields, identity rules and front-end behavior. Manage-only metadata can be an additional projection keyed by exact Work ID. Public hosting receives only the appropriate public data. Sharing the reader model does not require placing private metadata in public files or maintaining separate search implementations.

## Data Boundaries Before Folder Names

`studio`, `catalogue`, `working` and `preview` do not describe four equivalent data stores. They describe different aspects of the system.

| Name / distinction | What it owns | Consequence for an integrated design |
| --- | --- | --- |
| Studio / authoring | Editing capabilities and the components/services that implement them. | Can remain a code boundary without owning a separate lifecycle or canonical copy. |
| Catalogue | Work, Series and Gallery records, relationships, media references and their reader projections. | Is a content domain within the lifecycle. |
| Working | Editable source and current replaceable generated data. | Contains both canonical Catalogue data and its current reader projections in a logically unified model. |
| Preview | The completed prepared snapshot used for Review. | Contains captured reader data and necessary dependencies, with no persistent editable source tree. |
| Public deployment | The released files and media served publicly. | Remains an explicit destination and release boundary. |
| Source versus generated | Editable authority versus reproducible output. | Exists within Working; generation does not create another publication stage. |
| Manage versus public | Authoring capability and metadata exposure. | Controls which components/files a surface receives; it is not a second Work identity or an extra lifecycle stage. |

An unsaved editor draft is different from saved source marked as a draft for publication eligibility. “Saved” does not mean “eligible for release”. The current document `draft` and exclusion policy remains its own authority; this exploration does not introduce a new Catalogue Work publication flag.

## Possible Unified Storage Shape

The following is a schematic future workspace, not the current directory layout or an approved path migration. It illustrates ownership, preserves collection-owned document areas, and leaves exact registration and media layout for a later decision. The workspace is configured user data, separate from the application code/install directory.

```text
<configured workspace>/
  working/
    source/
      documents/…
      collections/…                  collection-owned document sources
      catalogue/
        works.json                   canonical Work records
        series.json                  canonical Series definitions
        galleries.json               canonical Gallery definitions
        galleries-by-work.json       canonical Gallery membership
    generated/
      documents/…
      collections/…                  document manifests, by-ID bodies, associations
      catalogue/
        works/…                      shared Work reader data
        series/…                     shared Series reader data
        galleries/…                  shared Gallery reader data
        reports/
          catalogue-works/…          report metadata/indexes if still useful

  preview/
    documents/…
    collections/…
    catalogue/…                      eligible public reader dependencies

<configured public destinations>/
  site document/Catalogue files
  public media
```

There is one canonical copy of each record. A `studio/` folder may still house authoring code, but it is not needed beside `working/` and `preview/` as another content state. `catalogue/` sits within the source/generated/snapshot distinction because it names the domain. Manage-only enrichment is not copied into the public snapshot.

Physical consolidation is optional until it has a clear benefit and an agreed migration. Today Catalogue source is repository-owned under `studio/data/canonical/catalogue/`, generated Catalogue files are in the Projects workspace, and Docs source/generated/Preview data use the configured Docs workspace. A shared UI and an explicit generated-data contract can be introduced while those roots remain separate. Moving authoritative records out of the repository would also require an explicit decision about version history and recovery.

Original project media and temporary derivative staging are not automatically moved into this proposed tree. Their configured ownership can remain external. A complete integration design must identify which media are reusable source, disposable staging or reader dependencies, and how the reviewed revision resolves them.

Catalogue Work records and Catalogue documents remain different entities. `work_id` identifies a Work; `doc_id` identifies a document. The existing Works document collection is also distinct from Catalogue's canonical Work records. Folder co-location must not turn those into aliases or duplicate canonical ownership. Exact generated associations continue to connect a Work to its document when one exists.

## Save And Working Freshness

The target requirement is observable: once a Work Save completes successfully, opening or reloading Catalogue Works must list and search that saved record without a separate build or publication action. Work creation/deletion and relevant Series/Gallery changes must refresh the projections they affect through their own owning mutations. Unsaved editor changes do not appear in the report.

A focused generator should own that projection independently of the UI. The owning Save operation can call it, while a development/recovery control can invoke the same generator directly. Complete generation and targeted updates are implementation choices to assess against actual cost; neither requires a persistent pending-publication queue for a Working report.

If canonical persistence succeeds and required report generation fails, the outcome must say that the data was saved but the Working report refresh is incomplete. Old generated data must not silently present itself as the confirmed current saved state. The exact revision/freshness check and whether the report blocks or explicitly marks stale output remain design decisions. Merely checking that two report files agree with each other does not prove they reflect the latest Save.

The report's metadata and index may remain separate files, or become shared Catalogue projections when other consumers adopt their contract. Per-report indexes are acceptable where they improve reading. The durable boundary is canonical input → owned generator → front-end reader files; a particular report filename and a manual build button need not be permanent.

The initial generation design can still be developed and inspected independently. A manual-only refresh is a development checkpoint, however, not the completed behavior of a report defined as “what I have saved”. Opening an already mounted report and preserving its query/page across refresh are separate UI lifecycle details to specify without making the user perform another publication step.

This direction does not move every action in the current Save inventory into a new lifecycle owner. The [action map](d-20260925-144813-17e45c.md) is the basis for deciding which work is essential to current Working data, which prepares expensive media, and which belongs at a later release boundary. No current media, lookup or output operation is changed by this document.

## Review And Public Consistency

The end-state Review snapshot needs the exact document and Catalogue reader revisions that will be released together. A Review page must not fetch current Working Catalogue metadata underneath a fixed document snapshot. Later Save operations must leave the reviewed content stable. Deployment should consume that reviewed set rather than regenerate from whatever source happens to exist at deployment time.

Catalogue document generation is a related boundary. Today Catalogue Regenerate can lag behind saved Work data. For an integrated Working experience, assign each displayed field an owner: a saved Work title or medium can come from current Work reader data, while authored document text belongs to the document. Where Work-derived values are embedded into document projections, their refresh must be coordinated. This avoids solving report freshness while leaving the opened document misleadingly stale.

Current Save already uploads and deletes R2 media, as the action map records. Renaming internal Catalogue generation does not change those remote effects. A complete saved/reviewed/public separation therefore also needs a media decision: prevent later Working preparation from changing or removing objects required by the reviewed or live public revision. Whether that uses existing versioned addressing, different preparation timing or another bounded change requires an explicit audit; this document does not prescribe a new storage scheme.

Review and public content also have different meanings: Review answers what the prepared release contains; the public site answers what readers can access now. Local generation, preparing a snapshot, copying files to the repository and completing the public deployment should report their own completion boundaries accurately.

## Effect On The Earlier Report Proposal

| Earlier proposal or design question | Direction established here |
| --- | --- |
| Catalogue Works shows the last manual report publication. | Catalogue Works represents the latest saved records. A separate manual refresh cannot be the permanent normal workflow. |
| Add a Studio Publish button for the new report files. | Keep a separately callable generator useful for development/recovery; use a name such as Rebuild Catalogue Works. Do not imply public publication. |
| Save does not refresh the new report files in the first delivery. | The final Working freshness contract requires the owning save/mutation workflow to complete the necessary projection refresh. The exact integration needs a revised bounded delivery. |
| Docs Viewer should never consume canonical data. | Reader components use generated data; hosted authoring components access canonical records through their owner. |
| Could canonical records move into `docs-viewer/studio/` with the editor? | UI integration, storage consolidation and lifecycle changes are separate decisions. There is no required new Studio data stage. |
| Introduce separate Catalogue Works metadata and index files. | Report-specific files remain permitted, with later sharing where the reader contracts fit. Generation remains owned and explicit. |

The isolated generated-data producer and front-end report conversion remain useful. Preserve the existing constraint that the first conversion does not change files consumed by other reports or collections. Before implementation, reconcile its completion gate, refresh trigger and proposed control/endpoint naming with this document. The earlier target filenames are suggestions; they are not a reason to introduce a new operation called Publish.

## Open Decisions And Direction For Deliveries

| Decision still open | Required outcome |
| --- | --- |
| Host the Work editor in Docs Viewer? | One focused authoring component that can be hosted in either shell; no unnecessary dependency on a Studio-only route. |
| Keep separate configured roots or consolidate storage? | One authoritative copy per entity, explicit configuration, and a deliberate version-history/recovery plan if canonical location changes. |
| How should Save refresh report data efficiently? | Saved-data freshness with a reusable generator; choose complete or affected updates from observed cost rather than assumptions. |
| How should failure expose a stale Working projection? | Distinguish saved source from incomplete reader refresh without a silent canonical fallback or an unsupported claim of freshness. |
| Which current Save actions can move? | Use the action map to assign ownership and completion dependencies before changing media, private lookups or existing consumer outputs. |
| How are Work fields and document projections coordinated? | Exact Work/document association and clear field ownership without duplicated editable values. |
| How are Catalogue dependencies captured for Review? | One consistent prepared revision of eligible documents, reader files and media references, excluding Manage-only data. |
| How are reviewed/live media protected from later Saves? | Make remote effects consistent with the intended release boundary before claiming full snapshot isolation. |

Integration remains optional. Each bounded change should make this end state easier: portable front-end readers and editor components, named canonical owners, reusable generators, exact identities, saved-data freshness and clear operation names. This document is an architectural direction, not a combined implementation delivery.
