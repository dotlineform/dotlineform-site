# Catalogue Authoring In Docs Viewer End State

Status: agreed architectural direction with a proposed first delivery. The delivery below establishes Catalogue storage, shared local assets and publication ownership before changing report behavior. Moving the Work editor into Docs Viewer and relocating canonical records remain separate, open decisions. Approval to consolidate this plan does not start implementation or migration.

**Catalogue Works means “what I have saved”.** It must show saved Catalogue data independently of later review or publication. Generating local Catalogue files is not called Publish. Publish copies prepared data to the repository and uploads referenced assets to R2; Deploy runs GitHub Actions. The interval between those two operations is accepted.

This document develops [Catalogue Reports Shared Front-End Browsing And Search](d-20260925-134621-42c838.md). The [Catalogue Save And Publish Action Map](d-20260925-144813-17e45c.md) remains the observed inventory of current Save behavior. Its earlier standalone report-Publish proposal is superseded as the final workflow. The current runtime has not yet adopted the storage or lifecycle changes specified here.

## The End State In Use

The author opens Catalogue Works in Working, finds a Work and opens its editor. In a possible integrated application, that editor is hosted in Docs Viewer; the data responsibilities are the same if it remains in Studio. The editor reads the exact saved canonical record. Unsaved changes belong to the editor session. Save persists edits and completes the Working outputs needed to find and display the saved Work.

Prepare Preview captures document and Catalogue JSON for Review. Preview reads those captured JSON files and the current shared local assets. There is one local reader-ready copy of each image, not a Working copy and a Preview copy. Replacing an image changes what both local stages display. If captured metadata such as dimensions no longer matches the image, the author prepares Preview again. No retained asset versions, additional asset hashes or automatic Preview invalidation mechanism are required.

Publish copies the prepared JSON to the repository and uploads its referenced current assets to R2. A later Deploy runs GitHub Actions against the committed repository state. Public images can consequently change at Publish before the site's JSON changes at Deploy. This is an accepted consequence of the manually gated deployment workflow, not a condition requiring a deployment-tracking system.

For example, Save a title change from “Study A” to “Study B”. Working uses “Study B”, while existing Preview and public JSON can still contain “Study A”. Prepare Preview captures “Study B”; Publish distributes that prepared JSON and referenced assets; Deploy releases the repository snapshot. An image replacement has different timing: both local stages see the replacement from `assets/`, and public readers can see it once Publish uploads it.

| Surface | Meaning of its data | Data owner |
| --- | --- | --- |
| Work editor | Saved canonical record plus unsaved form state. | Studio Catalogue authoring, regardless of the eventual UI host. |
| Catalogue Works in Working | Saved Works and the Manage metadata needed by the report. | Currently its canonical read path; later a generated Working report projection refreshed by the owning mutations. |
| Working document and media readers | Current Working JSON and current local assets. | Working document/Catalogue generation and the shared asset store. |
| Preview / Review | Captured document/Catalogue JSON with current local assets. | Preview preparation owns JSON and references; shared assets supply the bytes. |
| Site Preview and public site | Repository reader files and public asset URLs. | Published repository output and R2; Site Preview intentionally exercises these public paths. |

Saved Works and public Catalogue documents need not have identical membership. A Work can exist without a Catalogue document. Document eligibility continues to control document preparation; copying declared Catalogue by-ID files does not require a new Work-level publication policy.

## Operation Names And Ownership

The ambiguity to remove is “published from Studio” meaning “generated for another local reader”. Generation is an internal transformation. Review describes inspecting prepared content. Publish and Deploy have the distinct distribution responsibilities below.

| Operation | Required outcome |
| --- | --- |
| Save / generate | Persist canonical edits, prepare changed local images/downloads and generate Working Catalogue data. Studio owns image dimensions and media versions. |
| Build / Regenerate | Rebuild the outputs owned by that operation. A local build does not imply publication. Catalogue document Regenerate retains its separate document-generation responsibility. |
| Prepare Preview | Capture eligible document output and declared Catalogue JSON from Working; record referenced asset identities without copying asset bytes. |
| Review | Inspect Preview JSON using the shared current assets. Prepare Preview again when subsequent edits require a fresh review set. |
| Publish | Copy the prepared JSON to the configured repository destinations and upload referenced assets to R2. Preserve canonical data, prepared JSON and media versions. |
| Deploy | Run GitHub Actions against committed repository output. Git commit and push remain explicit, separate actions. |
| Manual cleanup | Deliberately reconcile obsolete assets when needed. Normal Save/Publish does not require a pending-deletion ledger or automatic remote deletion. |

The current user-facing Deploy Repo action becomes Publish in this delivery. Reuse its owning distribution workflow and completion/error reporting; do not introduce a second distribution implementation or compatibility endpoint merely for the name. Prepare Preview remains the operation name and `preview/` remains the storage name. The separate Docs Review package workflow is unchanged.

Media version represents an image change, not a transfer. Studio must establish the version when it completes preparation of the changed local image, before generating the JSON that Preview can capture. An unchanged image, a metadata-only edit, a relocation or an upload does not advance it merely because bytes were copied. Publish consumes the version already present in the prepared data and never writes a new canonical version after uploading.

The present implementation advances Catalogue media versions after remote upload and includes R2 work in Save. Changing those responsibilities is part of this delivery. Other Save work, such as canonical validation, Gallery/Series effects and private Studio lookup refresh, remains with its current owner unless a path adaptation is required.

## Canonical Records, Reader Data And UI Hosting

Authoring components need access to canonical records through their validated owner. Ordinary reader components should consume generated data shaped for their purpose. Hosting both in Docs Viewer does not merge those responsibilities or create another editable authority.

A generated report can represent the latest saved values without reading the canonical storage schema directly. Its generator owns field selection, joins and prepared search values; the report owns front-end filtering, sorting, pagination and navigation. Manage enrichment can extend a common public reader model by exact Work ID without placing private fields in public output.

The first storage delivery does not convert Catalogue Works to that model. It preserves existing report list/search/copy behavior and does not introduce its proposed metadata/index files. Shared image and stage-data readers do change to use the new locations. Report conversion and descending Work ID browsing with 20-row pages follow this delivery.

Canonical Catalogue records stay in `studio/data/canonical/catalogue/`. Private Studio lookups stay in `studio/data/generated/catalogue-lookup/`. Original Work images remain at their configured project sources. This delivery moves generated reader data and ready-to-read assets, not canonical records, project originals or the editor UI.

`work_id` identifies a Catalogue Work; `doc_id` identifies a document. The Works document collection is also distinct from canonical Catalogue Works. Exact generated associations connect them where an associated document exists. Co-locating output does not turn these identities into aliases or duplicate their editable fields.

## Agreed Storage Shape

`W` below means the existing workspace selected by `DOTLINEFORM_DOCS_BASE_DIR`, not the repository's application-code directory. Catalogue producers gain an explicit configured Docs-workspace destination; they do not reinterpret the Projects root as a Docs root or retain the old output directory as a fallback.

The following names make the delivery concrete. The workspace-wide document asset namespace is suggested as `workspace`; the collection namespace uses exact configured collection IDs. Confirm those naming details once during readiness and use one canonical layout.

```text
W/
  assets/
    media/
      workspace/
        img/  svg/  files/  html/
      collections/
        <collection-id>/
          img/  svg/  files/  html/
    works/
      primary/                       locally stored primary srcset images
      thumbs/                        locally stored Work thumbnails
      media/
        files/                       Catalogue Work downloads

  working/
    source/
      documents/…
      collections/…                  existing collection-owned sources
      media/
        build-source/…               editable build inputs such as Mermaid
    generated/
      documents/…
      collections/…                  document payloads and manifests
      search/…
      catalogue/
        media-config.json
        works/
          works_index.json
          index/<work_id>.json
        series/
          series_index.json
          index/<series_id>.json
        galleries/
          galleries_index.json
          index/<gallery_id>.json
        reports/…                    only when a later delivery adds a consumer

  preview/
    preview-manifest.json
    documents/…
    collections/…
    search/…
    catalogue/…                      declared JSON copied from Working
```

There is no persistent `working/generated/media/` or `preview/media/` byte store, including equivalent collection-owned stage media copies. Ready-to-read document media lives in `assets/media/`; Work derivatives and downloads live in `assets/works/`. Only editable build inputs remain under source media, including collection-owned build inputs where configured. Temporary converter/build files are allowed within their existing operation-owned boundaries; they are not another reader asset store.

Stage manifests record asset references in their existing document/build/snapshot structures, rather than retaining stage `media/` directories just to house a manifest. The design-time Catalogue copy inventory described below is separate from these generated reference lists. Existing JSON snapshot revisions and ordinary transfer comparison remain useful; they do not become an asset-version history or a requirement to invalidate Preview after an image edit.

The canonical Catalogue directory does not move into `working/source/catalogue/` in this delivery, and no empty placeholder there is required. Any later canonical relocation needs its own ownership and version-history decision. The `reports/` branch likewise illustrates an allowed future location, not a requirement to create unused report files now.

## Reader And Publication Contracts

### Stage-Owned JSON

Working Catalogue reads resolve from `W/working/generated/catalogue/`; Preview reads resolve from `W/preview/catalogue/`. Site Preview/public readers use their configured repository data paths. The active reader context selects the base. Catalogue JSON must not require embedded Working/Preview URLs or a request-time canonical-data join to choose its stage.

Preserve existing Work, Series and Gallery payload meaning and identity. Adapt media URL resolution where needed so local readers use local assets and public readers use the existing public destinations. This is not a redesign of the document schema, report search rules or collection policy.

Prepare Preview copies all by-ID JSON from explicitly declared Catalogue directories unchanged. It does not infer their selection from document titles or the set of prepared Catalogue documents. Root indexes, media policy and any report/system files come from an explicit design-time inventory. A suggested canonical configuration file is `docs-viewer/config/workspace/catalogue-artifacts.json`, with declared by-ID directory families and separately declared system/report files. The exact schema belongs to implementation, with one owner used by preparation and distribution.

The initial inventory covers current `works/index/`, `series/index/`, `galleries/index/`, their aggregate indexes, `media-config.json` and the existing empty Detail index while that artifact remains supported. No new Detail behavior is introduced. Future report files must be explicitly classified; Manage-only report enrichment is excluded from the public preparation/distribution inventory. Other files are not copied merely because they happen to sit under the Catalogue root.

Publish takes Catalogue JSON from Preview, alongside the prepared document/Search output. It must not recopy live Working Catalogue files, regenerate from canonical records or adjust prepared media versions during distribution. Existing document eligibility and Search/Recents copy ownership remain unchanged.

### Shared Current Assets

Both local stages resolve asset identities into the same `W/assets/` tree. An image edit replaces the current local image; Preview deliberately displays that replacement. If Preview JSON is no longer suitable, the recovery is Prepare Preview again. Do not add historical asset copies, content-hash receipts, automatic invalidation or a hidden media-version store to make Preview immutable.

Local Studio and Docs Viewer must be able to read their managed images and downloads without R2. Missing required local files fail visibly. The old “retain a download by checking only its R2 object” path cannot remain the normal local-source contract after migration. Site Preview continues to read public asset URLs from R2, as the deployed site does. User-authored external links remain external links; this delivery concerns owned document/Catalogue assets.

Publish resolves the asset references of the prepared output to current local files and uploads the required assets to their configured remote destinations. It does not upload the entire asset directory indiscriminately. Catalogue references include media needed by the copied Work/Series/Gallery data, in addition to ordinary document media references. Required missing files are surfaced in its existing planning/error flow rather than fetched silently from R2.

Retain the existing configured public destination for each asset family. Repository-backed assets are copied alongside JSON where required; R2-backed assets are uploaded. The new shared local layout does not itself relocate public thumbnails or other public asset URLs.

R2 updates at Publish can affect the currently deployed site before Actions runs. That interval is accepted. Do not add tracking of whether Actions ran, deferred upload jobs or automatic deployment. Remote obsolete-asset deletion is left to a separate manual cleanup operation initially; no pending-deletion manifest is needed. Reconciliation of generated JSON remains distinct from deletion of shared asset bytes. Avoid automatic shared-asset cleanup as part of a routine Save or Publish.

### Saved Data And Document Freshness

The eventual Catalogue Works generated reader must show saved records after the owning mutation completes. Its generation may be independently callable for development or recovery, but a separate manual action cannot be its normal freshness boundary. That report-specific integration remains follow-on work.

Catalogue Regenerate currently updates document projections separately from Work Save. This delivery preserves that distinction while adapting the Catalogue input location. Later report/document work must decide which displayed values come from saved Work reader data and which belong to authored document content. Do not claim that moving files alone removes that possible metadata lag.

### Process After Delivery

1. Save Catalogue edits in Studio. Canonical edits, required local media preparation, Studio-owned versions, Working Catalogue JSON and existing private lookups complete through their owners. Normal local consumption requires no R2 access.
2. Read Working documents, media and current reports. Shared readers resolve current Working Catalogue JSON and assets from the configured workspace. Report UI behavior remains as before this delivery.
3. Prepare Preview. Capture eligible document output and the declared Catalogue JSON set, retaining their asset references and copying no media bytes.
4. Review Preview. It uses captured JSON and the same current assets as Working. If a later image edit makes the JSON unsuitable, prepare Preview again.
5. Publish. Review the existing distribution plan, copy prepared JSON to repository destinations and upload the required current assets to R2. Do not regenerate Catalogue data, increment media versions or delete obsolete remote objects.
6. Commit and push explicitly, then run Deploy through GitHub Actions. Site Preview reads repository output and R2, exposing the same public paths. The timing gap is accepted.
7. Run separate manual asset cleanup when wanted. No routine authoring or publication operation waits for it.
