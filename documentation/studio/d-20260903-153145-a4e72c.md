# Catalogue CSS

## Purpose

Define the presentation boundary that must be accepted before Stage 4 expands into a representative Catalogue token pilot. Moving current Work pages into Docs Viewer is not just a data or token migration: the essential Work and Work Detail presentation must be re-expressed as a host-neutral component without copying the public site's general stylesheet into Docs Viewer.

This document covers full and image-only Work presentation and Work Details, including galleries, captions and ordinary full-image links. [Catalogue Navigation](/docs/?scope=studio&doc=d-20260903-222617-28475e) follows the migration and owns Catalogue previous/next together with [Catalogue Media Focus View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b), the additional view needed to traverse Work Details without individual documents. Neither Media Focus nor either navigation feature is required by this presentation pilot. Series pages may compose these Work variants, but Series index, list and grid presentation is a separate concern and must not force unrelated public Catalogue CSS into this component.

## Current CSS Problem

`site/assets/css/main.css` is currently a 2,345-line mixed stylesheet containing theme values, global element defaults, site shell, navigation, page components and legacy Catalogue-specific Work, Work Detail and Series rules. `site/assets/css/catalogue.css` is a 249-line partial Catalogue component stylesheet which explicitly continues to depend on global shell and legacy route styles in `main.css`.

The public Analysis route currently loads `main.css` before Docs Viewer theme, core and report styles. The local Manage shell loads Docs Viewer styles without `main.css`, and a native host must not acquire a dependency on the public-site shell. Docs Review remains primarily a text-review surface and is not an interactive Work-presentation acceptance host. A Work fragment which happens to look correct only on the public route is therefore not portable and is not an acceptable pilot.

The migration must not copy all of `main.css`, retain its generic `.page`, `.seriesNav`, `.workDetails`, `.gridPager` or `.supplements` class contracts as compatibility aliases, or accumulate Catalogue rules inside `docs-viewer.css`. It must inventory the rules actually required by Work presentation and re-express only those rules behind a dedicated namespace.

## Result

The Catalogue projector emits trusted, semantic and versioned HTML beneath one component root:

~~~html
<article class="catalogueWorkPresentation" data-catalogue-presentation="work-v1">
  <header class="catalogueWorkPresentation__header">...</header>
  <figure class="catalogueWorkPresentation__primaryMedia">...</figure>
  <div class="catalogueWorkPresentation__metadata">...</div>
  <section class="catalogueWorkPresentation__details">...</section>
</article>
~~~

The proposed canonical asset is a separate tracked `docs-viewer/static/css/catalogue-work-presentation.css`, projected to the public Docs Viewer code boundary and bundled or otherwise registered once by every local and native Docs Viewer host. Its physical location beside Docs Viewer assets does not transfer presentation ownership to Docs Viewer core: Catalogue owns the projector markup, class contract, stylesheet and presentation version; each Docs Viewer host owns loading the registered asset after `docs-viewer.css`.

The built document records a requirement for the exact presentation contract, provisionally `catalogue-work-presentation@1`. A host loads that registered asset once rather than accepting arbitrary per-document stylesheet URLs. Publish must not accept a document whose required presentation version is unavailable to the intended consumers. Stage 4 readiness must freeze the exact asset path, requirement field and version check before implementation.

All selectors are rooted beneath `.catalogueWorkPresentation` or the exact version attribute. The stylesheet may use Docs Viewer public custom properties and component-local properties only. It must render correctly when `main.css` and all legacy Catalogue route JavaScript are absent.

## Essential Presentation Baseline

“Essential presentation unchanged” means preserving the content, visual hierarchy and interactions by which a Work is understood; it does not mean reproducing the old page shell or every old selector.

The component retains:

- the Work title and clear metadata hierarchy, including year, medium, dimensions, Catalogue identity, exact Series context when present, and documents, downloads or external links;
- the primary Work media with its intended aspect ratio, responsive containment, full/open target and caption;
- full and image-only token variants with one shared identity and presentation contract rather than unrelated markup families;
- Work Detail groups, titles and thumbnail galleries as key within-Work navigation, retaining captions and ordinary links to accepted full images;
- exact gallery item identities, labels and accepted gallery order, without implying a document or media previous/next sequence;
- current light and dark colour roles, content-link and visited-link distinction, hover and keyboard-focus states;
- responsive spacing, readable measure and media behaviour at narrow and wide widths; and
- semantic headings, figures, captions, links, lists and navigation landmarks that remain understandable without CSS.

The component excludes:

- the public site header, footer, theme toggle and generic page frame;
- legacy `/works/`, `/series/`, `/work-details/`, Recent and Catalogue Search route behaviour;
- public Catalogue index, list and discovery shell that is not part of one Work's presentation;
- generic page-back navigation already owned by the Docs Viewer document shell;
- Media Focus and previous/next, counters and sequence-return controls, owned by the post-migration Catalogue Navigation feature;
- global element resets, base typography, utility classes and unrelated rules from `main.css`; and
- legacy Catalogue fetch, query-string or swipe runtime unless a specific Work interaction is separately accepted as essential and cannot be expressed by ordinary links.

The frozen archive remains the side-by-side behavioural reference. Differences that follow from the Docs Viewer shell are intentional; loss of Work content, hierarchy, media meaning, useful context, responsive behaviour or accessible interaction is not.

## Gallery Destination Contract

The current destination model follows [Concept](/docs/?scope=studio&doc=d-20260904-014334-f3dab5) and exact Catalogue identities:

| gallery | destination |
| --- | --- |
| Series-level Work thumbnails | Media View for the exact `work_id` |
| Work-level Work Detail thumbnails | Media View for the exact `detail_uid`; wider Detail support remains implementation work |

A Series-level gallery uses supplied exact Work identities. Catalogue grouping may supply membership; document parentage and associated-document links remain separate. The unified `cat_id` proposal is abandoned in favor of explicit subject fields.

A Work can open in Media View with no associated document, one or many. Document count does not determine image availability and does not select a definitive Work document. Bulk source migration is abandoned; batch New doc supports selected authoring as described in [Delivery Sequence](/docs/?scope=studio&doc=d-20260902-122221-1879db).

The Series gallery's full layout is outside this Work component, but its available and unavailable item states should reuse the accepted thumbnail, typography, theme and focus primitives rather than preserve legacy route CSS. The Work-level gallery belongs to `work-v1` and requires no Work Detail documents. Later Media Focus must extend the versioned Catalogue presentation contract for its image and caption; it is not an asset or behaviour required to accept the migration's first component.

## CSS Contract

### Namespace And Specificity

Every production selector starts with `.catalogueWorkPresentation` or `[data-catalogue-presentation="work-v1"]`. Element selectors are allowed only beneath that root. The component must not style `body`, `.docsViewer`, generic `.page`, unqualified headings, links, figures or images, and must not use `!important` to defeat host rules.

Class names express component structure rather than old route structure. The provisional family includes `__header`, `__title`, `__primaryMedia`, `__primaryMediaLink`, `__primaryMediaImage`, `__caption`, `__metadata`, `__metadataRow`, `__details`, `__detailGroup`, `__detailTitle`, `__detailGrid`, `__detailItem`, `__detailImage`, `__pager`, `__pagerButton` and `__pagerStatus`. Exact names freeze with `work-v1`; they are not aliases for the legacy classes.

The root owns component-local sizing properties such as `--catalogue-work-thumbnail-size`, `--catalogue-work-grid-cell`, `--catalogue-work-media-aspect-ratio` and `--catalogue-work-pager-gap`. Record-specific aspect ratio may be set as a validated inline custom-property value on the component or media element; arbitrary inline declarations are not accepted.

### Existing Value Migration

The current rules use public-site variables which must be translated explicitly rather than inherited accidentally:

| current dependency | Work component dependency |
| --- | --- |
| `--content-measure` | `--docs-viewer-measure` when an internal maximum is needed; otherwise the Docs Viewer document container |
| `--space-1` through `--space-7` | `--docs-viewer-space-1` through `--docs-viewer-space-7` |
| `--font-body` | `--docs-viewer-font-body` |
| `--font-caption` | `--docs-viewer-font-caption` |
| `--font-small` | `--docs-viewer-font-small` |
| `--font-heading-2` and related heading sizes | the corresponding `--docs-viewer-font-heading-*` property |
| `--line-snug` | `--docs-viewer-line-snug` |
| `--text` and `--muted` | `--docs-viewer-text` and `--docs-viewer-muted` |
| `--panel` and `--panel-2` | `--docs-viewer-panel` and `--docs-viewer-panel-2` |
| `--border` and `--border-strong` | `--docs-viewer-border` and `--docs-viewer-border-strong` |
| `--link`, `--link-hover` and `--link-visited` | `--docs-viewer-link`, `--docs-viewer-link-hover` and `--docs-viewer-link-visited` |
| `--content-link` and `--content-link-visited` | `--docs-viewer-content-link` and `--docs-viewer-content-link-visited` |
| focus outlines based on `--border-strong` | `--docs-viewer-focus-ring` |
| generic `--radius` or hard-coded shared radii | `--docs-viewer-radius` unless a distinct component radius is justified |
| `--list-thumb-size`, `--list-column-gap` and `--list-row-padding` | component-local thumbnail, column-gap and row-padding properties |
| `--nav-gap-grid`, `--nav-grid-margin-top`, `--nav-counter-gap` and Series navigation spacing | no Work component dependency; future Catalogue navigation defines its own control and spacing boundary |
| `--work-ar` | validated `--catalogue-work-media-aspect-ratio` |
| debug outline variables and public shell measurements | no production component dependency |

The existing Docs Viewer theme already supplies the light and dark canvas, surface, text, muted, border, link, content-link, focus, selection and status roles. The component consumes those roles; it does not duplicate colour literals or introduce a second theme switch.

### Layout And Media

The component fits the ordinary Docs Viewer content column and must not use viewport-width breakout rules from the public site. Its main blocks use the available width, with an internal maximum only where the Work composition materially requires it. It must tolerate the public two-rail layout, the local Manage layout and the narrower native WebKit viewport without host-specific selectors.

Primary images remain `display: block`, use `width: 100%`, `max-width: 100%`, `height: auto`, the validated Work aspect ratio and `object-fit: contain`. Thumbnail and grid images use explicit square containers and `object-fit: cover` only where cropping is already an intentional part of the Work Detail presentation. Placeholder surfaces use the Docs Viewer subtle panel role.

Work Detail grids use component-local cell and gap values, start-aligned auto-fill behaviour at ordinary widths and an explicitly reviewed maximum-density rule at wide widths. Any distinct thumbnail-gallery paging controls retain clear enabled, hover, focus and disabled states; their counter remains visually secondary but readable. Narrow layouts must not rely on fixed multi-column metadata or gallery-paging widths.

### Links And Controls

Metadata and prose links use the Docs Viewer content-link roles, including a distinct visited state and underline on hover or focus. Thumbnail-gallery pager controls use the Docs Viewer ordinary link, panel, border and focus roles. Focus-visible styling uses a two-pixel ring with offset and must not be replaced by hover-only feedback.

Real destinations remain ordinary anchors. Buttons are reserved for in-page actions such as paging a client-side detail set, if that interaction remains necessary after the baseline review. Disabled buttons expose a real disabled state rather than only reduced opacity. Touch targets and no-wrap behaviour are reviewed at the native iPad width rather than inherited from the legacy route.

### Responsive And Theme Behaviour

The component relies on Docs Viewer theme variables, so light and dark appearance changes with the host root and requires no Work-specific theme selector. The initial responsive breakpoint may follow the current 640-pixel behaviour, but only after checking the actual Docs Viewer and iPad content widths; it is not retained merely because it existed in `main.css`.

At narrow widths, metadata rows may stack, Work Detail grids reduce naturally, media remains contained, and thumbnail-gallery paging remains legible without horizontal scrolling. At wide widths, the component must not exceed the readable Docs Viewer measure or assume the public site's old container width. Reduced-motion and high-contrast behaviour inherit from the host unless the component introduces motion or a presentation-specific contrast problem.

## Ownership

| owner | responsibility |
| --- | --- |
| Catalogue presentation | projector HTML, semantic structure, namespace, component CSS, variants and `work-v1` compatibility contract |
| Docs Viewer core | theme roles, document container, Content Detail lifecycle and the host hook which loads a registered presentation asset |
| Docs Build | exact token resolution, trusted-fragment insertion, dependency tracking and recording the required presentation contract |
| Docs Publish | rejecting unavailable presentation requirements and accepting one revision-consistent document-and-Catalogue snapshot |
| Public, Manage and future native hosts | loading the same registered component release after Docs Viewer core without adding host-specific Work CSS |
| Docs Review | primarily text review; no requirement to compose the interactive gallery or Media Focus View |
| frozen archive | immutable legacy `main.css`, `catalogue.css`, route markup and runtime used only as the historical public presentation |

Stage 1 copies the accepted legacy CSS into the archive and removes the legacy Catalogue-only family from active site assets. Stage 4 does not use that cleanup as an opportunity for a broad redesign of `main.css`; it builds the new component from the archived presentation inventory and leaves unrelated active-site styling alone.

## Stage 4 Checkpoints

### 4A — Freeze The Presentation Baseline

Choose one representative complex Work with multiple metadata rows, primary media, links, Series context and several Work Detail groups. Inventory the exact legacy markup, selectors, variables, runtime interactions and breakpoint behaviour required to present it. Classify every dependency as Work content, Work interaction, Docs Viewer shell or frozen public-site shell, and accept the inclusion/exclusion boundary above.

### 4B — Prove The Host-neutral Component

Implement `work-v1`, its dedicated stylesheet and the registered host-loading seam for the representative Work. Present the same built fragment in public and Manage Docs Viewer without `main.css` reliance. Review light and dark themes, wide and narrow widths, media, metadata, links, keyboard focus and Work Detail galleries with captions and ordinary full-image links. Media Focus and Catalogue/media previous/next belong to the post-migration Catalogue Navigation feature and are not part of this proof. Include the native host in this proof when its Docs Viewer composition seam exists; until then the no-public-shell contract and responsive WebKit review are readiness evidence, not a claim of native acceptance. Docs Review remains outside the interactive proof.

### 4C — Expand The Token Pilot

After 4B is accepted, add full and image-only Work tokens, Work Details, Series composition, exact dependency rebuilds and Search destinations for the complete representative sample named in [Delivery Sequence](/docs/?scope=studio&doc=d-20260902-122221-1879db). Include Series-gallery links to root and parented Work documents, clean unavailable states for missing or ambiguous Work documents, and the advisory Work Document Coverage report. New variants reuse `work-v1` primitives or deliberately version the contract; they do not grow one-off style blocks in generated document HTML.

## Migration Method

Use the frozen archive as the visual and behavioural reference. Extract an inventory of selectors actually reached by the representative Work and Work Detail pages, then rewrite the required declarations under the new namespace using Docs Viewer roles and component-local dimensions. Do not mechanically paste a contiguous block from `main.css` or `catalogue.css` because those blocks include shared variables, generic selectors and route assumptions which would recreate the coupling.

Build one exact representative fixture through the real Catalogue projector and Docs Build path. The fragment must remain readable as semantic HTML before styling. Load the component stylesheet through the explicit host asset registry, not through an inline `<style>`, token-generated `<link>`, broad wildcard include or runtime CSS discovery.

Review the public and local renderings side by side with the archive. Fix presentation differences in the component or projector rather than by adding host overrides. Expand to the other token shapes only after the complex case proves the seam, because the simpler image-only case cannot expose the metadata, navigation, detail-grid and responsive risks.

## Verification

Deterministic checks should prove exact projector identity, escaping and sanitization; versioned root markup; exact Series-gallery Work-document resolution; unavailable output for zero or multiple matches; advisory report classification; dependency and presentation-requirement recording; registered asset availability in each host; public code projection; absence of un-namespaced production selectors; and absence of `main.css`, legacy variable or legacy route-runtime dependencies. A stylesheet/source check can protect this boundary more cheaply and reliably than a screenshot suite.

Manual review is the acceptance authority for visual parity and interaction quality. Compare the representative archived and Docs Viewer Work and Work Detail pages in light and dark themes at narrow and wide widths, including primary media, captions, metadata hierarchy, content and visited links, keyboard focus, contextual navigation, detail thumbnails, paging and long or missing values. Record deliberate shell differences and unresolved presentation defects.

Do not add permanent screenshot or click-choreography tests merely to freeze layout. Retain a browser smoke only if Stage 4 introduces a durable host asset-loading or route/module integration boundary that cannot be verified through static, build or service checks.

## Open Decisions Before 4B

- Freeze the representative Work and Work Detail records and the exact archive views used for comparison.
- Confirm the canonical stylesheet name and its public projection, local-service and native-bundle registrations.
- Define the built document field or manifest entry for `catalogue-work-presentation@1` and the host/version failure behaviour.
- Freeze the final `work-v1` fragment structure, class names and full versus image-only variant relationship.
- Keep Media Focus and Catalogue document/detail previous/next in the post-migration Catalogue Navigation feature; do not require their sequence or control design to accept `work-v1`.
- Freeze the migration's gallery grouping, paging, caption and ordinary-image-link baseline without creating one document per Work Detail.
- Freeze Series-gallery unavailable-item copy and Work Document Coverage report presentation without making either an enforcement path.
- Confirm whether any interaction beyond ordinary anchors and optional detail paging needs Catalogue presentation JavaScript; the default is CSS plus semantic HTML only.
- Confirm the narrow-width thresholds against public, Manage and native WebKit content widths.

## Supporting Architecture

- [Catalogue Media Focus View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) belongs to post-migration Catalogue Navigation and defines the image-and-caption view needed for Work Detail previous/next without individual documents. Its later CSS extension must preserve this component's ownership and isolation.
- [Context Navigation](/docs/?scope=studio&doc=d-20260903-160226-5c6a3e) is a separate scope-level document proposal, not the navigation owner or a delivery dependency for Catalogue sub-scope documents or focused media.
