# Reorder docs

## Purpose

Allow a scope's documents to follow an editorial sequence, including books with chapters and pages, without changing document parentage or rebuilding after every drag. The proposed local Manage index-panel **Reorder** mode edits a working copy of sibling order and persists it only on Save.

This is a general Docs Viewer improvement which can be considered for delivery before Unified Analysis And Catalogue Presentation. It is not Catalogue-specific and does not depend on Catalogue tokens or the native app.

This document owns scope ordering and its Reorder editor. [Context Navigation](/docs/?scope=studio&doc=d-20260903-160226-5c6a3e) consumes the resulting ordered tree for previous/next traversal; it does not maintain another ordering source. Reorder is useful independently of those navigation controls.

## Scope Ordering Policy

Each scope has one consistently applied ordering policy: **A–Z** or **curated order**. Studio can retain A–Z; Analysis can use curated order. Do not introduce per-root or per-parent ordering modes within one scope. Separate sibling groups still have their own positions under the same scope policy.

Sub-scope reports retain their independent field-based sorting. An A–Z report does not change the scope index or become its ordering authority. This proposal concerns scope-level document hierarchy, not reordering report rows or Catalogue records.

The normal index panel renders the supplied tree in its supplied order. Upstream generation/loading resolves scope policy and saved editorial order. The index panel and hierarchy navigation must not independently re-sort that tree or treat expand/collapse state as ordering data.

## Two Distinct Drag-and-drop Actions

| action | changes | does not change |
| --- | --- | --- |
| existing Change parent | the selected document's parent through the existing source mutation workflow | an explicitly chosen position among destination siblings |
| Reorder mode | positions among documents with the same parent, including root-level siblings | any document's parent or hierarchy membership |

In Reorder mode a document can move before or after its siblings only. It cannot be dropped into another parent or moved to a different hierarchy level. Moving a parent within its sibling list carries its whole subtree visually; descendant parentage and internal sibling order remain unchanged.

Reorder is not a combined hierarchy editor and does not replace the existing Change parent action. Its gestures must not invoke that action accidentally.

## Reorder Mode

1. Enter Reorder explicitly in local Manage for a curated-order scope, retaining the saved tree and creating an in-memory working copy.
2. Drag siblings into the required order in that draft. Each drop changes draft arrays and their presentation only: no source write, live Change parent request, Build, Publish or deployment.
3. Keep the draft visibly distinct from normal browsing, with Save and Cancel. The normal document/navigation model remains based on the saved order until Save succeeds.
4. Cancel discards the draft and restores the saved tree without any persistent change.
5. Save validates the complete ordering change against its source context, persists canonical ordering data, and uses the normal generation/loading path to display the resulting saved tree.

Save changes ordering only, not Markdown content, document identity or `parent_id`. A successful Save must survive later ordinary Builds. It does not implicitly Publish, Deploy Repo, commit or deploy publicly.

Exact placement of controls, drag handles, keyboard/touch alternatives, dirty-state presentation and handling of navigation away from an unsaved draft remain design decisions. The distinction between draft and saved state is required; a particular modal, report or interaction framework is not.

## Source And Generated Ownership

The generated `documents/index-tree.json` is an output, not the place to store an arrangement that must survive Build. Saving only that generated file would lose the editorial change when the builder reconstructs it.

Document sources remain authoritative for exact `doc_id`, `parent_id`, title and other metadata. Separate scope-owned canonical ordering data supplies relative sibling positions without becoming another hierarchy authority. A source JSON representation containing ordered arrays of exact document IDs for sibling groups is the proposed direction; array position can express order without reviving per-document numeric `sort_order` fields. Its exact filename, schema and integration are not yet confirmed.

Build combines canonical hierarchy and metadata with the scope policy and saved order to produce the normal consumer-ready tree. The ordering input cannot move a document to another parent, create a document, copy stale titles/URLs into source authority or silently hide a document omitted from its lists.

The current builder alphabetises siblings, and the browser tree helpers also alphabetise them. Implementation must align those owners so ordinary rendering preserves the supplied tree order. Reorder mode is a deliberate draft editor using that panel, not permission to retain competing runtime ordering logic in normal browsing.

Docs Publish carries the accepted ordering through its existing document selection boundary, preserving the relative order of retained documents. Downstream consumers use that accepted tree rather than reading live curation data. Public consumers do not acquire editing capability.

## Arrivals And Existing Documents

The destination scope's policy applies consistently regardless of the operation which introduces a document. In a curated-order scope:

| operation | placement rule |
| --- | --- |
| create a document | append to the end of its sibling group |
| import a new document | append to the end of its destination sibling group |
| copy into the scope | append the incoming root or roots to their destination sibling group |
| move into the scope | append the incoming root or roots to their destination sibling group |
| existing Change parent | append to the end of the new parent's sibling group; a move to scope root appends among root siblings |
| update or overwrite without changing identity or parent | preserve the existing position |

In an A–Z destination, normal alphabetical placement applies instead. The destination policy takes precedence over the source scope's policy.

For a copied or moved subtree arriving in a curated-order scope, append its root while preserving the subtree's relative internal order and hierarchy after the operation's normal identity/parent remapping. Multiple incoming roots append as a block in the operation's defined order. That order must be deterministic; an import format with no defined incoming order needs an explicit rule before implementation.

Documents already at the destination keep their relative order. A rename in a curated scope does not reposition the document; the normal A–Z policy still responds to title changes in an alphabetical scope. A no-op Change parent must not act as an implicit Reorder.

The append rule also needs to cover new or reparented documents discovered through direct canonical source edits, not only Manage actions. How source reconciliation identifies and persists new arrivals, and removes references after deletion or departure, remains an implementation decision. It must not silently replace the saved order with A–Z or drop newly discovered documents.

## Validation And Concurrent Changes

Save must accept only a reordering of the intended sibling memberships: exact existing IDs, no duplicates, no missing existing members and no parent changes. It must not persist document metadata copied from a stale browser payload.

If document creation, import, deletion, parent changes or another source update makes the draft's membership/order baseline stale, Save must not overwrite those changes. Use a bounded revision check and an explicit reload/retry outcome; a general multi-user merge or background synchronisation system is not required. The precise revision boundary and failed-Save behaviour remain to be chosen.

## Verification Boundary

Deterministic checks should prove sibling-only reorder validation, unchanged parentage and document identity, preservation of moved subtrees, no persistent writes before Save or after Cancel, saved-order survival through Build, and append/preserve behaviour for each relevant create/import/copy/move path. Check that generated and consumer tree order agree and that A–Z scopes and independently sorted reports retain their intended behaviour.

Manual review owns drag-and-drop clarity, Save/Cancel feel, scope-root and nested-group usability, accessibility and narrow-width presentation. Do not add permanent click-choreography or screenshot tests merely to freeze the interaction design.

## Open Decisions Before Implementation

- Freeze the scope ordering configuration and initial transition from existing A–Z order to curated order, including any later policy change.
- Freeze the canonical ordering storage location and schema, its exact hierarchy validation, and its Build/Publish integration.
- Define how create, import, copy, transfer, Change parent and direct-source reconciliation maintain append order and remove departed IDs without changing their existing identity or lifecycle responsibilities.
- Define deterministic incoming order for batches whose source format does not already provide it.
- Freeze Save's revision boundary, handling of unseen/filtered documents and source changes during a draft, and recovery when source Save succeeds but generated follow-through fails.
- Design the Reorder entry/exit controls, sibling-only drop targets, keyboard/touch alternatives and unsaved-change handling without changing normal Change parent semantics.
- Decide Reorder availability in A–Z scopes without silently switching a scope's policy through a drag gesture.

## Status

Proposed. Scope-wide policy, sibling-only Reorder, in-memory draft editing, explicit Save/Cancel and destination append rules are agreed requirements. Exact storage and UI mechanics remain open. No runtime changes, new ordering files, source migration or delivery commencement are authorised by this document.
