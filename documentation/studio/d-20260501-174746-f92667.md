# Run Checks

## Role

`tests/run_checks.py` coordinates optional repo check profiles and writes one local evidence snapshot under `var/test-runs/`.

It is not a mandatory gate. Select an existing focused command when its coverage addresses the current risk; select a profile only when its members provide necessary evidence at a proportionate cost. [Test Contract Discipline](/docs/?scope=studio&doc=d-20260627-212121-7cf7de) requires an agreed specification before changing tests or collection membership and a durable coverage description outside delivery documents.

## Commands

```bash
$HOME/miniconda3/bin/python3 tests/run_checks.py --list
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile quick
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile quick --profile catalogue
```

`--list` and the profile definitions in code are the exact current command inventory. Inspect them before choosing a collection. They do not explain all test scenarios, fixtures, assertions, or coverage limits and do not replace the maintained test record.

## Repository Source Lint

`tooling/lint/` owns the pinned repository lint tools, rules, lockfile, and
maintained boundaries. Install its isolated tool environments with:

```bash
$HOME/miniconda3/bin/python3 -m venv tooling/lint/.venv
tooling/lint/.venv/bin/python -m pip install -r tooling/lint/python-requirements.txt
npm ci --prefix tooling/lint
```

Use explicit paths for new or materially changed source:

```bash
bin/lint-python <path> [path ...]
bin/lint-js <path> [path ...]
```

Use the checked maintained boundary for an application-wide claim:

```bash
bin/lint --list
bin/lint --scope studio
$HOME/miniconda3/bin/python3 tests/run_checks.py --profile source-lint
```

Explicit commands fail without eligible targets. Scope commands resolve
`tooling/lint/targets.json`; Ruff and ESLint rules remain in that package.
Command output reports language, file count, and maintained roots. Processing,
generated/vendor source, dependency trees, caches, canonical data, and retired
source remain outside the Python/JavaScript coverage claim.

## Docs Viewer Site Code Projection

Shared/public Docs Viewer runtime code is canonical under `docs-viewer/`; its tracked public deployment copy remains under `site/docs-viewer/`. After changing a canonical file represented by `site-tools/config/site-code-update.json`, run:

```bash
bin/site-code-update
git diff -- site/docs-viewer
bin/site-code-update --check
bin/site-validate
```

Inspect the generated delta before handoff and commit canonical and projected files together. Add, remove, or change the public status of a runtime file by editing the manifest explicitly; local-only files in mixed source directories remain excluded. `--check` and `bin/site-validate` are non-mutating and require no external Docs Viewer scope workspace.

This is a code-development gate only for represented runtime files. It is not part of document Build, Publish, Deploy Repo, Deploy Public, or ordinary document editing.

## Profile Intent

- `quick` — grouped repo/config/projection/readiness/Python checks; the name is not a runtime or cost guarantee.
- `studio` — the selected Studio deterministic Python collection plus Studio source lint; collection does not mean complete behavior coverage.
- `catalogue` — catalogue Python contracts plus representative build preview.
- `docs` — Docs Viewer/Data Sharing Python contracts plus Studio docs/search generation.
- `source-lint` — all six adopted maintained Python/JavaScript boundaries.
- `docs-viewer-smoke`, `studio-smoke` —
  app-owned browser/runtime boundaries.
- `full` — the broad configured aggregate, including `source-lint`; inspect
  `--list` because it does not imply every app smoke or Processing coverage.

These labels describe broad intent, not audited coverage specifications. Maintain each collection's exact membership or selection rules with exclusions, linked case coverage, setup, side effects, limits, commands/triggers, and costs in its durable test record. Check that record against the runner before relying on it. A collection without that documentation is unreviewed; this policy update does not certify it or initiate a suite-wide audit.

Include generation, browser/server startup, configured external workspace access, and output writes when assessing cost and effects. In particular, the documented `docs` profile includes document and Search generation; ordinary document edits do not justify those operations. Prefer the relevant individual check when the rest of a profile is unnecessary.

## Outputs

Each run writes:

- `var/test-runs/<run-id>/summary.md`
- `var/test-runs/<run-id>/summary.json`
- one log per command

Closeout should report profile, pass/fail, and the Markdown summary path.

## Extension Method

- agree a bounded test specification before creating, updating, removing, or regrouping test commands; feature approval does not authorize profile maintenance automatically;
- update the durable coverage record with implemented membership and behavior; keep run results in the delivery or evidence snapshot;
- add a command only when it proves a durable contract;
- assign it to the app/profile that owns the behavior;
- add a source root to `tooling/lint/targets.json` only after its runtime
  context, exclusions, findings, and complete clean boundary are reviewed;
- require a maintained target boundary before promoting a lint check into a normal profile; a fixed specimen or toolchain smoke is not app-wide evidence;
- keep expensive/niche checks focused unless routine grouped confidence is valuable;
- do not add UI choreography merely because a browser harness exists;
- keep `source-lint`, app-profile placement, and `full` composition intentional
  and visible in `--list`.

[Testing](/docs/?scope=studio&doc=d-20260501-174746-efd581) owns evidence selection. [Browser Smoke Testing](/docs/?scope=studio&doc=d-20260501-000000-49b626) owns browser harness rules.
