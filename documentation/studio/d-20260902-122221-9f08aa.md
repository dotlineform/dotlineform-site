# Architecture

## Purpose

Define the proposed target architecture in which `analysis` is the sole mutable public content destination, Docs Viewer presents ordinary documents plus Catalogue-backed content, and the current Catalogue remains available as a frozen archive.

This architecture separates canonical data, document source, navigation, presentation composition, public acceptance and deployment. It does not require Docs Viewer runtime to interpret Catalogue records and does not preserve current site-navigation constraints as Catalogue editor rules.

## Legacy Catalogue Archive

The complete existing public Catalogue is physically relocated during the freeze into one self-contained immutable subtree beneath `site/archive/`. Its public routes become `/archive/series/`, `/archive/works/`, `/archive/work-details/`, `/archive/recent/` and `/archive/search/`. The subtree owns the exact JSON payloads, Catalogue Search and Recent inputs, Catalogue-specific browser runtime, local media and copies of every shared shell or stylesheet dependency required to preserve the reviewed presentation.

Archive dependencies are deliberately copied rather than read from mutable active asset paths. After the reviewed transition, the active `site/assets/` boundary contains no legacy Catalogue-only runtime, payload or local-media family, and no Studio generator, cleanup operation, shared-code projection, Docs Publish operation or Deploy Repo reconciliation may write, clean or regenerate `site/archive/`. A recorded archive manifest and Git history identify the accepted bytes.

Archiving does not depend on the replacement Analysis presentation being ready. Until public cutover, the homepage or primary Works link may point to the archived presentation. Once the replacement is accepted, `/analysis/` becomes the sole mutable publishing destination and the primary site destination, while a permanent site-footer link keeps `/archive/` discoverable. GitHub Pages continues to deploy the complete tracked site containing both the frozen archive and the current Analysis projection.

The archive owns immutable copies of its required remote media beneath `media.dotlineform.com/archive/catalogue/`, divided into `works/img/`, `works/files/` and `work_details/img/`. Stage 1 copies the exact currently referenced R2 objects once, verifies their bytes, records their keys and checksums in the archive manifest, and rewrites the archived snapshot to the new bases. Active upload, replacement and cleanup operations must reject this prefix; later Catalogue media continues under active non-archive ownership.

## Target Flow

~~~text
canonical Catalogue records and media
        -> Studio build-time Catalogue projector

Analysis Markdown source
        + registered Catalogue tokens
        -> Docs Build
        -> generated document pages, token dependencies and composed Search
        -> Docs Publish
        -> accepted consumer-ready Analysis snapshot in iCloud
        -> Deploy Repo
        -> tracked /analysis/ site projection

current Catalogue routes, runtime, payloads and local media
        -> one reviewed relocation into site/archive/
        -> tracked and deployed as one immutable snapshot
~~~

The current Catalogue generator must stop targeting both the former active Catalogue paths and the new archive subtree under `site/`. New replaceable Catalogue projection belongs beneath the existing external Catalogue workspace at `catalogue/generated/`; Analysis Build consumes it into the external Analysis generated and Published lifecycle. A second tracked generated Catalogue tree is not introduced merely to replace the current one.

## Page And Token Model

When a Series, Work or Detail has an associated page, it is an ordinary Markdown document with normal document identity and one exact Catalogue subject. [Catalogue Data Model](/docs/?scope=studio&doc=d-20260903-231534-b63aa9) retains the shared public `analysis.works` sub-scope and Works name. Its accepted subject fields are `series_id`, `work_id` or `detail_uid`; a plain document has none, and a real Folder subject is available only in `dotlineform`. A Catalogue-backed page needs no visible Markdown heading when its presentation supplies the title.

~~~yaml
---
doc_id: d-...
title: Nerve
work_id: "00123"
---

{{ catalogue_work }}
~~~

The unparameterised Work-page token uses the document's exact `work_id` subject. A Series or ordinary document may instead embed explicit Work targets and presentation variants:

~~~yaml
---
series_id: "108"
---

{{ catalogue_work 1 }}
{{ catalogue_work_image_only 2 }}
~~~

The Studio build-time Catalogue projector resolves the exact canonical record and produces a trusted HTML fragment plus any explicit searchable or dependency metadata required by the build. The Docs builder inserts the fragment into ordinary `content_html`. The Docs Viewer page runtime loads the resulting document exactly as it loads any other document.

Token arguments are exact Catalogue identities, not filenames, routes or inferred context. A presentation variant changes rendered output only. Missing, malformed or unresolved targets fail explicitly without fallback from titles, selected rows or page context.

## Independent Structures

There is no required universal Series-to-Work hierarchy:

| structure | relationship | participants |
| --- | --- | --- |
| Catalogue data hierarchy | optional singular `series_id` in a Work record | canonical Series and Works |
| document hierarchy | optional `parent_id` in document front matter | documents only |
| presentation graph | registered Catalogue tokens in document bodies | documents and referenced Catalogue records |

The builder never infers one relationship from another. They may align when a conventional Series-to-Work presentation is useful, but alignment is not a validity or publication rule.

A Work document may use a Series document as `parent_id` and participate in the normal document tree. It may instead be a root document regardless of its Catalogue `series_id`. A Work may have no document and appear only through a token, participating in Catalogue grouping and presentation but not document hierarchy. A canonical Work with no own page and no accepted token appearance remains a valid Studio record without consumer presentation.

A Series document is valid with no child documents and no embedded Works. A Work is valid with no Series. A report can reproduce a complete conventional hierarchy by traversing normal document `parent_id` relationships. Explicit Work tokens provide authored composition and need not match document children.

## Gallery Destination Model

Gallery destinations use Catalogue identity directly, following [Concept](/docs/?scope=studio&doc=d-20260904-014334-f3dab5):

| gallery context | item identity | destination |
| --- | --- | --- |
| Series-level gallery | canonical `work_id` | the Work's image and metadata in Media View |
| Work-level gallery | canonical `detail_uid` | the selected Detail in Media View; wider Detail support remains implementation work |

A Series-level gallery may use Catalogue `series_id` grouping to choose its Work items, but it does not infer document parentage or select a document about a Work. Associated documents and files are separate destinations.

The unified `cat_id` proposal is abandoned. Documents retain explicit `series_id`, `work_id` or `detail_uid` subjects. An entity may have no associated document, one or many; none of these states makes its Media View unavailable or establishes a definitive document.

Bulk document migration and automatic Details-document creation are abandoned. [Delivery Sequence](/docs/?scope=studio&doc=d-20260902-122221-1879db) instead plans batch New doc for selected Works or Series alongside the existing Project docs backlog. Any future coverage report helps curation without enforcing one document per entity.

Work-level galleries require no document per Detail. [Catalogue Navigation](/docs/?scope=studio&doc=d-20260903-222617-28475e) owns future sequence behavior using the gallery context that opens Media View, independently of bulk document creation.

## Publication And Consumer Snapshot

Series and Work records have no independent draft-to-published lifecycle. Saving creates or updates real canonical Catalogue data. Catalogue-backed documents initially remain excluded from Publish, while Build combines their current Markdown and Catalogue dependencies into previewable generated output.

Docs Publish is the sole public acceptance decision. It starts from the accepted document set, validates each reachable Catalogue token, expands the snapshot through those dependencies, and records one revision-consistent consumer-ready result in the iCloud-backed Analysis Published workspace. The existing Published snapshot remains unchanged when canonical Catalogue or Markdown source changes until a later Publish is accepted.

A Catalogue record is publicly presented when an accepted document is its own page or reaches it through a registered token. A record with no accepted appearance remains available to Studio but has no public destination. Removing every accepted appearance withdraws its consumer projection on the next Publish without deleting the canonical record.

Catalogue still owns target identity, canonical validation, public-safe field selection, media readiness and fragment generation. These are readiness conditions, not a second publication status. Public Catalogue availability is derived from the accepted document-and-token closure rather than stored in a parallel Work or Series lifecycle.

Deploy Repo copies the complete accepted Analysis snapshot into its owned tracked destination. It does not rebuild, re-filter or mutate the frozen Catalogue archive. Future web or Swift consumers may read the same accepted iCloud snapshot without using canonical editing data or treating `site/` as their API.

## Search

The public interface retains one Search box, one result list and one Docs Viewer query path. Docs Search indexes authored Markdown but ignores HTML inserted by Catalogue presentation tokens. The Catalogue projector separately emits searchable fields from canonical Work and Series data.

The Analysis Search build composes those records for Catalogue targets reachable from the accepted document-and-token closure. Catalogue results retain exact entity identity; document results retain exact document identity. Decide how each Catalogue result opens Media View or offers associated documents without selecting a definitive Work document. Several accepted appearances require a deliberate de-duplication policy. Titles and URLs remain display values, never join keys.

This composition preserves separate field authority without exposing two search boxes or asking the browser to reconstruct Catalogue data from rendered HTML.

## Navigation And Discovery

The main Analysis presentation is curated rather than an obligatory rendering of every root and descendant. Normal document parentage, contextual links, Search, tags, semantic relationships and reports expose detail progressively without eagerly loading every Catalogue projection.

Inventory is not navigation. Complete alphabetical, chronological, Series and hierarchy views remain possible as reports. They do not become editor validity rules or require the main index to announce the complete size of the portfolio.

[Doc Navigation](/docs/?scope=studio&doc=d-20260903-220300-694ee5), including scope-level Context Navigation and Reorder, is independent of the migration and Catalogue Navigation. Catalogue documents belong to a sub-scope and need their own navigation model.

Catalogue Navigation depends on the accepted presentation and collection data, not a bulk migration cohort. Decide how authored galleries establish sequence membership, order, section boundaries, controls, history and return behavior. Shared counters or suspended Series context are not settled requirements.

## Ownership Invariants

- Catalogue owns canonical Series, Work, Work Detail and media records, optional `series_id`, readiness validation, the HTML projector and Catalogue search fields.
- Analysis owns Markdown page source, exact Catalogue subject declarations, optional `parent_id` and authored token composition.
- Docs Build owns registered token resolution, dependency tracking, fragment insertion, document payloads and composed Search output.
- Docs Publish owns the sole public eligibility decision and the complete accepted document-and-token snapshot.
- Docs Viewer owns the shared shell, ordinary page loading, navigation and Search presentation; it acquires no Catalogue page runtime.
- Deploy Repo owns only the active Analysis site projection and cannot rewrite or clean the frozen Catalogue archive.
- `site/archive/` exclusively owns the frozen Catalogue pages, runtime, configuration, payloads, local media and copied shell dependencies; active site code does not serve as an archive dependency.
- Exact `doc_id`, `series_id`, `work_id` and `detail_uid` identities cross boundaries without inference from titles, filenames, routes or current UI state.
- A Catalogue change rebuilds every dependent document even when its Markdown source is unchanged.
- Work and Series page documents are optional; token-only and no-presentation records remain valid states.
- Series-gallery items open exact Works in Media View independently of document associations.
- Work Details do not require documents. Their gallery and Media View sequence are presentation capabilities; batch New doc is selected authoring, not a migration prerequisite.
- Catalogue Navigation owns its sequence semantics and controls; scope-level Doc Navigation is independent. Neither a single reusable toolbar nor any particular wrap, return or counter policy is implied by this migration.
- No compatibility alias or parallel publication status is retained to keep the frozen archive synchronized with the new model.

## Open Decisions

- Complete the exact archive file and R2 object inventory, checksum manifest and byte-verified copy into `media.dotlineform.com/archive/catalogue/` before the freeze closes.
- Decide whether former `/series/`, `/works/`, `/work-details/`, `/recent/` and `/catalogue/search/` URLs disappear at relocation or remain as narrowly justified redirect shells with explicit retention criteria.
- Retain `analysis.works`, its public Works name, existing document identity and upstream relationships as defined in Catalogue Data Model. Keep any proposed subject-metadata migration separate from collection naming.
- Freeze token syntax, HTML fragment structure, image-only and other justified variants, assets, failure presentation and Work Detail treatment.
- Define the dependency index and targeted invalidation contract for canonical record or projector changes.
- Define the accepted snapshot revision marker and atomic failure behaviour across documents, Catalogue projections, media and Search.
- Audit and retire every current Catalogue publication-status, multi-Series, reciprocal-navigation and direct-`site/` generation consumer.
- Freeze migration from the current collection-valued Series field to optional singular `series_id` without making it a document or publication requirement.
- Freeze embedded anchors, multiple-appearance destination selection, Search field/ranking/snippet ownership and exact de-duplication.
- Choose new canonical public URLs and the relationship, if any, between them and frozen archive URLs.
- Decide which existing Works receive their own documents, which are embedded only, and which initially receive no new presentation.
- Freeze the Work Document Coverage report placement, ordering and unavailable-item copy without turning its findings into editor, Build or Publish enforcement.
- Settle batch New doc selection, starter content and destinations; leave Catalogue previous/next, Media Focus, sequence membership, order, history and return behavior to the Catalogue Navigation feature.
