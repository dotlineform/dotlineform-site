# Document Sub-scope Metadata

## Requirements

Make collection membership inspectable in document source across every configured scope. `doc_id` identifies the document; membership classifies the material it contains. A document in `concepts` discusses concepts without having to define one unique Concept. Moments follow the same document model. Work–Concept meaning can later be derived from document links and the linked documents' collection and Catalogue subject metadata.

The Markdown field is `sub-scope`. Missing, null or empty means a normal scope-level document. A nonempty value is the exact configured sub-scope name, such as `concepts`, `moments` or `works`; it needs no translated label. Existing config and API target fields named `sub_scope` retain their transport role, with an explicit mapping to the source field rather than a second accepted front-matter spelling.

```yaml
doc_id: d-20260624-204534-0d6ae2
title: bird
sub-scope: concepts
```

Configured collection storage remains authoritative. The field records that membership and must agree with it; editing the value alone does not move a document or its media. Parent hierarchy, Catalogue subjects and stage remain independent.

## Deliverables

- One shared metadata rule used across scopes and configured sub-scopes, including scope-level documents and staged sources.
- Automatic destination-owned values on every supported new-document, copy/transfer and import write path, including import overwrites. A sub-scope destination sets its exact name; a scope-level destination removes any inherited value. Incoming metadata cannot select or redirect the destination.
- Maintain the source field when supported body, metadata, Subject and publishability writes save an existing document. Use resolved collection storage as the authority; incoming front matter cannot redirect a write.
- A one-off in-place backfill for existing documents in every configured source sub-scope, including retained source stages. Enumerate configured roots, report unavailable roots, and review conflicting values before writing. Preserve document identities, body content, titles, unrelated metadata and media; do not move directories or rewrite accepted Published snapshots.
- Focused contract evidence and an update to Source Organisation after implementation.

This delivery only creates and maintains the Markdown front-matter field. No existing index, Search JSON, semantic-token JSON or generated document schema needs updating. There is no field editor, selector, button, badge or modal. A document-link token, search-filter UI, authored relationship persistence and publication/deployment actions are follow-on work.

## Process

The author uses the existing New, Copy and Import workflows. Saving into a sub-scope supplies `sub-scope` automatically from the resolved destination. Copying between sub-scopes replaces the source collection value; copying into the normal scope clears it. Supported Move writes follow the destination too. Existing body saves and actual metadata, Subject and publishability writes maintain the same rule. Missing or stale membership is repaired when those source writes occur; metadata no-op requests remain no-ops. Existing documents have received the field through the one-off backfill.

Import retains its existing supported destinations; this delivery does not enable staged Import authoring. Pre-publish remains read-only through authoring services. Its retained source documents were included only in the explicitly authorised one-off backfill. Direct filesystem edits remain the author's responsibility; the watcher does not infer or move collection storage from metadata.
