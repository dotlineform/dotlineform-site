# View Caching and History - Delivery

## Requirements

Deliver one shared navigation and data-reuse policy for document-associated views. Links and Media View are the initial adopters; future hosted views inherit the same behavior unless their definition explicitly overrides it for a documented reason. Users can follow a link from a view and use browser Back to return to that exact view and position, using data already obtained during the page session and without briefly displaying its underlying document.

The approach was agreed on 2026-09-10 during [DR - Delivery](/docs/?scope=studio&doc=d-20260909-124914-76d536). This separate delivery records the shared result and its implementation sequence. The approach is agreed; implementation has not started. [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea) is the feature parent.

### Agreed Defaults

| concern | default behavior |
| --- | --- |
| First use | Fetch the required document or view data once, validate its identity and shape, and retain the successful result for the page session. Reuse a request already in progress for that exact resource. |
| Subsequent navigation | Reuse retained data when revisiting documents, opening or reopening views, and using Back/Forward. Navigation does not trigger freshness checks, background revalidation or expiry-driven rereads. |
| Refresh | Browser refresh starts a fresh page session and obtains current data from the configured owner. Local current data means generated output; public current data means deployed output. |
| Browser history | Opening a hosted view creates a navigation step. Back/Forward restores its exact document and view target, including the selected child document where applicable. |
| View restoration | Restore the view's scroll position and any selection needed to identify the same presentation. Reveal the completed destination directly, with no intermediate document display. |
| Exceptions | A view definition explicitly overrides history participation or data reuse only when its purpose requires different behavior. Omitted settings inherit the common defaults. Record why an override exists. |

Data may change outside the page after it was first read. That is acceptable: browser refresh is the ordinary way to obtain the changed data. Do not add navigation-time revalidation or speculative invalidation to solve that accepted condition. Existing explicit Save and management completion must still update their own visible result; this does not justify refreshing other previously opened data during navigation.

### Shared Ownership

The shared navigation host owns history participation, restorable view state and the transition to the destination presentation. Shared data providers own resource reuse, so callers do not maintain separate copies or competing freshness policies. In particular, an inline Catalogue image and Media View reuse the same Work record.

A view supplies its stable target identity and how to prepare and render that target. The shared mechanism supplies the defaults. Configuration belongs to the existing view-definition/registration boundary; do not introduce Links-specific or Media-specific branches to decide whether common behavior applies. Settle exact field and callback names during implementation.

Document identity remains exact `{scope, stage, sub_scope, doc_id}`. A Media target additionally identifies the actual Work, Detail or supplied gallery selection; a report host must not substitute for its displayed child. Resource keys follow their data owner: Catalogue Work identity is independent of the invoking document. Retained history state must not depend on a discarded DOM control, temporary record number or document-mount generation.

Keep validation of newly obtained data and protection against obsolete asynchronous responses. These checks prevent a wrong target or late response from replacing the selected view; they do not require rereading unchanged data. Failed reads remain retryable rather than being retained as successful content.

### Transport And Session Lifetime

Application-level reuse and the browser's HTTP cache are separate responsibilities. A retained successful result should require no fetch call on ordinary navigation. When a read is needed, allow ordinary content caching through a coherent request and response policy, while ensuring that browser refresh actually obtains current content. Changing only the client fetch option is insufficient if the local server still sends `Cache-Control: no-store`.

Review only the document, child-document, Links and Catalogue content-read paths needed by this delivery. A blanket cache-header change across management, capability, source or write endpoints is not part of the result. Page-session reuse does not require persistent storage or an offline cache.

Browser history state is sufficient for the agreed navigation. A shareable/bookmarkable Links or Media URL is a separate choice; this delivery does not require a new view query parameter.

### Current Behavior To Replace

- Ordinary document payloads already have an in-memory cache. Sub-scope detail navigation performs another fetch even though it records loaded detail payloads.
- Links reads its relationship record each time it opens. Local generated-data requests and JSON responses use `no-store`.
- Catalogue image mounting reads the Work record to display the inline image; selecting that image reads the same Work again to open Media View. The adapter shares simultaneous reads but discards a completed read. Local Catalogue reads use `no-store`; public reads require HTTP revalidation with `no-cache`.
- Browser routing remembers the document and child route, but hosted Links and Media presentations have no restorable browser-history entry. Their current mount-bound state cannot simply be replayed after document navigation.

This agreed direction replaces the per-activation freshness requirement in [Media View Text Links And Catalogue Images](/docs/?scope=studio&doc=d-20260908-224845-502b95). [Catalogue Media View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) still describes the implemented fresh-read behavior and should change when this delivery ships. Catalogue ownership and its independence from document publication remain intact.

## Deliverables

- A shared default policy for page-session data reuse and browser-history participation, with validated explicit overrides at the view-definition boundary.
- Links and Media adoption, including shared Catalogue reads for inline images and their opened Media View, plus supporting document and child-document reuse.
- Restorable exact targets, scroll/selection state and coordinated browser Back/Forward and **Back to document** behavior, with no intermediate document flash.
- Aligned content request/response caching and browser-refresh behavior in local and public compositions, preserving their separate data authorities and existing availability rules.
- Focused evidence, user review and transfer of the accepted shared policy into durable documentation.

The links-builder, relationship JSON schema, Catalogue schema and DR pilot eligibility remain unchanged. This delivery does not widen the pilot or perform Publish, deployment or public activation. Existing host layouts remain presentation choices: Links retains document width and its index panel; Media retains its expanded layout.

## Process

1. Open Doc A. Obtain its data on first use and retain it. Opening a child document uses that child's exact identity and retains its payload as well.
2. Open Links or Media View for A. Reuse any data already available; otherwise obtain it once. Record the view as a history entry and show it when ready. Opening Media View from an inline image reuses the Work record used to display that image.
3. Follow an available document link to Doc B. Keep A's data and view state available for history restoration.
4. Browser Back restores the view for A at its previous position. Another Back returns to Doc A. Forward retraces those steps. Restoring cached data must not visibly render Doc A before replacing it with the view.
5. **Back to document** returns to the invoking document through the same navigation owner, without creating duplicate history entries or a Back loop.
6. Browser refresh obtains current data. A genuine missing cache entry uses the normal read path; any required document/child preparation stays hidden until the requested destination is ready.
