# Scope-configured Authoring Controls

**Superseded on 2026-09-24 by [Document Action Context And Toolbar Placement](d-20260924-144840-e62c72.md).** The replacement primarily consolidates how existing controls receive the active document/collection context. Top-row button placement, including subdocument Back at the left edge, is its visible result. It refactors the existing integration without a new ownership or configuration system. The per-scope availability and Search/Find copy proposals below are historical and are not carried into that delivery. Breadcrumb removal already shipped and remains in place.

The remainder of this document is retained historical proposal text, not active implementation guidance.

## Outcome

Give each displayed document an appropriate set and arrangement of controls. Scope configuration determines authoring availability; the displayed document and report context determine action targets and toolbar placement. A scope should offer the tools appropriate to its content without hard-coded scope inclusion or exclusion in individual buttons. This is a proposed feature for later review and does not block [DR - Delivery](/docs/?scope=studio&doc=d-20260909-124914-76d536).

Ordinary document linking is useful across editable scopes. Catalogue-specific actions such as **Add Media View link** and **Add Catalogue Image** may be useful only in selected scopes. Configuration should express those choices; the initial selection of controls for each scope remains to be agreed.

## Existing Model And Gap

Route configuration already enables broad features such as `source-editing` and supports individual registered control IDs through `view_policy.hidden_controls`. Docs Review uses this to hide Bookmark. The shared control registry validates those IDs and combines route policy with feature, capability, view and mode availability.

All editable scopes share the Manage route, so its policy cannot currently give Studio and Analysis different authoring controls. Scope configuration and its browser projection carry no equivalent control policy. Existing sub-scope customisation capabilities cover particular operations, including Subject assignment, rather than a general authoring-control selection.

Toolbar placement also needs a document-level distinction. An ordinary report often follows authored body content, so its controls belong in the report header. A sub-scope report increasingly serves as the document's main content with nothing above it. Its separate toolbar then creates an unnecessary second row beneath the viewer's top row, particularly in Published where only Search and a few generic controls remain above it.

In Working sub-scope detail, the top Manage controls and the report controls can both act on the displayed child document. Manage provides general document actions such as editing source and metadata; the sub-scope group provides actions for that collection or child. Their distinct responsibilities should remain visible while their buttons share one row.

The former breadcrumbs following Search competed for top-row space, particularly with long paths. They repeated the parent hierarchy available through the Index and described the outer report's ancestry rather than the full context of a displayed collection child. Breadcrumb removal was implemented independently on 2026-09-20. Readers with the Index closed now open it to inspect an ordinary document's hierarchy or navigate to an ancestor.

## Document-Level Toolbar Placement

- Move the sub-scope report's buttons into the viewer's existing top row in both list and child-document detail views. Keep Manage buttons together and sub-scope buttons together as separate groups in that row.
- Implemented: remove the visible breadcrumbs from the shared viewer toolbar, including ordinary documents and collection report views in local and public compositions. Hierarchy navigation remains in the Index, and collection detail retains its Back control for returning to the list.
- Apply this special placement to configured sub-scope reports. They remain ordinary report blocks for content rendering; other report blocks keep their toolbars in the report header, including reports with no preceding prose. Do not infer placement from an empty body or visual position.
- In Working, show each group's available controls in the shared top row. In Published, retain the same placement for reader controls and hide unavailable authoring controls. Empty groups and their separators must not leave gaps or an empty second button row.
- Preserve action ownership and targets when moving the controls. General document actions operate on the exact displayed document; sub-scope list actions retain their collection or explicitly checked-document targets, and detail actions retain the exact displayed child target. Moving a button must not make it act on the outer report host or another selected document.
- Switch the sub-scope group between its list and detail actions as the report changes view, including Back and existing child actions in detail. Returning to the list or leaving the report must clear the previous child controls and restore the appropriate current controls, without duplicate buttons in the report header.
- Keep control placement separate from availability policy. Sharing the top row does not make sub-scope actions generic Manage actions or enable them on a read-only stage.

## Search And Sub-Scope Find

Keep both search inputs: main Search provides the existing scope-wide search, while the sub-scope input provides the useful local title filter for its own list. Their search behavior and coverage remain unchanged.

- Keep the main input's placeholder as `search`.
- Give the sub-scope input a content-specific placeholder, such as `work` for Works or `concept` for Concepts, using wording appropriate to the collection. This distinguishes finding an item in the current list from the main Search.
- Treat this as placeholder copy, preserving the separate inputs, query state, filtering behavior and accessible labels.
- Eventually we could just have a single Search box which is context-specific?

## Scope-Configured Availability

- Extend the existing view-policy model into canonical scope configuration and project the required browser-safe policy through the existing config owner. Reuse registered control IDs and the shared control registry.
- Resolve policy for the exact mounted document's scope and stage, including a displayed child document. Do not derive it from an outer report selection or an unrelated route default.
- Define explicit defaults and inheritance. Sub-scopes should inherit the scope policy; add explicit sub-scope overrides only if the authoring requirements warrant them.
- Keep route, stage and service restrictions authoritative. A scope policy must not enable editing on a read-only stage or expose a control whose required capability is unavailable.
- Apply one resolved policy consistently to control availability and invocation. Avoid per-button scope tests or a second independently maintained list of permitted actions.
- Treat authoring availability separately from token parsing, existing content rendering, document-link targets and relationship eligibility. Changing a toolbar policy must not silently invalidate existing content or change Build rules.

## Decisions For Later Review

Agree the initial per-scope control selections, whether to retain the existing hide-list form or introduce an explicit allowlist, the default for newly registered controls, and whether any sub-scope needs an override. Validate unknown IDs and define inheritance without ambiguous empty or missing values.

The toolbar placement outcome, breadcrumb removal and distinct search placeholders are concrete and can be delivered independently of the later per-scope control selections. Review the shared top row in Working and Published, navigation through the Index and sub-scope Back control, distinct Search and Find inputs, sub-scope list/detail transitions, exact action targets, and ordinary reports retaining their header toolbars. Visual grouping, spacing and placeholder wording remain manual review; action availability and invocation must agree for the mounted target.

The availability change crosses scope configuration, its browser projection and the existing control-policy resolver. The placement change uses the existing viewer toolbar and sub-scope report owners. Neither requires a new toolbar framework or arbitrary per-document control configuration. Breadcrumb removal is complete in the repository; the remaining proposal still needs review against the current workspace and collection model before a bounded delivery is defined.

The breadcrumb change removes `docsViewerPath`, its runtime references, link rendering and dedicated CSS, while retaining the ancestor lookup used by Index expansion and document context. Focused source/diff review found no remaining breadcrumb consumers or changes to action targets. JavaScript lint passed for the three changed shared modules; the four-file public code projection and site validation passed. Visual review remains manual; no tests, commit or deployment were performed.
