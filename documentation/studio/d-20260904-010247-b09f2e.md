# Nav Implementation

## Purpose

Record how the current public Catalogue implements navigation and how to borrow that working pattern for Docs. [Catalogue Navigation](/docs/?scope=studio&doc=d-20260903-222617-28475e) owns the required behaviour and acceptance cases; this document explains the implementation starting point, not a replacement navigation framework.

The current-site and Docs observations below were checked against repository code on 4 September 2026. The adaptation is proposed, not implemented. Code remains the authority for current behaviour.

## Current Site: Small URLs, Loaded Sequences

The URL supplies identity and optional browsing context, not calculated navigation values:

- `/works/?series=084&work=00520` selects a Work within explicit Series context.
- `/works/?work=00520` selects the same Work without sequence context.
- `series_page`, when supplied, is carried through previous/next and the return-to-Series link.

The selected Series route loads `site/assets/series/index/<series_id>.json`. Its lightweight, ordered `member_works` entries provide the Works for the gallery. Work thumbnail links carry the selected Series ID.

The Work route loads `site/assets/works/index/<work_id>.json` for the selected Work's content, metadata and Details. It passes Work identity and membership to `createSelectedWorkSeriesNavigation()`, which loads the relevant exact Series payload. The current multi-Series model can require both a primary Series and a different explicitly requested Series; when they are the same, one payload serves both uses.

The navigation owner validates the exact Series record and the Work's membership. It exposes sequence controls only for valid incoming Series context, not merely because the Work belongs to a Series. Membership-based Series links and contextual browsing are separate concerns. Current public-status and membership checks belong to today's model; the migration must adapt them to the accepted Analysis snapshot rather than recreate a second publication lifecycle.

### Neighbours And Counter

`exactSeriesWorkIds()` extracts the ordered IDs. `projectSeriesNavigation()` finds the current index and derives:

- previous: the preceding entry, wrapping from the first to the last;
- next: the following entry, wrapping from the last to the first;
- position/total: current index plus one, divided by array length.

Controls are hidden when the current Work is absent or the sequence has fewer than two entries. Previous/next URLs retain Series context and any supplied return-page value. No `work_prev`, `work_next`, `work_total` or full member list is stored in the URL.

The inspected Series `084` payload gives a concrete example:

~~~text
ordered Works: 00520, 00521, 00522, 00523
current Work:  00520
previous:      00523
next:          00521
counter:       1/4
~~~

Navigation uses the payload's order, not a scan of the visible gallery DOM. The Series route also has presentation sorting; do not assume an arbitrary user-selected display sort is automatically carried into Work navigation. The Docs gallery and its navigation sequence must use the same agreed order.

### What Is Retained In Memory

`createSelectedWorkSeriesNavigation()` holds a `payloadPromises` Map keyed by Series ID. The first request stores its promise; subsequent requests within that instance reuse the same pending or completed result. Current Work identity, Series context and return-page information are ordinary JavaScript variables. Neighbour calculations then use loaded data, without a separate request for each control or counter.

This cache is page-local. Work previous/next links are ordinary page navigations, so another page creates another navigation instance. `fetchJson()` uses `fetch(url, { cache: 'default' })`: normal browser HTTP caching may satisfy or revalidate repeated requests. The in-memory Map is not persistent storage and does not survive a full reload. Source inspection establishes that behaviour, not a measured network-download guarantee.

### Current Work Detail Navigation

`work-detail-page.js` loads the containing Work payload, locates the selected Detail in its sections and derives a section's ordered Detail IDs. It uses the same index/wrap/count pattern and carries Work, Series and return-page context in its links. The current code falls back to all sections if the requested section yields no Details. That fallback is not a proposed Media Focus rule: the new view must use its explicitly supplied collection. No separate JSON request is needed for each neighbour or total.

Reuse the sequence handling for Media Focus. The composite `detail_uid` encodes the exact Work and Detail IDs, which the new integration can parse directly without an ownership lookup. Studio owns that data-quality contract, as clarified in [Catalogue Data Model](/docs/?scope=studio&doc=d-20260903-231534-b63aa9). Media locations come from the consumer payload; parsing identity does not itself define an image URL.

## Current Code To Start From

Catalogue paths below are relative to `site/assets/js/catalogue/`.

| source | responsibility |
| --- | --- |
| `routes/series-index.js` | exact Series payload, gallery items and contextual Work links |
| `routes/work-page.js` | exact Work payload and navigation-owner composition |
| `navigation/work-series-navigation.js` | exact membership, page-local promise cache, neighbours, counter and return links |
| `shared/catalogue-urls.js` | query parsing, payload URLs and destination construction |
| `shared/fetch-json.js` | default browser-cache fetch policy |
| `routes/work-detail-page.js` | section-based Detail sequence and contextual return links |

The reusable part is the small data/sequence calculation and ownership pattern. Do not make the new surface import frozen archive runtime or preserve legacy routes as compatibility aliases.

## Borrowing The Pattern For Docs

Keep document identity, browsing context and calculated navigation separate:

| state | where it belongs |
| --- | --- |
| report host and selected sub-scope document | ordinary Docs route: scope, `doc`, `subdoc` |
| originating Series/gallery and return-page context | minimal explicit route context |
| accepted ordered sequence and exact Work-document destinations | loaded data retained by the active navigation owner |
| current position, neighbours and total | derived together from the selected target and sequence |
| controls | sub-scope report document toolbar |

A document's explicit `work_id` subject identifies the Work it is about; `cat_id` is abandoned. That subject does not make the document the Work's unique presentation. The route sketch below belongs to this earlier document-navigation proposal; [Concept](/docs/?scope=studio&doc=d-20260904-014334-f3dab5) now separates document routing from exact Work and gallery targets in Media View.

An illustrative, not final, URL is:

~~~text
/docs/?scope=analysis&doc=<report-host>&subdoc=<work-document>&series=084
~~~

The context representation must also resolve the exact originating Series document/gallery. One Series identifier may suffice for a single unambiguous gallery; multiple distinct galleries need enough additional identity to distinguish their sequences. Do not pre-empt that decision with previous/next IDs or totals in the URL.

### Three Adaptation Points

1. **Payload source:** consume the accepted Catalogue/gallery projection belonging to the displayed Analysis output, not mutable canonical records or frozen archive JSON.
2. **Destinations:** resolve each Work through its typed Catalogue reference to the exact document target and build a Docs URL carrying the browsing context. Missing or ambiguous Work documents remain unavailable; do not use title, route or embedded-occurrence guesses.
3. **Presentation and lifetime:** put document controls on the sub-scope report toolbar and retain the loaded sequence in its navigation owner across Work-document changes, independently of the replaced content DOM.

Reuse an already loaded gallery sequence when entering a Work from that gallery. Opening a fresh contextual URL may require loading the sequence once. While its context and accepted data revision remain unchanged, moving between Works should not reload Series JSON merely to calculate neighbours or counters.

A missing or invalid context leaves a valid Work readable without sequence controls. A direct Work URL must not inherit a previous gallery from the cache. Define cache release/invalidation for a changed collection, context or data revision; persistent browser storage and a general-purpose caching framework are not requirements.

### Existing Docs Seams And Limits

Canonical `docs-viewer/runtime/js/shared/docs-subscope-report.js` already provides `renderDetailToolbar()` contributions, exact sub-scope document loading and `writeSubdocUrl()` history updates. Use those owners; the tracked `site/docs-viewer/` files are their public projection.

Today, `writeSubdocUrl()` updates `doc`/`subdoc` while its report history state records only `subdoc`. Carrying and clearing Catalogue context coherently across links and history therefore needs explicit integration; incidental query preservation is not a complete implementation.

`renderDetailById()` currently fetches the selected document payload on each selection using normal browser caching. Although `detailPayloads` stores loaded payloads, this loading path does not consult it as a fetch cache. Loading the next Work document is distinct from repeatedly loading Series data for navigation; this proposal does not assume document fetching is already eliminated or require a broader caching rewrite.

## Media Focus Uses The Same Principle, Not The Same Controller

[Catalogue Media Focus View](/docs/?scope=studio&doc=d-20260903-154141-7c9e4b) receives an ordered image collection and selected image ID. It derives its own previous/next and position/total in memory and updates the image, caption and original-image target together. Moving between images may load image resources; it should not reload Catalogue JSON to discover neighbours.

Use the existing Content Detail adapter lifecycle in `docs-viewer/runtime/js/shared/docs-viewer-content-detail-view.js`. It currently supports table, diagram and report adapters, not an image adapter. Media Focus is new work, with its own image controls; it does not navigate between sub-scope documents.

Retain the Work's optional Series-gallery context underneath that view. Returning restores the same Work-document navigation state, including the absence of context on a direct visit.

## Still To Decide

- Exact context query fields, gallery identity and Series-document return resolution.
- Where the accepted sequence and Work-to-document lookup are projected, and their revision/invalidation boundary.
- Treatment of unavailable Work documents in traversal and totals.
- Any gallery sorting that should change the sequence, rather than merely its visual presentation.
- Series-to-Series navigation and image-collection boundaries; Work-within-Series cycling does not settle those designs.

No implementation, migration or delivery-sequence change is authorised by this document. Scope-level Doc Navigation remains independent.
