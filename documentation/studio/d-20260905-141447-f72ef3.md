# Gallery List Design

## Purpose

Define the list block being explored in [UAC 3](/docs/?scope=studio&doc=d-20260904-204816-0f31be), alongside [Gallery Design](/docs/?scope=studio&doc=d-20260905-120654-ab5e59). A thumbnail gallery supports visual browsing in Media View. A list helps readers find a specific item through identifying metadata and choose among available image, document and file actions.

The list does not have to use the existing report mechanism. Decide content generation, data loading and interaction separately; no new category between tokens and reports is required. This document records requirements and questions, not a completed implementation design.

## Required Behaviour

- Parameterisation selects a list of Works in a Series or a list of Details in a Work.
- The block derives its Catalogue context from the containing document's declared subject. It belongs in a document about the relevant entity; placement anywhere in a document does not mean arbitrary unrelated target selection.
- The block is insertable at an authored position, surrounded by ordinary document content, and has toolbar button(s).
- Its visible size is bounded. Scrolling or pagination handles longer collections without making the block take over the document.
- Rows expose useful identifying metadata and separate actions where available. Opening an image uses Media View; associated documents and files remain distinct destinations.
- Returning from Media View preserves the containing document and the block's filter, page or scroll position.

## Subject And Parameters

Keep the document's identity, its subject, and the identities of listed items separate. The existing public collection remains `analysis.works`. [Catalogue Data Model](/docs/?scope=studio&doc=d-20260903-231534-b63aa9) records the five accepted subject choices: none, a real Folder only in `dotlineform`, `series_id`, `work_id` or `detail_uid`. Detail-subject support is a new field to implement.

The two collection modes have these direct subject mappings:

| list requested | containing document's subject | row identity |
| --- | --- | --- |
| Works in a Series | exact Series, identified by `series_id` | `work_id` |
| Details in a Work | exact Work, identified by `work_id` | `detail_uid` |

`detail_uid` encodes `<work_id>-<detail_id>`, so a Detail-subject document gives both exact IDs by parsing, without a formal ownership lookup. Studio owns the data-quality contract; Docs Viewer uses it. Decide which collection or selected-item presentation the block offers in a Detail-subject document. Access to the owning Work does not change that document's declared subject.

Detail does not imply a supplementary or less-important item. Series `023` contains one Work, a printed list of photograph dates, and 523 Details that are independent photographs. Direct Detail subjects and suitable list/gallery presentation must accommodate that use.

Parameters should express the requested collection or presentation without duplicating the subject's target ID. Decide which choices follow automatically from subject kind and which remain authored options, including Detail sections and ordering.

## Implementation Questions

1. Can Build supply useful rows and links, with shared JavaScript adding filtering, sorting and Media View actions? Our table and Media View adapters already provide examples of attaching behaviour to document content.
2. When should the block fetch a compact membership/list payload instead? The runtime must support on-demand by-ID loading; embedding every member's full presentation is not a production requirement.
3. Which existing report facilities are useful, if any? Module size, dependencies, requests and responsibilities determine cost; runtime JavaScript alone does not make something a report.
4. What is the source form, and how is it inserted? Define the block toolbar's actions and any source-editor toolbar insertion button(s) separately.
5. Which columns, search fields, filters and ordering suit Works and Details? Does a Detail list preserve section headings, and what sequence does opening an item establish in Media View?
6. What sets the block's maximum size? Choose scrolling, pagination or appropriate parameters, including keyboard access and narrow public layouts. UI pagination and downloading data in separate pages are independent decisions.
7. Can a document contain several instances, and how does each retain its own controls and state?
8. How does the wider content initialization and cleanup run in ordinary and sub-scope documents? UAC 3B now mounts ordinary inline reports in child documents using the existing loaders and exact child context. Work title actions supply an on-demand presentation to Media View while preserving the child and list. Child Expanded Report View and general authored media markers remain open; nested sub-scope collection reports remain unsupported.

## Data And Publication

Follow [Publish workflow](/docs/?scope=studio&doc=d-20260905-141447-c33de1): Manage reads generated consumer data; public readers fetch only the accepted published snapshot. Dynamic loading changes when bytes are fetched, not which publication is authoritative.

Measure compact list data separately from thumbnails and full images. Load selected images as needed. Keeping all rows hidden behind pagination does not reduce their initial download. Decide data partitioning and caching using representative Series and Work Detail collections after the small interaction proof.
