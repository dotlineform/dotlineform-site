# Export

Docs Viewer Export creates a browseable dated static HTML snapshot from existing generated document payloads. Every snapshot includes the existing multi-file site plus a text-first `portable.html` containing the same selected documents in one file. The output is a user-owned visual and text reference outside Docs Viewer; it is not canonical source, an import package, or a managed archive.

## Workflow

Export is available in each Collection Actions menu while Manage is active. Collection selection is its only entry point and input contract.

Collection **Export…** uses the existing collection checkboxes and All/Clear/Done controls shared with Prepare Package. Choose **Select** (`list-check.svg`) before Actions to enter selection mode; Select is replaced by All/Clear/Done until Done clears selection and restores it. Opening Actions does not change selection mode; Export is disabled until at least one document is checked. All retains the existing filtered collection selection scope. Export captures the checked IDs and exact collection when invoked, including checks retained across page/filter changes, and uses the common confirmation and snapshot writer. Catalogue offers Export while its authoring and Prepare Package restrictions remain unchanged. No manifest reload, document build, Search refresh or publication work follows an export.

The confirmation identifies the collection, destination and media plan:

```text
Export N document(s) to:
/docs-export/<dated folder>/
Includes M media file(s).
Leaves E external media reference(s) unchanged.
```

The external-reference line is omitted when its count is zero.

The primary button is **Create snapshot**, **Replace**, or disabled **Unavailable** according to the previewed target. Replacement uses the danger tone and initially focuses **Cancel**. The document IDs are captured when Export starts and retained through its confirmation.

## Input And Eligibility

Export needs:

- `$DOTLINEFORM_PROJECTS_BASE_DIR` resolves the external `docs-export` workspace;
- the selected collection's generated `manage-manifest.json`; and
- its configured generated by-ID root is a directory.

Collection actions use their mounted management contribution and existing loaded selection. There is no separate Export capability projection or preflight. Explicit Preview requires a configured `collection`, resolves that Working owner, reads its `manage-manifest.json` and opens only selected by-ID payloads. Missing configuration, metadata, payloads or export storage fails at that operation. Canonical-source ownership and source writability are not capability gates. Draft and publication-excluded collection documents present in Manage remain eligible.

Export reads generated flat collection membership/order, titles and selected payloads. Each request invokes `docs_catalogue_static.py` once per selected document, sharing operation-local Work/policy/relationship inputs and carrying the prepared values into planning/writing. It does not read the ordinary Index, parse canonical Markdown, rebuild documents or apply a second publishability filter.

Selected filenames and collection membership are checked at the request boundary. Payload loading, plan hashing and both renderers then trust the completed generated records without repeating ID/schema agreement checks, replacing missing IDs, coercing fields or falling back to substitute titles/content. Each Preview or Apply request resolves the export workspace once and carries that root through destination confinement and installation.

An expanded `[[summary]]` contains the builder's restricted bold/italic markup, escaped literal HTML and explicit `<br>`/paragraph elements. Both the browseable snapshot and `portable.html` retain that formatting and include Summary panel/paragraph styling; YAML syntax is not part of either HTML output. Export does not place a metadata-only Summary into the body automatically. Rebuild the owning generated documents to obtain changed rendering before creating a new snapshot. Existing exported folders are unchanged until explicitly exported/replaced. [Package Prepare](Package_Prepare.md#package-output) separately flattens Summary for its text-oriented packages.

From the exact selected generated HTML, Export recognizes media only when a supported URL attribute maps beneath the owner's generated logical media prefix, derived from its configured served prefix. Prefixes are prepared once per request. One HTML pass collects distinct owned references/external dependencies and rewrites owned URLs to their deterministic package paths; there is no separate discovery-only HTML pass or second media-rewrite pass. Documents without owned media retain their original HTML. It then reads each distinct confined identity once through that media type's configured repository, external-local, or R2 artifact location. Missing, invalid, escaping, or unreadable owned media blocks preview. Unmatched media references remain external and unchanged; Export does not fetch their served URLs or inventory unrelated media.

The selected collection owner supplies its resolved document-media map directly to media planning. The shared preparer separately supplies exact configured Work-media descriptors, preserving Catalogue's `document_media: false` boundary. The same HTML pass converts Work image/text openers into ordinary links to the presentation's standard `image.src` rendition, currently 800px, and retains Gallery opener text. Export removes larger responsive candidates, original image dimensions and the viewer's fixed frame ratio from Work images/controls; images display at their natural size and shrink proportionally to the available page width. Only emitted images/linked files map into deterministic `media/catalogue/works/...` package paths. Each distinct selected object is read once from Working; Export does not fetch public image URLs or package every Gallery member. Browseable output contains visible Entry/images/captions/summary without viewer JavaScript. `portable.html` retains its text-first image placeholders and unrelated external dependencies keep their existing behavior. Prepared HTML and packaged media bytes participate in the existing Preview/Apply revision, so meaningful Work changes require a new confirmation.

## Destination And Naming

Snapshots live under:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-export/
```

The server derives the folder from its local export date:

- a complete collection uses `<collection title> - YYYY-MM-DD`;
- a partial collection, including one document with unselected peers, uses `<collection title> selection - YYYY-MM-DD`.

Complete-set classification takes precedence for a one-document collection. Labels receive only bounded filesystem-safe normalization. There is no **Save As**, arbitrary destination, or background scheduling.

One equivalent label and local date names one destination. Preview classifies it as `absent`, `directory`, or `non_directory`. Every existing directory requires explicit replacement confirmation; a non-directory target is blocked. Export does not parse or audit a prior `snapshot.json`, distinguish recognized/unrecognized snapshots, or return an unused prior-snapshot summary. The existing exact destination-byte revision still guards replacement.

## Preview And Apply

The management-only endpoints are:

```text
POST /docs/export/static-html/preview
POST /docs/export/static-html/apply
```

Preview requires exact `doc_ids` and one configured `collection`; the service resolves Working. It returns `docs_static_html_snapshot_preview_v2` with collection identity, IDs in generated manifest order, selection kind, deterministic default, local date, display-safe destination label, packaged-media count, unchanged-external-dependency count, target state, `replacement_required`/`replace_allowed` decisions, and plan/target revisions. Confirmation displays the number of packaged media files without a byte count. Preview writes nothing and exposes no media identities or absolute workspace path, but it reads and hashes each exact referenced owned object to make the plan truthful. The browser consumes the supplied decisions directly for confirmation and Apply, without schema/count/ID/revision audits, target-state reclassification or a post-confirmation availability recheck.

Apply is assembled from that preview and carries:

```json
{
  "collection": "library",
  "doc_ids": ["d-20260426-164043-e14f49"],
  "export_date": "2026-07-31",
  "plan_revision": "<sha256>",
  "target_revision": "<sha256>",
  "confirm": true,
  "replace_existing": false
}
```

Apply carries the preview's exact `collection` and document IDs; it does not infer the owner from the currently displayed view. Collection identity, title and the configured public viewer route participate in the existing plan revision.

The service recomputes the complete plan and destination state once for Apply, including selected generated-body digests and fresh media byte digests, and compares them with the confirmed revisions. Selected payload/media rereads and destination hashing across Preview and Apply remain intentional parts of exact-bytes confirmation. A changed generated payload, media object, configuration or target requires a fresh preview. It then updates the confirmed destination in place: an absent final directory is created directly; the completion manifest and existing files are removed; directory paths still required by the new artifact are retained; other emptied directories are removed; and the complete desired file set is written directly, with `snapshot.json` last. Installation prepares one required-directory set, creates each directory once and passes that same set to final file-set/byte verification; the per-file writer does no directory creation. Verification includes the manifest bytes. No additional pre-install destination scan or post-install provenance parse/hash scan runs. Configured path/symlink safety remains. Regular Finder `.DS_Store` files are preserved and excluded from destination revision and artifact validation; no other extra entry is ignored.

There is no staging directory, backup rename, rollback, locking, or retry machinery. If writing or verification fails, the completion manifest is removed and the partial destination remains; resolve the problem, preview again, and rerun **Replace**.

There is no export delete route or capability. Snapshot folders are user-owned after creation; Docs Viewer does not list, rename, prune, retain, or remove them.

## Artifact Contract

Each snapshot’s managed artifact contains exactly:

```text
<dated folder>/
  index.html
  portable.html
  styles.css
  snapshot.json
  docs/
    <selected doc_id>.html
  media/
    <media type>/
      <confined relative identity>
```

`index.html` preserves the selected flat collection manifest order and uses the owning collection title. The first selected document in that order is the default.

`portable.html` is an additive single-file view for platforms such as iPadOS where local `file` navigation between exported files is unreliable. It inlines the export stylesheet, renders one article per selected document, and uses in-page fragments for its index and selected document links within the same collection identity. Deep links to a selected document heading resolve to that document article in the portable view. Images are represented as `[image: alt text]`, or `[image]` without alt text; the existing multi-file pages and packaged media remain unchanged. Beneath each **Back to index** link, a caption-style code line shows a literal Markdown reference token using the configured public viewer route and the exact collection/document identity, such as `[document title](/?collection=library&doc=<doc_id>)`, for direct reuse in notes.

Each document page inserts its existing generated `content_html` without adding another heading. Docs Viewer links become local only when the target's collection identity matches the exported owner and its document is included. Links to unselected documents and other collections retain their viewer target; query-only links receive the configured public viewer route so they do not resolve within the exported folder. External locations retain their original targets. Fragments are preserved in the multi-file pages.

Each exact referenced workspace-owned object is copied once to `media/<media type>/<identity>`, even when several selected documents use it. Matching `src`, `srcset`, `poster`, `data`, and configured media `href` references become document-relative packaged URLs. Cache queries are removed after the bytes are frozen and fragments are preserved. Unmatched media references remain unchanged and are recorded as external dependencies without credentials or query strings.

The snapshot does not recursively inspect copied HTML, CSS, scripts, frames, fonts, or site-shell dependencies. All fenced code remains readable source; diagram images use ordinary imported SVG media.

`snapshot.json` uses `docs_static_html_snapshot_v3` and records the required collection identity, exact ordered IDs, selection kind, document count, default ID, local export date, generation time and plan revision, without scope/stage fields. Each packaged media row records its media type, confined identity, provider kind, packaged path, SHA-256 digest and referencing selected document IDs; separate rows record unchanged external dependencies. Preview, Apply and saved provenance carry no media byte total or per-media size field. Folder names are presentation labels; the manifest records the completed export identity, while the exact destination-byte revision guards replacement without auditing that manifest's fields.

## Ownership

Backend planning, rendering, provenance, target inspection and direct in-place Apply:

```text
docs-viewer/services/docs_static_html_export.py
docs-viewer/services/docs_static_html_export_media.py
```

Routes and management access:

```text
docs-viewer/services/docs_management_routes.py
docs-viewer/services/docs_management_service.py
docs-viewer/services/docs_viewer_service.py
```

The single browser workflow owner contains Preview/Apply requests, confirmation, busy completion and status handling:

```text
docs-viewer/runtime/js/management/docs-viewer-collection-export-workflow.js
```

The collection contribution owns checked-row presentation, the action resolver owns its `collection-selection` target and `docs-viewer-management-document-reports.js` supplies the exact target and shared management services to the workflow. Generic HTTP transport remains in `docs-viewer-management-client.js`. Python's snapshot service owns planning/rendering/writing and delegates referenced-media preparation to its media helper; there is no duplicated workspace or Index export workflow.
