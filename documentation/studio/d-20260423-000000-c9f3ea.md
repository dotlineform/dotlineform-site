# Builder

The Docs Viewer builders turn canonical Markdown and front matter into generated reader and search payloads. They do not deploy the site.

## Commands

```bash
$HOME/miniconda3/bin/python3 docs-viewer/build/build_docs.py --scope studio
$HOME/miniconda3/bin/python3 docs-viewer/build/build_docs.py --scope studio --write

$HOME/miniconda3/bin/python3 docs-viewer/build/build_search.py --scope studio
$HOME/miniconda3/bin/python3 docs-viewer/build/build_search.py --scope studio --write
```

Dry-run is the default. Use `--help` for current flags rather than relying on a copied inventory here. `--only-doc-ids` selects ordinary document payloads after orchestration has calculated a safe affected set. A full scope build can initialise or reconcile ordinary generated output. Links uses the scoped refresh described below; missing Links records warn and skip even during a scope build.

## Registry And Owners

`docs-viewer/config/scopes/docs_scopes.json` owns:

- scope ids and types
- source roots
- published docs and search locations
- viewer routes and default documents
- public publish paths where applicable
- nested/sub-scope rules
- media types, source roles, publication locations, and browser-safe viewer settings

`build_docs.py` delegates focused work to `docs-viewer/build/docs_builder/`. `build_search.py` owns Docs Viewer search projection. Both consume the scope registry; neither should contain a hand-maintained list of scopes.

## Docs Build Flow

1. load and validate the configured source corpus
2. parse identity/tree metadata from front matter
3. run configured media producers into their configured build outputs, then resolve supported media and semantic tokens
4. interpret Unicode-whitespace-only lines as blank outside fenced code and explicit `<pre>` blocks, then render Markdown and permitted raw HTML
5. build the tree, Recent, per-document, local semantic-token usage, and browser-config projections
6. compare content versions, write changed payloads, and remove stale owned payloads
7. for an enabled Working scope, await Links refresh for the selected changed/deleted documents and their affected neighbours before returning success

The source Markdown is canonical. Generated JSON is a projection and can be rebuilt. Render-time blank-line hygiene does not rewrite source files; managed Source Save and Docs Import apply the same narrow rule when they write canonical Markdown.

Configured media producers run before document rendering. A full build requests every configured build-media identity; `--only-doc-ids` derives same-scope build outputs from the selected documents' logical media tokens and requests only those identities. Mermaid is the first registered producer: canonical `.mmd` remains source authority and its same-basename sanitized SVG is the published reader asset.

## Reader Subject Metadata

Every ordinary and sub-scope `by-id/<doc_id>.json` payload and every document row in a sub-scope `manifest.json` contains `subject`. A valid Catalogue declaration becomes an exact `{kind, key}` object, such as `{"kind": "work", "key": "00635"}`. Supported kinds are `work`, `series` and `detail`; keys remain strings, including leading zeroes and the complete Detail UID. Missing, malformed, conflicting or Folder declarations produce `null`. `docs-viewer/services/docs_document_subjects.py` owns this compact reader projection through the existing authoring normalizer; it does not consult Catalogue data or infer identity.

The same projection serves local and public reader payloads without exposing Folder paths, raw source values or authoring diagnostics. `manage-manifest.json` retains its separate `authoring_subject` metadata for management controls and diagnostics. Document Build updates the reader Subject in both manifest and by-ID output, including clearing it after a declaration is removed. Accepted Published and deployed site snapshots receive the field through their normal publication workflow.

Manifest rows do not repeat `sub_scope`: their configured report supplies exact collection context to list and detail consumers. Subject metadata supports subsequent icon rendering but does not add icons itself.

## Document Relationship Maintenance

Scope-level and child Doc Build call `docs-viewer/build/docs_builder/links_builder.py` after ordinary document output and await its completion. `docs-viewer/config/links-builder.json` selects Analysis Working, including its configured sub-scopes. Source-write operations and the watcher pass the exact changed, created and deleted document IDs separately from the ordinary renderer's target set. A full child render or an ordinary-renderer fallback does not expand an ordinary save's Links target set.

Resolve exact `{scope, stage, sub_scope, doc_id}` ownership through configured storage. Canonical source filenames are `<doc_id>.md`, with front matter confirming identity; generated destinations are exact by-ID files. Child viewer links resolve through their exact Working report host. Stored relationship targets contain `{scope, sub_scope, doc_id}`; stage belongs to the containing source/output context. Stored hrefs omit stage, and the browser adds the current stage when navigating. Links for a different scope or stage are excluded. Ordinary authored Markdown/HTML document links supply references; Catalogue media/image tokens do not create document relationships.

`links_model.py` owns per-document relationships and contributor replacement. `links_schema.py` validates and serializes separate `generated/documents/links-by-id/<doc_id>.json` records beneath the configured scope/stage documents root, shared by parent and child documents. Version 1 contains `self`, `incoming`, `outgoing` and `counts`. Summaries carry the exact target, title, ordinary href and normalized Subject. Counterpart entries retain repeated occurrence labels and hrefs, with occurrence and distinct-document counts. [Links View](/docs/?scope=studio&doc=d-20260910-202325-53b5f9) consumes one prepared record directly.

The existing Links record is the refresh's only relationship prior state:

1. Read the current record, preserving its incoming and previous outgoing entries.
2. Parse the current document's Markdown and resolve its available outgoing targets.
3. Read each linked neighbour's record, replace the current document's incoming contribution there, and copy the neighbour's details into the new outgoing list. Preserve every other contributor.
4. When the current title, Subject or location changes, update its outgoing summary in each known incoming neighbour.
5. Remove its incoming contribution from previously linked neighbours absent from the new list.
6. Write the current details and outgoing list while preserving incoming entries; write only changed records.

A neighbour update does not rebuild that neighbour's Markdown or ordinary payload and does not recurse into its neighbours. No collection Index/manifest, scope-wide reference baseline or whole-graph pass supplies Links refresh state. Both endpoints must have their exact available source and ordinary by-ID payload and satisfy fixed eligibility. Unavailable targets are silently omitted; Broken Links diagnoses destinations independently.

Links reads the configured Analysis Working ordinary `source/documents/unpublishable.json` once per operation through `docs_publication_ignore.py`. Exact ordinary IDs in that set are excluded; sub-scope IDs do not participate. Drafts remain linkable. Editing the file does not reconcile existing relationships automatically; subsequent ordinary builds use the new set, and any consequential full refresh is an explicit user operation. `folder_path`, `work_id`, `series_id` and `detail_uid` are independent subjects and never determine eligibility. Folder documents follow the same rule as all other subjects. Subject edits refresh summaries; draft-only changes leave Working Links unchanged.

A genuinely new document receives its initial Links record through explicit creation information from the owning source operation or existing watcher snapshots, including the parent report created with a new Working sub-scope. Creation is never inferred from missing ordinary or Links output, and source rollback does not authorise initial creation. An unexpectedly missing current record emits an identity-bearing warning and skips that document's Links refresh. A missing neighbour record warns and skips processing that relationship. Warnings do not fail Save/Build and do not create replacement records, retries or a recovery workflow.

An explicitly approved one-off backfill on 2026-09-13 completed the existing Working dataset: 221 missing records were created and all 588 eligible documents' relationships were refreshed from current sources. Four obsolete records for ignored ordinary documents were removed, and the aggregate was updated. The normal Links refresh subsequently reported no missing records or proposed changes across all five Working collections. This completed the initial data population without adding an automatic repair or permanent bulk mode.

Deletion uses the previous record to remove the document's contributions from known neighbours before removing its own record, including the final document in a child collection. Collection placement keeps the immutable ID: the destination builds first and transfers the exact prior Links record after the old source is removed. The former collection's deletion cannot remove the destination-owned record. The placement owner rewrites authored source links; Links updates counterpart identities and hrefs, including self-links and fragments.

A scope/stage lock serializes relationship writes. Success means ordinary output and every non-skipped Links write/removal have completed. Malformed records and actual operation/write failures propagate synchronously; a failure can leave ordinary output and some relationship writes completed. There is no automatic repair or full-refresh fallback. Investigate and correct affected documents or records individually.

Scope Build applies this same refresh to the documents it builds and then aggregates the prepared records at the existing scope completion point. Ordinary saves leave the aggregate alone. `docs-viewer/tests/python/test_docs_links_builder.py` protects relationships, exact destinations, scoped reads, creation, moves, deletion, warnings and failures; write/watcher/lifecycle tests protect the identity handoffs. The separate `docs_backlinks_v1` output remains owned by `backlinks.py`. Source inventories, backlinks, collection indexes and full child rendering still contribute to whole-Save cost; scoped Links maintenance does not imply collection-independent total Save time.

## Working Scope Rebuild And Links Aggregate

The separate **Pre-publish** action in Working replaces Pre-publish source/generated derivatives from the current Working source snapshot and awaits ordinary documents, every configured collection and Search. It excludes draft documents and ordinary documents explicitly listed in `unpublishable.json`, together with all their descendants. The JSON file retains only the explicitly listed IDs; inherited exclusions are computed during preparation without adding descendant IDs to the file. Any excluded report host, including one beneath an ignored ancestor, excludes its collection. Sub-scope document IDs do not participate in the ignore-list lookup; their existing draft rules remain. Working defaults missing draft metadata to draft. Report declarations are preserved without per-report `access`; report type does not select or rewrite documents. Authoring-only subject fields are removed while exact valid Catalogue subjects survive into normalized reader payloads. No existing Published or site JSON migration is required.

**Publish** in Pre-publish validates its complete, stage-bound Build and accepts all prepared documents and indexes without another eligibility filter. It reconciles the scope-owned `published/` snapshot through the existing revision-bound publication owner, retaining identity, payload and media validation. Failed preparation leaves no valid Build completion marker and cannot publish a previous generated snapshot. Working changes and deletions appear in Pre-publish on the next explicit preparation. Public deployment remains a separate operation over accepted Published data.

Links remains Working-only. Neither Pre-publish nor Publish refreshes or validates Links. If ready A links to draft B, Pre-publish omits B and preserves A's authored link; Publish consumes that prepared set. The reference does not block A, include B, suppress its link or produce a publication warning. The current Analysis Broken Links report audits Working, where an existing draft target is available; it adds no publication-stage gate.

### Existing Pre-publish Selection Evidence

The bounded existing selection in `docs-viewer/tests/python/test_docs_pre_publish.py` is `test_readiness_and_intent_exclude_descendants` (explicit and missing draft state), `test_ignore_set_is_additional_and_does_not_exclude_child_collection_ids` (ordinary ignore membership, draft coexistence, sub-scope identity isolation, ignore-file removal and no policy-file projection), and `test_excluded_host_omits_collection_and_next_rebuild_removes_deleted_content` (draft and ignored report hosts remove prepared child output). These five cases use the file's `repo` fixture: temporary documents, one Works host/child, a draft parent and ready descendant, and a local SVG. They exercise production source parsing and preparation; apply cases run the real Docs/Search builders in process through a substituted rebuild-command launcher. All writes stay in pytest temporary storage, with Docs and Projects environment settings isolated by the shared fixture; no real workspace publication, network, browser, or live service is used. The selection protects the existing rules around the changed descendant traversal; it does not directly exercise a ready ignored parent with multiple descendant levels. New coverage needs a separately agreed test specification. Expected cost is seconds to tens of seconds with local filesystem/build work; setup and failure diagnosis dominate. Run once for a relevant selection change and repeat only for a related failure or fix.

```bash
set -a
source .env.local
set +a
$HOME/miniconda3/bin/python3 -m pytest -q docs-viewer/tests/python/test_docs_pre_publish.py -k 'readiness_and_intent_exclude_descendants or ignore_set_is_additional_and_does_not_exclude_child_collection_ids or excluded_host_omits_collection_and_next_rebuild_removes_deleted_content'
```

### Working Rebuild

The Analysis Working **Rebuild docs and Search** action calls the existing `/docs/rebuild` service with exact scope and stage. `docs-viewer/services/docs_write_rebuild.py` awaits the main document collection, every configured child collection and Search, then aggregates relationships before recording the completed Build manifest and returning success. Working stage is preserved through every build and in generated Search navigation. The Search CLI accepts `--scope analysis --stage working`; running it alone does not perform the complete scope rebuild or refresh Links. Pre-publish remains unavailable through this authoring action.

`docs-viewer/services/docs_scope_links.py` combines every prepared `links-by-id/<doc_id>.json` beneath the configured Analysis Working generated documents root into the sibling `links.json`. Its version 1 envelope contains `schema_version`, `scope`, `stage` and `documents`. Included records retain their original shape, titles, targets, hrefs, Subjects, occurrences and counts in deterministic file order. Only records with both incoming and outgoing lists empty are omitted; incoming-only records remain. Document Build owns existence, eligibility and relationship rules.

Aggregation reads all inputs before writing and replaces the saved snapshot only when its serialized content changes. An empty prepared directory produces a valid empty aggregate. Missing or unreadable input, invalid JSON or malformed list fields fail the rebuild visibly before completion is recorded; aggregation does not silently skip an input or save a partial result. Removed upstream records disappear on the next completed scope rebuild.

Save, watcher builds and individual-document rebuilds update the prepared records but leave `links.json` at the last completed scope rebuild. Opening or refreshing the local [Links report](/docs/?scope=analysis&stage=working&doc=d-20260910-214604-f9e841) only reads that saved snapshot. [Reports](/docs/?scope=studio&doc=d-20260513-105343-6de36b) owns its presentation and navigation. Focused coverage lives in `test_docs_scope_links.py`, `test_docs_write_rebuild.py`, `test_build_search_python.py` and `test_docs_workflow_stages.py` under `docs-viewer/tests/python/`.

## Source Contract

The common front matter is `doc_id`, `title`, `parent_id`, `added_date`, `last_updated`, optional `summary`, and optional `ui_status`. `publishable` is retired and rejected. Draft readiness through `draft` is supported in all Analysis Working collections; other scopes/stages reject that authoring field. The ignore list is separate Working source policy data and is not copied into prepared or published content. Exact defaults and validation are in the builder/source model.

- new documents give `added_date` and `last_updated` one captured full timestamp; after creation, only body, `title`, or `summary` changes advance `last_updated`.
- edited Recent includes only full `last_updated` timestamps; legacy date-only values become eligible after the next qualifying edit.
- `publishable: false` keeps an ordinary Analysis Working document available for authoring while excluding it from relationship data and document-picker suggestions. Publication snapshot selection remains separately owned.
- `draft: true` records readiness and does not exclude an otherwise eligible Working relationship source or target.
- hierarchy comes from `parent_id`, not folders.
- whether nested Markdown is allowed comes from scope config.
- sibling order is title-based with a stable id tie-breaker.

Authoring extensions supported by the renderer include:

- <code>&#91;&#91;media:...&#93;&#93;</code> for configured docs media
- <code>&#91;&#91;html-media:docs/&lt;scope&gt;/html/...&#93;&#93;</code> for sandboxed published HTML media
- explicit Catalogue `media` and `image` tokens for Media View links and Catalogue images; the retired three-part Catalogue text form has no compatibility alias

Ordinary Markdown document links are the relationship input. Local document href rewriting preserves explicit child selection, fragments and HTML escaping; URLs with a hostname, including protocol-relative external URLs, retain their authored destination.

Use [Docs Images And Assets](/docs/?scope=studio&doc=d-20260423-155039-e36925) for authoring guidance and `docs-viewer/build/docs_builder/` for the exact token rules.

## Publication Boundary

Build produces replaceable `generated/` output. Publish accepts the reviewed generated snapshot into the configured external `published/` boundary and owns publication eligibility. Analysis Deploy Repo consumes one complete Published snapshot to update its configured repository/public projections; it does not run Build or Publish. The manual GitHub Actions workflow remains the separate gate that deploys the tracked `site/` artifact.

The builder derives local and public `recent.json` projections independently from complete eligible source sets. Each projection declares its route-configured `added` or `edited` basis; public eligibility is applied before sorting and limiting.

Local scopes have no public publish target by default.

## Diagnostics And Safety

- the builder prints a compact human summary; `--diagnostics` adds machine-readable console diagnostics
- unchanged content is skipped unless forced
- targeted writes require an existing full-scope output tree
- renderer output allows raw HTML and is not a sanitization boundary
- management/service writes validate source and paths before calling builders
- the live watcher rebuilds document projections after source changes; Search remains unchanged until the Manage Rebuild control or a direct complete-scope search build

## Change Guide

- scope/source/output change: `docs_scopes.json` and scope-config tests
- Markdown/front-matter parsing: builder source model
- rendered document behaviour: renderer/token modules and acceptance fixtures
- search fields: `build_search.py` and Docs Viewer search runtime
- public promotion: management publish service and configured publish paths
- watcher invalidation: Docs live rebuild watcher
- build-source producer: producer registry, scope `source.build_media`, published `build_inputs`, full/targeted build tests, and reader-runtime boundary

Keep exhaustive output filenames, diagnostics fields, and CLI flags in code. This page should change when the build boundary changes.
