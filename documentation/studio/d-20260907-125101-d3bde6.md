# Doc Relationships

## Summary

**Document Build calls one links-builder to complete relationship maintenance.** The links-builder owns reference extraction, eligibility, link differences and incoming/outgoing contributions. Its separate serializer owns the accepted version 1 JSON shape, copied summaries and counts. The implementation covers every configured Analysis Working source collection. The test-document restriction was removed after the user accepted the proof as sufficient on 2026-09-10.

Scope-build combines completed records. Pre-Publish/Publish select and copy prepared content. Neither needs to understand or repair relationships.

The remaining algorithm can evolve within that boundary. If we discover a missed update, we fix Document Build rather than adding corrective logic downstream. The completion rule holds it together: Save finishes only when every affected relationship record is current.

Relationship records describe the documents that currently exist. If a linked target has no ordinary document by-ID JSON, Document Build silently skips it. Relationship data is stored separately in `generated/documents/links-by-id/<doc_id>.json`; a missing relationship file is an initialisation concern, not evidence that the document is missing. Authoring intentions and broken-link repair belong to the author and the separate Broken Links report.

## Direction

Use ordinary Markdown links to author references between documents. A single **Insert doc link** button selects a document and inserts its title and normal document location. Document Build extracts those references, records eligible relationships and enriches them with the linked documents' collection membership and optional Catalogue subjects. Incoming references are the generated reverse view of those same recorded links.

`doc_id` identifies a document. A document in `concepts` is about concepts without having to define one unique Concept; Moments use the same document model. Catalogue retains canonical Work, Series and Detail identities. A document's `work_id`, `series_id` or `detail_uid` associates it with an existing Catalogue item. Folder subjects retain their supported authoring boundary. Document identity, collection and Subject remain independent.

[Source Organisation](/docs/?scope=studio&doc=d-20260423-000000-8fd731) owns the implemented `sub-scope` front matter and completed source backfill. A nonempty value is the exact configured collection name; missing, null or empty means a normal scope-level document. Configured storage remains authoritative. Concept/Moment IDs and `group` metadata are retired.

This is the agreed direction within [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea). Link insertion and scope-wide Working relationship maintenance are implemented. The version 1 per-document shape is accepted for this delivery. Scope aggregation, other scope/stage rollout and publication integration retain their separate delivery boundaries.

## Insert Doc Link

- **Insert doc link** authors ordinary document references. **Add Media View link** and **Add Catalogue Image** remain distinct Catalogue-owned authoring actions. **Add Catalogue Token** and **Insert Subject Link** are retired; Subject metadata remains independently supported.
- Search and select the target document, then insert `[doc title](<doc link>)`, using its ordinary document location without a workflow-stage parameter.
- Exclude targets explicitly marked `publishable: false` from picker results. Keep drafts and documents without publication metadata selectable, including local-scope and child documents. This target-selection filter does not rewrite existing links or restrict typed or pasted links.
- Replace any selected text with the complete link. The replaced text has no semantic significance and does not become the link label or carry an association.
- When no text is selected, insert the link at the current cursor position.
- In source editor mode, selecting a link does not cause the Info panel to display metadata about the link or its target document.
- Link insertion changes Markdown only. Relationship JSON is updated at Build time.

The picker can search All documents, Scope-level documents, or one exact sub-scope. All documents and Scope-level documents are distinct filters. Use raw collection names such as `concepts`, `moments` and `works` without translated labels.

Selection preserves the exact document target: scope, collection and `doc_id`. A child document location retains its existing host/child URL structure; the selected child is the referenced document. Titles are display text and never supply a missing identity.

Manually pasted and manually edited document links receive the same Build treatment as links inserted by the button. There is no special token syntax or hidden insertion metadata. The link label remains ordinary authored text; a later target-title change updates generated relationship data without silently rewriting the referring document's Markdown.

The links-builder compares current authored references with its last completed reference baseline to detect additions, removals and occurrence changes during normal Doc Build. This supports Source Save, watcher builds and builds without an open editor. Link creation and deletion do not require dedicated controls; **Insert doc link** is a selection convenience and shares the same Save/Build path as typing, pasting or deleting a link.

### Document Identity And Stage Context

Analysis uses the same ordinary document-link semantics as other scopes. Working is its only authoring stage; Pre-publish is a prepared version of that content. An authored link refers to the document, without selecting a workflow stage. Ordinary document hrefs therefore omit `stage=working` and other workflow-stage parameters.

Stage remains explicit where needed to select storage, run a Build or review a snapshot. It describes the context containing the prepared data, not another document identity. The viewing context determines which available version a document link opens, under an explicit routing rule; links do not pin the target to Working as content proceeds through Pre-publish and publication. Workflow navigation may select a particular stage, but that selection does not create a separate document relationship target.

Document Build applies reference eligibility in Working. `publishable: false` excludes a document from relationship data; draft readiness does not. A draft document's references must be recorded and visible before Pre-publish. Publication selection and snapshot readiness are separately owned by the publishing workflow; they do not require stage parameters in authored document links.

## Authored Links And Generated Relationship Data

Markdown is the authoritative store of the authored link. If A links to B, the direction is `A → B`. When that link is eligible for relationship data, B's incoming reference to A records that same link; it does not author a reciprocal `B → A` link or create another association store. Not every authored link becomes a generated relationship.

### Relationship Eligibility

The links-builder omits a relationship whenever either endpoint is marked `publishable: false` or declares the supported Folder Subject field `folder_path`. For `A → B`, B's exact ordinary document by-ID JSON must exist and both documents must pass those rules before B appears in A's outgoing list and A appears in B's incoming list. Apply the rule to both directions and every occurrence, including permanently non-publishable documents that link to publishable documents. The Folder exclusion below refers to this existing metadata owner, not a new front-matter alias.

Publication intent and draft readiness are different. Include otherwise eligible documents with `draft: true`, whether they are the source or target, in Working `links-by-id` records, counts and scope aggregation. They do not have to reach Pre-publish first. Changing draft readiness alone must not remove or restore relationship entries; changing publication intent can. [Semantic Token References Across Collections](/docs/?scope=studio&doc=d-20260909-225129-591b60) adopts the same rule for token usage. Apply existing collection defaults rather than requiring an explicit `publishable: true`; sub-scope documents currently do not carry that field.

Document Build applies the rule to generated relationship entries and occurrence counts. It also omits the complete `links-by-id/<doc_id>.json` file for a non-publishable document or one declaring `folder_path`, removing an existing file when eligibility changes. That document supplies no entry to the proposed scope relationships index and does not appear as an isolated node. It does not remove or rewrite ordinary Markdown links, their rendered content, or the document's own front matter. An excluded document retains its ordinary Working by-ID payload and its own fields. A Folder declaration's separate relationship exclusion does not itself change publication intent or readiness.

Keep excluded authored links in the unfiltered in-memory reference index used by Document Build. The filtered `links-by-id` lists and proposed scope relationships index are UI projections, not a complete dependency map. Removing `folder_path` or making a document publishable can restore relationships without any link text changing.

### Missing Targets And Broken Links

If Document Build encounters a document link whose exact ordinary document by-ID JSON does not exist, skip that target silently. Do not emit an incoming or outgoing relationship, occurrence count, placeholder, lookup-status field, warning, error or broken-link finding for it. Do not create a replacement document payload or infer existence from a remaining index row or source file. Refreshing a relationship list removes any previous entry whose target document no longer exists. This existence rule checks the document payload, not `links-by-id`: initial generation must be able to create a relationship file for an existing eligible document.

Leave the ordinary authored link and rendered content unchanged. The link can remain in the unfiltered edit-comparison input, but it contributes nothing to generated relationship data. The relationship system reflects what currently exists, not what the author intended to exist or what existed earlier.

The author uses the implemented [Analysis Working Broken Links report](/docs/?scope=analysis&stage=working&doc=d-20260909-140121-53c381) to find and correct broken references across the scope-level and all configured Working collections. Studio excludes Analysis from its source-scope selection while retaining valid Analysis destinations for Studio-authored links. [Broken Links Script](/docs/?scope=studio&doc=d-20260423-165116-c83a81) owns audit operation, exact correction locations and diagnosis. The report audits authored links independently of filtered relationship records; it is not part of Document Build, scope aggregation or Pre-Publish/Publish validation.

### Non-publishable Documents Report

Provide a Working report listing documents marked `publishable: false`. It is a document inventory, separate from Broken Links, and neither report is a Pre-Publish validation or approval gate. There is no combined Pre-Publish report of Folder declarations, publication eligibility or link problems. Corrections remain ordinary edits in Working, and Pre-Publish does not block on report findings.

### Generated Records

Each document's ordinary generated `by-id/<doc_id>.json` retains its content, collection and supported Subject metadata. An eligible document has a separate `links-by-id/<doc_id>.json` relationship record with:

- **Outgoing links:** its eligible document links, with each target's exact identity, title, document location, `sub-scope` and supported Subject fields.
- **Incoming links:** eligible contributions from documents linking to it, with the same information about each referring document.

The relationship record is a separate JSON file, not a `relationships` property added to the ordinary document payload. Resolve its location from the configured scope/stage generated documents root. For Analysis Working, the agreed location is:

```text
$DOTLINEFORM_PROJECTS_BASE_DIR/docs-viewer/scopes/analysis/working/generated/documents/links-by-id/<doc_id>.json
```

The scope/stage-owned directory supplies relationship records for scope-level and configured sub-scope documents. Each record retains the exact `{scope, sub_scope, doc_id}` identity; the filename does not replace that identity. Ordinary document payloads continue to use their existing configured collection locations. The serializer emits the version 1 shape below, accepted after the Links proof.

### Links-builder And Schema Ownership

`docs-viewer/build/docs_builder/links_builder.py` owns configured source loading, exact route/host resolution, the private reference baseline and changed-file writes. `links_model.py` represents document identities, authored references, differences and shallow incoming/outgoing views independently of JSON. `links_schema.py` serializes one view to the accepted version 1 `links-by-id` shape. The model never reads the old UI JSON back as its reference baseline.

`docs-viewer/config/links-builder.json` selects `analysis` and `working`. Every ordinary parent or child Doc Build for that selection invokes relationship maintenance, including a Build that empties a collection. Sources are discovered through the configured scope-level and sub-scope loaders; no document allowlist or title-based discovery remains. Immutable document IDs must be unique across those collections. Both relationship endpoints must belong to that configured source set and meet the existing eligibility/existence rules.

The builder projects the configured source graph in memory and compares each serialized record with its existing file, writing only differences. It removes obsolete immutable-ID files from the owned `links-by-id` directory, including after source deletion or loss of the private baseline. Schema-only changes can regenerate affected files without changing link detection or reading an obsolete output shape. A schema change that introduces a new kind of relationship or new source meaning can still require model/input work; field layout alone does not.

The test restriction is removed. The browser consumes prepared relationship JSON and does not duplicate extraction or change detection. Public activation, publication integration and other scope/stage rollout remain separately owned.

A single scope-level relationship index combines the separate relationship records across the scope, including its sub-scopes. Staged scopes retain separate output ownership for each stage; that ownership does not become part of a relationship's document target. The index contains the same document-link and association data already prepared in `links-by-id`.

Recorded relationship entries preserve the actual existing document target even when it has no collection or Subject association. Only defined collection and supported Subject fields enrich the entry; arbitrary front matter is not copied into it. Missing ordinary document by-ID targets, non-publishable documents and Folder documents contribute no relationship entries under the rules above.

## Payload Shape And UI Fit

The per-document version 1 shape is accepted. The scope-level index and additional display fields below remain proposed follow-on work.

Design these generated payloads around likely reads. Repeating information is acceptable when it makes the UI straightforward: Document Build pays the preparation and consistency cost. A one-document-deep view should be able to label, group and open its linked documents from one `links-by-id` response, without fetching each neighbour or resolving Catalogue identities in the browser. The scope index should similarly support a scope-wide view in one response.

### Document Summaries

Use one shared summary shape for the document itself and for every counterpart in its incoming and outgoing lists:

| Field | Purpose |
| --- | --- |
| `target` | Exact `{scope, sub_scope, doc_id}` document target. Use `sub_scope: ""` for a scope-level document. Stage belongs to the containing data context and is not part of this target. |
| `title` | Current document title for lists, pills, graph labels and sorting. |
| `href` | Ready-to-use ordinary document location without a workflow-stage parameter, including the existing host/child route where applicable. The viewing context determines the available version. The UI does not reconstruct the location from titles or guess a host. |
| `subject` | Reuse the existing normalized Subject projection from `docs_document_subjects.py`: `state`, `kind`, `key` and the originating `fields`. This retains the distinction between no Subject, a valid Subject, and malformed or conflicting declarations. |
| `subject_display` | Possible future prebuilt Subject label and link; not included in version 1. Its owning projection and refresh behavior must be agreed before adding it. |

The JSON `target.sub_scope` carries the resolved collection recorded as `sub-scope` in Markdown; it does not introduce another accepted source spelling. Subject labels and locations are useful redundancy if they avoid runtime lookups, but their owning refresh path must be agreed before including them. A missing Subject display label must not be treated as a missing Subject identity.

Keep a counterpart summary shallow. It does not embed that counterpart's incoming/outgoing lists or their counts. This preserves the one-document-deep refresh boundary. Optional document summaries or thumbnails can be added if a concrete UI exercise needs them; any added display field becomes part of the same counterpart-refresh responsibility.

### Links-by-ID JSON

For an eligible document, write a complete relationship record to `links-by-id/<doc_id>.json`. Its version 1 top-level members are `schema_version`, `self`, `outgoing`, `incoming` and `counts`. Document Build omits this file entirely for a non-publishable or `folder_path` document. An eligible document, including a draft, with no links still has a record with empty incoming/outgoing lists and zero counts, so it can appear as an isolated node. This presence decision belongs entirely to Document Build. The proposed scope-level Build simply appends the records already present in `links-by-id`; it has no eligibility field to inspect and no relationship rules to apply. Absence of a relationship file does not control publication selection; the publishing workflow owns that decision.

Existing document content remains owned by the ordinary document payload; it is not copied into relationship records. The document's source supplies its own fields and outgoing references. Incoming entries are contributions from other documents' outgoing references and must be preserved or deliberately updated by the coordinated Build operation, not recreated from the viewed document's Markdown.

The example below illustrates the version 1 contents of `links-by-id/A.json`. A and B are publishable and neither has `folder_path` front matter, so their link is recorded. `A`, `B`, `concepts-host` and `works-host` are symbolic example identities and locations, not live document targets. Targets and hrefs identify documents without a workflow stage; the relationship file's storage context identifies the prepared version.

```json
{
  "schema_version": 1,
  "self": {
    "target": {"scope": "analysis", "sub_scope": "concepts", "doc_id": "A"},
    "title": "Document A",
    "href": "/docs/?scope=analysis&doc=concepts-host&subdoc=A",
    "subject": {"state": "none", "kind": "none", "key": "", "fields": []}
  },
  "outgoing": [
    {
      "document": {
        "target": {"scope": "analysis", "sub_scope": "works", "doc_id": "B"},
        "title": "Document B",
        "href": "/docs/?scope=analysis&doc=works-host&subdoc=B",
        "subject": {"state": "valid", "kind": "work", "key": "00001", "fields": ["work_id"]}
      },
      "occurrences": [
        {"label": "Document B", "href": "/docs/?scope=analysis&doc=works-host&subdoc=B"},
        {"label": "the detail", "href": "/docs/?scope=analysis&doc=works-host&subdoc=B#detail"}
      ]
    }
  ],
  "incoming": [],
  "counts": {
    "outgoing_documents": 1,
    "incoming_documents": 0,
    "outgoing_occurrences": 2,
    "incoming_occurrences": 0
  }
}
```

Version 1 uses one incoming/outgoing entry per exact counterpart document, with all occurrences retained in source order. Multiple links to B therefore produce one document row or graph edge, while preserving their individual labels, destinations and fragments. These labels are ordinary link text, not semantic classifications. Each incoming entry carries the corresponding occurrences from the referring document's source; they are not positions in the viewed document.

Precomputed counts make badges and empty states convenient and distinguish unique linked documents from link occurrences. They count only the recorded relationships and occurrences after eligibility filtering, not every link in the Markdown. Directional counts do not imply a total of distinct neighbours: a reciprocal link can place the same document in both lists. Counts belong to the document's relationship record, not to the summaries copied into other records. Source-editor offsets and click-to-source positioning are not assumed requirements of this proposal.

### Scope-level Index JSON

The proposed index envelope contains `schema_version`, `scope`, `stage` and a `documents` array. Here `stage` records the Build context that prepared the data; use `null` for an unstaged scope. It is not repeated in document targets or hrefs, and copying the prepared JSON does not rewrite it. Each array entry is one complete record copied unchanged from `links-by-id/<doc_id>.json`. Append every prepared record, including those with empty link lists. Non-publishable documents and those declaring `folder_path` contribute no record because Document Build has already omitted it; scope-level Build makes no eligibility or membership decision.

Scope-level Build only combines these already prepared records. It does not read Markdown, inspect front matter, resolve Subjects, validate or filter relationships, recalculate counts or regenerate `links-by-id` data. The index repeats counterpart summaries as well as each document's own summary intentionally: per-document lists and a scope-wide view use the same data shape. Full document bodies and unrelated payload fields are excluded from the index.

For a scope graph, each record's `self` provides the document node and its `outgoing` entries provide the directed links. The incoming list is the reverse view of those same links; drawing both lists as independent links would double-count them. Reciprocal authored links remain two different directed links. Use the complete `{scope, sub_scope, doc_id}` target for matching nodes within the selected data context, including existing cross-scope endpoints where supported. Missing targets have no placeholder nodes or edges. Stage selects the dataset being viewed; it does not create another document node identity.

Any additional graph or table fields remain part of payload review. Document Build must prepare any additional per-document relationship projection in its `links-by-id` output so scope-level Build can continue to combine completed contributions unchanged. Do not add relationship derivation or rule evaluation to scope aggregation for a new UI.

### Future UI Exercises

The initial Links proof accepted the version 1 per-document schema. Use the following cases to assess future scope-index or display-field additions; they are likely consumer needs rather than commitments to specific screens.

| Likely UI need | Data needed and review question |
| --- | --- |
| One-document incoming/outgoing lists | Counterpart title, location, collection and Subject are available in one response. Can the UI render without fetching neighbours? |
| Filter or group by collection or Subject | `target.sub_scope` and `subject.kind`/`subject.key` support grouping while preserving scope-level and no-Subject documents. Are usable display labels available? |
| Scope graph | The index includes document summaries, directed links and isolated documents. Can the graph distinguish reciprocal links and avoid counting incoming mirrors twice? |

| Documents connected to a Work, Series or Detail | Counterpart Subjects can be queried while preserving the contributing document link. Does the UI distinguish the viewed document's own Subject from a linked document's Subject? |

Keep authoring multiplicity and Catalogue reassociation policy separate from future payload review. Reuse the current supported Subject model until that policy changes explicitly. Identify useful additional display data, its owner, refresh behavior and payload-size cost before extending the accepted version 1 record.

## Document Build: Maintain Both Ends

Document Build reads current Markdown and relevant front matter as the authority for relationships. Literal examples in code do not count as links. It updates the saved document's ordinary generated payload and separately coordinates relationship updates in its own and its direct neighbours' `links-by-id` files. Relationship-only neighbour updates do not modify their ordinary document by-ID payloads. A relationship record cannot be recreated from that document's source alone, because its source cannot supply incoming links.

### Ownership Of Each Section

| Section or contribution | Owner and update rule |
| --- | --- |
| A's content and front-matter projection | A's own source Build refreshes them. |
| Presence of A's `links-by-id/A.json` and its `self` summary | A's own Build applies the eligibility rules and prepares the complete record or removes its file. Eligible documents receive a current `self` summary even when they have no links. Scope-level Build only appends records already present. |
| A's outgoing relationships | A's authored links supply the references; current endpoint metadata and eligibility determine the recorded entries. A target's metadata or eligibility change can refresh its entry here through the coordinated operation. |
| A's contribution to B's incoming relationships | The authored `A → B` link supplies this contribution. Add, update or remove it together with the corresponding entry in A's outgoing list. Preserve B's other incoming contributions. |
| A's incoming relationships | These come from other documents' outgoing references. Preserve them during A's own content Build, except where coordinated link or eligibility changes deliberately update those contributions. A's Markdown alone cannot reconstruct this list. |
| Relationship counts | Recalculate the affected counts from the final filtered lists in each changed `links-by-id` record. |

### Reference Baseline And Direct Neighbours

The links-builder loads all configured Working documents' current Markdown and relevant metadata, retaining references to excluded endpoints and sources whose ordinary payload is missing in its internal model. It compares this model with the last completed baseline in `var/docs-viewer/links-builder/<scope>/<stage>/state.json`. This private cache survives the separate Python process used by normal Doc Build and remains outside generated documents and publication data. It contains reference-model data, not the Links UI schema.

Current source is authoritative. A missing baseline is initialised from the source graph, and missing relationship files can be regenerated for existing eligible documents. Incoming contributions are reconstructed from all authored outgoing references in the configured source set, so they do not depend on a filtered output file or on opening an editor first. Rebuilding the graph in memory does not rewrite unchanged relationship files or ordinary neighbour payloads.

Compare the saved source with that baseline. Detect added and removed links as well as changed occurrences, such as labels or fragments on an unchanged target. Compare relationship-bearing front matter too: title, collection, Subject and eligibility can change copied relationship data while the link list stays the same.

For each changed document, the possible affected records are that document plus its previous and current direct outgoing targets and incoming sources. Previous neighbours remain relevant when a link is deleted; excluded neighbours remain discoverable when eligibility changes. The builder prepares the configured source graph in memory and compares serialized records, so ordinary changes write only affected files. Counterpart summaries are shallow: a neighbour's relationship-list change does not alter the summary held by a second-hop document. A serializer revision or recovery of missing output can deliberately change more files.

### Save And Build Sequence

1. Complete the ordinary document payload build, then invoke the links-builder for the configured Working scope. Read the last completed private baseline and every configured source collection. Extract authored link occurrences without applying relationship eligibility yet.
2. Compare previous and current links and metadata. Prepare the updated unfiltered outgoing and reverse-incoming reference view, preserving the previous view until the operation completes.
3. Resolve current metadata and ordinary document payload existence across the configured collections. Skip references to missing document payloads without reporting them or creating replacement documents. A missing `links-by-id` file for an existing eligible document is initialised from the complete reference model. Filtered relationship lists are not the dependency-discovery authority.
4. Apply relationship eligibility to the internal graph. For each eligible existing document, prepare its `self` summary and eligible outgoing entries, with incoming contributions derived from the referring documents' authored links. For excluded or deleted documents, plan removal of their owned relationship files.
5. Apply relationship changes at both ends. Update the saved document's contributions in its targets' incoming lists, and update its summary or eligibility in its referring documents' outgoing lists. Apply any corresponding additions or removals to its own incoming list using those referring documents' authored links. Preserve unrelated sections and contributions, and recalculate affected counts.
6. Write the saved document's ordinary output and each affected `links-by-id` file only where its resulting content changed. Apply required relationship-file removals for excluded or deleted documents. Neighbour updates touch only their separate relationship records; they do not rerender or rewrite the neighbours' ordinary document payloads.
7. Advance the private baseline only after every relationship write and removal succeeds. A per-scope/stage lock serializes concurrent builder invocations. A failure leaves the previous baseline available for an ordinary retry. Doc Build awaits this work before returning success; Save retains its existing synchronous completion rule.

### Example 1: Delete A Link

Initially, C links to A, A links to B, and B links to D. All four documents are eligible. Delete A's last link to B and save A.

- **A's ordinary by-ID:** rebuild A's edited content.
- **A's links-by-ID:** remove B from A's outgoing relationships and update the outgoing counts. Preserve C's incoming contribution to A.
- **B's links-by-ID:** remove A's contribution from B's incoming relationships and update the incoming counts. Preserve B's outgoing link to D and other incoming contributions. B's ordinary document payload is unchanged.
- **C and D:** no JSON change is needed. A's own summary has not changed, and B's incoming-list change is not part of the shallow summary that another document holds about B.

The previous baseline records the removed occurrence even though A's current Markdown no longer mentions B. Reprojecting the current graph removes the obsolete incoming contribution from B while preserving other sources. If another occurrence of A's link to B remains, retain the document-level entries and update the occurrences and counts at both ends instead of deleting the relationship.

### Example 2: Add A Link

Initially, C links to A and B links to D. Add A's first link to B and save A. All four documents are eligible.

- **A's ordinary by-ID:** rebuild A's edited content.
- **A's links-by-ID:** add B's current document summary and occurrences to A's outgoing relationships, and update the counts. Preserve C's incoming contribution.
- **B's links-by-ID:** add A's current summary and occurrences as an incoming contribution and update the counts. Preserve B's other relationship sections and contributions. B's ordinary document payload is unchanged.
- **C and D:** no JSON change is needed; neither A's nor B's own summary changed.

If either A or B is non-publishable or has `folder_path` front matter, keep the new ordinary link in A's content and in the unfiltered reference index, but create no relationship entry at either end. If B's ordinary document by-ID JSON is missing, also omit the relationship silently and do not create B's document payload. Adding another occurrence to an existing eligible link updates the existing entries and occurrence counts rather than creating duplicate document rows.

### Example 3: Change Front Matter

Initially, A links to B, B links to C, and D links to A. All documents are eligible. Change B's Subject from Work 1 to Work 2 and save B without editing any links.

- **B's ordinary by-ID:** refresh B's own front-matter projection.
- **B's links-by-ID:** refresh `self`. Its outgoing summary of C and incoming summary of A remain unchanged because A and C have not changed.
- **A's links-by-ID:** refresh B's summary in A's outgoing entry so it displays Work 2. A's ordinary document payload is unchanged.
- **C's links-by-ID:** refresh B's summary in C's incoming entry so it displays Work 2. C's ordinary document payload is unchanged.
- **D:** no change. A's own summary is unchanged, so D's relationship with A is unaffected. Relationship counts remain unchanged throughout this Subject edit.

Title or other fields copied into the document summary follow the same direct-neighbour rule. An unrelated front-matter field that does not affect relationship identity, display or eligibility requires only the saved document's ordinary output update.

Eligibility is another front-matter case. If B becomes `publishable: false` or gains `folder_path`, remove B's complete `links-by-id` file, remove B from A's outgoing and C's incoming lists, and update the remaining counts at each end. Keep all authored links and the unfiltered references. If B becomes eligible again, prepare its relationship file and restore both ends from those references wherever the other endpoint is also eligible. Its incoming contributions still come from the referring documents' links, not from B's own Markdown. B becoming non-publishable changes publication intent; B gaining `folder_path` alone does not.

In each example, Save completes the ordinary document output and separate `links-by-id` changes. A future scope-refresh or Pre-Publish integration will aggregate completed relationship records under the separately proposed index contract. B contributes an index entry only when its separate relationship file exists. Aggregation must perform no eligibility checks, relationship discovery or sanitisation.

The app-wide operation rule is synchronous from the user's perspective: do A, wait for its complete outcome, then do B. [Development Checklist](/docs/?scope=studio&doc=d-20260523-190651-7157ec) owns this rule. Prefer awaited server operations; any necessary internal asynchronous work remains hidden within the same operation and finishes before the UI returns to ready.

Document Build runs as part of document Save, while controls are unavailable. One coordinated operation completes the document's own output and the required relationship updates at both ends before controls become available again. Ordinary body changes affect another document's separate relationship JSON only when the relationship data it displays changes.

## Scope-level Build: Aggregate Completed JSON

This is the proposed aggregation contract, separate from the delivered single-document view. Scope-level aggregation will read completed `links-by-id/<doc_id>.json` files and append every record already present to the scope-level index. It copies records unchanged and must not scan Markdown, inspect `publishable` or `folder_path`, follow links, resolve Subjects, apply relationship rules, validate entries, recalculate counts or regenerate relationship files. Normal parent-document Build already invokes the links-builder; the separately proposed aggregation step does not replace that maintenance owner.

The app's operation ordering provides the guarantee: document JSON is current when Save completes and controls become available, and scope-level Build aggregates that completed data.

## Scope Refresh, Pre-Publish And Publish

A future scope-wide relationship visualisation can read the proposed scope-level index, including otherwise eligible draft documents. The delivered Links view reads one separate per-document record and requires neither an aggregate index nor a scope-refresh or Pre-publish operation after Save.

Pre-Publish's planned initial scope-level Build combines completed `links-by-id` data. Publication intent and readiness then belong to the publishing workflow, independently of Working reference eligibility. The earlier assumption that checking only `publishable` and copying all relationship JSON unchanged settles the snapshot boundary must be reviewed against the current draft model: if a publication snapshot omits a draft counterpart, its treatment of that reference needs an explicit prepared-data design. Keep Document Build as the relationship-maintenance owner and scope-build as aggregation; do not solve snapshot selection by hiding drafts from Working or adding relationship discovery/repair downstream.

Publish copies the prepared JSON files unchanged. It does not extract links, enrich associations, refresh connected documents, assemble the scope index or add a content-validation gate. The non-publishable documents report is informational and does not gate Pre-Publish or Publish.

## One-document-deep Views

The Links adapter and exact generated-record read are implemented and reviewed for Analysis Working; [Links View](/docs/?scope=studio&doc=d-20260910-202325-53b5f9) is the durable runtime reference. Availability is projected from the scope/stage setting in `links-builder.json`; there is no document allowlist. The provider currently reads one separate record on each opening, preserves staged navigation and rejects mismatched identities. Public-safe rendering is present but public data preparation and activation remain pending. The proof and version 1 schema were accepted for the completed rollout. [View Caching and History - Delivery](/docs/?scope=studio&doc=d-20260910-193232-e511cd) separately owns the agreed replacement for per-opening reads and browser-history restoration.

After opening the initial view, the user chose normal document width without an outer border. Links now selects that layout through the shared host and retains the index panel's existing state. Media and other expanded presentations keep their own layout setting.

The agreed **Links** view presents one document's related documents in the shared Content Detail host, with a dedicated adapter and a **🔀 Links** document-toolbar action. The initial plain layout groups Concepts from `analysis/concepts`, Works with a Work Subject, and References limited to scope-level documents. Empty sections are hidden; entries sort A–Z by title. Incoming and outgoing relationships are combined into one displayed link per exact `{scope, sub_scope, doc_id}`, without arrows or direction labels. Repeated and reciprocal links share an entry; different documents with the same title remain distinct. Direction, occurrences and counts stay in the generated data for other visualisations and reports. Moments is omitted and Processing presentation is deferred until it has content. Pills and additional styling can follow later. The view reads the displayed document's separate `links-by-id/<doc_id>.json`, including neighbour display fields, without fetching a scope index or each neighbour. The user accepted the proof as sufficient for the completed Working rollout.

The local view must reflect current eligible relationships, including drafts, without waiting for Publish. It remains separate from the Source Info panel, which does not inspect selected document links. Scope- and sub-scope-level exploration belongs to Catalogue Data Visualisation.

For example, eligible A links to eligible B and B is associated with Work 1. A's outgoing entry displays B with Work 1. When B changes its Subject to Work 2, the coordinated Build uses the unfiltered incoming-reference lookup to refresh B's summary in A's outgoing list. A's view then displays B with Work 2.

The view goes one document deep. If C links to A, the change to B does not propagate to C because A's own associations have not changed. A generated incoming entry does not imply reciprocal authorship, and a document link does not establish transitivity or a direct Catalogue association on the referring document.

Links remain useful without a Catalogue Subject, including links to scope-level documents. Multiple documents may discuss overlapping concepts without requiring the system to decide whether they represent the same concept.

## Open Decisions

- **Series-gallery text authoring:** Work text links and Work/Detail image authoring are implemented through the shared Media View opener. Any future direct Series-gallery text control must coordinate gallery identity and ordering with Gallery Design. Existing Series image rendering remains supported.
- **Additional payloads:** the version 1 per-document `links-by-id` shape is accepted. The scope index, copied Subject labels and additional graph/display fields remain proposed; define their read and refresh ownership when separately delivered.
- **Working rollout:** DR-6 is complete. All configured Working collections are reconciled through the same links-builder; further scope/stage rollout and scope-level aggregation remain separate. Aggregation must remain a consumer of completed records.
- **Cross-scope writes and snapshot boundaries:** define the source set covered by the reference index and counterpart-update ownership across scopes. Relationship updates belong to authoring Build; Pre-publish and accepted snapshots receive prepared copies. Authored document targets remain independent of stage.
- **Draft references at publication boundaries:** Working records and displays otherwise eligible drafts. If a selected publication snapshot omits a draft source or target, decide how its prepared relationship data represents that boundary before retaining the unchanged-copy assumption. This must not remove draft references from Working or move relationship maintenance into aggregation or Publish.
- **Presentation enhancements:** the picker and simple grouped Links proof are accepted for the completed Working rollout. Pills, additional styling and expanded association coverage remain separate enhancements. Scope- and sub-scope-level visualisation belongs to Catalogue Data Visualisation.
- **Separate Catalogue policy:** Subject multiplicity, reassociation and any future derivation through Series membership remain independent of this direct document-link model.
