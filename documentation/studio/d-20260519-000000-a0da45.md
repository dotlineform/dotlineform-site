# Catalogue Source Model

## Canonical Families

Catalogue authoring source lives below `studio/data/canonical/catalogue/`:

| Family | Canonical location | Owns |
| --- | --- | --- |
| Works | `works.json` | Work identity, optional Series membership, descriptive metadata, project-media references, downloads, links and media version |
| Series | `series.json` | Series identity, descriptive metadata and ordering policy |
| Work details | `work_details/<work_id>.json` | Work-owned sections and nested Detail records |

`studio/services/catalogue/catalogue_source.py` owns exact fields, normalization, omit-empty rules, serialization and validation. Works and Series use schema v2. Catalogue prose has no parallel Markdown source family.

## Relationships And Identity

- Each Work has a stable `work_id` and zero or one `series_id`. An ungrouped Work omits `series_id`; an assigned ID must identify an existing Series.
- Empty Series are valid. Series membership is held on Works; changing membership never requires a replacement member or deletion.
- Catalogue membership, document subjects, document `parent_id` and token composition are independent. None establishes another relationship.
- Catalogue Works and Series have no `status` or `published_date`. Series have no `primary_work_id` or `series_type`.
- A Work with Details has one aggregate file. Sections own their identity, title, media subfolder and ordering; nested Details retain exact composite identity. See [Catalogue Per-Work Detail Source](/docs/?scope=studio&doc=d-20260622-160612-b986f3).

## Metadata And Ordering

Project-media references identify a configured source, project folder, optional direct subfolder and filename without storing an absolute path. `media_source_id` is omitted for the configured default. Dimensions and `media_version` remain maintained media fields. Downloads and links remain optional Work-owned arrays.

Series `sort_fields` remains the ordering policy. The shared ordering calculation feeds Studio's exact Series lookup, including `ordered_work_ids`, from all canonical members. A new sort token requires matching source validation, ordering support and consumer handling. Generated Series member ordering uses the same policy.

## Save And Delete

Services validate the combined canonical state and use the existing source transaction writer. Saves and deletes use opaque server-issued record revisions; a stale edit is rejected. A combined Series/member save checks the Series and every changed Work before writing either family.

Save completes affected generated Catalogue records, indexes and required media after the canonical transaction, then refreshes private Studio lookups with current records and revisions. Membership reassignment includes both affected Series; changed Details include their parent Work. Output failures preserve the saved canonical change and report the incomplete step. [Catalogue Build And Lookup Refresh](/docs/?scope=studio&doc=d-20260519-202931-0c703e) owns the workflow.

Deleting a Series clears its Works' assignments and keeps the Works. Deleting a Work removes its dependent sections and Details. Section deletion removes its nested Details. They then reconcile affected generated output and exact obsolete media through the same completion owner.

Canonical files use stable schema headers and deterministic record ordering. Optional empty fields follow the source serializer's omission rules. Volatile write timestamps belong in operation logs, not source records.

## Validation And Field Changes

Run the read-only canonical validator with:

```bash
$HOME/miniconda3/bin/python3 studio/services/catalogue/validate_catalogue_source.py
```

It checks allowed fields, exact IDs and map keys, optional membership, supported sort fields, media metadata and Detail aggregate integrity. Work imports accept optional `series_id` and reject the retired Work columns.

When changing a field, update its source definition, serializer, validation, editor and affected read projections together. The [Catalogue Field Registry](/docs/?scope=studio&doc=d-20260501-172902-96e85d) inventories current source fields and output families; it does not plan Save or own serialization.

## Output Boundary

Ordinary Studio Catalogue production is available. Save, import and delete maintain the complete output under `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/`; private `studio/data/generated/catalogue-lookup/` remains editor-owned. Staging resolves through `catalogue/media-staging/`, while generated thumbnails use `works/thumbs/` and `work_details/thumbs/` beneath the output root.

There are no separate Catalogue Build, media-publish or record-publication API actions. Full JSON maintenance is available without media conversion or upload. The frozen site and media archive remain outside active writes. Docs Publish owns public acceptance; Catalogue Save does not make a record public or refresh Docs semantic lookups. The coordinated Docs reader and publication integration remains separate work.

Some validators and transaction planners load the complete Detail corpus. Generated output is replaceable data, not another canonical source.
