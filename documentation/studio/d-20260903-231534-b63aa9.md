# Catalogue Data Model

## Direction

Retain the existing `analysis.works` sub-scope and its public name, **Works**. Catalogue remains the internal term for the structured Work and Series model; it does not require a different public collection name. This naming decision is accepted.

Series, Works and optional Detail documents can belong to the same mixed collection. Retain explicit subject fields and add `detail_uid`; this replaces the earlier common `subject`/`cat_id` proposal.

The existing collection already deliberately mixes Series and Work subjects. Series being abstract groupings while Works represent things does not require separate document collections. The collection contains documents about different kinds of Catalogue entities, not a claim that those entities are equivalent.

Keep one existing collection through the shared Analysis Search and publication lifecycle. No collection rename, parallel collection or path migration is required for this naming decision.

The intended Studio Catalogue schema makes Series and Works independent canonical entities and removes their per-record draft/published states. [Publish workflow](/docs/?scope=studio&doc=d-20260905-141447-c33de1) owns acceptance through the Analysis snapshot: Manage reads generated Catalogue data; public readers use its published projection. These schema and workflow changes remain to be implemented.

## Document Subject

`doc_id` identifies the document. Its optional subject identifies what that document is about, without giving it exclusive ownership of the subject. The accepted choices are:

| subject choice | source representation | meaning and scope |
| --- | --- | --- |
| none | no subject field | a plain document, not about one Catalogue item; may still reference several items |
| folder | `folder_path` | a real folder; available only in the `dotlineform` scope |
| Series | `series_id: "008"` | one exact Series |
| Work | `work_id: "00008"` | one exact Work |
| Detail | `detail_uid: "00008-001"` | one exact Detail |

These are mutually exclusive subject choices. A Detail document records `detail_uid`; it does not also declare a Work subject just because the owning Work ID is available from that value. Keep identifiers as strings, including leading zeros.

For example, the new Detail subject field is:

~~~yaml
detail_uid: "00008-001"
~~~

This extends the existing field-based subject model. The unified `cat_id` proposal is abandoned; no common ID field or additional stored `subject` discriminator is introduced.

## Detail Identity And Data Quality

`detail_uid` is defined as `<work_id>-<detail_id>`. Parsing `"00008-001"` gives the exact `work_id` `"00008"` and `detail_id` `"001"`. No formal lookup is needed to establish those identities or the owning Work. This is decoding an explicit composite identifier, not guessing a relationship.

Studio owns the Catalogue data-quality contract, including agreement between the composite UID, its component IDs and the canonical records. Docs Viewer consumes that contract and can parse the UID directly. It does not need a second ownership check or a relationship lookup to establish what Studio's identifier already states. Loading the Work or Detail content remains a separate operation.

## Detail Does Not Mean Less Important

The term Detail describes the Catalogue structure, not artistic importance or a requirement that the item be merely supplementary. As the user described, Series `023` contains one Work, a printed list of photograph dates, and 523 Details, each an independent photograph.

A Detail is therefore a valid direct document subject and presentation target in its own right. Its encoded relationship to a Work does not reduce its significance or require its discussion to live only in a Work document.

## Identity Is Not Membership

In document front matter, `series_id` declares a Series subject, `work_id` a Work subject and `detail_uid` a Detail subject. A Work document does not also use `series_id` to record membership. Its Catalogue Work record owns that relationship; document `parent_id` separately owns document hierarchy.

Catalogue records retain their own identity and relationship fields. Optional singular Work `series_id` remains part of the proposed Catalogue migration; this document does not claim the current collection-valued membership model has already changed.

Parsing a Detail UID makes its containing Work available without changing the document's subject from Detail to Work. Several documents may discuss the same entity, and an entity may have no document; neither case changes Catalogue identity.

## Catalogue Lookup And Hierarchy

Subject-driven content uses the corresponding consumer data:

| subject field | content available |
| --- | --- |
| `series_id` | Series data and ordered member Works |
| `work_id` | Work data, membership and sectioned Details |
| `detail_uid` | parse Work and Detail IDs, then load the required content using those exact IDs |

The planned data provider supplies external `$DOTLINEFORM_PROJECTS_BASE_DIR/catalogue/generated/` consumer JSON to both local `dotlineform` and `analysis` scopes, including subject pickers and Catalogue lookups. That coordinated delivery removes reads of Studio canonical JSON and repository-generated Catalogue lookups. Work/Series subject search keeps its existing provider until then. Public consumers read accepted published output, following [Publish workflow](/docs/?scope=studio&doc=d-20260905-141447-c33de1). Parsing a Detail UID does not require a separate JSON file for each Detail or determine its image URL.

Series lead to Works, and Works expose their sectioned Details, while the document collection can remain flat. [Gallery List Design](/docs/?scope=studio&doc=d-20260905-141447-f72ef3) uses the declared subject and requested presentation to select content. Media View, associated documents and files remain separate possible actions.

## Optional Detail Documents And Navigation

A Detail may have its own document, several associated documents, or none. [Concept](/docs/?scope=studio&doc=d-20260904-014334-f3dab5) allows a deliberately authored Work-subject document containing that Work's Details gallery, alongside separately authored Detail-subject documents. Bulk source migration and automatic Details-document creation are abandoned. Batch New doc will support selected Works and Series; its starter content and destinations remain open. Media View provides image presentation without requiring a document for every item.

Collection membership, Catalogue hierarchy, token composition and previous/next sequence remain distinct. The data can inform navigation without automatically deciding whether next/previous traverses Series, stays within one Series, crosses Detail sections or includes independently documented Details.

[Context Navigation](/docs/?scope=studio&doc=d-20260903-160226-5c6a3e) remains scope-level only and independent. Detail previous/next is an intended Media View capability; its sequence semantics remain open.

## Migration Boundary

Retain the existing collection configuration and locations, document identities and URLs, report host, Copy-to-Analysis targets and publication lineage. Any later subject-metadata change must name its own migration boundary; retaining the public Works name does not require moving or retargeting these owners.

`docs_document_subjects.py` now derives subject kind from `work_id`, `series_id`, `detail_uid` or `folder_path`. [UAC 3C](/docs/?scope=studio&doc=d-20260905-165519-38a6df) implements Detail metadata, assignment and private associations, with Folder supported only in `dotlineform`. Existing unsupported declarations remain visible for explicit correction; no bulk source rewrite is performed.

Existing Projects and Processing Copy-to-Analysis workflows continue to target `analysis.works`. Preserve their separate lineage ownership through any later subject-metadata changes.

## Live Subject Assignment

UAC 3C makes `detail_uid` available in `dotlineform.projects` and `analysis.works`, and in the shared Processing editor. Authors can assign, edit or clear a subject directly in Analysis Works through the existing subject editor and exact-document metadata service. Implementation and focused checks are complete; manual review remains open.

| collection | subject choices for this delivery |
| --- | --- |
| `dotlineform.projects` | None, Folder, Series, Work, Detail |
| `dotlineform.processing` | None, Folder, Series, Work, Detail |
| `analysis.works` | None, Series, Work, Detail |

Projects is an optional authoring route. Documents can originate directly in Analysis Works and must have the same ability to acquire a Catalogue subject without a preceding Copy operation or publication lineage. A copied document is also an independent document whose subject can be edited locally.

Detail subjects remain intact through Save, generated projection and Projects-to-Analysis Copy. Detail uses exact UID entry and appears as a non-linking UID in subject rows and Info. Detail token and destination behavior remains separate work.

## Questions For Further Discussion

## Status

The public `analysis.works` identity and Works name are retained. The five subject choices and Studio-owned composite Detail identity are accepted design decisions within [Unified Analysis And Catalogue Presentation](/docs/?scope=studio&doc=d-20260902-102745-8379ea). Detail-subject support and the Folder scope restriction are implemented in UAC 3C and await manual review. Wider Catalogue schema and data-provider changes remain later work.
