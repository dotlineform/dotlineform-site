# Catalogue Hosting And Storage

## Status And Decision

The user retired the hosting/storage proposal so future hosting decisions can be informed by app development. Revisit these choices when app requirements and implementation provide a useful basis. The [App roadmap](../app/Docs_Viewer_App_Roadmap.md) is retained for that later review. No editor-host, canonical-source or public-JSON migration was selected.

These notes preserve the earlier tradeoffs for that future decision. The earlier preference for a local Docs host had no approved implementation sequence.

## Three Independent Boundaries

Editor placement, canonical storage and public JSON hosting are separate decisions. One local Docs shell could reduce entry-point switching while retaining Catalogue operations. It also requires mount/release, style and unsaved/busy navigation integration. Keeping Studio avoids that migration. Neither choice requires moving source records or public data.

Aggregate Git records make whole-store inspection and history simple. Exact by-ID authoring files could reduce selected source I/O, but membership, bulk writes and derived indexes still need an owner. Existing generated by-ID JSON omits private authoring/storage inputs and includes calculated values, so it cannot become canonical unchanged. Choose one editable authority and preserve history through an explicit migration.

Tracked Pages JSON uses the existing publication path. R2 could reduce tracked data and decouple storage, while introducing URL, CORS, cache and coordinated-release decisions. Media already using R2 does not establish a JSON provider: current workspace parsing permits only repository Catalogue JSON. A migration would extend that contract and the existing transfer owner rather than introduce a second distribution path.

No measured source-I/O or hosting limit establishes a need for these changes. Choose a concrete problem before a migration; keep browser filtering and loaded-state choices with the frontend.
