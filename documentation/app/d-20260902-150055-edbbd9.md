# Repository Boundary And Codex Instructions

## Purpose

Define how the native application participates in the existing `dotlineform-site` repository without acquiring a parallel development rulebook or accidental website assumptions. The repository-wide instructions and machine-local Codex configuration remain the starting authority; App-specific guidance is added only where its ownership and discovery are clear.

## Current Authority

The repository-root `AGENTS.md` owns rules that apply across the website, Docs Viewer, Processing, and the native application. The repository-root `.codex/config.toml` owns trusted-project sandbox and approval settings for this laptop and is intentionally machine-local and ignored by Git. The tracked `.codex/setup.sh` owns shared repeatable environment setup where that setup is genuinely useful outside one interactive Xcode installation.

The root configuration is sufficient because native source lives inside the writable repository and the configured external Docs Viewer root covers App documentation. Xcode signing, Keychain access, GUI interaction, physical-device installation, and cloud deployment remain explicit workflow operations; broadening Codex filesystem configuration would not replace their own approval and review boundaries.

## Instruction Placement

The application uses two instruction levels:

| owner | content |
| --- | --- |
| repository-root `AGENTS.md` | A concise native-application boundary that every repository task must know: the application is a separate product inside this repository, is not part of `site/` or the Processing project, owns documentation in the `app` scope, does not inherit static-site build assumptions, keeps credentials and signing state untracked, and treats device, cloud, commit, and deployment effects explicitly. |
| application-root `AGENTS.md` | Exact Swift and Xcode working conventions: authoritative project/workspace, maintained scheme and destinations, command-line Mac/iPad build and test shapes, DerivedData policy, source and resource membership, dependency policy, focused testing boundary, tracked and ignored Xcode state, configuration ownership, and the native Mac and physical-iPad review gates. |

Do not duplicate the complete root instructions in the child file. The child file extends them with facts that apply specifically beneath the accepted native-application root. Do not introduce an `AGENTS.override.md`; an override would replace the ordinary file at the same level and no temporary or exceptional instruction regime is required.

## Discovery And Task Working Directory

App-focused tasks start at the repository root. The root instructions keep every critical App boundary effective and explicitly require reading `app/AGENTS.md` before an App change. The child file owns the exact commands and local conventions without duplicating the repository rulebook. SAF-1.5's fresh-task probe confirmed this instruction chain and repeated `bin/app-check` without conversational context.

## Configuration Boundary

Do not create an application-root `.codex/config.toml` merely to mirror the repository configuration. Add project configuration only after an implementation step identifies an exact missing capability, such as a genuinely necessary writable root or an App-specific tool integration, and records why ordinary repository configuration or an explicit operation is insufficient.

When a child configuration is justified, review its precedence from the intended App working directory and specify complete values for any setting it overrides. Validate a configuration change in a fresh trusted task with the smallest reversible probe. Keep private paths, signing identities, credentials, tokens, and service secrets out of tracked instructions and examples.

Prefer an explicit ignored repository-local or temporary DerivedData location in repeatable `xcodebuild` commands when it makes build products inspectable without requiring broader writable access. The accepted path belongs to the build workflow, not to Codex permissions by default.

## Setup Boundary

Do not expand `.codex/setup.sh` merely because Xcode is required on the development Mac. Xcode installation, Apple account state, signing, and device trust are host capabilities rather than portable repository bootstrap steps. Add App setup to the tracked script only when a repeatable non-secret dependency or validation is useful for another suitable checkout or cloud task; otherwise keep the exact Xcode preparation and diagnostic commands in the App build documentation or a focused App-owned script.

## Current Boundary

The demonstrated boundary is:

- use `app/` as the repository-local application root and keep App-focused Codex tasks rooted at the repository root;
- retain the repository-root `AGENTS.md` and `.codex/config.toml` as the general authorities;
- add a concise native-application section to the root instructions that requires App work to read `app/AGENTS.md`;
- add `app/AGENTS.md` with exact Swift/Xcode conventions when the real project is created;
- create no child `AGENTS.override.md` and no child `.codex/config.toml` without a demonstrated need;
- keep critical rules effective for tasks that begin at repository root;
- use the already ignored `var/app/DerivedData/` boundary for repeatable command-line build products;
- retain the repository `.codex/setup.sh` unchanged unless implementation demonstrates a portable non-secret setup responsibility;
- keep signing, device installation, paid cloud activation, deployment, commit, and push as explicit operations rather than implied configuration effects.

`app/README.md` is the human entry point, `app/AGENTS.md` owns App-specific development rules, and `bin/app-check` composes the retained local evidence. Another host must install Xcode and establish its own trusted-project permissions, external paths, Apple account, signing, and device trust; those remain host state rather than tracked setup inputs.

## Change Triggers

Review this boundary when the application root moves, task startup changes, a second native target or package creates a real instruction boundary, a new external writable source is required, App-specific MCP or automation becomes valuable, setup becomes useful outside the original laptop, or configuration precedence produces an observed conflict. Do not add layers in anticipation of those events.
