# Application Architecture And Development Conventions

## Purpose

Record the durable structure demonstrated by the first native application delivery so later features can extend real owners without repeating avoidable ownership and module problems. These conventions constrain current responsibilities; they do not require speculative abstractions, empty architecture, or a framework of our own.

## Current Composition

```text
SwiftUI application composition
  -> About view
      -> WebKit host and About bridge coordinator
          -> bundled About HTML, CSS, and JavaScript
          -> About rotation service
              -> exact URLSession client
                  -> configured Cloud Python endpoint
```

SwiftUI owns application lifecycle, native presentation, and dependency composition. The bundled About page owns its button, working/success/failure presentation, and completed quarter-turn state. `WebKitHost` is the sole owner of `WKWebView` setup, message registration, payload validation, async dispatch, and reply serialization. The About service protocol is the substitution seam; `WorkOnTheDecayedClient` alone owns HTTP transport and strict response validation. The single non-secret endpoint enters through `AppConfiguration` rather than feature, page, WebKit, or transport code.

## Dependency Direction

Prefer a simple dependency direction:

```text
application composition
  -> feature view
      -> platform host and feature bridge
          -> feature service interface
              -> transport implementation
```

Views do not construct URLs, perform HTTP requests, decode arbitrary payloads, access files, or script WebKit directly. The About page does not know whether its result is local or remote and never sees transport details. The first delivery did not justify a separate Swift feature-state object: page-owned presentation state and the focused bridge coordinator are sufficient for this feature. A later feature should add native state only when native behavior actually owns it.

Use protocols only for an actual substitution, test seam, or platform boundary. Do not create a dependency-injection framework, universal service registry, global application manager, generic action bus, or abstraction for hypothetical future consumers.

## WebKit Boundary

The initial WebKit host loads bundled application-owned HTML, CSS, and JavaScript. It exposes a small named message contract in both directions and validates message names and payload shapes before dispatch. Feature views do not reach into the web view or distribute `evaluateJavaScript` calls through the application.

The About page is a retained application feature and a lightweight diagnostic surface for the bridge and cloud boundary. Its content begins with:

```text
WORK ON THE DECAYED
䷑
```

Later Docs Viewer embedding must extend or replace the bundled page through an explicit host contract. It must not turn the first page into an accidental generic viewer framework or make JavaScript another unrestricted application-control surface.

## Swift Conventions

- Use SwiftUI and Apple frameworks by default. Introduce AppKit/UIKit or a third-party package only for a named capability that the existing platform APIs cannot satisfy adequately.
- Use focused types and files named by responsibility. Avoid `Manager`, `Helper`, `Utils`, and other generic owners unless their responsibility is genuinely narrow and clear.
- Keep state ownership explicit and local. Do not place every feature and service in one global observable object.
- Use typed `Codable` request, response, and configuration models for stable JSON boundaries. Do not pass unstructured dictionaries through the application without a concrete reason.
- Use Swift concurrency consistently with `async`/`await`. Keep UI state on the main actor and keep network, decoding, file, or CPU work from blocking it.
- Treat compiler warnings and concurrency warnings as work. Do not allow a permanently noisy build to become the baseline.
- Prefer semantic native controls and accessible labels. Icon-only controls require meaningful accessible names.
- Use structured Apple logging for retained diagnostics. Do not log secrets, private document content, or complete service payloads.
- Keep configuration and secrets outside feature implementation. Tracked source may contain safe examples and configuration keys, never credentials or machine-specific private paths.
- Format source consistently with the selected Swift toolchain. Add a linter only when it enforces useful project rules that formatting and compiler diagnostics do not cover.

## Source Structure

The repository-local application root is `app/`. `app/dotlineform.xcodeproj` contains one shared Swift 6 app target with native Mac and iPad supported destinations and no iPhone destination. Its product, target, maintained scheme, and display name are `dotlineform`, while Swift types retain normal upper-camel-case names such as `DotlineformApp`. The deployment targets are macOS 26.0 and iPadOS 26.0. Current folders have demonstrated owners for application composition, the About feature, WebKit host, service/configuration boundaries, bundled resources, and tests.

Folders express ownership; they are not module boundaries by themselves. Introduce Swift packages only after a real independently useful boundary exists. Do not create empty `Core`, `Infrastructure`, `Shared`, or future-feature trees merely to display an intended architecture.

The project and source layout should make it obvious where the next Docs Viewer feature belongs without pre-creating that feature or promoting About-specific code into generic shared infrastructure.

## Canonical Data

Swift types are runtime representations, not automatic new authorities. When Docs Viewer data enters the application, its canonical source, generated products, accepted published products, identities, and mutation owner must remain explicit. Do not move canonical documents or Catalogue data into SwiftData, Core Data, or application-private JSON merely because the consumer is native.

## Proportional Assurance

Prefer inexpensive tests for deterministic models, message validation, request construction, response decoding, and state transitions. Use a focused WebKit integration check only for the bridge behavior that lower-level tests cannot establish. Native Mac and physical-iPad presentation and interaction remain manual acceptance evidence.

Do not create a large UI suite, test every SwiftUI composition detail, or introduce extensive mocks and fixtures before they protect a real boundary. Each permanent test must name the plausible regression it catches.

## Extension Rule

Before adding a capability, name its feature owner, state owner, service boundary, platform dependency, data authority, failure behavior, and lowest adequate evidence. Extract shared code when a second real use shows common ownership, not merely because future reuse can be imagined.

## Status

The architecture is accepted through [Work On The Decayed](/docs/?scope=app&doc=d-20260902-144239-b793ea). It retains one shell, one About-owned bridge, one service seam, one transport client, and one provider-neutral Python workload without a global state object, generic action bus, dependency-injection framework, third-party Swift package, or speculative Docs Viewer structure. The cloud demonstration is replaceable without replacing the shell or WebKit host. The next product direction and Git boundary remain follow-on decisions.
