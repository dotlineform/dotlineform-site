# Build And Device Deployment

## Purpose

Make the first native Mac build and physical-iPad installation the beginning of the real Docs Viewer-capable workflow rather than an ad hoc sequence that must later be rediscovered or replaced. The local workflow should be understandable, repeatable, source-controlled where appropriate, and automatable without requiring CI or distribution infrastructure before it has value.

## Ownership

The Xcode project owns Apple target configuration, application resources, schemes, build settings, and test targets. Repository-local commands or scripts may compose repeatable developer actions around Xcode and cloud deployment, but they do not duplicate Xcode project configuration or hide failures behind a generic build system.

The laptop is the initial authoritative build environment and supplies native Mac acceptance. The connected iPad supplies physical-device acceptance. Google Cloud Run supplies the remote Python execution environment described by [Cloud Python Runtime](/docs/?scope=app&doc=d-20260902-144238-a77d8b).

## Source-Control Boundary

Commit durable files required for another suitable checkout to understand and build the application, including application source, project/workspace metadata, shared schemes required by command-line use, resources, tests, safe configuration declarations, and concise build instructions.

Do not commit DerivedData, per-user Xcode state, signing certificates, private keys, provisioning artifacts, device-specific transient state, cloud credentials, endpoint secrets, or local caches. Personal signing configuration remains local even when the project contains safe team-independent settings.

The generated-file inspection confirms the narrow repository rules: ignore every `xcuserdata/` directory, `*.xcuserstate`, `.DS_Store`, and the existing repository-wide `var/` boundary. Track `project.pbxproj`, workspace contents, shared source/resources/tests, entitlements, and any future shared scheme required by command-line use. Do not import a broad generic Xcode ignore template without an observed missing transient path.

## Accepted Readiness Boundary

The application root is `app/`. Create `app/dotlineform.xcodeproj` from Xcode's Multiplatform App template. Its one app target has the native Mac and iPad supported destinations, no iPhone destination, `dotlineform` as product, target, maintained scheme, and display name, and `com.dotlineform.app` as its bundle identifier. Swift type names retain normal capitalization, beginning with `DotlineformApp`.

The initial deployment targets are macOS 26.0 and iPadOS 26.0, established from the development Mac running macOS 26.6.2 and the paired target iPad running iPadOS 26.6.1. Repeatable command-line builds place DerivedData beneath the ignored `var/app/DerivedData/` boundary. The retained destinations, local signing behavior, narrow ignore entries, and command shapes are now established in `app/AGENTS.md` and the repository App README.

## Local Build Workflow

The workflow must establish both:

```text
Xcode Run
  -> interactive native Mac build/run and physical-iPad build/sign/install/diagnosis

xcodebuild
  -> repeatable command-line Mac/iPad builds and focused automated evidence
```

The exact `xcodebuild` project, scheme, destination, and configuration are recorded only after the project exists and Xcode has established the correct identifiers. Do not hard-code a guessed simulator or device identity into tracked commands.

When Codex runs `xcodebuild`, it must request escalated sandbox permission before the first attempt. Xcode 26's Swift preview macro plugin launches its own sandbox, and that nested sandbox fails inside the ordinary Codex workspace sandbox even when every output path is writable. This is a command-specific execution requirement: keep non-Xcode checks sandboxed, do not add writable roots as a workaround, and do not grant the whole task unrestricted access.

The repository entry point composes the accepted checks without hiding their Xcode ownership:

```text
bin/app-check
bin/app-check --signed-mac
```

The default mode runs the focused Swift tests on native Mac and builds the app and test bundle for a generic iPad without signing. The optional signed mode additionally builds the Mac app through local automatic signing, verifies the signature strictly, and inspects the actual signed product for the app sandbox, read-only user-selected-file, and outgoing-network entitlements. Direct command forms remain in `app/AGENTS.md` for diagnosis.

Clean command-line builds for the native Mac and iPad destinations are required before the foundation closes. Manual Mac execution and physical-iPad installation remain distinct gates because command-line builds do not prove application launch, signing, device trust, installation, WebKit behavior, networking, or the actual interaction on either target.

## Application Configuration

Development configuration makes the single public Cloud Run endpoint explicit in `AppConfiguration.swift`, outside feature, view, WebKit, and transport code. The value is non-secret and there is only one application/cloud environment, so a tracked source literal is the smallest honest configuration boundary. A second environment or a required local override is the trigger to move it into an Xcode configuration and generated application setting rather than scattering conditionals through features.

Do not create development, staging, production, feature-flag, remote-config, or secret-management systems until each environment has a real use. The first delivery has one development application and one development cloud workload.

## Deployment Workflow

Application deployment and Cloud Python deployment are separate operations with separate outcomes:

```text
application
  -> build native Mac and iPad destinations
  -> run locally on Mac
  -> sign locally and install/run on connected iPad

cloud workload
  -> test locally
  -> build container
  -> deploy configured Cloud Run service
  -> run focused deployed smoke
```

The cloud path must be expressible through a documented repository command or small focused script after the manual platform steps are understood. Do not leave the only deployable state in an undocumented web-console sequence. Do not hide provider operations behind a general deployment framework.

The retained one-environment workflow uses the documented `gcloud run deploy --source` command. It records the service Git state before deployment and the regional Cloud Build, Cloud Run revision, immutable image digest, endpoint, and contract smokes afterwards. A separate build-once/promote-by-digest path waits for a real second environment, exact-artifact redeployment, or stronger rollback boundary. Commit and push remain explicit user-approved actions.

## CI And Distribution

The first foundation delivery makes local commands automatable but does not require GitHub Actions, a macOS runner, TestFlight, App Store Connect, notarization, archives, or release distribution. App Store distribution is not an objective. Continue using the free Personal Team for development; consider a paid Apple Developer Program membership only if the current seven-day device provisioning and reinstall cadence becomes materially disruptive, not as a premature distribution step. Add CI only when a stable local command protects a valuable shared boundary and its cost and platform requirements are understood.

Release configuration still needs one bounded compilation check even though distribution does not. SAF-1.6 runs one unsigned Release build for native Mac and one for generic iPad after the review diff is settled, proving the optimized configurations without creating an archive or changing the routine Debug `bin/app-check` workflow.

Do not report unavailable macOS/Xcode execution in a Linux environment as passing Swift evidence. Platform-specific checks run in the correct environment or are named as unavailable.

## Recovery

The initial recovery model is deliberately ordinary: retain source and project configuration in Git, keep private signing and cloud credentials outside it, document required local setup, and rebuild/redeploy through the owning workflow. Do not add backup bundles, migration machinery, automatic rollback, or a second project generator before a concrete failure requires them.

## Completion Standard

Before this foundation is accepted, the same project must build through the recorded Debug Mac and iPad commands, complete one unsigned Release build for native Mac and generic iPad, run natively on the development Mac, install and run on the connected iPad through Xcode, load its bundled About page on both destinations, reach the configured development Cloud Run workload from both, and leave enough concise setup information for the workflow to be repeated without relying on memory. Release compilation proves configuration only; archives and distribution remain outside the foundation.
