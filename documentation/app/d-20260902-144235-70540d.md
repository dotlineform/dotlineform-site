# Proof of Concept

## Outcome

The first durable slice of the dotlineform Swift application is established through one deliberately small experience on native macOS and iPadOS. The retained About page contains **WORK ON THE DECAYED** and **䷑**, hosts bundled HTML and JavaScript through WebKit, crosses an explicit JavaScript-to-Swift bridge, invokes a provider-neutral Python capability deployed to Google Cloud Run, and applies the response visibly in the page.

This is not a disposable proof application. The Xcode project, SwiftUI shell, WebKit host, bridge, cloud-client boundary, build and device workflow, development conventions, and documentation ownership are intended to become the foundation of the real application. The initial page and its cloud operation are small so those foundations can be understood and corrected before Docs Viewer feature complexity arrives.

## Foundation Principle

Approach the foundation as important production work without manufacturing enterprise complexity for a personal application built and run natively on one Mac and run on one iPad. Decisions should be explicit, repeatable, inspectable, and proportionate to credible failures. Do not add generic frameworks, speculative portability layers, elaborate authorization, broad test programmes, or operational machinery that has no present responsibility.

The durable and replaceable parts are different:

| durable foundation | initially replaceable behavior |
| --- | --- |
| Xcode project and maintained target/scheme | the first cloud operation |
| SwiftUI application shell and lifecycle | the visual mutation used to demonstrate its result |
| WebKit host and explicit bridge contract | temporary fixtures used only while developing the first slice |
| Swift service/configuration boundary | deployment details that later evidence shows should change |
| repeatable Mac/iPad build, Cloud Run deployment, and physical-iPad workflow | none of the foundation merely because the first feature is simple |
| focused assurance and App-scope documentation ownership | |

The About page is retained as part of the application rather than discarded after the first delivery.

## Product Boundary

The opening product is one SwiftUI Multiplatform App target with native Mac and iPad supported destinations and no iPhone destination. Swift owns application lifecycle, native integration, configuration, and network calls. A contained WebKit view owns the bundled page presentation. JavaScript sends narrow messages to Swift and does not call the cloud service directly. Swift calls a provider-neutral Python HTTP workload deployed to Google Cloud Run and returns the result to the page.

Application code belongs in the `dotlineform-site` repository under one explicit native-application boundary selected at delivery readiness. App product, architecture, and delivery documentation belongs in the `app` Docs Viewer scope. The Studio Roadmap remains the workflow authority for independent repository changes and links to active App work where needed.

## Relationship To Docs Viewer

The first delivery proves and retains the application foundation; it does not embed or migrate Docs Viewer. Selection of the next product slice, its Git boundary, and whether it begins with a read-only Docs Viewer are intentionally deferred to the post-closeout follow-on discussion.

Future Docs Viewer work should extend the established owners rather than create a second application shell, WebKit bridge, service client, configuration system, build path, or documentation workflow. It must still inspect real Docs Viewer behavior and choose Swift, shared JavaScript, retained desktop Python, or a cloud workload according to the responsibility being moved.

## Boundaries

This feature does not authorize a full Docs Viewer migration, Studio migration, repository clone on iPad, Git client, native document editor, scope filesystem integration, Catalogue mutation, public deployment automation, iPhone or additional Apple-platform support, App Store distribution, or a generalized cloud backend. Those remain separate outcomes if later evidence makes them worthwhile.

The first cloud operation carries no private document content and mutates no canonical or accepted data. A later feature must make a new security, privacy, authentication, connectivity, and recovery decision before real project content crosses the cloud boundary.

## Known Limits

The application currently has one About feature, one development endpoint compiled from a non-secret source literal, one public side-effect-free Cloud Run operation, no CI, and free Personal Team provisioning that may require periodic reinstall on the iPad. The command-line destination-resolution warning is retained because every selected Mac and iPad build succeeds and no corrective owner has been demonstrated. Before any later cloud workload handles private content, authoritative data, expensive processing, or mutation, it requires a new privacy, authentication, authorization, abuse, retry, retention, and recovery decision.

## Current State

The foundation is accepted. One Swift 6 target in `app/dotlineform.xcodeproj` supports native Mac and iPad destinations only, while `app/AGENTS.md`, `app/README.md`, and `bin/app-check` expose the retained development workflow from the repository root. The bundled About page, narrow reply-capable WebKit bridge, injected rotation-service seam, exact `URLSession` client, provider-neutral Python operation, Flask adapter, Cloud Run deployment, signed Mac capabilities, and physical-iPad path are demonstrated. Focused Debug checks and one-off unsigned Release builds pass for the supported destinations. The delivery is closed without starting a Docs Viewer feature, creating a branch, changing cloud state, or beginning distribution work.
