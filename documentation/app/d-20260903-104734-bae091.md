# Delivery

## Requirements

The complete result is a coherent native Mac and iPad holding application that can be built, signed, inspected, and run in Release configuration before Docs Viewer integration starts. The main window says **Docs Viewer goes here** without pretending that the viewer already exists. The retained **WORK ON THE DECAYED** and **䷑** page moves into a real About surface, the Mac Help command opens one useful bundled Help page, and iPad exposes the relevant application information through one minimal native menu.

The application has a deliberate pre-1.0 identity: a proper display name, an original icon created in Apple's Icon Composer, an explicit marketing version and build number, and matching About information. The existing public-site `apple-touch-icon.png` provides the visual starting point for the user's creative Icon Composer task. The emoji or hexagram is retained as About content rather than used as the application icon. No empty Settings surface or placeholder product controls are added.

[SF Symbols](https://developer.apple.com/design/human-interface-guidelines/sf-symbols) provides ordinary interface glyphs for controls such as About, Help, menus, toolbars, and, if useful, the holding-page illustration. Icon Composer and SF Symbols have separate owners: the original `.icon` source defines application identity, while system symbols communicate actions and interface concepts. Do not use an SF Symbol or confusingly similar artwork as the application icon or logo. Prefer an available system symbol such as `info.circle`, `questionmark.circle`, or `book` where it communicates the exact control; do not create a custom-symbol subsystem before a real recurring interface concept requires one.

Apple's Human Interface Guidelines are a quick design and platform-reference baseline rather than a compliance exercise or a hidden specification. Start with the simplest standard native behavior. If a requested idea departs meaningfully from an Apple convention, identify the standard behavior, the proposed difference, and its practical consequence before adding custom code; do not silently customise the application because the departure may have been unintentional. Conversely, do not silently discard an intentional product decision merely to conform. Unless the difference has explicit and important product value, code simplicity and the ordinary platform behavior win. Accessibility, discoverability, unsupported behavior, or a significant maintenance cost must always be surfaced.

The rotation demonstration remains available as an explicit diagnostic, but its Swift transport becomes a small reusable typed Python-service boundary. Rotation stays one finite operation layered over that transport. Neither Swift nor Python gains arbitrary function-by-name dispatch, a service registry, plugin framework, job system, or speculative Docs Viewer action API. The deployed Cloud Run service, URL, public exposure, and provider configuration remain unchanged unless a later separately approved operation requires them to change.

The delivery establishes a genuine development-signed Release product rather than treating an unsigned optimized compilation as the release workflow. It should retain an inspectable Mac archive or equivalent Release artifact beneath the ignored `var/app/` boundary, verify its signature, entitlements, version, icon, About, and Help resources, and run the exact Release product on native Mac. The physical-iPad Release build and installation path is also exercised where the free Personal Team permits it. App Store distribution, TestFlight, Developer ID distribution, notarisation, paid cloud changes, commit, push, and public deployment are excluded.

The durable App documentation hierarchy is established before implementation and updated as each accepted behavior becomes current. Roadmap documents remain temporary planning and delivery records rather than the final operational authority.

## Process

The person launches the application into the native holding page without requiring network availability. On Mac, the application menu opens the custom About content and the standard Help command opens the bundled Help page. On iPad, one minimal native menu exposes the application information appropriate to that platform. The Python operation runs only when the person explicitly invokes its About diagnostic and reports bounded working, success, or failure state without affecting application launch or canonical data.

Development continues from the repository root against the maintained `dotlineform` scheme. Debug checks remain the fast development boundary, while the delivery adds an explicit Release operation that produces the retained signed result and then inspects and manually reviews that exact product. A branch remains optional and is reconsidered only at the feature's named isolation triggers.

Implementation uses native controls and standard platform behavior by default. HIG review is limited to the surfaces being changed and exists to expose choices, not to generate a broad conformance programme. Any meaningful customisation is proposed explicitly before implementation so the user can decide whether its product value justifies the additional code and maintenance.
